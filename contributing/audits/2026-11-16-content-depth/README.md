### 2.1 P0：内容准确性与历史信息

- **Istio 选型文章**：扩展性章节停在半句话；将 gRPC 和数据库协议一起归为“支持程度有限”；基于 1.0/1.5 与 2021 年历史变动描述不带版本范围的现状，Kiali 不可用于生产的绝对判断缺证据。当前官方协议说明区分 HTTP/2/gRPC 与 opaque TCP、数据库协议解析，不能混写。[Istio 协议说明](https://istio.io/latest/docs/ops/configuration/traffic-management/protocol-selection/)
- **Nginx 基础数据结构文章**：`nelts` 被解释为未使用元素数，后文又说已用元素数；`sync` 被解释成同步/阻塞操作开关。官方定义中前者是当前元素数量，后者是特殊缓冲语义；还应区分 `last_buf` 与 `last_in_chain` 的输出结束边界。[Nginx Array](https://nginx.org/en/docs/dev/development_guide.html#array)、[Nginx Buffer](https://nginx.org/en/docs/dev/development_guide.html#buffer)

这两篇说明“文章长、代码多、图片多”也不保证理解正确，不能靠字数或行数筛出全部问题。

### 2.2 P1：Redis 不是唯一缺口

| 模块 | 已有内容 | 仍缺的关键桥梁 |
| --- | --- | --- |
| Redis | `maxmemory` 淘汰专项已经深化；复制、Sentinel、Cluster 有主线概念 | `appendfsync` 各策略故障边界、位点/积压算例、选主时序、ASK/MOVED 交互、Streams pending/重试过程；连接数和客户端缓冲限制还需补定位和解释 |
| MySQL | Redo/Undo/Binlog 职责、提交路径和安全配置已有 | `innodb_flush_log_at_trx_commit`、`sync_binlog` 不同取值的写/刷盘时间及故障后果，Buffer Pool/刷脏的指标推演 |
| Kafka | Producer/Consumer 主线、事务与源码章节已有 | ACK/重试/幂等的配置约束，慢 poll 与分区所有权变化，MM2 位点转换的实际例子 |
| Nginx | Upstream 参数和边界已有较完整解释 | HTTP Phase 源码文缺固定版本及文件/函数→请求轨迹的映射；不要重复扩写已完善的 Upstream 文 |

Secret 引用的行为已对照 Kubernetes 官方说明：非可选的 Secret 缺失会阻止对应容器正常启动，不能只删除创建步骤而保留引用。[Kubernetes Optional Secrets](https://kubernetes.io/docs/concepts/configuration/secret/#optional-secrets)

## 6. 验收标准与记录方法

技术文章按其目标检查以下问题，不机械要求每篇全部覆盖：

- 名词是否在使用前解释，前置知识是否有可达入口？
- 机制是否说明状态、因果和失败条件，而不只是重复结论？
- 参数/策略是否解释具体分支、选择依据及与其他参数的关系？
- 例子是否包含输入、过程、输出和结果解释，教学假设是否写清？
- 排障是否说明证据能证明什么、不能证明什么，以及下一步如何决定？
- 部署/恢复是否覆盖依赖、安全和成功验收，危险动作是否有边界？
- 版本、平台、产品差异是否明确，旧信息是否误当现状？
- 有练习时是否有明确解答，引用是否真正支持关键断言？

全文阅读也不自动等于运行验证。后续每条修复至少记录：源文件、范围、版本/源码依据、具体问题、修复内容和验证结果；保留“尚未核验”，不填虚假的通过状态。
