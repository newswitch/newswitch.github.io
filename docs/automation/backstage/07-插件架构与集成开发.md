# Backstage 插件架构与集成开发

一个页面能显示“服务正常”，不代表插件已经正确接入身份、权限和数据源。需要回答：页面由谁注册，后端地址如何发现，凭据怎样传递，授权发生在哪一步，以及页面展示的是当前状态还是旧缓存。

以下以 **Backstage v1.56.5 的新 Backend System 与新 Frontend System**为 API 基线，构造只读 `ops-status` 示例。数据源明确为 fixture，先解释框架链路，再讨论替换为真实集成。[配套核心文件](https://github.com/newswitch/newswitch.github.io/tree/main/examples/automation/backstage-ops-status)需要放入对应版本的 Backstage workspace，不是能在博客仓库独立启动的应用。

## 1. 先判断是否需要插件

简单链接、Entity Card 配置或现有插件能解决时，不创建新插件。新插件意味着依赖、权限、数据库、升级和 SLO 的长期维护责任。

### 1.1 Plugin、Module 与 Extension 不是同义词

| 概念 | 负责什么 | 本例对应 |
| --- | --- | --- |
| Frontend Plugin | 组织页面、导航、Utility API 等前端功能 | `/ops-status` 页面 |
| Frontend Extension / Blueprint | 按 App 的扩展模型提供页面、卡片或 API | 用 `PageBlueprint` 定义页面扩展 |
| Backend Plugin | 拥有后端能力、路由与依赖服务 | `pluginId: ops-status` |
| Backend Module | 扩展某个后端插件暴露的扩展点 | 宿主 Permission 插件的策略模块，不是另一个页面 |
| Utility API | 前端可注入的共享接口及实现 | Discovery、Fetch；复杂集成还可定义自己的 API |

不要把旧前端 `createPlugin`/`FlatRoutes` 的注册方式与新 `createFrontendPlugin`/Blueprint 直接拼在同一份示例里。旧应用仍需按其迁移方式接入，后端与前端的迁移也不是同一个开关。

### 1.2 发布号不等于每个包的版本

该 release 中，`@backstage/backend-plugin-api` 为 `1.11.0`，`@backstage/frontend-plugin-api` 为 `0.18.2`，`@backstage/plugin-permission-common` 为 `0.9.12`。不能给所有依赖统一填写 `1.56.5`。

使用目标 release 对齐的 workspace、升级工具和 lockfile 管理依赖，再记录自研插件与生产镜像版本。API 依据分别见 [后端包](https://github.com/backstage/backstage/blob/v1.56.5/packages/backend-plugin-api/package.json)、[前端包](https://github.com/backstage/backstage/blob/v1.56.5/packages/frontend-plugin-api/package.json)和 [权限包](https://github.com/backstage/backstage/blob/v1.56.5/plugins/permission-common/package.json)。

## 2. 前后端边界

```text
Frontend Page
  → DiscoveryApi 解析 ops-status 的地址
  → FetchApi 携带当前身份发请求
  → /api/ops-status/snapshots/orders
  → Backend 身份检查 → Permission 决策
  → 受控 serviceId 映射 → 数据适配器 → DTO
  → 前端运行时校验 → 展示来源与采样时间
```

浏览器不能持有外部系统长期 Token，也不能接受实体 Annotation 后任意请求内网 URL。

### 2.1 后端注册与路由挂载

下面是配套 `backend/plugin.ts`。`registerInit` 声明依赖，由框架注入，插件不自行构造一个“没有宿主策略”的权限客户端。

```ts title="backend/plugin.ts"
import { coreServices, createBackendPlugin } from '@backstage/backend-plugin-api';
import { opsStatusReadPermission } from '@internal/plugin-ops-status-common';
import { createRouter } from './router';
import { readFixtureSnapshot } from './model';

export const opsStatusPlugin = createBackendPlugin({
  pluginId: 'ops-status',
  register(env) {
    env.registerInit({
      deps: {
        httpRouter: coreServices.httpRouter,
        httpAuth: coreServices.httpAuth,
        permissions: coreServices.permissions,
        permissionsRegistry: coreServices.permissionsRegistry,
      },
      async init({ httpRouter, httpAuth, permissions, permissionsRegistry }) {
        permissionsRegistry.addPermissions([opsStatusReadPermission]);
        httpRouter.use(createRouter({
          httpAuth, permissions, readSnapshot: readFixtureSnapshot,
        }));
      },
    });
  },
});
```

后端插件包的 index 将 `opsStatusPlugin` 导出为 default，并让宿主 backend 加载该包：

```ts
backend.add(import('@internal/plugin-ops-status-backend'));
```

这行应追加在现有 backend 的注册位置，不要为了它重建第二个 backend。插件内部注册 `/snapshots/:serviceId`，框架按插件 ID 挂到 `/api/ops-status`；不要在内部再重复写一次 `/api/ops-status`。前置依赖与默认鉴权见 [固定版本后端文档](https://github.com/backstage/backstage/blob/v1.56.5/docs/plugins/backend-plugin.md)。

### 2.2 新前端通过 Blueprint 提供页面

```tsx title="frontend/plugin.tsx"
import React from 'react';
import { createFrontendPlugin, PageBlueprint } from '@backstage/frontend-plugin-api';

const statusPage = PageBlueprint.make({
  params: {
    path: '/ops-status',
    title: 'Operations status',
    loader: () => import('./OpsStatusPage').then(m => <m.OpsStatusPage serviceId="orders" />),
  },
});

export default createFrontendPlugin({
  pluginId: 'ops-status',
  info: { packageJson: () => import('../package.json') },
  extensions: [statusPage],
});
```

`../package.json` 指目标插件包的真实 manifest，页面组件见配套源码。插件包默认导出该实例，宿主新前端可以通过 `createApp({features: [...]})` 显式加入它，或在已启用 feature discovery 的配置下从应用依赖发现它。仅创建源文件、没有加入宿主依赖/发现范围，不会自动出现在页面上。

前端 `/ops-status` 与后端 `/api/ops-status` 是两条不同路由。页面里的 `discovery.getBaseUrl('ops-status')` 在请求前解析后端地址，随后使用 `fetchApiRef` 的客户端，而不是硬编码 localhost 或手工保存用户 Token。`Discovery` 与 `Fetch` 的行为见 [新前端插件文档](https://github.com/backstage/backstage/blob/v1.56.5/docs/frontend-system/building-plugins/01-index.md)。

## 3. API 合约

定义请求/响应 Schema、错误码、分页、超时、缓存和版本。前端显示数据来源及时间；后端把外部 401、429、5xx 分类，而不是统一返回“插件失败”。

### 3.1 先把响应语义收窄

本例 `GET /api/ops-status/snapshots/orders` 的响应为下面这份固定教学数据：

```json
{
  "serviceId": "orders",
  "environment": "staging",
  "status": "ready",
  "source": "fixture",
  "observedAt": "2026-11-16T00:00:00Z"
}
```

`ready` 只是 fixture 的一个字段，不能解释成已查询 Kubernetes、完成健康探测或代表当前线上状态。真实适配器应返回实际来源、采样时间及陈旧状态，不能在读取旧缓存时偷偷把 `observedAt` 改成当前时间。

共用 DTO/Permission 的代码放在 common-library，避免浏览器依赖 backend-plugin 包。TypeScript 的 `Snapshot` 类型不会验证网络上的 JSON；本例额外调用 common 中的 `parseSnapshot`，核对字段、枚举、标识与时间，再更新页面。仅写 `await response.json() as Snapshot` 不能实现运行时校验。

### 3.2 成功之外的状态也属于合约

| 状态 | 本例含义 | 不能混淆的情况 |
| --- | --- | --- |
| 401 | 缺少可接受的身份 | 不等于外部 Kubernetes Token 过期 |
| 403 | 已处理请求身份，但 Permission 未允许 | 不应改成 200 加空数据 |
| 400 | serviceId 格式错误 | 不需要继续请求外部资源 |
| 404 | 标识格式合法，但无受控映射 | 不自动扫描所有集群寻找同名服务 |
| 200 | 返回符合当前合约的数据 | 仍需检查 source/observedAt，不等于实时可用性 |

接真实适配器时，再为外部超时、429、不可用等定义稳定错误分类。前端请求要有超时与卸载取消，区分加载、无映射、禁止访问和依赖失败；不能给每次渲染启动一个永不结束的轮询。

缓存也需要遵守权限边界：检查授权之后再取数据；若不同用户/租户可见结果不同，缓存键和失效必须包含相应安全范围，不能只按 `serviceId` 共享全部结果。

## 4. Entity 驱动集成

插件从稳定 Annotation/Relation 获取外部资源标识，并验证格式和允许范围。找不到映射时显示配置建议，不猜测或扫描所有外部资源。

例如 Catalog 中的 Component 可以保存业务标识，而不是保存任意外部 URL：

```yaml
apiVersion: backstage.io/v1alpha1
kind: Component
metadata:
  name: orders
  annotations:
    example.com/ops-service-id: orders
spec:
  type: service
  lifecycle: experimental
  owner: group:default/ops-readers
```

本例独立页面固定展示 `orders`，**不会自动读取上面实体的 Annotation**。改为 Entity 页面时，再通过该页面的实体上下文取得标识，向同一后端请求；后端仍应校验 ID 并查受控映射，不能因为值来自 Catalog 就信任它。

正式映射可以在受控配置中保存 `serviceId → tenant/cluster/namespace/resource`，外部 endpoint 由后端配置和身份管理决定。标识正则只能过滤格式，不能证明用户有权访问目标资源；Catalog 的 `owner` 也不会自动成为本例的授权规则。

## 5. 权限

后端路由在服务端检查 Permission，不依赖前端隐藏按钮。高风险动作使用用户委托身份或受控工作流，并再次验证资源 Owner、环境和操作范围。

### 5.1 一个请求怎样通过认证与授权

本例基础权限名为 `ops-status.read`，属性为 `action: read`，在 common 包用 `createPermission` 定义。`permissionsRegistry.addPermissions` 让宿主可发现它；**登记不是放行**，决策由宿主策略给出。

后端的核心路由如下：

```ts title="backend/router.ts"
import type { HttpAuthService, PermissionsService } from '@backstage/backend-plugin-api';
import { InputError, NotAllowedError, NotFoundError } from '@backstage/errors';
import { AuthorizeResult } from '@backstage/plugin-permission-common';
import { opsStatusReadPermission, type Snapshot } from '@internal/plugin-ops-status-common';
import Router from 'express-promise-router';
import { isServiceId } from './model';

type Options = {
  httpAuth: HttpAuthService;
  permissions: PermissionsService;
  readSnapshot: (id: string) => Promise<Snapshot | undefined>;
};

export function createRouter({ httpAuth, permissions, readSnapshot }: Options) {
  const router = Router();
  router.get('/snapshots/:serviceId', async (req, res) => {
    const credentials = await httpAuth.credentials(req, { allow: ['user'] });
    const [decision] = await permissions.authorize(
      [{ permission: opsStatusReadPermission }],
      { credentials },
    );
    if (decision?.result !== AuthorizeResult.ALLOW) {
      throw new NotAllowedError('Not allowed to read operations status');
    }
    const id = req.params.serviceId;
    if (!isServiceId(id)) throw new InputError('Invalid service id');
    const snapshot = await readSnapshot(id);
    if (!snapshot) throw new NotFoundError('Service is not configured');
    res.json(snapshot);
  });
  return router;
}
```

顺序是接受用户身份 → 请求授权 → 只有明确 ALLOW 才读数据 → 校验并解析受控标识。空决策或其他结果不会被当成允许。`allow: ['user']` 是本例主动选择的边界，因此服务身份也不能直接调用；后台任务集成需另行设计服务授权，不能简单删除检查。

这里没有开放匿名的 auth policy。直接 curl 而没有相应凭据时，不能因 401 就把整个插件改成 unauthenticated。真正需要匿名健康端点时，要独立设置且不返回业务数据。参见 [Permissions Service](https://github.com/backstage/backstage/blob/v1.56.5/docs/backend-system/core-services/permissions.md)。

### 5.2 宿主策略必须实际启用

宿主配置包含：

```yaml
permission:
  enabled: true
```

还需加载 Permission backend 和一个实际策略模块。已有应用应在原策略中加入此权限分支；隔离示例可以用 `yarn new --select permission-policy-module` 生成模块，再使用配套的 `CustomPolicy`。该类通过注入的 `UserInfoService` 读取已解析身份中的 ownership refs：

```ts title="policy/CustomPolicy.ts"
import type { UserInfoService } from '@backstage/backend-plugin-api';
import { AuthorizeResult, isPermission, type PolicyDecision } from '@backstage/plugin-permission-common';
import type { PermissionPolicy, PolicyQuery, PolicyQueryUser } from '@backstage/plugin-permission-node';
import { opsStatusReadPermission } from '@internal/plugin-ops-status-common';

// Isolated example policy. Merge its branch into an existing production policy.
export class CustomPolicy implements PermissionPolicy {
  constructor(private readonly userInfo: UserInfoService) {}

  async handle(request: PolicyQuery, user?: PolicyQueryUser): Promise<PolicyDecision> {
    if (!user || !isPermission(request.permission, opsStatusReadPermission)) {
      return { result: AuthorizeResult.DENY };
    }
    const info = await this.userInfo.getUserInfo(user.credentials);
    return {
      result: info.ownershipEntityRefs.includes('group:default/ops-readers')
        ? AuthorizeResult.ALLOW
        : AuthorizeResult.DENY,
    };
  }
}
```

这个隔离策略拒绝其他 permission，**不能直接覆盖已有生产策略**。其组引用依赖正确、可信的登录身份解析；不能让浏览器传一个 Group 字符串就通过。策略模块需要注入 `coreServices.userInfo`，移除原 allow-all 模块，保留一个真正生效的策略。仅写 `permission.enabled: true` 而继续用 Allow-All，也不等于已限制访问。宿主接入见 [v1.56.5 权限入门](https://github.com/backstage/backstage/blob/v1.56.5/docs/permissions/getting-started.md)。

### 5.3 基础读权限不等于按资源隔离

`ops-status.read` 是本例的插件级基础权限，获准用户可读后端允许映射的资源。它没有实现按 Entity、租户或环境的细粒度隔离。

要做到“只能看自己团队的 Entity”，需定义资源权限、资源标识与受控加载/条件判断，并在后端兑现宿主的条件决策；不是只在请求里多传一个 `entityRef`。跨租户缓存、外部 Token 的权限和 Catalog 读取权限也必须配套。更完整的身份模型见 [认证与权限](./08-认证权限RBAC与多租户.md)。

## 6. 测试

### 6.1 拒绝时不读取数据也是断言

配套 `router.test.ts` 使用固定版本的 `mockServices`、Supertest 和实际 Router，注入认证/授权结果。拒绝路径中的一个用例为：

```ts title="backend/router.test.ts#denied"
it('does not read data when denied', async () => {
  permissions.authorize.mockResolvedValue([{ result: AuthorizeResult.DENY }]);
  expect((await request(app).get('/api/ops-status/snapshots/orders')).status).toBe(403);
  expect(readSnapshot).not.toHaveBeenCalled();
});
```

完整文件构造 Express 应用，挂载真实路由及 Backstage 的错误处理中间件，覆盖下面 6 项：

| 用例 | 关键断言 |
| --- | --- |
| 用户获准 | 200、source 为 fixture；授权参数包含当前 credentials 与目标 permission |
| 显式拒绝 | 403；不调用数据适配器 |
| 没有决策 | 403，默认拒绝；不调用数据适配器 |
| 没有可接受身份 | 401；不继续授权和取数 |
| 标识格式不合法 | 400；不调用数据适配器 |
| 标识没有映射 | 404；不猜测或扫描外部资源 |

在完成依赖/入口接入的 **Backstage workspace** 中运行，而不是在博客根目录：

```bash
yarn tsc --noEmit
yarn workspace @internal/plugin-ops-status-backend test --watchAll=false
yarn workspace @internal/plugin-ops-status-backend build
```

Mock 身份测试不验证真实令牌签名、Audience、Session 或宿主策略加载。不能因为一个 mock 用户读到了 fixture，就声称匿名请求、真实 Group 或跨租户隔离已经验收。

### 6.2 接入真实环境还需哪些测试

分别验证已登录获准、已登录拒绝、匿名和服务身份；核对浏览器经 Discovery/Fetch 到真实插件的路径，以及真实策略的组判定。页面还要检查 Loading、Forbidden、无映射、格式错误、请求取消和超时。

外部适配器需要契约测试与超时/429/5xx/过期凭据/部分数据用例；缓存验证身份隔离与陈旧时间。最后再按目录规模和外部 API 延迟测试吞吐、连接池与限流，不能在一个慢集成下拖垮整个门户。

## 7. 生命周期

固定插件依赖，跟踪 Backstage 兼容性和安全更新。记录 Owner、用户量、SLO、升级计划和弃用迁移。社区插件先评估维护活跃度、权限、数据流和供应链，再进入生产。

发布时至少区分 common 合约、后端插件、前端插件、宿主策略和外部适配器的变化。后端先改字段、前端仍读旧 Schema 时，页面可加载但业务功能已经损坏；升级检查不能只有“构建成功”。

弃用插件还需处理路由引用、实体 Annotation、Secret、缓存、数据库与后台任务。门户短时不可用不应导致被展示的业务服务停止运行；只读集成尤其不应因为页面刷新而触发底层变更。

## 8. 练习与答案

### 8.1 创建插件文件后为什么页面没有出现

答案：还要有正确的包默认导出、宿主依赖和插件发现/注册。新前端的 Blueprint 不是旧 FlatRoutes 的自动入口，后端也需单独注册。

### 8.2 前端路径与后端 API 地址有什么区别

答案：本例 `/ops-status` 是页面，`/api/ops-status` 是后端插件前缀。内部 Router 再挂 `/snapshots/:serviceId`，浏览器通过 Discovery 取得后端地址。

### 8.3 登记 permission 是否表示所有人已被限制

答案：不是。Registry 是发现/登记，宿主还要启用权限、加载实际策略。Allow-All 仍会允许请求，路由必须检查结果后才取数。

### 8.4 前端隐藏按钮为什么不能替代后端授权

答案：客户端展示不是服务端安全边界，请求可以来自其他客户端。后端要接受身份、请求 Permission 决策并执行资源范围检查。

### 8.5 为什么拒绝路径要断言适配器没有被调用

答案：只返回 403 还可能在拒绝前已经查询或泄露外部数据。断言调用未发生可检查路由内部顺序，但不能替代真实身份与策略集成测试。

### 8.6 Entity Annotation 能否直接存任意 URL 给后端读取

答案：不应这样设计。Annotation 不是可信网络访问授权；使用业务标识，后端查受控映射、校验资源权限并使用受限外部身份。

### 8.7 Snapshot 类型能否验证网络 JSON

答案：不能，TypeScript 类型在运行时不会自动检查数据。本例用 parseSnapshot 验证窄合约，字段不符应显示错误而不是渲染成正常状态。

### 8.8 source 为 fixture 的 ready 是否代表线上服务正常

答案：不是，它是固定教学数据。真实集成必须标出来源、采样时间和陈旧状态，不能拿页面展示成功冒充外部健康验收。

### 8.9 基础读权限是否已经实现按 Entity 的多租户隔离

答案：没有。它只控制插件级读能力；资源权限、条件决策的兑现、外部身份与缓存隔离还需单独实现。

### 8.10 Backstage 的所有包能否统一使用发布号作为版本

答案：不能。发布号组织一组相容的独立包版本，需按对应 workspace 与 lockfile 对齐，不能把所有包都填成 1.56.5。
