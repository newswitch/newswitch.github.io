# Backstage 定位、架构与请求路径

## 1. Backstage 解决什么

它为开发者提供统一发现入口、组件目录、自助模板、文档、搜索和外部系统聚合页面。它不替代 Git、Jenkins/GitHub Actions、Harbor、Kubernetes、Prometheus 或 CMDB。

## 2. 主要组件

```text
Browser
→ Backstage Frontend / Frontend Plugins
→ Backstage Backend / Backend Plugins
   ├── Auth / Permission
   ├── Catalog
   ├── Scaffolder
   ├── TechDocs / Search
   ├── Database
   └── Git、CI、Kubernetes、Harbor、监控等外部 API
```

前端负责呈现和交互，后端持有敏感集成凭据、执行授权和外部 API 访问。不要把长期 Token 下发到浏览器。

## 3. 一次组件页面请求

1. 用户通过身份提供商登录。
2. 前端请求 Catalog 中的 Entity 和 Relation。
3. 插件按 Entity Annotation/Relation 查询 CI、Kubernetes 或监控后端。
4. 后端以用户/服务身份访问外部系统。
5. 页面组合结果并显示数据来源和更新时间。

## 4. 聚合而不是复制

Catalog 保存服务元数据和关系；构建日志仍在 CI，镜像仍在 Harbor，运行状态仍在 Kubernetes。若将外部状态复制进 Catalog，需要定义刷新、过期和冲突，避免页面显示陈旧“绿色”。

## 5. 故障边界

Backstage 不应位于线上业务数据路径。门户故障会影响发现和自助操作，但不应让已运行服务停止。高风险动作跳转到受控工作流或调用有审批、幂等和审计的后端。

## 6. 平台产品思维

成功标准不是插件数量，而是开发者能否更快找到 Owner、创建合规服务、定位运行证据并完成可审计操作。每个能力要有 Owner、SLO、用户反馈和弃用流程。
