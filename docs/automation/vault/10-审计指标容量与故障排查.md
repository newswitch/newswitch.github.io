# Vault 审计、指标、容量与故障排查

Vault CPU 很低不代表平台健康。一个请求可能在 DNS、TLS、Standby 转发、Raft、Audit、KMS、数据库或身份源上等待。可观测体系必须覆盖整条请求链。

## 1. Audit Device 不是普通访问日志

审计记录认证和 Secret 请求的结构化证据，包括时间、请求 Path、Operation、身份、来源、结果和 Request ID。许多敏感字符串会使用 HMAC 处理，既保留同值关联能力，又降低直接暴露风险。

审计日志仍包含高度敏感的元数据：谁访问了哪个系统、工作负载名称、策略和网络来源。必须加密传输、限制读取、设置保留期并防止被普通日志平台广泛检索。

## 2. 多审计设备的故障语义

推荐启用两个独立故障域的 Audit Device，例如本地受控文件加可靠日志采集，以及独立 Socket/Syslog 目标。

Vault 需要把审计事件写入至少一个可用设备才能完成相关请求。如果全部审计设备都不可写，请求可能被拒绝；某一个设备失败但另一个成功时，服务可以继续，同时必须告警修复失败设备。

风险链：

```text
审计文件磁盘写满 / 日志服务阻塞
→ Audit Write 延迟上升
→ Vault 请求 P99 上升
→ 全部设备不可写
→ 业务请求失败
```

审计目标容量和延迟属于生产 SLO，不是“安全团队以后再看”的附属项。

## 3. 审计 HMAC 的使用

不能直接从日志中的 HMAC 反推出 Token 或 Secret，但可以通过受控 Audit Hash 接口计算某个候选值在指定审计设备中的 HMAC，用于事件调查。

这个接口本身应严格授权和审计。不要为了便于搜索而关闭敏感字段 HMAC；确需非 HMAC 字段时要逐字段评估泄漏风险。

## 4. 请求关联字段

故障记录至少包含：

```text
精确时间与时区
客户端/工作负载
Vault 集群与 Namespace
Auth Mount 与 Role
Entity/Accessor（脱敏）
API Path 与 Operation
HTTP 状态码和错误类型
Request ID
命中的 Vault 节点、Active 节点
下游数据库/KMS/身份源目标
```

Request ID 用于关联客户端日志、Vault 服务日志、Audit 和下游事件。不要在工单中粘贴 Token、密码、Private Key 或完整 JWT。

## 5. 指标分层

| 层次 | 关注指标 |
| --- | --- |
| 客户端 | 登录、读取、续租、换证成功率；剩余 TTL；重试次数 |
| Listener/Core | 请求率、状态码、P50/P95/P99、并发、限流 |
| Auth/Engine | 各 Mount 的登录、签发、续租、撤销和错误 |
| HA/Raft | Active、Leader、Peer、Commit/Apply、复制延迟 |
| 主机 | CPU、内存、FD、网络重传、磁盘延迟/容量 |
| Audit | 各设备写入延迟、错误、队列和磁盘 |
| 外部依赖 | KMS、Kubernetes API、OIDC、数据库、云 API、DNS |

高基数的 Token、Lease ID、完整 Path 或用户名不应直接作为 Prometheus Label，避免监控系统本身失控。

## 6. SLO 要按能力拆分

示例：

- Kubernetes Login 成功率和 P99；
- KV Read 成功率和 P99；
- Database Credential Issue/Revoke；
- PKI Issue 及续签余量；
- Transit Encrypt/Decrypt 延迟；
- Active 切换恢复时间；
- Raft Snapshot 恢复 RTO/RPO。

Database 签发慢可能是数据库 DDL 慢，Transit 慢可能是 Payload 或加密计算，不能合并为一个“Vault API 延迟”后得出错误结论。

## 7. 容量模型

总请求不只是业务读取：

```text
QPS = 登录 + KV 读取 + 动态凭据签发
    + Token/Lease Renew + Revoke
    + PKI 签发/CRL + Transit
    + 控制器协调 + 管理操作
```

每种请求的成本不同：

- 登录会访问 Auth Backend，可能调用 Kubernetes/OIDC/云 API；
- 动态凭据会写 Raft、写 Audit 并调用数据库；
- Transit 受 Payload 和算法影响；
- Renew/Revoke 在大规模 Pod 环境容易形成周期峰值；
- 每个请求可能写多个 Audit Device。

容量报告要保留业务比例，而不是只用简单 KV Read 压测。

## 8. 必测峰值场景

1. 集群正常业务峰值；
2. Deployment/Job 批量启动；
3. Kubernetes 节点故障导致 Pod 重建；
4. 大量 Token/Certificate 同时续期；
5. Vault Active 切换；
6. 一个 Audit Device 变慢；
7. 一个 Raft Follower 故障；
8. 下游数据库或 KMS 限流；
9. Vault 恢复后的客户端重试风暴。

压测环境必须启用与生产相似的 TLS、Policy、Audit 和存储，否则结果会过度乐观。使用测试 KMS/数据库和虚构 Secret，不要用生产凭据压测。

## 9. 通用故障树

```text
请求失败或变慢
├── 客户端：超时、连接池、Token/TTL、无限重试
├── DNS/TCP/TLS/LB：解析、路由、SAN、SNI、健康检查
├── Vault 状态：Sealed、无 Active、失去 Quorum
├── Auth：Kubernetes/OIDC/LDAP/云身份源
├── Authorization：Entity、Policy、Path、Operation、Namespace
├── Core：Raft 磁盘、Leader、内存、FD、Audit
└── Secret Engine：数据库、KMS、CA、云 API
```

每一层先收集证据，再进入下一层。不要因为 `curl /sys/health` 成功就断言动态数据库凭据链路正常。

## 10. 常见症状与判断

### 10.1 所有请求突然变慢

检查 Active 节点、Raft 磁盘、节点间网络和 Audit Device。若 KV、Auth、Transit 同时受影响，公共 Core/存储/审计层的可能性高。

### 10.2 只有新 Pod 启动失败

现有 Pod 仍持有有效 Secret，新 Pod 需要 Kubernetes Login 和首次读取。检查 TokenReview、Injector/CSI/VSO、Vault Auth 和启动风暴。

### 10.3 只有 Database Credential 慢

检查数据库管理连接、TLS、DDL Lock、账号上限、插件错误和撤销队列。Vault CPU 低是正常现象，因为时间可能消耗在下游。

### 10.4 `permission denied`

比较实际 Token Policies、Entity/Alias、Namespace、Mount Accessor、API Path 和 Operation。不要直接附加 Root Policy。

### 10.5 切主后错误激增

检查 LB 健康收敛、Standby 转发、客户端连接复用、重试退避和 DNS。切主几秒钟的正常抖动可能被无限重试放大。

## 11. 安全调试

- 使用最小权限测试身份和测试 Path；
- 先提高单组件日志级别，不要全局长期 Debug；
- 收集前确认日志是否包含 Authorization Header、JWT、Secret；
- 将支持包和审计日志放入受控存储；
- 结束后撤销测试 Token、删除临时 Policy 并恢复日志级别。

“为了排障把 TLS Verification 关闭”会改变故障链且引入新风险，不应成为常规步骤。

## 12. 告警分级

| 级别 | 例子 | 动作 |
| --- | --- | --- |
| 紧急 | Sealed、无 Active、失去 Quorum、全部 Audit 失败 | 立即响应，冻结变更 |
| 高 | 磁盘延迟/容量临界、KMS 错误、Revoke 大量失败 | 快速介入，防止扩散 |
| 中 | 单 Audit Device 失败、证书续签余量不足 | 在剩余冗余消失前修复 |
| 趋势 | Token/Lease 增长、P99 缓慢上升 | 容量和配置治理 |

告警要附带集群、节点、Mount、影响能力和 Runbook 链接，不能只显示“Vault error”。

## 13. 练习与答案

**问题：Vault CPU 只有 10%，为什么请求 P99 仍很高？**

答案：请求可能在等待 Raft fsync、多数派网络、Audit 写入、KMS、数据库或身份源。CPU 不是端到端瓶颈的充分证据。

**问题：为什么只启用一个本地审计文件风险很高？**

答案：文件系统写满或 I/O 故障可能同时失去审计和业务请求能力。至少要有独立故障域，并监控每个设备。
