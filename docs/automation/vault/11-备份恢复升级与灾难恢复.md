# Vault 备份、恢复、升级与灾难恢复

“每天有一个 Snapshot 文件”不代表 Vault 可以恢复。可恢复性由数据、Seal、配置、软件、外部依赖和人员权限共同决定，并且只能通过隔离演练证明。

## 1. 恢复资产清单

| 资产 | 缺失后的影响 |
| --- | --- |
| Raft Snapshot | Vault 持久数据、Policy、Mount、Key 状态无法恢复 |
| Seal/Recovery 材料 | 无法解封或执行受控恢复操作 |
| Auto Unseal KMS Key/IAM | 恢复出的数据仍打不开 Barrier |
| Vault 版本与配置 | 存储格式、Listener、地址和行为不兼容 |
| Plugin 二进制与版本 | Database 等 Engine 无法正常运行 |
| TLS CA/证书/DNS/LB | 客户端或节点间无法建立可信连接 |
| 外部身份源与下游 | OIDC/Kubernetes/数据库/KMS 链路不完整 |
| Runbook 与人员权限 | 故障时无法安全执行步骤 |

Snapshot 和 Auto Unseal Key 不能放在同一个账号、区域和权限边界中，否则一个事故会同时拿走数据和解密能力。

## 2. RPO 与 RTO

- RPO：最多允许丢失多少时间范围内的 Vault 变更；
- RTO：从宣布灾难到恢复业务能力最多允许多久。

快照每 24 小时一次，理论 RPO 就可能接近 24 小时；恢复脚本从未演练，RTO 就不是“启动三台机器的时间”。还要考虑恢复 KMS、DNS、TLS、Auth 和下游连接。

不同数据影响不同：丢失最新 KV 版本、Transit Key Version、PKI Issuer 或未撤销 Lease 的后果并不相同。

## 3. 创建与检查 Raft Snapshot

```bash
vault operator raft snapshot save vault-20261014.snap
vault operator raft snapshot inspect vault-20261014.snap
sha256sum vault-20261014.snap
```

生产自动化应记录：

```text
集群标识、Vault 版本、时间、Snapshot Index/Term
文件大小、SHA256、加密存储位置
保留策略、复制结果、最近一次恢复测试
```

Snapshot 本身包含敏感 Vault 数据，即使受 Barrier 保护，也要按最高敏感等级加密、最小授权、不可变保留和访问审计。

## 4. 隔离恢复为什么重要

不能把生产 Snapshot 直接恢复到一个能访问生产数据库和云 API 的测试 Vault。恢复的数据可能包含：

- 仍可使用的 Auth 配置和 Token；
- Database 管理身份；
- PKI Intermediate Key；
- Transit Key；
- Lease 与撤销状态。

如果测试集群连上生产下游，它可能创建或撤销真实资源。

隔离恢复需要替换或封锁：Listener、DNS、LB、KMS/IAM、Audit、OIDC、Kubernetes API、数据库、云 API 和邮件/Webhook 等外联。

## 5. 恢复执行思路

```text
准备与 Snapshot 兼容的 Vault 版本
→ 建立隔离网络、临时 TLS 和测试 Seal 能力
→ 启动最小新集群
→ 执行 Raft Snapshot Restore
→ 重启/解封并确认 Leader/Peer
→ 使用测试身份验证数据和功能
→ 记录数据 Index、RTO、错误和人工步骤
→ 销毁隔离环境与临时敏感材料
```

Force Restore 会重写集群状态，是灾难恢复动作，不应对健康生产集群试验。具体参数必须以部署版本官方文档和演练 Runbook 为准。

## 6. 恢复验收不能只看 `vault status`

至少验证：

1. Seal/Unseal、Leader 和 Raft Peer；
2. OIDC/Kubernetes 等 Auth 配置结构；
3. Entity、Group、Policy 与权限拒绝测试；
4. KV 多版本、CAS、删除元数据；
5. Database Plugin 配置，并只对测试数据库签发/撤销；
6. PKI Issuer、Chain、CRL 和测试签发；
7. Transit 对已知测试向量可解密/验签；
8. Audit Device 和 Metrics；
9. 客户端 Agent/CSI/VSO 兼容性。

真实生产 Secret 不应在普通恢复报告中展示明文。

## 7. 多数派丢失与单节点损坏不同

| 故障 | 处理原则 |
| --- | --- |
| 一个 Follower 损坏 | 保持多数派，移除/替换该节点并追赶日志 |
| Active 节点故障 | 剩余多数派选主，修复或替换旧节点 |
| 失去 Quorum | 停止盲目重启，保全磁盘和证据，评估恢复多数派或 Snapshot |
| 全集群/区域损毁 | 从验证过的 Snapshot 建立新集群并切换依赖 |

没有 Quorum 时强行让不同节点各自启动，可能破坏一致性证据。先冻结变更、复制受影响数据并确认最可信恢复点。

## 8. Auto Unseal 灾难

### 8.1 KMS 短时不可用 {/* #kms-短时不可用 */}

已解封节点可能继续服务，但重启或新节点可能无法解封。此时不应同时滚动重启集群。

### 8.2 KMS 权限被撤销 {/* #kms-权限被撤销 */}

修复工作负载身份、IAM、网络和 Key Policy，不要误以为 Shamir Recovery Key 一定能替代外部 Seal Key。

### 8.3 KMS Key 永久删除 {/* #kms-key-永久删除 */}

这可能导致 Snapshot 和在线数据都无法打开，是最高级别灾难。必须依靠删除保护、多人审批、跨账号治理和预先验证的 Seal 迁移/恢复方案预防。

## 9. 升级前检查

1. 阅读每个目标版本的 Release Note、Upgrade Guide 和 Breaking Change；
2. 确认是否允许跨版本直接升级；
3. 盘点 Enterprise 功能、Plugin、Agent、Injector、CSI、VSO 和 SDK；
4. 创建 Snapshot 并完成隔离恢复；
5. 验证磁盘空间、Raft/Autopilot 和全部节点健康；
6. 预生产复现真实 Auth、Engine 和负载；
7. 写出继续、暂停和回退条件。

不能只看到新二进制能启动，就判断存储格式和插件可回退。

## 10. 滚动升级顺序

```text
冻结无关变更
→ 升级一个 Standby
→ 等待重新加入并确认 Autopilot Healthy
→ 重复处理其他 Standby
→ Step-down/切换 Active
→ 升级原 Active
→ 观察完整业务周期
```

始终保持多数派，不要一次重启多个 Voter。每一步检查 Peer、版本、Seal、请求错误、P99、Audit 和下游 Engine。

升级发生不可逆数据迁移后，回退不能只把二进制换回旧版。要使用官方支持路径或从兼容 Snapshot 重建，并计算回退产生的数据损失。

## 11. 区域灾备

社区版常见方案是异地复制加密 Snapshot，在灾难时建立新集群；Vault Enterprise 可根据版本和许可评估 Performance/DR Replication。无论使用哪一种，都要解决：

- DNS/LB 和客户端信任怎样切换；
- 备用区域能否访问 Seal Key；
- 外部数据库、Kubernetes 和身份源是否可达；
- 两个站点是否会同时签发/撤销导致冲突；
- 切回原区域如何避免双写和陈旧状态。

“备用 Vault 已启动”不等于端到端 Secret 服务恢复。

## 12. Secret 或 CA 泄漏不是普通数据恢复

若管理 Token、Database Root、PKI Intermediate 或 Transit 权限泄漏，需要：

1. 隔离攻击路径并保全审计；
2. 撤销 Token、Lease 和外部身份；
3. 轮换管理凭据或 CA/Key；
4. 重发应用 Secret/证书并确认生效；
5. 调查历史访问和密文导出范围；
6. 修复源头后再恢复常态。

从旧 Snapshot 回滚可能重新引入已泄漏或已撤销的凭据，不能把它当默认处置方案。

## 13. 演练评分

每次演练记录：

- 实际 RPO/RTO；
- 自动步骤与人工步骤；
- 需要哪些人员、权限和外部团队；
- 哪些 Secret/Lease 与生产当前状态不同；
- 下游是否产生副作用；
- 证据、审批和清理是否完整；
- Runbook 哪一步已经过时。

恢复成功一次后仍需按版本升级、KMS 变化和组织人员变动定期复测。

## 14. 练习与答案

**问题：Snapshot 文件校验和正常，是否能证明备份可恢复？**

答案：不能。校验和只证明文件传输后字节一致，不证明版本兼容、Seal Key 可用、配置完整，也不证明 Auth、PKI、Transit 和下游链路能恢复。

**问题：KMS 暂时故障时为什么不应重启所有 Vault 节点？**

答案：已解封节点可能继续服务，重启后则需要再次调用 KMS 解封；全重启会把外部 KMS 故障扩大成 Vault 全不可用。
