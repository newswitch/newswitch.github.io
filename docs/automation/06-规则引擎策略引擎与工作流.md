# 规则引擎、策略引擎与工作流：自动化决策系统如何选型

“CPU 超过 90% 就重启”看起来是一条规则，但它同时混合了事实、判断、动作和风险控制。可靠自动化必须把这四层拆开，否则规则越多，行为越难预测。

> 本文讨论的是稳定的架构边界，不绑定某一产品版本。涉及 OPA、Drools、Temporal 或具体表达式语法时，应继续以对应版本的官方文档为准；不要把多年以前的示例语法直接放入当前生产规则包。

## 1. 六种技术不是同一个东西

| 形态 | 解决的问题 | 状态特点 | 典型例子 |
| --- | --- | --- | --- |
| `if/else` | 局部、固定的程序分支 | 随代码发布 | 参数校验、少量业务条件 |
| 表达式引擎 | 运行时计算布尔值或结果 | 通常无状态 | 告警阈值、过滤条件 |
| 规则引擎 | 多条规则对事实匹配、冲突消解和推导 | 可有 Working Memory | 诊断、定价、风控、告警关联 |
| 策略引擎 | 判断某行为是否允许或合规 | 输入+策略→决策 | OPA、准入、权限、合规门禁 |
| CEP | 从有时间关系的事件流识别模式 | 窗口与事件状态 | 5 分钟内连续失败、乱序事件关联 |
| 工作流引擎 | 可靠执行一系列步骤 | 持久化执行状态 | 审批、重试、补偿、长任务 |

一个系统可能组合它们：

```text
事件流
→ CEP 识别“异常模式”
→ 规则引擎生成诊断 Finding
→ OPA 判断是否允许自动处置
→ 工作流执行扩容、验证和回滚
```

规则引擎负责“根据事实得出什么结论”，工作流负责“动作如何可靠执行”。让规则直接 SSH 到服务器并重启服务，会把决策和副作用耦合在一起。

## 2. 规则引擎的核心对象

### 2.1 Fact：已经观测到的事实

事实应是结构化、带来源和时间的数据：

```yaml
kind: NodePressure
node: worker-07
observedAt: 2026-09-22T08:10:00Z
window: 5m
values:
  cpuUtilization: 0.42
  memoryAvailableBytes: 3221225472
  conntrackUsageRatio: 0.97
sources:
  - prometheus
  - node-probe
```

“节点网络坏了”不是原始事实，而是结论。原始事实应保留 conntrack 使用率、丢包计数、路由、探针结果和时间窗口。

### 2.2 Rule：条件与结论

规则至少包含：

```yaml
id: NET-CONNTRACK-001
version: 3
when:
  all:
    - field: values.conntrackUsageRatio
      operator: gte
      value: 0.90
    - field: evidence.conntrackInsertFailedRate
      operator: gt
      value: 0
then:
  finding: ConntrackTablePressure
  severity: critical
  confidence: 0.95
requires:
  - source: prometheus
    maxAge: 2m
  - source: node-probe
    maxAge: 2m
```

`then` 最好先生成 Finding，而不是直接执行动作。Finding 可以交给后续策略、审批和工作流。

### 2.3 Working Memory：本次求值的数据集合

规则引擎在一次评估中持有的事实集合称为 Working Memory。需要定义：

- 同一对象多份事实如何去重；
- 数据多旧算过期；
- 缺失表示 `false`、`unknown` 还是错误；
- 不同来源冲突时相信谁；
- 规则推导的新事实是否继续触发其他规则。

把缺失指标当作 0 会产生危险结论。例如 Prometheus 查询失败时，GPU 利用率不是 0，而是 unknown。

## 3. 匹配、议程与冲突消解

规则数量少时可以逐条扫描：

```text
for rule in rules:
    if rule.matches(facts):
        emit(rule.result)
```

规则和事实很多时，成熟引擎会构建共享条件网络，避免重复计算；Rete 及其变体就是常见思路。但性能优化不能替代清晰语义。

多条规则同时命中时，需要冲突消解：

| 机制 | 含义 | 风险 |
| --- | --- | --- |
| salience/priority | 高优先级先执行 | 规则顺序形成隐式依赖 |
| specificity | 条件更具体的优先 | “更具体”定义可能不直观 |
| recency | 新事实相关规则优先 | 对事件顺序敏感 |
| rule group | 每组只允许一个命中 | 分组错误会吞掉有效结论 |
| 显式互斥 | 规则声明排斥关系 | 维护成本随规则数增长 |

生产系统不要依赖“文件中靠前的规则先执行”这种隐含行为。冲突策略必须可测试、可解释。

## 4. 正向链与反向链

### 4.1 正向链推理

从已有事实出发，不断触发规则并产生新事实：

```text
conntrack 使用率高 + insert_failed 增长
→ ConntrackPressure

ConntrackPressure + ServiceIP 超时 + PodIP 正常
→ ServiceNATPathDrop
```

适合事件驱动、诊断和发现“当前能推导出什么”。风险是规则循环和事实爆炸。

### 4.2 反向链推理

从目标假设出发，寻找证明它所需的事实：

```text
目标：是否为 ServiceNATPathDrop？
→ 需要 PodIP 正常吗？
→ 需要 ServiceIP 超时吗？
→ 需要 conntrack/iptables/ipvs 哪些证据？
```

适合交互式诊断和按需采集，避免一开始收集所有昂贵证据。AI Infra 诊断工具可以把它实现成“假设—所需证据—验证结果”的图，而不必先引入复杂商业规则引擎。

## 5. 为什么很多场景不需要规则引擎

满足以下条件时，普通代码更清楚：

- 规则少且变更频率低；
- 条件只属于一个模块；
- 没有事实推导和冲突消解；
- 发布必须随应用代码一起评审；
- 团队不需要非开发人员配置规则。

过早引入规则引擎会带来第二种编程语言、调试困难、运行时发布、优先级冲突和性能不确定性。

适合引入的信号包括：

- 数百条以上规则由多个团队独立维护；
- 规则更新频率明显高于应用发布；
- 同一事实需要被大量规则复用；
- 必须输出“命中了哪条规则、为什么”；
- 需要模拟某一规则集在历史数据上的影响；
- 决策与执行必须解耦。

## 6. 规则引擎与 OPA 的边界

OPA 接收结构化输入、策略和数据，返回决策，很适合：

```text
是否允许部署 privileged Pod？
这个 Terraform Plan 是否违反组织策略？
该自动修复动作是否允许在生产执行？
调用者是否可以修改这个 namespace？
```

传统规则引擎更擅长：

```text
哪些事实共同表明某类故障？
多条规则如何推导新事实？
冲突规则按什么优先级触发？
```

可以这样组合：

```text
Rule Engine
  输入：监控、日志、Kubernetes、GPU、网络事实
  输出：Finding + confidence + evidence

OPA
  输入：Finding、环境、变更窗口、权限、风险等级
  输出：allow / deny / require_approval
```

OPA 不负责执行动作；规则引擎也不天然提供身份、审批和补偿。

## 7. 规则引擎与工作流的边界

规则：

```text
如果 Deployment 可用副本不足且节点资源充足
则生成 WorkloadReplicaFailure Finding
```

工作流：

```text
锁定目标
→ 保存现场
→ 验证变更窗口
→ 执行 rollout restart
→ 等待 Available
→ 业务探测
→ 成功关闭 / 失败回滚和升级人工
```

工作流必须处理超时、重试、幂等、取消、补偿和人工审批，这些不是在规则 `then` 中调用几条命令就能可靠解决的。

## 8. 规则引擎与 CEP 的边界

表达式 `error_rate > 0.05` 只看当前窗口。CEP 更关注事件间关系：

```text
10 分钟内出现 3 次 Leader 变更
并且每次变更后 30 秒内出现写延迟上升
且事件可能乱序到达
```

CEP 需要处理事件时间、处理时间、窗口、水位线、迟到事件和状态过期。若只需要 Prometheus 时间窗口和静态阈值，Recording/Alerting Rule 往往更简单。

## 9. AI Infra/SRE 诊断规则的设计

一条可维护规则应输出完整解释链：

```json
{
  "finding": "ServiceNATPathDrop",
  "severity": "critical",
  "confidence": 0.95,
  "ruleId": "K8S-NET-017",
  "ruleVersion": 4,
  "matched": [
    "pod_direct_success=true",
    "service_timeout_ratio=0.31",
    "conntrack_insert_failed_rate=18.2"
  ],
  "notEvaluated": [
    "mtu_probe_missing"
  ],
  "evidenceTime": "2026-09-22T08:10:00Z",
  "recommendedChecks": [
    "inspect conntrack count/max",
    "capture insert_failed delta"
  ]
}
```

关键原则：

- 结论必须指向证据，不输出无法解释的“AI 判断”；
- 区分 true、false、unknown 和 error；
- 给每条事实设置最大年龄；
- confidence 不能伪装成精确概率，应说明计算方式；
- 建议动作与自动执行分离；
- 同一事件重复输入应产生相同 Finding ID，便于去重。

## 10. 规则模型与副作用隔离

推荐三层：

```text
Evaluator：纯函数，facts + rules → decisions
Planner：decisions + environment → proposed actions
Executor：经策略/审批后执行并验证
```

Evaluator 不访问 SSH、不修改 Kubernetes、不发通知。纯决策层更容易做单元测试、历史回放和版本对比。

动作层至少需要：

- 幂等键；
- 目标范围；
- 锁和并发限制；
- 超时与有限重试；
- 前置条件和停止条件；
- 验证与回滚；
- 审计和执行者身份。

## 11. 测试与版本治理

### 11.1 表驱动测试

每条规则至少覆盖：

| 用例 | 预期 |
| --- | --- |
| 所有条件满足 | 命中并输出完整解释 |
| 临界值上下 | 边界行为明确 |
| 字段缺失 | unknown 或明确不命中 |
| 数据过期 | 拒绝得出强结论 |
| 来源冲突 | 按来源优先级或输出冲突 |
| 两条规则同时命中 | 冲突消解结果稳定 |

### 11.2 历史回放

用脱敏后的历史事件回放新规则集，比较：

```text
新增 Finding
消失的 Finding
严重级别变化
误报/漏报
每条规则耗时
事实和内存增长
```

规则版本必须随结果保存，否则事故复盘时无法解释“当时为什么命中”。

### 11.3 Shadow 与渐进发布

新规则先 Shadow：计算结果但不通知、不执行；确认稳定后只对测试环境或小比例对象启用，再扩大范围。回滚应切回旧规则版本，而不是现场修改数据库中的条件。

## 12. 性能与安全

- 对事实建立类型和 Schema，拒绝任意深度或超大输入；
- 限制单次评估规则数、递归深度、推导事实数和执行时间；
- 防止规则互相产生事实形成无限循环；
- 规则包签名、版本化并经过评审；
- 表达式语言默认禁止文件、网络和进程访问；
- 多租户规则隔离 namespace、数据和配额；
- 指标记录评估次数、延迟、命中率、unknown、错误和规则版本；
- 不把 Secret 原文放入 Fact、解释链或决策日志。

## 13. 选型流程

```text
条件少、仅在一个函数内？
  → if/else

只需要可配置布尔表达式？
  → 表达式引擎

需要多规则共享事实、推导和解释？
  → 规则引擎

核心问题是授权与合规？
  → OPA/策略引擎

核心问题是时间窗口中的事件模式？
  → CEP/流处理

核心问题是长时间可靠执行、重试和补偿？
  → 工作流引擎
```

选型可以组合，但每个组件只承担清晰职责。

## 14. 练习与答案

**问题 1：Prometheus 告警规则算不算规则引擎？**

它具有规则求值能力，但主要面向时间序列表达式和告警状态，不等同于具有 Working Memory、事实推导和通用冲突消解的业务规则引擎。根据问题规模使用 Prometheus Rule 往往更简单。

**问题 2：为什么规则命中后不应直接重启服务？**

诊断可能误判，动作还涉及权限、锁、变更窗口、幂等、验证和回滚。规则输出 Finding，再由策略和工作流决定是否执行，可以控制风险并保留证据。

**问题 3：指标查询失败时，`cpu=0` 与 `cpu=unknown` 有什么区别？**

`0` 是有证据证明没有使用 CPU；`unknown` 是没有得到可信值。把 unknown 当 0 会掩盖监控链路故障并触发错误决策。

**问题 4：规则越来越多，优先级不断增加，说明什么？**

通常说明规则边界、事实模型或互斥关系不清。应分析冲突图、拆分规则域、显式定义决策表，而不是继续用更大的数字覆盖旧规则。
