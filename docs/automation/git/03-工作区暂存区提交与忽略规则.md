# Git 工作区、暂存区、提交与忽略规则

高质量提交的关键不是提交次数，而是每个提交只表达一个可以独立解释、测试和回退的变化。暂存区允许把混在工作区里的修改拆成多个逻辑提交。

## 1. 先读状态

```bash
git status
git status --short --branch
git status --porcelain=v1
```

短格式前两列分别表示 Index 和工作区状态。例如 `MM file` 表示文件已有一部分暂存，同时工作区又产生了未暂存修改。

自动化解析应使用 Porcelain 格式，不要解析面向人的彩色长输出。

## 2. 三种 Diff

| 命令 | 比较对象 | 回答的问题 |
| --- | --- | --- |
| `git diff` | 工作区与 Index | 哪些修改还没有暂存 |
| `git diff --cached` | Index 与 `HEAD` | 下一次提交会包含什么 |
| `git diff HEAD` | 工作区与 `HEAD` | 当前全部已跟踪修改是什么 |

提交前至少执行：

```bash
git diff --check
git diff --cached --stat
git diff --cached
```

`--check` 可以发现冲突标记和部分空白错误，但不能替代测试。

## 3. 精确暂存

```bash
git add path/to/file
git add --patch
git add --update
```

- 指定路径最容易审计。
- `--patch` 可以按 Hunk 拆分同一文件中的不同意图。
- `--update` 只更新已跟踪路径，不会加入新文件。

不要在包含密钥、日志、数据库文件或构建产物的未知目录中直接执行 `git add .`。

撤销暂存但保留工作区内容：

```bash
git restore --staged path/to/file
```

## 4. 提交契约

```bash
git commit -m "feat: add inventory validation"
git show --stat --oneline HEAD
git show --format=fuller --no-ext-diff HEAD
```

推荐提交具备：

- 单一目的。
- 能独立通过测试。
- 不夹带格式化、调试输出或凭据。
- 说明“为什么改变”，而不只是重复 Diff。
- 与 Issue、变更单或故障记录建立关联。

`git commit --amend` 会创建新 Commit 并移动当前分支。未共享时可以整理；已经推送到共享分支时要评估历史改写影响。

## 5. 忽略规则

仓库共享规则写入 `.gitignore`：

```gitignore
# 构建输出
/build/
/dist/

# 本地虚拟环境
/.venv/

# 默认忽略环境文件，但允许提交示例
.env
!.env.example
```

诊断匹配来源：

```bash
git check-ignore -v -- path/to/file
```

重要边界：`.gitignore` 只影响未跟踪文件。文件一旦被跟踪，新增忽略规则不会自动把它从历史或 Index 中删除。

仅个人使用的规则可放在 `.git/info/exclude` 或全局 excludes 文件，不应污染团队仓库。

## 6. 删除与重命名

```bash
git rm obsolete.conf
git mv old-name.conf new-name.conf
```

Git 最终根据快照相似度展示重命名，它没有永久的“重命名对象”。即使使用普通文件系统命令，只要正确暂存新旧状态，也可能被识别为重命名。

## 7. Secret 误提交

发现密钥进入工作区但尚未提交：停止暂存并删除或移出文件。

如果已经提交甚至推送：

1. 立即吊销或轮换凭据。
2. 阻止进一步传播。
3. 根据团队流程清理历史。
4. 协调所有克隆和下游制品。
5. 增加 Secret 扫描与提交门禁。

删除 Git 历史不能让已经泄露的凭据重新安全，轮换是第一动作。

## 8. 提交前清单

```bash
git status --short --branch
git diff
git diff --cached
git diff --cached --check
```

- [ ] 新文件都属于本次变更。
- [ ] 没有凭据、Token、私钥和真实生产地址。
- [ ] 没有调试输出和构建产物。
- [ ] 暂存差异能独立解释。
- [ ] 测试结果与提交对应。
