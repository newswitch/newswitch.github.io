# Git 大型仓库性能与维护

大型仓库慢并不只有“仓库体积大”一种原因。需要区分对象传输、历史遍历、Index 扫描、工作区文件数量、Hook 和 CI 构建成本。

## 1. 建立基线

```bash
git count-objects -vH
git status --porcelain=v1
git branch --all --contains HEAD
git config --show-origin --get-regexp '^(core|feature|index|fetch|maintenance)\.'
```

记录：

- 克隆和 Fetch 时间、传输字节。
- `status`、`log`、`diff` 和 Checkout 时间。
- Loose Object、Pack 和引用数量。
- 工作区文件数量与平台文件系统。
- Hook、杀毒软件和网络文件系统影响。

## 2. 浅克隆

```bash
git clone --depth=1 https://example.invalid/team/repo.git
git fetch --deepen=50
git fetch --unshallow
```

浅克隆减少历史传输，适合只构建当前版本的临时 CI。局限包括历史查询、Merge Base、Tag 和部分工具行为不完整。需要版本生成、Bisect 或完整审计的任务不应默认浅克隆。

## 3. 部分克隆

```bash
git clone --filter=blob:none https://example.invalid/team/repo.git
```

部分克隆先获取提交和 Tree，需要内容时再向支持该能力的远端请求 Blob。它保留提交历史语义，但依赖网络和远端能力；离线构建前要确保所需对象已取得。

## 4. 稀疏检出

```bash
git sparse-checkout init --cone
git sparse-checkout set services/api shared
git sparse-checkout list
```

稀疏检出减少工作区路径，不等于自动减少全部对象传输。它可与部分克隆组合，用于大型 Monorepo 的局部开发。

修改稀疏范围时要检查构建工具是否隐式依赖未检出路径。

## 5. Commit Graph、Index 和维护

现代 Git 可以通过维护任务优化提交遍历和对象布局：

```bash
git maintenance register
git maintenance run
git commit-graph verify
```

具体维护任务和默认策略随 Git 版本变化，应查看当前版本帮助：

```bash
git help maintenance
git help commit-graph
```

不要在不了解磁盘余量、并发访问和备份状态时手工删除 `.git/objects` 或强制重打包。

## 6. 大文件处理

首先查找来源，而不是只看当前工作区：

```bash
git count-objects -vH
git rev-list --objects --all
```

频繁变化的大型二进制会降低 Delta 效果并扩大克隆成本。选择：

- 构建产物进入制品仓库。
- 模型、备份和数据集进入对象存储或专用仓库。
- 与源码严格绑定且规模可控的文件评估 Git LFS。

历史重写会改变 Commit ID，并要求所有克隆协调迁移，必须作为正式变更处理。

## 7. CI 优化原则

- 缓存对象库时验证来源和并发安全。
- 根据任务需要选择完整、浅或部分克隆。
- 使用 Commit ID 和锁文件确保可复现。
- 路径过滤只能减少任务，不应漏掉跨目录依赖。
- 将 Git 时间与构建、下载依赖时间分开测量。

优化前后用同一网络、同一缓存状态和同一 Commit 对比，避免把缓存命中误认为结构优化。
