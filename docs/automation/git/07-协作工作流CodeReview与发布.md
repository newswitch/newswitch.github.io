# Git 协作工作流、Code Review 与发布

Git 提供对象和引用机制，协作平台负责身份、评审、检查和分支保护。有效工作流的目标是缩短反馈时间、限制变更范围，并让任一生产版本都能追溯到源码和验证证据。

## 1. 常见工作流

| 工作流 | 特点 | 适用边界 |
| --- | --- | --- |
| 主干开发 | 小批量、短分支、频繁集成 | 自动测试成熟、发布频繁 |
| 功能分支 | 每项变更通过 Review 合入主分支 | 大多数团队 |
| 发布分支 | 为稳定版本保留维护线 | 多版本长期维护 |
| Fork 协作 | 贡献者无主仓库写权限 | 开源和跨组织协作 |

复杂分支模型不是成熟度标志。长期分支越多，漂移、重复修复和合并成本越高。

## 2. 推荐的最小协作流

```text
Issue / 变更单
→ 从最新 main 创建短生命周期分支
→ 小提交 + 本地测试
→ Push 并创建合并请求
→ CI、静态检查、安全扫描
→ 至少一名合适 Reviewer
→ 合入受保护 main
→ 创建不可变制品
→ 使用标签关联发布
```

## 3. 分支保护

主分支至少应考虑：

- 禁止直接推送和强制推送。
- 必须通过指定 CI 检查。
- 必须完成 Code Review。
- 重要路径使用 CODEOWNERS 或等价规则。
- 合并后分支自动清理。
- 管理员绕过也留下审计记录。

保护策略在 Git 托管平台配置，不应只依赖本地 Hook。

## 4. Code Review 看什么

Review 不只检查语法：

- 变更意图是否清楚。
- 影响目标和权限是否扩大。
- 是否具备幂等、超时、停止和回滚条件。
- 是否泄露 Secret 或真实生产数据。
- 测试是否覆盖失败路径。
- 文档和配置 Schema 是否同步。
- 是否存在无法从 Diff 看出的生成制品变化。

大型 Diff 应先拆分机械重构和行为变化，降低审查噪声。

## 5. 合并策略

| 策略 | 历史结果 | 适合场景 |
| --- | --- | --- |
| Merge Commit | 保留分支拓扑 | 需要完整协作边界 |
| Squash Merge | 一个汇总提交 | 功能分支提交较碎 |
| Rebase Merge | 线性复制各提交 | 每个提交本身质量高 |

团队应统一策略，并明确提交作者、评审记录和签名在平台中的保留方式。

## 6. Tag 与发布

推荐使用 Annotated Tag：

```bash
git tag -a v1.4.0 -m "release v1.4.0" <commit>
git show v1.4.0
git push origin refs/tags/v1.4.0
```

Tag 应指向已经通过测试的 Commit。制品构建后记录：

```text
源码 Commit ID
Tag
构建任务 ID
依赖锁文件摘要
镜像或包 Digest
测试与扫描结果
部署环境和时间
```

不要在同一版本标签下重新构建并覆盖制品。需要修复时创建新版本。

## 7. 紧急修复

```text
从当前生产 Commit 创建修复分支
→ 最小修改
→ 执行针对性测试和风险审批
→ 发布新版本
→ 将修复同步回主干和仍受支持的维护线
```

紧急不等于跳过证据。可以缩短审批链，但必须保留修改者、审核者、测试、目标和回退方式。

## 8. 发布验收

- [ ] 生产版本能解析到唯一 Commit。
- [ ] Commit 已通过受保护分支流程。
- [ ] 制品使用内容摘要而不是可变标签识别。
- [ ] 发布说明包含风险、迁移和回退。
- [ ] 修复分支已同步到其他需要维护的分支。
- [ ] 标签和制品禁止静默覆盖。
