# Git 签名、凭据、Hook 与供应链安全

Git 保存的是内容和历史，不自动证明作者身份、代码安全或评审有效。生产链路必须把认证、签名、授权、检查和制品验证组合起来。

## 1. 四个问题分别解决

| 机制 | 回答的问题 |
| --- | --- |
| 远端认证 | 谁在访问托管平台 |
| 授权与分支保护 | 此身份能更新什么 |
| Commit/Tag 签名 | 此对象是否由对应密钥签署且内容未变 |
| CI 与制品签名 | 代码和产物是否通过规定流程 |

签名提交不代表代码经过审查；通过 CI 也不代表发起者有权发布生产。

## 2. 凭据管理

优先级通常是：短期联合身份或平台令牌、机器专用部署凭据、个人凭据。自动化禁止共享个人长期 Token。

安全要求：

- 凭据最小 Scope、最短有效期。
- 读仓库、写分支、创建发布和部署生产使用不同权限。
- 不把 Token 写入 Remote URL、命令参数和日志。
- SSH Key 配置 Passphrase、主机指纹验证和轮换。
- CI Fork 或不可信合并请求不能读取生产 Secret。

查看 Remote 时注意输出可能包含敏感 URL：

```bash
git remote -v
```

## 3. 签名 Commit 和 Tag

Git 可根据环境使用受支持的签名格式。配置前先确定组织密钥生命周期和托管平台验证能力。

```bash
git commit -S -m "feat: add validation"
git tag -s v1.0.0 -m "release v1.0.0"
git verify-commit HEAD
git verify-tag v1.0.0
```

生产策略还应处理密钥过期、吊销、机器人身份和历史验证。不能只看到托管页面上的“Verified”标识就忽略仓库策略。

## 4. Hook 的边界

客户端 Hook 可以执行格式化、测试和 Secret 扫描，但 `.git/hooks` 默认不随仓库正常版本控制分发，且本地 Hook 可被跳过。

服务端或托管平台规则更适合强制执行：

- 受保护分支。
- 必需状态检查。
- Commit/Tag 签名策略。
- 路径所有者审核。
- Secret 和恶意文件扫描。

Hook 输入是不可信数据。脚本必须正确引用变量、限制资源，并避免执行提交中未经审查的任意代码。

## 5. 不可信仓库和依赖

克隆外部仓库后，不要立即以高权限执行其中的：

- 构建脚本和 Makefile。
- Git Hook 安装脚本。
- Dev Container 和 CI 配置。
- Terraform Provider 或模块。
- Ansible Collection、Role 和自定义插件。

在隔离环境中审查 Commit、依赖锁文件、子模块 URL 和构建入口。自动化 Runner 使用临时工作区和最小网络、文件系统权限。

## 6. Secret 已进入历史怎么办

1. 立即吊销或轮换。
2. 检查使用记录和泄漏范围。
3. 停止包含 Secret 的构建和制品传播。
4. 经过协调后清理历史。
5. 要求所有下游重新同步。
6. 增加提交前和服务端扫描。

历史清理属于减少暴露，不代替凭据轮换。

## 7. 供应链闭环

```text
受保护源码分支
→ 固定依赖与可复现构建环境
→ CI 测试和扫描
→ 生成 SBOM 与来源证明
→ 制品签名
→ 按 Digest 部署
→ 保存 Commit、构建、审批和部署关联
```

Git 是链路起点，不是全部供应链保证。
