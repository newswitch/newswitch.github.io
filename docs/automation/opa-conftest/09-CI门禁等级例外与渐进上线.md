# 策略 CI 门禁、等级、例外与渐进上线

## 1. 策略流水线

```text
Policy/Data 变更
→ Format/Lint/Schema
→ Unit Test/Coverage
→ Golden Inputs 回归
→ 性能预算
→ 对历史真实输入做差异分析
→ Owner 评审
→ 构建签名 Bundle
→ 灰度/告警模式
→ 分阶段 Enforce
```

策略是生产代码，不能在 CI 中在线下载 `latest` 后直接执行。

## 2. 风险等级

| 等级 | 行为 | 示例 |
| --- | --- | --- |
| Critical | 阻断 | 公网暴露管理端口、特权容器 |
| High | 阻断或审批 | 删除生产数据库、未签名镜像 |
| Medium | Warning + 截止期 | 缺少成本标签、资源配置不合理 |
| Info | 报告 | 命名和推荐性规范 |

等级依据影响和可利用性，不依据规则作者偏好。

## 3. 结构化例外

```yaml
policy_id: K8S-IMAGE-001
resource: team-a/api
environment: production
owner: team-a
reason: legacy migration
expires_at: 2026-09-30
ticket: CHG-0000
```

例外由独立权限审批，范围精确并自动过期。禁止在 Rego 中添加永久用户名/资源名绕过，也不使用全局 `skip-policy=true`。

## 4. 影响分析

对过去一段时间真实 Plan/清单重放新策略，统计按团队、环境和规则的新增 Deny。抽样确认 False Positive，给出修复工具和迁移期，再决定 Enforce 日期。

## 5. 失败与回滚

若 Bundle 下载、编译或策略调用异常，按风险确定 Fail Open/Closed 并告警。策略逻辑误阻断时回滚到已知良好 Revision，而不是临时关掉全部准入。保留 Break-glass，但每次使用都审计和复盘。

## 6. 开发者体验

结果包含稳定 Policy ID、资源路径、违规值、期望值、修复示例和文档链接；本地命令与 CI 行为一致。政策清楚、反馈快速，才能减少绕过需求。

## 7. 策略变更也要做影响差异

对历史脱敏 Input 同时运行旧、新 Revision：

```text
旧 Allow → 新 Deny：新增阻断，必须重点确认
旧 Deny → 新 Allow：安全放宽，需要评审
Violation 内容变化：ID、资源定位、Severity 是否兼容
延迟变化：是否超过预算
```

只统计新 Deny 会漏掉意外放宽。结果按 Policy ID、团队、环境和资源类型汇总，不能把一百万条相同违规当一百万种问题。

## 8. Exception 的匹配与过期

Conftest 支持由 Rego 定义 `exception`，按具名 `deny_<id>`/`violation_<id>` 精确豁免。空字符串可能匹配全部 Deny/Violation，不应在生产例外中使用。

例外数据至少验证：Owner 存在、Ticket 可追踪、`expires_at` 未过期、环境与资源精确、批准者有权。过期不是 Warning，而应自动恢复原有 Policy 结果。

## 9. Policy ID 的生命周期

Policy ID 是用户、报表和例外的契约：

- 规则实现重构时保留 ID；
- 规则语义拆分时创建新 ID 并迁移例外；
- Severity 变化进入影响评审；
- 删除规则时清理无效例外和文档。

不要用文件行号或自然语言 Message 充当 ID。

## 10. 分阶段执行

| 阶段 | 决策行为 | 退出条件 |
| --- | --- | --- |
| Observe | 只生成报告 | 已知影响范围和误报率 |
| Warn | CI 可继续但通知 Owner | 修复文档、工具和期限已明确 |
| Enforce New | 只阻止新增/恶化 | 新变更稳定，无大面积 Break-glass |
| Enforce All | 阻止全部违规 | 存量完成治理或有精确例外 |

关键漏洞不必完整经过长期 Warning，但仍要有最小回归、应急回滚和影响评估。

## 11. CI 自身失败语义

区分：

```text
Policy Deny：输入被明确判定违规
Policy Error：编译、Schema、Undefined 或插件错误
Infrastructure Error：Registry/Runner/网络不可用
```

三者应使用不同状态和告警。把工具崩溃视为“零违规”是危险 Fail Open；把所有基础设施抖动永久 Fail Closed 又会推动绕过。核心策略可使用本地缓存的已验证 Bundle，并为异常设置有时限的人工路径。

## 12. 练习与答案

**问题：某团队请求永久跳过 `K8S-PRIV-001`，因为旧应用不能整改，应该怎样处理？**

答案：拒绝全局永久绕过。建立精确到资源/环境的有期限例外，记录 Owner、风险接受、补偿控制和 Ticket，并在到期前通知，过期自动恢复阻断。

**问题：新规则没有新增 Deny，是否说明可以安全发布？**

答案：不一定。还要检查旧 Deny 是否意外变 Allow、违规元数据是否兼容、决策延迟和未知 Input 类型。
