# OPA/Rego 测试、覆盖率、调试与静态检查

## 1. 测试与策略同库

```text
policy/
├── kubernetes/
│   ├── image.rego
│   └── image_test.rego
├── terraform/
├── data/
├── schemas/
└── testdata/
```

测试文件使用同 Package 或明确导入目标规则，输入来自最小内联对象或版本化测试夹具。

## 2. 测试允许和拒绝路径

```rego
package kubernetes.image_test

import rego.v1
import data.kubernetes.image

test_digest_is_allowed if {
  result := image.allow with input as {
    "spec": {"containers": [{"name": "api", "image": "repo/api@sha256:abc"}]}
  }
  result
}
```

除布尔结果外，还要断言违规数量、规则 ID、严重级别和消息中的稳定字段。不要过度绑定自然语言标点，导致无意义测试脆弱。

## 3. 覆盖率不是质量结论

覆盖率发现未执行的表达式，但不能证明边界条件、冲突规则和 Undefined 已处理。将覆盖率与变异思维结合：删除条件、交换默认值或缺失字段时，测试是否会失败？

## 4. 调试方法

- 先保存脱敏后的真实 Input 和 Bundle Revision。
- 使用 `opa eval` 查询中间 Rule，而不是只看最终 `allow`。
- 使用 Explain/Trace 理解变量绑定和失败表达式。
- 将大策略缩小到最小失败输入。
- 对比最近成功的策略、数据和 OPA 版本。

Trace 可能包含完整 Input，不能直接上传生产敏感数据。

## 5. 静态检查

使用格式化、严格语法、Schema、Lint 和能力集检查，防止使用目标 OPA 版本不支持的 Built-in。CI 固定工具版本，对 Policy、Data、测试和 Bundle 构建统一执行。

## 6. 性能回归

为热路径保留代表性 Input，使用 Benchmark 对比 P50/P95、分配和大集合行为。新增规则若让决策延迟显著增加，先优化索引与数据结构，再扩大资源。

## 7. 合并门禁

要求格式、静态检查、单元测试、覆盖率阈值、性能预算和代表性集成测试通过。策略 Owner 评审语义，业务 Owner 确认影响范围。
