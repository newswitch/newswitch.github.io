# OPA/Rego 测试、覆盖率、调试与静态检查

## 1. 测试与策略同库

```text
policy/
├── kubernetes/
│   ├── image.rego
│   └── image_test.rego
├── terraform/
├── data/
├── schemas/
└── testdata/
```

测试文件使用同 Package 或明确导入目标规则，输入来自最小内联对象或版本化测试夹具。

## 2. 测试允许和拒绝路径

```rego
package kubernetes.image_test

import rego.v1
import data.kubernetes.image

test_digest_is_allowed if {
  result := image.allow with input as {
    "spec": {"containers": [{"name": "api", "image": "repo/api@sha256:abc"}]}
  }
  result
}
```

除布尔结果外，还要断言违规数量、规则 ID、严重级别和消息中的稳定字段。不要过度绑定自然语言标点，导致无意义测试脆弱。

## 3. 覆盖率不是质量结论

覆盖率发现未执行的表达式，但不能证明边界条件、冲突规则和 Undefined 已处理。将覆盖率与变异思维结合：删除条件、交换默认值或缺失字段时，测试是否会失败？

## 4. 调试方法

- 先保存脱敏后的真实 Input 和 Bundle Revision。
- 使用 `opa eval` 查询中间 Rule，而不是只看最终 `allow`。
- 使用 Explain/Trace 理解变量绑定和失败表达式。
- 将大策略缩小到最小失败输入。
- 对比最近成功的策略、数据和 OPA 版本。

Trace 可能包含完整 Input，不能直接上传生产敏感数据。

## 5. 静态检查

使用格式化、严格语法、Schema、Lint 和能力集检查，防止使用目标 OPA 版本不支持的 Built-in。CI 固定工具版本，对 Policy、Data、测试和 Bundle 构建统一执行。

## 6. 性能回归

为热路径保留代表性 Input，使用 Benchmark 对比 P50/P95、分配和大集合行为。新增规则若让决策延迟显著增加，先优化索引与数据结构，再扩大资源。

## 7. 合并门禁

要求格式、静态检查、单元测试、覆盖率阈值、性能预算和代表性集成测试通过。策略 Owner 评审语义，业务 Owner 确认影响范围。

## 8. 常用命令闭环

```bash
opa fmt --fail policy/
opa check --strict --schema schemas/ policy/
opa test policy/ data/ -v
opa test policy/ data/ --coverage --format=json
opa eval --data policy/ --data data/ --input testdata/pod.json \
  'data.kubernetes.image.decision' --format=pretty
```

`opa check` 负责语法、编译和部分类型问题；`opa test` 验证规则语义；二者都不能替代使用真实 Parser/Input 的集成测试。

CI 要固定 OPA 与 Regal/Conftest 版本，并按目标生产 OPA 的 Capabilities 检查 Built-in。开发机用新函数、生产旧 OPA 不支持，是常见发布失败。

## 9. Table-driven Test

```rego
cases := [
  {"name": "digest", "image": "repo/api@sha256:abc", "denied": false},
  {"name": "tag", "image": "repo/api:v1", "denied": true},
]

test_image_cases if {
  every case in cases {
    actual := count(image.deny) > 0 with input as {
      "spec": {"containers": [{"name": "api", "image": case.image}]},
    }
    actual == case.denied
  }
}
```

表驱动测试适合大量边界，但失败消息要保留 Case Name，避免只看到整体 False。复杂夹具放入 `testdata/`，并去掉 Secret 和个人数据。

## 10. Mock 与 `with`

`with input as ...` 可替换本次输入，`with data... as ...` 可注入测试基础数据。这能隔离团队目录、允许列表等依赖，但不应把被测 Rule 本身全部替换，导致测试只验证 Mock。

同时保留一组完整 Bundle 集成测试，防止单元测试中的 Data 结构与真实 Bundle 漂移。

## 11. Explain、Trace 与 Profile

```bash
opa eval -d policy -i input.json 'data.main.decision' --explain=notes
opa eval -d policy -i input.json 'data.main.decision' --profile
opa eval -d policy -i input.json 'data.main.decision' --metrics
```

- Explain/Trace：看表达式为什么成功或失败；
- Profile：看哪些表达式耗时或重复求值；
- Metrics：观察解析、编译和执行阶段。

Trace 可能包含完整 Input 和 Data，上传前必须脱敏。

## 12. 覆盖率与变异思维

100% 表达式覆盖仍可能漏掉：字段缺失、规则冲突、错误默认值和不支持资源类型。评审时尝试：

- 删除一个关键条件，测试是否失败；
- 把 `default allow := false` 改成 True；
- 删除 Input 字段或改变类型；
- 将允许列表置空、过期或损坏；
- 添加一个未知 Kind/API Version。

测试能发现这些变异，才说明它保护了规则意图。

## 13. 练习与答案

**问题：覆盖率 100%，能否直接发布阻断策略？**

答案：不能。覆盖率只证明表达式被执行过，不证明断言正确、边界完整或历史输入不会大面积误阻断；还要做 Schema、Golden Input、差异和性能测试。
