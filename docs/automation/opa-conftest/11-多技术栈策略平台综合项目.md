# OPA/Conftest 多技术栈策略平台综合项目

## 1. 目标

建立统一但不混淆 Schema 的策略平台：开发者在本地获得快速反馈，CI 对 Plan 和渲染清单执行门禁，集群 Admission 防止绕过，生产 OPA 使用签名 Bundle，并能复现任意决策。

## 2. 仓库结构

```text
policy-platform/
├── policy/
│   ├── terraform/
│   ├── kubernetes/
│   └── supply-chain/
├── lib/
├── data/
├── schemas/
├── testdata/
├── exceptions/
├── bundles/
└── docs/
```

公共库只封装稳定算法；技术栈 Package 分开，防止 Kubernetes 路径意外用于 Terraform Input。

## 3. 策略集合

| 技术栈 | 核心策略 |
| --- | --- |
| Terraform/OpenTofu | 禁止高风险删除、公网暴露、无备份数据库和未知关键值 |
| Kubernetes | 受信 Digest、非特权、资源请求、ServiceAccount 和网络边界 |
| GitHub Actions | 工作流最小权限、Action 固定 SHA、高权限 Runner/Environment 约束 |
| Harbor 制品 | 受信仓库、签名、SBOM、来源证明和漏洞例外 |

## 4. 交付链

```text
Policy PR
→ Test/Lint/Schema/Coverage/Benchmark
→ 历史输入决策差异报告
→ 安全与业务 Owner 评审
→ 构建并签名 Bundle
→ Harbor/对象存储发布
→ 测试 OPA 灰度加载
→ 合成决策验证
→ 分阶段生产激活
→ Status/Decision Log 观测
```

## 5. 应用交付链

GitHub Actions 对 Terraform Plan JSON 和渲染后的 Kubernetes YAML 运行 Conftest。通过后生成不可变制品与 Policy Report；部署时 Admission 使用当前生产 Bundle 再验证关键规则。

CI 结果记录 Policy Revision；若上线时生产 Revision 更新，应以生产决策为准并提示规则差异。

## 6. 例外与职责

应用团队提出精确例外，安全/平台 Owner 审批，到期自动变为失败。Policy Author 无权单独发布生产 Bundle；发布身份使用 OIDC 短期凭据；Decision Log 读取受审计。

## 7. 故障演练

- 新规则误拒绝大量历史输入，差异门禁阻止发布；
- Bundle 签名错误，OPA 保留旧 Revision 并告警；
- 一部分 OPA 未更新，Revision 一致性告警；
- Admission OPA 超时，按安全等级验证 Fail 策略；
- 例外到期，流水线给出明确 Owner 和修复信息；
- 决策争议可用脱敏 Input 与 Revision 完整重放。

## 8. 验收

交付策略目录、Input Schema、测试与性能报告、签名 Bundle、权限矩阵、Revision 看板、例外清单、回滚和 Break-glass Runbook。平台的价值是稳定执行组织规则并能解释每次判断，而不是拥有最多 Rego 文件。

## 9. 先定义每种 Input 契约

| Entrypoint | Input | PEP |
| --- | --- | --- |
| `terraform.plan.decision` | Plan JSON + 环境元数据 | IaC CI |
| `kubernetes.manifest.decision` | 渲染后的单个对象 | Conftest CI |
| `kubernetes.admission.decision` | AdmissionReview | Admission Webhook |
| `workflow.decision` | Workflow AST/结构化数据 | CI Linter |
| `artifact.decision` | Digest、签名、SBOM、漏洞摘要 | 发布控制器 |

公共 Policy ID 可以共享，但适配层必须独立测试。不要让规则自行猜测 Input 是 Terraform 还是 Kubernetes。

## 10. 最小可用策略集

第一阶段只选择可高置信执行的规则：

1. Terraform 生产数据库 Delete/Replace；
2. Kubernetes Privileged、HostPath、受信镜像 Digest；
3. Workflow 过宽 Token Permission 与未固定 Action SHA；
4. Artifact 来源、签名和 SBOM 缺失。

成本、命名和推荐标签先 Warning。策略越多不代表平台越成熟；错误阻断和大量无 Owner 告警会快速消耗信任。

## 11. Policy 仓库所有权

```text
platform/：Input Schema、公共库、Bundle 构建
security/：核心安全 Policy 与 Severity
cloud/：Terraform Provider 专项规则
kubernetes/：工作负载和准入规则
data/：允许列表与组织映射
exceptions/：独立审批的临时风险接受
```

CODEOWNERS 只是一层控制。生产发布身份、签名 Key、Bundle Registry 和 Discovery Bootstrap 都要最小权限，Policy Author 不能单人完成编写、批准和发布。

## 12. 两条发布链

### 12.1 Policy 发布 {/* #policy-发布 */}

```text
Policy/Data PR
→ Format/Lint/Schema/Test/Coverage
→ Golden Input + 历史决策差异
→ Benchmark
→ Owner 审批
→ 构建并签名 Bundle
→ 灰度 OPA 激活
→ Status + 合成决策
→ 扩大生产
```

### 12.2 应用发布 {/* #应用发布 */}

```text
代码/IaC PR
→ 生成 Plan 与渲染清单
→ 拉取固定 Policy Bundle
→ Conftest
→ 生成 Policy Report
→ Apply/Deploy 不可变制品
→ Admission 再验证核心规则
```

两条链通过 Policy Revision、Artifact Digest 和 Commit 关联，任何重新 Plan/Render 都需要重新决策。

## 13. 例外服务

例外不是散落 YAML：平台校验申请者、Owner、资源、环境、Policy ID、理由、Ticket、补偿控制和到期时间。发布时把已批准例外转为版本化 Data；Decision Log 记录命中例外。

到期前通知，过期后自动恢复原 Decision。续期等同新的风险接受，不能自动无限延期。

## 14. Revision 看板

至少展示：

- 期望与实际 Bundle Revision；
- OPA 实例更新比例和错误；
- 每个 Policy ID 的 Allow/Deny/Exception；
- 新增 Deny 与意外放宽；
- P95/P99 和 Fail-open 次数；
- 最旧例外、即将到期例外；
- 决策日志丢失和 Mask 状态。

看板按环境和 PEP 区分，避免 CI Warning 与生产 Admission Deny 混在一起。

## 15. 灾难与回滚

保存最近多个签名 Bundle，并让 OPA 保留最后已知良好版本。错误策略发布时：停止扩散 → 指向上一不可变 Revision → 验证 Status → 执行合成决策 → 评估被错误允许/拒绝的变更。

Break-glass 不能依赖当前已损坏的 Policy 发布链。使用独立、多方授权、短期且全审计的路径，结束后立即恢复正常门禁并复盘。

## 16. 容量模型

分别估算：PR/Plan 峰值、Admission QPS、Input P95 大小、Bundle 数量、Decision Log 量和历史重放量。集中服务需要 N+1 容量；Sidecar 需要核算每 Pod 内存和 Bundle 下载风暴。

容量测试开启真实 TLS、签名验证、Decision Log Mask 和代表性 Data，不能只 Benchmark 一个布尔 Rule。

## 17. 最终验收题

**问题：CI 记录的 Revision 与 Admission 当前 Revision 不同，部署应看哪个结果？**

答案：生产最终执行点以 Admission 当前有效策略为准，同时提示策略差异。若组织要求审批时策略冻结，则需在发布流程中固定允许 Revision 或重新审批，不能悄悄忽略差异。

**问题：策略平台最重要的恢复资产是什么？**

答案：不仅是 Rego 源码，还包括 Input Schema、Data、Exception、工具版本、签名根信任、不可变 Bundle、Revision 状态和决策证据；缺任何一项都可能无法重放判断。
