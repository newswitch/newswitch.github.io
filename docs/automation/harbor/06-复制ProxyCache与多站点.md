# Harbor 复制、Proxy Cache 与多站点

## 1. 复制与缓存的区别

| 模式 | 数据何时到本地 | 适用目标 |
| --- | --- | --- |
| Push/Pull 复制 | 事件或计划触发后 | 明确制品集合的异地分发和灾备 |
| Proxy Cache | 首次请求上游时 | 降低公共/上游 Registry 访问压力 |

复制不是数据库级双主，也不能自动解决两个站点同时覆盖同一 Tag 的冲突。必须规定唯一写入站点或不可变 Tag，并以 Digest 验证结果。

## 2. 设计复制规则

规则至少包含：源与目标、Repository/Tag 过滤、触发方式、覆盖策略、目标 Namespace、网络带宽和失败重试。

生产建议分层：

```text
构建站点 → 安全验证项目 → 各地域生产只读项目
```

不要把开发仓库全部无差别复制到所有地域。

## 3. 一致性与恢复

应用发布前应确认目标站点已经存在预期 Digest，而不是只看复制任务“已触发”。网络中断后需要可重放、限速和积压告警。大规模补复制前评估对象存储、Jobservice Worker、链路和目标 Registry 的容量。

## 4. Proxy Cache 边界

- 首次拉取仍依赖上游可用性和延迟。
- 上游凭据、限流和删除策略会影响缓存。
- 使用 Digest 可避免 Tag 在上游变化造成内容漂移。
- 缓存项目也需要保留、容量和访问控制。
- 不应把不受信任的上游内容直接视为生产可信制品。

## 5. 多站点演练

1. 停止主站点外部访问。
2. 验证备用站点包含关键 Digest、签名和证明。
3. 切换 DNS/流量并验证集群拉取。
4. 记录 RTO、RPO 和遗漏制品。
5. 恢复后处理写入方向与冲突，避免双向循环复制。
