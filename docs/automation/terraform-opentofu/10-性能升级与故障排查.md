# Terraform/OpenTofu 性能、升级与故障排查

IaC 故障经常被笼统称为“Terraform 卡住”。实际上它可能在等待 Backend 锁、刷新数千个资源、Provider 限流退避、远端异步任务或业务验收。排障第一步是确定卡在哪一层。

## 1. 先冻结风险并保存证据

```bash
terraform version
terraform workspace show
terraform providers
terraform state list
```

同时保存：源码 Commit、Lock File、Backend/State 标识、任务 ID、开始时间、目标账号/区域、错误原文和云侧事件。

不要为了获得日志立即重跑 Apply。旧请求可能仍在远端执行，重复创建会扩大问题。

State、Plan 和 Debug 日志可能包含 Secret，只能进入受控证据位置。

## 2. 分层模型

```text
CLI/Core 解析与求值
→ Module/Provider 下载
→ Backend State 与锁
→ Provider Plugin RPC
→ 远端 API / 配额 / 异步任务
→ 新 State 写回
→ 业务验收
```

通过最后一条日志、进程状态、网络连接、Provider 日志和云审计确认当前层，不要只看终端没有输出。

## 3. `init` 慢或失败

依次检查：

1. DNS、代理、TLS 和时间；
2. Registry Discovery/内部镜像；
3. Module Source 和认证；
4. Provider 约束是否有交集；
5. Lock Hash 是否包含当前平台；
6. 临时目录、插件目录和执行权限；
7. Backend 端点与凭据。

```bash
terraform providers
```

可显示 Provider 约束由哪个 Module 引入。不要通过删除锁文件永久解决约束或校验问题。

## 4. Plan 慢

Plan 时间可拆为：配置加载、State 下载、Refresh、Data Source、图求值和差异生成。

常见原因：

- 巨型 State 中资源过多；
- Data Source 对每个实例重复查询；
- Provider Read 串行或被 API 限流；
- 跨区域/代理网络延迟；
- 大量宽 `depends_on` 使值延迟和并发下降；
- Remote State/Backend 下载慢；
- Provider Bug 或永久 Diff 计算昂贵。

先测各阶段和 API 请求，不要凭资源数量直接拆 State。拆分必须按 Owner、生命周期和爆炸半径设计。

## 5. Apply 长时间卡住

```text
Core 是否仍等待 Provider RPC？
→ Provider 是否在轮询远端任务？
→ 云 API 中任务是 Pending、失败还是已完成？
→ 是否被配额、IAM、依赖或最终一致阻塞？
```

例如负载均衡、数据库和 Kubernetes 集群创建常是异步任务。终止 CLI 前查云审计和资源事件，确认远端是否仍会完成。

资源 `timeouts` 可控制等待边界，但缩短超时不会让 API 更快，只会更早产生部分执行。

## 6. Provider 无响应或崩溃

Provider 是独立进程，可能因 OOM、Schema Bug、API 响应或插件协议异常退出。处理：

1. 不并发重跑；
2. 保存 Core/Provider 版本和崩溃日志；
3. 检查远端对象是否已创建/修改；
4. 保护最新 State；
5. 在测试 State 复现；
6. 根据兼容说明升级/回退 Provider；
7. 重新 Refresh/Plan，而非沿用旧 Plan。

Provider 崩溃后强制解锁之前，仍需确认原进程和远程执行已停止。

## 7. 永久 Diff

每次 Apply 后同一字段仍变化，常见原因：

- API 把 `null` 归一化为空值或默认；
- List/Set 顺序语义不一致；
- 外部 Controller 持续改字段；
- 服务端自动轮换/生成值；
- Provider Read/Update Bug；
- 时间、随机数或“latest”数据源参与配置；
- 两个 State 管理同一对象。

先比较配置、State 和远端 API 三者，再查 Provider Issue/Changelog。`ignore_changes` 只用于明确外部 Owner，不用于隐藏未知根因。

## 8. 突然出现大量 Replace/Destroy

立即停止，按以下顺序核对：

```text
Backend/Workspace 是否正确
→ 云账号/区域是否正确
→ State 是否为空、旧版本或新 Lineage
→ Provider/Module/CLI 是否升级
→ 地址/for_each Key 是否重构
→ Read 是否因权限/API 故障返回缺失
→ ForceNew Schema 是否变化
```

大量危险动作通常是系统性输入变化，不应逐个资源人工批准。

## 9. 锁冲突

区分真正并发任务和遗留锁。查询 CI、远程执行平台、进程、Backend 锁对象和任务所有者。

若任务仍活跃，等待或终止任务；只有确认永远不会再次写 State 才强制解锁。解锁后运行全量 Plan，检查 State 是否分叉。

频繁锁冲突说明流水线并发键或 State 边界设计有问题，不能长期靠提高 `-lock-timeout` 掩盖。

## 10. State 写回失败

最危险的情况是远端资源已改变，但新 State 未能写回 Backend。CLI 可能提供本地恢复文件或推送指引。

立即：

- 停止所有该 State 任务；
- 保护本地恢复文件和日志；
- 修复 Backend 网络/权限；
- 按官方错误指引恢复 State；
- 对比 Serial/Lineage 和远端对象；
- 全量 Plan 验证。

不要丢弃本地文件后重新 Apply，也不要盲目覆盖 Backend 较新版本。

## 11. Debug 日志

Terraform/OpenTofu 和 Provider 支持不同级别日志。只在隔离环境或严格受控窗口临时启用，因为可能记录 API Header、响应、State 属性和 Secret。

采集原则：最短复现、最小权限、独立日志文件、上传前脱敏、设置自动删除。不要把 TRACE 永久留在共享 Runner。

## 12. 性能优化

- 缓存可信 Provider/Module，但锁定来源和 Hash；
- 消除重复 Data Source 和宽依赖；
- 按故障域合理拆 State；
- 根据 API 配额调节并发，而非一味提高；
- 使用稳定不可变制品 ID，减少“latest”刷新；
- 升级已知性能问题的 Provider，但先测试 Plan；
- 为 Backend 选择低延迟、可靠网络；
- 把高频数据面操作移出 IaC。

优化指标包括 Init/Refresh/Plan/Apply 分阶段耗时、API 请求/限流、锁等待、State 大小和 Provider RSS。

## 13. 安全升级顺序

```text
读取 CLI/Provider/Module/Backend 变更说明
→ 备份并验证 State 恢复
→ 一次只改变一个主要层
→ 测试 State 和测试账号 Plan/Apply/Destroy
→ 生产只读 Plan
→ 审查 Schema、默认、Replace、State Upgrade
→ 小爆炸半径 Apply
→ 业务验收和观察
```

不要同批升级 CLI、多个 Provider、Module 并重构地址。Provider 可能在 Read 时升级 State Schema，回退前要确认旧版本还能读取。

Terraform 与 OpenTofu 切换不是普通 CLI Minor 升级，尤其要验证 State/Plan、加密、Provider 地址、Backend 和功能兼容。

## 14. Runbook 模板

```text
症状与首次时间：
影响的 State/环境：
最后成功 Commit/运行：
CLI/Provider/Module 版本：
当前层：Core / Backend / Provider / API / Business
远端真实状态：
State/锁状态：
已执行动作及结果：
禁止动作：
恢复标准：
后续全量 Plan 与业务验收：
```

恢复标准不是“命令不报错”，而是 State 映射正确、全量 Plan 可解释、远端资源健康、业务验收通过且临时权限/日志已清理。

## 15. 练习与答案

**问题：降低 `parallelism` 后 Apply 成功，根因一定是 Terraform 并发过高吗？**

答案：不一定。它可能只是绕开远端 API 限流、Provider 并发 Bug 或共享资源锁。应结合 API 429、Provider 日志和资源事件定位，避免永久用低并发掩盖问题。

**问题：Plan 显示全部资源要创建，最先检查什么？**

答案：先检查 Backend、Workspace、State Lineage、账号和区域，而不是检查每个资源 HCL。系统性 Create 通常说明 State 未加载或环境选错。
