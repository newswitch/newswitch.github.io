# Terraform/OpenTofu 性能、升级与故障排查

## 1. 保存证据

```bash
terraform version
terraform providers
terraform workspace show
terraform state list
terraform plan -out=diag.plan
```

日志、Plan 和 State 可能含敏感数据，不直接贴到公开工单。

## 2. 分层定位

| 症状 | 优先检查 |
| --- | --- |
| Init 慢/失败 | Registry、代理、镜像、锁文件、证书 |
| Plan 慢 | Data Source、State 规模、Provider 读取、API 限流 |
| Apply 卡住 | Provider 请求、异步资源、锁、下游配额 |
| 永久 Diff | API 归一化、Provider Bug、外部控制器、类型顺序 |
| 大量 Replace | Provider Schema、地址变化、版本升级、Import 错误 |
| 锁冲突 | 是否有活动任务、Backend 锁语义、异常退出 |

## 3. Debug 日志

临时启用工具支持的日志级别，在隔离环境复现并脱敏。Debug 可能包含 Header、State 属性和 API 正文，收集后及时删除。

## 4. 性能

优化前测 Init、Refresh、Graph、Provider API 和 State 读写。拆分 State 按团队/生命周期/爆炸半径，而不是仅为加速任意切割。并发度受 API 配额约束。

## 5. 升级顺序

```text
备份 State
→ 阅读 CLI/Provider/Module 升级说明
→ 锁定一次小范围变化
→ 测试 State 和测试账号 Plan/Apply
→ 生产只读 Plan
→ 审批 Apply
→ 业务验收和观察
```

不要同一批同时升级 CLI、多个 Provider、Module 和重构资源地址。

## 6. Provider 崩溃或部分失败

停止并发 Apply，保存日志和 State 版本，检查远端真实资源，再运行新 Plan。不要直接删除锁或手工删资源来“恢复干净”。

## 7. Runbook 结论

结论应指出故障属于配置、状态映射、Provider、Backend、远端 API 还是业务层，并写明证据边界。
