# GitHub Actions 架构、事件与执行路径

## 1. 对象关系

```text
Repository Event / API / Schedule
→ Workflow Run
→ Job DAG
→ Runner 获取一个 Job
→ Step 按顺序执行 Shell 或 Action
→ Check、日志、Artifact、状态和部署结果
```

一个 Workflow 文件可因多种事件产生多次 Run；一次 Run 可包含并行 Job；一个 Job 在同一 Runner 上执行，因此 Step 共享工作目录和该 Job 生命周期内的环境。

## 2. 各对象负责什么

| 对象 | 职责 | 常见误区 |
| --- | --- | --- |
| Event | 触发候选 Workflow | 事件 Payload 都可信 |
| Workflow | 声明触发、权限和 Job 图 | 文件只是脚本 |
| Job | 选择 Runner、权限、环境和依赖 | 不同 Job 自动共享文件 |
| Step | 执行命令或 Action | 每个 Step 都是新容器 |
| Action | 封装可复用操作 | Marketplace Action 天然可信 |
| Runner | 拉取任务并执行代码 | 自托管 Runner 自动隔离 |

## 3. 一次 Push Run 经历什么

1. GitHub 接收提交并匹配默认分支中的 Workflow。
2. `on`、路径和分支过滤决定是否创建 Run。
3. Job 的 `if` 与依赖图决定是否进入队列。
4. 调度系统根据 Label/Runner Group 选择 Runner。
5. Runner 获取短期 Job 凭据，准备工作目录并执行 Step。
6. Step 使用 Context、环境、`GITHUB_TOKEN` 和显式 Secret。
7. Runner 上传日志、检查结果与 Artifact，报告 Job 终态。
8. 下游 Job 根据 `needs` 和条件运行。

## 4. 控制面与执行面

GitHub 承担事件、排队、权限和状态控制；Runner 执行仓库代码并访问网络。自托管 Runner 一旦被恶意 Job 控制，可能影响所在网络和后续任务，因此它属于高敏感执行面。

## 5. 排查第一问

- 没有 Run：检查事件、Workflow 所在分支和过滤规则。
- Run 有但 Job Skipped：检查 `if`、`needs` 和表达式值。
- Job Queued：检查 Runner Label、Group、容量和并发限制。
- Job Started 后失败：进入 Checkout、依赖、命令、权限或外部系统层。
