# GitHub Actions 日志、指标、成本与故障排查

## 1. 时间拆分

```text
事件到 Run 创建
+ Job 排队
+ Runner 启动/准备
+ Checkout/依赖下载
+ 构建测试
+ Artifact 上传
+ 审批等待
+ 发布与验证
```

只看总耗时无法判断应该扩 Runner、优化缓存，还是缩短审批和外部服务延迟。

## 2. 指标体系

| 层 | 指标 |
| --- | --- |
| Workflow | 成功率、取消率、P50/P95、重跑率 |
| Queue/Runner | 排队、在线/忙碌、启动、离线、容量 |
| Job/Step | 各阶段耗时、错误类型、Matrix 数量 |
| Cache/Artifact | 命中、上传下载耗时、存储用量 |
| 外部系统 | GitHub API、Harbor、Vault、云 API、集群延迟 |
| 成本 | 执行分钟、Runner 规格、存储、重复 Job |

按仓库、工作流、分支信任级别和 Runner 类型聚合，避免把提交 SHA 放进高基数指标标签。

## 3. 故障树

```text
没有预期结果
├── Workflow 未触发：分支/路径/事件/语法
├── Job Skipped：if/needs/权限上下文
├── Job Queued：Label/Group/并发/配额/Runner离线
├── 准备失败：Checkout/镜像/工具链/网络
├── Step 失败：代码/依赖/权限/Secret/下游
├── 上传失败：Artifact/容量/超时
└── 发布失败：Environment/OIDC/策略/健康门禁
```

## 4. 证据记录

记录 Repository、Workflow 文件与提交 SHA、Run/Job ID、Event、Ref、Actor、Runner Name/Group/Image、Action SHA、失败 Step、状态码和外部 Request ID。日志只保存脱敏元数据。

开启调试可能扩大 Secret 泄漏，先在隔离仓库和低权限身份复现。

## 5. 成本优化顺序

先删除重复触发和无意义 Matrix，再取消过期 PR Run、优化依赖与镜像、使用可验证缓存，最后调整 Runner 规格。降低单步耗时但增加重跑率和排队并不是真正优化。

## 6. Runbook

每个告警包含影响范围、快速判断、证据、临时止损、恢复验证和升级条件。不要将“Re-run all jobs”设为默认动作，外部副作用可能重复。
