# Rundeck 高可用、备份、升级与灾难恢复

## 1. HA 组成

```text
LB / TLS
→ 多个 Rundeck Server
→ 外部高可用数据库
→ 共享/对象化 Execution Log
→ 一致的项目配置、插件和 Key Storage
```

调度和执行归属必须使用版本支持的集群机制，不能让每个副本独立触发同一个 Schedule。

## 2. 备份清单

- 数据库中的 Job、Execution 和系统元数据；
- Project 配置、ACL、Framework/系统配置；
- Execution Log 与外部存储；
- Key Storage 数据及其加密/外部密钥；
- 插件二进制、版本清单和自定义脚本；
- TLS、SSO、通知和外部集成配置。

Git 中的 Job 定义不能替代执行历史和凭据恢复。

## 3. 恢复顺序

在隔离环境恢复数据库和配置，加载完全一致的插件，恢复 Key Storage/日志，再验证登录、ACL、节点发现、只读 Job、调度唯一性和日志读取。恢复环境不能误连生产目标并执行 Schedule。

## 4. 升级

阅读目标版本和发行版迁移路径，在生产数据副本测试数据库、插件、ACL、Job、API 和 UI。备份后按集群滚动/维护方案升级，观察调度和正在运行 Execution。数据库迁移后不只回滚应用包。

## 5. 灾难场景

- 单个 Server 丢失：Execution 是否转移/状态如何；
- 数据库不可用：禁止继续创建未知状态操作；
- 日志存储不可用：是否阻断高风险执行；
- Key Storage/KMS 不可用：Job 明确失败而非降级到共享密码；
- 区域故障：RPO/RTO、DNS 和目标网络；
- 插件缺失/错误：受影响 Job 可定位并回退。

## 6. 演练输出

记录实际 RTO/RPO、丢失的 Execution 状态、重复副作用、人工步骤和改进 Owner。没有验证“恢复后不会重复调度”的备份方案是不完整的。
