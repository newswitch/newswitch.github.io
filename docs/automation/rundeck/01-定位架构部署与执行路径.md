# Rundeck 定位、架构、部署与执行路径

## 1. 系统边界

```text
User / API / Webhook / Schedule
→ Rundeck Web/API 与认证授权
→ Job 定义、Options 和 Workflow
→ 调度与 Execution
→ Plugin / Node Executor / Workflow Step
→ SSH、WinRM、Kubernetes、Ansible、HTTP API 等目标
→ 日志、状态、通知与审计
```

Rundeck 控制执行和记录证据；目标系统仍负责自身事务、权限和最终状态。

## 2. 主要状态

数据库通常保存项目、Job、Execution 元数据等；执行日志可能位于本地或外部存储；Key Storage 保存/引用凭据；项目配置和插件决定行为。备份必须覆盖这些对象及其一致性。

## 3. 部署阶段

| 阶段 | 方案 | 注意 |
| --- | --- | --- |
| 学习 | 单节点、隔离目标 | 不连接生产，不使用真实凭据 |
| 团队 | 外部数据库、TLS、集中认证 | 备份、权限、日志容量 |
| 生产 | 多节点/受支持 HA、共享/外部日志 | 调度唯一性、会话、故障切换 |

具体 HA 能力与版本/发行版有关，部署前按官方版本文档确认。

## 4. 一次执行

1. 触发源创建 Execution，并保存输入快照。
2. ACL 检查用户是否能运行 Job 和访问目标。
3. Node Filter 解析为目标节点集合。
4. Workflow 按策略执行 Step，节点步骤调用 Executor。
5. 日志和状态持续写入，错误处理决定继续/停止。
6. 最终通知、审计和输出引用关联 Execution ID。

## 5. 生产边界

Rundeck 不应直接用共享 Root 身份执行所有 Job。每类动作使用受限服务身份，并在目标系统二次限制。门户不可用不应影响已运行业务；紧急手工路径必须受控并回填审计。
