# Temporal 测试、时间跳跃与故障注入

“等三十天没有审批就过期”不适合用真实等待验证；但把 Activity 换成一个成功 Mock，也不能证明 Worker 崩溃后外部变更只执行一次。**不同测试验证的是不同边界，必须让断言与测试环境提供的能力一致。**

以下使用 **Python 3.11+、`temporalio==1.36.1`、标准库 unittest**。配套代码在 [Temporal 测试示例](https://github.com/newswitch/newswitch.github.io/tree/main/examples/automation/temporal-testing)，包含 Workflow、替身 Activity、4 个独立 Activity 测试和 4 个 Workflow/Replay 测试。它只操作合成变更标识，不调用生产基础设施。

## 1. 测试金字塔

| 层 | 目标 |
| --- | --- |
| 纯函数测试 | 业务判断、状态转换、参数校验 |
| Workflow 测试环境 | Timer、Signal、重试、分支、补偿 |
| Activity 单元/契约 | 下游 API、幂等、错误分类 |
| Replay Test | 新代码兼容历史 |
| 集成/故障测试 | 真实 Service、Worker、数据库和网络 |

### 1.1 先固定 SDK 与测试服务器边界

SDK 1.36.1 中有三种不同入口：

| 入口 | 时间行为 | 适用边界 |
| --- | --- | --- |
| `WorkflowEnvironment.start_time_skipping()` | V1，环境共享虚拟时间 | 本篇基础 Timer、Signal、Activity Retry 案例；底层为旧式测试服务器，不与生产功能完全等价 |
| `start_local()` | 真实时间 | 本地完整服务能力集成，不自动把长 Timer 变成瞬时 |
| `start_time_skipping_v2()` | 每个 Workflow 的虚拟时钟 | 该版本仍标为实验/不稳定，不能照搬 V1 的全局时间假设 |

本例选择第一种。初次运行可能下载测试服务器二进制；固定 SDK 不等于已固定该二进制。隔离 CI 应预置验收过的文件，记录版本/SHA256，并通过 `TEMPORAL_TEST_SERVER` 传给示例的 `test_server_existing_path`。

还要确认 OS/CPU 架构支持。V1 的 ARM 支持有限，下载失败、端口绑定失败与 Workflow 业务失败是不同问题，不能通过关闭 sandbox 或修改业务分支来“修好”测试。具体版本边界见 [SDK 1.36.1 测试环境实现](https://github.com/temporalio/sdk-python/blob/1.36.1/temporalio/testing/_workflow.py)。

### 1.2 分开运行不需要服务与需要服务的测试

在配套示例目录中准备独立虚拟环境、激活后执行：

```bash
python -m pip install -r requirements.txt
python -m unittest -v test_activity
```

这组 4 个测试只使用 SDK 的 Activity 上下文，不启动 Server/Worker。要运行时间跳跃、Server 重试和生成 History 的测试，再执行：

```bash
python -m unittest -v test_workflow
```

后一组会启动临时测试服务器和 Worker。每个测试独享环境，并在退出 Worker 后 `shutdown`；不要将 V1 环境共享给并行跳时测试，避免一个用例推进另一个用例的时钟。

## 2. 时间跳跃

### 2.1 用可观察的状态而不是真实 sleep 对齐

示例 Workflow 先等待审批，超时则直接返回；审批成功后才调度 Activity。状态 Query 只读取状态，不改变它。

```python title="workflows.py"
from datetime import timedelta

from temporalio import workflow
from temporalio.common import RetryPolicy

@workflow.defn
class ApprovalWorkflow:
    def __init__(self) -> None:
        self.approved = False
        self.phase = "waiting"

    @workflow.signal
    def approve(self) -> None:
        self.approved = True

    @workflow.query
    def status(self) -> str:
        return self.phase

    @workflow.run
    async def run(self, change_id: str) -> str:
        try:
            await workflow.wait_condition(
                lambda: self.approved, timeout=timedelta(days=30)
            )
        except TimeoutError:
            self.phase = "expired"
            return "expired"
        self.phase = "applying"
        result = await workflow.execute_activity(
            "apply_change",
            change_id,
            result_type=str,
            start_to_close_timeout=timedelta(seconds=2),
            schedule_to_close_timeout=timedelta(seconds=10),
            retry_policy=RetryPolicy(
                initial_interval=timedelta(seconds=1),
                maximum_interval=timedelta(seconds=1),
                maximum_attempts=3,
            ),
        )
        self.phase = "completed"
        return result
```

`workflow.wait_condition` 是持久化执行语义中的等待，不是让 Python 线程睡三十天。Activity 的 2 秒限制一次尝试，10 秒限制含排队/重试的整体生命周期；`maximum_attempts=3` 包含首次尝试，不是“首次加三次重试”。

### 2.2 自动跳时与手动跳时的顺序

V1 环境中，等待 `handle.result()`（也包括 `execute_workflow`）会启用自动跳时，推进可跳过的 Timer。若要先在第二十九天发送 Signal，就不能一开始直接等待最终结果；应先启动、观察状态、手动推进，再发 Signal。

下面是配套 `WorkflowTests` 中的一个方法。`self.env` 来自 `start_time_skipping()`；`self.worker` 注册上面的 Workflow 和同名替身 Activity；`self.start` 使用独立 Workflow ID/Task Queue 启动合成实例。

```python title="test_workflow.py#test_signal_before_deadline_and_retry"
async def test_signal_before_deadline_and_retry(self) -> None:
    fake = ChangeActivities(failures=2)
    async with self.worker(fake):
        handle = await self.start()
        self.assertEqual(await handle.query(ApprovalWorkflow.status), "waiting")
        await self.env.sleep(timedelta(days=29))
        self.assertEqual(await handle.query(ApprovalWorkflow.status), "waiting")
        await handle.signal(ApprovalWorkflow.approve)
        self.assertEqual(await handle.result(), "applied")
    self.assertEqual(
        fake.calls,
        [("change-001", 1), ("change-001", 2), ("change-001", 3)],
    )
```

Query 用于确认执行已进入等待状态，避免靠 `asyncio.sleep(0.1)` 猜测 Worker 是否准备好。没有审批的另一个测试则直接等待结果，断言返回 `expired` 且 Activity 调用列表为空。

自动跳时不意味着真实 HTTP 请求、数据库调用或 Activity 内的普通等待也会被加速。不要在 Mock 中真的等待二十九天。取消、多个 Timer、晚到 Signal、Continue-As-New 和时区/业务日历仍需独立用例；本例没有覆盖的分支，不能从一次通过推断出来。

## 3. Activity Mock

### 3.1 名称要与 Workflow 调度的 Activity 相同

Workflow 用字符串调度 `apply_change`。测试 Worker 可以注册另一个实现，但其装饰器名称必须仍是 `apply_change`，不能只把函数名改成 `fake_apply` 后期待 SDK 自动替换。

```python title="fakes.py"
from temporalio import activity
from temporalio.exceptions import ApplicationError

class ChangeActivities:
    """Test double only: records attempts, performs no external change."""

    def __init__(self, *, failures: int = 0, reject: bool = False) -> None:
        self.failures = failures
        self.reject = reject
        self.calls: list[tuple[str, int]] = []

    @activity.defn(name="apply_change")
    async def apply_change(self, change_id: str) -> str:
        attempt = activity.info().attempt
        self.calls.append((change_id, attempt))
        activity.heartbeat(change_id)
        if self.reject:
            raise ApplicationError(
                "change rejected", type="RejectedChange", non_retryable=True
            )
        if attempt <= self.failures:
            raise ApplicationError("temporary failure", type="TransientChange")
        return "applied"
```

这个替身记录参数和尝试号，不创建真实资源。成功用例验证“前两次失败、第三次成功”，不可重试用例验证 `RejectedChange` 只有一次调用，并检查 WorkflowFailureError→ActivityError→ApplicationError 的原因链。只断言最外层报错文本不足以区分故障分类。

### 3.2 ActivityEnvironment 不负责 Server 重试

直接测试 Activity 时，可以提供 `activity.info()`、捕获 Heartbeat 和模拟取消上下文。例如：

```python title="test_activity.py#test_success_and_heartbeat"
async def test_success_and_heartbeat(self) -> None:
    env = ActivityEnvironment()
    heartbeats = []
    env.on_heartbeat = lambda *details: heartbeats.append(details)
    fake = ChangeActivities()
    self.assertEqual(await env.run(fake.apply_change, "change-001"), "applied")
    self.assertEqual(fake.calls, [("change-001", 1)])
    self.assertEqual(heartbeats, [("change-001",)])
```

这验证的是一次调用及本地 Heartbeat 回调，不是服务器确实收到了心跳，也不验证生产 Worker 的发送节流。设置 `env.info=replace(env.info, attempt=3)` 可以验证第三次尝试的业务分支，但**不等于实际发生了两次重试**。

配套测试专门断言 `ActivityEnvironment.run` 遇到可重试错误仍只调用一次；Server 重试策略由上一节的 Worker/测试服务器用例检查。接口依据见 [ActivityEnvironment 实现](https://github.com/temporalio/sdk-python/blob/1.36.1/temporalio/testing/_activity.py)。

## 4. Replay Test

### 4.1 Replay 消费历史，不重新完成外部变更

已经完成的 Activity 结果来自 History，Replay 不应再次向下游提交变更。配套用例完成合成 Workflow 后取得 History，关闭原 Worker，再交给 Replayer：

```python title="test_workflow.py#test_completed_history_replays_without_activity"
async def test_completed_history_replays_without_activity(self) -> None:
    fake = ChangeActivities()
    async with self.worker(fake):
        handle = await self.start()
        await handle.signal(ApprovalWorkflow.approve)
        self.assertEqual(await handle.result(), "applied")
        history = await handle.fetch_history()
    before = list(fake.calls)
    result = await Replayer(workflows=[ApprovalWorkflow]).replay_workflow(history)
    self.assertIsNone(result.replay_failure)
    self.assertEqual(fake.calls, before)
```

默认 `raise_on_replay_failure=True` 会将回放错误抛出。这里同时保留 `replay_failure` 与调用记录断言，避免把“调用函数没报异常”写成唯一检查。这个用例只覆盖一条合成历史的当前代码，不代表所有旧版本都兼容。API 见 [Replayer 1.36.1](https://github.com/temporalio/sdk-python/blob/1.36.1/temporalio/worker/_replayer.py)。

### 4.2 新启动测试与历史兼容不能互相替代

如果历史的第一个外部命令是 Timer，新代码却在等待之前插入 Activity，命令类型/顺序就可能与旧历史冲突；新启动 Workflow 能成功，仍不代表运行中的旧 Workflow 能继续。相反，Replay 通过也不能证明新增分支、下游权限或生产时延正确。

应保存不同版本、长短流程、Signal/Update、重试与异常分支的 History 样本。优先使用合成记录；真实 History 含 Payload 等敏感内容，需要授权、隔离存储和兼容的 Data Converter/Codec。不要随意删事件、重排 ID 或改动影响分支的 Payload 来“脱敏”，否则回放的已经不是原行为。版本发布边界见 [兼容发布](./09-Workflow版本演进与兼容发布.md)。

## 5. 故障注入

必须在隔离环境按一个故障因素一次实验，并预先保留恢复出口。Mock 抛异常没有覆盖进程真正退出、传输结果未知和持久化恢复。

| 故障窗口 | 需要观察 | 恢复后的关键断言 |
| --- | --- | --- |
| Activity 尚未完成时 Worker 退出 | timeout、重试尝试号、其他 Worker 是否接手 | 流程继续，业务资源数量符合预期 |
| 外部操作已提交，Activity 完成确认尚未记录时退出 | 下游业务幂等键、提交记录、Temporal History | 新尝试可查回同一结果，不重复创建资源 |
| Temporal 服务短时不可达 | Worker/Client 的 RPC 重试和 backlog | 恢复后继续推进；调用方超时的 Workflow 仍需按 ID 查询真实状态 |
| 下游 429/5xx/权限拒绝 | 有限重试、退避与错误类型 | 可恢复错误恢复，永久错误不持续冲击下游 |
| Signal 重复/晚到、多个发送者 | 消息语义、当前状态、业务去重键 | 不重复执行状态转换；不能把多个客户端的业务顺序当成天然全序 |
| 滚动升级或 History 增长 | Replay 失败、版本路由、Continue-As-New | 老实例可继续，新实例行为正确，结果关联不丢失 |
| Codec/KMS 不可用 | Payload 解码、重试与权限错误 | 恢复访问后可读历史，而不是通过跳过解码继续执行 |

“外部提交成功、确认丢失”尤其重要：Temporal 重试的是 Activity，不会撤销已发生的现实副作用。需要下游稳定幂等键、唯一约束或可查询的提交记录；Worker 内存中的 `fake.calls` 不是生产幂等账本。背景见 [Activity 可靠性](./03-Activity超时重试Heartbeat与幂等.md)。

## 6. 断言最终状态

建议按三层记录结果：

| 层 | 本例或集成测试的断言 | 避免的误判 |
| --- | --- | --- |
| Workflow | `expired/applied`、状态分支、错误原因链、Replay 结果 | Completed 不代表业务执行了正确路径 |
| Activity | 参数、尝试号、不可重试标记、Heartbeat 内容 | Mock 次数不等于外部副作用次数 |
| 外部系统 | 持久化幂等记录、资源数量、补偿后状态与审计 | 只看 Workflow 成功，漏掉重复资源或部分提交 |

涉及 Search Attribute、取消/补偿或 Continue-As-New 的业务，应为这些机制另设明确断言。本篇 4 个 Workflow 用例不是完整故障覆盖率报告。

测试结束关闭本次 Worker/测试服务器，清理由本用例拥有的合成资源；失败时保留版本、Task Queue、Workflow/Run ID、原因链和相关 History。不要为了让测试变绿而自动删除未知 Namespace 或终止其他进程。

## 7. 生产合成测试

在隔离 Namespace 周期运行无破坏的短 Workflow，验证启动、Task Queue、Worker、Activity、Signal、可见性和告警链。不能用真实生产变更作为健康检查。

它使用真实时间和真实服务链路，不应将测试服务器的“跳过三十天”当成生产能力。探测失败也要按鉴权、排队、Worker、Activity、外部依赖分层定位，不能直接重置正在运行的真实业务 Workflow。

## 8. 练习与答案

### 8.1 为什么测试过期分支不需要真实等三十天

答案：V1 测试环境在等待 Workflow 结果时可以推进可跳过的 Timer。它验证 Workflow 的时间分支，不把外部 HTTP 或普通 Python 等待都变成虚拟时间。

### 8.2 为什么第二十九天发 Signal 的用例不先等待 result

答案：等待结果会启动自动跳时，可能直接推进到过期。应先启动并观察等待状态，手动推进二十九天，再发 Signal，最后等待结果。

### 8.3 多个用例能否并行共用一个 V1 环境

答案：不宜。V1 跳时影响环境共享时钟，一个用例会改变另一个的时间条件。本例每个用例独享环境；不能把此结论直接套到实验性 V2 的逐 Workflow 时钟。

### 8.4 maximum_attempts 为三代表重试三次吗

答案：不是，包含首次尝试，总共最多三次。本例预期调用记录的 attempt 为 1、2、3。

### 8.5 ActivityEnvironment 能验证服务器重试吗

答案：不能。它提供一次本地 Activity 调用的上下文，错误直接返回。手工设置 attempt=3 只是测试该分支，Server 重试要用带 Worker 和服务的测试。

### 8.6 捕获 Heartbeat 回调是否证明服务端收到心跳

答案：不是。ActivityEnvironment 捕获的是本地调用，不能证明 Worker 的网络发送、节流、服务记录或取消传递正常。

### 8.7 不可重试错误应断言什么

答案：除失败结果外，还应检查错误类型/标记、Workflow 到 Activity 的原因链和调用次数；本例 `RejectedChange` 预期仅调用一次。

### 8.8 Replay 成功是否证明新版本可以直接上线

答案：不足。它只证明样本历史与相应代码的回放兼容，还需其他历史分支、真实下游、权限和新逻辑测试。一次当前版本的合成回放不能替代历史样本集。

### 8.9 Activity 成功但确认丢失为何可能再次执行

答案：外部提交与 Temporal 完成记录不是一个跨系统原子事务。恢复后可能再次投递，需要下游持久化幂等键与结果查询，而不是 Worker 内存去重。

### 8.10 测试成功后最重要的清理边界是什么

答案：关闭本次创建的 Worker/测试服务，只清理用例拥有的资源；保留失败证据，不误删其他 Namespace、业务资源或用户进程。
