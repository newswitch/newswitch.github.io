# Temporal 定位、架构与任务执行路径

## 1. 对象关系

```text
Client 启动/交互
→ Temporal Service（Namespace、History、状态）
→ Workflow Task Queue
→ Worker 执行 Workflow Task 并提交 Command
→ Service 追加 Event History
→ Activity Task Queue
→ Worker 执行 Activity 外部副作用
→ 结果写回 History，继续 Workflow
```

Task Queue 是逻辑路由名称，不是用户直接管理的消息队列数据文件。

## 2. 核心对象

| 对象 | 作用 |
| --- | --- |
| Namespace | 隔离 Workflow、保留、搜索属性和安全边界 |
| Workflow ID | 业务稳定身份与重复启动策略 |
| Run ID | 某次具体运行 |
| Event History | 已发生事件的权威记录 |
| Workflow Task | 让 Worker Replay 并产生下一步 Command |
| Activity Task | 执行网络、数据库、文件等副作用 |
| Worker | 轮询 Task Queue，加载注册的代码 |

## 3. 一次 Activity 调用

Workflow 代码调度 Activity，Service 写入 Scheduled Event 并把 Task 放入队列。Worker 获取任务、调用下游并完成；结果追加到 History。Workflow Worker 再 Replay 历史，看到结果后决定下一步。

## 4. Temporal 不保存什么

它保存工作流状态所需 History 和 Payload，但不是大文件/模型/日志仓库。大数据放对象存储，Workflow 只保存不可变引用和校验和，避免 History 膨胀。

## 5. 与其他工具的边界

- Argo Workflows：Kubernetes Pod/DAG 批处理；
- Rundeck：人触发的 Runbook 和节点运维；
- Temporal：跨服务、长时间、需等待和恢复的持久化业务/运维流程；
- Kubernetes Controller：持续协调资源期望状态。

选择取决于状态模型，不按“都叫 Workflow”混用。
