# Temporal 部署、高可用、备份与灾难恢复

## 1. Cloud 与自建

| 方案 | 团队负责重点 |
| --- | --- |
| Temporal Cloud | Namespace、Worker、身份、配额、数据和业务恢复 |
| 自建 Temporal Service | 还负责服务组件、Persistence、可见性、升级、备份和容量 |

托管不等于业务工作流自动具备正确补偿和幂等。

## 2. 自建组成

Temporal Service 包含前端、History、Matching、内部 Worker 等逻辑角色，并依赖持久化和可见性存储。实际部署组件和支持数据库随版本变化，应按官方兼容矩阵设计。

## 3. 高可用

- 服务组件跨故障域多副本；
- Persistence 使用受支持 HA/备份方案；
- Worker 独立多副本并跨故障域；
- mTLS、DNS、LB 和时间同步可靠；
- Namespace 配额、保留和权限明确；
- 可见性故障与核心 History 执行故障分开处理。

## 4. 备份对象

核心 Persistence、可见性索引/重建方案、动态配置、Namespace/安全配置、TLS/KMS、Worker 代码与版本映射、Payload Codec 和外部业务幂等数据。

只备份 Temporal 数据而丢失兼容 Worker 代码，旧 Workflow 可能无法 Replay。

## 5. 恢复验证

在隔离环境恢复，禁止 Schedule/Worker 误连生产下游。验证已有 Workflow Query/Replay、新 Workflow、Activity、Signal、可见性、Codec 解密和 Worker 版本。检查是否会重复外部副作用。

## 6. 升级

遵循版本路径和持久化 Schema 迁移说明，先升级测试环境和兼容 Worker。备份后分阶段升级服务组件，持续观察 Task、History、可见性和延迟。数据库迁移后回滚必须按演练方案。

## 7. 区域灾难

跨区域能力、Namespace 复制和故障切换取决于部署/产品方案。无论使用何种能力，都要定义 RPO/RTO、外部系统可达性、DNS、Worker 路由、重复执行和回切。季度演练而不是只看复制状态。
