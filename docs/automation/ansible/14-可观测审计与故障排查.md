# Ansible 可观测、审计与故障排查

`FAILED!` 只是执行器结论。快速排障需要定位失败发生在目标选择、连接、权限、模块传输、目标执行还是业务验收。

## 1. 分层模型

```text
0 代码与依赖：Commit、ansible-core、Collection、EE
1 配置解析：ansible.cfg、环境变量、CLI
2 Inventory：来源、组、Host Pattern、变量
3 网络与认证：DNS、路由、SSH/API、Host Key
4 Become：sudo/su 权限、TTY、密码
5 Runtime：Python、临时目录、磁盘、SELinux
6 Module：参数、依赖、返回值、Check 支持
7 目标系统：包锁、systemd、文件系统、外部 API
8 业务：Ready、流量、数据一致性与 SLO
```

## 2. 最小证据集

```bash
ansible --version
ansible-config dump --only-changed
ansible-inventory -i <inventory> --host <host>
ansible <host> -i <inventory> --list-hosts
ansible <host> -m ansible.builtin.ping -vvv
```

并保存：错误时间、作业 ID、目标主机、Task UUID/名称、委派对象、前后变更、最近版本和目标端日志。脱敏后再共享。

## 3. 状态分类

| 状态 | 含义 | 下一步 |
| --- | --- | --- |
| `ok` | Task 成功且无变化 | 仍需业务验收 |
| `changed` | 模块报告产生变化 | 检查是否预期及 Handler |
| `failed` | 模块/条件失败 | 查看结构化返回和目标日志 |
| `unreachable` | 未能建立/保持连接 | 网络、认证、Host Key、连接插件 |
| `skipped` | 条件/Tag/Check 导致未执行 | 验证条件和覆盖范围 |
| `rescued` | Block 失败后 Rescue 成功 | 原失败仍需处理 |
| `ignored` | 失败被忽略 | 确认是否形成错误成功 |

## 4. SSH 排障

顺序：

1. `ansible-inventory --host` 确认地址、用户、端口和 Proxy。
2. 从同一控制/执行节点使用等价 `ssh -vvv` 测试。
3. 检查 DNS、路由、安全组、防火墙和跳板机。
4. 核对 Host Key 变化是否为合法重装，不要直接删除所有 Known Hosts。
5. 检查密钥权限、Agent 和服务端 `authorized_keys`。
6. 再使用 Ansible `-vvvv` 对比实际 SSH 参数。

## 5. Python 与临时目录

典型现象：Interpreter 未找到、模块 Syntax Error、Permission denied、Exec format。检查：

- `ansible_python_interpreter` 最终值。
- 目标 Python 版本与模块要求。
- `/tmp`/`remote_tmp` 权限、空间和 `noexec`。
- SELinux/AppArmor 拒绝日志。
- 目标架构和原生 Python 包。
- Become 前后使用的环境和用户目录。

Bootstrap 可临时使用 `raw` 安装 Python，完成后立即回到普通模块。

## 6. Become

先在目标主机以相同登录用户执行：

```bash
sudo -l
sudo -n true
```

`sudo -n true` 失败可能表示需要密码或命令不允许。检查 `requiretty`、环境清理、目标用户 Shell 和 sudoers Include 顺序。不要通过授予 `NOPASSWD: ALL` 快速消除错误。

## 7. 模块与业务故障

模块错误先查：

```bash
ansible-doc <fqcn>
ansible-doc -t module <fqcn>
```

确认参数是否属于当前 Collection 版本、返回字段是否存在、目标 Python SDK 是否安装在正确位置。API 模块常在控制端执行，因此 SDK 应进入 EE，而不是目标节点。

Task 成功但业务失败时检查服务日志、配置加载版本、端口、依赖、LB 数据面和真实请求。不要只看 `systemctl is-active`。

## 8. `-vvvv` 与保留远端文件

详细模式可显示插件选择、SSH 参数、解释器发现和模块临时路径。必要时可在隔离环境保留远端模块文件进行分析，但其中可能含参数和 Secret，排障后安全清理。禁止把详细日志未经脱敏发布。

## 9. 可观测指标

| 指标 | 维度 |
| --- | --- |
| 作业成功率/持续时间 | Template、Inventory、EE、版本 |
| Task 延迟和失败 | Role、Task、模块、错误类别 |
| 主机 Unreachable | 区域、跳板机、连接类型 |
| Changed 比例 | Role、版本、环境 |
| Fork/队列/Pending | 执行节点和 Instance Group |
| Retry/429 | 外部 API 和模块 |
| Canary 停止次数 | 发布版本和失败门禁 |

主机名、用户和参数可能是敏感标签；指标维度还要控制基数。

## 10. 结构化事件与审计

事件至少包含：

```text
job_id / change_id
git_commit / ee_digest / collection_versions
inventory_id / host_id
play/task/role/action
started/ended/duration
status / changed / error_class
delegated_host / batch
```

不保存 Secret、完整模块参数和敏感 Diff。审计回答“谁授权、用什么版本、对哪些目标、产生什么结果”，而不是只保存终端输出。

## 11. Runbook

```text
发现失败
→ 停止后续批次/并发作业
→ 保持服务容量
→ 保存控制端和目标端证据
→ 按分层模型定位
→ 判断已变更/未变更/未知主机
→ 修复根因或执行已批准恢复
→ 明确 --limit 重跑
→ 独立业务验收
→ 复盘并补测试/门禁
```

## 12. 常见场景

| 症状 | 首要判断 |
| --- | --- |
| 全部 Unreachable | 控制节点网络、共享 Credential、跳板机 |
| 单区域失败 | 路由、区域跳板、动态 Inventory |
| 只有 Become 任务失败 | sudoers、密码、TTY、目标用户 |
| 每次都 Changed | 非确定模板、Command、权限/时间戳漂移 |
| 本地成功 AWX 失败 | EE、Credential、工作目录、网络 |
| 批次中断后状态不明 | 每主机任务事件与目标实际状态 |
| 模块参数突然无效 | Collection/ansible-core 版本漂移 |

## 13. 掌握标准

- [ ] 能在十分钟内判断失败层级。
- [ ] Unreachable、Failed 和业务失败分开统计。
- [ ] 详细日志和 Artifact 有脱敏与访问控制。
- [ ] 中断后建立每主机状态，不盲目全量重跑。
- [ ] 复盘结果转化为测试、Assert 或发布门禁。
