# Packer 性能、缓存、升级与故障排查

Packer 构建横跨 Runner、Plugin、云 API、网络、Guest OS、软件仓库和镜像服务。“构建慢”不是一个根因，必须先定位耗时属于哪个阶段。

## 1. 保存最小证据集

```bash
packer version
packer plugins installed
packer plugins required .
packer inspect .
```

同时记录：

- Build ID、任务 URL、Git Commit；
- Packer/Plugin 精确版本和 Hash；
- Source/Builder 名称、账号、区域、实例规格；
- Base Image ID、目标 Artifact 名称；
- 各阶段开始/结束时间；
- 临时实例、磁盘、网卡、安全组和快照 ID；
- 错误原文和云审计事件。

日志可能含 Secret，不能直接发到公开 Issue。

## 2. 按阶段定位

| 阶段 | 主要证据 | 常见根因 |
| --- | --- | --- |
| Init | Registry/Release 请求、Plugin 目录 | DNS、代理、TLS、来源变化、版本约束 |
| Builder Create | 云审计、配额、临时资源 | IAM、区域容量、Base ID、网络 |
| Guest Boot | 串口、Console、Cloud-init | Kernel、固件、磁盘驱动、首次启动 |
| Communicator | 路由、安全组、SSH/WinRM 日志 | 用户、Key、代理、Host Key、服务未就绪 |
| Provisioner | Script/Ansible/包管理日志 | 包锁、仓库、退出码、重启、Secret |
| Artifact | 镜像/快照事件 | KMS、命名冲突、快照时间、权限 |
| Post-process | Post-processor 输出 | 链顺序、复制、Manifest、输入被删 |
| Cleanup | 资源列表与审计 | 进程终止、删除权限、依赖仍附着 |

## 3. Init 故障

官方 Plugin 分发来源发生过变化，旧 Packer 或只允许 GitHub 的企业代理可能无法获取新版官方 Plugin。检查：

```text
DNS/TLS/Proxy
→ Packer Core 版本是否支持当前官方来源
→ required_plugins Source/Version
→ 当前 OS/Architecture 是否有构建
→ PACKER_PLUGIN_PATH 权限
→ 临时目录可写/可执行
```

不要通过关闭证书校验或从随机镜像下载二进制解决。内部制品库应保存官方校验和与来源元数据。

## 4. Builder 创建失败

错误通常来自：

- Base Image 不存在、无共享权限或架构不匹配；
- 实例/CPU/公网 IP/磁盘配额；
- 子网无可用地址；
- KMS Key Policy；
- Spot/可抢占容量；
- Security Group、IAM PassRole；
- 名称冲突和残留镜像。

先在云审计中查真实 API 和错误码，而不是修改 Packer 超时。重试无法解决确定性的权限和配额问题。

## 5. Communicator 超时

排障链路：

```text
实例是否真正启动
→ 串口/Console 是否有 Kernel/文件系统错误
→ NIC、路由、NACL/Security Group
→ Runner 到 Guest 路径
→ SSH/WinRM 进程和监听
→ 用户、Key/Password、Host Key
→ Cloud-init/自动更新是否仍占用启动
```

端口 22 打开不等于目标用户已可用。使用平台 Console 和 Boot Diagnostics 区分 Guest 未启动与网络不可达。

## 6. Provisioner 卡住或失败

优先检查：

- 包管理器是否被 Cloud-init/自动更新持锁；
- DNS/代理/仓库证书；
- 交互式命令等待输入；
- Shell 管道是否吞掉退出码；
- Ansible Handler/Reboot 是否使连接预期中断；
- 磁盘空间、inode 和内存；
- 下载是否没有超时；
- Script 是否依赖生产 DNS/Secret。

给每个外部调用设置合理超时和有限重试；失败时输出阶段化证据，不要把所有脚本合成一个黑盒。

## 7. 镜像/快照耗时

生成 Artifact 常受系统盘容量、已写块、零块、加密和云快照服务影响。增大磁盘到 500 GB 即使只用 10 GB，也可能改变复制与快照行为。

优化：清理缓存/临时数据、控制基础磁盘大小、使用合适文件系统和 Trim/零块策略，并依据平台实测。不要用破坏文件系统安全的“压缩技巧”。

镜像服务后台 Copy 可能在 Packer 返回后仍有区域任务，发布前等待全部目标 Ready。

## 8. 缓存设计

适合缓存：

- 固定 Hash 的软件包/安装介质；
- 已校验的 Plugin；
- 受控包仓库快照；
- 大型驱动/Runtime 安装包。

缓存 Key 包含版本、架构、OS 和 Hash。缓存命中仍校验内容；缓存失效时应回源可信仓库而不是使用过期未知文件。

不要缓存：短期 Secret、Guest 机器身份、动态注册证书和未经校验的 `latest`。

## 9. 性能分解

```text
总时间 = Init
       + 临时资源创建
       + Guest 启动/Communicator
       + Provisioner
       + Reboot
       + Snapshot/Image
       + Copy/Post-process
       + Cleanup
```

先记录阶段分位数再优化。常见大头是软件包下载、Windows Update、内核/驱动重启和跨区域复制，而不是 HCL 解析。

将稳定、大型依赖放入更底层镜像可以加速，但会增加基础镜像更新耦合。建立分层镜像时必须记录父子谱系和漏洞重建触发。

## 10. 并行构建

不同架构/区域并行可以缩短流水线，但共享限制包括：

- 云 API 与实例配额；
- NAT/代理带宽；
- 包仓库并发；
- vCenter/Datastore；
- 镜像名称和 Manifest 文件；
- KMS/扫描服务限流。

并行任务应使用唯一名称和独立 Manifest，最终由汇总阶段合并。失败后不要让所有任务同时无退避重试。

## 11. 孤儿资源处理

任务终止后按 Build ID 查询临时实例、磁盘、网卡、快照、安全组和 Key Pair：

```text
确认任务已终止且不会恢复
→ 记录对象和依赖
→ 删除临时 Compute
→ 等待 Detach
→ 删除磁盘/网卡/安全组
→ 对候选快照/镜像按状态处理
→ 保存审计记录
```

自动清理器应有 Dry-run、年龄阈值和 Owner 标签，不对模糊名称执行递归删除。

## 12. 升级 Packer 与 Plugin

```text
阅读 Core 与 Plugin Changelog
→ 固定单一升级层
→ 在相同 Base ID 上构建
→ 对比 Manifest、包清单和镜像配置
→ 启动/功能/安全/性能测试
→ 金丝雀晋级
```

不要同一批同时升级 Packer、Builder Plugin、基础镜像、Ansible 和 OS 包。否则产物变化无法归因。

升级后检查：Plugin 下载来源、HCL Schema、Communicator、默认磁盘、标签、加密、Artifact ID 和清理行为。

## 14. 练习与答案

**问题：使用更大 Builder 实例后构建更快，能否说明 CPU 是瓶颈？**

答案：不能直接说明。更大规格可能同时提高网络、磁盘和突发额度。应分阶段采集 CPU、下载、磁盘和等待时间，并在相同网络/仓库条件对比。

**问题：Packer 退出后云中没有实例，是否代表清理完整？**

答案：不一定。还可能残留磁盘、快照、网卡、安全组、Key Pair、公网 IP 和不可用镜像，应按 Build ID 全量盘点。
