# Packer 镜像测试、版本、复制、回退与晋级

镜像发布不是“Build 成功后把 AMI ID 发给 Terraform”。镜像必须经过启动、功能、安全、性能和升级验证，并以同一 Artifact 晋级到生产。

## 1. 测试金字塔

```text
HCL fmt / init / validate / inspect
→ Provisioner 单元与幂等测试
→ Builder 完整构建
→ 镜像启动 Smoke Test
→ OS/服务/安全/Secret 扫描
→ 真实规格与负载测试
→ Terraform 金丝雀节点池
→ 生产分批替换
```

每层都不能替代下一层。Packer Validate 不调用完整云 API，镜像内 Chroot 扫描也不能证明 Cloud-init 和网络可用。

## 2. 启动测试

从候选 Image ID 创建全新实例，验证：

- Kernel 和 initramfs 正常；
- UEFI/BIOS、磁盘和网卡识别；
- 根盘自动扩容；
- Cloud-init 完成且无错误；
- SSH/WinRM/云 Agent 可用；
- DNS、NTP、证书与包仓库；
- 重启、关机和再次启动；
- Machine ID、Host Key、Agent ID 唯一。

不能直接在 Packer 临时 Builder 上做完测试，因为它已经经历了 Provisioner，无法模拟克隆后的第一次启动。

## 3. 功能与服务测试

检查包版本和服务只是起点：

```bash
uname -r
systemctl --failed
cloud-init status --long
```

还要执行真实行为，例如启动容器、挂载磁盘、拉取镜像、发送监控指标、执行安全 Agent 心跳。GPU/NPU 节点需在真实硬件验证驱动、Runtime、设备插件和通信库。

## 4. 安全测试

- Secret/私钥/Token/历史扫描；
- 默认账号、空密码、sudo 与 SSH；
- 文件权限、SELinux/AppArmor、防火墙；
- SBOM 和 CVE；
- 开放端口与服务；
- 构建用户、临时仓库配置和日志残留；
- 合规基线及有到期日的例外。

测试应从新实例运行，而不只扫描静态文件系统，因为部分风险由首次启动生成。

## 5. 性能基线

镜像变化可能影响启动时间、CPU、磁盘、网络和应用性能。记录：

- 从创建到 SSH/Ready 的时间；
- Cloud-init 各阶段；
- 基础空闲 CPU/RSS/启动服务数；
- 磁盘和网络基线；
- 容器启动/模型加载等关键路径；
- 与上一生产镜像的差值。

性能回归应控制实例类型、区域、磁盘和测试负载，避免把云噪声当镜像变化。

## 6. 版本和命名

人类可读名称：

```text
linux-rocky9-amd64-20261014.1
```

真正消费使用不可变 Image ID/Digest。版本元数据至少记录：

- 基础镜像 ID/Digest；
- Git Commit；
- Packer/Plugin 精确版本；
- Provisioner/Role/Collection 版本；
- OS 包清单/SBOM；
- Build ID 和时间；
- 测试与扫描报告；
- 复制后的各区域/账号 ID。

名称可重复或被误选，不能作为唯一身份。

## 7. Candidate、Staging 与 Production Channel

Channel 是“当前允许消费哪个不可变版本”的指针：

```text
candidate → 通过自动测试
staging   → 通过集成/容量验证
production → 通过审批和金丝雀
```

可以使用 HCP Packer Registry、内部镜像目录或受控配置仓库实现。Channel 更新必须审计且可原子回退；下游要解析到不可变 ID并把结果记录进 Plan。

若使用 HCP Packer，版本/Artifact 数据源与旧 Iteration/Image 数据源的弃用状态需要按当前文档选择，避免新系统继续依赖已弃用接口。

## 8. 跨区域与跨账号复制

```text
源 Artifact
→ 复制 Snapshot/Image
→ 目标区域生成新 Image ID
→ 验证 KMS Key、权限、标签和启动
→ 建立源 ID ↔ 目标 ID 关系
```

复制后的 ID 不同，但应指向同一内容/版本谱系。必须确认：

- Snapshot 都已完成；
- KMS Key 在目标账号可用；
- 启动权限和 Service-linked Role；
- 区域实例类型/Architecture 可用；
- 标签、SBOM 和证明未丢失；
- 目标区域实际启动测试通过。

## 9. 同一产物晋级

不要在 test、staging、production 各自重新构建“同版本”。仓库、时间、Plugin 或基础镜像变化会使内容不同。

正确路径是构建一次候选 Artifact，经过测试后复制/共享并更新 Channel。环境特有配置在实例启动时注入。

## 10. 回退模型

不可变镜像的回退通常是：

```text
Production Channel 指回上一已验证版本
→ Terraform/节点池创建旧镜像新实例
→ 健康检查
→ 迁移流量/工作负载
→ 下线问题实例
```

不是把运行中系统盘原地降级。数据库 Schema、控制面版本和数据格式必须保持向后兼容，否则旧镜像能启动但应用不能工作。

## 11. 生命周期与删除保护

不能只按“创建超过 90 天”删除镜像。清理前查：

- Launch Template/Instance Template；
- Auto Scaling/节点池；
- Terraform State 和生产变量；
- 灾备区域；
- 当前和上一 Production Channel；
- 运行实例和快照依赖；
- 合规保留/事故证据。

先标记 Deprecated/Disabled，经过观察期再删除。镜像和底层 Snapshot 的删除顺序依平台而异。

## 12. 发布验收

```text
候选 Image ID 唯一
→ Manifest/SBOM/测试证据完整
→ 所有目标区域复制并启动验证
→ Terraform Plan 使用预期 ID
→ 金丝雀实例/节点池健康
→ SLO 与性能观察
→ 更新 Production Channel
→ 保留上一版本回退
```

## 13. 练习与答案

**问题：复制到目标区域显示 Completed，为什么仍要启动测试？**

答案：复制成功只证明平台生成了目标镜像/快照，不证明 KMS 权限、实例规格、网络、Cloud-init 和驱动可用。

**问题：镜像已经签名，为什么仍不能直接晋级？**

答案：签名证明来源和完整性，不证明启动、功能、安全策略和性能满足要求。仍需完整测试与审批。
