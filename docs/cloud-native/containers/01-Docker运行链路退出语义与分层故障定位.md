# Docker 运行链路退出语义与分层故障定位

“容器起不来”至少可能指客户端连不上、镜像未取得、容器未创建、进程无法启动、启动后退出或应用不健康。先定位最早失败边界，才能选择证据与最小动作，而不是反复重装 Docker 或提升权限。

命令语法见[Docker 命令参考](../kubernetes/commands/14-docker命令详解.md)。本篇面向 Docker Engine 的 Linux 容器模型；Docker Desktop 内部虚拟机、Rootless 和其他平台的设备及网络路径要分别核对。

## 1. 从请求到业务有多层状态

```text
CLI 与目标 Context
→ Docker API 与 Daemon
→ 镜像内容、平台及解包
→ 容器配置、挂载、网络和 OCI 规格
→ Runtime 创建隔离环境并启动进程
→ 应用依赖与业务就绪
```

这是职责链，不是承诺所有版本内部函数顺序相同。镜像层存在不证明解包和挂载成功；容器对象创建不证明进程已执行；进程存活不证明服务可用。

定位前先确认目标 Daemon。Context、环境变量或连接配置可能把 CLI 指向远端；本机看不到文件或设备，未必就是目标 Daemon 的事实。连接失败的依据见[Daemon 排障](https://docs.docker.com/engine/daemon/troubleshoot/)。

## 2. 创建配置与运行时事实分开

容器配置包括入口、参数、环境、用户、工作目录、挂载、网络、安全与资源约束。OCI Runtime 依据相应规格建立执行环境，最终仍是宿主内核上的进程，不会得到镜像自带的独立内核。

同一镜像在两台 Host 行为不同，可能来自内核、架构、设备、挂载内容、权限或外部服务；镜像 Digest 一致并不能排除这些因素。错误架构、缺失动态加载器和文件权限也发生在不同位置，不应统一归为“程序路径写错”。

GPU 又增加一条运行时契约：宿主驱动、设备分配、OCI 注入和用户库都需要正确。宿主 `nvidia-smi` 正常，不代表容器获得了设备；容器里看到库，也不证明能执行 CUDA。见[GPU 设备使用链路](../../gpu/cluster/device-management/03-Pod如何使用上GPU：Device%20Plugin与Container%20Toolkit.md)。

## 3. Exit Code 不能单独决定根因

Docker 对运行请求的 125、126、127 等状态有特定含义；应用自己的退出状态则要结合命令和执行层判断。[运行与退出说明](https://docs.docker.com/engine/containers/run/)区分了这些情况。

常见的 137 可能表示 SIGKILL，但不能只凭它断言发生 OOM：手工强杀、超时升级为强制终止等也可能产生该结果。应同时查看容器状态中的 OOM 证据、内核与 cgroup 事件、停止时间线和操作者动作。

应用退出 0 也不代表应长期运行的服务正常。若入口启动后台服务后自己退出，容器主进程的生命周期就可能与预期不一致。应修正进程和监督模型，而不是添加无限空循环掩盖问题。

## 4. 内存限制与 GPU 显存不是同一预算

容器内存限制主要约束相应主机内存；GPU 显存的分配与隔离是另一层机制。主机内存不足、cgroup OOM 和 CUDA 显存分配失败需要不同证据。资源限制语义见[Docker 资源约束](https://docs.docker.com/engine/containers/resource_constraints/)。

教学例子：应用匿名内存 3 GiB，共享内存和其他被计费使用 1 GiB，限制 4 GiB。此时不能再假设还有 1 GiB 余量；真实记账还受共享页、缓存与内核配置影响，应读取有效 cgroup 指标。GPU 空闲显存再多也不能解决该主机预算问题。

增加限制可能缓解症状，却不能解释内存泄漏、并发和数据预取是否合理。先识别增长来源，再决定配置调整。

## 5. 日志不是全部输出与状态

`docker logs` 依赖日志驱动和应用输出方式；应用写入内部文件而非标准输出时，空日志不能证明没有错误。[日志说明](https://docs.docker.com/engine/logging/)给出了这个边界。

重启会改变原始现场，删除容器还可能失去可写层和部分诊断上下文。故障发生后先保存状态、事件、目标身份及必要日志，再决定是否复现；检查环境变量和日志中的秘密，不公开原始凭据。

健康检查失败与主进程退出也不同。独立容器的健康状态不会天然具有 Kubernetes 控制器的全部重启、摘流和重调度语义，必须查实际监督者与策略。

## 6. 网络和挂载按实际路径判断

端口发布只表达 Host 到容器的转发配置，不保证应用监听正确地址，更不保证云安全组、Host 防火墙和外部 DNS 正确。容器内访问自身环回地址成功，不能证明外部用户能访问。

挂载则可能遮住镜像中的原有目录。镜像内文件明明存在，运行时却不见，先比较实际 Mount，而不是重复构建。权限还涉及数值 UID/GID、Rootless 映射和文件系统策略；`--privileged` 不能被当作通用修复。

空间不足也要区分镜像层、容器可写层、日志、构建缓存和卷。Prune 不理解业务未来需要什么，不能作为不经归因的清理动作。

## 7. 用反例选择最小动作

| 观察 | 先调查 | 不应直接做 |
| --- | --- | --- |
| 连接 Daemon 失败 | Context、Socket、服务与认证 | 删除所有镜像 |
| 镜像取得后无法启动进程 | 架构、入口、加载器、权限 | 重配所有网络 |
| 137 且无 OOM 证据 | 停止与信号时间线 | 断言显存不足 |
| 运行但端口不通 | 监听、发布和完整网络路径 | 赋予全部宿主权限 |
| Host GPU 正常而容器失败 | 分配、注入、库与进程 | 重装全部物理节点 |

## 8. 掌握检查

**镜像相同是否能排除 Host 差异？** 不能，它主要固定用户态内容。

**137 是否必然 OOM？** 不是，需要结合信号、内核及 cgroup 证据。

**空日志和 Running 是否足以证明健康？** 不足，需确认日志路径、依赖和业务结果。
