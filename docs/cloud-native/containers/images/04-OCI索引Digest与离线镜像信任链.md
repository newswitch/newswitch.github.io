# OCI 索引、Digest 与离线镜像信任链

固定一个镜像 Digest，可以限定内容，却不能单独证明它来自可信构建者。离线复制镜像层，也不保证索引、签名和来源证明都已保留。需要把内容图与信任关系放在一起理解。

前置阅读 [NGC 身份与镜像引用](./02-NGC镜像身份权限与制品生命周期.md)。这里解释通用 OCI 原理，NGC、Harbor 或其他 Registry 仍各有自己的权限与分发行为。

## 1. 镜像是一张内容图，不是一个 tar 文件名

```text
Tag → Index Digest
      ├─ linux/amd64 → Manifest A → Config A + Layers
      └─ linux/arm64 → Manifest B → Config B + Layers
```

Index 汇总具体平台的 Manifest，Manifest 引用配置和层；部分镜像直接引用单平台 Manifest，不经过 Index。父对象保存子对象的内容描述，形成内容寻址关系。定义见 [OCI Index](https://github.com/opencontainers/image-spec/blob/main/image-index.md) 与 [OCI Manifest](https://github.com/opencontainers/image-spec/blob/main/manifest.md)。

因此顶层 Index Digest、选中的平台 Manifest Digest、Config Digest 和本地运行时显示的 Image ID 不应混为一谈。排查“同版本为什么不同”时，先确定比较的是哪一层。

## 2. Digest 验证字节，不替代来源授权

Digest 根据内容计算。文件被改动后，应当不能继续匹配原来的摘要；但攻击者完全可以给恶意内容计算一个新的正确摘要。下载内容与摘要一致，证明的是完整性，不是组织是否允许使用它。

Tag 还可被重新指向。只记录 `release`，下一次拉取可能得到不同内容；固定顶层 Digest 后，多架构节点仍可能选择不同的平台子 Manifest。这不是漂移，而是被同一个 Index 明确引用的不同内容。

GPU 兼容性属于另一层：平台 Manifest 指向 AMD64，不表示对应 CUDA、驱动和 GPU 架构都已兼容。内容身份和运行契约都需要验证。

## 3. 删除一个平台，为什么顶层身份也会变化

假设 Index I 引用 A、B 两个平台 Manifest。离线转存时仅保留 A，并重新生成单平台 Index J。即使 A 的字节完全没有改变，J 的内容也与 I 不同，因此不能继续把 J 声称为 I。

如果签名绑定的是 I，就不能仅因为 A 来自 I，自动把对 I 的信任当成对任意新 J 的签名。策略需要明确验证顶层对象、平台对象以及两者引用关系中的哪些部分。

相同道理适用于改 annotations、重新序列化或转换清单格式：逻辑上看似相同的对象，其字节身份可能已经改变。迁移验收应检查工具实际保留了什么，而不只比较可读名称。

## 4. 签名验证还需要允许的身份

签名校验至少要回答：签名是否有效，绑定哪个 Digest，验证使用哪个受信任公钥或证书链，以及签名者是否符合组织策略。Keyless 验证还需要约束身份与 OIDC issuer，不能只检查“证书存在”。见 [Cosign 签名验证](https://docs.sigstore.dev/cosign/verifying/verify/)。

例如两个构建流水线都能产生数学上有效的签名，但只有指定发布流程被允许进入生产。若准入策略只检查“有签名”，仍会接受不应信任的签名者。

签名也不承诺内容无漏洞。来源证明说明构建来源与过程，SBOM 描述组成，漏洞扫描则依赖扫描规则和数据库时间。它们回答不同问题，不能互相代替。

## 5. 关联制品不会因复制层而必然一起迁移

OCI 使用 subject、referrers 等机制关联其他制品；实际 Registry、签名工具及旧式兼容存储方式会影响发现与复制。内容图的下载与反向关联查询不是同一个动作，参见 [OCI Distribution 规范](https://github.com/opencontainers/distribution-spec/blob/main/spec.md)。

只复制镜像的 Config 和 Layers，可能留下签名、SBOM 或证明材料。即使 Registry 支持保存它们，也要确认复制工具是否请求了关联对象、是否保留引用，以及接收端验证工具能否找到。

因此离线清单应分别记录镜像根、实际平台集合、依赖对象、验证材料与信任策略。制品存在但无法发现，和制品根本没有复制，是两种不同问题。

## 6. 离线验证必须提前准备信任材料

没有网络时，验证方不能临时依赖在线获取全部证书、日志证据或策略。应按所用签名方案准备受信任根、签名或 bundle、身份约束及所需时间/透明度证据，再验证具体工具支持的离线模式。

不能为了解决离线报错就跳过身份、摘要绑定或日志相关检查。哪些证据可离线验证、哪些新鲜度要求需要另行满足，应由明确策略决定。把验证器、可信根和镜像都从同一个未验证包里取出，还会形成自证信任的循环。

受信任根应通过独立可信渠道引入；同一个包内附带的公钥可以作为材料，但不能仅凭它附在包里就被信任。

## 7. 用闭包理解完整离线交付

设部署根引用主镜像、init 镜像和 sidecar；主镜像又有两个平台版本。完整交付取决于目标平台策略以及全部运行依赖，而不是只看 Deployment 的第一个容器。

教学例子：两个平台各有 2 GiB 的独有层，共享层 1 GiB。保存完整多架构内容，在忽略元数据时共需 5 GiB；只保存其中一个平台则约 3 GiB。后者更小，但不再具备两个平台的交付能力，也不能沿用未核对的顶层身份。

完整性验证后还要进行目标环境的启动与功能验证；签名有效不能代替 CUDA 或目标应用验收。实践入口见[离线分发与运行验证](./03-NGC拉取故障离线分发与运行验证.md)。
