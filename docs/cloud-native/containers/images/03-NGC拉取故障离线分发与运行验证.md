# NGC 拉取故障离线分发与运行验证

镜像部署经历网络访问、认证授权、清单选择、层下载、校验解包、容器创建和应用启动。把它们统称为“NGC 不通”，会把无关的恢复动作混在一起。

## 1. 失败阶段

| 现象 | 优先检查 |
| --- | --- |
| DNS/TLS/连接错误 | 节点网络、代理、信任链、时钟 |
| 拒绝访问 | 实际拉取身份、作用域、过期与仓库授权 |
| 找不到清单或 Tag | 完整引用、路径和已发布版本 |
| 找不到匹配平台 | AMD64/ARM64 与多架构索引 |
| 下载或解包失败 | 网络中断、磁盘/inode、运行时存储 |
| 已启动但 CUDA 失败 | 驱动、库、设备注入、权限与应用 |

HTTP 状态只能作为线索，某些服务还会出于安全原因模糊不存在与未授权；不要从单个状态码直接推出唯一根因。

## 2. Kubernetes 的额外层

先读 Pod 事件确认是镜像拉取还是运行失败，再到对应节点核对 CRI。Pod Spec 中的镜像引用与节点实际缓存必须对应。Docker 能运行不代表 Kubernetes 使用的 containerd Namespace 已有该镜像。

如果只在新节点失败，优先比较凭据、代理、CA、架构、磁盘和预热差异。缓存命中可能掩盖权限失效，不能用一台旧节点成功证明全部节点状态一致。

## 3. 离线制品清单

离线包应包含实际平台镜像、依赖的辅助镜像、Chart、配置、Digest 与版本记录，以及完整性校验。DOCA 或平台服务还可能需要 Sandbox 镜像和服务脚本；只导出主镜像不是完整部署包。

转存仓库时确认多架构信息、签名/扫描记录和引用规则是否保留。导入后先查询目标运行时实际可见清单，再在独立环境执行功能验证。不要把应用运行权限与镜像分发权限合成一个无限权限凭据。

### 3.1 复制内容与复制信任关系

离线包的闭包至少有两部分：运行时需要的镜像与依赖，以及策略要求的签名、身份和来源证据。复制工具可能只保存所选平台的 Manifest 与层，没有保存原始多架构 Index 或关联制品。

例如顶层 Index 引用 AMD64 与 ARM64，导出时只保留 ARM64，再重新生成清单，平台内容可能仍正确，但顶层 Digest 已变化。不能继续拿旧顶层签名为新清单背书；应明确验证的是哪一层，详见 [OCI 索引、Digest 与离线信任链](./04-OCI索引Digest与离线镜像信任链.md)。

| 验收对象 | 应保留的事实 | 单独不能证明什么 |
| --- | --- | --- |
| 目标平台内容 | 实际平台 Manifest、Config、Layer 身份 | 来源是被允许的发布者 |
| 根清单 | 原 Index 是否保留、是否重建或裁剪 | 全部辅助镜像已交付 |
| 关联证据 | 签名、证明、SBOM 及其绑定对象 | 目标运行时一定支持发现它们 |
| 离线策略 | 独立引入的可信根、身份限制和验证材料 | GPU 应用运行契约满足 |

测试离线可恢复性时，应在受控的无缓存环境验证，不靠清空生产缓存或临时跳过签名检查制造“可用”。

## 4. 批量拉取的时间模型

教学条件：20 节点各下载 10 GiB，未缓存、无共享去重，共需约 200 GiB。分发源有效聚合 5 GiB/s 时，纯传输下界约 40 秒；解压、写盘和校验还会增加时间。单节点测速不能直接乘以节点数作为集群吞吐。

控制并发、按层缓存、预热与失败重试可以减少突发，但必须记录版本和命中口径。镜像拉取策略、缓存存在和 Tag 漂移共同决定实际内容，生产应使用可追溯引用。

## 5. 运行成功的分级证据

镜像可拉取、进程可启动、管理工具可访问 GPU、CUDA 计算正确、真实应用满足目标，是逐级不同的证据。没有 GPU 硬件时可以验证镜像清单和配置，但不能声称已验证 CUDA 或通信性能。
