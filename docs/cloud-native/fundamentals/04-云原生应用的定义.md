# 云原生应用的定义

云原生应用不是“放进容器的应用”，也不由某一种 YAML 或平台定义。更有用的工程定义是：应用从设计阶段就适应自动化基础设施、动态环境和持续交付，能够以声明式方式交付，以可观测证据运行，并在故障和变化中受控演进。

## 1. 从三个维度判断 {/* #从三个维度判断 */}

### 1.1 可交付 {/* #可交付 */}

- 构建结果不可变、可追溯，镜像和依赖有版本及供应链证据；
- 环境差异通过配置和 Secret 注入，而不是重新改代码；
- 部署声明可审查、可重复执行、可回滚；
- 数据库变更、配置变更和应用版本有明确兼容窗口。

### 1.2 可运行 {/* #可运行 */}

- 提供启动、存活、就绪和优雅终止语义；
- 暴露指标、日志、追踪和业务 SLI；
- 明确 CPU、内存、网络、存储和外部依赖边界；
- 实例可以被替换，状态被放在有一致性、备份和恢复设计的系统中。

### 1.3 可演进 {/* #可演进 */}

- 支持灰度、回滚、横向扩展与故障隔离；
- API、事件和数据 Schema 有兼容策略；
- 平台能力通过稳定契约提供，而不是让每个团队直接拼接底层设施；
- 变更结果由自动化测试和运行证据验证。

## 2. 应用、平台和基础设施如何分工 {/* #应用平台和基础设施如何分工 */}

```text
应用开发者：业务代码、API、依赖、资源需求、健康与可观测契约
平台团队：交付模板、策略、身份、网络、弹性、观测和自助接口
基础设施团队：计算、网络、存储、集群、容量与故障域
```

边界不是组织墙。应用声明“需要什么”，平台把意图翻译成 Kubernetes、云服务或虚拟机资源，基础设施保证底层能力。SLO、成本、安全和变更证据贯穿三层。

## 3. OAM 是一种应用建模方法 {/* #oam-是一种应用建模方法 */}

[Open Application Model（OAM）](https://github.com/oam-dev/spec)试图用高层抽象分离开发与运维关注点。其核心思想仍有学习价值：

- `Component` 表达应用组件；
- `Trait` 为组件附加扩缩、路由等运维行为；
- `Application`/配置把组件和运维能力组合为一次交付；
- 平台实现负责把高层意图转换成底层资源。

但 OAM 不是所有云原生应用的唯一标准，也不应代替 Kubernetes 原生对象、Operator、GitOps 或内部平台 API。实践中可将它与以下模型比较：

| 模型 | 主要关注点 | 适合解决的问题 |
|---|---|---|
| Kubernetes Workload/Service | 基础编排对象 | 通用运行与网络抽象 |
| Helm/Kustomize | 配置与打包 | 多环境资源生成 |
| Operator/CRD | 领域状态机 | 有复杂生命周期的服务 |
| GitOps | 期望状态与审计 | 持续交付和漂移收敛 |
| OAM/KubeVela | 应用级抽象 | 开发与平台关注点分离 |

选择模型时关注团队是否能稳定维护契约、调试转换链路和完成回滚，而不是只比较 YAML 是否更短。

## 4. 一个最小应用契约 {/* #一个最小应用契约 */}

```yaml
application:
  name: orders
  version: 2026.08.1
  image: registry.example.com/orders@sha256:<digest>
  ports: [8080]
  resources:
    requests: {cpu: 500m, memory: 512Mi}
  health:
    readiness: /readyz
    liveness: /livez
  dependencies:
    - name: mysql
      contract: orders-db-v3
  slo:
    availability: 99.9%
    p95_latency_ms: 200
```

这不是某个真实 API，而是审查清单：如果镜像、资源、健康、依赖和 SLO 都无法说清楚，即使生成了合法 Deployment，也还没有形成可靠的云原生应用。

## 5. 常见误区 {/* #常见误区 */}

- **用了 Kubernetes 就是云原生**：平台只能提供机制，应用仍需具备健康、终止、配置和观测语义。
- **无状态等于没有数据**：无状态实例仍依赖外部状态，必须设计连接、幂等和恢复。
- **微服务越多越云原生**：服务拆分会增加网络和数据一致性成本，应由领域边界驱动。
- **声明式等于绝对安全**：错误期望状态也会被自动放大，仍需准入、灰度和回滚。

## 6. 学习完成标准 {/* #学习完成标准 */}

能够从可交付、可运行、可演进三个维度评审一个应用；能说明应用、平台、基础设施团队的契约；能把 OAM 放在应用模型体系中，而不是把它等同于云原生定义。
