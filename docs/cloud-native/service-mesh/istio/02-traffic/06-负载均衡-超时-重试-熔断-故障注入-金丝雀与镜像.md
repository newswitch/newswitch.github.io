# 负载均衡、超时、重试、熔断、故障注入、金丝雀与流量镜像

流量治理不是开启越多功能越可靠。代理重试和应用重试叠加会放大请求，错误熔断可能把剩余实例压垮；所有策略必须服从端到端时间与容量预算。

## 1. 时间预算

```text
客户端总Timeout
≥ 网关排队 + Istio路由
 + 每次尝试Timeout × 尝试次数
 + Retry Backoff
 + 应用处理和返回
```

上游 Timeout 应小于客户端截止时间，下游单次 Timeout 再小于上游。gRPC Deadline 应传播，避免客户端已放弃而服务继续占资源。

## 2. 重试边界

只对幂等或有请求 ID 去重的操作重试。明确 `retryOn`、次数、每次 Timeout 和预算；跨三层每层重试 3 次可能把一次请求放大到 27 次。

监控原始请求、Upstream Attempt、Retry、Overflow 和最终错误率。

## 3. 连接池与熔断

DestinationRule 可限制连接、Pending Request、并发 Request 和请求/连接数量。触发 Overflow 是保护动作，不应简单调大。Outlier Detection 根据连续错误等信号暂时驱逐异常 Endpoint，需限制最大驱逐比例并避免低流量误判。

## 4. 负载均衡

Round Robin、Least Request、Random、一致性 Hash 等适合不同场景。长连接会降低权重调整的即时性；有状态 Session 应优先外置状态，不把 Hash 当强一致粘性保证。

## 5. 金丝雀

```text
部署v2但权重0
→ 影子/内部Header验证
→ 1% → 5% → 25% → 50% → 100%
→ 每步比较请求数、错误、P99和业务指标
```

按权重路由的是请求而非一定等量用户。低流量样本不足时使用 Header/Cookie 定向；回滚只改路由不等于旧版本数据/Schema 兼容。

## 6. 镜像和故障注入

镜像流量不应影响主请求响应，但目标仍可能执行写副作用，必须使用只读/隔离环境并脱敏。故障注入用于验证超时、重试和告警，只在明确选择的测试流量范围启用。

## 7. 验收

压测正常基线，再分别注入 500、延迟和单 Endpoint 故障；记录尝试数、连接池、驱逐、P99 与下游负载。证明策略在失败时减少而非放大损害。
