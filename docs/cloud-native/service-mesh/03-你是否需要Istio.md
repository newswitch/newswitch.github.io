# 你是否需要 Istio？

Istio 主要治理服务之间的通信：把连接加密、服务身份、访问策略、流量路由和通信指标放到代理层统一实现。它是否值得引入，取决于这些能力能否解决当前系统的问题，以及增加的代理路径和运维成本是否可接受。

只有一个入口反向代理需求时，Ingress/Gateway 往往更直接；大量服务之间需要统一身份和策略时，才更能体现服务网格的价值。这里的区别是治理对象，不是“服务数量到某个数字就必须上 Istio”。

本文分别讨论 Sidecar 与 Ambient。二者并非同一条数据路径，协议、扩展、多集群和平台支持也应按实际安装版本核对，不能把某一模式的限制推及整个 Istio。

## 1. 前置评估清单 {/* #前置评估清单 */}

先画出一条实际调用链，再判断现有能力缺在哪里：

```text
外部客户端 → Gateway → 订单服务 → 库存服务
                              → 支付服务 → 外部支付接口
```

入口网关能够管理进入集群的请求，但不会因此自动治理订单到库存的调用。这里既有服务间的东西向流量，也有支付服务访问外部的出站流量，策略执行点需要分别设计。

| 问题 | 需要核对的技术条件 |
| --- | --- |
| 服务间是否需要统一加密与身份 | 证书签发、信任域、ServiceAccount 与授权模型 |
| 是否需要按请求灰度和观测 | 代理能否看到 HTTP/gRPC，是否具备相应七层执行点 |
| 是否已由 SDK 实现重试、熔断 | 网格接入后谁负责哪项行为，是否重复执行 |
| 是否承受得起代理成本 | 相同流量下的 CPU、内存、连接数、P99 与失败率 |
| 是否能够升级和排障 | 能否区分应用、代理、策略、证书、发现和底层网络问题 |

不能只比较接入前后的平均延迟。大报文、TLS 握手、长连接、流式响应和配置规模，都可能改变尾延迟与资源成本。

## 2. 应用透明性的挑战 {/* #应用透明性的挑战 */}

“不改业务代码也能代理连接”，不等于应用不需要配合。

重试必须有统一预算。假设应用一次逻辑调用最多尝试 3 次，每次到代理后代理又最多尝试 3 次，最坏可能放大成 9 次后端尝试；这里的次数包括首次发送，不是某个配置字段的默认值。后端变慢时，这种放大会进一步增加负载。即使两层都可重试，也应约束总时长、总尝试次数，并判断请求是否可能已产生副作用。[流量管理与重试](https://istio.io/latest/docs/concepts/traffic-management/#retries)

链路追踪也不能只靠代理。代理可以生成 Span，但应用收到请求后再调用其他服务时，仍需传播对应的 Trace Context，否则下游 Span 无法可靠关联到同一条 Trace。[Trace Context 传播要求](https://istio.io/latest/docs/tasks/observability/distributed-tracing/overview/#building-applications-to-support-trace-context-propagation)

同样，网格不知道“扣款请求重试是否安全”，也不能替应用修复未提交事务。通信治理与业务正确性需要协同，而不是互相替代。

## 3. Sidecar 与 Ambient 的部署边界 {/* #多环境支持的局限性 */}

两种模式都包含控制面，但数据面的部署粒度不同：

| 模式 | 主要数据路径 | 需要理解的代价 |
| --- | --- | --- |
| Sidecar | 应用流量经过工作负载旁的 Envoy | 代理资源通常按 Pod 配置，代理生命周期与 Pod 紧密关联 |
| Ambient 基础层 | 流量经过节点上的 ztunnel | 提供四层安全与遥测，不能仅凭这一层获得 HTTP 路由等七层能力 |
| Ambient 加 Waypoint | 需要七层处理的流量再经过相应 Waypoint | 增加七层代理容量与配置，需要确认流量确实经过该执行点 |

因此，“没有 Sidecar”不等于“没有代理”，也不等于“零开销”。比较两种模式时，应保持业务、策略和七层能力一致，而不是拿仅四层加密的路径与完整七层处理路径直接比性能。[数据面模式与能力](https://istio.io/latest/docs/overview/dataplane-modes/)

跨集群、跨网络和虚拟机还涉及服务发现、可达性、证书信任与故障域。Sidecar 和 Ambient 的支持进度并不完全一致；不能把一个 Kubernetes 单集群例子直接推广成所有混合环境的安装方案。

## 4. 协议支持的限制 {/* #协议支持的限制 */}

先区分“能转发字节”与“理解应用协议”。同一条 TCP 连接可以被四层代理转发，却未必能按业务方法或报文字段进行路由。

| 流量 | 主要判断 |
| --- | --- |
| HTTP/HTTP2 | 七层代理识别后可以使用相应路由、指标等能力 |
| gRPC/gRPC-Web | 属于官方列出的 HTTP/2 协议能力，不能笼统归为不支持 |
| 应用自身建立的 HTTPS | 只透传 TLS 时，代理无法直接读取加密的 URL/Header |
| 数据库与私有 TCP 协议 | 可以按不透明 TCP 流量处理；专用协议解析能力另有开关和版本边界 |
| UDP 等非 TCP 流量 | 不属于这里讨论的常规 TCP/HTTP 代理路径，不能套用相同七层规则 |

协议识别会影响结果。Kubernetes Service 的端口名称与 `appProtocol` 可用于显式声明；例如服务实际提供明文 gRPC 时，可以这样声明端口，不能把一个普通 TCP 服务仅改个名称就当作 gRPC：

```yaml
ports:
  - name: grpc-api
    appProtocol: grpc
    port: 50051
    targetPort: 50051
```

网关到上游的协议选择也要单独核对。客户端使用 HTTP/2，不证明代理到后端必然仍使用 HTTP/2；MySQL 等服务端先发数据的协议还要关注自动识别限制。[官方协议识别与选择](https://istio.io/latest/docs/ops/configuration/traffic-management/protocol-selection/)

## 5. 扩展性和定制化成本 {/* #扩展性和定制化成本 */}

先使用声明式路由、安全和遥测 API；只有确实无法表达的需求，再考虑外部授权、Wasm 或更低层的 Envoy 扩展。扩展代码会进入请求路径，其超时、CPU、内存和失败策略都可能影响业务。

例如每个请求都调用外部授权服务，链路变为“业务请求 → 代理 → 授权服务 → 代理 → 上游”。授权服务超时后放行还是拒绝，必须按接口风险明确选择：放行可能绕过保护，拒绝可能扩大故障影响。增加副本只能改善容量和部分可用性，不能代替这项语义设计。[外部授权](https://istio.io/latest/docs/tasks/security/authorization/authz-custom/)

直接修改低层代理配置还会增加版本耦合。Sidecar 可用的扩展方式不能自动视为 Ambient 同样支持；扩展接口、执行位置与升级兼容性都应随目标版本确认。

## 6. Istio 组件故障时是否有退路？ {/* #istio-组件故障时是否有退路 */}

先区分数据面故障和控制面故障，二者影响不同：

| 故障位置 | 可能影响 | 需要观察的证据 |
| --- | --- | --- |
| 单个 Sidecar | 经过该代理的请求失败或连接中断 | 容器重启、就绪状态、代理日志、应用与代理连接 |
| 节点 ztunnel | 该节点相关的 Ambient 通信受影响 | 节点代理、隧道连接、节点与工作负载范围 |
| Waypoint | 经过它的七层流量受影响 | 副本健康、路由执行位置、容量与上游连接 |
| istiod 不可用 | 配置更新、发现变化与证书相关操作受影响 | 配置同步、Endpoint 更新、证书有效期、控制面状态 |

控制面暂时不可用，不等于所有已有请求立即停止；已有配置仍可支撑一部分通信。但这不保证新 Pod、新 Endpoint 或证书到期后的行为正常，影响会随持续时间和资源变化扩大。

数据面不可用时，也不能假设会自动绕过代理直连。流量捕获、mTLS 与授权可能让直连既不可用也不被允许。恢复方式应是替换不健康实例、恢复代理或按已验证的版本/策略回退；临时绕过还必须满足独立的访问控制要求。[安全边界与纵深防御](https://istio.io/latest/docs/ops/best-practices/security/)

## 7. 版本与升级兼容性 {/* #isito-技术架构的成熟度还没有达到预期 */}

早期版本的组件拆并属于历史背景，不能据此直接判断当前发行版不稳定。实际应检查：Istio 与 Kubernetes 的支持矩阵、目标补丁版本、安全公告、使用功能的成熟度，以及控制面与数据面的版本偏差要求。[版本支持政策](https://istio.io/latest/docs/releases/supported-releases/)

Sidecar 的 revision 金丝雀升级可以让新旧控制面并存，先把一部分工作负载迁移到新 revision。安装了新控制面，并不会自动把已有 Pod 中的代理全部更新；还要按注入与重建方式迁移数据面。回滚也要考虑新配置是否仍能被旧版本理解，而非只把镜像标签改回去。[金丝雀升级机制](https://istio.io/latest/docs/setup/upgrade/canary/)

验证重点是实际请求结果：路由、mTLS、授权、重试、长连接和 P99 是否符合预期。组件全为 Running 只说明进程状态，不能单独证明升级后的通信语义未变。

## 8. Kiali 与周边系统的职责 {/* #istio-缺乏成熟的产品生态 */}

Kiali 是服务网格的可观测与配置管理项目，可以提供拓扑、流量健康、Istio 配置检查及与追踪系统的集成。它不是数据面代理，也不替应用执行请求；不能把“不是完整业务运维平台”解释成“无法用于生产”。[Kiali 功能说明](https://kiali.io/docs/features/)

是否满足当前环境，应具体检查身份认证、RBAC、命名空间访问范围、指标后端容量和版本兼容。Prometheus、日志、追踪后端与证书管理仍有各自职责：一个控制台展示了它们的数据，不代表已经替它们实现存储、保留和权限隔离。

## 9. 通信治理之外的边界 {/* #istio-目前解决的问题域还很有限 */}

Istio 不会自动实现数据库事务、消息幂等、业务锁或模型推理调度。加密了 Redis/Kafka 的连接，不等于替客户端实现了复制一致性或消费提交语义。

对于大模型流式服务，网格可以参与连接、安全与遥测，但 Token 预算、KV Cache、模型副本的真实排队仍需要推理框架和相应网关处理。选择了请求级负载均衡，也不能直接推出 GPU 利用率或 TTFT 一定改善；需要把代理开销与模型执行、队列和长连接行为一起测量。

## 10. 判断与自测 {/* #写在最后 */}

需求只有对外入口时，可以先完善现有 Gateway。需要统一服务间身份、加密和策略时，再比较 Sidecar 与 Ambient 的能力、成本与适用边界；不要把引入网格当作架构升级的必选步骤。

### 10.1 gRPC 能通过网格，为什么按方法路由仍可能不生效？

能转发连接不证明经过了七层执行点。还要核对协议声明、网关到上游的协议、路由匹配条件；Ambient 场景还需确认相应流量经过了提供七层能力的 Waypoint。

### 10.2 开启 mTLS 是否意味着任意有证书的服务都应该能访问？

不是。mTLS 提供通信加密和对端身份验证；哪些身份能访问哪些资源，要由授权策略决定，并与 NetworkPolicy 等边界配合。

### 10.3 为什么应用与代理都重试，故障时可能更慢？

重试会放大后端尝试次数，并消耗原请求的时间预算。在后端已饱和时，额外流量还可能继续拉长排队；需要统一预算与业务幂等边界。

### 10.4 istiod 停止后，已有请求仍成功，是否说明控制面不重要？

不是。已有配置可以暂时继续服务，但配置更新、服务发现变化和证书生命周期仍依赖控制面；短时成功不代表长期可用。

### 10.5 没有 Sidecar 是否代表应用流量没有经过代理？

不是。Ambient 仍有节点级 ztunnel，需要七层能力时还有相应 Waypoint；代理从哪里部署、谁共享它，决定了不同容量和故障边界。
