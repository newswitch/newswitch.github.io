# 多集群推理路由、流量切换与容量保护

## 1. 三层路由

```text
GTM/DNS/Anycast：选择Region或Cluster
→ Gateway：身份、配额、连接和HTTP路由
→ Model Router/EPP：选择模型版本、LoRA、KV亲和和副本
```

DNS TTL 控制缓存刷新，不保证所有客户端立即切换；长连接和 SSE 已建立后通常不会因 DNS 更新自动迁移。

## 2. 健康不是 `/healthz` 返回 200

目标集群接收流量前验证：

- Gateway 和依赖可用；
- 指定模型不可变版本已加载；
- 至少 N 个副本完成真实推理；
- KV/Queue/显存有余量；
- Tokenizer/Chat Template 一致；
- 下游鉴权、日志和计费可用；
- 目标 Region 数据策略允许。

## 3. Warm Capacity

故障集群原有流量为 `L`，目标集群剩余可用容量必须覆盖切入后的峰值和抖动。若没有 Warm Capacity，自动把 100% 流量切过去只会制造第二次过载。

使用分阶段权重、全局并发和 Token Budget，先保护目标集群已有租户。

## 4. 状态与亲和

大多数请求可无状态路由，但 Prefix Cache、KV Cache、LoRA Adapter 和会话上下文可能只在特定副本/集群。切换会降低 Cache Hit 或要求客户端重发上下文，成本和 TTFT 会突增。

## 5. 流式请求

切流只影响新连接。旧集群 Drain 时：停止新请求、保留现有 SSE、设置最大 Drain 时间、传播取消，并确保 Load Balancer 不提前断开。跨集群重试仅在确认请求幂等且没有已经输出 Token 时安全。

## 6. 发布与故障切换不同

发布按预期比较新旧版本；故障切换在容量和依赖受损时进行。两者可以使用相同流量机制，但健康门槛、速度和回退条件不同。

## 7. 观测

全局按 Cluster/Model/Version 观察 QPS、Input/Output Token、TTFT、TPOT、Error、Queue、Cache Hit 和拒绝。Request ID 贯穿 GTM/Gateway/Router/Backend。

## 8. 演练

注入单副本、整个集群 Gateway、模型存储、区域出口和控制面故障；验证检测、停止新流量、容量保护、流式请求、回切和数据完整性。
