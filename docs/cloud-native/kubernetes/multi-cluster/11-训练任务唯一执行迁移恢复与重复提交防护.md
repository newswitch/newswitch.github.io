# 训练任务唯一执行、迁移恢复与重复提交防护

## 1. 超时不代表提交失败

全局平台向集群 A 创建任务时网络超时，任务可能已经成功。如果立即向集群 B 重试，同一 Run 会在两个集群执行并写同一 Checkpoint。

```text
Submit Timeout
→ 用Workload UID查询A
→ 若状态未知，禁止B获得同一Fencing Lease
→ 只有确认A未运行或Lease过期并隔离后才能迁移
```

## 2. 稳定身份

任务拥有全局不可变 `Run ID`，每次执行尝试拥有 `Attempt ID`。输出路径按 Run/Attempt 隔离；最终指针只由持有最新 Fencing Token 的 Attempt 更新。

## 3. Lease 与 Fencing

Lease 有 Owner、Epoch/Token 和 Expiry。续约证明当前执行者仍活跃。新 Owner 获得更高 Token 后，存储/元数据写入必须拒绝旧 Token，才能防止暂停的旧集群恢复后继续写。

只有分布式锁而没有数据面的 Fencing，无法彻底阻止旧执行者。

## 4. 迁移前提

- 源 Attempt 已停止或被 Fencing；
- 目标有相同代码、镜像、Runtime 和硬件兼容；
- 最近 Checkpoint 已复制且验证完成；
- Dataset Version 在目标可用；
- World Size/并行策略支持恢复；
- Queue 和 Fabric 容量足够。

运行中的 GPU 内存状态不能透明迁移，通常从持久化 Checkpoint 恢复。

## 5. 幂等输出

指标、评测、模型注册和完成事件都使用 Run/Attempt/Step 作为幂等键。消息重复投递不能创建两个模型版本；旧 Attempt 的完成事件不能覆盖新 Attempt 状态。

## 6. 状态机

```text
Queued → Reserved → Starting → Running → Checkpointing
→ Succeeded/Failed
或 Running → Fencing → Migrating → Starting(new attempt)
```

状态转换使用 Generation/Version CAS，禁止客户端直接从任意状态跳到 Succeeded。

## 7. 故障测试

在创建成功后丢弃响应、断开 Hub—成员网络、暂停旧 Agent、延迟 Checkpoint 复制并让旧集群恢复。验证最终只有一个有效 Owner，输出没有交叉覆盖，配额只计算一次。

参考：[Kubernetes Leases](https://kubernetes.io/docs/concepts/architecture/leases/)、[Kubernetes API Resource Versions](https://kubernetes.io/docs/reference/using-api/api-concepts/)。
