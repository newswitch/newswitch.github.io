# 服务质量等级（QoS）

> 合理配置 QoS 等级是保障 Kubernetes 集群资源高效利用与关键业务稳定运行的基础。

在 Kubernetes 中，QoS（Quality of Service，服务质量等级）由 Pod 内各容器的 CPU/内存 `requests` 和 `limits` 自动推导。它描述资源保障和节点压力下的驱逐倾向，但**不决定 kube-scheduler 的调度优先级**；调度优先级由 `PriorityClass` 表达。

## 1. QoS 等级分类 {/* #qos-等级分类 */}

Kubernetes 将 Pod 的 QoS 等级分为三类，分别适用于不同业务场景。下表总结了各等级的特征和适用场景。

| 等级         | 配置要求                                               | 适用场景         |
|--------------|------------------------------------------------------|------------------|
| Guaranteed   | 每个容器都设置 `limits` 和 `requests`，且值相等         | 关键业务应用      |
| Burstable    | 至少有一个容器设置了 `requests` 或 `limits`，但不完全相等 | 一般业务、开发测试 |
| BestEffort   | 所有容器都未设置 `limits` 和 `requests`                | 非关键、批处理任务 |

### 1.1 Guaranteed（保证级） {/* #guaranteed保证级 */}

Guaranteed 等级要求 Pod 中每个容器都同时设置 CPU 和内存的 `limits` 与 `requests`，且两者数值完全一致。

**配置示例：**

```yaml
spec:
  containers:
  - name: app
    resources:
      limits:
        cpu: 100m
        memory: 128Mi
      requests:
        cpu: 100m
        memory: 128Mi
```

### 1.2 Burstable（突发级） {/* #burstable突发级 */}

Burstable 等级适用于部分资源有保障、部分可突发的场景。只要有一个容器设置了 `requests` 或 `limits`，但不满足 Guaranteed 的全部要求，即为 Burstable。

**配置示例：**

```yaml
spec:
  containers:
  - name: app
    resources:
      limits:
        memory: 180Mi
      requests:
        memory: 100Mi
        cpu: 50m
```

### 1.3 BestEffort（尽力而为级） {/* #besteffort尽力而为级 */}

BestEffort 等级适用于资源要求最低的场景。所有容器都未设置任何 `limits` 或 `requests`，即为 BestEffort。

**配置示例：**

```yaml
spec:
  containers:
  - name: app
    resources: {}
```

## 2. QoS 的作用机制 {/* #qos-的作用机制 */}

QoS 参与 kubelet 的节点压力驱逐判断，并影响 Linux cgroup 的资源控制方式。它不是“业务重要性”的完整表达：同一个 Guaranteed Pod 仍可使用较低的 PriorityClass，一个 BestEffort Pod 也可以被配置为高优先级，因此必须分别理解两套机制。

### 2.1 QoS 与调度、PriorityClass 的边界 {/* #qos-与调度priorityclass-的边界 */}

- 调度过滤首先检查 Pod 的 `requests`，不是 QoS 名称。没有 CPU request 的 BestEffort Pod 在资源过滤阶段等价于请求 0，但这不代表它具有固定的最低队列优先级。
- 调度队列顺序与抢占依据 Pod Priority；通过 `priorityClassName` 引用 `PriorityClass`。
- 节点压力驱逐会综合“使用量是否超过 request”、Pod Priority 和相对使用量；不能简单表述为永远按 BestEffort → Burstable → Guaranteed 删除。

```yaml
apiVersion: scheduling.k8s.io/v1
kind: PriorityClass
metadata:
  name: online-high
value: 100000
preemptionPolicy: Never
globalDefault: false
description: 在线服务优先进入调度队列，但不抢占现有 Pod
```

### 2.2 资源回收策略 {/* #资源回收策略 */}

当节点发生内存、磁盘或 PID 压力时，kubelet 先判断软/硬阈值，再对候选 Pod 排序。以节点压力驱逐为例，主要因素依次包括：是否超过 request、Pod Priority、超出 request 的相对程度。Guaranteed Pod 若实际使用未超过 request，通常比超额使用的 Burstable Pod更不容易被驱逐，但并非绝对“永不驱逐”。

容器触发自身内存 limit 时发生的是 cgroup OOM；节点整体内存紧张时可能发生节点压力驱逐或系统 OOM。三者的日志、事件和责任主体不同，排障时不要混为一谈。

## 3. 查看 Pod 的 QoS 等级 {/* #查看-pod-的-qos-等级 */}

可以通过以下命令查看 Pod 的 QoS 等级：

```bash
kubectl get pod <pod-name> -o yaml | grep qosClass
```

或使用 `describe` 命令：

```bash
kubectl describe pod <pod-name>
```

同时查看调度优先级和近期驱逐事件：

```bash
kubectl get pod <pod-name> -o jsonpath='{.status.qosClass}{"\n"}{.spec.priorityClassName}{"\n"}'
kubectl get events --field-selector involvedObject.name=<pod-name> --sort-by=.lastTimestamp
kubectl describe node <node-name>
```

## 4. 最佳实践 {/* #最佳实践 */}

- 对延迟敏感且资源画像稳定的关键应用，可使用 Guaranteed；仍需单独配置 PriorityClass、PDB、副本和反亲和
- 开发测试环境可采用 Burstable 等级，提高资源利用率
- 批处理任务适合使用 BestEffort 等级，充分利用集群闲置资源
- 合理设置资源请求，避免设置过高的 `requests` 值造成资源浪费

## 5. 总结 {/* #总结 */}

Kubernetes QoS 通过资源配置自动分级，帮助建立资源保障和节点压力驱逐边界；它不替代 PriorityClass，也不自动保证可用性。只有把 requests/limits、PriorityClass、PDB、扩缩容和容量水位联合设计，才能形成完整的资源治理方案。
