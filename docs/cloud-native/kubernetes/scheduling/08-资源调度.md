# Kubernetes 调度器：从 Pod Pending 到 Scheduler Framework

Kubernetes 调度不是“找一台资源最多的节点”，也不只有过滤、打分、绑定三个词。一个 Pod 会先
进入内部调度队列，再经历调度周期和绑定周期；资源、标签、污点、拓扑、端口、PVC、优先级以及
扩展插件都可能影响结果。

本文以原生 `kube-scheduler` 为主。Scheduler Framework 和配置 API 会随 Kubernetes 版本演进，
生产集群应以本集群版本文档及 `kube-scheduler` 配置 API 为准。

## 1. 学习目标

完成本文后，应能够：

- 解释 Pod 从创建到写入 `spec.nodeName` 的完整时序；
- 区分调度队列、调度周期和绑定周期；
- 解释每个 Scheduler Framework 扩展点的职责；
- 手工推导一组节点经过 Filter 和 Score 后的结果；
- 理解 CPU、内存、GPU、端口、PVC 和拓扑怎样共同约束节点；
- 使用 Event、日志、指标和对象状态定位 Pending；
- 判断原生调度、抢占、Descheduler、Gang Scheduling 和 DRA 分别解决什么。

## 2. kube-scheduler 做什么，不做什么

`kube-scheduler` 关注尚未绑定的 Pod，为它选择一个 Node，并通过 Bind 把决策写回 API Server。

```text
Pod 已创建，spec.nodeName 为空
→ kube-scheduler 选择 Node
→ 创建 Binding / 更新 Pod
→ spec.nodeName=<node>
→ 目标节点 kubelet 才开始创建 Sandbox、挂卷、分配设备和启动容器
```

它不负责：

- 创建 Deployment/StatefulSet 的 Pod；
- 在节点上启动容器；
- 持续移动已经运行的 Pod；
- 根据实时 GPU 利用率自动迁移任务；
- 保证多个训练 Worker 原子地同时获得资源。

原生调度器主要做“首次放置”。已运行 Pod 的再平衡通常由控制器、Descheduler、滚动发布或业务
系统驱逐并重建后重新调度。

## 3. 调度器看到的输入

调度决策基于 Informer/Cache 中的集群状态，而不是每次都同步遍历 API Server：

| 输入 | 关键字段 |
|---|---|
| Pod | Requests、Selector/Affinity、Toleration、Priority、PVC、Ports |
| Node | Allocatable、Labels、Taints、Conditions、Unschedulable |
| 已绑定 Pod | 已申请资源、亲和/反亲和、拓扑分布、端口占用 |
| PV/PVC/StorageClass | NodeAffinity、BindingMode、CSI 拓扑、容量 |
| 调度器配置 | Profile、Plugin、Weight、Plugin Args |
| 扩展资源 | `nvidia.com/gpu`、DRA ResourceClaim 等 |

最容易混淆的是：默认调度主要依据 **Requests**，不是 `top` 中的实时使用量。

```text
可调度剩余量 = Node Allocatable - 已绑定 Pod Requests - 调度器已假设占用
```

某节点 GPU 利用率为 0%，但 `nvidia.com/gpu` 已全部被 Pod Request，占用视角仍然是“没有 GPU”。

## 4. Pod 为什么要进入调度队列

Pod 创建速度可能远高于一次调度计算速度，而且失败的 Pod 不能无间隔死循环。因此调度器内部维护
不同状态的队列/集合，可用以下心智模型理解：

```text
新 Pod / 可能变得可调度的 Pod
→ Active Queue
→ Scheduling Cycle
   ├── 成功：进入 Binding Cycle
   ├── 暂时失败：Unschedulable Pods
   └── 错误/退避：Backoff Queue

Node、Pod、PVC 等集群事件发生
→ QueueingHint 判断事件是否可能解除失败原因
→ 重新进入 Active/Backoff Queue
```

- `PreEnqueue`：进入 Active Queue 前检查；
- `QueueSort`：决定队列中 Pod 的先后顺序；
- `QueueingHint`：集群对象变化时判断哪些 Pod 值得重试；
- Backoff：避免持续失败的 Pod 消耗全部调度器 CPU。

“Pod Pending 了 20 分钟”不表示调度器一直占用一个线程计算 20 分钟，它大部分时间可能在等待
资源或相关对象变化后重新入队。

## 5. 两个周期和完整扩展点

一次调度尝试分为：

```text
Scheduling Cycle：选择 Node
Binding Cycle：把选择应用到集群
```

调度周期通常串行推进，绑定周期可以并发。Scheduler Framework 主要扩展点如下：

| 扩展点 | 作用 | 失败后的典型结果 |
|---|---|---|
| PreEnqueue | 判断能否进入 Active Queue | 留在不可调度集合 |
| QueueSort | 排序待调度 Pod | 决定谁先尝试 |
| PreFilter | 预计算 Pod/集群共享状态 | 中止本轮 |
| Filter | 淘汰不可行 Node | 没节点时进入 PostFilter |
| PostFilter | 无可行节点后的补救 | 默认抢占是典型实现 |
| PreScore | 为打分预计算状态 | 中止本轮 |
| Score | 为可行节点打分 | 选综合得分最高者 |
| NormalizeScore | 把某插件分数归一化 | 影响最终加权 |
| Reserve | 暂存/假设资源状态 | 后续失败则 Unreserve |
| Permit | 批准、拒绝或等待 | 可用于协同等待 |
| PreBind | 绑定前准备 | 失败则回队列并 Unreserve |
| Bind | 把 Pod 绑定到 Node | 写回 API Server |
| PostBind | 绑定后的通知/清理 | 不改变已完成绑定 |

最终得分可抽象成：

```text
FinalScore(node) = Σ Normalize(PluginScore(node)) × PluginWeight
```

硬约束只能通过 Filter；提高 Score 权重不能让一个不满足硬约束的节点“复活”。

## 6. 默认插件怎样影响结果

常见默认插件：

| 插件 | 典型扩展点 | 解决的问题 |
|---|---|---|
| NodeUnschedulable | Filter | 排除被 Cordon 的节点 |
| TaintToleration | Filter/Score | 硬污点与软偏好 |
| NodeAffinity | Filter/Score | Selector、硬/软节点亲和 |
| NodeResourcesFit | PreFilter/Filter/Score | CPU、内存、扩展资源是否足够 |
| NodePorts | PreFilter/Filter | HostPort 是否冲突 |
| InterPodAffinity | PreFilter/Filter/Score | Pod 亲和和反亲和 |
| PodTopologySpread | PreFilter/Filter/Score | 跨拓扑域均衡 |
| VolumeBinding | PreFilter/Filter/Reserve/PreBind | PV/CSI 拓扑与延迟绑定 |
| ImageLocality | Score | 倾向已有镜像的节点 |
| DefaultPreemption | PostFilter | 高优先级 Pod 无节点时尝试抢占 |

插件和扩展点会随版本变化。判断现场时读取实际 `KubeSchedulerConfiguration`，不要只靠网上某一版
“默认插件列表”。

## 7. 资源请求怎样计算

### 7.1 普通容器

对大部分可加和资源：

```text
Pod 常驻 Request = 所有普通容器 Requests 之和 + Pod Overhead
```

### 7.2 Init Container

传统顺序 Init Container 不同时运行，调度侧通常取其中最大值，再与普通容器总和比较。Sidecar
形式的可重启 Init Container 会改变计算方式，因此排障时应查看当前版本规则和 Pod 实际 Request。

概念上可先用：

```text
Pod 调度 Request ≈ max(普通容器总和, 最大 Init 阶段需求) + Overhead
```

### 7.3 GPU 等扩展资源

设备插件上报：

```yaml
resources:
  limits:
    nvidia.com/gpu: 4
```

扩展资源通常按整数计数，不允许超卖；GPU 常只写 Limit，Kubernetes 会把 Request 视作同值。
默认调度器看到的是“4 张 GPU”，看不到这四张卡是否属于同一 NVLink/NVSwitch 域、是否靠近目标
NIC，也不了解当前显存碎片。

## 8. 硬约束、软偏好和运行期约束

### 8.1 Node Selector 与 Node Affinity

```yaml
nodeSelector:
  accelerator.example.com/model: h100

affinity:
  nodeAffinity:
    requiredDuringSchedulingIgnoredDuringExecution:
      nodeSelectorTerms:
      - matchExpressions:
        - key: accelerator.example.com/pool
          operator: In
          values: [training]
    preferredDuringSchedulingIgnoredDuringExecution:
    - weight: 80
      preference:
        matchExpressions:
        - key: model-cache.example.com/qwen3-70b
          operator: In
          values: [ready]
```

- Required：进入 Filter，不满足就淘汰；
- Preferred：进入 Score，没有匹配仍可调度；
- `IgnoredDuringExecution`：节点标签之后变化，已运行 Pod 不会自动被驱逐。

模型缓存通常适合软偏好，GPU 型号和合规隔离通常是硬约束。

### 8.2 Taint 与 Toleration

```text
Taint：节点拒绝哪些 Pod
Toleration：Pod 可以容忍哪些 Taint
```

Toleration 只表示“允许进入”，不会主动选择这个节点。专用 GPU 节点一般要同时使用 Taint 和
Label/Affinity。

### 8.3 Pod Affinity 与 Topology Spread

Pod 反亲和可以防止副本同节点，但大规模集群计算成本较高。Topology Spread 更适合表达“在 Zone、
机架、主机间尽量均衡”：

```yaml
topologySpreadConstraints:
- maxSkew: 1
  topologyKey: topology.kubernetes.io/zone
  whenUnsatisfiable: DoNotSchedule
  labelSelector:
    matchLabels:
      app: inference
```

所有候选节点必须具有一致的 Topology Label，否则可能出现意外域或无法调度。

### 8.4 PVC 与 VolumeBinding

`WaitForFirstConsumer` 让卷的选择/创建推迟到 Pod 调度时，使计算节点和存储拓扑共同决策。

```text
Pod 需要 Local PV / Zone Volume
→ VolumeBinding 检查 PV NodeAffinity / CSI Topology
→ 只有计算资源和存储都满足的节点才能通过
```

`volume node affinity conflict` 是真实硬约束，增加 GPU 数量不能解决。

## 9. 手工推导一次调度

Pod 需求：4 GPU、训练池、容忍 GPU Taint、模型缓存优先、PVC 只能在 Zone A。

| Node | GPU 剩余 | Pool | Zone | Cache | Filter 结果 |
|---|---:|---|---|---|---|
| node-a | 8 | training | A | ready | 通过 |
| node-b | 4 | inference | A | ready | NodeAffinity 失败 |
| node-c | 2 | training | A | ready | Insufficient GPU |
| node-d | 8 | training | B | missing | VolumeBinding 失败 |

只有 `node-a` 进入 Score，Cache 权重再高也不会让 `node-d` 跨越 PVC 硬约束。

如果 `node-a`、`node-e` 都可行：

```text
NodeResourcesFit × 1
+ TaintToleration × 1
+ NodeAffinity(Cache Preference) × 80
+ ImageLocality × 1
→ 综合得分
```

“权重 80”只在本轮可行节点之间比较，不是 80% 的调度概率。

## 10. Reserve、Assume 与绑定失败

调度器选中节点后，会在内部 Cache 中先假设 Pod 已占用资源，避免后续 Pod 同时选中同一份剩余资源。
随后进入 Reserve/Permit/PreBind/Bind。

如果后续失败：

```text
Reserve 成功
→ Permit 超时或 PreBind/Bind 失败
→ Unreserve 逆序清理插件状态
→ 移除假设占用
→ Pod 回到调度队列
```

这解释了为什么调度插件的 `Unreserve` 必须幂等，以及为什么“调度器日志显示选中 Node”不一定
代表 API Server 最终已经绑定成功。

## 11. Priority 与抢占

高优先级 Pending Pod 在没有可行节点时，DefaultPreemption 可以尝试寻找节点并驱逐较低优先级
Pod，使资源未来可用。

```yaml
apiVersion: scheduling.k8s.io/v1
kind: PriorityClass
metadata:
  name: production-inference
value: 100000
preemptionPolicy: PreemptLowerPriority
globalDefault: false
description: "生产推理服务"
```

抢占不等于立即运行：

- 被选 Victim 需要终止；
- Grace Period 可能很长；
- PVC、Affinity、GPU 拓扑等其他约束仍要满足；
- PDB 会影响 Victim 选择，但不能把 PDB 当绝对防护；
- 资源可能在等待期间再次变化。

Priority 设计错误会让批量训练驱逐在线服务，必须配合 Namespace/Queue 配额、PDB、审计和演练。

## 12. Scheduler Profile 与扩展

`KubeSchedulerConfiguration` v1 可以配置 Profile 和插件：

```yaml
apiVersion: kubescheduler.config.k8s.io/v1
kind: KubeSchedulerConfiguration
profiles:
- schedulerName: default-scheduler
- schedulerName: ai-scheduler
  plugins:
    score:
      enabled:
      - name: NodeResourcesFit
        weight: 3
```

Pod 使用特定 Profile：

```yaml
spec:
  schedulerName: ai-scheduler
```

生产原则：

- 先用原生 Label、Taint、Affinity、TopologySpread、VolumeBinding；
- 只有原生对象无法表达时才增加插件；
- 修改 Score Weight 前用离线回放或影子调度验证；
- 自定义 Filter/Reserve/Permit 失败会阻塞业务，必须有指标、日志和回退 Profile；
- 配置 API 版本与 Kubernetes 版本必须匹配。

## 13. GPU、网卡、存储为何需要额外能力

默认扩展资源只能表达数量：

```text
nvidia.com/gpu=8
```

AI 任务真正需要的可能是：

```text
8 张 GPU 在同一 NVSwitch 域
+ 靠近同一组 RDMA NIC
+ 同一无损网络 Rail 可用
+ 本地 NVMe 已缓存模型
+ PVC/数据集拓扑可达
+ 8 个 Worker 整组同时启动
```

常见补充方式：

| 能力 | 解决的问题 |
|---|---|
| GFD/NFD Label | 节点级 GPU 型号、能力、拓扑标签 |
| Node Affinity/TopologySpread | 节点池、机架、Zone 放置 |
| Volcano/Kueue | Queue、配额、Gang、批任务准入 |
| DRA | 更结构化、可声明的设备分配 |
| Topology Manager | 节点内 CPU、Device、NUMA 对齐 |
| Local PV/CSI Topology | 计算与存储共同放置 |
| 自定义调度插件 | 特殊设备/网络拓扑评分 |

完整联合放置见[GPU、网卡、存储联合拓扑调度](../../../projects/ai-infra-end-to-end/05-GPU网卡存储联合拓扑调度.md)。

## 14. Pod Pending 的证据链

### 14.1 第一步：固定 Pod 与事件

```bash
kubectl get pod -n <ns> <pod> -o wide
kubectl describe pod -n <ns> <pod>
kubectl get events -n <ns> \
  --field-selector involvedObject.name=<pod> \
  --sort-by=.metadata.creationTimestamp
kubectl get pod -n <ns> <pod> -o yaml
```

先看 `PodScheduled=False` 的 Reason/Message。典型信息：

```text
Insufficient cpu / memory / nvidia.com/gpu
node(s) had untolerated taint
node(s) didn't match Pod's node affinity/selector
node(s) didn't match pod topology spread constraints
node(s) had volume node affinity conflict
node(s) didn't have free ports
preemption is not helpful for scheduling
```

### 14.2 第二步：复算候选节点

```bash
kubectl get nodes --show-labels
kubectl describe node <node>
kubectl get node <node> -o json | jq '.status.allocatable,.spec.taints,.metadata.labels'
kubectl get pods -A --field-selector spec.nodeName=<node> -o wide
```

不要只看 `kubectl top node`。需要加总 Node 上所有 Pod Requests，检查 Terminating、Static Pod、
DaemonSet、扩展资源和调度器假设状态。

### 14.3 第三步：检查 PVC 和拓扑

```bash
kubectl get pvc -n <ns> <pvc> -o yaml
kubectl get pv <pv> -o yaml
kubectl get storageclass <sc> -o yaml
kubectl get csinode <node> -o yaml
```

重点看 `volumeBindingMode`、PV `nodeAffinity`、StorageClass `allowedTopologies` 和 CSI Node。

### 14.4 第四步：调度器日志和指标

```bash
kubectl -n kube-system get pods -l component=kube-scheduler
kubectl -n kube-system logs <scheduler-pod> --since=30m
kubectl -n kube-system get --raw /metrics
```

不同部署可能使用 Static Pod，Label 和指标访问方式会不同。常见指标方向：

- Pending Pod 数量及 Active/Backoff/Unschedulable 队列；
- Scheduling Attempt 时延和结果；
- 每个 Pod 调度尝试次数；
- Plugin 执行时延；
- API Client 请求错误/延迟。

指标名称具有版本差异，应从本集群 `/metrics` 发现并固定 Dashboard。

## 15. 常见错误判断

### “集群有 8 张空闲 GPU，8 卡 Pod 就能运行”

8 张卡分散在 8 个节点，而 Pod 请求 8 张时，需要单节点同时提供 8 张。资源总量不等于可行形状。

### “Toleration 会把 Pod 调度到 GPU 节点”

Toleration 只解除排斥，还需要 Selector/Affinity 表达选择。

### “副本一定会自动分散”

Deployment 不天然保证跨节点/Zone 分散，需要 TopologySpread 或 Anti-Affinity。

### “增加节点后旧 Pod 会自动重平衡”

已运行 Pod 通常不会自动移动。需要扩容控制器、滚动、Descheduler 或业务重建。

### “提高 Priority 就能解决所有 Pending”

抢占无法修复标签错误、PVC Zone 冲突、HostPort 冲突、GPU 拓扑不匹配和不可容忍 Taint。

## 16. 六个递进实验

### 实验一：资源不足

创建 Request 超过单节点剩余量的 Pod，观察 `Insufficient` Event；删除一个占用 Pod后观察重新入队。

### 实验二：Taint 与 Affinity

给测试节点加 `NoSchedule` Taint，分别验证：无 Toleration、只有 Toleration、Toleration + Selector。

### 实验三：硬约束与软偏好

准备两个节点，只有一个带 Cache Label。先用 Required，再改 Preferred，比较候选集和结果。

### 实验四：TopologySpread

部署 6 个副本，跨 Host/Zone 观察 `maxSkew`；移除某节点 Topology Label，分析结果变化。

### 实验五：WaitForFirstConsumer

使用受 Zone 限制的 StorageClass，证明 PVC 与 Pod 怎样共同选择 Node/PV；故意制造 Zone 冲突。

### 实验六：Priority/Preemption

仅在隔离 Namespace 创建低优先级占用和高优先级 Pod，记录 Victim、Nominated Node、PDB 和实际
恢复时间。实验后清理 PriorityClass 和工作负载。

每个实验保存：YAML、Event、Scheduler Log、对象快照、预期、实际结果和恢复证据。
