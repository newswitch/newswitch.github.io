# 多环境 Kubernetes 集群新增节点纳管与验收

新增节点不是把机器变成 `Ready`，而是把一份已经验证的计算能力安全地交给调度器。`kubeadm join` 只负责引导 kubelet 注册到集群，不能证明节点的硬件、网络、存储、加速卡、监控和业务性能合格。

生产环境应把节点纳管设计为一条有状态、有证据、可暂停和可回退的流水线：

```text
Discovered      已登记资产，但尚未安装
    ↓
Provisioned     OS、网络与运行时基线已完成
    ↓
Qualified       硬件和宿主机测试通过
    ↓
Joined          已注册到正确的 Kubernetes 集群
    ↓
Quarantined     保持准入污点，业务不可调度
    ↓
RuntimeReady    CNI、CSI、GPU/NPU 运行栈正常
    ↓
Observed        监控、日志、事件和告警已经接入
    ↓
Canary          测试任务与小流量业务通过
    ↓
InService       解除隔离，正式进入目标资源池
```

本文以 kubeadm 管理的 Linux 工作节点为主，同时说明开发、预发布、生产、离线、NVIDIA、昇腾和 RDMA 环境的差异。托管 Kubernetes 的节点加入方式不同，但准入、隔离和验收思想相同。

## 1. 先区分“注册成功”和“纳管完成”

下面几种状态不能画等号：

| 状态 | 能证明什么 | 不能证明什么 |
| --- | --- | --- |
| `kubeadm join` 成功 | TLS Bootstrap 和节点注册基本成功 | CNI、CSI、加速卡和业务可用 |
| Node 为 `Ready` | kubelet持续汇报，基础运行条件正常 | 网络性能、存储可靠性和计算正确性 |
| 出现 GPU/NPU Allocatable | Device Plugin 已上报资源 | 容器内计算、集合通信和性能达标 |
| 测试 Pod 为 `Succeeded` | 该测试路径成功一次 | 重启恢复、持续稳定和生产容量达标 |
| 已经承载业务 | 调度器可以使用该节点 | 节点已经完成规范验收 |

因此，正确的完成标准应该是：

> 目标集群身份明确，节点在隔离状态下通过硬件、系统、网络、存储、设备、可观测性和业务基线验收，证据已经归档，随后才解除隔离。

## 2. 不同环境的差异放进环境档案

不要为每个集群维护一套互不相关的临时命令。应维护统一的节点纳管流程，再用“环境档案”描述差异。

### 2.1 环境档案至少包含什么

| 类别 | 需要记录的事实 |
| --- | --- |
| 集群身份 | 环境名、集群 ID、业务等级、负责人、变更窗口 |
| 控制面 | API Server 地址、CA 指纹、Kubernetes 版本、HA 拓扑 |
| 主机基线 | OS、CPU 架构、内核、软件仓库、时区、NTP、SELinux/安全策略 |
| 容器层 | containerd/CRI-O 版本、CRI Socket、cgroup 模式、镜像仓库和 CA |
| 集群网络 | CNI、Pod CIDR、Service CIDR、节点网段、MTU、NetworkPolicy |
| 高性能网络 | NIC/HCA 型号、固件、VLAN、Bond、RoCE/IB、PFC、ECN、GID |
| 存储 | CSI 驱动、StorageClass、Ceph/NFS/对象存储地址和网络路径 |
| 加速设备 | CPU/NVIDIA/Ascend、驱动、固件、CUDA/CANN、Device Plugin |
| 调度策略 | 节点池、Label、Taint、RuntimeClass、配额和队列 |
| 可观测性 | Node Exporter、GPU/NPU Exporter、日志、事件、BMC 和告警 |
| 验收策略 | 测试集合、基线范围、证据位置、通过条件、回退条件 |

环境档案中的版本必须来自目标集群，而不是从另一套环境复制。尤其不能跨集群复用 Join Token、CA Hash、管理员 kubeconfig 或仓库凭据。

### 2.2 环境差异矩阵

| 环境 | 不能省略的重点 | 可以调整的部分 |
| --- | --- | --- |
| 开发 | 唯一身份、基础网络、运行时、CNI/CSI、最小计算测试 | Burn-in 时长和性能门限可以较低 |
| 测试 | 与待验证功能相关的完整组件、故障注入和重启测试 | 可使用测试数据与较小容量 |
| 预发布 | 版本、网络拓扑、安全策略、镜像源尽量与生产一致 | 节点数量可小于生产 |
| 生产 | 完整 Burn-in、故障域控制、变更审批、灰度和回退 | 不应以工期为由跳过门禁 |
| 离线 | 内部软件源、镜像、Chart、驱动、证书、校验和 | 不能依赖运行时临时访问公网 |
| RDMA | 交换机与主机联合验收、PFC/ECN/GID、集合通信 | 普通 TCP 测试只能作为基础检查 |
| 多集群 | 每个集群独立身份、独立凭据、独立准入结果 | 上层平台只汇总已经合格的容量 |

## 3. 变更前锁定目标和责任边界

节点加错集群比加入失败更危险。执行任何安装前应形成一张变更单，至少回答：

1. 这台机器加入哪个集群、哪个节点池？
2. 它是工作节点还是控制平面节点？
3. 由谁修改宿主机、交换机、Kubernetes 和监控配置？
4. 哪些步骤会重启主机、containerd 或 kubelet？
5. 验收失败时，机器保留在哪个状态？
6. 谁根据哪些证据批准解除隔离？

本文后续默认纳管的是工作节点。扩容控制平面还涉及 API Server 负载均衡、控制面证书、etcd 成员和 quorum 风险，不能把工作节点命令简单增加一个 `--control-plane` 就直接用于生产。

### 3.1 在集群侧采集事实

以下命令在具有只读或管理员权限的运维终端执行：

```bash
kubectl cluster-info
kubectl version
kubectl get nodes -o wide
kubectl get nodes -L topology.kubernetes.io/zone,node-pool,accelerator.vendor
kubectl get pods -n kube-system -o wide
kubectl get daemonsets -A
kubectl get storageclass
```

如果集群由 kubeadm 创建，可检查已经上传的 kubeadm 配置：

```bash
kubectl -n kube-system get configmap kubeadm-config -o yaml
```

输出可能包含内部地址和集群信息，归档前需要按安全规范处理。不要把 `/etc/kubernetes/admin.conf`、Join Token 或私钥提交到 Git 仓库和工单正文。

### 3.2 选择一台同池健康节点作为基准

新节点不能只与产品说明书比较，还要与同机型、同固件和同拓扑的健康节点比较。记录基准节点的：

- OS、内核、containerd、kubelet和驱动版本；
- CPU、内存、NUMA、GPU/NPU、NIC、NVMe和PCIe拓扑；
- Label、Taint、RuntimeClass与Allocatable；
- MTU、路由、Bond、RDMA和存储挂载配置；
- GPU/NPU单卡、卡间互联和跨机通信性能。

如果找不到同规格基准，应先定义临时验收范围，不能把任意一台旧机器的性能当成标准。

## 4. 第一层门禁：资产与硬件验收

新机器还没有加入 Kubernetes 时，先确认“物理节点是否完整”。

### 4.1 资产和唯一身份

在新节点执行：

```bash
hostnamectl
cat /etc/machine-id
cat /sys/class/dmi/id/product_uuid
ip -br link
ip -br addr
lscpu
free -h
lsblk -o NAME,SIZE,TYPE,FSTYPE,MOUNTPOINTS,MODEL,SERIAL
lspci -nn
```

确认主机名、Machine ID、DMI UUID、MAC 和管理地址没有与现有节点重复。虚拟机由模板克隆时尤其要检查 Machine ID；重复身份可能造成 DHCP、监控、日志或节点注册混乱。

资产表至少记录：

- 服务器序列号与机架位置；
- BMC 地址和固件版本；
- CPU、内存、磁盘、NIC/HCA、GPU/NPU 型号与数量；
- 交换机端口、VLAN、Bond 成员和故障域；
- 系统盘、数据盘和缓存盘用途。

### 4.2 BIOS、固件和PCIe拓扑

检查设备是否缺失或降级：

```bash
lspci -tv
lspci -vv
dmesg -T | grep -Ei 'aer|pcie|mce|edac|iommu|error|fail'
journalctl -k -b -p warning
```

`grep` 命中 `error` 不等于一定存在故障，应结合设备、时间、错误计数是否持续增长判断。对于 GPU/NPU 服务器，还要核对：

- BIOS 的 SR-IOV、IOMMU、Above 4G Decoding 等选项是否符合厂商基线；
- PCIe Link Speed 和 Link Width 是否达到设计值；
- NUMA、GPU/NPU、NIC 和 NVMe 的亲和关系是否符合机型拓扑；
- BMC SEL 中是否存在电源、温度、风扇、PCIe 或内存告警。

### 4.3 Burn-in与性能基线

生产节点应在加入业务资源池前完成 CPU、内存、磁盘、加速卡、互联和网卡压力测试。测试不能只看退出码，还要同步采集：

- MCE、EDAC、PCIe AER和IOMMU日志；
- GPU Xid、ECC、温度、功耗、频率和降频原因；
- NPU健康状态、HBM、错误码和温度；
- NIC/RDMA丢包、错误包、PFC、ECN和链路重训；
- NVMe SMART、介质错误和尾延迟；
- 与同规格节点的性能偏差。

完整方法见 [GPU服务器Burn-in压力测试与交付验收](../../../../gpu/bare-metal-fleet/05-GPU服务器Burn-in压力测试与交付验收.md)。硬件验收不通过时，节点应停留在 `Qualified` 之前，不要通过 Kubernetes 污点掩盖物理故障。

## 5. 第二层门禁：操作系统与容器基线

### 5.1 确认操作系统和内核

```bash
cat /etc/os-release
uname -r
uname -m
systemd-detect-virt
timedatectl
```

检查目标环境是否支持该 OS、CPU 架构和内核组合。麒麟、Ubuntu、Rocky Linux 的包名和服务配置可能不同；x86_64 镜像不能直接运行在 aarch64 节点。

### 5.2 时间、DNS、证书和软件源

```bash
timedatectl status
getent hosts <API_SERVER_FQDN>
getent hosts <INTERNAL_REGISTRY_FQDN>
```

必须验证：

- NTP/Chrony 正在同步且时间偏差在基线内；
- DNS 能稳定解析 API Server、仓库、存储和监控地址；
- 内部 CA 已安装到系统和容器运行时需要的信任位置；
- 包仓库和镜像仓库指向正确环境；
- HTTP/HTTPS 代理及 `NO_PROXY` 包含集群内部地址、Pod/Service 网段和必要域名。

时间错误会影响 TLS、日志关联和分布式任务；`NO_PROXY` 缺失则可能让 API、Service 或对象存储流量错误地经过代理。

### 5.3 swap和cgroup遵循目标集群基线

```bash
swapon --show
stat -fc %T /sys/fs/cgroup
systemctl status containerd kubelet
crictl info
```

较新的 Kubernetes 可以在满足配置条件时支持 Linux swap，但 kubeadm 和既有集群通常仍有明确基线。不要机械执行 `swapoff -a`，也不要因为系统允许 swap 就自行启用；应复制目标集群已经验证的 KubeletConfiguration。

kubelet 与容器运行时的 cgroup driver 必须一致。在 systemd 系统上通常使用 `systemd`，但最终以目标集群配置为准。

### 5.4 锁定Kubernetes组件版本

```bash
kubeadm version
kubelet --version
containerd --version
```

节点上的 kubelet 不得高于它可能连接的 kube-apiserver。当前 Kubernetes 官方策略允许 kubelet 在一定范围内低于 kube-apiserver，但部署工具可能有更严格限制；新增节点通常优先使用与控制面相同的小版本和经过验证的补丁版本。

不要用“官方允许三个小版本偏差”替代企业兼容测试。CNI、CSI、Device Plugin和操作系统厂商可能只认证其中一部分组合。

## 6. 第三层门禁：网络、仓库和存储可达性

### 6.1 API Server和基础服务

在新节点验证解析、路由和端口：

```bash
getent hosts <API_SERVER_FQDN>
ip route get <API_SERVER_IP>
nc -vz <API_SERVER_FQDN> 6443
nc -vz <INTERNAL_REGISTRY_FQDN> 443
```

还应从控制面或受信节点验证到新节点 kubelet 端口的路径。具体开放范围取决于网络策略和部署方式，不能因为 `6443` 可达就认为 Kubernetes 网络已经完整。

需要形成环境自己的端口矩阵：

| 流向 | 典型用途 | 验收方式 |
| --- | --- | --- |
| 新节点 → API Server | 注册、Watch和状态上报 | DNS、路由、TCP、TLS |
| 控制面 → 新节点 | kubelet API、日志和执行 | 防火墙、ACL、双向验证 |
| 节点 ↔ 节点 | CNI、Service和分布式任务 | 跨节点Pod与业务端口测试 |
| 节点 → 仓库 | 镜像与软件包下载 | CA、认证、代理、实际拉取 |
| 节点 ↔ 存储 | Ceph/NFS/CSI/对象存储 | 挂载、读写、重连和性能 |
| 节点 ↔ 监控 | 指标、日志、事件 | Target、标签和告警验证 |

### 6.2 CIDR和路由冲突

至少核对：

```bash
ip route
ip rule
ip addr
```

Pod CIDR、Service CIDR不能与节点网段、BMC网段、VPN、办公网、存储网或现有静态路由冲突。冲突可能表现为：节点能加入，但部分 Service、Pod 或外部地址无法访问。

### 6.3 MTU不是只看网卡配置

```bash
ip -d link show
ping -M do -s 1472 <同网段节点IP>
```

在1500字节MTU的IPv4链路中，1472字节负载加28字节IP/ICMP头部正好达到1500；Overlay、IPv6、IPsec或其他封装会改变可用负载。应根据实际封装逐步测量端到端Path MTU，而不是只比较 `ip link` 输出。

### 6.4 存储不能等业务启动后再测

加入前先验证到存储网络的路由、DNS、端口和认证依赖；加入后再通过目标 StorageClass 完成：

```text
PVC 创建
→ 卷挂载
→ 写入与读取校验
→ Pod 重建后再次读取
→ 卷卸载
→ 节点重启或网络闪断后的恢复
```

本机路径可见不代表 CSI 可用，宿主机 `mount` 成功也不能替代 Pod 内挂载测试。

## 7. 第四层门禁：按节点类型准备运行栈

### 7.1 普通CPU节点

CPU节点主要确认：

- CPU Manager、Topology Manager和HugePage策略符合节点池要求；
- CPU、内存和临时存储预留一致；
- 节点不存在错误的GPU/NPU标签和运行时；
- 通用DaemonSet可以运行。

### 7.2 NVIDIA GPU节点

先在宿主机确认硬件与驱动：

```bash
lspci | grep -i nvidia
nvidia-smi
nvidia-smi -L
nvidia-smi topo -m
```

然后明确组件所有权：

| 模式 | 驱动 | Container Toolkit | Device Plugin/监控 |
| --- | --- | --- | --- |
| Operator完整管理 | GPU Operator | GPU Operator | GPU Operator |
| 宿主机驱动 | OS自动化 | GPU Operator | GPU Operator |
| 宿主机驱动和Toolkit | OS自动化 | OS自动化 | GPU Operator或独立组件 |

同一层只能有一个管理者。不要让OS脚本和GPU Operator同时升级驱动或修改containerd。GPU Operator默认可以管理驱动、Container Toolkit、Device Plugin、GPU Feature Discovery、DCGM Exporter等组件，具体支持组合应以目标版本的[NVIDIA GPU Operator文档](https://docs.nvidia.com/datacenter/cloud-native/gpu-operator/latest/getting-started.html)为准。

加入后应看到真实资源：

```text
nvidia.com/gpu: <实际GPU数量>
```

厂商组件生成的 `nvidia.com/*` 标签和资源不能人工伪造。

### 7.3 昇腾NPU节点

昇腾节点按下面的层次验收：

```text
PCIe和硬件
→ 固件与驱动
→ npu-smi
→ CANN
→ Ascend Docker Runtime/containerd
→ Ascend Device Plugin
→ NPU Exporter
→ 最小计算与HCCL
```

宿主机先执行：

```bash
lspci
npu-smi info
```

驱动、固件、CANN、torch_npu、vLLM-Ascend和Device Plugin必须来自经过验证的兼容组合。不同产品和组件版本上报的扩展资源键可能不同，应读取节点 `Allocatable`，不能假定永远是同一个名称。

完整部署链路见 [部署昇腾NPU资源池](../../../../projects/heterogeneous-cluster/12-部署昇腾NPU资源池.md)。

### 7.4 RDMA节点

RDMA节点除了普通网络，还要验证：

- NIC/HCA型号、固件、驱动与OFED/rdma-core组合；
- 端口速率、Bond、VLAN、RoCEv2或InfiniBand模式；
- PFC、ECN、ETS等交换机配置；
- GID index、网卡名、NUMA与GPU/NPU亲和性；
- `ib_write_bw`、`ib_read_bw`等点对点基线；
- NCCL/HCCL集合通信的带宽、尾部和稳定性。

普通 `ping` 成功只能证明基础IP可达，不能证明RDMA无损网络或集合通信合格。

## 8. 加入前先设置准入隔离

### 8.1 为什么加入后再cordon存在时间窗口

如果节点先以普通状态注册，再由人工执行 `kubectl cordon`，两条命令之间调度器可能已经放入业务 Pod。低负载环境中这个窗口很短，但生产流程不应依赖“操作够快”。

更稳妥的方法是在 kubelet 第一次注册时携带准入污点。先使用目标 kubeadm 版本生成 JoinConfiguration 骨架：

```bash
kubeadm config print join-defaults
```

再按照该版本API结构，把类似配置合入 `nodeRegistration`：

```yaml
nodeRegistration:
  kubeletExtraArgs:
    - name: register-with-taints
      value: "node.lifecycle.example.com/phase=acceptance:NoSchedule"
```

上例是当前配置结构的表达方式；实际使用前必须用目标节点上的 `kubeadm config validate` 或目标版本文档校验，不能把其他版本的 `apiVersion` 原样复制。

准入污点使用 `NoSchedule`，只阻止没有对应Toleration的新Pod，不驱逐系统中已有Pod。基础设施DaemonSet是否应该容忍该污点，需要在设计阶段明确。

### 8.2 cordon作为第二道保护

节点注册后立即在控制端确认并执行：

```bash
kubectl get node <NODE_NAME> -o wide
kubectl cordon <NODE_NAME>
kubectl get node <NODE_NAME> -o jsonpath='{.spec.unschedulable}{"\n"}'
kubectl get node <NODE_NAME> -o jsonpath='{.spec.taints}{"\n"}'
```

`cordon`与准入污点可以同时存在：前者表明节点整体不可调度，后者记录其生命周期状态。验收工具如果需要进入已cordon的节点，应由运维人员明确绑定测试Pod，并在结束后删除，不能给所有业务增加宽泛Toleration。

## 9. 使用正确的身份执行kubeadm join

### 9.1 生成短期Join Token

在目标集群的控制端执行：

```bash
kubeadm token create --ttl 30m --print-join-command
```

得到的命令形式如下：

```bash
sudo kubeadm join <API_SERVER_FQDN>:6443 \
  --token <BOOTSTRAP_TOKEN> \
  --discovery-token-ca-cert-hash sha256:<CA_PUBLIC_KEY_HASH>
```

Token是短期引导凭据，应通过受控通道传递，不要写入博客、Git、共享终端历史或长期脚本。官方默认Token通常有过期时间；生产上应按变更窗口设置更短TTL，用后让其自然过期或主动删除。

### 9.2 先做预检

在新节点执行：

```bash
sudo kubeadm join <API_SERVER_FQDN>:6443 \
  --token <BOOTSTRAP_TOKEN> \
  --discovery-token-ca-cert-hash sha256:<CA_PUBLIC_KEY_HASH> \
  --dry-run
```

预检错误应逐项解决。不要用 `--ignore-preflight-errors=all` 把主机名重复、端口占用、CRI异常、版本错误或旧集群残留一起跳过。

### 9.3 执行加入并观察日志

```bash
sudo kubeadm join <API_SERVER_FQDN>:6443 \
  --token <BOOTSTRAP_TOKEN> \
  --discovery-token-ca-cert-hash sha256:<CA_PUBLIC_KEY_HASH>
```

同时观察：

```bash
sudo journalctl -u kubelet -f
```

`kubeadm join`内部主要经历：

```text
Discovery验证目标集群
→ Bootstrap Token认证
→ kubelet申请客户端证书
→ 获取集群级kubelet配置
→ 启动kubelet
→ 创建或更新Node对象
→ 持续上报Node Status与Lease
```

加入Linux工作节点的官方基础流程见 [Adding Linux worker nodes](https://kubernetes.io/docs/tasks/administer-cluster/kubeadm/adding-linux-nodes/) 和 [`kubeadm join`参考](https://kubernetes.io/docs/reference/setup-tools/kubeadm/kubeadm-join/)。

## 10. 节点注册后的身份治理

### 10.1 使用组织自己的标签域

示例：

```bash
kubectl label node <NODE_NAME> \
  infra.example.com/environment=prod \
  infra.example.com/node-pool=nvidia-h20 \
  infra.example.com/accelerator=nvidia \
  infra.example.com/rack=rack-a12
```

真实环境应将 `example.com` 替换为组织控制的域名，并统一标签词典。不要同时出现 `gpu=true`、`is-gpu=yes`、`accelerator=nvidia` 等互相重叠的自由命名。

标签分为三类：

| 类型 | 示例 | 管理者 |
| --- | --- | --- |
| 基础设施事实 | 环境、机房、机架、资源池 | 集群管理自动化 |
| 厂商发现事实 | GPU型号、MIG能力、设备数量 | GFD/NFD/Device Plugin等组件 |
| 业务策略 | 推理池、训练池、租户专用 | 平台控制器或管理员 |

涉及安全或合规隔离的标签不能允许 kubelet 自行修改。启用Node authorizer与NodeRestriction时，可使用受保护的 `node-restriction.kubernetes.io` 命名空间策略，并由管理员写入。

### 10.2 节点池污点

NVIDIA资源池示例：

```bash
kubectl taint node <NODE_NAME> \
  workload.example.com/accelerator=nvidia:NoSchedule
```

昇腾资源池示例：

```bash
kubectl taint node <NODE_NAME> \
  workload.example.com/accelerator=ascend:NoSchedule
```

污点负责排斥不合适的Pod，Label、Node Affinity和调度队列负责选择目标池。Toleration只代表“允许进入”，不保证Pod一定调度到该节点。

## 11. 加入后的七类验收

### 11.1 Node对象与kubelet

在控制端执行：

```bash
kubectl get node <NODE_NAME> -o wide
kubectl describe node <NODE_NAME>
kubectl get node <NODE_NAME> \
  -o jsonpath='{range .status.conditions[*]}{.type}{"="}{.status}{" reason="}{.reason}{"\n"}{end}'
```

重点检查：

- `Ready=True`且在观察期内保持稳定；
- `MemoryPressure`、`DiskPressure`、`PIDPressure`为False；
- InternalIP、Hostname、Architecture和OS Image正确；
- Capacity与Allocatable符合预留策略；
- 没有意外Label、Taint和旧集群注解；
- kubelet日志没有证书、CRI、cgroup和PLEG持续错误。

### 11.2 系统DaemonSet

```bash
kubectl get pods -A -o wide --field-selector spec.nodeName=<NODE_NAME>
kubectl get daemonsets -A
kubectl get events -A --sort-by=.lastTimestamp
```

确认CNI、kube-proxy、CSI Node、Node Exporter、日志Agent以及目标设备插件都已进入节点。不要只检查Pod为Running，还要看Ready、Restart次数、日志和事件。

### 11.3 Pod网络与DNS

验收至少覆盖：

```text
目标节点Pod → 同节点Pod
目标节点Pod → 其他节点Pod
其他节点Pod → 目标节点Pod
目标节点Pod → ClusterIP Service
目标节点Pod → CoreDNS
目标节点Pod → 必要外部服务
```

如果节点仍处于cordon状态，可以由运维人员创建设置了 `spec.nodeName: <NODE_NAME>` 的专用测试Pod。`nodeName`会绕过调度器，必须只用于受控验收，测试完成后立即删除。

排查时关联查看：

```bash
kubectl describe pod <TEST_POD>
kubectl logs <TEST_POD>
ip route
ip neigh
ip -s link
```

网络验收不能只使用ICMP；还应测试DNS、TCP连接、Service NAT、NetworkPolicy以及真实业务负载大小下的MTU。

### 11.4 镜像与容器运行时

使用内部仓库中的固定摘要镜像完成：

- 公共和私有镜像拉取；
- Registry CA和认证；
- amd64/aarch64架构匹配；
- Sandbox创建与删除；
- 容器日志和退出码采集；
- 节点重启后的镜像与Pod恢复。

如果使用代理，分别测试经代理和应当绕过代理的地址。

### 11.5 CSI与持久化存储

针对节点池实际使用的每个StorageClass，执行PVC创建、挂载、写入校验、Pod重建读取和卸载。使用校验和验证数据，而不是只执行一次 `touch`。

检查：

```bash
kubectl get pods -A -o wide --field-selector spec.nodeName=<NODE_NAME>
kubectl get pvc,pv -A
kubectl describe pod <STORAGE_TEST_POD>
```

对于Ceph同时观察客户端、CSI、网络和集群健康；对于NFS检查协议版本、锁、权限和服务端导出；对于本地盘检查拓扑绑定和节点丢失后的数据边界。

### 11.6 GPU/NPU和集合通信

NVIDIA节点依次证明：

```text
宿主机nvidia-smi
→ Device Plugin与Operator健康
→ Node出现nvidia.com/gpu
→ 容器内nvidia-smi
→ 最小CUDA计算
→ 单机P2P/NVLink
→ 跨机NCCL/RDMA
```

昇腾节点依次证明：

```text
宿主机npu-smi
→ Ascend Runtime与Device Plugin健康
→ Node出现实际NPU资源键
→ 容器内设备可见
→ 最小NPU计算
→ 单机卡间通信
→ 跨机HCCL/RDMA
```

集合通信必须与同规格健康节点比较带宽、延迟和离散度。一个慢节点会拖慢整个同步并行组，即使所有设备利用率看起来都很高。

### 11.7 可观测性和告警

纳管完成前确认：

- Prometheus中的Node Exporter/kubelet/cAdvisor Target为Up；
- GPU使用率、显存、温度、功耗、Xid和ECC可以查询；
- NPU利用率、HBM、温度和错误事件可以查询；
- 系统日志、kubelet、containerd和设备插件日志进入日志平台；
- BMC/硬件事件已经接入或有明确巡检责任；
- 节点标签能正确进入指标维度；
- 测试告警能够触发、路由和恢复。

“有Exporter Pod”不等于可观测性完成，必须从监控查询端和告警接收端反向验证。

## 12. 验收结果必须可以审计

建议为每台节点生成一份验收记录：

| 字段 | 示例内容 |
| --- | --- |
| 资产身份 | 节点名、序列号、BMC、机架、交换机端口 |
| 目标环境 | 集群、节点池、故障域、业务用途 |
| 软件组合 | OS、内核、containerd、kubelet、驱动、CANN/CUDA |
| 配置摘要 | Label、Taint、MTU、RuntimeClass、StorageClass |
| 原始证据 | 命令输出、日志、监控截图、测试报告和时间戳 |
| 基线对比 | 同规格中位数、允许偏差、实际结果 |
| 异常和处置 | 发现的问题、修复动作、复测结果 |
| 最终结论 | 通过、隔离复测、退回维修 |
| 审核信息 | 执行人、审核人、变更单和时间 |

结论不应写成“暂时没发现问题”。应为每个门禁定义可判定的通过条件。

## 13. 灰度入池而不是直接全量放开

所有门禁通过后，先移除生命周期准入污点：

```bash
kubectl taint node <NODE_NAME> \
  node.lifecycle.example.com/phase=acceptance:NoSchedule-
```

如果执行过cordon，再恢复调度：

```bash
kubectl uncordon <NODE_NAME>
```

不要立即让整批节点承载关键业务。推荐顺序：

```text
一台节点解除隔离
→ 调度可重试的Canary任务
→ 验证功能、性能、错误率和告警
→ 同机架小批量放开
→ 跨机架逐批放开
→ 达到观察条件后完成变更
```

灰度条件应根据业务定义，例如：

- 节点和设备健康指标持续正常；
- 测试任务成功率和尾延迟达到基线；
- 没有新增PCIe、ECC、Xid、NPU或网卡错误；
- 模型加载、TTFT、TPOT和吞吐符合对应节点池基线；
- 没有异常驱逐、容器重启或存储重连。

生产批次要限制同一机架和同一故障域同时变更的节点数。

## 14. 失败回退和重新纳管

### 14.1 先隔离并保留证据

发现故障时先执行：

```bash
kubectl cordon <NODE_NAME>
kubectl taint node <NODE_NAME> \
  node.lifecycle.example.com/phase=failed:NoSchedule --overwrite
```

如果节点已经承载业务，在确认PodDisruptionBudget、本地数据、DaemonSet和优雅退出影响后再驱逐：

```bash
kubectl drain <NODE_NAME> --ignore-daemonsets
```

不要为了让 `drain` 成功而习惯性增加 `--delete-emptydir-data` 或 `--force`。这些选项可能删除本地临时数据或绕过工作负载保护，必须经过业务确认。

隔离后保存：

- `kubectl describe node`、Pod和Event；
- kubelet、containerd、CNI、CSI和Device Plugin日志；
- 内核、BMC、GPU/NPU和NIC错误计数；
- 故障任务、时间线、输入、镜像摘要和调度位置；
- 修复前后的版本与配置差异。

### 14.2 什么时候删除Node对象

短期排障通常不需要删除Node对象。只有确认要重新引导、退役或清除错误身份时，才在控制端执行：

```bash
kubectl delete node <NODE_NAME>
```

随后仅在已经确认的目标机器上执行：

```bash
sudo kubeadm reset
```

`kubeadm reset`不会自动替你完成所有CNI、防火墙、网卡、数据目录和厂商运行时清理。是否清除这些内容必须根据所用CNI、CSI和设备栈的官方卸载流程决定，不能直接复制一组递归删除命令。

修复后节点要从硬件或系统门禁重新开始，不能因为曾经通过验收就跳过复测。

## 15. 常见故障的分层定位

| 现象 | 优先检查 | 不要急着做什么 |
| --- | --- | --- |
| `kubeadm join` Discovery失败 | API地址、DNS、路由、Token、CA Hash、时间 | 不要关闭TLS校验 |
| TLS Bootstrap超时 | Token、CSR、RBAC、API连通和时间 | 不要复制其他集群证书 |
| kubelet启动失败 | CRI Socket、cgroup、配置、证书、端口和日志 | 不要反复重装而不保存首错 |
| Node长期NotReady | kubelet Condition、CNI、容器运行时、磁盘压力 | 不要先安装GPU插件 |
| `NetworkPluginNotReady` | CNI DaemonSet、配置、路由、MTU、内核模块 | 不要用重启掩盖配置差异 |
| `ImagePullBackOff` | 仓库DNS、CA、认证、代理、架构和镜像名 | 不要改成未知公网镜像 |
| PVC挂载失败 | CSI Node、存储网络、凭据、拓扑和服务端 | 不要只在宿主机手工mount |
| Node没有GPU资源 | 宿主机驱动、Device Plugin、kubelet设备注册 | 不要手工添加 `nvidia.com/gpu` |
| Node没有NPU资源 | `npu-smi`、Runtime、Device Plugin、实际资源键 | 不要猜测资源名称 |
| Pod能运行但跨机很慢 | NUMA、PCIe、MTU、RDMA、PFC/ECN、NCCL/HCCL | 不要只看GPU/NPU利用率 |
| 监控没有新节点 | 服务发现、标签、网络、认证、时间和Exporter | 不要因为Pod Running就判定完成 |

排障时固定从下往上：

```text
硬件/BMC
→ OS与内核
→ 网卡、路由和存储路径
→ containerd与kubelet
→ CNI/CSI
→ Device Plugin与Runtime
→ 调度和资源申请
→ 业务框架与模型
```

## 16. 托管Kubernetes和多集群平台怎么处理

### 16.1 托管Kubernetes

EKS、ACK、CCE等托管集群通常通过Node Group、Machine Pool、Auto Scaling Group或平台节点池扩容。此时：

- 使用平台支持的节点镜像、启动模板和身份角色；
- 不绕过平台直接执行 `kubeadm join`；
- 把Label、Taint、磁盘、网络和Bootstrap脚本写入节点池模板；
- 等平台完成实例注册后，仍执行本文的隔离、运行栈、监控和业务验收；
- 扩缩容控制器只能使用已经验证的镜像和节点模板。

### 16.2 多集群管理平台

多集群纳管分为两层：

```text
机器 → 目标成员集群
成员集群 → 上层多集群/资源管理平台
```

先在成员集群完成节点验收，再把容量暴露给上层平台。不能让上层调度器把一台仍处于 `Quarantined` 的节点计入可售或可调度容量。

## 17. 如何把流程自动化

手工执行适合学习和首台验证，批量生产纳管应拆成可重复的自动化阶段：

```text
CMDB/BMC发现
→ PXE/镜像装机
→ Ansible系统基线
→ 硬件和Burn-in流水线
→ 生成目标环境Join配置
→ kubeadm/节点池注册
→ 自动添加准入污点与标签
→ CNI/CSI/设备/监控验收
→ 生成验收报告
→ 人工或策略审批
→ 灰度解除隔离
```

自动化要满足：

- 幂等：重复执行不会破坏已正确配置；
- 可观察：每一步有开始、结束、退出码和原始证据；
- 可暂停：失败节点停留在隔离状态，不影响下一台；
- 有差异检测：实际配置偏离环境档案时失败，而不是自动覆盖所有差异；
- 凭据短期化：Token、证书和仓库密码不写入静态Inventory；
- 分批：按机架、故障域和节点池限制并发；
- 可回退：系统、驱动、容器运行时和Kubernetes层分别定义回退边界。

## 20. 本篇小结

不同环境的节点纳管不应该变成多套临时命令，而应由一条统一流程和多份环境档案组成：

```text
统一流程：准入 → 注册 → 隔离 → 验收 → 灰度 → 入池
环境差异：版本、网络、存储、硬件、运行栈、调度和门限
安全底线：凭据不串用、节点不裸奔、失败不放行、证据可追溯
```

真正的完成标志不是终端出现 `This node has joined the cluster`，而是调度器获得了一份身份正确、能力可信、状态可见、故障可隔离且性能有基线的资源。
