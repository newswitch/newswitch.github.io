# Distro、Raft/JRaft、AP/CP 与数据一致性

> 版本基线：Nacos 3.2；最后核验：2026-08-18。本文用数据生命周期分析一致性，不把内部实现名称当作跨版本不变的 API 契约。

一句“Nacos 是 AP”或“Nacos 是 CP”都不完整。Nacos 同时管理临时服务实例、持久服务资源、配置内容、订阅关系和客户端缓存，这些对象的生命周期、复制路径与故障语义并不相同。

分析一致性时必须先问：**哪一种数据、哪一个版本、哪一种部署模式、哪一个 API？**

## 1. 先按数据生命周期分类

| 数据或状态 | 典型生命周期 | 更关注什么 |
| --- | --- | --- |
| 临时服务实例 | 与客户端连接/心跳绑定，可重新注册 | 注册可用性、快速收敛 |
| 持久服务与实例 | 不应因一次断连自动消失 | 强一致变更、恢复 |
| 配置内容 | 需要审计、版本和回滚 | 持久化正确性、发布可见性 |
| 订阅关系 | 与客户端会话相关 | 推送效率、断线恢复 |
| Consumer 本地缓存 | 进程本地派生状态 | 控制面故障下继续服务 |

同一个“服务发现结果”还可能经历服务端过滤、订阅推送和客户端缓存，因此服务端存储一致并不代表所有 Consumer 立即看到相同结果。

## 2. Distro 的设计目标

Distro 面向可按节点分工、可以从活跃客户端和其他节点重新构建的运行时数据，强调分区期间的注册发现可用性与恢复后的最终收敛。

可以用下面的简化模型理解：

```text
instance/service key
→ 根据规则确定负责节点
→ 请求转发或由负责节点处理
→ 节点间增量同步
→ 周期校验与缺失数据修复
→ 各节点形成服务发现视图
```

这不是说“写到任意一个节点就永远不会丢”，而是要结合负责节点、同步是否完成、客户端是否仍在线以及故障发生时间判断。

### 2.1 分区期间可能发生什么 {/* #分区期间可能发生什么 */}

```text
client-a → nacos-1: 注册 provider-a 成功
client-b → nacos-2: 查询实例列表
nacos-1  -X-  nacos-2: 同步链路中断
```

在恢复收敛前，两个客户端可能短暂看到不同列表。Consumer 的本地缓存还会把这个窗口继续延长。应用数据面必须有连接超时、重试、熔断和被动摘除，不能把所有正确性都压给注册中心。

## 3. Raft/JRaft 的设计目标

需要强一致变更的持久资源通常采用基于 Raft/JRaft 的路径。简化写路径：

```text
request
→ group leader
→ append log
→ majority replicate
→ commit
→ state machine apply
→ response/notification
```

它提供的是已提交操作的顺序和多数派安全，不保证所有 Follower 在同一微秒完成 Apply。失去法定多数时拒绝需要共识的写，是为了避免网络分区两侧同时确认冲突状态。

尾延迟常由以下因素放大：

- Leader 所在节点 CPU/GC；
- Raft 日志持久化；
- 多数派节点间 RTT；
- Apply 队列；
- Snapshot、日志压缩或磁盘抖动；
- 选举和 Leader 切换。

## 4. Config 不能简单画成一条 Raft 线

在集群部署中，配置服务通常还涉及共享关系数据库、服务端变更通知、长连接推送和客户端本地快照：

```text
publish config
→ authentication/validation
→ persistent database transaction
→ change notification
→ server push
→ client listener
→ application refresh
```

因此要分别验证：

- 数据库是否已提交；
- 其他 Nacos 节点何时感知变更；
- 客户端何时收到推送；
- 应用是否成功执行动态刷新；
- 刷新失败时是否仍使用旧配置。

“控制台已经显示新值”不能证明所有应用已使用新值。配置一致性、发布传播和应用生效是三个阶段。

## 5. AP/CP 标签的正确用法

CAP 只描述发生网络分区时一致性与可用性的取舍，不描述以下问题：

- 正常状态下的复制延迟；
- 客户端缓存能陈旧多久；
- 写成功响应等待了哪些步骤；
- 业务框架何时应用新列表；
- 数据面是否有重试和熔断；
- 恢复后如何证明已经收敛。

更好的分析模板：

| 问题 | 需要得到的证据 |
| --- | --- |
| 谁负责这条数据 | Service 类型、数据 key、负责节点或 Raft Group |
| 写成功等待谁 | 请求日志、数据库提交、Raft commit 或 Distro ack |
| 从哪里读 | Server 本地视图、共享 DB、Consumer 缓存 |
| 何时对订阅者可见 | Push 日志、客户端事件时间、缓存版本 |
| 分区时是否接受写 | 实际 API 结果、超时和错误码 |
| 恢复如何收敛 | 节点摘要、实例列表、客户端缓存和实际调用目标 |

## 6. 四条时间线必须分开

一次变更至少有四个完成点：

```text
T1: API 返回成功
T2: 服务端各副本/数据库状态稳定
T3: Consumer 收到通知并更新缓存
T4: 新请求实际使用新实例或新配置
```

生产变更不能只测 T1。真正影响业务的是 T4，T1 到 T4 的差值才是控制面传播窗口。

## 7. 故障矩阵

三节点实验集群至少覆盖：

| 故障 | 临时实例注册/发现 | 持久资源变更 | 配置发布 | 需要观察 |
| --- | --- | --- | --- | --- |
| 停止一个非关键节点 | 通常应继续 | 有多数派时继续 | DB/服务路径健康时继续 | 客户端是否切换 |
| 停止 Raft Leader | 选举窗口可能抖动 | 选举后恢复 | 取决于具体路径 | Leader 切换时间 |
| 节点间网络分区 | 可能出现视图差异 | 少数侧应不能确认强一致写 | 分别验证 DB 与通知 | 两侧响应与收敛 |
| Nacos 与 DB 断开 | Naming 运行时状态可能部分继续 | 分类型验证 | 发布通常受影响 | 连接池、失败重试 |
| Consumer 与 Nacos 断开 | 使用旧缓存 | 不适用 | 收不到新推送 | 旧缓存安全窗口 |

“通常”不能替代验收，目标版本和部署模式必须实际验证。

## 8. 可复现实验设计

准备：

- 三个 Nacos Server；
- 独立外部数据库；
- 两个 Provider、两个 Consumer；
- 一个临时服务和一个持久服务；
- 一条可动态刷新的配置；
- 统一时钟与 request_id 日志。

### 8.1 实验一：少数节点故障 {/* #实验一少数节点故障 */}

1. 记录所有节点的服务视图；
2. 停止一个节点；
3. 从仍存活节点分别执行注册、查询、持久资源修改和配置发布；
4. 记录 API 延迟、Consumer 收到事件时间和实际调用目标；
5. 恢复节点，观察数据追赶和客户端收敛。

### 8.2 实验二：网络分区 {/* #实验二网络分区 */}

将三节点分成 1/2 两侧，仅在隔离实验环境阻断节点间通信：

1. 两侧分别查询同一服务；
2. 尝试注册临时实例；
3. 尝试修改需要共识的持久资源；
4. 尝试发布配置并检查数据库；
5. 恢复网络后比较所有节点与 Consumer 的最终视图。

必须记录错误码和超时，不能只写“成功/失败”。

### 8.3 实验三：服务端一致但客户端陈旧 {/* #实验三服务端一致但客户端陈旧 */}

1. 让 Consumer 正常订阅；
2. 阻断该 Consumer 的 Nacos 连接；
3. 在服务端下线一个 Provider；
4. 证明服务端视图已经变化；
5. 观察 Consumer 是否仍调用旧 Provider；
6. 恢复连接并记录 T1 到 T4 的收敛时间。

这个实验能说明为什么 AP/CP 标签不足以解释真实请求。

## 9. 可观测证据

按层收集：

| 层 | 证据 |
| --- | --- |
| API | 请求类型、目标节点、耗时、错误码 |
| Distro | 负责节点、同步/校验失败、数据摘要 |
| Raft/JRaft | Group、Leader、Term、Commit/Apply、选举 |
| Database | 连接池、事务延迟、锁、可用性 |
| Push | 待推送任务、连接数、推送成功/失败 |
| Client | Server 列表、连接状态、缓存版本、事件时间 |
| Data plane | 最终 Provider IP、配置版本、请求结果 |

日志必须能用 service、namespace、group、client ID 或 request_id 关联，不能依靠人工对时间猜测。

## 10. 生产设计原则

- 临时和持久服务分开规划，不在同一服务身份中混用；
- Nacos Server、外部数据库和客户端连接分别设置 SLO；
- 控制面超时不能触发无限重试风暴；
- 配置发布要带版本、灰度、验证和自动回滚；
- Consumer 使用旧缓存必须有最大安全时间和数据面保护；
- 节点跨故障域部署，同时控制节点间 RTT；
- 升级前用真实 SDK/Server 组合重跑故障矩阵。

## 11. 验收题

- 为什么临时实例适合不同于持久服务的复制路径？
- Distro 恢复收敛前，两个 Consumer 可能看到什么？
- Raft 失去多数派为什么拒绝需要共识的写？
- 配置数据库已经更新，为什么应用仍可能使用旧值？
- T1“API 成功”和 T4“真实请求生效”之间有哪些步骤？
- 如何证明服务端、客户端缓存与数据面最终全部收敛？
