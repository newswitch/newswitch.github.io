# 服务数、实例数、配置数、推送连接与容量压测

## 容量维度

```text
Naming: services × instances × metadata × change rate × subscribers
Config: dataIds × content size × publish rate × listeners
Connection: SDK clients × long connections × reconnect storm
Storage: external DB rows/index/backup + logs
```

平均注册数不足以定容，发布/扩容/机房网络恢复时的推送和重连风暴决定峰值。

## Server/JVM

观察 Heap/GC、连接、线程池/队列、gRPC、Distro/Raft、数据库池、CPU 和网络。多个模块同进程竞争资源；纯微服务场景可使用目标版本 function mode 减少不需模块。

## 数据库

外部 DB 的连接数、事务/慢 SQL、IOPS、HA 和备份同样是瓶颈。Nacos 节点扩容会乘数据库连接池，先计算总连接。

## 压测

固定 Server/SDK 版本和三节点拓扑，模拟注册/注销、心跳、订阅、配置读取/发布、节点故障和所有客户端重连。报告 P95/P99、推送收敛时间、错误、GC/DB/网络和恢复。

## SLO

分别定义注册/发现、配置发布到全实例生效、控制面可用和旧缓存容忍时间。

## 验收题

- 为什么连接恢复比稳态更考验容量？
- Nacos 扩节点如何增加 DB 连接？
- 发布 API P99 与全实例生效时间有何不同？
- 元数据过大怎样影响推送？
