# 服务数、实例数、配置数、推送连接与容量压测

> 版本基线：Nacos 3.2；最后核验：2026-08-18。官方历史性能数字只能作参考，生产容量必须使用自己的 SDK、元数据大小和故障模型复测。

容量不是“集群能存多少服务”，而是它在一次发布、批量扩容、Server 滚动或网络恢复时，能否在 SLO 内把正确视图送到全部 Client。

## 1. 先定义四类 SLO {/* #先定义四类-slo */}

| 能力 | 建议测量点 | 示例目标形式 |
| --- | --- | --- |
| 配置查询 | Client 发起 → 返回内容 | P99、错误率 |
| 配置收敛 | 发布成功 → 全部目标应用 effective hash 生效 | 99%/100% 收敛时间 |
| 注册发现 | Provider 注册 → Consumer 可选中 | P99 收敛、陈旧实例时间 |
| 控制面恢复 | Server/网络故障 → Client 重连并恢复意图 | 最大恢复时间、缓存容忍时间 |

管理 API 延迟与业务收敛时间是两个不同指标。发布 P99 很低，但 Listener 回调、Client 重连或框架刷新很慢，业务仍然不达标。

## 2. 六张容量账 {/* #六张容量账 */}

```text
Naming state    = services × instances/service × metadata bytes
Naming fan-out  = instance changes/s × subscribers/service × pushed view bytes
Config state    = formal configs + gray versions + history × content bytes
Config fan-out  = publishes/s × listeners/config × query/result bytes
Connection      = SDK processes × SDK instances/process × gRPC connections
Persistence     = DB rows/index/history + backup + logs + local dump
```

还要单独统计 AI Registry、管理查询、模糊监听和全量列表等平台流量。它们数量可能少，但响应大、遍历广，不能与普通 Client 查询混为一个 QPS。

平均注册数不能定容。大规模 Deployment 扩容、配置批量发布、机房网络恢复或 Server 滚动会同时触发连接建立、认证、Redo 注册、订阅恢复和全量视图下发，峰值常由这个“恢复风暴”决定。

## 3. 配置容量保护不等于性能承诺 {/* #配置容量保护不等于性能承诺 */}

Nacos 3.2 默认配置容量控制包含 Cluster/Namespace/Group 的 `quota`、当前 `usage` 和单配置 `maxSize`。官方当前默认值包括集群正式配置 100000、Tenant/Group 200、单项约 100 KiB；灰度版本不作为独立正式配置计数。

这些是防止无界增长的保护默认值，不表示某规格集群在这些上限下仍满足你的 SLO。提高 quota 前要重新测数据库、Dump、查询、启动恢复、备份和 Console 大列表行为。

配置内容也不应逼近上限长期使用。大文件增加数据库与网络负载、Client 解析时间和发布风暴成本；模型、证书包和大规则集应放对象存储或专用系统，Nacos 保存小型控制信息和引用。

## 4. Server/JVM {/* #serverjvm */}

多个模块共享 JVM、线程、网络和数据库池。按节点采集：

- CPU 使用、Throttle、Load、Heap/Old Gen、Direct Memory、GC pause/frequency；
- HTTP/gRPC 请求、连接数、活跃/重连、线程池 active/queue/reject；
- Naming 服务/实例/订阅者、推送量/失败/重试、Distro 同步；
- Config 数量/历史、Listener、查询/发布、Dump 任务与失败；
- JRaft Leader/Term/Apply、成员健康、7848/9849 网络；
- 数据库池 active/wait/timeout、SQL P99、锁、IOPS 和连接总数。

不要只看集群汇总；单节点连接倾斜、单机 GC 或单 AZ 网络异常会被平均值掩盖。Micrometer Timer 会导出带 `_seconds_count`、`_seconds_sum` 等后缀的序列，先在目标版本 `/actuator/prometheus` 中确认真实名称和 Label，再写告警。

## 5. 数据库 {/* #数据库 */}

外部数据库保存配置、历史、权限和持久 Naming 等权威数据。Nacos 扩容会把每节点连接池叠加：

```text
数据库最大连接需求
≈ Nacos 节点数 × 每节点池上限
 + Console/维护工具
 + 备份、迁移和监控连接
 + 安全余量
```

扩 Nacos 前先检查数据库是否允许新增连接；否则应用层增加节点反而制造连接等待。压测同时记录数据库事务、慢 SQL、锁、Buffer Cache、IOPS、复制延迟与故障切换时间。

## 6. 压测环境与工作负载 {/* #压测环境与工作负载 */}

固定以下变量并写进报告：Nacos Server/Client/JDK/插件版本、三/五节点拓扑、数据库规格和 Schema、认证/TLS、VIP/LB、单配置/元数据大小、Client 进程数及每进程 SDK 实例数。

分阶段测试：

1. **正确性基线**：小流量验证注册、订阅、发布、Listener 和权限。
2. **稳态阶梯**：逐级增加服务、实例、配置、连接与变更速率，持续跨越 GC、Dump 和数据库检查周期。
3. **变化风暴**：批量扩缩容、Provider 上下线、配置批量发布、热点服务大订阅扇出。
4. **故障测试**：滚动一个 Server、杀 Leader、数据库延迟/短时不可用、9848 中断、一个 AZ 隔离。
5. **恢复风暴**：让全部 Client 断开后分批/同时恢复，观察认证、连接、Redo 和推送。
6. **降级边界**：验证 Cache/Fallback 在控制面不可用期间能支撑多久，恢复后多久回到权威视图。

每一阶段报告 QPS、P50/P95/P99/P999、错误/超时、全实例收敛分布、陈旧视图时间、Server/JVM/DB/网络指标。只报告平均值和“无错误”不能说明尾部 Client 是否永远没有收敛。

:::warning
配置发布、注册和批量变更会真实改变 Nacos 状态。压力测试必须使用隔离集群和专用 Namespace，提前设计清理与 quota；不要在生产直接运行破坏性压测。
:::

## 7. 找到安全容量，而不是最大容量 {/* #找到安全容量而不是最大容量 */}

把压力逐级提高，找到第一个违反任一 SLO 的点；再从它向下保留节点故障、数据库故障、发布风暴和未来增长余量。安全容量还必须满足“Nacos 少一个节点仍达标”，不能直接采用健康集群极限值。

扩容决策按瓶颈层进行：

| 证据 | 更可能的瓶颈 | 优先动作 |
| --- | --- | --- |
| CPU/队列高，DB 正常 | Server 计算/线程 | 降低大查询和推送扇出，评估扩节点 |
| DB pool wait、SQL P99 高 | 外部数据库 | 修连接/索引/IO/HA，再考虑节点数 |
| 单节点连接远高于其他节点 | LB/Client 地址倾斜 | 修负载策略和长连接分布 |
| 稳态正常，恢复时超时 | 重连/认证/Redo 风暴 | 客户端抖动退避、分批恢复、流控 |
| 发布快但应用收敛慢 | Client/框架回调 | 查 9848、Listener、线程池和 effective hash |
| Heap 高且 GC 频繁 | 连接、缓存、元数据或大视图 | 缩小资源/订阅范围，做 Heap 取证 |

流控插件应先以 monitor 模式观察命中和阈值，再进入 intercept；如果误限 Client 重连或配置查询，可能放大控制面故障。

## 8. 容量评审模板 {/* #容量评审模板 */}

```text
当前 / 12 个月目标：Service、Instance、Config、Listener、Client connection
P50/P99：Config bytes、Instance metadata bytes、Subscribers per service
稳态 / 峰值：Register、Deregister、Publish、Query、Push events per second
SLO：查询 P99、发现收敛、配置 99%/100% 收敛、故障恢复
容错：失去 1 Server、DB failover、1 AZ 网络故障
余量：CPU、Heap、Connection、DB pool、IOPS、Network、quota
```
