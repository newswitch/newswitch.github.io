# 服务注册、订阅、健康检查、客户端缓存与负载均衡

> 版本基线：Nacos 3.2；最后核验：2026-08-18。Nacos 2.x 的 HTTP 心跳、长连接和 SDK 行为存在差异，升级前必须重新执行本文实验。

服务发现不是“把 IP 写进注册中心”这么简单。一次调用真正经历的是：

```text
provider 完成初始化
→ 注册 Instance 并维持存活
→ Nacos 形成服务发现视图
→ 推送或通知订阅者
→ consumer 更新本地缓存
→ 框架过滤候选实例
→ 负载均衡选择目标
→ 建立连接并发起 RPC
```

任何一层状态不一致，都可能出现“控制台看着正常，但请求仍打到旧 IP”的现象。

## 1. 资源模型决定你查的是不是同一个服务

Nacos 服务标识不只有 `serviceName`：

```text
namespace
  └─ group
      └─ service
          └─ cluster
              └─ instance(ip, port, metadata)
```

排障时必须同时核对：

- Namespace 是否一致；
- Group 是否一致；
- Service 名称和大小写是否一致；
- Cluster 是否被客户端筛选；
- Instance 的 IP、端口、enabled、healthy 和 metadata；
- Provider 与 Consumer 使用的 SDK/配置中心 Profile 是否相同。

“控制台能看到”只证明管理视图中存在对象，不一定等于某个 Consumer 的运行时发现视图。

## 2. 临时与持久实例

当前 Nacos 模型中，ephemeral/persistent 是服务生命周期和一致性路径的重要语义。不要在同一服务身份下随意混用两类实例。

| 类型 | 适合对象 | 故障后的主要行为 | 需要重点验证 |
| --- | --- | --- | --- |
| 临时实例 | 随进程存活的应用副本 | 连接/心跳失效后从发现视图移除 | 摘除窗口、客户端旧缓存 |
| 持久实例 | 需要保留管理状态的资源 | 进程离线不等于对象被删除 | 主动健康检查、人工恢复 |

临时实例强调运行时可用性，持久实例强调资源状态不能因为一次断连就消失。具体心跳、长连接、探测和复制实现随 Server/SDK 版本变化，部署前必须验证兼容矩阵。

## 3. Provider 注册路径

Provider 的正确启动顺序：

```text
读取配置
→ 初始化线程池/连接池/模型
→ 完成本地健康检查
→ 开始监听业务端口
→ 注册为可用实例
→ readiness 成功
```

如果先注册、后初始化，Consumer 可能在 Provider 尚不能服务时收到新实例。

Java SDK 的最小语义示例：

```java
Properties properties = new Properties();
properties.put("serverAddr", System.getenv("NACOS_SERVER"));
properties.put("namespace", System.getenv("NACOS_NAMESPACE"));

NamingService naming = NamingFactory.createNamingService(properties);

Instance instance = new Instance();
instance.setIp("10.0.1.23");
instance.setPort(8080);
instance.setClusterName("zone-a");
instance.setWeight(1.0);
instance.setHealthy(true);
instance.setEnabled(true);
instance.setEphemeral(true);
instance.addMetadata("version", "v2");

naming.registerInstance("order-service", "DEFAULT_GROUP", instance);
```

示例用于展示字段关系；实际项目应由框架集成管理生命周期，并使用与 Server 匹配的 Nacos Client 版本。不要把 Pod IP、宿主机 IP 和 Service VIP 混为一谈。

## 4. 优雅下线不是只调用 deregister

推荐时间线：

```text
1. readiness=false，不再接收新入口流量
2. 将实例禁用或注销
3. 等待 Nacos 推送传播
4. 等待 Consumer 本地缓存刷新
5. 排空已有 HTTP/RPC 长连接
6. 等待在途请求完成
7. 终止进程
```

直接终止进程会产生三个窗口：

- Nacos 尚未判断实例失效；
- Nacos 已摘除，但 Consumer 尚未收到或应用变更；
- Consumer 已更新列表，但连接池仍复用旧连接。

因此 Pod 的 `terminationGracePeriodSeconds`、preStop、readiness、SDK 注销和应用连接排空必须协同设计。

## 5. Subscription、Push 与本地缓存

Consumer 通常先获取一次服务视图，再通过订阅接收变化，并保存本地缓存：

```text
full snapshot
→ subscribe
→ receive change event
→ validate/version compare
→ replace local service view
→ notify load balancer
```

本地缓存带来控制面故障时继续调用的能力，也带来陈旧风险：

| 故障 | Consumer 可能看到什么 |
| --- | --- |
| Nacos 短时不可用 | 继续使用最后一次缓存 |
| Provider 已崩溃 | 摘除前仍可能选择旧实例 |
| Push 通道异常 | Server 已更新，客户端仍旧 |
| Consumer 重启且 Nacos 不可用 | 取决于本地故障转移缓存及 SDK 策略 |

应用必须给业务 RPC 配置超时、重试和熔断。注册中心不能替代数据面健康保护。

## 6. 健康、启用和保护阈值

候选实例通常要经过多层筛选：

```text
service instances
→ cluster/metadata selector
→ enabled
→ healthy
→ protection/failover policy
→ client load balancer
```

`healthy=true`、`enabled=true`、权重非零表达的语义不同：

- healthy：健康检查或运行时存活判断；
- enabled：运维上是否允许进入发现视图；
- weight：候选实例之间的相对选择权重；
- metadata：版本、机房、能力等自定义筛选信息。

不要通过把权重设为零替代所有下线流程；不同 SDK 和负载均衡实现对零权重、缓存与已有连接的处理可能不同。

## 7. 负载均衡究竟由谁执行

Nacos 提供发现信息，不等于它代理每次业务请求。常见路径是：

```text
Nacos: 返回候选实例和属性
Client/Framework/Gateway: 选择实例
HTTP/RPC client: 建连与发送
```

因此配置权重后必须验证具体调用框架：

- 是否真的读取 Nacos weight；
- 是否优先同 Cluster/Zone；
- 是否支持标签或版本路由；
- 是否对新实例慢启动；
- 被动失败是否临时摘除；
- 重试会不会继续命中同一故障实例；
- 长连接何时重建。

问题可能出在 Spring Cloud LoadBalancer、Dubbo、网关或自研 SDK，而不是 Nacos Server。

## 8. 四视图排障法

不要只截一张控制台页面，应同时保存四个视图：

| 视图 | 要回答的问题 |
| --- | --- |
| Provider | 注册参数、连接状态、注销日志是否正确 |
| Nacos Server | 管理视图与运行时发现视图是否一致 |
| Consumer | 本地缓存包含哪些 IP，最后更新时间是什么 |
| 实际请求 | TCP/RPC 最终连接到了哪个 IP、端口和版本 |

建议给每次调用记录：

- consumer instance；
- selected provider IP/port；
- provider version/zone；
- request/trace ID；
- 重试次数和失败原因。

只有把客户端选择结果和真实连接目标记入日志，才能证明“负载均衡到底选了谁”。

## 9. 可复现实验

准备一个独立 Nacos 集群、两个 Provider 和一个持续调用的 Consumer：

```text
provider-a: 10.0.1.11:8080, zone-a, version=v1
provider-b: 10.0.2.12:8080, zone-b, version=v2
consumer: 每秒调用一次并记录目标实例
```

### 9.1 实验一：注册与订阅 {/* #实验一注册与订阅 */}

1. 仅启动 provider-a，确认 Consumer 缓存和实际目标；
2. 启动 provider-b，记录 Server 变化到 Consumer 首次调用它的时间；
3. 对比控制台更新时间、Consumer 收到事件时间和真实请求时间；
4. 修改 metadata，确认框架是否会据此筛选。

### 9.2 实验二：优雅下线与强制终止 {/* #实验二优雅下线与强制终止 */}

分别执行：

- A 组：readiness 失败 → 注销 → 排空 → 退出；
- B 组：直接终止进程。

记录错误请求数、旧实例最后一次被选择时间、连接池最后一次复用时间。由结果确定生产环境需要的下线等待窗口。

### 9.3 实验三：控制面中断 {/* #实验三控制面中断 */}

1. 保持 Consumer 持续调用；
2. 暂停 Consumer 到 Nacos 的连接，但不影响到 Provider 的数据面；
3. 观察旧端点是否继续工作；
4. 此时终止一个 Provider，记录陈旧缓存造成的失败；
5. 恢复 Nacos 连接，确认缓存和实际目标最终收敛。

网络故障注入只能在隔离实验环境进行，并准备明确回滚。

## 10. 生产验收

- Provider 未就绪前不会注册为可用；
- 正常下线不会产生明显错误尖峰；
- Consumer 能输出本地实例列表和最后更新时间；
- Nacos 中断时有界使用旧缓存，不发生无限重试；
- 权重、Zone 和 metadata 路由经过真实请求验证；
- 可以从请求日志反查最终 Provider；
- SDK/Server 版本兼容关系和升级回滚已记录。
