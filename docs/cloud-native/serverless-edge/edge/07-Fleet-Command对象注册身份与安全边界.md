# Fleet Command 对象注册身份与安全边界

Fleet Command 把分散的边缘系统纳入集中应用管理，但集中管理不意味着一个云端状态可以代替现场全部事实。需要分别理解位置、物理系统、应用制品、部署意图和运行结果。

本篇区分 2021 年架构、2022 年配对与远程访问说明，以及[公开 NGC CLI 参考](https://docs.ngc.nvidia.com/cli/cmd_fleet-command.html)的接口约束，不将历史供应条件作为当前服务承诺。通用安全模型与已公开的产品流程分别说明；教学阶段不是未公开的内部状态枚举。先读[边缘生命周期](./06-Fleet-Command与边缘AI生命周期.md)。

## 1. 位置 系统 应用与部署

位置描述站点边界，系统是承担执行的设备，应用是可部署软件，部署表达将何种应用及配置放在哪些目标上。公开架构使用 Kubernetes 和 Helm 分发容器化应用，因此不能只把一个镜像 Tag 当成完整应用版本。[官方架构问答](https://developer.nvidia.com/blog/accelerated-edge-ai-with-metropolis-and-fleet-command/)说明了这种分工。

教学例子：同一个门店有两台 GPU 服务器，部署一个视频分析应用。门店身份不等于两台机器的身份；部署目标存在不证明两台都已取得制品；Pod 启动不证明摄像头输入、模型版本及业务输出正常。

记录关系应能从应用发布追踪到站点、具体系统、镜像 Digest、Chart 版本、配置与模型修订，以及运行中的实际结果。不要用服务器 IP 作为永久主键，地址可以变化或被其他设备复用。

## 2. 注册建立信任 不只是建立连接

```text
现场资产与组织归属确认
→ 获取受限的注册资格
→ 验证目标管理端身份
→ 设备身份与管理对象关联
→ 授予日常管理能力
→ 验证遥测和应用交付
```

这些阶段用于检查安全不变量，不规定某个产品必须采用何种证书字段。引导凭据应受目标、用途和有效期约束；长期设备身份则要支持轮换、审计与退役。注册完成后不应继续保留可在任意设备上重复使用的高权限引导材料。

反例：将注册配置复制到另一台机器后，两台同时报告为同一系统。即使连接都成功，资产账本、告警和发布结果也可能互相覆盖。发现这种情况应先冻结有风险的远程变更，核对真实设备，不能仅靠改一个显示名称修复身份冲突。

### 2.1 公开的激活码配对流程

[2022 年 LaunchPad 流程说明](https://developer.nvidia.com/blog/?p=44519)给出了具体配对顺序：先创建 Location，在其中添加 System，取得激活码；现场系统完成初始安装后输入该码，再由管理界面确认已配对并可远程管理。创建云端 System 记录不是物理服务器已经接入。

CLI 的 `add-system` 示例也返回配对码、到期倒计时与系统 `CONNECTING` 状态。这证明该示例涉及有时效的配对材料，但不是所有版本固定有效期的承诺，也没有说明完整证书链、单次使用规则或硬件证明协议。激活码应按敏感引导材料处理，不能写进博客、工单公开截图或镜像。

按信任阶段定位失败，才能判断下一份证据是什么：

| 已知事实 | 尚不能证明 | 需要继续确认 |
| --- | --- | --- |
| 管理端已有 System 对象 | 现场机器已认领该对象 | 现场配对结果与对象身份是否对应 |
| 安装器接受了一次输入 | 管理端已完成关联并收到新观察 | 管理端记录、现场结果和时间是否一致 |
| 系统显示可管理 | 有权拉取私有应用且业务输入有效 | 拉取者身份、制品权限与业务结果 |

例如输入码后浏览器超时，不应立刻删除系统再重复注册。先检查目标对象和现场状态；原关联可能已经成功，只是返回链路失败。是否能重用、重新签发或解绑激活码，要按目标服务的契约处理，不能从“有一个码”推导这些操作。

## 3. 一次身份不等于所有权限

设备到控制面的管理身份、系统登录身份、NGC 拉取身份、应用访问业务系统的身份，各自有不同的权限和撤销条件。统一身份提供方可以关联它们，却不会自然使授权集合相同。

| 权限 | 主要风险 | 需要独立确认 |
| --- | --- | --- |
| 查看状态与日志 | 现场数据或配置泄露 | 数据范围、保留期和脱敏 |
| 应用发布 | 在大量系统执行代码 | 目标集合、制品来源和审批 |
| 系统更新 | 设备失联或业务中断 | 恢复通道、兼容和维护窗口 |
| 远程调试 | 读取或修改现场系统 | 操作者、时效和操作审计 |
| 制品拉取 | 私有软件和模型外泄 | Registry/组织范围与轮换 |

这是一份授权设计表，不声称产品已经提供任意细粒度权限。采用实际平台时应验证支持的粒度，而不是用管理员账户替代缺失的授权设计。

还有一条可从较新的资料独立核对的产品边界：[NGC Catalog 用户指南](https://docs.nvidia.com/ngc/latest/ngc-catalog-user-guide.html#ngc-api-keys)仍单列 Fleet Command 对 Personal Key 的支持例外，并指向 Legacy Key。这只说明不能把通用 NGC Key 建议无条件套到该服务，不证明历史注册命令或控制台操作今天仍然有效。文档中的弃用计划也不能被解释为实际服务已经停用；须核对目标账户、服务授权和当期接口要求，不在博客中放真实密钥。

组织成员与服务角色的主归属见[NGC 身份与权限](../../containers/images/02-NGC镜像身份权限与制品生命周期.md)。Fleet Command 的 `apikey set` 则用于私有 Helm、模型和容器仓库的访问凭据，不是现场配对码，也不能靠设置它授予操作者远程控制权。

### 3.1 创建时的安全配置可能决定替换边界

公开 CLI 把部分设备访问、Host 路径和特权能力定义为部署创建时的安全开关，且注明有关选项变更需要重建 Deployment，并有站点版本前提。这是明确的生命周期约束，不能默认全部权限都支持原地热修改。

教学例子：应用上线后才发现需要访问额外 Host 资源。先确认目标依赖是否合理，再判断配置变更是否跨过替换边界；若需要重建，应纳入流量、状态和恢复计划。不能为了避免替换，直接把所有特权提前打开。

### 3.2 远程应用访问会改变谁能到达服务

CLI 的 `remote app-access` 提供本地应用代理，而 `--allow-external-traffic` 会把流量入口扩展到所有接口。这个参数改变的是可达范围，不是普通诊断输出选项。

代理终点仍可能拥有敏感业务能力。即使远端身份验证成立，也要核对本机监听、网络边界与会话结束条件；共享工作站或跳板机尤其不能默认只有当前操作者能访问。会话安全不能只看远端系统是否开启了 SSH。

### 3.3 远程授权是多层条件的交集

[2022 年远程管理说明](https://developer.nvidia.com/blog/remotely-operating-systems-and-applications-at-the-edge/)描述了角色控制、按需授予的 JIT 权限与有时限的会话；[2023 年说明](https://developer.nvidia.com/blog/bringing-data-center-management-features-to-the-edge/)补充动态证书认证与授权的安全隧道。这些能力没有给出每个版本的角色名称和逐动作权限矩阵，不能由此假定承包商只能访问某一站点。

可用下面的检查模型理解一次访问，变量是分析用的条件，不是产品字段：

```text
允许本次操作 = 服务资格 ∧ 操作者动作权限 ∧ 目标范围
             ∧ 功能已开启 ∧ 会话仍有效 ∧ 现场身份接受操作
```

任何一项不成立，都不能由“用户能登录”补足。应用代理打通后，应用自己的登录和业务授权也不能省略；隧道终止则不等于撤销长期操作者身份。

会话总时限与空闲时限也不同。教学条件：会话最长 30 分钟，连续空闲最长 5 分钟。持续输入可能避免空闲超时，却不应绕过总时限；第 10 分钟撤销操作者权限时，既有会话是否马上终止仍需服务契约确认，不能拿最长 30 分钟反推即时撤销。撤权、会话结束、现场进程停止应分别核对。

## 4. 启动安全 制品签名与业务正确性

NVIDIA 的历史产品资料描述签名容器、静态加密及安全启动等分层机制。[产品资料](https://www.nvidia.com/content/dam/en-zz/Solutions/gtcf20/fleet-command/gtcf20-nvidia-fleet-command-datasheet-us-1433255-r5-web.pdf)中的能力需要结合所用平台和配置理解。

安全启动主要约束启动链，镜像签名回答制品身份和授权来源，漏洞检查关注已知问题，业务验证关注结果是否符合目标。它们不能互相替代：签名正确的软件也可能读取错误模型；启动链可信也不意味着应用无逻辑漏洞。

保留校验过的制品不够，还需要保护信任策略本身。若攻击者能修改允许的签名者或替换部署配置，就可能绕过原来的版本约束。离线制品图与签名关联见[OCI 信任链](../../containers/images/04-OCI索引Digest与离线镜像信任链.md)。

## 5. 断连使身份生命周期更复杂

假设某站点离线 20 天，而部署策略每 7 天轮换一次拉取凭据。已有进程可能仍在运行，但它重启或需要拉取新制品时，已经无法使用过期凭据。这不与“管理断连期间应用继续运行”矛盾，因为运行中的依赖和重建时依赖不同。

设计时应分别回答：最长离线时间是什么，哪些身份必须保持有效，离线时怎样处理过期，重新连接如何安全更新。不能通过无期限共享管理员密钥回避问题，也不能未经风险判断就让设备跳过服务端认证。

站点已被停用时，还要防止旧设备恢复联网后重新取得部署资格。管理对象删除、凭据撤销、数据处置和设备擦除是不同动作，退役需要逐项记录。

## 6. 审计绑定目标集合和修订

一次“向所有门店发布”的操作应保存当时的目标清单、版本、审批和逐站点结果。若执行时临时重新展开标签，新增站点可能在未经同等验证时被纳入。

并发管理员与断连旧设备还会产生新旧意图竞争。教学上可为部署使用单调修订号，要求站点报告自己已应用的修订，并拒绝过期动作；具体产品使用何种字段需查其接口，不把教学修订号当成真实 API 参数。

不要仅凭目标版本推算部署完成率。实际应用版本、设备身份、观察时间及业务验证必须一起回报，尤其不能将失联站点从分母悄悄移除。

## 7. 掌握检查

**设备已经注册，能否默认允许上传全部日志？** 不能，管理授权与数据处理授权不同。

**镜像签名正确是否意味着推理输出正确？** 不意味着，还需版本契约和业务测试。

**删除控制台里的系统是否等于安全退役？** 不等于，设备、凭据、现场数据和恢复联网行为仍要处理。

**取得激活码和出现可管理状态分别说明什么？** 前者是配对入口，后者是管理链路的观察；两者都不单独证明镜像授权、输入与业务输出正确。

**JIT 会话是否等于永久最小权限或即时撤权？** 不等于。还要确认目标范围、角色动作和既有会话失效规则。
