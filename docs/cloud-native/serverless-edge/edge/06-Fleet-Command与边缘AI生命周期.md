# Fleet Command 与边缘 AI 生命周期

Fleet Command 的公开产品定位是集中管理分散部署的边缘 AI 系统与应用。它与数据中心 BCM、Run:ai 或泛指的 GPU Fleet 工程不是同义词。以下以该定位讨论边缘管理原理，不把旧资料中的界面和命令当作当前可购买服务的承诺。

产品对象和配置语义补充采用当前可访问的 [NGC CLI Fleet Command 参考](https://docs.ngc.nvidia.com/cli/cmd_fleet-command.html)。CLI 接口、账户服务授权、站点 NodeStack 版本及服务端行为仍需匹配；公开命令入口不代表任何账户都可直接执行。

## 1. 三类对象

边缘系统是运行设备，位置表达站点与物理管理边界，部署表达要在哪些系统上运行何种应用版本。应用镜像、模型、配置和所需权限必须共同形成可追溯版本。

设备注册需要把真实资产与管理身份建立信任关系；知道 IP 地址不等于获准远程执行。证书或令牌的轮换、设备退役后的身份撤销，与应用升级同样属于生命周期。

### 1.1 Application AppConfig 与 Deployment

CLI 单列 Application、AppConfig、Deployment、Location/System：应用定义、YAML 配置、部署关系和运行目标不能互相替代。Deployment 关联应用、可选 AppConfig 与位置；应用显示名也不应未经核对就当成接口要求的应用标识。

教学例子：两个门店运行同一应用，但摄像头地址与区域参数不同。应用制品相同不代表配置相同，Deployment 名字相同也不保证实际内容没变。应保存应用身份、配置内容修订、目标集合与观察时间，而不只截一张部署列表。

### 1.2 缺省配置仍然是一份配置

该 CLI 规定：未提供 AppConfig 时使用 DEFAULT；`--appconfig-clear` 也是改用 DEFAULT，并不等于应用没有配置。清空自定义项因此可能改变应用行为，不能把这个动作理解为无影响的元数据清理。

推演：门店之前以定制配置选择摄像头 A，后来切回 DEFAULT。即使容器版本没变，输入源也可能改变；需要核对默认内容和实际运行输入，再判断输出是否正确。博客中的修订账本是运维设计，不假定产品已提供任意版本回溯功能。

## 2. 管理链与业务链

```text
集中控制面 → 注册和策略 → 站点侧系统与应用
本地输入    → 边缘推理   → 本地输出或业务系统
```

管理断连时，本地应用能否继续取决于实际部署、依赖和服务契约。不能因为控制面显示离线就宣告业务已停，也不能默认离线期间所有更新、身份和日志功能仍完整可用。

### 2.1 边缘位置高可用不等于业务零中断

NVIDIA 在 [2023 年功能介绍](https://developer.nvidia.com/blog/bringing-data-center-management-features-to-the-edge/)中描述了至少三系统位置的高可用，以及系统兼任控制与工作节点的模式。公开 CLI 进一步规定：创建位置时的 `--allow-high-availability` 让最先加入的三台系统成为 controller-workers，且该设置创建后不能修改。不能把“随后加到三台”直接等同于已经启用这项能力。

需要分开判断管理服务、位置控制面、应用副本和持久数据四种可用性。控制节点仍可工作，不会自动补回失去的 GPU、摄像头连接或本地磁盘数据；应用还需要合法落点、足够容量、可用数据和流量切换。控制面多数派的通用原理见[Kubernetes 控制面与 etcd](../../../gpu/bare-metal-fleet/base-command-manager/09-Kubernetes集群对象角色与初始化.md)，不据此补造 Fleet Command 的内部选举实现。

教学条件：三台系统各有 1 GPU，三个不可共享 GPU 的副本各占 1 GPU，暂不计控制组件开销。失去一台后只剩 2 GPU，最多承载两个副本；若要求单节点失效后仍容纳三个副本，同构系统数量至少满足 `N−1≥3`，即四台。这只是容量必要条件，尚未证明应用可以迁移，或时延、数据与故障域满足要求。

### 2.2 管理平台升级与站点升级不是同一件事

上述 2023 年介绍中的零停机管理更新指云端管理平台更新；它不能推导站点 NodeStack、驱动、MIG 重配或应用数据迁移都无中断。一次变更要先标明修改哪一层，再判断哪一层需要维护窗口和恢复计划。

## 3. 发布是多制品协调

教学场景：新模型要求新预处理逻辑，但只更新模型文件。容器仍启动成功，却可能输出错误结果。因此版本需要绑定镜像、模型、配置和接口契约；验证不仅是进程健康，还包括结果质量和业务延迟。

站点带宽、缓存、磁盘和断电条件不同，应先覆盖代表性 Canary，再按站点故障域分批。计划中明确下载、校验、激活和回退阶段，不让下载中的半份模型覆盖仍在使用的版本。

## 4. 断连和恢复的推演

假设 100 站点中 5 个在发布时断连，控制面目标版本变为 B，但这些站点仍运行 A。恢复网络后应核对每站点实际版本及发布策略，不能只根据全局目标显示 B 就认定全量完成。

故障恢复要保留现场可用版本、剩余存储和独立管理入口。回退应用版本不一定回退持久化数据格式，存在数据迁移时需要专门恢复协议。

## 5. 权限与数据

远程 Shell、系统升级、镜像拉取和日志上传具有不同权限及数据影响。边缘系统可能接触敏感现场数据，应明确哪些遥测和日志允许外传，不能以设备已注册替代数据授权。

## 6. 掌握检查

为什么应用已部署不证明模型版本一致？镜像、模型与配置是不同制品。为什么控制面恢复不代表站点全部恢复？管理、采集、应用及业务数据分别有状态和时效，需要逐层确认。

三台系统是否足以保证三副本应用在失去一台后仍完整运行？先计算失效后的资源形状，再检查数据与输入依赖；位置高可用开关本身不能回答。云端控制台无停机更新也不是站点升级无停机的证据。
