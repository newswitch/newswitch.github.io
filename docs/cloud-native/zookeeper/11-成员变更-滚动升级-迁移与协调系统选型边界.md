# 成员变更、滚动升级、迁移与协调系统选型边界

成员变更和版本升级都会触碰多数派、日志格式、协议兼容和 Session。安全原则是一次只改变一个变量，并在每一步等待 Ensemble 和客户端恢复稳定。

## 1. 成员变更

动态重配置允许通过受控 API 修改成员集合。变更前确认：

- 当前 Ensemble 健康且有多数派；
- 新节点版本、配置、身份、TLS 和数据盘合格；
- 新旧成员集合都不会因为同一故障域丢失多数派；
- 客户端连接字符串能够发现新节点；
- 监控覆盖同步进度和配置版本。

先增加并等待同步，再删除旧节点。不要同时替换多数成员。

## 2. 滚动升级

1. 阅读目标版本升级说明和兼容矩阵；
2. 备份配置、成员关系和数据；
3. 升级一个 Follower；
4. 验证加入、同步、读写和 TLS；
5. 逐个继续，Leader 放在可控步骤切换；
6. 全部升级后才启用不可逆新特性。

回滚能力取决于数据格式和协议兼容，不能把“二进制可以替换”当成一定能降级。

## 3. 迁移到新 Ensemble

若使用双集群，旧、新 ZooKeeper 不会自动保持强一致。常见方案是维护窗口导出/导入并切换，或由应用双写并做业务级校验。Ephemeral、Session 和 Watch 不能简单复制，客户端必须在新集群重新建立。

## 4. 与相邻系统的边界

| 需求 | 更自然的选择 |
| --- | --- |
| Kubernetes 控制面、Revision/Lease/Txn | etcd |
| 微服务注册与配置产品能力 | Nacos |
| Hadoop/HBase/Dubbo 生态、Session/Ephemeral Recipe | ZooKeeper |

迁移不是协议替换，而是重新实现数据模型、Watch/Lease、Session、ACL、客户端库和故障语义。先列出所有路径与 Recipe，再逐项设计等价行为。

## 5. 验收

成员变更或升级后，验证读写、CAS、Watch、Ephemeral 生命周期、Leader 切换、ACL 和失去单节点的行为。迁移完成还要停掉旧集群访问，证明应用没有隐藏依赖。
