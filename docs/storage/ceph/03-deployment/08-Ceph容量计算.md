# Ceph 容量规划：原始容量、可用容量、恢复预留与 Full 红线

《Ceph 从零基础到生产运维实战》第 8 篇

← [第 7 篇：部署前的集群规划](./07-部署前的集群规划.md)

「十台机器，每台 2 TB，做 Ceph 以后还能用多少？」

这是 Ceph 入门阶段最常见的问题，也是生产环境最容易计算错误的问题之一。

如果每台机器只有一块 2 TB 数据盘，那么磁盘标称原始容量是 20 TB，但业务真正能安全使用的空间一定小于 20 TB。中间至少要考虑：

- TB 与 TiB 的单位差异
- 三副本或纠删码的冗余开销
- Ceph 内部元数据和文件系统开销
- OSD 之间利用率不均
- 快照、克隆、版本和删除延迟
- nearfull、backfillfull、full 等阈值
- 最大 Host 或机架故障后的恢复空间
- 业务未来增长与运维缓冲

本篇将建立一套可以复用的容量计算方法。

## 1. 先区分四种容量 {/* #先区分四种容量 */}

### 1.1 标称容量 {/* #1-标称容量 */}

硬盘厂商一般使用十进制：

```text
1 TB = 1,000,000,000,000 Bytes
```

Linux 和部分 Ceph 输出可能以二进制单位显示：

```text
1 TiB = 1,099,511,627,776 Bytes
```

因此：

```text
2 TB ≈ 1.819 TiB
10 × 2 TB = 20 TB ≈ 18.19 TiB
```

看到 18.2 TiB 不代表丢了 1.8 TB，首先可能只是单位不同。

### 1.2 Raw Capacity：原始容量 {/* #2-raw-capacity原始容量 */}

所有 OSD 数据设备的容量总和称为原始容量。

```text
Raw = 所有 OSD 容量之和
```

它还没有扣除副本或纠删码开销。

### 1.3 Theoretical Usable：理论可用容量 {/* #3-theoretical-usable理论可用容量 */}

按保护策略换算出的理想业务容量：

```text
副本池理论可用 = Raw ÷ 副本数
纠删码理论可用 = Raw × k ÷ (k + m)
```

它假设磁盘利用率完全均匀、没有任何预留，也没有元数据和内部开销，因此不能直接作为生产可售容量。

### 1.4 Planned Usable：规划可用容量 {/* #4-planned-usable规划可用容量 */}

真正应该对业务承诺的是：

```text
规划可用容量
= 理论可用容量
- 恢复预留
- 增长预留
- 分布不均与内部开销
- 快照、版本和运维缓冲
```

换句话说，「Ceph 还能用多少」至少有两个答案：

1. 理论上能存多少
2. 生产上应该允许业务用到多少

后者通常更重要。

## 2. 副本池容量怎么计算 {/* #副本池容量怎么计算 */}

假设总 Raw 为 20 TB。

### 2.1 三副本 {/* #1-三副本 */}

```text
理论业务容量 = 20 TB ÷ 3 ≈ 6.67 TB
空间利用率 ≈ 33.3%
```

如果再按理论可用容量预留 20% 运维空间：

```text
规划上限示例 = 6.67 TB × 80% ≈ 5.33 TB
```

这里的 20% 只是说明算法，不是所有集群通用的安全值。若最大主机占总容量 20%、节点数很少或恢复窗口很严格，20% 可能仍然不够。

### 2.2 两副本 {/* #2-两副本 */}

```text
理论业务容量 = 20 TB ÷ 2 = 10 TB
空间利用率 = 50%
```

两副本看起来节约很多空间，但任意 PG 只剩两份完整数据。一个副本故障后只剩最后一份，恢复期间再次故障就可能导致数据丢失。

因此不能为了容量把生产池随意改成两副本。保护级别应根据数据价值、故障域、备份和可用性目标决定。

### 2.3 副本开销不是「浪费」 {/* #3-副本开销不是浪费 */}

三副本带来的空间放大，换取的是：

- 多个完整副本
- 较直接的读写路径
- 相对简单的恢复
- 对随机写和 RBD 场景通常更友好
- 故障时仍可能继续提供 IO

不能只用「每 TB 价格」比较副本池与单机磁盘，还要计算可用性和恢复成本。

## 3. 纠删码容量怎么计算 {/* #纠删码容量怎么计算 */}

纠删码 k+m 中：

```text
k = 数据块数
m = 校验块数
```

### 3.1 EC 4+2 {/* #1-ec-42 */}

```text
理论可用 = 20 TB × 4 ÷ 6
          ≈ 13.33 TB

理论利用率 = 4 ÷ 6
           ≈ 66.7%
```

如果示例性预留 20%：

```text
规划上限示例 ≈ 13.33 TB × 80%
             ≈ 10.67 TB
```

### 3.2 EC 8+3 {/* #2-ec-83 */}

```text
理论利用率 = 8 ÷ 11 ≈ 72.7%
```

利用率比 4+2 高，但每个条带需要 11 个放置位置，故障域数量、网络、CPU、恢复读放大和小 IO 成本也更高。

### 3.3 为什么不能只追求更大的 k {/* #3-为什么不能只追求更大的-k */}

更大的 k 通常提高空间利用率，但同时可能带来：

- 需要更多独立故障域
- 恢复一个缺失块时读取更多数据块
- 编解码消耗更多 CPU
- 小对象、小随机写的放大更明显
- 故障和维护期间更难满足完整放置

纠删码适合大对象、顺序 IO 和容量效率优先的场景，但是否适用于特定 RBD、CephFS 或 RGW 负载，需要按当前 Ceph 版本和业务实测。

## 4. 十台 2 TB 机器到底能用多少 {/* #十台-2-tb-机器到底能用多少 */}

假设：

```text
10 台服务器
每台 1 块 2 TB OSD 数据盘
Raw = 20 TB ≈ 18.19 TiB
故障域 = host
```

理论结果如下：

| 保护方式 | 理论业务容量 | 示例预留 20% 后的上限 |
| --- | --- | --- |
| 两副本 | 10.00 TB | 8.00 TB |
| 三副本 | 6.67 TB | 5.33 TB |
| EC 4+2 | 13.33 TB | 10.67 TB |
| EC 8+3 | 无法满足 11 个独立 Host 放置 | 不适用 |

这里必须补充三个条件。

### 4.1 条件 1：每台一块盘的 10 台集群，单 Host 占 Raw 的 10% {/* #条件-1每台一块盘的-10-台集群单-host-占-raw-的-10 */}

一台 Host 故障会损失约 2 TB 原始容量。剩余 9 台既要承载业务，又要接收恢复数据。

如果故障前已接近容量阈值，Recovery 可能无法完成，甚至触发 `backfillfull` 或 `full`。

### 4.2 条件 2：实际分布不会完全平均 {/* #条件-2实际分布不会完全平均 */}

CRUSH 会尽量分散数据，但不同 PG 大小、池规则、设备权重和历史变更都会产生偏差。某个 OSD 可能先达到阈值，即使集群总平均使用率还不高。

### 4.3 条件 3：十台机器不代表只有十块盘 {/* #条件-3十台机器不代表只有十块盘 */}

真实生产服务器通常每台有多块 OSD 盘。容量计算应基于全部 OSD 的实际 Raw，同时按最大 Host 的容量占比预留，而不是只数服务器。

所以，对这个例子更准确的回答是：

> 20 TB 是标称 Raw。三副本理论约 6.67 TB，EC 4+2 理论约 13.33 TB；生产可用还必须根据最大 Host 故障、阈值、分布不均、快照和增长继续打折，不能只凭「预留 20%」直接承诺。

## 5. 为什么恢复空间必须单独计算 {/* #为什么恢复空间必须单独计算 */}

假设一个三副本集群有 5 台相同容量的 OSD 主机，每台占 Raw 的 20%。

一台主机故障后：

1. 该主机上的 OSD 离线
2. 大量 PG 变为 `degraded` 或 `undersized`
3. Ceph 需要在剩余 4 台上重建缺失副本
4. 剩余主机的空间和写入带宽同时承受恢复压力

如果故障前集群 Raw 使用率已经达到 85%，粗看还剩 15%，但最大主机占 20%。此时剩余空间可能无法容纳全部恢复数据，而且利用率不均会让某些 OSD 更早触发红线。

### 5.1 一个实用的规划思路 {/* #1-一个实用的规划思路 */}

至少同时考虑：

```text
最大故障域的 Raw 占比
+ OSD 利用率偏差
+ Full 阈值之前的安全距离
+ 故障期间新增业务数据
+ Recovery 产生的性能压力
```

如果要求容忍整个 Rack 故障，就必须按最大 Rack，而不是最大 Host 计算。

### 5.2 容量预留与恢复时间是两件事 {/* #2-容量预留与恢复时间是两件事 */}

有空间不代表能按时恢复。恢复时还需要：

- 磁盘读取和写入带宽
- OSD CPU
- 网络带宽
- 足够的 PG 并行度
- 不把客户端延迟推到不可接受水平

因此容量规划应与恢复压测配套：模拟最大允许故障域下线，测量恢复时长和业务延迟，再决定安全水位。

## 6. Ceph 为什么会提前阻止写入 {/* #ceph-为什么会提前阻止写入 */}

Ceph 设置容量阈值，是为了避免 OSD 彻底写满后出现更严重的一致性和恢复问题。

阈值的逻辑顺序必须满足：

```text
nearfull < backfillfull < full < failsafe_full
```

| 阈值 | 含义 |
| --- | --- |
| nearfull | 接近满，提前告警，要求运维介入 |
| backfillfull | 接近无法安全接收 Backfill，限制数据迁入 |
| full | 达到满阈值，集群会阻止相关写入以保护数据 |
| failsafe_full | 最后的安全保护阈值 |

不同版本、发行版和历史配置的实际值可能不同，不要只背某组默认百分比。应直接查看当前集群：

```bash
ceph osd dump | grep -E 'nearfull|backfillfull|full'
```

### 6.1 为什么还有总空闲却报 Full {/* #为什么还有总空闲却报-full */}

Ceph 数据必须遵守 Pool 的 CRUSH 规则和故障域约束。某个 PG 的目标位置不能随意换到任何空闲磁盘。

因此可能出现：

```text
集群平均使用率只有 75%
某些 OSD 已经达到 95%
相关 PG 无法继续安全写入或迁移
```

生产容量的上限由「最受约束的部分」决定，而不是简单看所有磁盘平均值。

## 7. 如何查看容量 {/* #如何查看容量 */}

### 7.1 查看集群整体与 Pool 容量 {/* #1-查看集群整体与-pool-容量 */}

```bash
ceph df
```

更详细的输出：

```bash
ceph df detail
```

重点关注：

- RAW STORAGE 中的总量、已用和可用
- POOLS 中的 STORED、OBJECTS、USED 和 MAX AVAIL
- 副本或 EC 造成的物理占用差异
- 各 Pool 是否设置配额

### 7.2 查看 OSD 利用率分布 {/* #2-查看-osd-利用率分布 */}

```bash
ceph osd df
ceph osd df tree
```

不要只看平均值，要看：

- 使用率最高的 OSD
- 同一 Host 内是否明显不均
- 某个设备类是否接近满
- VAR 等相对偏差指标
- OSD 权重和 CRUSH 权重是否异常

### 7.3 查看健康告警 {/* #3-查看健康告警 */}

```bash
ceph -s
ceph health detail
```

常见容量相关告警可能包括：

- `OSD_NEARFULL`
- `OSD_BACKFILLFULL`
- `OSD_FULL`
- `POOL_NEARFULL`
- Pool 配额相关告警

### 7.4 定期保存容量趋势 {/* #4-定期保存容量趋势 */}

单次 `ceph df` 只能说明当前状态。生产环境还应监控：

- 每天或每周增长量
- 预计达到告警线的日期
- 最大 OSD 与平均 OSD 的差距
- 快照和对象数量增长
- Recovery 期间容量变化
- 各 Pool 和租户的增长速度

扩容交付需要采购、上架、安装、数据均衡等时间，因此不能等到 Nearfull 再开始申请硬件。

## 8. Pool 配额与容量治理 {/* #pool-配额与容量治理 */}

如果多个业务共享集群，某个业务可能快速消耗全部空间。可以根据版本和使用方式设置 Pool 配额：

```bash
ceph osd pool set-quota <pool-name> max_bytes <bytes>
ceph osd pool set-quota <pool-name> max_objects <object-count>
```

查看 Pool 信息：

```bash
ceph osd pool get-quota <pool-name>
ceph df detail
```

设置配额前应确认：

- 配额是按逻辑数据还是对象数限制
- RBD 快照、RGW 版本等如何计入使用
- 达到配额后业务会出现什么错误
- 监控是否在达到硬限制前告警
- 是否为关键业务保留独立 Pool

配额不是物理容量扩展，只是防止单个使用方无限占用共享资源。

## 9. Nearfull 或 Full 时怎么处理 {/* #nearfull-或-full-时怎么处理 */}

### 9.1 第一步：确认范围 {/* #第一步确认范围 */}

```bash
ceph -s
ceph health detail
ceph df detail
ceph osd df tree
ceph osd dump | grep -E 'nearfull|backfillfull|full'
```

确认是：

- 整体容量不足
- 单个或少数 OSD 不均
- 某个设备类或 CRUSH 根受限
- 某个 Pool 配额达到上限
- OSD 离线导致剩余节点承压
- 大量快照、版本或测试数据增长

### 9.2 第二步：控制新增写入 {/* #第二步控制新增写入 */}

根据业务等级采取限流、暂停非关键导入、停止批量任务等措施，防止情况继续恶化。不要在不了解影响时直接停止整个集群。

### 9.3 第三步：选择根因对应措施 {/* #第三步选择根因对应措施 */}

| 根因 | 常见处理方向 |
| --- | --- |
| 总容量确实不足 | 尽快增加符合现有 CRUSH 规则的 OSD 或节点 |
| 某个 Host/设备类满 | 向同一受限故障域体系补容量，检查权重与规则 |
| OSD 异常离线 | 修复 OSD，恢复原有容量和数据分布 |
| 无效数据增长 | 经业务确认后删除测试数据、过期快照或历史版本 |
| Pool 配额过小 | 确认物理空间足够后，按审批调整配额 |
| 分布异常 | 检查 CRUSH 权重、OSD reweight、PG 状态和 Balancer |

### 9.4 第四步：持续验证恢复 {/* #第四步持续验证恢复 */}

```bash
watch -n 10 'ceph -s'
ceph osd df tree
ceph progress
```

观察：

- 是否开始 Recovery/Backfill
- 最满 OSD 的使用率是否下降
- 是否产生新的慢请求
- 客户端延迟是否恶化
- PG 能否逐步回到 `active+clean`

## 10. 哪些「快速处理」很危险 {/* #哪些快速处理很危险 */}

### 10.1 直接提高 Full 阈值 {/* #1-直接提高-full-阈值 */}

提高阈值只是把最后的安全空间继续消耗掉，不会创造容量。它可能让业务短时恢复写入，但也可能让 OSD 真正写满，导致恢复更困难。

只有在明确根因、确认剩余物理空间、已准备立即扩容或释放空间，并经过风险批准时，才可能把它作为短时应急动作。事后必须恢复并复盘。

### 10.2 随意执行 OSD reweight {/* #2-随意执行-osd-reweight */}

Reweight 会改变数据分布并触发迁移。错误调整可能把数据推向另一个接近满的 OSD，或造成长时间 Recovery。应先理解 CRUSH 权重、Override Reweight 和 Balancer 之间的区别。

### 10.3 看到空闲磁盘就执行 all-available-devices {/* #3-看到空闲磁盘就执行-all-available-devices */}

```bash
ceph orch apply osd --all-available-devices
```

这是一条会把所有符合条件的空白设备创建为 OSD 的持久化声明。生产中必须先执行 `--dry-run` 检查匹配设备，并优先使用清晰的 OSD ServiceSpec。

### 10.4 未确认就删除快照或对象 {/* #4-未确认就删除快照或对象 */}

快照、克隆、RGW 版本和回收站可能涉及数据保留要求。删除动作可能不可恢复，也不一定立即释放全部物理空间。先确认数据所有者、依赖关系和回收机制。

### 10.5 把 Full 告警当作监控误报 {/* #5-把-full-告警当作监控误报 */}

Ceph 的 Full 保护直接关系到能否写入和恢复。任何 Nearfull 都应进入容量处置流程，而不是简单屏蔽告警。

## 11. 容量规划模板 {/* #容量规划模板 */}

可以按下面步骤完成一次容量测算。

### 11.1 第 1 步：计算未来有效数据 {/* #第-1-步计算未来有效数据 */}

```text
未来有效数据
= 当前有效数据
+ 预测增长
+ 快照/版本/克隆增长
+ 业务保留缓冲
```

### 11.2 第 2 步：换算冗余后的 Raw 需求 {/* #第-2-步换算冗余后的-raw-需求 */}

副本池：

```text
所需 Raw = 未来有效数据 × size
```

EC 池：

```text
所需 Raw = 未来有效数据 × (k + m) ÷ k
```

### 11.3 第 3 步：加入内部与不均衡余量 {/* #第-3-步加入内部与不均衡余量 */}

给对象元数据、BlueStore、分布偏差和测量误差留出空间。

### 11.4 第 4 步：加入最大故障域恢复预留 {/* #第-4-步加入最大故障域恢复预留 */}

按最大 Host、Chassis 或 Rack 的实际容量占比估算，并通过故障模拟验证。

### 11.5 第 5 步：检查 Full 阈值安全距离 {/* #第-5-步检查-full-阈值安全距离 */}

规划水位应显著低于 Nearfull，而不是把 Full 当作正常可用上限。

### 11.6 第 6 步：检查性能和恢复窗口 {/* #第-6-步检查性能和恢复窗口 */}

容量足够后，还要确认网络与磁盘能否在目标时间内恢复。

### 11.7 第 7 步：设置扩容触发线 {/* #第-7-步设置扩容触发线 */}

例如按以下条件中最早发生者启动扩容：

- 预计 N 个月内达到规划水位
- 最大 OSD 达到内部告警线
- 故障后空间不再满足恢复目标
- 性能或恢复时间先于容量成为瓶颈

具体 N 值应覆盖公司的采购和交付周期。

## 12. 本篇总结 {/* #本篇总结 */}

Ceph 容量要分层理解：

```text
磁盘标称容量
→ Raw 原始容量
→ 冗余后的理论可用容量
→ 扣除恢复、阈值、偏差和增长后的规划可用容量
```

需要记住：

1. 10 块 2 TB 盘的 Raw 是 20 TB，约 18.19 TiB
2. 三副本理论可用约 6.67 TB，不是 20 TB
3. EC 4+2 理论可用约 13.33 TB，但性能与故障域要求不同
4. 「预留 20%」只能作为示例，必须按最大故障域和实测恢复能力校验
5. 最满 OSD、最受限 CRUSH 规则和 Pool 配额可能比集群平均使用率更早限制写入
6. 阈值顺序是 `nearfull < backfillfull < full < failsafe_full`
7. Full 时提高阈值不是扩容，只是在继续消耗安全空间
8. 生产承诺应基于规划可用容量，而不是理论极限

**使用 cephadm 从主机准备、Bootstrap、添加 Host 到安全创建 OSD，搭建一个可继续扩展的 Ceph 集群。**

## 13. 自测题 {/* #自测题 */}

1. 20 TB 为什么在 Linux 中可能显示约 18.19 TiB？
2. 20 TB Raw 在三副本下理论可用多少？
3. EC 4+2 的理论空间利用率是多少？
4. 为什么集群平均使用率不高，某些 Pool 仍可能无法写入？
5. `backfillfull` 的主要保护目的是什么？
6. 为什么最大 Host 故障占比会影响正常容量水位？
7. 提高 full 阈值为什么不是根本解决方案？
8. 规划可用容量与理论可用容量的区别是什么？

### 13.1 参考答案 {/* #参考答案 */}

1. 磁盘厂商TB按十进制`10^12`字节，Linux常按二进制TiB=`2^40`字节显示；`20×10^12 / 2^40 ≈ 18.19 TiB`。
2. 三副本理论业务容量为`20/3≈6.67TB`，没有包含安全水位、BlueStore、元数据和恢复余量。
3. EC 4+2理论利用率为`4/6=66.67%`。
4. 数据按CRUSH和PG分布，某些OSD/Device Class/CRUSH Root可能先达到nearfull/full；Pool配额也可能单独耗尽，因此集群平均值会掩盖局部瓶颈。
5. `backfillfull`在目的OSD过满时阻止继续Backfill，避免恢复流量把它推到full并使更多PG不可写。
6. 最大Host离线后，其数据需要迁移到剩余Host；正常水位必须预留至少该故障量及分布不均、增长和恢复写放大的空间，否则没有合法恢复目的地。
7. 提高阈值只缩短最后的安全距离，不能创造磁盘，也可能让集群更接近无法恢复的状态。根治是清理、扩容、均衡或迁移数据并修正增长计划。
8. 理论值只应用副本/EC比例；规划值还扣除格式差异、BlueStore/元数据、full阈值、故障恢复余量、分布偏差、增长提前量和业务保留，因此明显更小。
