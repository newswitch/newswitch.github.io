# cuFile 请求、对齐、注册与回退机制

GDS 的核心收益是减少特定存储路径经过主机中转内存的复制，不是让每个文件请求都变成一次无开销 DMA。一次 cuFile 调用仍可能包含注册、请求拆分、GPU 内部中转或 CPU 兼容回退。

前置阅读 [GDS 数据路径](./02-GPUDirect-Storage原理与实践.md)。这里聚焦文件接口；对象存储专用接口和第三方文件系统必须对应各自支持条件。

## 1. 句柄注册与 Buffer 注册是两件事

`cuFileHandleRegister` 将文件描述符纳入 cuFile 的文件句柄模型；`cuFileBufRegister` 则显式注册 GPU 缓冲区。前者不说明任意 GPU Buffer 已建立最佳 DMA 映射，后者也不能让不受支持的文件系统自动支持 GDS。

显式 Buffer 注册并非所有使用场景的必选项。cuFile 可以使用内部缓冲区处理未显式注册的请求，但可能增加额外复制；一次性大 Buffer 与长期复用 Buffer 的权衡不同。见 [cuFile Best Practices](https://docs.nvidia.com/gpudirect-storage/best-practices-guide/)。

```text
文件与挂载身份 → cuFile 句柄
GPU 分配与生命周期 → 可选的显式注册
请求参数 → 路径选择与实际 IO → 完成检查 → 消费或重用 Buffer
```

两个入口最后在请求中汇合，因此只检查句柄注册返回成功，不能证明后续请求全都走同一条直接路径。

## 2. 一份请求至少有四个范围参数

理解请求时分别检查文件 offset、请求字节数、GPU Buffer 基址和 Buffer 内偏移。文件范围合法，不保证 Buffer 范围合法；Buffer 是对齐分配，也不保证偏移后的地址仍对齐。

例如 Buffer 基址按 4096 字节对齐，随后把其中偏移 1024 字节的地址交给 IO，对齐条件已经改变。排查时不能只打印最初 `cudaMalloc` 返回的指针。

对显式注册的 Buffer，cuFile 要求基址参数仍使用注册时的地址，内部位置通过 Buffer offset 表达。不能把偏移后的指针当成新的已注册基址。地址范围、注册范围和请求范围必须分别匹配。

还要检查 API 的返回字节数与错误。同步读到 EOF 可能少于请求长度；异步提交成功则更不能直接当成读完全部内容。接口的具体结果与参数生命周期见 [cuFile API Reference](https://docs.nvidia.com/gpudirect-storage/api-reference-guide/index.html)。

## 3. 对齐会改变实际搬运量

下面按 4096 字节粒度建立教学模型：从文件 offset=1024 读取 1024 字节，覆盖一个完整对齐块；如果内部按完整块读取，则实际读 4096 字节，读取放大为 4 倍。

把 offset 改为 3584，同样读取 1024 字节，会跨越两个块；完整块模型需要读 8192 字节，放大为 8 倍。应用请求大小相同，实际工作量却不同。

未对齐写还可能需要 Read-Modify-Write。若为更新一个块中的 512 字节，先读取 4096、再写回 4096，底层总 IO 与有效写入之比为 `8192/512=16`。这是完整块 RMW 模型，不代表所有文件系统和 cuFile 版本每次都产生相同物理流量。

GDS 对未对齐请求的处理可能使用 GPU bounce buffer、POSIX 路径或其他机制，应按配置与实际统计判断，不能把所有额外复制都叫 CPU fallback。

## 4. GPU 中转不等于 CPU 兼容路径

存在三个需要区分的结果：直接到应用 GPU Buffer；先到内部或邻近 GPU Buffer，再进行设备间复制；通过 CPU 内存的兼容路径。

GDS 的动态路由在受支持组合中可能借助更靠近存储 NIC 的 GPU，再搬运到目标 GPU。某些 NVMe 路径自 CUDA 12.8 起还可以使用受支持的 PCI P2PDMA 组合，不再依赖 `nvidia-fs`。这些条件见 [GDS Overview](https://docs.nvidia.com/gpudirect-storage/overview-guide/)，不能推广成所有文件系统都不需要该模块。

因此“没有模块”“发生了复制”“调用成功”都不是足够的路径判据。需要关联目标挂载、请求形状、配置、统计和性能证据。

## 5. 注册收益取决于复用次数

假设显式注册与释放共耗时 200 微秒，每次传输通过避免内部中转节省 5 微秒。忽略其他开销时，复用超过 40 次才抵消这部分固定成本；只读一次可能反而更慢。

这不是注册阈值建议，而是摊销关系。真实系统还受 Buffer 大小、映射资源、缓存和竞争影响。把所有显存长期注册，可能占住有限映射资源；反复注册又可能把固定开销放到关键路径。

更合适的问题是：哪些 Buffer 会稳定复用、生命周期能否正确追踪、注册资源峰值有多大。它与 [GPUDirect 注册缓存](../../networking/rdma-roce/ai-cluster/13-GPUDirect内存注册DMA-BUF与生命周期.md)共享生命周期原理，但具体 API 不可互换。

## 6. 异步提交只移动了等待位置

同步、Batch 和 CUDA Stream 接口的提交与完成语义不同。CPU 很快返回，不代表 IO 已完成；独立 stream 上的 kernel，也不会因为程序书写顺序在后面就自动等待另一条 stream 的 IO。

应建立“存储写入 Buffer 完成 → GPU 消费 → Buffer 可再次覆盖”的依赖。句柄、Buffer 和异步参数必须活到 API 要求的完成点，再注销和释放，不能在提交后立即复用。

吞吐还受在途数据量约束。若目标为 16 GiB/s、平均完成延迟 1 ms，教学模型需要约 16.384 MiB 在途数据。每个请求 1 MiB 时，至少约 17 个并发请求才有机会覆盖该延迟；这只是必要容量估算，不保证设备实际达到目标吞吐。

## 7. IO 更快不等于模型加载同比例更快

假设原始文件读取 4 秒，反序列化与张量处理 6 秒，串行总计 10 秒。即使 IO 翻倍变成 2 秒，总时间也只是 8 秒，加速比为 1.25。若数据还需要 CPU 解压或重新排布，直接进入 GPU 的路径也可能无法消除这些阶段。

因此应同时报告有效字节、实际 IO、复制、CPU 处理与端到端耗时。对齐优化主要降低放大，注册优化主要摊销准备成本，流水线优化则尝试重叠阶段，它们不是同一个参数旋钮。
