# 节点模型缓存与容量水位治理

将模型从对象存储或共享文件系统缓存到 GPU 节点本地 NVMe，可以显著减少冷启动和共享后端压力。但如果只写一个“下载到 `/models`”脚本，很快会遇到：

- 多个 Pod 同时下载同一模型；
- 下载一半就被进程当成完整模型；
- revision 更新后仍加载旧缓存；
- 节点盘被模型填满，kubelet 和 containerd 受影响；
- 淘汰正在使用的模型；
- 所有节点同时未命中形成回源风暴；
- 节点重启后缓存状态与控制面不一致。

缓存不是持久存储，它是一套有状态的性能系统。

## 1. 目标与边界

一个合格的节点模型缓存应满足：

- **可重建：**唯一来源在模型制品库，不依赖单节点；
- **不可变：**同一 revision 对应固定 manifest 和 checksum；
- **原子可见：**未完成下载不会被服务加载；
- **并发安全：**同节点相同 revision 只回源一次；
- **容量可控：**软/硬水位、预留空间和淘汰策略明确；
- **使用安全：**不会删除正在使用或即将发布的模型；
- **可观测：**命中、下载、校验、占用、淘汰和错误可追踪；
- **防风暴：**跨节点回源有速率、批次和抖动控制；
- **故障隔离：**缓存损坏只影响当前节点和 revision。

不应承担：

- 模型的唯一副本；
- 训练 Checkpoint 的最终提交；
- 没有 manifest 的“最新”目录；
- 跨节点强一致共享写入。

## 2. 三层模型分发

```text
权威制品层
  S3/RGW/模型仓库：revision、manifest、checksum、权限
        ↓
区域/集群分发层（可选）
  代理、镜像、P2P、共享只读缓存、带宽整形
        ↓
节点缓存层
  Local NVMe：可重建、按节点命中、最终加载到 HBM
```

节点缓存缓解最后一公里，不应掩盖源仓库的版本、完整性和可用性问题。

## 3. Cache Key 设计

不能只用模型名：

```text
bad:  /cache/llama/model.safetensors
good: /cache/<repository>/<model>/<immutable-revision>/<manifest-digest>/...
```

Cache key 至少包含：

- 模型仓库/租户；
- 模型名；
- 不可变 revision 或对象 version；
- manifest digest；
- 必要时包含量化、格式、Tokenizer revision 和张量并行转换版本。

如果服务请求 `latest`，控制面应先解析为不可变 revision，再传给缓存。节点不应各自在不同时刻解析“最新”。

## 4. Manifest 是缓存正确性的核心

示例逻辑：

```json
{
  "model": "<name>",
  "revision": "<immutable-id>",
  "files": [
    {"path": "model-00001.safetensors", "size": 123, "sha256": "..."},
    {"path": "tokenizer.json", "size": 456, "sha256": "..."}
  ],
  "totalSize": 579,
  "format": "safetensors"
}
```

下载端先验证 manifest 的来源/签名（若系统要求），再按文件 size/checksum 校验。S3 ETag 不应被普遍当成对象内容 MD5，特别是 Multipart、加密或厂商实现下。

## 5. 原子下载与发布

推荐状态机：

```text
Absent
  → Reserving
  → Downloading to temp directory
  → Verifying files and manifest
  → Fsync/commit（按数据安全要求）
  → Atomic rename / publish marker
  → Ready
  → InUse
  → Evictable
  → Deleting
```

目录示例：

```text
/var/lib/model-cache/
├── tmp/<download-id>/
├── blobs/<digest>/
├── revisions/<model>/<revision> -> ../../blobs/<digest>
├── leases/<pod-uid-or-instance>/
└── metadata/
```

在同一文件系统内，目录/文件 rename 通常可提供原子名称切换；跨文件系统 rename 不具备相同语义。完成标记必须最后写，加载端只接受 Ready revision。

## 6. 同节点并发控制

多个 Pod 同时请求同一 revision 时：

```text
Pod A ─┐
Pod B ─┼→ cache agent → per-revision lock → one download
Pod C ─┘                         └→ others wait and reuse
```

可使用每 revision 锁、单节点 DaemonSet agent 或 Unix socket/gRPC 服务统一管理。锁要处理：

- 持有者崩溃；
- 超时与租约；
- 临时目录清理；
- 下载进度和等待者取消；
- 不同 revision 可并行；
- 防止全局锁让所有模型串行。

简单 `flock` 适合单机文件锁，但容器挂载、进程生命周期和网络文件系统语义需实际验证。

## 7. 容量不能只用“剩余 10%”

至少分四类空间：

```text
总容量
- 系统/文件系统保留
- kubelet/containerd/日志安全预留（若共盘）
- 正在使用模型
- 已预热保护模型
- 可淘汰模型
- 下载临时空间
= 可接收新 revision 的真实空间
```

下载一个 100 GiB 模型可能需要：

- 100 GiB 最终文件；
- 临时下载空间；
- 解压/转换后的额外空间；
- 原旧 revision 在滚动升级完成前仍保留；
- 并发下载的其他 reservation。

因此“当前 free > 模型大小”仍可能不足。

## 8. 软水位、硬水位与紧急水位

示例概念，不是统一阈值：

| 水位 | 行为 |
|---|---|
| 低于软水位 | 正常下载和预热 |
| 超过软水位 | 后台淘汰冷模型，限制预热 |
| 超过硬水位 | 新下载必须先 reservation/淘汰，拒绝低优先级请求 |
| 超过紧急水位 | 停止非必要下载，保护 kubelet/containerd，节点可标记不接新任务 |

阈值应同时使用百分比和绝对剩余空间。大盘剩 5% 可能仍有数百 GiB，小盘剩 10% 可能放不下一个 revision。

## 9. Reservation：先占预算，再下载

下载前计算：

```text
required = final_size
         + temporary_overhead
         + transform_overhead
         + safety_margin
```

控制面原子创建 reservation，防止多个下载都看到同一份 free space。reservation 需要过期和崩溃恢复，实际占用与估算偏差要监控。

如果 manifest 没有完整 size，就无法可靠做容量准入。

## 10. 淘汰策略

### 10.1 LRU 不是万能答案

纯 LRU 可能淘汰即将发布或代价很高的模型。更实用的评分可考虑：

```text
eviction_score = age
               × inverse(hit_frequency)
               × size_weight
               × reload_cost
               × priority/protection
```

### 10.2 不能淘汰的对象

- 有有效 lease 的运行实例；
- 正在下载/校验/转换；
- 当前发布版本和回滚版本；
- 即将调度的预热任务已 reservation；
- 管理员临时 pin 的关键模型。

### 10.3 删除流程

```text
mark deleting
→ prevent new leases
→ recheck active leases
→ delete revision reference
→ GC unreferenced blobs
→ fsync metadata as required
→ update metrics
```

删除前后二次检查，避免 TOCTOU 使刚被使用的缓存遭删除。

## 11. Lease 与使用计数

Pod 开始加载/服务前获取 lease，退出后释放。lease 需要包含：

- model/revision/digest；
- Pod UID、namespace、workload；
- 创建和续租时间；
- 预期 TTL；
- 使用状态（loading/serving/draining）。

不能只依赖进程创建的普通文件，因为 Pod 被强杀后可能残留。agent 应对照 kubelet/API 实际 Pod UID，并在 API 不可用时采用保守策略。

## 12. 预热与调度协同

两种基本模式：

### 12.1 调度后下载

```text
Pod 被放到节点 → initContainer/agent 下载 → 模型加载
```

简单，但调度未考虑缓存，冷启动不可预测。

### 12.2 预热后放置

```text
发布计划 → 选择节点 → reservation + prefetch
→ checksum Ready → 更新受控缓存状态
→ 调度工作负载
```

可降低启动时延，但控制面更复杂。缓存状态变化快，不应直接给每个 revision 创建高基数永久 node label。可由专用调度插件/扩展资源/控制器查询缓存索引，并防止状态过期。

调度缓存命中是软偏好还是硬约束取决于 SLO。若设为硬约束，所有缓存节点不可用时可能导致任务永久 Pending。

## 13. 防止回源风暴

场景：新模型发布或节点池重启，100 台节点同时下载 100 GiB。

理论回源量：

```text
100 × 100 GiB = 10,000 GiB
```

控制措施：

- 分批/滚动预热；
- 全局和每源并发限制；
- 每节点带宽限制；
- 随机抖动；
- 区域镜像/代理缓存；
- P2P 分发（需完整性与安全设计）；
- 旧版本容量在新版本 Ready 前保持；
- 源端 429/503 的指数退避与抖动；
- 发布控制器根据后端负载暂停批次。

重试必须有上限和退避，否则失败会放大流量。

## 14. 与 Kubernetes 的实现方式

### 14.1 initContainer

优点：清单简单，下载完成才启动主容器。缺点：每 Pod 可能重复逻辑；并发锁、水位和跨 Pod 复用难治理。

### 14.2 DaemonSet cache agent

每节点一个 agent 管理下载、manifest、lease、水位和指标。Pod 通过共享 hostPath/Local PV 只读访问缓存。需要严格权限，防止普通容器篡改共享目录或 agent socket。

### 14.3 Image/volume-based distribution

模型打入 OCI artifact/image 或使用 CSI image/volume 能复用分发体系，但超大制品、layer 生命周期、解包空间、运行时 GC 和兼容性需要验证。

### 14.4 Local PV

适合将缓存卷显式暴露给 Pod，但仍需节点亲和、清理和丢盘恢复。缓存通常不需要用户级 PVC 生命周期，可由平台封装。

## 15. 安全

- 源仓库使用最小只读凭证；
- Secret 不写入缓存目录和日志；
- manifest/revision 不接受路径穿越；
- 下载文件先写临时目录，权限默认不可执行；
- 只加载允许格式和签名/可信来源；
- 缓存 agent API 鉴权，限制普通 Pod 删除/pin；
- 多租户模型按权限隔离，不能因节点缓存绕过仓库授权；
- 日志不记录带签名 URL 或 Token。

## 16. 可观测性

### 16.1 容量

- bytes total/used/free/reserved；
- inode；
- soft/hard/emergency watermark；
- per model/revision size；
- temporary/orphan bytes。

### 16.2 性能

- hit/miss；
- download queue；
- source first-byte 与吞吐；
- checksum/transform 时间；
- cache-to-host 与 H2D 时间；
- cold/warm startup 分位数。

### 16.3 正确性与故障

- checksum mismatch；
- incomplete/abandoned download；
- lease/reconciliation error；
- eviction success/failure；
- source retry/429/5xx；
- disk I/O error 和 NVMe health。

Prometheus 标签不要包含无限增长的完整 digest/request ID；明细可放日志/Trace。

## 17. 故障恢复

### 17.1 agent 重启

扫描 metadata、temp、ready marker 和 lease，执行 reconciliation：

- 未完成下载继续或删除；
- ready 目录重新校验必要元数据；
- 过期 reservation 释放；
- lease 与实际 Pod UID 对齐；
- orphan blob 按 grace period GC。

### 17.2 节点重启

缓存盘若保留，可以重建索引；若 ephemeral，则重新预热。工作负载 readiness 必须等待目标 revision Ready。

### 17.3 磁盘损坏

隔离节点，标记 cache unavailable，停止新调度；业务迁移到有容量节点。更换盘后从权威制品库重建。不要尝试把缓存恢复当业务数据恢复。

### 17.4 checksum mismatch

删除隔离的临时/损坏副本，记录源对象 version、范围和下载节点，限次重试；多个节点同时 mismatch 时停止发布并检查源制品/代理。

## 18. 验收实验

1. 首次请求 revision，记录下载、校验、加载和 H2D。
2. 同节点第二个 Pod 请求相同 revision，验证不回源。
3. 两个 Pod 同时首次请求，验证只有一个下载。
4. 注入中途进程退出，验证半文件不可见且能清理/续传。
5. 制造 checksum 错误副本，验证拒绝加载。
6. 将占用推到软水位，验证后台淘汰。
7. 有 lease 的模型在硬水位下仍不被删除。
8. 多节点分批预热，验证源端流量不超过阈值。
9. 重启 agent/节点，验证 reconciliation。
10. 删除本地缓存，验证从权威源完整重建。

所有实验使用测试 revision 和专用节点/目录，不破坏生产唯一制品。

## 19. 常见误区

1. **目录存在就是缓存命中。**可能只有部分文件。
2. **ETag 就是 SHA-256/MD5。**Multipart 和实现细节会改变语义。
3. **剩余空间大于模型就能下载。**忽略临时、转换、旧版本和 reservation。
4. **LRU 可以直接删除最老目录。**可能仍在使用或是回滚版本。
5. **所有节点一起预热最快。**可能压垮对象存储和网络。
6. **节点 label 适合记录所有缓存 revision。**高基数、变化快且容易过期。
7. **本地 RAID 让缓存成为持久仓库。**整机和逻辑故障仍会丢失。
8. **Pod 退出就一定释放使用状态。**强杀和网络分区会残留 lease。

## 20. 掌握标准

应能：

- 设计不可变 cache key 与 manifest；
- 实现临时下载、checksum 和原子发布；
- 使用 per-revision 锁避免重复回源；
- 计算真实 reservation 和升级双版本空间；
- 设计软/硬/紧急水位与安全淘汰；
- 用 lease 保护正在使用的 revision；
- 将预热与调度作为可退化的偏好/约束；
- 控制跨节点回源风暴；
- 在 agent、节点或磁盘故障后重建；
- 通过指标把缓存命中与模型 TTFT/启动时延关联。
