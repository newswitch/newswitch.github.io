# 容量、Small Object、Multipart、并发、网卡、磁盘与性能测试

对象存储性能取决于对象大小分布、并发、读写比例、纠删码、磁盘、网卡和客户端。只用一个大文件顺序上传得到的 GB/s，不能代表百万小文件或模型并发冷启动。

## 1. 容量模型

```text
逻辑数据 = 当前版本 + 历史版本 + 未完成Multipart + Delete Marker相关状态
物理数据 ≈ 逻辑数据 × 纠删码开销 × 复制站点数 + 元数据/后台开销
```

还要预留 Healing、Decommission、扩容/升级、生命周期异步清理和故障期间增长空间。生产水位应保证失去一个节点后仍能写入和完成恢复。

### 1.1 完整容量算例

假设一个Set有16块10 TiB盘、K=8/M=8，暂不考虑压缩和小对象内联，原始160 TiB、纠删码理论正文80 TiB。如果规划只使用理论正文的70%，业务及保留数据预算为56 TiB。

```text
当前版本30 TiB + 历史版本12 TiB + 未完成上传2 TiB = 44 TiB
规划预算56 TiB - 已规划44 TiB = 12 TiB
```

这12 TiB是上述假设中的逻辑预算余量，不是精确磁盘读数；元数据、分配粒度、不均衡与其他后台开销仍需实测。复制站点按各自冗余及保留策略分别计算，不能先把所有站点容量合并再认为源站有更多空间。

盘离线后，也不能简单把可用容量乘剩余盘比例。部分对象仍占用已有分片，Set写入门槛、最满盘和修复临时空间分别制约新写，集群平均水位可能掩盖局部耗尽。

## 2. Small Object

小对象让请求、签名、元数据、网络往返和磁盘操作占比上升，吞吐常由 IOPS/QPS 而非带宽决定。海量小文件数据集可考虑打包为可并行读取的 Shard 格式，但要权衡随机访问和增量更新。

总量1 TiB若按4 KiB对象组织，约有268435456个对象；若按1 GiB组织，则只有1024个。两者不能用同一套容量单价、扫描时间或恢复条目预算来比较。

打包为较大Shard可减少请求，但修改一个小样本可能重写更大的对象。索引必须记录准确偏移、长度及Shard版本；打包不是无代价优化。

## 3. Multipart 与并发

大对象用 Multipart 并行可提高带宽利用，但 Part 太小会增加请求和内存，太大则失败重试成本高。并发要同时考虑：

- 客户端 CPU/内存和连接池；
- LB 最大连接和超时；
- MinIO 节点 CPU、网络；
- Erasure Set Drive 并行能力；
- KMS/加密开销；
- 多租户公平性。

### 3.1 并发和内存预算

在稳定工作量下，用Little定律做量级估算：若平均完成延迟25毫秒，目标2000请求/秒，平均在途约 `2000 × 0.025 = 50`。它不保证设置50线程就能达到2000QPS，还需考虑排队、长尾和资源上限。

若实现为16个上传Part各保留64 MiB正文，仅这些正文缓冲就是1 GiB；SDK额外缓冲、TLS、重试和进程开销另算。流式或文件型上传可能采用不同缓冲策略，不能把这个算例写成所有SDK的固定公式。

并发应扫描1、2、4、8等值，观察吞吐增加是否仍大于错误、CPU和尾延迟的代价。多个节点共享同一源端时，还需要总并发预算，而不是每台都取单机最优值。

## 4. 模型冷启动测试

```text
N个Pod同时启动
→ HEAD/List读取Manifest
→ 并发Range/Multipart GET模型分片
→ 写本地NVMe临时目录
→ Checksum
→ 原子切换缓存目录
→ 加载主机内存/NPU或GPU
```

测量 DNS/TLS、TTFB、下载吞吐、重试、Checksum、本地写和模型加载，避免把全部 Ready 时间归因于 MinIO。

## 5. 测试矩阵

| 维度 | 覆盖 |
| --- | --- |
| 对象大小 | 4 KiB、1 MiB、100 MiB、多 GiB 与真实分布 |
| 操作 | PUT、GET、Range、List、Delete、Multipart |
| 并发 | 单客户端、多节点、突发冷启动 |
| 状态 | 正常、单 Drive/Node 故障、Healing、复制追赶 |
| 安全 | TLS、SSE/KMS 开启后的真实开销 |

### 5.1 受控读取比较

先在专用测试桶准备已校验的不可变对象，明确大小、版本及预算。以下仅做四个并发下载，写到新的本地目录；会产生读取/流量费用，不用于共享生产桶：

```bash
READ_DIR="$(mktemp -d)"
pids=()
for task_number in 1 2 3 4; do
  aws --endpoint-url "$S3_ENDPOINT" s3api get-object \
    --bucket "$BUCKET" --key "$KEY" \
    "$READ_DIR/result-$task_number.bin" > "$READ_DIR/meta-$task_number.json" &
  pids+=("$!")
done
failed=0
for task_pid in "${pids[@]}"; do
  wait "$task_pid" || failed=1
done
test "$failed" -eq 0
```

KEY必须不可变，或在请求中固定已记录的VersionId。这个短脚本验证退出结果，不是完整基准工具；测试还要记录墙钟耗时、实际字节、重试及逐文件摘要，不能只因四个进程成功就宣称性能达标。

同时在客户端和存储节点观察：

```bash
iostat -xz 1 10
sar -n DEV 1 10
pidstat -u -r -d 1 10
```

记录工具版本及采样窗口，不把全机CPU或网卡总量直接归到一个请求。不要在生产全局执行drop_caches模拟冷读，应使用新测试数据/新实验客户端并明确缓存条件。

## 6. 瓶颈证据

客户端 CPU 高查签名/Checksum；TTFB 高查 LB、MinIO 请求队列和磁盘；吞吐平台期查网卡/Drive；P99 抖动查 Healing、GC、对象存储依赖和邻居噪声；小对象 QPS 低查请求/元数据开销。

### 6.1 同一现象的不同归因

| 对照结果 | 更有依据的下一步 |
| --- | --- |
| 网络接近上限，本地盘很空闲 | 看共享网络与源端聚合带宽，继续加线程通常无益 |
| 网络低、客户端单核满 | 看签名、摘要和串行处理，不先扩存储节点 |
| 客户端缓存盘延迟高 | 比较直接流式读取与落盘路径，排查本地写入竞争 |
| 吞吐不变，5xx与重试随并发增长 | 降并发并看服务端排队/限流与Set热点 |
| 正常快，Healing期间慢 | 比较后台修复流量和前台P99，不能关闭修复后忘记冗余风险 |

## 7. 练习与答案

### 7.1 示例容量为什么不是160TiB业务配额

答案：K=8/M=8先得到80 TiB理论正文，再按70%规划为56 TiB；历史、Multipart及其他开销还要占用预算。

### 7.2 2000QPS和25毫秒能否推出50线程必然达标

答案：不能。50是稳定状态平均在途量估算，线程、连接池、排队、尾延迟与后端上限还需测试。

### 7.3 并发提高吞吐不变但错误变多应如何处理

答案：停止继续加并发，识别客户端或源端饱和，并按错误、延迟与成功有效吞吐选择工作点。

### 7.4 四个下载成功是否证明所有内容正确

答案：不证明。还需验证准确版本、长度、摘要和完整工作量；HTTP/CLI结果不能替代内容校验。
