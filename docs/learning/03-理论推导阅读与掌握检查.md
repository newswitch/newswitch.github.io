# 理论推导阅读与掌握检查

理论学习的目标是能从假设推到结论，再指出假设失效时的反例。下面串联 GPU、操作系统、检索、数据库、消息快照、拥塞控制与训练的核心推导，不把部署实验作为阅读前提。

需要进一步理解产品的设计特色时，进入[按设计特色阅读源码](./04-按设计特色阅读源码.md)：选择 Redis、Nginx、Kafka、ClickHouse、vLLM 与 SGLang 的关键实现，而不是给所有章节附上完整调用栈。

## 1. 先补齐预备知识

需要能读懂求和、对数、矩阵乘法和链式法则，区分状态与事件、虚拟地址与物理地址、逻辑行与物理分片。成本计算统一写出单位：字节与位、容量与流量、CPU cost 与毫秒、局部耗时与墙钟时间不能混用。

第一次阅读抓住对象和数据路径；第二次遮住答案重算例子；第三次改变一个假设，例如 Rank 数、过滤比例、缓存命中或故障位置，再重新推导。无法解释反例时，应返回对应机制，而不是继续背参数名。

## 3. 跨方向的共同不变量

并发首先问谁拥有对象、何时发布、何时可重用。RCU grace period、CUDA event 和 Checkpoint staging 不是同一种机制，但都要求区分“调用返回”与“后续使用已经安全”。不要用内存排序替代对象保活，也不要用异步上传替代一致快照。

合并首先问保留的状态是否足够。局部 Softmax 输出、局部平均数和局部热门桶都可能丢掉全局计算需要的信息；正确的统计状态或完整候选才支持所需合并。实数上的结合性还要与浮点归约顺序分开。

性能首先问完整工作量和关键路径。索引少算距离可能牺牲召回，Tile 少写 HBM 可能增加片上资源，重叠通信可能抢占计算资源。局部成本下降只有影响系统的瓶颈路径，才能转成可见收益。

## 4. 什么算理论掌握

能写出对象、公式假设、单位和状态转移；能重算正文例子；能解释至少一个失败反例；改变规模、布局或故障点后仍能给出正确结论。达到这些标准表示掌握所覆盖的理论模型，不代表凭阅读就精通所有产品版本和源代码。架构指令、实现限制和格式兼容必须按目标版本继续核对，工程操作熟练度则是另一类目标。
