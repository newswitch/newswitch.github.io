# AI 集群运维知识体系与掌握检查

AI 集群运维的学习主线是解释系统为何按当前状态运行、如何分配资源、故障在哪里、怎样安全恢复。基础原理只有一个正文归属，产品专题说明自身对象与机制，不按某个证书重复编写 Linux、GPU 或 Kubernetes。

零基础读者先建立术语和对象关系，再推导状态变化与性能，最后使用实际环境验证。阅读完成、教学模型算对和生产能力达标是不同层次，不能用文章数量或一道题的成绩代替。

## 1. 前置知识

先掌握进程、权限、内存、文件系统、网络接口、DNS、时间与身份，能够解释一次应用如何经过内核与设备。对应入口为[Linux 原理](../linux/system-internals/00-Linux系统原理学习路线.md)、[服务器硬件](../hardware/00-服务器硬件学习路线.md)、[网络](../networking/00-网络学习路线.md)和[存储](../storage/00-存储技术学习路线.md)。

不必先通读所有基础文章。遇到术语时回到其主归属补足，再回到当前链路。比如认证失败需要检查时钟，并不要求先读完全部路由协议。

## 3. 节点供应与配置一致性

从[裸金属路线](../gpu/bare-metal-fleet/00-GPU裸金属与Fleet工程学习路线.md)进入资产身份、BMC、PXE、固件矩阵、Burn-in 和隔离恢复，再阅读[BCM](../gpu/bare-metal-fleet/base-command-manager/00-BCM集群供应与管理学习路线.md)。

先在纸面写出“配置期望、镜像内容、节点实际文件、运行内核、调度注册”五份事实，再解释每次变更分别影响哪份。BCM 的 Category、Role 和 Software Image 是产品特有机制；PXE、配置继承和安全发布则是可复用原理。

检查题：修改镜像后节点仍使用旧内核，应能依次检查绑定、覆盖、异步任务、引导和生效过程，不反复编辑同一个文件。

高可用继续学习 [BCM 主备切换与恢复一致性](../gpu/bare-metal-fleet/base-command-manager/07-BCM主备切换故障隔离与恢复一致性.md)，分别推导管理角色、共享入口、状态副本和恢复后协调。共享 IP 可用不等于镜像、凭据与调度事实已经一致。

产品机制继续进入[头节点安装依赖](../gpu/bare-metal-fleet/base-command-manager/08-头节点安装网络与基础服务依赖.md)、[Kubernetes 对象与初始化](../gpu/bare-metal-fleet/base-command-manager/09-Kubernetes集群对象角色与初始化.md)、[真实设备状态](../gpu/bare-metal-fleet/base-command-manager/10-设备状态任务结果与健康检查.md)和[网络与管理授权](../gpu/bare-metal-fleet/base-command-manager/11-网络对象证书Profile与权限边界.md)。应能解释 Type 3 为什么需要 Relay、Overlay 如何影响角色，以及 CLOSED 为什么不能单独证明已停止调度。

供应深入[安装模式、排除规则与重试](../gpu/bare-metal-fleet/base-command-manager/12-节点安装模式排除规则与供应重试.md)及[内核与 initramfs 发布](../gpu/bare-metal-fleet/base-command-manager/04-镜像发布内核更新灰度与回退.md)。应能解释 NOSYNC 为何不是数据保护、no-new-files 与已有文件保留有何差别，以及头副本、供应源副本、节点文件和运行内核为何可能不同。

检查题：总空闲 8 GPU 却不能启动两节点各 4 GPU，列出型号、节点形状、组织资格、拓扑和时间窗口的不同反例；再说明增加账户预算为何未必解决问题。

继续区分通用监控与时间型 Fairshare 的专用历史账本；按 v3.0 配置入口追到实际卷和恢复数据，说明为什么数据库已恢复、监控曲线仍在，也不能证明公平账本一致。

治理继续进入 [Access Rules 与角色作用域](../gpu/cluster/scheduling/run-ai/09-AccessRules角色作用域与权限治理.md)和[策略继承、模板与资产](../gpu/cluster/scheduling/run-ai/10-工作负载策略继承模板与资产治理.md)：从主体到执行端核对授权，分别手算原生与注册类型的有效规则。分数 GPU 还需区分 v3.0 CUDA time-slicing 与 SM-sharing 的模式互斥、错误域和计算归因，不能把旧版共享机制直接沿用为新版结论。

存储从[数据到 GPU](../storage/training-data-plane/01-训练数据从对象存储到GPU的一次完整路径.md)进入[DataLoader/H2D](../storage/training-data-plane/03-PyTorch-DataLoader-多进程预取Pinned-Memory与H2D.md)、[GDS](../storage/ai-workloads/02-GPUDirect-Storage原理与实践.md)和[Checkpoint](../storage/training-data-plane/07-Checkpoint-Storm-IO基准监控容量与故障排查.md)。

继续阅读 [GPUDirect 注册与 DMA-BUF](../networking/rdma-roce/ai-cluster/13-GPUDirect内存注册DMA-BUF与生命周期.md)，解释地址复用、注册缓存失效和跨设备同步，不能只停留在“网卡直接访问显存”的路径图。

协议与 IO 深入 [UCX 协议选择和 Progress 源码](../networking/rdma-roce/ai-cluster/14-UCX协议选择Eager-Rendezvous与Progress源码.md)及 [cuFile 请求机制](../storage/ai-workloads/09-cuFile请求对齐注册与回退机制.md)，用固定成本、带宽、对齐放大和在途数据量推导收益。

One-Sided 同步深入 [NVSHMEM](../networking/rdma-roce/ai-cluster/11-NVSHMEM与GPU-One-Sided通信模型.md)：分清源可复用、目标交付、消费通知和消费确认，推演 Fence/Quiet、CPU/GPU/Stream 域和等待环。旧式 peermem 与云路径的适用范围统一见[网络检查](../networking/rdma-roce/ai-cluster/08-IB-RoCE与GPU集群检查.md)，不以模块存在或单次带宽作为路径证明。

CPU/GPU 小消息路径的源码选学见 [GDRCopy v2.6](../gpu/pcie-numa/06-GDRCopy映射拷贝生命周期与源码.md)：沿后端、Pin/Map、拷贝、Fence 和撤销解释低开销的代价，并手算准备成本摊销与同口径的传输交点。它不替代网络 RDMA 文章。

Magnum IO 通信组件补充 [HPC-X 软件栈](../networking/rdma-roce/ai-cluster/15-HPC-X组件分层动态装载与版本契约.md)与 [MPI 标签匹配](../networking/rdma-roce/ai-cluster/16-MPI标签匹配队列硬件卸载与源码.md)：区分发行集合与实际组件，追踪构建、启动、装载及数据路径，手算 expected/unexpected 队列与到达不平衡。硬件 Tag Matching 的支持条件单列，不能将其与 SHARP 归约卸载混用。

Fabric 生命周期比较 [IB SM 选举与收敛](../networking/ai-fabric/production/12-SubnetManager选举重扫与路由收敛.md)和 [NVSwitch 分区与注册](../gpu/nvlink-nvswitch/03-NVSwitch分区GPU注册与故障域.md)，明确两类管理器的对象与恢复范围不同。

## 6. 健康与恢复

GPU 时序与身份映射见[DCGM Exporter](../sre/observability/gpu/01-DCGM%20Exporter%20GPU%20监控指标详解.md)，整机健康见[NVSM](../gpu/bare-metal-fleet/08-NVSM整机健康告警与证据关联.md)，动作闭环见[隔离与重新入池](../gpu/bare-metal-fleet/07-GPU节点自动隔离修复重新入池与RMA判定.md)。

按“现象、身份、时间线、假设、否定证据、最小动作、复验”组织分析。监控缺失不是利用率零，恢复可见性不等于恢复性能，清除告警不等于修复部件。

诊断深入[DCGM 插件结果与源码](../gpu/bare-metal-fleet/09-DCGM诊断插件结果与故障归因.md)和[NVSM 对象树与证据包](../gpu/bare-metal-fleet/10-NVSM对象树健康检查与证据包.md)，用逐实体覆盖矩阵解释汇总信息的损失，区分共用数据源、独立证据和正式现场诊断流程。

容量与多租户归因见 [GPU 容量与利用率口径](../sre/observability/gpu/06-GPU容量利用率与多租户归因.md)。应能手算资源时间分母，识别共享指标重复关联，区分忙碌与有效产出。

[DPU 路线](../networking/dpu/00-BlueField-DPU-DOCA与AI基础设施卸载.md)补充 Host/Arm 管理边界、DOCA 服务和 BlueMan 遥测；[边缘 AI 生命周期](../cloud-native/serverless-edge/edge/06-Fleet-Command与边缘AI生命周期.md)补充站点注册、制品协调和断连恢复。两者复用基础知识，但并非每个数据中心 GPU 工作负载都必须使用它们。

用 DPF 26.4 的 BFB 矩阵区分完整支持、旧 LTS 运行条件与未列出的组合，并将 Operator 相邻版本升级和 BFB 演进分开。Fleet Command 则按公开 CLI 继续区分 AppConfig/DEFAULT、部署安全替换边界、远程代理曝光和位置重建，不把位置重置当作普通查询修复。

边缘专题进一步区分已公开的激活码配对、JIT 会话和动态证书隧道，以及用于学习的修订、幂等和崩溃窗口模型。位置高可用需要单独计算失效后的应用容量；云端管理平台更新不等于站点升级无中断。

## 8. 三层掌握检查

第一层是解释：不运行硬件也能区分对象、控制链和边界。第二层是推演：能手算资源分配、数据量、流水线周期和 Checkpoint 切断点。第三层是运行验证：在获授权的目标版本与平台中，观察真实状态、验证假设并完成安全恢复。

每次实际验证保存机型、版本、配置、输入、原始结果和适用范围。不具备 GPU、BCM、Run:ai 或 DPU 环境时，可完成前两层，但不能据此宣称已完成平台操作或性能验收。

### 8.1 用反例确定证据边界

掌握一个机制，应先说清要证明的命题，再找能推翻它的最小反例。下面不是待执行的破坏性实验清单，而是区分证据层次的检查题；运行验证应在有授权且有恢复条件的环境另行安排。

| 待判断的命题 | 最小反例 | 有效验证还需关联 |
| --- | --- | --- |
| BCM 镜像修改后节点已经生效 | 节点仍启动旧内核或旧初始化产物 | 目标镜像、生成产物、实际启动来源与运行版本 |
| Slurm 有空闲 GPU 就能启动作业 | GPU 总数足够，但节点形状或账户资格不符 | 作业请求、资格、逐节点资源和调度原因 |
| Run:ai 数据库恢复后公平性也恢复 | 专用历史用量存储缺失，工作负载仍在运行 | 数据库、历史账本、调度配置及执行状态的对应时间点 |
| GDRCopy 拷贝调用完成就能被 GPU 正确消费 | 缺少当前路径所需的提交或同步关系 | 后端、内存寿命、CPU 完成与 GPU 消费的顺序 |
| DPF 的对象就绪就代表业务已卸载 | 服务可运行，但业务流未匹配到目标规则 | 对象身份、服务链、规则完成、命中计数与实际流量 |
| Fleet Command 位置 ONLINE 就代表新版本发布完成 | 部署仍在 DEPLOYING，或运行的模型未更新 | 位置、部署、实际制品、业务结果和观察时效 |

合格答案不仅说“还要检查”，还要指出哪个对象掌握哪份状态、两份状态靠什么身份和时间关联，以及证据缺失时结论应停在哪一层。来自同一数据源的两个面板，不自动构成独立佐证。

### 8.2 固定组合才能复现结论

版本记录要覆盖与命题相关的依赖边，而不是只写主产品版本。研究 DPF 升级时记录硬件、BFB、固件、Operator 与服务要求；研究 GDRCopy 时记录源码标签、后端、驱动、内核和平台；研究 Run:ai 恢复时记录部署类型、版本、实际持久化配置和恢复时点。没有参与当前命题的字段不必机械收集。

一条结论至少区分四种范围：文档允许的组合、实际安装的组合、当前激活的组合、已经验证该命题的组合。前者不自动推出后者；一组通过也不代表矩阵中的每个组合都已通过。恢复前后需要比较同一身份的资源和状态，替换了机器、对象或数据集就应显式记录变化。

例如一组目标版本的 Run:ai 历史卷恢复成功，只能支持该组合与恢复点下的结论；不能直接证明另一个部署类型、存储类或历史窗口也有相同结果。纸面分析可以解释为什么这些依赖重要，实际结论仍需要原始观察。
