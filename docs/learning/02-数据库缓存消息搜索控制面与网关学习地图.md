# 数据库、缓存、消息、搜索、控制面与网关学习地图

这些技术不是一条链路上的同类替代品，而是分别承担事实存储、低延迟访问、异步解耦、检索分析、向量召回、控制面状态和流量接入。正确学习方式是先掌握每个系统内部的数据路径，再研究它们怎样交接状态。

## 1. 完整职责地图

```text
Client
  → Nginx / HAProxy / APISIX / Higress      流量接入、路由、安全、治理
  → Application
       ├─ MySQL / PostgreSQL                事务事实与关系数据
       ├─ Redis                             缓存、临时状态、原子数据结构
       ├─ Kafka / Pulsar / RocketMQ / RabbitMQ 异步消息、事件日志或队列路由
       ├─ Elasticsearch                     全文/混合搜索与时序检索
       ├─ ClickHouse                        大规模列式聚合分析
       └─ Milvus                            大规模向量近似检索

Platform control plane
  ├─ etcd                                  强一致 KV、Lease、Watch、DCS
  ├─ ZooKeeper                             层级命名空间、Session、Watch、协调
  ├─ Nacos                                 服务发现与配置中心
  └─ Consul                                混合基础设施服务发现与服务网络
```

### 1.1 一个典型业务写入 {/* #一个典型业务写入 */}

```text
HTTP request
→ Gateway authentication/routing
→ Application transaction
→ MySQL/PostgreSQL commit
→ Outbox/Debezium/Canal/Maxwell CDC
→ Kafka/Pulsar/RocketMQ/RabbitMQ + Schema Registry
→ Redis invalidation
→ Elasticsearch/ClickHouse/Milvus projection
```

事务库保存权威事实，缓存/搜索/分析/向量系统通常保存可重建的派生视图。消息系统负责传输和重放变化，但不会自动保证每个下游与业务事务绝对同步。

## 3. 推荐学习顺序

### 3.1 共同基础 {/* #第一阶段共同基础 */}

先掌握 Linux 进程/内存/文件系统、TCP/TLS/DNS、磁盘 I/O、分区/副本/多数派、序列化、幂等和一致性。否则每个产品都会变成一组孤立参数。

### 3.2 事实与缓存 {/* #第二阶段事实与缓存 */}

```text
MySQL 或 PostgreSQL
→ Redis
```

先理解事务事实、WAL/Redo 和恢复，再学习缓存。这样才能正确处理 Cache-Aside、失效、穿透、击穿和数据库保护，而不是把 Redis 当主库使用。

### 3.3 事件与派生数据 {/* #第三阶段事件与派生数据 */}

```text
Kafka / Pulsar / RocketMQ / RabbitMQ
→ Elasticsearch / ClickHouse / Doris / Milvus
```

消息系统用于传播事实变化，搜索/分析/向量系统构建不同查询模型。用 Debezium 或 Canal/Maxwell 把 Binlog/WAL 变成事件，用 Schema Registry 管理契约，再由 Airflow 编排批处理与补数。重点验证 Offset、重试、重复、顺序、Schema 变化和重建流程。

### 3.4 控制面 {/* #第四阶段控制面 */}

```text
etcd → ZooKeeper → Nacos / Consul
```

先理解 etcd 的 Raft、MVCC、Watch 与 Lease，再学习 ZooKeeper 的层级 ZNode、Session、一次性 Watch 与 ZAB，最后比较 Nacos 的配置/注册中心和 Consul 的混合基础设施服务发现。它们都可能参与协调，但数据模型、客户端语义和产品目标不同，不能仅按“都能存配置”比较。

### 3.5 流量数据面 {/* #第五阶段流量数据面 */}

```text
Nginx / HAProxy → Envoy → APISIX / Higress
```

先用 Nginx/HAProxy 掌握 HTTP/TCP 代理、Upstream、健康检查和连接；再用 Envoy 掌握 Listener/Filter/xDS；最后比较 APISIX 的 Nginx/Lua/etcd 插件网关和 Higress 的 Envoy/Wasm/Gateway API 路线。

## 4. 每条路线统一的文章标准

每项技术都必须包含：

1. 解决什么问题，与相邻技术怎样选；
2. 一条请求/数据从客户端到内存、日志、磁盘、副本的完整路径；
3. 核心数据结构、线程/进程、控制面与数据面；
4. Package/二进制、Docker、集群、Kubernetes 等多种部署与原理；
5. 一致性、持久化、复制、高可用与数据丢失边界；
6. 性能、容量、Benchmark、指标和 SLO；
7. 权限、TLS、Secret、审计和多租户；
8. 备份恢复、升级回滚、扩缩容和跨集群；
9. 命令/API、实验、故障注入和 Runbook；
10. 源码主路径与可扩展点。

## 5. 统一验收方式

```text
画路径：不看文档画出组件和状态
做部署：至少完成单机与三节点/生产形态
测基线：吞吐、P95/P99、资源、正确性
造故障：进程、节点、网络、磁盘、依赖
做恢复：证明数据/角色/路由正确
写复盘：根因、证据、修复、副作用、回滚
```

“从零到精通”不是每个参数都背过，而是面对请求慢、数据不一致、节点故障、容量不足和升级失败时，能沿数据、日志、复制、控制面和资源找到可验证证据。
