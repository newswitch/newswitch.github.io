# 服务器带宽与延迟预算：CPU、DDR、PCIe、NIC、NVMe、GPU 与 NVLink

看到“400 GbE、PCIe 5.0 x16、八通道 DDR5、3 TB/s HBM”时，不能把这些数字直接当成应用吞吐。它们描述的对象、方向、编码方式和测试条件不同；数据真正经过的路径中，还存在协议头、事务开销、共享上行、内存复制、NUMA 和同步等待。

带宽预算的目标不是计算一个看起来精确的理论数字，而是回答三个问题：

1. 哪一段可能成为上限；
2. 当前实测离合理上限还有多远；
3. 下一步应观察或扩容哪一层。

## 1. 先区分五种指标

| 指标 | 回答的问题 | 常见单位 |
| --- | --- | --- |
| 容量 | 一共能放多少数据 | GB、TB |
| 带宽 | 单位时间最多搬多少字节 | GB/s、Gb/s |
| 延迟 | 一次操作从发起到完成要多久 | ns、μs、ms |
| IOPS/PPS | 每秒可完成多少次 I/O 或报文 | IOPS、pps |
| 计算吞吐 | 单位时间完成多少计算 | FLOPS、Tokens/s |

容量大不等于带宽高，带宽高也不等于小请求延迟低。一个 3 TB/s HBM 系统可能因为 Kernel 太小而计算单元空闲；一块峰值 7 GB/s 的 NVMe 也可能在低 Queue Depth 同步写时只表现出数万 IOPS。

## 2. 四个容易混淆的“带宽”

### 2.1 信号速率

PCIe 使用 `GT/s` 描述每条 Lane 每秒发生多少次传输。它不是直接可用的 `GB/s`，还要考虑编码和协议。

### 2.2 编码后的原始数据率

PCIe 3.0、4.0、5.0 使用 128b/130b 编码。简化计算为：

```text
单向理论数据率
≈ GT/s × Lane 数 × 128/130 ÷ 8
```

| 代际 | 每 Lane 信号速率 | x4 单向理论值 | x16 单向理论值 |
| --- | ---: | ---: | ---: |
| PCIe 3.0 | 8 GT/s | 约 3.94 GB/s | 约 15.75 GB/s |
| PCIe 4.0 | 16 GT/s | 约 7.88 GB/s | 约 31.51 GB/s |
| PCIe 5.0 | 32 GT/s | 约 15.75 GB/s | 约 63.02 GB/s |

表中的数字仍未扣除 Transaction Layer Packet、DLLP、流控、地址和实现开销。PCIe 6.0 引入 PAM4 与 FLIT Mode，不能继续直接套用 128b/130b 的公式。

### 2.3 协议有效带宽

以 400 GbE 为例：

```text
400 Gb/s ÷ 8 = 50 GB/s
```

50 GB/s 是线路比特率换算结果，不是 HTTP、TCP、RDMA 或存储应用一定能获得的 Payload 吞吐。还要扣除以太网帧、FEC、IP/UDP/TCP/RDMA Header、帧间间隔以及重传等开销。

### 2.4 应用有效吞吐

应用看到的是端到端结果：

```text
应用有效吞吐
= 有效数据字节 ÷ 完成时间
```

它还受到内存分配、复制、Checksum、序列化、系统调用、锁、Queue Depth、Batch Size 和同步点影响。

因此排障报告必须注明数字属于哪一个口径，不能只写“带宽 50 GB/s”。

## 3. DDR 理论带宽怎样计算

DDR 标注通常使用 `MT/s`。单个 64-bit 数据通道的简化理论带宽为：

```text
带宽 = MT/s × 64 bit ÷ 8
```

例如八通道 DDR5-5600：

```text
5600 MT/s × 8 Byte × 8 Channel
= 358400 MB/s
≈ 358.4 GB/s / Socket
```

这不是应用可持续带宽。实际值还受以下因素影响：

- DIMM 插法是否填满所有 Channel；
- 每通道 DIMM 数导致的降频；
- 读写比例、访问步长和并发；
- Cache 命中、Prefetch 和 Write Allocate；
- NUMA 远端访问与 Socket 互联；
- CPU 型号、BIOS 和功耗策略。

“服务器有 2 TB 内存”只说明容量，不能推导它拥有足够内存带宽。

## 4. 整机数据路径先画图再算账

普通网络数据进入 GPU 推理进程时，可能经历：

```text
400 GbE Link
→ NIC RX Queue
→ PCIe
→ Host DRAM
→ CPU 协议与应用处理
→ Pinned Buffer
→ PCIe
→ GPU HBM
```

GPUDirect RDMA 的数据面可能缩短为：

```text
NIC
→ PCIe Switch / Root Complex
→ GPU HBM
```

但直接路径是否成立还取决于拓扑、ACS、IOMMU、驱动、内存注册和软件是否真正选择 GDR。控制面仍然需要 CPU。

模型从本地盘加载到 GPU 时，普通路径通常是：

```text
NVMe
→ PCIe
→ Page Cache / Host Buffer
→ 反序列化与权重整理
→ Pinned Buffer
→ PCIe
→ GPU HBM
```

因此冷启动慢不一定是磁盘慢，还可能是单线程反序列化、Host DRAM、跨 NUMA 或 Host-to-Device Copy。

## 5. 最窄链路公式

对于一条串行数据路径，可以先使用上限模型：

```text
端到端吞吐上限 ≤ min(
  数据源持续吞吐，
  每段互联有效带宽，
  Host DRAM 可用带宽，
  CPU 处理速度，
  目标设备接收与消费速度
)
```

这只是第一步。若数据需要先写 Host DRAM 再被读出，100 GB/s 的 Payload 可能消耗约 200 GB/s 的 DRAM 流量；若还有一次额外复制，消耗继续增加。

因此要记录：

```text
Payload 字节数
× 每层读写次数
= 该层实际流量需求
```

## 6. 一个 400 GbE 到 GPU 的预算示例

假设：

- 单端口 400 GbE NIC；
- NIC 使用 PCIe 5.0 x16；
- GPU 使用 PCIe 5.0 x16；
- NIC 与 GPU 在同一 Socket；
- 普通 Host DRAM 中转路径；
- 不考虑业务计算，只分析 Payload 搬运。

理论口径：

| 层次 | 标称上限 | 第一轮判断 |
| --- | ---: | --- |
| 网络线路 | 50 GB/s | 扣协议后低于 50 GB/s |
| NIC PCIe 5.0 x16 | 约 63 GB/s/方向 | 单端口线路更可能先到上限 |
| GPU PCIe 5.0 x16 | 约 63 GB/s/方向 | 足够承接单端口理论 Payload |
| Host DRAM | 依平台而定 | 要承担 NIC 写入和 GPU 读取 |
| GPU HBM | 通常远高于 PCIe | 本例不代表 Kernel 不会受 HBM 限制 |

如果有效网络 Payload 为 45 GB/s，Host DRAM 至少要处理近似：

```text
NIC DMA Write 约 45 GB/s
+ GPU DMA Read 约 45 GB/s
= 约 90 GB/s Host DRAM 流量
```

再加上 CPU 访问、其他任务和额外复制，内存控制器可能先于 PCIe 进入饱和。只看“DDR 理论 358 GB/s”仍不够，因为业务只能使用其中一部分，而且可能集中在一个 NUMA Node。

## 7. PCIe Switch 的上行过订阅

假设八块 PCIe 4.0 x4 NVMe 连接到一个 PCIe Switch，而 Switch 到 CPU 只有 PCIe 4.0 x16：

```text
八块盘下行总理论带宽
= 8 × 7.88 GB/s
≈ 63 GB/s

Switch 上行理论带宽
≈ 31.5 GB/s
```

这是约 2:1 的带宽过订阅。单盘测试可能都正常，八盘并发才会撞到共享上行。类似关系也可能出现在：

- 多个 NIC Port 共用一条 PCIe 上行；
- 多张 GPU 经 PCIe Switch 连接一个 Root Port；
- Riser 或背板共享 CPU Lane；
- 多设备同时跨 Socket 访问远端内存。

所以设备数量乘以单设备峰值，不能直接作为整机吞吐。

## 8. GPU 间通信要区分路径

两张 GPU 可能通过不同路径通信：

```text
GPU ↔ NVLink ↔ GPU
GPU ↔ NVSwitch Fabric ↔ GPU
GPU ↔ PCIe Switch ↔ GPU
GPU ↔ Root Complex / Socket Fabric ↔ GPU
GPU ↔ Host Memory Staging ↔ GPU
```

判断时不能只看 GPU 型号。还要确认：

- `nvidia-smi topo -m` 的实际可达关系；
- P2P Read/Write 是否允许；
- NCCL/HCCL 实际选择的 Transport；
- Link 是否降速、降宽或出现重放；
- 多个通信流是否共享同一上行。

NVLink 的标称带宽也必须说明是单 Link 还是聚合、单向还是双向、每 GPU 注入带宽还是 Fabric 总带宽。

## 9. 延迟预算不能用带宽代替

总延迟可以先按关键路径拆分：

```text
端到端延迟
= 排队等待
+ 软件处理
+ 数据搬运
+ 设备执行
+ 同步与返回
```

近似传输时间为：

```text
传输时间 ≈ 固定延迟 + 数据量 ÷ 有效带宽
```

小消息主要受固定延迟、Doorbell、中断、协议栈和同步影响；大块连续传输才更接近带宽上限。因此：

- `ping` 小包正常不能证明大块传输正常；
- 大块带宽测试正常不能证明 RPC P99 正常；
- 提高链路带宽不一定降低短请求延迟；
- Batch 能提高吞吐，但可能增加排队延迟。

## 10. 如何采集实际拓扑与协商状态

### 10.1 PCIe

```bash
lspci -tv
lspci -s 41:00.0 -vv
```

关键字段示例：

```text
LnkCap: Speed 32GT/s, Width x16
LnkSta: Speed 16GT/s (downgraded), Width x8 (downgraded)
```

这表示设备能力不等于当前链路状态，预算必须使用 `LnkSta`。

### 10.2 NUMA

```bash
numactl -H
cat /sys/bus/pci/devices/0000:41:00.0/numa_node
```

### 10.3 GPU

```bash
nvidia-smi topo -m
nvidia-smi topo -p2p r
nvidia-smi topo -p2p w
```

### 10.4 NIC 与 NVMe

```bash
ethtool eth0
ethtool -S eth0
nvme list
nvme smart-log /dev/nvme0
```

工具输出必须和主板 Block Diagram、BDF、NUMA、上游 Switch 一起解释。

## 11. 从现象反推最可能的层次

| 现象 | 优先检查 |
| --- | --- |
| 单设备快，多设备并发慢 | 共享 PCIe 上行、DRAM、Socket 互联、功耗 |
| 本地 NUMA 快，远端 NUMA 慢 | UPI/xGMI、内存归属、IRQ 与线程亲和 |
| 小 I/O 正常，大块传输慢 | Link Width/Speed、MTU、带宽与热降频 |
| GPU HBM 很空但加载慢 | 存储、CPU 反序列化、Host DRAM、PCIe Copy |
| GPU 算力低但 PCIe 流量高 | 频繁搬运、Batch 太小、数据布局或 Offload |
| NIC 线速正常但应用吞吐低 | CPU、协议处理、复制、锁、队列和响应端 |
| 压测前几分钟快，之后下降 | 温度、功耗、SSD GC、缓存耗尽或降频 |

## 12. 一份可复用的带宽账本

| 段 | 来源/目的 | 标称能力 | 当前状态 | 实测 | 是否共享 | 证据 |
| --- | --- | ---: | ---: | ---: | --- | --- |
| NIC Link | Switch↔NIC | 400 Gb/s | 400 Gb/s | 待测 | 否 | `ethtool` |
| NIC PCIe | NIC↔CPU | Gen5 x16 | Gen5 x16 | 待测 | Root Port | `lspci -vv` |
| DRAM | IMC↔DIMM | 理论值 | 当前频率/通道 | 待测 | 是 | DMI/PMU |
| Socket Link | CPU0↔CPU1 | 平台值 | 当前状态 | 待测 | 是 | Uncore PMU |
| GPU PCIe | CPU↔GPU | Gen5 x16 | 实际 Speed/Width | 待测 | 可能 | `nvidia-smi`/`lspci` |
| GPU Fabric | GPU↔GPU | NVLink/NVSwitch | 实际拓扑 | 待测 | 是 | topo/NCCL |

任何一列写“未知”，都表示当前还不能对瓶颈下结论。

## 13. 常见误区

### 13.1 双向带宽可以直接用于单向业务

不可以。厂商有时把两个方向相加，业务却可能主要单向传输。

### 13.2 多块设备的峰值可以直接相加

不可以。它们可能共享 PCIe Switch 上行、Root Port、IMC、Socket Link、供电或散热能力。

### 13.3 同一 NUMA Node 就一定是直连

不一定。同 NUMA 只说明 CPU/内存归属接近，设备之间是否 P2P 还受 PCIe 层级、ACS、IOMMU 和驱动影响。

### 13.4 HBM 带宽很高，GPU 就不可能等数据

错误。数据可能尚未进入 HBM，也可能因为访问模式、Kernel、同步和 Cache 行为无法有效使用 HBM 带宽。

## 14. 练习与答案

**问题：四块峰值 7 GB/s 的 NVMe 是否只需要 28 GB/s 的 PCIe 上行？**

答案：28 GB/s 只是设备峰值相加，还要确认读写方向、协议开销和持续性能。PCIe 4.0 x16 理论约 31.5 GB/s，看似足够但余量很小；若还有其他设备共享上行，或设备峰值口径不同，就可能进入过订阅。

**问题：400 GbE NIC 和 PCIe 4.0 x16 搭配时，哪一层先成为上限？**

答案：400 GbE 线路换算为 50 GB/s，而 PCIe 4.0 x16 编码后理论约 31.5 GB/s/方向，所以 PCIe 上行的理论上限更低。实际还需检查 NIC 是否使用多个 Function/Link、当前协商状态和协议有效负载。

**问题：为什么一次 100 GB 数据传输可能消耗超过 100 GB 的内存总线流量？**

答案：数据可能先被设备 DMA 写入 DRAM，再被 CPU 或另一个设备读出，还可能发生用户态、页缓存和 Pinned Buffer 之间的额外复制。每一次读写都会消耗内存控制器带宽。
