# 单算子、算子链与端到端性能归因

“新 Kernel 快了 30%”和“在线服务快了 30%”是两种完全不同的结论。性能分析需要建立从局部到整体的证据链：

```text
Kernel微基准
→ 相邻算子链
→ 模型Prefill/Decode Step
→ 推理引擎调度
→ 在线请求TTFT/TPOT/吞吐/P99
```

任意一层缺失，都可能把优化收益或回归归错对象。

## 1. 四个测量层级

### 1.1 单 Kernel

回答“这个实现对固定输入 Shape 是否更快”：

- Kernel Duration；
- 实际 FLOPs/s 或 Bytes/s；
- HBM/L2 流量；
- Occupancy、寄存器、Shared Memory；
- Workspace；
- 数值误差。

### 1.2 算子链

回答“融合、布局转换和同步加入后是否仍有净收益”：

```text
Router → Top-k → Dispatch → Grouped GEMM → Combine
```

单 GEMM 更快，但若需要额外 Transpose、Packing 或同步，链路可能更慢。

### 1.3 模型 Step

回答“优化在 Prefill、Decode 或训练 Step 中占多少”：

- 每层和全模型时间；
- Kernel 空洞；
- Attention/MLP/MoE/Collective 占比；
- Graph 与 Eager 路径；
- 不同 Batch/Token Shape。

### 1.4 在线服务

回答“用户和容量是否真正受益”：

- TTFT、TPOT、E2E 的 P50/P95/P99；
- Prompt/Generation tokens/s；
- Goodput，即满足 SLO 的有效吞吐；
- 错误、超时和流式完成率；
- 最大安全并发、显存余量和单位 Token 成本。

## 2. Amdahl 定律给出收益上限

若某 Kernel 占端到端时间比例为 `p`，它加速 `s` 倍，整体理论加速上限：

```text
Speedup_total = 1 / ((1 - p) + p / s)
```

例如 Kernel 占 10%，即使它加速 2 倍，整体理论加速也只有约 1.053 倍。若报告端到端提高 30%，说明还有 Batch、同步、通信或测量条件发生变化，不能全归因于该 Kernel。

## 3. 基线必须冻结什么

```text
模型与Tokenizer Revision
镜像、框架、驱动、CUDA/CANN版本
GPU/NPU型号、频率、功耗模式和拓扑
TP/PP/DP/EP配置
输入/输出Token联合分布
并发、到达模型和Prefix命中率
Scheduler、KV、Graph和量化参数
编译/Autotune Cache状态
```

只写“同一台机器”远远不够。GPU 温度、频率、其他进程、NUMA 位置和网络路径也会影响结果。

## 4. 冷启动与稳态分开

冷启动可能包含：

- 权重下载和加载；
- Kernel JIT 编译；
- Autotune；
- CUDA/ACL Graph Capture；
- NCCL/HCCL 初始化；
- Prefix/KV/文件 Cache 预热。

稳态测量应规定 Warmup 条件，冷启动则单独记录每阶段时间。丢掉所有首轮数据会掩盖发布和扩缩容风险，把首轮混入稳态又会扭曲常态性能。

## 5. 控制变量与消融矩阵

假设候选版本同时包含：确定性 GEMM、Decode 融合、CUDA Graph 和通信融合。正确矩阵至少包括：

| 组别 | GEMM | Decode融合 | Graph | 通信融合 |
| --- | --- | --- | --- | --- |
| A 基线 | 旧 | 关 | 关/原配置 | 关 |
| B | 新 | 同A | 同A | 同A |
| C | 新 | 开 | 同A | 同A |
| D | 新 | 开 | 开 | 同A |
| E 最终 | 新 | 开 | 开 | 开 |

若成本允许，再对关键交互做正交组合。至少要有“只改变一个因素”的证据，才能做单项归因。

## 6. 为什么平均值不够

在线延迟分布通常长尾明显。应报告：

- 请求数和持续时间；
- P50/P95/P99；
- 均值与标准差；
- 多轮重复结果和置信区间；
- 异常值是否剔除及理由；
- 每轮硬件频率、温度和错误情况。

不同版本应使用同一请求回放或同一随机种子生成的负载。比较两个独立的随机流量窗口，流量差异可能大于代码差异。

## 7. 吞吐测试最容易犯的错误

| 错误 | 后果 |
| --- | --- |
| 只固定请求数，不固定Token | 工作量不同 |
| 只报requests/s | 长短请求混合时不可比较 |
| 无限压测后报最大值 | 尾延迟和错误已失控 |
| 一个版本排队更深 | GPU更忙但用户更慢 |
| Prefix命中率不同 | 节省的Prefill被误算为Kernel收益 |
| 输出长度被EOS改变 | 实际生成Token不同 |

更有意义的是在相同 SLO 下比较 Goodput，以及相同 Token 分布下的 Prompt/Generation tokens/s。

## 8. 正确性是性能结论的前置门槛

一个跳过计算、错误复用 Buffer 或改变输出长度的版本当然更快。每个性能实验先验证：

- 输出数值误差在目标范围；
- Router/Token/协议行为符合要求；
- 没有 NaN、错误和隐藏回退；
- 生成长度和停止条件可比；
- 多卡 Rank 都完成同一轮 Collective。

若优化改变数学语义，应把它作为算法变更，单独做质量权衡，不能称作“等价性能优化”。

## 9. 用时间线做因果证据

一份可复核的时间线应能回答：

```text
CPU什么时候提交工作？
GPU什么时候空闲？
目标Kernel实际运行多久？
前后是否多了Memcpy、同步或Collective？
所有Rank是否同序执行？
Graph是否命中还是回退？
```

框架日志和 GPU Util 只能提供线索，Profiler Trace 才能证明局部执行路径变化。

## 10. 一个归因示例

现象：替换 Router GEMM 后，单 Kernel 快 25%，端到端吞吐提高 12%。

进一步测量：

```text
Router GEMM单Kernel：-25%
Router完整算子链：-14%（新增布局转换抵消部分收益）
Decode Step：-3%（Attention和通信占大头）
服务吞吐：+12%（同时Batch增大且排队更深）
P99 TPOT：+9%（变差）
```

正确结论是：GEMM 对 Decode Step 有约 3% 可测收益；12% 吞吐包含 Batch/排队策略影响，而且尾延迟回归。不能只保留“吞吐提升 12%”。

## 12. 自测题与答案

### 12.1 多个优化一起上线后，能否把总吞吐收益归给其中一个 Kernel？

不能。需要单变量消融，至少分别测单 Kernel、算子链、模型 Step 和服务。没有消融时只能报告组合版本收益。

### 12.2 为什么单 Kernel 提速 50%，端到端可能只提高 2%？

该 Kernel 在端到端时间中占比很小，收益受 Amdahl 定律限制；其他阶段、同步和排队没有改变。

### 12.3 为什么“GPU Util 更高”不一定更好？

更高可能来自更深排队、低效 Kernel、忙等或更大的 Batch。必须同时看 Goodput、尾延迟、实际 Kernel 效率和资源余量。

### 12.4 如何证明 Graph 是收益来源？

固定其他条件，对同一 Shape 做 Eager/Graph A/B；在时间线上验证 Launch 空洞减少、Graph Replay 命中，并回到端到端指标确认收益。若 Graph 同时改变了融合或通信路径，需要继续拆分。
