# 驱动升级状态机、客户端引用与可用性预算

驱动容器更新，不只是替换容器里的普通库：它可能修改宿主机内核模块，并影响同节点全部 GPU 客户端。升级正确性需要同时满足对象生命周期、平台兼容性和业务中断预算。

前置阅读 [Operator 升级与维护](./08-GPU%20Operator%20升级、回滚与节点维护.md)。下面以 **GPU Operator 26.3 的 ClusterPolicy 管理路径**解释状态；其他版本和 NVIDIADriver 管理模式的字段与作用范围应分别核对。

## 1. 磁盘上的新文件不等于运行中的新驱动

系统可以已经安装新驱动包，却仍加载旧内核模块；也可以启动了新 Driver Pod，但 GPU 客户端尚未退出，卸载重载未完成。用户态库、内核模块、设备上下文和运行任务不是同一个生命周期。

因此检查要比较期望版本、实际运行模块、进程加载库和最小计算结果。单看镜像标签或磁盘包版本，无法证明当前请求已经经过新驱动。

容器化驱动与宿主机预装驱动还必须区分所有权。Operator 管理的驱动路径不会自动成为所有主机安装方式的统一升级器，不能让两个系统同时管理同一套驱动文件与模块。

## 2. 训练进程退出后，设备仍可能有使用者

除了训练进程，显示服务、监控、持久化服务、Fabric 管理及其他设备客户端也可能持有资源。比如 NVIDIA Persistence Daemon 会维持设备打开以保持相应初始化状态，见 [Persistence Daemon](https://docs.nvidia.com/deploy/driver-persistence/persistence-daemon.html)。

GPU 内存导出、通信上下文和相关驱动依赖也需要按其生命周期释放。不能仅凭 GPU 利用率为零或进程列表里没有训练脚本，就判断可以安全卸载。

引用未释放时，正确问题是“谁仍在使用哪份资源，怎样按其协议停止”，不是强制卸载或批量结束所有进程。后者可能破坏数据面和恢复证据。

## 3. 状态机把破坏性动作拆成可观察阶段

26.3 文档的升级链路包含如下状态，drain 是符合配置与失败条件时才进入的分支。见 [GPU Driver Upgrades](https://docs.nvidia.com/datacenter/cloud-native/gpu-operator/26.3/gpu-driver-upgrades.html)。

```text
upgrade-required → cordon-required → wait-for-jobs-required
→ pod-deletion-required → 必要时 drain-required
→ pod-restart-required → validation-required
→ uncordon-required → upgrade-done
```

状态表示当前协调步骤，不是业务已经满足 SLO 的证明。停在等待阶段与停在模块装载阶段，后续证据和动作完全不同；修改标签跳过阶段也不等于满足了阶段前提。

`waitForCompletion` 选择哪些任务等待、等多久；后续删除与 drain 又有不同范围。不能认为“配置了等待”就让节点上所有业务自动完成 Checkpoint。

## 4. 并行数与不可用预算是两个限制

`maxParallelUpgrades` 限制同时进行的升级数量；`maxUnavailable` 还考虑当前已经不可用的节点。已有维护占用预算时，即使升级并行数尚未用满，也可能不能继续。

教学条件：12 个适用节点，最大不可用 25%，因此预算为 3 个；其中已有 2 个不可用，即使允许并行升级 2 个，此刻也只剩约 1 个新增不可用位置。若已有 3 个，新增位置就是 0。

这个预算按节点计算，不是按 GPU、机架或模型副本的有效容量计算。一台八卡节点与一台单卡节点都可能只算一个节点，但移除它们对作业形状的影响完全不同。节点预算之外还需要业务容量与拓扑预算。

## 5. PDB 不保护全部中断

Kubernetes 的 PDB 约束特定自愿驱逐；直接删除 Pod、控制器更新和非自愿故障并不都受它保护。实际工具应采用什么 API、何时可能强制处理，必须分别核对，不能从 `podDeletion` 的字段名推导出完整 PDB 保证。参见 [Kubernetes Disruptions](https://kubernetes.io/docs/concepts/workloads/pods/disruptions/)。

即使驱逐遵守 PDB，剩余副本也未必能接下全部流量，训练任务也未必能在另一节点继续。GPU 形状、模型装载时间、本地 PV 和通信组约束都可能阻止快速恢复。

例如服务原有 3 个副本，每个稳定承载 100 请求/秒，当前负载 250。允许中断一个后只剩 200 的教学容量，虽然副本预算允许，业务仍会排队。PDB 是数量保护，不是性能容量证明。

## 6. 验证完成与业务重新入池要分层

Validator 通过说明相应检查成功，仍应核对驱动版本、设备资源、MIG/CDI 身份及代表性应用。若节点有 NVSwitch、RDMA 或 GDS，还需要验证相应依赖，不能只做单卡初始化。

资源重新公布后，调度器可能迅速派发任务。如果平台需要更严格的业务验收，应在维护设计中安排额外准入门禁，而不是一边允许调度、一边假定验证尚未完成的节点不会被使用。

监控也要排除升级造成的缺失窗口。采集恢复但 GPU 指标身份变了，需要重新关联，不能把旧序列的停止解释成零故障。

## 7. 回滚需要恢复一组兼容状态

Helm rollback 可以回到旧发布配置，却不自动恢复已装载模块、MIG 布局、CRD 变化、外部驱动包和被中断的作业。回滚目标应至少覆盖控制器/CRD、驱动与内核、运行时注入、设备资源和应用恢复点。

恢复旧驱动也可能需要再次处理客户端与重启条件。不能为了尽快取消维护状态，先放开调度再补模块验证。升级失败应保留最早失败阶段及前置事实，不循环重试掩盖根因。

## 8. 掌握检查

解释磁盘版本与运行模块为什么可能不同；列出训练进程之外的客户端；手算 12 节点预算与 250 请求/秒例子；说明 PDB、升级并行数和业务 SLO 分别保护什么。最后画出一次安全回滚需要恢复的状态集合。
