# 队列感知的大模型推理自动扩缩容

普通 Web 服务常按 CPU 扩容；大模型推理按 GPU Utilization 扩容往往太晚或方向错误：

- GPU 利用高可能是健康高效，不一定需要扩容；
- GPU 利用低可能因 CPU、存储、NCCL 故障，扩容会放大问题；
- 请求成本由输入/输出 token 和上下文差异决定；
- 新副本要下载模型、占 GPU、预热，冷启动很长；
- KV Cache 与 continuous batching 决定并发上限；
- 新副本可能没有可用 GPU，只会 Pending。

因此应从“队列与 SLO”设计闭环。

## 1. 目标不是 GPU 利用率，而是业务 SLO

主要 SLI：

- success/error/rejection；
- TTFT；
- TPOT；
- waiting requests/tokens；
- running sequences；
- input/output token throughput；
- KV Cache 使用/抢占；
- 每模型和长度桶的 P95/P99；
- cost per token/request。

扩容要保护 SLO；缩容要避免浪费且不杀在途长请求。

## 2. 推理容量的简化模型

```text
arrival work rate = requests/s × expected tokens/request
service work rate per replica = tokens/s under target SLO
required replicas ≈ arrival work rate / safe service rate
```

请求的 Prefill 与 Decode 成本不同，更精细地拆分：

```text
work ≈ input_tokens × prefill_cost
     + output_tokens × decode_cost
```

在线无法知道真实输出长度，可用模型/租户/参数的滚动分布估算，并对 `max_tokens` 设置上限。

## 3. Little 定律与队列

```text
L = λW
```

等待请求 L 持续增长，说明到达工作量超过完成能力或服务率下降。队列本身是领先于 TTFT 的信号：TTFT 只有请求完成首 token 后才可观测，队列可以更早触发扩容。

## 4. 推荐指标组合

### 4.1 主扩容信号 {/* #主扩容信号 */}

- waiting requests；或
- waiting tokens / estimated work；或
- queue delay P95。

### 4.2 保护信号 {/* #保护信号 */}

- TTFT SLO burn；
- KV Cache 使用/无可用 block；
- rejection/429/503；
- running sequences 和 batch；
- GPU HBM/利用率/功耗。

### 4.3 抑制错误扩容 {/* #抑制错误扩容 */}

- 可用 GPU/队列配额；
- 模型下载后端健康；
- 新副本冷启动 P95；
- 当前 rollout；
- Xid/NCCL/节点故障；
- Pending replica 数。

## 5. 为什么 waiting tokens 比 waiting requests 更好

两个队列都 10 个请求：

```text
A: 每个 100 input + 100 output
B: 每个 32k input + 4k output
```

B 的工作量远大于 A。若引擎暴露 waiting token/sequence 长度分布，应优先使用；否则网关可统计已知 input tokens 与请求参数估算。

Prometheus label 不应使用原始 token 数造成高基数，应分桶。

## 6. HPA 计算直觉

HPA 对平均型指标近似：

```text
desiredReplicas = ceil(currentReplicas × currentMetric / targetMetric)
```

例如每 Pod waiting=6，目标每 Pod=2，4 副本：期望约 12。但实际受 maxReplicas、behavior、缺失指标和就绪 Pod 处理规则影响。

队列指标有两类：

- per-pod average：每实例队列；
- global external：整个模型队列。

全局队列若直接作为 AverageValue 可能口径错误。必须明确 adapter/KEDA 向 HPA 暴露的是总量还是每副本值。

## 7. HPA 自定义/外部指标

`autoscaling/v2` 支持 Pods/Object/External 等指标与 `behavior`。概念示例：

```yaml
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: llm
spec:
  minReplicas: 2
  maxReplicas: 16
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: llm
  metrics:
    - type: External
      external:
        metric:
          name: llm_waiting_work
        target:
          type: AverageValue
          averageValue: "2"
  behavior:
    scaleUp:
      stabilizationWindowSeconds: 0
      policies:
        - type: Pods
          value: 2
          periodSeconds: 60
    scaleDown:
      stabilizationWindowSeconds: 600
      policies:
        - type: Pods
          value: 1
          periodSeconds: 300
```

这是设计示例。指标 API、查询和阈值按平台验证。

## 8. KEDA + Prometheus

KEDA 可轮询 Prometheus scaler 并创建/管理 HPA。示例结构：

```yaml
apiVersion: keda.sh/v1alpha1
kind: ScaledObject
metadata:
  name: llm-queue
spec:
  scaleTargetRef:
    name: llm
  minReplicaCount: 2
  maxReplicaCount: 16
  pollingInterval: 15
  cooldownPeriod: 600
  advanced:
    horizontalPodAutoscalerConfig:
      behavior:
        scaleDown:
          stabilizationWindowSeconds: 600
  triggers:
    - type: prometheus
      metadata:
        serverAddress: http://<prometheus>
        query: <model-scoped-query-returning-one-value>
        threshold: "2"
```

KEDA 版本、认证字段、`metricType` 与 fallback 行为以当前官方 scaler 文档为准。PromQL 必须：

- 只选目标模型/版本/服务；
- 返回单个有效值；
- 对空值、NaN 和监控故障有策略；
- 不把已终止 Pod 的 series 留在查询；
- 使用 recording rule 降低查询开销。

## 9. 指标采集架构

```text
vLLM/Triton/KServe engine metrics
  + gateway request/token metrics
  + Kubernetes/GPU metrics
→ Prometheus recording rules
→ custom/external metrics adapter or KEDA
→ HPA desired replicas
→ Deployment/serving controller
→ scheduler/queue/GPU nodes
→ readiness/EndpointSlice
```

扩容闭环的总时延：

```text
metric scrape + query/poll + HPA decision + scheduling
+ image/model download + model load + warmup + readiness
```

如果总共 10 分钟，15 秒决策一次不会让容量立即出现。

## 10. 冷启动决定前置量

假设：

- 流量每分钟增长 20%；
- 新副本 Ready 需要 8 分钟；

等队列严重积压再扩容一定来不及。组合：

- 最小热副本；
- 计划流量/预测扩容；
- 节点模型缓存预热；
- warm pool；
- 分级限流；
- 更早的 queue slope/burn 信号；
- GPU 节点 autoscaler 与 Pod autoscaler 协同。

## 11. 两级扩容

```text
Level 1: Pod replicas on existing GPU capacity
Level 2: GPU node pool capacity
```

若 Level 1 创建 Pod 但无 GPU：

- Pending 增长；
- queue 未下降；
- autoscaler 可能继续创建更多 Pod；
- 模型发布控制面混乱。

需要：

- max replicas 受可用/可扩 GPU 约束；
- 节点扩容更早触发；
- Provisioning/Cluster Autoscaler 状态进入指标；
- GPU quota 与成本上限；
- 节点 Ready 后驱动/Operator/缓存验收。

## 12. 扩容策略

LLM 副本昂贵，通常每次增加 1～若干个，取决于：

- 单副本安全 token/s；
- 队列增长率；
- 冷启动；
- GPU 可用数；
- 模型后端带宽；
- rollout surge；
- 成本。

扩得太慢，SLO 恢复不了；一次扩太多，会触发模型下载风暴和 GPU 碎片。

## 13. 缩容策略

缩容比扩容危险：

- 流式请求可能持续数分钟；
- KV Cache 不能直接迁移；
- 新流量必须先摘除；
- 请求取消/完成后释放；
- 副本有热模型和图缓存价值；
- 缩到零后冷启动太长。

流程：

```text
mark/drain replica
→ readiness false / router stop new requests
→ wait active requests or deadline
→ cancel per policy
→ preStop + grace
→ terminate
```

HPA 只改 replica 数，不天然理解哪个 Pod 最空闲或已 drain。需要 serving controller/router 配合。

## 14. Stabilization 与防抖

队列具有突发性。策略：

- scaleUp 快，使用短窗口/较大增量；
- scaleDown 慢，长 stabilization/cooldown；
- 只在持续低负载、无排队、容量安全时缩；
- 发布/故障期间暂停缩容；
- 指标异常时保持安全副本，不缩零；
- 为 scale action 设置最小间隔。

## 15. TTFT/TPOT 在扩缩容中的职责

- Queue 指标：领先、用于容量；
- TTFT：验证排队+Prefill 用户体验；
- TPOT：验证 Decode 速度，扩副本不一定修复单实例慢；
- 错误率：保护性指标；
- GPU/KV：原因与安全边界。

如果 TPOT 因 GPU 降频/NCCL 变慢，扩容可能暂时分流，但仍需隔离慢节点并修根因。

## 16. 多模型与异构 GPU

不能用全服务一条队列：

- 每模型/版本独立容量和 SLO；
- GPU SKU/显存不同；
- TP size 不同，每副本需要多张卡；
- 冷启动和 token/s 不同；
- 长短上下文租户不同。

路由层将请求送到模型池；autoscaler 按模型池计算；scheduler/Kueue/ResourceFlavor 确保对应 GPU。

## 17. 失败模式

### 17.1 指标丢失 {/* #指标丢失 */}

Prometheus/KEDA 异常时不应自动缩容。告警 scaler error/metric freshness，采用安全 fallback。

### 17.2 新副本永不 Ready {/* #新副本永不-ready */}

HPA 继续扩容会积累 Pending/Loading。设 max unavailable/download concurrency，并用 startup failure 指标暂停扩容/发布。

### 17.3 队列下降但 TTFT 仍高 {/* #队列下降但-ttft-仍高 */}

可能 Prefill/CPU/网关/网络慢，不是副本数。使用分段 Trace。

### 17.4 KV Cache 满 {/* #kv-cache-满 */}

可扩容，也可能请求上下文/输出上限变化；同时治理 admission、长度和 batching。

### 17.5 缩容震荡 {/* #缩容震荡 */}

cooldown 太短、指标噪声、请求周期或 Pod warmup 未排除。

## 18. 压测与参数标定

1. 固定模型/引擎/GPU/参数；
2. 用短/长 prompt、输出长度分桶；
3. 阶梯增加 arrival rate；
4. 找单副本在 TTFT/TPOT SLO 内的安全吞吐；
5. 记录 queue→TTFT 的拐点；
6. 测冷/热新副本 Ready 时间；
7. 设置 target 与 min/max；
8. 回放突增、突降、周期流量；
9. 注入指标丢失、GPU 不足、模型下载慢；
10. 验证成本和 SLO。

使用开放环 arrival rate 压测比“前一个完成再发下一个”的闭环更能暴露排队。

## 19. 验收矩阵

| 场景 | 期望 |
|---|---|
| 平稳增长 | 队列触发扩容，TTFT 不越界或快速恢复 |
| 突发 | 限流+热容量保护，不无限排队 |
| 流量下降 | 等在途完成，慢速缩容，不震荡 |
| 无 GPU | Pod 不无限增长，节点容量链路触发 |
| 模型冷加载慢 | 分批下载，旧容量保留 |
| 指标丢失 | 不危险缩容，触发告警 |
| 慢 GPU/副本 | 路由摘除/隔离，不用扩容掩盖 |
| 发布 | rollout 与 autoscaler 不争夺容量 |

## 20. 常见误区

1. **GPU 利用率 90% 就扩容。**高利用可能正是高效批处理。
2. **waiting request 不分长度。**工作量误差巨大。
3. **HPA 创建 Pod 就有容量。**可能无 GPU或加载 10 分钟。
4. **缩容直接删 Pod。**会中断 SSE 和丢 KV。
5. **副本越多吞吐线性。**路由、存储、GPU碎片和网关会限制。
6. **TTFT 是最佳领先指标。**它已经包含结果延迟，queue 更早。
7. **PromQL 返回空按 0。**监控故障会触发危险缩容。
8. **scale-to-zero 适合所有 LLM。**冷启动可能远超 SLO。
