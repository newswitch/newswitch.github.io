# Run:ai 状态观测容量分析与恢复边界

管理平台把不同来源的状态集中显示，但这些状态可能具有不同采样时间和更新链路。分析问题必须回到原始对象和时间线，不能只根据仪表盘最后一个颜色执行恢复。

## 1. 五层证据

| 层 | 检查对象 | 常见误读 |
| --- | --- | --- |
| 管理同步 | 集群连接、最后更新时间、身份与证书 | 断连等于全部任务已停 |
| 资源资格 | 项目/部门、池、配额、Rank、借用 | 预算足够等于一定有可用节点 |
| 调度与分组 | PodGroup、事件、节点条件 | 整组准入等于应用就绪 |
| 执行与设备 | Pod、kubelet、运行时、UUID | Running 等于 GPU 正在有效计算 |
| 应用数据面 | Rank、模型、存储、网络与请求指标 | 超时最多的组件就是根因 |

每层都要有一个能否定当前假设的观测。例如“配额不足”可以用有效资格与请求量检验；若资格满足，就不应继续靠增加配额处理镜像下载失败。

## 2. 容量的三种口径

物理 GPU 数量、已经分配的 GPU 资源和形成有效业务进展的容量不同。共享实例还可能使可调度资源数量大于物理卡数量。按项目计费或展示时应说明单位、时间窗口与物理身份映射。

教学例子：16 张物理 GPU，12 张被分配，分配利用率 75%；其中 4 张等待数据。不能据此声称只有 50% 物理卡健康，也不能把等待全部解释为可回收预算。需结合应用进展、配额政策和共享资源瓶颈。

## 3. 恢复前先保留身份

记录工作负载 ID、Pod UID、节点、GPU UUID、镜像 Digest、资源请求、组成员、首个错误和时间。重建对象后名称可能相同而 UID 已变化；只按名称拼日志容易把多次尝试误连成一次运行。

修复范围应尽量小：仓库认证失败更新相关 Secret；节点掉卡先隔离节点；调度器异常先核对组件日志和版本。不要因为控制面页面落后就删除整个集群注册，这可能扩大配置与身份差异。

## 4. 升级与管理面恢复

控制面与集群组件升级应遵守目标版本兼容窗口，保留配置、持久化服务和身份材料的恢复点。回退 Chart 不一定回退数据库格式、CRD 或运行中对象，不能把 Helm 回退当作完整灾备。

先在隔离环境或 Canary 验证查询、提交、调度、GPU 访问、指标同步与失败恢复，再逐步推广。离线环境还要确认旧版本制品可取回；只有“新版本拉取成功”不能证明回退路径存在。

## 5. 掌握检查

界面显示 Pending，但底层 Pod 已运行，应查同步、对象对应和时间，不能直接再次提交重复工作负载。配额没有变化却发生回收，应进一步检查其他队列需求、当前 Fairshare 与保护条件，而不是只看一个静态配额数字。
