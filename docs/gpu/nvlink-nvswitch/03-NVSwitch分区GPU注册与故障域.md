# NVSwitch 分区、GPU 注册与故障域

NVSwitch 系统中的 GPU 能被 PCIe 发现，不代表它已经加入可用的 NVLink Fabric。反过来，Fabric 注册成功，也不代表所有卡对都达到预期性能。理解分区、注册和故障范围，才能把“八张卡都在”与“八卡训练可用”分开。

前置阅读 [FM/NVLSM 初始化](./02-Fabric-Manager-NVLSM初始化与故障分析.md)。下面区分 HGX/DGX A100、H100 和引入 NVLSM 的较新代际，具体配置必须对应机型，不能跨代复制参数。

## 1. 三种分区不应混用

| 名称 | 主要管理对象 | 不代表什么 |
| --- | --- | --- |
| MIG 实例 | 一张 GPU 内的硬件资源形状 | 多张 GPU 的 NVSwitch 连接域 |
| NVSwitch Fabric 分区 | 受支持模式中的 GPU 互联成员关系 | 任意 Kubernetes Namespace 隔离 |
| Slurm/Kubernetes 资源分组 | 调度资格与资源选择 | 硬件转发表已按租户自动隔离 |

某些共享或虚拟化模式通过 FM API 管理受支持的分区。它与裸金属整机初始化不是同一种操作。分区是否合法、支持哪些 GPU 组合及如何激活，需要对应平台支持表，见 [Fabric Manager 用户指南](https://docs.nvidia.com/datacenter/tesla/fabric-manager-user-guide/index.html)。

调度器说某任务获得四张 GPU，仅说明其分配结果；仍需确认这四张在预期互联域中、具有正确访问条件，并且应用采用了相应数据路径。

## 2. 注册把设备存在变成 Fabric 成员

在相关 NVSwitch 系统中，GPU 还需要完成 Fabric 注册。NVML 和 `nvidia-smi -q` 可以提供相应状态；应同时解释 State 与 Status，而不是只看到其中一个字段就宣布可用。

例如 `In Progress` 与 `Completed / Success` 表达不同阶段。注册一直不完成时，单卡管理查询仍可能正常，CUDA 启动却可能失败。代际行为与注册检查见上述用户指南。

```text
PCIe 枚举 → 驱动与设备管理可用 → Fabric 管理与 GPU 注册
→ 目标 GPU 对可通信 → Collective 正确 → 业务性能达标
```

每条边都需要不同证据。一个只分配显存的测试，不能覆盖跨卡通信；一次 AllReduce 通过，也不说明每种访问方向和消息规模都达到基线。

## 3. 管理进程存活与 Fabric 状态一致是两个条件

管理程序可能仍在运行，却持续等待某个设备注册；重新启动进程也可能需要配套的设备恢复才能建立一致状态。因此不要把 systemd Active 当成完整的 Fabric 健康检查。

旧配置参数还存在代际边界。比如官方说明 `ABORT_CUDA_JOBS_ON_FM_EXIT` 对 H100 及后续相应系统不生效，不能用 A100 的参数推导 H100 停服务后的行为。相同参数名称并不构成跨代兼容承诺。

这类服务与设备变更可能影响整个互联域。实际恢复要先处理运行中的 CUDA 客户端和相关服务，按机型要求执行，不能在业务还运行时通过反复重启试探。

## 4. 卡对矩阵帮助识别共同故障范围

假设八张 GPU 的无向卡对共有 `8×7/2=28` 对。若把它们分成两个四卡集合，每个集合内有 6 对，共 12 对；跨集合有 16 对。

若集合内部全部正常、跨集合全部异常，值得优先调查共同路径、分区与配置，而不是把八张 GPU 都判成计算故障。这只是教学图的归因方法，真实交换拓扑不必长成两个集合，必须对照平台拓扑。

方向也有意义。A 到 B 与 B 到 A 的读取/写入结果可能不同；将 28 对当成所有有向操作覆盖会漏掉条件。测试还要固定数据类型、消息大小、进程绑定和访问方式。

## 5. 可达性下降与带宽下降不同

某条路径失效可能导致设备无法注册、部分成员不可达，也可能在支持的恢复模式下减少可用带宽。故障模式由平台与配置决定，不能把链路数量变化统一翻译成“完全不可用”或“必然线性掉速”。

假设单卡计算时间为 60 ms，通信阶段为 40 ms；若故障只使通信时间翻倍且二者不重叠，step 从 100 ms 变成 140 ms，吞吐约下降 28.6%，不是直接下降 50%。若二者可充分重叠，结论又会改变。

因此要把链路、P2P、Collective 与业务耗时放在同一模型里。硬件带宽变化只是输入，最终影响还取决于通信占比和流水线。

## 6. 隔离单卡前先检查共享依赖

单卡错误可能发生在它自己的计算或内存，也可能来自与其他卡共享的交换路径、供电或初始化状态。排查应结合 GPU UUID、交换设备、Xid/SXid、卡对结果与首次异常时间。

当需要重置某个成员时，还要确定受影响的互联域和当前管理服务依赖。支持独立恢复的条件随代际变化，不能仅凭“一张卡报错”就承诺只影响这一张卡。

恢复验收至少应重新核对注册、成员与分区、目标卡对和代表性 Collective。新任务可启动是必要证据之一，但不能代替故障前后性能对比。

## 7. 掌握检查

区分 MIG、Fabric 分区和调度分组；解释为什么设备可查询但注册仍失败；算出 28 个卡对与 16 个跨集合卡对；推导通信翻倍后的 140 ms。最后为“特定卡对失败、单卡测试正常”列出至少三类可证伪假设。
