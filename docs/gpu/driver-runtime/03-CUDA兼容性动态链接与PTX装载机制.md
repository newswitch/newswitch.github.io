# CUDA 兼容性、动态链接与 PTX 装载机制

理解了[驱动、CUDA 与容器运行时的关系](./01-NVIDIA驱动CUDA与容器运行时的关系.md)，还不能仅凭版本字符串判断程序是否能运行。真正需要验证的是一条调用链：应用找到哪些库，这些库请求哪些驱动能力，设备代码能否在目标 GPU 上装载。

本文讨论 Linux 上的 NVIDIA CUDA。兼容规则以 NVIDIA 当前支持矩阵为准；版本数字只是筛选条件，不是完整验收。

## 1. 把四种“CUDA 版本”分开

| 看到的对象 | 实际说明 | 不能推出的结论 |
| --- | --- | --- |
| `nvidia-smi` 的 CUDA Version | 驱动所报告的 CUDA 支持级别 | 容器内已安装同版本 Toolkit |
| `nvcc --version` | 被执行的编译器版本 | 应用运行时一定加载它旁边的库 |
| `libcudart`、cuBLAS、cuDNN | 应用使用的运行库与计算库 | 所有库之间的依赖都满足 |
| fatbinary 中的 cubin、PTX | 编译产物支持的设备目标与中间表示 | 目标驱动一定能 JIT 这份 PTX |

例如，Python 环境可以携带计算库，容器注入宿主机驱动库，PATH 又指向另一套编译器。三个命令各自正常，不代表三者组成了一套一致环境。应记录“应用实际加载了什么”，而不只记录“管理员安装了什么”。

## 2. 三种兼容路径解决不同问题

较新驱动运行较旧 CUDA 应用属于向后兼容；同一 CUDA 大版本内，新小版本应用使用满足最低要求的较旧驱动，可能走小版本兼容，但新驱动特性和较新 PTX 会形成限制。不能把“小版本兼容”读成“这个大版本中的所有程序都无条件可用”。参见 [NVIDIA 小版本兼容说明](https://docs.nvidia.com/deploy/cuda-compatibility/latest/minor-version-compatibility.html)。

Forward Compatibility 则通过兼容包提供一组较新的用户态驱动库，在支持的 GPU、系统和内核驱动组合上工作。它不是升级内核模块，也不是给任意消费级显卡提供通用补丁；依赖新内核能力的功能仍可能不可用。安装兼容包以后，还必须确认进程确实找到了相应库。参见 [Forward Compatibility 支持范围与矩阵](https://docs.nvidia.com/deploy/cuda-compatibility/latest/forward-compatibility.html)。

判断顺序应是：先确认目标 GPU 和驱动仍受支持，再查应用所需功能，最后选受支持的兼容路径。不要遇到报错就全局追加一个 `compat` 目录；驱动升级后遗留的旧兼容库反而可能覆盖正确库。

## 3. 为什么同一个二进制在两个容器里结果不同

Linux 动态链接器处理无斜杠的库名时，会综合 RPATH、环境变量、RUNPATH、缓存与默认目录。RPATH 与 RUNPATH 的优先级和对子依赖的作用不同，安全执行模式还会忽略部分环境变量。因此不能简单断言“LD_LIBRARY_PATH 永远优先”。完整规则见 [ld.so 手册](https://man7.org/linux/man-pages/man8/ld.so.8.html)。

一个常见装载错误是把 Toolkit 的 `stubs` 目录放进运行时搜索路径。stub 用于构建时解析符号，不是可工作的 GPU 驱动实现。另一个错误是镜像打包了不合适的驱动库，遮蔽了运行时注入的宿主机库。

只读排查可以从下面开始，命令中的路径应替换为自己的可信程序：

```bash
readelf -d ./my_cuda_app
printf '%s\n' "$LD_LIBRARY_PATH"
# 在应用仍存活时查看真正映射的库；PID 换成实际进程号
rg 'libcuda|libcudart|libcublas|libcudnn' /proc/PID/maps
```

`readelf` 展示声明的依赖，`maps` 展示已经映射的文件。对使用 `dlopen` 延迟加载的程序，应在触发相关算子后再检查。不要对未知来源的可执行文件随意运行诊断命令来“看看它加载什么”。

## 4. SASS 与 PTX：可装载比“编译成功”多一层

可以把设备代码分成已经面向 GPU 指令集生成的机器码，以及仍需驱动编译的 PTX。fatbinary 可以同时携带多种目标；能否直接使用某份 cubin，要看其目标与当前 GPU 的兼容关系。没有合适机器码时，运行时可能尝试 PTX JIT。

这带来两个独立问题：目标 GPU 是否有可用代码，以及驱动是否理解该 PTX 版本。升级容器中的编译器并不会自动升级宿主机的 PTX JIT 能力。只测到张量分配成功，也可能尚未触发真正失败的 kernel。

下面是教学推演，不是某一框架的实测结果：

1. 应用初始化成功，说明基础驱动调用至少有一部分可用。
2. 普通算子使用已携带的目标机器码，因此成功。
3. 扩展算子只携带较新 PTX，第一次调用时才 JIT，随后失败。

所以“前面跑了几分钟”不能排除兼容问题。验收需要覆盖实际算子、目标 GPU、扩展模块和 JIT 路径，而不是只运行 `nvidia-smi`。

## 5. 用最小证据定位故障层

| 现象 | 首先补充的证据 | 不宜直接采取的动作 |
| --- | --- | --- |
| 找不到共享库或符号 | NEEDED、搜索路径、实际库文件及其版本 | 立刻重装内核驱动 |
| 管理查询正常，CUDA 初始化失败 | 设备节点、进程加载的 libcuda、容器注入结果 | 认定硬件正常所以一定是应用错误 |
| 只有某种 GPU 失败 | 设备代码目标、计算能力、扩展构建选项 | 只比较 CUDA 大版本 |
| 首次特定算子失败 | PTX、JIT 日志及驱动功能支持 | 只扩大显存限额 |

复现环境至少应关联 GPU 型号、内核驱动、镜像 digest、框架与扩展构建信息、实际加载的库路径。同名镜像标签和同名虚拟环境都不足以固定环境身份。

## 6. 掌握检查

能解释以下三个反例，才算理解装载边界：为什么没有 `nvcc` 的运行镜像仍能训练；为什么 `nvidia-smi` 正常而某个 CUDA 算子失败；为什么升级宿主机驱动后还要检查遗留的兼容库搜索路径。

进一步学习时，尝试画出一个真实应用从 Python 扩展到 `libcuda` 再到内核驱动的依赖链，并标明每个文件来自镜像、虚拟环境还是宿主机。这里的重点是验证依赖关系，不是把所有组件升级成同一个版本号。
