# GPU NPU 裸金属容器与虚拟机边界

“裸金属容器”一般指直接在物理服务器操作系统上运行容器，而不是先创建虚拟机再在其中运行容器。它不是一种新显卡，也不自动提供独占算力、独立内核或所有设备故障隔离能力。

理解部署形态，应分别问：操作系统内核由谁提供，设备由谁管理，任务获得哪部分资源，哪些故障会影响相邻任务。本文聚焦 Linux 以及 NVIDIA、华为昇腾的常见概念，不把某一种虚拟化能力写成全部设备都支持的功能。

## 1. 三个维度不要混成一个选择题

| 维度 | 可能取值 | 回答的问题 |
| --- | --- | --- |
| 计算节点 | 物理机、虚拟机 | 程序的操作系统运行在哪里 |
| 进程交付 | 直接运行、容器运行 | 用户态依赖与进程环境怎样组织 |
| 设备分配 | 整设备、受支持切分、共享策略 | 任务实际得到什么设备能力 |

因此，“容器还是 MIG”不是同一维度的二选一：受支持的 MIG 实例可以交给容器；整卡直通后的虚拟机也可以再运行容器。昇腾的 vNPU、软切分等方案同样需要分别核对硬件、软件和调度支持，不能仅凭名字推断隔离强度。

## 2. 不同形态的内核与驱动在哪里

| 形态 | 程序看到的用户态 | 内核与设备边界 |
| --- | --- | --- |
| 物理机直接运行 | Host 包或虚拟环境 | 直接使用 Host 内核与驱动 |
| 物理机上运行容器 | 镜像、挂载与运行时注入 | 仍共享 Host 内核，访问分配到的设备 |
| 虚拟机 | Guest 的用户态 | Guest 内核与相应虚拟化/直通方案 |
| 虚拟机里运行容器 | 容器用户态 | 共享 Guest 内核，再经过设备方案的边界 |

容器隔离文件系统视图、进程和其他命名空间，并可结合 cgroup 与安全策略；它不会仅因使用了镜像就复制出另一个内核。虚拟机有 Guest 内核，但设备是否独占、是否可热迁移及怎样恢复，仍由所用直通或虚拟化方案决定。

更完整的内核/设备原理见 [内核模块与驱动绑定](../../linux/system-internals/09-devices-drivers/04-内核模块符号依赖与驱动绑定.md)。

## 3. 设备可见、独占、限额与隔离是四件事

可见性控制程序能枚举和打开哪些设备；独占描述分配策略是否允许其他任务同时获得相同资源；限额约束可使用量；隔离则要进一步区分安全、性能、内存、故障和管理影响。

| 机制示例 | 通常解决什么 | 不能自动保证什么 |
| --- | --- | --- |
| 设备节点与容器注入 | 访问入口和设备视图 | 单独的显存容量或算力配额 |
| 调度整卡资源 | 平台分配粒度与占用管理 | 用户绕过平台后仍有同样约束 |
| 软件时间共享 | 多任务复用设备机会 | 每任务固定显存、固定带宽和完整故障隔离 |
| 受支持硬件切分 | 对应实例的资源边界 | 所有机型、所有资源和所有故障均等价隔离 |
| 整设备直通 | 将设备交给相应 Guest 使用 | 任意迁移、任意重置或无代价跨机共享 |

NVIDIA MIG 在支持设备上提供特定的计算与内存系统分区能力，但不是全部 NVIDIA 显卡的通用开关。昇腾也有不同虚拟化方案；产品名带“虚拟”并不能替代具体支持矩阵。参见 [MIG 原理与支持范围](https://docs.nvidia.com/datacenter/tesla/mig-user-guide/introduction.html)。

## 4. 四种内存预算必须单独看

### 4.1 Host RAM

操作系统、服务线程、Tokenizer、模型加载、Page Cache 和部分通信工作使用 Host 内存。CPU Memory cgroup 的约束主要面向这类受其记账的系统内存，不能直接解释为 HBM 限额。

### 4.2 GPU 或 NPU 设备内存

设备上驻留权重、KV、激活和工作区。框架的内存预算参数主要控制该框架的规划行为，不是防止所有进程使用设备的通用硬隔离。容器设置 `--memory=8g`，不会因此把显卡容量限定为 8 GB。

### 4.3 /dev/shm 共享内存

共享内存用于进程间交换数据；容器中 `/dev/shm` 常采用 tmpfs。它使用系统内存资源，不是第三块独立物理内存，更不是显存。

`--shm-size` 设置该共享文件系统的容量上限，通常不是启动时立即预留全部物理页；实际使用仍受 Host 和内存记账约束。增大它可能解决进程间共享空间不足，但不能解决 NPU HBM OOM，也不能代替 CPU Memory 预算。

### 4.4 磁盘与缓存

镜像层、临时文件、下载权重和编译缓存占用存储；Page Cache 又可能占用内存。应区分存储空间、缓存页与设备分配，而不是看到“缓存”就统一归因于显存。

## 5. 怎样读容器内存与共享内存配置

只读查询已有 Docker 容器，示例名称按实际替换：

```bash
docker inspect --format 'Memory={{.HostConfig.Memory}} ShmSize={{.HostConfig.ShmSize}}' model-server
```

教学示例输出：

```text
Memory=8589934592 ShmSize=1073741824
```

这些字段按字节表示：示例设置为 8 GiB 容器内存上限与 1 GiB `/dev/shm` 上限。不能将它们相加，宣称容器必然额外拥有 9 GiB 独立物理内存；也不能把 `ShmSize` 当作 GPU 显存。

已有容器中还可查看当前挂载和用量：

```bash
df -h /dev/shm
findmnt /dev/shm
```

`df` 显示文件系统视图，不直接等于进程可分配的全部物理内存。共享页被多个进程映射时，也不能简单累加每个进程 RSS 来认定实际物理消耗。

Kubernetes 常通过挂载内存型 `emptyDir` 提供 Pod 共享空间；其实际使用会参与内存约束，不是无成本的额外 RAM。`--ipc=host` 则改变隔离范围，不是扩大共享内存的通用替代方案。底层语义见 [Page Cache、mmap 与共享内存](../../linux/system-internals/04-memory-management/04-Page-Cache-mmap与共享内存.md)。

## 6. 为什么相同镜像在不同形态里表现不同

镜像固定用户态文件，但不固定宿主或 Guest 的内核、设备分配、驱动、NUMA、PCIe/RDMA、挂载和安全策略。故障可能来自不同层，而不是“容器天然损失一半性能”。

例如，多卡通信可能需要访问相应互联与网卡；虚拟机的拓扑呈现、P2P 支持和直通方式也要验证。单卡矩阵运算成功，不足以证明跨设备通信与存储路径保持相同能力。

性能比较至少要固定模型、精度、并行方式、CPU/内存策略、设备资源和版本，再分别测量 Host 准备、设备执行、通信和服务指标。没有固定这些条件，不应把全部差异归因于“是不是裸金属”。

## 7. 故障影响范围怎样判断

进程退出、容器被终止、设备上下文异常、整设备故障、驱动失效与节点宕机，不是一个级别。容器重建只重建其进程环境，不保证修复底层硬件，也不能默认安全地重置共享设备。

如果设备由多个任务共享，复位、切分重配、驱动维护和互联配置变化都可能影响其他任务。排障先保存“节点—物理设备—切分实例—容器—进程—Rank”映射，再界定维护范围。

遇到权限错误，应查设备访问、挂载、seccomp 或其他安全策略，不将关闭隔离作为默认修复。裸金属上的 privileged 容器仍是共享 Host 内核，风险不会因为没有虚拟机而消失。

## 8. 练习与答案

**问题一：裸金属容器是否拥有独立于 Host 的内核？**

答案：通常没有。它直接运行在物理机操作系统上，共享 Host 内核；镜像主要交付用户态文件与依赖，不能等同于虚拟机。

**问题二：容器内存限额 8 GiB，是否也限制 GPU 只能使用 8 GiB 显存？**

答案：不是。Host 系统内存和设备内存具有不同分配与限额机制，应分别验证 cgroup、设备分配和框架预算。

**问题三：将 /dev/shm 上限设为 1 GiB，是否启动时就额外分配 1 GiB 显存？**

答案：不是。它设置共享文件系统容量，按实际使用消耗系统内存资源，并受相关记账约束；既不是额外显存，也通常不是立即预留全部 RAM。

**问题四：删除故障容器，是否能保证其他共享同一设备的任务不受影响？**

答案：不能。要区分容器级退出和底层设备/驱动故障；故障与维护动作可能超出容器边界，应基于资源映射界定影响范围。
