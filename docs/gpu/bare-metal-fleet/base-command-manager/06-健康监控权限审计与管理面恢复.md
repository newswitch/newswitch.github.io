# 健康监控权限审计与管理面恢复

集群管理能一次影响大量节点，因此管理面的可用性和权限错误都可能放大为业务故障。观察、决策与执行应分别留下证据，而不是把“发现告警”直接连接到“批量重装”。

## 1. 三种健康

管理可达性回答能否访问节点；系统健康回答服务、硬件和配置是否满足基线；工作负载健康回答目标任务是否正确并达到性能要求。这三种健康可能不一致。

教学例子：管理 Agent 正常，但训练网 HCA 不通，SSH 和主机指标都可能绿色。相反，管理链断开时已有本地计算可能仍继续。监控需要保留最后成功时间、采集路径与数据新鲜度，不能把旧绿色当成当前健康。

## 2. 隔离决策需要范围

将故障关联到节点、GPU UUID、PCI BDF、NIC GUID、机架和作业。单卡应用错误、整节点掉线与同一交换域多节点退化具有不同影响范围。执行设备重置、节点重启或重新供应前，先停止新分配并确认运行任务及本地数据。

隔离后应保存管理日志、内核事件、DCGM/NVSM 结果、供应版本和调度状态。修复后的资格验证见[节点恢复与 RMA](../07-GPU节点自动隔离修复重新入池与RMA判定.md)，不能用清空告警代替复验。

## 3. 账户与管理接口

将只读观察、镜像编辑、供应、批量电源和账户管理划分为不同授权能力。BCM 管理员权限、节点 Root、BMC 凭据和 Slurm/K8s 用户权限应分开评估，不因使用同一身份提供方就认为权限自动一致。

自动化使用可审计的服务身份，保留操作者、对象集合、变更前后值、任务结果和关联工单。界面显示一个 Category 时，批量操作可能影响其中全部节点，因此执行前还需要冻结并复核目标集合，防止成员变化扩大范围。

产品层面继续区分管理证书与 Profile、节点功能 Role 和 Linux 用户。Profile 限定管理操作资格，不替代批量目标核对；Network 与设备接口配置也不自动完成交换机及防火墙配置，详见[网络对象、证书与授权](./11-网络对象证书Profile与权限边界.md)。健康结果需要结合实际设备状态、采集新鲜度和调度准入，见[设备状态与健康检查](./10-设备状态任务结果与健康检查.md)。

## 4. 备份需要覆盖什么

恢复点不仅包括软件镜像，还包括管理配置、对象绑定、分类与角色、网络服务配置、证书密钥，以及外部数据库和存储的恢复约束。备份应离开单一故障域，凭据材料单独保护，并验证能在恢复环境解密使用。

镜像备份解决文件内容问题，不保存正在运行的 Slurm Allocation、GPU 显存或外部 Checkpoint 最新状态。管理面恢复后，应先核对物理事实与调度器账本，再开放自动化批处理。

## 5. 恢复演练题

管理服务恢复到昨天的快照，但今天新增了两台节点、升级了一个分类。若立即按旧快照全量协调，可能把新节点误当成未知对象，也可能回写旧配置。正确步骤是确认恢复点差异、冻结破坏性批量动作、重建身份和版本映射，再逐类恢复协调。

管理 UI 恢复只是第一项证据；还要验证只读查询、受控变更、节点报告、调度注册和最小业务。演练使用独立测试节点或恢复环境，不在真实业务上通过断网与删除状态来“验证”。

继续阅读[主备切换、故障隔离与恢复一致性](./07-BCM主备切换故障隔离与恢复一致性.md)，把 Active/Passive 角色、共享入口、状态副本与旧快照协调分别放入时间线。HA 保护服务连续性，备份保护历史恢复点，二者不能互相替代。
