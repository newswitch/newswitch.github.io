# 节点安装模式排除规则与供应重试

同样一次“重启节点”，可能只同步差异，也可能重新分区。决定结果的不只是镜像名字，还包括节点安装器的有效模式、磁盘检查、排除规则和供应源状态。本篇以 [BCM 11 管理手册](https://docs.nvidia.com/base-command-manager/manuals/11/admin-manual.pdf)第 5.3、5.4、5.6 节为产品基线，不把普通 rsync 的经验直接当成 BCM 的完整行为。

## 1. 五种模式只管节点安装器阶段

| Install mode | 节点安装器阶段的行为 | 容易误解的边界 |
| --- | --- | --- |
| `AUTO` | 检查分区和文件系统；正常时增量同步，不匹配或损坏时进入全量安装 | 自动不等于无损，受管理范围内多余本地文件也可能被删除 |
| `FULL` | 按布局重新分区、建立文件系统，再供应完整镜像 | 不是“多复制一些文件”，可能清除原盘内容 |
| `MAIN` | 进入维护环境，供人工调查，不继续常规磁盘检查与安装 | 不是已经运行目标根文件系统的正常业务模式 |
| `NOSYNC` | 检查正常时不做镜像同步；检查失败仍可能进入全量安装 | 不能作为数据保留保证 |
| `SKIP` | 跳过分区/文件系统检查与镜像同步 | 不修复坏文件，也不证明已有系统可用 |

`installmode` 控制的是启动时的 node-installer，不是运行中 `imageupdate` 的开关。即使设为 `NOSYNC`，后来主动提交的运行中镜像更新仍可同步文件。这两个阶段必须分别审查。

推演：节点根盘健康，分类采用 `AUTO`，镜像里删除了一个受管理路径下的旧脚本。重启后的同步可以删除节点上该脚本，而不只是添加新文件。反过来，若分区布局不匹配，问题已不再是“同步是否删除脚本”，而是是否允许重新创建文件系统。

## 2. 先确定本次真正生效的模式

BCM 11 的决策涉及新节点模式、启动菜单、下一次启动覆盖、节点属性和分类属性；安装器控制台还提供最后的干预机会。新节点的 `newnodeinstallmode` 默认是 `FULL`，普通分类的 `installmode` 默认是 `AUTO`，不能只读取分类默认值就推断新节点安全。

`nextinstallmode` 是一次性覆盖，手册说明其在安装器完成任务后清除。因此“上次设置过一次”不是以后每次启动的长期保证。模式选择与磁盘检查结论应从头节点 `/var/log/node-installer` 中核对，再与节点身份和配置关联。

以下是只读观察示意，`node001` 必须替换为已经核对资产的目标：

```bash
cmsh -c "device use node001; get installmode"
cmsh -c "device use node001; get nextinstallmode"
cmsh -c "device use node001; get datanode"
cmsh -c "softwareimage provisioningstatus"
```

不要把 `get` 显示的一个属性、当前启动菜单选择和最终安装日志当成同一份事实。详细优先顺序及交互条件以目标 BCM 版本手册为准。

## 3. 排除列表按阶段和方向分开

| 操作 | 数据方向 | 对应列表 |
| --- | --- | --- |
| 启动时全量供应 | 镜像 → 启动中的节点 | `excludelistfullinstall` |
| 启动时增量供应 | 镜像 → 启动中的节点 | `excludelistsyncinstall` |
| `imageupdate` | 镜像 → 运行中的节点 | `excludelistupdate` |
| 抓取回已有镜像 | 运行节点 → 镜像 | `excludelistgrab` |
| 抓取为新镜像 | 运行节点 → 新镜像 | `excludelistgrabnew` |

把凭据加入 update 列表，不会自动保证 grab 时不把它带回镜像；只配置 sync 列表，也不等于运行中更新会保留该目录。先决定“这份状态由谁拥有、向哪个方向流动”，再配置相应规则。

节点级非空列表可以覆盖对应分类列表，角色和 Overlay 还可能引入隐含规则。故障排查应看有效列表，不只看分类编辑框。BCM 11 可在设备上下文观察：

```text
device use node001
excludelist list
excludelist get sync /
excludelist get update /
excludelist get full /
```

路径和可用性受节点的镜像配置影响。`full` 在这里是查看该模式的有效过滤规则，不是执行全量安装。

## 4. “已存在时保留”不等于“永不下发”

BCM 的 sync/update 排除规则包含普通子列表与 `no-new-files:` 子列表。对一个匹配的目标文件，已有内容可以保留；但目标尚不存在时，只有普通排除规则不一定阻止镜像中的文件被创建。`no-new-files:` 用于表达连新增也不下发的意图。具体模式仍采用手册规定的 rsync 过滤语法，不能当成任意路径字符串。

教学例子：镜像中有 `/etc/example/token`，希望每个节点独立生成，不能从镜像复制：

| 节点现状 | 只有普通排除匹配 | 同时有对应 no-new-files 规则 |
| --- | --- | --- |
| 已有自己的 token | 保留现有文件 | 保留现有文件 |
| 尚无 token | 镜像副本仍可能被复制 | 不从镜像新增该文件 |

这张表限定于上述 sync/update 语义，不是全量安装的数据恢复承诺。对目录还需验证目录本身、子项、递归匹配与规则顺序；不要把一个未经 dry-run 验证的通配符复制到全部分类。

## 5. 文件排除救不了重新分区

设系统盘旁还有数据盘，设备枚举变化后，原来的数据盘恰好占用了布局中的目标名称。`AUTO` 或 `NOSYNC` 检查到布局异常，可能走向 `FULL`。即使某个目录出现在排除列表里，已经被重新建立的文件系统也不会因为“排除复制”恢复原有数据。

BCM 11 的 `datanode` 属性可以要求 FULL 安装前显式确认，应与稳定磁盘身份、布局断言、备份和人工授权一起设计。它是特定流程的确认门，不是所有写盘动作的防护罩；手册另有显式清盘功能，其行为可能绕过该确认，不能互相代替。

另一种风险是同步时碰到动态挂载的数据目录。不要默认任何手工挂载或 autofs 目录都会被自动识别和保护；应按实际挂载方式核对排除范围及生效规则。运行中数据写入、快照一致性、备份恢复也不是 exclude list 能解决的问题。

## 6. 重试需要固定输入，不只是重复命令

BCM 的供应链可以包含头节点镜像和多个 provisioner 副本。头节点修改已保存，不代表本次被选中的供应源已经取得同一份内容。手册给出 `updateprovisioners`、供应状态及同步日志等入口；不要把默认自动更新时间窗口当成强一致提交。

```text
目标资产与盘身份
  + 有效模式/布局/排除规则
  + 镜像修订和供应源副本
  + 请求编号与阶段结果
  → 才构成一次可解释的供应尝试
```

运行中 `imageupdate` 默认是 dry-run，须读取 `synclog` 才能理解计划；`-w` 才实际写入。不带 `-w` 的演练也应限定到目标节点，不随意在整个分类上重复创建请求。

安全重试的教学顺序是：保存原请求和最早错误，确认是否仍有任务执行，区分传输中断、源副本滞后和模式/布局错误，再固定输入进行新尝试。传输可重试不代表脚本、格式化或外部注册自动幂等；initialize/finalize 中的自定义动作必须另行审查。

反例：第一次复制失败后，管理员修改镜像又立即重试，另一个 provisioner 提供了旧副本。第二次“成功”只能证明该次任务结束，不能证明期望修订已落地。应对比目标文件和供应源记录，再验证运行状态。

## 7. 与内核发布的连接

供应完成只是文件事实。内核注册、initramfs 生成、早期驱动、节点引导、服务重启以及调度资格仍有独立边界，继续阅读[镜像发布与内核更新](./04-镜像发布内核更新灰度与回退.md)。不要用重新分区修复一个本可定位到 initramfs 模块的启动错误。

## 8. 掌握检查

**NOSYNC 加排除列表，能保证数据盘不丢吗？** 不能。先审查盘身份、布局检查与 FULL 分支，再讨论文件同步规则。

**只改分类排除规则，为什么节点仍被覆盖？** 检查本次操作类型、节点覆盖、角色/Overlay 和有效列表；另核对目标是否经历了重新分区。

**dry-run 没有删除文件，是否可以无条件执行？** 不可以。输入、挂载和源副本可能在两次操作间变化，且 dry-run 不能替代服务停机及数据一致性设计。
