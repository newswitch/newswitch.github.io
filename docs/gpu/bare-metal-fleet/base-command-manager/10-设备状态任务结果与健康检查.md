# 设备状态任务结果与健康检查

BCM 的设备状态不是一条从“新机器”走向“生产可用”的单向进度条。它同时表达设备观测和管理意图，还需要与任务、健康、配置生效和调度状态组合阅读。先读[四种事实](./01-BCM架构控制面与状态模型.md)，本篇把抽象模型落实到真实产品字段。

## 1. UP DOWN 与 CLOSED 的产品含义

NVIDIA 的 DGX SuperPOD 管理指南列出了以下关键设备状态。它们是产品状态；后文用于教学的验收谓词不是产品枚举。

| 显示状态 | 设备观测 | 管理含义 |
| --- | --- | --- |
| `[ UP ]` | 设备处于 UP | 正常受监控 |
| `[ DOWN ]` | 设备处于 DOWN | 仍在预期管理范围，通常需要调查 |
| `[ CLOSED ] (UP)` | 设备仍为 UP | 管理员将其关闭到主要忽略的管理状态 |
| `[ CLOSED ] (DOWN)` | 设备为 DOWN | 通常表达有意不可用，而不是意外离线 |

这里的 CLOSED 不等于电源关闭，UP 也不等于每个 GPU 与服务都健康。产品说明使用的是 “mostly ignored”，不能扩大解释为没有任何采集或控制行为。参见[设备状态定义](https://docs.nvidia.com/dgx-superpod/administration-guide-dgx-superpod/latest/cluster-management.html)。

尤其不能把 CLOSED 解释成 Slurm Drain 或 Kubernetes Cordon 的通用替代品。是否存在站点集成钩子、钩子是否执行成功、调度器实际状态如何，必须另行确认。

## 2. 一个节点至少有五个状态维度

```text
管理意图：是否有意退出正常管理
设备观测：是否收到符合条件的节点响应
配置生效：目标配置、文件、内核与进程是否一致
健康证据：检查了什么、何时检查、结果怎样
调度资格：是否允许新分配、是否仍有任务
```

例如“CLOSED 且 UP，但 Slurm 仍允许分配”在没有联动配置的环境中并不矛盾；只是管理员少完成了一项隔离动作。另一个反例是“UP，但需要重启”：节点可达与版本变更尚未生效可以同时成立。

不要把这五个维度压成同一个布尔字段。自动化若只判断 UP 就放回资源池，会跳过维修、资格验证和管理员维护意图。

## 3. 重启提示不是自动重启授权

BCM 11 安装手册的工作负载管理示例中，`ds` 可以同时报告 `[ UP ]` 和 `restart required`。含义是该节点有需要通过重启生效的变更，不是已经重启，也不是当前运行任务已经安全退出。

```bash
cmsh -c "ds"
cmsh -c "device;list"
cmsh -c "task list"
```

这些是管理环境中的只读入口。观察时记录节点身份、提示原因与时间。重启前另行确认调度隔离、任务结束、持久数据和维护窗口；不要把状态查询脚本扩展成“看到提示立即重启”。[重启提示示例见安装手册第 1.4 节](https://docs.nvidia.com/base-command-manager/manuals/11/installation-manual.pdf)。

## 4. 任务成功有明确终点

某个任务的结果只应覆盖该操作承诺的终点。克隆镜像结束、供应文件结束、执行节点命令结束，与运行内核、驱动初始化和业务结果不同。应记录操作类型、目标集合、输入版本、开始结束时间以及逐目标结果。

教学反例：镜像更新任务成功，随后节点仍用旧内核。若任务只负责文件更新，这不是逻辑矛盾；还需检查引导选择和生效动作。相反，任务超时后节点也可能已经完成部分写入，不能按“失败等于完全没执行”无条件重试。

批量结果尤其不能只看最后一行。假设 32 台节点中 31 台完成、1 台超时，后续应依据逐目标证据决定是否重试该台，而不是把全部节点再执行一遍可能非幂等的操作。

## 5. 健康检查必须携带观察上下文

健康结果至少需要关联对象、检查项、执行时间、采集来源、版本和有效期。指标样本、健康检查和管理告警有不同时间语义，不能只因为都显示绿色就认为具有相同覆盖范围。

教学时间线：最后一份成功健康结果产生于 10:00，10:03 管理采集失联，10:10 设备重新可达。10:00 的结果不能证明 10:10 当前健康；10:03 失联也不能单独证明 GPU 已损坏。恢复采集后，应检查身份、运行基线、事件连续性及所需复验。

若教学策略要求健康结果最多陈旧 5 分钟，那么 10:10 使用 10:00 的结果，陈旧时间 10 分钟，已不满足该策略。5 分钟是例题假设，不是 BCM 内建通用阈值。节点更换 GPU 后，即使时间未过期，旧 UUID 的检查也不能授予新卡资格。

## 6. 用不变量定义重新入池

一个用于设计验收的教学谓词是：

```text
允许接收新任务 = 身份一致
                且目标版本已生效
                且所需健康检查新鲜有效
                且数据路径资格通过
                且管理员允许
                且调度器已经执行对应准入动作
```

它不是 BCM 内部状态计算公式。作用是揭示仅凭 UP、任务成功或告警消失，无法推出完整结论。修复闭环见[隔离、修复与 RMA](../07-GPU节点自动隔离修复重新入池与RMA判定.md)。

恢复操作还要防止竞态：检查结束之后、解除隔离之前，资产或配置可能又变了。应绑定同一设备身份与配置版本，必要时在真正放行前重新确认关键条件，而不是让几小时前的验收一直有效。

## 7. 掌握检查

**CLOSED 能否证明机器已关机？** 不能，它可以与 UP 同时出现。

**任务成功但版本没生效，是管理系统一定出错吗？** 先核对任务终点、目标和生效条件，不用含糊的“成功”推断全部下游结果。

**设备 UP 且健康全绿，仍可能禁止调度吗？** 可以。维护意图、目标版本、资格检查和调度器状态都是独立约束。
