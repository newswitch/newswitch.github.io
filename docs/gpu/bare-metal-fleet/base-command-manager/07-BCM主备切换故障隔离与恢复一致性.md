# BCM 主备切换、故障隔离与恢复一致性

BCM 高可用保护的是集群管理服务的连续性，不是把全部计算节点复制一遍。理解切换需要同时看四件事：谁正在提供服务，谁有权修改状态，状态存在哪里，以及下游节点是否已经接受了变化。

前置阅读[管理面恢复](./06-健康监控权限审计与管理面恢复.md)。下面以 BCM 11 相关文档和 NVIDIA Enterprise RA 的双 Head Node 方案为背景；共享存储、网络和切换方式仍要对应实际安装方案。

## 1. Primary、Secondary 与 Active 不是同一维度

Primary/Secondary 标识配置中的两台 Head Node；Active/Passive 表示当前服务角色。切换后，Secondary 可以成为 Active，不能因为它仍叫 Secondary 就判断流量应回到 Primary。

NVIDIA 的参考架构配置共享服务 IP、独立 failover 网络，并可通过外部 NFS 保持 `/home` 与 `/cm/shared` 的访问。共享 IP 接管的是入口身份，不是把所有底层状态自动复制过去。参见 [BCM HA 部署关系](https://docs.nvidia.com/enterprise-reference-architectures/base-command-manager-enterprise-ra-deployment-guide/latest/configure-ha.html)。

```text
管理客户端 → 共享服务入口 → 当前 Active Head Node
                           ├─ 管理配置与数据库
                           ├─ 共享目录与外部存储
                           └─ 节点供应、身份与调度集成
另一台 Head Node → 状态同步与接管准备
```

这张图表达依赖关系。服务入口切过去之后，数据库、文件、凭据或外部存储若没有满足条件，仍可能出现“能登录但不能完成管理操作”。

## 2. 心跳超时只能证明观察失败

设 A 为 Active，B 为 Passive。B 收不到 A 的响应，可能是 A 宕机，也可能只是两者之间的链路断开。第二种情况下，A 仍可能服务计算节点；如果 B 立刻开始修改相同资源，就可能产生双主写入。

因此安全接管需要区分故障检测、接管授权和旧写入者隔离。专用心跳网络提供额外观测，不能从逻辑上把“没有响应”变成“已经断电”。BCM 的具体判定、隔离和人工确认选项，应按 [BCM 11 管理手册的 High Availability 章节](https://docs.nvidia.com/base-command-manager/manuals/11/admin-manual.pdf)配置，不把通用教学时间线当成产品状态枚举。

对学习者更重要的反例是：把超时调得更短，可能缩短真实宕机的发现时间，也可能增加瞬时网络抖动造成的误判。切换速度与错误接管风险不能只优化其中一个。

## 3. 多副本与共享依赖形成不同故障域

两台 Head Node 若使用同一个不可用的 NFS、同一供电支路或同一管理交换机，数量上的冗余不一定形成故障隔离。参考架构中的共享目录只是依赖设计，外部 NFS 的高可用需要另外完成。

恢复设计应逐项识别：入口地址如何移动，数据库状态如何同步，共享目录如何访问，镜像是否已到达供应节点，以及身份与证书是否仍有效。不能把“备用系统能启动”当成这些条件全部成立。

例如备用 Head Node 接管正常，但它无法访问共享的软件路径，新作业可能启动失败；已有进程却可能继续执行。这种局部恢复并不矛盾，说明受影响的是不同依赖。

## 4. 切换不是从备份还原

HA 切换使用仍可用的服务与状态副本；备份恢复则把系统带回过去的恢复点。前者不能防止错误配置同步到两台节点，后者也不能承诺不丢失恢复点之后的管理变化。

教学条件：配置每 15 分钟备份一次，10:00 快照完成，10:07 发布新镜像绑定，10:12 管理状态损坏。仅恢复 10:00 时，最近 12 分钟的变化需要另行核对，10:07 的发布不会因为镜像文件仍在就自动回到配置数据库中。

还要区分恢复管理状态与恢复训练状态。Head Node 备份不包含 GPU 显存、所有运行中分配以及最新 Checkpoint；它们分别属于工作负载与调度器的恢复边界。

## 5. RTO 要按依赖链计算

假设故障发现耗时 10 秒，隔离与接管确认 20 秒，服务启动和入口恢复 30 秒，下游重新协调 40 秒。若这些步骤串行，管理能力恢复约需 100 秒，不是其中最快的 10 秒。

该例没有包含镜像重新分发和业务恢复。实际过程有些步骤可重叠，有些必须等待安全前提，因此应以时间线测量关键路径，而不是把几个最好结果相加或只报告共享 IP 的恢复时间。

## 6. 恢复后先核对，再恢复批量协调

从旧快照恢复时，物理节点可能已经换过硬件、升级过镜像或加入过新分类。旧期望如果直接全量下发，可能覆盖本来正确的当前配置。

先确认当前活动管理者和各类状态的权威来源，再对照资产身份、分类绑定、运行内核、供应镜像和调度注册。把破坏性自动动作保持在受控范围，先用少量目标验证协调方向正确，再扩大范围。

这里的“少量”不只是节点数量少，还应覆盖不同角色：登录节点、供应节点与计算节点的恢复条件不同。WebUI 正常仅证明入口的一部分，不能代替供应和任务验证。

## 7. 掌握检查

解释 Secondary 为什么可以是 Active；列出心跳丢失但旧主仍存活的场景；区分共享 IP、共享目录和状态副本；算出 100 秒恢复例子，并说明它为什么不包含训练恢复时间。最后回答：误配置已经同步到两台 Head Node 时，为什么主备切换可能没有帮助。
