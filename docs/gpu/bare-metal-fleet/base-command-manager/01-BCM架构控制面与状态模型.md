# BCM 架构控制面与状态模型

一台服务器能通过 SSH 登录，并不意味着它已经成为可交付的 GPU 计算节点。集群管理需要把机器身份、操作系统内容、网络配置、运行服务和验收结果关联起来。BCM 的价值在于维护这些关联，而不是把散落命令包装成界面。

## 1. 四种事实

| 事实 | 例子 | 不能推导什么 |
| --- | --- | --- |
| 管理配置 | 节点属于某 Category，分配了某软件镜像 | 文件已全部同步 |
| 镜像内容 | 镜像目录中安装了驱动与服务 | 节点运行的新内核已加载该驱动 |
| 执行任务 | 克隆或供应任务结束 | 真实训练已经正确运行 |
| 节点观测 | 版本、设备、服务、健康结果 | 全集群都具有相同状态 |

配置、内容、操作和观测应有不同的标识和时间戳。把它们缩成一个“已完成”按钮，就无法解释为什么同一分类中两台节点实际版本不同。

## 2. 控制链路与数据链路

```text
管理员通过 cmsh 或管理界面表达配置
→ 管理服务保存对象关系并发起相应操作
→ 供应路径准备引导和系统文件
→ 节点启动服务并报告状态
→ Slurm 或 Kubernetes 注册资源
```

图是职责划分，不是内部线程调用栈。训练期间的 Tensor 通常通过 GPU、NIC 和存储数据面移动，不需要每一字节都绕回 BCM 管理服务。管理面不可用与数据面中断可能有关联，但不是同一故障。

## 3. 从错误现象回溯

教学场景：同一 Category 的 10 台节点，9 台完成版本切换，1 台仍报告旧内核。先检查这台机器的对象覆盖、镜像绑定、供应任务和最近启动记录；不要立即在 10 台节点上重复升级。

若目标文件已在节点上但内核版本仍旧，问题可能在引导选项或缺少计划重启；若新内核已运行但驱动未加载，继续查模块、签名、依赖和固件。通过层层否定假设，才能缩小操作影响范围。

## 4. 管理端不可用时的判断

已有应用能否继续运行，取决于它是否仍依赖共享服务、认证、网络及存储，不取决于管理 UI 是否可访问。反过来，管理 UI 可访问，也不证明节点能从镜像源启动。

恢复管理服务之前，应先确认配置与状态存储的恢复点、凭据和证书、网络服务与主备关系。不能启动一个空白管理实例后把所有节点重新识别为“可安全重装”。物理节点仍可能持有运行中作业和本地数据。

## 5. 只读观察与管理操作

`cmsh` 是有上下文的管理 Shell，不是普通 Bash。先用帮助了解当前对象与可查询字段，再区分查看、修改未提交值、提交配置和启动异步操作。下面是只读入口，需在已安装 BCM 的管理环境使用：

```bash
cmsh -c "softwareimage;list"
cmsh -c "task list"
```

输出中的任务成功、配置引用正确和节点实际一致，应作为三个独立检查结果保留。把查询脚本误写成带修改或批量电源操作的命令，可能跨越整个节点集合的安全边界。

进一步对应[真实设备状态](./10-设备状态任务结果与健康检查.md)：`[ UP ]`、`[ DOWN ]` 和 `[ CLOSED ]` 不是供应阶段编号。CLOSED 可以和实际 UP 同时存在，反映管理意图与设备观测的分离；它也不能自动替代 Slurm Drain 或 Kubernetes Cordon。

## 6. 掌握检查

节点可登录但不能训练，需要重装吗？不能直接得出结论。先按配置、镜像内容、节点实际状态和调度注册逐层定位。若只是 GRES 映射或容器设备注入错误，重装既不能解释原因，也可能破坏证据。

继续阅读[配置继承](./02-Category-Role-SoftwareImage与配置继承.md)，理解同一个默认配置为何不会覆盖一切。
