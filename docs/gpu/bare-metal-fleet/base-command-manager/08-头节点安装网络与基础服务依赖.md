# 头节点安装网络与基础服务依赖

BCM 安装不是只给管理服务器装一个软件包，而是建立一组相互依赖的服务。控制台能登录，只证明入口可用；新节点能启动、能正确识别自己、能获得预期系统，才证明供应链路成立。本篇以 BCM 11 安装模型为基线，重点解释各项配置为什么必须在安装前确定。

先读[节点发现与供应](./03-节点发现网络启动与供应状态流转.md)。这里补充管理服务如何成为那条链路的上游，不重复通用 PXE 协议。

## 1. 头节点不是所有流量的必经点

Head Node 是管理角色，不是“全体应用的网关”的同义词。把它的职责拆成管理对象与认证、引导与供应、镜像内容、基础网络服务、工作负载管理集成，才能判断某项故障的传播范围。部分职责可以按受支持的架构分散到其他节点。

```text
管理员 → BCM 管理对象与身份
新节点 → 引导与身份确认 → 节点安装器 → 软件镜像
运行节点 → 名称解析、时间及所配置的共享服务
应用 → GPU、训练 Fabric、存储数据路径
```

最后一行不天然经过 Head Node。但如果站点把路由、用户目录或存储入口放在头节点，其故障确实可能影响应用。画架构时应写出真实依赖，不能由“管理面与数据面分离”推断业务一定不受影响。

## 2. 三种网络拓扑改变什么

BCM 11 安装指南区分三种拓扑；它们改变外部路由和启动报文的路径，而不改变“节点仍需访问供应服务”这一要求。

| 拓扑 | 节点访问集群外的路径 | 必须额外检查 |
| --- | --- | --- |
| Type 1 | 私有内部网，经 Head Node 路由到外部网 | 转发策略、出口容量和管理面的故障影响 |
| Type 2 | 节点经站点路由器访问外部；通常与头节点直接通信 | 站点 DHCP 是否冲突、外部到节点的访问边界 |
| Type 3 | 头节点和计算节点位于不同的路由网络 | DHCP Relay、往返路由及各阶段访问策略 |

其中 Type 3 不能依靠普通路由器转发二层广播。DHCP Relay 是站点网络的配置责任，不是安装 BCM 后自动补齐的能力。以上分类来自[BCM 11 Installation Manual 第 3.3.9 节](https://docs.nvidia.com/base-command-manager/manuals/11/installation-manual.pdf)。

教学例子：Head Node 在 `10.10.0.0/24`，计算节点在 `10.20.0.0/24`。系统启动后两边能够互相 ping，并不能证明尚无静态地址的机器能取得引导信息。分别验证 DHCP 请求及响应、引导对象访问、安装器到供应源的连接，才覆盖完整路径。

## 3. 名称 时间与信任先于上层初始化

名称至少涉及节点名、域、地址和服务入口。错误的解析可能把正确证书交给错误目标，也可能让节点注册到错误集群。DNS 可查询还不够，要比较调用方实际使用的名字、返回地址与证书中的服务身份。

时钟偏差会影响证书有效期判断、日志排序和某些身份系统。应区分“本机时间已设置”与“节点能持续同步到可靠时间源”。离线网络需要自己的可达时间源，不能保留一个不可达的公网地址后认为配置已经完成。

信任材料则说明谁有资格管理、谁被允许成为节点。管理端证书、节点身份、镜像中的账户材料和 BMC 凭据不应合并成一个共享密码。密钥需要备份，但备份可读范围不能等同于普通软件镜像的分发范围。

一个常见错误是先让集群“全通”，再收紧防火墙。更可控的设计是在安装前列明源、目的、服务和阶段：预启动、安装器、正常系统、管理客户端分别需要什么；服务端能监听不等于每个阶段都有权访问。

## 4. 头节点系统与软件镜像是两份根文件系统

管理服务器安装了某个包，不表示计算节点镜像也有该包。软件镜像中的内核、驱动、库和启动脚本，最终要与节点对象绑定并经过供应、生效过程。只在头节点执行一次包管理器，容易产生“管理端命令存在，节点端组件缺失”。

设计镜像存储时，还要留出候选版本、回退版本、临时构建内容和日志空间。教学条件：每个完整镜像 60 GiB，保留 4 个版本，构建临时峰值再需要 60 GiB，另留 20% 的空闲比例，则镜像空间预算下界是：

```text
(4 × 60 + 60) / (1 - 0.20) = 375 GiB
```

这是无去重、无快照共享的容量模型，不是 BCM 最低配置。数据库、系统盘、备份副本和日志还应单独计算。把同一份镜像的快照误当成独立备份，也不能抵御底层存储故障。

## 5. 从网络启动进入节点安装器

BCM 的 node-installer 是最终系统之前的安装环境。它需要先识别物理节点，再依据配置完成供应；未知节点等待身份分配，不代表已经安全获得某个生产主机名。BCM 11 的只读观察入口包括：

```bash
cmsh -c "device;newnodes"
cmsh -c "softwareimage;list"
cmsh -c "task list"
```

`newnodes` 不带分配参数用于观察等待识别的机器；不要把带批量分配参数的示例混进巡检脚本。节点安装器及发现行为参见[安装指南第 1.3 节](https://docs.nvidia.com/base-command-manager/manuals/11/installation-manual.pdf)。

必须在启动前核对磁盘和保留策略：默认供应流程可能覆盖已有系统。旧服务器“当前离线”并不构成擦盘授权。安装器的可达性、身份审批与磁盘处置是三个独立决策。

## 6. 用最早失败边界缩小范围

| 最早失败处 | 下一份关键证据 | 不应先做的动作 |
| --- | --- | --- |
| 固件未发起网络启动 | 启动顺序、接口和交换机端口 | 更新 CUDA |
| 无地址或引导参数 | VLAN、Relay、DHCP 作用域和冲突源 | 修改应用镜像 |
| 安装器无法识别节点 | MAC、资产、交换机端口与对象对应 | 按出现顺序盲目绑定生产名称 |
| 身份已识别但供应失败 | 镜像绑定、供应源、访问日志和磁盘 | 重建全部管理对象 |
| 系统运行但服务未就绪 | 有效配置、角色、版本及服务日志 | 重做所有网络配置 |

全机架失败优先寻找共享上游；同一机架仅一台失败优先比较身份、端口和本机差异。这是排查顺序，不是排除其他原因的定理。

## 7. 掌握检查

**节点能 SSH，能证明 Type 3 的 Relay 正确吗？** 不能。运行中系统可能使用已有配置，必须观察预启动阶段。

**镜像目录存在，能证明新节点可供应吗？** 不能。绑定、网络、身份、镜像完整性和目标磁盘仍可能失败。

**头节点故障一定使训练停止吗？** 取决于运行任务的实际依赖。应沿路由、身份、存储与调度链分析，不能只根据服务器名称回答。
