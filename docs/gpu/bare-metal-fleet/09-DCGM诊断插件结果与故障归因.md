# DCGM 诊断插件结果与故障归因

`dcgmi diag` 的核心价值不是生成一个绿色结论，而是在确定的设备、配置与观察窗口中，验证特定能力。理解它要回答三个问题：测试有没有真正执行、测试在检查什么、结果能支持多大范围的判断。

前置阅读为[GPU 健康模型](./06-DCGM-NVML-Xid-ECC-PCIe-NVLink健康模型.md)。命令参数统一放在[dcgmi 命令参考](../commands/02-dcgmi命令详解.md)，本篇解释诊断机制；源码分析固定为 DCGM `v4.4.1`，不冒充所有后续版本的实现。

## 1. 被动健康与主动负载不是同一件事

持续监控观察运行中的字段和事件，适合发现趋势；主动诊断则施加计算、内存或通信负载，让潜在问题在受控条件下暴露。前者“未看到异常”可能只是从未施加相应压力，后者通过也只覆盖测试实际触及的路径。

例如空闲温度正常，不能证明持续高功耗下散热足够；本机 P2P 成功，也不能证明跨节点 NIC、交换机与存储正常。因此诊断前应明确假设，而不是无差别运行全部插件。

## 2. 按待验证能力选择插件

以下是理解插件意图的简化分类，不是固定版本的完整插件清单：

| 类别 | 主要验证对象 | 结果不能扩大到 |
| --- | --- | --- |
| `software` | 库、权限及运行环境等前提 | 长时间硬件稳定性 |
| `memory`、`memtest` | 相应显存访问与正确性测试 | 任意程序的所有访存模式 |
| `pcie` | Host/GPU 和 GPU 间通信检查 | 必然走 PCIe 而不走 NVLink |
| `diagnostic`、压力及功耗测试 | 所选计算、功耗和错误观察 | 应用精度、业务 SLO 或正式 RMA 结论 |

`pcie` 插件在可能时也会使用 NVLink，因此插件名字不等于实际传输介质。各 Run Level 选择的测试随版本演进，应以目标版本的[诊断手册](https://docs.nvidia.com/datacenter/dcgm/latest/user-guide/dcgm-diagnostics.html)和本机帮助核对，不固化一张跨版本“等级等于耗时”的表。

测试参数也属于结果的一部分。降低压力、屏蔽错误码、放宽阈值或缩短时间以后，新的 Pass 与原先要求不是同一证明。参数来源应与结果一起保存。

## 3. 执行成功 测试通过与完整覆盖要分开

分析结果时先分层：

```text
客户端能连接管理服务
→ 诊断请求可启动
→ 目标实体与插件可用
→ 测试实际执行并完成
→ 逐实体结果满足判断条件
→ 测试集合覆盖本次验收目标
```

连接失败、诊断进程被终止、测试不适用和设备确实失败，不能都转成“坏卡”。反过来，也不能把一份可解析的 JSON 当成已完成全部测试。CLI 退出码包含执行层错误，应与结构化结果一起解释；不能只用字符串搜索 `Pass`。

`Not Supported` 通常回答能力是否可用，`Skip` 回答某项是否执行；它们未必是同一个字段中的可互换枚举。要检查具体原因、设备类型和版本，而不是把这两种文本自动映射成健康。

## 4. 源码为什么说明总结果会丢失信息

固定版本 [v4.4.1 的 `nvvs/src/Plugin.cpp`](https://github.com/NVIDIA/DCGM/blob/v4.4.1/nvvs/src/Plugin.cpp) 中，`Plugin::GetResult` 取得测试的 GPU 结果，再调用 `Plugin::GetOverallResult`。后一函数的规则可改写为：

```text
发现任一 FAIL → FAIL
否则存在 WARN → WARN
否则所有条目都是 SKIP → SKIP
否则 → PASS
```

因此下列输入会得到不同的覆盖含义：

| 输入结果集合 | 该函数输出 | 可以支持的判断 |
| --- | --- | --- |
| PASS、PASS | PASS | 两个条目都通过 |
| PASS、SKIP | PASS | 仍有一个条目未被验证 |
| PASS、WARN | WARN | 存在需调查的条目 |
| PASS、FAIL | FAIL | 至少一个条目失败 |
| SKIP、SKIP | SKIP | 该集合没有通过的测试条目 |

空集合在这个函数中也满足“跳过数等于集合大小”，返回 SKIP。这是局部函数的边界行为，不能推断正常诊断流程允许任意空输入，更不能认为全套 CLI 报告的每一层汇总都采用同一函数。

这个实现特色揭示的是信息压缩：总状态不是逐实体覆盖矩阵。自动验收需要同时检查“预期实体是否齐全、必需测试是否实际执行、是否有跳过”，而不是对一个总字段做真假判断。

## 5. 执行原因与故障位置不是一一对应

以显存分配失败为例，它可能来自显存不足、进程占用、权限与运行环境，也可能是设备异常的后果。应先看错误发生在分配、执行、校验还是取样阶段，再关联驱动事件。

以带宽偏低为例，至少存在拓扑差异、NUMA 绑定、链路降宽、竞争负载、功率或温度限制等假设。只有当测试输入、路径、阈值及硬件基线可比时，性能差值才有诊断意义。多张卡同时慢，尤其要调查共享供电、上游链路和主机因素。

教学数据：同构基线中位数为 300 GB/s，待查节点结果为 210 GB/s；在相同计量口径下，比例为 `210/300=70%`，相对下降为 30%。它只说明离群，不说明损坏概率为 30%，也没有给出通用送修阈值。

## 6. Skip 应进入覆盖矩阵

假设验收要求 8 张卡各完成 4 项独立的单卡测试，共有 32 个“卡与测试”组合。若 28 项 Pass、4 项 Skip，通过项占要求的 87.5%；不能写成“100% 已验证且通过”。这一计算只是覆盖记账，不是测试置信度或硬件可靠性估计。

P2P 还需要连接对覆盖：8 张卡的无向组合有 `8×7/2=28` 对，但实际测试可能有方向、分组或拓扑筛选。单卡数齐全不能证明全部所需连接对都已检查；也不应要求不存在或不受支持的路径拥有相同带宽。

把不适用测试从验收集合删除，需要说明平台依据；把暂时无法执行的测试视为待完成，需要保留原因。两者都不能静默改写成 Pass。

## 7. 诊断执行也有安全边界

压力测试可能占用 GPU、显存、CPU、互联和功率预算。应先停止新分配、确认旧任务与残留进程，保存原始事件，再在维护窗口运行限定目标的测试。不要在生产任务故障后立即全节点压测，覆盖其最初现场。

Host Engine 的连接模式也影响观察。`v4.4.1` 的 [`StartDiag::DoExecuteConnectionFailure`](https://github.com/NVIDIA/DCGM/blob/v4.4.1/dcgmi/Diag.cpp) 含有启动嵌入式 Host Engine 的回退路径；这不意味着所有 dcgmi 子命令都会如此。因此一次 diag 可以执行，不足以证明常驻 Host Engine、持续采样和长期健康监控正常。

## 8. 从证据到隔离与 RMA

诊断发现问题时，先确定故障范围并保留身份、版本、输入、逐实体结果、内核日志和时间线。环境类问题修复环境后复测；持续硬件迹象则结合平台正式现场诊断和支持流程处理。DCGM 不替代完整现场硬件诊断或 RMA 流程。

重新入池还要复验原先失败的能力和目标业务路径，见[隔离恢复与 RMA 判定](./07-GPU节点自动隔离修复重新入池与RMA判定.md)。仅把测试参数调到通过或重启后清零计数，都没有解释故障是否真正消除。

## 9. 掌握检查

**总结果 Pass，是否证明每张卡都通过？** 未必。必须看实际执行集合和逐实体结果，源码例子已经给出 Pass 与 Skip 混合的反例。

**PCIe 插件结果是否只反映 PCIe？** 不是，需确认实际路径、子测试和平台拓扑。

**复测通过是否立即解除隔离？** 还要确认身份、配置、故障重复性及业务资格，不能仅依据一次总结果。
