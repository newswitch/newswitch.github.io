# NVSM 对象树健康检查与证据包

NVSM 将服务器的 GPU、CPU、内存、磁盘、网络与平台信息组织成可查询对象。深入学习的关键不是多记几条命令，而是理解总健康如何关联到具体部件、部件如何关联到事件，以及一份报告究竟覆盖了什么。

以 NVSM 25.03 用户指南及受支持的 DGX Server 能力为基线；不同机型与版本的目标路径和功能可能不同，不能把下面的对象树复制为任何 OEM 服务器的固定结构。前置阅读为[整机健康与告警模型](./08-NVSM整机健康告警与证据关联.md)。

## 1. 对象树是定位坐标 不是根因结论

NVSM CLI 的 Target 表示可查询对象，Properties 表示属性，Verbs 表示该目标支持的操作。先发现当前对象，再按部件身份关联其他工具；不要反过来根据手册的一张截图猜设备编号。

下面是依据指南整理的简化对象关系，省略平台特有目标：

```text
/systems/localhost
├── gpus → 具体 GPU → health → incident
├── processors → CPU 与相关告警
├── memory → 主机 DIMM
└── storage
    ├── drives → 物理盘
    └── volumes → 卷与成员关系
```

GPU 显存不归主机 DIMM 的健康结论覆盖，物理盘也不等于文件系统与应用数据。即使每块盘都可读，RAID 或卷仍可能降级；卷可挂载，也不保证 Checkpoint 完整。对象层次用于指明下一份证据的位置，而不是把下层部件健康自动外推到上层业务。

## 2. 从 HealthRollup 下钻到 Incident

NVSM 使用 DCGM 持续观察 GPU 健康。指南中的 GPU 集合属性 `Status_HealthRollup` 表示集合级健康；接着看具体 GPU 的 `Status_Health`，再进入该 GPU 的 `health` 与 incident 获取问题信息。[GPU 健康对象说明](https://docs.nvidia.com/datacenter/nvsm/nvsm-user-guide/latest/using-nvsm-cli.html)给出了这条下钻路径。

读取时保留对象路径、GPU UUID、序列号、PCI BDF 与发生时间。`GPU0` 或列表下标只是显示位置，设备更换或枚举变化后未必仍指同一张卡。

集合级异常说明至少需要继续调查，但不直接说明根因数量。假设两个 GPU 都报告同一互联的异常，它可能是一条连接的两端观测，也可能是共同上游引发的后果。不能按 incident 条数决定换卡数量。

## 3. 检查报告 活动健康与历史告警

| 证据 | 回答的问题 | 常见误读 |
| --- | --- | --- |
| `show health` 检查报告 | 此次执行的检查结果 | 当作持续覆盖整个业务周期 |
| GPU health incident | GPU 健康子系统当前报告什么 | 当作与 DCGM 完全独立的第二份证据 |
| `show alerts` | 告警系统记录什么 | 当作当前全部硬件实况 |
| `dump health` 证据包 | 支持分析可获得哪些材料 | 当作已经定位并修复 |

NVSM 对 DCGM 结果的呈现并不是完全独立的重复实验。两者同时报告相同 GPU 健康事件，增加了可关联性，不应简单算作“两票独立硬件故障证明”。更有价值的独立线索可能来自 BMC、内核 AER、应用错误或实际链路测量。

历史告警也要附带时间。修复动作后仍保留历史记录可以用于复盘；清除记录不会改变物理设备。没有新告警时，还需确认监控服务与采集路径正在工作。

## 4. 全绿结论受检查集合约束

教学场景：旧报告包含 200 项检查，新报告只执行 120 项且全部通过。新报告的“全部通过”没有覆盖旧报告的另外 80 项；先解释平台、配置、版本与可执行范围的差异，再讨论健康改善。

若预期同一平台必须有 200 项，其中 120 项 Pass、80 项因采集失败未完成，则完成覆盖为 60%。这是例题的集合计算，不是 NVSM 固定检查数，也不是系统可靠性为 60%。反过来，因硬件型号不适用而移除的检查，不应被错误计为故障。

因此比较报告应按检查身份和对象进行，而不是只比较总数或最后一行。完整的健康记录包括预期集合、实际集合、不适用原因、未完成原因和采集时间。

## 5. 用时间线区分原因与后果

教学时间线：14:00 某供电域出现异常，14:00:02 多张 GPU 降频，14:00:05 应用报通信超时，14:01 管理侧产生多条告警。最后产生的告警不一定是最早的故障。

先核对时钟和采样延迟，再关联共享物理路径：同一机箱、供电、PCIe 上游、NVLink 连接或交换域。若只有一张卡反复异常，应保留其 UUID、槽位与版本；若换卡后同槽位仍复现，故障假设就应扩大到通道、供电与平台，而不是机械重复换卡。

这些是归因思路，不应未经授权通过拔线、关电或移动生产部件制造对照。硬件交换和压力复验属于独立维护操作，需要停机条件与支持流程。

## 6. 证据包为什么要在修复前保存

`nvsm dump health` 生成用于支持分析的材料。它能保留配置、日志与系统信息的截面，但不保证所有文件恰好来自同一时刻，也不能重建任意过去状态。原始错误、复测结果和修复后状态应分别留存，避免后一次采集覆盖原始现场。

指南还提供加速采集选项，并说明可能增加 CPU 与内存消耗。更快不等于对在线业务影响更小。采集前核对资源、磁盘空间和目标范围；输出路径以实际命令返回为准，不依赖历史示例中的文件名。

证据包可能包含主机名、地址、序列号、配置和日志。使用获授权的支持渠道，记录文件校验值、采集人、时间、机型与软件版本；对外分享前做敏感信息审查。脱敏副本与原始包应明确区分，避免修改诊断关键字段后仍宣称材料完整未变。

## 7. 修复后的验收层次

首先恢复采集与对象身份，再验证原先失败项，最后验证目标计算、通信和存储路径。一个风扇或温度问题修复后，空闲健康检查通过，仍不代表负载热稳定性已经验证；磁盘告警消失也不说明应用数据已恢复到预期恢复点。

返回资源池的流程见[节点隔离恢复](./07-GPU节点自动隔离修复重新入池与RMA判定.md)。NVSM 给出平台证据，调度器决定是否接收任务，组织的验收标准决定是否允许放行，三个职责不应混在一个“修复成功”字段里。

## 8. 掌握检查

**GPU 集合 Critical 后先换哪张卡？** 先下钻到具体对象和 incident，再关联物理路径；汇总状态不能选择待换部件。

**NVSM 与 DCGM 同时报错，是否已有两份独立证明？** 未必，GPU 健康信息可能有共同来源。

**证据包成功生成，是否已经完成诊断？** 没有，它是材料，不是因果结论或送修许可。
