# NVIDIA 主流 GPU 架构解剖：以 P100 为起点读懂 Pascal 到 Blackwell

学习 GPU 时很容易得到一组彼此孤立的名词：SM、CUDA Core、Warp、Register、HBM、PCIe、NVLink。Tesla P100 适合用来把它们串成一个系统，因为它在同一代产品中集中引入或强化了几项影响至今的技术：高吞吐 FP16、CoWoS + HBM2、NVLink 和可按需迁移页面的 Unified Memory。

本文先以 **Pascal GP100 核心的 Tesla P100 SXM2 16 GB** 做一次完整解剖，再把同一套分析方法扩展到 Volta、Turing、Ampere、Ada、Hopper 和 Blackwell。PCIe 版 P100 的频率、算力、显存规格和互联能力并不完全相同，其他代际内部也存在相似的产品分化，不能把不同芯片或不同形态的参数拼成一张卡。

本文不是逐张罗列数百个 SKU，而是解决三个更稳定的问题：哪些结构是 NVIDIA CUDA GPU 长期复用的共同骨架，各代架构真正改变了什么，以及拿到任意一张显卡时怎样独立读懂它。

范围从仍常见于存量环境的 Pascal P100 开始，到数据中心与 RTX 两条 Blackwell 路线为止；更早的 Kepler/Maxwell 作为历史架构不逐代展开。中文语境经常把 GPU 都称为“显卡”，但 P100、A100、H100、B200 等没有面向桌面显示设计的产品，更准确的名称是 GPU 加速器。

## 1. 学习目标

读完本文，应当能够回答：

- GP100、Tesla P100、P100 SXM2 和 P100 PCIe 分别是什么；
- 为什么 GP100 完整设计有 60 个 SM，而 P100 常见规格是 56 个 SM；
- 一个 CUDA Kernel 如何从 Grid、Block、Warp 落到 SM 的执行管线；
- P100 为什么能达到约 21.2 TFLOPS FP16，以及它为什么没有 Tensor Core；
- HBM2 的 4096-bit 位宽和 732 GB/s 是怎样得到的；
- NVLink 的 20、40、80、160 GB/s 分别表示什么；
- Unified Memory、GPU P2P 和“多卡显存合并”为什么不是一回事；
- 理论算力、显存带宽和互联带宽分别限制哪一段数据路径；
- Pascal、Volta、Turing、Ampere、Ada、Hopper 和 Blackwell 的关键演进；
- 为什么 A100 与 RTX 3090 都属于 Ampere，却不能按同一种 GPU 理解；
- 数据中心、推理、工作站、GeForce 和 Jetson 产品线分别强化了什么；
- 怎样通过 Compute Capability、精度、显存、互联和形态读懂陌生 GPU。

## 2. 先区分芯片、板卡和服务器

| 名称 | 层级 | 含义 |
| --- | --- | --- |
| Pascal | GPU 架构代际 | Maxwell 之后、Volta 之前的一代 NVIDIA 架构 |
| GP100 | GPU 芯片 | 面向 HPC 和深度学习的 Pascal 大核心 |
| Tesla P100 SXM2 | 加速器模块 | GP100 + HBM2，使用 SXM2 形态，可连接 NVLink |
| Tesla P100 PCIe | PCIe 加速卡 | 安装在 PCIe 插槽中的 P100，规格与 SXM2 版不同 |
| DGX-1 | 完整服务器 | CPU、内存、PCIe Switch、8 张 P100、电源、散热和软件组成的系统 |

“GP100 支持四条 NVLink”描述的是芯片接口能力；“两张 P100 之间有几条 NVLink”取决于服务器布线；“程序是否使用 NVLink”还取决于 P2P、CUDA/NCCL 和通信模式。三个层次必须分开。

### 2.1 本文使用的规格边界

P100 SXM2 16 GB 的代表性规格如下：

| 项目 | 规格 | 解释 |
| --- | ---: | --- |
| 制程 | 16 nm FinFET | 相比上一代 28 nm 提升晶体管密度和能效 |
| 晶体管 | 153 亿 | GP100 芯片规模 |
| 启用 SM | 56 | 完整逻辑设计最多 60 个 SM，产品关闭其中 4 个 |
| CUDA Core | 3584 | `56 SM × 64 FP32 Core/SM` |
| FP64 Unit | 1792 | `56 SM × 32 FP64 Unit/SM` |
| HBM2 | 16 GB | 四组 HBM2 堆栈 |
| HBM2 带宽 | 732 GB/s | 理论峰值，不是应用必然达到的持续带宽 |
| L2 Cache | 4 MB | 所有 SM 和显存分区共享的末级片上缓存 |
| NVLink 1.0 | 4 Link | 每条 Link 为全双工点对点链路 |
| 峰值 FP16/FP32/FP64 | 21.2/10.6/5.3 TFLOPS | 按 Boost 频率和 FMA 计数得到的理论值 |

产品资料中的峰值采用特定时钟和计数口径。真实工作负载还受温度、功耗、指令混合、数据依赖、访存、占用率和通信影响。

## 3. 从整颗 GP100 看组件关系

[![GP100 芯片中的 GPC、SM、L2、显存控制器、HBM2、PCIe 与 NVLink 逻辑关系](/images/gpu/p100-gp100/gp100-chip-overview.svg)](/images/gpu/p100-gp100/gp100-chip-overview.svg)

*图：GP100 教学逻辑图，用于说明组件连接关系，不表示真实 Die Floorplan 的几何比例。*

GP100 可以按下面的层次理解：

```text
GP100
├── 6 个 GPC（Graphics Processing Cluster）
│   └── 每个 GPC 在完整设计中包含 10 个 SM
├── 全芯片互连与 4 MB L2 Cache
├── 8 个显存控制器分区
├── 4 组 HBM2 堆栈
├── PCIe 3.0 x16 接口
└── 4 条 NVLink 1.0
```

### 3.1 GPC 和 SM 分别解决什么问题

GPC 是从 NVIDIA 图形架构沿用下来的上层分组。对 CUDA 计算来说，更重要的执行资源是 SM。Kernel 的 Grid 会被拆成 Thread Block，硬件把可运行的 Block 分派到各个 SM；Block 内的线程再按 Warp 执行。

```text
一个 Kernel 的 Grid
→ 多个 Thread Block
→ Block 分配给某个 SM
→ 每 32 个 Thread 组成一个 Warp
→ Warp Scheduler 发射指令
→ FP32/FP64/LD-ST/SFU 等执行管线
```

一个 Block 在执行期间不会拆到多个 SM，因为它使用的寄存器、Shared Memory 和同步屏障属于同一个 SM。一个 SM 可以同时驻留多个 Block，具体数量由线程数、寄存器和 Shared Memory 配额共同决定。

### 3.2 为什么 60 个 SM 只启用 56 个

GP100 完整逻辑包含 `6 GPC × 10 SM = 60 SM`，Tesla P100 产品启用其中 56 个。关闭部分单元常用于提高大芯片制造良率、产品分档并保留冗余，不表示操作系统“丢了四个 SM”。

因此计算 P100 峰值时必须使用产品实际启用的 56 个 SM，而不是芯片框图中的 60 个。

## 4. 一次 Kernel 到底经历了什么

假设应用执行一次已经把输入放进显存的矩阵乘法：

```text
Python / C++ 调用
→ CUDA Runtime / CUDA Driver
→ Kernel Launch 写入命令队列
→ GPU 前端取得 Grid
→ Thread Block 被分配到空闲 SM
→ Block 拆成 Warp
→ Warp Scheduler 选择就绪 Warp
→ Load 指令从 HBM2/L2 取数据
→ 数据进入 Shared Memory 或 Register
→ FP16/FP32/FP64 指令在相应管线执行
→ 结果经 Register、Cache 写回 HBM2
```

如果输入最初位于主机内存，前面还要增加一次 Host-to-Device 搬运；在普通 x86 P100 服务器中，这通常经过 PCIe。如果结果需要另一张 GPU，后面可能增加 PCIe P2P、NVLink P2P 或主机内存中转。

所以“GPU 在计算”至少包含三类时间：

1. **命令与调度**：CPU 提交、驱动处理、Kernel Launch 和 Block 调度；
2. **芯片内数据移动**：HBM2、L2、L1/Shared Memory、Register 之间传输；
3. **算术执行**：Warp 指令进入 FP、整数、LD/ST 或特殊函数管线。

GPU Util 高只说明采样周期内有 Kernel 在执行，不代表 FP 单元已经跑满，也不能证明 HBM2 或 NVLink 没有瓶颈。

## 5. 进入一个 GP100 SM

[![GP100 SM 的两个处理分区、Warp Scheduler、Register、FP32、FP64、LD-ST、SFU、Shared Memory 与 Cache](/images/gpu/p100-gp100/gp100-sm-architecture.svg)](/images/gpu/p100-gp100/gp100-sm-architecture.svg)

*图：一个 GP100 SM 被划分为两个处理分区，每个分区拥有独立调度和执行资源。*

一个完整 GP100 SM 的关键资源可以概括为：

| 资源 | 每个 SM | 作用 |
| --- | ---: | --- |
| 处理分区 | 2 | 降低控制复杂度，让调度和发射更独立 |
| Warp Scheduler | 2 | 每个处理分区一个，从驻留 Warp 中选择就绪指令 |
| FP32 CUDA Core | 64 | 单精度、整数及打包 FP16 相关运算 |
| FP64 Unit | 32 | 双精度 HPC 运算 |
| LD/ST Unit | 16 | 在寄存器、Shared/Cache 和显存层次间执行加载存储 |
| SFU | 16 | 处理部分特殊函数和插值类指令 |
| Shared Memory | 64 KB | 同一 Block 内显式共享和复用数据 |
| Register File | 65536 个 32-bit Register | 保存线程私有工作集和中间结果 |

这里的“64 个 CUDA Core”不是说一个 SM 同一时刻只能运行 64 个 Thread。SM 会保持多个 Warp 驻留，并在某些 Warp 等待数据时调度其他就绪 Warp，用并发隐藏延迟。

### 5.1 Warp Scheduler 不等于 CPU Scheduler

CPU 调度器管理进程或线程的时间片；GPU Warp Scheduler 在已经驻留 SM 的 Warp 中选择满足依赖、且目标执行管线可用的指令。它不负责 Kubernetes Pod 调度，也不负责把某个 CUDA Thread 永久绑定到一个 CUDA Core。

### 5.2 Register、Shared Memory 和 Occupancy

一个 Block 使用的寄存器越多、Shared Memory 越多，同一个 SM 能同时驻留的 Block 和 Warp 就越少。Occupancy 下降不一定造成性能下降，但如果没有足够的就绪 Warp 隐藏 HBM2 或指令延迟，执行单元就可能出现空泡。

```text
寄存器/线程增加
→ 单个 Block 占用的 Register File 增加
→ 每个 SM 可驻留 Block/Warp 下降
→ 可用于隐藏延迟的 Warp 减少
```

如果编译器无法把线程私有变量全部保存在 Register 中，会发生 Register Spill。溢出的值进入逻辑上的 Local Memory，而 Local Memory 通常由设备显存承载并经过 Cache，代价远高于寄存器访问。

## 6. P100 的 FP16、FP32 和 FP64

### 6.1 P100 没有 Tensor Core

Tensor Core 从后续 Volta 架构开始出现。P100 的 FP16 高吞吐来自 GP100 SM 指令集对打包半精度运算的支持，而不是 Tensor Core。

一个 32-bit Register 可以保存两个 FP16 值，`half2` 类指令能够让一个 FP32 CUDA Core 的数据通路同时处理两个 FP16 Lane。准确的理解是：

```text
不是：FP16 先扩展成 FP32，模拟计算后再截断

而是：GP100 提供原生打包 FP16 指令
      一个 32-bit 操作数中包含两个 FP16
      同一条指令并行处理两个半精度值
```

只有数据布局、对齐和代码生成真正使用到打包 FP16 指令时，才可能接近 2 倍于 FP32 的理论吞吐。

### 6.2 峰值算力怎么计算

浮点峰值的一般公式是：

```text
峰值 FLOPS
= 执行单元数量
× 时钟频率
× 每周期每单元完成的浮点运算数
```

FMA（`a × b + c`）通常按一次乘法和一次加法计为 2 FLOPs。

以 P100 SXM2 的 1480 MHz Boost 频率计算：

#### 6.2.1 FP32 {/* #fp32 */}

```text
56 SM × 64 FP32 Core/SM × 1.480 GHz × 2 FLOP/FMA
= 10.60864 TFLOPS
≈ 10.6 TFLOPS
```

#### 6.2.2 FP64 {/* #fp64 */}

```text
56 SM × 32 FP64 Unit/SM × 1.480 GHz × 2 FLOP/FMA
= 5.30432 TFLOPS
≈ 5.3 TFLOPS
```

#### 6.2.3 FP16 {/* #fp16 */}

每条打包 FP16 FMA 同时处理两个 FP16 Lane，每个 Lane 的 FMA 计 2 FLOPs：

```text
56 SM × 64 Core/SM × 1.480 GHz × 2 Lane × 2 FLOP/FMA
= 21.21728 TFLOPS
≈ 21.2 TFLOPS
```

这解释了 `FP16 : FP32 : FP64 ≈ 2 : 1 : 0.5` 的峰值比例，但不代表任意程序换成 FP16 就会加速两倍。

### 6.3 为什么实测达不到峰值

- 指令不是全部 FMA；
- 数据依赖导致下一条指令不能发射；
- HBM2、L2 或 Shared Memory 供数不足；
- 分支发散让部分 Lane 空闲；
- 寄存器和 Shared Memory 限制驻留 Warp；
- 实际频率低于 Boost，或者发生功耗、温度降频；
- 数据没有按 `half2` 方式组织；
- Kernel 太小，启动与同步开销占比过高。

## 7. HBM2 为什么能把带宽提升到 732 GB/s

[![P100 SXM2 中 GP100、四组 HBM2、硅中介层、TSV、显存控制器和带宽计算关系](/images/gpu/p100-gp100/p100-hbm2-cowos.svg)](/images/gpu/p100-gp100/p100-hbm2-cowos.svg)

*图：左侧是封装俯视逻辑关系，右侧是单组 HBM2 的堆叠剖面。*

传统 GDDR 把多个显存颗粒放在 GPU 周围，通过较高频率和相对有限的总线宽度提高吞吐。HBM 采用不同思路：

- 多层 DRAM Die 垂直堆叠；
- 使用 TSV（Through-Silicon Via，硅通孔）连接堆叠层；
- GPU Die 与 HBM Stack 放在同一硅中介层上；
- 用极宽接口和相对较低频率提供高带宽。

Tesla P100 SXM2 16 GB 使用四组 **4-Die HBM2 Stack**，每组提供 4 GB 容量和 1024-bit 接口，合计：

```text
容量 = 4 Stack × 4 GB/Stack = 16 GB
总位宽 = 4 Stack × 1024 bit/Stack = 4096 bit
```

按照约 1.43 Gbit/s 的有效 Pin Rate：

```text
理论带宽
= 4096 bit ÷ 8 bit/Byte × 1.43 Gbit/s
= 732.16 GB/s
≈ 732 GB/s
```

这里应使用有效数据率，不应把物理时钟、DDR 倍率和有效 Pin Rate 重复相乘。

### 7.1 HBM2 没有消灭内存墙

732 GB/s 是设备内存接口的峰值。一个 Kernel 的有效带宽还会受到以下因素影响：

- Warp 的访存是否合并；
- 地址是否连续、是否对齐；
- L1/L2 命中率；
- Load/Store 指令和计算能否重叠；
- ECC、写回和其他流量；
- 多个 SM 是否形成足够并发；
- 实际时钟和功耗状态。

HBM2 大幅抬高了“内存屋顶”，但只要算力增长快于数据供给速度，内存墙仍然存在。

## 8. PCIe 与 NVLink 不是替代关系

[![P100 系统中 PCIe、主机内存中转、PCIe P2P 与 NVLink P2P 的路径和带宽口径](/images/gpu/p100-gp100/p100-pcie-nvlink-path.svg)](/images/gpu/p100-gp100/p100-pcie-nvlink-path.svg)

*图：NVLink 提供 GPU 间高速 P2P，PCIe 仍承担设备枚举、控制和主机数据搬运。*

### 8.1 PCIe 仍然负责什么

在典型 x86 P100 系统中，PCIe 仍用于：

- CPU 枚举 GPU 和访问 BAR 空间；
- 驱动下发命令和管理设备；
- Host Memory 与 HBM2 之间的数据搬运；
- 不支持或未启用 NVLink 的 GPU P2P；
- 连接 NIC、NVMe 和其他高速设备。

PCIe P2P 并不必然经过 CPU Core，也不一定经过主机内存。如果两张 GPU 的 PCIe 拓扑和 IOMMU/ACS 配置允许，它们可以通过 PCIe Fabric 直接进行 Peer DMA；只有 P2P 不可用或软件没有选择该路径时，才可能经 Host Memory Staging。

### 8.2 读懂 NVLink 的四组带宽数字

P100 的一条 NVLink 1.0 是全双工链路：

```text
一条 Link、一个方向：20 GB/s
一条 Link、双向聚合：40 GB/s

四条 Link、一个方向合计：80 GB/s
四条 Link、双向聚合：160 GB/s
```

这四个数字都可能出现在资料中，但含义不同。一次从 GPU0 向 GPU1 的单向复制不能把相反方向的带宽也算进去；两张 GPU 之间能使用几条 Link，还取决于服务器实际布线。

PCIe 3.0 x16 理论有效带宽约为每方向 16 GB/s、双向聚合约 32 GB/s。因此统一使用双向聚合口径时：

```text
160 GB/s ÷ 32 GB/s ≈ 5
```

不能一边使用 NVLink 双向聚合值，一边使用 PCIe 单向值，然后得出“10 倍”的结论。

### 8.3 有 NVLink 不等于程序一定使用 NVLink

还要同时满足：

1. 两张卡在物理拓扑上存在 NVLink 路径；
2. 驱动报告链路正常；
3. CUDA Peer Access 可用并启用；
4. 通信库选择 P2P/NVLink，而不是 Host Staging；
5. 消息足够大，能够摊薄调度和同步开销。

NCCL 会根据拓扑构建 Ring/Tree 等通信路径，但最终仍应通过拓扑输出、NCCL 日志和带宽基线验证。

## 9. Unified Memory 到底统一了什么

Pascal GP100 增加了更大的统一虚拟地址空间和硬件 Page Fault 支持。使用 `cudaMallocManaged` 分配的页面可以在 CPU 和 GPU 之间按需迁移，程序看到的是统一指针，但物理数据仍位于某处。

```text
CPU 访问某 Managed Page
→ 页面可能迁移到 Host Memory

GPU 访问同一 Managed Page
→ GPU 触发 Page Fault
→ 驱动把页面迁移或映射到 GPU 可访问位置
→ GPU 继续执行
```

它带来的主要价值是编程模型和超额分配能力，而不是免费带宽：

- 页面迁移仍会消耗 PCIe 或互联带宽；
- CPU 与 GPU 反复访问同一批页面可能发生 Thrashing；
- 远端 GPU Memory 的访问延迟和带宽不等于本地 HBM2；
- 多张 16 GB P100 不会自动变成一张拥有连续 32/64/128 GB 本地显存的 GPU。

Unified Virtual Addressing、Unified Memory、Peer Access 和 NCCL 集合通信是四个不同概念。

## 10. 用 Roofline 理解 P100 为什么会快或慢

只看 21.2 TFLOPS FP16 无法预测应用性能，还要比较算法的算术强度：

```text
算术强度 = 完成的 FLOPs ÷ 从显存搬运的 Byte
```

P100 的理论 Ridge Point 可以粗略估算为：

```text
FP32 Ridge Point ≈ 10.6 TFLOPS ÷ 0.732 TB/s ≈ 14.5 FLOP/Byte
FP16 Ridge Point ≈ 21.2 TFLOPS ÷ 0.732 TB/s ≈ 29.0 FLOP/Byte
```

- 实际算术强度低于 Ridge Point 时，更容易受 HBM2 带宽限制；
- 高于 Ridge Point 后，才更可能接近计算吞吐上限；
- 缓存复用会减少实际 HBM Traffic，使有效算术强度提高；
- 多卡任务还需要增加 NVLink/PCIe 通信屋顶。

这也解释了为什么 FP16 理论算力翻倍后，某些内存受限 Kernel 几乎不会提速两倍：计算屋顶升高了，HBM2 屋顶没有随之翻倍。

## 11. 从现象判断瓶颈在哪一层

| 现象 | 优先怀疑 | 下一步证据 |
| --- | --- | --- |
| GPU Util 高、HBM 吞吐接近基线、FP 管线不高 | Memory-bound | Nsight 指标、有效带宽、访问合并和缓存命中 |
| GPU Util 低、HBM 和 FP 都低 | 输入、Launch、同步或 CPU 瓶颈 | CPU Timeline、Kernel 间隙、DataLoader、同步调用 |
| FP16 没比 FP32 快 | 未使用打包 FP16、访存受限或转换开销 | 指令类型、数据布局、算术强度 |
| 两卡比单卡慢 | P2P/NVLink 未使用或同步占比过高 | `topo -m`、P2P 矩阵、NCCL 日志、消息大小 |
| NVLink Link Up 但带宽低 | 软件路径、Link 数、方向口径或负载不足 | Pairwise Copy 与 NCCL 基线 |
| Managed Memory 时延抖动 | Page Fault 与页面反复迁移 | Unified Memory Fault/Migration Timeline |
| 长时间运行后频率下降 | 温度、功耗或可靠性限制 | `clocks.*`、`power.draw`、温度、Throttle Reason |

## 12. 在真实 P100 上怎样验证

### 12.1 确认型号与资源

```bash
nvidia-smi -L

nvidia-smi --query-gpu=\
name,uuid,pci.bus_id,memory.total,driver_version,\
clocks.current.sm,clocks.max.sm,power.draw,power.limit \
--format=csv
```

输出应先帮助确认是 P100 PCIe 还是 SXM2，以及驱动实际识别到的显存容量。不要只根据资产表判断。

### 12.2 查看拓扑

```bash
nvidia-smi topo -m
```

重点看：

- GPU Pair 是 `NV#`、`PIX/PXB/PHB` 还是 `SYS`；
- `NV#` 后面的数字表示这一对设备之间绑定的 NVLink 数量，不是带宽倍数；
- CPU Affinity 和 NUMA Affinity 是否匹配数据加载线程；
- GPU 与 NIC 是否位于较近的 PCIe/NUMA 域。

### 12.3 查看 NVLink 状态

不同驱动版本支持的子命令略有差异，可先查看帮助：

```bash
nvidia-smi nvlink --help
nvidia-smi nvlink --status
```

Link Up 只证明链路建立，不证明应用流量使用了该 Link，也不证明带宽达到预期。

### 12.4 CUDA Samples

```bash
./deviceQuery
./bandwidthTest
./p2pBandwidthLatencyTest
```

建议按下面顺序建立基线：

1. 单 GPU Host-to-Device、Device-to-Host 和 Device-to-Device；
2. 两 GPU Pairwise P2P Enable 矩阵；
3. P2P Disabled 与 Enabled 的带宽和时延对比；
4. 相同拓扑 GPU Pair 之间的横向对比；
5. 最后再运行 NCCL Collective 基线。

测试结果必须记录驱动、CUDA、GPU 时钟、Persistence Mode、消息大小和 GPU Pair，否则不同时间的数字无法比较。

## 13. 从 P100 提炼可迁移的共同骨架

P100 不是所有 NVIDIA GPU 的固定模板，但它能建立一套可迁移的观察顺序。CUDA 编程模型长期保持 `Grid → Block → Warp → Thread`，硬件长期以 SM 为主要执行单元，并通过缓存、显存控制器和设备显存为计算管线供数。变化主要发生在每层的数量、宽度、专用单元和连接方式。

| 层次 | 可以迁移的认知 | 不能照搬 P100 的内容 |
| --- | --- | --- |
| 软件任务 | Kernel 拆为 Grid、Block、Warp 和 Thread | 新架构可能增加 Thread Block Cluster 等层次 |
| SM | Block 驻留 SM，Warp Scheduler 选择就绪 Warp | Scheduler 数量、执行端口和每种 Core 数量会变 |
| 片内存储 | Register、Shared Memory、L1 和 L2 共同影响性能 | 容量、是否统一、Bank 和数据搬运能力会变 |
| 执行单元 | FP、INT、Load/Store 和特殊函数管线协作 | Tensor Core、RT Core、DPX、TMA 等并非每代都有 |
| 设备显存 | Global Memory 位于显存背后，经 Memory Controller 访问 | 可能是 GDDR5、GDDR6、GDDR6X、GDDR7、HBM2、HBM3 或 HBM3e |
| 主机连接 | 离散 GPU 通常通过 PCIe 枚举、控制和搬运 | PCIe 代际、Lane 数和 P2P 能力取决于平台 |
| 高速互联 | 部分产品提供 GPU Peer 高速路径 | NVLink/NVSwitch 只属于部分产品，不能从架构名直接推断 |

因此，看到陌生 GPU 时不应该问“它是不是和 P100 一样”，而应该依次问：共同骨架还在不在，这一代给 SM 增加了什么，这个型号又从完整架构中保留了什么。

## 14. 先分清架构、芯片、型号、模块和系统

NVIDIA 的命名至少包含五个层次。把它们混在一起，是阅读规格时最常见的错误。

```text
架构代际：Ampere
    ↓
具体芯片：GA100、GA102、GA104……
    ↓
产品型号：A100、A40、RTX 3090……
    ↓
板卡/模块：PCIe、SXM、NVL 等具体形态
    ↓
服务器系统：HGX、DGX 或厂商定制 GPU 服务器
```

以 Ampere 为例：

- `GA100` 面向数据中心计算，形成 A100、A30 等产品，重点是 HBM、Tensor/FP64、MIG 和高速多 GPU 扩展；
- `GA102/GA10x` 面向图形、工作站和通用推理，形成 A10、A40、RTX A6000、RTX 3090 等产品，通常使用 GDDR，并包含图形与 RT 管线；
- A100 还有 PCIe、SXM、不同显存容量等版本，功耗、带宽、NVLink 和部署方式并不相同；
- HGX A100 是多 GPU 基板，DGX A100 才是包含 CPU、内存、网卡、存储、散热和软件的整机系统。

所以“同属 Ampere”只能说明它们共享一个时代的基础技术，不能证明显存、FP64、MIG、NVLink、媒体引擎或部署形态相同。

## 15. Pascal 到 Blackwell 架构演进地图

[![NVIDIA Pascal、Volta、Turing、Ampere、Ada、Hopper 与 Blackwell 的产品分支和架构演进](/images/gpu/p100-gp100/nvidia-architecture-evolution.svg)](/images/gpu/p100-gp100/nvidia-architecture-evolution.svg)

*图：架构名称描述技术代际，同代还会分成数据中心计算、通用推理、专业图形和消费级产品；图中的代表型号用于定位，不表示完整 SKU 清单。*

### 15.1 Pascal：通用骨架已经成形

代表产品包括 GP100/P100，以及使用其他 Pascal 芯片的 GTX 10 系列。P100 的关键进步是：

- GP100 为 HPC 提供较强 FP64 与 packed FP16；
- 使用 HBM2 提高设备显存带宽；
- 使用 NVLink 1.0 建立比 PCIe 更快的 GPU Peer 路径；
- Unified Memory 增加硬件 Page Fault 和按需页面迁移能力。

需要注意，P100 和 GTX 1080 虽然都属于 Pascal，却不是同一颗芯片。消费级 GP10x 通常使用 GDDR，FP64 比例、FP16 路径、NVLink 和图形单元配置也与 GP100 不同。不能用 P100 的结构图推导所有 Pascal 产品规格。

### 15.2 Volta：Tensor Core 改变 AI 计算路径

代表产品是 GV100/V100。Volta 没有简单地增加 CUDA Core，而是在 SM 中加入第一代 Tensor Core，让矩阵乘加从普通标量/向量管线转移到专用矩阵执行单元。

Volta 的关键变化包括：

- 第一代 Tensor Core，主要加速 FP16 输入的矩阵乘加；
- Independent Thread Scheduling，使同一 Warp 内线程拥有更独立的调度状态；
- 重新组织 L1 Data Cache 与 Shared Memory；
- NVLink 2.0 提高 GPU 间和支持 CPU-GPU 系统的互联能力。

从这一代开始，分析深度学习性能不能只看 CUDA Core 和 FP32。是否进入 Tensor Core、输入形状能否满足矩阵指令、数据布局和混合精度策略开始决定吞吐。

### 15.3 Turing：AI 推理、光线追踪和图形汇合

代表产品包括 T4、Quadro RTX 和 GeForce RTX 20 系列。Turing 把数据中心推理与实时图形中的专用计算进一步拆开：

- 第二代 Tensor Core 增强 FP16，并加入 INT8、INT4 等推理路径；
- RT Core 负责光线与包围盒、三角形等求交工作；
- FP32 和 INT32 管线可以在更多场景并行发射；
- GDDR6 和改进后的缓存系统提高通用数据供给能力。

T4 是典型的低功耗 PCIe 推理卡，重点是 Tensor、INT8/INT4、视频编解码和部署密度；RTX 20 则同时强调图形、显示和光线追踪。两者共享 Turing 基础，但系统用途并不相同。

### 15.4 Ampere：同代分成 GA100 与 GA10x 两条主线

Ampere 是最需要避免“只看架构名”的一代。

`GA100 / Compute Capability 8.0` 的代表是 A100、A30，面向训练、HPC 和多租户数据中心：

- 第三代 Tensor Core；
- TF32 让原本使用 FP32 的深度学习矩阵计算更容易进入 Tensor Core；
- BF16、FP16、INT8 与结构化稀疏路径；
- A100 引入 MIG，将一张 GPU 划分为具有硬件隔离的实例；
- HBM2/HBM2e、更大的 L2，以及 NVLink 3.0/NVSwitch 扩展。

`GA10x / Compute Capability 8.6` 的代表包括 A10、A40、RTX A6000 和 RTX 30 系列：

- 同样属于 Ampere，但更强调图形、RT Core、GDDR 和显示/媒体能力；
- Tensor Core、FP64 比例、显存、缓存和互联配置不同于 GA100；
- MIG 和 NVLink 必须查具体型号，不能从“Ampere”三个字推断。

这就是为什么“RTX 3090 的 CUDA Core 数更多”不能直接推出它比 A100 更适合训练或 HPC。两种芯片的执行资源定义、精度路径、显存带宽、可靠性和多 GPU 扩展目标不同。

### 15.5 Ada Lovelace：推理、视频和图形能效路线

代表产品包括 L4、L40/L40S、RTX 6000 Ada 和 GeForce RTX 40 系列，Compute Capability 通常为 8.9。关键变化包括：

- 第四代 Tensor Core，并支持 FP8 等低精度路径；
- 第三代 RT Core 和更强的图形流水线；
- 显著增大的 L2 Cache，降低部分工作负载访问外部显存的压力；
- 更强的 NVENC、NVDEC、AV1 和 Optical Flow 能力；
- 数据中心产品通常使用 GDDR6，消费产品常见 GDDR6X。

Ada 适合高密度推理、视频理解/生成、图形渲染和虚拟工作站，但并不等于 Hopper 的廉价版本。例如 L40S 使用 PCIe、没有 NVLink 和 MIG，面对需要高带宽全互联的大规模训练时，系统能力与 H100 不在同一层次。

### 15.6 Hopper：从“算得快”演进到“搬运和协作也由硬件编排”

代表产品包括 H100、H200 和 Grace Hopper GH200，Compute Capability 为 9.0。Hopper 的重点不只是第四代 Tensor Core：

- Transformer Engine 在 FP8 与较高精度之间动态协作；
- TMA（Tensor Memory Accelerator）负责多维 Tensor 在 Global Memory 与 Shared Memory 之间的异步搬运；
- Thread Block Cluster 让多个位于相邻 SM 的 Block 形成可协作层级；
- Distributed Shared Memory 允许 Cluster 内访问其他 Block 的 Shared Memory；
- DPX 指令加速动态规划算法；
- NVLink 4.0、HBM3 和新的异步执行能力加强系统扩展。

H200 仍属于 Hopper。它的重要升级主要在更大容量、更高带宽的 HBM3e，而不是换成一套新的 CUDA 执行模型。因此“架构相同”与“产品性能、容量相同”仍然是两件事。

### 15.7 Blackwell：数据中心与 RTX 再次使用同一个代际名称、不同的芯片路线

Blackwell 需要至少分成两类理解。

数据中心 Blackwell 包括 B200、GB200，以及后续 Blackwell Ultra 的 B300、GB300：

- 第五代 Tensor Core，重点扩展 FP8、FP6、NVFP4 等大模型训练与推理路径；
- 数据中心 B200 使用双 Die 封装，把两颗大规模计算 Die 作为一个 GPU 工作；
- HBM3e 提供大容量和高带宽；
- 第五代 NVLink 扩大单机、机柜级 Scale-Up 域；
- 更强的解压、RAS、安全和数据搬运能力服务于大规模 AI 系统。

RTX Blackwell 包括 RTX PRO Blackwell 和 GeForce RTX 50 系列：

- 使用另一组面向图形与工作站的 Blackwell 芯片；
- Compute Capability 与数据中心 B200 不同；
- 典型使用 GDDR7，而不是 B200 的 HBM3e；
- 强调第五代 Tensor Core、第四代 RT Core、神经渲染、显示和媒体路径；
- 通常不能获得 B200 的 HBM、NVLink Fabric 和机柜级扩展能力。

因此，“B200 与 RTX 5090 都是 Blackwell”类似于“A100 与 RTX 3090 都是 Ampere”：说明时代相近，但不能把两者当作同一颗 GPU 的不同显存版本。

## 16. 用 Compute Capability 识别硬件能力

Compute Capability（计算能力）也叫 SM Version，用 `major.minor` 表示。它描述 GPU 能识别的指令、执行特性和资源限制，不是 CUDA Toolkit 版本。

| 架构/分支 | 常见 Compute Capability | 代表产品 |
| --- | --- | --- |
| Pascal | 6.0、6.1 | P100、GTX 10 系列 |
| Volta | 7.0 | V100、Titan V |
| Turing | 7.5 | T4、RTX 20、Quadro RTX |
| Ampere GA100 | 8.0 | A100、A30 |
| Ampere GA10x | 8.6 | A10、A40、RTX 30、RTX A 系列 |
| Ada | 8.9 | L4、L40S、RTX 40、RTX 6000 Ada |
| Hopper | 9.0 | H100、H200、GH200 |
| Blackwell 数据中心 | 10.0、10.3 | B200/GB200、B300/GB300 |
| RTX Blackwell | 12.0 | RTX 50、RTX PRO Blackwell |

需要同时区分三种版本：

```text
CUDA Toolkit 版本：本机安装的编译器和用户态库版本
驱动显示的 CUDA Version：当前驱动最高兼容的 CUDA Runtime 版本
Compute Capability：GPU 硬件支持的 SM 指令与能力版本
```

例如，`nvidia-smi` 顶部显示 `CUDA Version: 12.4`，不代表机器已经安装 CUDA Toolkit 12.4，也不代表 GPU 的 Compute Capability 是 12.4。

编译产物还要区分 SASS/Cubin 与 PTX：

- Cubin 是为某个 `sm_xy` 生成的本机机器码；
- PTX 是虚拟指令表示，可以由较新的驱动 JIT 为目标 GPU 生成机器码；
- 只携带旧架构 Cubin、没有兼容 PTX 的程序，换到新 GPU 后可能出现 `no kernel image is available`；
- 架构专属的 `sm_90a`、`sm_100a` 特性不应被误认为可以自动跨代运行。

## 17. 主流产品线应该怎样分类

型号表会不断变化，但产品目标相对稳定。先判断产品线，再看具体 SKU，比先比较 CUDA Core 数更可靠。

| 产品线 | 代表型号 | 常见硬件取向 | 主要场景 | 需要特别检查 |
| --- | --- | --- | --- | --- |
| 数据中心训练/HPC | P100、V100、A100、H100/H200、B200/B300 | HBM、ECC、较强低精度与 FP64、高速互联 | 大模型训练、科学计算、多 GPU 推理 | SXM/PCIe、NVLink、HBM 容量、MIG、功耗 |
| 数据中心推理/通用加速 | T4、A2、A10、A40、L4、L40S | GDDR、PCIe、低精度、媒体引擎、较高部署密度 | 在线推理、视频、渲染、VDI | NVLink/MIG 未必存在，检查被动散热与服务器风道 |
| 专业工作站 | Quadro RTX、RTX A6000、RTX 6000 Ada、RTX PRO Blackwell | 大显存、ECC/专业驱动、RT/Tensor/显示 | CAD、渲染、仿真、桌面 AI 开发 | 驱动认证、显示口、虚拟化与数据中心支持边界 |
| GeForce | GTX 10、RTX 20/30/40/50 | GDDR、图形与显示、高 FP32/低精度性价比 | 游戏、个人开发、单机推理 | FP64、ECC、NVLink、散热、许可和长期运行能力 |
| Jetson SoC | Xavier、Orin、Thor | CPU、GPU、内存控制器和 I/O 集成在 SoC/模块 | 边缘推理、机器人、车载 | 共享系统内存、JetPack/BSP、功耗模式，不能套离散 GPU 拓扑 |

这里的“常见”不是硬性规则。比如同属数据中心产品的 L40S 与 H100，就分别走 GDDR + PCIe 的通用路线和 HBM + NVLink 的 Scale-Up 路线。最终判断必须回到具体产品手册和服务器拓扑。

## 18. 拿到任意 NVIDIA GPU，按八步读规格

### 18.1 确认完整型号和形态

不要只记录“A100”或“H100”。至少确认：

```text
型号 + 显存容量 + PCIe/SXM/NVL 形态 + 功耗档 + 服务器拓扑
```

同名 GPU 的 PCIe 与 SXM 版本可能有不同频率、功耗、显存带宽和 NVLink 能力。

### 18.2 确认架构、芯片与 Compute Capability

架构决定大类能力，具体芯片和 Compute Capability 决定 Kernel 可以使用哪些指令。框架安装前，还要对照 CUDA、驱动、PyTorch/TensorRT 和目标 `sm_xy` 的支持矩阵。

### 18.3 分开读取普通计算与 Tensor Core 算力

至少区分：

- FP64：科学计算和部分高精度仿真；
- FP32：通用浮点计算；
- TF32：Tensor Core 上兼顾 FP32 使用习惯与吞吐的矩阵路径；
- BF16/FP16：训练、微调和推理；
- FP8/INT8/INT4/NVFP4：需要量化、缩放或专用 Kernel 支持的低精度路径。

不能把 Tensor TFLOPS 当成任意 CUDA Kernel 的算力，也不能把稀疏峰值当成稠密模型峰值。规格表出现两个数值时，要确认第二个是否使用结构化稀疏。

### 18.4 同时看显存容量、带宽和类型

容量回答“模型和 KV Cache 能不能放下”，带宽回答“数据能多快送到计算单元”，类型说明封装与成本取向：

```text
HBM：宽总线、高带宽，常见于高端训练/HPC 加速器
GDDR：板级部署灵活，常见于图形、推理和工作站产品
```

HBM 产品不一定在所有负载上更快；如果 Kernel 受计算、同步、启动或 CPU 供给限制，更高显存带宽不会自动转化为吞吐。

### 18.5 看互联，而不是只数 GPU

确认：

1. GPU 到 CPU 经过哪一代 PCIe；
2. GPU Pair 是否支持 PCIe P2P；
3. 是否有 NVLink、每对 GPU 实际连接几条；
4. 是否通过 NVSwitch 构成全互联域；
5. 网卡与 GPU 的 NUMA、PCIe Root Complex 和 GPUDirect RDMA 关系。

“服务器里有八张 GPU”并不能说明八张卡之间有等价带宽。

### 18.6 看虚拟化、隔离和可靠性

检查 ECC、MIG、vGPU、机密计算、错误隔离和 RAS 能力。MIG 是否支持、可以切成多少实例以及各实例包含哪些资源，都属于具体产品能力，不应只按架构判断。

### 18.7 看媒体和图形单元

视频推理、数字人、转码和视觉生成服务还要检查 NVDEC、NVENC、JPEG Decoder、AV1、RT Core 和显示能力。只比较 Tensor Core 会遗漏整条输入输出链路。

### 18.8 看功耗、散热和服务器约束

被动散热 GPU 依赖服务器风道；SXM 模块依赖专用基板和散热系统；高功耗 GPU 还会影响 PSU、机柜功率、液冷和降频。峰值性能只有在供电、温度和时钟不受限时才有意义。

## 19. 在机器上确认“我拿到的到底是哪张 GPU”

### 19.1 查看型号、显存、功耗和 PCI 地址

```bash
nvidia-smi --query-gpu=name,uuid,pci.bus_id,memory.total,power.limit --format=csv
```

### 19.2 查看驱动可见的详细能力

```bash
nvidia-smi -q
nvidia-smi topo -m
nvidia-smi nvlink --status
```

最后一条只对驱动支持且实际具有 NVLink 的产品有意义。没有输出不能直接判断硬件损坏，先确认型号和命令帮助。

### 19.3 用 PyTorch 查询 Compute Capability 与 SM 数

```python
import torch

index = 0
props = torch.cuda.get_device_properties(index)

print("name:", props.name)
print("compute capability:", torch.cuda.get_device_capability(index))
print("SM count:", props.multi_processor_count)
print("memory GiB:", props.total_memory / 1024**3)
```

这只能证明当前 PyTorch 和驱动实际识别到的设备能力。Tensor Core 代际、NVLink 拓扑、显存带宽和媒体引擎仍要结合产品资料与实测。

### 19.4 查看当前软件是否包含目标架构代码

```bash
nvcc --list-gpu-arch
cuobjdump --list-elf ./your_binary
cuobjdump --dump-ptx ./your_binary
```

`nvcc --list-gpu-arch` 表示当前 Toolkit 能生成哪些架构，不表示机器安装了对应 GPU；`cuobjdump` 用于确认已有二进制包含哪些 Cubin/PTX。

## 20. 三组最容易判断错误的同代产品

### 20.1 A100 与 RTX 3090

共同点是 Ampere 时代的基础技术；差异是 GA100 与 GA102 两条芯片路线。A100 强调 HBM、MIG、Tensor/FP64 和数据中心互联，RTX 3090 强调 GDDR6X、图形、RT 和桌面形态。CUDA Core 数不能跨这两种设计直接决定训练性能。

### 20.2 H100 与 L40S

两者都能执行 FP8 Tensor 计算，但 H100 属于 Hopper，具有 HBM、TMA、Thread Block Cluster 和高端 NVLink 扩展；L40S 属于 Ada，使用 GDDR6、PCIe，强化图形、视频和通用推理。单卡模型推理、视频服务与大规模多卡训练的选型结论可能完全不同。

### 20.3 B200 与 RTX 5090

两者都使用 Blackwell 名称，但 B200 属于数据中心 Compute Capability 10.0 路线，使用 HBM3e 和第五代 NVLink；RTX 5090 属于 RTX Blackwell Compute Capability 12.0 路线，使用 GDDR7 并强化图形、显示和神经渲染。软件编译目标和系统拓扑都不能互相照搬。

## 21. 从工作负载反推应该关注什么

| 工作负载 | 第一优先级 | 第二优先级 | 经常被遗漏的条件 |
| --- | --- | --- | --- |
| 大模型训练 | BF16/FP8 Tensor、HBM 容量与带宽 | NVLink/NVSwitch、跨节点网络 | Framework/Kernel 是否真正使用目标精度 |
| 大模型在线推理 | 模型 + KV Cache 是否放得下、显存带宽 | 低精度吞吐、批处理与调度 | TTFT、TPOT、并发、功耗和尾延迟 |
| 多卡推理 | 单卡容量和 Tensor Parallel 通信量 | GPU Pair 拓扑与 Collective | 有 NVLink 不等于任意 Pair 都满带宽 |
| 科学计算 | FP64、显存带宽与数值正确性 | NVLink、MPI/NCCL、GPUDirect | 消费卡 FP32 很高但 FP64 可能不合适 |
| 视频 AI | NVDEC/NVENC/JPEG 与显存容量 | INT8/FP8 推理效率 | 解码可能先于模型计算成为瓶颈 |
| 图形/渲染 | RT Core、显存和专业驱动 | Tensor、显示与编码能力 | 数据中心计算卡未必提供显示输出 |
| 多租户服务 | MIG/vGPU、故障隔离和可观测性 | 单位功耗吞吐与调度 | 并非所有数据中心卡都支持 MIG |

选型最终不是“哪一张卡峰值最大”，而是以下约束的交集：

```text
模型与数据能放下
∩ Kernel 支持目标架构和精度
∩ 内存与互联不会饿死计算单元
∩ 服务器能够供电和散热
∩ 运维、隔离和软件生命周期满足生产要求
```

## 22. 常见误区

### 22.1 P100 支持 FP16，所以有 Tensor Core

错误。P100 通过 GP100 CUDA Core 的 packed FP16 指令提高半精度吞吐，Tensor Core 从 Volta 开始出现。

### 22.2 GP100 完整设计的 60 个 SM 和 P100 的 56 个 SM 互相矛盾

不矛盾。60 是完整芯片逻辑配置，56 是 Tesla P100 产品启用数量。计算产品峰值要用 56。

### 22.3 HBM2 带宽高，所以所有 Kernel 都能达到 732 GB/s

错误。访问不连续、并发不足、缓存行为、依赖和指令混合都会降低有效带宽。

### 22.4 四条 NVLink 就表示任意两张 GPU 都有 160 GB/s

错误。160 GB/s 是单颗 GPU 四条 Link 的双向聚合上限；实际 GPU Pair 的 Link 数由服务器拓扑决定。

### 22.5 NVLink 把多卡显存自动合并

错误。它提供高速 Peer 数据路径；模型和框架仍需要显式切分、通信或使用相应内存 API。

### 22.6 GPU 间 PCIe 通信一定经过 CPU 复制

错误。PCIe P2P 可以通过 PCIe Fabric 直接 DMA；只有拓扑、IOMMU/ACS、驱动或软件不允许时，才可能由主机内存中转。

### 22.7 同一架构的 CUDA Core 可以直接比较

仍然不严谨。同代不同芯片可能采用不同 SM 配置、频率、缓存、显存和专用管线；跨代比较更不能只数 Core。应比较目标精度的实际 Kernel、显存和端到端性能。

### 22.8 Tensor Core 支持某种精度，应用就会自动加速

错误。框架、算子、矩阵形状、数据布局、量化/缩放策略和编译产物都必须进入对应执行路径。否则硬件单元存在也可能闲置。

### 22.9 架构相同，CUDA 镜像就一定通用

错误。还要检查驱动、Toolkit、框架 Wheel、算子库、Cubin/PTX、Compute Capability 和架构专属指令。容器携带用户态库，宿主机驱动和物理 GPU 仍决定底层能力。

## 23. 本篇总结

Tesla P100 的关键不是某一个数字，而是四条协同路径：

```text
计算：Grid → Block → Warp → Scheduler → FP/INT/Tensor/其他执行单元
片内存储：Register/Shared/L1 → L2
设备存储：Memory Controller → HBM 或 GDDR
设备互联：显存 → PCIe/NVLink → Peer GPU、Host 或网卡
```

从 Pascal 到 Blackwell，NVIDIA 没有抛弃这套骨架，而是在骨架上持续增加：

```text
Tensor Core 与更多低精度
→ 更高容量和带宽的显存
→ 更强的异步数据搬运
→ Block Cluster 和跨 SM 协作
→ 更高代 NVLink/NVSwitch
→ MIG、RAS、安全和媒体专用能力
```

分析任意 NVIDIA GPU 时，应分别问：

1. 它属于哪个架构、哪颗芯片和哪个产品分支；
2. Kernel 能否使用目标 Compute Capability 和计算管线；
3. SM 是否有足够并发隐藏延迟；
4. 数据是否高效经过 Cache 和 HBM/GDDR；
5. 多 GPU 通信是否使用正确的物理链路；
6. 型号、形态、功耗、散热、隔离和软件生命周期是否满足部署要求；
7. 理论峰值、稀疏峰值、单向带宽和双向聚合值是否采用统一口径。

## 24. 课后练习

1. 为什么 GP100 完整设计有 60 个 SM，而计算 P100 峰值时使用 56？
2. 为什么 P100 FP16 峰值约为 FP32 的两倍？它与 Tensor Core 有什么区别？
3. `4096 bit × 1.43 Gbit/s ÷ 8` 为什么得到约 732 GB/s？
4. 为什么四条 NVLink 的 160 GB/s 不能作为一次单向复制带宽？
5. PCIe P2P 为什么不一定经过 CPU Core 或 Host Memory？
6. Unified Memory 为什么不等于多 GPU 显存池？
7. 为什么 A100 与 RTX 3090 都是 Ampere，却不能只比较 CUDA Core 数？
8. Volta 相对 Pascal 对 AI 计算路径产生了什么根本变化？
9. Hopper 的 TMA 与 Thread Block Cluster 分别解决什么问题？
10. H100 与 H200 架构相同，为什么运行大模型的能力仍可能不同？
11. B200 与 RTX 5090 都叫 Blackwell，为什么编译目标和部署方式不能照搬？
12. Compute Capability、CUDA Toolkit 版本和 `nvidia-smi` 显示的 CUDA Version 有什么区别？
13. 一个支持 FP8 的 GPU 运行模型时仍使用 BF16，可能有哪些原因？
14. 如何证明两张 GPU 的通信确实走了 NVLink，而不是 PCIe 或 Host Staging？

### 24.1 参考答案

1. 60 是 GP100 完整逻辑配置，P100 产品因制造良率和产品分档启用 56 个 SM；产品峰值必须使用实际启用资源。
2. GP100 的 packed FP16 指令可以让一个 32-bit 数据通路处理两个 FP16 Lane，因此理论吞吐是 FP32 的两倍；Tensor Core 则是后续架构中面向矩阵乘加的专用执行单元。
3. 4096 bit 是总位宽，除以 8 转换为 Byte，再乘有效 Pin Rate，得到每秒可传输的字节数。
4. 单向复制只使用一个方向，不能把反方向带宽加入同一传输；160 GB/s 还是单颗 GPU 四条 Link 全部可用时的双向聚合上限。
5. 支持 Peer DMA 时，数据可以沿 PCIe Switch/Root Complex 的 P2P 路径直接传输，不需要 CPU Core 执行复制；是否可用由拓扑和平台配置决定。
6. Unified Memory 统一的是地址与页面管理模型，页面仍有物理位置，迁移和远程访问仍消耗带宽；框架还需要决定数据与模型如何切分。
7. A100 使用 GA100 数据中心计算路线，RTX 3090 使用 GA102 图形路线；两者的 SM 定义、Tensor/FP64、HBM/GDDR、MIG、NVLink、可靠性和功耗目标不同。
8. Volta 首次加入 Tensor Core，把深度学习的主要矩阵乘加从普通 CUDA Core 路径迁移到专用矩阵执行路径。
9. TMA 把多维 Tensor 地址生成和 Global/Shared Memory 异步搬运交给硬件；Thread Block Cluster 让多个相邻 SM 上的 Block 获得协作、同步和 Distributed Shared Memory 能力。
10. H200 通过更大容量、更高带宽的 HBM3e 改变模型、KV Cache 和访存上限，即使 SM 架构仍属于 Hopper，端到端能力也会不同。
11. 数据中心 B200 与 RTX Blackwell 使用不同芯片分支和 Compute Capability，前者侧重 HBM3e、NVLink 和 Scale-Up，后者侧重 GDDR7、图形与显示，二进制目标和物理平台均不同。
12. Compute Capability 是 GPU 硬件能力；CUDA Toolkit 是编译器和用户态工具链版本；`nvidia-smi` 的 CUDA Version 是驱动可兼容的最高 CUDA Runtime 版本，不等于已安装 Toolkit。
13. 可能是框架或算子不支持 FP8、模型没有完成量化/校准、矩阵形状或布局不适合、精度策略回退，或者当前编译产物没有生成对应架构 Kernel。
14. 先用 `nvidia-smi topo -m` 确认 GPU Pair 的物理 `NV#` 路径，再确认 CUDA P2P 可用，最后通过 Pairwise 带宽测试、NCCL 拓扑/调试日志和 NVLink 计数器变化交叉验证。
