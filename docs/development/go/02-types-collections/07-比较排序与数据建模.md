# Go 比较、排序与数据建模：从值相等到业务身份

程序里的相等不一定等于业务里的同一对象。集合键、稳定排序、时间和浮点数需要各自的判定规则，才能形成可靠的数据模型。

## 1. 可比较不等于适合当身份

结构体字段全部可比较时，可以使用 == 并作为 Map key；Slice 通常需要 slices.Equal，结构化嵌套数据要明确比较深度。函数除 nil 比较外不支持一般相等比较。

指针相等比较地址，不比较对象内容。把数据库对象的指针作为业务 key，会把同一行的两个加载结果当作不同对象。适合的身份往往是 tenant 与 ID 的组合。

## 2. 复合 key 与排序实验

```bash
cd examples/go/core-lab
go run ./cmd/lab -case comparison
```

```text
key=one sorted=[1 2 3]
```

完整实现和断言见 [core-lab](https://github.com/newswitch/newswitch.github.io/tree/main/examples/go/core-lab)。

复合结构体 key 避免手工用冒号连接字符串产生歧义。slices.Sort 修改原 Slice；需要保留输入时先 Clone。排序比较函数必须自洽，不可用有溢出风险的 a-b 草率实现所有整数比较。

## 3. 稳定、时间与金额

稳定排序保持比较相等项原有顺序，但如果输入来自无序 Map，仍不能保证跨次运行稳定。分页排序应有唯一的 tie-breaker，例如创建时间相同再按 ID。

时间用 time.Time.Equal 比较同一时刻，不能把含 Location 和单调钟信息的结构体 == 当作通用语义。金额优先定点整数或明确精度的十进制方案，浮点数的 NaN 与舍入不能靠 == 随意处理。

## 4. 把非法状态限制在边界

使用有意义的命名类型和构造函数表达单位、状态及校验。Go 的命名 string 状态仍可能被显式转换成非法值，入站 JSON、数据库读取与事件消费仍需验证。

业务对象与传输 DTO 不必完全相同。密码散列、租约 token、内部租户字段应从公开 JSON 中排除；这不是单纯把所有字段导出就能解决的。

## 5. 练习与答案

### 5.1 稳定排序能把 Map 输出变成跨次固定顺序吗

仅稳定不足够，还需完整且确定的排序键。

### 5.2 两个对象指针不同代表业务实体不同吗

不代表，业务身份通常由稳定 ID 定义。

### 5.3 JSON DTO 应直接包含全部数据库字段吗

不应，公开契约与内部状态应分离。
