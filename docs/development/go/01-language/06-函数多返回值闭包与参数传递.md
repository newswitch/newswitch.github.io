# Go 函数 多返回值 闭包与参数传递

函数不仅接收输入并返回结果，也决定状态由谁持有、失败由谁处理。Go 的参数传递是值传递；看起来像“引用传递”的效果，通常来自复制后的值仍引用同一底层对象。

## 1. 调用时复制了什么

普通整数、结构体、指针、Slice 和 Map 参数都会发生相应值的传递。指针值的复制让两边能指向同一对象；Slice 描述信息的复制让两边可能共享底层数组。修改函数内的参数变量，不自动替换调用方变量。

多返回值适合把正常结果和 error 一起表达。错误不为 nil 时，结果是否还能使用由 API 契约决定，不能默认忽略错误继续处理。命名返回值是函数内变量，不是自动消除错误传播的机制。

以下函数放在已有包内，第一个需导入 errors：

```go
func divide(a, b int) (int, error) {
    if b == 0 { return 0, errors.New("zero divisor") }
    return a / b, nil
}

func counter() func() int {
    n := 0
    return func() int { n++; return n }
}
```

调用 `next := counter()` 后，next() 返回 1，再调用返回 2。闭包捕获变量而非冻结常量；这个 next 不支持无同步并发调用。调用 divide 后先处理 err，再使用商。

counter 返回的函数保留 n 的状态，因此两次调用分别为 1、2。它捕获的是变量关系，不是简单冻结当时的数字。闭包被多个 Goroutine 调用时，该共享计数仍需要同步；“它是局部变量”不能证明并发安全。

## 3. 回调与可变参数

函数可以作为参数、字段和返回值，用于注入时钟、执行器或外部调用。在小接口已经足够时，不需要构建复杂反射容器。可变参数在函数内表现为 Slice，传入现有 Slice 展开时仍需考虑共享数据。

不要把 nil 函数和空实现混用；调用 nil 函数会 panic。测试替身应保持真实函数的错误、取消和资源约定，否则单元测试可能验证了一条生产中不存在的路径。

## 4. 复制参数后修改哪一层才会被看见

函数接收一个 *Task 的副本，修改其指向字段会影响原对象；把参数重新指向另一个 Task，不会替换调用方的指针。要替换调用方持有的值，通常返回新值比使用多层指针更容易读懂。

Slice 也类似：修改元素可能被看到，重新切片只修改本地描述符；append 的新描述符需要返回。Map 的插入删除会作用于共享映射，但把本地参数赋成新 Map 不会替换外部变量。

不要把这些现象归结为“某些类型引用传递”。所有权问题应具体到描述符、元素和对象，才能知道哪些操作需要复制或同步。

## 5. 闭包保存变量，工厂调用建立不同状态

counter 每调用一次，会创建一份新的 n；同一次调用返回的 next 函数多次使用同一份状态。把同一个 next 复制给另一个变量，不会再次创建 n，只是增加了对同一闭包状态的使用路径。

回调保存指针、连接或大缓冲区时，也可能延长它们的生命周期。注册后何时移除、回调是否并发、失败谁处理，都要在注册 API 中定义，而不只是规定 func 的参数列表。

函数值可以是 nil，调用前是否检查取决于 API 是否允许“未配置”；必需回调应在构造时拒绝 nil，不能让每个业务调用都猜测。

## 6. 可变参数与部分结果需要显式契约

把现有 Slice 用 values... 展开，参数切片仍可能共享元素。配套 language 实验在回调中把第一个元素设为 9，调用方也看到修改。若函数承诺不修改输入，应在实现中遵守，而不是期待可变参数自动复制。

多返回值并不规定“error 非 nil 时所有结果无效”：Reader 允许数据与 EOF 同时返回，批量 API 也可能返回已处理数量。调用方应按契约消费有效部分，再分类错误。

可复用边界通常使用明确输入输出、Context 和 error；不要把所有内容装进 any，再让每层猜测类型。小函数与小接口的组合，往往比复杂反射注入更能保留静态约束。

## 7. 练习与答案

### 7.1 函数接收指针就变成了引用传递吗

不是。传入的是指针值的副本；它能访问共享对象，但函数内给指针变量重新赋值不会替换调用方指针。

### 7.2 闭包里的 n 是局部变量 为什么仍会竞争

多个闭包调用可能访问同一被捕获变量。生命周期和并发所有权是不同问题。

### 7.3 返回了结果和错误 能否只用结果

必须看 API 契约。很多函数在错误发生时结果不完整，忽略 error 可能继续传播错误状态。
