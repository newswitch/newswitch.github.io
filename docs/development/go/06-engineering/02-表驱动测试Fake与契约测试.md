# Go 表驱动测试、Fake 与契约测试：测试什么才有价值

覆盖率不能代替断言质量。一个可靠测试应说明输入、可观察结果和失败边界，并区分内存替身、真实协议与外部服务验证。

## 1. 表驱动结构

把输入、期望值和错误类别放入 test case，逐条 t.Run。比较结果时关心行为，而不是私有函数调用顺序。错误使用 errors.Is/As，不把易变化文本作为全部契约。

t.Helper 改善失败位置，t.Cleanup 绑定资源释放，t.TempDir 避免污染工程。并行测试共享环境变量、端口、全局 Gin mode 或数据库时，需要明确隔离，不要盲目 t.Parallel。

## 2. 运行实际断言

```bash
cd examples/go/core-lab
go test ./... -count=1 -timeout=30s
go test ./internal/demos -run TestPipeline -v
```

TestExperiments 对每个案例的输出逐条比较，TestPipeline 检查大于队列容量的输入、取消和非法 Worker 上限。测试不通过时应保留完整失败证据，不应过滤输出后只显示 PASS。

## 3. Fake 不能证明什么

内存 Publisher 可模拟“实际接收但返回超时”，用于验证稳定事件 ID、重试与 Inbox 去重；它不能证明 Kafka ACL、分区、重平衡和客户端版本兼容。

httptest.Recorder 验证 Handler，httptest.Server 验证本机真实 HTTP，外部 Postgres/Redis/Kafka 才验证对应系统契约。这些层次都需要，但不能互相冒充。

## 4. 故障测试的断言

事务失败不只断言 error，还要查询业务行和 Outbox 是否同时回滚；租约过期要证明旧 token 不能提交；跨租户请求应看不到目标，而不只是返回非 200。

不要把外部服务缺失时 t.Skip 的测试计作通过。本系列外部联调使用显式 build tag 与必要环境变量，未配置就失败，默认本地测试不触碰真实服务。

## 5. 一个测试用例至少包含四类证据

输入与前置状态决定测什么，执行动作决定经过哪条边界，结果断言决定看到什么，清理与剩余状态决定有没有留下资源。只断言 err!=nil，无法区分正确拒绝、连接失败与实现根本没有运行。

表驱动适合共享执行逻辑、变化输入与期望的情况；复杂场景可以拆成有名称的独立测试，避免一个巨大表格把状态准备藏成条件分支。t.Helper 让失败指向业务断言调用点，而不是只显示公共辅助函数。

错误断言通常优先 Is/As 与稳定协议字段。只有文本本来就是公开契约时才严格比较整段文本；不能让数据库驱动升级改变内部措辞就使全部业务测试失效。

## 6. 并发测试用通知建立顺序，不用等待猜测

例如要证明请求在等 DB 连接，可以先借走唯一连接，再启动请求，通过已到达阶段的通知建立前置条件；用有限 Context 观察等待结果，归还连接后再验证恢复。固定 Sleep 只能制造机会，不能证明所需交错发生。

t.Cleanup 与 defer 都有作用范围：并行子测试会改变执行时机，父测试的资源必须活到全部子测试完成。测试环境变量与进程全局 Gin mode 不适合被多个并行用例来回改写。

每个自建 Goroutine 都应有退出信号与 Join；超时失败路径也要清理。否则测试虽显示 PASS，残留任务却可能污染下一个用例。

## 7. Fake 的价值是控制故障，不是冒充生产系统

Fake 可以精确模拟“已接收但确认丢失”“第一次失败第二次成功”“旧 token 迟到”等交错，用来检查幂等与状态不变量。它应保留真实接口的取消、错误和资源约定，不能永远瞬时成功。

Recorder 检查 Handler 控制逻辑，真实回环 HTTP 检查连接和提交行为，真实中间件检查驱动与服务协议，目标部署再检查网络和权限。为每类结论选择最低但足够的层次，比把所有事情塞进慢集成测试更清楚。

可重复的有限本地实验和外部联调互为补充。外部服务未启动时应明确未执行，不把编译通过、测试被跳过或返回假的固定数据计作服务验证。

## 8. 断言“没有发生的副作用”同样重要

事务失败后查询业务行与 Outbox 都未提交；Inbox 处理失败后去重标记不应残留；请求结束后 active 数与连接许可应归零；旧租约持有者不能覆盖新结果。这些都是错误返回之外的行为证据。

配套 foundation 测试还检查字符串前缀、帧边界、旧循环变量复用、泛型方法与文件生命周期。requestflow 的路由测试则验证注册时机、405/Allow 与 301/307，而不只是返回一个 200。

可先运行 go test ./internal/foundation -v -count=1，再查看每个测试实际断言的字段。覆盖率用于找未经过的代码，不替代这些不变量。

## 9. 练习与答案

### 9.1 覆盖率 100% 能证明故障恢复正确吗

不能，需要具体失败场景与状态不变量断言。

### 9.2 Fake Kafka 通过等于真实 Broker 通过吗

不等于。Fake 只能证明被模拟的确认、错误与去重逻辑；真实 Broker 的 ACL、分区、重平衡和网络行为仍需显式联调。

### 9.3 测试资源关闭应该依赖人工清理吗

不应，使用 Cleanup、defer 和有界等待。
