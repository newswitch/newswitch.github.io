# Go 栈增长、逃逸分析与对象生命周期

变量写在函数里，不代表它一定存在栈上；返回指针，也不代表每个调用都分配堆对象。用 Go 1.27.3 的编译报告与四组分配实验，区分生命周期、逃逸分析和实际保留。

## 1. 先分清作用域、生命周期与存储位置

作用域决定源码中哪里可以使用一个名字；生命周期决定对象何时仍可能被访问；栈或堆是编译器与运行时为满足语义选择的实现方式。

函数返回一个有效指针时，Go 必须保证它引用的对象仍然可用，不能像错误的手工内存管理那样指向已销毁栈帧。但编译器可能通过内联看清整个调用，消除对象或者把它放进调用者的生命周期，因此“源码返回指针”不等于“这个调用必有一次堆分配”。

局部变量也可能被全局引用、闭包或后台任务保留。决定分配位置的是引用和使用关系，不是变量名字所在的缩进层级。

## 2. Goroutine 的栈怎样增长

每个 Goroutine 有自己的栈，承载调用帧、局部数据和相关元信息。需要更多空间时，运行时可以分配更大的栈、复制有效内容并调整受管理的内部引用；合适时也可能收缩。Go 1.27.3 可以从 runtime/stack.go 的 newstack、copystack 阅读增长和复制，再关联目标架构汇编中的 morestack 入口。

不要把 Goroutine 栈当成固定大小的 C 线程栈，也不要把所有栈增长都算成应用对象堆分配。goroutine 数量很大、调用链很深或仍持有大局部值时，栈内存本身也值得观察；HeapAlloc 不是进程全部内存。

Go 管理的指针可被运行时识别；把地址转换成 uintptr 后长期保存，不能指望 GC 和栈复制继续把它当有效指针处理。unsafe 的地址技巧不能拿来证明或延长对象生命周期。

## 3. 逃逸分析是编译期的数据流分析

cmd/compile/internal/escape/escape.go 说明两条核心约束：栈对象地址不能被存入寿命更长的堆位置；对象不能在其栈存储失效后仍被引用。

编译器分析赋值、取地址、解引用、返回值和调用关系，记录参数如何流向结果或堆。即使某个函数没有内联，已知的参数流摘要也可以帮助调用者判断对象不逃逸。它不是运行时看到一个指针被返回后，临时把该对象从栈搬到堆。

常见影响包括全局保存、未知调用、闭包捕获、动态大小分配和对象过大。接口不一定分配，取地址不一定分配，闭包也不一定分配；要看具体调用点和优化结果。

## 4. 四个实验只改变对象如何被使用

配套 Record 为 64 字节，Value 是 int64，Padding 占 56 字节。InlineRecord 与 OpaqueRecord 都返回 &Record；后者用 go:noinline 固定边界。ReadRecord 只借用指针读字段，不保存它。

```bash
cd examples/go/core-lab
go test ./internal/mechanism -run TestAllocationEvidence -v -count=1
go test ./internal/mechanism -run '^$' -bench 'Benchmark(Inline|Opaque|Published|Borrowed)' -benchmem -count=3
```

Go 1.27.3、Windows/amd64 的结果重点是分配数：

| 场景 | B/op | allocs/op | 原因 |
| --- | --- | --- | --- |
| InlineRecord 返回后立即读 Value | 0 | 0 | 内联后对象不必保留为堆对象 |
| OpaqueRecord 返回后立即读 Value | 64 | 1 | 固定非内联函数需要让返回对象存活 |
| InlineRecord 返回指针写入全局 | 64 | 1 | 调用结束后仍能通过全局访问 |
| 局部 Record 地址传入只读 ReadRecord | 0 | 0 | 指针被借用但未被保留 |

实验使用 AllocsPerRun 与 Benchmark 双重观察，并把计算结果保留，避免整个工作被无用代码消除。零堆分配不证明一定真的在栈上建立了完整对象，它也可能被标量化或消除。测试中的精确数字是固定工具链的回归基线，不是 Go 语言对所有版本的保证。

## 5. 编译报告必须看具体调用点

```bash
go test ./internal/mechanism -run '^$' -gcflags='newswitch.dev/go-core-lab/internal/mechanism=-m=2'
```

报告会同时出现如下信息，路径行号随代码调整变化：

```text
can inline InlineRecord
cannot inline OpaqueRecord: marked go:noinline
record does not escape
inlining call to InlineRecord
&Record{...} does not escape
&Record{...} escapes to heap
```

看起来相互矛盾，是因为有“独立函数体”和“内联后的不同调用点”。InlineRecord 自身返回对象的路径可报告逃逸；它内联到立即读字段的位置后，对象又可不逃逸；内联到写全局的位置仍然逃逸。

先核对文件、行号、函数与调用上下文，再用 allocs/op 验证。不要把整份报告里任意一条 escapes to heap 归到某个热点，也不要用 all=-m=2 带来的大量标准库输出掩盖目标包。

## 6. 堆分配、长期保留与泄漏分别怎么查

堆分配表示对象在堆上建立，不代表对象永远不回收。alloc_space 高可能是高频短命对象；inuse_space 高更接近当前仍被引用的对象。闭包、全局 Map、缓存和仍阻塞的 Goroutine 都可能延长寿命。

小 Slice 留住大数组的问题，核心不是那个 Slice 描述信息分配在哪里，而是它仍能访问整块底层存储。已有 [小切片保留大数组案例](../07-diagnostics/06-小切片保留大数组的内存排查.md) 使用相同可见长度比较 view 与 clone。

优先减少无意义的大对象保留和重复编码，再考虑小对象分配。sync.Pool 可能降低分配频率，但不能当持久缓存，也必须控制复用容量、敏感数据和并发所有权；为了追求零分配而共享可变缓冲，可能把性能问题改成正确性问题。

## 7. 比较前固定构建与输入

记录 go version、go.mod、GOOS/GOARCH、优化标志和输入大小。-N、-l、Race、覆盖率和 PGO 都可能改变生成代码；诊断构建与正式构建不能混为一组数据。

这里的 go:noinline 是实验控制条件，不是建议给生产构造函数普遍加这个指令。若升级工具链导致分配测试变化，先比较编译报告与对象使用关系，再决定是否更新基线，不要为了保住旧数字关闭有价值的优化。

## 8. 练习与答案

### 8.1 返回指针的函数为何既有 escapes 报告，又能零分配

独立函数体与内联后的具体调用点分析不同。内联让调用者看到对象只用于立即读字段，从而避免堆分配；必须对应调用点与实测结果解释。

### 8.2 一个局部变量取地址传给函数，就必须逃逸吗

不一定。被调函数只借用且不保留地址时，编译器可利用参数流信息证明它不需要超过当前生命周期。ReadRecord 的非内联实验就是这种情况。

### 8.3 allocs/op 降为零就说明内存泄漏解决了吗

不是。它衡量新分配，不衡量已有全局引用、切片底层数组和未退出 Goroutine 的保留。还要分析 inuse、对象可达性和进程整体内存。
