# Go 栈增长、逃逸分析与对象生命周期

局部变量不一定在栈上，返回指针也不会自动悬空。编译器根据对象的使用与生命周期安排存储，具体结果必须结合优化后的代码验证。

## 1. 词法作用域与存储位置

变量在函数里声明，只说明名字的作用域，不能直接确定它在栈还是堆。对象需要活得比当前栈帧更久、被间接共享或动态大小难以静态安排时，可能逃逸到堆；优化也可能消除分配。

Goroutine 栈可按需增长，不能随意保存指向栈内部的裸地址并假定永远不变。unsafe 的错误使用无法靠 GC 自动修复。

## 2. 返回指针实验

```bash
cd examples/go/core-lab
go run ./cmd/lab -case escape
```

```text
value=survives-return
```

完整实现和断言见 [core-lab](https://github.com/newswitch/newswitch.github.io/tree/main/examples/go/core-lab)。

实验返回局部构造对象的指针，调用者仍能安全读取。它证明语言层面的生命周期安全，不证明这个具体对象在所有编译配置下必然进行一次堆分配。

## 3. 读取编译器报告

```bash
cd examples/go/core-lab
go build -gcflags='all=-m=2' ./cmd/lab
```

报告中 `escapes to heap`、`moved to heap` 和可内联信息应结合位置阅读。all 会包含依赖和标准库，输出很多；日常定位可缩小包范围。不要把日志格式化导致的临时接口逃逸误判成整个业务对象必须长期存活。

关闭内联后得到的结果不一定代表正常构建。先用真实构建的 allocs 与 heap 证明成本，再用诊断参数解释原因。

## 4. 优化要考虑对象保留

减少一次小分配可能比不上解除一个大 Slice 或闭包对请求对象的长期引用。逃逸描述分配位置，不等于泄漏；可达但已不再需要的对象仍会被保留。

sync.Pool 是临时复用机制，元素可能随时被丢弃，不是可靠缓存。归还含敏感数据或过大容量的 Buffer 前要清理或限制，避免内存和隐私问题。

## 5. 练习与答案

### 5.1 返回局部变量地址会必然悬空吗

不会，Go 会保证合法对象生命周期。

### 5.2 逃逸到堆等于内存泄漏吗

不等于，失去引用后仍可被 GC 回收。

### 5.3 关闭优化后的逃逸报告能代表生产构建吗

不能直接代表，应与正常构建及分配测量交叉验证。
