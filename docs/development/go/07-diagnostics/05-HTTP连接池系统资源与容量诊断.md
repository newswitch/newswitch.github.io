# Go 服务容量诊断：从 P99 到连接池、FD、CPU 和队列

接口慢可能发生在准入、排队、DNS、连接、TLS、数据库、计算或写回任一阶段。容量分析要建立分层时间预算，而不是看到超时就加机器。

## 1. 拆解一条请求

总延迟可以按业务观测拆成入口排队、应用处理、依赖等待和响应传输，但并行子调用有重叠，不能盲目求和。用 Trace 标记关键阶段，并用池指标确认是否在等连接。

例如 CPU 30%、P99 三秒：先看在途请求与队列、DB WaitDuration、HTTP 连接等待、锁和下游分布。CPU 空闲可能意味着等待严重，而不是容量富余。

## 2. 容量估算

稳定系统中平均在途量可用 L≈λW 估算：100 req/s、平均持有 DB 连接 40 ms，平均占用约 4 个连接。这里用平均值，不用 P99 直接代替 W，也不是说池只需要精确四个连接。

峰值、方差、事务混合与数据库可承受并发决定余量。服务扩到十个副本会把总池容量也放大十倍，必须算全局连接预算。

## 3. 诊断顺序

```text
到达率 / 完成率 / 拒绝率
→ Handler 并发与队列
→ DB/HTTP 池等待
→ 下游延迟与错误
→ CPU / GC / 锁 / Goroutine
→ FD / TCP / cgroup throttling / OOM
```

DB.Stats 提供连接与累计等待信息，观察增量而不是把总 WaitDuration 当瞬时耗时。HTTP 客户端可用 httptrace 观察 DNS、连接与首字节等阶段，但要注意连接复用和采样。

Linux 上配合 ss、pidstat、iostat 与容器指标；宿主机“CPU 低”不能替代容器 quota 检查。

## 4. 修复和验收

优先限制无界在途请求，缩短不必要事务，复用连接，修复未关闭 Body/Rows，再按依赖容量调整池。调大队列通常提高等待上限，并不提高真正处理能力。

固定到达率、输入分布和持续时间，比较吞吐、P99、错误率、资源峰值及恢复时间。压测只针对隔离授权环境，服务健康和真实业务正确性都要纳入验收。

## 5. 练习与答案

### 5.1 CPU 低能说明可以继续提高并发吗

不能，可能已被依赖或队列阻塞。

### 5.2 平均连接占用等于建议最大池大小吗

不等于，还需考虑方差、峰值与依赖容量。

### 5.3 增加副本不改变数据库压力吗

会改变总连接和请求并发预算。
