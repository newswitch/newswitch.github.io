# Go 服务容量诊断：从 P99 到连接池、FD、CPU 和队列

服务容量取决于正在执行和正在等待的全部工作。把请求关键路径、平均在途量、连接池等待、背压与取消收敛放在一起分析，才能解释 CPU 不高但 P99 持续变差。

## 1. 先问延迟发生在哪一段

一条请求可能等待入口许可、应用队列、连接池、DNS/TCP/TLS、SQL、CPU 计算或响应写回。总耗时与关键路径有关，并行阶段有重叠，不能把所有 Span 耗时直接相加。

例如入口等待 20 ms，两个并行依赖分别耗时 40 ms 与 80 ms，再串行编码 10 ms，理想化关键路径约为 20+80+10=110 ms，而不是 150 ms。真实还要考虑调度和协议开销；不同请求的各阶段 P99 也不能简单相加得到总 P99。

CPU 30%、P99 三秒只是一组现象。先看完成率、在途量、队列年龄和等待分布，再判断是依赖堵塞、CPU 配额、锁、分配还是准入失控，不要先下“还可以继续加并发”的结论。

## 2. 区分到达、接受、完成和拒绝

| 指标 | 回答的问题 |
| --- | --- |
| 到达率 | 入口实际收到多少请求 |
| 接受率与拒绝率 | 多少工作进入本实例，多少被限流或容量门禁拒绝 |
| 完成率与成功率 | 已接受的工作完成多少，结果是否成功 |
| 在途量与队列年龄 | 还压着多少任务，最老任务等了多久 |
| 活动任务与等待者 | 资源在执行，还是被占在其他等待点 |
| 取消后的剩余任务 | 返回超时后是否仍有工作消耗资源 |

若到达率持续大于完成率，积压会增长；只看当前完成吞吐“很稳定”会漏掉排队膨胀。超时后不退出的后台任务，又会进一步让新的请求与旧任务争夺同一资源。

固定 Worker 或连接池只限制一个环节，不能替代入口准入。每个请求再启动多个依赖调用时，还要算请求到下游的放大系数。

## 3. Little 定律只用于明确边界的稳定平均

在稳定、统计边界一致的系统中，平均在途量 L≈到达率 λ×平均停留时间 W。假设每秒 100 次数据库操作，平均持有连接 40 ms，平均占用约为 4 个连接。

这不是“最大池应该设为 4”：突发、耗时方差、事务组合、管理连接与数据库可承受并发决定余量。也不能把接口 P99 三秒直接代替平均数据库持有时间，二者既不是同一个量，也不一定是同一个阶段。

持续过载时队列不断增长，系统不满足这种稳定平均关系。先恢复受控的接受率，再讨论容量估计。用增加缓冲来延迟拒绝，通常只是提高等待与内存上限。

## 4. 读 DBStats 与 HTTP Trace 的增量

database/sql.DBStats 中，InUse 表示当前借出的连接，Idle 表示可复用连接，WaitCount/WaitDuration 是累计等待信息。比较同一观察窗口的增量，不要把服务启动以来的等待总时长当成一次请求耗时。

ΔWaitDuration/ΔWaitCount 可作为窗口等待的近似线索，但计数与耗时累积的时点不同，跨窗口或仍在等待的请求会影响解释。还要关联持有连接的事务、Rows、调用栈和请求预算。

HTTP 端可结合 httptrace 的 GetConn/GotConn、DNS、Connect、TLS 与首字节事件。复用连接不会每次重新出现 DNS/TCP/TLS，因此不能把缺少建连事件读成“请求没有发出”；要看完整事件组合与服务端计数。

## 5. 用两个真实实验区分池等待与慢执行

```bash
cd examples/go/core-lab
go run ./cmd/mechanism-lab -mode http-client
```

这个 HTTP/1.1 单连接实验中，第二个响应正文被持有，后续请求触发 GetConn 但没有 GotConn，预算到期时服务端累计请求仍为 2。它还没进入服务端，不能归因于慢 Handler。正文释放并正常消费后，连接与请求恢复。

```bash
cd ../../gin/service-lab
go test ./internal/app -run TestPoolWaitDiagnosisAndRecovery -v -count=1
```

SQLite 对照用唯一连接制造明确等待，核心输出为：

```text
held-connection: status=504 wait-count-delta=1 in-use=1
after-close: status=200 in-use=0 permits=0
```

SQL 还没有执行也会超时。两个实验验证等待层与资源归还，不是在本机测出了一条生产 P99，也不能替代真实数据库服务端指标。

## 6. 把容量控制和取消收敛一起验收

```bash
cd examples/go/core-lab
go run ./cmd/lifecycle-lab -mode pipeline
cd ../../gin/service-lab
go test ./internal/requestflow -run TestGinDeadline -v -count=1
```

流水线检查固定活动上限、有限队列和返回时 active=0；Gin 对照表明同样返回 504，后台活动量可以分别是 1 或 0。超时率下降而后台积压继续增长，不能算容量治理完成。

增加副本也要重新计算全局预算。例如 10 个实例各配 20 个数据库连接，仅 API 就可能建立 200 个连接，还没算独立 Worker、迁移任务与管理工具。应用扩容可能把瓶颈转移到数据库，而不是消除它。

## 7. 把 Go 等待和操作系统资源对应起来

CPU 热点用 CPU profile；大量分配与保留用 alloc/heap；锁与 Channel 等待用 Mutex/Block；具体调度与网络等待顺序用 trace。聚合热点说明时间花在哪里，但不能单独解释调用者为何增加。

Linux 上再关联进程 FD 数、连接状态、重传、cgroup CPU throttling、内存事件与 OOM。宿主机总体 CPU 低，不能替代容器配额检查；大量网络等待也可能只是正常空闲长连接，仍需业务状态区分。

不要为了“监控更全”无节制开启昂贵采样。先按问题缩小采集范围，控制采样持续时间，并把管理接口与业务入口隔离。

## 8. 修复要形成同输入下的对照

先修复无界在途量、未关闭 Body/Rows、过长事务和取消不收敛，再依据下游能力调整并发与池上限。队列满时明确有限等待、拒绝还是持久化，不能用后台 Goroutine 无限兜底。

对照固定输入分布、到达方式、持续时间与外部依赖，比较完成吞吐、延迟分布、错误与拒绝、资源峰值和负载回落后的恢复时间。闭环压测在服务变慢时可能自己降低到达率，因此还要核对实际到达量，不能只看配置的并发数。

一个有效修复要同时保持结果语义，并证明资源能收敛；不是只让某个平均值变好。

## 9. 练习与答案

### 9.1 接口 P99 是三秒，可以用 100 req/s×3s 推算数据库需要 300 个连接吗

不能。Little 定律使用稳定平均与一致统计边界，接口 P99 不是平均数据库连接持有时间；直接套用会高估或误判。

### 9.2 连接池已经限为 4，为什么内存还会持续增长

等待这 4 个连接的请求、Goroutine 和缓冲仍可能没有上限。连接数约束不等于入口或队列有界。

### 9.3 超时率不再升高，可以认为容量恢复了吗

还要看后台活动数、完成率、队列年龄、连接归还以及负载下降后的恢复。如果超时只是让调用者离开，旧工作继续运行，系统仍可能恶化。
