# 装饰器、包装函数与执行时机

装饰器把一个函数对象交给另一个可调用对象，再把处理结果绑定回原名称。它可以返回包装函数，也可以返回原函数或其他可调用对象；`@` 不是“框架专属语法”。

## 1. 定义时与调用时

`@audit` 放在 `def work` 前面，大致等价于先定义函数，再执行 `work = audit(work)`。装饰器内部创建包装函数的代码在定义阶段运行；包装函数体则在以后调用时运行。

多个装饰器从靠近函数的那层开始组合：`@outer`、`@inner` 相当于 `outer(inner(function))`。实际调用的进入与退出顺序，应按包装关系逐层展开。

## 2. 完整实验

```python title="objects_decorator.py"
from functools import wraps

def traced(label):
    def decorate(function):
        @wraps(function)
        def wrapper(*args, **kwargs):
            print("enter", label)
            try:
                return function(*args, **kwargs)
            finally:
                print("exit", label)
        return wrapper
    return decorate

@traced("outer")
@traced("inner")
def add(first, second):
    """Add two values."""
    return first + second

def main():
    print(add(2, 3))
    print(add.__name__)
    print(add.__wrapped__.__name__)

if __name__ == "__main__":
    main()
```

```text title="objects_decorator.out"
enter outer
enter inner
exit inner
exit outer
5
add
add
```

`finally` 使包装层在正常返回或异常传播时都执行退出动作，但这里没有吞掉异常。`wraps` 保留有用的元数据并设置 `__wrapped__`，让文档、诊断与部分签名工具能够追到原函数；它不会使所有运行行为自动与原函数等价。

## 3. 参数、状态和副作用

带参数的装饰器通常多一层工厂：先用 `traced("outer")` 创建装饰器，再用它包装函数。闭包里保存的是对象引用，若捕获可变配置，后来修改也可能影响调用。

记录耗时应使用单调计时；记录参数要考虑 Secret、个人信息和超大对象，不要无条件把 `args` 全部写进日志。重试装饰器更需要定义幂等性、次数和总 Deadline，不能把异常一律重做。

## 4. 同步与异步不能随意套用

给 `async def` 套一个普通同步 wrapper，并在里面直接返回协程，测到的可能只是创建协程的时间，而不是实际工作时间。正确的异步包装通常也需要 `async def` 和 `await`。

框架会通过签名、类型或可调用对象性质决定如何处理函数。装饰器改变这些信息，可能影响依赖解析、线程池分派和错误栈；`wraps` 很重要，但仍应通过框架级测试证明契约。

缓存装饰器也有状态归属：缓存键是否包含租户，结果是否可变，内存是否有上限，进程重启与多 Worker 是否共享。不能把一个 `cache` 标记当成分布式缓存系统。

### 4.1 异步包装的正确等待位置

下面是包装协程函数的核心实现，不自动重试，也不记录参数内容：

```python
from functools import wraps
from time import perf_counter

def measured_async(function):
    @wraps(function)
    async def wrapper(*args, **kwargs):
        started = perf_counter()
        try:
            return await function(*args, **kwargs)
        finally:
            print("elapsed:", perf_counter() - started)
    return wrapper
```

调用 wrapper 只创建协程；等待 wrapper 才进入计时，里面 await 原函数，最后记录成功、失败或取消路径的耗时。若省掉 await，finally 会在返回协程对象时就执行，真正工作还没开始。对于生成器和异步生成器，还要按每次推进与关闭设计包装，不能直接照搬这个协程模板。

框架路由装饰器的顺序也很重要。`@router.get` 在外、`@measured_async` 在内时，路由注册的是包装结果；顺序反过来，路由可能已经保存原函数，而名称后来才被替换。应观察路由保存的 endpoint 并用请求测试确认，而不是只看模块里的函数名。

将包装后的函数交给 inspect.signature，观察 wraps 提供的 __wrapped__ 如何帮助还原签名；再去掉 wraps，观察参数可能只剩 args/kwargs。静态类型层使用 ParamSpec 保留参数关系，运行时层保留签名与协程行为，两层缺一不可。

## 5. 练习与答案

### 5.1 装饰器里的所有代码都在每次请求执行吗？

答案：不是。工厂与装饰过程通常在定义时运行，wrapper 的函数体才在调用时运行。导入阶段创建连接的副作用不会因为使用装饰器就变安全。

### 5.2 wraps 会自动处理异常和重试吗？

答案：不会。它主要保留元数据和包装关系；异常、取消、重试与资源释放仍由包装实现负责。

### 5.3 同步 wrapper 直接返回异步函数的结果，能准确记录耗时吗？

答案：通常不能。它可能只记录到协程对象创建完成。需要等待协程实际执行，并区分成功、异常和取消。
