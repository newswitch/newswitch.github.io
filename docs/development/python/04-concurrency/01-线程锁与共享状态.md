# 线程、锁与共享状态

线程共享进程地址空间，因此通信方便，也容易共享到不该共享的可变状态。GIL 不是业务锁，不能保证“读取、判断、更新”这一整段逻辑原子完成。

## 1. 线程的状态与责任

`Thread.start` 安排线程运行，`join` 等待结束，不会自动传播目标函数异常或强制停止线程。需要结果与异常时，Future 通常比手工管理线程更清晰。

取消应通过 Event 等协作信号，等待点还需要超时或可唤醒机制。daemon 线程可能在进程退出时被直接终止，不适合承担必须提交与清理的工作。

## 2. 锁保护不变量

```python title="concurrency_threads.py"
from threading import Lock, Thread

def main():
    state = {"count": 0}
    lock = Lock()

    def increment():
        for _ in range(1000):
            with lock:
                state["count"] += 1

    workers = [Thread(target=increment) for _ in range(4)]
    for worker in workers:
        worker.start()
    for worker in workers:
        worker.join(timeout=5)
    if any(worker.is_alive() for worker in workers):
        raise RuntimeError("worker did not stop")
    print(state["count"])

if __name__ == "__main__":
    main()
```

```text title="concurrency_threads.out"
4000
```

这里锁保护完整的计数更新。不能把本机某次不加锁仍得到 4000，作为代码无竞态的证明；字节码、解释器版本和调度都可能改变观察结果。

## 3. 临界区的大小

临界区应覆盖需要共同保持一致的状态，但尽量不要持锁调用网络或用户回调，否则会把慢操作传染给其他线程。多个锁要约定全局获取顺序，防止 A 等 B、B 等 A。

RLock 支持同一线程重入，不会自动防止不同锁间死锁。Condition 用于“等待某个状态条件”，需要在锁内循环检查谓词；被唤醒不等于条件一定仍成立。

跨线程传递消息可用 Queue，减少共享状态范围。容器的某个单独操作即使受实现保护，也不表示多个操作组成的业务事务安全。

## 4. 错误与资源边界

每个线程的连接、事务和上下文要明确归属。不要跨线程随意共享不支持并发使用的 Session；线程局部数据也需要在线程复用时清理。

定位挂起时，获取自有进程的线程堆栈，区分锁等待、外部 I/O 与任务死循环。提高线程数只可能让争用、连接数和内存更糟。

## 5. 练习与答案

### 5.1 有 GIL，count += 1 就能当作业务原子更新吗？

答案：不能将其作为跨实现和跨版本同步契约。需要用锁或消息模型维护完整业务不变量。

### 5.2 join 超时，会杀掉线程吗？

答案：不会，只结束等待。必须检查线程是否仍存活，并设计工作自身能响应的停止信号。

### 5.3 为什么不持锁完成所有网络请求？

答案：这样会把不可控等待放进临界区，扩大尾延迟与死锁风险。通常先取必要状态，释放锁后 I/O，再按版本/条件提交结果。
