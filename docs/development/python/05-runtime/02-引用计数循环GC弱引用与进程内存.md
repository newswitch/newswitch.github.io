# 引用计数、循环 GC、弱引用与进程内存

对象不再使用、对象被回收、分配器释放内存、操作系统 RSS 下降，是四个不同事件。内存排障先确认指标口径，再判断哪个阶段没有按预期发生。

## 1. 引用与循环

常规 CPython 广泛使用引用计数，并借助循环 GC 处理部分循环引用。类型、构建方式和不可朽对象等机制会影响细节，不能把“每个对象引用数变零就立刻所有资源归还”当成跨实现规范。

`del` 删除绑定，不是直接释放对象。文件与连接仍应明确关闭，而不是把资源安全寄托在回收时机。

## 2. 循环与弱引用实验

```python title="runtime_memory.py"
import gc
import tracemalloc
import weakref

class Node:
    pass

def main():
    node = Node()
    node.self_reference = node
    observed = weakref.ref(node)
    del node
    gc.collect()
    print("collected:", observed() is None)
    tracemalloc.start()
    values = [bytearray(1024) for _ in range(10)]
    current, peak = tracemalloc.get_traced_memory()
    print("tracked:", current > 0, peak >= current)
    del values
    tracemalloc.stop()

if __name__ == "__main__":
    main()
```

```text title="runtime_memory.out"
collected: True
tracked: True True
```

弱引用本身不延长普通对象寿命；不是所有类型都支持弱引用。它适合缓存与观察某些对象，但读取时仍要处理对象已经消失的情况。

## 3. 为什么 RSS 不下降

Python 对象回收后，分配器可能保留 arena/pool 供后续使用；原生库也可能拥有独立内存池。碎片、线程栈、mmap、共享页和外部扩展都会影响进程内存。

tracemalloc 主要跟踪它能观察到的 Python 分配，不等于完整 native/GPU 内存。对比快照可以找分配增长位置，但还需结合 RSS、原生分配与对象可达链路。

## 4. 排障顺序

固定负载与数据规模，观察多轮预热后的趋势；区分一次性缓存增长、工作集稳定与持续无界增长。再检查全局容器、LRU、闭包、Task、Traceback 与连接返回路径。

手动频繁 `gc.collect` 不是普遍修复，还可能增加停顿。调整阈值前应取得回收耗时与实际回收量证据，避免把分配压力或原生缓存误诊为循环垃圾问题。

## 5. 练习与答案

### 5.1 del 一个变量，为什么对象可能仍在？

答案：其他名称、容器、闭包或帧仍可能引用它。del 只去掉当前绑定。

### 5.2 tracemalloc 稳定但 RSS 上升，能排除泄漏吗？

答案：不能。增长可能位于原生库、线程、映射或它未覆盖的分配路径，需要补充对应证据。

### 5.3 gc.collect 后 RSS 不降，说明 GC 失效吗？

答案：不一定。对象回收与分配器向 OS 归还内存是不同层次，也可能存在仍可达的缓存。
