# 时间点、时区、时间戳与耗时测量

“现在几点”和“过去了多久”是不同问题。系统校时可能改变墙上时间，因此不能直接用两个本地时间相减实现可靠超时。

## 1. 三种时间模型

| 模型 | 用途 | 注意事项 |
| --- | --- | --- |
| UTC 时间点 | 日志、存储、跨系统关联 | 保留精度与来源 |
| 本地民用时间 | 展示、预约、日历规则 | 时区、夏令时与歧义 |
| 单调计时 | 超时、耗时、Deadline | 一般不能持久化为跨机器时间点 |

`datetime` 分 naive 与 aware。naive 缺少足够时区上下文，不要假设所有库都把它当 UTC。优先显式使用 `datetime.now(UTC)`。

## 2. 转换示例

```python title="io_time.py"
from datetime import UTC, datetime, timedelta, timezone
from time import monotonic

def main():
    moment = datetime(2026, 10, 20, 0, 0, tzinfo=UTC)
    east_eight = timezone(timedelta(hours=8))
    local = moment.astimezone(east_eight)
    print(moment.isoformat())
    print(local.isoformat())
    print(moment == local)
    deadline = monotonic() + 3.0
    remaining = deadline - monotonic()
    print(0 < remaining <= 3.0)

if __name__ == "__main__":
    main()
```

```text title="io_time.out"
2026-10-20T00:00:00+00:00
2026-10-20T08:00:00+08:00
True
True
```

示例使用固定偏移，不依赖机器时区数据库；真实地区规则应使用 `ZoneInfo` 与 IANA 名称，Windows 等环境可能需要安装 `tzdata`。固定 UTC+8 并不代表所有地区历史和未来规则。

## 3. 转换不等于替换标签

`astimezone` 保持同一时间点，改变展示时区；`replace(tzinfo=...)` 通常只是重新附加解释标签，不能用来随意把一个本地时间转换成 UTC。

夏令时回拨会让某些本地时刻出现两次，前拨会让某些时刻不存在。预约系统需要保存地区时区及消歧规则，不能只存 `2026-... 01:30` 这种无上下文文本。

时间戳也必须标单位：秒、毫秒、微秒混淆会产生千倍误差；浮点时间戳可能损失精度。JSON、数据库与日志格式应统一。

## 4. Deadline 与预算

用 `monotonic` 或适当的高分辨率单调时钟计算本机剩余预算，再把预算分配给连接、重试与处理。每次重试重新给三秒，会把一个三秒请求拉长成多次三秒。

跨进程/机器传递 Deadline 需要明确时钟语义与时钟偏差，不能把某台机器的单调计数直接发给另一台解释。

## 5. 练习与答案

### 5.1 系统时钟回拨，会让 monotonic 倒退吗？

答案：单调时钟用于避免此类墙上时间调整影响；仍要了解目标平台对休眠等行为的定义，不把它当 UTC 时间。

### 5.2 给 naive 时间 replace UTC，就完成本地转 UTC 了吗？

答案：没有。那通常是重新贴标签。先知道原时区，再用正确的转换规则保持同一时间点。

### 5.3 重试三次，每次 timeout 三秒，总耗时最多三秒吗？

答案：不是，可能叠加等待与退避。需要一个总 Deadline，各阶段只能消费剩余预算。
