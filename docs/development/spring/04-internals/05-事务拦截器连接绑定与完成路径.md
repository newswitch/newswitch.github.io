# 事务拦截器、连接绑定与完成路径

`@Transactional` 不会直接向数据库发送 BEGIN。它先让代理中的事务拦截器解析事务属性，交给事务管理器决定开启、加入或挂起，再让业务 SQL 使用正确资源。最终数据是否提交，还取决于传播状态、回滚规则和数据库结果。

本篇讨论普通同步 JDBC 与 `DataSourceTransactionManager`，不把线程绑定实现套到响应式事务或分布式事务上。

## 1. 从注解到真正的数据库动作

![事务拦截器、线程资源与 JDBC 连接的关系](/img/development/transaction-binding.svg)

图把代理上下文、线程资源和数据库动作分开；它们协作，但不是同一个对象或同一份全局状态。

```text
代理中的 TransactionInterceptor
→ TransactionAspectSupport.invokeWithinTransaction
→ 解析 TransactionAttribute，选择事务管理器
→ getTransaction：创建或参与事务
→ 调用后续拦截器和目标方法
→ 根据返回、异常与 rollback-only 决定完成方式
→ 管理器执行实际提交/回滚并清理资源
```

[TransactionInterceptor](https://github.com/spring-projects/spring-framework/blob/v7.0.9/spring-tx/src/main/java/org/springframework/transaction/interceptor/TransactionInterceptor.java) 是代理链中的入口，[TransactionAspectSupport](https://github.com/spring-projects/spring-framework/blob/v7.0.9/spring-tx/src/main/java/org/springframework/transaction/interceptor/TransactionAspectSupport.java) 组织属性解析、业务调用与完成。传播行为不由代理类名决定，而由事务属性与管理器已有状态共同决定。

## 2. 三种状态不能混为一个 ThreadLocal

| 状态 | 用来做什么 | 不等于什么 |
| --- | --- | --- |
| 拦截器的 TransactionInfo | 保存当前切点与事务调用上下文，支持嵌套恢复 | 数据库连接本身 |
| TransactionStatus | 记录新事务、参与、完成与 rollback-only 等状态 | 当前数据源的全部连接池状态 |
| 同步管理器绑定的资源 | 让协作组件取得线程上的连接等资源 | 任意线程都能共享这个事务 |

在 JDBC 路径中，事务管理器取得或复用连接，为适当事务关闭自动提交，并按数据源资源键绑定连接。`JdbcTemplate` 通过协作式获取路径使用它，而不是任意 new 一个 Connection 自动加入事务。

连接相关逻辑可对照 [DataSourceTransactionManager](https://github.com/spring-projects/spring-framework/blob/v7.0.9/spring-jdbc/src/main/java/org/springframework/jdbc/datasource/DataSourceTransactionManager.java) 与 [DataSourceUtils](https://github.com/spring-projects/spring-framework/blob/v7.0.9/spring-jdbc/src/main/java/org/springframework/jdbc/datasource/DataSourceUtils.java)。换数据源、换线程或直接绕开协作获取，都需要重新分析资源归属。

## 3. 正常返回也不保证物理提交

新事务与参与事务的完成不同：参与者正常退出可能只是结束这一层调用，物理提交仍由外层负责。全局 rollback-only 还可能使外层正常返回时得到 UnexpectedRollbackException。

异常路径也不是“只要抛异常就回滚”。默认规则与自定义 rollbackFor/noRollbackFor 共同决定；普通默认配置下，运行时异常和 Error 会触发回滚，受检异常通常不会。应用也可以配置更广的默认规则，因此排查应读取实际属性。

事务完成模板可定位 [AbstractPlatformTransactionManager](https://github.com/spring-projects/spring-framework/blob/v7.0.9/spring-tx/src/main/java/org/springframework/transaction/support/AbstractPlatformTransactionManager.java)。它组织同步回调、提交回滚和清理，具体管理器才完成对应资源动作。

## 4. 两种 cleanup 的时机不同

`cleanupTransactionInfo()` 恢复拦截器的调用上下文；它不是“连接已归还”的同义词。在同步正常分支，业务调用退出后先恢复这一上下文，随后还会进入提交逻辑。

数据库连接解绑、状态恢复、释放和挂起资源恢复，则属于管理器完成路径。若只在第一个 cleanup 打断点就断言事务已经提交，会把源代码读错。

此外，提交本身也会失败。业务方法正常返回，只证明目标代码完成；最终调用方仍可能收到提交异常。不能在事务内提前对外宣告一个尚未提交的结果。

## 5. 实验：真实 SQL 与管理器回调

使用独立 H2 内存库和有界连接池，不连接已有数据库。池由 Spring 在关闭上下文时 dispose；内存库不设置永久保留，最后连接关闭后可以释放。

<details>
<summary>提交、回滚、绑定与清理实验</summary>

```java title="src/main/java/demo/internals/transaction/TransactionPathDemo.java"
package demo.internals.transaction;

import org.h2.jdbcx.JdbcConnectionPool;
import org.springframework.context.annotation.*;
import org.springframework.jdbc.core.JdbcTemplate;
import org.springframework.jdbc.datasource.DataSourceTransactionManager;
import org.springframework.transaction.annotation.*;
import org.springframework.transaction.support.*;
import javax.sql.DataSource;
import java.util.*;

public final class TransactionPathDemo {
    public static class Trace { public final List<String> events = new ArrayList<>(); }
    public static class Manager extends DataSourceTransactionManager {
        private final Trace trace;
        public Manager(DataSource dataSource, Trace trace) { super(dataSource); this.trace = trace; }
        @Override protected void doBegin(Object transaction, org.springframework.transaction.TransactionDefinition definition) {
            super.doBegin(transaction, definition); trace.events.add("begin");
        }
        @Override protected void doCommit(DefaultTransactionStatus status) {
            super.doCommit(status); trace.events.add("commit");
        }
        @Override protected void doRollback(DefaultTransactionStatus status) {
            super.doRollback(status); trace.events.add("rollback");
        }
        @Override protected void doCleanupAfterCompletion(Object transaction) {
            try { super.doCleanupAfterCompletion(transaction); } finally { trace.events.add("cleanup"); }
        }
    }
    public static class Work {
        private final JdbcTemplate jdbc; private final Trace trace;
        public Work(JdbcTemplate jdbc, Trace trace) { this.jdbc = jdbc; this.trace = trace; }
        @Transactional public void write(String name, boolean fail) {
            trace.events.add("body:" + TransactionSynchronizationManager.isActualTransactionActive());
            jdbc.update("insert into entries(entry_name) values (?)", name);
            if (fail) throw new IllegalStateException("failed");
        }
        @Transactional public void checked() throws Exception {
            jdbc.update("insert into entries(entry_name) values (?)", "checked");
            throw new Exception("checked failure");
        }
    }
    @Configuration(proxyBeanMethods = false) @EnableTransactionManagement
    public static class Config {
        @Bean public Trace trace() { return new Trace(); }
        @Bean(destroyMethod = "dispose") public JdbcConnectionPool dataSource() {
            var pool = JdbcConnectionPool.create("jdbc:h2:mem:source-tx;DB_CLOSE_DELAY=0;LOCK_TIMEOUT=500", "sa", "");
            pool.setMaxConnections(4); return pool;
        }
        @Bean public JdbcTemplate jdbc(DataSource dataSource) {
            var jdbc = new JdbcTemplate(dataSource);
            jdbc.execute("create table entries(entry_name varchar(40))"); return jdbc;
        }
        @Bean public Manager transactionManager(DataSource dataSource, Trace trace) { return new Manager(dataSource, trace); }
        @Bean public Work work(JdbcTemplate jdbc, Trace trace) { return new Work(jdbc, trace); }
    }
    public static void main(String[] args) {
        try (var context = new AnnotationConfigApplicationContext(Config.class)) {
            var work = context.getBean(Work.class); var trace = context.getBean(Trace.class);
            work.write("ok", false); System.out.println("commit=" + String.join(",", trace.events));
            trace.events.clear();
            try { work.write("failed", true); } catch (IllegalStateException expected) { }
            System.out.println("rollback=" + String.join(",", trace.events));
            System.out.println("rows=" + context.getBean(JdbcTemplate.class).queryForList("select entry_name from entries", String.class));
            System.out.println("afterCallActive=" + TransactionSynchronizationManager.isActualTransactionActive());
            System.out.println("boundConnection=" + TransactionSynchronizationManager.hasResource(context.getBean(DataSource.class)));
        }
    }
}
```

</details>

运行 `demo.internals.transaction.TransactionPathDemo`：

```text title="expected-output"
commit=begin,body:true,commit,cleanup
rollback=begin,body:true,rollback,cleanup
rows=[ok]
afterCallActive=false
boundConnection=false
```

这组日志记录管理器覆盖点，不冒充所有同步回调的完整顺序。数据只留下 ok 是提交/回滚的独立证据，调用后两个 false 则验证线程事务状态与绑定资源已释放。

## 6. 按症状回到对应状态

方法执行但没有事务：检查代理、属性来源、传播和线程。事务有活动标志但 SQL 不受控制：检查数据源与实际连接获取路径。返回后连接池耗尽：检查资源是否被其他路径持有、是否有长事务或异常清理问题。

提交后事件、审计和外部通知需要另外分析。`AFTER_COMMIT` 并不会把外部动作纳入已完成的数据库事务，相关可靠性边界见[编程式事务与提交后动作](../02-aop-transactions/07-编程式事务事务事件与提交后动作.md)。

## 7. 练习与答案

### 7.1 cleanupTransactionInfo 执行后，是否能断言连接已归还

不能。它恢复的是拦截器上下文。连接解绑、状态恢复和释放由事务管理器的完成清理负责，应检查具体资源状态。

### 7.2 受检异常离开方法，为什么记录仍可能提交

普通默认回滚规则通常不包含所有受检异常。应检查实际事务属性、自定义规则与 rollback-only，而不是把异常类型全部视为相同处理。

### 7.3 两个不同线程里访问同一个 DataSource，是否自动属于一个 JDBC 事务

不自动属于。这里的资源按线程和数据源键绑定。跨线程调用需要重新设计事务边界，不能把同一个 DataSource 实例当成事务共享令牌。
