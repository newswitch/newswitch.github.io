# 自调用、异常与线程事务边界

所谓“事务失效”可能是三种不同情况：根本没有进入事务边界；进入了，但回滚规则与预期不同；事务确实执行，却操作了另一个资源。先分类，再决定如何修改。

本篇讨论 Spring 命令式代理事务与 JDBC；响应式事务使用 Reactor Context 等不同机制，不能把线程绑定结论无条件推广。

## 1. 四个检查点

| 检查点 | 应取得的证据 |
| --- | --- |
| 调用入口 | 拿到的是容器代理，还是原始对象/手动 new |
| 方法匹配 | 注解、可见性、代理机制、切点与最终属性 |
| 退出结果 | 哪个异常离开了拦截边界，是否已标 rollback-only |
| 资源和线程 | 哪个管理器、哪个 DataSource、哪个执行上下文 |

`isActualTransactionActive()` 是有用观察，但只能描述当前协调状态，不能单独证明每条 SQL 都用了正确连接；仍要查询最终数据。[注解事务边界](https://docs.spring.io/spring-framework/reference/data-access/transaction/declarative/annotations.html)

## 2. 将几种现象放在同一实验里

```java title="src/main/java/demo/tx/boundaries/BoundaryDemo.java"
package demo.tx.boundaries;

import java.io.IOException;
import java.util.concurrent.Executors;
import java.util.concurrent.TimeUnit;
import demo.tx.support.LabDatabase;
import demo.tx.support.TxInfrastructure;
import org.springframework.context.annotation.AnnotationConfigApplicationContext;
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;
import org.springframework.context.annotation.Import;
import org.springframework.transaction.annotation.Transactional;
import org.springframework.transaction.support.TransactionSynchronizationManager;

public class BoundaryDemo {
    public static class Service {
        private final LabDatabase database;
        public Service(LabDatabase database) { this.database = database; }
        @Transactional public boolean probe() { return TransactionSynchronizationManager.isActualTransactionActive(); }
        public boolean selfProbe() { return probe(); }
        @Transactional public boolean threadProbe() throws Exception {
            var executor = Executors.newSingleThreadExecutor();
            try {
                return executor.submit(TransactionSynchronizationManager::isActualTransactionActive).get(3, TimeUnit.SECONDS);
            } finally {
                executor.shutdownNow();
                if (!executor.awaitTermination(3, TimeUnit.SECONDS)) throw new IllegalStateException("worker did not stop");
            }
        }
        @Transactional public void checkedDefault() throws IOException {
            database.insert(1, "checked"); throw new IOException("checked failure");
        }
        @Transactional(rollbackFor = IOException.class) public void checkedRollback() throws IOException {
            database.insert(2, "checked"); throw new IOException("checked failure");
        }
        @Transactional public void swallowed() {
            database.insert(3, "swallowed");
            try { throw new IllegalStateException("local failure"); } catch (IllegalStateException expected) { }
        }
    }
    @Configuration(proxyBeanMethods = false) @Import(TxInfrastructure.class)
    public static class Config {
        @Bean Service service(LabDatabase database) { return new Service(database); }
    }
    public static void main(String[] args) throws Exception {
        try (var context = new AnnotationConfigApplicationContext(Config.class)) {
            LabDatabase database = context.getBean(LabDatabase.class);
            Service service = context.getBean(Service.class);
            System.out.println("proxy=" + service.probe());
            System.out.println("self=" + service.selfProbe());
            System.out.println("manual=" + new Service(database).probe());
            System.out.println("thread=" + service.threadProbe());
            try { service.checkedDefault(); } catch (IOException expected) { }
            System.out.println("checkedDefaultRows=" + database.count());
            database.clear();
            try { service.checkedRollback(); } catch (IOException expected) { }
            System.out.println("checkedRollbackRows=" + database.count());
            service.swallowed();
            System.out.println("swallowedRows=" + database.count());
            System.out.println("resourceAfter=" + TransactionSynchronizationManager.hasResource(database.dataSource()));
        }
    }
}
```

使用[公共工程和支持类](./03-事务管理器连接与提交回滚.md)，运行主类 `demo.tx.boundaries.BoundaryDemo`：

```text title="expected-output"
proxy=true
self=false
manual=false
thread=false
checkedDefaultRows=1
checkedRollbackRows=0
swallowedRows=1
resourceAfter=false
```

每种结果都对应一个不同原因，不应该全部归咎于“Spring 没扫描到注解”。新线程只做状态观察，任务有等待上限，执行器在 finally 中关闭，不会留下常驻线程。

## 3. 自调用不是“里面一定没有事务”

本例 selfProbe 本身没有事务，所以其内部 probe 不经代理时看到 false。如果外层已经有事务，自调用中的 SQL 仍可能加入现有资源；失去的是内层注解独立应用的机会，例如 REQUIRES_NEW、超时或回滚规则并未按预期生效。

优先拆分独立协作者或用明确 TransactionTemplate 边界。不要用无条件自注入、AopContext 或字段注入来掩盖职责循环，再把偶然运行当成正确设计。

## 4. checked exception 和吞异常要分别看

默认规则未配置为全部异常回滚时，普通 checked exception 可以导致“方法抛错但数据已提交”。rollbackFor 可以表达需要的规则；按类型声明比宽泛字符串匹配更容易审查。

swallowed 捕获的是本方法里的普通业务异常，没有让事务拦截器看到失败，所以本例提交。它不意味着吞掉任何数据库异常都一定能提交：资源可能已失败，或另一个参与者已经标记 rollback-only。

日志切面转换异常也可能改变规则。应检查穿过最外事务边界的最终异常，而不是只看目标方法某一行 throw。

## 5. 新线程为什么不继承 JDBC 事务

命令式资源绑定通常属于当前执行线程。Executor、异步方法、CompletableFuture 或新虚拟线程，不会自动继承同一 JDBC 事务。在线程里通过另一个事务代理调用，可以建立那条线程自己的事务，但不是让原事务变成跨线程共享连接。

也不应手动复制 Spring 的资源绑定对象到子线程，让多个线程同时操作原连接。需要并行工作时，先明确各自提交、失败汇合和业务一致性协议。

## 6. 多管理器与超时带来的错觉

多个 DataSource 或多个事务管理器时，要明确注解选择和实际客户端使用的资源。管理器 A 开了事务，客户端 B 不会仅因同线程而自动加入。

timeout 不代表任意耗时方法会被强制终止。方法运行、SQL 执行、连接获取、锁等待和远程调用各自可能有不同计时与取消机制；应看实际异常产生阶段及最后资源状态。

## 7. 排查时先观察，再修改

确认实际 Bean 和代理；记录事务进入/退出及线程；核对管理器、DataSource、连接和 SQL；查询提交后数据；最后针对证据修改结构或属性。

不要为了看到回滚就一律 `rollbackFor=Exception.class`，也不要为了避免异常就一律 REQUIRES_NEW。前者是错误语义选择，后者会改变原子性和资源占用，必须符合业务契约。

## 8. 练习与答案

### 8.1 SelfProbe 返回 false，把 probe 改成 public 能修复吗

本例 probe 已经是 public。问题是内部调用没有穿过代理，不是可见性；应调整调用边界。

### 8.2 外层方法抛 IOException，为什么数据库仍多了一行

默认规则下普通 checked exception 不自动要求回滚。需确认规则与资源状态，按业务明确 rollbackFor 或编程式状态。

### 8.3 把线程池换成虚拟线程，是否能共享原 JDBC 事务

不会自动共享。线程成本与事务上下文传播是两件事，仍须定义每个执行单元的事务边界。
