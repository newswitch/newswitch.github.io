# 编程式事务、事务事件与提交后动作

有时事务只应包住一小段数据库写入，而不应覆盖前后的远程调用。TransactionTemplate 允许明确表达这段边界；事务事件则让监听与提交/回滚阶段关联。但“提交后触发一次回调”不等于“可靠发送一条消息”。

## 1. 声明式与编程式怎样选择

声明式适合清晰的服务方法边界；编程式适合需要在同一流程中明确划分短事务、检查结果或主动标记回滚的情况。两者仍使用相应事务管理器，不因 API 不同而改变资源原子性的范围。

TransactionTemplate 的回调内使用 status.setRollbackOnly 可要求回滚；回调返回值也不是已经独立持久化的证明，模板还要完成提交或参与外层事务。传播配置仍然适用。[编程式事务](https://docs.spring.io/spring-framework/reference/data-access/transaction/programmatic.html)

## 2. 事务同步阶段各意味着什么

| 阶段 | 适合理解为 | 不能推导 |
| --- | --- | --- |
| BEFORE_COMMIT | 提交前的相应通知 | 最后一定提交成功 |
| AFTER_COMMIT | 已经完成提交后的通知 | 此时异常还能撤销原提交 |
| AFTER_ROLLBACK | 回滚后的相应通知 | 所有外部副作用都被撤销 |
| AFTER_COMPLETION | 事务结束后的状态通知 | 可继续把任意新写入加入已结束事务 |

TransactionSynchronization 提供更底层的回调协议；TransactionalEventListener 把事件匹配与事务阶段组合起来。默认阶段为 AFTER_COMMIT，没有事务时默认不执行，除非明确配置 fallbackExecution。[事务事件](https://docs.spring.io/spring-framework/reference/data-access/transaction/event.html)

## 3. 提交后持久化审计，使用新的事务边界

```java title="src/main/java/demo/tx/completion/CompletionDemo.java"
package demo.tx.completion;

import java.util.ArrayList;
import java.util.List;
import demo.tx.support.LabDatabase;
import demo.tx.support.TxInfrastructure;
import org.springframework.context.annotation.AnnotationConfigApplicationContext;
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;
import org.springframework.context.annotation.Import;
import org.springframework.transaction.annotation.Propagation;
import org.springframework.transaction.annotation.Transactional;
import org.springframework.transaction.event.TransactionPhase;
import org.springframework.transaction.event.TransactionalEventListener;
import org.springframework.transaction.support.TransactionTemplate;

public class CompletionDemo {
    public record Completed(int id) { }
    public static class EventLog { public final List<String> events = new ArrayList<>(); }
    public static class AuditWriter {
        private final LabDatabase database;
        public AuditWriter(LabDatabase database) { this.database = database; }
        @Transactional(propagation = Propagation.REQUIRES_NEW)
        public void write(int id) { database.insert(100 + id, "audit"); }
    }
    public static class Listener {
        private final EventLog log;
        private final AuditWriter writer;
        public Listener(EventLog log, AuditWriter writer) { this.log = log; this.writer = writer; }
        @TransactionalEventListener(phase = TransactionPhase.AFTER_COMMIT)
        public void committed(Completed event) {
            log.events.add("afterCommit:" + event.id());
            writer.write(event.id());
        }
    }
    @Configuration(proxyBeanMethods = false) @Import(TxInfrastructure.class)
    public static class Config {
        @Bean EventLog eventLog() { return new EventLog(); }
        @Bean AuditWriter auditWriter(LabDatabase database) { return new AuditWriter(database); }
        @Bean Listener listener(EventLog log, AuditWriter writer) { return new Listener(log, writer); }
    }
    public static void main(String[] args) {
        try (var context = new AnnotationConfigApplicationContext(Config.class)) {
            LabDatabase database = context.getBean(LabDatabase.class);
            EventLog log = context.getBean(EventLog.class);
            TransactionTemplate template = new TransactionTemplate(database.manager());
            template.executeWithoutResult(status -> {
                database.insert(1, "order"); context.publishEvent(new Completed(1));
            });
            System.out.println("committedRows=" + database.labels());
            System.out.println("committedEvents=" + log.events);
            database.clear(); log.events.clear();
            template.executeWithoutResult(status -> {
                database.insert(2, "order"); context.publishEvent(new Completed(2)); status.setRollbackOnly();
            });
            System.out.println("rollbackRows=" + database.labels());
            System.out.println("rollbackEvents=" + log.events);
            context.publishEvent(new Completed(3));
            System.out.println("outsideEvents=" + log.events);
            database.jdbc().execute("create table outbox(id int primary key, state varchar(16))");
            template.executeWithoutResult(status -> {
                database.insert(4, "order"); database.jdbc().update("insert into outbox values(4, 'NEW')");
            });
            System.out.println("outboxRows=" + database.jdbc().queryForObject("select count(*) from outbox", Integer.class));
            System.out.println("orderRows=" + database.count());
        }
    }
}
```

使用[公共工程](./03-事务管理器连接与提交回滚.md)，编译运行 `demo.tx.completion.CompletionDemo`：

```text title="expected-output"
committedRows=[order, audit]
committedEvents=[afterCommit:1]
rollbackRows=[]
rollbackEvents=[]
outsideEvents=[]
outboxRows=1
orderRows=1
```

审计写入调用了独立 Bean 的代理，用 REQUIRES_NEW 明确建立新事务。提交后阶段原事务资源可能尚未完成全部清理，但原提交已经结束；不要在此直接沿原资源写入，然后假设还会再提交一次。

## 4. 回调失败后，业务可能已经成功

提交后的通知失败不能撤销已提交数据；不同回调机制对异常向调用者传播或日志处理也有具体规则。不能只凭客户端收到异常就认定原事务一定回滚。

因此要定义重试标识和幂等语义，避免调用方因不确定状态重复创建订单。若审计必须与业务原子提交，就应放在同一个原事务内，而不是在 AFTER_COMMIT 中制造两个成功与失败彼此独立的事务。

## 5. 为什么普通事件不是可靠消息

数据库提交完成后，进程可能在回调执行前崩溃；回调中的网络发送也可能超时，而接收方实际上已经处理。同步监听没有消除这两个窗口，改成异步又会增加队列与退出管理问题。

需要可靠外部通知时，可以把业务记录和 Outbox 记录写入同一个本地数据库事务，再由独立投递器读取、发送和更新状态。进程重启后待投递记录仍可恢复，这是纯内存回调不具备的保证。

## 6. Outbox 仍需处理重复与积压

本例只验证两张表的本地原子写入，没有运行消息投递器。真实记录还需要事件 ID、类型、必要载荷、创建时间、重试状态等；投递器需有批量、锁或租约、失败退避与积压指标。

发送成功而状态更新前崩溃，可能再次投递，所以消费方仍需按事件 ID 或业务键实现幂等。仅用一个 NEW/SENT 字段不能证明跨数据库与 MQ 的端到端 exactly-once。

## 7. 事务边界越明确，外部等待越容易分析

长远程调用宜放在持锁事务之外，进入短事务后重新校验必要前提，不能使用已过期的先读结果直接覆盖。提交后的动作也要分成可丢的观测、需重试的通知、必须原子持久化的数据，不同责任采用不同机制。

## 8. 练习与答案

### 8.1 AFTER_COMMIT 的审计失败，原订单是否自动撤销

不会。原提交已经完成。要么接受独立失败并恢复，要么在业务要求下把审计放入原事务，或记录可靠待处理项。

### 8.2 没有事务发布事件，为什么本例没有增加审计

TransactionalEventListener 默认不对无事务发布执行 fallback；它与上一阶段的普通同步 EventListener 不是同一个触发契约。

### 8.3 Outbox 写入成功，是否意味着消息已经发送且只发一次

不是。它先保证本地业务与待发送记录的原子性；后续投递、重复、确认和消费幂等仍要实现并验证。
