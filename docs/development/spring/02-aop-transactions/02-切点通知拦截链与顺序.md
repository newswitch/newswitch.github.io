# 切点、通知、拦截链与顺序

AOP 不只是“方法前后打印两行日志”。它先决定某个调用是否匹配，再将匹配的增强组织成链。链上的代码可以继续执行、修改结果、抛异常，也可能完全不调用目标。

理解链的进入和退出方向，才能解释为什么同一个重试和事务组合会得到不同结果。

## 1. 五个名称分别描述什么

| 名称 | 作用 |
| --- | --- |
| Join Point | 可以介入的执行位置；Spring 代理 AOP 主要面向方法执行 |
| Pointcut | 判断哪些类、方法或调用参数符合条件 |
| Advice | 匹配后要执行的行为 |
| Advisor | Spring 中将切点与相应增强组织在一起的对象 |
| Aspect | 对一组相关切点与增强的组织方式 |

`execution` 匹配方法执行签名，`within` 限定类型范围，`args` 根据运行时参数匹配，`@annotation` 可按注解匹配。不要把任意字段访问、构造调用等 AspectJ 能力都当成 Spring 代理天然支持的位置。

## 2. 不同通知关注不同退出路径

Before 在继续调用前执行；AfterReturning 只针对正常返回；AfterThrowing 针对匹配异常；After 类似 finally 的退出通知；Around 可以控制是否及怎样继续。

Around 的 proceed 不是装饰性语句。漏调用可以跳过业务，调用两次可能重复写入，捕获后不重抛则可能让外层看到正常返回。选用尽可能明确的通知形式，特别不要把记录日志的切面写成吞异常的恢复层。[通知语义](https://docs.spring.io/spring-framework/reference/core/aop/ataspectj/advice.html)

## 3. 用两个有序切面观察成功和异常

```java title="src/main/java/demo/tx/chain/AdviceChainDemo.java"
package demo.tx.chain;

import java.util.ArrayList;
import java.util.List;
import org.aspectj.lang.ProceedingJoinPoint;
import org.aspectj.lang.annotation.Around;
import org.aspectj.lang.annotation.Aspect;
import org.springframework.context.annotation.AnnotationConfigApplicationContext;
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;
import org.springframework.context.annotation.EnableAspectJAutoProxy;
import org.springframework.core.annotation.Order;

public class AdviceChainDemo {
    public static class Log { public final List<String> events = new ArrayList<>(); }
    public static class TaskService {
        private final Log log;
        public TaskService(Log log) { this.log = log; }
        public String run(boolean fail) {
            log.events.add("target");
            if (fail) throw new IllegalStateException("task failed");
            return "done";
        }
    }
    public static Object invoke(String name, Log log, ProceedingJoinPoint point) throws Throwable {
        log.events.add(name + ":before");
        try {
            Object result = point.proceed();
            log.events.add(name + ":return");
            return result;
        } catch (Throwable error) {
            log.events.add(name + ":throw");
            throw error;
        } finally {
            log.events.add(name + ":finally");
        }
    }
    @Aspect @Order(10)
    public static class OuterAspect {
        private final Log log;
        public OuterAspect(Log log) { this.log = log; }
        @Around("execution(* demo.tx.chain.AdviceChainDemo.TaskService.run(..))")
        public Object around(ProceedingJoinPoint point) throws Throwable { return invoke("outer", log, point); }
    }
    @Aspect @Order(20)
    public static class InnerAspect {
        private final Log log;
        public InnerAspect(Log log) { this.log = log; }
        @Around("execution(* demo.tx.chain.AdviceChainDemo.TaskService.run(..))")
        public Object around(ProceedingJoinPoint point) throws Throwable { return invoke("inner", log, point); }
    }
    @Configuration(proxyBeanMethods = false) @EnableAspectJAutoProxy
    public static class Config {
        @Bean Log log() { return new Log(); }
        @Bean TaskService taskService(Log log) { return new TaskService(log); }
        @Bean OuterAspect outer(Log log) { return new OuterAspect(log); }
        @Bean InnerAspect inner(Log log) { return new InnerAspect(log); }
    }
    public static void main(String[] args) {
        try (var context = new AnnotationConfigApplicationContext(Config.class)) {
            Log log = context.getBean(Log.class);
            TaskService service = context.getBean(TaskService.class);
            service.run(false);
            System.out.println("success=" + String.join(",", log.events));
            log.events.clear();
            try { service.run(true); } catch (IllegalStateException expected) { }
            System.out.println("failure=" + String.join(",", log.events));
        }
    }
}
```

使用[公共工程](./01-JDK动态代理CGLIB与调用边界.md)编译，运行主类 `demo.tx.chain.AdviceChainDemo`：

```text title="expected-output"
success=outer:before,inner:before,target,inner:return,inner:finally,outer:return,outer:finally
failure=outer:before,inner:before,target,inner:throw,inner:finally,outer:throw,outer:finally
```

较小 Order 值的切面在本例中优先进入，也最后退出。使用两个独立切面和明确顺序，避免依靠同一切面多个同类通知方法的声明顺序。

## 4. 为什么重试与事务的外内层不同

```text
重试 → 事务 → 目标
每次尝试可以经过一个新的事务边界

事务 → 重试 → 目标
多次尝试可能仍在同一个已标记失败的事务内
```

这只是边界关系，不是鼓励对所有异常自动重试。数据库事务一旦进入失败状态，继续在同一事务内重试未必有效；已发生外部副作用时还可能重复执行。必须同时定义可重试错误、幂等性、最大次数与总时间预算。

事务增强有自己的顺序设置，普通自定义切面的 Order 不自动等于“永远在事务外”。应验证实际 Advisor 链和调用记录。

## 5. 切点范围为什么要窄

全包通配符可能把配置、内部基础设施和不适合增强的对象也纳入。按明确服务契约或语义注解选择范围，既便于理解，也降低循环依赖和额外开销。

运行时参数匹配可能增加逐次判断；复杂序列化日志还会改变延迟并泄露数据。性能分析要区分业务耗时、增强自身成本和输出成本。

## 6. 结果改变与异常传播也属于契约

切面把异常转换为另一个类型，可能改变外层事务回滚规则；吞异常可能导致提交；在 finally 抛出新异常又可能遮住原始错误。记录异常应保留 cause，不为“统一处理”丢掉原有语义。

因此调试时不只看目标方法，还要沿链确认：谁调用 proceed，谁看见异常，谁最终决定返回或抛出。

## 7. 练习与答案

### 7.1 Around 没调用 proceed，会发生什么

后续链和目标可能完全不执行。缓存命中等场景可以有意这样做，但普通观测切面漏调用通常会改变业务。

### 7.2 为什么先进入的 outer 最后打印 finally

调用链是嵌套结构：outer 等待 inner，inner 等待目标。退出时按相反方向返回或传播异常。

### 7.3 日志切面捕获异常后返回 null，是否只影响日志

不是，它改变返回与异常契约，可能导致外层认为操作成功、事务提交或后续空值错误。应按原语义传播，除非明确承担恢复责任。
