# 隔离级别、数据库锁与并发控制

传播行为解决方法进入时如何参与事务，隔离级别解决并发事务允许看到哪些状态。数据库再通过锁、版本和冲突检测实现具体语义。给方法写一个隔离枚举，不能代替分析 SQL、索引和实际数据库实现。

本篇以 H2 2.4.240 的独立内存库观察机制，不能据此推导 MySQL、PostgreSQL 的全部锁范围和快照规则。

## 1. 四个层次分别约束什么

| 层次 | 主要问题 |
| --- | --- |
| Spring 传播 | 当前调用加入、挂起还是建立事务 |
| 数据库隔离 | 并发读写允许的可见性与冲突 |
| SQL 和索引 | 实际读取、更新、扫描与锁住哪些记录或范围 |
| 业务并发协议 | 库存不能负数、状态不能重复迁移等不变量 |

隔离强不等于业务协议自动正确。两个事务先读后写同一值，可能仍需要条件更新、锁定读取或冲突重试，具体看实现与 SQL。

## 2. 常见隔离名称怎样理解

READ_UNCOMMITTED、READ_COMMITTED、REPEATABLE_READ、SERIALIZABLE 从传统异常模型描述越来越强的约束，但不同产品的映射、默认级别及实现并不相同。普通快照读与锁定读也可能采用不同路径。

读到另一个已提交版本，不是“脏读”；同一事务两次读取变化，才是本篇 RC 实验展示的不可重复读。幻读讨论的是谓词匹配集合变化，不只是某行的字段更新。写偏斜等异常又不能只靠背这三种读异常完整解释。

H2 使用版本与锁等机制实现支持的隔离模式，正式说明见 [H2 Advanced](https://h2database.com/html/advanced.html)。

## 3. 双连接按确定顺序交错

实验不用随机 sleep 猜并发时机。reader 先读，writer 在另一个连接提交，再让 reader 重读；这已经建立了两个重叠事务的交错关系，不需要两个线程同时抢跑。

```java title="src/main/java/demo/tx/isolation/IsolationDemo.java"
package demo.tx.isolation;

import java.sql.Connection;
import java.sql.ResultSet;
import java.sql.SQLException;
import java.sql.Statement;
import demo.tx.support.LabDatabase;

public class IsolationDemo {
    public static String label(Connection connection) throws SQLException {
        try (Statement statement = connection.createStatement();
             ResultSet result = statement.executeQuery("select label from entries where id=1")) {
            if (!result.next()) throw new IllegalStateException("entry missing");
            return result.getString(1);
        }
    }
    public static String readTwice(LabDatabase database, int isolation) throws SQLException {
        database.jdbc().update("update entries set label='v1' where id=1");
        try (Connection reader = database.dataSource().getConnection();
             Connection writer = database.dataSource().getConnection()) {
            reader.setTransactionIsolation(isolation);
            reader.setAutoCommit(false);
            try {
                String first = label(reader);
                try (Statement statement = writer.createStatement()) {
                    statement.executeUpdate("update entries set label='v2' where id=1");
                }
                return first + "->" + label(reader);
            } finally { reader.rollback(); }
        }
    }
    public static boolean lockTimesOut(LabDatabase database) throws SQLException {
        try (Connection owner = database.dataSource().getConnection();
             Connection contender = database.dataSource().getConnection()) {
            owner.setAutoCommit(false);
            contender.setAutoCommit(false);
            try (Statement first = owner.createStatement(); Statement second = contender.createStatement()) {
                first.executeUpdate("update entries set label='locked' where id=1");
                second.execute("set lock_timeout 200");
                second.setQueryTimeout(2);
                try {
                    second.executeUpdate("update entries set label='contender' where id=1");
                    return false;
                } catch (SQLException error) {
                    if (error.getErrorCode() != 50200) throw error;
                    return true;
                }
            } finally {
                try { contender.rollback(); } finally { owner.rollback(); }
            }
        }
    }
    public static void main(String[] args) throws Exception {
        try (LabDatabase database = new LabDatabase()) {
            database.insert(1, "v1");
            System.out.println("readCommitted=" + readTwice(database, Connection.TRANSACTION_READ_COMMITTED));
            System.out.println("repeatableRead=" + readTwice(database, Connection.TRANSACTION_REPEATABLE_READ));
            System.out.println("lockTimeout=" + lockTimesOut(database));
            database.jdbc().execute("create table stock(id int primary key, available int, version int)");
            database.jdbc().update("insert into stock values(1, 2, 0)");
            String sql = "update stock set available=available-1, version=version+1 where id=1 and version=? and available>0";
            int first = database.jdbc().update(sql, 0);
            int stale = database.jdbc().update(sql, 0);
            System.out.println("optimisticUpdates=" + first + "," + stale);
        }
    }
}
```

使用[公共支持类](./03-事务管理器连接与提交回滚.md)，编译运行 `demo.tx.isolation.IsolationDemo`：

```text title="expected-output"
readCommitted=v1->v2
repeatableRead=v1->v1
lockTimeout=true
optimisticUpdates=1,0
```

writer 保持默认自动提交，因此其更新在第二次读前已经提交。锁实验则主动关闭自动提交、持有更新锁，并给竞争者设置短等待；不依赖无上限的阻塞来证明锁存在。

## 4. 版本条件更新验证什么

两个调用都基于 version=0，第一次更新把版本推进到 1；第二次影响行数为 0，表示旧版本条件不再成立。应用必须检查影响行数，不能把 JDBC 没抛异常当成业务成功。

available>0 同时保护余额类不变量。仅比较版本，却没有正确的业务条件，也可能提交合法版本下的不合法状态。重试时应重新读取并重新评估业务，不是无限重放旧输入。

## 5. 悲观锁要看事务和执行计划

更新通常会取得相应写锁；`SELECT ... FOR UPDATE` 等锁定读取也可以参与协议。锁一般持续到相应事务结束，而不是 Java 方法返回或 ResultSet 关闭就一定释放。

在不同数据库中，索引、范围条件、隔离级别与执行计划会改变锁范围。没有合适索引的更新可能扫描并影响更多资源；不能从 H2 的一行实验推出 InnoDB 没有间隙锁或 PostgreSQL 采用相同快照。

## 6. 锁等待、死锁与序列化失败分开处理

锁等待超时说明在预算内未取得进展；死锁需要循环等待关系；序列化失败可能由数据库冲突检测触发。三者都可能要求回滚并从合适事务边界重试，但错误码、资源状态和安全重试条件不同。

本例的 50200 是 H2 锁等待错误，不是跨数据库通用错误码。生产要保留数据库产品、完整错误、事务 SQL、持锁者和等待者信息。

先减少事务中不必要的远程调用、统一更新顺序、缩小锁范围，再根据证据决定容量和超时。把等待时间调大不能消除错误的资源依赖。

## 7. Spring 注解的属性要落到真实连接

新事务可以请求相应隔离级别；加入已有事务时，内层隔离注解通常不会把已有连接原地切换。连接池默认值、管理器支持和数据库能力还要一起确认。

readOnly 不能替代隔离，timeout 不能替代锁协议；串行化也不是不需要失败处理和重试。数据库自己因冲突拒绝一次提交，可能正是它维护正确性的方式。

## 8. 练习与答案

### 8.1 READ_COMMITTED 第二次读到 v2，是否数据库读到了未提交数据

不是。writer 已通过另一个自动提交连接完成提交。这里展示的是两次读取之间可见已提交版本改变。

### 8.2 update 返回 0 行，能否仍给用户返回扣减成功

不能直接这样做。它可能代表版本过期、余额不足或目标不存在，应用应按契约识别结果，而不是只检查有没有 SQLException。

### 8.3 Repeatable Read 下所有数据库的幻读、锁范围是否完全一致

不是。必须核对具体产品、语句类型和实现。隔离名称是理解入口，不是替代数据库专项原理的万能表。
