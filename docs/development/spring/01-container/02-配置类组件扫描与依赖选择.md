# 配置类、组件扫描与依赖选择

容器装配首先要回答两个问题：有哪些对象定义；一个依赖位置应该选择哪些候选对象。`@ComponentScan` 解决发现与注册，`@Primary`、`@Qualifier` 等参与候选解析，二者不是同一步。

## 1. 显式工厂与自动扫描

`@Bean` 适合明确描述第三方客户端、复杂构造和配置边界；`@Component` 及其组合注解适合让自己的类成为扫描候选。`@Service`、`@Repository` 等表达语义，也可被默认扫描规则识别，但不是给任意普通对象贴上后马上自动生效。

扫描必须从明确的包或标记类开始。过宽扫描可能把实验配置、旧实现和不相关模块一起注册；扫描不到则要检查包路径、过滤器、条件及所加载的 ApplicationContext。

## 2. 配置方法调用不一定是容器取 Bean

`@Configuration` 默认的完整模式可以拦截配置类中符合条件的 Bean 方法调用，协调容器语义。`proxyBeanMethods=false` 不做这类方法拦截；方法体里直接调用另一个工厂方法，就是普通 Java 调用，可能产生额外对象。

本系列使用 `proxyBeanMethods=false`，并通过 `@Bean` 方法参数声明依赖，而不靠方法互调。因此更容易区分“向容器请求对象”和“自己执行构造代码”。准确约束见 [Bean 注解说明](https://docs.spring.io/spring-framework/reference/core/beans/java/bean-annotation.html)。

## 3. 候选解析不是看到同类型就随机选一个

| 声明 | 主要语义 |
| --- | --- |
| 一个必需的单值依赖 | 必须解析出适合的候选 |
| `@Primary` | 单值候选解析中的优先候选，不从容器删除其他实例 |
| `@Qualifier` | 用限定信息进一步筛选，不只是给参数改名字 |
| `List<T>` | 收集符合类型和限定条件的候选，可按 Order 排序 |
| `Map<String,T>` | Bean 名称到候选的映射，不据此假设业务优先级 |
| `ObjectProvider<T>` | 将解析或获取推迟到调用点，不自动保证唯一性 |

现代 Spring 还有 fallback 等候选规则；不要把内部解析简化为所有场景都完全相同的一张优先级表。参数名可能参与回退匹配，因此工程保留 `-parameters`，但业务选择宜用明确类型与限定表达。构造器规则见 [Autowired 文档](https://docs.spring.io/spring-framework/reference/core/beans/annotation-config/autowired.html)。

## 4. 同时观察单值、集合与可选依赖

```java title="src/main/java/demo/container/selection/DependencyDemo.java"
package demo.container.selection;

import java.util.List;
import java.util.Map;
import java.util.stream.Collectors;
import org.springframework.beans.factory.ObjectProvider;
import org.springframework.beans.factory.annotation.Qualifier;
import org.springframework.context.annotation.AnnotationConfigApplicationContext;
import org.springframework.context.annotation.ComponentScan;
import org.springframework.context.annotation.Configuration;
import org.springframework.context.annotation.Primary;
import org.springframework.core.annotation.Order;
import org.springframework.stereotype.Component;

public class DependencyDemo {
    public interface TaskExecutor {
        String name();
        default String execute(String task) { return name() + ":" + task; }
    }
    public interface OptionalReporter { }

    @Component("localExecutor") @Order(20)
    public static class LocalExecutor implements TaskExecutor {
        public String name() { return "local"; }
    }
    @Component("remoteExecutor") @Primary @Order(10)
    public static class RemoteExecutor implements TaskExecutor {
        public String name() { return "remote"; }
    }
    @Component
    public static class Dispatcher {
        final TaskExecutor selected;
        final TaskExecutor local;
        final List<TaskExecutor> all;
        final Map<String, TaskExecutor> named;
        final ObjectProvider<OptionalReporter> reporter;
        public Dispatcher(TaskExecutor selected,
                          @Qualifier("localExecutor") TaskExecutor local,
                          List<TaskExecutor> all, Map<String, TaskExecutor> named,
                          ObjectProvider<OptionalReporter> reporter) {
            this.selected = selected; this.local = local;
            this.all = all; this.named = named; this.reporter = reporter;
        }
    }
    @Configuration(proxyBeanMethods = false)
    @ComponentScan(basePackageClasses = DependencyDemo.class)
    public static class Config { }

    public static void main(String[] args) {
        try (var context = new AnnotationConfigApplicationContext(Config.class)) {
            Dispatcher d = context.getBean(Dispatcher.class);
            System.out.println("primary=" + d.selected.execute("job"));
            System.out.println("qualified=" + d.local.execute("job"));
            System.out.println("ordered=" + d.all.stream().map(TaskExecutor::name).collect(Collectors.joining(",")));
            System.out.println("names=" + d.named.keySet().stream().sorted().collect(Collectors.joining(",")));
            System.out.println("missing=" + (d.reporter.getIfAvailable() == null));
        }
    }
}
```

使用[前一篇的工程](./01-从手动装配到IoC与依赖注入.md)，重新编译后运行主类 `demo.container.selection.DependencyDemo`：

```text title="expected-output"
primary=remote:job
qualified=local:job
ordered=remote,local
names=localExecutor,remoteExecutor
missing=true
```

单构造器不必额外标 `@Autowired`。Primary 影响单值选择，List 仍包含两个执行器；Order 影响这里的集合顺序，而不是全局 Bean 初始化顺序。Map 的键专门排序后输出，避免把注册顺序误当承诺。

## 5. 延迟获取与可选不是同义词

`getIfAvailable()` 在没有候选时可返回 null，但多个候选无法唯一解析时仍可能报错；`getIfUnique()` 表达不同的唯一性要求。Provider 也可用于每次获取 prototype，而不是在 singleton 创建时固定一个实例。

需要“失败时也能正常运行”的依赖，还必须写出缺省行为。把一个必需的数据库依赖改成 Optional，只会把启动时的问题推迟到请求阶段。

`@Lazy` 注入可以通过延迟解析代理改变创建时刻，但它不是解除循环业务依赖或保证依赖健康的通用手段。

## 6. 三种故障怎样缩小范围

没有候选时，确认对象是否注册、所在容器和条件；候选过多时，列出每个 Bean 名、类型、限定和主候选；已经拿到对象却不是预期实现时，检查实际代理类型、配置入口及是否手动 new 了另一份。

构造器形成 A 需要 B、B 又需要 A 的循环，意味着不能按这组构造条件先得到任何完整对象。不要首先改成字段注入来隐藏关系；优先拆分责任或引入明确的第三方协调对象。

## 7. 练习与答案

### 7.1 标记 Primary 后，另一个执行器还会被创建吗

可能会。它仍是容器中的定义，默认非懒 singleton 通常在刷新时创建，也仍可进入集合或被限定注入。

### 7.2 Order=1 是否保证这个 Bean 最先初始化

不是。这里的 Order 用于排序候选集合等特定机制；创建还受依赖关系、懒加载和生命周期阶段影响。

### 7.3 Provider 没有报启动错误，是否说明依赖一定存在

不是。解析可能被推迟到实际获取时；必须根据缺失或不唯一的语义处理结果，不能把延迟失败当成问题消失。
