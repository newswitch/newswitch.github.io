# 并发压测与瓶颈对照实验

一个接口写成 async def，并不保证并发请求能前进。这里把完全相同的二十毫秒等待放到三种执行位置，通过真实 HTTP 比较延迟与吞吐，解释为什么 CPU 不高也会排队。

## 1. 固定工作内容

`api_bottlenecks.py` 有三个仅供本机实验的接口：

| 路径 | 实现 | 等待时谁被占用 |
| --- | --- | --- |
| /blocking | async 路由调用 time.sleep | 事件循环线程 |
| /threaded | def 路由调用 time.sleep | 框架线程池中的线程 |
| /asynchronous | async 路由 await asyncio.sleep | 协程暂停，循环可处理其他工作 |

这里只比较等待，不比较数据库性能或 CPU 计算。请求 delay 有上限，服务只绑定环回地址，不把故意阻塞的接口暴露到业务环境。

## 2. 运行有限实验

安装深化依赖，从 framework-lab 执行：

```bash
python compare_load.py
```

脚本启动自己拥有的 Uvicorn 子进程，临时选择本机端口，检查启动成功，然后分别用并发 1、4 请求三个接口，每组二十次。结束只关闭它创建的进程，不扫描或终止其他 Python 服务。

一次 Windows 11、CPython 3.14.8、Uvicorn 0.54.0、单 Worker 的环回实验得到以下结果；等待参数均为 0.02 秒，没有数据库、代理或外部下游：

| 实现 | 客户端并发 | 完成数 | 吞吐 请求/秒 | 样本 P50 毫秒 | 样本 P99 毫秒 |
| --- | --- | --- | --- | --- | --- |
| blocking | 1 | 20 | 41.5 | 22.9 | 44.5 |
| threaded | 1 | 20 | 39.1 | 22.8 | 72.6 |
| asynchronous | 1 | 20 | 30.7 | 31.6 | 52.0 |
| blocking | 4 | 20 | 45.6 | 86.3 | 107.4 |
| threaded | 4 | 20 | 151.7 | 23.3 | 32.1 |
| asynchronous | 4 | 20 | 127.1 | 30.7 | 33.0 |

这份小样本不是容量报告。它没有消除冷启动与调度噪声，也未记录可用于跨机器比较的完整 CPU、功耗及配额条件；二十个样本的 nearest-rank P99 就是最大值，不能据此声称稳定的生产尾延迟。实际使用先增加预热、重复轮次和样本量，并保留原始输出。

## 3. 从数据解释执行路径

blocking 并发从一增加到四，吞吐基本没增加，但 P50 明显变长，符合等待在一个循环线程上串行发生、请求逐渐排队的机制。线程池与异步等待让多个等待区间重叠，所以这一工作负载下能够完成更多请求。

单并发时异步版本没有更快，这并不矛盾：没有别的工作可切换时，异步并不消除那二十毫秒，还存在调度与计时器成本。也不能从表格推导线程池普遍快于异步；底层平台、驱动、负载和样本都影响数值。

把 sleep 换成纯 Python CPU 循环，常规带 GIL 构建中的线程池可能无法获得相同收益。更换实验工作后，应重新测量，而不是套用本表。

## 4. 进一步分辨池等待与锁等待

加入数据库时，给每层建立独立证据：入口在途、事件循环 lag、线程令牌等待、连接池等待、事务时间、SQL 锁等待、下游调用与发送。只有总延迟曲线，无法知道是哪一层先饱和。

例如五连接池中每条事务都占用两秒，同时提交二十项工作会出现池排队。把池增加到二十之前，要确认数据库能承载，并排除不该留在事务里的 HTTP 等待。数据库只有一个热点行时，再多连接也不会让互斥更新同时提交。

## 5. 从机制实验走向容量报告

固定硬件和配额、数据规模、请求比例、依赖延迟、Worker、池、连接复用与响应大小。先做正确性检查，再预热；逐级提高到达率，记录成功工作量、错误率、P50/P95/P99 和资源。

闭环客户端会在服务慢时降低到达率，可能隐藏过载；需要开环测量时，使用能报告实际发送速率、排队与丢失的工具。客户端本身也要监控，不能把发压端饱和当成服务容量。

修复前后使用相同负载、相同结果和相同安全校验。最后再测试取消、断开与退出，避免吞吐提高只是因为工作被丢弃。容量结论应表述为某工作负载和延迟目标下的可持续成功速率，而非一个脱离条件的最大 QPS。

## 6. 练习与答案

### 6.1 blocking 加并发后延迟上升，但吞吐不升，下一步看什么？

答案：检查事件循环 lag、同 Worker 健康接口和同步调用栈。用相同工作改为真实非阻塞等待或有界卸载做对照，不先盲目增加线程数。

### 6.2 二十次请求没有错误，能确定生产 P99 吗？

答案：不能。样本太少，P99 接近最大样本且很不稳定。需要预热、重复、足够样本、工作负载说明和更完整的计时边界。

### 6.3 增加 Worker 后吞吐上升，需要同时检查什么？

答案：CPU/内存总量、数据库连接总预算、下游负载、尾延迟和结果正确性。每进程池与缓存会复制，收益不等于资源成本没有变化。
