# 请求、依赖、响应与清理源码

一次请求的核心不是“找到函数后直接执行”。框架还要读取输入、求解依赖、校验、决定执行位置、处理响应，并在正确阶段关闭资源。

## 1. 主路径

FastAPI 0.150 中，APIRoute 的处理入口连接到 get_request_handler；它读取适当请求体并调用 solve_dependencies，之后在没有输入错误的路径执行端点，再准备响应。

普通返回值会进入相应校验/序列化路径；直接返回 Response 则承担不同责任。HTTP、SSE/JSONL 与 WebSocket 的分支不能简单视为同一种 JSON 返回。

## 2. 用事件验证退出栈

```python title="api_source_request.py"
import asyncio
from typing import Annotated
from fastapi import Depends, FastAPI

events = []
app = FastAPI()

def request_resource():
    events.append("open-request")
    try:
        yield object()
    finally:
        events.append("close-request")

def function_resource():
    events.append("open-function")
    try:
        yield object()
    finally:
        events.append("close-function")

@app.get("/jobs")
async def jobs(
    first: Annotated[object, Depends(request_resource, scope="request")],
    second: Annotated[object, Depends(function_resource, scope="function")],
):
    events.append("handler")
    return {"ok": True}

async def main():
    events.clear()
    scope = {"type": "http", "asgi": {"version": "3.0"},
             "http_version": "1.1", "method": "GET", "scheme": "http",
             "path": "/jobs", "raw_path": b"/jobs", "query_string": b"",
             "root_path": "", "headers": [], "server": ("test", 80),
             "client": ("test", 1)}

    async def receive():
        return {"type": "http.request", "body": b"", "more_body": False}

    async def send(message):
        events.append(message["type"])

    await app(scope, receive, send)
    print(events)

if __name__ == "__main__":
    asyncio.run(main())
```

```text title="api_source_request.out"
['open-request', 'open-function', 'handler', 'close-function', 'http.response.start', 'http.response.body', 'close-request']
```

直接调用 ASGI 并观察 send，避免仅凭客户端函数返回推测清理时点。这里没有建立真实 TCP，也没有应用公共资源需要 lifespan。

## 3. 依赖求解

solve_dependencies 递归求解子依赖、观察请求级缓存，区分生成器、协程与普通同步可调用。生成器进入对应退出栈，异步函数 await，普通同步依赖进入相应线程池。

参数来源随后被整理到调用所需映射，错误统一聚合。依赖缓存包含相应上下文，不是只用一个函数名字符串；不要跨请求手工复用内部缓存。

## 4. 两个退出时点

request_response 在请求级退出栈内再建立函数级退出栈。函数级资源在取得 Response 后退出，随后发送 Response；请求级资源覆盖相应响应周期后再退出。这解释了 function/request scope 的差异。

清理中的异常可能改变结果，吞掉原异常也会破坏框架预期。流式响应开始后，资源失败不能再简单转换成一个全新 JSON 状态码。

## 5. 练习与答案

### 5.1 端点返回字典后，请求就一定已经结束吗？

答案：没有，还可能序列化、发送响应、执行相关后台工作与资源退出。

### 5.2 同步依赖是在事件循环里普通调用吗？

答案：框架对普通同步依赖通常使用线程池；但业务函数内部的普通同步工具调用不因此自动卸载。

### 5.3 为什么源码分析要观察 ASGI send？

答案：它能区分响应对象准备好与协议消息实际发送的时点，帮助解释流与资源关闭顺序。
