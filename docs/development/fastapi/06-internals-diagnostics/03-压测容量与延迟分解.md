# 压测、容量与延迟分解

容量不是某台机器上的最大 QPS 数字，而是在给定请求结构、错误率与延迟目标下，系统能够持续承载的工作量。压测必须保留正确性、输出大小与依赖行为。

## 1. 定义工作负载

记录硬件、CPU 配额、内存、解释器、依赖、Worker、连接池与数据规模；说明读写比例、长短请求、上下游延迟、客户端连接复用与负载模型。

闭环客户端等待响应后再发送，可能在服务变慢时自动降低输入；开环按到达率发送，更容易观察排队和拒绝。两者回答的问题不同，不能把闭环吞吐直接等同于可承诺到达率。

## 2. 平均关系不是尾延迟公式

稳定系统中，Little 定律表达平均在系统中的数量约等于平均到达率乘平均停留时间。它不是用 P99 相乘就能算出 P99 并发，也不能替代过载条件分析。

```python title="api_capacity.py"
def mean_inflight(rate_per_second, mean_seconds):
    return rate_per_second * mean_seconds

def main():
    print("mean inflight:", mean_inflight(100, 0.12))
    workers = 2
    pool_per_worker = 10
    pods = 3
    print("connection budget:", workers * pool_per_worker * pods)
    cpu_capacity = 400
    db_capacity = 200
    print("illustrative ceiling:", min(cpu_capacity, db_capacity))

if __name__ == "__main__":
    main()
```

```text title="api_capacity.out"
mean inflight: 12.0
connection budget: 60
illustrative ceiling: 200
```

这些数字是模型输入，不是实测结果。真实服务还需要为波动、故障、长请求和发布留余量，不能在理论瓶颈处长期满载。

## 3. 延迟分解

入口等待、应用并发许可、线程池、数据库池、语句执行、下游调用和序列化分别观测。总平均值不能通过简单相加各组件 P99 获得，跨请求相关性也会影响尾部。

依次提高到达率，观察吞吐是否继续增长、队列是否积累、超时/拒绝是否增加。饱和点后继续加并发，可能只增加延迟与错误。

## 4. 可重复压测步骤

先验证固定输入输出，再预热、稳定运行和冷却；至少比较多个负载点与多次运行。客户端也可能成为瓶颈，需要记录其 CPU、连接数与生成速率。

本系列 `load_probe.py` 提供有限请求、有界并发和明确超时的本机 HTTP 探测。它适合验证方法，不代表成熟开环压测平台；真实容量结论仍需目标环境与完整报告。

## 5. 练习与答案

### 5.1 平均每秒一百请求、平均一百二十毫秒，平均在途多少？

答案：稳定前提下约十二个。不能据此直接推导 P99 或故障时的最大并发。

### 5.2 三个 Pod、每个两个 Worker、每池十连接，总预算多少？

答案：可能达到六十个，还要加其他进程与服务使用量，不能只看某一个配置。

### 5.3 吞吐升高但错误率也升高，能说容量提升吗？

答案：必须按成功工作量与延迟目标判断，不能把快速拒绝或丢失工作计成有效性能收益。
