# 启动、路由注册与应用构建源码

源码分析先分阶段：导入与注册阶段建立路由/参数元数据；lifespan 阶段准备资源；请求阶段才取得实际输入并调用业务。混在一起读，会误以为每次请求都重新分析整份应用。

## 1. 阅读入口

以安装的 FastAPI 0.150.0 源码为基线，重点追踪：

| 文件/对象 | 负责什么 |
| --- | --- |
| applications.FastAPI | 应用设置、路由委托、ASGI 入口与原生遥测 |
| routing.APIRouter | 注册与组织路由，组合前缀/依赖等上下文 |
| routing.APIRoute | 保存端点相关模型并提供请求处理入口 |
| dependencies.utils.get_dependant | 分析签名与依赖关系 |
| openapi.utils | 将路由声明转换为接口 Schema |

这不是要求记住所有函数，而是知道定义被保存在哪里、什么时间转为实际工作。当前版本包含路由组合与有效上下文机制，不应将旧版本“include_router 一定直接复制成某个平面列表”的说法当成稳定 API。

## 2. 观察声明产物

```python title="api_source_start.py"
from importlib.metadata import version
from typing import Annotated
from fastapi import APIRouter, Depends, FastAPI

router = APIRouter(prefix="/jobs")

def limit():
    return 10

@router.get("/{job_id}")
def job(job_id: int, maximum: Annotated[int, Depends(limit)]):
    return {"id": job_id, "limit": maximum}

app = FastAPI()
app.include_router(router)

def main():
    route = router.routes[0]
    print(version("fastapi"))
    print(route.dependant.call is job)
    print(route.dependant.dependencies[0].call is limit)
    print("/jobs/{job_id}" in app.openapi()["paths"])

if __name__ == "__main__":
    main()
```

```text title="api_source_start.out"
0.150.0
True
True
True
```

这里检查依赖函数对象已进入元数据，而不是已经执行依赖业务。OpenAPI 生成也不是一次真实 HTTP 请求，不会证明 limit 函数运行正确。

## 3. 装饰器到注册

装饰器取得函数对象，将路径、方法、依赖、响应模型等交给路由注册。签名和 Annotated 等声明参与构建；函数的普通调用约定仍然存在，只是框架在请求期为它准备参数。

注册期间若注解不可解析或声明不合法，可能启动前就失败。模块顶层联网、读取未准备好的 Secret 或创建池，会把导入与资源初始化耦合，应移动到配置/lifespan 边界。

## 4. 应用真正开始运行

Uvicorn 导入应用，驱动 lifespan，然后调用 ASGI 入口。FastAPI 0.150 的入口还组织原生遥测，再委托到下层中间件与路由链；旧版本没有相同能力，源码结论必须带版本。

多进程会分别导入和启动，因此路由表、依赖缓存与应用资源不等于跨进程共享。动态注册还会影响文档与缓存，应在受控启动期完成，不随普通请求任意改动。

### 4.1 用综合工程定位注册时与请求时

沿 main.create_from_env → Settings → api.create_app 阅读。创建 CreateJob 类时形成模型规则，定义 submit 时路由装饰器保存函数及参数声明，include_router 组合应用路径；这些动作都不应领取任务或执行数据库写入。

lifespan 之后才有 app.state.database。请求到来时，框架根据已建立的声明读取本次 body、credentials 和 key，再调用对应依赖；不要把 get_dependant 的签名分析误读成已经验证某个用户。OpenAPI 只描述声明，也不会执行 Worker。

对照安装版本源码时，先用 inspect.getfile 找到实际模块，再从 APIRoute、get_request_handler 和 solve_dependencies 跟踪，按阶段记录输入输出。相比粘贴整段源码，明确“这一处保存声明，下一处使用本次值”更能解释框架为什么这样组织。

## 5. 练习与答案

### 5.1 get_dependant 建立依赖图时，会执行所有数据库查询吗？

答案：不应这样理解，它主要分析声明；依赖函数的实际执行属于请求/相应调用阶段。导入副作用则是应用自己的另一个问题。

### 5.2 OpenAPI 包含路径，就说明端点已处理过请求吗？

答案：不是，它可以仅由路由元数据生成。

### 5.3 为什么不能照抄旧文章里的内部路由对象布局？

答案：内部组合与优化会变化。应固定版本，观察真实对象与源码，并优先使用稳定公开接口。
