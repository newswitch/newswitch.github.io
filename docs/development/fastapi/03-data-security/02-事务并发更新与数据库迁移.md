# 事务、并发更新与数据库迁移

事务解决一组数据库操作的提交与回滚，但不会自动防止所有业务竞态。两个请求都读到“任务尚未执行”，再各自提交，仍可能重复触发外部工作。

## 1. 先确定状态机

定义允许的状态转换，再决定原子边界。可以使用唯一约束防重复创建，用条件更新/版本号防丢失更新，用适合目标数据库的锁处理互斥。

应用先查再写若没有数据库约束，通常存在时间窗口。HTTP 幂等键也要绑定请求摘要与租户，并保存处理结果，不能只存在一个进程字典里。

## 2. 条件更新与回滚实验

```python title="api_transactions.py"
from sqlalchemy import create_engine, insert, select, update, func
from sqlalchemy.orm import DeclarativeBase, Mapped, Session, mapped_column

class Base(DeclarativeBase):
    pass

class Job(Base):
    __tablename__ = "jobs"
    id: Mapped[int] = mapped_column(primary_key=True)
    revision: Mapped[int] = mapped_column(default=0)

def change(session, expected):
    result = session.execute(
        update(Job).where(Job.id == 1, Job.revision == expected)
        .values(revision=Job.revision + 1))
    return result.rowcount

def main():
    engine = create_engine("sqlite://")
    try:
        Base.metadata.create_all(engine)
        with Session(engine) as db, db.begin():
            db.add(Job(id=1))
        with Session(engine) as db, db.begin():
            print("first:", change(db, 0))
        with Session(engine) as db, db.begin():
            print("stale:", change(db, 0))
        try:
            with Session(engine) as db, db.begin():
                db.add(Job(id=2))
                db.flush()
                raise RuntimeError("abort")
        except RuntimeError:
            pass
        with Session(engine) as db:
            print("rows:", db.scalar(select(func.count()).select_from(Job)))
    finally:
        engine.dispose()

if __name__ == "__main__":
    main()
```

```text title="api_transactions.out"
first: 1
stale: 0
rows: 1
```

更新条件与写入在数据库中共同决定结果。rowcount 为零表示当前条件未成立，不能继续按成功处理。本例顺序验证过期版本与回滚，不据此声称已经复现真实并发锁竞争。

## 3. 外部消息的一致性

数据库事务不能同时原子提交任意 HTTP/消息系统。提交前发消息可能发出后回滚，提交后发消息可能提交成功但发送失败。Outbox 将业务状态与待发送记录放在同一数据库事务，再由可重试投递器发送；消费者仍需幂等。

## 4. 迁移的边界

Alembic 维护结构版本。初始化迁移目录后，使用 revision 生成文件，审查 upgrade/downgrade，再在隔离库执行 upgrade head；autogenerate 不是自动理解数据迁移。

生产升级采用先扩展、兼容读写、回填、再收缩。大表加列/索引、非空约束与回滚有数据库特定成本；不要把 create_all 当成 schema 升级。

部署过程中只由受控步骤执行迁移，避免每个 Worker 同时改库。回滚应用版本前，还要确认它仍理解当前数据结构。

配套工程已经提供 `alembic.ini`、`migrations/env.py` 与 `0001_jobs`。先进入 `examples/fastapi/framework-lab/`，确认默认目标为当前目录的新建实验库 `tasks.db`，再执行：

```bash
python -m alembic -c alembic.ini upgrade head
python -m alembic -c alembic.ini current
```

`upgrade head` 执行到最新迁移，`current` 查询库中记录的版本；再次 upgrade 不应重复建表。已有迁移目录不要重新执行 init。需要新结构时，在独立开发分支创建 revision，审查生成文件后，在可丢弃的数据库测试升级、数据兼容和失败恢复。

综合服务的普通入口不会自动建表，必须先迁移。测试使用临时库验证 upgrade 与 downgrade；downgrade 会删除本例表，不能把该命令当成已有业务数据的无损回退。

## 5. 练习与答案

### 5.1 查询版本后再无条件写，等价于条件更新吗？

答案：不等价，查询与写入间可能被其他事务修改。版本条件需要进入原子更新或适当锁定边界。

### 5.2 数据库 commit 成功后发消息，就绝对不丢消息吗？

答案：不能保证，进程可能在两者之间失败。需要 Outbox 等可恢复设计，并处理重复投递。

### 5.3 autogenerate 生成迁移就可以直接上线吗？

答案：不应如此。需要审查结构、数据、锁影响、运行时间与兼容性，再在目标数据库验证。
