# 授权、多租户与浏览器安全

登录成功不表示能访问任意 job_id。多租户隔离必须贯穿查询、更新、缓存、消息和日志，而不是只在 HTTP Header 中多放一个 tenant 字段。

## 1. 身份到资源

先验证凭证，取得服务端认可的身份与租户；再根据操作和资源执行授权。不能直接信任客户端传来的 tenant_id，也不能先按全局 ID 取出资源，再只靠前端隐藏。

数据库查询应包含归属条件，更新也需保持相同约束；缓存键、幂等键与对象存储路径同样要包含正确的隔离维度。

## 2. 小型授权实验

```python title="api_authorization.py"
from fastapi import FastAPI, HTTPException

def create_app():
    app = FastAPI()
    rows = {("tenant-a", 1): {"id": 1, "name": "import"}}

    @app.get("/jobs/{job_id}")
    async def job(job_id: int):
        tenant = "tenant-a"
        row = rows.get((tenant, job_id))
        if row is None:
            raise HTTPException(404, "job not found")
        return row

    return app

def main():
    from fastapi.testclient import TestClient
    with TestClient(create_app()) as client:
        print(client.get("/jobs/1").status_code)
        print(client.get("/jobs/2").status_code)

if __name__ == "__main__":
    main()
```

```text title="api_authorization.out"
200
404
```

示例固定可信身份，只展示查询维度，不是完整认证实现。真实应用由已验证身份依赖提供 tenant，并测试租户 A 不能读取或修改租户 B 的资源。

## 3. CORS 不是访问控制

CORS 约束浏览器是否允许页面读取跨源响应，不阻止 curl、服务间调用或所有跨站请求。Origin、scheme、host、port 要精确匹配；携带凭证时不要将任意来源当成可信。

使用 Cookie 自动携带认证时，还要考虑 CSRF、SameSite、Secure、HttpOnly 与请求校验；Bearer 令牌存储则面临相应的 XSS/泄露风险。TLS 保护传输，不替代这些应用安全边界。

## 4. 纵深隔离与审计

最小权限包括对象、动作和范围，必要时由数据库行级策略补强；不能因此省略应用语义检查。管理员跨租户操作要显式授权并留下稳定审计事件。

错误选择 403 或隐藏式 404 应按接口威胁模型决定；不应无意泄露其他租户对象存在性。异步任务必须携带受控身份信息，不在工作执行时读取已经消失的“当前请求”。

## 5. 练习与答案

### 5.1 开启 CORS 白名单后，服务端还需要鉴权吗？

答案：需要。CORS 是浏览器策略，不是服务端身份与资源权限校验。

### 5.2 tenant_id 来自请求体，可以直接写入记录吗？

答案：通常不能，应从可信身份或受控授权关系确定。否则用户可能伪造归属。

### 5.3 读取接口隔离了，更新接口忘加租户条件会怎样？

答案：仍可能跨租户修改，隔离需要覆盖所有查询与写入路径，还包括缓存与后台任务。
