# 中间件、异常与请求上下文

中间件包在应用调用链外侧，可以观察请求与响应，但不是所有异常都能在任意位置转换成新的响应。先理解调用顺序，再放置认证、日志和计时逻辑。

## 1. 进入与返回顺序

外层先处理请求，再调用内层；响应沿相反方向返回。多个中间件的实际顺序取决于注册与构建方式，应通过小实验观察，不按配置文件视觉顺序猜测。

框架中的处理型异常、未捕获服务器错误与响应发送后的异常，具有不同处理边界。不要指望一个 try/except 在任何时刻都能重发 JSON 错误。

## 2. 请求上下文示例

```python title="api_middleware.py"
from contextvars import ContextVar
from uuid import uuid4
from fastapi import FastAPI

request_id = ContextVar("request_id", default="none")
app = FastAPI()

@app.middleware("http")
async def context(request, call_next):
    identifier = uuid4().hex
    token = request_id.set(identifier)
    try:
        response = await call_next(request)
        response.headers["X-Request-ID"] = identifier
        return response
    finally:
        request_id.reset(token)

@app.get("/jobs")
async def jobs():
    return {"has_context": request_id.get() != "none"}

def main():
    from fastapi.testclient import TestClient
    with TestClient(app) as client:
        response = client.get("/jobs")
        print(response.status_code, response.json())
        print(len(response.headers["X-Request-ID"]) == 32)
    print(request_id.get())

if __name__ == "__main__":
    main()
```

```text title="api_middleware.out"
200 {'has_context': True}
True
none
```

服务端生成请求 ID，不直接信任任意客户端字符串。上游 Trace/请求标识需要验证格式与信任边界，再选择保留或重新生成。

## 3. 异常的责任

HTTPException 表达预期的 HTTP 拒绝；RequestValidationError 对应输入契约问题；未预期异常应保留服务器端堆栈，对外使用稳定且不泄密的错误体。

避免在每层重复记录同一异常。响应尚未开始时可以构造错误响应；SSE 或下载已经开始后失败，通常只能终止流并记录关联证据。

## 4. 上下文传播限制

ContextVar 绑定与可变对象共享是两回事。跨线程、后台任务和第三方中间件实现的传播，也有各自边界；Starlette 的 BaseHTTPMiddleware 存在需要了解的上下文行为限制，要求严格传播时可考虑纯 ASGI 中间件。

不要将大请求对象长期保留在上下文或后台回调。请求结束必须恢复 token，避免逻辑状态延长到不该存在的生命周期。

## 5. 练习与答案

### 5.1 日志中间件能记录响应后所有后台异常吗？

答案：不能自动保证。响应与后台工作的执行边界不同，需要分别观察与关联异常。

### 5.2 客户端的请求 ID 可以不加限制写日志吗？

答案：不应如此。可能包含超长或特殊内容，应按信任边界验证，并使用结构化日志。

### 5.3 为什么 finally 里还要 reset token？

答案：恢复进入前的上下文绑定，正常与异常路径都保持生命周期完整，不依赖请求碰巧结束。
