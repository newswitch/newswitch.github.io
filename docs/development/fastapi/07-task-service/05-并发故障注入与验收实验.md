# 并发故障注入与验收实验

综合项目的价值在于验证多个边界一起工作。只测试 POST 返回 201，无法发现重复创建、租约过期写回、跨租户读取、断线漏事件或提交前返回成功。

## 1. 先读测试的资源范围

`examples/fastapi/task-service/tests/test_tasks.py` 为每个测试建立临时 SQLite 文件；异步测试使用 AnyIO 的 asyncio 后端。Engine 与会话在同一测试循环内创建和关闭，不把一个循环创建的池拿到另一个循环使用。

```bash
python -m pytest -q tests
```

从 task-service 目录执行。HTTPX ASGITransport 不自动替代全部启动行为，所以测试显式进入 app.router.lifespan_context；TestClient 另用上下文管理器覆盖相应同步入口。进程内测试不证明 TCP、代理与容器行为。

## 2. 并发不是顺序请求的另一种名字

四个 create_job 通过 gather 同时提交相同租户、键和内容。检查只有一个 created=True、所有返回 id 相同；数据库和事件表也应只有一个创建结果。每项工作各用独立 Session，保留唯一约束竞争窗口。

领取竞争让三个 Worker 同时 claim 一个任务，只有一个得到 Lease。测试使用真实数据库事务竞争，而不是直接 Mock 一次“领取成功”；但 SQLite 的锁模型仍不能证明 PostgreSQL 分支完全相同。

把隔离数据库换成 PostgreSQL 后，应重做重复提交、SKIP LOCKED、锁超时与断连测试。使用独立学习库，不让并发测试在生产表上创建或清理数据。

## 3. 用时钟控制恢复，而不是等待碰巧超时

Worker 接收可替换 clock，测试可以精确推进租约时间：

| 动作 | 应观察的状态 |
| --- | --- |
| 时间 100，W1 领取 | running，attempts=1 |
| 有效期内另一个领取者请求 | 无可领取项 |
| 时间推进到租约之后 | W2 可以接手，token 不同 |
| W1 尝试提交 | False，没有旧结果 |
| W2 提交 | done，唯一结果 |
| W2 再提交 | False，不重复产生结果 |

类似地验证重试的 available_at 与预算，最后一次领取后直接消失也会收敛到 failed。可控时钟验证状态判断，不模拟真实跨机器时钟漂移；后者需要目标环境时间源与暂停实验。

## 4. 取消和断线要验证清理

执行函数用 Event 告知“已经进入受保护工作”，然后等待另一个 Event。测试取消 Worker Task，再 await 它，最后检查 finally 已执行、Result 没有出现。只调用 cancel 后立刻检查，会把“已请求取消”误认为“已经完成取消”。

API 取消与 Worker 提交还存在并发顺序：谁先取得并成功提交条件变化，决定结果。客户端要处理取消请求遇到 409 的情况，不能在工作已经完成后宣称副作用被撤销。

事件测试先读第一条，保存位置，再带 Last-Event-ID 重读，确认不重返已确认位置且不包含其他租户数据。无限流的真实客户端断开、代理缓冲与慢读需要额外的真实 HTTP 实验，有限 ASGI 测试不能替代。

## 5. 从失败现象追到证据

| 现象 | 先验证 | 不能直接下的结论 |
| --- | --- | --- |
| POST 超时但出现任务 | 幂等键与事务是否已提交 | 超时等于没执行 |
| 长时间 running | 租约、最后续租、Worker 与 DB 状态 | 改成 pending 就安全 |
| Worker 完成但 API 无结果 | 实际数据库、提交结果、租户与事务 | 一定是接口缓存 |
| SSE 没新事件 | 事件表、游标、租户、代理缓冲 | TCP 通就保证首块及时到达 |
| 连接池耗尽 | 谁持有会话、事务与发送等待 | 把池调大就根治 |

修复后使用同一输入和负载重跑，并检查错误路径没有留下资源。不要只通过增加重试掩盖失败，否则数据库与下游会一起承受放大流量。

## 6. 分清已经验证的层

本机测试覆盖 Python 规则、SQLite 事务、ASGI 请求和有限事件重放；真实环回服务实验见[压测对照](../06-internals-diagnostics/05-并发压测与瓶颈对照实验.md)。PostgreSQL 锁分支、Linux 信号、容器与 Kubernetes 需要在对应环境完成相同断言，不能从其他平台测试通过推导。

读者可以先独立实现一个“重试失败任务”的受权接口：只允许 failed 转回 pending，使用版本条件，保留审计事件，不能重试 cancelled/done。通过这些断言，比仅增加一个成功返回的路由更能验证对状态机和一致性的理解。

## 7. 练习与答案

### 7.1 怎样证明任务恢复不是重新提交碰巧生成的？

答案：保存原任务 id 和幂等键，不再发 POST，模拟领取者消失并推进租约；接手后检查相同任务 attempts 增加且只有一份最终结果。

### 7.2 Mock Worker 总返回成功，能代替租约测试吗？

答案：不能。它能测试调用方分支，但没有运行条件更新、事务竞争和过期所有权判断。需要真实隔离数据库中的状态断言。

### 7.3 实现重试接口后，最重要的反例有哪些？

答案：过期版本、其他租户、权限不足、终态不允许、并发两次重试、事务失败。失败后原状态与事件应保持一致，不能只检查返回码。
