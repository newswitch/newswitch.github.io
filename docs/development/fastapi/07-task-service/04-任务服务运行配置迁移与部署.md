# 任务服务运行配置、迁移与部署

先用独立 SQLite 文件把 API、数据库和 Worker 连起来，再把相同结构放到 PostgreSQL 与容器环境。教学目录的文件不是现有业务数据库的升级脚本，所有命令都应指向新建实验环境。

## 1. 创建统一解释器环境

从仓库根目录执行 Windows 命令：

```powershell
python -m venv .python-article-checks/study-venv
.\.python-article-checks\study-venv\Scripts\python.exe -m pip install -r examples/fastapi/deepening.lock
.\.python-article-checks\study-venv\Scripts\python.exe -m pip check
```

先确认 python 是常规 CPython 3.14。Linux 使用 `python3 -m venv`，解释器在 study-venv/bin/python。后续 python 指向同一个环境；可以激活，也可以始终使用完整路径，不能给一个解释器安装、让另一个执行。

进入 `examples/fastapi/task-service` 后设置配置：

```powershell
$env:APP_JWT_SECRET = python -c "import secrets; print(secrets.token_hex(32))"
$env:APP_DATABASE_URL = 'sqlite+aiosqlite:///./tasks.db'
python -m alembic upgrade head
$token = python -m task_service.cli token --tenant lab
$headers = @{Authorization="Bearer $token"; 'Idempotency-Key'='first'}
```

首次迁移创建四张表与 Alembic 版本表，重复 upgrade 不重复建表。相对 SQLite URL 以进程工作目录为基准，API 与 Worker 必须在相同目录运行；迁移、启动和测试不得误指向已有数据库。

Settings 检查显式异步驱动与密钥长度。生成的是本地实验秘密，不使用测试代码中的固定密钥；token 是十五分钟有效的实验凭证，后续过期时重新签发。

## 2. 启动 API 并发出第一个请求

在配置已准备的终端启动：

```bash
python -m uvicorn task_service.main:create_from_env --factory --host 127.0.0.1 --port 8000
```

该终端被前台服务占用。在另一个客户端终端设置相同的本地签发配置并取得 token/headers，再请求：

```powershell
Invoke-RestMethod -Method Post -Uri http://127.0.0.1:8000/jobs -Headers $headers -ContentType application/json -Body '{"name":"import"}'
```

新库应返回 id=1、state=pending、revision=0、attempts=0。已有数据时以实际 id 为准。重复同键同内容返回已有任务，改内容而不改键应冲突。

环境变量不会自动跨终端共享。需要让多个终端使用同一实验配置时，可用编辑器将 .env.example 复制为项目目录的 .env，把占位密钥替换为刚生成的本地秘密；Settings 会读取该文件，环境变量优先于文件。.env 已被忽略，不提交 Git，Linux 应限制文件权限；生产使用受控 Secret，不沿用实验配置。若签发 token 的密钥与 API 不同，收到 401 是正确拒绝，不是数据库没连上。

## 3. 启动独立 Worker

Worker 终端使用相同数据库 URL，执行：

```bash
python -m task_service.cli worker --once
```

有一个可领取任务并成功提交时输出 `{"completed": true}`；没有可领取项时为 false。随后查询 `GET /jobs/1`，状态应为 done、attempts=1、result=IMPORT。多次执行不会再次完成同一终态任务。

不加 --once 会持续轮询。Linux Worker 收到 SIGTERM 后停止领取，等待当前有限工作结束并关闭 Engine；异常中断依赖租约过期恢复。协程超时不能强行抢占一个永不让出的 CPU 循环，长期 CPU 工作需要适当进程隔离与独立终止协议。

## 4. 切换 PostgreSQL 与 Compose

同目录的 compose.yaml 包含独立 PostgreSQL、迁移、API 与 Worker。数据库只把 5433 绑定到主机环回，API 同样只暴露本机 8000。为实验生成不含 URL 保留字符的十六进制密码和密钥后：

```powershell
$env:PG_PASSWORD = python -c "import secrets; print(secrets.token_hex(16))"
$env:APP_JWT_SECRET = python -c "import secrets; print(secrets.token_hex(32))"
docker compose up --build -d
docker compose ps
docker compose logs --tail 50 migrate api worker
```

先确认端口没有被自己的其他实验占用。Compose 等数据库健康后执行一次迁移，迁移成功后才启动 API/Worker；仅 depends_on 启动顺序不等于数据库已经可用，因此这里明确健康与完成条件。

Dockerfile 的构建上下文是 examples/fastapi，以便读取统一依赖。示例包含测试依赖，生产应裁剪运行集合并对目标 Linux/架构重新锁定。基础镜像与 postgres:18 标签可能移动，部署应固定已验证 digest；本机 Windows 测试不替代镜像内验证。

pgdata 保存数据库数据。普通停止保留数据；不要在不知道内容的情况下执行删除卷命令。凭证改变但沿用旧卷时，数据库初始化环境变量不会自动重建已有用户密码。

## 5. Kubernetes 与退出边界

deploy.yaml 是目标测试环境模板。先准备真实镜像与同命名空间 Secret，包含 APP_DATABASE_URL、APP_JWT_SECRET；迁移 Job 使用同一结构版本。先运行并等待迁移成功，再上线 API 与 Worker，整份 YAML 一次 apply 不会自动保证这条依赖。

API readiness 查询任务表，缺表或数据库不可用时拒绝接流量；liveness 检查应用还能响应，不因一次数据库故障就循环重启。资源数值是示例，连接预算应同时计算 API 副本、Worker 与迁移。

API 退出时先停止新请求，再等待在途并关闭生命周期资源；入口摘流存在传播时间，长连接还要重新连接。Worker 退出与 API 退出不同：前者关心停止领取和租约，后者关心连接与响应。宽限时间必须覆盖其有限收尾，而不是只统一设置一个很短的值。

## 6. 练习与答案

### 6.1 API 和 Worker 都显示同一个相对 URL，为什么看不到同一任务？

答案：工作目录可能不同，实际打开了不同 tasks.db。核对绝对路径、进程目录与迁移目标；不要只比较 URL 字符串。

### 6.2 重建 API 容器后任务还在，说明数据存在哪？

答案：该部署中应在 PostgreSQL 的持久卷，而不是 API 内存。进一步停止 Worker 再提交任务，恢复 Worker 后仍能领取，才能验证持久化执行链路。

### 6.3 迁移失败，可以先把所有 API 拉起来再处理吗？

答案：不应把未满足结构契约的应用投入服务。先定位目标、权限、版本与锁；readiness 应阻止接流量，但它不能替代正确的迁移依赖。
