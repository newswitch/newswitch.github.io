# GC 日志、安全点与延迟归因

请求慢时恰好发生了一次 GC，只能说明时间相关，不足以证明 GC 是根因。要把应用停止的区间、请求所处阶段和系统资源放在同一时间轴上。

## 1. 先让日志可关联且有边界

在可写、独立且已评估容量的目录配置：

```bash
java -Xlog:gc*,safepoint:file=gc-%p.log:time,uptime,level,tags:filecount=5,filesize=10m -jar app.jar
```

`time` 是墙钟时间，`uptime` 是进程启动后时间，`%p` 代入 PID；轮转限制文件数量和目标大小，不是总文件永远精确等于 50 MiB。日志 I/O、磁盘空间和时钟同步也要监控。

固定 JDK 与实际收集器后再解读。旧的 `PrintGCDetails`、CMS 日志样式不能直接拿来套 JDK 25；也不要按 G1 的代数列解释 ZGC。

## 2. 读懂一组 G1 日志

以下为教学示意，数值不是某个生产事故的实测：

```text
[1.100s][info][gc,start] GC(7) Pause Young (Normal) (G1 Evacuation Pause)
[1.104s][info][gc] GC(7) Pause Young (Normal) (G1 Evacuation Pause) 80M->12M(128M) 4.000ms
[1.104s][info][gc,cpu] GC(7) User=0.01s Sys=0.00s Real=0.00s
```

用 GC(7) 关联同一事件，不把不同编号的阶段拼成一次回收。`80M->12M` 表示事件前后堆占用；4 ms 是暂停。CPU 行精度有限，Real 显示 0.00s 不代表零耗时。并行工作时多个线程的 User 总和可以大于墙钟 Real。

如果 Real 明显变大而 User/Sys 没同比例增加，要继续看 CPU 限流、主机抢占等，不能马上认定“回收算法变慢”。

## 3. 安全点多了一段到达时间

日志中的 safepoint 行常区分 Reaching safepoint、Cleanup、At safepoint、Total 等部分。字段随版本略有变化，应读当前输出：

```text
Safepoint "...", ... Reaching safepoint: ... ns,
Cleanup: ... ns, At safepoint: ... ns, Total: ... ns
```

“到达安全点慢”和“安全点内工作慢”是两类方向。前者要查线程执行状态、native 路径与调度，后者看操作类型及分阶段成本。安全点也可能服务于非 GC 操作，因此不能把所有暂停都记到 GC 的账上。

## 4. 对齐业务时间，才谈贡献

假设一个请求从 1.090s 到 1.390s，共 300 ms，其中与一次 4 ms 全局暂停重叠。这次暂停不足以单独解释 300 ms；继续拆分入口排队、取连接、下游、序列化及 CPU 等待。

但也不能反过来说“只有 4 ms，所以完全无影响”：高利用率系统可能在暂停后积累队列，造成更长尾部恢复。要同时看暂停前后到达率、服务能力、队列深度和恢复速度，区分直接停顿与间接放大。

P99 不是把各组件 P99 相加；不同请求经历的阶段、相关性和样本集不同。应优先对同一慢请求或同一窗口进行关联分析。

## 5. 用已知负载产生自己的日志

使用 [GcWorkload](../04-jvm/05-G1-Region标记复制与暂停.md)，先编译到 out：

```bash
java -Xms64m -Xmx64m -XX:+UseG1GC -Xlog:gc*,safepoint:file=gc-lab.log:time,uptime,level,tags -cp out GcWorkload
```

Linux 筛选片段：

```bash
grep -E 'Using G1|Pause Young|Pause Full|Evacuation|Safepoint' gc-lab.log
```

PowerShell 对照：

```powershell
Select-String -LiteralPath ./gc-lab.log -Pattern 'Using G1|Pause Young|Pause Full|Evacuation|Safepoint'
```

检查启动行确实为 G1，至少找到年轻代回收及相关事件。程序的正确性输出固定，但 GC 次数、Region 角色和耗时不固定。这不是验证线上吞吐或 P99 的压测，不能从中得出业务容量上限。

## 6. 从现象到下一条证据

| 现象 | 候选方向 | 下一条证据 |
| --- | --- | --- |
| Young 很频繁，回收后很低 | 分配速率高 | 分配采样、输入和批大小 |
| GC 后基线持续上升 | 长期存活或泄漏 | 同负载趋势、引用链 |
| 复制阶段长 | 存活量、对象结构、CPU | 分阶段日志、配额与 Profile |
| Humongous 占比高 | 大数组/连续区域压力 | 分配路径、大小分布 |
| ZGC pause 短但线程等分配 | 回收追不上分配 | Allocation Stall、余量、CPU |
| 慢请求没有暂停重叠 | 非暂停主导 | 队列、锁、连接、下游、限流 |

候选方向不是结论，必须有能推翻它的观测。出现 Full GC 也要看 cause，外部诊断工具触发与自然空间压力的处理不同。

## 7. 如何做一次有效参数实验

固定版本、负载和正确性；记录基线；只改一个有明确意图的配置；同时比较吞吐、延迟、错误、CPU、内存与 GC。若暂停降低但错误上升或内存突破容器限制，应判定整体不满足目标，而不是只挑一项变绿。

采集本身也影响现场。高等级日志、堆直方图、转储与动态增强若同时打开，可能制造额外停顿；必须把这些采集时间记录进时间轴。

## 8. 练习与答案

### 8.1 Concurrent Cycle 200 ms，是否所有请求都停了 200 ms

不是。周期中有与应用并发执行的工作，应分别观察暂停和分配等待；不能把整个周期当成 STW。

### 8.2 User 时间比 Real 大，是否日志坏了

不一定。多个 GC 线程并行时，累计 CPU 时间可以超过墙钟时间；也要注意显示精度和单位。

### 8.3 GC 次数少了，是否证明优化成功

不一定。可能每次更长、堆更大、错误更多或排队加重。应以相同负载下的业务目标及总体资源成本判断。
