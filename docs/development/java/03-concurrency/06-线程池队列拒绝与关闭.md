# 线程池、任务队列、拒绝策略与关闭

线程池复用执行线程，并为任务提供统一生命周期。它也是排队系统：生产速度长期超过处理能力时，必须在等待时间、内存占用与拒绝之间做明确选择。

本篇使用 JDK 25，用一条被控制阻塞的任务稳定演示“运行一个、排队一个、拒绝一个”。

## 1. execute 接收任务的主要路径

![线程池的提交、排队、扩展与拒绝路径](/img/development/executor.svg)

核心线程之后先尝试排队，队列不能接收时才可能扩展到最大线程数。图中的拒绝与执行是不同结果，不能把拒绝策略当成无代价等待。

```text
工作线程少于 corePoolSize → 尝试增加线程执行
否则 → 尝试入队
       ├── 入队成功：由工作线程取走
       └── 入队失败：尝试增至 maximumPoolSize
                      └── 仍无法接收：执行拒绝策略
```

实现还会重新检查关闭状态和工作线程存活等条件，上图用于理解主要容量关系，不是并发源码的逐行替代。

关键点是**先排队，再尝试扩到最大线程数**。无界队列通常会让 maximumPoolSize 对过载扩容几乎不起作用，积压转移到堆内存和等待时间。SynchronousQueue 没有普通存储容量，体现直接交接，行为又不同。[ThreadPoolExecutor API](https://docs.oracle.com/en/java/javase/25/docs/api/java.base/java/util/concurrent/ThreadPoolExecutor.html)说明了策略组合。

## 2. 拒绝必须成为调用契约

AbortPolicy 抛 RejectedExecutionException；CallerRunsPolicy 在特定状态下由提交者执行，可能形成反馈，但会占住请求线程或事件循环，关闭后也有丢弃边界。Discard 类策略可能静默丢任务，配合 submit 更要防止 Future 永远没有正常完成路径。

容量要综合线程数、任务队列、下游连接与请求正文大小，不能只看队列元素数量。超时预算还要包含排队等待，而不是任务开始执行后才计时。

## 3. 有界队列实验

```java title="PoolDemo.java"
import java.util.concurrent.ArrayBlockingQueue;
import java.util.concurrent.CountDownLatch;
import java.util.concurrent.RejectedExecutionException;
import java.util.concurrent.ThreadPoolExecutor;
import java.util.concurrent.TimeUnit;

public class PoolDemo {
    public static void main(String[] args) throws Exception {
        var entered = new CountDownLatch(1);
        var release = new CountDownLatch(1);
        var pool = new ThreadPoolExecutor(1, 1, 0, TimeUnit.SECONDS,
                new ArrayBlockingQueue<>(1), new ThreadPoolExecutor.AbortPolicy());
        try {
            var first = pool.submit(() -> {
                entered.countDown();
                release.await();
                return 7;
            });
            if (!entered.await(5, TimeUnit.SECONDS)) {
                throw new IllegalStateException("first task did not enter");
            }
            var second = pool.submit(() -> 21);
            System.out.println("queued=" + pool.getQueue().size());
            try {
                pool.execute(() -> {});
                throw new IllegalStateException("expected rejection");
            } catch (RejectedExecutionException expected) {
                System.out.println("rejected=true");
            }
            release.countDown();
            System.out.println("first=" + first.get(5, TimeUnit.SECONDS));
            System.out.println("second=" + second.get(5, TimeUnit.SECONDS));
        } finally {
            release.countDown();
            pool.shutdown();
            if (!pool.awaitTermination(5, TimeUnit.SECONDS)) {
                pool.shutdownNow();
                if (!pool.awaitTermination(5, TimeUnit.SECONDS)) {
                    throw new IllegalStateException("pool did not terminate");
                }
            }
        }
        System.out.println("terminated=" + pool.isTerminated());
    }
}
```

```bash
javac -encoding UTF-8 --release 25 -d out PoolDemo.java
java -cp out PoolDemo
```

```text title="expected-output"
queued=1
rejected=true
first=7
second=21
terminated=true
```

release 在 finally 也会打开，避免主线程错误后把工作线程永久留在等待中。正常运行时不靠暂停时间制造队列满，而是由 entered 与 release 明确控制。

## 4. execute 与 submit 的异常差异

execute 中未捕获的任务异常通常走线程的未捕获异常处理；submit 使用 Future 保存失败，调用 get 时以 ExecutionException 报告。提交后从不观察 Future，可能让失败在日志中“消失”。

为线程命名、为任务记录等待与运行耗时，并让失败与请求标识关联。线程池钩子可以辅助观测，但要理解 Future 包装后的异常，不要只依赖 afterExecute 的 Throwable 参数。

## 5. 容量规划与隔离

CPU 密集任务首先受可用 CPU 和竞争影响；阻塞任务还受等待比例与下游容量影响。公式只是估算起点，应在真实容器 CPU 配额、任务分布和下游限制下测试。

给数据库、远端 API 与批处理共用一个池，某个依赖变慢可能占满所有执行能力。可按依赖建立舱壁，并限制入口队列。队列再大也不能修复处理能力不足，只会推迟失败并增加尾延迟。

线程池内部再提交任务到同一个已饱和池，然后同步 get 等待，可能形成线程饥饿死锁。改成不阻塞的组合、分离执行域，或重新设计任务依赖。

## 6. 关闭不是取消所有业务

shutdown 停止接收新任务，已接收任务继续处理；shutdownNow 尝试中断运行任务，并返回尚未开始的任务。它不保证立即终止，也不自动替所有排队 Future 完成取消，调用方需要处理返回任务与结果通知。

ExecutorService.close 可用于结构化资源释放，但可能等待任务结束，不是天然的短时关闭策略。服务退出需要定义停止入口、排空预算、取消与最终报告，且任务自身必须响应取消。

## 7. 练习与答案

### 7.1 核心 4、最大 100、无界队列，为什么通常只看到 4 个忙线程

核心线程达到后，任务持续成功入队，通常不触发进一步扩线程。应同时看队列与等待时间，而不是只调大 maximumPoolSize。

### 7.2 CallerRunsPolicy 能放在网络事件循环里随意使用吗

不能。提交者可能直接执行慢任务，拖住所有依赖该事件循环的连接。背压策略必须与调用者线程职责匹配。

### 7.3 get 超时后，任务会自动从池里消失吗

不会。等待超时不等于任务取消，仍可能继续占用线程或排队。需要显式取消与资源协议，下一篇继续分析。
