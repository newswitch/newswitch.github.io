# 虚拟线程、载体线程与资源上限

平台线程通常与操作系统线程一一对应；虚拟线程由 JVM 调度到载体平台线程上执行。大量任务等待 I/O 时，虚拟线程可以降低“每个等待任务必须长期占住一个平台线程”的成本，但不会增加 CPU、数据库连接或远端容量。

本篇使用 JDK 25 正式 API。先区分线程成本和业务资源成本，再决定是否迁移。

## 1. 挂载与卸载

```text
虚拟线程 A 执行 Java 代码 → 挂载到载体线程
遇到可支持的阻塞等待 → 保存执行状态、卸载
载体执行其他虚拟线程
等待条件满足 → A 再次被调度，载体不一定还是原来的
```

Thread.currentThread 返回当前虚拟线程，不是其载体。线程本地上下文属于虚拟线程，不会因为换载体就变成其他任务的值。也不能依赖载体身份绑定业务状态。

虚拟线程适合以简单同步代码表达大量等待型任务。CPU 密集计算仍受可用核心限制，创建更多线程不能让相同 CPU 工作无限加速。[Thread API](https://docs.oracle.com/en/java/javase/25/docs/api/java.base/java/lang/Thread.html)描述了平台线程与虚拟线程的区别。

## 2. 不为虚拟线程再造固定工作池

newVirtualThreadPerTaskExecutor 为每个任务创建虚拟线程，不是固定数量的虚拟工作线程。通常应把限制放在数据库连接、HTTP 并发、在途任务数等真正稀缺资源上，而不是为了复用线程再建一个虚拟线程池。

资源隔离仍需要排队上限和 deadline。即使每个虚拟线程较轻，百万个等待任务仍有对象、栈块、上下文、请求正文和响应状态成本。

## 3. 六个任务共享两个许可

```java title="VirtualDemo.java"
import java.util.ArrayList;
import java.util.concurrent.CountDownLatch;
import java.util.concurrent.Executors;
import java.util.concurrent.Future;
import java.util.concurrent.Semaphore;
import java.util.concurrent.TimeUnit;
import java.util.concurrent.atomic.AtomicInteger;

public class VirtualDemo {
    public static void main(String[] args) throws Exception {
        var permits = new Semaphore(2);
        var firstTwo = new CountDownLatch(2);
        var release = new CountDownLatch(1);
        var active = new AtomicInteger();
        var peak = new AtomicInteger();
        var results = new ArrayList<Future<Boolean>>();
        try (var executor = Executors.newVirtualThreadPerTaskExecutor()) {
            try {
                for (int i = 0; i < 6; i++) {
                    results.add(executor.submit(() -> {
                        if (!permits.tryAcquire(5, TimeUnit.SECONDS)) {
                            throw new IllegalStateException("permit timed out");
                        }
                        try {
                            int current = active.incrementAndGet();
                            peak.accumulateAndGet(current, Math::max);
                            firstTwo.countDown();
                            if (!release.await(5, TimeUnit.SECONDS)) {
                                throw new IllegalStateException("release timed out");
                            }
                            return Thread.currentThread().isVirtual();
                        } finally {
                            active.decrementAndGet();
                            permits.release();
                        }
                    }));
                }
                if (!firstTwo.await(5, TimeUnit.SECONDS)) {
                    throw new IllegalStateException("tasks did not enter");
                }
            } finally {
                release.countDown();
            }
            int virtual = 0;
            for (Future<Boolean> result : results) {
                if (result.get(5, TimeUnit.SECONDS)) virtual++;
            }
            System.out.println("completed=" + results.size());
            System.out.println("virtual=" + virtual);
            System.out.println("peakActive=" + peak.get());
            System.out.println("available=" + permits.availablePermits());
        }
    }
}
```

```bash
javac -encoding UTF-8 --release 25 -d out VirtualDemo.java
java -cp out VirtualDemo
```

```text title="expected-output"
completed=6
virtual=6
peakActive=2
available=2
```

两个任务同时进入后才开放 release，确保 peak 确实达到 2；许可保证不会超过 2。这里的阻塞只是协调实验，不是 I/O 性能基准。虽然只放行两个任务，仍然创建了六个虚拟线程；生产入口还需单独控制在途总量。

## 4. JDK 25 中的固定问题

旧资料经常指出 synchronized 区域中的阻塞会把虚拟线程固定在载体上。JDK 24 通过 JEP 491 改进监视器实现，JDK 25 不能继续照搬“只要 synchronized 就必然固定”的结论，参见 [JDK 24 变更说明](https://docs.oracle.com/en/java/javase/25/migrate/significant-changes-jdk-24.html)。保持正确同步比机械把所有 synchronized 改成 Lock 更重要。

native/foreign 调用及具体底层路径仍可能存在固定或占住载体的情况；也有操作并不表现为简单的可卸载等待。需要按 JDK 版本、调用栈和实测证据分析。[JDK 25 虚拟线程说明](https://docs.oracle.com/en/java/javase/25/core/virtual-threads.html)与 [JEP 491](https://openjdk.org/jeps/491)解释了相关范围，不能把一次版本改进扩大为“所有阻塞都免费”。

## 5. 排查应观察什么

同时看请求并发、等待时间、活跃下游连接、CPU、分配与内存，而不是只数操作系统线程。传统 Thread.activeCount/getAllStackTraces 等观察接口对虚拟线程有范围限制，不能据此计算全部任务。

可以用 JDK 的线程转储和 JFR 工具查看虚拟线程活动；事件和默认记录阈值随版本及配置变化，应检查当前工具支持。若阻塞集中在同一连接池，先分析连接池和下游，不要直接调大载体调度参数。

虚拟线程是 daemon 线程，不应依赖它们让进程继续存活。示例明确关闭执行器并等待结果；服务中也要定义接收停止、取消、排空与最终退出。

## 6. 迁移前检查

任务是否以等待为主；库是否支持所用 JDK；是否持锁跨慢调用；是否把大缓存存于 ThreadLocal；连接池与入口是否有边界；取消是否可达底层操作。这些条件比“把执行器替换成虚拟线程”更决定收益。

## 7. 练习与答案

### 7.1 虚拟线程增加十倍，模型计算能快十倍吗

不能。CPU/GPU 计算受硬件和执行路径限制，等待线程的成本降低不等于算力增加。仍需批处理、并行算法和资源调度。

### 7.2 Semaphore 设为 20，就最多只有 20 个等待请求吗

不是。它只限制成功获得许可的并发，可能还有大量等待者。入口还应限制总在途数量、等待时间和请求内存。

### 7.3 JDK 25 是否应该删除所有 synchronized

不应该。它仍是正确同步机制，旧版本的固定问题不能作为全面替换理由。根据实际争用、持锁范围和执行路径决定改动。
