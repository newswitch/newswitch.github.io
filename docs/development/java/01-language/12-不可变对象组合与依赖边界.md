# 不可变对象、组合与依赖边界

对象设计的目标不是堆满 getter/setter，而是让合法操作容易表达，让不合法状态难以产生。不可变值负责稳定地传递事实，可变对象负责约束状态迁移，接口负责把业务与外部资源隔开。

本篇使用 JDK 25，用纯 Java 完成一次装配。Spring 后续接管的是对象连接过程，不会替代业务规则。

## 1. 不可变对象需要哪些条件

只写 final 不够。对象创建时要完成有效初始化；不要提供修改其可观察状态的方法；可变输入要复制；返回可变内部数据时也要保护；构造期间不要把 this 泄露给其他代码。

不可变对象便于共享和复用，但“保存不可变对象的容器”仍可能可变，多个线程更新共享引用也仍需要同步。final 字段的初始化语义不能替代整个程序的并发设计。

## 2. 用组合划分责任

```text
调用者 → TaskService → TaskStore 接口 → 内存或数据库实现
                   ↘ TaskSnapshot 不可变值
```

TaskService 并不是一种 TaskStore，因此不应该继承仓储类来获得保存能力。让它持有接口引用表达“使用仓储”，可以单独测试规则，也能替换存储实现。

接口不是越多越好。只有稳定能力或真实替换边界才值得抽象；为每个只有一行转发的方法再造接口，会增加理解成本。

## 3. 完整实验

```java title="DesignDemo.java"
import java.util.ArrayList;
import java.util.List;
import java.util.Objects;

public class DesignDemo {
    record TaskSnapshot(String title, List<String> labels) {
        TaskSnapshot {
            title = Objects.requireNonNull(title).strip();
            if (title.isEmpty()) {
                throw new IllegalArgumentException("empty title");
            }
            labels = List.copyOf(labels);
        }
    }

    interface TaskStore {
        void save(TaskSnapshot task);
        List<TaskSnapshot> findAll();
    }

    static final class MemoryStore implements TaskStore {
        private final List<TaskSnapshot> tasks = new ArrayList<>();

        public void save(TaskSnapshot task) {
            tasks.add(Objects.requireNonNull(task));
        }

        public List<TaskSnapshot> findAll() {
            return List.copyOf(tasks);
        }
    }

    static final class TaskService {
        private final TaskStore store;

        TaskService(TaskStore store) {
            this.store = Objects.requireNonNull(store);
        }

        void submit(String title, List<String> labels) {
            store.save(new TaskSnapshot(title, labels));
        }
    }

    public static void main(String[] args) {
        var store = new MemoryStore();
        var service = new TaskService(store);
        var labels = new ArrayList<>(List.of("daily"));
        service.submit(" backup ", labels);
        labels.clear();
        List<TaskSnapshot> snapshot = store.findAll();
        service.submit("verify", List.of());
        System.out.println("firstLabels=" + snapshot.getFirst().labels());
        System.out.println("oldSize=" + snapshot.size());
        System.out.println("currentSize=" + store.findAll().size());
        try {
            snapshot.clear();
        } catch (UnsupportedOperationException expected) {
            System.out.println("snapshot=unmodifiable");
        }
    }
}
```

```bash
javac -encoding UTF-8 --release 25 -d out DesignDemo.java
java -cp out DesignDemo
```

```text title="expected-output"
firstLabels=[daily]
oldSize=1
currentSize=2
snapshot=unmodifiable
```

构造器接收依赖，就是最直接的依赖注入；main 是本例的装配点。读取仓储得到快照，不是可写的内部列表。示例不提供并发安全或事务保证，换成数据库实现时必须重新定义这些契约。

## 4. 快照、视图和深复制

`List.copyOf(tasks)` 表达不可修改的结构快照。`Collections.unmodifiableList(tasks)` 只是只读视图，仓储再新增任务时，旧视图也会变化。二者都不递归复制元素。[List API](https://docs.oracle.com/en/java/javase/25/docs/api/java.base/java/util/List.html)明确了不可修改列表的边界。

本例元素由 String 和不可修改的 String 列表组成，能够稳定表达快照。如果将来增加可变 Date、数组或其他业务对象，需要重新审视输入复制、输出访问器和相等性，而不能只看外层 record。

## 5. 从包边界到模块边界

真实工程可以把 TaskSnapshot 和 TaskStore 放在业务 API 包，将 MemoryStore 放到实现包。public 决定 Java 层面的可访问性，不意味着所有实现都应该成为长期公共 API。

Java 模块系统进一步区分：`requires` 声明模块依赖，`exports` 暴露包给普通访问，`opens` 允许相应深反射。它们不是 Maven 下载依赖的替代品；Classpath 与 Module Path 也不是同一套组织方式。模块细节遵循 [JLS 包与模块](https://docs.oracle.com/javase/specs/jls/se25/html/jls-7.html)。

入门项目先把包和依赖方向理清，再根据交付边界使用模块，不必为了一个小程序拆出大量模块。

## 6. 从设计规则落到测试

应验证空标题被拒绝、外部 labels 改动不影响已保存任务、旧快照不随仓储增长，以及替换仓储后业务规则保持一致。异常也应表达明确边界：存储失败不能返回“提交成功”。

如果为保存操作增加重试装饰器，应通过组合包装 TaskStore，并先确认重复调用是否会产生重复任务。面向接口并不会自动获得幂等性。

## 7. 练习与答案

### 7.1 把 tasks 声明 final，为什么还需要复制

final 只禁止把字段指向另一列表，仍允许 tasks.add。直接返回 tasks 会让调用者绕过仓储方法修改内部数据，因此仍要保护输出。

### 7.2 TaskService 为什么不能直接 new 数据库仓储

可以这样写，但业务将绑定实现、连接参数和资源生命周期，测试也难以隔离。由装配点传入接口实现，可以分别验证业务和存储；并不要求必须使用框架。

### 7.3 不可变快照是否意味着 MemoryStore 线程安全

不是。ArrayList 的并发读写仍不安全，生成快照时也可能与写入竞争。要使用明确同步、并发容器或单线程所有权，并定义复合操作的一致性。
