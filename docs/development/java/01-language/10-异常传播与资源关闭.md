# 异常传播、错误边界与资源关闭

文件打开失败、请求被拒绝与程序下标越界都可能表现为异常，但处理策略不同。异常机制把正常返回和异常返回分开；可靠的处理还必须说明谁能恢复、谁负责关闭资源、谁向调用者报告失败。

本篇使用 JDK 25。异常不是“打印之后继续执行”的统一信号。

## 1. 异常从哪里走到哪里

```text
main 调用 save
  save 调用 write
    write 抛出异常
  write 没有匹配处理器，退出并执行必要的清理
save 查找匹配 catch；没有则继续向 main 传播
```

throw 抛出异常对象，throws 声明方法可能向外传播的受检异常。catch 按声明顺序选择匹配类型，子类型应放在父类型前面。异常被捕获后，控制流进入 catch，不会回到抛出点的下一行。

Java 的异常体系以 Throwable 为根。Error 通常表示程序不宜在普通业务层尝试恢复的严重问题；Exception 表示异常情况，其中 RuntimeException 及其子类是非受检异常。其余常见 Exception 子类属于受检异常，编译器要求捕获或声明。分类与编译规则见 [JLS 异常](https://docs.oracle.com/javase/specs/jls/se25/html/jls-11.html)。

## 2. 选择异常和处理边界

| 情况 | 处理方向 |
| --- | --- |
| 参数违反方法前置条件 | IllegalArgumentException，调用者修正输入 |
| 文件或网络操作失败 | 保留 IOException 等原因，在有恢复能力处处理 |
| 业务状态不允许操作 | 明确领域异常或结果类型，不伪装成成功 |
| 需要转换异常类型 | 使用带 cause 的构造方法，保留原始异常 |

受检不等于“轻微”，非受检也不等于“不用处理”。应在应用边界统一转换为适当响应，并保留诊断信息。重试还需要幂等性、次数、退避与总时间预算，不是 catch 所有异常后无限循环。

## 3. 关闭顺序与 suppressed 实验

```java title="ExceptionDemo.java"
import java.io.IOException;

public class ExceptionDemo {
    static final class Resource implements AutoCloseable {
        private final String name;

        Resource(String name) {
            this.name = name;
            System.out.println("open=" + name);
        }

        @Override
        public void close() throws IOException {
            System.out.println("close=" + name);
            throw new IOException("close-" + name);
        }
    }

    static void save() throws IOException {
        try (var first = new Resource("first");
             var second = new Resource("second")) {
            throw new IOException("write");
        }
    }

    public static void main(String[] args) {
        try {
            save();
        } catch (IOException failure) {
            System.out.println("primary=" + failure.getMessage());
            for (Throwable suppressed : failure.getSuppressed()) {
                System.out.println("suppressed=" + suppressed.getMessage());
            }
        }
    }
}
```

```bash
javac -encoding UTF-8 --release 25 -d out ExceptionDemo.java
java -cp out ExceptionDemo
```

```text title="expected-output"
open=first
open=second
close=second
close=first
primary=write
suppressed=close-second
suppressed=close-first
```

try-with-resources 从左向右初始化，按逆序关闭已经成功初始化的资源。业务代码先失败时，关闭失败放入主异常的 suppressed 列表，而不是遮住业务异常。若业务正常、关闭失败，则关闭异常可以成为主异常。第二个资源初始化失败时，第一个仍会被关闭。[JLS 资源语句](https://docs.oracle.com/javase/specs/jls/se25/html/jls-14.html#jls-14.20.3)规定了这些顺序。

## 4. cause 与 suppressed 不相同

```java
// 片段：转换边界上的异常类型，保留原始失败。
throw new IllegalStateException("task snapshot unavailable", originalIOException);
```

cause 解释“这个失败由什么失败引起”；suppressed 记录“处理同一退出过程时，还有什么异常被抑制”。分析完整异常树时，两者都应查看。仅打印 getMessage 会丢掉调用栈与这两类关系。

自定义受检异常可以继承 Exception，非受检异常可以继承 RuntimeException；都应提供合适的 message/cause 构造方法。避免每层重复记录同一异常，最终边界记录一次完整事件通常更清楚。

## 5. finally 的常见误用

finally 一般在 try/catch 退出时执行，包括 return 或 throw 的退出路径；它不是进程被强制终止、JVM 崩溃等情况下的持久化保证。

不要在 finally 中 return 或抛出新的异常：它们可能覆盖先前返回值或异常。资源支持 AutoCloseable 时优先使用 try-with-resources。关闭必须与资源所有权一致：借来的流、共享客户端不能由每个使用者任意关闭。

线程中断也不能被静默吞掉。无法向上抛出 InterruptedException 时，通常应恢复中断标志并退出或向上报告，而不是当作普通失败继续无限工作。

## 6. 怎样保留有效诊断

错误上下文应包含操作、任务标识、目标的非敏感部分和必要状态。不要把密码、请求中的令牌直接塞进异常消息。服务对外返回稳定错误标识，详细栈在受控日志中保留。

异常栈回答“异常创建和传播经过哪些位置”，不自动证明底层根因。网络超时还需要结合连接阶段、服务日志、时间线和重试行为判断。

## 7. 练习与答案

### 7.1 第二个资源构造失败，是否关闭第一个

会。第一个已经成功初始化，应在退出时关闭；第二个构造未成功，不会按已初始化资源关闭。构造内部已经获得的资源仍须由构造逻辑负责失败清理。

### 7.2 catch Exception 后返回空列表是否安全

只有业务明确把该失败定义为空结果时才合理。否则“查询失败”被伪装成“查询成功但没有数据”，会引发错误决策。应传播失败或返回可区分的结果。

### 7.3 为什么不在每个方法都打印栈再向外抛出

一次失败会生成重复日志并割裂上下文。下层提供原因，上层在拥有请求上下文的处理边界记录完整异常；确实恢复或改变处理策略时再记录相应事件。
