# 解释器、JIT、内联与反优化

同一份字节码第一次运行和稳定运行时，可能走不同的机器执行路径。HotSpot 可以先解释执行并收集信息，再编译热点；运行条件变化时，还可能放弃某段已编译代码。性能不是源码行数的静态属性。

## 1. 解释器与编译器如何分工

解释器按照字节码语义执行，启动时不必等待所有方法编译。常见 HotSpot 分层编译结合 C1 与 C2：较低层较快生成代码并收集画像，较高层利用更多信息做优化。

分层常见编号为 0 到 4，但不代表每个方法都按 0、1、2、3、4 完整走一遍；阈值、队列、资源和配置会影响路径。方法调用热度与循环回边热度都可能触发编译。

## 2. OSR 为什么能加速已经进入的循环

一个方法可能只调用一次，却在内部循环很久。OSR，On-Stack Replacement，允许执行中的方法在合适位置切换到编译后的循环路径，而不是一定等方法返回、下一次调用才用机器码。

因此一个长循环的后半程也可能比前半程快；用总耗时除以迭代次数，未必测得某一种稳定执行路径。

## 3. 内联把跨方法优化连起来

```text
调用者 + 热点小方法
→ 把方法体带入调用点
→ 常量传播、消除检查、消除临时对象等机会
```

内联不只是省一次调用。去虚拟化也可能基于当前看到的接收者类型，把多态调用变成可优化的直接路径。若以后出现不满足假设的类型，JVM 必须保持语义正确，不能继续盲用旧假设。

## 4. 反优化不是自动判定为故障

JVM 可以恢复适合解释执行的状态，退出不再合适的优化代码，随后重新收集或编译。类加载、类型画像变化等都可能关联这种过程。少量反优化是正常机制；频繁反优化且与性能退化重合时，才需要针对触发原因分析。

`made not entrant` 表示某段编译代码不再作为新的调用入口，不等价于“刚发生异常”或“每个已有栈帧立即被停掉”。

## 5. 观察一个有确定结果的热方法

```java title="JitDemo.java"
public class JitDemo {
    static int score(int value) {
        return value * 31 + 7;
    }

    public static void main(String[] args) {
        long sum = 0;
        for (int i = 0; i < 1_000_000; i++) {
            sum += score(i);
        }
        System.out.println("sum=" + sum);
    }
}
```

```bash
javac --release 25 -d out JitDemo.java
java -cp out JitDemo
java -XX:+PrintCompilation -cp out JitDemo
java -Xint -cp out JitDemo
```

没有编译诊断输出时，确定性结果为：

```text title="expected-output"
sum=15499991500000
```

三种启动的业务结果必须一致。`PrintCompilation` 额外输出时间、编译编号、层级、方法等，顺序和哪些方法被编译受运行情况影响。查找 `JitDemo::score` 与 `JitDemo::main`；看见 `%` 时通常涉及 OSR 编译。

想观察内联，可在独立实验进程中使用：

```bash
java -XX:+UnlockDiagnosticVMOptions -XX:+PrintInlining -cp out JitDemo
```

输出可能很大。不要把诊断开关长期无条件带入所有生产副本。该程序是机制观察器，不是可信性能基准。

## 6. Code Cache 为什么也是资源

编译后的代码及相关信息占用 Code Cache。大量生成类、方法多态和代码膨胀可能增加压力；查看目标进程：

```bash
jcmd 12345 Compiler.codecache
jcmd 12345 Compiler.queue
```

先确认是代码缓存压力、编译排队还是应用本身计算重，再决定是否调整。盲目增大 Code Cache 不会消除低效算法。

## 7. 为什么自己写 nanoTime 循环容易误导

结果不使用可能被消除；常量输入可能被提前计算；预热与稳定期混在一起；一项测试先运行会改变另一项的画像；容器 CPU 限流又会让墙钟时间变化。

需要可信微基准时使用 [JMH 官方工程与样例](https://github.com/openjdk/jmh)，明确状态、输入、结果消费、预热、测量与独立 fork。即使单方法更快，也必须回到端到端负载验证，防止成本转移到分配、锁或 I/O。

## 8. 练习与答案

### 8.1 程序只有一次方法调用，是否不会 JIT

不一定。内部长循环可能因回边热度触发 OSR。应观察实际编译事件，而不是只数源码调用次数。

### 8.2 关掉 JIT 后结果不同，可以说是正常优化差异吗

不能直接接受。先排除程序数据竞争、未定义的外部依赖、测试输入不同等因素，再考虑 JVM 问题；正确优化必须保留规定的可观察语义。

### 8.3 更短的方法一定更容易快吗

不一定。算法复杂度、分配、内存访问、实际内联和资源等待共同决定成本，源码短不等于机器路径短。
