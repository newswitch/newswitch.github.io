# ZGC：分代、屏障与并发回收

ZGC 把更多回收工作放到应用运行期间，以减少全局暂停。代价是应用与 GC 争用 CPU、额外的引用处理，以及回收完成前必须保留可继续分配的空间。选择 ZGC 是资源与延迟的权衡，不是给原进程加一个“永不卡顿”开关。

## 1. 先确定版本：JDK 25 只有分代模式

JDK 21 引入分代 ZGC，JDK 23 将它作为 ZGC 默认模式，JDK 24 移除了非分代模式。因此 JDK 25 直接使用：

```bash
java -XX:+UseZGC -Xms128m -Xmx128m -jar app.jar
```

不要照旧教程添加 `-XX:-ZGenerational`，也不需要为了开启分代再添加 `-XX:+ZGenerational`。移除说明见 [JDK 24 正式变更](https://docs.oracle.com/en/java/javase/24/migrate/significant-changes-jdk-24.html)。具体发行版和 CPU/OS 是否支持仍要实际启动确认。

## 2. 移动对象时，应用还在读引用怎么办

若对象从地址 A 移到 B，应用可能仍拿着指向 A 的旧引用。ZGC 通过引用中的元信息和相应屏障，协调存活性、代际引用及位置变化，使应用访问到正确对象；不能把它理解成“移动后把全部线程的所有指针瞬间改完”。

读写引用是 GC 与应用协作的重要边界。屏障的快路径尽量便宜，必要时进入慢路径处理。分代版本使用加载与存储屏障配合，各自责任不能直接照搬早期非分代 ZGC 的介绍。

这里只解释责任关系，不把某个平台的位布局、地址位数或某个补丁的快路径当成语言契约。

## 3. 并发周期不等于暂停

```text
应用继续分配和执行业务
  ↕ 屏障协调
并发标记 → 选择重定位集合 → 并发重定位等工作
  ↕ 必要的短暂停顿与阶段切换
年轻代 / 老年代按各自压力协作回收
```

一个周期持续 100 ms，可能大部分时间应用仍在运行。反过来，GC 暂停很短时，请求仍可能因 CPU 被并发 GC 占用、分配等待或外部依赖而变慢。统计时应分别看 cycle、pause、allocation stall 与业务延迟。

## 4. 为什么空余堆是工作空间

并发回收不是立即产生空闲空间。GC 正在识别和移动对象时，业务仍在分配；如果分配追上回收速度，应用可能等空间，即 Allocation Stall。

可以用容量关系帮助理解，但它不是精确选型公式：

```text
需要的堆空间
≈ 长期存活对象
 + 一个回收周期中新增且尚未可用回收的空间
 + 突发、重定位及算法余量
```

分配速率、CPU 配额和存活集不同，相同 Xmx 的结果也会不同。不能用“Heap Used 还有 10%”证明余量足够，也不能认为 `SoftMaxHeapSize` 能代替实际硬上限。官方参数边界见 [JDK 25 ZGC 指南](https://docs.oracle.com/en/java/javase/25/gctuning/z-garbage-collector1.html)。

## 5. 用同一个程序做机制对照

复用[上一章](./05-G1-Region标记复制与暂停.md)的 `GcWorkload.java`，先编译，再分别启动两个独立进程：

```bash
javac --release 25 -d out GcWorkload.java
java -Xms128m -Xmx128m -XX:+UseG1GC -Xlog:gc*:file=g1-128.log:uptime,level,tags -cp out GcWorkload
java -Xms128m -Xmx128m -XX:+UseZGC -Xlog:gc*:file=zgc-128.log:uptime,level,tags -cp out GcWorkload
```

两个进程的业务输出都应是 `allocatedMiB=256`、`retainedBlocks=16`、`lastByte=-1`。启动日志应分别确认 G1 和 ZGC。

这只证明两种机制在当前环境能完成相同正确性任务，不能拿这段短程序的启动耗时宣布谁在生产更快。不同 GC 的日志标签和堆表示也不能逐列生搬。

## 6. 真实选型怎样比较

使用相同 JDK、请求分布、数据集、限流和 CPU/内存限制；让应用完成预热，再观察稳定期与突发期。保留失败请求，不要只比较成功请求平均值。

| 证据 | 回答的问题 |
| --- | --- |
| P50/P95/P99、错误率 | 业务是否真的改善 |
| GC 暂停与分配等待 | 停顿减少后是否转成其他等待 |
| 吞吐、应用 CPU 与 GC CPU | 低暂停花了多少算力 |
| RSS、容器峰值、堆存活量 | 是否还能放进资源预算 |
| 重负载和长期运行 | 峰值是否仍有足够回收余量 |

对于明显被数据库连接池卡住的服务，先解决连接池与排队；换收集器未必改变主瓶颈。对于确实由暂停主导的延迟，则通过对照测量决定是否承担额外资源成本。

## 7. 练习与答案

### 7.1 ZGC 是否完全没有 Stop-The-World

不是。它把大量工作并发化，仍有必要暂停。应看实际日志和当前 JDK 的实现，而不是用“并发”推导“零暂停”。

### 7.2 没有长 GC pause，为什么分配线程仍卡住

可能是空间来不及回收产生 Allocation Stall，也可能是 CPU 调度或其他资源等待。检查分配速率、周期、余量和限流，不能只看 pause 最大值。

### 7.3 G1 换 ZGC 后吞吐降低是否说明部署错误

不一定。不同机制有不同成本。先确认配置正确，再按业务延迟目标和资源预算判断收益，而不是要求每个指标都同时改善。
