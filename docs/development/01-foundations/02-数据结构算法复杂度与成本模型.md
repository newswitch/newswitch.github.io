# 数据结构、算法、复杂度与系统成本模型

数据结构不是算法题专用知识。缓存索引、任务队列、路由表、调度器、KV Cache Block 管理、数据库索引和 Kubernetes Workqueue 都是在选择数据布局与操作成本。

只写 `O(1)` 或 `O(log n)` 仍不够：真实系统还受 Cache Miss、对象数量、锁、序列化、网络往返和磁盘随机 I/O 影响。

## 1. 先建立五维成本模型

分析一个实现时同时问：

| 维度 | 问题 | 常用度量 |
| --- | --- | --- |
| 时间 | 操作次数怎样随输入增长 | Big-O、CPU Time、Wall Time |
| 空间 | 有效数据之外还保存什么 | Bytes/Item、Peak RSS、Allocation Rate |
| 局部性 | 数据是否连续、能否命中 Cache | Cache Miss、TLB Miss、Memory Bandwidth |
| 并发 | 是否需要锁、复制或分片 | Lock Wait、Contention、Queue Depth |
| 外部 I/O | 是否跨网络、磁盘或设备 | RTT、IOPS、Throughput、P99 |

一个内存中的哈希查询可以近似 `O(1)`，但若每次查询都触发远程 RPC，主要成本是 RTT，不是哈希槽计算。

## 2. Big-O 表达什么

Big-O 描述输入规模趋大时增长率的上界类别，通常忽略常数和低阶项：

```text
O(1) < O(log n) < O(n) < O(n log n) < O(n²) < O(2ⁿ)
```

它适合比较扩展趋势，不表示实际时间：

- `O(1)` 可能包含一次跨区网络请求；
- `O(n)` 的连续扫描可能比指针跳转的 `O(log n)` 更快；
- 平均 `O(1)` 的哈希表在扩容或严重冲突时会抖动；
- `n` 必须先定义，是用户数、请求数、字节数还是节点数。

### 2.1 最坏、平均与摊销复杂度

| 类型 | 含义 | 例子 |
| --- | --- | --- |
| Worst Case | 单次操作的最坏上界 | 哈希冲突退化 |
| Average Case | 假设某种输入分布的期望 | 均匀哈希查找 |
| Amortized | 一组操作平摊后的成本 | Dynamic Array 扩容 |

延迟敏感系统不能只看摊销均值。一次扩容复制或 GC 可能直接进入 P99。

## 3. 数组与动态数组

连续数组的核心优势是：

- 按下标访问 `O(1)`；
- 元素紧凑，预取和 Cache Line 利用率高；
- 批量遍历容易向量化；
- 元数据和指针开销少。

代价是中间插入/删除通常需要移动 `O(n)` 个元素。Dynamic Array 预留 Capacity，满时申请更大区域并复制：追加的摊销复杂度可为 `O(1)`，但某一次仍是 `O(n)`。

容量规划要区分：

```text
Length   = 逻辑元素数
Capacity = 已分配槽位数
RSS      ≠ Length × 业务字段大小
```

对象头、对齐、Allocator Size Class、Slice/List 元数据和保留 Capacity 都会增加内存。

## 4. 链表为什么常常没有想象中快

链表已知节点位置时插入/删除可为 `O(1)`，但查找位置仍为 `O(n)`。每个节点还可能包含指针、Allocator 元数据和 Padding；节点分散会带来 Cache Miss 和 TLB 压力。

因此“频繁插入就用链表”缺少条件。若数据量不大、遍历很多或可以批量移动，连续结构往往更好。链表适合节点地址稳定、已有节点引用、需要常数时间摘挂等场景。

## 5. 哈希表

哈希表把 Key 变成 Bucket/Slot：

```text
key → hash(key) → bucket index → collision resolution → value
```

需要同时理解：

- Hash 质量与攻击性输入；
- Load Factor 与扩容阈值；
- Open Addressing 或 Chaining；
- Tombstone 和删除成本；
- 扩容时延与内存峰值；
- 并发读写时的锁、分片或 Copy-on-Write。

哈希表不保持自然顺序。需要范围查询、有序遍历或 Prefix 语义时，树、Trie 或有序数组可能更合适。

## 6. 树、B-Tree 与 LSM 的边界

### 6.1 二叉搜索树

平衡情况下查找、插入、删除为 `O(log n)`；失衡会退化为 `O(n)`。红黑树、AVL 等通过旋转维护高度约束。

### 6.2 B-Tree/B+Tree

一个节点保存多个 Key 和 Child，降低树高并提高块/页利用率，适合数据库和文件系统的页式存储。一次节点访问成本不等于一次 CPU 指令，它可能对应 Buffer Pool 命中或一次存储 I/O。

### 6.3 LSM Tree

写入先进入内存结构和日志，再生成有序文件并后台 Compaction。它把随机写转成顺序/批量写，但引入 Write Amplification、Read Amplification、Space Amplification 和 Compaction 抖动。

选择索引结构是在读、写、空间和后台工作之间取舍，不是比较两个 Big-O 字符串。

## 7. Heap 与优先队列

Binary Heap 常用于：

- Timer；
- Top-K；
- 调度优先级；
- K 路归并；
- 最短路径。

| 操作 | 复杂度 |
| --- | --- |
| 查看最小/最大值 | `O(1)` |
| 插入 | `O(log n)` |
| 删除顶端 | `O(log n)` |
| 从数组建堆 | `O(n)` |

Heap 只保证父子偏序，不保证整个数组已经排序。从 Heap 中间找任意值并不天然高效。

## 8. Queue、Ring Buffer 与背压

队列不仅是容器，也是生产者和消费者之间的时间缓冲：

```text
Producer Rate λ > Consumer Rate μ
→ Queue Depth 持续增长
→ Waiting Time 增长
→ Memory/Deadline 耗尽
```

无界队列只是把过载从“立即拒绝”改成“稍后 OOM 或超时”。生产设计必须说明：

- 最大元素数和最大字节数；
- 满时阻塞、丢弃、拒绝还是覆盖；
- 优先级和公平性；
- 消费失败后重试、死信和顺序边界；
- 关闭时如何唤醒等待者。

固定大小 Ring Buffer 能避免频繁分配，但要处理 Head/Tail、满空判定、内存可见性和覆盖策略。

## 9. Set、Bitmap、Bloom Filter 与 HyperLogLog

| 结构 | 回答的问题 | 代价/误差 |
| --- | --- | --- |
| Hash Set | 元素是否精确存在 | 保存实际 Key，内存较大 |
| Bitmap | 稠密整数集合是否存在 | 范围大而稀疏时浪费 |
| Bloom Filter | 元素可能存在还是一定不存在 | 有 False Positive，无 False Negative（在正确实现和不删除条件下） |
| HyperLogLog | 不同元素数量约多少 | 近似基数，不返回具体成员 |

Bloom Filter 常放在昂贵查询之前减少无效 I/O，但“可能存在”仍必须查真实数据源。

## 10. 图与依赖关系

图适合表达网络拓扑、任务 DAG、依赖、调用关系和资源绑定：

- BFS：无权图最少边数、分层遍历；
- DFS：可达性、拓扑排序、环检测；
- Dijkstra：非负权最短路径；
- Topological Sort：DAG 调度顺序；
- Union-Find：动态连通分量。

邻接矩阵需要 `O(V²)` 空间，适合稠密小图；邻接表接近 `O(V+E)`，适合稀疏图。算法正确还要定义负权、重复边、自环和动态图更新语义。

## 11. 从复杂度进入容量规划

假设缓存保存 1000 万项：

```text
业务 Payload          120 B/item
Key                   40 B/item
对象头、指针、Hash 槽   估算 80 B/item
Allocator/碎片余量      25%
副本数                 2
```

粗算：

```text
单副本 ≈ 10,000,000 × (120 + 40 + 80) × 1.25
      ≈ 3.0 GB
双副本 ≈ 6.0 GB
```

还未包含进程 Runtime、连接、临时查询结果和 Rehash 峰值。容量模型应通过 Heap Profile 或真实数据校准，而不是把业务字段相加后当作 RSS。

## 12. CPU Cache 会改变选择

现代 CPU 按 Cache Line 搬运数据。连续扫描具有空间局部性；指针追逐可能每个节点都触发新的 Cache Line。相同 `O(n)`：

```text
连续数组扫描：顺序预取、SIMD、少量指针
链表扫描：随机地址、分支、Cache/TLB Miss
```

性能判断要使用 Benchmark 和 Profile：

- 固定数据规模与分布；
- 预热并区分冷/热 Cache；
- 避免编译器删除无副作用计算；
- 记录 CPU、内存、Allocation、GC 和 P99；
- 不用单次运行结论替代统计分布。

## 13. 并发会改变数据结构语义

普通 Map 在并发读写下可能不安全。加一把全局锁虽能保证互斥，但热点会串行化。常见选择：

- Sharded Map：按 Key 分片锁；
- Read/Write Lock：读多写少，但仍需评估写饥饿；
- Copy-on-Write：读快，更新复制成本高；
- Immutable/Persistent Structure：通过结构共享保留旧版本；
- Single Owner/Event Loop：一个执行单元独占可变状态；
- Lock-free Structure：需要严格内存模型和回收策略。

“线程安全”只说明某种并发契约，不表示公平、无锁、无等待或线性扩展。

## 14. 选择数据结构的步骤

1. 定义操作集合：读、写、范围、Top-K、过期、遍历；
2. 定义输入规模和分布：均匀、热点、有序、攻击性；
3. 定义一致性和顺序：允许近似吗，允许重复吗；
4. 估算单项字节和峰值副本；
5. 定义并发模型和资源上限；
6. 使用真实工作负载 Benchmark；
7. 用 Profile 验证 CPU、Cache、分配和锁；
8. 对最坏输入和扩容/Compaction 建立保护。

## 15. 常见误区

### 15.1 `O(1)` 一定比 `O(log n)` 快

Big-O 忽略常数、局部性和外部 I/O，只描述增长趋势。

### 15.2 内存足够就可以使用无界 Map/Queue

无界增长会增加 GC、Rehash、恢复时间和故障半径；内存只是最后一道限制。

### 15.3 更复杂的数据结构一定更专业

如果数组排序后加二分已经满足更新频率，复杂并发树只会增加维护和故障成本。

### 15.4 Benchmark 快就代表线上快

数据分布、并发、NUMA、GC、I/O、限流和依赖延迟不同，Microbenchmark 只能验证受控问题。

## 16. 练习与答案

### 16.1 练习 1：为何链表插入 `O(1)` 仍可能比数组慢？ {/* #练习-1为何链表插入-o1-仍可能比数组慢 */}

答案：前提是已经持有目标节点；寻找插入位置可能是 `O(n)`。节点分配、指针写入、Cache Miss 和 GC/Allocator 成本也可能超过连续数组的批量移动。

### 16.2 练习 2：队列增长但 CPU 只有 40%，能否通过增加队列容量解决？ {/* #练习-2队列增长但-cpu-只有-40能否通过增加队列容量解决 */}

答案：不能据此判断。消费者可能等待下游、锁、磁盘或限流。扩大队列只增加可等待时间和内存，应先比较到达率、完成率、等待时间和下游延迟，再扩消费者或实施拒绝/降级。

### 16.3 练习 3：Bloom Filter 判断存在后，为什么还要查数据库？ {/* #练习-3bloom-filter-判断存在后为什么还要查数据库 */}

答案：Bloom Filter 允许 False Positive，只能可靠回答“一定不存在”。删除、参数选择和容量超标还会进一步影响误判率。

### 16.4 练习 4：为什么平均复杂度不能替代 P99 分析？ {/* #练习-4为什么平均复杂度不能替代-p99-分析 */}

答案：扩容、冲突、Compaction、GC 或锁竞争可能只影响少数请求，却直接形成尾延迟。必须观察延迟分布和最坏路径。
