# 程序从源码到进程：编译、链接、ELF、装载与 Runtime

“运行一段代码”不是 CPU 直接读取源文件。源代码要先变成目标平台能够装载的产物，Kernel 再创建执行环境，语言 Runtime 和动态库完成初始化，最后才进入业务入口。

```text
Source
→ Preprocess / Parse / Type Check / Optimize
→ Assembly / Bytecode / Machine Code
→ Object File
→ Link
→ Executable / Shared Library / Package
→ execve + ELF Loader + Dynamic Linker
→ Language Runtime
→ main / module entry
→ Library → System Call → Kernel → Hardware
```

## 1. 先区分三类执行模型

| 模型 | 典型语言 | 交付物 | 启动时的关键组件 |
| --- | --- | --- | --- |
| Ahead-of-Time 原生编译 | C、C++、Go、Rust | ELF/PE/Mach-O 原生二进制 | OS Loader、动态链接器、语言 Runtime |
| 字节码 + 虚拟机/JIT | Java、部分 .NET | Bytecode/IL + 依赖 | JVM/CLR、解释器、JIT、GC |
| 解释器执行 | Python、Ruby、Shell | 源码/Bytecode + 依赖 | 解释器、模块加载器、Runtime |

边界并非绝对：Python 会缓存 Bytecode；JVM 先解释再 JIT；Go 通常生成原生二进制但仍带调度器、GC 和网络 Poller。不要把“编译型/解释型”当成只有两个格子的分类。

## 2. C 工具链的四个阶段

GCC 文档把常规路径分为预处理、编译、汇编和链接。用一个最小程序观察中间产物：

```c title="hello.c"
#include <stdio.h>

int main(void) {
    puts("hello");
    return 0;
}
```

```bash
gcc -E hello.c -o hello.i     # 预处理后文本
gcc -S hello.i -o hello.s     # 汇编代码
gcc -c hello.s -o hello.o     # 可重定位目标文件
gcc hello.o -o hello          # 链接为可执行文件
```

### 2.1 预处理

处理 `#include`、宏和条件编译。它不是类型检查；宏替换后的代码才进入编译器前端。错误的 Feature Macro 或 Header 搜索路径会让相同源码生成不同接口。

### 2.2 编译

完成词法/语法分析、类型检查、IR 生成、优化和目标指令选择。优化级别会改变内联、循环、寄存器分配和调试可见性，因此 `-O0` 的复现不能自动代表生产 `-O2`。

### 2.3 汇编

把汇编表示变成包含 Section、Symbol、Relocation 的 `.o` 文件。目标文件尚未拥有所有符号的最终地址。

### 2.4 链接

链接器合并目标文件和库，解析符号，执行 Relocation，并按照 Linker Script 组织输出 Section/Segment。常见错误分别意味着：

| 错误 | 所在阶段 | 典型原因 |
| --- | --- | --- |
| `syntax error` | 编译 | 语法或类型不成立 |
| `undefined reference` | 链接 | 声明存在，但实现未参与链接或顺序错误 |
| `cannot open shared object file` | 运行时装载 | 动态库搜索路径或 ABI 不匹配 |
| `Illegal instruction` | 运行期 | 二进制使用了目标 CPU 不支持的指令 |

## 3. 静态链接与动态链接

### 3.1 静态链接

需要的库代码在构建时进入产物。优点是运行时依赖较少；代价是文件更大、相同库代码难共享、库安全更新通常需要重新构建和发布。

### 3.2 动态链接

可执行文件记录所需共享对象和动态符号，装载时由动态链接器寻找并映射 `.so`。多个进程可共享只读代码页，但 ABI、SONAME、搜索路径和符号版本都成为运行契约。

```bash
file ./hello
readelf -h ./hello
readelf -l ./hello
readelf -d ./hello
readelf -Ws ./hello | head
ldd ./hello
```

`ldd` 可能通过目标的动态链接器机制工作，不应对不可信二进制随意执行。静态观察优先使用 `readelf -d`、`objdump -p`。

## 4. ELF Section 与 Segment 不一样

| 视图 | 主要使用者 | 作用 |
| --- | --- | --- |
| Section | 编译器、链接器、调试器 | 组织代码、数据、符号、重定位和调试信息 |
| Segment / Program Header | Kernel Loader、动态链接器 | 描述运行时要映射的区域及权限 |

常见 Section：

- `.text`：机器指令；
- `.rodata`：只读常量；
- `.data`：有初始值的可写全局数据；
- `.bss`：零初始化数据，文件中通常不保存同等大小的零字节；
- `.symtab/.dynsym`：符号信息；
- `.rela.*`：重定位记录；
- `.debug_*`：调试信息。

Kernel 主要按 `PT_LOAD` 等 Program Header 映射 Segment，而不是逐个 Section 装载。这也是“文件布局”和“运行地址空间”不能画成同一张表的原因。

## 5. `execve()` 做了什么

Shell 执行 `./hello` 时，通常先创建或准备子进程，再调用 `execve()` 用新程序替换当前进程映像：

```text
Shell
→ PATH/权限检查
→ fork/clone/posix_spawn
→ execve("./hello", argv, envp)
→ Kernel 识别 ELF 或 shebang
→ 建立新地址空间和初始栈
→ 映射程序解释器/动态链接器
→ 跳到 ELF Entry
```

`execve()` 成功后不会“返回到旧程序”；PID 可以保持，但旧代码、Heap、Stack 和大多数 Memory Mapping 被替换。打开的 FD 是否保留由 `FD_CLOEXEC` 决定，这直接影响 Secret 泄露、锁未释放和子进程继承 Socket 等问题。

## 6. 动态链接器启动路径

动态 ELF 的 `PT_INTERP` 指定程序解释器，例如：

```bash
readelf -l /usr/bin/ls | rg 'interpreter'
```

示意输出：

```text
[Requesting program interpreter: /lib64/ld-linux-x86-64.so.2]
```

动态链接器大致完成：

1. 映射所需共享对象；
2. 解析依赖和符号版本；
3. 执行 Relocation；
4. 初始化 TLS 和库 Constructor；
5. 把控制权交给程序启动代码；
6. 启动代码初始化 Runtime 后调用 `main()`。

`main()` 因此不是 ELF 的绝对第一条指令。

## 7. 进程地址空间

简化布局：

```text
高地址
┌──────────────────────┐
│ Kernel 映射区域       │
├──────────────────────┤
│ User Stack           │ ← argv、envp、调用栈
├──────────────────────┤
│ mmap 区域             │ ← 共享库、文件、匿名映射
├──────────────────────┤
│ Heap                 │ ← malloc/对象分配器
├──────────────────────┤
│ Data / BSS           │
├──────────────────────┤
│ Text / Read-only     │
└──────────────────────┘
低地址
```

ASLR 会改变实际地址；不同架构、PIE、Runtime 和 Kernel 配置会改变布局。虚拟地址空间大不等于物理内存已占用，RSS、PSS、匿名页、文件页和 Swap 要分开观察。

```bash
cat /proc/$PID/maps
cat /proc/$PID/smaps_rollup
pmap -x $PID
```

## 8. Runtime 在做什么

Runtime 不是“语言附带的一点库”，它可能负责：

- 线程/Goroutine/Coroutine 调度；
- Heap 分配、GC 与对象元数据；
- Exception、Panic、Stack Unwind；
- Module/Package 加载；
- JIT 或 Bytecode 解释；
- DNS、Timer、网络 Poller；
- Signal、TLS、Profiler 和调试接口。

因此相同系统调用压力，在不同 Runtime 中可能表现为不同的线程数、GC Pause、Heap 曲线和 CPU Profile。

## 9. 库函数与系统调用

应用通常先调用语言或 C 库，再由库决定是否进入 Kernel：

```text
Python file.read()
→ CPython I/O object
→ libc read()/直接 syscall wrapper
→ read(2)
→ VFS / Page Cache / Filesystem / Block Layer
```

并非每个库函数都对应一次系统调用：`printf()` 可能只写用户态 Buffer；`malloc()` 常从现有 Arena 分配；DNS 解析可能读取缓存、文件或发网络请求。用 `strace` 看到的是 Kernel 边界，不是全部业务函数。

```bash
strace -f -tt -T -o trace.log ./hello
```

## 10. 容器没有改变程序装载原理

容器主要改变 Namespace、Cgroup、Mount 和安全边界。容器内 ELF 仍由宿主 Kernel 装载：

- 镜像架构必须能被节点 CPU 执行或有明确仿真；
- 动态链接器和共享库来自容器 Rootfs；
- System Call 由宿主 Kernel 实现；
- Seccomp/LSM/Capability 可能拒绝调用；
- Cgroup 限制影响 CPU、Memory、PID 和 I/O。

“镜像里有完整 Linux”不等于镜像里有独立 Kernel。

## 11. 一套排查顺序

程序在目标机器启动失败时：

```bash
uname -m
file ./app
readelf -h ./app
readelf -l ./app
readelf -d ./app
ldd ./app
env | sort
strace -f -tt -T -o app.strace ./app
```

依次回答：

1. 文件格式和 CPU 架构是否匹配；
2. ELF Interpreter 是否存在；
3. 动态库和符号版本是否满足；
4. 执行权限、Mount `noexec`、SELinux/AppArmor/Seccomp 是否允许；
5. Runtime 配置和模块路径是否正确；
6. 最后一个成功系统调用和首个失败返回码是什么。

## 12. 常见误区

### 12.1 编译成功就能在任意 Linux 运行

CPU ISA、glibc/musl、动态库 ABI、Kernel Feature 和系统调用策略都可能不同。

### 12.2 静态链接就完全没有运行依赖

程序仍依赖 Kernel ABI、CPU 指令集、配置、证书、时区、DNS 和外部服务；部分 libc 功能也可能具有额外运行边界。

### 12.3 `ldd` 正常就说明装载没有问题

它只覆盖共享对象解析的一部分，不能证明初始化函数、配置、权限、CPU 指令或业务入口正常。

### 12.4 解释型语言没有编译和装载过程

解释器本身是被装载的原生程序，模块可能生成 Bytecode 或本地扩展，依赖仍涉及 ABI 和动态库。

## 13. 练习与答案

### 13.1 练习 1：为什么会出现“编译通过，但链接报 undefined reference”？ {/* #练习-1为什么会出现编译通过但链接报-undefined-reference */}

答案：编译阶段只需知道符号声明和类型；链接阶段才必须找到唯一、兼容的定义。实现文件未加入、库顺序/搜索路径错误、条件编译排除了实现或 C/C++ 符号修饰不匹配都会触发。

### 13.2 练习 2：为什么 `main()` 不是进程执行的第一行？ {/* #练习-2为什么-main-不是进程执行的第一行 */}

答案：Kernel 从 ELF Entry 开始，动态链接器和 C/语言 Runtime 先完成映射、重定位、TLS、Constructor、参数和 Runtime 初始化，启动代码之后才调用 `main()`。

### 13.3 练习 3：容器里的程序为什么会出现宿主 Kernel 不支持的系统调用错误？ {/* #练习-3容器里的程序为什么会出现宿主-kernel-不支持的系统调用错误 */}

答案：容器复用宿主 Kernel。镜像提供用户态文件，不提供独立 Kernel；程序、libc 和 Seccomp Profile 必须与宿主能力兼容。

### 13.4 练习 4：为什么虚拟地址空间 10 GiB 不代表 RSS 也是 10 GiB？ {/* #练习-4为什么虚拟地址空间-10-gib-不代表-rss-也是-10-gib */}

答案：地址范围可能尚未 Fault In，也可能是共享文件映射、稀疏映射或可回收页。要结合 RSS/PSS、匿名页、文件页和 Page Fault 分析实际驻留。
