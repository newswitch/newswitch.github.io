# 自动配置、条件与评估报告

自动配置不是“框架猜测所有需求”，而是在候选配置中按条件选择默认装配。用户提供自己的对象时，默认实现通常应该退让；显式关闭功能时，也不该继续创建它的资源。

## 1. 自动配置不等于组件扫描

![Boot 自动配置候选、条件和创建路径](/img/development/boot-autoconfiguration.svg)

候选被发现、条件满足、定义注册和对象创建分别观察；最后用条件报告和实际 Bean 结果核验，不靠依赖名称猜测。

```text
启用自动配置
→ 发现自动配置候选
→ 排除、分组与排序等处理
→ 根据类、环境和 Bean 条件评估
→ 注册满足条件的定义
→ 正常创建对象
```

Boot 使用专门的候选发现机制，不能把某个库中的 `@Configuration` 类放进去，就假设应用默认扫描一定能找到它。自定义库采用 `AutoConfiguration.imports` 提供候选，应用的普通扫描范围可以完全不包含这个库的包。

候选发现与注册也不等于实例已经存在。运行时可从条件报告、定义与实际 Bean 三个层面分别取证。[自动配置机制](https://docs.spring.io/spring-boot/reference/using/auto-configuration.html)

## 2. 三类常用条件分别约束什么

| 条件 | 主要问题 | 容易误解的地方 |
| --- | --- | --- |
| ConditionalOnClass | 相应类型在目标 ClassLoader 中是否可用 | 不等于远端服务可用 |
| ConditionalOnProperty | 配置值是否满足指定规则 | 不等于所有任意字符串都按同一布尔逻辑处理 |
| ConditionalOnMissingBean | 当前已知定义中是否缺少相应对象 | 受处理顺序与搜索范围影响 |

`havingValue`、`matchIfMissing`、目标类型与上下文层级，都应按实际注解配置解释，不能只读条件名字。

Bean 条件尤其依赖当前已处理的定义。自动配置应放在合适阶段，并通过清晰类型签名表达默认服务；不能把它当成任意时间查询所有未来定义的全知规则。

## 3. 回退不等于覆盖同名定义

用户提供 GreetingService 后，默认实现的条件不成立，是“默认定义不注册”，不需要靠开启同名 Bean 覆盖来互相替换。它也不保证该自动配置中的所有其他定义都停止创建。

例如问候库的属性对象在配置类上统一启用，用户提供自定义服务时，属性绑定仍可能发生。禁用整个功能与只替换某个默认 Bean，是两个不同选择。

对候选排序的设置通常控制定义处理顺序，不直接承诺最终实例构造顺序；实例仍受依赖关系等因素影响。实现要求见[自定义自动配置文档](https://docs.spring.io/spring-boot/reference/features/developing-auto-configuration.html)。

## 4. 用同一个库观察默认、回退和关闭

本篇使用[第 6 篇](./06-自定义Starter扩展点与测试.md)的问候自动配置。它不在应用普通扫描范围内，通过库资源提供候选；这里不对它执行显式 `@Import`。

```java title="demo-app/src/main/java/demo/boot/conditions/AutoConfigDemo.java"
package demo.boot.conditions;

import io.newswitch.greeting.*;
import org.springframework.boot.*;
import org.springframework.boot.autoconfigure.*;
import org.springframework.boot.autoconfigure.condition.ConditionEvaluationReport;
import org.springframework.boot.builder.SpringApplicationBuilder;
import org.springframework.context.ConfigurableApplicationContext;
import org.springframework.context.annotation.*;

public final class AutoConfigDemo {
    @SpringBootConfiguration @EnableAutoConfiguration public static class Defaults {}
    @Configuration(proxyBeanMethods = false) public static class Custom {
        @Bean public GreetingService customGreeting() { return name -> "custom:" + name; }
    }
    public static ConfigurableApplicationContext start(Class<?> extra, String... args) {
        var builder = new SpringApplicationBuilder(Defaults.class).web(WebApplicationType.NONE);
        if (extra != null) builder.sources(extra);
        return builder.run(args);
    }
    public static boolean defaultMatches(ConfigurableApplicationContext context) {
        var outcomes = ConditionEvaluationReport.get(context.getBeanFactory()).getConditionAndOutcomesBySource()
                .get(GreetingAutoConfiguration.class.getName() + "#greetingService");
        return outcomes != null && outcomes.isFullMatch();
    }
    public static void main(String[] args) {
        try (var context = start(null)) {
            System.out.println("default=" + context.getBean(GreetingService.class).greet("Spring"));
            System.out.println("defaultMatch=" + defaultMatches(context));
        }
        try (var context = start(Custom.class)) {
            System.out.println("custom=" + context.getBean(GreetingService.class).greet("Spring"));
            System.out.println("defaultMatch=" + defaultMatches(context));
        }
        try (var context = start(null, "--newswitch.greeting.enabled=false")) {
            System.out.println("disabledCount=" + context.getBeansOfType(GreetingService.class).size());
        }
    }
}
```

完成[构建和运行期依赖复制](./03-Starter-BOM依赖树与可执行JAR.md)后运行 `demo.boot.conditions.AutoConfigDemo`：

```text title="expected-output"
default=hello, Spring
defaultMatch=true
custom=custom:Spring
defaultMatch=false
disabledCount=0
```

示例显式使用非 Web 类型，所以不会因为 Classpath 中有 MVC Starter 就额外启动 HTTP 服务。三个上下文分别关闭，不共享一次启动留下的 Bean。

## 5. 条件报告怎样用于排查

完整应用可以用 `--debug` 辅助输出条件报告；本实验将根日志关闭，因此主程序直接读取报告。不要把“设置 debug 但没看见报告”立即判断为框架没做条件评估，要同时核对日志配置。

报告说明某一条件为什么匹配或不匹配，不证明外部依赖健康，也不保证 Bean 的构造与初始化成功。检查顺序是候选有没有被发现、配置是否被排除、条件结果、定义存在性、最后的实例创建异常。

若后续启用 Actuator 的 conditions 等诊断端点，需要单独考虑管理端口、认证与暴露范围，不应为了排查就把内部配置明细公开给所有用户。

## 6. 练习与答案

### 6.1 类存在，为什么默认服务还没创建

可能自动配置候选未发现、功能属性关闭、被排除，或用户对象已经满足 MissingBean 条件。类条件只是其中一关。

### 6.2 用户提供服务是否必须开启 Bean 定义覆盖

不必须。默认配置应按条件退让，让默认定义不再注册，而不是依赖同名 Bean 相互覆盖。

### 6.3 条件报告显示匹配，是否说明服务一定可用

不是。定义还可能在实例化、绑定、校验或初始化时失败，远端系统也可能不可用。报告与实际 Bean、运行状态需要分别核对。
