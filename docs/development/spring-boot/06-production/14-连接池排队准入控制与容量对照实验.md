# 连接池排队、准入控制与容量对照实验

数据库 SQL 很快，API 仍可能等几百毫秒；开启准入控制后 P95 大幅降低，也可能只是大量请求更快地失败。性能实验必须同时保留成功量、拒绝量和统计边界，才能判断改动究竟改变了什么。

## 1. 实验固定哪些变量

使用 [telemetry 实验](https://github.com/newswitch/newswitch.github.io/tree/main/examples/spring-boot/deepening-lab/telemetry)：JDK 25、Boot 4.1.1、H2 内存库，JVM 最大堆 384MiB，Tomcat 最大线程 16，连接池默认最大连接 2，connectionTimeout=250ms。

每个请求拿到连接后人为持有 80ms，再执行 SELECT 1 并关闭连接。实验故意让连接成为瓶颈；这不模拟某款真实数据库的执行能力，H2/loopback 结果不能填进生产容量表。

压测脚本固定目标为 127.0.0.1，最多 16 并发、500 请求、单次持有 200ms。它不是可任意指向公网的压力工具，也不应为更好看的曲线直接放大限制。

## 2. 四组对照

| 实验 | 客户端并发 | 连接数 | 准入控制 | 要观察什么 |
| --- | --- | --- | --- | --- |
| 串行 | 1 | 2 | 无 | 单次请求基线 |
| 排队 | 8 | 2 | 无 | 等连接、尾延迟与可能超时 |
| 扩池 | 8 | 4 | 无 | 下游确有余量时的变化 |
| 准入 | 8 | 2 | 最多 2 个在处理 | 快速拒绝是否保护已接收请求 |

扩大连接池只有在数据库还有承载余量时才有意义。此实验的“数据库”在本机且工作是受控睡眠，所以增加连接能并行重叠更多持有时间；真实数据库可能反而出现锁竞争、IO 饱和和更慢 SQL。

## 3. 手动执行

从实验根目录构建并启动：

```bash
mvn -B -ntp -pl telemetry verify
java -Xmx384m -jar telemetry/target/telemetry-lab-1.0.0.jar --management.tracing.export.otlp.enabled=false
```

另一个终端运行，先做一轮小规模预热：

```bash
node telemetry/load.mjs --requests 12 --concurrency 1 --hold-ms 10
node telemetry/load.mjs --requests 80 --concurrency 1 --hold-ms 80
node telemetry/load.mjs --requests 80 --concurrency 8 --hold-ms 80
```

关闭本次应用后，用 `--spring.datasource.hikari.maximum-pool-size=4 --spring.datasource.hikari.minimum-idle=4` 启动扩池组，或用 `--lab.admission=true` 启动准入组，再以相同命令压测。不要同时启动多个占用相同端口的进程。

也可以在仓库根目录运行自动化对照，前提是已完成四模块 verify：

```bash
node scripts/verify-boot-deepening.mjs --run-http --java-home /你的/JDK25目录
```

脚本顺序启动三个自有 JVM，使用临时端口，完成后关闭；输出写在忽略目录 `.java-article-checks/deepening-load/`。它不会关闭其他 Java 进程。长时间生产级压测需要另外的隔离环境与到达率工具。

## 4. 先算理论关系，再看数据

如果一个连接每次被独占约 0.08 秒，2 个连接对应的理想处理上界约为：

```text
2 / 0.08 ≈ 25 次/秒
```

这个上界忽略了网络、调度、SQL、连接管理和资源竞争，只用于形成假设。实际结果可能更低，不能将 25 当成承诺 QPS。

8 个请求争用 2 个连接，后续请求会分批等待。连接没有泄漏，仍可能一直接近满载；CPU 很低也不代表能无限增加吞吐。若等待超过 250ms，某些请求会在拿到连接前失败，数据库慢查询日志中自然没有这些“慢 SQL”。

## 5. 读懂脚本输出

```text
model                    closed-loop
completed                收到响应或明确网络错误的请求数
successes                HTTP 200 数
failures                 按 HTTP 状态或 network 分类
completedPerSecond       所有完成数 / 测量时间
successfulPerSecond      成功数 / 测量时间
allP95ms                 包含失败的总体 P95
successP95ms             仅成功请求 P95
```

这是闭环并发：某个 worker 收到响应后才发下一次。服务慢会自然降低后续发压速率，无法模拟固定到达率下持续积压；成功 P95 排除了失败请求，也不能代表所有用户体验。80 请求的 P95 仅是少量样本的观测，不适合报告精细 P99 或显著性结论。

## 6. 准入控制“更快”为什么不等于“更强”

2026-10-21 在 Windows、JDK 25.0.4、Boot 4.1.1 的一次本机执行得到以下样本。每档预热后发送 80 个请求，关闭 OTLP 导出；数值只用于展示统计如何解释，不是跨机器可复制的性能承诺。

| 实验 | 成功 / 总数 | 503 | 成功请求/秒 | 所有完成/秒 | 全体 P95 ms |
| --- | --- | --- | --- | --- | --- |
| 2 连接、并发 1 | 80 / 80 | 0 | 10.69 | 10.69 | 95.59 |
| 2 连接、并发 8 | 62 / 80 | 18 | 21.34 | 27.54 | 299.37 |
| 4 连接、并发 8 | 80 / 80 | 0 | 42.30 | 42.30 | 191.08 |
| 2 连接、准入 2、并发 8 | 6 / 80 | 74 | 19.76 | 263.40 | 106.11 |

最后一行的“263.40 次完成/秒”主要来自快速拒绝，成功吞吐没有随它增长；成功样本只有 6 个，不能拿该组的成功尾延迟作严肃统计。若只保留完成速率与总体 P95，结论很容易被完全读反。应在自己的环境重复多轮，保留原始结果后再决定参数。

开启 admission 后，Semaphore.tryAcquire 拿不到名额立即返回 503；客户端很快完成失败，再立即发送下一次。总体完成速率可能大幅提高，但成功请求数可能很少。

因此至少联合比较：

- successfulPerSecond 是否增加。
- successes / completed 是否下降。
- 成功延迟、全体延迟和拒绝耗时分别是多少。
- 故障解除后，连接和队列能否回到基线。

准入控制的目标是保护资源和控制等待，不是凭空创造数据库能力。生产客户端需要遵守退避、重试预算和 Retry-After 等约定，否则快速失败与立即重试会形成重试风暴。不同客户端、业务和租户还可能需要公平性策略。

## 7. 把 Trace、指标和线程证据合起来

不关闭 tracing 并连接 Collector 时，检查 db.acquire 和 db.hold：前者反映租借时间，后者反映连接持有。Prometheus 中同时观察 Hikari active/pending、连接获取/使用计时、HTTP 状态分布和自定义拒绝计数。

取线程证据时先确认本次应用 PID。在 getConnection 等待栈上出现多个请求线程，配合 active 接近上限、pending 增长，才能支撑“连接排队”的判断。单份栈、单个 CPU 利用率都不足以定因。

若扩池后 acquire 降低而 hold 上升，说明瓶颈可能移动到数据库内部；若两者都低而客户端仍慢，就继续查入口排队、网络、序列化和响应写出。

## 8. 从教学对照到容量规划还差哪些测量

将受控睡眠换为真实数据量、索引和事务，把本机依赖换为目标环境，固定读写比例、热点和请求大小；采用开放到达率模型观察 offered、accepted、completed 和 rejected。

在预热后逐级增加负载，每档持续足够时间，至少重复多轮；还要测试缓存冷启动、一个副本故障、滚动发布和依赖变慢。保留 JDK、GC、容器 CPU/内存限制、数据库版本与负载机配置，才有可复核的容量结论。

本机实验可教会“为什么等待”和“怎样比较”，不能直接推导生产单副本承载 1000 QPS，也不证明扩大连接池是通用修复。

## 9. 练习与答案

### 9.1 completedPerSecond 上升十倍，为什么业务吞吐可能没提高

可能是大量 503 更快完成。必须看 successfulPerSecond、成功比例以及成功与失败各自延迟，不能把完成响应数等同完成业务数。

### 9.2 连接池只有两个连接，应该直接加到一百吗

不应该。先确认持有原因、数据库承载能力和应用总并发；过多连接可能把排队从应用移到数据库，放大锁和内存压力。

### 9.3 同样 80 个请求为何不能据此严肃比较 P99

尾部只有极少样本，预热、调度和随机误差影响很大，闭环模型又会改变到达过程。需要更长窗口、足够样本、重复实验和正确负载模型。
