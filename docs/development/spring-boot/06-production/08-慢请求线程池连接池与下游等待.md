# 慢请求、线程池、数据库连接池与下游等待

假设 API P99 从 100ms 升到 2s，CPU 只有 30%，数据库执行统计也正常。此时不应立即扩大线程池：延迟可能花在尚未进入数据库执行统计的等待里。

## 1. 按边界分解时间

![请求对线程、连接、下游和内存资源的依赖](/img/development/request-resources.svg)

```text
客户端总时间
= DNS / 建连 / TLS
+ 网关与入口等待
+ 应用排队
+ CPU / 锁 / 调度
+ 连接租借
+ 下游执行与读取
+ 序列化与响应发送
```

这些时间可能重叠，不能无脑相加不同系统的平均值。先统一一次请求的时间线，明确指标开始/结束边界。

## 2. 症状到证据

| 观察 | 候选原因 | 继续核验 |
| --- | --- | --- |
| active 请求高、CPU 低 | IO、锁、资源排队 | 线程栈与等待指标 |
| Hikari pending 高 | 池小、持有长、泄漏 | usage、事务与数据库锁 |
| HTTP pending 高 | 连接/流上限、body 未释放 | 目标级连接统计 |
| CPU 高且分配率高 | 计算、序列化、GC | JFR、热点和分配 |
| 应用计时快、客户端慢 | 入口、网络、响应写出 | 网关、连接与分包证据 |

这些是候选，不是单指标定论。同一 CPU 百分比还受容器核数与统计分母影响。

## 3. 先保存低风险证据

Linux/JDK 环境中先确定本应用 PID，再执行：

```bash
jcmd -l
jcmd <pid> Thread.print -l
jcmd <pid> JFR.start name=slow settings=profile duration=60s filename=/safe-path/slow.jfr
```

`<pid>` 和路径需替换，使用与进程权限/版本匹配的工具。只采集有权限的目标，转储文件可能含敏感信息，profile 采样也有开销。隔一段时间再取线程栈，区分瞬时状态和长期相同等待，不每秒无限导出。

线程处于 WAITING 不自动说明故障；线程池空闲也会等待。要把栈中的租借、锁、socket、队列与请求/池指标对上。CPU 热点可用 JFR 等分析，而不根据一个线程名字猜。

## 4. 一个典型连接池等待链

事务开始租借连接，执行快 SQL，然后在事务内等远端接口 2 秒。连接 active 很高，数据库 CPU 很低；新请求卡在 getConnection。扩池会把更多请求和远端调用同时放进去，可能短期缓解、长期放大。

正确方向是明确副作用协议，缩短数据库事务，限制远端并发，并让入口 deadline 与内部等待一致。不能为了“去掉事务内 HTTP”简单改成提交后无可靠发送，见 [Outbox](../03-data/06-业务事务Outbox与外部副作用.md)。

可以先运行[连接池排队对照实验](./14-连接池排队准入控制与容量对照实验.md)：每次 SQL 很简单，但人为持有连接 80ms，8 个并发请求竞争 2 个连接，便会出现获取等待和部分 503。配套[遥测实验](./13-OTLP链路导出指标日志与等待分解实战.md)将 db.acquire 与 db.hold 拆为兄弟 span；这比把一个大 DB span 全称为“SQL 慢”更准确。

## 5. 修复后的验证

在同负载、数据和版本下比较租借等待、连接持有、下游在途、P99、错误和重试数。恢复后池和队列应回基线；只看到 CPU 上升、QPS 上升不能证明尾延迟或可靠性改善。

生产故障不先重启销毁证据，也不批量 kill 数据库连接。涉及变更的操作应经过明确授权和隔离验证。

## 6. 练习与答案

### 6.1 数据库慢查询为零，为何请求仍在等数据库相关资源

可能还没拿到连接，或在网络/结果读取；慢查询日志只覆盖其中某个阶段。

### 6.2 更多线程一定减少等待吗

不会，可能增加同时争用连接、锁和内存，放大排队。

### 6.3 一份线程栈能证明根因吗

通常不够，要结合多时刻栈、指标与请求时间线验证假设。
