# 依赖兼容、行为变化与升级回归

升级后编译成功只排除了部分 API 错误。默认值、序列化、过滤器、超时和连接行为可能改变，即使一行源码都没改，运行结果也会不同。

## 1. 固定一组可解释的版本

本系列使用 JDK 25、Boot 4.1.1；Boot 管理的 Spring 等模块不逐个随意覆盖。第三方 Starter、数据库驱动、构建插件、Agent 和 Native 工具链分别核对支持矩阵。

```text
JDK / 构建工具
  → Boot parent / BOM
    → Spring / Security / Jackson / 容器 / 连接池
      → 第三方 Starter 与外部服务协议
        → 最终 JAR / OCI 镜像 / 部署环境
```

“用了最新”不是可复现说明。记录确切版本、依赖树、构建 commit、镜像摘要和配置；升级应是明确改变，而不是每次构建自动漂移。

## 2. 典型跨代边界

javax 到 jakarta 的包变化不是字符串替换就完成，依赖也需支持同一规范；Boot 4 的模块化改变 Starter 和测试包；Jackson 3 改变部分导入与扩展接口；服务器/JDK 升级可能改变默认协议和资源行为。

看官方迁移与发行说明，尤其关注废弃项移除、默认安全行为、属性重命名和测试模块。不要靠强制依赖版本把不兼容 Starter “压到能编译”。[Boot 4.1 发行说明](https://github.com/spring-projects/spring-boot/wiki/Spring-Boot-4.1-Release-Notes)

## 3. 四类回归

第一类是契约：请求字段、错误响应、时间/精度、HTTP 状态与安全规则。第二类是数据：事务、迁移、锁、缓存与消息协议。第三类是资源：线程、连接、内存、退出和探针。第四类是性能：固定负载下的吞吐与尾延迟。

```bash
mvn dependency:tree
mvn clean verify
jar tf target/boot-service-lab-1.0.0.jar
```

这些命令是起点，不替代真实目标数据库、IdP、代理和容器验证。打包后还应实际运行 JAR，不能只通过 IDE 启动判断产物正确。

## 4. 回退必须和 schema 协调

旧代码能否读取新字段、缓存新格式、消费新消息？数据库若已收缩，回退镜像可能也无法工作。使用兼容扩展、双版本契约和明确收缩窗口，见 [数据库迁移](../03-data/05-Flyway-Liquibase与兼容数据库变更.md)。

Agent、运行镜像和配置也属于发布单元的一部分。回退代码但保留新参数，可能仍不能恢复原行为。

## 5. 建立最小而有效的证据

startup-lab 验证普通库/可执行 JAR、条件、属性和生命周期；service-lab 验证真实 Boot 数据/安全链；已有 Spring/Java 实验验证相应机制。每次升级重跑对应证据，再补外部服务和部署环境的真实回归。

配套的 31 项服务测试覆盖明确的本地边界；中间件、Native、systemd 和 Kubernetes 仍需要各自的环境回归，结果不能互相替代。

## 6. 以后如何继续深入

当前 42 篇 Boot 正文形成启动→HTTP→数据→集成→安全→生产的学习闭环。深入不是继续堆技术名，而是选一个真实请求，把配置来源、对象/线程、连接、事务、外部副作用和失败恢复逐一用运行证据说明。

遇到具体版本 bug，再沿相应源码追踪，保留最小复现、版本、预期与实际结果，修复后回归正常与异常路径。阅读资料提供地图，熟练度来自自己完成这些验证。

## 7. 练习与答案

### 7.1 BOM 能保证所有第三方库兼容吗

不能，BOM 管理有明确范围，第三方 Starter 和额外依赖仍需支持矩阵与运行测试。

### 7.2 源码没变为何还需要回归 JSON

序列化库、默认设置或消息转换器变化也会改变字段、格式与错误行为。

### 7.3 旧镜像还在就一定可回退吗

不一定，schema、消息、缓存、Secret 和配置可能已不再兼容。
