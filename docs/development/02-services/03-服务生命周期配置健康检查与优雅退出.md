# 服务生命周期：配置、启动、健康检查、排空与优雅退出

一个服务的正常路径不只是“监听端口并处理请求”。发布、扩容、缩容、节点驱逐和配置错误都会反复触发启动与退出。生命周期设计不正确，会表现为短时 502、重复任务、连接中断、数据未刷盘和 Pod 长时间 Terminating。

## 1. 完整状态机

```text
Created
→ ConfigLoaded
→ DependenciesInitialized
→ Listening
→ Ready
→ Draining
→ Stopping
→ Stopped
```

状态转换必须有条件：

- Config 校验失败：启动失败，不进入 Listening；
- 关键依赖未就绪：不进入 Ready；
- 收到退出信号：先离开 Ready，再 Drain；
- Grace Period 到期：强制取消剩余任务并留下证据。

不要让“端口已监听”自动等于“可以接业务流量”。

## 2. 配置是有类型的输入

配置来源常见优先级：

```text
Built-in Defaults
< Config File
< Environment Variables
< Explicit CLI Arguments
```

是否采用该顺序取决于项目，但必须唯一且可解释。启动时把最终配置解析为类型化对象：

| 字段 | 校验 |
| --- | --- |
| `listen_address` | 合法地址和端口 |
| `request_timeout` | 正数且小于上游总 Deadline |
| `max_inflight` | 正数，有平台安全上限 |
| `db_dsn` | Scheme/Host/Database 完整，Secret 不进入日志 |
| `log_level` | 受控枚举 |
| `model_path` | 路径存在只是第一步，还需格式/权限/容量检查 |

不要让无效配置运行到第一次请求才失败。

## 3. Secret 与普通配置分开

Secret 的生命周期更严格：

- 不出现在命令行参数和进程列表；
- 不打印原值、完整 URL 和 Authorization Header；
- 文件权限和 Mount 范围最小化；
- Rotation 时定义新旧凭据重叠窗口；
- Error Wrap 不包含 Secret；
- Core Dump、Trace 和诊断包同样可能泄露。

“从环境变量读取”不自动安全，仍可能通过 `/proc`、Crash Report、Debug Endpoint 或日志暴露。

## 4. 启动阶段怎样排序

推荐顺序：

1. 读取并校验配置；
2. 初始化日志、指标和 Trace 的最小能力；
3. 建立资源限制和 Runtime 参数；
4. 创建 DB/HTTP/Queue 等 Client；
5. 完成必要 Schema/Capability 检查；
6. 启动后台 Worker；
7. 监听端口；
8. 自检通过后标记 Ready。

初始化失败要关闭已经创建的资源，不能在失败重试中泄漏 Thread、Socket 或临时文件。

## 5. Fail Fast 与 Retry Startup

并非所有依赖失败都应让进程无限重试：

| 失败 | 建议 |
| --- | --- |
| 配置语法、证书格式、权限策略错误 | Fail Fast，修正配置 |
| DNS/依赖短暂不可用 | 有界退避，保持 NotReady |
| 数据库 Schema 不兼容 | Fail Fast，阻止错误版本接流量 |
| 可选依赖不可用 | 明确 Degraded Mode，不伪装完全健康 |
| Secret 永久无权 | Fail Fast 或受控 NotReady，避免无限打认证服务 |

无限 Startup Retry 会让错误版本看起来“仍在恢复”，掩盖发布失败。

## 6. 三类健康检查

### 6.1 Liveness

回答：进程是否进入无法自行恢复、需要重启的状态？

不应因为普通外部依赖短暂不可用就失败，否则数据库抖动会触发所有应用重启，形成风暴。

### 6.2 Readiness

回答：当前实例是否应该接收新流量？以下情况可 NotReady：

- 尚未完成 Warm-up；
- 连接池/关键依赖不可用且无法服务；
- 正在 Drain；
- 本实例资源严重不足；
- 必要模型尚未加载。

### 6.3 Startup Probe

为慢启动应用提供独立启动窗口，在成功前避免 Liveness 过早杀死进程。它不能替代优化启动或永久掩盖卡死。

## 7. 健康检查不能太重

错误例子：每秒对所有数据库、对象存储、消息队列做写测试。它会：

- 放大依赖压力；
- 因一个共享依赖故障让所有实例同时摘除；
- 让探针本身产生慢查询；
- 产生无意义测试数据。

更合理的分层：

```text
/health/live   → Event Loop/关键线程有进展，进程状态未损坏
/health/ready  → 能否接当前类型的新请求
/health/detail → 受保护的诊断端点，展示依赖状态但不直接给平台重启判定
```

## 8. Readiness 的状态传播有延迟

在 Kubernetes 中，应用返回 NotReady 后仍要经过 Probe、Pod Condition、EndpointSlice、kube-proxy/数据面和已有连接。不能假设状态切换瞬间停止所有流量。

因此退出顺序通常为：

```text
收到 SIGTERM
→ readiness=false
→ 等待流量端点传播/执行 pre-drain
→ 停止接受新请求
→ 等待 In-flight
→ 取消剩余请求
→ Flush/Close
→ 退出
```

已有 Keepalive、HTTP/2 Stream、gRPC 长流和 Gateway 连接可能继续存在，需要服务端主动执行 Graceful Stop/GOAWAY 等协议动作。

## 9. Signal 处理

容器中主进程应正确接收 SIGTERM：

- 使用 Exec Form ENTRYPOINT，避免 Shell 吞信号；
- PID 1 的 Signal/Child Reaping 行为要验证；
- Handler 不做复杂阻塞工作，只触发 Shutdown；
- 第二次信号可升级为快速退出，但要记录未完成状态；
- SIGKILL 无法捕获，所有正确性不能依赖最终 Cleanup 一定执行。

```text
SIGTERM → set draining → close listener → cancel context → wait group
SIGKILL → immediate termination, no handler
```

## 10. 优雅退出的时间预算

假设 Pod `terminationGracePeriodSeconds=60`：

```text
0-5s    从 Endpoint 摘除并停止新任务
5-45s   完成大多数 In-flight
45-55s  取消剩余任务、归还 Lease、Flush
55-60s  Close Client、输出最终指标并退出
```

内部 Shutdown Deadline 必须短于平台 Grace Period，留出 Runtime 和容器退出余量。单个 Request Deadline 也不能大于可用排空预算，否则永远等不完。

## 11. Listener、连接与请求的关闭顺序

推荐依赖逆序关闭：

1. 标记 NotReady；
2. 停止新的 Scheduler/Consumer Claim；
3. 停止接受新连接/请求；
4. 等待或取消 In-flight；
5. 等待后台 Worker；
6. Flush Batch/Buffer；
7. 关闭 DB、HTTP、Message Client；
8. Flush Telemetry（有短 Deadline）；
9. 退出。

先关闭数据库再等 Handler，会让所有在途请求在收尾阶段失败。

## 12. 后台任务的生命周期

每个后台任务都要回答：

- 谁启动；
- Ready 前是否必须完成第一轮；
- 失败是重启 Task、降级还是终止进程；
- 是否继承进程级 Cancel；
- Shutdown 时是否 Join；
- 是否持有 Lease/Lock/Partition；
- Checkpoint 在哪里；
- 重启后是否重复执行。

不受管理的 Fire-and-forget Task 是常见泄漏源。

## 13. 消费者与任务服务的退出

消息消费者不能只 Close Connection：

```text
Stop Fetch/Claim New Messages
→ Wait In-flight Handler
→ Commit/Ack 成功消息
→ 不 Ack 未完成消息
→ Release Partition/Lease
→ Close Client
```

Ack 在处理前会丢任务；处理完成后 Ack 失败会重复任务。因此 Handler 必须幂等，Exactly-once 通常需要业务存储与消息状态的协同设计。

## 14. 配置 Reload

先把配置分为：

| 类型 | 示例 | 策略 |
| --- | --- | --- |
| Immutable | Listen Address、Storage Engine | 重启生效 |
| Reloadable | Log Level、Feature Flag、部分限流 | 原子替换 Snapshot |
| Secret/Certificate | TLS Cert、Token | 双 Buffer/新连接使用新值 |
| Dangerous | 并发、Timeout、Queue Size | 校验范围、渐进发布 |

Reload 必须是事务性的：完整解析和校验新配置，成功后一次替换；不能逐字段更新让请求看到半新半旧状态。失败时继续使用旧配置并告警。

## 15. Warm-up 与冷启动

AI/数据服务启动可能包含：

- 模型权重读取；
- CUDA/CANN Context 与 Kernel/JIT Cache；
- DB Pool 建连；
- DNS/TLS Session；
- Cache/Index 加载；
- Lazy Import/Class Loading。

Readiness 应反映“关键请求能否满足 SLO”，但 Warm-up 不能无限延长。记录各阶段耗时和字节，才能区分存储、网络、编译、内存分配或设备初始化。

## 16. 一份 Kubernetes 配置示意

```yaml
startupProbe:
  httpGet: {path: /health/startup, port: 8080}
  periodSeconds: 5
  failureThreshold: 60
livenessProbe:
  httpGet: {path: /health/live, port: 8080}
  periodSeconds: 10
readinessProbe:
  httpGet: {path: /health/ready, port: 8080}
  periodSeconds: 3
terminationGracePeriodSeconds: 60
```

数值只是示意，必须由真实启动分布、流量传播和最大请求时间推导。过短 Probe Timeout、同步访问远程依赖、所有 Pod 同时探测都可能制造误杀。

## 17. 生命周期指标

- Process Start Time / Build Info；
- Config Version/Hash（不包含 Secret）；
- Startup Stage Duration；
- Ready State 与最后变化原因；
- In-flight、Queue Depth、Active Worker；
- Shutdown Reason；
- Drain Duration；
- Forced Cancellation Count；
- Unflushed/Unacked Work；
- Exit Code。

日志应包含一次生命周期的 Instance ID 和 Build Commit，避免把旧 Pod 的退出日志与新 Pod 的启动日志混在一起。

## 18. 常见误区

### 18.1 Liveness 检查数据库

数据库故障会使所有 Pod 同时被重启，而重启不能修数据库，还会增加连接压力。

### 18.2 收到 SIGTERM 立刻退出

Endpoint 传播和已有连接存在延迟，会造成请求中断和消息重复。

### 18.3 `preStop: sleep 10` 就完成优雅退出

固定 Sleep 不能感知端点传播和 In-flight，也不能管理长连接。应用必须实现 Drain，Sleep 只能作为经过验证的传播余量。

### 18.4 Shutdown 一定能执行 Cleanup

OOM、节点掉电、SIGKILL 和进程崩溃都可能绕过 Cleanup。数据正确性必须依赖事务、日志、Lease TTL 和幂等恢复。

## 19. 练习与答案

### 19.1 练习 1：Pod 能接受 TCP 连接，为什么还不能 Ready？ {/* #练习-1pod-能接受-tcp-连接为什么还不能-ready */}

答案：端口监听只证明 Socket 已建立。模型、Schema、Cache、Worker 或关键依赖可能尚未完成，接入请求会超时或失败。

### 19.2 练习 2：为什么 Shutdown 时先停止接新请求，再关闭数据库？ {/* #练习-2为什么-shutdown-时先停止接新请求再关闭数据库 */}

答案：在途 Handler 仍需要数据库完成工作。先关依赖会主动制造失败；应先截断新流量，再等待工作，最后逆序释放依赖。

### 19.3 练习 3：依赖暂时不可用时，Liveness 和 Readiness 应如何变化？ {/* #练习-3依赖暂时不可用时liveness-和-readiness-应如何变化 */}

答案：若进程自身仍可恢复，Liveness 保持成功；若实例无法提供服务，Readiness 可失败。这样平台停止分流但不会制造重启风暴。

### 19.4 练习 4：为什么配置 Reload 要原子替换？ {/* #练习-4为什么配置-reload-要原子替换 */}

答案：逐字段修改会让并发请求看到不一致组合，例如新 Endpoint 配旧 Credential。应先完整解析验证，再发布不可变 Snapshot。
