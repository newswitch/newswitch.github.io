# 并发、异步、背压与取消：从任务到可控系统

并发不是把所有任务同时启动。没有上限的线程、Goroutine 或 Coroutine 会把下游容量、内存和 Deadline 一起耗尽。可靠并发的核心是：明确所有权、限制在途工作、传播取消，并让失败能够收敛。

## 1. 先区分四个概念

| 概念 | 含义 |
| --- | --- |
| Concurrency | 多个任务的生命周期重叠，系统在它们之间推进 |
| Parallelism | 多个任务在多个执行资源上同时计算 |
| Asynchrony | 发起操作后不阻塞当前执行流，完成时再通知 |
| Distribution | 任务跨进程/机器，存在网络与部分失败 |

单核 Event Loop 可以高并发但不并行；多核矩阵计算可以并行；Async API 也可能在内部使用线程池完成阻塞操作。

## 2. 执行单元与调度者

```text
OS Thread
├── 由 Kernel 调度
├── 有独立 Stack 和调度成本
└── 可在多核并行

User-space Coroutine / Goroutine / Task
├── 由 Runtime/Event Loop 调度
├── 数量可远大于 Thread
└── 阻塞系统调用处理不当仍会拖住执行线程
```

不同 Runtime 的细节不同：Python Thread 受解释器实现与 GIL 影响；`asyncio` Task 依靠协作 `await`；Go Runtime 把 Goroutine 多路复用到 OS Thread。选择模型前先确认工作负载是 CPU-bound 还是 I/O-bound。

## 3. CPU-bound 与 I/O-bound

| 工作负载 | 主要等待 | 常见策略 |
| --- | --- | --- |
| CPU-bound | 指令执行、Memory Bandwidth | 多进程/原生线程/向量化/GPU，数量接近可用核或实测最优值 |
| I/O-bound | 网络、磁盘、数据库 | Async I/O 或有界线程池，提高在途并发 |
| Mixed | 解析 + RPC + 压缩 | 分离 Stage，分别限流和观测 |

I/O-bound 也不是并发越大越好。下游连接池 100，启动 10 万个请求只会让 99,900 个任务排队并占用内存。

## 4. Race Condition 与 Data Race

两个概念相关但不完全相同：

- Race Condition：结果依赖不可控的执行顺序；
- Data Race：多个执行单元未同步访问同一内存位置，且至少一个写。

```text
read balance=100
read balance=100
write balance=90
write balance=80
```

即使语言 Runtime 防止内存破坏，Read-Modify-Write 仍可能发生业务 Lost Update。数据库 CAS、事务或单一所有者模型同样重要。

## 5. Happens-Before 与内存可见性

“源码中先写 data 再写 ready”不自动保证另一个 CPU 按同样顺序观察。编译器、CPU Store Buffer 和 Cache Coherence 都参与可见性。

高级同步原语通常建立 Happens-Before：

- Mutex Unlock → 后续成功 Lock；
- Channel Send → 对应 Receive；
- Thread Start/Join；
- Atomic Release → 读取同一同步对象的 Acquire。

不要用 `sleep()` 代替同步；它只改变时间概率，不建立内存顺序。

## 6. Mutex、RWLock、Semaphore 与 Channel

| 原语 | 保护/表达 | 常见风险 |
| --- | --- | --- |
| Mutex | 临界区互斥 | 锁顺序死锁、持锁 I/O、粗粒度竞争 |
| RWLock | 多读单写 | 写饥饿、读临界区过长、升级困难 |
| Semaphore | 同时持有某资源的数量 | Permit 泄漏、与真实容量不一致 |
| Condition/Event | 状态变化通知 | Lost Wakeup、条件未循环检查 |
| Channel/Queue | 数据与所有权传递 | 无界增长、关闭语义、消费者泄漏 |
| Atomic | 小型状态的原子操作 | ABA、复合不变量、内存序误用 |

锁保护的是不变量，不只是某一行变量。先写出“哪些字段必须一起变化”，再选择锁范围。

## 7. 死锁、活锁与饥饿

### 7.1 Deadlock

经典条件：互斥、持有并等待、不可抢占、循环等待。常见预防：

- 固定全局锁顺序；
- 不在持锁时调用未知 Callback 或远程 I/O；
- 缩小临界区；
- 使用 Timeout 只能暴露/缓解，不自动修复状态；
- 通过 Profile/Thread Dump 查看等待图。

### 7.2 Livelock

任务都在运行并不断礼让/重试，却没有进展。需要随机退避、仲裁或减少对称竞争。

### 7.3 Starvation

某任务长期拿不到 CPU、锁、队列或配额。公平队列、优先级老化和分租户限流可以缓解，但可能降低峰值吞吐。

## 8. 有界并发

一个常见模式：

```text
Input
→ Bounded Queue
→ N Workers
→ Bounded Result Buffer
→ Aggregator
```

必须同时限定：

- Worker 数；
- Input Queue 元素数和字节数；
- 每任务内存/文件/连接；
- 单任务与总 Deadline；
- Result Buffer；
- Retry 中的在途任务；
- 每租户和全局并发。

只限制 Worker、不限制 Queue，仍可能 OOM。

## 9. Little's Law 与并发估算

稳定系统中近似：

```text
L = λ × W

L：系统平均在途数量
λ：平均完成/到达率
W：平均停留时间
```

若目标 1000 req/s，平均响应 0.1 s，平均在途约 100。若下游延迟升到 1 s，而流量不变，在途会升到约 1000。这个关系解释了下游变慢时为何连接、协程和内存同时上涨。

Little's Law 不是自动配置公式：突发、尾延迟、非稳定状态和多阶段排队仍需额外余量与实测。

## 10. Backpressure（背压）

背压表示消费者容量不足时，把压力传回生产者：

| 策略 | 行为 | 适用边界 |
| --- | --- | --- |
| Block/Wait | 生产者等待槽位 | 上游能等待且 Deadline 足够 |
| Reject | 立即返回 429/RESOURCE_EXHAUSTED | 在线请求、保护系统 |
| Drop | 丢弃新/旧/低优先级数据 | Telemetry、可容忍丢失流 |
| Spill | 写磁盘/消息队列 | 能接受更高延迟和恢复复杂度 |
| Sample/Coalesce | 合并或采样更新 | 状态刷新、监控事件 |
| Scale | 增加消费者 | 下游和资源仍有余量时 |

“写到 Kafka”不是自动解决背压，只是把缓冲持久化。Kafka Lag 仍需容量、保留和恢复时间设计。

## 11. Timeout、Deadline 与 Budget

Timeout 是一段时间，Deadline 是终止时间点。调用链应传播 Deadline：

```text
Client 2s
→ Gateway 剩余 1.9s
→ Service 剩余 1.6s
→ DB 最多 0.8s
→ 保留响应编码和网络预算
```

每层重新设置 2s 会使总时长膨胀。每次 Retry 也必须消耗同一总预算。

阶段 Timeout 常见包括：DNS、Connect、TLS Handshake、Pool Acquire、Request Headers、Body Read 和 Idle。只有总 Timeout 无法指出耗在哪一段。

## 12. Cancellation 是协作协议

取消通常不能安全地在任意指令处强杀执行单元，因为它可能正持锁、写文件或更新共享状态。可靠取消要求：

1. 发出 Cancel Signal；
2. Task 在安全点检查；
3. 向子任务和下游传播；
4. 停止创建新工作；
5. 释放资源并保留错误；
6. Parent 等待 Child 收敛；
7. 超过 Grace Period 才升级为强制终止。

取消不等于事务回滚。已经提交的副作用要靠补偿、幂等或状态机收敛。

## 13. Structured Concurrency（结构化并发）

核心思想是 Child Task 的生命周期不逃逸出 Parent Scope：

```text
Parent Scope
├── Child A
├── Child B
└── Child C

Scope 结束前：全部成功，或取消其余并收集失败
```

它解决“Fire-and-forget Task 谁负责、错误去哪、何时结束”的问题。Python `TaskGroup`、Go 中显式 `Context + WaitGroup/errgroup` 都可表达类似结构，但取消和错误细节随语言实现不同。

## 14. Fan-out/Fan-in 的尾延迟

一次请求并行访问 100 个 Shard，整体通常等待最慢一部分：

```text
Request
→ 100 subrequests
→ wait all
→ overall latency ≈ max(subrequest latency)
```

即使每个 Shard P99 不高，大 Fan-out 也提高至少一个慢请求出现的概率。优化方向：

- 减少 Fan-out；
- 分层聚合；
- 只请求需要的 Shard；
- Partial Result/Quorum（业务允许时）；
- 独立 Deadline 和 Bulkhead；
- Hedging 只用于严格受控的幂等读。

## 15. Retry Storm 与并发放大

原始 1000 req/s，若失败后立即重试 3 次，可能变成 4000 attempts/s。依赖越慢，Attempt 占用越久，进一步降低容量。

保护组合：

- Exponential Backoff + Jitter；
- Retry Budget；
- Circuit Breaker；
- Concurrency Limit；
- Load Shedding；
- Bulkhead；
- 幂等与去重；
- 明确不可重试错误。

## 16. Async I/O 的常见陷阱

### 16.1 在 Event Loop 中执行阻塞调用

一个同步 DNS/文件/SDK 调用会阻塞整条 Loop。应使用真正 Async API 或受控线程池，并观测线程池队列。

### 16.2 创建 Task 后不保存引用

错误无人收集，退出时任务仍在运行。使用 Task Group 或显式 Registry。

### 16.3 吞掉 Cancellation

捕获所有异常后不重新传播取消，会让 Deadline 失效并阻止 Shutdown。清理后应遵守语言的取消契约。

### 16.4 Async 等于更快

Async 主要提高等待期间的资源利用率；CPU-bound 代码不会因 `async` 自动并行，反而增加调度开销。

## 17. 观测并发系统

至少记录：

| 指标 | 解释 |
| --- | --- |
| In-flight | 当前执行数量 |
| Queue Depth/Bytes | 等待数量和内存压力 |
| Queue Wait | 在开始执行前等待多久 |
| Active Workers | 实际忙碌执行单元 |
| Completion Rate | 完成速度，而非只看到达速度 |
| Rejected/Dropped | 过载保护是否发生 |
| Deadline/Cancel | 谁先终止 |
| Retry Attempts | 流量放大 |
| Lock Wait/Contention | 串行化热点 |
| Goroutine/Thread/Task Count | 生命周期泄漏 |

队列等待和执行时间要分开，否则会把排队误判为业务慢。

## 18. 常见误区

### 18.1 协程轻量，所以可以无限创建

每个 Task 仍持有 Stack/Frame、Future、上下文、请求和结果引用；更重要的是它代表对下游的在途压力。

### 18.2 加锁后程序就线程安全

锁范围、顺序、外部副作用、状态机和数据库并发仍可能错误。

### 18.3 Timeout 能终止服务端工作

客户端停止等待不代表远端自动停止。协议要传播取消，Handler 也必须协作检查。

### 18.4 扩大连接池能解决下游慢

若数据库已饱和，更多连接会增加竞争和尾延迟。连接池是并发闸门，不是吞吐生成器。

## 19. 练习与答案

### 19.1 练习 1：服务有 100 个 Worker，为什么队列仍持续上涨？ {/* #练习-1服务有-100-个-worker为什么队列仍持续上涨 */}

答案：到达率长期高于完成率，或 Worker 被下游/锁阻塞。应比较 λ、μ、Queue Wait 和下游延迟；增加 Worker 只有在下游仍有容量时有效。

### 19.2 练习 2：设置 2 秒 Client Timeout 后，数据库查询会在 2 秒自动停止吗？ {/* #练习-2设置-2-秒-client-timeout-后数据库查询会在-2-秒自动停止吗 */}

答案：不一定。必须把 Deadline/Cancel 传到服务端和数据库 Driver，并由其支持取消。即便查询停止，之前提交的事务也不会自动撤销。

### 19.3 练习 3：为什么 `sleep(1)` 不能修复 Race？ {/* #练习-3为什么-sleep1-不能修复-race */}

答案：它不建立 Happens-Before，只改变调度概率。机器负载或执行顺序变化后问题仍会出现。

### 19.4 练习 4：何时应该拒绝而不是排队？ {/* #练习-4何时应该拒绝而不是排队 */}

答案：当预估 Queue Wait 已超过请求 Deadline，或队列继续增长会威胁系统恢复能力时，尽早返回 429/RESOURCE_EXHAUSTED 通常比让请求超时更可控。
