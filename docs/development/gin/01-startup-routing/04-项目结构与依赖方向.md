# Gin 项目结构与依赖方向：Handler、Service、Store 和 Transport

目录拆分的目标是让改变有明确位置，而不是机械建立越多层越好。一个小项目也应能替换入口、测试业务，并看清事务和资源由谁管理。

## 1. 工程地图

```text
service-lab/
├── cmd/taskd/             # 入口、配置、信号与资源装配
├── cmd/webdemo/           # 有限请求链实验
├── internal/app/          # HTTP 边界、认证和任务执行
├── internal/store/        # SQL、事务、租约、Outbox/Inbox
├── internal/transport/    # Redis 与 Kafka 客户端
├── internal/observe/      # Metrics 与 OTel
├── internal/session/      # SQL 会话与 HTTPS 生命周期
├── internal/keyauth/      # RS256 受信公钥轮换实验
├── internal/migrate/      # 固定连接与事务 DDL 实验
├── integration/           # 显式外部联调测试
└── deploy/                # Collector 与 Kubernetes 实验配置
```

这是一个刻意保持紧凑的教学工程：简单任务业务没有为每个结构体强行创建接口。复杂业务增长时，可提取纯领域包和用例层，但不要让领域代码依赖 gin.Context。

## 2. 数据如何越过边界

Handler 接收 DTO、验证协议、提取身份并将 Request.Context 传下去；Store 返回 Task 或可识别错误；HTTP 边界把 Missing、Conflict、Deadline 映射状态码。

事务由能覆盖完整不变量的用例/存储操作组织，不能每个 Repository 方法自行提交后，再假装上层操作原子。缓存与 Broker 客户端只执行各自协议，不持有整个 Gin Context。

## 3. 依赖反转的实际位置

当需要在真实 Kafka 与故障注入之间替换时，Store 的 Relay 接受小 Publisher 接口。接口由使用方定义，避免依赖某个 Broker 客户端的全部 API。

不要对每层建立万能 `interface{Do(any)any}`。丢掉静态类型后会把错误挪到运行时，测试也更难表达。

## 4. 闭环而不是 CRUD 拼接

综合项目覆盖创建与重复提交、状态读取、版本取消、Worker 租约、过期恢复、Outbox 确认及消费去重。每条路径都有自己的状态与失败测试。

它没有内建完整 OIDC 身份平台、任意任务脚本执行或生产数据库迁移器，不能因目录齐全就宣称这些能力已完成。学习时把已实现与待选型的扩展分开。

## 5. 目录边界最终应对应可替换的变化

修改 HTTP 错误结构应主要发生在协议边界；修改任务合法状态应发生在用例或领域边界；更换 SQL 参数占位与驱动应集中在存储边界。若一个简单变化需要横跨所有层复制同一段判断，职责可能并未真正分开。

项目小的时候可以在紧凑的 app/store 中保持清楚顺序，没必要为每个结构体强制建立 Interface、Service 与 Manager。拆层的依据是依赖方向与变化，不是目录数量。

新增 protocol、requestflow 等实验包只服务于相应机制验证，不意味着生产任务服务自动采用每个独立实验的策略。例如 protocol 的 413 与 taskd 统一 400 是两份有明确边界的协议。

## 6. 事务边界由业务不变量决定

创建 Task 和保存 TaskCreated 事件必须同事务，不能让上层先调用一个自动提交的 Create，再调用另一个自动提交的 PublishRecord，然后称为原子操作。

如果事务需要协调多个仓储，应由能表达整个用例的对象控制 Tx，或提供明确的事务执行接口。不要把 sql.Tx 塞进 Gin Context 的任意 Key，再让全部层自行猜是否需要提交。

请求 Context 可以向下传递取消，框架 Context 则停留在边界。领域对象不应持有 c.Writer，也不应为了记录日志依赖全部 HTTP 请求，这样 Worker 与 HTTP 才能复用相同业务规则。

## 7. 依赖注入要暴露时钟、网络与资源责任

对故障测试有意义的替换点包括时钟、Publisher 与外部执行器。接口由使用方表达最小要求，返回稳定的错误与确认语义，而不是把某个客户端的全部方法原样复制一份。

依赖的创建与关闭集中在入口；长生命周期客户端不在每请求重新构造。测试可以注入有限时钟或明确故障，不必通过修改系统时间、删除真实数据或启动永久进程观察行为。

工程目录图中的 deploy/integration 与业务包也不是同一层：前者验证运行环境和真实协议，不能用它们的存在替代已执行证据。看代码时追一次 Task 创建和一次 Worker 完成，比先背所有目录名更有效。

## 8. 练习与答案

### 8.1 所有项目都必须四五层吗

不必，按变化边界拆分，避免空转发层。

### 8.2 领域对象应保存 gin.Context 吗

不应，框架请求对象应停留在协议边界。

### 8.3 接口越多越容易测试吗

不一定，小而明确的替换点比全量抽象更有价值。
