# Gin 对象权限与多租户隔离：认证之后还要检查什么

知道调用者是谁，不等于知道他可以读取哪个对象。跨租户越权通常发生在已经通过 JWT 验证之后，而非登录之前。

## 1. 身份、能力与对象

认证确认 subject 与可信 tenant，scope 表达粗粒度能力，资源查询再限制对象归属。task:read 只允许进入读接口，不代表读取所有租户的任务。

service-lab 从验证后的声明取 tenant，而不是信任 Body、Query 或 X-Tenant-ID。每个查询、取消与事件流都用 tenant+ID 条件；Task JSON 不向客户端展示内部租约字段。

## 2. 贯穿所有入口的隔离

列表、详情、修改、下载、SSE、缓存和消息消费都要检查租户语义。只保护详情 GET，但列表仍返回全部对象，是常见缺口。

异步事件在可信生产/消费边界仍需校验 schema 与 tenant；Kafka Topic ACL 也不能自动替代消息里的对象授权。分库、RLS 等是可选的纵深防御，不是应用无需过滤的理由。

## 3. 回归测试

```bash
cd examples/gin/service-lab
go test ./internal/app -run 'TestCrossTenant|TestScopeDenied' -count=1 -v -timeout=30s
```

另由 Store 的 TestTenantVisibility 直接检验存储边界。alpha 创建对象，beta 用真实有效但不同租户 Token 请求，应该看不到；未登录和合法身份越权是两个不同测试。

本项目将跨租户目标表现为 404，减少资源存在性泄露。具体接口需定义 403/404 策略，不能让不同路径随机返回不同信息。

## 4. 更新、批量与审计

批量接口不能只检查第一条对象归属；更新应将 tenant 与 version 同时纳入条件，防止查询后对象状态变化。后台任务和管理员能力需要显式权限，不应因“内部调用”就跳过所有检查。

审计记录主体、操作、对象标识与结果，但不要记录完整 Token。高权限操作的日志与业务事务失败如何关联，也要有明确证据链。

## 5. 认证、能力授权与对象授权需要分别成立

合法 JWT 证明凭证来自受信签发方且声明满足验证规则，scope 决定能否进入某类操作，对象查询再限制租户与资源身份。这三步不能用“已经登录”一句话合并。

当前 tenant 来自验证后的 Claims，而非请求体或任意 Header；Get/List/Cancel/SSE 都应把这个 tenant 传到存储层。缓存键、幂等键和异步事件也要保持同一身份模型，否则隔离会在另一条链路丢失。

管理员跨租户能力应是显式、可审计的额外权限，不能把 tenant 为空理解为“查询全部”。默认拒绝的边界比到处猜测空值含义更容易维护。

## 6. 把约束放进原子更新，而不是先查再相信

先查归属、再用只有 ID 的 UPDATE 修改，查询与更新之间还可能发生状态变化。更新条件应同时包含 tenant、ID 和必要 version/state，并按受影响行数判断结果。

列表与批量接口不能只过滤展示层或第一条对象；分页游标也不能跨租户随意复用。返回 404 隐藏资源存在性时，要让读取、修改与事件流保持一致策略，避免一个入口又透露目标状态。

数据库唯一约束、RLS 或分库可以提供纵深防御，但不能弥补应用把不可信身份当成租户的根本问题。权限模型与数据模型需要共同设计。

## 7. 回归断言覆盖返回值与数据状态

现有测试使用不同租户的合法实验身份，检查读取不可见、scope 拒绝和存储过滤；这与“无凭证返回 401”是不同规则。审查时沿列表、详情、更新、流、缓存与消息分别追踪身份来源。

更新拒绝后还应确认目标内容与版本未变；批量操作需明确全部成功或逐项结果，不应部分写入后返回一个含糊错误。审计只记录受控主体、操作、对象和结果，不保存完整 Token。

测试通过不意味着以后新增路由自动继承正确授权。新入口应复用可信身份边界与存储条件，并加入相应回归，而不只添加一个中间件名称。

## 8. 练习与答案

### 8.1 有 task:read 能读取所有任务吗

不能，还需要资源归属约束。

### 8.2 X-Tenant-ID 可以直接作为可信租户吗

不能，除非有受验证的可信注入和授权协议。

### 8.3 只测无 Token 返回 401 足够吗

不够，要测合法身份的越权与跨租户情况。
