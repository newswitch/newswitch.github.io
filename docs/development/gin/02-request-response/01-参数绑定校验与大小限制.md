# Gin 参数绑定、验证与大小限制：从合法 JSON 到合法业务输入

绑定负责把协议值放入结构体，验证负责拒绝不符合规则的输入，授权决定当前身份能否操作。三者不能相互替代。

## 1. 输入位置与 DTO

Path、Query、Header、JSON、Form 的来源不同，必须明确每个字段从哪里获取。避免同一权限字段同时从 Body 和 Header 读取后再猜优先级。

用专用 DTO 限制可写字段。租户、创建者、内部状态和版本控制字段不能因为与数据库模型同名，就无条件允许客户端覆盖。

## 2. 绑定失败实验

```bash
cd examples/gin/service-lab
go run ./cmd/webdemo -case binding
```

```text
status=400
{"error":"invalid input"}
```

完整代码与断言见 [service-lab](https://github.com/newswitch/newswitch.github.io/tree/main/examples/gin/service-lab)。

ShouldBind 系列通常把错误交给调用方，Bind 系列可能已经写入错误状态并中止；选择后不要重复写第二份响应。Tag 的 required 对零值有特定含义，缺失、null、零值仍需设计。

## 3. 严格 JSON 与资源上限

service-lab 使用自定义 decode：MaxBytesReader 限制 4096 字节，DisallowUnknownFields 拒绝未知字段，再次 Decode 要求 EOF，只允许一个 JSON 对象。随后检查名称、幂等键长度与空白。

当前练习实现把输入非法与超限统一为 400；若公开协议要求 413，应按 MaxBytesError 分类并加测试，不能文档写 413 而代码始终返回 400。代理的正文上限也应与应用一致。

## 4. 错误信息与演进

返回稳定错误类别与必要字段说明，内部错误、SQL 和 DSN 不回传。未知字段拒绝有助于发现拼写错误，但前后端增加字段时需协调兼容策略。

测试语法坏、类型错、缺失、null、零值、超长、多对象尾部、未知字段及 Unicode 空白。不要仅测试一个正确 POST 后就认为输入边界完善。

## 5. 练习与答案

### 5.1 绑定成功代表有操作权限吗

不代表，授权另行判断。

### 5.2 required 能完整表达所有业务规则吗

不能，跨字段、状态和资源权限仍需代码检查。

### 5.3 文章写 413 但代码返 400 算完成吗

不算，契约、实现和测试要一致。
