# Gin 响应、状态码与 JSON 契约：错误不只是一个字符串

客户端依赖的是稳定的状态与结构，而不是服务内部的异常文本。响应设计应表达成功、冲突、无权限、依赖失败和结果未知。

## 1. 状态与业务语义

200、201、202 的选择取决于资源是否已创建和工作是否已完成。service-lab 创建持久任务记录后返回 201，并不声称后台任务已经 SUCCEEDED；也可设计 202 加查询地址，但应保持契约一致。

400 是输入问题，401 是身份缺失或无效，403 是身份有效但权限不足，404 可用于隐藏跨租户资源，409 表示状态/幂等冲突。不要一律返回 200 再让客户端读 error 字符串。

## 2. 输出实验

```bash
cd examples/gin/service-lab
go run ./cmd/webdemo -case json
```

```text
status=200
{"count":0,"id":"t1"}
```

完整代码与断言见 [service-lab](https://github.com/newswitch/newswitch.github.io/tree/main/examples/gin/service-lab)。

明确的 0 可以有业务意义，不要为了省字段不加区分使用 omitempty。对内部 tenant、lease token 等使用专用 DTO 或 json:"-" 排除。

## 3. 写入时机与二次响应

第一次 WriteHeader 或正文写入会提交状态与头，后续再设置状态通常不能改变已经发出的协议。JSON 编码也可能失败，应保证类型可序列化并测试边界。

204/304 等状态的正文规则、HEAD 请求与缓存头要按 HTTP 语义处理，不要把某个框架方法当作忽略协议的特权。

## 4. 分页与演进

列表应限制 limit，并使用稳定游标。本工程用 ID keyset 顺序，含义是稳定词典序分页，不保证随机 ID 与创建时间一致；需要按创建时间分页时应加入时间和唯一 ID 的联合游标。

新增可选字段、错误码与枚举变化都可能影响客户端。为响应设置契约样例，避免把数据库新增的私有字段自动暴露出去。

## 5. 练习与答案

### 5.1 创建任务返回 201 表示任务完成了吗

不表示，它只确认任务资源已建立。

### 5.2 随机 ID 排序等于创建时间排序吗

不等于。

### 5.3 所有错误都返回 200 更方便吗

会破坏 HTTP 语义、重试与监控，不建议。
