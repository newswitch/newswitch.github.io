# Gin 综合实战：持久化任务、独立 Worker、重启与可靠事件

综合工程将语言、并发、HTTP、事务、安全和观测串起来。完成标准不是“接口能调用”，而是正常与失败路径都能解释、运行和验证。

## 1. 准备与两个进程

```bash
git clone https://github.com/newswitch/newswitch.github.io.git
cd newswitch.github.io/examples/gin/service-lab
go version
go mod download
go test ./... -count=1 -timeout=60s
go build -trimpath -o out/taskd ./cmd/taskd
# 终端 A：仅本机隔离演示
./out/taskd -demo -listen=127.0.0.1:8084 -dsn=tasks.db
# 终端 B：取得实验 Token
./out/taskd -mode=token -demo
```

Windows 构建 out/taskd.exe 并通过 PowerShell 执行。不要把 -demo 用于远端服务。本文所有 Token、任务 ID 都是本地运行时生成，不提供可误用的真实凭证。

## 2. 创建、执行与查询

```bash
# 先把上一步输出放入当前 shell 的 TOKEN；示例为 POSIX shell
curl -i http://127.0.0.1:8084/api/tasks \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -H "Idempotency-Key: first-task" \
  -d '{"name":"first-task"}'
# 独立进程执行一次；数据库路径必须指向同一个文件
./out/taskd -mode=worker -dsn=tasks.db
# 将 TASK_ID 换成实际响应 ID
curl http://127.0.0.1:8084/api/tasks/TASK_ID -H "Authorization: Bearer $TOKEN"
```

创建返回 NEW，Worker 领取后写为 SUCCEEDED，result 为 completed:first-task。相同键同正文得到同一 ID，相同键不同正文返回 409；错误租户读取返回 404。Windows 的完整请求步骤在工程 README 中。

## 3. 重启、租约和事件

停止并重启 API，使用同一文件数据库，已完成任务仍应可查询。Worker 崩溃遗留 RUNNING 时，由租约到期后恢复；随机 token 阻止旧持有者迟到提交，三次耗尽转 FAILED。

Outbox 与任务同事务保存，relay 模式每次发送一条；consume 模式读取 Kafka 并用 Inbox 去重。消息链路需启动 README 中的隔离 Broker，API 与 Worker 本身不依赖 Kafka 才能演示持久任务。

## 4. 验收与真实边界

```bash
# 仓库根目录运行，传入实际 Go 可执行文件
node scripts/verify-go-gin-labs.mjs --go /path/to/go
```

脚本验证两模块测试、命令实验、profile、Fuzz、微基准、真实 API、独立 Worker 和重启持久性，创建的子进程用完即关闭。

尚需在具备条件的环境单独运行 Race、PostgreSQL/Redis/Kafka 联调、Collector、Linux 信号排空与 Kubernetes 发布。SQL Session、RS256 轮换和事务迁移有独立模块与测试，可分别阅读安全和 Schema 章节；基础 taskd 的 HMAC 入口保持不变，不把不同认证模型无条件混用。工程不执行任意用户代码，也不承担完整 OIDC 提供方或持久事件重放平台的职责。

## 5. 沿一次创建请求串联实际执行链

HTTP 请求先进入观测与 Recovery，再经过身份、准入与 scope；create 解码和校验 DTO，从可信 Claims 取得 tenant，建立 task.create Span，调用 Store.Create。

Store 用 tenant+request_key 唯一约束组织幂等：新请求写 Task 与 Outbox，同键同内容返回已有任务，同键不同内容返回冲突。只有事务成功后 Handler 才输出 201，含义是任务资源已建立，而非业务计算已完成。

响应传输失败不撤销已提交的 Task；客户端应沿用幂等键确认同一请求，而不是生成新键重新创建。用这些步骤能解释“超时了但任务后来出现”的现象。

## 6. Worker 与消息链不依赖 API 进程一直存活

Worker 使用同一个持久库领取任务，短事务取得 token，有限计算后条件提交结果。API 重启只改变请求入口，不应抹掉 Task；Worker 崩溃则由租约与重试预算决定恢复。

Outbox 的 Relay 独立负责发送，Consumer 独立负责 Inbox 与通知。API 没有自动启动这些模式，命令分别运行时必须确认 DSN、Topic 和身份配置指向同一套隔离环境。

随机任务 ID 的词典序不是时间顺序，事件 key 相同也不自动保证业务 version 顺序，快照 SSE 更不补全部历史。串联工程时要保留各专题的这些边界，不能因链路图连起来就扩大保证。

## 7. 按故障窗口完成一轮学习验收

先验证创建、查询与独立 Worker，再验证重复请求、版本取消和跨租户不可见；随后观察旧租约拒绝、三次耗尽、事件写失败回滚、确认丢失去重和 API 重启持久性。

语言实验解释值、闭包、泛型与 I/O；protocol/requestflow 解释路由、绑定和响应；Store 与 transport 解释事务和外部协议；observe 解释可观测链。遇到异常时应能判断属于哪一层，而不是只记启动命令。

最后把编译、普通测试、真实回环、独立进程与外部联调结果分别记录。目标是解释每个保证在哪里成立、如何验证和何处失效，不是以目录存在或测试数量宣布“已经精通全部系统”。

## 8. 练习与答案

### 8.1 API 启动会自动运行 Worker 吗

不会，需启动独立 worker 模式。

### 8.2 API 与 Worker 的相对数据库路径不同会怎样

可能打开不同文件，必须指向同一个确定数据库。

### 8.3 重启结果保留就证明所有消息已可靠消费吗

不能，任务持久性与消息确认/消费是不同链路。
