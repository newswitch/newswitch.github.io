# Gin 综合实战：持久化任务、独立 Worker、重启与可靠事件

综合工程将语言、并发、HTTP、事务、安全和观测串起来。完成标准不是“接口能调用”，而是正常与失败路径都能解释、运行和验证。

## 1. 准备与两个进程

```bash
git clone https://github.com/newswitch/newswitch.github.io.git
cd newswitch.github.io/examples/gin/service-lab
go version
go mod download
go test ./... -count=1 -timeout=60s
go build -trimpath -o out/taskd ./cmd/taskd
# 终端 A：仅本机隔离演示
./out/taskd -demo -listen=127.0.0.1:8084 -dsn=tasks.db
# 终端 B：取得实验 Token
./out/taskd -mode=token -demo
```

Windows 构建 out/taskd.exe 并通过 PowerShell 执行。不要把 -demo 用于远端服务。本文所有 Token、任务 ID 都是本地运行时生成，不提供可误用的真实凭证。

## 2. 创建、执行与查询

```bash
# 先把上一步输出放入当前 shell 的 TOKEN；示例为 POSIX shell
curl -i http://127.0.0.1:8084/api/tasks \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -H "Idempotency-Key: first-task" \
  -d '{"name":"first-task"}'
# 独立进程执行一次；数据库路径必须指向同一个文件
./out/taskd -mode=worker -dsn=tasks.db
# 将 TASK_ID 换成实际响应 ID
curl http://127.0.0.1:8084/api/tasks/TASK_ID -H "Authorization: Bearer $TOKEN"
```

创建返回 NEW，Worker 领取后写为 SUCCEEDED，result 为 completed:first-task。相同键同正文得到同一 ID，相同键不同正文返回 409；错误租户读取返回 404。Windows 的完整请求步骤在工程 README 中。

## 3. 重启、租约和事件

停止并重启 API，使用同一文件数据库，已完成任务仍应可查询。Worker 崩溃遗留 RUNNING 时，由租约到期后恢复；随机 token 阻止旧持有者迟到提交，三次耗尽转 FAILED。

Outbox 与任务同事务保存，relay 模式每次发送一条；consume 模式读取 Kafka 并用 Inbox 去重。消息链路需启动 README 中的隔离 Broker，API 与 Worker 本身不依赖 Kafka 才能演示持久任务。

## 4. 验收与真实边界

```bash
# 仓库根目录运行，传入实际 Go 可执行文件
node scripts/verify-go-gin-labs.mjs --go /path/to/go
```

脚本验证两模块测试、命令实验、profile、Fuzz、微基准、真实 API、独立 Worker 和重启持久性，创建的子进程用完即关闭。

尚需在具备条件的环境单独运行 Race、PostgreSQL/Redis/Kafka 联调、Collector、Linux 信号排空与 Kubernetes 发布。教学业务没有执行任意用户代码，没有完整 OIDC、事件历史重放或生产迁移器；这些边界应在扩展时补充，而不是隐去。

## 5. 练习与答案

### 5.1 API 启动会自动运行 Worker 吗

不会，需启动独立 worker 模式。

### 5.2 API 与 Worker 的相对数据库路径不同会怎样

可能打开不同文件，必须指向同一个确定数据库。

### 5.3 重启结果保留就证明所有消息已可靠消费吗

不能，任务持久性与消息确认/消费是不同链路。
