# Gin 服务排障：超时、内存增长、任务卡住与消息积压

排障不是把所有命令跑一遍，而是逐层提出可被证据推翻的假设。先确定故障发生在进入、等待、执行、提交还是写回，再用最小对照验证原因。

## 1. 先按失败阶段分类

401/403 先看身份与权限，409 看版本或幂等冲突，503 分辨准入耗尽和依赖不可用，504 检查剩余预算耗尽在哪一层。状态码只是起点，需结合内部错误类别与 Trace。

在同一时间范围关联 route、状态、耗时、在途请求、池等待及依赖。不要把所有 timeout 都解释为网络，也不要用一张宿主机 CPU 图替代容器和进程证据。

## 2. CPU 低而请求慢

先看 G 是 runnable 还是 waiting，再看 DB/HTTP 池、锁、Channel 与下游延迟。CPU 空闲可能是请求没有取得资源，不代表还有可用业务容量。

若 DB WaitCount/WaitDuration 增量上升、InUse 接近上限、数据库又没有相应慢 SQL，优先验证是否在执行前等连接。复现与恢复见 [连接池案例](./08-SQL执行前超时的连接池排查.md)。

不能根据这些现象直接宣判泄漏：池过小、合法长事务、过量并发与资源未归还都可能造成等待，需要追踪持有者。

## 3. CPU 高与内存增长如何分流

CPU profile 看计算与 GC，heap 看分配和保留，goroutine/锁/trace 看等待关系。alloc_space 高但 live 稳定，查临时对象；live 持续涨，查引用链；RSS 独立涨，查非 Go 分配与页归还。

例如小切片可以保留大数组，GC 正常运行也不会回收仍可达对象。对照 [内存案例](../../go/07-diagnostics/06-小切片保留大数组的内存排查.md) 先验证所有权，再决定复制、清理或调预算。

## 4. 任务一直 RUNNING

检查 Worker 是否真的部署、租约截止、尝试次数、当前 token、进程日志与时间来源。API 可创建记录不代表 Worker 会自动执行。

旧 Worker 做完不代表仍有资格提交；当前 token 和租约应共同约束结果。过期任务可重新领取，三次预算耗尽后进入 FAILED。不要人工改成 SUCCEEDED 掩盖实际未完成。

若外部副作用已经发生而本库提交失败，随机 lease token 不能撤销对方结果，需要对方幂等、确认或对账。

## 5. Outbox 和消费者分别看什么

Outbox 看未发送数量、最老年龄、领取 token、租约、重试和 Broker 确认；消费者看 lag、业务事务、Inbox 去重、毒消息与 offset 提交。

手工把 sent=1 或直接推进 offset 只会改变记录，不证明业务完成。结果未知时保留稳定事件 ID，重试与去重处理窗口，而不是生成新 ID 将同一事件伪装成新业务。

本工程毒消息会停止并返回错误，没有自动 DLT；隔离、修复和受控重放需要明确协议，不能默默跳过。

## 6. 认证与迁移故障要守住安全边界

密钥轮换先查新旧公钥分发、issuer/audience、时间偏差与 kid，不用关闭验签临时恢复。会话库故障返回依赖失败，不能失败开放为已登录。

迁移失败先检查 ledger、checksum、锁与数据库事实；提交结果未知时重新确认，不盲目 down 或删库重建。普通 API 账号不应为处理故障临时长期持有 DDL 权限。

## 7. 构造有限的回归证据

```bash
cd examples/gin/service-lab
go test ./internal/app -run TestPoolWaitDiagnosisAndRecovery -count=1 -v
go test ./internal/store -run 'TestExpired|TestExhausted|TestRelayRetryAndDedup|TestInbox' -count=1 -v
go test ./internal/session ./internal/keyauth ./internal/migrate -count=1 -v -timeout=30s
```

每项都要验证故障后的事实：许可是否释放、旧 token 是否拒绝、事务是否回滚、事件是否重复、授权是否仍受保护。重新返回 200 不是唯一标准。

真实环境需要对等的部署、协议与权限验证，但不应在生产上无边界反复杀进程或清理数据来“看看能否复现”。

## 8. 把一次判断写成可复用结论

保留现象与范围、环境版本、候选假设、支持/反对证据、最小对照、根因、修复和回归。没有证据的猜测就保持为假设，不用故事语气把它写成已证实原因。

重启后恢复只证明退出释放了部分状态，不等于找到根因。好的技术记录能让下一次读者复现实验、识别不适用条件，并知道什么时候停止操作。

## 9. 练习与答案

### 9.1 数据库看起来正常为什么仍可能属于数据库访问路径

请求可能卡在客户端连接池而尚未执行 SQL。需要结合池等待与持有者，不仅看服务器慢查询。

### 9.2 重启后恢复能否直接记为根因已修复

不能，它通常只清除了状态或积压。仍需解释状态为何产生以及相同工作量下修复后不再复现。

### 9.3 故障恢复时能否关闭认证或手工推进消息状态

不能把绕过安全或伪造完成当作一般恢复。应使用有权限、可核验的修复协议，并保持业务事实和可追踪性。
