# Gin 服务排障：超时、内存增长、任务卡住与消息积压

排障应把现象定位到可观测阶段，再用最小变更验证假设。重启可能暂时释放资源，但不能解释哪一层为何失去推进能力。

## 1. HTTP 慢与失败分类

先按 route/status/Trace 区分认证、准入、数据库、处理和写回。401/403 不应按网络故障重试，409 需要检查版本或幂等冲突，503 要看是许可耗尽还是依赖不可用。

CPU 低且延迟高：看 DB 池等待、锁、HTTP 连接等待和下游；CPU 高：看 CPU profile、GC、重复编码与 runnable 排队。不能只根据一个利用率下判断。

## 2. 任务一直 RUNNING

核对 lease_until、attempts、当前 lease_token、Worker 心跳/日志与时间源。旧 Worker 仍执行不代表它还有提交资格。租约过期后应重领，三次预算耗尽后恢复到 FAILED。

若 Worker 根本未运行，API 能创建任务但不会自动执行，这是部署缺失，不是 Gin 调度器故障。示例没有把 Worker 隐式塞进每个 API 副本。

## 3. 消息与内存症状

Outbox 增长看未发送量、最老年龄、重试、claim 租约和 Broker 确认；消费者 lag 增长看业务事务、毒消息和 offset 提交。不要直接把 sent=1 或手工推进 offset 当作“修复”。

内存增长分清 alloc_space、inuse_space、RSS 和 Goroutine；检查大 Slice 保留、未关 Rows/Body、无限流、无界缓存与积压事件。自动清理必须有已确认消费与审计保留规则。

## 4. 实验回归

```bash
cd examples/gin/service-lab
go test ./internal/store -run 'TestExpired|TestExhausted|TestRelayRetryAndDedup|TestInbox' -count=1 -v
go test ./internal/transport -run TestCacheOutage -count=1 -v
```

这些是有限故障注入，不对线上反复杀进程。修复后验证业务状态、重复副作用、错误率和恢复时间，而不只看“接口重新返回 200”。

若要恢复真实数据库或重放消息，先确认对象、备份与隔离环境，不把教学命令直接作用于生产。

## 5. 练习与答案

### 5.1 任务卡住就应直接手工改 SUCCEEDED 吗

不应，会伪造完成并破坏业务事实。

### 5.2 手工提交 offset 能证明消息已处理吗

不能，可能造成丢业务处理。

### 5.3 重启后内存下降就找到泄漏根因了吗

没有，只证明资源被进程退出释放。
