# Gin 配置、健康检查、信号与优雅退出

服务可靠性包含启动失败能解释、接流量前已就绪、退出时工作能收敛。不能只看 ListenAndServe 没报错，就认为生命周期已经完整。

## 1. 启动与健康检查

liveness 表示进程仍能工作，readiness 表示当前适合接流量。service-lab 的 live 不依赖 DB，ready 用 500 ms 预算 Ping DB；认证服务不应把健康接口和用户接口混成同一个失败条件。

如果每次下游短暂抖动都触发所有实例 liveness 失败，重启可能放大故障。慢启动需要 startupProbe 或合适门限，而不是不断提高随机 sleep。

## 2. 进程退出顺序

```text
收到 Interrupt/SIGTERM
→ 停止并等待监听中的 Serve
→ 独立五秒预算 Shutdown API/管理入口
→ 超时则 Close
→ 等待本进程自建 Goroutine
→ 有限 Shutdown 观测导出
→ 关闭缓存与 DB
```

命令代码用 signal.NotifyContext，但排空使用新的有限 Background 子 Context，不能沿用已经取消的信号 Context。收到信号后持久任务状态由租约恢复，而不是强行把所有 RUNNING 改成成功。

## 3. 超时与长连接

HTTP Header、Body、Write 和 Keep-Alive 设置不同预算。教学 SSE 最长三秒，所以可以放在当前五秒 WriteTimeout 内；生产长流要专门管理，不能直接无限延长所有接口。

管理端 pprof 采样也会占资源和时间，监听虽在回环仍应限制使用。超时 Close 可能中断活动请求，客户端需要幂等确认，而不是认定请求必然没有提交。

## 4. 跨平台验证

Windows 可以验证 API 创建、独立 Worker 和重开数据库，但 Node 在 Windows 终止子进程不等于 Unix 上优雅发 SIGTERM。Linux 环境要实际发信号，验证有限请求完成、新连接停止、SSE 结束和进程按宽限期退出。

Kubernetes 还要考虑 readiness 摘流传播、terminationGracePeriodSeconds 与网关连接复用；应用五秒排空预算只是其中一部分。

## 5. 练习与答案

### 5.1 DB 抖动应让所有 liveness 失败吗

通常不应，需区分依赖与进程存活。

### 5.2 已取消的信号 Context 能作为 Shutdown 预算吗

不宜，应使用新的有限 Context。

### 5.3 进程被强制终止证明优雅退出了吗

没有。
