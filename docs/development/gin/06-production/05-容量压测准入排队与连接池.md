# Gin 容量与压测：准入、排队、连接池和延迟预算

框架路由很快，不意味着数据库写接口可以无限接收。容量来自完整请求路径中的最紧约束，稳定性要求过载时有明确拒绝与恢复。

## 1. 建立资源账本

本项目每进程最多 16 个 API 请求持有许可，单请求三秒预算，DB 最大连接 4，SQLite 实验单连接，Redis 池 4。每个数字控制不同资源，不能把许可数等同于数据库并行事务数。

长 SSE 同样持有许可，因此小规模教学可行，但生产应把长连接与短请求分池、按租户配额，避免少量订阅者吃掉全部接口容量。

## 2. 用平均持有量估算

例如目标 100 req/s，每次平均持有数据库连接 40 ms，平均占用约 4 条。还需留出波动、慢事务和其他调用余量，并检查数据库可承受程度；不能拿 P99 替平均数直接代入。

如果数据库只能稳定处理 80 req/s，把入口队列加大到一万只会扩大等待和内存，无法提高持续完成率。超过预算时及时返回 503 与受控重试提示通常更可靠。

## 3. 压测如何设计

先在隔离环境固定工具版本、请求大小、读写比例、租户分布、认证和连接复用；记录到达率与完成率，不只看工具汇报 QPS。按阶梯加压，监控 P50/P95/P99、拒绝、错误、队列、DB 等待、CPU、GC 与 RSS。

不能用 /health/live 的吞吐代表 POST /api/tasks 的容量，也不能用同一幂等键连续命中去重来冒充新任务写入性能。结果需标明实际工作量。

## 4. 故障容量与优化归因

```bash
cd examples/gin/service-lab
go test ./internal/app -run TestAdmissionRejectsBeforeDatabase -count=1 -v
```

测试先占满许可，再验证请求 503，证明准入在数据库前拒绝；它不是完整压力测试。真实压测还需 Redis 故障、DB 变慢、Broker 中断和负载回落后恢复。

每次只调整一个瓶颈，固定条件重测。把并发、缓存、SQL 和副本一起改后得到吞吐上升，无法把收益全部归因于 Gin 或某个参数。

## 5. 练习与答案

### 5.1 准入上限越大吞吐越高吗

不一定，可能只增加排队与依赖争用。

### 5.2 健康接口 QPS 能代表任务创建容量吗

不能，成本完全不同。

### 5.3 SSE 是否没有并发占用

有，长连接需要独立预算。
