# Gin 容量与压测：准入、排队、连接池和延迟预算

服务容量由请求路径中最紧的资源约束决定。稳定性既要求正常负载有足够完成率，也要求过载时有界拒绝、故障时不放大压力、负载回落后能恢复。

## 1. 把资源上限列成账本

基础 taskd 每进程准入许可 16，请求预算三秒，DB 最大连接四个；SQLite 实验限制为一个，Redis 池四个。这些上限作用于不同对象，不能把在途请求等同于活动 SQL 数。

SSE 会长时间占用一个请求许可，上传/下载还占连接和缓冲，Worker 与 Relay 是独立资源路径。生产应按工作类型分预算，避免少量长连接吞掉短请求入口容量。

入口无界接受，再把任务放到无限 Goroutine 或 Slice，仍是无界排队，不是背压。

## 2. 从到达率和持有时间推导

稳定条件下平均在途量近似 L=λW。例如每秒 100 次操作、每次平均持有连接 40 ms，平均约占四条连接。这是平均占用估算，不是建议精确把池设为四。

峰值、方差、事务混合和数据库可承受并发决定余量。P99 不能直接替代平均 W，系统已持续积压时也不能把稳定公式当作恢复保证。

若持续到达率超过完成能力，队列只会增长。扩大队列提高的是可等待量与内存成本，不会增加数据库真实处理能力。

## 3. 计算副本放大的全局预算

每副本四条连接、二十副本就可能形成八十条活动连接，再加 Worker、迁移、管理任务与其他应用。扩容 API 前需要检查数据库总连接与实际执行能力。

客户端池限制比数据库最大连接数更保守是常见的保护手段，但具体值要测量。让所有实例同时尝试建立最大池，也可能在重启或扩容时产生连接风暴。

连接生命周期、空闲数量和活动上限不同。仅提高 MaxIdleConns 不能解决所有活动连接被占住的问题。

## 4. 把超时预算分给实际阶段

一个请求可能经历准入、池等待、SQL 执行、编码与写回。重试也消耗同一次业务预算，不能每层重新获得完整三秒。

连接池等待过久时，应先确认资源是否归还、事务是否包含远端调用，再考虑加池。超时发生前 SQL 甚至可能还没发送，慢 SQL 仪表盘因此没有相应记录。

具体证据见 [SQL 执行前超时的连接池排查](./08-SQL执行前超时的连接池排查.md)。该实验通过释放已持有的唯一连接修复，而不是改变 SQL 或扩大池。

## 5. 压测要记录真实工作量

固定工具版本、构建、输入大小、认证、读写比例、缓存状态和到达模型。健康接口吞吐不能代表创建任务；重复使用同一个幂等键测的是去重路径，不是持续新增写入。

同时记录到达率、完成率、拒绝率、超时、P50/P95/P99、在途量、队列、池等待、CPU/GC 与峰值内存。闭环客户端会在服务变慢时自动降速，需要理解其对排队观察的影响。

按阶梯增加到达量，保留预热和稳定窗口；异常后降低负载，观察资源和延迟是否收敛。只看某一分钟最大 QPS 不足以定义可用容量。

## 6. 故障负载与恢复同样要测

缓存不可用时回源是否有并发保护；数据库变慢时队列是否有界；Broker 不确认时 Outbox 是否积压且可恢复；客户端取消后许可和连接是否释放。

先用有限测试验证关键不变量：

```bash
cd examples/gin/service-lab
go test ./internal/app -run 'TestAdmissionRejectsBeforeDatabase|TestPoolWaitDiagnosisAndRecovery' -count=1 -v
go test ./internal/transport -run TestCacheOutage -count=1 -v
```

这些测试证明拒绝或释放路径，不替代整个系统的容量测量。故障测试必须在隔离授权环境进行，不向真实业务无控制地注入延迟或重试。

## 7. 一次优化如何验收

先明确假设，例如“池中有连接未归还”，只改对应释放路径；比较等待增量、完成率、P99 和业务结果。不能同时改副本、缓存、SQL 与并发后把全部收益归给某个框架参数。

性能改善还要守住正确性：事务仍原子，重复请求不重复执行，租约失效不能提交，跨租户不可见。更快但错了数据不是优化。

最终容量应留出发布、依赖故障与流量波动余量，并定义过载返回与客户端退避。

## 8. 练习与答案

### 8.1 为什么平均连接占用不能直接当最大池大小

平均值没有覆盖波动、慢事务、不同操作混合和故障余量，池上限还必须受数据库可承受并发约束。

### 8.2 增加副本能否无条件解决数据库排队

不能，可能放大全局连接和执行压力；若根因是连接泄漏或数据库饱和，反而更严重。

### 8.3 为什么负载回落后的恢复也属于容量验收

有些系统在高峰后仍保留积压、连接或 G，不能及时恢复。稳态峰值和恢复能力共同决定实际可用性。
