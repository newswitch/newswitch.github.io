# 测试体系、契约测试与故障注入：证明正常和失败路径

测试不是为了把 Coverage 变成 100%。它的目标是对关键风险建立可重复证据：规则是否正确、边界是否兼容、失败是否可控、修复是否不会回归。

## 1. 先写测试目标

每个测试应说明：

```text
Given：初始状态与输入
When：发生的操作
Then：可观察结果和不变量
And：不应发生的副作用
```

例如“创建任务超时”：

- 返回可分类的 Timeout；
- 相同幂等键重试不会创建第二个任务；
- 连接被归还；
- Attempt Count 和 Request ID 可观测；
- 不把 Token 写入日志。

只断言抛出某异常，不能证明副作用被正确处理。

## 2. 测试分层

| 层次 | 验证对象 | 是否需要真实外部系统 | 特点 |
| --- | --- | --- | --- |
| Unit | 纯规则、状态机、函数 | 否 | 快、定位准 |
| Component | 一个服务/模块及受控 Adapter | 部分 | 验证组合和生命周期 |
| Integration | DB、Queue、HTTP 等真实协议 | 是 | 发现驱动、Schema、事务差异 |
| Contract | Producer/Consumer 接口兼容 | 可使用 Stub + Schema | 防止独立升级破坏 |
| End-to-End | 用户关键路径 | 是 | 覆盖真实集成，但慢且定位粗 |
| Performance | 容量与延迟分布 | 是/专用环境 | 验证 SLO 和资源曲线 |
| Resilience | 超时、重启、分区、过载 | 是/故障注入 | 验证恢复与降级 |

测试金字塔不是固定比例。底层多、端到端少的原则用于降低反馈成本，但关键取决于风险和系统类型。

## 3. Unit Test 应围绕行为

好的 Unit Test：

- 输入、输出和状态明确；
- 不依赖真实时间、网络和随机数；
- 失败能直接定位规则；
- 重构内部实现时仍可保持；
- 覆盖边界和错误，而非只覆盖 Happy Path。

不推荐测试私有函数每一步调用顺序。过度 Mock 内部实现会让重构引发大量无意义失败。

## 4. Test Double 的边界

| 类型 | 作用 |
| --- | --- |
| Stub | 返回预设响应 |
| Fake | 有简化但可工作的实现，如内存仓库 |
| Mock | 验证交互是否发生 |
| Spy | 记录真实/包装调用 |

Fake Database 不能替代真实数据库集成测试，因为它通常没有事务隔离、Unique Constraint、SQL Planner、连接池和 Driver 行为。它适合快速验证业务编排。

## 5. 时间、随机与 ID 要可控

不要在测试中依赖真实 `sleep()`：

```text
Clock.now()
Clock.sleep()/advance()
Random.next()
IdGenerator.next()
```

通过显式 Clock/Random/ID Port：

- 精确测试过期边界；
- 重现 Jitter 序列；
- 避免测试随机器速度变化；
- 不必等待数分钟 TTL。

但集成测试仍需少量验证真实 Timer/Runtime 行为，Fake Clock 不能证明 Event Loop 或 Kernel Timer 正常。

## 6. Table-driven 与边界值

对解析和规则使用表驱动测试：

| 输入 | 预期 |
| --- | --- |
| `0` | 拒绝或明确 Zero 语义 |
| `1` | 最小合法值 |
| `max` | 最大合法值 |
| `max+1` | 拒绝 |
| Missing | Default 或 Required Error |
| Null | 与 Missing 是否不同 |
| Unicode/长字符串 | 编码、长度和截断行为 |

典型边界：空集合、单元素、重复、排序相同、负数、溢出、跨日/时区、EOF、Partial Read 和零字节成功。

## 7. Property-based Test

不枚举固定样例，而定义应始终成立的性质：

- `decode(encode(x)) == x`；
- 排序结果有序且元素 Multiset 不变；
- 幂等操作 `f(f(x)) == f(x)`；
- Parser 不因任意输入 Crash；
- 状态机永远不进入非法 Transition；
- 分页拼接结果不重复且满足总序。

Framework 生成输入并在失败后 Shrink 出最小反例。性质本身必须正确，否则会把错误规则自动验证得很彻底。

## 8. Fuzz Testing

Fuzz 通过变异输入探索 Parser、协议、序列化和边界。适合：

- 配置/文件/网络格式 Parser；
- 压缩、解码、正则和路径处理；
- API Validation；
- 状态机命令序列；
- 安全边界。

有效流程：

1. 准备高质量 Seed Corpus；
2. 定义不变量和 Crash/Timeout 上限；
3. 保存触发样例；
4. 把样例加入固定回归测试；
5. 在 CI 运行短 Fuzz，在持续环境运行长 Fuzz；
6. 监控 Corpus、Coverage 和资源。

Fuzz 找到的是执行过的路径；不能证明未覆盖路径安全。

## 9. Contract Test

API/事件 Producer 和 Consumer 独立发布时，需要验证 Wire Contract：

```text
Schema Compatibility
+ Required/Optional/Enum 行为
+ Status/Error Mapping
+ Header/Metadata
+ Pagination Token
+ Unknown Field
+ Timeout/Retry 语义
```

OpenAPI/Protobuf Diff 能发现结构破坏，但行为契约还要通过示例或 Consumer-driven Contract 验证。例如 Schema 无法证明 `409` 何时返回，或相同 Idempotency-Key 是否真能去重。

## 10. Integration Test 要用真实依赖特性

数据库集成测试至少覆盖：

- Migration 从空库和上一版本升级；
- Unique/Foreign Key/Check Constraint；
- Transaction Isolation 和并发更新；
- Timeout、Cancellation 和 Pool Exhaustion；
- 时区、字符集、NULL 和大字段；
- Failover/Connection Reset 后的错误分类。

容器化测试依赖能提高可重复性，但版本、扩展、参数和架构要接近生产，并记录镜像 Digest。

## 11. 并发测试

并发 Bug 不能只靠重复跑单元测试。需要组合：

- Race Detector/Thread Sanitizer；
- Barrier 控制关键交错；
- 大量并发读写；
- Deadlock/Leak 超时；
- 多核和目标 CPU 架构；
- 真实连接池和事务；
- 结束后检查 Thread/Goroutine/Task 数。

Race Detector 只能发现被执行到的 Race，并有明显开销，适合 CI 和受控环境，不应假设一次通过即无 Race。

## 12. 故障注入层次

| 层次 | 故障 |
| --- | --- |
| 函数 | 返回错误、延迟、Partial Result |
| Client | Connect Reset、429、503、Malformed Response |
| 进程 | Crash、SIGTERM、OOM |
| 网络 | Delay、Loss、Reorder、Partition、DNS Failure |
| 存储 | ENOSPC、fsync 慢、Read-only、Corruption |
| 依赖 | Leader 切换、Quota Exhaustion、Slow Query |
| 集群 | Node Drain、Pod Eviction、Zone Failure |

故障注入不是随机破坏。每个实验要有假设、范围、停止条件、观测和恢复验证。

## 13. 必测失败路径

- Connect Timeout 与 Read Timeout；
- 请求已提交但响应丢失；
- Retry 中途 Deadline 耗尽；
- 部分批次成功；
- 配额不足与 Queue Full；
- Secret 过期/Rotation；
- Schema 新旧版本重叠；
- SIGTERM 排空；
- DB/Message Failover；
- 磁盘满和临时目录不可写；
- 时钟跳变/证书过期；
- 重复事件与乱序事件。

## 14. Snapshot/Golden Test

适合稳定的 CLI 输出、配置渲染和协议 Fixture，但风险是 Reviewer 直接接受大面积更新。规范：

- Snapshot 小且可读；
- 动态字段先规范化；
- 更新必须解释契约变化；
- 关键语义仍使用显式断言；
- 不把 Secret/绝对路径写入 Fixture。

## 15. Coverage 怎样使用

Line Coverage 只能说明某行被执行，不说明结果被正确断言。还需关注：

- Branch Coverage；
- Condition/Decision；
- Mutation Testing；
- State Transition；
- Error/Retry Path；
- Contract Scenario；
- Production Incident Regression。

Coverage 适合作为“哪里还没观察”的地图，不适合作为唯一质量目标。

## 16. Flaky Test

常见原因：

- 真实时间和固定 Sleep；
- 端口/临时目录共享；
- 测试顺序依赖；
- 全局状态未恢复；
- 并发任务未 Join；
- 网络/公共服务依赖；
- 随机 Seed 未记录；
- 资源不足和并行度失控。

不要用自动重跑隐藏 Flaky。重跑可用于收集概率证据，但测试应被隔离、修复，并保留首次失败日志。

## 17. Performance Test 不等于功能测试加计时

需要固定：

- 硬件、CPU Governor、NUMA 和资源限制；
- 数据规模与分布；
- Warm-up；
- 并发模型和到达率；
- 下游版本与配置；
- P50/P95/P99、吞吐、错误和资源曲线；
- 原始结果和代码 Commit。

只报告平均响应和最高 QPS 会隐藏排队、错误和尾延迟。

## 18. CI 中的分层

```text
每次提交：Lint + Unit + Schema/Contract + 快速 Race/Fuzz
合并请求：Component + Integration + Migration
主干/夜间：长 Fuzz + 性能趋势 + 故障注入
发布候选：E2E + Upgrade/Rollback + Restore
生产前后：Canary + SLO + 自动回滚条件
```

把最容易定位且最快的检查放前面，失败后不继续消耗昂贵环境。

## 19. 测试证据

一次测试结果至少关联：

- Source Commit；
- Build/Dependency/Image Digest；
- Test Data/Seed；
- 环境和配置摘要；
- 开始结束时间；
- 原始日志与报告；
- 失败重试次数；
- 性能基线版本。

“上周测过”没有可重复证据，无法用于回归比较。

## 20. 常见误区

### 20.1 Mock 越多，Unit Test 越纯

过度 Mock 调用顺序会绑定实现，且无法发现真实协议和事务错误。

### 20.2 E2E 通过就不需要低层测试

E2E 反馈慢、组合多、定位粗，难覆盖边界和故障交错。

### 20.3 Coverage 100% 就没有 Bug

执行一行不等于验证所有输入、并发顺序和环境故障。

### 20.4 Chaos Experiment 越大越真实

没有假设和停止条件的大规模破坏只增加风险。先在最小层复现，再逐步扩大。

## 21. 练习与答案

### 21.1 练习 1：为什么内存 Fake Repository 不能完全替代 PostgreSQL 测试？ {/* #练习-1为什么内存-fake-repository-不能完全替代-postgresql-测试 */}

答案：它通常不具备真实隔离级别、Unique Constraint、SQL 类型、锁、Driver、连接池和 Failover 错误，无法证明存储契约。

### 21.2 练习 2：Race Detector 通过能否证明无并发问题？ {/* #练习-2race-detector-通过能否证明无并发问题 */}

答案：不能。它只观察实际执行路径和交错；还需扩大负载、控制交错、检查业务 Race、跨进程事务和生命周期泄漏。

### 21.3 练习 3：接口 Schema Diff 通过，为什么仍需要契约测试？ {/* #练习-3接口-schema-diff-通过为什么仍需要契约测试 */}

答案：Schema 不能完整表达状态码条件、幂等、排序、错误和业务状态机。行为可能在结构不变时破坏客户端。

### 21.4 练习 4：故障注入后服务恢复，实验是否结束？ {/* #练习-4故障注入后服务恢复实验是否结束 */}

答案：还要验证数据一致性、重复/丢失任务、资源泄漏、告警和恢复时间，并确认故障已撤销、环境回到基线。
