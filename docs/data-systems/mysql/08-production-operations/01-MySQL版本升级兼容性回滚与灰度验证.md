# MySQL 版本升级、兼容性、回滚与灰度验证

数据库升级同时改变数据字典、存储格式、认证、SQL 语义、优化器和工具链。真正的目标不是“新版本能启动”，而是业务可正确运行、性能可接受且失败时有可执行回退。

## 1. 先确认支持路径

核对源/目标精确版本、LTS/Innovation、操作系统、驱动、复制和备份工具的官方兼容矩阵。不能假设任意跨版本原地升级或降级受支持。

```javascript
// MySQL Shell，参数以目标版本为准
util.checkForServerUpgrade('admin@db:3306', {
  targetVersion: '8.4.x'
})
```

Checker 是自动检查，不覆盖全部应用语义和性能测试。

## 2. 兼容面清单

```text
被移除/弃用参数与语法
保留字、sql_mode、默认值
字符集/排序规则/时区
认证插件与 TLS
数据类型、分区、函数
驱动/ORM/连接池
复制与 GTID
备份/监控/审计/CDC
执行计划和资源需求
```

扫描代码与 Schema，收集真实 digest，不能只跑单元测试。

## 3. 建立目标环境

用生产备份恢复脱敏副本，执行升级，解析 error log，跑数据校验、应用集成、代表性 workload 和故障演练。比较 Top digest 计划、P95/P99、CPU、内存、I/O、锁和复制。

## 4. 升级策略

### 原地升级

步骤少，但回退最困难；升级后的数据字典通常不能靠降级二进制直接恢复。回退往往意味着恢复旧版本备份并重放兼容日志。

### 新集群迁移

新版本从备份/复制/CDC 构建，允许并行验证和分批切流，但要处理跨版本复制兼容、最终同步、双写风险和更大资源成本。

### 滚动升级复制拓扑

按官方支持的版本顺序先副本后源，逐个验证；不能让不支持的版本组合长期运行。

## 5. 回退契约

在升级前写清：何时停止、旧环境保留多久、升级后写入如何回到旧版本、是否允许双写、RPO/RTO、备份和 Binlog 连续性。若升级后数据已使用旧版本不认识的功能，回退会更复杂。

## 6. 灰度

```text
离线恢复验证
→ 影子读/回放
→ 内部或低风险只读
→ 小比例业务
→ 全量读
→ 写切换
→ 稳定观察
→ 释放旧环境
```

每阶段有指标和回滚阈值。数据库写路径不要做无约束流量镜像，避免重复副作用。

## 7. 切换窗口

冻结非必要 DDL/批任务；确认备份可恢复、GTID/复制追平；切换路由并刷新连接；执行合成读写；观察错误、P99、锁、复制和业务对账。保留明确事故指挥和回退决策人。
