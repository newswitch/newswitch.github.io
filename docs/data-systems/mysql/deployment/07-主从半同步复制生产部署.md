# 主从与半同步复制生产部署

复制部署不是把两台 MySQL 连起来就结束。必须同时解决实例身份、初始数据一致性、后续事务定位、传输认证、回放并行度、只读保护、延迟监控和故障切换。半同步可以缩小已提交事务只存在于源端的窗口，但不能自动消除所有数据丢失和脑裂风险。

本文使用 MySQL 8.4 的 source/replica 术语、ROW Binlog 与 GTID 自动定位。

## 1. 复制数据路径

```text
Client COMMIT on Source
  → InnoDB Redo/事务提交
  → Binlog 写入并刷盘
  → Binlog Dump Sender
        │ network + TLS
        ▼
  Replica Receiver Thread
  → Relay Log
  → Coordinator / Applier Workers
  → Replica InnoDB
```

### 三种“完成”不是一回事

```text
源端提交完成：事务在源端达到其持久化策略
副本收到：Receiver 已把事件接收/写入 relay log
副本应用完成：Applier 已在副本 InnoDB 提交
```

异步复制中，源端提交不等待副本；半同步等待指定数量副本的接收确认，但通常不等业务 SQL 已在副本回放完成。因此半同步开启后仍可能有复制延迟。

## 2. 拓扑与故障域

实验拓扑：

```text
              app writes
                  │
                  ▼
         db-source-01 (AZ-A)
           /              \
          / GTID + TLS     \
         ▼                  ▼
 db-replica-01 (AZ-B)  db-replica-02 (AZ-C)
   semi-sync ack          async/backup/read
```

节点必须位于独立电源、宿主机和存储故障域。三台虚拟机都在同一物理宿主机，不能抵抗宿主机故障；三个实例共用同一块有单点风险的存储，也不是独立副本。

规划表：

| 项目 | Source | Replica 1 | Replica 2 |
| --- | --- | --- | --- |
| 主机 | `db-source-01` | `db-replica-01` | `db-replica-02` |
| `server_id` | 501 | 502 | 503 |
| `server_uuid` | 初始化生成且唯一 | 唯一 | 唯一 |
| 角色 | 读写 | `super_read_only` | `super_read_only` |
| 故障域 | AZ-A | AZ-B | AZ-C |
| 用途 | 主写 | 候选切换 | 查询/备份 |

## 3. 共同前置条件

- Server 主版本和补丁兼容，字符集/排序规则与关键配置一致；
- DNS 正反向、时钟和 TLS 证书有效；
- Source 到 Replica 的网络不是唯一需要验证的方向，管理和监控路径也要通；
- 每个实例独立初始化，不能复制 `auto.cnf` 后保留相同 UUID；
- 已明确 RPO、允许的半同步提交延迟和超时降级策略；
- 备份能够在独立环境恢复。

先记录身份：

```sql
SELECT @@hostname, @@port, @@server_uuid, @@server_id,
       @@read_only, @@super_read_only;
```

## 4. 配置 Source

```ini
[mysqld]
server_id = 501
log_bin = binlog
binlog_format = ROW
gtid_mode = ON
enforce_gtid_consistency = ON

# 副本将来可以被提升，并保留回放事务的 Binlog
log_replica_updates = ON

# 生产持久性基线，最终仍需以 RPO/性能测试决定
sync_binlog = 1
innodb_flush_log_at_trx_commit = 1
```

配置验证和受控重启后确认：

```sql
SHOW VARIABLES WHERE Variable_name IN (
  'server_id', 'log_bin', 'binlog_format', 'gtid_mode',
  'enforce_gtid_consistency', 'log_replica_updates',
  'sync_binlog', 'innodb_flush_log_at_trx_commit'
);
SELECT @@GLOBAL.gtid_executed;
```

## 5. 配置 Replica

```ini
[mysqld]
server_id = 502
log_bin = binlog
relay_log = relay-bin
relay_log_recovery = ON
log_replica_updates = ON

binlog_format = ROW
gtid_mode = ON
enforce_gtid_consistency = ON

read_only = ON
super_read_only = ON
```

第二副本使用另一个唯一 `server_id`。MySQL 8.4 默认启用多线程回放基线，但 worker 数量仍应结合 CPU、事务依赖和延迟实测，不能只追求更大数值。

`read_only`/`super_read_only` 是误写保护，不是严格的网络隔离或 fencing。高权限账户和复制线程有特殊行为，应用凭据必须从副本移除写权限，路由层也不能把写流量发给副本。

## 6. 创建复制专用账户与 TLS

在 Source 创建只允许复制网段、要求 TLS 的账户：

```sql
CREATE USER 'repl'@'10.20.30.%'
  IDENTIFIED BY '<secret-from-vault>'
  REQUIRE SSL;
GRANT REPLICATION SLAVE ON *.* TO 'repl'@'10.20.30.%';
```

不要复用应用或管理员账户。证书应由受信 CA 签发，实例主机名与证书身份匹配；CA、Server 证书和私钥的读取权限要最小化。

## 7. 建立一致的初始数据

GTID 解决“下一笔从哪里继续”，不会自动让空副本拥有 Source 的历史数据。副本上线前必须先获得一致基线：

```text
Source consistent backup at T0
  ├─ backup data
  └─ GTID set / backup metadata
          ↓
restore on empty Replica
          ↓
GTID auto-position requests transactions after T0
```

可选方法：

- MySQL Shell dump/load：跨平台、可并行，适合逻辑迁移；
- 经过验证的物理备份：适合大库和较短恢复时间；
- Clone Plugin：快速克隆兼容实例，但会覆盖接收端实例数据，必须严控目标；
- 存储快照：只有满足 MySQL 一致性、日志和恢复要求才可使用。

恢复后先做表数量、关键行数、校验抽样和 GTID 核对，再配置复制。不要在源库业务持续写入时直接复制数据文件。

## 8. 配置 GTID 自动定位

在 Replica 通过受保护的管理会话执行：

```sql
CHANGE REPLICATION SOURCE TO
  SOURCE_HOST = 'db-source-01.example.internal',
  SOURCE_PORT = 3306,
  SOURCE_USER = 'repl',
  SOURCE_PASSWORD = '<secret-from-vault>',
  SOURCE_AUTO_POSITION = 1,
  SOURCE_SSL = 1,
  SOURCE_SSL_CA = '/etc/mysql/tls/ca.pem',
  SOURCE_SSL_VERIFY_SERVER_CERT = 1;

START REPLICA;
```

真实密码不能进入终端历史、录屏和工单。复制连接信息会进入复制元数据，主机磁盘加密、MySQL 文件权限和备份保护也必须覆盖它。

`SOURCE_AUTO_POSITION=1` 的核心是双方交换 GTID 集合，Source 发送 Replica 尚未执行的事务，不再依赖人工填写 Binlog 文件和位置。

## 9. 验证复制，而不只看两个 Yes

```sql
SHOW REPLICA STATUS\G
```

还应查询 Performance Schema：

```sql
SELECT *
FROM performance_schema.replication_connection_status\G

SELECT *
FROM performance_schema.replication_applier_status_by_coordinator\G

SELECT *
FROM performance_schema.replication_applier_status_by_worker\G
```

验收维度：

| 层次 | 要确认的证据 |
| --- | --- |
| 连接 | Receiver 线程运行，TLS 已使用，Source 身份正确 |
| 接收 | Relay Log 增长，接收 GTID 推进，无网络错误 |
| 应用 | Coordinator/Workers 运行，无 last error |
| 延迟 | 提交时间、队列和业务可见时间均符合 SLO |
| 一致性 | 核心表校验、GTID 集合包含关系正确 |
| 角色 | Replica `super_read_only=ON`，写流量不路由过去 |

`Seconds_Behind_Source` 不是完整延迟真相：空闲、时钟差、并行回放和线程停止都可能影响解释。应结合 GTID 队列、事务时间戳、worker 状态和业务探针。

## 10. 启用半同步复制

MySQL 8.4 使用 source/replica 命名的新插件；旧 master/slave 命名插件已经废弃。

在 Source：

```sql
INSTALL PLUGIN rpl_semi_sync_source SONAME 'semisync_source.so';
SET GLOBAL rpl_semi_sync_source_enabled = ON;
```

在参与确认的 Replica：

```sql
INSTALL PLUGIN rpl_semi_sync_replica SONAME 'semisync_replica.so';
SET GLOBAL rpl_semi_sync_replica_enabled = ON;
STOP REPLICA IO_THREAD;
START REPLICA IO_THREAD;
```

重启 Receiver 线程是为了重新向 Source 注册半同步能力。验证插件：

```sql
SELECT PLUGIN_NAME, PLUGIN_STATUS
FROM INFORMATION_SCHEMA.PLUGINS
WHERE PLUGIN_NAME LIKE 'rpl_semi_sync%';

SHOW VARIABLES LIKE 'rpl_semi_sync%';
SHOW STATUS LIKE 'Rpl_semi_sync%';
```

持久配置示例：

```ini
# Source
[mysqld]
rpl_semi_sync_source_enabled = ON
rpl_semi_sync_source_timeout = 1000
rpl_semi_sync_source_wait_for_replica_count = 1

# Acknowledging Replica
[mysqld]
rpl_semi_sync_replica_enabled = ON
```

超时、确认副本数和 wait point 直接改变延迟与 RPO。必须通过网络延迟、故障和峰值负载实验决定，不能照搬示例。

### 半同步的降级边界

当确认副本不可用并超过超时，Source 可能回落到异步复制继续提交。需要告警：

- `Rpl_semi_sync_source_status`；
- `Rpl_semi_sync_source_clients`；
- `Rpl_semi_sync_source_no_tx`；
- `Rpl_semi_sync_source_no_times`；
- 等待会话和平均等待时间。

因此“配置项是 ON”不等于每笔事务都获得半同步确认。

## 11. 故障演练

### 演练 A：停止 Replica Receiver

观察半同步状态是否降级、Source 提交延迟如何变化、告警是否触发。恢复后验证接收和应用均追平。

### 演练 B：制造大事务或慢回放

确认“收到”与“应用”差异：半同步提交可能正常，但业务在副本读取仍明显落后。

### 演练 C：Source 故障切换

高层次顺序：

```text
确认 Source 真故障
→ fencing：阻止旧 Source 接受任何写入
→ 比较候选副本 GTID 与数据完整性
→ 选择最完整且健康的候选
→ 停止其复制并解除只读
→ 路由写流量到新 Source
→ 其他副本改为跟随新 Source
→ 旧 Source 重新初始化后作为副本加入
```

先 fencing 再提升是防止脑裂的关键。DNS/VIP/Proxy 切流不会自动阻止旧 Source 继续接受直连写入。任何 GTID 跳过、事务注入或强制提升都需要明确数据差异和业务决策。

## 12. 上线门禁

- 三个实例身份唯一，配置基线可审计；
- 初始数据恢复来源和 GTID 元数据可追溯；
- TLS 与最小权限复制账户已验证；
- Receiver、Applier、延迟、错误与半同步状态有告警；
- 副本只读保护、备份和读路由已验证；
- Source/Replica 重启、网络中断、磁盘满、复制错误演练通过；
- 手工或自动切换 Runbook 包含 fencing、数据判断和回滚；
- 恢复的旧 Source 不会直接带旧数据重新提供写服务。
