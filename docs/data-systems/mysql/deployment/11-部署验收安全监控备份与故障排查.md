# 部署验收、安全、监控、备份与故障排查

部署完成的证据不是截图里有一个绿色 Running，而是一组可重复验证的结果：制品正确、配置真实生效、数据可持久化、角色与路由正确、备份可恢复、故障能收敛、业务 SLO 达标、回滚边界明确。

本篇是所有部署方式的统一收口。命令以只读为主；任何重启、写入测试、切换和故障注入都必须在隔离环境或已批准维护窗口执行。

## 1. 四层 Ready 模型

```text
L1 Process Ready
   mysqld 进程存在、协议端口响应
          ↓
L2 Database Ready
   InnoDB 恢复完成、数据字典可用、账户可认证
          ↓
L3 Topology Ready
   角色正确、复制/多数派/Router/PVC 正常
          ↓
L4 Business Ready
   真实业务查询、延迟、错误率和一致性满足 SLO
```

systemd Active、容器 Running、Pod Ready 都最多只是部分 L1/L2 信号。生产切流必须达到 L4。

## 2. 部署证据包

每个实例/集群保存一份不含 Secret 的部署记录：

```yaml
deployment_id: mysql-orders-prod-20260817
change_ticket: CHG-2026-0000
git_commit: <configuration-commit>
artifact:
  server_version: <8.4.x>
  source: <official-repository-or-private-registry>
  sha256: <digest>
platform:
  os_or_kubernetes: <version>
  architecture: <arch>
topology:
  type: innodb-cluster
  members: [db1, db2, db3]
  failure_domains: [az-a, az-b, az-c]
storage:
  class_or_device: <value>
  capacity_gib: 500
backup:
  last_verified_restore: <timestamp-and-report>
rollback:
  restore_point: <identifier>
owner: order-platform
```

没有制品摘要、配置版本和恢复点，后续无法复现“当时到底部署了什么”。

## 3. 制品与版本验收

主机部署：

```bash
mysqld --version
mysql --version
rpm -qi mysql-community-server
# Debian/Ubuntu 使用 dpkg 与 apt-cache policy 检查来源
```

容器/Kubernetes：

```bash
docker image inspect <mysql-image>
kubectl get pod -n <namespace> -o jsonpath='{range .items[*]}{.metadata.name}{"\t"}{.spec.containers[*].image}{"\n"}{end}'
```

检查点：

- Server 属于批准的 8.4 LTS 补丁版；
- 安装源、镜像 registry 和 digest 正确；
- Server、Shell、Router、Operator 兼容；
- 没有意外启用 Innovation 仓库或漂移 tag；
- 安全扫描和 Release Notes 风险已处理。

## 4. 实例身份与路径验收

```sql
SELECT VERSION() AS version,
       @@hostname AS hostname,
       @@port AS port,
       @@server_uuid AS server_uuid,
       @@server_id AS server_id,
       @@read_only AS read_only,
       @@super_read_only AS super_read_only;

SELECT @@basedir, @@datadir, @@socket, @@tmpdir, @@plugin_dir;
```

跨实例汇总检查：

- `server_uuid` 和非零 `server_id` 唯一；
- Source/Primary 才允许预期写入；
- Replica/Secondary 的只读状态符合角色；
- datadir 位于预期设备/PVC，而不是根盘或临时层；
- 容器重建后 UUID 不变，新复制成员 UUID 不与 donor 重复。

主机路径证据：

```bash
findmnt <datadir>
df -hT <datadir>
df -i <datadir>
ls -ld <datadir>
```

Kubernetes：

```bash
kubectl get pod,pvc -n <namespace> -o wide
kubectl describe pvc -n <namespace> <pvc-name>
kubectl get pv <pv-name> -o yaml
```

```sql
  'innodb_buffer_pool_size', 'max_connections',
  'log_bin', 'binlog_format', 'gtid_mode',
  'enforce_gtid_consistency', 'sync_binlog',
  'innodb_flush_log_at_trx_commit',
  'slow_query_log', 'long_query_time'

```

同时保存：

```bash
my_print_defaults mysqld
mysqld --validate-config
systemctl cat mysqld
```

## 6. 功能与持久化验收

在专用验收 Schema 执行可追溯测试，不使用业务表：

```sql
CREATE DATABASE IF NOT EXISTS deployment_acceptance;

CREATE TABLE IF NOT EXISTS deployment_acceptance.probe (
  id BIGINT PRIMARY KEY,
  token VARBINARY(32) NOT NULL UNIQUE,
  created_at TIMESTAMP(6) NOT NULL DEFAULT CURRENT_TIMESTAMP(6)
) ENGINE=InnoDB;

INSERT INTO deployment_acceptance.probe(id, token)
VALUES (2026081701, UNHEX(SHA2('deployment-acceptance-2026081701', 256)));

SELECT id, HEX(token), created_at
FROM deployment_acceptance.probe
WHERE id = 2026081701;
```

在批准窗口执行正常重启/容器重建/Pod 重建后再次读取，并确认：

- 数据存在且校验值一致；
- `server_uuid` 符合重建语义；
- 实际 datadir/PVC 没有变化；
- 错误日志展示正常关闭或可解释的 Crash Recovery；
- 启动和达到业务 Ready 的时间符合目标。

验收数据清理由独立审批 SQL 完成，不能让自动化使用模糊 DROP 目标。

## 7. 账户与安全验收

### 账户面

```sql
SELECT User, Host, plugin, account_locked, password_expired
FROM mysql.user
ORDER BY User, Host;
```

检查：

- 应用、监控、备份、复制、AdminAPI 职责分离；
- 应用不拥有 `SUPER`、全局管理或 DDL 权限；
- root 不作为应用账户，不开放无边界远程来源；
- 离职/临时账户已锁定，密码和证书有轮换日期；
- 账户 Host、网络策略和防火墙相互收敛。

### 传输面

```sql
SHOW STATUS LIKE 'Ssl_cipher';
SHOW SESSION STATUS LIKE 'Ssl_version';
```

从真实应用连接路径验证 TLS 证书链、主机名、到期时间和吊销策略，而不是只看服务端“支持 TLS”。复制、Router、备份和监控连接也要验证。

### 主机/平台面

- `mysqld` 使用非 root 用户；
- 程序目录只读，数据/日志/Secret 权限最小；
- SELinux/AppArmor 保持 enforcing 并使用最小例外；
- Kubernetes Secret 静态加密、RBAC、审计和 NetworkPolicy 生效；
- 镜像禁止漂移 tag、特权容器和不必要 capability；
- 错误日志、进程参数和备份不泄露密码。

## 8. 复制与高可用验收

### GTID 复制

```sql
SHOW REPLICA STATUS\G

SELECT *
FROM performance_schema.replication_connection_status\G

SELECT *
FROM performance_schema.replication_applier_status_by_worker\G
```

### 半同步

```sql
SHOW STATUS LIKE 'Rpl_semi_sync%';
SHOW VARIABLES LIKE 'rpl_semi_sync%';
```

### InnoDB Cluster

```javascript
var cluster = dba.getCluster()
cluster.status({extended: 2})
cluster.listRouters()
```

统一验收：

- 成员位于独立故障域；
- 初始数据和 GTID 关系正确；
- Replica/Secondary 无业务误写；
- 半同步真实 operational，不只是配置 ON；
- Router 至少两个，应用不直连物理成员；
- 单节点、Primary、Router、网络和整组恢复演练有记录；
- RTO 按业务首笔成功请求计算。

## 9. 性能基线与容量验收

部署完成后先建立“空载”和“目标负载”基线：

| 维度 | 基线 |
| --- | --- |
| 业务 | QPS/TPS、P50/P95/P99、错误率、连接数 |
| MySQL | Buffer Pool 命中、Redo、脏页、锁、临时表、线程 |
| 主机 | CPU、run queue、内存、swap、磁盘延迟/IOPS/吞吐、网络 |
| 复制 | 接收/应用延迟、worker 队列、半同步等待、GR 流控 |
| 存储 | 空间、inode、增长率、扩容提前期 |

内存预算：

```text
峰值内存
≈ Buffer Pool
+ 全局缓存和 Performance Schema
+ 活跃连接 × 每连接峰值内存
+ 复制/备份/DDL 临时开销
+ mysqld/allocator/线程栈余量
```

存储预算：

```text
目标容量
≥ 当前数据和索引
+ 规划期增长
+ Online DDL 临时空间
+ Binlog/Relay Log
+ 临时表和排序
+ 安全水位
```

基准测试必须模拟数据量、读写比、热点、并发、事务大小和 SQL 分布。只跑空表 sysbench 峰值不能作为生产容量结论。

## 10. 监控与告警最小集

### 可用性

- 业务连接与轻量查询成功率；
- mysqld 重启、Crash Recovery 时间；
- 集群 ONLINE/Primary/Router 状态；
- 备份任务与最近成功恢复时间。

### 饱和与延迟

- CPU 使用、run queue、steal/throttle；
- 内存、swap、cgroup OOM、连接水位；
- 磁盘利用率、await/P99、队列和错误；
- 数据盘/Binlog/备份空间和增长预测；
- 查询 P95/P99、锁等待、Redo 写和脏页；
- 复制接收/应用延迟、半同步降级、GR 流控。

### 变更关联

Dashboard 标记：

- 包/镜像/Operator/配置版本变化；
- DDL 与应用发布；
- 主从/Primary 切换；
- 节点、CSI 和网络维护；
- 备份、恢复和大批量任务。

告警必须有 owner、严重级别、Runbook、静默规则和验证方式。只有指标没有行动说明，不能形成运维闭环。

## 11. 备份恢复验收

```text
业务 RPO/RTO
→ 备份频率与 Binlog 保留
→ 逻辑/物理/快照组合
→ 独立账户与独立故障域存储
→ 加密、不可变保留和删除保护
→ 定期完整恢复 + PITR
→ 业务校验 + 实际耗时
```

验收报告至少包含：

- 备份来源实例、版本、时间范围和 GTID；
- 备份对象摘要、大小、加密和保留；
- 恢复目标是全新实例/集群，不覆盖原环境；
- 恢复步骤、开始/结束时间、瓶颈和失败重试；
- 核心表数量/校验、账户、事件、触发器和时区检查；
- Binlog 应用到的目标时点；
- 实际 RPO/RTO 与目标差异。

“备份任务成功”只证明工具退出成功；只有恢复并通过业务校验，才证明备份可用。

## 12. 配置与软件升级验收

任何变更使用相同漏斗：

```text
兼容性/Release Notes
→ 备份和恢复点
→ 静态配置验证
→ 预生产真实升级
→ Replica/Secondary/灰度
→ 观察窗口
→ 滚动其余节点
→ 业务回归与证据归档
```

回滚分三类：

| 类型 | 例子 | 回滚 |
| --- | --- | --- |
| 尚未改变持久格式 | 某些动态参数 | 恢复旧值并观察 |
| 进程/配置变化 | unit、镜像、配置 | 恢复批准版本，验证数据与角色 |
| 数据/元数据已升级 | Server 升级、迁移 | 从升级前恢复点建立兼容环境并切流 |

“换回旧二进制/镜像”不自动等于数据库降级成功。

## 13. 通用故障定位树

```text
业务报错/超时
  ├─ 只有单业务？
  │    └─ SQL、连接池、权限、事务和发布
  ├─ 所有业务？
  │    ├─ Router/Service/DNS/TLS/网络
  │    └─ MySQL 可用性与角色
  └─ MySQL 不 Ready？
       ├─ 控制器：systemd/container/Operator 是否启动
       ├─ 配置：实际二进制和 defaults/CR
       ├─ 存储：datadir/PVC/挂载/空间/权限
       ├─ 恢复：Crash Recovery/Clone/Group recovery
       ├─ 资源：OOM/CPU/磁盘/网络
       └─ 拓扑：复制/多数派/Primary/Router
```

## 14. 启动失败 Runbook

### 第一步：冻结变化

- 停止自动化反复重启/滚动升级；
- 保留错误日志、journal、Pod previous logs、events 和 core；
- 不删除 Redo、Undo、表空间、PVC 或数据目录；
- 确认是否还有健康副本与业务流量。

### 第二步：确认目标身份

```bash
systemctl cat mysqld
systemctl status mysqld
journalctl -u mysqld --since "30 minutes ago"
```

容器/Kubernetes：

```bash
docker inspect <container>
docker logs --since 30m <container>
kubectl describe pod -n <namespace> <pod>
kubectl logs -n <namespace> <pod> --all-containers --previous
```

确认二进制/镜像、配置、datadir/PVC、运行用户和最近变更。

### 第三步：按错误类型取证

| 错误 | 检查 |
| --- | --- |
| unknown variable | 版本、废弃参数、include/CR 实际配置 |
| permission denied | Unix 权限、SELinux/AppArmor、UID、PVC mount |
| no space left | 数据/Binlog/tmp/log/inode，禁止盲删数据库文件 |
| address in use | 旧进程、端口、socket、Router 冲突 |
| tablespace/redo error | 版本与数据目录是否匹配、存储损坏、恢复日志 |
| killed/137 | 主机或 cgroup OOM、内存预算、kernel events |
| long recovery | Redo/Undo 工作量、磁盘延迟、未完成事务 |

### 第四步：恢复后验证

进程起来后继续检查数据、角色、复制/集群、业务查询、错误日志和延迟。仅执行 `SELECT 1` 不能关闭事故。

## 15. “Running 但业务不可用” Runbook

1. 从业务所在网络解析 Service/DNS；
2. 验证 TCP/TLS 和 Router 后端，而不是只在数据库本机测试；
3. 使用业务同等最小权限账户测试认证；
4. 查询实例身份与只读角色，排除写到 Replica；
5. 检查连接池是否持有旧 Primary 连接；
6. 查看 InnoDB 恢复、锁、连接上限和资源饱和；
7. 检查业务核心表和真实轻量查询；
8. 关联最近发布、DDL、切换、证书和网络变更。

## 16. 部署方式专项故障表

| 方式 | 最容易遗漏的层 | 第一证据 |
| --- | --- | --- |
| RPM/DNF | 仓库轨道、SELinux、自动初始化 | dnf repo/history、journal、error log |
| APT | 包替换、自动重启、AppArmor | apt history、unit、kernel/audit log |
| 离线二进制 | 动态库、defaults-file、手工 unit | `ldd`、进程参数、systemd unit |
| Docker | Volume、entrypoint 首次初始化、OOM | inspect mounts/state、container logs |
| GTID 复制 | 初始基线、Receiver/Applier、延迟 | P_S replication tables、GTID sets |
| InnoDB Cluster | 多数派、恢复、Router | `cluster.status`、GR/Router logs |
| Operator | reconcile、scheduler、CSI、CR status | events、CR condition、Operator/Pod logs |
| Ansible | 目标范围、变量、幂等、handler 重启 | run artifact、diff、inventory snapshot |

## 17. 最终故障演练矩阵

| 故障 | 预期保护 | 验收 |
| --- | --- | --- |
| mysqld 异常退出 | 控制器拉起 + Crash Recovery | 数据正确、恢复时长符合 RTO |
| 单副本停止 | Source 继续，冗余告警 | 恢复并追平，无静默降级 |
| Source/Primary 停止 | fencing、选主/提升、Router 切流 | 无脑裂，业务重试后恢复 |
| 单 Router 停止 | 另一个 Router 接管新连接 | 应用不依赖单点 |
| 单节点/zone 故障 | 成员跨故障域、多数派继续 | 实际调度与存储均独立 |
| 数据盘延迟/满 | 提前告警、限流和扩容 Runbook | 不靠删除数据库文件救火 |
| 网络分区 | 少数派隔离、无双写 | 恢复后成员安全重加入 |
| 误删数据 | 备份 + Binlog PITR | 达到 RPO/RTO 并业务校验 |
| 错误升级 | 灰度阻断 + 恢复点 | 可回到兼容独立环境 |
| Secret/证书轮换 | 双凭据/渐进轮换 | 无明文泄露、业务无长中断 |

故障注入不得直接在生产首次尝试。先在同构预生产验证命令、观察项、停止条件和恢复路径。

## 18. 最终上线签字表

### 架构

- [ ] 部署方式与业务 RPO/RTO、规模、团队能力匹配；
- [ ] 所有单点、故障域和降级模式已经画出；
- [ ] 应用连接、读写路由、超时和幂等重试完成验证。

### 制品与配置

- [ ] 8.4 LTS 版本、来源、摘要和发布轨道可追溯；
- [ ] 配置静态检查通过，运行变量与期望一致；
- [ ] 升级、回滚和维护窗口已演练。

### 数据与恢复

- [ ] datadir/PVC、挂载、空间、性能和回收策略正确；
- [ ] 备份加密、异地、不可变保留；
- [ ] 完整恢复与 PITR 达到 RPO/RTO。

### 安全

- [ ] 最小权限、TLS、Secret、审计、防火墙/NetworkPolicy 生效；
- [ ] 日志、命令行、Git 和 CI 不含凭据；
- [ ] 证书和账户轮换已验证。

### 可观测与故障

- [ ] L1～L4 健康探针、Dashboard、告警和 owner 完整；
- [ ] 单进程、节点、存储、网络、Primary、Router 故障演练通过；
- [ ] 事故证据、Runbook 与复盘模板可用。

## 19. 完成标准

真正掌握 MySQL 部署，应能解释并现场证明：

1. 软件包/镜像怎样变成正在运行的 `mysqld`；
2. 配置从哪里进入进程，冲突时谁覆盖谁；
3. 初始化写了什么，为什么只能对空的专用目录执行；
4. 进程/Pod 重建时哪些状态保留、哪些消失；
5. 异步、半同步和多数派复制分别确认到哪一层；
6. 为什么三个节点不一定等于三个故障域；
7. 为什么 Running 不等于业务 Ready；
8. 为什么备份成功不等于能够恢复；
9. 为什么降级不能简单换回旧二进制；
10. 故障时如何沿控制器、配置、存储、恢复、资源、拓扑和业务逐层取证。

能完成这套闭环，才算从“会安装 MySQL”走到“能交付和维护 MySQL 生产系统”。
