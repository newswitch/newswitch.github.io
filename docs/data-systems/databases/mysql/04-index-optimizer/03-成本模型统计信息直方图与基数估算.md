# 成本模型、统计信息、直方图与基数估算

优化器不会真正执行所有候选方案再挑最快的一个。它根据表和索引统计信息估算每条访问路径会产生多少行、要付出多少 I/O 与 CPU 成本，再从可行计划中选出估算成本较低者。

因此很多“优化器为什么选错索引”的问题，根因不是优化器完全没有规则，而是它看到的统计、数据相关性或成本假设与真实世界不同。

---

## 1. 优化器要做哪些决定

一条查询可能存在多种方案：

```text
全表扫描 or 索引访问
索引 A or 索引 B
先访问表 A or 先访问表 B
Nested Loop or Hash Join
合并派生表 or 物化
使用索引顺序 or 额外排序
一次扫描聚合 or 临时结果
```

候选表越多，Join 顺序组合越多。优化器必须在有限时间内搜索和剪枝，不可能穷举所有理论组合。

---

## 2. 成本不是毫秒

`EXPLAIN` 中的 `cost` 是优化器内部用于比较计划的单位，不是预计执行毫秒数。

一个简化模型可以写成：

```text
plan cost
≈ page reads × I/O cost
+ rows evaluated × CPU cost
+ sort/materialize cost
+ repeated inner lookups × loop count
```

真实延迟还受以下因素影响：

- Page 是否已在 Buffer Pool；
- 存储设备延迟与队列；
- CPU 并发和 NUMA；
- 锁与 latch 竞争；
- 返回行大小与网络；
- 同时运行的备份、DDL 和其他查询。

所以成本适合在同一优化环境中比较候选计划，不适合直接换算成 SLO。

---

## 3. 基数、选择性与行数传播

### 3.1 基数

基数通常描述列或索引前缀中不同值的数量。例如一百万行有十万个不同 `customer_id`，平均每个客户约十行。

### 3.2 选择性

可粗略表示为：

```text
selectivity = matching rows / total rows
```

若条件匹配 0.1% 的行，索引通常很有吸引力；若匹配 80%，全表扫描可能更便宜。但最终还取决于行宽、覆盖、排序、缓存和回表。

### 3.3 误差如何放大

假设优化器估算：

```text
A 过滤后 100 行
每行在 B 匹配 2 行
Join 输出 200 行
```

实际却是：

```text
A 过滤后 50,000 行
每行在 B 匹配 20 行
Join 输出 1,000,000 行
```

上游 500 倍误差与内表 10 倍误差相乘，原本看似便宜的 Nested Loop 会执行大量索引查找。阅读 `EXPLAIN ANALYZE` 时，要找最早出现估算偏差的节点。

## 4. InnoDB 索引统计信息

可以查看表和索引基数估算：

```sql
SHOW INDEX FROM orders;

SELECT TABLE_NAME,
       INDEX_NAME,
       COLUMN_NAME,
       SEQ_IN_INDEX,
       CARDINALITY
FROM information_schema.STATISTICS
WHERE TABLE_SCHEMA = DATABASE()
  AND TABLE_NAME = 'orders'
ORDER BY INDEX_NAME, SEQ_IN_INDEX;
```

`CARDINALITY` 是估算，不保证等于 `COUNT(DISTINCT column)`。InnoDB 可以通过对索引树随机抽样估算分布，因此多次分析可能有小幅差异。

常用参数先查询目标实例，不要照抄固定值：

```sql
SHOW VARIABLES LIKE 'innodb_stats_persistent';
SHOW VARIABLES LIKE 'innodb_stats_auto_recalc';
SHOW VARIABLES LIKE 'innodb_stats_persistent_sample_pages';
SHOW VARIABLES LIKE 'information_schema_stats_expiry';
```

持久统计信息能跨重启保存并提高计划稳定性，但不代表永远准确。大量导入、归档、分布突变后仍可能需要重新分析。

## 5. ANALYZE TABLE 做了什么

```sql
ANALYZE TABLE orders;
```

它会更新表的键分布统计，帮助优化器估算索引访问与 Join。它不会重建表，也不是“让数据自动变快”的命令。

适合考虑执行的场景：

- 批量导入或删除后分布显著变化；
- 执行计划的估算与实际偏差很大；
- 新建索引后需要稳定验证；
- 计划突然变化且怀疑统计陈旧。

生产注意事项：

- `ANALYZE TABLE` 需要访问和更新统计信息，并会涉及表锁/元数据协调；
- 默认情况下语句可能写入 Binary Log 并传播到副本；
- 大表、繁忙时段和大量表同时分析应先评估影响；
- 更新统计可能让计划变好，也可能使其他 SQL 改选计划。

正确流程是：先保存关键 SQL 的基线计划和延迟，再受控执行，最后回归所有核心查询。

## 6. 数据倾斜为何破坏平均值

假设 `status` 分布如下：

| status | 行数 | 比例 |
|---:|---:|---:|
| 0 | 9,700,000 | 97% |
| 1 | 250,000 | 2.5% |
| 2 | 50,000 | 0.5% |

只有“3 个不同值”无法表达每个值的差异。如果优化器假设近似均匀，每个值约占三分之一，就会严重误估 `status=2` 或 `status=0`。

类似倾斜还包括：

- 少量超级租户拥有大部分数据；
- 热门商品订单远高于长尾商品；
- 最近一天数据远多于历史单日；
- `NULL` 或默认值占绝大多数；
- 某状态只出现在特定时间段。

---

## 7. 直方图补充了什么

直方图记录非均匀值分布，帮助优化器估算对列的过滤效果，尤其适合没有索引或索引统计不足以表达的条件列。

创建直方图：

```sql
ANALYZE TABLE orders
  UPDATE HISTOGRAM ON status
  WITH 64 BUCKETS;
```

查看：

```sql
SELECT SCHEMA_NAME,
       TABLE_NAME,
       COLUMN_NAME,
       HISTOGRAM
FROM information_schema.COLUMN_STATISTICS
WHERE SCHEMA_NAME = DATABASE()
  AND TABLE_NAME = 'orders';
```

删除：

```sql
ANALYZE TABLE orders
  DROP HISTOGRAM ON status;
```

桶数越多不代表越好：

- 更多桶可能描述得更细；
- 创建和维护需要资源；
- 抽样仍可能漏掉重要稀有值；
- 数据分布变化后会陈旧；
- 不值得给所有列都建直方图。

应针对实际存在严重误估、且能影响计划选择的条件列进行验证。

## 8. 单列统计看不见列相关性

考虑：

```sql
WHERE country = 'CN'
  AND province = 'Zhejiang'
```

`country` 与 `province` 强相关。如果优化器把两个条件当成独立概率相乘，估算可能偏低。

另一个例子：

```sql
WHERE status = 'PAID'
  AND paid_at IS NOT NULL
```

这两列在业务上几乎绑定，单列分布不能完整表达组合关系。

处理方向：

- 设计能表达常用组合的联合索引；
- 调整模型，减少模糊或重复状态；
- 使用生成列表示稳定业务分类；
- 用 `EXPLAIN ANALYZE` 验证组合谓词；
- 必要时谨慎使用 Hint，并建立复查机制。

直方图主要解决单列分布，不应被当作任意多列相关性的万能答案。

## 9. 计划漂移是怎样发生的

```text
数据增长或倾斜改变
→ 统计信息更新
→ 行数与成本估算改变
→ 优化器选择另一个索引/Join 顺序
→ 延迟阶跃
```

也可能由这些事件触发：

- MySQL 版本升级；
- 新增或删除索引；
- 参数、字符集或 SQL mode 改变；
- 绑定参数的实际取值分布改变；
- 分区或归档策略变化；
- 缓存与硬件环境改变。

生产上要保存关键查询的 digest、计划指纹、统计更新时间和发布/DDL 时间线，才能回答“为什么从昨天开始慢”。

## 10. 从误估到修复的排查流程

### 10.1 保存证据

```sql
EXPLAIN FORMAT=JSON SELECT ...;
EXPLAIN ANALYZE FORMAT=TREE SELECT ...;
SHOW CREATE TABLE orders\G
SHOW INDEX FROM orders;
```

同步记录参数值与执行时段，不要用另一组选择性完全不同的参数替代。

### 10.2 找第一个数量级误差

逐节点比较：

```text
estimated rows vs actual rows
estimated loops vs actual loops
```

如果叶子扫描就错，优先看列分布和统计；如果在 Join 后放大，优先看关联基数和列相关性。

### 10.3 验证数据分布

```sql
SELECT status, COUNT(*)
FROM orders
GROUP BY status;

SELECT tenant_id, COUNT(*) AS n
FROM orders
GROUP BY tenant_id
ORDER BY n DESC
LIMIT 20;
```

大表直接全量聚合也可能昂贵，应在副本、离线数据或受控范围执行。

### 10.4 选择最小修复

按优先级评估：

1. 修正 SQL 条件和类型转换；
2. 更新已陈旧的统计信息；
3. 对明确倾斜列建立直方图；
4. 设计更符合访问模式的联合索引；
5. 调整数据模型或查询拆分；
6. 最后才考虑 Hint 或成本参数。

### 10.5 完整回归

不能只验证一条受益 SQL。统计和索引变化可能影响同表的其他查询，至少覆盖高频、高延迟、高业务风险三类 digest。

## 11. Optimizer Trace：看优化器考虑过什么

当普通计划不能回答“为什么没选另一个方案”时，可在隔离会话中启用 Optimizer Trace：

```sql
SET optimizer_trace = 'enabled=on';

SELECT ...;

SELECT TRACE
FROM information_schema.OPTIMIZER_TRACE\G

SET optimizer_trace = 'enabled=off';
```

Trace 可能很大，应只在排障会话短时启用，并注意 SQL 和数据内容的敏感性。重点寻找：

- 哪些访问路径被考虑；
- 估算行数和成本；
- 某索引为何被剪枝；
- Join 顺序选择；
- 子查询合并、半连接或物化决策。

---

## 12. Hint 与 FORCE INDEX 的边界

```sql
SELECT /*+ JOIN_ORDER(c, o) */ ...;

SELECT ...
FROM orders FORCE INDEX (idx_tenant_status_created)
WHERE ...;
```

它们可以用于：

- 快速验证另一计划是否真的更好；
- 已知优化器缺陷下的临时止血；
- 极稳定、可监控的特殊查询。

但长期风险包括：

- 数据规模变化后被固定在旧计划；
- 索引重命名或删除导致维护问题；
- 版本升级后阻止优化器使用更好的新能力；
- 掩盖统计或建模根因。

任何 Hint 都应带上：适用版本、加入原因、基准数据、失效条件、负责人和复查日期。

---

## 13. 实验：制造并修复一次误估

1. 在测试库生成明显倾斜的 `status` 数据；
2. 记录查询的 `EXPLAIN FORMAT=JSON`；
3. 用 `EXPLAIN ANALYZE` 比较估算和实际；
4. 创建直方图；
5. 重新比较计划和真实行数；
6. 再测试另一组高频参数，确认没有只优化稀有值；
7. 删除直方图，验证可回退。

验收不是“计划发生变化”，而是：

```text
估算更接近真实
并且代表性负载的 P95/P99 改善
且 CPU、I/O、写入和其他 SQL 没有明显退化
```

---

## 14. 结论

优化器问题可以归纳成一个闭环：

```text
真实数据分布
→ 统计信息和基数估算
→ 成本比较
→ 计划选择
→ 真实执行
→ 用 ANALYZE 结果校正理解
```

当估算错误时，优先修复信息和访问模型；当估算正确但真实仍慢，再沿缓存、I/O、锁、并发和返回数据继续排查。
