# 逻辑备份、导出导入与跨版本迁移

逻辑备份把 Schema 和数据表示成 SQL 或结构化文件，适合对象级恢复、审查与跨环境迁移；代价是大库导出/导入慢、产生扫描负载并重建索引。

## 1. 备份清单

不只有表数据：

```text
database/table/view
trigger/event/routine
user/role/grant（谨慎单独处理）
character set/collation/time zone
GTID/binlog coordinates
tool and server versions
```

缺少 DEFINER 对象、事件或权限，恢复后可能“表都在但业务不可用”。

## 2. InnoDB 一致性导出

```bash
mysqldump --host=db.example --user=backup --password \
  --single-transaction --quick \
  --routines --events --triggers \
  --set-gtid-purged=AUTO \
  appdb > appdb.sql
```

`--single-transaction` 为事务表提供一致性快照，但期间执行某些 DDL 仍会破坏预期；非事务表不获得同样保证。`--quick` 流式取行，降低客户端内存。所有选项应先用同版本 `mysqldump --help` 验证。

避免命令行明文密码，使用安全登录路径或受控提示。导出账户最小权限，备份文件视同生产敏感数据。

## 3. 大库导出影响

长快照会阻止旧版本清理、增加 undo；扫描会污染缓存和占 I/O；网络和压缩消耗 CPU。优先从健康副本备份，但先确认副本数据完整、延迟和只读保护。

## 4. 恢复前检查

```text
目标版本支持性
字符集/排序规则
sql_mode 与保留字
磁盘临时和最终空间
用户 DEFINER 是否存在
GTID 目标是否为空/允许
关闭应用写入或使用新环境
```

恢复到全新隔离实例比直接覆盖生产安全。

```bash
mysql --host=restore.example --user=restore --password \
  --binary-mode appdb < appdb.sql
```

## 5. 导入性能

瓶颈可能是单线程解析、索引维护、redo/binlog、磁盘和外键检查。可按表并行、使用 MySQL Shell dump/load utilities 或专用工具，但必须保留依赖顺序、一致性和错误处理。为了提速关闭持久性/校验只限隔离重建环境，并要在开放服务前完整验证。

## 6. 跨版本迁移

```text
阅读支持升级路径与变更
→ Upgrade Checker
→ 在目标版本导入副本数据
→ Schema/SQL/驱动兼容测试
→ 真实 workload 回放与性能比较
→ 增量同步/停写窗口
→ 最终校验和切流
→ 保留回退环境
```

逻辑导出不会自动解决被移除语法、认证插件、排序规则、默认值和优化器计划差异。

## 7. 校验

对比对象数量、行数/分块 checksum、关键聚合、最大 ID、时间边界、用户权限和业务合成读写。解析导入日志，不能只看最后 exit code。
