# 数据库、表、数据类型、字符集与排序规则

表设计决定了数据能否正确表达、索引是否高效、迁移是否安全和应用能否长期演进。很多“性能问题”其实从错误类型、缺少约束或不一致字符集开始。

本篇不追求列出所有类型，而是建立选择方法。

## 1. 从业务事实而不是字段列表开始

以订单系统为例，先描述事实：

```text
一个用户可以有多个订单
订单有唯一编号、状态、金额和创建时间
一个订单包含多个商品明细
金额必须精确到分
订单状态只能来自有限集合
历史订单不能因为商品改名而丢失成交时名称
```

再映射为表和约束，而不是先创建一个拥有几十个 `VARCHAR(255)` 的宽表。

## 2. 创建 Database/Schema

```sql
CREATE DATABASE shop
  CHARACTER SET utf8mb4
  COLLATE utf8mb4_0900_ai_ci;
```

Schema 默认字符集和排序规则会被后续表/列继承，但对象可以覆盖。必须通过实际定义验证：

```sql
SHOW CREATE DATABASE shop\G
```

### 2.1 为什么使用 `utf8mb4` {/* #为什么使用-utf8mb4 */}

它用于完整 Unicode 编码，包括 Emoji 和许多扩展字符。不要把历史名称 `utf8` 当作完整 UTF-8 设计。

字符集回答“怎样编码字符”，排序规则回答“字符怎样比较、排序和判断相等”。

## 3. 排序规则会影响正确性

排序规则可能决定：

- 大小写是否敏感；
- 重音是否敏感；
- Unicode 版本和排序权重；
- 唯一索引认为什么值相同；
- Join 时是否需要字符集转换；
- `ORDER BY` 的顺序。

`utf8mb4_0900_ai_ci` 中的名称反映其 Unicode、重音和大小写比较特征。具体选择必须由业务语义决定。

例如用户名是否区分大小写、产品编码是否必须二进制精确比较，不能由“数据库默认值”替产品决定。

## 4. 整数类型

常见整数：`TINYINT`、`SMALLINT`、`MEDIUMINT`、`INT`、`BIGINT`，并可使用 `UNSIGNED`。

选择依据是数值范围和业务增长，不是显示宽度。

```sql
id BIGINT UNSIGNED NOT NULL
quantity INT UNSIGNED NOT NULL
status_code TINYINT UNSIGNED NOT NULL
```

注意：

- 主外键类型必须一致，包括 signed/unsigned；
- `UNSIGNED` 不能表达负数，但会扩大正数范围；
- ID 是否可能跨系统合并、分片或长期增长；
- 过小类型会溢出，过大类型会增加行和索引空间；
- Boolean 语义应通过命名、约束和应用验证，不只依赖类型别名。

## 5. 金额为什么用 `DECIMAL`

```sql
total_amount DECIMAL(18,2) NOT NULL
```

`FLOAT`/`DOUBLE` 是近似浮点，适合科学计算和允许误差的测量，不适合要求十进制精确相等的金额账务。

金额设计还要明确：

- 币种；
- 最小单位；
- 允许的最大值；
- 是否允许负数；
- 舍入规则由应用还是数据库负责；
- 汇率和税率需要多少精度。

只选 `DECIMAL` 仍不能自动解决跨币种和舍入规则问题。

## 6. 字符串类型

| 类型 | 适用 | 主要边界 |
| --- | --- | --- |
| `CHAR` | 真正固定长度代码 | 尾部空格和排序规则语义需测试 |
| `VARCHAR` | 有明确最大长度的变长文本 | 长度按字符定义，存储按字节变化 |
| `TEXT` 家族 | 大文本 | 默认值、索引前缀、行外存储与查询模式 |
| `BINARY/VARBINARY` | 原始字节、大小写敏感标识 | 不执行字符排序语义 |
| `BLOB` | 二进制大对象 | 不应默认把所有文件塞进主库 |

`VARCHAR(255)` 不是万能值。长度应来自 API 契约和业务限制；过宽列会影响行大小、内存、临时表和索引设计。

大文件通常更适合对象存储，数据库保存对象键、摘要、大小、状态和权限元数据。

## 7. 时间类型

常见类型：

- `DATE`：日期；
- `TIME`：时间/时长语义需区分；
- `DATETIME`：日期时间值；
- `TIMESTAMP`：与 Session 时区转换和范围语义相关；
- 可配置小数秒精度，例如 `(6)`。

```sql
created_at DATETIME(6) NOT NULL DEFAULT CURRENT_TIMESTAMP(6)
```

设计时回答：

1. 存储的是绝对时刻、当地墙上时间还是持续时长？
2. 数据库连接时区是什么？
3. 应用、MySQL 和报表如何转换？
4. 是否需要微秒精度？
5. 夏令时重复/缺失时间如何解释？

跨地区系统通常以 UTC 表达绝对时刻，在展示层转换；但日历日、门店营业时间等业务可能必须保留当地时区语义。

## 8. `NULL` 不是空字符串或零

`NULL` 表示未知、缺失或不适用。它使用三值逻辑：

```sql
WHERE deleted_at IS NULL
```

不能写：

```sql
WHERE deleted_at = NULL
```

设计原则：

- 明确列是否业务必填；
- 能确定存在的值使用 `NOT NULL`；
- 不用魔法值 `0`、`1970-01-01`、`N/A` 代替所有缺失情况；
- 聚合、唯一约束和排序对 NULL 的行为要测试；
- 默认值不能掩盖调用方漏传关键数据。

## 9. JSON 类型的边界

JSON 适合：

- 结构确实稀疏或快速演进；
- 保存外部事件的扩展属性；
- 不需要对每个字段建立强关系约束。

不适合把所有字段都塞进 JSON 来逃避 Schema 设计。

需要频繁过滤、Join、排序和约束的核心字段，应成为普通列。JSON 内字段若要高效查询，需要结合生成列、函数索引或其他索引能力，并用执行计划验证。

```sql
attributes JSON NULL
```

数据库能验证 JSON 语法，不会自动验证完整业务 Schema。

## 10. 主键与 InnoDB 聚簇索引

```sql
id BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
PRIMARY KEY (id)
```

InnoDB 使用主键组织聚簇索引记录。二级索引叶子通常包含主键值，因此主键宽度会传播到多个索引。

一个好的 InnoDB 主键通常：

- 非空、唯一、稳定；
- 尽量短；
- 不频繁更新；
- 插入模式与热点、分布式生成需求经过权衡。

业务自然键可以使用唯一约束保护，同时使用短代理主键；是否采用要结合查询、跨系统标识和生命周期，不是绝对规则。

## 11. 建立订单 Schema

```sql
USE shop;

CREATE TABLE customers (
    id BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
    email VARCHAR(320) NOT NULL,
    display_name VARCHAR(100) NOT NULL,
    created_at DATETIME(6) NOT NULL DEFAULT CURRENT_TIMESTAMP(6),
    PRIMARY KEY (id),
    UNIQUE KEY uk_customers_email (email)
) ENGINE=InnoDB;

CREATE TABLE orders (
    id BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
    order_no VARCHAR(32) CHARACTER SET ascii COLLATE ascii_bin NOT NULL,
    customer_id BIGINT UNSIGNED NOT NULL,
    status TINYINT UNSIGNED NOT NULL,
    currency CHAR(3) CHARACTER SET ascii COLLATE ascii_bin NOT NULL,
    total_amount DECIMAL(18,2) NOT NULL,
    created_at DATETIME(6) NOT NULL DEFAULT CURRENT_TIMESTAMP(6),
    updated_at DATETIME(6) NOT NULL DEFAULT CURRENT_TIMESTAMP(6)
      ON UPDATE CURRENT_TIMESTAMP(6),
    PRIMARY KEY (id),
    UNIQUE KEY uk_orders_order_no (order_no),
    KEY idx_orders_customer_created (customer_id, created_at),
    CONSTRAINT fk_orders_customer
      FOREIGN KEY (customer_id) REFERENCES customers(id)
) ENGINE=InnoDB;
```

这个示例仍需要业务补充状态约束、金额非负规则、币种字典和删除策略。数据库结构不是业务规则的全部。

## 12. 表定义评审清单

```text
[ ] 每列能用一句业务语义解释
[ ] 主键非空、唯一、稳定且宽度合理
[ ] 外键两侧类型完全一致
[ ] 金额、时间和状态的边界明确
[ ] 必填列使用 NOT NULL
[ ] 默认值不会掩盖错误
[ ] 字符集和排序规则符合比较语义
[ ] 索引服务明确查询，不是“以后也许有用”
[ ] 表和列有必要注释，但不包含敏感信息
[ ] 数据保留、归档、删除和审计已设计
```

## 13. 通过元数据验证实际定义

```sql
SHOW CREATE TABLE orders\G

SELECT
  column_name,
  column_type,
  is_nullable,
  column_default,
  character_set_name,
  collation_name,
  column_key,
  extra
FROM information_schema.columns
WHERE table_schema = 'shop'
  AND table_name = 'orders'
ORDER BY ordinal_position;
```

不要只检查迁移脚本。实际实例可能因为默认值、版本、历史变更和环境差异得到不同定义。

## 14. 字符集不一致的故障

常见表现：

- 插入 Emoji 报错或变成问号；
- Join 无法使用索引或发生隐式转换；
- 唯一索引认为两个业务标识相同；
- 排序与应用预期不同；
- 从旧库迁移后出现乱码；
- 连接字符集与列字符集不一致。

检查四层：

```text
Server 默认
→ Database 默认
→ Table/Column 定义
→ Client/Connection 字符集
```

转换前必须识别源数据真实编码，不能把已经乱码的数据简单 `ALTER ... utf8mb4` 就期待恢复原字符。

## 15. 类型选择与性能

类型影响：

- 每行和每索引项大小；
- 单页能放多少记录；
- B+Tree 高度与缓存命中；
- 排序、临时表和网络返回量；
- 比较和隐式转换；
- Redo、Undo、Binlog 与备份大小。

但不要为了节省几个字节牺牲正确业务范围。先保证语义正确，再基于真实规模优化。

## 16. 常见错误

| 错误 | 问题 |
| --- | --- |
| 所有列都用 `VARCHAR(255)` | 丢失类型约束，空间和索引设计混乱 |
| 金额用 `FLOAT` | 十进制精确比较和累计可能出现误差 |
| 时间全存字符串 | 无法可靠校验、排序、计算和时区治理 |
| 核心字段全塞 JSON | 约束、索引和查询复杂度转移到运行时 |
| 所有列允许 NULL | 数据完整性和查询逻辑复杂 |
| 使用 `utf8` 就认为支持全部 Unicode | 可能无法保存完整字符集 |
| 随意修改排序规则 | 唯一性、比较与索引行为可能变化 |
| 依赖 ORM 自动生成全部 DDL | 缺少类型、索引、约束和迁移评审 |

## 17. 实验

1. 创建 `shop` Schema 和两张示例表；
2. 插入中文、英文、Emoji 和大小写不同的标识；
3. 比较不同排序规则下的相等与排序；
4. 尝试插入超范围整数、非法金额、NULL 和重复唯一键；
5. 使用 `SHOW CREATE TABLE` 与 `information_schema.columns` 验证实际定义；
6. 对字符串列做隐式类型转换查询，随后使用 `EXPLAIN` 观察索引行为。

所有失败都记录错误码、SQLSTATE 和消息，不只记录“报错了”。
