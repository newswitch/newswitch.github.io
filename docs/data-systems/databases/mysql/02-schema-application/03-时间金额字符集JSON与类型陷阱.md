# 时间、金额、字符集、JSON 与数据类型陷阱

数据类型不仅决定存储大小，还决定比较、排序、索引、协议转换和错误处理。类型选错后，问题往往在数据量增长、跨时区、迁移或结算时才暴露。

---

## 1. 先定义语义再选类型

每列回答：

```text
它表示标识、数量、金额、比率、绝对时刻、当地时间还是持续时长？
范围和精度是多少？
允许 NULL 吗？
怎样比较和排序？
是否参与索引、Join、聚合？
是否跨语言、时区和系统传输？
```

同一个“时间”可能需要三种完全不同的模型；同一个“数字字符串”也可能根本不应做数学运算。

---

## 2. 标识符不是数值

手机号、邮编、订单号和证件号即使全由数字组成，也通常是字符串：

- 可能有前导零；
- 不参与算术；
- 长度和格式比数值范围重要；
- 可能包含国家码、字母或校验位。

```sql
order_no VARCHAR(32) CHARACTER SET ascii COLLATE ascii_bin NOT NULL
```

内部自增 ID 才适合整数。不要为了“整数比较快”破坏业务语义。

---

## 3. 整数溢出与 signed/unsigned

主外键两侧必须一致：

```text
BIGINT UNSIGNED ↔ BIGINT UNSIGNED
```

关注：

- 当前值与日增长率；
- 峰值写入与生命周期；
- 自增耗尽时间；
- 应用语言能否精确表示 64 位无符号值；
- JSON/JavaScript 等跨协议精度。

类型扩大是生产 DDL，不能等到接近上限才处理。

---

## 4. 金额、比例与浮点

```sql
amount DECIMAL(18,2) NOT NULL
tax_rate DECIMAL(9,6) NOT NULL
```

`DECIMAL(p,s)` 的精度和小数位必须覆盖：最大金额、中间计算、税率、汇率和舍入。

建议：

- 金额同时保存币种；
- 统一舍入模式和发生阶段；
- 合计使用与业务一致的精度；
- 对退款/冲正明确正负语义；
- 账务流水不可只保存最终浮点结果。

`DOUBLE` 可用于允许近似误差的科学测量，但不能用二进制浮点相等判断账务余额。

---

## 5. 三类时间

### 绝对时刻

例如支付发生时间。推荐统一 UTC 传输和保存，展示时转换。

### 当地日历时间

例如“门店每天 09:00 开门”。它必须和时区/地区规则一起保存，仅转换为 UTC 可能丢失业务意图。

### 持续时长

例如请求耗时 350 ms。应保存明确单位的整数或适当类型，不把它伪装成一天中的时刻。

类型选择前明确这三者。

---

## 6. `TIMESTAMP` 与 `DATETIME`

二者在范围、时区转换和内部语义上存在差异。不要靠记忆一句“TIMESTAMP 自动转时区”完成设计，必须在目标版本做实验：

```sql
SELECT @@session.time_zone, @@system_time_zone;
```

用两个不同时区会话插入和读取相同值，记录结果。设计同时保存：

- 数据库 Session 时区；
- 应用驱动时区；
- API 时间格式；
- 小数秒精度；
- 零日期/非法日期在 SQL Mode 下的行为。

---

## 7. 字符长度与字节长度

`VARCHAR(100)` 的业务长度以字符语义定义，但实际存储、索引和网络使用字节。`utf8mb4` 字符最多可能占多个字节。

这会影响：

- 最大行大小；
- 索引键长度；
- 临时表和排序内存；
- API 请求与响应大小；
- 批量导入估算。

同时限制字符数和请求字节数，防止少量超大多字节文本突破应用内存/网络预算。

---

## 8. 排序规则与唯一键

```text
ai = accent insensitive
ci = case insensitive
bin/binary = 按二进制或更严格语义比较
```

名称只是入口，最终用目标值测试：

- 大小写；
- 重音；
- 全角/半角；
- Unicode 组合字符；
- 尾部空格；
- 多语言排序。

修改排序规则可能让原本不同的唯一值发生冲突，也可能改变索引和 Join。迁移前先找冲突集合。

---

## 9. 隐式类型转换使索引失效

字符串列与数字比较：

```sql
WHERE order_no = 123456
```

如果 `order_no` 是字符串，隐式转换可能产生意外匹配、告警或无法按预期使用索引。正确参数类型应与列一致：

```sql
WHERE order_no = '123456'
```

Join 两侧类型、长度、字符集和排序规则也应兼容。用 `EXPLAIN` 和 Warning 证明，不只凭经验判断。

---

## 10. SQL Mode 是正确性边界

严格模式影响超范围、截断、非法日期和分组等行为。开发、测试、生产若 SQL Mode 不同，可能出现“一边报错、一边静默改值”。

```sql
SELECT @@GLOBAL.sql_mode, @@SESSION.sql_mode;
```

原则：

- 固定并版本化 SQL Mode；
- 应用上线前用生产模式测试；
- 不以关闭严格检查解决坏 SQL；
- 升级前审查默认值和废弃模式变化。

---

## 11. JSON 的三种 NULL

需要区分：

```text
SQL NULL                 整列缺失
JSON null                JSON 文档中的字面值
path 不存在              JSON 路径没有该成员
```

查询、索引和应用反序列化要明确三者。核心可查询字段提取为普通列；JSON 扩展字段定义版本、大小上限和 Schema 校验。

JSON 更新也可能产生日志和行版本成本，不因为“只改一个 path”就假设零写放大。

---

## 12. ENUM 与状态建模

`ENUM` 能限制有限字符串，但状态演进、跨语言映射和 DDL 变更需要权衡。其他方案：

- 数字状态码 + CHECK；
- 字符串状态 + CHECK；
- 状态字典表；
- 应用枚举 + 数据库约束。

无论使用哪种，必须定义合法转换，而不只是合法集合：已取消订单不能随意回到已支付。

---

## 13. 默认值与自动时间

自动 `created_at`/`updated_at` 很方便，但要明确：

- 是数据库时间还是业务事件时间；
- 回放历史数据是否允许保留原时间；
- `updated_at` 是否因无业务意义更新而变化；
- CDC 消费者如何解释；
- 多实例时钟是否同步。

审计时间、业务发生时间和数据库写入时间经常需要分列保存。

---

## 14. 类型迁移流程

1. 统计 NULL、最大/最小、长度、非法格式和冲突；
2. 在应用先支持新旧表示；
3. 选择 Online DDL 或新列回填；
4. 分批回填并校验；
5. 双写/切读的每一步可回滚；
6. 检查索引、复制延迟和 Binlog；
7. 最后删除旧列，且保留恢复窗口。

类型转换可能改变值，不能只比较行数；应比较业务校验和、分桶统计与异常样本。

---

## 15. 验收实验

1. 在不同时区会话读写 `TIMESTAMP`/`DATETIME`；
2. 比较 `DECIMAL` 与 `DOUBLE` 的多次累计；
3. 对大小写/重音不同字符串创建唯一键；
4. 用字符串列与数字参数比较并查看 `EXPLAIN`/Warning；
5. 区分 SQL NULL、JSON null 和 path 不存在；
6. 在严格和非严格模式观察超范围与截断；
7. 为类型迁移写出校验与回滚计划。
