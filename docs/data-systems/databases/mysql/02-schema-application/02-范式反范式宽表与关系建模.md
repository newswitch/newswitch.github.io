# 范式、反范式、宽表与关系建模

范式不是为了把一张表拆成最多的表，反范式也不是为了少写 Join。建模目标是让每个事实有明确归属，并在正确性、查询、写入、演进和运维之间做可证明的取舍。

---

## 1. 先定义事实与粒度

每张表先用一句话说明“一行代表什么”：

```text
customers：一行代表一个客户
orders：一行代表一次订单
order_items：一行代表订单中的一个商品明细
products：一行代表当前商品目录中的一个商品
payments：一行代表一次支付尝试
```

粒度不清会造成：

- 主键不知道如何定义；
- Join 后重复；
- 聚合口径不一致；
- 更新一处却漏掉另一处；
- 历史事实被当前维度覆盖。

---

## 2. 函数依赖的直觉

如果 `order_id` 唯一决定订单客户、状态和创建时间：

```text
order_id → customer_id, status, created_at
```

如果 `(order_id, line_no)` 唯一决定商品和数量：

```text
(order_id, line_no) → product_id, quantity, unit_price
```

字段应依赖本行的键和粒度。把客户当前地址、每个商品明细和支付尝试都重复塞进订单主表，会混合多种粒度。

---

## 3. 第一、第二、第三范式的工程理解

### 1NF：列值可按当前模型原子处理

不要用逗号字符串保存多个商品 ID：

```text
product_ids = "12,19,27"
```

它难以约束、Join、索引和更新。应使用 `order_items` 多行。

“原子”取决于业务：完整地址可以是展示字符串，也可以按国家、城市、街道拆分，取决于是否需要独立查询与验证。

### 2NF：非键列依赖完整组合键

在 `(order_id, line_no)` 为键的明细表中，订单创建时间只依赖 `order_id`，不应在每行明细重复保存为主事实。

### 3NF：非键列不要依赖另一非键列

订单中若保存 `customer_id`、客户当前等级和等级折扣规则，后两者可能依赖客户/等级而非订单键。要区分当前维度与成交快照。

---

## 4. 更新异常

假设单表重复保存客户信息：

```text
order_id | customer_id | customer_email | order_total
```

可能出现：

- **更新异常**：客户改邮箱，要更新大量订单；
- **插入异常**：没有订单时无法保存新客户；
- **删除异常**：删掉最后一个订单，客户信息也消失；
- **不一致**：部分历史行更新失败，出现多个“当前邮箱”。

范式化让当前客户事实只保存一处，订单通过 `customer_id` 引用。

---

## 5. 历史快照不是错误重复

订单成交时的商品名称、单价、收货地址需要保留历史语义：商品目录以后改名或客户改地址，历史订单不能随之改变。

```text
products.name          当前商品名称
order_items.item_name  成交时名称快照
```

这是有明确来源、时间和不可变语义的冗余，不是随意复制。

快照列要说明：

- 在哪个事件生成；
- 是否允许修正；
- 来源对象与版本；
- 与当前维度不一致是否正常。

---

## 6. 多对多关系

用户与角色是多对多：

```sql
CREATE TABLE user_roles (
  user_id BIGINT UNSIGNED NOT NULL,
  role_id BIGINT UNSIGNED NOT NULL,
  granted_at DATETIME(6) NOT NULL,
  PRIMARY KEY (user_id, role_id),
  CONSTRAINT fk_user_roles_user FOREIGN KEY (user_id) REFERENCES users(id),
  CONSTRAINT fk_user_roles_role FOREIGN KEY (role_id) REFERENCES roles(id)
) ENGINE=InnoDB;
```

关联表不仅保存两个 ID，还可保存授权时间、来源和操作者。主键/唯一键防止重复关系。

## 7. 反范式什么时候合理

反范式必须从已测量问题出发，例如：

- 高频查询每次聚合大量历史记录；
- 读延迟 SLO 严格，而写入可承担增量维护；
- 跨服务/跨库无法实时 Join；
- 需要不可变业务快照；
- 分析查询使用专门读模型。

典型形式：

- 冗余展示字段；
- 预聚合计数/余额；
- 物化读模型；
- 事件驱动的搜索或缓存索引；
- 订单历史快照。

不能只因为“Join 一定慢”就反范式。正确索引的小范围 Join 可能非常高效。

---

## 8. 反范式的成本模型

每个冗余字段都要回答：

```text
Source of Truth 是谁？
同步写还是异步更新？
失败会出现什么不一致？
怎样检测漂移？
怎样重建？
变更 Schema 时更新几处？
备份恢复后怎样对账？
```

收益：减少 Join/聚合和跨系统调用。

代价：

- 写放大；
- 事务更大或最终一致；
- 数据漂移；
- 修复与回放复杂；
- Binlog、复制、备份和存储增加；
- 删除与隐私合规范围扩大。

---

## 9. 宽表的边界

宽表可能降低部分查询的 Join 数，但会带来：

- 行更大，每页记录更少；
- Buffer Pool 缓存效率下降；
- 更新无关列仍产生行与日志成本；
- 稀疏字段大量 NULL；
- Online DDL 和复制成本增加；
- 多个业务生命周期被绑定；
- `SELECT *` 网络流量扩大。

判断宽表不只看列数，还看平均/最大行大小、访问局部性、更新频率和热点分布。

把很少读取的大文本拆到扩展表，可能改善主表缓存；但额外 Join 和一致性也需要测量。

---

## 10. 聚合字段与余额

`account.balance` 是派生值还是权威当前状态，必须定义。

若从流水随时求和：

- 写入简单；
- 查询余额可能扫描大量记录。

若保存当前余额并同时写流水：

- 读取快；
- 必须在同一事务中保证余额与流水一致；
- 需要对账和重建流程。

```text
账务流水 = 不可变事实
当前余额 = 可验证的派生/状态
```

不要异步更新余额却没有幂等、顺序和对账设计。

---

## 11. 状态表与事件表

业务常同时需要：

- 当前状态：快速回答“订单现在是什么状态”；
- 状态历史：回答“何时从什么变成什么”。

```text
orders.status                 当前状态
order_status_events           不可变历史事件
```

在同一事务中更新当前状态并追加事件，或使用 Transactional Outbox 可靠发布。事件表不是随便把每次 UPDATE 的整行复制一遍，需定义 event_id、版本、顺序和幂等。

---

## 12. 跨库与微服务边界

外键不能直接跨独立实例/服务强制执行。此时要使用：

- 稳定全局业务 ID；
- API/事件契约；
- 幂等消费者；
- Outbox/CDC；
- 定期对账；
- 删除前引用检查或软状态；
- 补偿与重建工具。

把所有服务放进一个库只为使用 Join，会扩大耦合和故障域；把强事务随意拆成微服务也会把简单一致性变成复杂分布式协议。边界要由业务一致性和团队运维能力决定。

---

## 13. 读模型与写模型

OLTP 写模型优先正确事务和局部更新；报表/搜索读模型可按查询形态反范式。

```text
MySQL 规范化写模型
→ Binlog / Outbox
→ CDC / 消息
→ 搜索索引、缓存、OLAP、湖仓
```

下游读模型可以重建，必须保存源位置、事件 ID、Schema 版本和对账方法。不要让异步读模型反过来成为无法恢复的唯一真相。

---

## 14. 建模评审问题

```text
一行代表什么？
主键是什么，业务唯一键是什么？
每个字段依赖哪个键？
哪些是当前值，哪些是历史快照？
NULL 表示什么？
关系是一对一、一对多还是多对多？
删除和更新如何传播？
Source of Truth 在哪里？
冗余怎样同步、检测和重建？
最大行数、增长率和保留期是多少？
关键查询和写入路径是什么？
```

## 15. 实验

1. 把订单、客户、商品、明细和支付事实画成关系图；
2. 明确每张表粒度和主/业务键；
3. 构造一个重复客户信息的大表，演示三类更新异常；
4. 为订单设计成交快照，说明为何允许与当前商品不同；
5. 设计当前余额 + 流水，并写出事务与对账规则；
6. 为一个报表创建反范式读模型，记录同步、漂移和重建方案；
7. 用真实数据量比较规范化 Join 与读模型的延迟和写放大。
