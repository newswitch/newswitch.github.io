# 主从切换、脑裂、数据丢失边界与故障演练

高可用不是“把 VIP 指向副本”。一个安全 failover 必须同时解决：旧主是否仍可写、候选是否拥有最完整事务、客户端何时重连、丢失/分叉事务如何处理。

## 1. 两条时间线

服务恢复时间：

```text
failure → detection → decision → fencing → promotion → routing → client recovery
```

数据安全时间：

```text
last client commit → binlog durable → replica received → replica applied
```

RTO 关注前者，RPO 关注后者。更快切换不一定数据更安全。

## 2. 脑裂

网络分区时旧主可能仍服务部分客户端，新主又开始接受写入，形成两条无法自动合并的事务历史。

防线：

- 外部 fencing：关机、隔离网络/存储、撤销路由或云 API fence；
- 单一仲裁和自动化控制面；
- 应用写端点只指向确认主；
- 旧主恢复后以新副本重建，不能直接重新加入写服务。

“ping 不通旧主”不等于旧主已停止写。

## 3. 候选选择

综合：GTID 完整度、relay backlog、数据校验、实例健康、版本/配置、故障域和剩余容量。延迟数字最小不等于事务集合最完整。

对候选集合比较：

```sql
SELECT @@GLOBAL.gtid_executed;
```

若候选之间存在 errant/divergent transactions，自动提升可能扩大数据问题，应暂停并人工决策。

## 4. 计划切换

```text
冻结/排空写入
→ 等候选追平目标 GTID
→ 将旧主只读并 fence
→ 提升候选
→ 重配下游
→ 切换 Router/DNS/VIP
→ 合成读写验证
→ 恢复流量
```

计划切换应尽量达到可证明的 RPO=0，但仍需验证客户端连接、长事务和缓存。

## 5. 非计划故障

```text
确认影响并停止自动重试风暴
→ 确认旧主不可安全服务并 fence
→ 选择最完整健康候选
→ 记录已知 GTID 边界
→ 提升、路由、合成验证
→ 观察错误/P99/复制
→ 保存旧主介质用于取证
```

如果源上存在已返回成功但未到任何候选的事务，切换后即构成数据丢失。应基于异步/半同步配置和证据说明边界，不承诺无法证明的零丢失。

## 6. 客户端行为

连接不会自动变成新主连接。应用应有：有限重试、指数退避与抖动、事务整体重试、幂等键、连接生命周期、明确的只读/读写端点。提交结果未知时不能无脑重做非幂等扣款。

## 7. 回切不是反向切 VIP

旧主可能有分叉事务或较旧数据。通常：保留证据 → 从新主备份/Clone 重建旧主 → 作为副本追平 → 验证 → 以后再计划切换。不要让两个分叉数据集直接互相复制。

## 8. 演练矩阵

```text
mysqld crash
主机掉电
网络分区但旧主仍运行
跨 AZ 链路中断
候选严重延迟
磁盘满/只读
Router 故障
切换中控制面失败
旧主重新上线
```

每次测 MTTD、fence 时间、RTO、实际 RPO、客户端错误、人工步骤和恢复后数据校验。演练必须有爆炸半径、停止条件和回滚。
