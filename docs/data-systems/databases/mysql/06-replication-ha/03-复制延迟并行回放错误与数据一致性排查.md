# 复制延迟、并行回放、错误与数据一致性排查

“副本慢了”要先定位慢在哪一段：

```text
source binlog generation
→ network/receiver
→ relay log
→ coordinator scheduling
→ worker apply
→ replica storage commit
```

## 1. 不要只看 Seconds_Behind_Source

它可能为空、跳变或不能表达 backlog 大小。联合观察：

```sql
SHOW REPLICA STATUS\G
SELECT * FROM performance_schema.replication_connection_status\G
SELECT * FROM performance_schema.replication_applier_status_by_coordinator\G
SELECT * FROM performance_schema.replication_applier_status_by_worker;
```

关注 receiver/applier 状态、最后错误、已接收/已执行 GTID、relay space、worker 事务和 commit 时间。

## 2. 三类延迟

### 2.1 接收慢 {/* #接收慢 */}

源已生成大量 GTID，副本尚未接收。查源 sender、网络 RTT/重传/带宽、TLS、receiver 状态和 relay 磁盘写入。

### 2.2 应用慢 {/* #应用慢 */}

relay 持续增长、receiver 正常、executed 追不上 received。查 worker 利用、单个大事务、锁、磁盘 fsync、CPU、DDL 和副本查询竞争。

### 2.3 人为延迟 {/* #人为延迟 */}

Delayed replication 按策略保持延迟，用于误操作缓冲。监控必须区分预期 delay 与额外 delay。

## 3. 并行复制

增加 worker 只有在事务存在可并行性且 CPU/I/O 有余量时有效。单个巨型事务、同一热点行、依赖链或串行 DDL 仍会限制回放。

```sql
SHOW VARIABLES LIKE 'replica_parallel%';
SHOW VARIABLES LIKE 'replica_preserve_commit_order';
```

参数名和动态性以版本为准。调大 worker 后比较 apply throughput、CPU、磁盘、锁和内存；不是越多越快。

## 4. 大事务指纹

现象：延迟阶跃、某 worker 长时间处理、relay/binlog 空间激增，完成后突然追赶。使用 `mysqlbinlog`、P_S worker 和源端 digest 确认事务大小。永久修复是拆分业务批次，而不是每次人工跳过。

## 5. 错误处理

```text
保存 SHOW REPLICA STATUS 和错误日志
→ 确认失败 GTID/表/语句
→ 判断根因：Schema、数据差异、权限、磁盘、版本
→ 修复根因和数据
→ 在验证后恢复通道
```

盲目 `sql_replica_skip_counter` 或注入空 GTID 会让线程变绿但数据不一致。任何跳过都应有事务内容、业务影响、修复与校验记录。

## 6. 数据一致性

复制线程健康不证明历史数据一致。漂移来源：副本直写、过滤、跳错、非确定行为、恢复种子错误和工具缺陷。

校验分层：关键表行数/范围、业务不变量、分块 checksum、抽样读取与离线对账。校验工具本身会产生 I/O 和复制负载，应限速、分片并先测试。

## 7. 延迟止血

- 将报表/备份从落后副本移开；
- 暂停源端非核心大批任务；
- 限制写入峰值而非无限积压；
- 增加合理 worker 或提升副本资源；
- 延长必要 binlog 保留，防止未追完即被清理；
- 业务读路由排除超出新鲜度阈值的副本。

不要在未识别根因前反复重启复制，可能丢失关键现场和增加恢复时间。

## 8. 实验

分别暂停 receiver、暂停 applier、执行一个大事务、制造副本 I/O 竞争和数据冲突，记录每种情况下 received/executed GTID、relay space、worker 和业务陈旧度的不同表现。
