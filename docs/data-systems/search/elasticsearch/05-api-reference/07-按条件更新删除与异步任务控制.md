# Elasticsearch 按条件更新删除与异步任务控制

按条件批量修改不是“对很多文档执行一次原子 SQL”。搜索匹配与逐批写入之间可能发生并发变化；任务失败或取消时，前面完成的修改通常不会回滚。

本篇所有写操作只针对独立的 `es_api_lab_mutation_v1`，不修改六条基准数据。示例用于理解风险和参数，不应把索引名替换成生产通配符后直接执行。

## 1. 建立一次性变更副本

先完成 [基准数据篇](./01-HTTP请求认证响应与实验数据.md)，检查没有残留 demo 文档，再确认 mutation 索引不存在。以下 Mapping 只为本篇的 category/status/price/stock 条件演示，其他复制字段使用动态 Mapping，不替代生产建模：

```http
PUT es_api_lab_mutation_v1
{"settings":{"number_of_shards":1,"number_of_replicas":0},"mappings":{"properties":{"category":{"type":"keyword"},"status":{"type":"keyword"},"price":{"type":"integer"},"stock":{"type":"integer"}}}}

POST /_reindex?refresh=true
{"source":{"index":"es_api_lab_products_v1"},"dest":{"index":"es_api_lab_mutation_v1","op_type":"create"}}

GET es_api_lab_mutation_v1/_count
```

应 created=6、failures 为空、count=6。这是隔离实验副本，不是独立灾备；同一集群故障、误操作权限和磁盘风险仍共享。

## 2. 先执行同条件搜索与计数

准备把所有 GPU 商品状态设为 maintenance：

```http
GET es_api_lab_mutation_v1/_count
{"query":{"term":{"category":"gpu"}}}

GET es_api_lab_mutation_v1/_search
{"query":{"term":{"category":"gpu"}},"size":10,"_source":["doc_id","category","status"]}
```

预期三条 p1/p2/p5。先确认 ID 和字段，再发变更。**这不是锁，也不是服务端 dry-run**：有并发写入时，预览与变更看到的集合仍可能不同。范围必须包含必要的业务租户、时间边界与索引版本。

## 3. update_by_query 与幂等脚本

```http
POST es_api_lab_mutation_v1/_update_by_query?wait_for_completion=false&requests_per_second=2&slices=1
{"query":{"term":{"category":"gpu"}},"script":{"lang":"painless","source":"if (ctx._source.status == params.value) { ctx.op = 'noop' } else { ctx._source.status = params.value }","params":{"value":"maintenance"}}}
```

返回 `task` 只表示任务已启动，不代表三条都修改成功。按下面第 4 节等待完成并核验；无并发变更时首次 updated=3，再跑同一赋值脚本应主要表现为 noops，而不是再次产生业务加法。[Update by query](https://www.elastic.co/docs/api/doc/elasticsearch/operation/operation-update-by-query)。

| 参数 | 含义与限制 |
| --- | --- |
| `wait_for_completion=false` | 异步返回 task，需要继续查询结果 |
| `requests_per_second` | 控制批处理速率，存在批次间等待，不是平滑的业务 API QPS 限制 |
| `slices` | 分片式并行处理；越多不一定越快，会增加负载 |
| `max_docs` | 限制处理目标数量，但不是业务筛选条件，也不是天然确定的抽样 |
| `conflicts=proceed` | 跳过并统计版本冲突，不让冲突文档自动变更成功 |
| `refresh=true` | 完成后刷新受影响范围，不支持照搬单文档的 wait_for 语义 |

默认遇到版本冲突可中止，已经完成的写入不会回滚。即使使用 proceed，也要对 version_conflicts、failures 与最终业务数据对账；不能把“继续”解释成“强制覆盖所有文档”。

## 4. 查询、限速与取消异步任务

以下 `REPLACE_WITH_TASK_ID` 必须替换为实际返回的完整 `node:id`：

```http
GET /_tasks/REPLACE_WITH_TASK_ID
```

观察 `completed`；运行中看 status，完成后检查 response 或 error，特别是 total、updated、noops、version_conflicts、failures。HTTP 200 的任务查询可能只表明“成功取得任务结果”，并不代表任务执行没有错误。

对仍在运行的 update_by_query 调整限速：

```http
POST /_update_by_query/REPLACE_WITH_TASK_ID/_rethrottle?requests_per_second=1
```

需要停止时仅取消自己的精确任务：

```http
POST /_tasks/REPLACE_WITH_TASK_ID/_cancel
```

取消是协作式请求，不一定瞬时完成；继续观察状态。已修改的数据仍在，不会因为取消自动恢复。Tasks 的能力还受任务类型与版本影响，已经完成或节点重启后的任务不能永远按原 ID 找到。[任务 API](https://www.elastic.co/docs/api/doc/elasticsearch/operation/operation-tasks-list)。

六条数据可能在查看时已经处理结束，因此 rethrottle/cancel 仅演示运行中接口，不要求它们在小样本中必然成功；不要为了观察取消而放大生产任务。

## 5. 完成后刷新并对账

```http
POST es_api_lab_mutation_v1/_refresh
GET es_api_lab_mutation_v1/_count
{"query":{"term":{"status":"maintenance"}}}
GET es_api_lab_mutation_v1/_search
{"query":{"term":{"category":"gpu"}},"size":10,"_source":["doc_id","status"]}
```

确认任务完成、失败项为空且没有并发写入时，maintenance 应为三条。主动 Refresh 仅用于小型实验验证，不作为每批生产写入后的固定操作。

恢复有两种不同含义：重新赋值为某状态，或精确恢复变更前每个文档的原值。p2 原来是 inactive，其余 GPU 为 active，统一写回 active 并不能精确回滚。实际回滚需要保存原值、版本与业务变更边界，或从可信来源恢复。

## 6. delete_by_query 不会把完成部分撤回

在本篇前三条已完成变更的前提下，再预览 status=maintenance 的三条记录，然后才执行不可逆删除：

```http
GET es_api_lab_mutation_v1/_count
{"query":{"term":{"status":"maintenance"}}}

POST es_api_lab_mutation_v1/_delete_by_query?wait_for_completion=true&requests_per_second=2&slices=1&refresh=true
{"query":{"term":{"status":"maintenance"}}}

GET es_api_lab_mutation_v1/_count
```

正常情况下 deleted=3、failures 为空，最终剩下 p3/p4/p6，count=3。若前面的更新部分失败，不能继续按照“三条”假设盲删，应先解释差异。[Delete by query](https://www.elastic.co/docs/api/doc/elasticsearch/operation/operation-delete-by-query)。

删除只是将相应版本标记删除并改变搜索可见性，不表示文件空间立刻缩小。Segment Merge、PIT/Scroll 保留等会影响回收；不能为了立刻看到磁盘下降就对在线写入索引随意 force merge。

## 7. 请求超时与重跑

客户端断开并不证明后台任务终止。先记录 task ID 和请求追踪信息，再查运行状态；没有任务 ID 时结合日志、任务列表和最终数据确认，不直接重跑非幂等脚本。

赋值＋noop、带处理标识的过滤等可以帮助重跑，但也要考虑并发任务和新进入条件范围的文档。幂等逻辑不能替代范围审查、备份与对账。

实验结束后，确认任务已停止且没有后续依赖，再删除唯一副本：

```http
DELETE es_api_lab_mutation_v1
```

## 8. 练习与答案

**问题一：预览 count=3 是否保证变更最终一定处理三条？**

答案：不保证。预览与变更不共享写锁，并发更新和版本冲突可能改变实际结果，需要任务响应和数据对账。

**问题二：conflicts=proceed 能否保证冲突文档被更新？**

答案：不能。它允许继续并统计冲突，冲突项仍未按本次意图成功处理，必须评估后续动作。

**问题三：取消任务是否会恢复已经完成的修改？**

答案：不会。需要另行设计恢复，并区分统一赋值与逐文档原值回滚。

**问题四：为什么重新赋 active 不能精确恢复本次 GPU 商品？**

答案：p2 原状态是 inactive。精确回滚需要保存原值与并发边界，不能用一个统一值替代历史状态。
