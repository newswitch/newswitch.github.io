# Flink 反压、数据倾斜、状态膨胀与性能调优

流作业没有“最终完成时间”，性能目标是稳态处理能力持续大于输入，并满足新鲜度、checkpoint 和恢复 SLO。反压表示下游没有足够消费能力，排查应从最慢下游逆向追踪。

## 1. 容量条件

```text
稳定条件：processing_rate > arrival_rate
恢复追赶：catch_up_time = backlog / (processing_rate - arrival_rate)
```

平均满足还不够，峰值 buffer、状态和下游必须不失控。

## 2. 反压定位

沿 sink 向 source 检查每个 subtask：busy、idle、backpressured、records in/out。最早出现 busy 高、output 低的算子更可能是瓶颈；其上游 backpressured 是传播结果。

再拆：CPU/GC、同步外部 I/O、网络 buffer、序列化、状态访问、sink upload/commit、热点 subtask。Source lag 增长不是自动说明 Kafka 慢。

## 3. 数据倾斜

比较 subtask records、bytes、busy、state size、checkpoint duration 和 watermark。单热 key 会让一个 subtask CPU/状态/定时器集中，增加并行度无法拆开。

方案：改进 key 粒度、热 key 分流、两阶段聚合、异步 I/O、有界 broadcast、重新分配 Kafka key。任何 salting 都要保持窗口和去重语义。

## 4. 状态膨胀

来源：watermark 卡住、窗口/Join 无界、TTL 不生效、重复 key 高基数、timer 风暴、广播规则只增不删。表现为 checkpoint bytes/duration、local disk、restore time 持续增长。

治理先修语义边界，再 compaction/增量 checkpoint/扩容。直接删 checkpoint 会丢状态和位置。

## 5. Checkpoint 长尾

区分 barrier start delay/alignment、同步 state snapshot、异步上传和 sink commit。若单 subtask 慢，关联其 state/key/节点；若全部上传慢，查 checkpoint 存储/网络；若 alignment 慢，查下游反压。

## 6. 网络与内存

TaskManager 总内存包含 framework/task heap/off-heap、managed memory、network memory 和 JVM overhead。容器 OOM 时不能只看 heap。Buffer 太少限制吞吐，太多会增加 in-flight 数据和 checkpoint/恢复开销。

## 7. 调优闭环

固定代码/输入/状态 → 建立正常和峰值基线 → 找到最慢 operator/subtask → 只改一个变量 → 观察吞吐、新鲜度、checkpoint、恢复与成本 → 注入故障 → 业务校验。

常见无效动作：所有算子并行度翻倍、只加 TM 内存、无限延长 checkpoint timeout、用非对齐掩盖永久慢 sink。

## 8. 实验

构造均匀流、单热 key、慢 sink 和 idle partition 四组。记录每 subtask 指标、watermark、state、checkpoint 和 Kafka lag；逐个采用扩并行、salting、async I/O、idle detection，证明每种方法只解决对应根因。

## 9. 掌握验收

- 从 sink 逆向找到反压源；
- 区分平均负载和单 subtask 倾斜；
- 从 watermark/TTL/Join 条件解释状态增长；
- 分解 checkpoint 的四段耗时；
- 调优后验证恢复与业务正确性。
