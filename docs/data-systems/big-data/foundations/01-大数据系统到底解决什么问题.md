# 大数据系统到底解决什么问题：从单机极限到分布式数据平台

“数据很多”不是采用大数据系统的充分条件。真正的问题是：在规定时间和成本内，单机已经无法可靠地保存、处理和交付数据，而且系统还必须面对持续写入、多人并发、硬件故障、数据重放与审计。

这一篇先不讲某个产品。我们从需求出发，推导为什么会出现分区、并行计算、复制、调度、元数据和故障恢复。掌握这些约束后，再学习 Kafka、Spark、Flink、Iceberg 时，就能理解它们是在解决哪一段问题。

## 1. 从一个订单报表开始

假设订单记录平均 1 KiB，高峰每秒产生 50,000 条，每天原始数据量约为：

```text
50,000 × 1 KiB × 86,400 ≈ 4.12 TiB/天
```

如果保存 180 天，仅原始数据约 742 TiB。考虑副本、索引、中间结果、快照和 30% 安全余量，总空间很容易超过 2 PiB。与此同时，业务还要求：

- 实时风控在 2 秒内发现异常订单；
- 运营报表每天 08:00 前完成；
- 分析师可以交互查询近 90 天数据；
- 算法团队能重放历史数据生成训练集；
- 单台服务器或一块磁盘故障不能丢数据；
- 数据结果必须可追踪到源记录和处理版本。

这已经不是“买一块更大的硬盘”能够解决的问题。容量、吞吐、延迟、可靠性、并发和成本同时构成约束。

## 2. 单机在哪些地方遇到极限

### 2.1 容量极限

单机能挂载的磁盘数量、接口带宽、故障域和维护窗口都有限。即使容量勉强够，把数百 TiB 放在一台机器上也会形成巨大的故障域：主板、HBA 或操作系统故障都可能让全部数据暂时不可用。

### 2.2 计算时间极限

假设一个作业需要顺序读取 100 TiB，单机实际读取速度为 1 GiB/s，光读完就需要约 28 小时，还没计算。若将数据均匀分散到 100 个 worker，每个节点有效读取 1 GiB/s，理想读取时间可下降到约 17 分钟。

真实时间不会严格缩短 100 倍，因为还存在任务启动、网络交换、数据倾斜、慢节点和结果提交等开销，但并行化给出了突破单机时间窗的可能。

### 2.3 写入吞吐和并发极限

持续写入、批量扫描、压缩合并和临时 Shuffle 同时访问磁盘，会互相争抢 IOPS 与带宽。多租户情况下，一个错误的全表扫描可能拖慢所有任务。系统需要隔离资源并安排执行顺序。

### 2.4 可用性和恢复时间极限

硬件故障是概率事件。节点越多，集群每天遇到磁盘、进程或网络异常的概率越高。生产系统不能依赖“机器永不故障”，必须让数据有副本，让任务能够重试，并记录恢复点。

### 2.5 数据语义极限

把文件复制到多台机器只解决了字节保存问题，没有解决：

- 哪个文件属于哪张表；
- 哪一批文件构成一致的版本；
- 字段含义是否变化；
- 任务失败重试会不会产生重复；
- 下游使用的是哪次计算结果。

因此大数据平台一定还需要元数据、事务边界、数据质量和血缘。

## 3. 从约束推导六种核心机制

### 3.1 分区：把问题切开

分区将数据按 key、时间、范围或 hash 切成多个互不完全重叠的集合。不同节点分别存储和处理不同分区，系统才可能水平扩展。

分区也引入了新的问题：跨分区聚合需要网络交换；热点 key 会让某个分区过载；增加节点后可能需要重分布。后文的 [分区、并行度、Shuffle 与数据倾斜](./03-分区并行度Shuffle与数据倾斜.md) 会完整解释。

### 3.2 复制或纠删码：容忍数据节点故障

一份数据放在多个故障域中，某个副本不可用时仍能读取。复制恢复简单但占空间；纠删码空间效率更高，但编码和修复会消耗计算与网络。可靠性不是“副本数越多越好”，还必须保证副本不落在同一机架、电源或可用区。

### 3.3 并行执行：把计算移动到多个 worker

一个作业被拆成 stage 和 task，每个 task 处理一个或多个数据分区。并行度受 CPU、内存、磁盘和网络共同约束，不等于机器数量，也不是越大越快。

### 3.4 调度与资源隔离：决定谁在何处运行

调度器需要回答：

- 任务需要多少 CPU、内存、临时磁盘或 GPU；
- 哪个节点有数据、缓存和可用资源；
- 高优任务是否可以抢占低优任务；
- 租户最多能占多少资源；
- 失败 task 在哪里重试。

YARN、Kubernetes 和各计算引擎内部调度器处在不同层次。生产问题往往来自多层调度的资源口径不一致。

### 3.5 元数据与控制面：让分散的数据成为一个系统

数据块、Kafka partition、Iceberg snapshot、表 schema、作业 DAG、checkpoint 都是控制面状态。控制面通常数据量不如业务数据大，却决定系统能否找到和正确解释业务数据，因此需要持久化、备份和高可用。

### 3.6 容错与重放：失败后继续，而不是从头猜

批任务可以重试失败 task；流任务需要从 checkpoint 恢复算子状态和输入位置；表格式需要原子提交新的快照。恢复是否正确取决于 source、处理状态和 sink 三者能否对齐。

## 4. 一条数据的生命周期

```mermaid
flowchart LR
    A["产生"] --> B["采集"] --> C["传输"] --> D["处理"] --> E["存储"] --> F["查询/训练"] --> G["归档/删除"]
```

| 阶段 | 典型职责 | 常见技术 | 关键风险 |
|---|---|---|---|
| 产生 | 业务事务、日志、对象 | MySQL、PostgreSQL、应用日志 | 源记录缺失、时钟与 schema 变化 |
| 采集 | 快照、CDC、日志采集 | Debezium、Fluent Bit | 重复、乱序、断点位置错误 |
| 传输 | 缓冲、解耦、重放 | Kafka | 积压、热点 partition、保留期不足 |
| 处理 | 清洗、Join、聚合 | Spark、Flink | 倾斜、状态膨胀、失败重试 |
| 存储 | 文件、表、版本 | HDFS、对象存储、Iceberg | 小文件、提交冲突、元数据丢失 |
| 服务 | 报表、API、训练 | Trino、Doris、DataLoader | 并发过载、数据版本不一致 |
| 生命周期 | 归档、合规删除 | 调度器、Catalog、存储策略 | 误删、孤儿文件、无法审计 |

任何平台设计都应该先画出这条链路，再为每个交接点定义输入、输出、状态所有者和失败处理方式。

## 5. OLTP、OLAP 与数据平台不要混淆

**OLTP** 面向大量短事务，关注单条记录的低延迟读写、约束和并发事务。订单创建、余额扣减属于 OLTP。

**OLAP** 面向大范围扫描、聚合和复杂 Join，关注列裁剪、压缩、并行执行和批量吞吐。近 90 天销售趋势属于 OLAP。

大数据系统通常把数据从 OLTP 复制到面向分析的存储和计算系统，避免报表扫描拖垮业务数据库。这个复制过程带来一定延迟，也带来一致性、重复和 schema 演进问题。

## 6. 扩展方式：Scale Up 与 Scale Out

- **纵向扩展（Scale Up）**：给单机增加 CPU、内存和更快磁盘。简单、通信少，但存在硬件上限和大故障域。
- **横向扩展（Scale Out）**：增加节点并重新分配数据和任务。容量和吞吐可扩展，但需要处理分区、网络、协调和部分失败。

合理架构通常两者结合：先让单机资源配置均衡，再横向扩展。用大量低配节点并不必然便宜，因为网络端口、机架空间、运维和故障率也有成本。

## 7. 用数字定义问题

设计前至少收集以下输入：

| 维度 | 需要记录的量 | 用途 |
|---|---|---|
| 规模 | 每日新增量、总量、平均/最大记录大小 | 容量和分区规划 |
| 速度 | 平均/峰值 records/s、bytes/s | 网络、broker 和计算吞吐 |
| 时效 | P50/P95/P99 延迟、批任务完成时间 | 选择批、流或混合模式 |
| 保留 | 在线、近线、归档周期 | 存储分层和成本 |
| 正确性 | 可否重复、可否丢失、允许多晚到达 | 一致性和重放设计 |
| 并发 | 作业数、查询数、租户数 | 调度和隔离 |
| 可用性 | SLO、RPO、RTO | 副本、备份和恢复方案 |

最基本的容量估算可以写成：

```text
所需原始容量 = 日增量 × 保留天数
物理容量 = 原始容量 × 副本或编码系数 × (1 + 索引/元数据/临时空间比例)
规划容量 = 物理容量 / 目标最高利用率
```

如果一个 3 副本集群算出需要 900 TiB 物理空间，且目标最高使用率为 70%，应按约 1.29 PiB 可用物理空间规划，而不是磁盘刚好配到 900 TiB。还要单独预留重建和 Shuffle 临时空间。

## 8. 性能上限通常取决于最慢环节

一条流水线的稳态吞吐不会超过最慢阶段：

```text
pipeline_throughput ≤ min(source, network, compute, sink)
```

上游 5 GB/s、计算 4 GB/s、存储只接收 1 GB/s，最终稳定吞吐最多约 1 GB/s，多余数据会形成队列和反压。提升 CPU 在这种情况下没有意义。

排查时必须同时观察：

- 输入/输出 records/s 与 bytes/s；
- 队列长度、Kafka lag、Flink backpressure；
- CPU 使用率与 throttling；
- JVM heap、GC、managed memory；
- 磁盘吞吐、IOPS、await、队列深度；
- 网络吞吐、重传、丢包；
- P95/P99 task 时长和分区大小。

只看集群平均值会掩盖热点节点和长尾 task，必须至少下钻到 worker、partition 和 task。

## 9. 故障不是异常分支，而是主流程

生产设计要明确这些故障：

| 故障 | 可能结果 | 系统需要做什么 |
|---|---|---|
| worker 进程退出 | 部分 task 消失 | 重调度并恢复输入/状态 |
| 磁盘损坏 | block 或 segment 不可读 | 从其他副本读并重建 |
| 网络分区 | 两边都认为对方失败 | 使用明确的 leader/epoch/租约避免脑裂 |
| 慢节点 | 整个 stage 被长尾拖住 | 识别倾斜、推测执行或隔离慢盘 |
| 控制面故障 | 不能分配任务或提交元数据 | 高可用、持久化和一致性恢复 |
| 下游超时 | 上游积压或重试 | 背压、限流、熔断和幂等写入 |

“任务最终成功”不代表数据正确。每次恢复还应校验记录数、业务主键、金额汇总、最大事件时间和表快照版本。

## 10. 最小实验：证明并行不是免费加速

准备一个可重复的聚合任务，分别使用 1、2、4、8 个并行 worker 运行，记录总耗时、CPU、磁盘和网络。保持数据、代码和缓存状态一致。

实验表至少记录：

```text
数据规模 | worker 数 | 分区数 | 总耗时 | Shuffle bytes | 最大 task 时长 | 结果校验
```

预期会看到三个阶段：

1. worker 增加时，计算和读取被并行化，总耗时明显下降；
2. 达到磁盘或网络上限后，加速开始变小；
3. 并行度过高时，调度、小文件、连接和 Shuffle 开销反而让作业变慢。

实验目的不是得到一个通用的“最佳并行度”，而是学会用瓶颈指标解释拐点。

## 11. 常见误区

- **数据达到某个 TB 数就必须上 Hadoop。** 架构取决于时效、并发、可靠性、技能和成本，不只取决于容量。
- **节点越多一定越快。** 网络交换、调度和长尾开销会增长，串行阶段也无法并行。
- **有三副本就不需要备份。** 副本防硬件故障，不防误删、逻辑破坏和错误同步。
- **作业可以重试就不会丢数据。** source 位置、算子状态和 sink 提交必须形成一致的恢复边界。
- **CPU 没满说明资源足够。** 任务可能卡在磁盘、网络、锁、GC、背压或单个热点分区。

## 12. 掌握验收

不看本文，确认自己能做到：

- 用容量、吞吐、延迟、正确性、RPO/RTO 描述一个数据需求；
- 从需求推导分区、复制、调度、元数据和恢复机制；
- 区分 OLTP 与 OLAP，解释为什么分析负载要从业务库剥离；
- 画出数据面与控制面，并指出各自的状态所有者；
- 估算半年数据的原始容量、物理容量和安全水位；
- 根据指标判断流水线瓶颈大致位于 source、网络、compute 还是 sink；
- 解释为什么节点故障后的“重试成功”仍需做数据校验。
