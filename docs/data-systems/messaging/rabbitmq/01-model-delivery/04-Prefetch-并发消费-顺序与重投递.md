# Prefetch、并发消费、顺序与重投递

消费者吞吐不是把并发和 Prefetch 调得越大越好。Prefetch 决定 Broker 允许一个消费者同时持有多少条未确认消息，它本质上是信用窗口和背压边界。

## 1. 一条消息为什么会进入 Unacked

```text
Queue Ready
→ Broker投递
→ Consumer内存/线程池
→ 业务处理
→ ACK
```

从投递到 ACK 之间，消息计入 Unacked。Prefetch 为 100、每条消息 5 MiB 时，单消费者仅消息体就可能占用约 500 MiB，尚未计算反序列化和业务对象。

粗略估算：

```text
单消费者所需Prefetch ≈ 目标吞吐 × 单条平均处理时间
总在途内存 ≈ 消费者数 × Prefetch × 平均消息内存占用
```

从小值开始压测，CPU 密集任务通常不需要很大窗口，远程 I/O 任务可能受益于适度并发。

## 2. 并发与顺序边界

RabbitMQ 按队列中的顺序投递，但以下行为会改变业务完成顺序：

- 一个队列存在多个消费者；
- 单消费者把消息交给并行线程池；
- NACK/requeue 或连接断开引起重投递；
- 优先级队列、死信和重试链路；
- 消费者处理耗时不同。

若要求同一订单严格有序，可按业务键分片到固定队列，并让每个分片单线程处理；这牺牲弹性和吞吐。更常见的设计是让事件携带版本号，在业务端拒绝旧版本或按状态机幂等合并。

## 3. 重投递语义

消费者 Channel/Connection 关闭或节点发生 Leader 切换时，未确认消息会重新进入可投递状态。`redelivered=true` 只表示 Broker 知道它被投递过，不等于第一次处理一定失败，也不能作为唯一幂等键。

避免下面的热循环：

```text
消费失败 → nack(requeue=true) → 立即再次消费 → 再次失败
```

应将可恢复错误送入带退避时间的重试队列，把不可恢复错误送入隔离队列，并记录重试次数。

## 4. 调优步骤

1. 测量单条 P50/P95 处理时间和消息大小；
2. 固定消费者数，逐级增加 Prefetch；
3. 观察吞吐、ACK 延迟、Unacked、CPU、内存和下游连接池；
4. 再增加消费者数，确认队列、网络和下游是否成为瓶颈；
5. 用慢消息和消费者退出测试公平性与重投递；
6. 将配置写入容量模型，而不是凭经验固定为 1000。

## 5. 排障决策

| 现象 | 重点检查 |
| --- | --- |
| Ready 持续增长，Unacked 很少 | 消费者不足、连接中断或处理速率低 |
| Unacked 很高，ACK 速率低 | Prefetch 过大、下游慢或线程阻塞 |
| 单个消费者囤积大量消息 | 信用窗口过大或消费者性能不均 |
| 重投递率升高 | 消费者崩溃、ACK 超时、Channel 关闭、节点切换 |
| 业务状态倒退 | 并发完成乱序，缺少版本检查 |

## 6. 验收实验

构造快、慢两类消息，分别以 Prefetch 1、10、100 运行两个消费者；记录吞吐、Unacked 与进程 RSS。随后在慢消息处理中停止消费者，确认消息重投递、业务幂等和顺序边界。最终配置应同时满足吞吐、内存上限和下游保护目标。
