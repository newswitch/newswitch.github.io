# TTL、死信、重试、延迟消息与毒消息隔离

重试不是简单地把失败消息重新放回原队列。一个可靠的重试系统必须区分瞬时故障、永久错误和过期任务，并限制次数、速率与总停留时间。

## 1. 消息成为死信的原因

队列配置 Dead Letter Exchange 后，消息可能因为以下原因被重新发布到 DLX：

- 消费者 `reject/nack` 且不重新入队；
- 消息或队列 TTL 到期；
- 队列超过长度限制；
- Quorum Queue 超过投递次数限制等队列特定条件。

死信是 Broker 内部的一次重新发布，DLX 必须存在可匹配 Binding，否则仍可能丢在不可路由边界。优先使用 Policy 配置 DLX/TTL，减少修改队列声明参数带来的重建成本。

## 2. 有界退避重试拓扑

```text
work.queue
  ├─ 成功 → ACK
  ├─ 可恢复错误 → retry.10s → TTL → work.exchange
  ├─ 再失败 → retry.1m → TTL → work.exchange
  └─ 永久错误/超限 → parking.queue
```

消息应携带业务 ID、首次创建时间、当前尝试次数和错误分类。不要无限相信可被客户端篡改的 Header，关键计数可由受控消费者重建。

## 3. TTL 和延迟的限制

消息 TTL 可按队列或消息设置。过期检查与消息在队列中的位置、队列类型和版本实现有关，不应把 TTL 队列当高精度定时器。大量不同延迟如果各建一条队列，会造成拓扑和资源膨胀。

延迟需求的选择：

| 需求 | 方案 |
| --- | --- |
| 少量固定退避档位 | TTL 队列 + DLX |
| RabbitMQ 插件环境、灵活延迟 | 延迟消息 Exchange 插件，先验证兼容性 |
| 海量长周期定时任务 | 数据库/调度系统保存状态，到期再发布 |
| 需要审计和取消 | 业务调度表，不只依赖 Broker 内部消息 |

## 4. 毒消息隔离

毒消息通常包括格式错误、缺字段、业务状态永远不满足或代码缺陷触发的数据。隔离队列应保存原始消息、异常摘要、来源队列、重试历史和处理版本，并设置访问权限与保留周期。

恢复流程必须是：修复原因 → 在影子环境验证 → 限速重放 → 观察错误率 → 扩大批次。不要直接把整个隔离队列重新路由到主队列。

## 5. 监控与排障

- 各重试档位 Ready 数量和最老消息年龄；
- Dead-letter 速率与原因；
- Parking Queue 新增速率；
- 重试成功率和每条消息平均尝试次数；
- DLX 不可路由、队列长度上限和磁盘水位。

若主队列吞吐正常但重试队列持续增长，先查依赖恢复时间和退避是否过短；若同一消息快速循环，检查 `requeue=true`；若消息似乎没有按时到期，核对 TTL 类型、队头阻塞和实际队列参数。

## 6. 验收实验

构造瞬时错误、永久格式错误和依赖超时三类消息，证明它们分别成功重试、进入隔离队列或在总截止时间后停止。随后关闭 DLX Binding，确认监控能够发现不可路由风险。
