# 内存水位、磁盘水位、流控、容量规划与压测

RabbitMQ 在内存或磁盘接近安全边界时会限制发布，以保护节点继续运行。此时生产者变慢往往是保护机制生效，而不是简单的“网络卡顿”。

## 1. 流控链路

```text
Publisher速率 > Queue落盘/消费速率
→ 内存、磁盘或内部Mailbox累积
→ 资源告警/Connection flow
→ 发布连接被节流
→ Confirm延迟上升
```

内存水位基于 RabbitMQ 可用内存判断，容器环境必须核对运行时是否正确识别 Cgroup 限制。磁盘水位要留出积压、Compaction、分页、升级和故障恢复空间，不能只等文件系统 99% 才告警。

## 2. 容量模型

```text
积压条数 = 峰值进入速率差 × 最长故障恢复时间
原始积压字节 = 积压条数 × 平均消息大小
实际磁盘需求 = 原始字节 × 副本数 × 存储开销 × 安全系数
```

还要计入消息属性、索引、WAL、死信/重试副本、瞬时写放大和磁盘性能。容量验收同时约束：发布吞吐、Confirm P99、消费吞吐、最大积压恢复时间、节点故障后 Catch-up 时间。

## 3. 压测矩阵

| 变量 | 至少覆盖 |
| --- | --- |
| 消息大小 | P50、P95、最大值 |
| 队列类型 | Classic、Quorum 或 Stream 实际选型 |
| 可靠性 | persistent + Confirm + manual ACK |
| 拓扑 | 队列数量、Binding、消费者数 |
| 故障 | 停节点、慢盘、网络抖动、消费者停机 |
| 负载 | 稳态、突发、长积压与排空 |

不要用无 Confirm 的小消息峰值替代生产容量。压测数据必须记录 RabbitMQ 版本、实例规格、磁盘、网卡、队列参数和客户端批量策略。

## 4. 常见瓶颈证据

- `messages_ready` 增长：消费能力低于发布；
- `messages_unacknowledged` 高：消费者或下游慢；
- Confirm P99 上升：磁盘、副本 RTT、流控或 Leader 变化；
- Connection 处于 flow：Broker 正在施加背压；
- Disk alarm：发布被保护性阻断；
- 单核饱和：热点队列、加密或协议处理；
- 网络满：大消息、副本复制或扇出。

## 5. 处置顺序

先停止非关键发布或限流，保护磁盘和多数派；再确认积压增长斜率与最老消息年龄；随后扩消费者或修复下游。临时增加水位只会推迟故障，必须证明有足够恢复空间并设置回滚时间。

## 6. 验收

以业务峰值 1.5～2 倍运行稳态压测，再停止消费者形成目标积压，恢复后测排空时间。期间停止一个节点，确认 Confirm、重复投递和资源水位仍满足 SLO。
