# DataX 调度、容器、安全与可观测性

DataX 负责执行这次同步，调度器负责何时执行、执行哪个固定窗口、是否允许重跑以及谁来推进状态。增加一个定时器，不会自动补齐数据正确性和恢复协议。

## 1. 作业要携带哪些身份

区分逻辑任务名、数据窗口、配置版本和本次执行编号。同一个小时窗口的第二次尝试，逻辑范围应保持不变，但执行编号要能区分日志与暂存输出。

调度器应知道本次从哪个水位开始、是否持有互斥权、产物写在哪里、校验是否通过、发布是否完成。DataX 的 `jobid` 可以帮助关联日志，但不自动提供这些持久化状态。

Airflow 的数据区间、重试和 Executor 原理见 [Airflow 学习路线](../../orchestration/airflow/00-Airflow从零到精通学习路线.md)。DataX 应作为被调用的任务，而不是被误认为 Airflow 自身的执行引擎。

## 2. 保留真正的退出码

下面是 Bash 包装片段，`run_dir` 必须是已经创建并限制权限的本次专用目录：

```bash
umask 077
set +e
python3 /opt/datax/bin/datax.py /work/jobs/orders.json 2>&1 | tee "$run_dir/datax.log"
datax_status=${PIPESTATUS[0]}
set -e
exit "$datax_status"
```

`PIPESTATUS[0]` 必须紧接流水线保存，否则会被后续命令覆盖。只读取 `tee` 的返回值可能把同步失败误报成成功。包装层还要分别检查日志落盘失败与数据校验失败，不能只有一个“进程退出零”的判断。

超时终止后可能留下已提交批次。需要给 Python 启动器和 JVM 留出终止时间，检查自有进程树是否退出，再决定恢复策略；不要为了清理本次任务杀掉节点全部 Java 进程。

## 3. Kubernetes Job 的模板边界

以下是部署模板，必须替换审核镜像，并提前创建包含已渲染 `job.json` 的 `datax-orders-job` Secret。Secret 中的配置仍需限定权限和集群侧加密保护；Base64 本身不是加密。

```yaml
apiVersion: batch/v1
kind: Job
metadata:
  name: datax-orders-example
spec:
  backoffLimit: 0
  activeDeadlineSeconds: 2700
  template:
    spec:
      restartPolicy: Never
      automountServiceAccountToken: false
      terminationGracePeriodSeconds: 60
      securityContext:
        runAsNonRoot: true
        runAsUser: 10001
        runAsGroup: 10001
        fsGroup: 10001
        seccompProfile:
          type: RuntimeDefault
      containers:
        - name: sync
          image: registry.example.com/datax-sync:approved-build
          command: ["python3", "/opt/datax/bin/datax.py"]
          args: ["/run/job/job.json"]
          securityContext:
            allowPrivilegeEscalation: false
            readOnlyRootFilesystem: true
          resources:
            requests:
              cpu: "1"
              memory: 2Gi
            limits:
              cpu: "2"
              memory: 4Gi
          volumeMounts:
            - {name: job, mountPath: /run/job, readOnly: true}
            - {name: logs, mountPath: /opt/datax/log}
            - {name: temporary, mountPath: /tmp}
      volumes:
        - name: job
          secret:
            secretName: datax-orders-job
            defaultMode: 288 # 十进制 288 对应八进制 0440
        - name: logs
          emptyDir:
            sizeLimit: 2Gi
        - name: temporary
          emptyDir:
            sizeLimit: 1Gi
```

模板的资源值只是说明配置位置，不是容量结论。镜像还须允许指定 UID 读取运行包，提供 Python/JRE/CA，并让其他实际日志或临时路径也可写；根据实际 `logback.xml` 决定是否需要额外挂载。

没有幂等验收前，示例关闭 Job 层自动重试。即使单个 Job 的 parallelism 为一，两个不同 Job 仍可撞在同一业务窗口上；外部互斥与 fencing 不能省略。

## 4. 密码与权限如何分层

源账号通常只需读取明确的表；目标加载账号只写专用 staging；建表和正式发布使用单独权限边界。不要为了方便给同步账号超级用户权限。

口令不写入 Git、镜像、`-p` 参数或 Shell 历史。随文渲染器从环境获取必要字段并创建新的私有 JSON；生产上也可以从受限挂载文件获取。环境变量不是保险箱，进程诊断和权限范围仍需控制。

限制调试日志和脏行日志。即使框架对名为 password 的字段进行处理，自定义参数名、URL、SQL、错误值和插件日志也可能包含敏感内容，不能假设所有输出都会自动脱敏。

## 5. 网络与 TLS

DataX 节点或 Pod 需要分别到源端和目标端的连通性。网络策略按这两条连接及必要的 DNS、认证服务放行，不需要因为“同步”就开放所有端口。

使用匹配驱动版本的 TLS 参数与可信 CA，核对主机名和证书链。不能把 `useSSL=false`、跳过证书验证或降低认证强度当作常规排障修复。

## 6. 监控任务结果而不只监控进程

| 观测项 | 它回答什么 |
|---|---|
| 最后成功发布时间 | 下游多久没有拿到合格数据 |
| 当前窗口与水位滞后 | 同步是否跟上数据生产 |
| 启动、搬运、校验、发布时间 | 耗时发生在哪个阶段 |
| 读量、失败量、主动过滤量 | 数据是否完整或被排除 |
| 各 Task 耗时、等待与 JVM 资源 | 倾斜、背压、GC 和资源上限 |
| 源/目标连接、查询与锁 | 是否伤害数据库或被数据库限制 |

这类指标可以由包装器与日志采集构建，不表示开源 DataX 默认就提供一个 Prometheus HTTP 端点。标签优先使用稳定任务名和有限数据源标识，具体批次保留在日志或状态表，避免无限高基数。

## 7. 练习与答案

**问题一：流水线中 `tee` 成功，DataX 一定成功吗？**

答案：不是。必须保留 DataX 对应的退出状态，后续还要检查校验与发布状态。

**问题二：Kubernetes Job 自动重试为什么可能重复写入？**

答案：前一个 Pod 可能已经提交部分数据，新 Pod 会重新执行输入范围，若目标没有隔离和幂等就可能重复或冲突。

**问题三：Secret 的内容经过 Base64 编码，就足以公开存放了吗？**

答案：不可以。它只是编码，需要存储加密、访问权限、日志控制与密钥治理。

**问题四：进程运行十分钟没有异常，为什么仍应告警？**

答案：可能没有有效进度，或数据窗口已经超时。应结合任务进度、成功发布时刻和业务滞后判断。
