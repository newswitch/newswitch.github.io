# DataX 数据校验、发布与失败恢复

“同步成功”至少有三层含义：进程没有报告失败、目标包含正确数据、下游已经看到完整发布的那一批。三个判断不能互相替代。验收应该针对固定输入集合，而不是一边持续变化的源表。

## 1. 固定输入范围和输出批次

实验使用四行订单，字段契约见[类型转换](./08-类型转换Transformer与脏数据.md)。`customer_id` 是字符串，`amount` 是两位小数的十进制值或 NULL，`updated_at` 是约定的 UTC 文本。

| order_id | customer_id | amount | status | updated_at |
|---|---|---|---|---|
| 101 | 0007 | 10.10 | paid | 2026-11-01 00:10:00 |
| 102 | 0008 | 20.20 | paid | 2026-11-01 00:20:00 |
| 103 | 0009 | NULL | pending | 2026-11-01 01:10:00 |
| 104 | 0010 | 0.00 | cancelled | 2026-11-01 02:10:00 |

原始 CSV 用 `\N` 表示 NULL。全量输入的行数和唯一键数均为四，非空金额总和为 `30.30`，金额 NULL 数量为一；第一个小时窗口只包含 101 和 102。

## 2. 多层校验各自能发现什么

| 校验 | 能发现 | 仍可能漏掉 |
|---|---|---|
| 总行数 | 规模变化 | 少一行同时多一行 |
| 唯一业务键与缺失键 | 重复、漏键、多键 | 键正确但字段被改写 |
| 分区/窗口数量 | 局部缺失与范围错误 | 相同数量的错误替换 |
| 金额等控制总数 | 聚合差异 | 一增一减抵消、其他字段错误 |
| NULL 与状态分布 | 缺失值和分类变化 | 同分布的个体错配 |
| 规范化行哈希/字段比较 | 字段级差异 | 比较范围和规范化规则本身有误 |

因此验收不能只有一个 `COUNT(*)`。对于小批次可以直接按业务键比较字段；对于大批次，先分桶与聚合定位差异，再抽样或逐行核实。

## 3. 数据库侧的基础控制总数

```sql
SELECT COUNT(*) AS rows_total,
       COUNT(DISTINCT order_id) AS keys_total,
       SUM(amount) AS amount_total,
       SUM(amount IS NULL) AS amount_nulls
FROM datax_lab.orders
WHERE updated_at >= '2026-11-01 00:00:00'
  AND updated_at <  '2026-11-01 03:00:00';
```

对目标 staging 使用同一字段契约和同一批次范围执行对应查询。这里的四行实验预期是 `4、4、30.30、1`，不是生产环境的固定指标。

源端仍在变化时，先确定冻结快照、输入清单或其他稳定比较基准。源在验收期间被更新，不是可以忽略差异的理由，也不能直接把差异判成同步引擎丢数据。

## 4. 哈希之前先定义规范化

需要定义列顺序、字符编码、NULL 编码、小数 scale、时间时区与二进制表示。`NULL` 不能和空字符串编码相同，字符串中的分隔符不能造成拼接歧义。

随文校验器把类型化后的行编码为 JSON 数组，保留 NULL，金额统一两位小数，再按业务键比较；输入输出行顺序不影响判断。它拒绝重复键、非法金额和错误表头。

```bash
python examples/datax/sync-lab/sync_contract.py summarize examples/datax/sync-lab/fixtures/orders.csv
python examples/datax/sync-lab/sync_contract.py compare examples/datax/sync-lab/fixtures/orders.csv OUTPUT_FILE_1 OUTPUT_FILE_2
```

将 `OUTPUT_FILE_1 OUTPUT_FILE_2` 替换为本批真实输出清单，可以只有一个文件。不要把日志、别的批次文件或未完成输出混进来。文件可以乱序，记录的业务内容不能乱改。

## 5. 发布与水位的关系

写完 staging 后先校验，再执行发布。目标发布与控制状态能放在同一数据库事务中时，可以一起提交；跨系统则需要持久化发布标识与可重复确认的恢复协议，而不是假设存在全局事务。

校验器返回非零时，不得推进水位。若发布成功后状态记录失败，下次应先核实该批次是否已经发布，再幂等确认状态，避免重复发布。

随文的水位函数只演示状态推进的必要条件，不代替实际控制库、分布式锁或跨系统事务。它要求：DataX 退出成功、校验成功、发布成功，三者缺一则保留原水位。

## 6. 四个阶段的恢复选择

| 失败点 | 已有结果 | 安全恢复重点 |
|---|---|---|
| 写入之前 | 只有输入范围 | 修复环境后使用相同固定范围 |
| 写入中 | 可能存在部分提交 | 隔离旧批次，证明幂等或重建 staging |
| 校验阶段 | 暂存数据完整性未通过 | 定位差异，不发布，不推进 |
| 发布后、状态前 | 正式数据可能已可见 | 按批次标识核实并确认，防重复发布 |

旧 staging 的回收要以具体批次为单位，并满足保留和追溯策略。不要通过清空整个共享目录或正式表来“恢复干净环境”。

## 7. 练习与答案

**问题一：总行数、金额总和都一致，还可能同步错误吗？**

答案：可能。键或字段可能被互换，金额差异也可能互相抵消，还需键、NULL、状态和字段级校验。

**问题二：四行输入包含一行 NULL 金额，全部改成零金额可以通过完整验收吗？**

答案：不能。即使求和没变，NULL 数量和逐行语义已经改变。

**问题三：输出文件顺序改变，是否必然说明错误？**

答案：不是。并发传输不保证全局行序，按稳定业务键和规范化字段比较。

**问题四：发布完成后记录水位失败，恢复时应直接重发吗？**

答案：先通过批次标识核实发布结果，再幂等确认或补偿；否则可能产生重复发布和副作用。
