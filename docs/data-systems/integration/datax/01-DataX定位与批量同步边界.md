# DataX 定位与批量同步边界

假设要把 MySQL 的订单表同步到分析系统。第一个问题不是“装哪个插件”，而是：下游需要每天一次的订单快照、每小时变化的订单，还是每个事务的新增、更新和删除？三种目标决定三种不同的数据读取与恢复方式。

## 1. Reader 与 Writer 分别解决什么

Reader 把源系统的数据转换成 DataX 的 `Record`；Writer 把这些记录写到目标系统。框架组织并发、传输、转换和统计。更换数据源通常意味着更换 Reader，更换目标通常意味着更换 Writer，而不是重写整个同步引擎。

以订单为例，MySQLReader 执行查询，读出 `order_id`、`amount` 和 `status` 等字段；MysqlWriter 把它们按目标列顺序绑定到 JDBC 参数。DataX 运行机器需要能够分别连接两端，源库与目标库之间不一定直接传输数据。

插件能组合，不代表任意组合都能保持相同的数据语义。CSV 没有数据库约束，目标 `DECIMAL` 与文件里的文本也不是同一种物理表示。

## 2. 三类同步不能混为一谈

| 方式 | 读取对象 | 主要收益 | 不能自然获得的能力 |
|---|---|---|---|
| 全量查询 | 某次查询范围内的当前行 | 初始化、历史回灌 | 全库同一快照、执行期间的后续变化 |
| 条件增量 | `updated_at` 或 ID 范围 | 降低重复扫描量 | 硬删除、迟到提交完整性、事务日志顺序 |
| 日志 CDC | Binlog/WAL 等变更日志 | 持续捕获变化和日志位置 | 下游自动去重、跨系统原子提交 |

DataX 的常见关系型批任务主要承担前两类。不要因为配置里写了 `where updated_at ...`，就把它理解为持续订阅数据库事务日志。

对于 CDC 的读取和恢复状态，继续看 [Debezium 事件路径](../debezium/01-Debezium解决什么问题与一条变更事件的完整路径.md)。选择工具时先确定语义，而不是先比较一张吞吐量表。

## 3. ETL 中的转换能做到哪里

ETL 是 Extract、Transform、Load，即抽取、转换、加载。DataX 的 Transformer 适合逐条记录上的轻量处理，例如字段裁剪、脱敏或过滤。跨表 Join、大规模聚合、窗口计算或持续维护多条流之间的状态，不应假设由普通 Transformer 自动承担。

若目标是先收集原始数据再用 SQL 转换，可以让 DataX 先写入原始层，由目标数据库、Spark 或其他计算系统处理后续逻辑。这种安排还保留了重算的输入。

## 4. 全量查询为什么不等于一致性快照

假设 Task A 在 10:00 读取 ID 1—100，Task B 在 10:02 读取 ID 101—200。两次 JDBC 查询可能有各自的事务与视图。源库在两分钟内发生更新后，两部分数据不一定对应同一个时刻。

解决办法要针对需求选择：允许分析近似快照时，明确时间跨度；要求一致快照时，冻结输入、使用受控快照或经过验证的备份/CDC 初始化机制。仅把数据库隔离级别改成 Repeatable Read，不能让彼此独立的连接自动共享一个事务。

## 5. 迁移与备份的边界

数据库迁移还包括 Schema、索引、触发器、账号、字符集、DDL、增量追平、割接和回滚。DataX 可以完成其中的数据搬运部分，但传输结束不表示其他对象已经迁移。

备份则要求可恢复的历史状态、保留周期和灾难恢复能力。向另一张表定时复制当前数据，会把误删除或错误更新继续传播；它不能因此替代数据库备份与 PITR。两者的保护目标见[数据库可靠性学习路线](../../database-reliability/00-数据库可靠性与备份恢复学习路线.md)。

## 6. 为一个任务写清数据契约

订单任务至少要定义以下内容：

- 输入是“当前订单状态”还是“订单变化事件”；
- 主键是否稳定，更新是否会更换业务键；
- 时间字段的时区、精度和提交语义；
- NULL、空字符串、金额和编码的对应关系；
- 目标何时对下游可见，失败后如何识别部分数据；
- 验收使用哪个固定范围，能否重新得到同一份输入。

这些约束确定后，JSON 才有明确含义。下一篇沿[执行链路](./02-Job-Task-Channel与源码执行链路.md)理解各组件如何实现这次搬运。

## 7. 练习与答案

**问题一：每天全量覆盖分析表，可以当成七天历史备份吗？**

答案：不能。覆盖后的分析表没有天然保留前六天状态，也未必包含可恢复数据库所需的其他对象和事务日志。

**问题二：两个 Reader 连接都使用 Repeatable Read，就共享快照了吗？**

答案：没有。隔离级别约束各自事务的可见性；不同连接还需要专门机制才能共同指向一致的源状态。

**问题三：需要持续捕获被物理删除的订单，更新时间查询够吗？**

答案：不够。已删除行不再参与查询，需要删除标记、删除日志、CDC 或周期性完整对账等额外机制。

**问题四：任务把金额字符串写成浮点数后，总行数仍正确，算同步成功吗？**

答案：只完成了行的搬运，没有满足金额精度契约。必须核对端到端类型转换和金额控制总数。
