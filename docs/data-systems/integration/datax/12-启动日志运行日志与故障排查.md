# DataX 启动日志、运行日志与故障排查

排查 DataX 时，先回答两个问题：最后一个完成的阶段是什么，目标已经提交了哪些数据。前者决定检查哪个组件，后者决定恢复动作是否安全。

## 1. 先收集一份最小证据

记录执行编号、窗口、运行包与插件摘要、脱敏配置、完整异常链、退出码和任务最后进度。数据库侧保留对应时间段的查询、锁、连接和错误信息，容器侧保留退出原因与资源事件。

不要只截取最后一行 `DataXException`；上层统一错误往往把更具体的 `SQLException`、类加载异常或权限原因包在下面。分享日志前先移除密码、Token、内部连接信息和原始敏感行。

## 2. 按阶段定位

| 最后阶段 | 典型现象 | 首先检查 |
|---|---|---|
| Python 选项解析 | usage、参数数量错误 | Python 路径、引号、任务路径 |
| Java 启动与类装载 | 找不到 java、类或方法 | Java 版本、classpath、插件目录与混合 JAR |
| Job 初始化/准备 | JDBC、TLS、权限、preSql 失败 | 实际 URL、驱动、证书、账号与 SQL |
| Reader 切分 | 范围获取失败、Task 数异常 | splitPk 类型/索引、where、查询范围 |
| Task 运行 | 脏行、写入失败、速度停滞 | 字段、目标约束、两端负载与等待 |
| 收尾与发布 | postSql 或外部发布失败 | 已提交范围、校验结果、发布状态 |

一次任务没有进入 Task 运行阶段，先别用“数据库写慢”解释它。相反，已经写入多个批次后再报错，也不能当作“启动失败、没有数据变化”。

## 3. 一份教学日志怎样读

下面是刻意缩短并归一化的教学日志，不是固定版本必须逐字匹配的输出格式：

```text
INFO  Engine       configuration loaded, mode=standalone
INFO  JobContainer init / prepare completed
INFO  JobContainer reader split produced 4 tasks
INFO  TaskGroup    tasks running, active channels=2
INFO  Progress     read=20000, failed=0
ERROR Writer       SQLException: duplicate key
ERROR JobContainer job failed
```

这组信息能说明已经经过初始化和切分，错误发生在目标写入。它不能说明前 20000 条均未提交，也不能说明四个 Task 的工作量相等。接下来要查具体目标表、唯一键、失败 Task 和已提交批次。

## 4. 三类经常混淆的连接错误

类加载错误首先检查本机装载，不需要先调整网络；连接超时检查执行 Pod/节点到真实目标的路径，而不是只从个人电脑测试；认证与 TLS 失败则检查驱动、证书链、主机名、认证方法和账号边界。

在运行环境进行只读检查：

```bash
java -version
python3 /opt/datax/bin/datax.py --help
getent ahosts mysql.source.internal
ss -tnp
```

这些命令各自只提供一层证据。`ss` 看到 TCP ESTABLISHED 不代表 JDBC 已登录，模板能打印也不代表 Reader JAR 已加载。不要把暂时关闭 TLS 校验作为最终修复。

## 5. 不动的任务：区分等待与死锁

先检查是否被配置限速、是否只剩倾斜分片，再检查源查询、目标锁与网络。必要时采集本次自有 JVM 的线程栈和 GC 信息，比较多次采样是否仍在前进。

```bash
jcmd JOB_JAVA_PID Thread.print
jcmd JOB_JAVA_PID GC.heap_info
```

`JOB_JAVA_PID` 要替换为经过核对的本次进程，命令要求镜像提供相应 JDK 诊断工具与 Attach 权限；只有 JRE 的精简镜像未必有 `jcmd`。不要在共享机器上盲目附加所有 JVM。

看到 Reader 在发送队列处等待，优先验证 Writer 是否受阻；Writer 等记录则检查上游。单次线程栈不是死锁证明，要结合持续进度和资源状态。

## 6. OOM 与退出 137

Java `OutOfMemoryError`、容器 `OOMKilled`、人为 SIGKILL 与节点驱逐不是同一个现象。退出 137 表示与 SIGKILL 相关的退出，不能仅凭它断言 Java 堆耗尽。

对照容器 reason、事件、cgroup 内存、堆上限、GC、通道与 batch 设置。容器总内存还包含堆外、线程栈、驱动和其他进程；增大 `-Xmx` 却不增加可用空间，可能更容易触发容器级杀进程。

## 7. 恢复动作先过数据关

恢复前确认输入窗口可复现、目标是否部分提交、重复写入是否安全、正式表是否受影响以及水位有没有提前推进。先隔离旧输出与新尝试，再决定重跑、补偿或重建 staging。

禁止把“重启成功”当作“数据已经修复”。恢复验收要检查同一输入范围内的键、字段、控制总数与发布状态，详见[数据校验与恢复](./13-数据校验发布与失败恢复.md)。

## 8. 练习与答案

**问题一：`ClassNotFoundException` 应先检查数据库路由吗？**

答案：先检查运行时类名、插件装载路径和 JAR 组合，它可能还没尝试数据库连接。

**问题二：退出 137 能直接证明需要增加 Java 堆吗？**

答案：不能。需确认是否 OOMKilled、外部终止或其他 SIGKILL，并区分堆与容器总内存。

**问题三：目标重复键错误后，把模式改成 update 就能结束排障吗？**

答案：不能。先确认重复来源、目标已有状态、版本顺序和副作用，再选择经过验证的重跑协议。

**问题四：采样看到线程阻塞在队列，就一定发生死锁了吗？**

答案：不是。可能是正常背压或等待输入，需要持续进度、多个线程与多次采样共同判断。
