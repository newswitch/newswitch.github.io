# DataX 部署、构建、驱动与运行环境

一个可以运行的 DataX 环境需要同时具备 Java 运行时、Python 启动器、框架 JAR、Reader/Writer 插件和插件依赖。只下载一个 `datax.py`，或者只把新的 JDBC JAR 放到某个目录，都不等于已经完成环境适配。

## 1. 先记录兼容性基线

| 项目 | 需要记录什么 |
|---|---|
| DataX | 仓库提交、运行包摘要、构建方式 |
| Java | 厂商、完整补丁版本、体系结构、信任库和 JVM 参数 |
| Python | 明确的 Python 3 可执行文件及版本 |
| 插件 | 插件名、JAR、`plugin.json` 和依赖摘要 |
| 数据库 | 产品、版本、认证方式、TLS 和字符集 |
| 操作系统 | 架构、cgroup/容器限制、时区、可写目录 |

本系列固定的上游提交见[学习路线](./00-DataX学习路线.md)。其根 POM 使用 Java 8 编译基线，MySQL 驱动属性仍为 `5.1.47`，共享数据类型定义中也保留旧驱动类名。这里的 `0.0.1-SNAPSHOT` 不是足以识别发行物的版本号。

这不等于建议安装任意陈旧 JDK 8 更新版，更不等于宣称该包已经通过 MySQL 8.4 的认证、TLS 与类型回归。使用仍受维护的运行时补丁；切换更高 JDK 或更新驱动时，固定组合并执行插件级测试。不要为连接成功而降级数据库认证或关闭证书校验。

## 2. 两种交付方式

审核后的运行包适合直接部署，但必须能追溯来源、摘要、插件和依赖。来源不明的“全插件整合包”不能只靠文件名判断版本。

安装账号已经拥有 `/opt/datax/releases` 的写入权限后，可以把通过审核的包解压到一个新目录。摘要清单必须从可信发布链取得，不能只在下载后自行计算一个摘要就当作来源证明。

```bash
set -euo pipefail
sha256sum -c datax-approved.sha256
tar -tzf datax-approved.tar.gz
datax_release_dir=$(mktemp -d /opt/datax/releases/datax.XXXXXX)
tar -xzf datax-approved.tar.gz -C "$datax_release_dir" --no-same-owner
test -f "$datax_release_dir/datax/bin/datax.py"
export DATAX_HOME="$datax_release_dir/datax"
```

这段约定包内的顶层目录为 `datax/`；解压前核对清单，拒绝绝对路径、越界路径或异常链接。不要覆盖正在运行的目录。后面的 `/opt/datax` 是稳定运行入口示例，实际命令也可以使用此处确定的 `$DATAX_HOME`。

源码构建有利于控制依赖。以下命令在一个新工作目录中检出固定提交，不对已有工作区执行覆盖或清理：

```bash
git clone https://github.com/alibaba/DataX.git datax-source
cd datax-source
git checkout --detach 80ec23d5c5328eb90ca364d2749e92dfaf44541e
git rev-parse HEAD
mvn -version
mvn help:effective-pom -Doutput=effective-pom.xml
```

这一步先检查有效 POM 中实际采用的插件版本，不把“检出了源码”当成已经具备可复现构建链。固定上游根 POM 没显式锁定 Assembly 插件，根打包描述中的 ID 也为空。旧指南的 `assembly:assembly` 依赖旧目标；现代 Assembly 插件主要使用 `single`，并要求合法的描述 ID，不能只机械改一个目标名。

维护自己的构建基线时，至少完成这些工作：

1. 固定 Maven/JDK、Assembly 和其他构建插件版本，不依赖隐含版本；
2. 校正所需模块的 Assembly 描述 ID、继承与输出目录；
3. 先生成各模块产物，再组装总包，核对根 `package.xml` 的文件路径是否都已存在；
4. 检查运行目录、插件和依赖是否齐全，再执行测试与安全扫描。

上游历史布局是 `target/datax/datax/`，现代打包的 classifier、`appendAssemblyId` 等设置可能改变目录名；实际交付路径应以构建清单为准。源代码构建链的适配与运行包部署分开验收，不能把旧版本能出包的命令写成任意现代环境都可执行的一键步骤。

旧插件依赖、仓库可用性和构建工具版本都可能影响构建。遇到依赖解析失败，应检查具体坐标和可信制品仓库，不随意加入 HTTP 镜像或关闭 TLS。使用 `maven.test.skip` 跳过测试也不构成验收；`BUILD SUCCESS` 更不能证明目标数据库兼容性。

## 3. 认识运行目录

```text
datax/
├── bin/datax.py
├── conf/core.json
├── conf/logback.xml
├── lib/
├── plugin/reader/<插件名>/
├── plugin/writer/<插件名>/
├── job/
└── log/
```

`plugin.json` 描述插件入口，插件自己的 JAR 和 `libs/` 提供实现与依赖。插件装载器有自己的加载范围；不要假设替换 `lib/` 中一个文件就覆盖了所有 Reader/Writer 的驱动。

维护代码与插件的只读版本目录，把实际作业、临时文件和日志放到独立可写路径。保留上一个已验收的版本，可让运行入口指向具体版本；不要在运行中的插件目录原地混入新旧 JAR。

## 4. 最小检查按层推进

```bash
java -version
python3 --version
python3 /opt/datax/bin/datax.py --help
python3 /opt/datax/bin/datax.py -r txtfilereader -w txtfilewriter
```

第一条确认 PATH 上的 Java；第二条确认 Python；第三条只检查启动器选项；第四条展示插件模板，并不执行同步。模板输出前有说明文字，不应直接把整段标准输出重定向后当作纯 JSON 使用。

模板生成成功也不保证 Java 能加载插件 JAR。下一步用随文文件任务实际启动 JVM：先按示例 README 渲染路径，再执行任务，最后用校验程序比较输入和输出。

```bash
python3 /opt/datax/bin/datax.py /work/jobs/file-copy.json
```

其中 `/work/jobs/file-copy.json` 是已经渲染、检查并限制权限的真实配置，不是带 `${...}` 的模板。首次只使用专用实验文件夹与小数据集。

## 5. 驱动升级为什么要单独验收

驱动更新可能涉及类名、URL 参数、认证插件、TLS 默认值、时区解释、零日期和 unsigned 类型。更换 JAR 后如果旧类名不存在，甚至还没有进入数据库握手就会失败。

先验证加载与 TLS，再验证读取和写入，最后验证重试、精度、NULL、时区和批次提交。以驱动版本清单说明“哪一组通过了什么”，不要只写“支持所有 MySQL”。

## 6. 容器不改变这套依赖关系

容器把审核过的运行包、Java 和 Python 封装到镜像中，但不会自动修复它们的兼容性。镜像需要 Python 3、运行时 CA、可写日志/临时目录与正确的非 root 用户；业务配置和密码不应进入镜像层。

Kubernetes Job 如何接管进程、限制并发和处理失败，见[调度与安全](./11-调度容器安全与可观测性.md)。

## 7. 练习与答案

**问题一：`datax.py --help` 成功，可以证明 Reader JAR 正常吗？**

答案：不能。帮助选项可以在未执行 Java 插件逻辑时返回，还需要实际运行小任务。

**问题二：把驱动换成更高版本，为什么可能出现 `ClassNotFoundException`？**

答案：插件仍可能请求旧驱动类名，或新 JAR 不在实际插件装载路径。需同时检查类名与加载范围。

**问题三：上游 POM 写着 Java 8，是否可以使用任意旧补丁版？**

答案：不可以。语言基线、运行时安全补丁和数据库兼容性是不同问题，应使用受维护并经过回归的组合。

**问题四：为什么不把 `/opt/datax` 整个挂成可写共享目录？**

答案：运行任务可能改动其他任务依赖或混入新旧插件。代码版本应稳定，任务状态、日志与临时文件独立存放。
