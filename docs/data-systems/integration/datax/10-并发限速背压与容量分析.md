# DataX 并发、限速、背压与容量分析

DataX 慢，不能只把 `channel` 从 4 改到 32。可并行的读取任务、目标提交速度、网络、JVM 内存和调度器同时运行的作业数共同决定有效吞吐。

## 1. 先确认最终通道数怎样计算

在固定基线的 `JobContainer.adjustChannelNumber()` 中，有正的 Job 字节或记录速率限制时，先用“总速率 ÷ 单通道速率”计算通道数；两种限制都存在时，取较小的计算结果。此路径有结果后直接返回，不再使用 `speed.channel`。

没有正的总速率限制时，才使用配置的 `job.setting.speed.channel`。因此三项不能简单理解为三个并列的 `min()` 硬上限。

下面是需要合并到完整任务的配置片段，不含 Reader/Writer：

```json
{
  "core": {
    "transport": {"channel": {"speed": {"byte": 4194304}}}
  },
  "job": {
    "setting": {"speed": {"byte": 16777216}}
  }
}
```

这里按 16 MiB/s 总预算、4 MiB/s 每通道计算，得到四个通道。若只设置总速率，而默认每通道速率仍为非正值，会触发配置错误，不能期待框架猜一个值。

计算使用整数除法且至少保留一个通道，限速还有统计间隔和批量效应；参数表示逻辑记录搬运预算，不能替代网络设备的硬 QoS，也不能直接当作准确的网卡线上字节速率。

## 2. Task 数量与长尾会限制有效并发

请求八个通道，Reader 只生成一个可执行 Task 时，其余预算不能凭空生成工作。相反，100 个 Task 可以分批在四个通道中运行。

还要看各 Task 的完成分布。如果前三个通道很快结束，最后一个仍处理大部分数据，瓶颈更可能是切分倾斜，而不是总通道预算不足。比较每片的记录数、耗时、源查询计划与目标分布。

## 3. 从等待方向建立假设

| 现象 | 优先检查 | 不能直接下的结论 |
|---|---|---|
| Reader 等待向队列发送 | 目标写入、提交、限速、锁等待 | 源库一定慢 |
| Writer 经常等不到记录 | 源查询、网络、输入文件、Reader 转换 | 增大 batchSize 就能解决 |
| JVM CPU 高、数据库空闲 | 编码、Transformer、对象分配、GC | 需要更多数据库连接 |
| 两端空闲、速度稳定在固定值 | 实际限速和 Task 数 | 硬件性能不足 |
| 数据库延迟随 channel 升高 | 扫描、锁、I/O、连接与提交压力 | 再加并发一定更快 |

等待统计是调用路径上的线索，不是单独的根因判决。把它与实际查询、线程栈、数据库指标和网络重传交叉验证。

## 4. 队列、批次与堆内存

固定 Core 配置包含通道记录容量 512、字节预算 64 MiB、交换缓冲记录数 32，以及每 TaskGroup 的通道组织参数。这些值是此源码基线的默认项，不是通用调优建议。

字节预算不是每个 Channel 在启动时就预分配 64 MiB。内存还包括 Record/Column 对象、JDBC 缓冲、Writer batch、转换临时对象、线程栈和堆外/native 部分。

教学估算：四个活动通道，每个平均积累 200 条、每条有效载荷 2 KiB，队列有效载荷约 `4 × 200 × 2 KiB = 1.56 MiB`。这个数字既不是总堆占用，也不能用于把容器 memory limit 设置成 2 MiB；对象开销和驱动行为需要实测。

增大 batchSize 可能减少提交次数，也会扩大缓冲、单次请求和失败影响范围。先检查目标限制、最大行大小和锁持有时间，再渐进调整。

## 5. 一个窗口怎样做容量预算

假设固定输入为 100 GiB，测得相同数据口径的有效吞吐为 80 MiB/s，纯搬运时间下界约为：

```text
100 × 1024 MiB ÷ 80 MiB/s = 1280 s = 21 分 20 秒
```

如果窗口只有 30 分钟，仅剩 8 分 40 秒承担启动、扫描、长尾、校验、发布和波动。小表热缓存测试中的峰值不能直接当作长期吞吐。

还要核对压缩前后大小、DataX 逻辑字节和网络线上字节是否使用同一口径。估算结果应与代表性输入、峰值业务时段和失败恢复时间共同验证。

## 6. 调度并发乘上单任务并发

四个作业各使用四个通道，会形成最多约十六组活动读写工作，不是整个节点仍只有四通道。数据库连接还可能包含初始化与元数据连接，所以不能把活动通道数直接当作精确连接总数。

按源库、目标库和运行节点分别设置预算。调度器的池或并发限制与 DataX 单任务限速要配合，避免所有任务在整点同时冲击同一个源库。

## 7. 练习与答案

**问题一：总字节限速和单通道字节限速均为正，还配置 channel=2，通道数必然不超过二吗？**

答案：不能这样判断。固定实现优先按速率预算计算通道数，得到结果后不再读取 channel。

**问题二：八通道任务只有一个 Reader 切片，是否能靠增加 Writer 批量大小用满八通道？**

答案：不能。批量写入大小不改变缺少可并行读取工作的事实。

**问题三：队列预算四乘 64 MiB，是否就是 JVM 启动内存？**

答案：不是。预算不是统一的预分配 RSS，实际内存还受记录数量、对象与驱动缓冲等影响。

**问题四：100 GiB 在 80 MiB/s 下能在十分钟完成吗？**

答案：不能。按相同口径计算，纯搬运下界已经是 1280 秒，还没计入额外开销。
