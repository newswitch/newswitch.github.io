# SeaTunnel 部署、运行环境与集群模式

部署 SeaTunnel 要同时准备运行包、Java、连接器、驱动、网络和状态存储。只复制一个启动脚本，往往能启动客户端，却无法在 Worker 上真正读写。本篇固定 **3.0.0**，Linux 命令中的安装路径需要替换为自己的目录。

## 1. 固定发行物，不只固定文件夹名字

从 Apache 发布渠道取得对应发行包，核对该包的签名或 SHA-512，再解压到专用目录。保存包版本、校验结果、插件清单、驱动版本与 Java 输出，避免不同节点在相同目录名下运行不同 JAR。

3.0.0 部署文档列出 Java 8/11，并说明更高版本理论上可工作；这**不是任意新 JDK 都经过全部连接器认证**。新环境可先按文档选择 JDK 11，再核对实际连接器/数据库驱动是否提出更高要求。有冲突时应选择经过验证的组合，而不是只改 `JAVA_HOME`。

```bash
export SEATUNNEL_HOME=/opt/apache-seatunnel-3.0.0
java -version
printf '%s\n' "$JAVA_HOME"
ls "$SEATUNNEL_HOME/bin"
ls "$SEATUNNEL_HOME/connectors"
```

`SEATUNNEL_HOME` 是安装路径，`JAVA_HOME` 是 JDK 路径，两者不能互换。生产进程使用专用账号；配置、日志与凭据分别授权，不需要 root 运行。

## 2. 插件安装与第一次执行

编辑发行包自带 `config/plugin_config`，最小示例只保留所需连接器条目：

```text
--seatunnel-connectors--
connector-fake
connector-console
--end--
```

然后执行发行包自带的安装脚本和任务入口：

```bash
cd "$SEATUNNEL_HOME"
sh bin/install-plugin.sh
./bin/seatunnel.sh --config /path/to/smoke.conf -m local
```

插件下载需要访问对应仓库。离线环境应在受控网络准备匹配版本的依赖，保留来源与校验信息；不要把其他版本全部 JAR 混进 `lib`。Zeta 的 JDBC 驱动按 3.0.0 文档放在每个执行节点的 `lib/`，Spark/Flink 的位置不同。驱动存在于提交机，不代表远端节点也能加载它。

## 3. 三种运行形态

| 方式 | 进程与职责 | 适用边界 |
| --- | --- | --- |
| Local | 每个任务独立进程，运行结束退出 | 安装验证、小任务与本地调试 |
| Hybrid cluster | 同一成员可协调和执行任务 | 部署直观，但协调与数据处理争抢资源 |
| Separated cluster | Master 与 Worker 分工 | 隔离职责；3.0.0 部署总览仍标注实验性 |

3.0.0 的混合集群文档推荐分离以降低协调节点被作业负载拖垮的风险，同时部署总览对分离模式保留实验性标记。阅读时应保留这两个条件：**架构方向上的推荐，不等于所有场景的稳定性背书**。评估接口、恢复与负载后再决定生产形态。

Local 模式不提供与集群相同的任务暂停、恢复、列举和取消管理能力。不要把本地命令成功等同于已验证 HA。

## 4. 集群配置从发行包模板修改

混合集群至少核对：`config/hazelcast.yaml` 的集群名、成员发现、绑定/通告地址与端口；`seatunnel.yaml` 的资源、检查点与历史保留；JVM 配置；以及客户端发现地址。启动命令使用该发行包的 `seatunnel-cluster.sh`，在前台或服务管理器下观察日志后再后台化。

集群同名只用于成员归属，不是安全认证。跨主机需要双向可达；容器里通告一个其他节点无法访问的地址，会表现为反复加入、心跳失败。开放防火墙时只向集群及受控提交端放行实际使用端口，不公开整个管理面。

## 5. 三份状态不能混为一谈

作业元数据与成员状态、持久检查点、目标业务数据是三份不同资产。Hazelcast 内存副本能帮助单节点故障，但全部 JVM 停止后，内存副本不等于外部持久化。检查点存储配置也不自动替代作业元数据的持久化设置。

多节点检查点必须落在所有相关节点可访问的持久存储。两台机器都有 `/data/checkpoint`，通常仍是两块互不共享的本地目录。状态存储凭据应最小授权，并测试重启、换节点和读回旧状态。

## 6. 练习与答案

**问题一：在客户端装好 JDBC 驱动，为什么任务仍提示找不到类？**

答案：实际 Writer/Reader 可能运行在其他节点；需在对应引擎要求的位置部署兼容驱动，并让执行进程重新加载。

**问题二：两个节点都看到同名本地目录，是否算共享检查点？**

答案：不算。必须验证一个节点写入的文件能被另一节点读取，并具有持久性、一致权限与正确隔离。

**问题三：为什么不直接把分离模式写成生产默认答案？**

答案：固定版本的文档仍有实验性声明。要结合版本能力、工作负载和故障测试，而不是把部署形态当成无条件承诺。

**问题四：Local 任务成功，集群还需验证什么？**

答案：成员发现、远端驱动、资源调度、共享状态、权限、协调故障以及从其他节点恢复，都没有被本地模式覆盖。
