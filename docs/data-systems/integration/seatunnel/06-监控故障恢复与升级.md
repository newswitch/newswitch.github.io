# SeaTunnel 监控、故障恢复与升级

“任务还在 RUNNING”只说明它没有进入终态，不说明数据仍向前推进。排障要同时看执行状态、业务进度与目标数据。本篇以 **3.0.0、Zeta** 为基线，操作生产任务前先保留 Job ID、配置摘要和最近成功检查点。

## 1. 先找到最后一个成功阶段

| 阶段 | 已证明的内容 | 失败时先看 |
| --- | --- | --- |
| 进程启动 | Java 与入口基本可用 | JDK、权限、JVM、端口 |
| 配置和插件加载 | 任务可解析并找到实现 | 参数、插件/JAR、类冲突 |
| 连接建立 | 某个端点已连通 | DNS、TLS、账号、驱动 |
| 开始读写 | 有数据经过部分算子 | 源查询、转换、目标错误 |
| 持续推进 | 有吞吐和新检查点 | 背压、锁、状态存储 |
| 完成与发布 | 本次执行结束 | 字段校验、重复、漏数、可见性 |

顶层异常常是包装，应该沿 cause 链找到最早的有效错误，并关联具体插件、任务和时间。不能把所有 `Timeout` 都归为网络：等待资源、数据库锁、目标提交和状态上传都可能超时。

## 2. 有限、只读的现场检查

以下命令只读取本机状态，不会清理状态或重启任务。日志目录按自己的发行包与服务配置确认：

```bash
pgrep -af 'seatunnel|hazelcast'
df -h
free -m
ss -lntp
tail -n 200 "$SEATUNNEL_HOME/logs/seatunnel-engine-server.log"
```

若日志被重定向到 systemd 或容器，则使用对应服务日志，而不是认定文件不存在就没有运行。命令输出可能包含账号、URL 与 SQL，分享前脱敏。线程转储/堆转储有权限、停顿与磁盘成本，仅对确认的自有 Java 进程按需采集。

## 3. 三类高频问题怎样分辨

**插件与驱动问题**：`ClassNotFoundException` 优先检查执行节点的依赖位置和版本；`NoSuchMethodError` 可能是冲突 JAR 或不兼容 API，不应继续叠加更多版本。先还原可审核的依赖清单。

**运行中停住**：查看读写计数是否同时停止、是否只有一个 Split 拖尾、目标锁等待是否增加、检查点是否推进。源读取为零也可能是已经追平，而不是卡死；用源端新事件与端到端延迟交叉判断。

**检查点失败**：区分算子未完成快照、存储超时/拒绝、状态文件不可读、以及恢复时源日志过期。增大 timeout 只能处理确实需要更长时间的操作，不能修复无权限或日志丢失。

## 4. 恢复前回答四个问题

输入还能从哪个位置重放；目标已提交到哪里；旧配置与新配置是否兼容；重放是否会产生不可逆副作用。保存旧状态与目标校验结果，在隔离目标或测试任务中验证后再切换。

不能随意删检查点“解除卡住”。删除可能丢失唯一可恢复位置，也可能触发重新快照。也不要同时让新旧任务写同一目标：即使都按主键 UPSERT，也可能出现旧值覆盖与删除竞争。

## 5. 升级不是只替换引擎包

记录引擎、插件、驱动、Java、任务配置和状态格式。先核对发行说明中的参数/默认值、类型转换、表名处理、删除和提交协议变化，再验证旧状态是否允许由新版本读取。没有明确兼容承诺时，不应直接覆盖原目录。

验收至少包含：固定小数据、金额与时间边界、全量与增量衔接、重复事件、删除、Schema 变化，以及 Worker/协调进程中断后的恢复。回退也需要考虑新版本已经写出的数据和状态，旧二进制能启动不代表能安全接管。

## 6. 练习与答案

**问题一：任务 RUNNING 且读计数不变，一定故障吗？**

答案：不一定。流任务可能已追平；需检查源端是否有新事件、日志位置、检查点和业务延迟。

**问题二：`NoSuchMethodError` 应该先加更多 JAR 吗？**

答案：不应。先核对依赖与类加载冲突，建立单一兼容组合，否则新增 JAR 可能让问题更隐蔽。

**问题三：检查点存储拒绝访问，增大超时能解决吗？**

答案：不能。应修复凭据、授权、路径或网络策略，并验证所有相关节点都能访问。

**问题四：旧二进制保留着，是否代表升级可以无损回退？**

答案：不是。还要验证状态格式、目标数据变化、源日志保留和新旧任务交接，避免两个版本并行竞争。
