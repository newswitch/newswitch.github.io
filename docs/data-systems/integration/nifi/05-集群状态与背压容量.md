# NiFi 集群、状态与背压容量

NiFi 集群让多个节点共同执行流程，但不等于把一个单节点队列变成了自动多副本消息系统。理解集群，需要分开看控制协调、处理器状态与内容数据。本篇以 **2.12.0 Traditional Engine** 为基线。

## 1. Coordinator 与 Primary Node 是角色

Cluster Coordinator 负责成员协调，Primary Node 承担配置为主节点执行的工作。主节点发生变化，并不表示所有业务数据都集中或复制到那个节点。某些抓取/列表类组件需要限制执行位置，避免每个节点都重复发现同一批输入。

All Nodes 则让各节点执行组件。如果一个测试 GenerateFlowFile 在所有节点各运行一次，就会产生多份输入，不能用单节点预期判断漏数或重复。

## 2. 选举、组件状态与队列是三层

当前管理员指南提供 ZooKeeper 和 Kubernetes 相关能力，不能沿用“所有 NiFi 集群都必须外部 ZooKeeper”的笼统结论。Kubernetes Leader Election 使用 Lease；ConfigMap State Provider 用于共享组件状态，二者的权限与用途不同。

也不能从“部署在 Kubernetes”推断已经使用 Kubernetes 选举和状态提供器。要检查实际配置、ServiceAccount/RBAC、对象前缀与命名空间隔离。组件状态还受大小限制，不适合塞入大量业务记录。

每个节点的队列与内容通常属于该节点的 Repository。Connection 的 Load Balancing 可以分发 FlowFile，但“分发”不等于“为每份内容自动保留多份可接管副本”。节点丢盘时，控制面健康也不能让原字节重新出现。

## 3. 背压阈值不是内存上限

Connection 可按对象数与数据大小设置背压。达到相应阈值后，上游会受限，给下游追赶机会；并发处理、已经在执行的批次和组件行为会影响实际边界，因此阈值不是严格的进程 RSS 限额或零超调保证。

FlowFile Expiration 表示过期处置，会让数据被丢弃，不是无损清积压。队列 Prioritizer 决定优先处理顺序，也不会增加目标吞吐。把过期时间缩短到几秒可能让队列看起来“恢复”，但业务已经漏数据。

## 4. 用速率计算队列生存时间

假设输入 10 MiB/s、输出 6 MiB/s，净增 4 MiB/s。若可用于新增内容的空间为 20 GiB：

```text
可承受持续积压时间 = 20 × 1024 MiB ÷ 4 MiB/s
                   = 5120 s ≈ 85.3 min
```

实际还要扣除 Repository 元数据、Provenance、内容归档、日志和文件系统安全余量。背压触发后输入可能转移到源系统，必须同步检查源的保留和重试能力；不能只把风险从 NiFi 磁盘挪到消息保留窗口。

积压年龄比单独队列长度更接近业务时效。低流量长时间不动的十个文件，可能比高流量下短暂排队的一万条记录更严重。

## 5. 线程和 I/O 怎样一起看

增加 Concurrent Tasks 前观察组件线程是否真正忙、是否等待网络/数据库、磁盘是否饱和，以及下游连接池能提供多少并发。一个慢 HTTP 目标不一定需要整个集群扩容，可能需要合理的超时、限流和幂等重试。

Content 和 Provenance 写入共享盘时，大量血缘事件可能与业务内容争用 I/O；反过来，过度缩短保留也会降低诊断能力。应按恢复需求和敏感数据政策设保留，不从一个固定“最佳值”复制到全部环境。

## 6. 练习与答案

**问题一：Primary Node 故障后，其他节点是否自动获得它所有排队内容？**

答案：不是。角色可重新选举，但队列与内容的持久化、存储可接管性和恢复方式需要单独保证。

**问题二：Kubernetes 的 Lease 与 ConfigMap 在这里分别做什么？**

答案：前者用于相应选举实现，后者可用于共享组件状态；都不是保存大批内容字节的 Repository。

**问题三：净增 4 MiB/s、20 GiB 空间能撑约 85 分钟，为什么只是乐观估算？**

答案：它未扣除其他仓库、日志、归档、空间余量和峰值输入，实际可用窗口更短。

**问题四：把 FlowFile Expiration 改短，是否无损解决积压？**

答案：不是。它可能丢弃过期数据，必须把数据时效与业务丢弃策略明确批准，而不是当作性能优化。
