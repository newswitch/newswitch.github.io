# NiFi 部署、Java、TLS 与身份权限

NiFi 可以访问文件、数据库、消息系统和远端 API，因此它的管理界面接近一个具有数据访问能力的控制台。部署时不能只追求浏览器能打开，还要保证谁能登录、谁能改流程、谁能读内容。本篇基线为 **2.12.0、Java 21**。

## 1. 下载与运行前检查

从 Apache 官方渠道下载 2.12.0 发行物，校验签名/摘要，并检查所需组件是否包含在包中。使用专用非 root 账号，安装程序目录与可写数据目录分别授权。先阅读第 2—3 节并完成敏感密钥与访问配置，再执行启动命令。

```bash
export NIFI_HOME=/opt/nifi-2.12.0
java -version
test -x "$NIFI_HOME/bin/nifi.sh"
df -h
ulimit -n
"$NIFI_HOME/bin/nifi.sh" run
```

前台运行便于观察首次启动。稳定后可用同一脚本 `start`、`status`、`stop` 或受控服务管理器管理，不要让两种方式同时启动同一套目录。Java 能执行不代表版本正确，应检查输出确实为经过验证的 Java 21 环境。

## 2. 配置与数据分别存在哪里

`conf/nifi.properties` 描述运行配置；`conf/flow.json.gz` 保存流程定义；Repository 保存运行数据与历史；日志在 `logs/`，可能因服务管理方式重定向。

`nifi.sensitive.props.key` 用来保护流程中的敏感属性。按该版本要求生成并安全保存强密钥，首次启动前配置；不要把它当成普通可随时轮换的日志标签。丢失密钥后，即使流程文件还在，也可能无法解密原有敏感配置。轮换应按官方迁移工具和步骤验证。

运行盘要为 Content、FlowFile、Provenance 等留出容量。它们即使配置到不同路径，若落在同一物理盘，I/O 竞争和空间故障域仍相同。

## 3. HTTPS、认证、授权是三件事

TLS 加密连接并验证对端身份；登录机制识别用户；授权策略决定用户能对哪些资源做什么。一个能用 HTTPS 打开的页面，不代表所有访问者都拥有合理权限。

本地试用保留发行包的回环地址与 HTTPS 设置。首次生成的单用户凭据可能出现在日志中，只在受控终端查看，不截图发布。生产接入应配置可信证书与身份源，区分流程修改、启动停止、查看队列内容与管理用户等权限。

证书 SAN 要包含实际访问的 DNS 名，客户端信任链必须匹配。不要长期用跳过证书验证来掩盖主机名或 CA 问题；证书与私钥也不应打进公开镜像。

## 4. 通过代理访问为什么容易失败

反向代理会改变 Host、协议和路径，NiFi 还需要识别外部地址与允许的代理上下文。只加一条 TCP 转发规则，可能登录成功但重定向到错误地址，或因为代理头与安全设置不一致被拒绝。

先验证本机 HTTPS，再验证代理链；按官方代理配置使用受信代理和正确外部域名。只允许预期 Host/上下文，不把任意来源伪造的转发头当成可信身份。集群代理还要检查会话与请求路由要求。

## 5. 从能启动到可维护

记录版本、JDK、NAR、证书到期时间、敏感密钥保管位置、目录挂载与权限。备份流程与配置时保护秘密；备份运行数据时采用一致性策略，不能把不断变化的几个 Repository 随意复制后认定一定可恢复。

容器重新创建后还要保留合适的持久卷、身份和配置，不能只持久化安装目录。集群端口、Site-to-Site、管理 HTTPS 的用途不同，按部署需求开放到可信源，不需要对公网全部开放。

## 6. 练习与答案

**问题一：浏览器提示证书不受信，是否应关闭 HTTPS？**

答案：不应。检查域名、SAN、CA 链和客户端信任配置，修复身份校验，而不是取消加密和认证保护。

**问题二：为什么只备份 flow.json.gz 仍可能恢复失败？**

答案：还需要敏感属性密钥、组件与服务配置等；要恢复在途数据还需一致的 Repository 与运行状态。

**问题三：安装 Java 8 后能否按本文运行 NiFi 2.12.0？**

答案：不能。本文版本要求 Java 21，不应沿用旧版 NiFi 的运行环境结论。

**问题四：三个 Repository 在同一硬盘的不同目录，是否实现了 I/O 隔离？**

答案：没有。路径不同不等于设备与故障域不同，仍会竞争吞吐、IOPS 和空间。
