# NiFi 日志、故障恢复与版本迁移

NiFi 排障应先确定“没启动”“没被触发”“取不到输入”“处理失败”还是“写出后没有确认”。这些现象在界面上都可能表现为没有输出，但对应的修复完全不同。本篇使用 **2.12.0** 的概念与目录。

## 1. 组件没有输出，先检查什么

| 现象 | 优先检查 | 不应立即做 |
| --- | --- | --- |
| 组件 Invalid | 必填属性、服务引用、关系是否连接 | 重启整个集群 |
| 有效但未运行 | 运行状态、调度时间、主节点限制 | 假定输入系统故障 |
| 运行但输入不减 | 下游背压、Penalty、线程等待 | 清空队列 |
| failure 增长 | 解析、schema、权限、目标响应 | 无限零延迟重试 |
| 目标有数据但任务失败 | 外部提交与本地确认边界 | 直接全量重放 |

先看组件 Bulletin、状态历史、队列年龄与关系分布，再关联日志。绿色运行图标不表示每次执行都成功，自动终止的关系也可能使错误数据不再排队。

## 2. 日志分别能说明什么

常见日志包括应用日志 `nifi-app.log`、启动/进程管理日志 `nifi-bootstrap.log`、认证与授权相关日志 `nifi-user.log`。最终文件位置由日志配置决定。有限查看命令如下：

```bash
"$NIFI_HOME/bin/nifi.sh" status
tail -n 150 "$NIFI_HOME/logs/nifi-bootstrap.log"
tail -n 200 "$NIFI_HOME/logs/nifi-app.log"
df -h
```

根据同一时间窗口、组件 ID、节点和业务键串联证据。启动密码、Token、内容、SQL 参数可能敏感，不能为了方便把全部配置与 payload 开成公开日志。

## 3. 重试要区分暂时错误与永久错误

目标 429、临时网络超时与数据库暂时锁等待，通常需要受控退避和次数/时长限制；字段不合法、证书主机名错误、权限拒绝则需要修正契约或环境。把所有错误都立即返回输入，会在故障时放大外部压力。

对超时还要判断远端是否可能已经完成。HTTP 无响应不等于服务端没执行，SQL 客户端超时也不等于事务一定回滚。查幂等键与目标提交状态，再决定重放，而不是只根据 NiFi 的 failure 数推算成功数。

## 4. 流程版本管理不等于运行数据备份

版本化流程保存的是可审阅的配置变化，适合比较处理器、关系、参数引用与服务定义。它通常不包含全部在途内容、组件运行状态、外部数据和秘密，因此无法替代 Repository 与配置的恢复方案。

NiFi 2.x 的版本存储通过相应 Registry Client 等能力接入，具体实现与插件需按所选版本验证，不应把某个旧 Registry Server 的部署方式当成所有版本唯一答案。也不能把 Git 中的流程文件当成存有实时队列的快照。

## 5. 升级验收与回退边界

固定旧新 NiFi、JDK、NAR、驱动和外部服务版本；检查被移除/替换的 Processor、属性默认值、Record 解析变化及 Repository/状态兼容。先在独立环境导入脱敏流程并补齐参数、证书与服务引用，再运行固定测试输入。

切换前明确如何处理旧队列：安全排空、保留旧节点处理，还是按验证过的方式迁移。不能随意复制单个 Repository 到另一版本后直接运行。回退时也要防止新旧流程同时消费或写同一目标，检查重复、版本顺序和敏感配置是否可解密。

## 6. 练习与答案

**问题一：组件 Invalid，第一步是否重启 NiFi？**

答案：不是。先检查必填属性、Controller Service、参数引用与未处理关系，重启不会修复无效配置。

**问题二：目标超时后为何不能直接认定请求未执行？**

答案：响应可能丢失而外部操作已经提交；需结合目标状态和幂等键判定，防止重试产生重复副作用。

**问题三：流程已保存到版本库，是否等于队列有备份？**

答案：不是。版本库保存流程配置，运行内容、状态和秘密需要独立且一致的保护与恢复验证。

**问题四：升级后新旧流程能否同时写同一张表验证？**

答案：不能无条件这样做。它可能造成重复、旧值覆盖和消费竞争，应使用隔离目标或明确的影子验证设计。
