# Airbyte Schema 演进、类型与数据校验

同步没有报错，只说明一条执行路径结束了；不说明字段都被选择、类型没改变、重复已处理或目标结果可供业务使用。本篇依据 **2026-11-14 官方类型与同步文档**，建立独立于绿色状态的数据验收方法。

## 1. Schema 变化经过几道门

源端增加一列之后，连接器要重新发现，Connection 要按策略接受与选择，数据通路要能表达，Destination 还要把它映射为目标字段。任意环节拒绝或延后，都会造成“源已有列，目标看不到”。

新增可空字段、删除字段、改名、收窄长度、改为不可空和改变主键不是同一种风险。rename 可能被识别为删除加新增，旧字段值不会自动迁到新列。生产应明确自动接受哪些变化、哪些必须暂停和人工评估。

## 2. JSON schema 不等于目标数据库类型

Airbyte 用协议类型描述数据，目标存储还受数据库范围与精度约束。一个协议上可表示的整数或日期，目标可能无法存储；嵌套对象也可能被展开、序列化或保留为 JSON，行为由目标连接器决定。

```json
{
  "type": "object",
  "properties": {
    "order_id": {"type": "integer"},
    "amount_text": {"type": ["null", "string"]},
    "updated_at": {"type": "string", "format": "date-time"}
  },
  "required": ["order_id", "updated_at"]
}
```

这是用于说明的字段契约片段，不是完整 Airbyte API 请求。amount_text 允许显式 NULL，也允许字段缺失；order_id 与 updated_at 则要求存在。生产还要约定金额字符串格式、主键唯一与时间含义，JSON 类型本身没有覆盖这些业务约束。

## 3. 四类边界样本不能省

金额用大值、负数、多位小数和 NULL；时间用时区偏移、跨日、微秒与夏令时边界；字符串用前导零、多字节字符、空串和超长值；嵌套结构用空数组、缺失字段、显式 NULL 与复杂对象。

例如客户号 `00123` 若按整数传输，前导零不可逆丢失；金额若先进入精度不足的浮点表示，再写 DECIMAL，目标小数类型也无法自动找回已丢精度。应从源序列化开始保护契约，而不是只改目标列。

## 4. 校验不能只比 count

在同一稳定数据范围内核对：总行数、唯一业务键、重复键、NULL 分布、金额十进制合计、时间范围和抽样字段。对持续变化源，先确定一致快照或可对照窗口，否则源目标在不同时间测得的差值未必是漏数。

按 Stream、日期和业务键分桶对比，比单个全表 count 更容易定位问题。更新和删除需要独立测试，CDC 还要比较从日志到目标可见的延迟，以及重放后的最终结果。

## 5. 拒绝记录与目标内部表

某些目标会把类型错误、解析失败或不支持值记录在元数据/错误结构中，另一些会使任务失败；具体策略需查目标版本。不能认为目标有最终表就没有被拒绝记录，也不能在缺少依据时假定所有错误都被静默吞掉。

目标内部原始表、最终表、元数据字段与去重实现可能随连接器版本演进。对外查询应依赖经过约定的业务表或视图；排查时记录实际元数据，但不把历史教程里的内部字段当成所有目标的永久 API。

## 6. 练习与答案

**问题一：源和目标行数一样，为什么仍可能漏数？**

答案：可能漏一行又重复另一行，或同键多版本抵消；还可能字段、金额、时间已改变，所以需要键集合和字段校验。

**问题二：金额进入浮点后再转 DECIMAL，精度一定恢复吗？**

答案：不能。早期序列化丢失的信息无法由目标类型自动补回，应核对整个转换链和边界样本。

**问题三：源列改名，目标是否自然保留原列历史并迁移？**

答案：不保证。连接器可能视为删旧加新，需要明确变更、回填与查询兼容方案。

**问题四：Schema 中允许 NULL，是否也表示字段必然存在？**

答案：不是。是否存在由 required 等约束表达；字段缺失和字段值为 NULL 应分别约定并测试。
