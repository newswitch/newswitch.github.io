# 数据系统学习地图

数据系统解决的不是同一个问题。关系数据库保存事务事实，缓存降低访问延迟，消息系统传播变化，搜索和向量数据库提供不同形式的检索，OLAP 与大数据平台承担规模化分析和计算。学习时先理解每类系统的职责和数据一致性边界，再深入具体产品。

## 2. 一条数据如何经过不同系统

```text
业务请求
  │
  ├─ 同步事务 ───────────────→ MySQL / PostgreSQL
  │                               │
  ├─ 低延迟读取 ←────────────── Redis
  │                               │
  └─ Binlog / WAL / Outbox ───→ Kafka / RocketMQ
                                  │
                  ┌───────────────┼────────────────┐
                  ▼               ▼                ▼
           Elasticsearch       Milvus      ClickHouse / 数据湖
             全文搜索          向量检索       分析与离线计算
```

关系数据库通常保存权威事务状态。Redis、Elasticsearch、Milvus 和分析系统多为可以重建的派生视图，Kafka/RocketMQ 则把源端变化可靠地传播给下游。系统设计必须明确谁是事实源、数据如何传播、允许多大延迟、重复事件如何幂等处理，以及派生数据损坏后怎样重建。

## 3. 分类边界

- MySQL/PostgreSQL 保存事务事实，所以属于关系数据库，不属于大数据工程。
- Redis 的主问题是低延迟内存访问、缓存与临时状态，所以归入缓存。
- Kafka/RocketMQ 负责事件传输、缓冲与重放，所以归入消息与事件。
- Elasticsearch 面向倒排、全文与混合搜索；Milvus 面向大规模向量检索，两者的数据模型和索引目标不同。
- ClickHouse、Trino、Doris 面向列式聚合、MPP 和交互式分析，但存储计算关系与适用场景并不完全相同。
- Hadoop、Spark、Flink、Iceberg、Airflow 与数据治理共同构成大数据工程主线。

一个组件可能参与多条链路，但核心职责仍要明确。例如 Kafka 经常出现在大数据平台中，它首先解决的仍是事件日志、缓冲、顺序、重放和消费者解耦问题。

## 4. 推荐学习顺序

1. 先学 MySQL 或 PostgreSQL，建立表、索引、事务、锁、日志和恢复基础；
2. 再学 Redis，理解缓存模式、数据一致性、穿透/击穿/雪崩和持久化边界；
3. 学习 Kafka 或 RocketMQ，掌握分区、顺序、投递语义、幂等和消息积压；
4. 根据业务进入 Elasticsearch 或 Milvus，理解文本检索与向量检索的差异；
5. 学习 ClickHouse、Trino、Spark 和 Flink，建立批处理、流处理和 OLAP 模型；
6. 最后串联 CDC、缓存更新、搜索索引、实时数仓和数据湖治理。

单项产品掌握后，再阅读[数据库、缓存、消息、搜索、控制面与网关学习地图](../learning/02-数据库缓存消息搜索控制面与网关学习地图.md)，理解一次业务写入怎样从网关进入 MySQL/PostgreSQL，经 Kafka/RocketMQ 传播，再构建 Redis、Elasticsearch、ClickHouse 或 Milvus 派生视图。
