# 主流数据库数据保护方案选型

不同数据库的“数据”不只是表文件。元数据、事务日志、分片目录、集群身份、对象存储和协调服务可能分布在多个组件中。选型时先确定事实源和恢复对象，再选择工具。

## 1. 通用选型框架

对每个系统回答：

1. 权威数据、派生数据和缓存分别是什么；
2. 一次成功写入由哪些副本或多数派确认；
3. 本地 Crash Recovery 使用什么日志；
4. PITR 是否需要连续日志，位置怎样标识；
5. 备份包含数据、Schema、用户、权限和集群元数据中的哪些；
6. 备份能否在新主机、新集群、另一个账号和地域恢复；
7. 恢复是否要求相同大版本、插件、页格式或对象存储布局；
8. 哪些状态可以从权威源重建，重建需要哪些 Offset 和 Schema；
9. 实际 RPO、RTO、容量和业务校验是什么；
10. 备份被恶意删除时还有哪一份不可变副本。

## 2. 方案总览

| 系统 | 在线高可用 | 恢复基线 | 连续恢复信息 | 关键边界 |
| --- | --- | --- | --- | --- |
| MySQL | 异步/半同步、Group Replication/InnoDB Cluster | 物理备份、逻辑备份、快照 | Binlog、GTID/Position | Redo 负责 InnoDB 崩溃恢复，Binlog 支撑复制/PITR |
| PostgreSQL | Streaming Replication、同步 Standby、HA 控制器 | `pg_basebackup`、pgBackRest/WAL-G、逻辑转储、快照 | WAL、LSN、Timeline | Base Backup 后 WAL 必须连续，Slot 可能撑满磁盘 |
| Redis | Replica、Sentinel、Cluster | RDB、AOF、文件/云备份 | AOF 与复制 Offset | 异步复制和 AOF 策略决定数据损失窗口，缓存应优先可重建 |
| Elasticsearch | Primary/Replica、跨集群复制 | Snapshot Repository | Snapshot 增量引用、CCR History | 不能备份节点 Data Path 代替 Snapshot API |
| Milvus | 组件副本和底层对象存储冗余 | Milvus Backup/厂商能力、对象存储保护 | 元数据与对象版本 | 元数据、对象存储和消息状态必须匹配 |
| ClickHouse | ReplicatedMergeTree、Keeper | `BACKUP/RESTORE`、对象存储/工具 | Part、Mutation、Keeper 元数据 | Replication 不是历史备份，分布式表元数据也要恢复 |
| etcd | Raft 多数派 | `etcdctl snapshot save` 或存储快照 | Revision、Raft/WAL 由恢复流程处理 | Snapshot 恢复会形成新逻辑集群，Kubernetes Watch 需 Revision Bump |

## 3. MySQL

常见自建组合：

```text
主库 + 跨故障域半同步/Group Replication
+ MySQL Router/ProxySQL/HAProxy
+ MySQL Enterprise Backup 或匹配版本的 XtraBackup
+ 连续 Binlog 归档
+ 对象存储不可变副本
```

小库或对象级恢复增加 `mysqldump`/MySQL Shell Dump。多 TiB 数据库以物理备份为主，Binlog 提供基线之后的 PITR。

检查重点：

- `sync_binlog`、InnoDB 刷盘和半同步 ACK 点；
- Backup 与 GTID/Binlog Position 是否绑定；
- 增量链的父备份、Prepare 和版本兼容；
- 备份是否包含用户、事件、触发器、存储过程和配置；
- 误删恢复是否在隔离实例完成。

专项入口：[MySQL 备份、恢复与安全](../databases/mysql/07-backup-security/01-备份不是复制-RPO-RTO一致性与保留策略.md)。

## 4. PostgreSQL

常见自建组合：

```text
Primary + Streaming Replication
+ 同步 Standby（核心库）
+ Patroni/同类 HA 控制与可靠 DCS
+ pgBackRest、WAL-G、Barman 或 pg_basebackup
+ 连续 WAL Archive
+ PITR 与 Timeline 管理
```

`pg_dump`/`pg_restore` 适合对象级和跨版本迁移，物理 Base Backup + WAL 更适合大库完整恢复。PostgreSQL 18 的 `pg_basebackup` 已支持基于 WAL Summary 的增量备份，但版本、备份 Manifest、前序备份和 WAL 要求必须按实际环境验证。

检查重点：

- `archive_command`/Archive Library 是否持续成功；
- 最新 Archived LSN，而不是只看 Base Backup 时间；
- Replication Slot 的 `restart_lsn` 和磁盘保留上限；
- Tablespace、Extension、角色和配置文件；
- 恢复目标、Timeline 和旧主隔离。

专项入口：[PostgreSQL WAL、备份与 PITR](../databases/postgresql/16-pg_dump-pg_basebackup-WAL归档与PITR.md)。

## 5. Redis

先判断 Redis 是缓存还是权威数据源：

- 纯缓存：重点是容量保护、限流和从数据库/事件流重建；
- Session/队列/计数等重要状态：必须定义 RPO，配置 AOF/RDB、复制和外部备份；
- Redis Streams：还要保护 Consumer Group、Pending 和业务幂等状态。

```text
RDB：周期快照，恢复快但存在快照间隔损失
AOF：记录写命令，fsync 策略决定窗口
Replica/Sentinel/Cluster：高可用和扩展，不是历史备份
```

从在线节点复制 RDB/AOF 时要理解原子替换、AOF Rewrite 和父子进程。直接复制正在写入的临时文件可能得到不可用工件。

专项入口：[Redis RDB、AOF 与 Copy-on-Write](../cache/redis/07-Redis-RDB-AOF-fork与Copy-on-Write.md)。

## 6. Elasticsearch

Elasticsearch 应使用 Snapshot API 写入注册的 Repository。Snapshot 由集群协调 Shard 数据和元数据，并可能跨快照复用不可变 Segment；不能暂停一个节点后复制 Data Path 作为标准集群备份。

需要明确：

- Snapshot 是否包含所需 Data Stream、Index、Cluster State 和 Feature State；
- Repository 是否可被多个集群安全访问，写入权限是否唯一；
- Snapshot Lifecycle Management 的失败与保留；
- 恢复时 Index Template、ILM、Security 状态和版本兼容；
- CCR 用于在线灾备，但删除和错误写入仍可能传播。

搜索索引若可从关系数据库/Kafka 重建，也要备份 Mapping、Analyzer、Template、Pipeline、源 Offset 和重建程序。

专项入口：[Elasticsearch Snapshot、Restore 与 CCR](../search/elasticsearch/15-Snapshot-Restore-CCR与跨集群灾备.md)。

## 7. Milvus

Milvus 是多组件系统，恢复不能只看到对象存储中存在 Segment：

```text
对象存储中的 Segment/Index
+ 元数据服务中的 Collection/Partition/Segment 状态
+ 消息/时间戳相关恢复边界
+ 配置、用户和依赖组件
```

使用 Milvus Backup 或目标发行版支持的备份机制时，需要核对版本兼容、Collection 范围、对象存储路径和恢复后索引状态。底层对象存储的版本化与跨地域复制是额外保护，不自动成为一致的 Milvus 恢复点。

若向量库是派生视图，还应保留原始文档、Chunk 规则、Embedding 模型版本、标量字段 Schema 和重建 Offset，否则“重新嵌入”可能得到不同结果。

专项入口：[Milvus 备份、升级与迁移](../vector-databases/milvus/14-Milvus备份升级迁移安全与多租户.md)。

## 8. ClickHouse

ClickHouse 数据常按 Shard 和 Replica 分布。ReplicatedMergeTree 可以修复副本故障，但不会为错误 `DELETE`、Mutation 或 TTL 保留历史恢复点。

备份需要包括：

- Database/Table/View/Dictionary 等 DDL；
- Data Part 与分区；
- 用户、角色、配额和设置；
- Distributed/集群配置；
- Keeper 中与复制相关的元数据边界；
- 对象存储凭据和加密密钥。

使用原生 `BACKUP/RESTORE` 或生态工具时，核对目标 Disk、并发、增量 Base Backup、冻结/上传期间的资源，以及恢复到新集群后的 Shard/Replica 名称。

专项入口：[ClickHouse 备份恢复与故障 Runbook](../analytics/clickhouse/14-备份权限配额升级与生产故障Runbook.md)。

## 9. etcd

etcd Snapshot 保护键值和 MVCC 状态，不应把三成员数据目录分别复制后混合。恢复通常从一个已验证 Snapshot 创建新的逻辑集群，再重新配置所有成员。

Kubernetes 恢复还要处理：

- API Server 与 etcd 证书、Endpoint 和版本；
- 恢复点之后创建/更新的 Kubernetes 对象；
- Informer/Watch 对旧 Revision 的缓存假设；
- 外部 PV、云负载均衡和 Secret/KMS 等不在 etcd 内的数据；
- Revision Bump 与 Mark Compacted，促使控制器重新 List。

专项入口：[etcd Snapshot、Restore 与 Revision Bump](../../cloud-native/etcd/08-etcd-Snapshot-Restore-Revision-Bump与灾难恢复.md)。

## 10. 托管数据库

托管服务通常提供：

```text
Multi-AZ/Zone Redundancy
自动故障切换
自动全量/增量备份
连续日志和 PITR
跨地域备份复制
长期保留
KMS 加密与审计
```

“托管”不等于无需设计。仍要确认：

- PITR 是否默认启用、保留多长、最新可恢复时间是什么；
- 自动备份与实例删除的保留关系；
- 备份位于本地、区域还是跨地域存储；
- 账号被删除或入侵时能否跨账号恢复；
- KMS Customer-managed Key 被禁用后的影响；
- Snapshot 导出是否保留数据库事务语义；
- 恢复到新实例后的网络、参数组、扩展和权限；
- 服务承诺的 RPO/RTO 是否满足业务，而不是只看“高可用”标签。

## 11. 工具选型验证方法

不要只比较是否支持“全量/增量”。用同一套试验对候选工具评分：

1. 目标数据库版本、插件和平台兼容；
2. 在线备份期间 P99、IOPS、CPU 和复制延迟变化；
3. 备份吞吐、压缩率、增量变化率和对象数量；
4. 备份中断后的重试、断点续传和临时对象清理；
5. Checksum、签名、加密和 KMS 权限；
6. 缺失增量、日志段或对象时能否明确失败；
7. 跨账号、跨地域和新集群恢复；
8. 恢复吞吐、日志 Replay 和完整 RTO；
9. 数据库、数据和业务校验；
10. 监控指标、告警、审计与自动保留策略。

## 12. 最终方案模板

```yaml
system: <database-or-data-system>
data_role: source-of-truth | derived | cache
owner: <team>
rpo:
  node_failure: <duration>
  zone_failure: <duration>
  region_failure: <duration>
  logical_corruption: <duration>
rto:
  node_failure: <duration>
  region_failure: <duration>
ha:
  replication_mode: <sync-async-quorum>
  failure_domains: <description>
  fencing: <mechanism>
backup:
  base: <tool-and-frequency>
  logs: <archive-and-lag-target>
  immutable_copy: <location-and-retention>
recovery:
  catalog: <location>
  isolated_target: <method>
  validation: <checks>
  last_drill: <timestamp-and-result>
```

只有当模板中的目标由监控和演练数据支持，方案才从“部署了工具”变成可证明的数据保护能力。
