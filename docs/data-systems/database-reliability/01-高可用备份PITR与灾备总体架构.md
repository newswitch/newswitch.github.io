# 高可用、备份、PITR 与灾备总体架构

可靠的数据保护方案不是在主库旁边增加一个副本，而是让不同机制分别处理不同故障。设计起点应是业务损失和故障域，终点则是经过演练证明的恢复能力。

## 1. 四类目标不要混淆

| 目标 | 核心问题 | 常用机制 |
| --- | --- | --- |
| 持久性 | 成功提交的数据已写到哪里 | Redo/WAL、fsync、同步复制、校验 |
| 高可用 | 当前节点失效后谁继续服务 | Standby、选主、代理、Fencing |
| 可恢复性 | 数据错误后怎样回到正确状态 | 全量/增量备份、事务日志、PITR |
| 灾难恢复 | 整个故障域丢失后怎样恢复 | 跨地域副本、异地备份、恢复编排 |

复制追求最新，备份保留历史。两者方向不同，因此必须同时存在。

## 2. 先定义故障模型

```text
进程异常、OS 重启
单盘或存储控制器损坏
服务器、机架或交换机故障
可用区/机房不可用
地域级灾难
误删、错误 DDL、应用 Bug
数据库页或索引逻辑损坏
管理员凭据泄露、勒索加密
备份损坏、密钥丢失、恢复版本不兼容
```

“多副本”通常只覆盖其中一部分。误删和恶意操作会被复制，地域副本也可能接收到错误数据；同一存储阵列上的多个虚拟机也未形成真正独立的故障域。

## 3. 分层保护架构

```text
                         ┌──────── 只读副本：扩展查询
                         │
应用 → 数据库端点/代理 → 主库 ───── 同步 Standby：主机/AZ 故障接管
                         │
                         ├──────── 延迟副本：短窗口逻辑错误止损
                         │
                         ├──────── 连续 Binlog/WAL：秒/分钟级 PITR
                         │
                         └──────── 周期物理备份：恢复基线
                                            │
                                跨账号不可变对象存储
                                            │
                                  跨地域复制与冷归档
```

数据面之外还需要一个独立恢复控制面：备份目录、校验和、数据库版本、日志起止位置、密钥标识、恢复脚本、网络和账号。生产系统全部消失时，不能依赖生产系统内部的任务和密钥启动恢复。

## 4. RPO 与 RTO

**RPO（Recovery Point Objective）**表示允许回退多远。若事故发生在 12:00，最新可靠恢复点是 11:55，实际数据损失窗口约为 5 分钟。

**RTO（Recovery Time Objective）**表示多久恢复业务。它不只是复制数据的时间：

```text
RTO = 发现与决策
    + 准备计算/存储/网络
    + 下载或挂载备份
    + 解密、解压、prepare
    + 重放事务日志
    + 数据和业务校验
    + 切流与客户端恢复
```

RPO/RTO 应按数据等级定义，而不是整家公司统一一个数字。例如：

| 数据等级 | 示例目标 | 典型成本 |
| --- | --- | --- |
| 核心交易 | 同城故障 RPO 0、分钟级 RTO | 跨故障域同步复制、热 Standby |
| 一般业务库 | RPO 1～5 分钟、RTO 1 小时 | 异步副本、连续日志归档 |
| 内部报表 | RPO 24 小时、RTO 8 小时 | 周期备份、低成本恢复资源 |
| 可重建派生数据 | 由源数据重放决定 | 保留 Schema、Offset、构建程序和源数据 |

表中数值只是示例，真正目标应由业务影响、法规和预算共同决定。

## 5. 成功提交到底意味着什么

不同参数下，客户端收到 `COMMIT OK` 时的持久化边界不同：

```text
进程内存
→ OS Page Cache
→ 主库持久介质
→ 副本内存
→ 副本持久介质
→ 副本已回放并可读
```

同步复制也有不同确认点：收到日志、写入操作系统、刷入持久介质或已经回放。保护越强，提交路径越长，延迟和对副本可用性的依赖越高。设计时必须把“同步”翻译成具体 ACK 条件。

## 6. 不同故障怎样恢复

| 故障 | 第一恢复路径 | 为什么不能只靠另一种机制 |
| --- | --- | --- |
| 进程崩溃 | Redo/WAL Crash Recovery | 备份太慢，副本切换未必必要 |
| 主机/磁盘故障 | 同步或低延迟 Standby 接管 | 从备份恢复通常无法满足分钟级 RTO |
| 错误更新/误删 | 隔离恢复实例执行 PITR | 副本会复制错误事务 |
| 页面损坏 | 隔离坏节点，从健康副本或备份重建 | 未确认损坏范围前不能盲目提升副本 |
| 可用区故障 | 跨可用区副本和自动/受控切换 | 同区快照可能一起不可用 |
| 地域故障 | 跨地域副本或异地备份恢复 | 同地域 Multi-AZ 不覆盖地域故障 |
| 勒索/越权删除 | 跨账号不可变或离线备份 | 在线副本和普通备份可能同时被删除 |

## 7. 为什么 RAID、快照和副本都不是完整备份

- RAID 降低单盘故障影响，但无法防止误删、数据库逻辑损坏和整机丢失；
- 存储快照能快速复制块状态，但需要确认数据库一致性、快照故障域和保留权限；
- 数据库副本持续接收变化，错误和恶意操作同样会传播；
- 延迟副本只有有限时间窗口，且延迟任务可能被错误地继续推进；
- CDC 保存变化事件，但其保留、Schema、事务边界和下游处理不一定满足数据库恢复要求。

## 8. 恢复时坚持“新环境恢复”

除明确支持且经过验证的原地恢复外，优先恢复到隔离的新实例：

```text
冻结现场与备份保留策略
→ 选择早于事故的可验证基线
→ 创建隔离恢复实例
→ 重放到目标事务之前
→ 物理一致性检查
→ 业务不变量和权限检查
→ 决定整库切换或对象级回灌
→ 保留旧现场直到复盘完成
```

直接覆盖原实例会破坏取证材料，也会失去更换恢复点和重新执行的机会。

## 9. 生产验收清单

- [ ] 每类数据库都有明确 Owner、RPO、RTO 和最长保留期；
- [ ] 同步/异步复制的确认点和故障域已经记录；
- [ ] 全量基线与连续事务日志可以接续；
- [ ] 备份位于独立账号或权限域，关键副本不可变；
- [ ] 备份目录包含版本、校验和、日志位置和密钥标识；
- [ ] 监控最新可恢复点年龄，而不是只看任务成功；
- [ ] 定期从真实备份恢复到新环境并运行业务校验；
- [ ] 已演练单节点、可用区、误删、日志缺口和凭据泄露场景；
- [ ] DNS、代理、连接池和旧主 Fencing 纳入切换步骤；
- [ ] 实测恢复耗时满足 RTO，而不是用理论带宽估算后结束。
