# 备份容量、恢复吞吐与灾难恢复演练

“每天备份成功”只能证明任务退出状态，不能证明目标 RPO、RTO 和数据正确性。容量和恢复时间必须用实际数据量、日志生成速率、共享瓶颈和验证步骤计算，再通过真实恢复校准。

## 1. 建立工作负载画像

规划前收集：

- 当前逻辑数据量、物理数据量和索引比例；
- 每日新增、更新、删除与压缩后的变化量；
- 峰值/平均 Binlog、WAL 或其他事务日志速率；
- 全量与增量备份压缩率、去重率和对象数量；
- 源盘顺序读吞吐、备份网络、对象存储写吞吐；
- 目标恢复盘写吞吐、IOPS、CPU 解压/解密能力；
- 数据库启动恢复和日志 Replay 速度；
- 业务校验、索引重建、统计信息和切流时间。

不能用厂商标称带宽代替有效吞吐。生产业务、压缩、TLS、校验和、限速、多租户和小文件会共同降低速度。

## 2. 备份容量模型

设：

- `D`：当前物理全量大小；
- `c_full`：全量压缩后比例；
- `Δi`：第 i 个周期变化量；
- `c_inc`：增量压缩后比例；
- `L`：事务日志平均字节率；
- `T_log`：日志保留秒数；
- `R`：跨地域/跨账号副本数；
- `m`：Manifest、校验、临时对象和安全余量。

简化估算：

```text
capacity ≈ [D × c_full × full_set_count
          + Σ(Δi × c_inc)
          + L × T_log] × R × (1 + m)
```

还需要预留：

- 备份写入中的临时文件；
- 合成全量同时存在的新旧版本；
- 生命周期删除延迟；
- 恢复演练产生的临时副本；
- 数据库异常导致日志暴涨；
- Object Versioning 保留的旧版本和 Delete Marker。

## 3. 备份窗口

```text
backup_time ≈ bytes_to_read / min(source_read, network, cpu_encode, target_write)
```

这只是下界。真实备份还包括扫描、锁协调、日志追赶、分片合并、对象提交、校验和目录生成。

若 8 TiB 数据以 600 MiB/s 的有效吞吐读取：

```text
8 TiB / 600 MiB/s ≈ 3.9 小时
```

如果生产低峰只有 2 小时，方案必须采用并行、从副本备份、增量/快照或更高吞吐，而不是仅修改 Cron 时间。

## 4. RPO 看最新连续恢复点

需要区分：

```text
最后一次 Backup Job 成功时间
最后一个完整基线时间
最新连续日志归档位置
最新完成校验的位置
最新完成恢复演练的位置
```

例如今天全量任务成功，但最近 30 分钟 Binlog 归档中断，则 PITR 最新恢复点仍停在 30 分钟前。监控应直接输出“Latest Recoverable Point Age”。

## 5. RTO 是一条关键路径

恢复时间通常为：

```text
T_detect       发现和确认事故
T_provision    创建主机、存储、网络、账号与密钥权限
T_fetch        获取备份
T_prepare      解密、解压、合并增量、应用备份期日志
T_replay       重放到目标位置
T_startup      数据库启动与内部恢复
T_validate     物理、逻辑和业务校验
T_cutover      代理、DNS、应用和连接池切换
T_redundancy   重建副本与重新建立备份链
```

对业务恢复的 RTO 通常计算到 `T_cutover`，但事故关闭还必须包括 `T_redundancy`。刚恢复的单节点数据库仍处于高风险状态。

## 6. TiB 数据库示例 {/* #6-10-tib-数据库示例 */}

假设：

```text
备份压缩后 6 TiB
对象存储到恢复节点有效吞吐 1.2 GiB/s
解密/解压/写盘综合吞吐 900 MiB/s
需要重放 800 GiB 日志，Replay 350 MiB/s
准备资源 20 分钟，启动和校验 45 分钟
```

关键路径近似：

```text
恢复基线 ≈ 6 TiB / 900 MiB/s ≈ 1.94 小时
日志重放 ≈ 800 GiB / 350 MiB/s ≈ 39 分钟
总计 ≈ 20 分钟 + 1.94 小时 + 39 分钟 + 45 分钟
     ≈ 3.6 小时
```

若业务要求 RTO 2 小时，仅有“6 TiB 备份可下载”并不合格。可选改进包括存储快照、并行恢复、更短增量链、Warm Standby 或减少需要恢复的数据范围。

## 7. 恢复验证金字塔

### 7.1 工件层

- 对象存在、大小和数量符合 Manifest；
- Checksum 和签名正确；
- 全量、增量父链和事务日志连续；
- 解密密钥、证书和账号可用。

### 7.2 数据库层

- 数据库能够启动且恢复日志无异常；
- 页校验、Catalog、表空间和分片完整；
- 角色、权限、Extension、UDF、触发器和调度任务存在；
- 复制身份、Cluster ID、Timeline/Term 不与生产冲突。

### 7.3 数据层

- 库表、分区、行数和关键聚合符合预期；
- 主键、唯一约束、外键或业务关联正确；
- 最大业务时间、流水号和已确认事务边界正确；
- 抽样或分区级 Checksum 通过。

### 7.4 业务层

- 只读查询和关键交易合成测试通过；
- 消息、缓存、搜索索引和下游 CDC 起点可以重新对齐；
- 事故之后的合法写入有保留、回灌或放弃方案；
- 应用连接、TLS、时区、字符集和权限均正确。

## 8. 演练不是在原库执行恢复

建立隔离恢复环境：独立网络、域名、凭据和对象存储前缀，禁止生产应用误连。演练流程：

```text
随机选择真实恢复点
→ 自动创建隔离基础设施
→ 恢复基线和日志
→ 执行分层校验
→ 记录每阶段耗时与资源峰值
→ 删除临时计算资源
→ 保留审计、报告和失败工件
```

每次都使用固定“黄金备份”会掩盖日常链路故障。应从实际保留窗口中随机抽样，并定期恢复最老仍承诺可用的恢复点。

## 9. 故障注入矩阵

| 注入 | 预期发现 | 预期处理 |
| --- | --- | --- |
| 缺失一个增量 | 链校验失败 | 自动退到更早完整链，不继续拼接 |
| 某对象 Checksum 错 | 下载后校验失败 | 尝试独立副本并告警 |
| Binlog/WAL 中间缺段 | 可恢复区间中断 | 阻止声明缺口后的恢复点可用 |
| KMS Key 禁用 | 解密预检查失败 | 启动受控密钥恢复流程 |
| 对象存储限速 | Fetch 时间增加 | 限制并发或切换副本，更新实测 RTO |
| 恢复盘容量不足 | Prepare/Replay 前容量检查失败 | 扩容而不是恢复中途清理 |
| 版本不兼容 | 启动或工具预检失败 | 使用匹配镜像/二进制恢复后再升级 |
| Namespace/集群丢失 | 集群内 CR 与 Secret 不存在 | 从外部目录、Git/IaC 和备份账号重建 |

## 10. 监控与 SLI

至少建设：

- Backup Success Rate；
- Latest Recoverable Point Age；
- Log Archive Lag Bytes/Seconds；
- Backup Size 与变化率异常；
- Checksum/Signature Failure；
- Incremental Chain Depth；
- Immutable Retention Coverage；
- Cross-Region Replication Lag；
- Restore Drill Success Rate；
- Restore RTO 分位数与各阶段耗时；
- 恢复后的业务校验失败数。

告警应指向可执行动作。例如日志归档延迟首先检查归档端吞吐、权限、磁盘积压和对象存储错误，而不是立即删除本地日志释放空间。

## 11. 恢复演练完成标准

- [ ] 使用了生产策略生成的真实备份；
- [ ] 在隔离的新环境完成恢复；
- [ ] 日志重放停止在预期事务边界；
- [ ] 文件、数据库、数据和业务四层校验通过；
- [ ] 实测 RPO、RTO 满足目标；
- [ ] 恢复账号和密钥路径经过验证；
- [ ] 切流、回退和旧主隔离步骤可执行；
- [ ] 失败项形成修复 Owner 和期限；
- [ ] 恢复后重新建立了副本和备份能力。
