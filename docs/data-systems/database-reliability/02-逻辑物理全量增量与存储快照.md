# 逻辑、物理、全量、增量与存储快照

“全量”和“物理”不是一组对立概念。备份方案至少有三个维度：复制什么、复制多少、复制时数据库是否运行。只有先把维度拆开，才能正确比较工具。

## 1. 三个分类维度

### 1.1 复制什么

| 类型 | 复制对象 | 常见形式 |
| --- | --- | --- |
| 逻辑备份 | 表、行、DDL、权限等数据库对象 | SQL、CSV、归档格式 |
| 物理备份 | 数据页、表空间、控制文件、日志和元数据 | 数据目录、块、厂商备份格式 |
| 存储快照 | 卷或文件系统在某时刻的块映射 | LVM/ZFS/云盘/CSI Snapshot |

### 1.2 复制多少

| 类型 | 当前备份包含的内容 | 恢复依赖 |
| --- | --- | --- |
| 全量 | 当前选定范围的全部数据 | 当前全量本身和必要事务日志 |
| 增量 | 自上一个指定备份后变化的数据 | 基线和完整增量链 |
| 差异 | 自最近一次全量后变化的数据 | 最近全量和当前差异备份 |

### 1.3 是否停库

- 冷备份：数据库停止，容易得到稳定文件状态，但产生停机；
- 热备份：数据库继续读写，工具必须同时捕获数据页和恢复所需日志；
- 温备份：部分功能可用或写入受限，需要明确业务影响。

因此“在线物理增量备份”和“离线逻辑全量备份”都可能存在。

## 2. 逻辑备份

逻辑备份通过数据库接口读取对象，再编码成 SQL、行记录或工具归档格式。

优点：

- 可选择库、Schema、表甚至部分行；
- 适合对象级恢复、跨版本迁移和审计；
- 内容可被数据库重新解释，不依赖原始页布局；
- 可以分别恢复 DDL、数据、权限和统计信息。

边界：

- 大库导出和导入耗时长；
- 恢复时需要重新建表、索引、约束和统计信息；
- 并行导出多个对象时必须确认是否共享一个一致性快照；
- 函数、事件、触发器、角色、扩展和全局对象可能需要单独参数；
- 文本可读不等于字符集、排序规则、时区和精度完全兼容。

逻辑备份更像“重新执行一遍数据定义和装载”，不能按备份文件大小直接估算恢复时间。

## 3. 物理备份

物理备份复制数据库原生页和相关元数据，适合数据量较大的实例。

```text
读取数据页
→ 同时捕获备份期间的 Redo/WAL
→ 记录开始/结束日志位置
→ 校验、加密并保存
→ 恢复时 prepare/重放日志
→ 形成一致性数据目录
```

优点是备份和恢复通常比逐行重建快，索引页无需全部重新生成。代价是与数据库大版本、页格式、平台、扩展和工具版本的兼容关系更紧密。

运行中直接复制数据库数据目录通常不构成可靠热备份，因为不同文件可能来自不同时间点，内存中的脏页和恢复日志也没有被正确绑定。

## 4. 全量、增量与差异链

假设星期日执行全量 `F0`，之后每天变化量为 `D1...D6`：

```text
增量：F0 + I1(D1) + I2(D2) + ... + I6(D6)
差异：F0 + Diff6(D1...D6)
```

增量每天备份量小，但恢复需要完整链；差异备份会逐日变大，但通常只需要全量加最后一份差异。任何工具宣称“增量”时，都要确认它按文件、块、页、LSN 还是对象变化判断。

增量链必须记录：

- 基线 Backup ID；
- 父备份 ID；
- 开始/结束 LSN、GTID 或日志位置；
- 数据库和工具版本；
- Checksum、压缩和加密算法；
- KMS Key ID 与密钥版本；
- 所有分片、表空间和外部对象清单。

## 5. 存储快照的三种一致性

| 一致性级别 | 快照前动作 | 恢复后的性质 |
| --- | --- | --- |
| Crash-consistent | 不协调应用，捕获某一块设备时刻 | 类似突然掉电，依赖数据库崩溃恢复 |
| File-system-consistent | Freeze 文件系统或协调写缓存 | 文件系统结构一致，不保证跨文件事务语义 |
| Application-consistent | 数据库执行检查点/备份模式/Quiesce | 快照与数据库日志位置形成可恢复一致性点 |

单卷原子快照也不自动成为应用一致性备份。若数据文件、WAL/Redo、表空间分别位于多个卷，逐卷快照会得到不同时间点；需要应用协调或存储提供的一致性组/Volume Group Snapshot。

## 6. Copy-on-Write 不等于零成本

快照通常先保存元数据映射，速度很快；原卷随后写入时，存储需要保留旧块或写入新位置。其代价包括：

- 快照保留越久，变化块占用越多；
- 快照链过深可能影响读写或恢复；
- 与源卷共享底层阵列时，阵列故障会同时丢失；
- 删除父卷、快照策略或存储账号可能影响所有恢复点；
- 跨地域复制是否包含快照，需要单独确认。

所以快照常用于缩短 RTO，但还应复制到独立故障域或转换成独立备份。

## 7. 从副本备份

从副本读取可以降低主库 I/O，但需要验证副本本身：

```text
复制链路健康
→ 已接收日志位置
→ 已持久化日志位置
→ 已回放日志位置
→ 备份起止位置
```

如果副本落后 40 分钟，从它创建的备份天然比主库旧至少 40 分钟。某些系统备份会阻塞回放，完成后还可能产生更大延迟。备份元数据必须记录副本的实际恢复位置，而不是主库墙上时钟。

## 8. 怎样选择

| 需求 | 首选方向 |
| --- | --- |
| 小库、单表恢复、跨版本迁移 | 逻辑备份 |
| 多 TiB 数据库、要求较短 RTO | 在线物理备份或应用一致性快照 |
| 秒/分钟级恢复点 | 基线备份 + 连续事务日志 |
| 高频快速恢复环境 | 快照 + 事务日志 + 异地独立副本 |
| 长期审计和低频访问 | 加密全量/合成全量 + 冷归档 |
| 防勒索和管理员误删 | 跨权限域不可变副本 |

成熟方案经常组合使用：周期物理全量、增量或快照降低成本，连续日志提供 PITR，逻辑备份保留关键对象的可移植副本。

## 9. 恢复验证

不能只执行 `restore` 后看到进程启动：

1. 校验文件、Manifest 和增量链完整；
2. 验证解密、解压和 prepare；
3. 检查数据库版本、页校验和和启动日志；
4. 检查库、表、分区、行数、约束、角色和权限；
5. 执行业务不变量和合成事务；
6. 记录每阶段时间、峰值空间、IOPS、吞吐和错误；
7. 证明恢复后的实例不会误接生产流量或覆盖备份日志。
