# 数据库可靠性与备份恢复学习路线

数据库可靠性不是“每天执行一次备份命令”。它需要同时回答四个问题：事务什么时候算真正持久化、某个故障发生后由谁接管、错误数据传播后怎样回到正确时间点、现有备份能否在目标时间内恢复。

本模块不绑定某一种数据库。先掌握共通原理，再进入 MySQL、PostgreSQL、Redis、Elasticsearch、Milvus、ClickHouse 和 etcd 的产品实现。

## 1. 先建立完整边界

```text
Durability   已确认事务在什么介质和故障域持久化
Availability 单个组件失败后服务能否继续
Recoverability 数据被删除、损坏或加密后能否恢复
Disaster Recovery 整个可用区或地域失效后怎样恢复业务
```

这四项相互关联，但不能相互替代：

- Redo/WAL 可以完成本机崩溃恢复，但本机磁盘全部损坏后仍需要副本或备份；
- 同步副本可以接管主机故障，却会同步执行误删和错误 DDL；
- 快照可以缩短大库恢复时间，但未必具有数据库事务一致性；
- 跨地域异步副本可以缩短地域灾难的 RTO，却存在复制延迟和数据损失窗口；
- 备份文件存在不代表账号、密钥、网络、版本和恢复步骤都可用。

## 4. 一条建议的实验链

选择一个非生产数据库，构造可识别数据并记录提交序号：

```text
持续写入带序号事务
→ 创建全量基线
→ 连续归档事务日志
→ 注入误删
→ 恢复到隔离实例
→ 停在误删事务之前
→ 验证序号、约束、权限和业务查询
→ 记录实际 RPO、RTO 和每阶段吞吐
```

再依次注入副本延迟、日志缺口、备份损坏、密钥不可用、对象存储不可达和整个集群丢失。只有恢复路径也经过验证，备份策略才算闭环。

## 5. 学完后应能回答的问题

1. 为什么三副本数据库仍然必须备份？
2. 一次写入返回成功时，数据究竟到达了主库内存、主库磁盘还是异地副本磁盘？
3. 为什么文件系统快照成功，不一定代表数据库可安全恢复？
4. 全量备份存在但缺少一段 Binlog/WAL，哪些恢复点会失效？
5. 为什么跨地域同步复制很少作为所有业务的默认配置？
6. 10 TiB 数据库能否在 2 小时 RTO 内恢复，应如何计算？
7. 攻击者取得生产管理员权限后，为什么不能同时获得删除所有备份的权限？
8. Kubernetes 中删除 Namespace 后，备份是否仍然存在并可在新集群恢复？
