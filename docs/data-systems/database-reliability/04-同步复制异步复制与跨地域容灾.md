# 同步复制、异步复制与跨地域容灾

复制模式决定一次写入在什么时候向客户端报告成功，也决定主库突然消失时最多会丢到哪里。架构图上的“主从”两个方框不足以说明可靠性，必须把确认点、故障域、仲裁和切换条件展开。

## 1. 四种常见复制语义

| 模式 | 提交返回前等待什么 | 优点 | 主要边界 |
| --- | --- | --- | --- |
| 异步复制 | 主库达到本地提交条件 | 延迟低、跨地域容易 | 已确认事务可能尚未到副本 |
| 半同步复制 | 至少一个副本收到/写入日志，依实现而定 | 缩小数据损失窗口 | “收到”不一定等于持久化或回放 |
| 同步复制 | 指定副本达到配置确认点 | 可将指定故障下的 RPO 设为 0 | 增加提交延迟，副本故障可能阻塞写入 |
| 共识/多数派复制 | 多数副本持久化日志或达成提交条件 | 自动选主、明确提交索引 | 仍需备份，且多数派与故障域必须正确 |

产品名称相同也可能有不同语义。例如同步确认可以是 `remote_write`、`remote_flush` 或 `remote_apply`。必须以目标版本文档和运行指标确认。

## 2. 提交路径与延迟

同步复制的简化路径：

```text
Client
  → Primary 生成日志并写入持久介质
  → 网络发送日志
  → Standby 接收并达到指定确认点
  → ACK 返回 Primary
  → Primary 向 Client 返回成功
```

提交延迟至少增加副本链路和副本持久化等待。如果跨地域 RTT 为 40 ms，把每个事务同步到远端会直接影响短事务吞吐和尾延迟。因此常见设计是：

```text
同地域跨 AZ：同步副本，保护节点/AZ 故障
跨地域：异步副本或连续日志归档，保护地域灾难
```

核心交易若必须跨地域 RPO 0，需要评估专线 RTT、同步写可用性、双地域同时故障模型和业务能否承受提交延迟，不能只打开一个参数。

## 3. 复制延迟不是一个数

数据库复制通常至少有以下位置：

```text
Primary generated
→ Primary flushed
→ Standby received
→ Standby written
→ Standby flushed
→ Standby replayed/applied
```

字节差和时间差应一起观察：

```text
lag_bytes = primary_current_position - standby_replay_position
catchup_seconds ≈ lag_bytes / effective_replay_bytes_per_second
```

时间戳指标在主从时钟不一致、低流量或心跳不足时可能误导。字节差反映积压量，但不直接等于业务时间。生产监控应同时记录 Receive、Flush、Replay 位置和最后更新时间。

## 4. 故障域比副本数重要

三个副本如果共享同一风险，仍可能一起消失：

- 同一宿主机上的三个容器；
- 同一机架和同一 ToR 下的三个服务器；
- 同一存储阵列上的三块虚拟盘；
- 同一可用区的三个云实例；
- 使用同一管理员账号可同时删除的主库和备份。

故障域应覆盖供电、网络、机架、存储、可用区、地域、账号和密钥。Kubernetes 的 Pod Anti-Affinity 只能影响调度位置，不能证明底层盘、阵列和区域真正独立。

## 5. 选主必须配合 Fencing

网络分区时，旧主可能仍认为自己可写。如果新主同时接收写入，就形成双主分叉：

```text
Client A → old primary → history A
Client B → new primary → history B
```

恢复网络后无法靠简单日志追赶自动合并两条冲突历史。安全切换需要：

1. 仲裁确认旧主不再具备写入资格；
2. 通过 STONITH、云 API、存储租约、数据库 Lease 或网络隔离完成 Fencing；
3. 选择日志最完整且满足提升条件的副本；
4. 更新数据库端点、代理或服务发现；
5. 阻止旧连接池继续向旧主写入；
6. 将旧主作为新副本重新克隆或严格校验后加入。

“探测不到主库”不等于“主库已经停止写入”。

## 6. 自动切换的安全条件

自动化控制器应验证：

- 仲裁仍存在；
- 候选副本的 Receive/Flush/Replay 位置；
- 候选副本没有只读、存储或校验异常；
- 旧主已经 Fencing；
- 新主时间线、Term/Epoch 或 GTID 集合合法；
- 代理和应用具备重连、事务重试与幂等能力；
- 切换后仍有足够副本和故障余量。

如果无法判断哪个节点拥有最新已确认事务，自动提升可能扩大损失，应停止并保存证据。

## 7. 跨地域的四种形态

| 形态 | 平时状态 | 典型 RTO | 主要代价 |
| --- | --- | --- | --- |
| Backup & Restore | 只有异地备份 | 小时级 | 成本低，恢复和重放耗时长 |
| Pilot Light | 远端保留最小数据库/基础设施 | 数十分钟至小时 | 切换时需要扩容和补齐依赖 |
| Warm Standby | 远端持续运行较小副本 | 分钟级 | 持续资源成本、复制延迟 |
| Active/Active | 多地域同时服务 | 最短 | 冲突、一致性、路由和应用改造最复杂 |

关系数据库不能因为存在两个可写节点就自动获得正确的 Active/Active。主键、唯一约束、跨地域事务、冲突解决、读一致性和故障恢复都必须明确。

## 8. 地域切换流程

```text
确认主地域不可用或执行受控切换
→ 冻结/隔离旧地域写入口
→ 计算远端最新安全恢复点和实际 RPO
→ 提升远端数据库
→ 验证角色、时间线、约束和关键数据
→ 启动依赖服务并逐步切流
→ 监控错误率、延迟、连接和业务对账
→ 恢复冗余副本与备份链
```

DNS TTL 只是切流的一部分。客户端连接池、代理缓存、证书、Secret、Allowlist、消息 Offset、定时任务和第三方回调也可能继续指向旧地域。

## 9. 复制为什么不能替代备份

以下操作通常会快速复制：

- 无条件 `DELETE` 或错误 `UPDATE`；
- 删除表、Schema 或索引；
- 应用 Bug 写入错误值；
- 加密后的数据和破坏性迁移；
- 具有数据库权限的攻击操作。

副本用于维持当前服务，备份用于回到过去。跨地域副本也必须配合历史恢复点和不可变备份。

## 10. 演练矩阵

至少分别演练：

1. 主进程退出但主机仍可达；
2. 主机掉电；
3. 主从网络单向中断；
4. 主库与仲裁网络分区但客户端仍能访问旧主；
5. 同步副本变慢或磁盘写满；
6. 候选副本存在 Replay Lag；
7. 整个可用区不可用；
8. 地域切换后旧地域重新上线；
9. 切换期间客户端重试造成重复提交；
10. 切换后立即再损失一个副本。

每次记录实际丢失的最后确认事务、切换耗时、错误请求、重复事务和恢复冗余所需时间。
