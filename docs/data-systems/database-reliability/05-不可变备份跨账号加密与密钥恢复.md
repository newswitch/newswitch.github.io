# 不可变备份、跨账号、加密与密钥恢复

备份最危险的设计不是份数少，而是生产管理员使用同一组凭据可以删除主库、日志归档和全部备份。不可变备份的目标是：即使在线生产权限已经失守，仍保留攻击者在规定时间内无法修改或删除的恢复点。

## 1. 从 3-2-1 到 3-2-1-1-0

常用检查思路可以写成：

```text
3：至少三份数据副本
2：位于两类独立系统或介质
1：至少一份异地
1：至少一份离线、隔离或不可变
0：经过验证后有零个未处理的恢复错误
```

数字本身不是标准答案。关键是每份副本是否共享存储、账号、密钥、删除权限和地域故障。

## 2. 权限域设计

推荐将生产与备份分离：

```text
生产账号/项目
  └─ 备份写入身份：Put/Create，只能写指定前缀

备份账号/项目
  ├─ 保留策略和 Object Lock：生产身份无权修改
  ├─ 复制到第二地域/第二存储
  └─ 恢复身份：平时禁用，审批后临时授权读取
```

避免让生产数据库节点长期持有以下权限：

- 删除备份对象和所有历史版本；
- 缩短保留期或绕过 Governance Retention；
- 删除复制规则、Bucket/Vault 或 KMS Key；
- 读取其他租户或其他数据库备份；
- 修改审计日志和告警目标。

备份平台管理员与生产数据库管理员也不应天然拥有完全相同的权限集合。

## 3. Versioning、复制和 WORM 的区别

| 机制 | 主要作用 | 仍需防范的问题 |
| --- | --- | --- |
| Versioning | 保留对象历史版本 | 高权限用户仍可能永久删除版本 |
| Cross-Region Replication | 复制到另一地域 | 删除标记、权限和错误数据可能传播 |
| Object Lock/WORM | 保留期内禁止覆盖或删除指定版本 | 配置错误、保留期不足、密钥被毁 |
| Offline/Cold Copy | 与在线凭据和网络隔离 | 恢复慢、介质和目录需要维护 |

S3 Object Lock 等功能以对象版本为保护单位，需要同时理解 Versioning、Retention、Legal Hold、Governance 与 Compliance 模式。Governance 模式可能被具有绕过权限的身份解除；Compliance 模式更严格，但错误保留也会带来不可撤销的容量和合规影响。

## 4. 加密保护什么

备份需要同时考虑：

- 传输加密：数据库节点到备份存储；
- 静态加密：对象或介质上的备份；
- 客户端加密：上传前加密，云存储只看到密文；
- 密钥权限：谁能使用、轮换、禁用和销毁密钥；
- 密钥审计：解密和策略变更是否告警。

加密不能防止拥有解密和删除权限的攻击者。如果 KMS Key 与备份同时被删除，完整备份也无法恢复。

## 5. 密钥恢复设计

备份目录需要记录 Key ID 和 Key Version，但不能把明文密钥和备份放在同一位置。恢复方案至少回答：

1. 原生产账号不可用时，恢复账号能否调用 KMS；
2. Key 被禁用、轮换或区域不可用时怎样处理；
3. 跨账号复制后，目标对象使用源 Key 还是目标 Key；
4. 客户端加密密钥的密钥包和恢复审批在哪里；
5. 证书、数据库 TDE 主密钥、Vault Token 等外部状态是否单独备份；
6. 谁能执行 Break-glass，操作是否双人审批并全量审计。

密钥恢复演练必须真实解密一份备份，不能只检查 Key 状态为 Enabled。

## 6. 保留与生命周期

示例 GFS（Grandfather-Father-Son）策略：

```text
连续日志：保留 14～35 天
每日恢复点：保留 14 天
每周恢复点：保留 8 周
每月恢复点：保留 12 月
年度恢复点：按法规保留
```

真正的保留长度要覆盖：最大错误发现时间、调查时间、恢复时间和安全余量。攻击者可能潜伏数周后才破坏数据，只有最近七天备份可能全部包含已经被污染的数据。

生命周期删除前应验证：

- 至少还有一个可恢复全量基线；
- 基线后的日志链连续；
- 没有运行中的恢复依赖该对象；
- Legal Hold、审计或合规要求已经解除；
- 跨地域复制已经完成；
- 最近恢复演练覆盖了保留链中的真实对象。

## 7. 备份目录与证据

每个恢复点应有不可篡改 Manifest：

```yaml
backup_id: mysql-orders-20260908T020000Z
database_engine: mysql
database_version: 8.4.x
source_cluster: orders-prod
start_position: <gtid-or-lsn>
end_position: <gtid-or-lsn>
parent_backup: <id-or-null>
objects:
  - key: backups/orders/base/part-0001
    sha256: <digest>
encryption:
  key_id: <kms-key-id>
  key_version: <version>
retention_until: <timestamp>
restore_test:
  last_verified_at: <timestamp>
  result: passed
```

Manifest 自身也需要签名、版本化和不可变保留，否则攻击者可以把损坏对象替换成“校验通过”的新目录。

## 8. 勒索场景下的恢复顺序

```text
隔离受影响身份、网络和自动任务
→ 保留审计与现场证据
→ 确认干净时间点
→ 在新的可信账号/网络中重建基础设施
→ 使用独立恢复身份读取不可变备份
→ 解密、校验并恢复数据库
→ 修补入侵路径并轮换全部凭据
→ 业务验证后逐步切流
```

如果把备份恢复到仍被控制的原环境，攻击者可能立即再次加密或删除它。

## 9. 必须告警的事件

- 关闭 Versioning、Object Lock、Vault Lock 或跨地域复制；
- 缩短 Retention、增加 Bypass 权限；
- 删除 Bucket、Vault、KMS Key 或大量对象版本；
- 备份写入身份突然执行 List/Get/Delete；
- 恢复身份在非演练窗口启用；
- 日志归档中断或最新可恢复点年龄超标；
- Backup Size、压缩率或对象数量异常变化；
- 审计日志投递失败。
