# 数据质量、数据契约、元数据与血缘

数据平台稳定不只看作业成功。字段全是 null、金额单位错、未来 label 泄漏时，作业仍可能绿色。数据契约定义生产者和消费者的可执行承诺，质量与血缘用于验证和定位影响。

## 1. 元数据分类

- 技术：schema、类型、partition、location、snapshot；
- 业务：含义、粒度、指标公式、时区、单位；
- 运维：owner、SLA、保留、质量、成本；
- 安全：敏感级别、权限、加密、合规；
- 血缘：source→job→dataset→consumer。

Catalog 里只有字段名不等于数据已治理。

## 2. 数据契约

至少包含：数据集/事件标识、owner、主键/粒度、schema与兼容策略、事件时间/时区、允许迟到、SLO、质量阈值、安全分类和废弃流程。契约版本存 Git/registry，并在 Producer CI、ingestion和 consumer测试执行。

兼容策略要区分新增可选字段、删除/重命名、类型提升和语义变化。金额“分→元”即使类型不变也必须新版本。

## 3. 质量维度

| 维度 | 示例 |
|---|---|
| 完整性 | 分区到达、必填非空、offset无缺口 |
| 唯一性 | event_id/业务主键重复率 |
| 有效性 | 枚举、范围、正则、状态机 |
| 一致性 | 多表金额/数量守恒 |
| 新鲜度 | 最大事件时间与当前时间差 |
| 分布 | 均值、分位数、类别占比漂移 |
| 引用完整 | 外键/维度匹配率 |

阈值分硬失败、隔离和告警。核心金额守恒应阻止发布；轻微分布漂移可告警并观察。

## 4. 质量放在哪里

源端约束防坏数据产生；流入口验证 schema/隔离坏事件；表提交后做 snapshot级质量；发布前做业务对账；消费侧验证自己的假设。单点检查不能覆盖整链路。

## 5. 血缘

Job/run事件记录输入/输出 dataset、版本、代码和时间，形成 column/dataset lineage。血缘用于变更影响、故障定位、合规和成本归因，不等于数据正确。

自动解析 SQL可覆盖常见场景；UDF、动态 SQL、外部 API需要显式补充。使用 OpenLineage 等开放事件规范时，namespace/name/run ID要稳定。

## 6. 发布闸门

Staging snapshot → schema contract → 行数/唯一/业务规则 → 与上一版本漂移 → 人工审批（高风险）→ 原子切换 alias/tag → 发布 lineage和质量报告。失败版本保留证据但不可被正式 consumer发现。

## 7. 告警与处置

质量告警带 dataset、snapshot、rule、实际/阈值、owner、上游变更和影响 consumer。避免每行发告警；聚合后建立事件。修复后发布新版本或明确 backfill，不直接覆盖审计证据。

## 8. 实验

为订单表定义契约，注入 null、重复、负金额、未知状态、迟到和分布突变。验证哪些隔离、哪些阻止发布；改变上游 schema，用血缘列出受影响报表/特征。

## 9. 掌握验收

- 写出包含语义和 SLO 的契约；
- 设计六类质量规则与分级；
- 把质量闸门放在原子发布前；
- 用 dataset/run/version 构建血缘；
- 从 schema变更得到受影响 consumer清单。
