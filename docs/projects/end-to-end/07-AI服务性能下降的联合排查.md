# AI 服务性能下降：GPU、NVLink、网卡、存储与调度联合排查

AI 平台最难处理的通常不是“完全不可用”，而是“还能运行，但比昨天慢 30%”。此时每一层都可能显示正常：

- GPU 有利用率，没有 OOM；
- 网卡能通，没有 Link Down；
- 存储能读，没有 I/O error；
- Pod Running，没有 CrashLoop；
- NCCL 没超时，训练仍在继续。

但“能工作”不等于“走在设计路径上”。本篇建立一套从业务现象出发、跨调度、CPU、GPU、NVLink/NCCL、NIC 和存储的联合排查方法。

## 1. 第一原则：先定义到底慢了什么

不要从 `nvidia-smi` 开始。先把用户现象变成可比较的指标。

### 1.1 推理指标

- 请求成功率和错误码；
- TTFT；
- TPOT 或 inter-token latency；
- E2E latency；
- 输入/输出 token 吞吐；
- 活跃请求、等待请求和被拒绝请求；
- 冷启动和模型加载时间。

### 1.2 训练指标

- step time 及 P50/P95；
- samples/tokens per second；
- 数据加载等待占比；
- 前向、反向、优化器和通信时间；
- Checkpoint 写入和恢复时间；
- 有效训练时间占 wall-clock 的比例；
- 多节点扩展效率。

“GPU 利用率从 90% 降到 70%”只是平台信号，不是业务影响定义。

## 2. 保存一个真正可用的黄金基线

性能问题必须有对照。基线至少固定：

| 层级 | 需要固定的变量 |
|---|---|
| 请求/数据 | prompt 长度、输出长度、batch、数据集、随机种子 |
| 模型 | 名称、revision、Tokenizer、精度、量化 |
| 引擎 | 镜像摘要、CUDA/框架、关键参数、并行策略 |
| GPU | 型号、数量、MIG、驱动、功耗上限、时钟 |
| 拓扑 | 节点、GPU rank、NUMA、NVLink、NIC、机架 |
| 网络 | 传输方式、接口、MTU、交换域、RDMA 配置 |
| 存储 | 后端、客户端参数、缓存冷热、数据版本 |
| 调度 | 队列、优先级、节点标签、共置负载 |
| 时间 | 测试时段、后台任务、变更号 |

如果基线只保存一个平均吞吐数字，后续无法知道差异来自输入、版本还是基础设施。

## 3. 建立统一事件时间线

将以下事件放在一条时间线上：

- 首次 SLI 越界；
- Deployment、ConfigMap、模型 revision、驱动或固件变更；
- Pod 调度、重启、驱逐、节点 NotReady；
- GPU Xid、ECC、时钟或功耗变化；
- NIC Link/FEC/RDMA/PFC 变化；
- 存储延迟、错误和容量水位变化；
- 队列、配额、自动扩容和抢占变化；
- 同节点其他任务启动时间。

时间相关不自动等于因果，但能快速缩小候选范围。所有组件应时间同步，查询窗口应覆盖问题前的正常阶段。

## 4. 总体决策路径

```text
确认 SLI 退化与影响范围
  ↓
是否与版本/配置/放置变更强相关？──是→ 对照或回滚验证
  ↓否
请求/作业是否在排队？──────────是→ 容量、准入、调度、扩容
  ↓否
CPU/主机内存是否在等待或限流？──是→ Tokenizer、DataLoader、NUMA、cgroup
  ↓否
GPU 是否计算、访存、降频或失衡？─是→ Kernel、HBM、慢卡、共置
  ↓否/继续
单机 GPU 通信是否退化？────────是→ NVLink/PCIe/拓扑/rank
  ↓否/继续
跨机通信是否退化？────────────是→ NIC/RDMA/交换网络/NCCL 选路
  ↓否/继续
数据或模型 I/O 是否形成等待？───是→ page cache/NFS/对象存储/NVMe
  ↓
使用 profiler 定位应用同步、锁和框架执行
```

实际排查不是严格单线流程，但每一步都要形成“假设—证据—实验—结论”。

## 5. 第一步：确定影响范围

从四个维度切片：

1. **时间：**持续、周期、尖峰还是只在发布后？
2. **空间：**所有集群、可用区、机架、节点池、节点还是单 Pod？
3. **版本：**所有模型/镜像，还是某个 revision？
4. **负载：**短 prompt、长 prompt、某并发、单机或多机？

范围本身就是证据：

- 只在一台节点：优先查节点硬件、拓扑、共置和本地缓存；
- 只在多机训练：优先查跨机 NCCL、RDMA 和 Gang 放置；
- 只在冷启动：优先查模型分发、存储、CPU 解压和显存加载；
- 只在高并发：优先查队列、KV Cache、批处理和容量；
- 只在新版本：先做相同节点上的 A/B，而不是立即更换硬件。

## 6. 第二步：先排队，再看 GPU

### 6.1 Kubernetes 与队列层

检查：

```bash
kubectl get pods -A --field-selector=status.phase=Pending
kubectl describe pod <pod>
kubectl get events -A --sort-by=.lastTimestamp
kubectl get nodes -L <pool-label>,topology.kubernetes.io/zone
```

关注：

- GPU 数量或型号不足；
- node affinity、污点和 toleration；
- PVC 拓扑或 VolumeBinding；
- Gang 最小成员不足；
- 队列配额、优先级和借用；
- 拓扑约束把任务限制在容量不足的域；
- 新 Pod 启动需要重新下载模型。

### 6.2 引擎内部队列

Pod 已 Ready 不代表请求不排队。检查 waiting/running request、batched tokens、KV block 使用和拒绝数。若 GPU 已满且队列持续增长，问题可能只是容量到达极限。

利用 Little 定律验证一致性：到达率不变、停留时间增加时，系统内请求数应增加。若监控不符合，可能是埋点口径或丢失请求。

### 6.3 自动扩容陷阱

- 只看平均 GPU 利用率，忽略请求队列；
- 模型冷启动 10 分钟，扩容器每分钟继续加副本；
- 没有空闲 GPU，新 Pod 永远 Pending；
- 新旧版本并存需要额外 GPU，但 rollout 没预留；
- 缩容只看瞬时低利用率，终止仍有长请求的实例。

## 7. 第三步：CPU、内存与 NUMA

GPU 空洞经常由 CPU 供给不足造成。检查：

- 容器 CPU throttling；
- Tokenizer、JSON、采样、日志和 TLS 的 CPU；
- 训练 DataLoader worker、数据增强和 Python GIL；
- 内存压力、major page fault、swap；
- CPU 与 GPU 是否跨 NUMA；
- pinned memory 与 H2D 拷贝；
- 事件循环、线程池、锁和垃圾回收。

常用只读观察：

```bash
kubectl top pod -n <ns> <pod> --containers
kubectl top node <node>
numactl --hardware
pidstat -p <pid> 1
vmstat 1
```

需要在宿主机执行的诊断必须遵守权限和隐私策略。短时采样比长期高频 profiler 更安全。

### 7.1 典型证据组合

```text
GPU 利用率周期性归零
+ CPU throttled_seconds 增长
+ 请求 tokenize 或 DataLoader 时间增长
= CPU 配额/供给候选
```

如果只提高 CPU 后性能恢复，应继续确认根因是配额过低、线程数错误、NUMA 还是代码回归，而不是永久超配。

## 8. 第四步：GPU 计算、显存与硬件状态

### 8.1 先看每张卡，不看节点平均

```bash
nvidia-smi
nvidia-smi -L
nvidia-smi topo -m
nvidia-smi dmon -s pucvmet
nvidia-smi --query-gpu=uuid,pci.bus_id,utilization.gpu,utilization.memory,memory.used,power.draw,temperature.gpu,clocks.sm,clocks.mem --format=csv
```

需要结合 DCGM 时间序列检查：

- 某张卡是否持续比其他 rank 慢；
- 功耗、温度和时钟是否受限；
- 显存是否逼近上限；
- ECC、Xid 或 PCIe 重放是否增加；
- GPU 是否被未知进程共享；
- MIG profile 或 compute mode 是否变化。

### 8.2 GPU 利用率的四种解释

| 表现 | 可能含义 |
|---|---|
| 高利用、高吞吐 | 正常计算或接近饱和 |
| 高利用、低吞吐 | Kernel/形状回归、降频、重复计算或低效批处理 |
| 低利用、低吞吐 | CPU、I/O、排队、同步或小 batch |
| 周期性锯齿 | DataLoader、通信、GC、批处理或 Checkpoint 停顿 |

### 8.3 HBM 不只是“够不够”

推理中要区分权重、KV Cache、工作区和临时激活；训练中还包括梯度、优化器状态和激活。显存逼近上限可能造成：

- KV 抢占、换出或重计算；
- allocator 碎片；
- batch 被迫减小；
- OOM 后请求/作业重试；
- 多 rank 只有一个 rank 首先耗尽。

不要在生产上通过不断提高显存利用率阈值来掩盖容量问题。

## 9. 第五步：用 Profiler 区分计算与等待

当监控只能说明“GPU 慢”，应使用短时间、可复现负载分析：

- PyTorch Profiler：算子、CPU/GPU 时间、shape、调用栈；
- Nsight Systems：CPU thread、CUDA API、Kernel、Memcpy、NCCL 时间线；
- Nsight Compute：单个关键 Kernel 的吞吐、访存和 occupancy；
- 框架/引擎自带统计：Scheduler、KV、batch 和请求阶段。

先用 Systems 找到“时间花在哪一段”，再对少量关键 Kernel 使用 Compute。直接对长时间生产流量做最重分析可能产生明显开销。

典型时间线：

```text
CPU 空白 + GPU 空白       → 线程阻塞、I/O、锁或埋点缺口
CPU 忙 + GPU 空白         → 预处理/调度/序列化瓶颈
GPU Kernel 间空隙大       → launch、同步或 CPU 供给
NCCL 长且其他 GPU 等待    → 通信或慢 rank
Memcpy H2D 长             → PCIe/NUMA/pinned memory
Kernel 连续但吞吐下降      → 算子、形状、时钟或 HBM
```

## 10. 第六步：NVLink、NVSwitch 与单机通信

单机多卡任务先确认物理拓扑：

```bash
nvidia-smi topo -m
nvidia-smi nvlink --status
```

然后在同样的 GPU 集合和 rank 映射上运行受控 `nccl-tests`，比较不同消息大小，而不是只看峰值。关注：

- 任务是否跨越没有高速互联的 GPU 组；
- GPU P2P 是否启用；
- rank 顺序是否与物理拓扑匹配；
- NVLink 计数或错误是否异常；
- 是否经过 PCIe Host Bridge/跨 NUMA；
- 同机其他任务是否争用互联或 PCIe。

### 10.1 为什么一个慢 rank 拖慢所有卡

Collective 通常要求所有 rank 参与。某张 GPU 因降频、错误恢复或共置变慢时，其他 GPU 到达同步点后等待，于是出现：

```text
慢 GPU: Kernel ───────────────→ Collective
其他卡: Kernel → 等待等待等待 → Collective
```

节点平均 GPU 利用率会掩盖这个现象，因此应按 rank 与 GPU UUID 对齐。

## 11. 第七步：NCCL 选路和跨机网卡

多机训练或跨机推理需要继续检查：

- NCCL 实际选择了哪张 NIC；
- 使用 RDMA、GPUDirect RDMA 还是 Socket；
- HCA 与 GPU 是否位于合适的 PCIe/NUMA 路径；

- Channel、Ring/Tree 和协议选择；
- 是否因为接口、容器权限或库问题退回慢路径；
- 不同消息大小的性能是否符合设计。

调试日志应只在短时测试中启用，并保存版本、环境变量和拓扑。不要长期打开极高日志级别。

### 11.1 网络分层检查

```text
物理层：Link、速率、lane、光模块、FEC
二层/三层：VLAN、LAG、MTU、路由、ECMP
传输层：丢包、重传、拥塞、Socket buffer
RDMA：设备、GID、QP、CQ、PFC/ECN、错误计数
NCCL：接口、Transport、Channel、算法、超时
应用：Collective 大小、频率、同步模式
```

只做 `ping` 无法证明 RDMA 和大流量无损网络正常。

### 11.2 关键证据

节点侧：

```bash
ip -s link show dev <nic>
ethtool <nic>
ethtool -S <nic>
ss -s
```

RDMA 环境还应使用对应厂商和 `rdma` 工具读取设备与端口状态，并与交换机侧 PFC、ECN、队列丢弃和端口利用率对齐。计数器名称依设备而异，不能机械套用单一阈值。

### 11.3 常见慢路径

- NCCL 选中了管理网接口；
- RDMA 设备没有正确挂入容器；
- GID/路由配置不匹配；
- MTU 端到端不一致；
- PFC 配置不对称或拥塞扩散；
- ECMP 哈希导致热点；
- GPU 与 HCA 跨 NUMA/PCIe Root；
- 交换机端口 FEC 错误增加；
- 某节点 NIC 降速但 Link 仍是 UP。

## 12. 第八步：存储、Page Cache 与本地 NVMe

### 12.1 分清 I/O 发生在哪个阶段

| 场景 | I/O 路径 |
|---|---|
| 模型冷启动 | 对象/NFS → NIC → page cache/本地盘 → CPU → HBM |
| 模型热启动 | page cache 或本地 NVMe → CPU → HBM |
| 训练读取 | 数据源 → DataLoader → 主机内存 → GPU |
| Checkpoint | GPU/CPU 状态 → 文件系统/对象存储 |
| 推理稳态 | 通常以 HBM 为主，日志/外部检索除外 |

如果稳态纯生成请求仍强依赖模型文件读取，需要确认是否发生换出、按需加载或异常重启。

### 12.2 Linux I/O 证据

```bash
iostat -xz 1
vmstat 1
pidstat -d -p <pid> 1
cat /proc/meminfo
```

关注吞吐、IOPS、平均和尾延迟、队列深度、设备利用率、major fault、dirty/writeback，以及进程是否阻塞在 I/O。`%util` 接近 100% 的含义与设备并行能力有关，不能单独作为饱和结论。

### 12.3 NFS/共享文件系统

检查客户端挂载参数、RPC 重传、服务端延迟、元数据压力、锁、并发和网络。大量小文件扫描可能由元数据限制，单个大模型分片读取更接近吞吐限制。

### 12.4 对象存储

检查：

- 请求限速、503/SlowDown 和重试；
- Multipart/Range 并发；
- checksum 与重下载；
- 网关和跨区链路；
- 多节点同时扩容造成的下载风暴。

### 12.5 本地 NVMe 缓存

本地缓存通常能降低共享后端压力，但要验证：

- cache key 是否包含模型 revision；
- 临时下载与完成标记；
- checksum；
- 容量水位和淘汰；
- 多进程并发下载锁；
- 节点重建时缓存可丢失且可重建。

缓存命中率下降可能表现为模型启动变慢，而不是稳态 GPU 指标异常。

## 13. 第九步：调度放置如何制造性能问题

同样的 Pod 清单被放到不同节点，性能可能不同，因为调度决定：

- GPU 型号、显存和时钟能力；
- 多卡之间 NVLink/NVSwitch 路径；
- GPU 到 CPU/内存的 NUMA 距离；
- GPU 到 RDMA HCA 的 PCIe 距离；
- 本地 NVMe 是否已有模型缓存；
- PVC 是否跨区域或跨故障域访问；
- 多个 Worker 是否处于同一高速网络域；
- 是否与其他高负载任务共置。

检查实际结果，不要只看期望配置：

```bash
kubectl get pod -n <ns> <pod> -o wide
kubectl get pod -n <ns> <pod> -o yaml
kubectl get node <node> --show-labels
kubectl describe node <node>
```

标签是对硬件事实的声明，必须能追溯到自动发现或资产源。错误标签会让调度器稳定地做出错误决策。

## 14. 五类症状的快速分支

### 14.1 TTFT 变高，TPOT 正常

优先顺序：

1. 网关排队、连接和首包缓冲；
2. 请求 token 长度是否变化；
3. Tokenizer/CPU；
4. 引擎 waiting queue；
5. Prefill batch 和 GPU；
6. 新副本模型冷加载；
7. 多卡 Prefill 通信。

### 14.2 TTFT 正常，TPOT 变高

优先顺序：

1. 活跃序列和 Decode batch；
2. KV Cache 压力、抢占、重计算；
3. GPU 时钟、功耗、温度和 HBM；
4. Tensor Parallel 慢 rank；
5. NVLink/NCCL；
6. SSE 缓冲和客户端反压。

### 14.3 训练 step time 周期性尖峰

将尖峰周期与以下事件对齐：

- Checkpoint；
- 数据集分片切换或缓存未命中；
- Python GC；
- 日志/评估；
- NCCL 拥塞；
- 其他租户的定时任务；
- 温度和功耗限制。

### 14.4 模型冷启动变慢

拆分为：排队 → 镜像拉取 → 卷挂载 → 模型下载 → checksum → CPU 反序列化 → H2D → 图捕获/编译 → startup/readiness。哪个阶段增加，就查哪个责任域。

### 14.5 只有长尾变坏，平均值正常

长尾常来自少数节点、少数请求或周期性事件。按节点、Pod、模型 revision、输入长度和时间切片，并比较最慢样本 Trace。平均值会把慢 Endpoint 掩盖掉。

## 15. 证据矩阵：避免每个团队都说“我这里正常”

| 层级 | 主要问题 | 至少提供的证据 |
|---|---|---|
| 业务 | 哪个 SLI 退化、影响多少请求 | 仪表盘、样本请求、时间窗 |
| 网关 | 排队、超时、重试、后端分布 | 访问日志、upstream time、Trace |
| Kubernetes | 放置、事件、Endpoint、配额 | Pod/Node/EndpointSlice/Queue 状态 |
| 应用 | Tokenizer、队列、batch、KV | 引擎指标、结构化日志 |
| CPU | throttling、NUMA、page fault | cgroup、pidstat、vmstat |
| GPU | 计算、HBM、时钟、错误、慢卡 | DCGM、nvidia-smi、Profiler |
| NVLink/NCCL | 拓扑、rank、Collective | topo、NCCL 日志、nccl-tests |
| 网络 | 速率、错误、拥塞、RDMA | NIC/交换机/RDMA 计数器 |
| 存储 | 吞吐、尾延迟、重试、缓存 | 客户端、服务端、iostat、cache 指标 |

“链路可达”“Pod Running”“磁盘 util 不高”都不能单独关闭一个故障域。

## 16. 设计最小验证实验

每个候选根因都应有低风险验证：

| 假设 | 最小实验 | 预期证据 |
|---|---|---|
| 新版本回归 | 同节点、同输入 A/B | 只有版本改变时结果分离 |
| 调度到慢节点 | 把 canary 固定到基线节点 | 性能随节点改变 |
| 存储冷缓存 | 同 revision 比较首次与再次加载 | 热缓存显著恢复 |
| NCCL 慢路径 | 隔离环境比较 RDMA 与受控 Socket | 日志和带宽同步变化 |
| CPU 限流 | canary 临时提高 CPU 配额 | throttling 和 GPU 空洞同时下降 |
| 单 GPU 降频 | 同任务换到健康节点/GPU 集合 | 慢 rank 随设备移动 |

实验必须一次只改变一个主要变量，并保留回滚。不要为了验证网络问题同时升级驱动、修改 MTU 和更换 NCCL 版本。

## 17. 常见错误排障动作

1. **看到慢就重启。**重启会破坏现场，也可能因热缓存暂时恢复而误判。
2. **只比较 GPU 利用率。**不知道计算、访存、通信还是等待。
3. **直接打开所有 DEBUG。**日志量和同步开销可能进一步影响性能。
4. **生产环境跑无限压测。**压测本身改变队列与网络状态。
5. **看到丢包计数就归因网络。**要比较增量、时间和受影响路径。
6. **只用平均值。**少数慢节点和长尾被掩盖。
7. **用不同输入做版本对比。**结论不可复验。
8. **多个团队各用不同时钟和 ID。**无法建立同一事件链。
9. **所有优化一起上线。**即使恢复也不知道哪项有效。
10. **性能恢复就结束。**没有根因、预防动作和回归测试。

```markdown

## Follow-ups
```

根因不是“GPU 慢”“网络抖动”这种现象描述，而应具体到可修复机制，例如“新节点 NIC 固件导致端口协商为低速，调度标签未区分该节点，两个 TP rank 的跨机 Collective 吞吐下降”。

## 19. 从故障修复到系统性预防

一次联合排障应沉淀：

- 可自动发现的资产和拓扑标签；
- 按模型/版本/节点/GPU 切片的 SLI；
- GPU、NIC、存储和 NCCL 的周期基线；
- 发布、驱动、固件和网络变更的灰度门禁；
- 模型冷启动、训练恢复和慢节点的演练；
- 进入调度过滤或隔离流程的健康信号；
- 能从请求 Trace 关联到 Pod、Node 和 GPU 的上下文；
- 可复验的性能回归用例。

不要把瞬时性能指标直接变成自动驱逐依据。健康判断要有持续窗口、多信号确认、防抖、爆炸半径和人工接管。

## 20. 掌握标准

学习者应能完成以下闭环：

1. 用业务 SLI 定义问题和范围；
2. 找到相同输入、版本和拓扑的黄金基线；
3. 建立跨发布、调度、GPU、NIC 和存储的时间线；
4. 区分排队、CPU、计算、HBM、NVLink、跨机网络和 I/O；
5. 为候选根因设计一次单变量、可回滚实验；
6. 用 Trace、日志、指标和 profiler 给出相互支持的证据；
7. 验证恢复后的 SLI、模型和 Checkpoint 正确性；
8. 把根因转化为监控、门禁、容量、调度或架构改进。

到这里，“GPU 计算—显存—NVLink—网卡—存储—调度”不再是几篇孤立文章，而是一套可以用于真实系统的分析框架。
