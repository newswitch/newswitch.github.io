# 10 台 2TB 服务器建设 Ceph：从规划、部署到故障演练

《Ceph 从零基础到生产运维实战》第 29 篇

← [第 28 篇：大规模 Ceph 集群设计与运维](../../storage/ceph/07-performance/28-大规模Ceph集群优化.md)

前面的文章分别讲了 Ceph 原理、规划、部署、三类存储接口、监控、排障和优化。这一篇把它们组合成一个完整项目：

> 使用 10 台服务器搭建一套以三副本为主的 Ceph 集群，为虚拟机或普通服务器提供 RBD，为共享目录和 Kubernetes 提供 CephFS，并完成上线验收与故障演练。

这不是一份可以不经评审直接用于所有生产环境的采购模板，而是一条完整的学习主线。真实项目必须根据业务 IOPS、吞吐、延迟、增长、恢复时间、硬件型号和故障域重新计算。

本文默认使用 cephadm 和较新的 Active Release。命令选项可能随版本变化，执行前应阅读目标版本官方文档，并在隔离实验环境验证。


## 项目目标

完成本项目后，你应该能够独立完成：

- 从业务需求推导节点、角色、容量和网络
- 区分原始容量、理论可用容量与规划可用容量
- 使用 cephadm 部署和验收 10 节点集群
- 创建 RBD 与 CephFS 服务
- 创建最小权限 CephX 客户端
- 将 RBD 和 CephFS 接入 Kubernetes
- 建立 Prometheus 告警和业务探测
- 演练 OSD、MON 和容量异常
- 编写上线验收、回退和运维交接材料

## 实验边界与假设

### 硬件假设

每台服务器配置：

| 组件 | 假设 |
| --- | --- |
| CPU | 8 核或以上 |
| 内存 | 32 GiB 或以上 |
| 系统盘 | 独立 SSD，至少 240 GB |
| OSD 数据盘 | 1 块 2 TB 企业级 SSD 或 HDD |
| 网络 | 至少双 10 GbE；有条件使用双 25 GbE |
| 管理接口 | 独立 BMC/IPMI |
| 电源 | 双电源并分接不同 PDU |

关键假设是：

> “2 TB 服务器”表示每台有一块独立的 2 TB OSD 数据盘，操作系统不安装在这块盘上。

如果 2 TB 是整机唯一磁盘，不能同时把它既当系统盘又完整当作 OSD。生产 Ceph 应将操作系统盘和 OSD 数据盘分离。

### 容量与性能边界

这个方案只有 10 个 OSD，因此：

- 适合理解 Ceph 完整流程和承载中小规模业务
- 总 IOPS 受 10 块盘的并行度限制
- 单盘 2 TB 故障后需要恢复较大数据量
- 不适合仅根据“容量够”就承诺高性能数据库
- 如果使用 HDD，小随机写延迟会明显高于全闪集群

生产评审必须使用目标盘型的实测数据，而不是把实验数字当作厂商保证。

## 需求分析

假设业务需求如下：

| 维度 | 目标 |
| --- | --- |
| RBD | 虚拟机和普通块存储，初始有效数据 2 TiB |
| CephFS | Kubernetes RWX 和共享文件，初始有效数据 1 TiB |
| 一年增长 | 总有效数据预计达到 4 TiB |
| 数据保护 | 三副本 |
| failure domain | Host |
| 主机故障 | 任意 1 台离线时业务继续运行 |
| 恢复目标 | 单盘或单主机故障后 12 小时内恢复完整冗余 |
| 可用性 | MON 可容忍 1 个实例故障 |
| 运维 | 支持逐台滚动维护 |
| 监控 | Prometheus、Grafana、Alertmanager |
| Kubernetes | RBD RWO + CephFS RWX |

### 尚未被需求覆盖的问题

项目启动会还要回答：

- RBD 是 4 KiB 随机 I/O 还是大块顺序 I/O？
- CephFS 是大量小文件还是大文件？
- 快照保留多久？
- 是否需要异地灾备？
- 业务可接受的 P95/P99 延迟是多少？
- 每年增长是否包含快照、Clone 和删除保留？
- 维护期间允许多少性能下降？
- 发生 Full 时谁有权停写？

“有 10 台机器”只是资源输入，不是完整需求。

## 架构与角色规划

10 台主机命名为 `ceph01` 到 `ceph10`。

| Host | MON | MGR | OSD | MDS | 其他 |
| --- | --- | --- | --- | --- | --- |
| ceph01 | 是 | Active 候选 | 1 | Active 候选 | 管理入口 |
| ceph02 | 是 | Standby 候选 | 1 | Standby 候选 |  |
| ceph03 | 是 |  | 1 |  |  |
| ceph04 |  |  | 1 |  |  |
| ceph05 |  |  | 1 |  |  |
| ceph06 |  |  | 1 |  |  |
| ceph07 |  |  | 1 |  |  |
| ceph08 |  |  | 1 |  |  |
| ceph09 |  |  | 1 |  |  |
| ceph10 |  |  | 1 |  |  |

实际 cephadm placement 可以让 MGR Active 在主备间自动切换，表格表示候选分布，不是永久角色绑定。

### 为什么全部 10 台都运行 OSD

每台一块数据盘时，全部纳入才能获得：

- 20 TB 标称 Raw 容量
- 10 个独立 Host 故障域
- 10 块盘的并行度
- 任意单 Host 故障只损失约 10% Raw 容量

### 为什么使用 3 个 MON

3 个 MON 需要 2 个形成多数派，可容忍 1 个 MON 故障。将它们放在不同 Host、机架、电源和交换路径上，才能真正获得故障隔离。

5 个 MON 可以容忍 2 个 MON 故障，但会增加 Quorum 和维护复杂度。对于这个规模，3 个通常更合适。

### MDS 数量

CephFS 至少部署：

- 1 个 Active MDS
- 1 个 Standby MDS

单个 Active 是否满足元数据负载，要通过目录遍历、文件创建、重命名和小文件测试验证。不要因为数据吞吐不高就忽略 MDS 性能。

### CRUSH 拓扑

最低要求：

```text
root default
├── host ceph01
│   └── osd.0
├── host ceph02
│   └── osd.1
...
└── host ceph10
    └── osd.9
```

副本池使用：

```text
size = 3
min_size = 2
failure_domain = host
```

如果 10 台机器跨两个机架，需要在 CRUSH Map 中准确标记 Rack，但两个机架不足以在“机架级三副本”条件下放置三份数据。不能只添加 rack 层级就声称已获得机架级三副本容错。

## 容量计算

### 标称 Raw 容量

```text
10 台 × 2 TB = 20 TB Raw
```

硬盘厂商通常使用十进制 TB，操作系统和部分工具可能显示 TiB：

```text
20 TB 约等于 18.19 TiB
```

### 三副本理论有效容量

```text
20 TB ÷ 3 = 6.67 TB
```

这只是理论值，没有考虑：

- BlueStore 和内部元数据
- 数据分布不均衡
- 快照、Clone 和 Trash
- 最大故障域恢复空间
- nearfull/backfillfull/full 安全线
- 一年增长误差

### 规划可用容量

如果将正常运行上限控制在 Raw 的约 70%：

```text
20 TB × 70% ÷ 3 = 4.67 TB 有效数据
```

因此本案例将 4 TiB 左右作为一年期业务规划目标，而不是承诺完整使用 6.67 TB。

这个 70% 不是 Ceph 的固定公式，只是当前硬件和故障假设下的教学规划线。真实比例还要根据最大 Host 占比、增长提前量和恢复测试调整。

### 单 Host 故障恢复空间

每台只有一块 2 TB OSD，单 Host 约占 10% Raw。集群在 70% Raw 使用率时：

```text
已用 Raw：约 14 TB
总空闲 Raw：约 6 TB
单 Host 最大待恢复 Raw：平均约 1.4 TB 已用数据
```

从总量看有空间恢复，但还必须满足：

- 剩余 OSD 分布均衡
- CRUSH Rule 能找到新的 Host
- 没有其他 nearfull OSD
- 恢复期间还有业务余量

### Pool 容量预算

示例：

| Pool/服务 | 一年有效数据目标 | 三副本 Raw 预算 |
| --- | ---: | ---: |
| RBD | 2.5 TiB | 7.5 TiB |
| CephFS Data | 1.2 TiB | 3.6 TiB |
| CephFS Metadata | 0.1 TiB | 0.3 TiB |
| 运维、快照与误差 | 0.2 TiB | 0.6 TiB |
| 合计 | 4.0 TiB | 12.0 TiB |

剩余 Raw 空间用于分布偏差、恢复、内部开销和增长缓冲。

## 网络规划

### 网络平面

| 网络 | 示例 CIDR | 用途 |
| --- | --- | --- |
| 管理网络 | `10.10.10.0/24` | SSH、cephadm、Dashboard、监控 |
| Public Network | `10.10.20.0/24` | 客户端、MON、Ceph daemon 通信 |
| Cluster Network | `10.10.30.0/24` | OSD 复制、恢复和心跳 |
| BMC 网络 | `10.10.40.0/24` | IPMI/Redfish |

小型环境可以让 Public 与 Cluster 共用高带宽冗余网络，但必须验证业务流量和恢复流量同时出现时的性能。分网也不等于自动获得带宽，如果两个 VLAN 最终仍走同一物理链路和交换机，故障域并没有真正分离。

### 冗余

每台主机建议：

- 两张数据网卡或双口 NIC
- 分别连接两台独立交换机
- 根据交换机设计使用 LACP 或主备 Bond
- 端到端 MTU 一致

验收：

```bash
ip -br address
ip route
ip link
chronyc tracking
ping -c 5 <peer-public-ip>
ping -c 5 <peer-cluster-ip>
```

如果使用 Jumbo Frame，必须验证客户端、服务器、Bond、交换机端口和三层路径全部一致。不要只在服务器上设置 MTU 9000。

### 带宽与恢复时间

2 TB 磁盘不代表故障时一定需要复制完整 2 TB，只复制已使用且需要恢复的数据。

估算：

```text
恢复时间 = 待恢复数据量 ÷ 有效恢复吞吐
```

假设待恢复 1.4 TB，有效恢复吞吐 100 MB/s：

```text
约 3.9 小时
```

但有效吞吐会受业务、源盘、目标盘、网络、CPU 和 QoS 影响。项目必须通过真实故障演练验证 12 小时 RTO，而不能只使用理论网卡速率。

## 磁盘规划

### 系统盘与数据盘分离

系统盘保存：

- 操作系统
- 容器运行时
- 日志
- cephadm 管理文件

2 TB 数据盘完整交给 BlueStore OSD。不要提前格式化或挂载。

### 设备身份

建立资产表：

| Host | OSD | 设备路径 | WWN/序列号 | 型号 | 槽位 |
| --- | --- | --- | --- | --- | --- |
| ceph01 | 待分配 | `/dev/disk/by-id/...` | SN001 | Model-A | Bay 1 |

`/dev/sdb` 只适合临时观察，不适合换盘审批和自动化选择。

### 混合 SSD 与 HDD

如果 10 台中的介质不同，必须创建准确的 device class 和 CRUSH Rule。不能让性能目标不同的 Pool 随机混合到不同盘型。

本案例为了教学一致性，假设 10 块数据盘型号、容量和介质相同。

## 操作系统准备

所有 Host：

- 主机名唯一且稳定
- DNS 或 `/etc/hosts` 正确
- 时间同步正常
- 安装 Podman 或目标版本支持的容器运行时
- 安装 LVM2 等 cephadm 依赖
- 防火墙开放目标版本所需端口
- 数据盘无文件系统、分区、LVM 和旧 Ceph 签名
- 内核、NIC、磁盘固件通过兼容性评审

示例主机名：

```text
ceph01.example.internal
...
ceph10.example.internal
```

在每台主机检查：

```bash
hostname -f
timedatectl
chronyc sources -v
lsblk -o NAME,SIZE,MODEL,SERIAL,WWN,FSTYPE,MOUNTPOINTS
podman version
lvm version
```

## 使用 cephadm 部署

### 选择并固定版本

先选定 Active Release、目标容器镜像和升级策略。不要在 10 台主机上混用不同 Ceph 主版本。

本文使用占位符：

```text
<CEPH_IMAGE>
<CEPH_RELEASE>
```

执行前必须替换成已评审的准确值。

### Bootstrap ceph01

在第一台管理节点：

```bash
cephadm --image <CEPH_IMAGE> bootstrap \
  --mon-ip 10.10.20.11 \
  --cluster-network 10.10.30.0/24
```

验证：

```bash
cephadm shell -- ceph -s
cephadm shell -- ceph versions
cephadm shell -- ceph orch status
```

### 分发 cephadm SSH 公钥

```bash
ceph cephadm get-pub-key > ceph.pub
```

将公钥安全分发到 `ceph02` 至 `ceph10` 的 cephadm 管理用户。不同企业可能禁止 root SSH，此时应使用经过配置的专用用户和 cephadm SSH 配置。

### 加入 Host

```bash
ceph orch host add ceph02 10.10.20.12
ceph orch host add ceph03 10.10.20.13
ceph orch host add ceph04 10.10.20.14
ceph orch host add ceph05 10.10.20.15
ceph orch host add ceph06 10.10.20.16
ceph orch host add ceph07 10.10.20.17
ceph orch host add ceph08 10.10.20.18
ceph orch host add ceph09 10.10.20.19
ceph orch host add ceph10 10.10.20.20
```

验证：

```bash
ceph orch host ls
ceph cephadm check-host ceph02
ceph orch device ls --wide --refresh
```

### 添加标签

```bash
for host in ceph01 ceph02 ceph03 ceph04 ceph05 ceph06 ceph07 ceph08 ceph09 ceph10; do
  ceph orch host label add "$host" osd
done

ceph orch host label add ceph01 mon
ceph orch host label add ceph02 mon
ceph orch host label add ceph03 mon
ceph orch host label add ceph01 mgr
ceph orch host label add ceph02 mgr
ceph orch host label add ceph01 mds
ceph orch host label add ceph02 mds
```

Shell 循环仅用于展示。生产变更应有逐项输出、失败处理和幂等性，不要把长循环当作审计记录。

### 部署 MON 和 MGR

```bash
ceph orch apply mon --placement="ceph01,ceph02,ceph03"
ceph orch apply mgr --placement="2 ceph01 ceph02"
```

验证：

```bash
ceph quorum_status --format json-pretty
ceph mgr dump
ceph orch ps --daemon_type mon --refresh
ceph orch ps --daemon_type mgr --refresh
```

### 创建 OSD ServiceSpec

不要直接执行“使用所有可用设备”，先用明确的声明并预览。

`osd-2tb.yaml` 示例：

```yaml
service_type: osd
service_id: data-2tb
placement:
  label: osd
spec:
  data_devices:
    size: "1.8T:2.1T"
```

磁盘十进制/二进制显示、型号和实际容量可能不同。应用前检查匹配结果：

```bash
ceph orch apply -i osd-2tb.yaml --dry-run
```

逐台核对：

- 只匹配目标 2 TB 数据盘
- 没有匹配系统盘
- 没有匹配临时盘或维修盘
- Host 数量正好为 10

确认后：

```bash
ceph orch apply -i osd-2tb.yaml
```

观察：

```bash
ceph orch ps --daemon_type osd --refresh
ceph osd tree
ceph osd df tree
ceph -s
```

最终应有 10 个目标 OSD，分布在 10 个 Host。

## 创建 RBD

### 创建 Pool

先核对 CRUSH Rule：

```bash
ceph osd crush rule ls
ceph osd crush rule dump replicated_rule
```

创建并初始化：

```bash
ceph osd pool create rbd-prod 32 32 replicated replicated_rule --autoscale-mode=on
ceph osd pool set rbd-prod size 3
ceph osd pool set rbd-prod min_size 2
rbd pool init rbd-prod
```

让 autoscaler 了解容量目标：

```bash
ceph osd pool set rbd-prod target_size_ratio 0.6
ceph osd pool autoscale-status
```

这里的 `0.6` 表示该 Pool 预计占目标 CRUSH Root 数据量的相对比例，不是配额，也不是允许占用 60% 整个物理集群的安全承诺。

### 创建最小权限用户

```bash
ceph auth get-or-create client.rbd-prod \
  mon 'profile rbd' \
  osd 'profile rbd pool=rbd-prod' \
  -o /etc/ceph/ceph.client.rbd-prod.keyring

chmod 600 /etc/ceph/ceph.client.rbd-prod.keyring
```

### 功能验证

```bash
rbd --id rbd-prod --keyring /etc/ceph/ceph.client.rbd-prod.keyring \
  -p rbd-prod create acceptance-image --size 10G

rbd --id rbd-prod --keyring /etc/ceph/ceph.client.rbd-prod.keyring \
  -p rbd-prod info acceptance-image
```

在隔离验收客户端映射、创建文件系统、挂载并执行读写。确认测试数据后再通过 RBD 接口删除，不要操作底层 RADOS 对象。

## 创建 CephFS

使用 volume 命令创建文件系统：

```bash
ceph fs volume create cephfs-prod
```

检查自动创建的 Pool、应用标签和副本策略：

```bash
ceph fs status
ceph fs dump
ceph osd pool ls detail
```

部署 MDS：

```bash
ceph orch apply mds cephfs-prod --placement="2 ceph01 ceph02"
```

验证：

```bash
ceph fs status cephfs-prod
ceph orch ps --daemon_type mds --refresh
```

### 创建 Subvolume Group 和 Subvolume

```bash
ceph fs subvolumegroup create cephfs-prod team-a
ceph fs subvolume create cephfs-prod shared \
  --group_name team-a \
  --size 1099511627776
```

上面的大小是 1 TiB 的字节数。Quota 必须结合整个集群容量预算，不能因为命令允许就承诺全部空间。

查看路径：

```bash
ceph fs subvolume getpath cephfs-prod shared --group_name team-a
ceph fs subvolume info cephfs-prod shared --group_name team-a
```

### 创建最小权限用户

取得实际 Subvolume 路径后，使用 `ceph fs authorize` 将客户端限制到该路径：

```bash
ceph fs authorize cephfs-prod client.team-a \
  <subvolume-path> rw \
  root_squash \
  -o /etc/ceph/ceph.client.team-a.keyring
```

验证授权路径能读写，其他路径被拒绝。

## 普通客户端接入

客户端至少需要：

- Ceph 配置或 MON 地址
- 对应的 CephX keyring
- 当前版本兼容的内核客户端或 ceph-common
- 到 Public Network 的连通性

分发最小配置：

```bash
ceph config generate-minimal-conf > /etc/ceph/ceph.conf
```

不要向普通客户端分发 `client.admin` keyring。

### RBD 客户端

```bash
rbd --id rbd-prod \
  --keyring /etc/ceph/ceph.client.rbd-prod.keyring \
  -p rbd-prod ls
```

### CephFS 客户端

推荐使用挂载助手和 keyring 文件，避免将 Secret 直接放在命令行中。具体挂载语法取决于客户端版本和 CephFS 授权方式，应参考目标版本官方文档。

客户端验收：

- 重启后挂载是否恢复
- 网络短时中断后的行为
- Secret 权限是否正确
- 超出授权路径是否拒绝
- 读写延迟是否达到 SLO

## Kubernetes 接入

本案例假设 Kubernetes 在独立节点上，使用 Ceph CSI 连接外部 Ceph 集群。

### RBD StorageClass

需要准备：

- Ceph Cluster FSID
- MON 地址
- `rbd-prod` Pool
- Ceph CSI RBD 用户
- Kubernetes Secret

为 CSI 创建独立用户，不复用普通客户端或 `client.admin`：

```bash
ceph auth get-or-create client.csi-rbd \
  mon 'profile rbd' \
  osd 'profile rbd pool=rbd-prod' \
  mgr 'profile rbd pool=rbd-prod'
```

caps 应以正在使用的 Ceph CSI 官方部署文档为准，不同版本和功能需要的权限可能不同。

StorageClass 关键字段示意：

```yaml
apiVersion: storage.k8s.io/v1
kind: StorageClass
metadata:
  name: ceph-rbd
provisioner: rbd.csi.ceph.com
parameters:
  clusterID: "<ceph-fsid>"
  pool: rbd-prod
  imageFeatures: layering
  csi.storage.k8s.io/provisioner-secret-name: ceph-csi-rbd
  csi.storage.k8s.io/provisioner-secret-namespace: ceph-csi
  csi.storage.k8s.io/node-stage-secret-name: ceph-csi-rbd
  csi.storage.k8s.io/node-stage-secret-namespace: ceph-csi
reclaimPolicy: Delete
allowVolumeExpansion: true
volumeBindingMode: Immediate
```

`reclaimPolicy: Delete` 会让删除 PV 的生命周期可能继续删除后端 Image。生产环境必须按数据保留策略选择 Delete 或 Retain。

### CephFS StorageClass

CephFS CSI 需要独立最小权限身份、文件系统名称和对应 Secret。

```yaml
apiVersion: storage.k8s.io/v1
kind: StorageClass
metadata:
  name: cephfs
provisioner: cephfs.csi.ceph.com
parameters:
  clusterID: "<ceph-fsid>"
  fsName: cephfs-prod
  csi.storage.k8s.io/provisioner-secret-name: ceph-csi-cephfs
  csi.storage.k8s.io/provisioner-secret-namespace: ceph-csi
  csi.storage.k8s.io/node-stage-secret-name: ceph-csi-cephfs
  csi.storage.k8s.io/node-stage-secret-namespace: ceph-csi
reclaimPolicy: Delete
allowVolumeExpansion: true
```

不要直接复制示例上线。Ceph CSI 的 RBAC、ConfigMap、Secret 格式、sidecar 版本和 caps 要按所选 Ceph CSI 版本官方文档部署。

### Kubernetes 验收

RBD：

- 创建 RWO PVC
- Pod 挂载并写入校验文件
- 删除 Pod、在另一节点重建并校验数据
- 扩容 PVC 并验证文件系统
- 验证未授权 Namespace 无法读取 Secret

CephFS：

- 创建 RWX PVC
- 两个不同节点 Pod 同时挂载
- 一端写入，另一端读取
- 验证 Subvolume 和 Quota
- 验证回收策略

## 部署监控栈

检查 cephadm 当前服务：

```bash
ceph orch ls
ceph mgr module ls
```

根据目标版本部署或调整：

```bash
ceph orch apply prometheus
ceph orch apply alertmanager
ceph orch apply grafana
ceph orch apply node-exporter
```

生产环境要指定冗余 placement、持久化、保留时间、TLS、认证和外部通知，不应只依赖默认单实例。

### 第一层告警

至少覆盖：

| 告警 | 关注点 |
| --- | --- |
| MON Quorum 异常 | 控制面可用性 |
| OSD Down | 故障范围和持续时间 |
| PG Inactive | 数据不可访问风险 |
| PG Degraded | 冗余降低 |
| PG Inconsistent | 数据一致性 |
| Nearfull/Backfillfull/Full | 写入和恢复风险 |
| Slow Ops | 延迟与阻塞 |
| MDS 异常 | CephFS 元数据可用性 |
| RGW 5xx | 对象接口可用性 |
| 主机磁盘/网络错误 | 根因指标 |

### 容量分级

不要只设置一个 80% 告警。示例分层：

- Info：增长趋势要求开始评估扩容
- Warning：到达内部扩容执行线
- Critical：接近 Ceph nearfull 或恢复空间不足

阈值应依据当前 `mon_osd_nearfull_ratio` 等真实配置、采购周期和最大故障域计算。

### 业务探测

每 5～15 分钟在专用测试范围执行：

- RBD 小 Image 的创建或固定 Image 小块读写
- CephFS 测试目录的创建、读取、重命名、删除
- 如果部署 RGW，则执行 S3 PUT、HEAD、GET、DELETE

探测账号必须最小权限，测试数据必须有生命周期清理。

## 上线前性能基线

不要直接在生产 Pool 上使用破坏性测试参数。

建议分层测试：

### 单盘验收

- 顺序读写
- 随机读写
- 延迟分布
- 长时间稳定性
- SMART/NVMe 错误

### RADOS 基线

在专用测试 Pool 中使用 `rados bench`，明确对象大小、并发、持续时间和清理策略。

### RBD 基线

在专用 Image 上使用 fio，覆盖：

- 4 KiB 随机读
- 4 KiB 随机写
- 1 MiB 顺序读写
- 混合读写
- P95/P99 延迟

### CephFS 基线

- 大文件顺序吞吐
- 小文件创建与删除
- 目录遍历
- 多客户端并发

所有测试都要保存：

- Ceph 版本和配置
- 客户端版本
- 硬件与网络
- 测试参数
- 业务与恢复是否同时运行
- 平均值和尾延迟

## OSD 故障演练

### 演练目标

- 验证单 OSD 故障不会造成业务不可用
- 测量故障检测和恢复时间
- 验证告警、通知和 Runbook
- 验证 12 小时恢复目标

### 前置条件

- 当前 `HEALTH_OK` 或所有告警均已解释
- 所有 PG `active+clean`
- 容量足够
- 业务负责人知道演练窗口
- 监控和测试客户端在线
- 明确停止条件

### 安全注入

在测试环境可以通过编排器停止一个 OSD daemon：

```bash
ceph orch daemon stop osd.<id>
```

不要拔错物理盘，也不要用破坏设备数据的方式模拟普通 daemon 故障。

观察：

```bash
date -Is
ceph -s
ceph health detail
ceph osd tree
ceph pg stat
ceph orch ps --daemon_id <id> --refresh
```

同时持续执行 RBD 和 CephFS 业务探测。

### 恢复

```bash
ceph orch daemon start osd.<id>
```

完成标准：

- OSD 回到 `up/in`
- PG 回到预期状态
- 没有新的一致性告警
- 业务探测全程结果已记录
- 恢复时间和最大延迟已记录
- 临时告警静默已解除

如果演练超过预定时间，不要为了“做完演练”而把 OSD 标记 out 或强制执行其他高风险操作。按停止条件恢复现场并复盘。

## MON 故障演练

### 目标

验证 3 个 MON 中停止 1 个后：

- 剩余 2 个继续形成 Quorum
- 客户端 I/O 持续
- 告警能准确定位
- MON 恢复后重新加入 Quorum

确认目标 MON：

```bash
ceph quorum_status --format json-pretty
ceph orch ps --daemon_type mon --refresh
```

停止一个非唯一关键故障域内的 MON：

```bash
ceph orch daemon stop mon.<name>
```

观察：

```bash
ceph -s
ceph quorum_status --format json-pretty
```

恢复：

```bash
ceph orch daemon start mon.<name>
```

完成标准：

- 三个 MON 重新处于 Quorum 预期状态
- 没有时钟漂移和数据库异常
- 管理命令、RBD 和 CephFS 业务探测正常

不要在同一轮演练中停止第二个 MON。3 MON 集群同时丢失 2 个会失去多数派。

## 容量不足演练

### 不要真的把生产 OSD 写到 Full

真实 Full 会阻止写入并可能阻塞恢复。安全演练应该在隔离测试 Pool 中验证：

- 配额接近和达到上限
- 告警是否提前触发
- 应用如何处理写失败
- 清理和扩容 Runbook 是否可执行

### 创建测试 Pool 和配额

使用经过验证的 CRUSH Rule 创建小型实验 Pool：

```bash
ceph osd pool create capacity-drill
ceph osd pool application enable capacity-drill rados
ceph osd pool set-quota capacity-drill max_bytes 10G
```

使用独立最小权限客户端逐步写入可清理的测试对象，并观察：

```bash
ceph df detail
ceph osd pool get-quota capacity-drill
ceph health detail
```

不要为了演练修改集群 nearfull/full ratio。

### 演练响应

值班人员应该完成：

1. 识别是 `POOL_FULL` 还是 OSD/集群 Full
2. 定位增长来源
3. 通知业务并控制新增写入
4. 只删除已确认的测试数据
5. 验证写入恢复
6. 更新容量预测和扩容触发线

演练结束后通过 RADOS 接口清理测试对象，确认无引用后按审批流程删除实验 Pool。

## 滚动维护演练

选择一台没有 MON Active 单点风险的 Host：

```bash
ceph orch host maintenance enter ceph05
```

模拟重启或短时维护，回来后：

```bash
ceph orch host maintenance exit ceph05
ceph orch ps --hostname ceph05 --refresh
ceph osd tree
ceph -s
```

只有前一台完全恢复并通过业务验收后，才能维护下一台。

## 备份与恢复验证

Ceph 三副本不是备份。本项目至少要定义：

- RBD Snapshot 与异地 Export/镜像策略
- CephFS Snapshot 与外部备份策略

- Prometheus/Grafana 配置备份
- Kubernetes StorageClass、Secret 元数据和 CSI 配置备份

上线前随机选择一个测试 RBD Image 和一个 CephFS 目录执行真实恢复，并记录：

- 恢复点
- 恢复耗时
- 校验方法
- 是否需要业务停机
- Secret 和配置是否足以重建访问

## 安全验收

- 普通应用没有 `client.admin`
- 每个客户端身份限制到目标 Pool 或 CephFS 路径
- keyring 未进入 Git、镜像、工单和日志

- cephadm SSH 使用受控账号和密钥

## 本文小结

10 台 2 TB 服务器的理论计算很简单：

```text
20 TB Raw
→ 三副本约 6.67 TB 理论有效容量
→ 加入恢复、分布和增长余量后，规划约 4 TiB 业务数据
```

真正困难的是把容量数字落实成一套可运行、可观察、可维护、可恢复的系统：

```text
业务需求
→ 故障模型
→ 容量与性能预算
→ 角色、网络和 CRUSH 设计
→ cephadm 声明式部署
→ RBD/CephFS 与最小权限
→ Kubernetes 接入
→ 监控与业务探测
→ OSD/MON/容量演练
→ 验收、交接和持续改进
```

完成这个项目后，不要急着扩大规模。先重复演练、保存基线，并用真实业务数据校正规划模型。
