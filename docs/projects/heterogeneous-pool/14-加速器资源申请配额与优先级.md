# 资源申请、配额和优先级——让GPU与NPU可控地分给业务

:::info 系列与定位
**系列**：《NVIDIA＋昇腾双资源池 AI 推理集群：从 0 到部署、运维与故障排查》  
**阶段**：第四阶段——统一调度  
**本文定位**：资源治理与调度优先级篇
:::

:::tip 系列约定
资源池 A = **NVIDIA GPU**（vLLM）· 资源池 B = **华为昇腾 NPU**（vLLM-Ascend）· 同一 Kubernetes · 共享存储/网关/监控 · **禁止**跨池组成同一分布式模型实例。
:::

[第 13 篇](./13-使用Label-Taint与Affinity隔离两个资源池.md) 解决了「Pod 应该进入哪个资源池」，本篇解决另外三个生产问题：

1. 一个 Pod 到底要申请多少 CPU、内存、GPU 或 NPU  
2. 一个团队或 Namespace 最多能使用多少资源  
3. 在线服务和离线任务发生竞争时，谁应该优先运行  

本篇要建立如下治理链路：

```text
Container requests/limits
→ Scheduler 判断节点是否放得下
→ ResourceQuota 限制 Namespace 总量
→ PriorityClass 决定资源竞争顺序
→ 监控与审批控制实际使用
```

本站对照：[优先级与抢占](../../platform/gpu-cluster/scheduling-sharing/03-GPU%20集群优先级与抢占策略.md) · [多租户与资源配额](../../platform/gpu-cluster/governance/02-GPU%20多租户与资源配额设计.md)。

## 一、先分清 requests 和 limits

```yaml
resources:
  requests:
    cpu: "4"
    memory: 16Gi
  limits:
    cpu: "8"
    memory: 32Gi
```

**requests**  
调度器主要根据 requests 判断节点是否放得下 Pod。可以把它理解成：「为了让这个 Pod 正常运行，我至少需要预留多少资源。」

**limits**  
limits 描述容器允许使用的上限。CPU 和内存的执行方式不同：

- CPU 超过 limit 通常受到节流
- 内存超过 limit 可能被 OOM Kill
- 设备扩展资源不能像 CPU 那样随意超卖

官方说明：调度器使用 request 做放置决策，kubelet 和运行时负责执行 limit。见 [Resource Management for Pods and Containers](https://kubernetes.io/docs/concepts/configuration/manage-resources-containers/)。

---

## 二、GPU 和 NPU 属于扩展资源

GPU、NPU 通常通过 Device Plugin 以扩展资源的形式上报，例如：

```text
nvidia.com/gpu
<目标昇腾环境实际NPU资源键>
```

扩展资源与 CPU、内存有三个重要区别：

1. 数量只能按 API 允许的整数形式申请，不能写成半张卡  
2. 默认不能超额承诺  
3. request 和 limit 同时设置时必须相等  

稳妥的写法是同时设置相同值：

```yaml
resources:
  requests:
    nvidia.com/gpu: "1"
  limits:
    nvidia.com/gpu: "1"
```

如果 Pod 申请的扩展资源没有任何节点满足，它会保持 Pending，而不是自动降级为 CPU 执行。

**先查实际资源键**

```bash
kubectl get nodes \
  -o custom-columns='NAME:.metadata.name,CAPACITY:.status.capacity,ALLOCATABLE:.status.allocatable'

kubectl get node <NODE> -o json | \
  jq '.status.capacity, .status.allocatable'
```

不要根据文章、截图或别的集群猜昇腾资源键。

---

## 三、一个推理 Pod 不只消耗加速卡

| 资源 | 典型用途 | 配小的后果 |
|------|----------|------------|
| GPU/NPU | 权重、KV Cache、计算 | 无法启动、OOM、吞吐不足 |
| CPU | Tokenizer、请求处理、调度、数据拷贝 | TTFT 升高、GPU/NPU 吃不满 |
| 内存 | 模型加载中转、Tokenizer、缓存 | OOMKilled、启动失败 |
| ephemeral-storage | 镜像层、日志、临时文件 | Pod 被驱逐、节点磁盘压力 |
| 网络 | 拉取模型、跨卡通信、请求流量 | 启动慢、通信抖动 |
| PVC/本地盘 | 权重、缓存、日志 | 加载慢、空间耗尽 |

只写 `limits: nvidia.com/gpu: 1` 是不完整的生产配置。CPU、内存和临时存储必须通过压测和监控确定。

## 四、NVIDIA 推理 Pod 资源申请骨架

下面数值只是结构示例，不能当成任何模型的固定答案：

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: model-a-nvidia
  namespace: ai-prod
spec:
  replicas: 2
  selector:
    matchLabels:
      app: model-a-nvidia
  template:
    metadata:
      labels:
        app: model-a-nvidia
        model: model-a
        accelerator-vendor: nvidia
    spec:
      priorityClassName: ai-online-high
      tolerations:
        - key: accelerator
          operator: Equal
          value: nvidia
          effect: NoSchedule
      nodeSelector:
        accelerator.vendor: nvidia
        resource-pool: nvidia-pool
        accelerator.mode: full
      containers:
        - name: inference
          image: <内部NVIDIA推理镜像>
          resources:
            requests:
              cpu: "8"
              memory: 32Gi
              ephemeral-storage: 20Gi
              nvidia.com/gpu: "1"
            limits:
              cpu: "16"
              memory: 64Gi
              ephemeral-storage: 50Gi
              nvidia.com/gpu: "1"
```

**为什么 CPU request 和 limit 不一定相等**

| 策略 | 说明 |
|------|------|
| 相等 | 资源更可预测，QoS 更稳定，但利用率可能偏低 |
| limit 高于 request | 允许突发，但节点竞争时延迟可能抖动 |
| 不设 CPU limit | 避免不必要节流，但需要 Quota 和监控控制风险 |

生产推理不要凭习惯决定，应通过压力测试观察 CPU 节流、TTFT 和尾延迟。

## 六、如何从压测结果反推 requests

不要问「vLLM 通常配多少 CPU」，应该建立本模型、本镜像、本硬件的基线。

1. **先给足资源跑通**——确保不是因为资源不足导致假性性能问题  
2. **固定测试条件**——模型与量化、框架与镜像摘要、硬件、Token 分布、并发、TP、上下文、缓存与批处理  
3. **采集峰值与稳定值**——CPU、内存、临时盘、利用率、显存/HBM、TTFT/TPOT、吞吐与错误率  
4. **设置 requests**——`requests ≈ 稳态高分位使用量 + 安全余量`  
5. **设置 limits 和告警**——与应用承载能力、节点容量和故障方式一起评估  

---

## 七、使用 Namespace 划分责任边界

推荐从业务性质划分：

```text
ai-platform       平台控制组件
ai-prod           在线生产推理
ai-batch          离线评测与批处理
ai-dev            开发测试
gpu-operator      NVIDIA 平台组件
kube-system       Kubernetes 与昇腾基础组件等
monitoring        统一监控
```

也可以按团队拆分：`ai-team-a-prod`、`ai-team-b-prod`。但不要为每个模型创建 Namespace，否则 RBAC、Quota 和监控会过度碎片化。

Namespace 负责：RBAC、ResourceQuota、LimitRange、网络策略、成本与用量统计、资源所有者边界。

它不会自动决定 Pod 使用 NVIDIA 还是昇腾，资源池选择仍由第 13 篇规则完成。

## 八、ResourceQuota 限制 Namespace 总量

假设 `ai-prod` 最多允许：8 张 NVIDIA GPU；8 个目标 NPU 整卡资源；128 核 CPU requests；512Gi 内存 requests；最多 50 个 Pod 和 20 个 PVC。

```yaml
apiVersion: v1
kind: ResourceQuota
metadata:
  name: ai-prod-quota
  namespace: ai-prod
spec:
  hard:
    requests.cpu: "128"
    requests.memory: 512Gi
    limits.cpu: "256"
    limits.memory: 1Ti
    requests.ephemeral-storage: 500Gi
    limits.ephemeral-storage: 1Ti
    requests.nvidia.com/gpu: "8"
    requests.<实际NPU资源键>: "8"
    pods: "50"
    persistentvolumeclaims: "20"
```

注意：`requests.<实际NPU资源键>` 中的占位符需要替换为真实资源名。

Kubernetes 对扩展资源 Quota 只允许使用 `requests.` 前缀，因为扩展资源不能超额承诺。见 [Resource Quotas—Quota for extended resources](https://kubernetes.io/docs/concepts/policy/resource-quotas/#quota-for-extended-resources)。

```bash
kubectl get resourcequota -n ai-prod
kubectl describe resourcequota ai-prod-quota -n ai-prod
```

超过 Quota 时，创建或更新请求会被 API Server 拒绝并返回 403 Forbidden，不会把超过额度的 Pod 排队等资源释放。

修改 Quota 不会自动影响已有 Pod；缩减额度前要先盘点已使用量。

---

## 九、不要把资源池总容量全部分成 Quota

假设集群共有 16 张 GPU，不建议把四个团队的 Quota 都设置成 16 并认为完成了治理。

ResourceQuota 限制的是「上限」，默认不是预留和借用系统。

至少保留：平台组件需要的资源；故障迁移余量；滚动升级新旧副本并存余量；突发流量余量；节点维护导致的容量损失；紧急发布余量。

```text
物理总量
- 不可用/维修容量
- 平台保留
- 高可用保留
- 发布保留
= 可分配业务容量
```

Quota 之和可以大于当前物理总量以支持统计复用，但这会产生竞争和 Pending 风险，必须有优先级、队列和容量监控配套。

---

## 十、LimitRange 负责单个容器的默认与边界

ResourceQuota 控制 Namespace 总量；LimitRange 控制单个对象的最小、最大或默认 CPU/内存。

```yaml
apiVersion: v1
kind: LimitRange
metadata:
  name: ai-container-defaults
  namespace: ai-dev
spec:
  limits:
    - type: Container
      defaultRequest:
        cpu: "1"
        memory: 2Gi
      default:
        cpu: "4"
        memory: 8Gi
      min:
        cpu: 100m
        memory: 256Mi
      max:
        cpu: "32"
        memory: 128Gi
```

LimitRange 适合给 CPU 和内存设置默认值。GPU/NPU 数量、型号和切分规格应在平台模板或准入策略中明确声明，不要依赖一个模糊的默认加速卡。

## 十一、PriorityClass 解决谁先获得稀缺资源

| PriorityClass | 示例值 | 用途 |
|---------------|--------|------|
| ai-platform-critical | 100000 | 必要 AI 平台控制组件，严格控制使用 |
| ai-online-high | 10000 | 对外在线推理服务 |
| ai-online-normal | 5000 | 普通在线服务 |
| ai-batch | 1000 | 批处理、评测、离线任务 |
| ai-dev-low | 100 | 开发测试 |

```yaml
apiVersion: scheduling.k8s.io/v1
kind: PriorityClass
metadata:
  name: ai-online-high
value: 10000
globalDefault: false
preemptionPolicy: PreemptLowerPriority
description: "面向生产在线推理服务"
---
apiVersion: scheduling.k8s.io/v1
kind: PriorityClass
metadata:
  name: ai-batch
value: 1000
globalDefault: false
preemptionPolicy: Never
description: "可等待的离线批处理和评测任务"
```

```yaml
spec:
  priorityClassName: ai-online-high
```

## 十二、优先级不等于预留，也不能创造设备

假设高优先级 Pod 需要 4 张 GPU，但任何节点最多只有 2 张空闲 GPU：即使驱逐低优先级 Pod，如果没有一个节点能形成 4 张可用 GPU，高优先级 Pod 仍然无法调度。

优先级也不能解决：NVIDIA 工作负载只有昇腾容量；资源池 Affinity 写错；驱动或 Device Plugin 异常；模型显存超过单机容量；存储或网络不满足；节点处于不可调度状态。

见 [Pod Priority and Preemption](https://kubernetes.io/docs/concepts/scheduling-eviction/pod-priority-preemption/)。

---

## 十三、在线服务是否应该抢占离线任务

可以，但必须先回答：被抢占的离线任务能否从检查点恢复；终止是否会损坏结果或共享文件；释放 GPU/NPU 需要多长时间；在线服务冷启动和加载模型需要多长时间。

如果模型加载需要十几分钟，单纯依赖抢占未必能满足分钟级扩容。

更稳妥的组合：

```text
在线服务保有基础常驻容量
+
保留少量可用扩容容量
+
可抢占离线任务提供额外弹性
+
网关限流保护剩余实例
```

Batch 任务建议：使用较低 PriorityClass；支持断点续跑；设置合理的终止处理；结果写入持久化存储；不在容器本地保存唯一结果；设置最大运行时间和重试策略。

---

## 十四、PriorityClass 的安全治理

PriorityClass 是集群级对象，不能让所有业务随意创建和使用高优先级。

建议：仅平台管理员创建 PriorityClass；RBAC 限制高等级使用；准入策略校验 Namespace 与 PriorityClass 对应关系；高优先级工作负载必须设置 Owner 和 SLO 标签；对抢占事件和高优先级 Pending 告警；定期审计「所有业务都是最高优先级」的膨胀问题。

## 十五、双池 Quota 应该如何设计

### 模式 A：一个 Namespace 可以用两池

Quota 同时包含 `requests.nvidia.com/gpu` 与 `requests.<实际NPU资源键>`。

优点：一个团队管理简单；同一模型的两套 Deployment 放在一起；统一 RBAC 和服务发现。  
缺点：成本和用量分析需要额外标签；两套部署权限容易混淆；准入策略更复杂。

### 模式 B：按厂商拆 Namespace

例如 `team-a-nvidia`、`team-a-ascend`。

优点：Quota 和权限边界清晰；易于分别统计；降低镜像和模板误用风险。  
缺点：对象更多；网关、Secret 和配置需要跨 Namespace 治理；运维复杂度上升。

本系列默认采用「业务 Namespace + 厂商 Label」的方式，规模和权限要求更高时再拆分 Namespace。

## 十六、完整治理对象示例

```text
Namespace
├── ResourceQuota
├── LimitRange
├── Role/RoleBinding
├── NetworkPolicy
├── NVIDIA Deployment（可选）
├── Ascend Deployment（可选）
├── Service
├── ConfigMap/Secret
└── 监控与告警规则
```

资源治理不是只应用一个 Quota YAML，而是配额、权限、网络、调度和观测共同组成。

## 十七、Pending 时按什么顺序排查

1. **看事件**：`kubectl describe pod <POD> -n <NS>`  
2. **检查 Affinity 和 Taint**  
3. **检查真实 Allocatable**：区分 Capacity / Allocatable / Allocated resources  
4. **检查 Quota**：若 Pod 根本没有创建成功  
5. **检查优先级和抢占**  
6. **检查设备插件**：物理设备存在但 Allocatable 为 0 时回到第 11、12 篇  

---

## 十八、常见错误

1. **用实际利用率判断调度余量**——调度器主要根据 requests 和扩展资源分配记录判断  
2. **Quota 写成 `limits.nvidia.com/gpu`**——应使用 `requests.nvidia.com/gpu`  
3. **给 GPU 写 `500m`**——整卡扩展资源不能这样申请半张卡；切分见第 15 篇  
4. **所有工作负载都用最高 PriorityClass**——无法区分重要性  
5. **认为 PDB 绝对阻止抢占**——不要把它当作绝对禁止抢占的安全锁  
6. **只限制卡数，不限制 Pod、PVC 和临时盘**  
7. **修改 Quota 后期待旧 Pod 自动被清理**  

---

## 十九、上线验收清单

**工作负载**：CPU/内存/临时盘均有合理 request；加速器 request 与 limit 相等；使用真实扩展资源键；NodeAffinity、Toleration 和资源申请一致；PriorityClass 符合业务等级；模型压测记录可追溯。

**Namespace**：ResourceQuota 已配置；扩展资源 Quota 使用 `requests.` 前缀；LimitRange 策略明确；RBAC 限制高优先级和 Quota 修改；Pod/PVC/临时盘也有边界；已设置用量告警。

**集群**：预留维护和故障容量；预留滚动发布容量；PriorityClass 数量有限且含义明确；在线与离线抢占策略经过演练；Pending 和抢占事件纳入监控；NVIDIA 与昇腾容量分别统计。

## 二十一、本篇小结

双资源池的资源治理可以归纳为：

```text
requests 回答「调度时至少需要多少」
limits 回答「运行时最多允许多少」
扩展资源 回答「需要多少张设备」
ResourceQuota 回答「一个 Namespace 总共能用多少」
PriorityClass 回答「发生竞争时谁更重要」
```

这些机制都不能替代容量规划。它们负责执行规则，但规则仍需要根据模型压测、SLO、成本和故障余量制定。

下一篇将进入最容易被误解的主题：一张 GPU/NPU 能否分给多个 Pod，以及整卡、MIG、时间切片、vNPU 和软切分到底有什么区别。
