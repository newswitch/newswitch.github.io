# 双资源池所有服务器的系统初始化

:::info 系列与定位
**系列**：《NVIDIA＋昇腾双资源池 AI 推理集群：从 0 到部署、运维与故障排查》  
**阶段**：第三阶段——从系统环境到双池就绪  
**本文定位**：环境基线检查与实战篇
:::

:::tip 系列约定
资源池 A = **NVIDIA GPU**（vLLM）· 资源池 B = **华为昇腾 NPU**（vLLM-Ascend）· 同一 Kubernetes · 共享存储/网关/监控 · **禁止**跨池组成同一分布式模型实例。
:::

前面已经完成架构、资产和容量规划。接下来正式进入部署阶段。

系统初始化的目标不是执行一份「关闭所有安全功能」的脚本，而是让控制节点、普通工作节点、NVIDIA 节点和昇腾节点拥有一套**可验证、可重复、可回滚**的操作系统基线。

本文不会绑定某个 Linux 发行版的软件源命令。生产环境必须先用 [第 8 篇](./08-软硬件兼容矩阵与容量规划.md) 兼容矩阵确定操作系统、内核、驱动和 Kubernetes 版本，再将本文步骤转换为对应发行版的自动化脚本。

---

## 一、初始化前不要直接改系统

正式修改前，先确认：

- 服务器已经完成资产登记
- BMC 或其他带外管理可用
- 有系统配置备份或重装方案
- 已确认 NVIDIA / 昇腾支持的 OS 和内核
- 已确认 Kubernetes、CNI、CSI 支持 CPU 架构
- 维护窗口和责任人明确
- 加速器节点当前没有生产任务
- 软件包和镜像来源已经准备好

:::caution
如果没有带外入口，错误的网络、SSH 或内核配置可能让服务器彻底失联。
:::

---

## 二、先定义统一变量

建议为每台节点准备初始化参数表：

| 参数 | 示例含义 |
|------|----------|
| `NODE_NAME` | Kubernetes 节点名称 |
| `NODE_ROLE` | control-plane、worker、nvidia、ascend |
| `NODE_IP` | 节点管理 IP |
| `API_ENDPOINT` | Kubernetes API 高可用地址 |
| `DNS_SERVERS` | DNS 服务器 |
| `NTP_SERVERS` | 时间服务器 |
| `K8S_VERSION` | 计划安装版本 |
| `CONTAINER_RUNTIME` | containerd 等 CRI 运行时 |
| `POD_CIDR` | Pod 网段 |
| `SERVICE_CIDR` | Service 网段 |
| `IMAGE_REGISTRY` | 内部镜像仓库 |
| `MODEL_MOUNT` | 模型缓存或共享目录 |

不要在脚本中把所有节点写成同一个固定 IP 或主机名。

---

## 三、设置主机名和名称解析

Kubernetes Node 名称应稳定、唯一，并符合 DNS 子域名规则。

```bash
hostnamectl
hostname -f
```

设置主机名示例：

```bash
sudo hostnamectl set-hostname gpu-node-01
```

建议命名体现节点类型和编号：

```text
k8s-cp-01
k8s-cp-02
k8s-worker-01
gpu-node-01
npu-node-01
```

DNS 是首选方案；小型实验环境可以维护 `/etc/hosts`，但要保证所有节点一致。

```bash
getent hosts k8s-cp-01
getent hosts gpu-node-01
```

---

## 四、确认节点 IP 和默认路由

```bash
ip -br addr
ip route
ip route show default
```

需要确认：

- Kubernetes 使用哪一个管理 IP
- 默认路由是否经过预期网卡
- 多网卡节点是否可能选错 IP
- 存储网和 RoCE 网是否具有独立地址
- Pod 网段和 Service 网段是否与现有网络冲突

官方 kubeadm 文档指出，kubeadm 通常会从默认网关关联的接口寻找可用 IP，因此多网卡服务器必须提前验证地址选择。参考：[Creating a cluster with kubeadm](https://kubernetes.io/docs/setup/production-environment/tools/kubeadm/create-cluster-kubeadm/)。

---

## 五、统一时间、时区和时钟源

时间漂移会影响：证书验证、etcd 和控制面排障、日志关联、Prometheus 指标、分布式通信、告警时间线。

```bash
date
timedatectl
```

如果服务器统一使用北京时间：

```bash
sudo timedatectl set-timezone Asia/Shanghai
```

使用 chrony 时：

```bash
chronyc tracking
chronyc sources -v
```

验收要求：所有节点时区策略一致；NTP 源一致或可信；时间同步状态正常；节点间时间差满足企业标准。

容器一般继承宿主机时钟，时区显示问题和系统时间错误要分开判断。

---

## 六、确认操作系统、内核和 CPU 架构

```bash
cat /etc/os-release
uname -r
uname -m
lscpu
```

重点记录：

- NVIDIA 节点是否为 amd64
- 昇腾节点是 amd64 还是 arm64
- 驱动支持的内核范围
- CNI、CSI 和安全 Agent 是否支持该架构
- 内核头文件是否能与当前内核匹配
- 是否计划使用 cgroup v2

Kubernetes 推荐在支持条件满足时使用 cgroup v2，并要求 kubelet 与容器运行时在 cgroup 配置上保持一致。参考：[About cgroup v2](https://kubernetes.io/docs/concepts/architecture/cgroups/)。

不要在加速器节点上自动升级内核而不评估驱动。生产环境应将内核变更纳入兼容矩阵和维护窗口。

---

## 七、Swap 应该怎么处理

传统 Kubernetes 安装教程经常直接执行 `swapoff -a`。

当前 Kubernetes 已经支持经过配置的 Linux 节点 Swap，但默认情况下，kubelet 在检测到 Swap 时仍不会启动；要启用 Swap 需要显式配置 `failSwapOn` 和 `memorySwap` 策略。参考：[Swap memory management](https://kubernetes.io/docs/concepts/architecture/nodes/#swap-memory)。

因此有两种选择。

### 方案 A：统一关闭 Swap

适合希望配置简单、行为容易预测的加速器集群。

```bash
swapon --show
free -h
sudo swapoff -a
```

还需要根据发行版正确处理开机配置，不能只临时关闭。

### 方案 B：明确启用 Kubernetes Swap 能力

必须确认 Kubernetes 版本、kubelet 配置、cgroup 和业务策略，并完成压力测试。

本系列默认采用**方案 A**，除非兼容矩阵明确批准方案 B。

---

## 八、加载容器与网络常用内核模块

常见基线包括：

```bash
sudo modprobe overlay
sudo modprobe br_netfilter
lsmod | grep -E 'overlay|br_netfilter'
```

设置开机加载时，应通过发行版支持的模块配置文件持久化。

常见网络参数示例：

```text
net.ipv4.ip_forward=1
net.bridge.bridge-nf-call-iptables=1
net.bridge.bridge-nf-call-ip6tables=1
```

实际值要结合 CNI 插件和 IPv4/IPv6 方案确认。不要把不理解的内核参数整段复制到生产环境。

```bash
sysctl net.ipv4.ip_forward
sysctl net.bridge.bridge-nf-call-iptables
```

---

## 九、防火墙和 SELinux 不要一关了之

很多入门教程直接关闭防火墙与 SELinux，这不适合作为长期生产规范。

正确流程是：根据 Kubernetes、CNI、网关、存储和监控列出端口；确认节点间允许的方向；为控制面、工作节点和存储节点分别制定规则；根据 NVIDIA GPU Operator 和昇腾组件要求处理 SELinux；在启用安全策略的状态下完成验收。

```bash
getenforce 2>/dev/null || true
systemctl status firewalld 2>/dev/null || true
systemctl status ufw 2>/dev/null || true
```

如果实验阶段暂时放宽策略，也必须记录，不能把临时操作当成生产结果。

---

## 十、准备容器运行时目录和磁盘

至少规划：

```text
/var/lib/containerd    容器运行时数据
/var/lib/kubelet       kubelet 数据
/data/models           模型缓存或挂载入口
/data/logs             业务日志（如采用本地目录）
/data/tmp              临时文件
```

具体目录可以调整，但要避免所有数据都写入根分区。

```bash
lsblk -o NAME,SIZE,TYPE,FSTYPE,MOUNTPOINTS,MODEL
df -hT
findmnt
```

需要设置：文件系统、挂载参数、开机自动挂载、目录所有者与权限、磁盘监控和告警阈值、日志轮转。

---

## 十一、SSH、用户和权限基线

建议：禁止多人共享一个无审计账号；使用密钥认证；限制直接 root 登录；使用 sudo 授权；记录运维入口；对 BMC、SSH 和 Kubernetes 权限分别管理；不把密码、Token 和私钥写入初始化脚本仓库。

```bash
id
groups
sudo -l
```

---

## 十二、检查 DNS、镜像仓库和软件源

```bash
getent hosts <内部镜像仓库域名>
curl -I https://<内部镜像仓库域名> 2>/dev/null
```

需要验证：系统软件源可访问；Kubernetes 软件包源可访问；内部 Harbor 可访问；证书链可信；离线环境所需包和镜像已经同步；amd64 与 arm64 镜像都已准备；代理和 `NO_PROXY` 包含集群内部地址。

---

## 十三、节点级资源预留

模型 Pod 不能使用节点全部 CPU 和内存。应为以下进程预留资源：操作系统、sshd 和系统服务、kubelet、containerd、CNI 和 CSI、Device Plugin、GPU/NPU 监控、日志 Agent。

后续可以通过 kubelet 的 `system-reserved`、`kube-reserved` 和驱逐阈值实现更明确的节点保护。

资源预留需要基于压测和节点规模确定，不能所有机器照抄同一数值。

---

## 十四、只读基线检查脚本示例

先用只读检查脚本采集，不要把修改动作和检查动作混在一起：

```bash
#!/usr/bin/env bash
set -u

echo '[hostname]'
hostnamectl 2>/dev/null || hostname

echo '[os]'
cat /etc/os-release
uname -a

echo '[cpu]'
lscpu

echo '[memory]'
free -h

echo '[swap]'
swapon --show

echo '[network]'
ip -br addr
ip route

echo '[time]'
timedatectl 2>/dev/null || date

echo '[disk]'
lsblk -o NAME,SIZE,TYPE,FSTYPE,MOUNTPOINTS,MODEL
df -hT

echo '[cgroup]'
stat -fc %T /sys/fs/cgroup 2>/dev/null || true

echo '[kernel modules]'
lsmod | grep -E 'overlay|br_netfilter' || true

echo '[accelerator]'
command -v nvidia-smi >/dev/null && nvidia-smi || true
command -v npu-smi >/dev/null && npu-smi info || true
```

生产脚本应增加主机名、时间和输出文件管理，并避免输出密钥等敏感信息。

## 十五、系统初始化验收清单

- [ ] 主机名唯一且符合规范
- [ ] 管理 IP、路由和 DNS 正常
- [ ] 时区与 NTP 同步正常
- [ ] OS、内核、CPU 架构已进入兼容矩阵
- [ ] Swap 策略明确
- [ ] cgroup 模式已确认
- [ ] 内核模块和网络转发满足 CNI 要求
- [ ] 防火墙和 SELinux 策略已记录
- [ ] 系统盘、镜像盘和模型缓存盘已规划
- [ ] SSH、sudo 和审计满足要求
- [ ] 软件源、镜像仓库和证书可用
- [ ] amd64/arm64 依赖已经验证
- [ ] 带外管理和回滚入口可用
- [ ] 节点基线采集结果已归档

## 十六、本篇小结

系统初始化的核心不是「执行一组固定命令」，而是建立统一且经过兼容验证的节点基线：

```text
身份与网络
+ 时间与 DNS
+ OS、内核和 CPU 架构
+ cgroup 与 Swap 策略
+ 容器和网络内核能力
+ 安全策略
+ 磁盘与目录
+ 软件源和镜像仓库
+ 检查与回滚
```

下一篇将在这套基线上安装 CRI 容器运行时和 kubeadm，部署高可用 Kubernetes 控制面并加入两类工作节点。
