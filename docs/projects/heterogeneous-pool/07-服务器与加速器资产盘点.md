# 服务器与GPU/NPU资产盘点

:::info 系列与定位
**系列**：《NVIDIA＋昇腾双资源池 AI 推理集群：从 0 到部署、运维与故障排查》  
**阶段**：第二阶段——双资源池架构设计  
**本文定位**：资产盘点实战篇
:::

:::tip 系列约定
资源池 A = **NVIDIA GPU**（vLLM）· 资源池 B = **华为昇腾 NPU**（vLLM-Ascend）· 同一 Kubernetes · 共享存储/网关/监控 · **禁止**跨池组成同一分布式模型实例。
:::

AI 集群规划最常见的问题之一，是先决定部署方案，再去确认服务器到底有什么硬件。结果往往是镜像架构不匹配、驱动无法安装、模型卡数估算错误，或者高速网卡与加速器拓扑不合理。

正确顺序应该是：

```text
盘点真实资产
→ 建立兼容矩阵
→ 计算容量
→ 设计集群
→ 部署与验收
```

本文将产出一份可用于设计、部署、监控和故障处理的资产清单。模板见 [附录 C](./附录C-服务器资产清单模板.md)。

---

## 一、为什么不能只记录「8 卡服务器」

「一台 8 卡服务器」缺少大量关键信息：GPU/NPU 型号与显存/HBM、卡间互联、CPU 架构与 NUMA、网卡与 RoCE、本地盘类型、OS/内核、驱动与固件、机房机柜等。

这些信息会直接影响：镜像能否运行、模型能否加载、Tensor Parallel 如何分卡、多机通信性能、存储缓存策略、故障域和副本分布、驱动升级和备件管理。

---

## 二、建议的资产清单字段

### 1. 基础身份信息

| 字段 | 示例含义 |
|------|----------|
| 资产编号 | 企业内部唯一编号 |
| 主机名 | Kubernetes Node 名称候选 |
| 管理 IP | SSH 和集群管理网络 |
| BMC 地址 | 带外管理地址，不应公开展示 |
| 机房/可用区 | 故障域 |
| 机柜/机位 | 物理位置 |
| 服务器厂商型号 | 备件与支持依据 |
| 计划角色 | 控制面、普通节点、GPU 节点、NPU 节点等 |

### 2. CPU 和内存

| 字段 | 作用 |
|------|------|
| CPU 架构 | 决定 amd64 或 arm64 镜像 |
| CPU 型号 | 计算能力和兼容性 |
| Socket 数量 | NUMA 与进程绑定依据 |
| 核数/线程数 | 请求处理和数据准备能力 |
| NUMA 节点数 | 设备、网卡与 CPU 亲和性 |
| 总内存 | 模型加载、缓存和 Pod 容量 |
| 内存条分布 | 硬件性能和故障分析 |

### 3. GPU/NPU

| 字段 | 作用 |
|------|------|
| 设备厂商 | NVIDIA 或昇腾 |
| 设备型号 | 兼容矩阵和容量规划 |
| 设备数量 | 单机并行规模 |
| 单卡显存/HBM | 模型是否能放入 |
| 设备序号 | 拓扑与故障定位 |
| UUID/芯片标识 | 资产和监控映射 |
| 驱动版本 | 计算栈兼容性 |
| 固件版本 | 昇腾等设备的重要兼容项 |
| 互联方式 | PCIe、NVLink、HCCS 等 |
| 健康状态 | 是否存在错误、掉卡或降级 |

### 4. 网络

| 字段 | 作用 |
|------|------|
| 网卡型号 | 驱动和性能能力 |
| 端口数量 | 网络冗余和用途划分 |
| 端口速率 | 业务、存储和多机通信容量 |
| MAC/IP | 网络配置与排障 |
| MTU | RoCE 和集群网络一致性 |
| RDMA/RoCE 能力 | 多机集合通信 |
| NUMA 归属 | 网卡与加速器亲和性 |
| Bond/VLAN | 高可用与网络隔离 |

### 5. 存储

| 字段 | 作用 |
|------|------|
| 系统盘 | 操作系统和容器运行时 |
| 数据盘 | 镜像、日志和模型缓存 |
| 介质类型 | HDD、SATA SSD、NVMe |
| 容量 | 模型和镜像存放能力 |
| RAID 方式 | 性能与可靠性 |
| 挂载点 | Kubernetes 和模型目录规划 |
| 文件系统 | ext4、XFS 等 |
| 健康状态 | SMART、坏盘和寿命 |

### 6. 软件基线

| 字段 | NVIDIA 节点 | 昇腾节点 |
|------|-------------|----------|
| 操作系统 | 必填 | 必填 |
| 内核 | 必填 | 必填 |
| 驱动 | NVIDIA 驱动 | 昇腾驱动 |
| 固件 | 按设备记录 | 必填且重点记录 |
| 计算栈 | CUDA 兼容信息 | CANN 版本 |
| 容器运行时 | containerd 等 | containerd 等 |
| 设备容器组件 | Container Toolkit | 昇腾容器运行环境 |
| Device Plugin | 版本 | 版本 |
| 推理框架 | vLLM | vLLM-Ascend |

## 三、Linux 基础信息采集

**操作系统和内核**

```bash
cat /etc/os-release
uname -a
uname -r
```

**CPU 架构和拓扑**

```bash
uname -m
lscpu
lscpu -e
```

重点关注：Architecture、CPU 数量、Socket、Core、Thread、NUMA Node、虚拟化能力。

如果安装了 `numactl`，可以查看：

```bash
numactl --hardware
```

**内存**

```bash
free -h
cat /proc/meminfo
```

**PCIe 设备与拓扑**

```bash
lspci
lspci -tv
```

可以从中确认加速器、网卡、NVMe 和 PCIe 桥接关系。

---

## 四、NVIDIA 资产采集

**查看设备和驱动**

```bash
nvidia-smi
```

至少记录：驱动版本、GPU 型号与数量、总显存和已用显存、温度/功耗/利用率、当前进程、是否存在错误状态。

**查看 GPU 列表和唯一标识**

```bash
nvidia-smi -L
```

**查看拓扑**

```bash
nvidia-smi topo -m
```

拓扑矩阵可以帮助判断：GPU 之间是否通过 NVLink 连接；是否跨 CPU Socket；GPU 与网卡是否位于相近 NUMA；Tensor Parallel 应该优先选择哪些卡。

**查看更详细信息**

```bash
nvidia-smi -q
```

输出较长，建议保存到资产采集文件中，而不是每次人工查看。更多命令说明见 [nvidia-smi 常用命令](../../foundations/compute/gpu/06-nvidia-smi%20常用命令与指标说明.md)。

---

## 五、昇腾资产采集

**查看 NPU 状态**

```bash
npu-smi info
```

至少记录：NPU 型号和数量、芯片或设备编号、HBM 总量和占用、利用率、温度和功耗、健康状态、当前运行进程、驱动和固件相关信息。

**查看 PCIe 识别情况**

```bash
lspci
lspci -tv
```

不同型号和版本的 `npu-smi` 子命令、字段可能不同，采集脚本必须先在目标设备上验证，不能直接照搬其他型号输出解析规则。

:::caution 为什么固件必须纳入资产清单
昇腾环境的兼容关系不仅涉及驱动和 CANN，还可能涉及固件。只记录 CANN 版本而忽略固件，会让升级和故障复现缺少关键依据。
:::

## 六、网络资产采集

```bash
ip -br addr
ip link show
ethtool <网卡名称>
ethtool -i <网卡名称>
ip route
ip rule
```

查看网卡 PCIe 和 NUMA 位置：

```bash
ethtool -i <网卡名称>
lspci -s <PCI地址> -vv
```

结合 `lspci -tv`、`lscpu` 和设备拓扑工具，可以判断网卡与加速器是否跨 NUMA。

RDMA 检查入口会在多机通信文章中展开。资产阶段至少要回答：哪些网卡支持 RDMA/RoCE；每个端口速率；计划使用哪个网段；MTU；网卡对应哪个 NUMA；是否存在冗余链路。

---

## 七、磁盘资产采集

```bash
lsblk -o NAME,SIZE,TYPE,FSTYPE,MOUNTPOINTS,MODEL
df -hT
findmnt
fdisk -l
```

生产环境还应采集磁盘健康、寿命和错误信息。

模型节点至少要区分：

```text
系统盘
容器镜像盘
模型缓存盘
日志盘
临时计算盘
```

如果所有数据都写入系统盘，容易因模型下载、镜像层或日志增长导致节点根分区被写满。

## 八、如何读懂 NUMA 和设备拓扑

一台双路服务器通常存在多个 NUMA 节点。某块 GPU/NPU 和某张高速网卡可能更靠近某个 CPU Socket。

如果进程、设备和网卡跨 NUMA 访问，可能增加数据传输开销。

资产盘点要建立关系：

```text
CPU Socket / NUMA
├── GPU/NPU 设备
├── 高速网卡
└── NVMe 设备
```

多卡多机部署时，应尽量让参与同一任务的设备、CPU 线程和通信网卡使用合理拓扑，而不是只按设备编号顺序选择。

:::tip
设备编号不一定等于物理拓扑顺序，必须用实际工具确认。
:::

## 九、资产信息如何转换为 Kubernetes 标签

资产清单是事实源，Kubernetes Label 是调度使用的简化结果。

例如：

```text
accelerator.vendor=nvidia
accelerator.model=<型号>
accelerator.memory-class=large
resource-pool=nvidia-pool
network.rdma=true
storage.local-nvme=true
topology.kubernetes.io/zone=zone-a
```

不要把所有资产字段都变成 Label。Label 适合保存调度真正需要、取值稳定且数量有限的信息。

设备 UUID、序列号、BMC 地址等敏感或高基数字段应保存在资产系统中，不适合作为普通 Kubernetes Label 公开传播。

## 十、推荐的资产表结构

| 分类 | 字段示例 |
|------|----------|
| 身份 | 资产编号、主机名、管理 IP、机房、机柜 |
| 系统 | OS、内核、CPU 架构、计划角色 |
| CPU | 型号、Socket、核心、NUMA |
| 内存 | 总容量、通道和健康状态 |
| 加速器 | 厂商、型号、数量、内存、UUID、互联 |
| 软件栈 | 驱动、固件、CUDA/CANN、Device Plugin |
| 网络 | 网卡、速率、IP、MTU、RoCE、NUMA |
| 存储 | 磁盘、容量、介质、RAID、挂载点 |
| 运维 | BMC、保修、责任人、最近变更时间 |

资产表必须有「采集时间」和「最后验证时间」，否则很难判断信息是否仍然有效。

## 十一、盘点完成后的验收问题

每台加速器节点都应该回答：

1. CPU 架构是什么？
2. 操作系统和内核是什么？
3. 有多少 GPU/NPU，具体型号是什么？
4. 每张卡有多少显存/HBM？
5. 驱动和固件版本是什么？
6. 卡间互联是什么？
7. 高速网卡数量、速率和 NUMA 位置是什么？
8. 本地 NVMe 是否存在，容量是多少？
9. 服务器位于哪个故障域？
10. 当前是否有硬件告警或异常进程？
11. 是否具备 BMC 远程管理能力？
12. 计划加入哪个资源池？

任何关键问题没有答案，都应该在兼容评估和部署前补齐。

## 十三、本篇小结

可靠的 AI 集群规划不能从「有多少张卡」开始，而要从完整资产事实开始：

```text
服务器身份
+ CPU 和内存
+ GPU/NPU 型号与设备内存
+ 驱动、固件和计算栈
+ PCIe 与 NUMA 拓扑
+ 网卡与 RoCE 能力
+ 本地磁盘与共享存储
+ 机房和故障域
```

下一篇将使用这些资产数据建立 NVIDIA 与昇腾兼容矩阵，并计算模型权重、KV Cache、副本、网络、存储和冗余容量。
