# 为什么一个集群要划分NVIDIA与昇腾两个算力池

:::info 系列与定位
**系列**：《NVIDIA＋昇腾双资源池 AI 推理集群：从 0 到部署、运维与故障排查》  
**阶段**：第二阶段——双资源池架构设计  
**本文定位**：需求与选型篇
:::

:::tip 系列约定
资源池 A = **NVIDIA GPU**（vLLM）· 资源池 B = **华为昇腾 NPU**（vLLM-Ascend）· 同一 Kubernetes · 共享存储/网关/监控 · **禁止**跨池组成同一分布式模型实例。
:::

把 NVIDIA GPU 和昇腾 NPU 放入同一个 Kubernetes 集群，并不只是多贴几个节点标签。它会带来两套驱动、两套计算栈、两套推理镜像和两套专项运维方法。

因此，在开始部署之前必须先回答：

> 为什么要建设双资源池，而不是只使用一种加速器，或者直接建设两个独立集群？

本文不讲具体安装命令，而是帮助你判断双资源池的业务价值、适用边界和建设成本。

---

## 一、先明确什么是「双资源池」

本系列中的双资源池是：

```text
一个 Kubernetes 控制面
├── NVIDIA GPU 资源池
└── 昇腾 NPU 资源池
```

**两个资源池共享：**

- Kubernetes 管理体系
- 网络、DNS 和服务发现
- NFS、CephFS 或对象存储
- Harbor 镜像仓库
- AI 网关
- Prometheus、Grafana 和日志平台
- Namespace、RBAC、配额和审计能力

**两个资源池分别维护：**

- 设备驱动和固件
- CUDA 与 CANN
- 容器运行环境
- Device Plugin
- vLLM 与 vLLM-Ascend 镜像
- NCCL 与 HCCL 通信链路
- 设备监控与故障手册

:::caution
它不是把 GPU 和 NPU 拼成一个更大的模型实例，而是把两套独立推理能力纳入统一平台。
:::

---

## 二、建设双资源池的六个主要原因

### 1. 不同模型对硬件和推理框架的兼容程度不同

同一个模型是否能够在某类加速器上运行，取决于：

- 模型结构
- 算子支持
- 数据精度
- 量化格式
- 推理框架版本
- 驱动和计算栈
- 是否存在经过验证的部署方案

有些模型在 NVIDIA 上已经非常成熟，有些模型在昇腾上已经完成适配，还有一些模型只能在某一侧满足生产要求。

双资源池允许平台按照模型兼容性选择运行位置，而不是要求所有模型强行使用一种硬件。

### 2. 国产化和供应链要求

部分业务可能有国产化、供应链安全或自主可控要求，需要优先使用昇腾资源池；另一些业务可能依赖 NVIDIA 生态中的特定模型、算子或工具。

双池可以形成：

```text
普通兼容业务 → 优先昇腾
尚未完成适配的业务 → NVIDIA 承载
关键业务 → 双边分别部署并验证
```

这样可以逐步迁移，而不是一次性替换全部模型服务。

### 3. 性能和成本不同

硬件采购成本只是总成本的一部分，还要考虑：

- 单卡可承载模型大小
- 每秒输出 Token
- 首 Token 延迟
- 单机卡数和互联拓扑
- 功耗
- 软件适配工作量
- 运维人员学习成本
- 故障恢复时间

同一个模型可能在一类硬件上更快，在另一类硬件上更便宜。双资源池让调度策略可以同时考虑性能、成本和兼容性。

### 4. 在线和离线任务需要隔离

在线推理强调：低延迟、稳定并发、快速故障恢复、服务不能被长任务占满。

离线评测、批量生成或数据处理更关注总体吞吐，可以容忍更长等待。

可以根据业务特点设计：

```text
资源池或节点组 1：在线模型服务
资源池或节点组 2：批处理与离线任务
```

这里的在线 / 离线划分可以继续叠加在 NVIDIA、昇腾资源池内部，而不是简单认为 NVIDIA 一定在线、昇腾一定离线。

### 5. 提供服务层容灾能力

如果同一个模型已经分别在两类硬件上完成适配和验证，就可以形成两套独立副本：

```text
模型A-NVIDIA 服务
模型A-昇腾 服务
```

网关能够执行：权重分流、主备切换、灰度迁移、一个资源池故障后的请求级降级。

这种容灾不是正在运行的 Pod 热迁移，而是预先部署两个可独立服务的后端，由网关改变请求方向。

### 6. 统一平台可以减少重复建设

如果完全建设两个独立集群，通常需要重复维护两套控制面、CNI/CSI、Ingress、监控日志、权限审计和模型发布流程。

统一集群可以复用公共平台能力，让差异主要保留在计算节点和模型运行时中。

## 三、三种建设方案怎么选

### 方案一：只建设一种资源池

```text
一个 Kubernetes 集群
└── 单一厂商加速器
```

| | 说明 |
|--|------|
| 优点 | 架构简单；镜像和驱动统一；调度与监控简单；运维学习成本低 |
| 缺点 | 模型兼容范围受限；供应链和硬件选择单一；缺少跨硬件服务容灾；后续新增另一类设备时需要改造 |
| 适合 | 硬件和模型已经完全确定、规模较小的环境 |

### 方案二：建设两个独立 Kubernetes 集群

```text
NVIDIA Kubernetes 集群
昇腾 Kubernetes 集群
```

| | 说明 |
|--|------|
| 优点 | 故障域清晰；两边可独立升级；OS/架构/组件版本限制较少；一集群异常不易影响另一控制面 |
| 缺点 | 公共组件重复建设；跨集群发布和路由复杂；资源/权限/审计/监控难统一；日常运维工作量更大 |
| 适合 | 规模很大、不同团队管理，或两边基础环境差异过大 |

### 方案三：一个集群划分两个资源池

```text
统一 Kubernetes 控制面
├── NVIDIA 资源池
└── 昇腾 资源池
```

| | 说明 |
|--|------|
| 优点 | 统一 API 和管理入口；复用网络/存储/网关/监控；发布流程易标准化；便于统一模型服务平台与双池路由 |
| 缺点 | 节点类型复杂；需兼容不同 CPU 架构；调度隔离必须准确；控制面变更需评估所有资源池；需掌握两套硬件栈 |
| 本系列 | **选择方案三** |

## 四、什么情况下不建议强行使用一个集群

统一集群不是永远正确。如果存在以下情况，应认真评估两个独立集群：

- 两类节点处于完全隔离的网络安全域
- 由不同组织维护，权限边界不能共享
- Kubernetes 版本或基础组件无法统一
- CNI、CSI 在其中一种 CPU 架构上不受支持
- 两边需要完全不同的升级周期
- 单一控制面故障风险不可接受
- 集群规模已经大到需要按故障域拆分
- 合规要求禁止共享控制面或存储

架构目标应该是降低整体复杂度，而不是为了「看起来统一」制造更多耦合。

## 五、双资源池必须解决的五个核心问题

### 1. 节点如何分类

需要统一设计 Node Label，例如：

```text
accelerator.vendor=nvidia
accelerator.vendor=ascend
resource-pool=nvidia-pool
resource-pool=ascend-pool
```

还要记录型号、设备内存、CPU 架构、网络能力和故障域。

### 2. 工作负载如何避免误调度

必须结合：Label、Taint、Toleration、NodeAffinity、GPU/NPU 扩展资源申请。

只使用 Label 而不申请设备，或者只申请设备而不约束节点，都可能留下管理漏洞。

### 3. 模型制品如何管理

至少需要区分：

```text
原始模型权重
NVIDIA 专用量化或优化产物
昇腾专用转换或编译产物
NVIDIA 运行镜像
昇腾运行镜像
部署清单和兼容矩阵
```

### 4. 服务接口如何统一

两边底层不同，但可以提供相同的 OpenAI 兼容接口。网关需要知道：

- 模型部署在哪些资源池
- 每个后端是否健康
- 当前容量和超时
- 是否允许跨池切流
- 两个后端的功能是否一致

### 5. 运维责任如何划分

| 公共运维 | 资源池专项运维 |
|----------|----------------|
| Kubernetes、网络和存储 | 设备驱动、计算栈 |
| 网关、监控和日志 | Device Plugin、多卡通信 |
| 发布平台 | 设备故障、推理框架兼容 |

如果责任边界没有提前定义，发生故障时很容易在平台、网络和模型团队之间反复转交。

## 六、模型应该如何选择资源池

可以建立一个初步决策顺序：

```text
模型是否兼容该资源池？
  ↓ 是
能否满足精度和功能要求？
  ↓ 是
能否满足延迟和吞吐 SLO？
  ↓ 是
容量和成本是否合适？
  ↓ 是
是否需要双池容灾？
```

示例决策表：

| 模型/业务 | NVIDIA | 昇腾 | 推荐策略 |
|-----------|--------|------|----------|
| 已在两侧完成验证的核心模型 | 支持 | 支持 | 双池部署，网关切流 |
| 暂未完成昇腾适配的模型 | 支持 | 未验证 | 暂时部署 NVIDIA |
| 国产化要求明确的业务 | 可选 | 支持 | 优先昇腾，保留验证方案 |
| 大批量离线生成 | 支持 | 支持 | 根据成本和空闲容量分配 |
| 低延迟在线接口 | 支持 | 支持 | 根据真实压测选择主资源池 |

这里不能凭硬件宣传参数直接决策，必须用目标模型和真实请求压测。

---

## 七、双资源池不是天然容灾

很多架构图画出两个资源池后，就直接写「互为容灾」。实际上，至少满足以下条件才具备切流基础：

- 两边都部署了同一业务所需模型
- 模型版本和 Tokenizer 经过确认
- 最大上下文和功能能力基本一致
- 流式输出、Tool Calling 等接口行为兼容
- 两边都通过压力测试
- 网关持续检查后端健康
- 备用资源池预留足够容量
- 已经执行过切换和回切演练

如果备用池没有预热、没有容量或没有部署对应模型，它只是另一批硬件，不是容灾系统。

---

## 八、建设双资源池的成本

双资源池会增加：软件兼容测试量、镜像构建和扫描、驱动/固件/计算栈升级风险、监控指标标准化、两套故障手册、模型双边验证、备份容量与预热、运维培训等成本。

建设前应形成明确目标，例如：

```text
目标1：哪些模型必须支持昇腾
目标2：哪些模型必须双池部署
目标3：双池切换需要达到什么 RTO
目标4：备用资源需要保留多少容量
目标5：哪些组件统一，哪些组件分别维护
```

选择一个核心模型，检查它是否已经在两类资源池完成模型、接口、性能和容量验证。

## 十、本篇小结

一个集群划分 NVIDIA 和昇腾两个资源池，主要价值是：

1. 同时承载不同兼容范围的模型
2. 满足国产化与多硬件路线要求
3. 根据性能、成本和容量选择资源池
4. 复用 Kubernetes、存储、网关和监控
5. 为同模型双边部署和服务层切流提供基础

但它也会带来两套软件栈、两套镜像和两套运维体系。是否使用统一集群，应基于网络、安全、规模、团队边界和基础组件兼容性决定。
