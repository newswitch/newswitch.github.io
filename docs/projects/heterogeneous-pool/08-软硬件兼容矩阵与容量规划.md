# 软硬件兼容矩阵与AI推理集群容量规划

:::info 系列与定位
**系列**：《NVIDIA＋昇腾双资源池 AI 推理集群：从 0 到部署、运维与故障排查》  
**阶段**：第二阶段——双资源池架构设计  
**本文定位**：兼容与容量规划篇
:::

:::tip 系列约定
资源池 A = **NVIDIA GPU**（vLLM）· 资源池 B = **华为昇腾 NPU**（vLLM-Ascend）· 同一 Kubernetes · 共享存储/网关/监控 · **禁止**跨池组成同一分布式模型实例。
:::

资产盘点回答「我们拥有什么」，兼容矩阵回答「这些组件能否一起工作」，容量规划回答「这些资源能承载多少模型和请求」。

这一步如果做错，后续可能出现：驱动装好但 PyTorch 用不了设备；模型能启动但高并发 OOM；单机正常但多机通信失败；平时副本够却扛不住节点故障；存储容量够但启动吞吐不足；两边接口看似相同但功能不一致。

模板见 [附录 B](./附录B-软硬件兼容矩阵模板.md)；NVIDIA 侧容量也可对照 [vLLM 显存组成](../../ai-systems/inference/serving/02-vLLM%20GPU%20显存组成与容量规划.md)、[GPU 容量规划](../../platform/gpu-cluster/governance/03-GPU%20集群容量规划方法.md)。

---

## 一、为什么必须建立兼容矩阵

AI 计算环境不是一个软件包，而是一条依赖链。

**NVIDIA 链路**

```text
GPU 型号
→ 服务器与 BIOS
→ 操作系统与内核
→ NVIDIA 驱动
→ CUDA 兼容能力
→ NVIDIA Container Toolkit
→ PyTorch
→ vLLM
→ 模型与量化格式
```

**昇腾链路**

```text
NPU 型号
→ 服务器与 CPU 架构
→ 操作系统与内核
→ 驱动和固件
→ CANN
→ 昇腾容器运行环境
→ torch_npu
→ vLLM-Ascend
→ 模型与模型制品格式
```

升级任何一层，都可能影响上层和下层。

所以「安装最新版」不是兼容策略。正确方法是选择一套经过官方文档、项目支持列表和实际测试共同验证的组合，并把组合视为一个整体版本基线。

---

## 二、兼容矩阵应该记录哪些内容

### NVIDIA 资源池矩阵

| 分类 | 应记录内容 |
|------|------------|
| 硬件 | 服务器型号、GPU 型号、卡数、显存、互联 |
| 系统 | OS 版本、CPU 架构、内核 |
| 驱动 | NVIDIA 驱动版本 |
| 计算栈 | CUDA 兼容范围和所需运行库 |
| 容器 | containerd、Container Toolkit |
| K8s | Kubernetes、Device Plugin/GPU Operator |
| 框架 | Python、PyTorch、vLLM |
| 模型 | 模型版本、dtype、量化格式、最大上下文 |
| 通信 | NCCL、网卡、RoCE 配置 |
| 验证 | 单卡、多卡、多机、性能和稳定性结果 |

### 昇腾资源池矩阵

| 分类 | 应记录内容 |
|------|------------|
| 硬件 | 服务器型号、NPU 型号、卡数、HBM、互联 |
| 系统 | OS 版本、CPU 架构、内核 |
| 设备层 | 驱动和固件版本 |
| 计算栈 | CANN 版本及组件 |
| 容器 | containerd、昇腾容器运行环境 |
| K8s | Kubernetes、Ascend Device Plugin |
| 框架 | Python、PyTorch、torch_npu、vLLM-Ascend |
| 模型 | 模型版本、dtype、量化/转换格式、上下文 |
| 通信 | HCCL、网卡、RoCE 配置 |
| 验证 | 单 NPU、多 NPU、多机、性能和稳定性结果 |

---

## 三、兼容矩阵不是「版本登记表」

仅记录已安装版本还不够，还要记录状态：

| 状态 | 含义 |
|------|------|
| 计划 | 准备验证，尚未测试 |
| 安装通过 | 软件能够安装，设备可识别 |
| 功能通过 | 模型接口和核心功能正常 |
| 性能通过 | 达到 TTFT、TPOT 和吞吐要求 |
| 稳定性通过 | 长时间压测无异常 |
| 生产批准 | 已完成安全、备份和回滚评审 |
| 禁止组合 | 已知不兼容或存在严重风险 |

每套组合还应保存：测试日期、测试节点、镜像摘要、模型版本、启动参数、测试报告、已知问题、回滚版本。

---

## 四、CPU 架构和镜像兼容不能忽略

双池环境中可能出现：

```text
NVIDIA 节点：x86_64 / amd64
昇腾节点：x86_64 或 aarch64 / arm64
```

如果镜像只有 amd64 版本，就不能直接在 arm64 节点运行。

需要检查：基础镜像是否支持目标架构；Python Wheel 是否有目标架构构建；CNI、CSI 和监控 Agent 是否提供相应镜像；自研程序是否能够构建 Multi-Arch 镜像；镜像清单是否包含正确架构；NodeAffinity 是否防止架构误调度。

统一 Kubernetes 并不会自动解决二进制架构兼容问题。

---

## 五、先计算模型权重占用

模型权重的理论占用可以粗略估算为：

```text
权重占用 ≈ 参数量 × 每个参数字节数
```

| 精度 | 每参数理论字节数 |
|------|------------------|
| FP32 | 4 |
| FP16/BF16 | 2 |
| INT8 | 1 |
| INT4 | 约 0.5 |

例如一个 7B 参数模型使用 BF16，仅权重理论值约为：

```text
70亿 × 2 字节 ≈ 14GB
```

但这不是最终设备内存需求，还必须加入：KV Cache、算子和运行时空间、通信缓冲、模型加载临时开销、内存碎片和安全余量、量化格式的元数据与额外张量。

所以不能因为 14GB 小于一张卡的设备内存，就直接断言模型一定能稳定运行。

---

## 六、理解 KV Cache 容量

KV Cache 与模型结构、上下文和并发有关。对于常见注意力结构，可以使用下面的关系帮助理解：

```text
KV Cache
≈ 2
× 模型层数
× 总缓存 Token 数
× KV Head 数量
× Head 维度
× 每元素字节数
```

其中前面的 2 代表 Key 和 Value 两部分。总缓存 Token 数与「并发序列数量 × 每个序列实际缓存长度」相关。

需要注意：

- 不同模型可能使用 MHA、GQA 或 MQA
- Tensor Parallel 会影响每卡分布
- vLLM 和 vLLM-Ascend 的实际内存管理以对应版本实现为准
- 最大上下文只是上限，不等于每个请求都使用满长度
- 最终容量必须用目标框架的实际启动日志和压测验证

这个公式用于理解和初步预算，不用于替代真实测试。

---

## 七、每个模型实例需要多少张卡

可以按照以下步骤初步判断：

1. **确定模型和精度**：参数量、权重格式、是否经过后端转换  
2. **计算权重和运行空间**：估算权重，再为 KV Cache、算子、通信和安全空间留出容量  
3. **确定最大上下文和并发目标**：典型/P95 输入输出 Token、目标并发、延迟 SLO  
4. **确定并行方式**：单卡优先；放不下再考虑 TP；单机不够再多机；加卡不保证线性加速  
5. **分别验证 NVIDIA 和昇腾**：不能把一侧卡数和参数直接复制到另一侧

---

## 八、从单实例容量推算副本数量

假设压测得到单个模型副本在目标 SLO 下可承载 `QPS_per_replica`，业务峰值为 `Peak_QPS`：

```text
副本数 ≥ Peak_QPS ÷ QPS_per_replica
```

生产规划还要加入：流量增长、单节点故障、节点维护、请求长度波动、模型冷启动、网关重试放大、双池切流后的额外负载。

不能把所有设备长期规划到 100% 满载，否则任何故障都会立即导致排队和超时。

---

## 九、N+1 容量怎么理解

如果一个资源池在正常情况下必须使用全部节点才能承载流量，那么任意节点故障都会造成容量不足。

N+1 的基本思想是：在失去一台关键节点或一个模型副本后，剩余容量仍能满足约定的核心业务负载。

对于双资源池，还要分别考虑：

- NVIDIA 池内 N+1
- 昇腾池内 N+1
- 一个资源池整体异常时，另一资源池是否承接全部或部分业务
- 备用模型是否已经加载
- 网关切流是否会瞬间造成排队

如果另一资源池只能承载 30% 流量，那么容灾方案应明确「保核心业务、限制普通业务」，而不是写成无条件全量接管。

---

## 十、CPU 和内存容量规划

AI 推理不只消耗加速器。CPU 和主机内存负责：Tokenizer、请求解析、调度线程、模型加载、数据预处理、网络和存储 IO、容器与系统进程、文件缓存。

规划时要观察：每个模型 Pod 的 CPU 请求与限制；多副本是否争抢 CPU；Tokenizer 是否成为瓶颈；模型加载阶段的主机内存峰值；系统、监控和 Device Plugin 预留；NUMA 与加速器亲和性。

不能把节点 CPU 和内存全部分给模型 Pod，必须为操作系统、kubelet、容器运行时和监控组件保留空间。

---

## 十一、磁盘和模型存储容量规划

磁盘容量至少包括：

```text
操作系统
+ 容器镜像
+ 原始模型
+ NVIDIA 优化产物
+ 昇腾转换/编译产物
+ 节点模型缓存
+ 日志
+ 临时文件
+ 备份与版本保留
```

生产环境通常还需要：当前生产版本、待发布版本、可回滚版本、两类后端制品、校验文件、多节点缓存副本。

还要规划吞吐：多个 Pod 同时启动时可能并发读取同一模型。如果共享存储带宽不足，会出现所有 Pod 都在启动，但加载速度非常慢。

---

## 十二、网络容量规划

需要分别计算三类流量：

| 类型 | 说明 |
|------|------|
| 业务请求流量 | Prompt、输出 Token 和并发连接；流式接口还会保持较长连接 |
| 模型和镜像分发流量 | 大权重和镜像在节点扩容或 Pod 重建时产生突发 |
| 多机集合通信流量 | TP 等多机方案对带宽、时延、丢包和 RoCE 敏感 |

三类流量如果共用一张网卡，需要评估相互抢占；如果分网，需要规划路由、VLAN、MTU 和监控。

---

## 十三、性能容量必须以 SLO 为约束

| 指标 | 示例问题 |
|------|----------|
| 可用性 | 月度可用性要求是多少？ |
| TTFT | P95 首 Token 必须小于多少？ |
| TPOT | 流式输出速度要求是什么？ |
| 吞吐 | 峰值每秒请求或 Token 是多少？ |
| 错误率 | 允许多少 5xx 和超时？ |
| 上下文 | 最大和典型输入长度是多少？ |
| 恢复 | 节点或资源池故障后多久恢复？ |

同一个模型在追求低延迟和追求高吞吐时，启动参数和可承载并发可能完全不同。

---

## 十四、NVIDIA 与昇腾需要做对照压测

同一个模型双池部署时，至少使用相同测试集比较：模型版本、Tokenizer、输入输出长度、并发阶梯、TTFT、TPOT、Token 吞吐、错误率、利用率、显存/HBM、功耗、输出功能和结果差异。

不能只比较峰值吞吐，还要确认两边在真实业务 SLO 下能够承载多少请求。

---

## 十五、版本变更与回滚

兼容矩阵要进入变更流程：

```text
提出变更
→ 评估依赖链
→ 测试节点验证
→ 功能测试
→ 性能与稳定性测试
→ 小流量灰度
→ 生产发布
→ 观察
→ 保留回滚路径
```

禁止在所有节点同时直接升级。特别是驱动、固件和计算栈变更，通常需要节点维护、工作负载迁移和明确回滚方案。

## 十七、本篇练习

### 练习 1：建立一套兼容矩阵

选择一台 NVIDIA 节点和一台昇腾节点，填写从硬件到推理框架的完整版本链，并标明「计划、功能通过、性能通过」等状态。

### 练习 2：粗算一个模型

选择一个模型，计算 BF16 权重理论占用，然后列出还需要考虑的 KV Cache、运行时和安全空间。

### 练习 3：设计故障容量

假设资源池失去一台服务器，计算剩余副本能否满足核心流量。如果不能，写下降级策略。

## 十八、本篇小结

兼容矩阵解决「能不能稳定运行」，容量规划解决「能承载多少业务」。完整规划必须同时覆盖：

```text
硬件和 CPU 架构
+ 驱动、固件与计算栈
+ PyTorch 和推理框架
+ 模型与量化格式
+ 权重与 KV Cache
+ CPU 和主机内存
+ 存储容量与加载吞吐
+ 网络与多机通信
+ 副本、冗余和故障容量
+ 真实业务 SLO
```

到这里，**第二阶段完成**。下一阶段将进入真正的环境建设：统一服务器基线、部署高可用 Kubernetes、接入 NVIDIA 资源池，再接入昇腾资源池。
