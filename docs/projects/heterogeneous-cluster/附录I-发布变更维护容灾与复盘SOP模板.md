# 附录I：发布、变更、维护、容灾与复盘 SOP 模板

:::info 系列与定位
**所属系列**：《NVIDIA＋昇腾双资源池 AI 推理集群：从 0 到部署、运维与故障排查》  
**用途**：把「某个人会操作」变成「团队可以重复、安全、可审计地操作」  
**使用方法**：复制对应模板，补齐所有空项，经测试和审批后纳入正式运维手册
:::

:::tip 系列约定
资源池 A = **NVIDIA GPU**（vLLM）· 资源池 B = **华为昇腾 NPU**（vLLM-Ascend）· 同一 Kubernetes · 共享存储/网关/监控 · **禁止**跨池组成同一分布式模型实例。
:::

## 二、SOP 1：模型服务发布

**目的**：将一个新模型或新版本发布到指定资源池，或分别发布到 NVIDIA 和昇腾两池。

**前置条件**：权重来源/版本/哈希/许可证已登记；两池镜像分别完成漏洞扫描；使用不可变 Digest；兼容矩阵通过；离线正确性与 API 兼容通过；容量含稳态、Surge、单节点故障余量；PVC/Secret/SA/NetworkPolicy 就绪；探针/PDB/监控/Runbook 就绪；两池分别压测，不跨加速器组成一个实例。

**发布步骤**：

1. 冻结清单：模型版本、镜像 Digest、启动参数、资源申请、路由初始权重。  
2. 目标命名空间做服务端渲染和策略检查。  
3. 先创建不接生产流量的 Canary Deployment。  
4. 等待权重加载、图/算子初始化和 Readiness 通过。  
5. 执行模型列表、非流式、流式、长短上下文和异常输入测试。  
6. 验证启动时间、TTFT、吞吐、显存/HBM、队列、错误率。  
7. 将 1%～5% 可控流量导入 Canary。  
8. 每个观察窗口检查 SLO 和错误预算，再逐级扩大。  
9. 全量后保留旧版本至少一个回滚窗口。  
10. 记录实际参数、结果、异常、发布时间和执行人。  

```bash
kubectl -n <namespace> get deploy,pod,svc,endpointslice
kubectl -n <namespace> rollout status deployment/<deployment> --timeout=<approved-timeout>
kubectl -n <namespace> describe deployment/<deployment>
kubectl -n <namespace> logs deployment/<deployment> --tail=200 --timestamps
```

**停止条件**：Canary 出现未解释的 5xx；TTFT 或端到端 P95 超阈值；设备健康异常；显存/HBM 达风险阈值；输出一致性不通过；旧版本也异常（可能公共层故障）。

**回滚**：先将网关权重恢复至旧版本，确认新请求不再进入 Canary；再按已审批方式回退工作负载。不要先删除旧版本再尝试回滚。

**验收**：流量与权重一致；流式/非流式正常；TTFT/吞吐/错误率达标；无新增设备/K8s/存储告警；可定位到 `model_version`；回滚路径仍可用。

## 三、SOP 2：模型服务回滚

**触发**：发布后 SLO 恶化；输出正确性或安全性异常；设备/运行时错误增加；资源占用超预算；依赖或兼容问题。

**前置**：旧版本镜像 Digest、权重和配置仍可用；旧版本容量足够；明确仅回滚一池还是两池分别回滚；确认无不可逆格式变化。

**步骤**：宣布停扩新版本并记时间 → 保存新版本日志/指标/样例/设备状态 → 路由权重逐步切回已知良好版本 → 验证新请求进入旧版本且成功率恢复 → SSE 设排空窗口，不透明重试已输出 Token → 按发布历史或冻结清单回滚工作负载 → 观察完整业务周期或批准最短窗 → 新版本保留隔离供复现，不立即清证据。

**失败升级**：若旧版本也异常，停止反复回滚，转入公共层、存储、网关或设备故障排查。

---

## 四、SOP 3：加速器节点维护

**适用范围**：硬件巡检、系统补丁、网卡/磁盘处理、设备检查和计划重启。

**前置**：维护节点、设备与在跑 Pod 清单明确；备用容量可承接；PDB 允许计划不可用数；已识别 emptyDir/本地 PV/HostPath/节点缓存；多机 Rank 与调度方式已确认；HPA/路由不会与人工操作冲突。

**步骤**：排除新流量与新任务 → 逐个降网关权重并排空 → 确认备用 Ready、队列稳定 → 按批准排空 Runbook 执行并核对 PDB/本地数据 → 确认业务 Pod 已迁移 → 保存维护前设备/网络/温度/驱动状态 → 执行获批事项并记录重启时间 → 恢复后验主机/设备/Runtime/Plugin/网络/存储 → 解除维护，先测测试 Pod，再恢复低风险副本 → 逐步恢复流量后关闭窗口。

**停止条件**：备用不足或队列持续增长；PDB 阻止安全迁移；本地数据无法迁移；多机实例不能安全排空；恢复后设备数量/拓扑/健康变化。

不要使用忽略 PDB、强制删除或删除本地数据的参数，除非正式应急预案明确授权并完成影响评估。

## 五、SOP 4：NVIDIA 驱动或昇腾驱动/固件/CANN 升级

**核心原则**：两池独立升级；单节点金丝雀；完整兼容矩阵；先业务排空；可回退介质；禁止同一窗口顺带升级所有组件。

| 项目 | 当前版本 | 目标版本 | 兼容证据 | 回退版本 |
|------|----------|----------|----------|----------|
| OS / 内核 | | | | |
| NVIDIA 驱动 / 固件 | | | | |
| CUDA / Toolkit | | | | |
| GPU Operator / Plugin | | | | |
| 昇腾驱动 / 固件 | | | | |
| CANN | | | | |
| Ascend Device Plugin | | | | |
| vLLM / vLLM-Ascend 镜像 | | | | |

**步骤**：非生产同型号完成安装/重启/诊断/基准 → 选有备用容量的生产金丝雀节点 → 按节点维护 SOP 排空并保存证据 → 执行经确认的安装步骤 → 验证设备数量/健康/拓扑/Runtime/Plugin → 跑设备测试 Pod、单卡基准、通信测试、代表性模型 → 对比输出/TTFT/吞吐/功耗/错误 → 观察期通过后逐节点滚动 → 任一失败立即停扩并回退。

**禁止**：同节点同时试验内核/驱动/固件/Runtime/模型大版本；混用未验证宿主机库与容器用户态；跳过重启或健康测试；两池同时高风险底层升级；仅因「设备能被看到」就认定业务已验收。

## 六、SOP 5：网关路由与权重变更

| 模型 | 旧路由 | 新路由 | NVIDIA 权重 | 昇腾权重 | 版本 | 回退值 |
|------|--------|--------|-------------|----------|------|--------|
| | | | | | | |

**前置**：两池目标后端均通过模型/API/容量/SLO 验收；健康检查验证模型可服务；重试/超时/熔断/限流明确；SSE 切流影响明确；路由指标含后端池、版本和 fallback。

**步骤**：导出当前配置 → 配置校验与测试回放 → 先改少量权重观察分布 → 查两池成功率/TTFT/排队/KV/429·5xx → 逐级扩大（每级只调一次变量）→ 验证足够样本量下的实际分布 → 保存 Diff、审批、监控截图和验证 request_id。

**停止条件**：错误率超阈值；备用池排队或 KV 接近上限；输出一致性异常；实际权重与配置严重不符；fallback 循环或重复请求。

## 七、SOP 6：双资源池故障切换与回切

**切换前决策**：是否仅一池故障？备用池是否同模型/API/已验收版本？余量多少？哪些 P0/P1 优先？是否需降上下文/输出 Token/并发？切全部还是核心流量？

**故障切换**：确认故障池并阻止向坏实例分配 → 保留现场，不同时重启全池 → 启用租户优先级与并发/Token 限制 → 小比例核心流量切到备用池并验证 → 按队列/TTFT/设备余量逐步增加 → 容量不足时宁可明确 429/降级，也不拖垮两池 → 记录失败请求数、切换比例、排队与用户影响。

**回切**：故障池通过设备/K8s/模型/接口验收 → 预热与合成请求验证 → 保持备用服务，不一步回到原权重 → 按 5%→20%→50%→目标值逐级回切 → 每级观察完整窗口，异常退回上一级 → 恢复正常限流与 HPA，关闭临时配置。

**强制约束**：不能把一个分布式实例的一部分 Rank 放在 NVIDIA、另一部分放在昇腾。切换发生在服务和请求路由层。

---

## 八、SOP 7：Secret、API 密钥和 TLS 证书轮换

**前置**：新凭据已在安全系统生成并审批；明确使用方/有效期/权限/撤销；支持新旧并存或无中断切换；日志与工单不记录明文；证书 SAN/主机名/时间同步/完整链已验证。

**步骤**：盘点引用方 → 测试环境验证 → 创建新版本 Secret（不在命令行/聊天粘贴明文）→ Canary 验证鉴权/TLS → 滚动其余使用方 → 确认后撤销旧凭据 → 验证旧凭据失效，更新到期监控与资产记录。

**回滚**：在重叠窗口内恢复引用；若已撤销，走紧急签发流程，不得从日志或历史找回明文。

---

## 九、SOP 8：扩容、缩容与容量调整

**扩容前**：触发来自持续趋势；权重/镜像/设备/节点足够；存储不被并发冷启动打满；网关在预热完成后才接流量；配额/PDB/HPA 上限允许。

**扩容**：记录扩容前 QPS/Token/s/队列/TTFT/设备使用 → 一次增加批准数量副本 → 等待加载/预热/Ready → 逐步导流并查均衡 → 更新容量台账与成本/功耗。

**缩容**：确认目标时段与单节点故障后仍有余量 → 先降权重并排空 → 查 SSE/队列/PDB → 每次缩减批准批次并观察 SLO → 保留 Surge 与维护余量。

自动扩缩容需限制最大变化速度、冷却时间和上限。模型冷启动以分钟计，HPA 不能当作普通 Web 服务。

**响应步骤**：宣告级别与指挥角色 → 冻结非必要发布与自动变更 → 确认影响范围、开始时间与最近变更 → 选择最小风险止损（限流/摘除/切池/降级）→ 每 15～30 分钟更新事实、影响、动作与下一决策点 → 技术排查遵循[附录 H](./附录H-巡检与故障处理SOP.md) → 恢复后完成业务/路由/设备/监控四层验证 → 解除临时策略，保留观察窗后再关闭。

## 十一、SOP 10：故障复盘

**原则**：面向系统改进，不寻找「背锅人」；事实、推断和未知项分开；根因、触发、扩大因素和发现缺口分开；整改项必须可验证。

```markdown
事件标题 / 编号级别 / 日期 / 影响时长
受影响用户请求 / 业务与SLO影响

摘要 / 正常架构与预期行为 / 实际发生了什么

时间线：T0触发 → T1监控发现 → T2确认 → T3止损 → T4恢复 → T5关闭

根因 / 触发因素 / 扩大因素
为什么监控测试没有提前发现
哪些机制工作正常 / 未按预期工作

五个为什么：1. 2. 3. 4. 5.
```

| 编号 | 整改项 | 类型 | 优先级 | 负责人 | 截止时间 | 验证方式 | 状态 |
|------|--------|------|--------|--------|----------|----------|------|
| 1 | | 预防/检测/缓解/流程 | | | | | |

不能用「加强监控」「提高意识」「以后注意」作为唯一整改项。好的整改项应类似：增加可测试告警规则、把兼容矩阵作为发布门禁、每季度执行双池切换演练。

## 十三、SOP 上线检查清单

- [ ] SOP 有版本、负责人和适用范围  
- [ ] 明确 NVIDIA、昇腾或公共层，不混用底层步骤  
- [ ] 所有对象从通配符变为精确清单  
- [ ] 高风险动作经过测试和双人复核  
- [ ] 前置检查能阻止在容量不足时继续  
- [ ] 每个阶段有量化验收指标  
- [ ] 有明确停止条件和回滚路径  
- [ ] 回滚依赖的旧镜像、配置和权重真实存在  
- [ ] 长连接、PDB、本地数据和多机 Rank 影响已考虑  
- [ ] 日志和工单不含明文凭据  
- [ ] 证据归档位置可访问且有保留期  
- [ ] 至少演练过一次，而不是只写在文档里  

成熟运维的标准不是「从不出故障」，而是变更范围清晰、故障能够止损、动作可以回退、过程可以复盘、经验能够进入下一次门禁。
