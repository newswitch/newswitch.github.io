# 模型分发、节点缓存与预热——解决大模型冷启动和存储惊群

:::info 系列与定位
**系列**：《NVIDIA＋昇腾双资源池 AI 推理集群：从 0 到部署、运维与故障排查》
**阶段**：第五阶段——模型存储
**本文定位**：模型分发、校验、本地缓存、预热、回收与故障排查篇
:::

:::tip 系列约定
资源池 A = **NVIDIA GPU**（vLLM）· 资源池 B = **华为昇腾 NPU**（vLLM-Ascend）· 同一 Kubernetes · 共享存储/网关/监控 · **禁止**跨池组成同一分布式模型实例。
:::

到 [第 19 篇](./19-CephFS对象存储和CSI怎么选.md) 为止，我们已经可以把模型放在 NFS、CephFS 或对象存储中。但如果每个 Pod 启动时都直接从远端读取数百 GB 权重，会出现：扩容慢；发布慢；节点重启后恢复慢；大量 Pod 同时启动打爆 NFS/Ceph；对象存储产生大量重复下载；共享存储短暂抖动导致整批 Pod 启动失败；NVIDIA 和昇腾两池同时发布时相互争抢带宽。

本篇完成最后一段链路：

```text
权威模型制品
→ 安全分发
→ 节点 NVMe 缓存
→ 校验与原子发布
→ 模型加载
→ 推理预热
→ Ready 接流量
```

对照：[本地 NVMe 与 Local PV](../../storage/ai-workloads/03-本地NVMe与Local-PV实践.md) · [对象存储与模型仓库](../../storage/ai-workloads/04-对象存储与模型仓库设计.md) · [第 17 篇四层存储](./17-模型文件到底存在哪里.md)。

## 1. 先理解四种启动方式 {/* #一先理解四种启动方式 */}

| 方式 | 数据来源 | 优点 | 缺点 |
|------|----------|------|------|
| 直接读 NFS/CephFS | 共享文件系统 | 最简单，不复制 | 冷启动冲击共享存储 |
| InitContainer → emptyDir | 远端 → Pod 临时盘 | 与主容器解耦、校验方便 | 每个 Pod 重复复制，Pod 删除即丢失 |
| InitContainer → hostPath | 远端 → 节点缓存 | 同节点多个 Pod 复用 | 权限、安全、并发锁和清理复杂 |
| 节点预热 DaemonSet/Agent | 发布前主动下载 | Pod 启动最快 | 需要缓存控制面和状态治理 |

生产常用组合：小规模直接共享读取；中规模 InitContainer + 节点缓存；大规模模型分发服务/预热 Agent + 节点缓存 + 分批发布。

## 2. 二～三、节点缓存定位与目录规范 {/* #二三节点缓存定位与目录规范 */}

节点缓存通常位于 `/var/lib/model-cache`，底层使用独立 NVMe/SSD，不建议与 `/var/lib/containerd`、`/var/lib/kubelet`、`/var/log`、操作系统根分区无控制地共用系统盘。

缓存必须满足：可从权威源重建；目录按制品版本不可变；下载完成前对业务不可见；Manifest 和 SHA256 校验；多 Pod 并发下载有锁；节点磁盘有高低水位；删除前确认没有进程使用；NVIDIA 和昇腾制品分目录；节点故障不会造成权威模型丢失。

```text
/var/lib/model-cache/
├── artifacts/
│   ├── nvidia/
│   │   └── company-model-a/
│   │       └── 3.0.0-bf16/
│   └── ascend/
│       └── company-model-a/
│           └── 3.0.0-bf16/
├── runtime/
│   ├── nvidia/
│   └── ascend/
├── locks/
├── staging/
├── quarantine/
└── state/
```

| 目录 | 用途 |
|------|------|
| artifacts | 校验完成的不可变模型制品 |
| runtime | 框架、算子、编译等可重建缓存 |
| locks | 同节点下载锁 |
| staging | 未完成下载的临时目录 |
| quarantine | 校验失败或异常旧目录 |
| state | 缓存 Agent 状态与引用信息 |

正式制品目录禁止原地更新。

## 3. 四～五、内容摘要与下载状态机 {/* #四五内容摘要与下载状态机 */}

仅使用版本名 `company-model-a/3.0.0` 仍可能被覆盖。缓存键应至少包含：逻辑模型 + vendor + artifactVersion + Manifest 摘要。例如：

```text
company-model-a/nvidia/3.0.0-bf16/<manifest-sha256前缀>
```

这样可以发现：同版本名内容被替换；两节点缓存内容不同；NVIDIA 与昇腾制品混用；回滚版本不完整。

```text
ABSENT → DOWNLOADING → VERIFYING → READY

失败：DOWNLOADING/VERIFYING → FAILED → QUARANTINED → 重新下载
```

关键原则：业务只能看见 READY 目录，不能看见正在下载的半成品。实现：下载到 staging 随机临时目录 → 校验所有文件 → 写入本地状态 → 同一文件系统 rename 到最终目录 → 写 READY 标记 → 主容器只使用最终目录。

## 4. 六～七、下载脚本能力与安全骨架 {/* #六七下载脚本能力与安全骨架 */}

生产分发脚本至少支持：断点续传、超时、有上限重试与退避、下载锁、Manifest/SHA256 校验、临时目录、原子发布、日志隐藏凭证、磁盘空间预检、同版本幂等、校验失败隔离、指标和退出码。

不要使用 `cp -r /remote/model /cache/model` 然后仅凭目标目录存在就认定成功。

下面脚本用于展示流程，需要放进经过测试的内部缓存镜像；不能不经修改直接投入生产：

```bash
#!/usr/bin/env bash
set -Eeuo pipefail

: "${MODEL_ID:?MODEL_ID is required}"
: "${VENDOR:?VENDOR is required}"
: "${ARTIFACT_VERSION:?ARTIFACT_VERSION is required}"
: "${SOURCE_DIR:?SOURCE_DIR is required}"
: "${CACHE_ROOT:?CACHE_ROOT is required}"

case "$VENDOR" in
  nvidia|ascend) ;;
  *) echo "unsupported vendor: $VENDOR" >&2; exit 2 ;;
esac

target="${CACHE_ROOT}/artifacts/${VENDOR}/${MODEL_ID}/${ARTIFACT_VERSION}"
lock_dir="${CACHE_ROOT}/locks"
staging_root="${CACHE_ROOT}/staging"
quarantine_root="${CACHE_ROOT}/quarantine"

mkdir -p "$lock_dir" "$staging_root" "$quarantine_root"

exec 9>"${lock_dir}/${VENDOR}-${MODEL_ID}-${ARTIFACT_VERSION}.lock"
flock -x 9

if [[ -f "${target}/READY" ]] && \
   (cd "$target" && sha256sum -c MANIFEST.sha256); then
  echo "cache hit: $target"
  exit 0
fi

if [[ -e "$target" ]]; then
  quarantine="${quarantine_root}/${VENDOR}-${MODEL_ID}-${ARTIFACT_VERSION}-$(date +%s)"
  mv -- "$target" "$quarantine"
fi

staging="$(mktemp -d "${staging_root}/${VENDOR}-${MODEL_ID}-${ARTIFACT_VERSION}.XXXXXX")"
cleanup() {
  if [[ -n "${staging:-}" && -d "$staging" ]]; then
    rm -rf -- "$staging"
  fi
}
trap cleanup EXIT

test -f "${SOURCE_DIR}/MANIFEST.sha256"
rsync -a --partial -- "${SOURCE_DIR}/" "${staging}/"

(
  cd "$staging"
  sha256sum -c MANIFEST.sha256
)

mkdir -p "$(dirname "$target")"
mv -- "$staging" "$target"
staging=""

date -u +'%Y-%m-%dT%H:%M:%SZ' > "${target}/READY"
echo "cache ready: $target"
```

仍需补充：字符白名单、源 Manifest 签名、最低剩余空间、速率限制、Prometheus、结构化日志、对象存储下载、异常目录回收、权限设置。

**为什么使用 flock**：同一节点可能同时创建多个相同模型 Pod。锁的范围应是 `vendor + model + artifactVersion`；不同模型可以并发，同一制品只允许一个下载者。

## 5. 方式 A：InitContainer 复制到 emptyDir {/* #八方式-ainitcontainer-复制到-emptydir */}

共享模型 PVC → InitContainer 复制并校验到 emptyDir → 主容器从 emptyDir 加载。

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: model-emptydir-demo
  namespace: ai-prod
spec:
  initContainers:
    - name: prepare-model
      image: <内部模型分发镜像>
      env:
        - name: SOURCE_DIR
          value: /remote/company-model-a/nvidia/3.0.0
        - name: TARGET_DIR
          value: /local/model
      command:
        - bash
        - -c
        - |
          set -Eeuo pipefail
          rsync -a -- /remote/company-model-a/nvidia/3.0.0/ /local/model/
          cd /local/model
          sha256sum -c MANIFEST.sha256
      volumeMounts:
        - name: remote-models
          mountPath: /remote
          readOnly: true
        - name: local-model
          mountPath: /local/model
      resources:
        requests:
          cpu: "2"
          memory: 2Gi
          ephemeral-storage: 150Gi
        limits:
          cpu: "4"
          memory: 4Gi
          ephemeral-storage: 200Gi
  containers:
    - name: inference
      image: <NVIDIA推理镜像>
      args:
        - --model
        - /models/company-model-a
      volumeMounts:
        - name: local-model
          mountPath: /models/company-model-a
          readOnly: true
  volumes:
    - name: remote-models
      persistentVolumeClaim:
        claimName: model-repository-pvc
    - name: local-model
      emptyDir:
        sizeLimit: 200Gi
```

优点：不直接使用 hostPath；每个 Pod 文件隔离；逻辑简单；Pod 删除后自动清理。缺点：每个 Pod 都复制完整模型；同节点不能复用；占用 ephemeral-storage；Pod 重建再次复制；复制期间已占用该 Pod 申请的 GPU/NPU 调度位置。

## 6. InitContainer 会提前占住加速卡 {/* #九initcontainer-会提前占住加速卡 */}

如果 Pod 主容器申请 GPU/NPU，整个 Pod 调度到节点后才执行 InitContainer。即使 InitContainer 本身不使用加速卡，设备资源已经为这个 Pod 保留。

例如模型下载 20 分钟：GPU/NPU 被调度占用 20 分钟，但推理主进程尚未启动。小规模可以接受；大规模生产更适合：

```text
发布前由独立 DaemonSet/Agent 预热节点缓存
→ 缓存 Ready
→ 再创建申请 GPU/NPU 的推理 Pod
```

这样不会用昂贵设备等待网络下载。

## 7. 方式 B：InitContainer 复用节点 hostPath 缓存 {/* #十方式-binitcontainer-复用节点-hostpath-缓存 */}

```yaml
spec:
  initContainers:
    - name: prepare-model-cache
      image: <内部模型缓存镜像>
      env:
        - name: MODEL_ID
          value: company-model-a
        - name: VENDOR
          value: nvidia
        - name: ARTIFACT_VERSION
          value: 3.0.0-bf16
        - name: SOURCE_DIR
          value: /remote/company-model-a/nvidia/3.0.0-bf16
        - name: CACHE_ROOT
          value: /cache
      volumeMounts:
        - name: remote-models
          mountPath: /remote
          readOnly: true
        - name: node-cache
          mountPath: /cache
  containers:
    - name: inference
      image: <NVIDIA推理镜像>
      args:
        - --model
        - /cache/artifacts/nvidia/company-model-a/3.0.0-bf16
      volumeMounts:
        - name: node-cache
          mountPath: /cache
          readOnly: true
  volumes:
    - name: remote-models
      persistentVolumeClaim:
        claimName: model-repository-pvc
    - name: node-cache
      hostPath:
        path: /var/lib/model-cache
        type: Directory
```

:::caution hostPath 风险
hostPath 直接暴露节点文件系统，必须由平台统一管理：固定允许路径；不允许业务自定义任意 hostPath；容器使用非 root 和最小权限；只挂载缓存目录；主容器只读；缓存组件写权限受控；使用准入策略限制。普通业务开发者不应获得任意 hostPath 权限。
:::

## 8. 十一～十二、方式 C：DaemonSet 提前预热 {/* #十一十二方式-cdaemonset-提前预热 */}

DaemonSet 确保每个匹配节点运行一个缓存 Agent，适合在发布前主动下载模型。

NVIDIA 节点预热骨架：

```yaml
apiVersion: apps/v1
kind: DaemonSet
metadata:
  name: model-prewarm-nvidia
  namespace: ai-platform
spec:
  selector:
    matchLabels:
      app: model-prewarm-nvidia
  template:
    metadata:
      labels:
        app: model-prewarm-nvidia
    spec:
      nodeSelector:
        accelerator.vendor: nvidia
        resource-pool: nvidia-pool
      tolerations:
        - key: accelerator
          operator: Equal
          value: nvidia
          effect: NoSchedule
      containers:
        - name: prewarm
          image: <内部模型缓存Agent镜像>
          env:
            - name: DESIRED_ARTIFACTS_CONFIG
              value: /config/artifacts.yaml
            - name: CACHE_ROOT
              value: /cache
          volumeMounts:
            - name: desired-artifacts
              mountPath: /config
              readOnly: true
            - name: remote-models
              mountPath: /remote
              readOnly: true
            - name: node-cache
              mountPath: /cache
      volumes:
        - name: desired-artifacts
          configMap:
            name: nvidia-prewarm-artifacts
        - name: remote-models
          persistentVolumeClaim:
            claimName: model-repository-pvc
        - name: node-cache
          hostPath:
            path: /var/lib/model-cache
            type: Directory
```

昇腾侧使用独立 DaemonSet：`accelerator.vendor=ascend`、toleration `accelerator=ascend`、下载 ascend 目录制品、独立 runtime 缓存目录。不要用一个脚本根据设备自动猜测要下载哪个厂商制品。

Agent 需要：监听期望清单；限制并发下载；节点级锁；下载校验；上报状态；控制带宽；失败退避；磁盘水位；安全 GC；配置 Reload/Rollout；Prometheus；不申请 GPU/NPU；不执行推理。仅修改 ConfigMap 不代表进程一定重新加载，需要设计 Reload 或 Rollout 机制。

## 9. 如何让调度器知道缓存已经 Ready {/* #十三如何让调度器知道缓存已经-ready */}

Kubernetes 默认不知道某模型是否已缓存。小规模可为节点加 Label：

```bash
kubectl label node gpu-node-01 \
  cache.ai.example.com/model-a-v3=ready --overwrite
```

```yaml
affinity:
  nodeAffinity:
    preferredDuringSchedulingIgnoredDuringExecution:
      - weight: 100
        preference:
          matchExpressions:
            - key: cache.ai.example.com/model-a-v3
              operator: In
              values: ["ready"]
```

优先用 `preferred`：若使用 `required` 而所有 Ready 标签因 Agent 故障消失，Pod 可能永远 Pending。一种策略：优先已缓存节点；找不到时允许未缓存兼容节点，再由 InitContainer 补充下载。

模型很多时节点 Label 会膨胀。大规模应使用专用缓存控制器、自定义调度插件、调度队列、模型服务 Operator 或平台数据库中的节点缓存状态。本篇 Label 方案用于理解原理和小规模落地。

## 10. 对象存储下载方式 {/* #十四对象存储下载方式 */}

```text
s3://model-registry/models/company-model-a/nvidia/3.0.0
→ /cache/staging/...
→ SHA256 校验
→ /cache/artifacts/nvidia/company-model-a/3.0.0
```

InitContainer 可以获得对象存储只读 Secret，主推理容器不一定需要该 Secret：

```yaml
initContainers:
  - name: download-model
    volumeMounts:
      - name: object-credentials
        mountPath: /var/run/model-credentials
        readOnly: true
containers:
  - name: inference
    # 不挂载 object-credentials
volumes:
  - name: object-credentials
    secret:
      secretName: model-registry-readonly
```

不要在命令参数和日志中打印 Access Key 或 Secret Key。下载工具可用厂商 S3 CLI、rclone、s5cmd、企业客户端或自研 Downloader；必须固定工具版本并进行安全审查。

## 11. 镜像预热与模型预热是两件事 {/* #十五镜像预热与模型预热是两件事 */}

| 类型 | 内容 |
|------|------|
| 镜像预热 | NVIDIA/昇腾推理镜像、InitContainer 镜像、监控和工具镜像 |
| 模型预热 | 权重、Tokenizer、Manifest |
| Runtime 预热 | 框架缓存、算子编译、CUDA/CANN、图编译、通信初始化 |
| 推理预热 | 少量代表性请求：短输入、目标上下文、流式、Tool Calling 等 |

四种预热都完成后，才是真正可接流量。

## 12. vLLM 如何指定本地模型和缓存 {/* #十六vllm-如何指定本地模型和缓存 */}

```bash
vllm serve \
  /cache/artifacts/nvidia/company-model-a/3.0.0-bf16 \
  --served-model-name company-model-a
```

```yaml
env:
  - name: HF_HOME
    value: /cache/runtime/nvidia/huggingface
  - name: XDG_CACHE_HOME
    value: /cache/runtime/nvidia/xdg
```

网络文件系统加载策略随 vLLM 版本变化较快，必须查看目标版本文档，对比 NFS/CephFS 与本地 NVMe，记录加载时间与 CPU 内存峰值。官方排障也建议先把模型下载到本地并传入本地路径。昇腾侧使用目标 vLLM-Ascend 版本的本地路径和缓存参数，不能假定所有 CUDA 参数都能直接复用。

## 13. 启动探针和就绪探针如何配合预热 {/* #十七启动探针和就绪探针如何配合预热 */}

| 探针 | 职责 |
|------|------|
| startupProbe | 给模型加载、编译和预热留出时间，避免 liveness 过早重启 |
| readinessProbe | 只有模型真正可处理请求时才成功，让 Service 开始转发 |
| livenessProbe | 检测不可恢复状态，不能因一次推理慢就立即重启 |

```yaml
startupProbe:
  httpGet:
    path: <目标框架启动健康路径>
    port: 8000
  periodSeconds: 10
  failureThreshold: 180

readinessProbe:
  httpGet:
    path: <目标框架就绪路径>
    port: 8000
  periodSeconds: 5
  failureThreshold: 3

livenessProbe:
  httpGet:
    path: <目标框架存活路径>
    port: 8000
  periodSeconds: 10
  failureThreshold: 6
```

路径和频率必须按目标框架版本与实际冷启动时间设置。不要用固定 `sleep 600` 代替健康状态判断。

## 14. 发布时如何避免存储惊群 {/* #十八发布时如何避免存储惊群 */}

1. **分批预热节点**：例如每批 2～5 台，观察 NFS/Ceph/对象存储指标。
2. **限制每节点并发下载**：同一模型使用锁，不同模型设全局并发上限。
3. **限制全局下载带宽**：避免抢占 NCCL/HCCL、业务和 Ceph 恢复带宽。
4. **先缓存，再创建推理 Pod**。
5. **控制滚动策略**：

```yaml
strategy:
  type: RollingUpdate
  rollingUpdate:
    maxSurge: 1
    maxUnavailable: 0
```

大型模型可能需要按节点容量调整，避免新旧副本同时占用超过可用卡数。

6. **逐步放量**：Ready → 预热请求 → 1% → 10% → 30% → 100%。
7. **NVIDIA 与昇腾错峰**：两池若共享存储，不要在没有压测的情况下同时全量更新。

## 15. 模型预热请求怎么设计 {/* #十九模型预热请求怎么设计 */}

至少覆盖：Tokenizer；短 Prefill；Decode；流式响应；目标最大上下文的一部分；常用采样参数；Tool Calling/结构化输出；多模态 Processor（如有）；多卡通信初始化。

预热请求必须：使用专用租户或标记；不计入业务报表；不触发真实下游操作；有超时；失败时阻止 Ready；不在日志中泄露敏感内容。

## 16. 二十～二十一、缓存垃圾回收与引用判断 {/* #二十二十一缓存垃圾回收与引用判断 */}

直接删除目录可能：当前进程通过 mmap/fd 暂时继续但磁盘空间不释放；新副本无法加载；回滚版本消失；多 Pod 不一致。

删除前确认：

```bash
lsof +D /var/lib/model-cache/artifacts/<目标目录>
fuser -vm /var/lib/model-cache/artifacts/<目标目录>
```

大目录全扫描成本高，生产 Agent 应维护引用状态。推荐水位：低水位约剩余 30% 停止主动清理；高水位约剩余 15% 开始强制回收候选。

回收优先级：校验失败的 Staging → 已废弃且无人引用的旧版本 → 最久未使用的非关键模型 → 保留当前生产版本 → 保留至少一个回滚版本 → 正在使用的版本绝不删除。

不要只看 Pod 名称。结合 Deployment 期望版本、Pod Annotation 中的 artifact digest、缓存 Agent 租约、文件打开状态、网关后端、发布平台引用、最近访问时间、回滚保留策略：

```yaml
metadata:
  annotations:
    ai.example.com/model-artifact: company-model-a/nvidia/3.0.0-bf16
    ai.example.com/model-manifest-sha256: <摘要>
```

## 17. 二十二～二十三、节点磁盘水位、告警与缓存指标 {/* #二十二二十三节点磁盘水位告警与缓存指标 */}

至少监控：缓存盘容量与剩余；inode；吞吐/IOPS/延迟；NVMe 健康与寿命；Staging/Quarantine 占用；每模型大小；GC 成败；删除后未释放空间；containerd/kubelet 磁盘是否受影响。

告警示例：可用容量低于规划水位；无法容纳一个最大生产模型新版本；缓存盘只读/掉盘/I/O 错误；Staging 长时间未完成；同一模型连续校验失败。「还剩 100GB」对 120GB 模型等于无法发布，告警要结合最大制品大小和双版本并存需求。

建议指标：`model_cache_artifact_ready`、`model_cache_download_seconds`、`model_cache_hit_total` / `miss_total`、`model_cache_failure_total`、`model_cache_disk_available_bytes`、`model_cache_staging_age_seconds` 等。业务继续记录：Pod 创建 → Initialized → 模型启动 → Ready → 第一条成功请求，以及热/冷缓存时延差异。

## 18. 常见故障排查 {/* #二十四常见故障排查 */}

| 现象 | 方向 |
|------|------|
| Pod 卡在 Init | PVC、凭证、源路径、磁盘空间、校验失败、锁不释放、UID/GID、镜像工具、网络超时 |
| READY 但加载失败 | 再跑 `sha256sum -c`；READY 过早；Manifest 不全；同版本被覆盖；软链接坏；vendor 混用；镜像与制品不兼容 |
| 多 Pod 重复下载 | 锁目录是否真在共享 hostPath，而非各 Pod 的 emptyDir |
| 磁盘已满但目录不大 | `lsof +L1`；被删仍打开的文件 |
| 下载完成但 mv 失败 | Staging 与 Target 不在同一文件系统；目标已存在；权限不足 |
| 发布导致 NFS/Ceph 抖动 | 暂停新增预热；限制失败重试；保留已 Ready 服务；降低并发与带宽后逐批恢复 |
| Label 与实际不一致 | 先校验再写 Ready；失败/掉盘/目录丢失时及时移除标签 |
| 昇腾节点缓存了 NVIDIA 制品 | 期望清单、NodeSelector、vendor 白名单、两套独立 DaemonSet |

```bash
kubectl describe pod <POD> -n <NS>
kubectl logs <POD> -n <NS> -c <INIT_CONTAINER>
kubectl get pod <POD> -n <NS> \
  -o jsonpath='{.status.initContainerStatuses}' | jq
```

## 19. 不要让失败无限重试 {/* #二十五不要让失败无限重试 */}

无限重试会产生对象存储请求风暴、NFS/Ceph 持续高负载、大量日志、节点磁盘反复写入、GPU/NPU 被 Pending 初始化 Pod 占住。

推荐：有限次数快速重试 → 指数退避 → 标记失败原因 → 告警 → 等待人工或控制面重新触发。InitContainer 会按 Pod 重启策略重试，应用仍需设计幂等和外部限速。

## 20. 二十六～二十七、发布回滚与双池预热顺序 {/* #二十六二十七发布回滚与双池预热顺序 */}

**新版本**：权威不可变发布 → Manifest/业务回归 → NVIDIA/昇腾分批预热 → 校验 Ready 率 → 预拉镜像 → 各池少量新副本 → 推理预热与合成监控 → 网关逐步放量 → 保留旧版本观察 → 稳定后再缩容旧版本。

**回滚**：停新流量 → 确认旧缓存仍在 → 扩容旧 Deployment → 预热 Ready → 网关切回 → 隔离新版本缓存（不立即删除）→ 收集日志和 Manifest。不要在新版本全量后立即删除旧缓存。

双池发布建议：先备用/小流量池再主池；NVIDIA 与昇腾错峰下载；分别校验两套 Manifest 与 READY；网关先对单池小流量验证，再开启双池权重路由。

## 21. 三种规模的推荐落地方案 {/* #二十八三种规模的推荐落地方案 */}

| 方案 | 链路 | 要求 |
|------|------|------|
| A 实验/小规模 | NFS/CephFS 只读 → 直接加载 | 并发启动少，能接受冷启动 |
| B 中等规模 | 远端 → InitContainer → 节点 NVMe → 推理 | 平台统一 hostPath、锁和 GC |
| C 规模化生产 | 对象仓库 → 分发控制面 → 缓存 Agent → 缓存感知调度 → Operator/网关灰度 | 状态、指标、限速、回滚和准入平台化 |

不要从方案 A 直接堆补丁变成方案 C，应在规模达到边界前重构。

## 22. 二十九～三十、第五阶段综合验收与练习 {/* #二十九三十第五阶段综合验收与练习 */}

**权威仓库**：版本不可变；两厂商品分目录；Manifest/SHA256 完整；权限最小化；备份恢复演练完成。
**共享存储**：职责明确；推理只读；ReclaimPolicy 确认；并发冷启动压测；存储纳入双池公共依赖。
**节点缓存**：独立缓存盘；Staging/Ready/Quarantine 清晰；节点锁；哈希校验；原子发布；主容器只读；GC 不删在用版本；保留生产与回滚；水位与 NVMe 告警。
**发布**：镜像与模型分别预热；两池错峰；探针职责明确；Ready 后入网关；分批滚动与灰度；失败退避；回滚无需重下旧版本；缓存状态可观测。

**练习**：准备独立缓存目录；创建小模型 Manifest；InitContainer → emptyDir 再改 hostPath；两 Pod 验证只有一个下载者；故意破坏文件验证隔离重下；Ready Label 与亲和；磁盘水位与旧版本清理；两池错峰预热；记录冷/热缓存 Ready 时间；演练保留旧缓存的快速回滚。

## 23. 本篇小结 {/* #三十一本篇小结 */}

模型缓存的目标不是「把文件复制快一点」，而是建立一个可验证、可恢复、可回滚的分发系统。

```text
权威源不可变
→ 下载到 Staging
→ Manifest 和 SHA256 校验
→ 同文件系统原子发布
→ 节点缓存 Ready
→ 推理加载和预热
→ Readiness 成功
→ 网关逐步放量
```

必须避免：每个 Pod 重复下载；半成品目录被加载；共享存储惊群；GPU/NPU 等待下载时被长期占用；清理正在使用的模型；NVIDIA 和昇腾制品混用；新版本上线后立即删除回滚版本。

至此，第五阶段「模型存储」完成。下一阶段将正式部署推理服务：先计算显存/HBM 和启动参数，然后分别在 NVIDIA 上部署原生 vLLM、在昇腾上部署 vLLM-Ascend，最后进入 NCCL 与 HCCL 多卡多机。
