# GPU/NPU、显存/HBM、CUDA/CANN到底是什么

:::info 系列与定位
**系列**：《NVIDIA＋昇腾双资源池 AI 推理集群：从 0 到部署、运维与故障排查》
**阶段**：第一阶段——小白基础
**本文定位**：硬件与软件栈门户篇
:::

:::tip 系列约定
资源池 A = **NVIDIA GPU**（vLLM）· 资源池 B = **华为昇腾 NPU**（vLLM-Ascend）· 同一 Kubernetes · 共享存储/网关/监控 · **禁止**跨池组成同一分布式模型实例。
:::

在双资源池集群中，最容易产生的误解是：NVIDIA 和昇腾都能运行大模型，所以它们的软件和运维方式应该差不多。

实际上，两边解决的是相似问题，但硬件架构、软件栈、容器运行环境、集合通信和排障工具并不相同。**统一 Kubernetes 管理不等于统一底层运行时。**

本文的目标是建立一张一一对应的技术地图。更深的 GPU 拓扑与显存细节见本站 [k8s-gpu](../../gpu/cluster/00-Kubernetes-GPU集群学习路线.md) 专栏；本文只建立对照关系。

## 1. GPU 与 NPU 是什么 {/* #一gpu-与-npu-是什么 */}

### 1.1 NVIDIA GPU {/* #nvidia-gpu */}

GPU 最初广泛用于图形计算，但其并行计算能力非常适合矩阵乘法、向量运算和深度学习，因此成为当前大模型训练和推理的重要硬件。

在本系列中，GPU 特指 NVIDIA 加速卡。它负责执行模型中的矩阵计算、注意力计算和采样相关算子。

### 1.2 昇腾 NPU {/* #昇腾-npu */}

NPU 是面向神经网络计算设计的加速器。华为昇腾通过自身硬件、CANN 软件栈和相关框架适配完成模型训练或推理。

从集群运维视角看，可以暂时把两者理解成：

> GPU/NPU 都是 Kubernetes 节点上的可调度加速资源

但从安装和排障视角看，必须把它们视为**两套独立技术栈**。

## 2. VRAM 与 HBM 是什么 {/* #二vram-与-hbm-是什么 */}

### 2.1 NVIDIA 显存 {/* #nvidia-显存 */}

GPU 拥有自己的设备内存，通常称为显存或 VRAM。模型权重、KV Cache、中间张量和通信缓冲都可能占用显存。

### 2.2 昇腾 HBM {/* #昇腾-hbm */}

昇腾高性能设备使用的高带宽内存通常称为 HBM。对于模型部署人员而言，它承担的角色与 GPU 显存相近：保存模型权重、缓存和计算中的临时数据。

需要注意：

- CPU 内存大，不代表加速器内存也大
- 模型权重位于磁盘时不能直接计算
- 启动时需要把权重加载进显存 / HBM
- 模型文件大小小于设备内存，不代表一定能成功运行
- 还要为 KV Cache 和运行时工作空间预留容量

可以先使用下面的粗略关系理解：

```text
设备内存需求
≈ 模型权重
+ KV Cache
+ 算子工作空间
+ 通信缓冲
+ 框架及内存碎片开销
```

## 3. 驱动解决了什么问题 {/* #三驱动解决了什么问题 */}

操作系统默认无法完整控制 GPU 或 NPU，需要厂商驱动负责：

- 识别设备
- 初始化设备
- 管理进程与设备通信
- 提供设备内存管理
- 暴露健康状态和错误信息
- 为上层计算库提供接口

如果驱动异常，上层容器、PyTorch、vLLM 和 Kubernetes Device Plugin 通常都会受到影响。

所以排障顺序一般不是从 Pod 开始，而是先确认物理设备和驱动：

```text
服务器是否识别设备
  ↓
驱动是否正常
  ↓
容器是否能访问设备
  ↓
Kubernetes 是否识别资源
  ↓
模型服务是否正常
```

## 4. CUDA 与 CANN 是什么 {/* #四cuda-与-cann-是什么 */}

### 4.1 CUDA {/* #cuda */}

CUDA 是 NVIDIA 提供的并行计算平台和软件生态。上层框架通过 CUDA 及相关库使用 GPU 能力。

双资源池项目中常见的 NVIDIA 链路是：

```text
NVIDIA GPU
→ NVIDIA 驱动
→ CUDA 相关运行库
→ PyTorch CUDA
→ vLLM
→ 模型服务
```

### 4.2 CANN {/* #cann */}

CANN 是昇腾 AI 处理器的软件栈，为上层框架提供算子、运行时、通信和开发能力。

常见昇腾链路是：

```text
Ascend NPU
→ 驱动和固件
→ CANN
→ torch_npu
→ vLLM-Ascend
→ 模型服务
```

CUDA 与 CANN 解决的层次相似，但它们**不是可以互换的同一个软件包**。

## 5. PyTorch、torch_npu、vLLM 是什么关系 {/* #五pytorchtorchnpuvllm-是什么关系 */}

**PyTorch**
上层深度学习框架，模型代码通常通过 PyTorch 描述计算过程。

**torch_npu**
为 PyTorch 提供昇腾设备适配，使 PyTorch 程序能够使用 NPU。

**vLLM 与 vLLM-Ascend**

- NVIDIA 资源池通常使用原生 vLLM 及 CUDA 后端
- 昇腾资源池使用 vLLM-Ascend 及昇腾相关依赖
- 两边可以向上提供相近的 OpenAI 兼容接口
- 两边不能使用完全相同的运行镜像

正确理解是：

```text
同一种 API 协议 ≠ 同一套底层运行环境
```

## 6. PCIe、NVLink 和 HCCS 分别在哪一层 {/* #六pcienvlink-和-hccs-分别在哪一层 */}

### 6.1 PCIe {/* #pcie */}

PCIe 是服务器中 CPU、GPU/NPU、网卡和其他设备之间的重要连接通道。

PCIe 拓扑会影响：

- CPU 到设备的数据传输
- 多卡之间通过主机路径通信
- 加速器与高速网卡之间的通信
- NUMA 跨节点访问开销

### 6.2 NVLink {/* #nvlink */}

NVLink 是 NVIDIA 设备间的高速互联技术。相比仅通过 PCIe 通信，它通常能为适配的 GPU 拓扑提供更高的设备间带宽。

多 GPU 模型使用 Tensor Parallel 时，需要频繁交换数据，因此设备拓扑会影响推理性能。

### 6.3 HCCS 等昇腾互联能力 {/* #hccs-等昇腾互联能力 */}

昇腾设备也有自身的片间或设备间互联体系。具体能力取决于服务器、NPU 型号和硬件拓扑，不能只看到「有多张卡」就假设任意两张卡之间带宽相同。

运维前必须基于真实服务器拓扑和厂商工具确认连接关系。

## 7. NCCL 与 HCCL 是什么 {/* #七nccl-与-hccl-是什么 */}

当模型需要多卡运行时，各加速器需要进行集合通信，例如：

- AllReduce
- AllGather
- ReduceScatter
- Broadcast

NVIDIA 主要使用 NCCL，昇腾主要使用 HCCL。

两条链路可以概括为：

```text
NVIDIA：vLLM → PyTorch/CUDA → NCCL → GPU/网卡
昇腾：vLLM-Ascend → torch_npu/CANN → HCCL → NPU/网卡
```

它们解决相似的分布式通信问题，但配置、日志、环境变量和故障表现不同。

这也是为什么单个模型并行组不能一半使用 NVIDIA、一半使用昇腾：两边的设备执行环境和集合通信体系不同。

## 8. RDMA 与 RoCE 为什么会出现在模型集群中 {/* #八rdma-与-roce-为什么会出现在模型集群中 */}

单机多卡可以通过机内互联交换数据；多机多卡则必须经过网络。

普通 TCP 网络能够通信，但在大规模集合通信中，可能面临更高延迟和更多 CPU 参与。RDMA 允许数据在节点间高效传输，RoCE 是在以太网上承载 RDMA 的一种方式。

多机推理链路可能是：

```text
加速器
→ PCIe/片间互联
→ 高速网卡
→ RoCE 网络
→ 另一台服务器的高速网卡
→ 另一侧加速器
```

因此多机推理变慢时，不仅要检查模型参数，还要检查：

- 网卡是否选择正确
- MTU 是否一致
- RoCE 是否配置正确
- 交换机是否满足无损网络要求
- 网络是否丢包
- NUMA 绑定是否合理
- NCCL/HCCL 是否走了预期链路

## 9. 两类资源池常用检查入口 {/* #九两类资源池常用检查入口 */}

### 9.1 NVIDIA 节点 {/* #nvidia-节点 */}

```bash
lspci | grep -i nvidia
nvidia-smi
nvidia-smi topo -m
```

主要观察：

- GPU 是否全部识别
- 驱动是否加载
- 显存使用
- GPU 利用率
- 温度和功耗
- 进程占用
- GPU 与网卡、CPU 之间的拓扑

### 9.2 昇腾节点 {/* #昇腾节点 */}

```bash
lspci
npu-smi info
```

主要观察：

- NPU 是否识别
- 驱动和固件状态
- HBM 占用
- NPU 利用率
- 温度和功耗
- 芯片健康状态
- 运行进程和错误信息

具体字段会随硬件型号和工具版本变化，生产运维应以对应型号的命令输出和兼容文档为准。

## 10. 为什么必须建立兼容矩阵 {/* #十为什么必须建立兼容矩阵 */}

很多模型故障不是代码错误，而是版本组合不兼容。

**NVIDIA 资源池**至少要记录：

```text
GPU 型号
操作系统与内核
NVIDIA 驱动
CUDA 兼容范围
Container Toolkit
PyTorch
vLLM
模型与量化方式
```

**昇腾资源池**至少要记录：

```text
NPU 型号
CPU 架构
操作系统与内核
驱动与固件
CANN
torch_npu
vLLM-Ascend
模型与模型制品格式
```

升级任何一层，都要评估其上下游，而不是只判断「软件包能不能安装」。模板见 [附录 B](./91-附录B-软硬件兼容矩阵模板.md)。

## 11. 常见误区 {/* #十一常见误区 */}

**误区 1：服务器内存够大，模型就能运行**
模型计算主要使用 GPU 显存或 NPU HBM，CPU 内存不能直接替代设备内存。

**误区 2：安装 CUDA Toolkit 就等于驱动正常**
驱动和 CUDA 用户态运行库处在不同层。首先要确认驱动能够识别设备。

**误区 3：容器里有命令，就说明设备可用**
镜像中存在工具不等于容器真正获得了设备。还要执行实际设备查询和最小计算测试。

**误区 4：两边都提供 OpenAI 接口，所以镜像可以共用**
API 一致只代表上层协议相近，底层依赖完全不同。

**误区 5：同一 Kubernetes 集群就能跨 GPU/NPU 做 Tensor Parallel**
Kubernetes 统一管理不等于异构设备能够加入同一个模型并行通信组。

## 12. 本篇练习 {/* #十二本篇练习 */}

### 12.1 练习 1：画两条软件栈 {/* #练习-1画两条软件栈 */}

不看本文，分别写出 NVIDIA 和昇腾从硬件到模型服务的完整链路。

### 12.2 练习 2：建立节点信息表 {/* #练习-2建立节点信息表 */}

选择一台现有加速器服务器，记录：

- CPU 架构
- 操作系统
- 内核
- 加速器型号和数量
- 设备内存
- 驱动版本
- 计算栈版本
- 网卡和磁盘
- 当前运行进程

### 12.3 练习 3：解释一个故障 {/* #练习-3解释一个故障 */}

如果 Kubernetes 节点状态正常，但 Pod 中看不到 GPU/NPU，请列出至少三个需要检查的层次。

参考思路：驱动、容器运行环境、Device Plugin、Pod 资源申请与调度配置。

## 13. 本篇小结 {/* #十三本篇小结 */}

双资源池中最重要的对应关系是：

| NVIDIA | 昇腾 |
|--------|------|
| GPU | NPU |
| 显存 | HBM |
| CUDA | CANN |
| PyTorch CUDA | PyTorch＋torch_npu |
| vLLM | vLLM-Ascend |
| NCCL | HCCL |
| nvidia-smi | npu-smi |

统一 Kubernetes 只能解决管理和调度问题，不能消除底层硬件差异。后续部署时，我们会为两类节点分别建立驱动、容器运行环境、Device Plugin、推理镜像和故障处理手册。
