# I/O 合并、队列深度与调度器：吞吐和延迟如何权衡

块层调度的目标不是让“磁盘一直 100% 忙”，而是在设备能力、吞吐、尾延迟、公平性和优先级之间做权衡。NVMe 与机械盘的最优策略通常不同。

## 1. 为什么合并请求

相邻小 IO 合并可以：

- 减少命令和中断固定开销。
- 提高顺序访问比例。
- 更充分利用设备大请求吞吐。

但等待更多请求以便合并会增加延迟，且随机工作负载并无多少可合并空间。

## 2. 调度器解决什么

| 调度器 | 主要倾向 | 典型考虑 |
|---|---|---|
| `none` | 最少块层排序，快速下发 | 设备/虚拟后端自身调度能力强 |
| `mq-deadline` | 兼顾排序并限制请求饥饿 | 通用块设备、读延迟保护 |
| `bfq` | 按进程/组提供更强带宽公平与交互性 | 桌面、部分共享设备场景 |
| `kyber` | 以延迟目标和 token 控制并发（是否可用依内核） | 支持该调度器的环境 |

可用调度器由内核配置、设备类型和发行版决定：

```bash
cat /sys/block/DEVICE/queue/scheduler
```

方括号内为当前选中项。

## 3. 调度器并非唯一队列

NVMe 控制器、SAN 阵列、云盘后端和虚拟机宿主机还有内部队列。来宾系统选择 `none`，不代表全链路没有调度；选择复杂调度器也可能与下层再次排序互相影响。

## 4. 队列深度与 Little's Law

稳态近似：

```text
平均在途数 L = 完成率 λ × 平均响应时间 W
```

提高并发可把设备推到更高吞吐，超过拐点后吞吐增长有限、延迟快速上升。容量测试应画出并发—IOPS—P50/P99 曲线，而不是只记录一个最大 IOPS。

## 5. 读写竞争

大量后台写回可能挤占前台随机读：

- 写队列深度过大。
- flush/FUA 引入同步点。
- 设备 GC 或阵列重建。
- cgroup IO weight/max 配置不合理。
- 多租户共享同一底层 LUN。

块层调度只能控制看得到的请求，无法完全控制设备固件和共享远端后端。

## 6. cgroup IO 控制

cgroup v2 可通过 `io.weight`、`io.max`、`io.latency`（支持情况依内核/设备）等接口治理组间 IO。限制应用于指定主次设备号，Device Mapper 场景需确认实际记账和下层设备。

```bash
cat /proc/<PID>/cgroup
cat /sys/fs/cgroup/<path>/io.stat
cat /sys/fs/cgroup/<path>/io.max
```

## 7. 修改前的验证

调整 scheduler 或深度前保存：设备型号/固件、拓扑、当前值、工作负载块大小/读写比/并发、基线 P50/P99、错误和恢复方案。在线切换虽可能支持，也会改变生产性能，不应作为无证据试错。

## 8. 练习与答案

**问题：NVMe 应无条件使用 none 吗？**

答案：不能绝对化。设备、虚拟化、共享方式、读写竞争和延迟目标不同，应在目标环境测试 none 与可用调度器。

**问题：队列深度从 32 增到 256，IOPS 只涨 5%，P99 涨 4 倍说明什么？**

答案：设备或后端已接近饱和，新并发主要转化为排队而非有效吞吐，256 很可能超过该延迟目标下的合理工作点。
