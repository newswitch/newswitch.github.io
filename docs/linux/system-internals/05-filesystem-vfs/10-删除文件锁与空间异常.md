# 删除文件、文件锁与空间异常：df、du、inode 和打开引用

文件系统“满”至少可能指数据块不足、inode 不足、配额不足、保留空间、元数据空间或底层 thin pool 满。`df` 和 `du` 观察对象不同，差异本身就是定位线索。

## 1. unlink 只删除名称

```text
unlink(path)
→ 从父目录移除名称
→ inode 链接计数减少
→ 若仍有打开 fd/mmap，数据继续存在
→ 最后链接和引用都消失后才能最终回收
```

日志文件被删除但进程仍打开时，`du` 遍历不到名称，`df` 仍看到块被占用。

```bash
lsof +L1
ls -l /proc/<PID>/fd
```

正确处理通常是让进程重新打开日志、正常重启或明确关闭 fd；直接操作 `/proc/PID/fd` 截断文件会影响正在写入的应用语义，不能作为默认动作。

## 2. df 与 du

- `df` 读取文件系统整体块/inode 统计。
- `du` 遍历当前目录树可见文件并汇总已分配块。

差异来源：已删除打开文件、其他 Mount Namespace、目录被新挂载覆盖、快照/reflink、文件系统元数据、保留块、权限导致遍历缺失等。

## 3. inode 耗尽

文件系统可能还有大量数据块，却无法创建新文件，因为 inode/元数据资源耗尽：

```bash
df -hT
df -ih
find /path -xdev -type f | wc -l
```

海量小文件还会增加目录查找、备份、扫描、Page Cache/dentry 和恢复成本。删除前必须确认业务、保留策略和并发写入。

## 4. 配额和分层容量

用户/组/项目配额、容器 ephemeral-storage、LVM thin pool、存储阵列和云盘配额可以在不同层限制写入。文件系统显示有空间，不代表底层 thin metadata 或远端配额有空间。

错误日志中的 `EDQUOT`、`ENOSPC`、I/O error 应区别处理。ENOSPC 也可能来自元数据/Journaling 预留而不是简单数据块为零。

## 5. 文件锁

Linux 常见 advisory lock 只有协作程序遵守时有效：

- `flock` 风格锁。
- POSIX record lock。
- Open File Description lock。

锁的进程/打开实例语义、fork/dup/close 行为不同；网络文件系统支持也有边界。锁住文件不会阻止不遵守协议的程序直接读写。

```bash
lslocks
cat /proc/locks
```

数据库不应依赖人工删除 lock file 来“解锁”，应确认它使用的是内核锁、PID 文件还是应用协议。

## 6. 空间排查顺序

```text
df -hT / df -ih
→ findmnt 确认目标文件系统和 Namespace
→ du 分层定位可见目录
→ lsof +L1 查已删除打开文件
→ 查快照、reflink、配额和文件系统元数据
→ 查 LVM thin/RAID/远端存储容量
→ 查内核和设备错误
```

## 7. 练习与答案

**问题：`rm` 了 100GiB 日志，df 为什么没有下降？**

答案：写日志进程可能仍持有打开文件引用；也可能存在快照/reflink或观察了不同挂载。先用 `lsof +L1` 和 mount 证据确认。

**问题：df 显示 60% 但创建文件返回 ENOSPC，可能是什么？**

答案：inode、配额、文件系统元数据、项目配额或底层 thin pool 可能耗尽，数据块百分比不是唯一容量边界。
