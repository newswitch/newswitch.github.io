# 从现象到根因的分层观测方法：把工具清单变成证据链

根因不是“某指标高”，而是一套能解释现象、时间、范围和恢复行为，并经对照或实验支持的机制。

## 1. 六步闭环

1. **定义现象**：谁慢/错、从何时、比例、请求类型、用户影响。
2. **确定范围**：单请求、进程、Pod、节点、AZ、运营商还是全局。
3. **建立对照**：健康实例、Pod IP 与 Service、同节点与跨节点、故障前后。
4. **定位等待层**：CPU、锁、内存回收、块 IO、网络、外部依赖。
5. **验证机制**：用 trace/profile/packet/源码确认具体路径。
6. **回归和预防**：复现修复、反例测试、监控和容量阈值。

## 2. 证据层级

```text
用户端：DNS / connect / TLS / TTFB / body
应用：queue / worker / lock / downstream / GC
进程：run queue / syscall / page fault / FD
cgroup：throttle / reclaim / IO / PID / PSI
内核：scheduler / VFS / block / TCP / conntrack
驱动设备：queue / IRQ / DMA / firmware / error
硬件外部：NUMA / PCIe / disk / switch / upstream
```

每层都要找入口、队列、服务者、完成和错误计数。

## 3. 事实与推断分开

```text
事实：14:03:10-14:08:20，目标 cgroup cpu.stat nr_throttled 每秒增长。
推断：quota 在负载峰值提前耗尽，造成周期性调度等待。
验证：临时提高同一测试实例 quota 后，throttle 与 P99 同时消失。
边界：只解释该实例和时间窗，不代表所有超时根因。
```

## 4. 不要从平均值直接跳结论

- CPU 40%：可能一个允许 CPU 满载或 cgroup throttle。
- 内存可用：目标 cgroup 可能达到 max。
- 磁盘 `%util` 低：单个同步写仍可能高尾延迟。
- Ping 正常：TCP 端口、MTU、Service/NAT 或应用队列仍可能异常。

## 5. 采集预算

开始前写清持续时间、目标 PID/cgroup/CPU、采样频率、最大文件、停止命令和敏感字段。观测导致 CPU 或磁盘进一步过载时，应立即降级。

## 6. 练习与答案

**问题：重启服务后恢复，根因是什么？**

答案：仅能说明重启重置的某种状态参与问题。它同时重建进程、连接、内存、锁、缓存和调度位置，不能单独定位根因。

**问题：修复后指标恢复能否证明因果？**

答案：证据增强但仍需排除同期变化；最好有对照、单变量实验和可重复结果。
