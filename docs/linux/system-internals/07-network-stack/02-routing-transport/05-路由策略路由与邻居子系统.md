# 路由、策略路由与邻居子系统：一个目的地址如何找到出口和下一跳

发送 IP 包前，内核需要决定：这是本机地址还是转发流量、查哪张路由表、从哪个接口发、下一跳是谁、使用哪个源地址。二层网络还需要把下一跳 IP 解析为链路层地址。

**路由选择和邻居解析是相邻但不同的步骤：前者确定下一跳 IP/出口，后者在需要二层寻址时取得下一跳的链路层地址。**有路由不代表下一跳可达，能 ARP 到网关也不代表远端服务可用。

下面以普通双网卡、无 VRF/ECMP/NAT 的 IPv4 主机为教学场景，参数语义以 **Linux v6.12、iproute2 v6.12.0**为基线。文中规则、地址与输出是配套教学快照，不是生产抓取，也不要求修改本机路由来跟读；实际故障必须带上所在 Network Namespace、mark 与流量方向。

## 1. 策略规则与 FIB

```text
目的/源/mark/接口等条件
→ Routing Policy Database 规则
→ 选择路由表
→ FIB 最长前缀匹配
→ route type、下一跳、出口接口、metric
→ 源地址选择
```

### 1.1 先规则优先级，再表内前缀

RPDB（Routing Policy Database）是策略规则集合，FIB（Forwarding Information Base）是路由查询使用的转发表。规则的 `priority` 数值越小越先检查；`lookup` 选择一张表后，在该表中查匹配路由。

**不是把所有表的路由汇总后，找全局最长前缀。**前面规则查到可用结果就可能结束，后面表里的 `/32` 不会自动击败前面表里的默认路由。若表中没有可用路由，或命中 `throw`，则可能继续下一条规则。

表内先看适用路由的最长前缀；同一前缀等条件下再比较 metric 等属性。小 metric 的默认路由不会胜过同表适用的更具体前缀。真实查询还受路由类型、scope、接口、链路状态及多路径等约束；下面刻意只保留单路径案例。

### 1.2 双网卡与两套策略表

```text
eth0：192.0.2.10/24       网关 192.0.2.1
eth1：198.51.100.10/24    网关 198.51.100.1
目标：203.0.113.80
```

这里使用文档示例地址。查询命令与规则快照如下：

```bash
ip -4 rule show
```

```text
0:      from all lookup local
100:    from all fwmark 0x20/0xff lookup 200
200:    from 198.51.100.0/24 lookup 100
32766:  from all lookup main
32767:  from all lookup default
```

数字 100/200 在这里既可能作为规则优先级，也可能作为表 ID，含义由字段决定。`priority 100 lookup 200` 是先执行的规则，不是优先查表 100。

`ip -4 route show table 100` 的教学输出：

```text
198.51.100.0/24 dev eth1 proto kernel scope link src 198.51.100.10
203.0.113.0/24 via 198.51.100.1 dev eth1 metric 100
203.0.113.64/26 via 198.51.100.254 dev eth1 metric 500
default via 198.51.100.1 dev eth1 metric 100
```

`ip -4 route show table 200`：

```text
192.0.2.0/24 dev eth0 proto kernel scope link src 192.0.2.10
default via 192.0.2.1 dev eth0 metric 900
```

`ip -4 route show table main`：

```text
192.0.2.0/24 dev eth0 proto kernel scope link src 192.0.2.10
198.51.100.0/24 dev eth1 proto kernel scope link src 198.51.100.10
203.0.113.80/32 via 192.0.2.254 dev eth0 metric 1
default via 192.0.2.1 dev eth0 metric 100
```

local 表另有本机 `192.0.2.10`、`198.51.100.10` 等地址的 local 路由，此处省略回环与广播项。`lookup default` 指表 ID 253，不是“直接采用所有表中的默认路由”；本例该表没有提供结果。

### 1.3 一次指定源地址的查询

```bash
ip -4 route get 203.0.113.80 from 198.51.100.10
```

只摘录解释需要的结果字段，省略 uid/cache 等附加项：

```text
203.0.113.80 from 198.51.100.10 via 198.51.100.254 dev eth1 table 100
```

推演过程为：

1. 规则 0 查 local；目标不是本机地址，没有终止结果。
2. 规则 100 要求 mark 的低八位为 `0x20`，本例未标记，不匹配。
3. 规则 200 匹配源网段，查询表 100。
4. 目标同时命中 `/24`、`/26` 和默认路由；`/26` 最长，所以选 `198.51.100.254`，即使其 metric 500 大于 `/24` 的 100。
5. 已得到可用单播结果，不再查 main。main 里 metric 1 的 `/32` 不参与这次比较。

### 1.4 同一目的加 mark 后为什么换了出口

```bash
ip -4 route get 203.0.113.80 from 198.51.100.10 mark 0x20
```

```text
203.0.113.80 from 198.51.100.10 via 192.0.2.1 dev eth0 table 200 mark 0x20
```

规则 100 先匹配并从表 200 得到默认路由，查询结束；不再由源地址规则选择表 100。metric 900 也不意味着要跨表输给 main 的 metric 1。

mark 是内核包/套接字相关的本地元数据，不是自动放在 IP 包头中传到对端的字段。掩码规则比较的是 `mark & mask`：`0x120 & 0xff` 同样为 `0x20`，也会命中；`0x21` 则不命中。

这次查询保留了指定源地址 `198.51.100.10`，**换出口不等于自动 SNAT 成 192.0.2.10**。主机可以构造这样的流量，但上游反欺骗检查、返回路径和防火墙是否允许，还要另外验证。

### 1.5 未指定源地址时不能直接套用上一结果

```bash
ip -4 route get 203.0.113.80
```

本例普通本地输出查询会走 main 中的 `/32`，得到关键字段：

```text
203.0.113.80 via 192.0.2.254 dev eth0 src 192.0.2.10
```

源地址会受应用 `bind`、套接字选项、路由首选源地址及地址可用性等影响；不是“从 eth1 进入的连接，回复一定从 eth1 发出”。`ip route get ... connected` 可在未提供 `from` 时，用首次查询的首选源地址再次查询，因此策略路由下结果可能变化。更准确的排查应复原真实的源地址与条件，而不是只查目的地址。具体语义见 [iproute2 v6.12.0 ip route](https://github.com/iproute2/iproute2/blob/v6.12.0/man/man8/ip-route.8.in)。

## 2. Local、Unicast 与其他路由类型

### 2.1 路由结果不一定是发到网关

| 类型 | 主要动作 | 是否可当作普通未命中继续查表 |
| --- | --- | --- |
| `local` | 交本机协议栈处理 | 不是；本机交付也是有效结果 |
| `unicast` | 按选定路径发向目标/下一跳 | 不是；本地输出和转发都可能用它 |
| `throw` | 结束本表查询，按策略规则继续寻找 | 是其主要用途；若后续仍无结果则失败 |
| `blackhole` | 静默丢弃流量，本地发送者仍可能收到错误 | 不是普通未命中 |
| `unreachable` | 不可达，通常向发送端返回相应错误 | 不是普通未命中 |
| `prohibit` | 管理策略禁止，通常返回禁止类错误 | 不是普通未命中 |

因此，表 200 存在默认 `unicast` 时，会覆盖很大的目的范围并终止查找；若针对某目的实际命中的是 `throw`，才有机会继续由源规则查表 100。`blackhole` 不等于 `throw`，不会自动回退成另一条可用出口。

### 2.2 本地输出与转发要带不同条件

本地进程发包与包从接口进入主机再转发，使用的查询上下文不同。`ip route get` 未给 `iif` 时主要模拟本地输出；需要分析转发时，应提供实际输入接口、源地址及 mark，并考虑 `ip_forward` 和防火墙。

本例 local 表在规则 0 查询，因此访问本机的 `198.51.100.10` 会先命中本地交付，不会因为它也属于表 100 的直连前缀，就再发一个包到外部交换机。真实 Kubernetes Service、透明代理和 eBPF 数据面还可能在路由查询前后改变流量处理方式，不能只按 VIP 的外观判断路径。

## 3. 邻居子系统

### 3.1 ARP 与 NDP 解析的是所选下一跳

在普通以太网场景，IPv4 常用 ARP，IPv6 使用 Neighbor Discovery（NDP）。邻居缓存不仅保存 IP→MAC，还通过 NUD（Neighbor Unreachability Detection）管理可达性状态。它属于特定网络命名空间和设备，同一 IP 在不同设备上的条目不能混用。

在 1.3 的查询中，需要解析的是 **`198.51.100.254` 在 eth1 上的 MAC**，不是向远端网段广播询问 `203.0.113.80`。读取方式如下：

```bash
ip -4 neigh show to 198.51.100.254 dev eth1
ip -4 -s neigh show dev eth1
```

教学条目：

```text
198.51.100.254 dev eth1 lladdr 02:00:00:00:01:fe REACHABLE
```

它不保证下一跳之后的网络、目标主机或业务端口可用。更不能把条目中的 MAC 当成最终远端服务器的 MAC。

### 3.2 STALE 不等于故障

典型动态条目的部分状态变化如下，省略静态、NOARP 等特殊状态：

```text
首次解析：无条目 → INCOMPLETE ──解析成功──→ REACHABLE
                         └──解析失败──→ FAILED

已解析：REACHABLE ──确认过期──→ STALE
       STALE ──再次使用──→ DELAY ──仍未确认──→ PROBE
                                             ├─确认成功→ REACHABLE
                                             └─探测耗尽→ FAILED
```

STALE 表示已有链路层地址，但近期可达性需要重新确认；通常仍可先用已有 MAC 发包，不是每次都要等一次 ARP 才能继续。DELAY 给上层反馈等确认留下机会，必要时再进入 PROBE。FAILED 才表示这轮解析/验证失败，但仍须排查 VLAN、链路、网关、邻居容量和过滤等原因，不能直接归因到应用。

同一个邻居在不同时间的教学摘录可以是：

```text
198.51.100.254 dev eth1 INCOMPLETE
198.51.100.254 dev eth1 lladdr 02:00:00:00:01:fe REACHABLE
198.51.100.254 dev eth1 lladdr 02:00:00:00:01:fe STALE
```

不能把这三行理解为三个同时存在的邻居。状态要结合计数、事件与抓包观察，不应以 `ip neigh flush all` 作为默认修复动作；清掉仍有效的条目可能制造额外解析与丢包。状态定义见 [iproute2 neighbour 文档](https://github.com/iproute2/iproute2/blob/v6.12.0/man/man8/ip-neighbour.8)。

## 4. 同网段与跨网段

### 4.1 从路由结果推到二层头

| 本例流量 | 命中路径 | 需要解析的地址 | IP 目的 |
| --- | --- | --- | --- |
| `198.51.100.10 → 198.51.100.20`，未标记 | 表 100 的直连 `/24` | `198.51.100.20` | 仍为 `198.51.100.20` |
| `198.51.100.10 → 203.0.113.80`，未标记 | 表 100 的 `/26` | `198.51.100.254` | 仍为 `203.0.113.80` |
| 同一跨网段流量，mark=`0x20` | 表 200 的默认路由 | `192.0.2.1` | 仍为 `203.0.113.80` |

“同网段直接 ARP 目标”也有前提：必须是本次查询选择了直连路径。若更早的策略规则把流量送到另一条路由，地址看起来同网段也不能覆盖实际结果。点到点设备、隧道与代理 ARP 等还会改变二层处理方式。

第一条跨网段包离开 eth1 时，二层目的为网关 `.254` 的 MAC，IP 目的仍为远端 `.80`；沿普通路由逐跳前进时，二层头按下一链路重建，IPv4 TTL 或 IPv6 Hop Limit 递减。普通路由器不会因此重建 TCP 连接，NAT、隧道封装等则是另外的处理。

### 4.2 有界抓包只验证所处观察点

需要验证 eth1 上是否真的发生 ARP 或发送目标流量时，可在获准环境短时观察：

```bash
tcpdump -ni eth1 -e -c 20 '(arp or (ip and host 203.0.113.80))'
```

`-e` 显示链路层信息，`-c` 限定包数，但没有匹配流量时仍需手动结束。路由查询预期走 eth1、实际却没有抓到包时，还要确认抓包 Namespace/接口、应用是否发包，以及 Netfilter、TC/XDP、隧道和 offload 观察点，而不是立即认定网卡丢包。命令细节见 [tcpdump](../../../../networking/commands/02-diagnostics-performance/07-tcpdump命令详解.md)。

## 5. 反向路径过滤

### 5.1 三种模式检查的不是同一件事

`rp_filter` 是 **IPv4 入站源地址验证**。它根据反向 FIB 查询检查源是否合理，不是测试对方能否收到回复，也不是检查 TCP 握手是否成功。

| 值 | 模式 | 核心判断 |
| --- | --- | --- |
| 0 | 关闭此项源验证 | 不由该开关执行反向路径过滤；仍可能被防火墙等丢弃 |
| 1 | strict，严格 | 最佳反向路径应符合入接口；普通单路径下反向出口不同可能被丢弃 |
| 2 | loose，宽松 | 源地址经路由判断可达即可，不要求返回同一接口 |

以 1.2 的主机为例，包从 **eth1** 进入，源为 `203.0.113.80`，目的为本机 `192.0.2.10`，无 mark。反向查询的直观检查为：

```bash
ip -4 route get 203.0.113.80 from 192.0.2.10
```

本例 main 的 `/32` 指向 eth0，所以普通严格检查可能拒绝这个从 eth1 进入的非对称流量；宽松检查则可因源存在可用路径而通过。这里用 `ip route get` 帮助理解，**不是宣称它完整复刻内核的源验证上下文**；VRF、ECMP、iif、IPsec、mark 和路由类型等还会影响具体实现。

宽松模式也不是“关闭验证”，但若存在覆盖任意源的默认路由，很多来源都会满足可达条件。它不是完整的反欺骗方案，不能取代入口 ACL、安全组和业务网络边界。IPv6 不能直接套用这个 IPv4 sysctl。

### 5.2 all 与接口取值取数值最大值

在 Linux v6.12 中，接口生效值采用 `conf/all/rp_filter` 与 `conf/接口/rp_filter` 的**数值最大值**，不是“选安全上最严格的模式”。

```bash
sysctl net.ipv4.conf.all.rp_filter
sysctl net.ipv4.conf.default.rp_filter
sysctl net.ipv4.conf.eth1.rp_filter
```

| all | eth1 | eth1 生效模式 |
| --- | --- | --- |
| 1 | 0 | 1，接口单独写 0 不能覆盖 all=1 |
| 1 | 2 | 2，数值更大但语义更宽松 |
| 0 | 0 | 0，关闭此项检查 |

`default` 主要提供新建接口的初始设置，不是每次查询时与 all/接口再取一次最大值。内核文档默认值不等于发行版或 CNI 已配置的运行值，必须在目标 Namespace 读取。

### 5.3 mark 是否参加反向查询由另一项控制

```bash
sysctl net.ipv4.conf.all.src_valid_mark
sysctl net.ipv4.conf.eth1.src_valid_mark
```

`src_valid_mark=0` 时反向查询不纳入该包的 fwmark；为 1 时纳入，生效也取 all/接口最大值。在双向依赖相同 mark 的设计中，纳入 mark 可能必要；只对单向打标的透明代理场景则未必适合。**不能把设为 1 当成通用修复。**

仍用本例，假设包从 eth1 进入，源 `203.0.113.80`、目的 `198.51.100.10`，包在源验证时已经有 mark=`0x20`：

- 不纳入 mark：反向查询按源网段规则进入表 100，指向 eth1，普通严格检查可以符合入接口。
- 纳入 mark：更早的 mark 规则选择表 200，反向出口变成 eth0，反而可能不符合严格检查。

必须先核对打标发生的位置、规则优先级与双向路径，再决定是否修改。参数依据见 [v6.12 ip sysctl](https://github.com/torvalds/linux/blob/v6.12/Documentation/networking/ip-sysctl.rst)，实现入口为 [`fib_validate_source` / `__fib_validate_source`](https://github.com/torvalds/linux/blob/v6.12/net/ipv4/fib_frontend.c)。

## 6. 路由缓存与变更

Linux 从 3.6 起移除了旧式 IPv4 全局路由缓存，但这不等于系统里不再有任何缓存：套接字/dst 路径信息、邻居缓存、PMTU 等仍有各自生命周期。`ip route get` 输出中的 `cache` 也不证明旧式全局缓存又回来了。

因此，路由规则更新、已有长连接和新连接的行为不应只靠“flush cache”经验推断，更不能把重启业务作为唯一验证。先保存现状，再按实际流量条件查询：

```bash
readlink /proc/self/ns/net
ip -4 rule show
ip -4 route show table all
ip -4 route get 203.0.113.80 from 198.51.100.10 mark 0x20
ip -4 neigh show nud all
```

若目标进程位于另一网络命名空间，可在有相应权限的宿主机使用其**宿主 PID**查询：

```bash
nsenter -t "$PID" -n -- ip -4 rule show
nsenter -t "$PID" -n -- ip -4 route get 203.0.113.80 from 198.51.100.10 mark 0x20
```

示例地址需替换为实际元组。这些查询不发送测试业务包，也不修改持久路由规则；查询成功只证明该上下文能解析出路由，不证明 ARP、防火墙、MTU、对端监听和回程都正常。

恢复后应同时核对规则/表、实际发包出口和源地址、邻居状态、回包路径，以及原业务连接和新连接。单独看到默认路由存在、邻居 REACHABLE 或一次 `ip route get` 成功，都不足以结束排障。

## 7. 练习与答案

### 7.1 访问跨网段服务器时 ARP 查询谁

答案：通常查询路由选择出的下一跳网关 MAC；IP 目的地址仍是服务器。

### 7.2 默认路由存在是否保证所有目的都走默认路由

答案：不保证。更具体前缀、local table、策略规则、mark 和特殊路由类型都可能优先决定结果。

### 7.3 未标记且源为 eth1 地址时为何不选 main 的主机路由

答案：源规则先查表 100 并得到 `/26` 的可用结果，RPDB 查询已结束。main 的 `/32` 再具体也不是跨表全局候选。

### 7.4 表内较大的 metric 为何仍可能获选

答案：目标同时匹配 `/26` 与 `/24` 时，先选更长的适用前缀，所以 `/26 metric 500` 优先于 `/24 metric 100`。metric 不能跨前缀或跨表直接决定所有优先级。

### 7.5 mark 为 0x120 是否命中本例规则

答案：会命中，因为 `0x120 & 0xff = 0x20`。匹配的是受掩码保留的位，不是完整整数必须相等；`0x21` 则不匹配。

### 7.6 换成 eth0 出口是否自动改成 eth0 的源地址

答案：不会自动改写已经指定的源。本例 mark 查询仍保留 `198.51.100.10`，没有执行 SNAT。应用源地址选择、路由选择和 NAT 是不同机制。

### 7.7 STALE 邻居是否必须立即清理

答案：不是。它通常还有可用 MAC，可先发包并在后续确认/探测中更新状态。清理会强制重新解析，可能增加扰动；应关联流量和验证结果判断。

### 7.8 all 为一而接口为零时是否关闭反向过滤

答案：没有，数值最大值为 1，仍为严格模式。all=1、接口=2 时最大值为 2，却是更宽松的 loose，所以不是选“最严格”的意思。

### 7.9 将 src_valid_mark 设为 1 是否总能修好非对称路由

答案：不能。它会改变反向查询输入；本例带 mark 的查询可能因此从表 100/eth1 换到表 200/eth0，反而不符合严格检查。必须结合打标时机和实际双向策略判断。

### 7.10 ip route get 成功但请求超时下一步看什么

答案：先确认 Namespace、源、mark、方向与业务一致，再查所选下一跳的邻居解析、实际接口抓包、过滤/封装/MTU、回程与对端服务。该命令不会替你验证端到端可达性。
