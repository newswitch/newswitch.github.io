# 丢包、重传与延迟分层排查：从应用到网卡建立证据链

网络慢不能只靠一次 ping 或一端 tcpdump 判断。先确定请求在哪个阶段超时，再沿实际 Namespace、路由和设备逐层寻找首个异常点。

## 1. 先把时间拆开

```text
DNS
→ connect/TLS
→ 请求在客户端排队
→ 网络往返
→ 服务端 accept/调度
→ 应用处理/依赖
→ 响应传输
```

总耗时高不等于网络 RTT 高。使用应用时间戳、curl 分阶段、Socket 连接状态和服务端日志对齐。

## 2. 基础快照

```bash
date -Ins
ip -br addr
ip rule
ip route get <peer>
ip neigh
ss -s
ss -ti dst <peer>
ip -s link
tc -s qdisc
cat /proc/net/softnet_stat
```

同时记录所在 Network Namespace、节点、接口和时间窗口。容器命令结果不能代替宿主机物理网卡证据。

## 3. 丢包位置矩阵

| 层次 | 证据示例 |
|---|---|
| 应用/Socket | send/recv 阻塞、Socket queue、UDP RcvbufErrors |
| TCP | retrans、SACK、zero window、RTO、RTT |
| Netfilter/conntrack | rule counter、insert failed/table full |
| softnet/NAPI | dropped、time_squeeze、softirq CPU |
| qdisc | drops、overlimits、backlog |
| NIC/驱动 | missed/no-buffer/CRC/timeout 等驱动计数 |
| 链路/交换机 | 端口 CRC、drop、pause、拥塞队列 |
| 对端 | 对端抓包、Socket/应用指标 |

不同驱动计数命名不同，不能只搜索一个固定字段。

## 4. 多点抓包

在发送端和接收端同一时间窗抓包：

- 发送端有，对端无：中间路径或发送端更后层。
- 两端都有，服务端应用无：服务端协议栈、Socket 或应用调度。
- 对端回包有，客户端无：反向路径/NAT/防火墙。
- 重复序列号和 SACK：可识别重传、乱序和缺口。

抓包会包含敏感数据并消耗 CPU/磁盘，应使用过滤器、snaplen、文件轮转和最短必要窗口。

## 5. ICMP/MTR 的边界

中间路由器可能限速 ICMP 响应。如果某一跳显示高丢包、后续和目标恢复正常，常是控制面响应限速；如果丢包/高延迟从某跳持续到目标，更值得怀疑数据路径。但路径可能 ECMP，ICMP、UDP、TCP 探测也可能走不同策略。

## 6. Service 超时但 Pod IP 正常

这把范围缩小到额外路径：Service 规则/eBPF、conntrack、NAT、后端选择和返回路径。继续检查：

1. ClusterIP 对应数据面模式。
2. conntrack count/insert failed。
3. 选中的 Endpoint 是否健康。
4. SNAT 和反向路由是否一致。
5. MTU/封装是否仅在该路径不同。

不能只因 Pod IP 正常就重启 kube-proxy。

## 7. 高频误判

- ping 通不代表 TCP 端口和业务可用。
- 本机 tcpdump 没包不一定链路没到，XDP/硬件卸载可能更早处理。
- TCP retrans 增长不直接说明发送端网卡丢包。
- CPU 平均低不排除 softirq 单核热点。
- MTU 小包正常不排除大包黑洞。
- 重启恢复不等于根因是“缓存”。

## 8. 形成结论

合格结论应包含：

```text
现象和影响范围
→ 首个异常时间
→ 实际数据路径
→ 异常计数在哪一层首次增长
→ 上下游交叉证据
→ 根因与触发条件
→ 临时恢复和长期修复
→ 如何监控与复现验证
```

## 9. 练习与答案

**问题：发送端显示 TCP 重传，能否断定中间网络丢包？**

答案：不能。还可能是发送端 qdisc/NIC、对端接收、ACK 反向路径、严重乱序或抓包点卸载表现，需要两端和各层计数交叉验证。

**问题：某中间 hop 在 mtr 显示 80% loss，目标 0% loss，说明什么？**

答案：更可能是该设备限速/低优先处理探测响应，而非转发数据丢失；目标端结果和业务流证据优先。
