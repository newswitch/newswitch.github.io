# 系统调用追踪实验：验证一次 read 从用户态到内核态的路径

本实验不修改内核，通过同一输入分别观察 libc/syscall 边界、系统调用事件、函数采样和 IO 计数，验证缓存命中与冷读路径差异。

## 1. 实验问题

- 应用的一次 `read` 是否一定产生磁盘 IO？
- 返回字节数、文件 offset 和 Page Cache 如何变化？
- strace 看到的耗时与内核 on-CPU 时间是否相同？

## 2. 环境记录

```bash
uname -a
stat /path/to/lab-file
findmnt -T /path/to/lab-file
lsblk -o NAME,TYPE,FSTYPE,MOUNTPOINTS
```

选择独立测试文件。不要在生产通过 drop_caches 制造冷缓存；使用新文件、独立 VM 或足够大的实验数据。

## 3. 边界观察

```bash
strace -tt -T -yy -e trace=openat,read,close <reader> /path/to/lab-file
perf stat -e page-faults,major-faults,minor-faults,block:block_rq_issue,block:block_rq_complete -- \
  <reader> /path/to/lab-file
```

tracepoint 是否可用以 `perf list` 为准。第一次和第二次读取对比 block issue、fault、耗时，但文件系统预读和设备缓存会影响结果。

## 4. 源码对应

按目标版本追踪：架构 syscall table/wrapper → `ksys_read`/`vfs_read` 或当前等价入口 → `file_operations` read iterator → filesystem/page cache → 可选块层。函数名会演进，先从 trace/符号确认。

## 5. 预期与反例

缓存命中时通常无块请求，但仍有 VFS、权限/状态、copy_to_user 和调度成本。Direct IO 可能绕过 page cache，但对齐、文件系统和设备语义不同。mmap 读取在缺页时走 fault 路径，不表现为同样的 `read` syscall。

## 7. 练习与答案

**问题：第二次读取没有 block request，能否证明数据来自进程自己的缓存？**

答案：不能。更常见是内核 Page Cache，也可能有应用缓存；需根据是否仍执行 read、返回数据和内存映射区分。

**问题：strace 的 read 用时比 perf 采样函数 CPU 时间长，矛盾吗？**

答案：不矛盾。read wall time 可包含睡眠、IO 和调度等待，on-CPU profile 只统计运行样本。
