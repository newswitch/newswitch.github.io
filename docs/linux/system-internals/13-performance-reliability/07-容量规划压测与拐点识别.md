# 容量规划、压测与拐点识别：不要把峰值吞吐当安全容量

安全容量不是服务刚好不报错时的最大 QPS，而是在目标 SLO、真实流量形态、单故障和增长条件下仍能运行的负载。

## 1. 需要的输入

- 峰值/分时到达率与突发持续时间。
- 请求大小、类型、读写比和租户分布。
- CPU、内存、IO、网络和下游单请求成本。
- 扩容准备时间与数据重平衡成本。
- N+1/N+2、AZ 故障和维护冗余。
- 季节增长、发布放量和重试放大。

## 2. 服务曲线

逐步提高负载，记录吞吐、P50/P95/P99、错误率、队列和资源压力：

```text
线性区：吞吐随负载增长，延迟稳定
拐点区：队列/长尾开始快速上升
饱和区：吞吐不再增长，延迟和错误持续恶化
```

生产容量应位于拐点之前，并预留故障与扩容滞后，而不是以饱和吞吐乘机器数。

## 3. 横向扩展不是线性

共享数据库、锁、缓存一致性、网络 uplink、控制面和数据重平衡都会使效率下降。测 1、2、4、8 实例的 scaling curve，计算新增实例的边际吞吐。

## 4. 压测校准

压测器自身也会饱和。验证客户端 CPU/网络、连接数、端口和时间同步；使用真实数据大小、TLS、长短连接和下游，不要只测一个空 handler。

## 5. 故障容量

若 10 节点正常负载每台 60%，失去 2 节点后理论平均变为 75%，还未包括重试和重平衡。故障测试需验证 P99/SLO，而不是只看存活。

## 6. 练习与答案

**问题：单机最大 10k QPS，10 台是否可规划 100k QPS？**

答案：不能直接相乘。需要测多机效率、共享依赖、负载均衡、故障冗余和长尾目标。

**问题：自动扩缩容能否消除容量预留？**

答案：不能。检测、调度、镜像拉取、模型/缓存预热都有延迟，突发期间仍需 headroom。
