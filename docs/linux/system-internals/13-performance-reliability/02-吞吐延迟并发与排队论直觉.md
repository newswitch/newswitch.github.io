# 吞吐、延迟、并发与排队论直觉：利用率接近上限时为什么长尾爆炸

请求延迟由服务时间和等待时间组成。系统接近饱和后，轻微到达波动就会形成队列，P99 往往在吞吐达到理论峰值前先失控。

## 1. 基本量

- 到达率 `λ`：单位时间新请求数。
- 服务率 `μ`：服务者单位时间可完成数。
- 并发/在途量 `L`。
- 平均响应时间 `W`。

稳态下 Little 定律：`L = λ × W`。它是观测关系，不要求特定分布，但系统必须在观察窗内近似稳定、边界一致。

例：2000 req/s、平均端到端 50 ms，则平均约有 `2000 × 0.05 = 100` 个请求在途。

## 2. 利用率与队列

单服务台简化模型中，利用率趋近 100% 时等待非线性增长。真实系统有多核、批处理、缓存和相关到达，但“不能把长期目标设为永远满载”仍成立。

## 3. 并发不是吞吐

增加并发可填满流水线，超过饱和点后只会增加队列和内存。闭环压测中，客户端等待响应再发下一个请求，服务变慢时发送率也下降，可能漏报最严重长尾。

## 4. Coordinated Omission

若压测工具本应每 10 ms 发一次，但前一请求卡 1 秒导致后续请求根本没按计划发出，记录只包含那个慢请求，没有记录本应到达并排队的请求，延迟分布被低估。开放模型或校正直方图更接近独立到达。

## 5. 批处理

批处理摊薄固定开销、提高吞吐，却会让第一个请求等待 batch 填充并扩大方差。动态 batching 要同时控制最大 batch 和最大等待时间。

## 6. 练习与答案

**问题：吞吐不再增长、CPU 只有 50%，系统是否没饱和？**

答案：可能已经在单线程、锁、IO、网络、配额或下游连接池饱和；整机 CPU 不是唯一服务台。

**问题：把队列长度调大能提升服务能力吗？**

答案：队列主要吸收突发，不增加服务率。过大会增加延迟和超时后的无效工作。
