# 性能分析方法：从工作负载和基线到可证伪假设

性能数字只有在相同目标、工作负载和环境下才可比较。先定义“更快”对谁、在哪个负载、牺牲什么，再开始调参。

## 1. 问题定义

```text
目标：吞吐 ≥ X，P99 ≤ Y，错误率 ≤ Z
工作负载：请求分布、并发、数据集、冷热、读写比、连接模型
环境：硬件拓扑、内核、固件、容器限制、依赖版本
约束：正确性、可用性、成本、功耗、恢复时间
```

用平均请求和空缓存/热缓存不一致的两次测试对比，结论没有意义。

## 2. 建立基线

基线应同时保存：业务结果、系统资源、运行配置和原始数据。测试需经过预热并持续足够长，区分 steady state 与启动/缓存填充阶段。

至少重复多轮，报告分布或置信区间，而不是只取最好一次。

## 3. 假设格式

```text
观察：P99 在并发 64 后急升，同时目标 cgroup nr_throttled 增长。
机制：cpu.max 周期内提前耗尽，线程等待下一周期。
预测：提高 quota 后 throttle 下降，P99 拐点右移；吞吐可能提高。
反例：若 P99 不变，应转查锁或下游等待。
```

假设必须能被数据否定。`系统压力大` 不是可验证机制。

## 4. 单变量与现实系统

理想实验一次改一个变量；无法完全控制时，要记录所有同期变化并设置健康对照组。动态频率、NUMA、后台任务、网络路径和自动扩缩容都可能污染结果。

## 5. 正确性先于性能

关闭 fsync、丢弃校验、减少副本或扩大超时都可能让 benchmark 更好，却改变持久性和失败语义。优化必须回归数据正确性、错误处理和故障恢复。

## 6. 停止条件

优化到达业务目标后应评估复杂度和边际收益。继续追求峰值可能增加脆弱性、成本和维护负担。

## 7. 练习与答案

**问题：新版本吞吐高 10%，能否宣布优化成功？**

答案：不能。还要确认 workload/环境一致、统计波动、P99/错误率/资源/正确性和成本没有退化。

**问题：测试时固定 CPU 频率是否总比生产真实？**

答案：它提高可重复性但可能偏离生产功耗策略。可先固定做机制对比，再在真实策略下做验证。
