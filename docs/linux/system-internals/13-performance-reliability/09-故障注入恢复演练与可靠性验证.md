# 故障注入、恢复演练与可靠性验证：证明系统真的能恢复

“有副本、有备份、有重试”都是设计声明；只有在可控故障中完成检测、切换、恢复和数据校验，才能证明可靠性。

## 1. 实验卡片

```text
假设：单节点失联时，服务 60 秒内恢复且不丢已确认写入
范围：测试租户/一个实例/一个 AZ
注入：进程终止、网络隔离、磁盘延迟或节点重启
护栏：错误率、影响用户、最大时长、人工停止条件
证据：告警时间、切换日志、请求 trace、数据校验
回滚：解除注入、恢复资源、验证副本与积压
```

## 2. 从低风险开始

先在隔离环境验证工具，再从单进程、单副本、只读流量逐步扩大。生产注入需要业务授权、值守、冻结同期变更和明确终止按钮。

## 3. 故障类型

- CPU：quota/忙循环/调度延迟，而不只是 kill。
- 内存：限制、回收、OOM、NUMA 远端。
- 存储：延迟、错误、只读、空间/inode 满、fsync 失败。
- 网络：丢包、延迟、抖动、乱序、单向隔离、DNS。
- 进程/节点：crash、hang、重启、断电。
- 依赖：限流、部分错误、慢响应和不一致返回。

不要用会不可逆破坏数据的方式制造“更真实”故障。

## 4. 恢复不止服务可访问

还要校验：

- RTO：从影响开始到满足服务目标。
- RPO：允许丢失的数据时间范围。
- 已确认写入和顺序/唯一性。
- 积压清空时间、重试风暴和缓存预热。
- 故障副本重新加入后的数据一致性。
- 备份是否能在独立环境 restore 并通过业务校验。

## 5. 可靠性回归

每次架构、内核、运行时、存储或网络变更都可能改变恢复路径。把关键演练自动化为周期测试，但保留人工审查和停止条件。

## 6. 练习与答案

**问题：演练中主从切换成功，是否已验证 RPO=0？**

答案：没有。还需检查切换点已确认事务、复制模式、客户端重试和业务数据一致性。

**问题：Chaos 工具执行成功是否表示实验成功？**

答案：只表示注入动作完成；实验成功取决于假设、用户影响、检测、恢复和数据校验。
