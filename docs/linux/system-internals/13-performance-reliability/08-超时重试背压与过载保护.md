# 超时、重试、背压、熔断与过载保护：让失败停止扩散

系统过载时继续无限排队和重试，会把短暂慢请求变成全链路雪崩。可靠设计要限制在途工作，并把端到端 deadline 分配给各阶段。

## 1. 超时不是越大越可靠

超时过短会误杀正常长尾，过长会长期占用线程、连接、内存和队列。应根据下游分布、用户 deadline 和网络预算确定，并区分 connect、read、write、queue 等阶段。

端到端 deadline 应向下游传递，避免上游已放弃后下游仍执行昂贵工作。

## 2. 重试条件

只有以下条件同时满足才应重试：

- 错误可能瞬态恢复。
- 操作幂等或有 idempotency key/事务去重。
- deadline 仍足够。
- 有 retry budget、次数上限、指数退避和 jitter。
- 不会跨多层重复重试形成乘法放大。

三个层级各重试 3 次，最坏可能产生 `3³=27` 次尝试。

## 3. 背压

背压让上游感知下游消费能力：有界队列、并发 semaphore、TCP window、stream flow control、消息消费 credit 都是形式。无界队列只是把失败推迟到 OOM 和超时。

## 4. 熔断与负载丢弃

熔断在高失败期停止新尝试，半开探测恢复；load shedding 在入口拒绝低优先级/超预算请求，保护核心流量。它们要有按租户/优先级公平性，避免一个大客户占满预算。

## 5. Linux 层证据

- Socket backlog、send/recv queue、SYN/accept drop。
- thread/process pool、run queue、futex 等待。
- cgroup CPU throttle、memory/io PSI。
- conntrack、ephemeral port、FD 和 PID 上限。

应用队列与内核队列要联合观察。

## 6. 练习与答案

**问题：请求超时后客户端重试成功，是否说明策略正确？**

答案：不一定。第一次请求可能仍在执行并产生重复副作用；还要验证幂等、取消传播和总负载。

**问题：把队列改为有界会增加拒绝，为什么反而可靠？**

答案：它把不可服务负载快速、可预测地失败，保护已接收工作和恢复能力，避免所有请求一起超时。
