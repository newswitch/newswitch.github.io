# 启动失败与安全恢复：按最后成功阶段定位问题

启动排障最重要的不是尝试最多的修复命令，而是保住可回退路径和原始证据。先确定最后成功阶段，再只改变一项变量。

## 1. 建立时间线

记录：

```text
变更前最后一次成功启动
→ 做了什么变更
→ 固件/GRUB 是否出现
→ 最后一条内核日志
→ 是否进入 initramfs shell
→ 是否进入 systemd emergency/rescue
→ 哪些 Unit 成功，哪个目标没有到达
```

“重启后坏了”不等于内核问题。`fstab`、证书权限、网卡命名、LVM、驱动、initramfs 和应用配置都可能只在冷启动时暴露。

## 2. 四个恢复入口

| 入口 | 适用情况 |
|---|---|
| BMC KVM/SOL | 网络和 SSH 不可用、观察固件与内核早期日志 |
| GRUB 旧内核/临时编辑 | 新内核、initramfs 或参数导致失败 |
| initramfs emergency shell | 无法找到或挂载真实根 |
| systemd rescue/emergency | 真实根可用，但挂载或用户空间服务失败 |

进入恢复环境前确认键盘、串口、远程介质和磁盘写入边界。生产节点上的文件系统修复、LVM 修改和 initramfs 覆盖都可能扩大损坏。

## 3. 只读采集优先

成功进入旧内核或救援环境后先采集：

```bash
journalctl --list-boots
journalctl -b -1 -k
journalctl -b -1 -p warning
cat /proc/cmdline
lsblk -f
findmnt
systemctl --failed
```

`-b -1` 表示上一次启动，但只有 journal 持久化且启动记录存在时可用。发生 Kernel Panic 时，普通 journal 可能来不及落盘，需要串口、pstore/ramoops、kdump 或 BMC 记录。

## 4. 常见场景

### 4.1 `/etc/fstab` 导致 emergency mode {/* #etcfstab-导致-emergency-mode */}

非关键数据盘不存在、UUID 写错或远端挂载无超时可能阻塞启动。修复前先确认该挂载是否属于启动关键路径；`nofail`、`x-systemd.automount` 和合理超时可以改变启动依赖，但不能用来掩盖关键数据盘丢失。

### 4.2 新内核无法启动 {/* #新内核无法启动 */}

从 GRUB 选择旧内核验证。如果旧内核成功，对比内核参数、initramfs 内容、模块、驱动和 Secure Boot 状态，而不是立即删除新内核。

### 4.3 文件系统检查失败 {/* #文件系统检查失败 */}

不要在已读写挂载的文件系统上直接运行破坏性修复。确认备份、设备健康和文件系统类型，必要时离线检查。

### 4.4 网络未恢复 {/* #网络未恢复 */}

控制台登录后区分：接口不存在、链路未 Up、地址缺失、路由缺失、DNS 异常、防火墙阻断、sshd 未启动。不要把所有情况统称为网络没起来。

## 5. 回退优先于现场发明

可回退变更应提前准备：

- 保留旧内核和菜单项。
- 修改 GRUB、fstab、网络或认证前保存可验证副本。
- 维护带外控制台和恢复凭证。
- 驱动、固件和内核按兼容矩阵升级。
- 变更后执行真实重启验证，而不只检查文件生成成功。

## 6. 关机也是启动可靠性的一部分

正常关机会停止服务、终止进程、同步和卸载文件系统，最后调用内核重启/关机路径。强制断电可能留下未完成写入，日志文件系统只能保证其承诺范围内的一致性，不等于所有应用数据都已持久化。

数据库、etcd 等系统需要自己的刷盘、一致性和恢复协议，不能把 `sync` 或文件系统 journal 当成应用事务保证。

## 7. 练习与答案

**问题：旧内核能启动，新内核不能，是否已经证明新内核存在上游 Bug？**

答案：没有。它只把范围缩小到两套启动项的差异，还可能是新 initramfs 缺模块、第三方驱动不兼容、签名失败或命令行不同。

**问题：机器启动失败时为什么不应首先重装系统？**

答案：重装会破坏现场，且无法解释根因。多数启动问题可定位到明确阶段并回退；只有在数据和证据已保护、恢复成本评估后才考虑重建。
