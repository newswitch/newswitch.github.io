# 固件、热插拔、电源管理与驱动故障：设备消失前后发生了什么

设备“能枚举但不能用”常出在驱动加载之后：固件缺失、复位失败、电源状态错误、PCIe 链路异常、异步请求尚未停止或热拔插 teardown 不完整。

## 1. 设备与固件

驱动可通过 firmware loader 请求二进制，由用户态从固件目录提供。文件存在不保证兼容；设备 revision、驱动版本、签名和压缩格式都可能影响加载。

```bash
dmesg -T | grep -Ei 'firmware|microcode|failed to load'
find /lib/firmware -maxdepth 2 -type f | head
```

## 2. 电源状态

系统 suspend/resume 与 runtime PM 不同。runtime PM 可在系统运行时让空闲设备进入低功耗；驱动必须保存/恢复状态，并正确处理请求与电源转换竞态。

```bash
cat /sys/bus/pci/devices/<BDF>/power/runtime_status
cat /sys/bus/pci/devices/<BDF>/power/control
```

把 `control` 改为 `on` 可作为受控诊断变量，但会增加功耗，也不能直接证明驱动 bug。

## 3. 热移除顺序

```text
标记设备不可再接收新请求
→ 注销用户入口/上层子系统
→ 停止队列和 DMA
→ 屏蔽并同步 IRQ
→ cancel/flush timer 与 work
→ 释放 DMA/MMIO/IRQ
→ 删除 device 对象和引用
```

顺序错误会出现 completion 访问已释放内存、DMA 写入重用页面或卸载卡死。

## 4. PCIe AER 与复位

AER 可报告 corrected、non-fatal、fatal 错误。大量 corrected 错误也可能预示链路质量、电源或插槽问题；fatal 错误可能触发 function/bus reset，驱动需实现错误恢复回调。

```bash
lspci -s <BDF> -vv
dmesg -T | grep -Ei 'AER|pcie.*error|reset|timeout'
```

## 5. 分层排查

1. 固件/总线是否发现设备，BDF/USB path 是否存在。
2. driver 是否绑定，probe 是否报错/defer。
3. MMIO、IRQ、DMA/IOMMU 资源是否成功。
4. 固件加载、设备 init/reset 是否完成。
5. 上层 net/block/char 接口是否注册。
6. 请求是否提交，completion 是否回来。
7. 是否出现 AER、IOMMU fault、温度/电源或硬件错误。

## 6. 练习与答案

**问题：重载驱动后设备恢复，能否证明根因是驱动？**

答案：不能。重载同时执行 reset、重新分配资源、清空队列并改变时序，也可能暂时绕过固件或硬件状态问题。

**问题：AER corrected 错误既然已纠正，是否可以永远忽略？**

答案：不应。单次可能无害，持续增长需要结合链路、插槽、温度、电源、线缆/背板和固件分析。
