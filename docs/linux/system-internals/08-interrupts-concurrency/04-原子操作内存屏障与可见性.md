# 原子操作、内存屏障与可见性：写入完成为什么不等于别人已经看见

多核并发中，“CPU0 先写数据再写 ready”只是源码顺序。编译器和 CPU 都可能在允许范围内重排，缓存一致性也不等同于所有访问按源码顺序被观察。

## 1. 四个概念不要混用

| 概念 | 含义 |
|---|---|
| 原子性 | 某个操作不会被观察为中间撕裂状态 |
| 可见性 | 另一个执行者何时能观察到写入 |
| 顺序性 | 两次访问被其他执行者观察的先后 |
| 互斥 | 同时只有一个执行者进入临界区 |

`atomic_inc()` 保护的是该增量操作，不会让与它相关的普通字段自动形成一致事务。

## 2. 发布—获取模式

```c
/* producer */
WRITE_ONCE(obj->value, 42);
smp_store_release(&obj->ready, 1);

/* consumer */
if (smp_load_acquire(&obj->ready))
        use(READ_ONCE(obj->value));
```

release 保证其前的访问不会越过发布点，acquire 保证其后的访问不会跑到获取点之前；二者通过同一同步变量配对。真实内核代码应优先使用已有锁、RCU、completion 等高级原语，而不是随意手写无锁算法。

### 2.1 配对必须真的读到相应发布

限定一次性初始化：ready 初值为 0，生产者写 value=42 后只发布一次 ready=1，此后不再修改 value。消费者 acquire 读到了该 release 写入的 1，才建立“初始化 → 发布 → 获取 → 使用”的跨 CPU 顺序；读到 0 时不能据此读取已初始化值。如果变量反复在 0/1 之间切换，读取 1 可能来自另一个周期，需要序号、锁或更完整的所有权协议。

删除 acquire 后，即使控制流先检查 ready 再读 value，控制依赖也不一般地为后续 Load 提供所需顺序；删除 release 后，观察到 ready=1 也不足以证明 value 初始化已发布。只在生产者加屏障、消费者没有匹配获取，也不是完整证明。[Linux Memory Barriers](https://docs.kernel.org/core-api/wrappers/memory-barriers.html)区分了方向性屏障、控制依赖与配对条件。此处是内核原语模型，不可将普通 C/C++ 数据竞争代码照搬成合法用户态程序。

### 2.2 Acquire 与 Release 不是任意位置的全屏障

考虑 Store Buffering 教学例子，x/y 初值为 0：

```c
/* CPU0 */                         /* CPU1 */
smp_store_release(&x, 1);           smp_store_release(&y, 1);
r0 = smp_load_acquire(&y);          r1 = smp_load_acquire(&x);
```

两边的 acquire 都可能读到初始 0，而不是对方的 release 写入，因此并未建立相应跨 CPU 同步链。不能仅看到代码里同时有 release/acquire 就宣布 `r0=r1=0` 被禁止。要禁止这类 Store→Load 结果，可在写与读之间使用适合该协议的全屏障，或改用正确锁协议；是否禁止应由目标内存模型的 Litmus Test 判断。

“原子 RMW 成功”也不自动给所有周边访问所需顺序。返回值、Relaxed/Acquire/Release 变体与成功/失败分支的顺序保证都应分别核对。先写出要禁止的观察结果，再选原语，比不断叠屏障更可靠。

## 3. `READ_ONCE` / `WRITE_ONCE`

它们约束编译器只进行一次该对象访问并避免部分优化，但不是完整 CPU 内存屏障，也不让复合操作变为原子。以下仍可能丢更新：

```c
WRITE_ONCE(counter, READ_ONCE(counter) + 1);
```

两个 CPU 可读到同一个旧值后分别写回。

## 4. 屏障类别

- `smp_mb()`：SMP 全屏障，约束前后读写。
- `smp_rmb()` / `smp_wmb()`：针对读或写顺序。
- acquire/release：围绕同步点提供方向性顺序，通常比全屏障更精确。
- DMA/MMIO 屏障：处理 CPU 与设备之间的可见性，不能简单用普通 SMP 屏障替代。

在单核或强内存序架构上“测试没出错”，不证明算法在 ARM、RISC-V 或不同编译优化下正确。

## 5. 锁已经携带顺序语义

正确配对的锁获取/释放提供临界区所需的内存顺序。给锁保护代码额外堆屏障通常说明模型没有理清，也可能掩盖真正的数据竞争。

## 6. 设备所有权转换

描述符交给 NIC 前，驱动必须确保 buffer 和 descriptor 内容对设备可见；收到 completion 后，也要按 DMA API 规则同步 CPU/设备视图。缓存一致 DMA、非一致架构和流式 DMA 的规则不同，应使用 DMA API，不能靠 `volatile`。

### 6.1 顺序不等于生命周期

release 发布对象后立即 free，即使消费者用 acquire 读取，也可能拿到已经失效的地址。屏障解决“观察顺序”，不会增加引用、不等待读者、不延长对象寿命；安全发布还要配合锁、RCU 或引用所有权。反过来，引用计数非零保证对象未释放，不代表内部多个字段是同一版本。完整生命周期见 [RCU 与引用计数](./06-RCU引用计数与对象生命周期.md)。

## 7. 练习与答案

**问题：`volatile` 能否替代锁或内存屏障？**

答案：不能。它主要约束编译器对该访问的优化，不提供跨 CPU 互斥，也不完整表达内存顺序。内核对并发和 MMIO 提供专门原语。

**问题：缓存一致协议存在，为什么还要屏障？**

答案：一致协议保证同一缓存行最终一致，不保证不同内存访问按源码顺序被其他 CPU 观察。
