# 中断、时间与内核并发导读

内核同时面对进程、硬件中断、软中断和多个 CPU。理解并发的关键不是背锁名称，而是先回答：代码在哪种上下文执行、能否睡眠、谁可能同时访问对象、对象何时才允许释放。

## 1. 执行上下文地图

```text
进程上下文
├─ 用户态
└─ 系统调用/缺页等内核路径：通常有 current，部分位置可睡眠

中断上下文
├─ hardirq：快速确认硬件并安排后续工作，不得睡眠
└─ softirq：延后批处理，不能使用会睡眠的锁

可调度异步工作
├─ workqueue：由内核线程执行，可以睡眠
├─ threaded IRQ：把适合的处理放在线程上下文
└─ timer/hrtimer：回调语义由接口决定，不能想当然地阻塞
```

“内核态”不是一种统一上下文。系统调用中的代码和 hardirq 都在内核态，但允许的同步手段完全不同。

## 2. 并发问题的四个维度

| 维度 | 要回答的问题 |
|---|---|
| 互斥 | 同一时刻是否只允许一个执行者修改对象 |
| 可见性 | 一个 CPU 的写入何时对另一个 CPU 可见 |
| 顺序 | 编译器和 CPU 是否允许把两个访问重排 |
| 生命周期 | 读者仍持有指针时，对象能否释放 |

锁常同时提供互斥和必要的顺序保证；原子变量只保证特定操作的原子性；RCU 主要解决读多写少对象的发布与延迟回收。三者不能互相机械替换。

## 4. 统一分析顺序

```text
确认现场上下文
→ 枚举共享对象与并发参与者
→ 明确睡眠/抢占/中断约束
→ 检查同步、发布与释放规则
→ 用 tracepoint、lockstat、perf 或 eBPF 取证
→ 用最小实验验证，而不是在线上随意切锁
```

## 5. 掌握标准

学完后，应能解释：为什么自旋锁内不能睡眠，为什么 `atomic_t` 不能让复合状态天然安全，为什么 RCU 删除后不能立刻 `kfree`，以及为什么“CPU 利用率不高”仍可能出现 IRQ 单核热点或锁等待长尾。
