# 内核抢占、临界区与执行上下文：当前代码能不能被换下

并发分析必须区分“当前 CPU 会不会被调度走”“同一 CPU 会不会进入中断”“其他 CPU 会不会同时访问”。禁止抢占只解决第一个问题，不能阻止其他 CPU。

## 1. 三种不同动作

| 动作 | 阻止什么 | 不阻止什么 |
|---|---|---|
| `preempt_disable()` | 当前任务被普通内核抢占 | 硬中断、其他 CPU |
| `local_irq_disable()` | 当前 CPU 的可屏蔽本地 IRQ | NMI、其他 CPU |
| spinlock | 其他持同一锁的执行者进入 | 不相关数据；普通版本未必关本地 IRQ |

若同一对象同时被进程上下文和本 CPU hardirq 使用，进程侧只拿普通 spinlock 可能死锁：进程持锁时被 IRQ 打断，IRQ 又等待同一锁。此时需要正确的 irqsave 变体或重新设计所有权。

## 2. 抢占模型

内核构建配置决定普通内核代码的抢占程度。常见模型从偏吞吐到偏低延迟不同；PREEMPT_RT 还会线程化更多中断并改变部分锁实现。分析线上行为必须读取运行内核配置，不能只依据发行版名称。

```bash
uname -r
grep -E 'CONFIG_PREEMPT(_NONE|_VOLUNTARY|_DYNAMIC|_RT)?=' /boot/config-"$(uname -r)"
cat /sys/kernel/debug/sched/preempt 2>/dev/null
```

## 3. `preempt_count` 的意义

架构和版本实现细节不同，但它用于跟踪禁止抢占、softirq、hardirq/NMI 等嵌套状态，帮助内核判断当前能否调度。内核警告“scheduling while atomic”通常表示在不可睡眠上下文调用了可能阻塞的路径。

## 4. `might_sleep` 与原子上下文错误

常见错误：

- 持 spinlock 时使用 `GFP_KERNEL` 分配并触发回收。
- hardirq/softirq 中获取 mutex 或等待 completion。
- 禁抢占区调用可能 schedule 的函数。
- 长时间关中断导致定时器、网络和调度延迟。

调试内核中的 `might_sleep()`、lockdep 和相关 debug 配置可尽早暴露问题，但会增加开销。

## 5. Per-CPU 数据的边界

Per-CPU 数据减少跨核竞争，但访问期间任务若迁移到另一 CPU，就可能读写错误副本。因此某些接口会暂时禁抢占或固定 CPU。Per-CPU 也不自动防止本 CPU 的 IRQ 与进程路径并发。

## 6. 延迟观测

```bash
perf sched record -- sleep 10
perf sched timehist
cat /proc/interrupts
cat /proc/softirqs
```

实时/低延迟场景还需区分 IRQ-off、preempt-off、调度等待和运行时间。只看上下文切换总数无法定位哪一段不可抢占区过长。

## 7. 练习与答案

**问题：禁用当前 CPU 的中断能否保护两个 CPU 共享的链表？**

答案：不能。另一个 CPU 仍可并发修改。需要跨 CPU 同步；若本地 IRQ 也访问它，还要同时满足本地中断约束。

**问题：可睡眠的进程上下文是否任何时候都能使用 mutex？**

答案：不是。若当前已持自旋锁、禁抢占或处于其他原子区，仍不能进入可能睡眠的路径。
