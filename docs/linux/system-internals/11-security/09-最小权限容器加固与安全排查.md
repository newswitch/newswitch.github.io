# 最小权限、容器加固与安全排查：把多层机制组合起来

最小权限不是让程序“勉强启动”，而是为正常功能建立明确权限模型，并让越权行为在可观察、可恢复的方式下失败。

## 1. 加固层次

```text
受信任镜像/软件包与及时补丁
→ 非 root 身份和只读程序目录
→ 清空 capability 后按需增加
→ no_new_privs + seccomp allowlist/default profile
→ SELinux/AppArmor 强制策略
→ 明确的只读/可写 mount、nosuid/nodev/noexec
→ 设备 allowlist 与 cgroup 资源边界
→ 网络出口/入口和凭据最小化
→ Audit、告警、备份与恢复演练
```

## 2. 技术验证矩阵

| 目标 | 验证证据 |
|---|---|
| 不是宿主 root | uid_map、credential、securityContext |
| 无多余 capability | `/proc/PID/status` 与运行时 spec |
| syscall 受限 | Seccomp 字段、profile 与拒绝测试 |
| 文件访问受限 | mountinfo、mode/ACL、LSM label/profile |
| 无危险宿主入口 | volume、device、host namespace、runtime socket |
| 资源不会拖垮节点 | cgroup 限制、PSI、OOM/节流测试 |

## 3. 拒绝事件排查

1. 记录精确操作、时间、PID/容器实例和 errno。
2. 比较应用预期与实际 credential/namespace/cgroup。
3. `namei/getfacl` 检查 DAC 与路径。
4. 解析 capability effective/bounding。
5. 查 AVC/AppArmor/seccomp/Audit。
6. 核对挂载只读、noexec、nosuid 和设备策略。
7. 用最小权限变更验证，随后回滚诊断性放宽。

## 4. 常见反模式

- 为解决一个 bind 失败直接 `privileged: true`。
- 关闭 SELinux/AppArmor 而不分析标签。
- 使用 `chmod -R 777` 掩盖 UID 映射和 volume owner 问题。
- 把宿主 runtime Socket 暴露给管理面容器。
- 永久采用 unconfined seccomp 解决新 syscall 兼容。

## 5. 可用性也属于安全

过严策略若阻断健康检查、日志或优雅退出，会诱发绕过和紧急放权。策略上线需要功能测试、故障测试、回滚和版本管理。

## 6. 练习与答案

**问题：容器只读 rootfs 后还需要 LSM 吗？**

答案：需要。只读只约束特定挂载写入，LSM 还能控制读取、执行、网络、ptrace、capability 等行为。

**问题：为什么不能根据一条拒绝日志直接 `audit2allow` 上线？**

答案：日志可能来自错误标签、异常输入或攻击；自动规则不知道业务意图，容易放大权限。必须先定位根因并人工验证最小范围。
