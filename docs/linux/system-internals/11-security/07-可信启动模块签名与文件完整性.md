# 可信启动、模块签名与文件完整性：代码在运行前如何建立信任

可信链回答“启动和执行的代码是否来自被信任来源、是否被篡改”。它不等于代码没有漏洞，也不替代运行时最小权限。

## 1. 启动信任链

```text
平台固件信任数据库
→ 验证 Bootloader/shim
→ 验证内核和可选 initramfs/UKI
→ 内核根据策略验证模块
→ 用户态完整性机制验证/度量文件
```

链中任一未覆盖内容都可能成为边界，例如未签名 initramfs、可修改 kernel command line 或可写启动分区。

## 2. 模块签名与 Lockdown

启用强制模块签名后，内核只加载受信任 key 签名模块。UEFI Secure Boot 启用时，发行版可能自动进入 lockdown，限制 `/dev/mem`、kexec、内核调试等会绕过信任链的接口。

```bash
mokutil --sb-state 2>/dev/null
cat /sys/kernel/security/lockdown 2>/dev/null
modinfo -F signer <module>
dmesg -T | grep -Ei 'lockdown|verification|signature'
```

## 3. IMA 与 EVM

- IMA measurement：把文件度量扩展到 TPM PCR/日志，支持远程证明。
- IMA appraisal：按签名/hash 决定是否允许访问/执行。
- EVM：保护安全相关扩展属性完整性。

策略决定哪些 hook、文件和操作被覆盖；“启用了 IMA”不等于所有文件都强制验证。

## 4. fs-verity 与 dm-verity

- fs-verity：按文件构建 Merkle tree，适合只读文件的按需验证。
- dm-verity：验证只读块设备映射，常用于不可变 rootfs。

它们检测底层内容与已知 root hash 不一致，不负责加密数据，也不能阻止合法签名的软件含漏洞。

## 5. 更新与恢复

可信启动必须包含 key 生命周期、撤销、应急恢复和双分区/回滚设计。只有“禁止未签名代码”而没有可操作的 key rotation，会在证书过期或模块更新时造成不可恢复停机。

## 6. 练习与答案

**问题：Secure Boot 开启后，root 是否仍可加载自编译模块？**

答案：取决于模块签名强制、受信任 key、shim/MOK 和 lockdown 策略；传统 root 权限并不自动绕过强制验证。

**问题：dm-verity 能否保护可写数据库卷不被篡改？**

答案：它面向只读映射；可写数据需要其他完整性、访问控制、加密和备份机制。
