# Linux 信号机制：生成、排队、屏蔽、递送与处理

信号是异步事件通知机制，不是可靠消息队列。`kill` 命令的本质是发送信号，并不必然终止进程；最终动作由信号类型、目标权限、屏蔽状态和处理方式共同决定。

## 1. 信号生命周期

```text
事件产生信号
→ 检查发送权限和目标
→ 标记 pending/加入队列
→ 等待目标线程可递送
→ 应用屏蔽规则和 disposition
→ 忽略、执行默认动作或进入 handler
→ handler 返回并恢复原执行流
```

信号可由硬件异常、内核事件、终端、定时器、其他进程或线程自身产生。

## 2. 标准信号与实时信号

标准信号在阻塞期间多次产生时通常可能合并成一个 pending 状态，不能用次数表达可靠事件数量。实时信号支持排队和附加值，编号与具体平台/线程库有关。

`SIGKILL` 和 `SIGSTOP` 不能被捕获、忽略或屏蔽，但目标处于不可中断内核等待时，SIGKILL 仍不能使其瞬间消失。

## 3. 进程信号与线程信号

- 信号处理动作通常在线程组范围共享。
- 信号掩码是每线程属性。
- 进程定向信号可以递送给任一符合条件的线程。
- `pthread_kill`、`tgkill` 等可以定向到具体线程。
- 同步硬件异常通常递送给触发异常的线程。

多线程服务常让工作线程屏蔽控制信号，由专门线程使用 `sigwait` 同步处理，减少异步 handler 的复杂性。

## 4. Handler 中为什么不能随便调用函数

信号可能在任意用户指令处打断程序。若 handler 调用正在被中断代码持锁的非异步信号安全函数，可能死锁或破坏状态。安全做法包括：

- handler 只设置 `sig_atomic_t` 标志。
- 写入 self-pipe/eventfd 唤醒主循环。
- 使用 `signalfd` 把信号整合进事件循环。
- 避免 malloc、printf 等非安全调用。

## 5. 系统调用与 EINTR

阻塞系统调用遇到可处理信号时，可能返回 `EINTR`，也可能在 `SA_RESTART` 等规则下自动重启。程序不能假设所有系统调用行为相同；超时逻辑还要避免重试后把总等待时间无限延长。

## 6. 服务优雅退出

典型流程：

```text
收到 SIGTERM
→ 停止接收新请求
→ 等待或取消在途请求
→ 刷新必要状态
→ 关闭连接和文件
→ 在截止时间前退出
→ 超时后监督器才发送 SIGKILL
```

Kubernetes 终止 Pod、systemd 停止 Unit 和容器 Runtime 都依赖类似语义。应用忽略 SIGTERM、优雅期小于实际排空时间或 PID 1 没有转发信号，都会造成强杀和数据风险。

## 7. 观察信号状态

```bash
grep -E '^(SigPnd|ShdPnd|SigBlk|SigIgn|SigCgt):' /proc/<PID>/status
kill -l
ps -o pid,ppid,stat,blocked,ignored,caught,cmd -p <PID>
```

这些位图通常以十六进制显示，需要按本机信号编号解码。它们是采样瞬间，不提供完整历史。

## 8. 练习与答案

**问题：连续发送十次 SIGUSR1，程序一定执行十次 handler 吗？**

答案：不一定。标准信号在尚未递送时可能合并。需要可靠计数应使用合适 IPC、队列或实时信号，并处理容量和丢失边界。

**问题：为什么先发 SIGTERM，再在超时后发 SIGKILL？**

答案：SIGTERM 给应用清理和保存状态的机会；SIGKILL 作为最终强制手段，应用无法处理，可能中断事务或留下恢复工作。
