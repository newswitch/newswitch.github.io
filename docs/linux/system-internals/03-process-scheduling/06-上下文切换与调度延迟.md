# 上下文切换与调度延迟：线程被唤醒后为什么还不能立即运行

请求数据已经到达、锁已经释放或定时器已经到期，只表示线程具备运行条件。它还要被放入某个 CPU 的运行队列，等待调度器选择，才真正获得 CPU。

## 1. 三种容易混淆的切换

| 变化 | 是否换任务 | 示例 |
|---|---:|---|
| 用户态进入内核态 | 不一定 | 系统调用、缺页异常 |
| 同一任务从内核态返回用户态 | 否 | 系统调用完成 |
| 任务上下文切换 | 是 | A 睡眠，CPU 改运行 B |

统计 `context-switches` 主要关注第三类。一次系统调用如果立即完成，不必发生任务切换。

## 2. 上下文切换保存什么

架构相关切换需要保存/恢复必要寄存器、栈指针、指令位置和线程状态，并切换内核任务相关数据。跨地址空间切换还涉及页表上下文；现代 CPU 可用 ASID/PCID 等机制减少 TLB 全失效，但不会消除缓存和预测器扰动。

成本包括：

- 内核执行调度和切换代码的直接 CPU 时间。
- 新任务工作集不在 CPU Cache 的间接成本。
- TLB、分支预测和 NUMA 局部性变化。
- 多核之间迁移导致的缓存一致性流量。

因此“每次切换固定多少微秒”没有通用答案。

## 3. 自愿与非自愿切换

- 自愿切换：任务主动等待 IO、锁、条件或睡眠。
- 非自愿切换：时间片、抢占或更高优先级任务使其被换出。

```bash
grep -E 'voluntary|nonvoluntary' /proc/<PID>/status
pidstat -w -t -p <PID> 1
```

高自愿切换可能是大量阻塞、锁竞争或正常事件驱动；高非自愿切换可能是 CPU 竞争、时间片或优先级影响。必须结合吞吐和延迟判断。

## 4. 唤醒到运行的路径

```text
事件完成
→ try_to_wake_up 类路径检查任务状态
→ 选择目标 CPU
→ 把任务入队
→ 必要时通知/抢占目标 CPU
→ 调度器选中任务
→ 上下文切换
→ 任务继续执行
```

调度延迟是“已经 runnable 到真正 running”的时间。CPU 总利用率只有 40% 时也可能延迟高：线程亲和性限制在一个繁忙核、cgroup 配额耗尽、实时任务抢占或虚拟机 steal 都可能造成局部排队。

## 5. 观察运行队列和延迟

```bash
vmstat -w 1
pidstat -w -t -p <PID> 1
cat /proc/pressure/cpu
perf sched record -- sleep 10
perf sched latency
```

示例 PSI：

```text
some avg10=12.50 avg60=4.21 avg300=1.02 total=9876543
full avg10=0.00 avg60=0.00 avg300=0.00 total=0
```

CPU PSI `some` 表示至少有任务因为缺 CPU 而等待的时间比例趋势；不要把 `avg10` 当 CPU 利用率。PSI 是否在容器内按 cgroup 展示取决于读取位置和内核支持。

## 6. 常见根因

- 线程数远大于有效 CPU，频繁争抢。
- 单一热点线程打满一个核，整机平均值仍低。
- CPU affinity/cpuset 使任务只能在少数核运行。
- cgroup `cpu.max` 配额周期内提前耗尽。
- 高优先级实时任务长期占用 CPU。
- IRQ/softirq 集中在业务核。
- 锁竞争让线程在运行和睡眠间高频切换。
- vCPU 被宿主机抢占，产生 steal time。

## 7. 练习与答案

**问题：上下文切换次数高是否一定要优化？**

答案：不一定。高并发事件驱动服务可以自然产生大量切换。只有它与 CPU 开销、Cache Miss、运行队列等待或业务延迟相关时，才构成可证明的瓶颈。

**问题：CPU 平均利用率 30%，为什么某线程仍有 50ms 调度延迟？**

答案：平均值掩盖单核、亲和性、cgroup 配额、实时任务和虚拟化争用。要检查该线程允许使用的 CPU、每 CPU 队列和 throttling。
