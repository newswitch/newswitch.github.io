# 用户态、内核态与系统调用：一次权限切换究竟发生了什么

系统调用不是普通函数调用，也不是必然的进程切换。它是 CPU 从受限的用户执行环境进入受保护的内核入口，在校验参数后代替进程完成特权操作。

## 1. 为什么需要两个权限域

如果应用可以任意修改页表、关闭中断或直接编程磁盘控制器，一个进程就能破坏其他进程甚至整个系统。CPU 因此提供特权级和内存访问控制。以 x86-64 为例，Linux 主要使用 Ring 3 运行用户代码、Ring 0 运行内核；ARM64 使用较低异常级运行应用、较高异常级运行内核。

权限切换主要改变：

- CPU 当前特权级。
- 可执行的特权指令范围。
- 可访问的虚拟地址范围。
- 指令指针跳转到受控入口。
- 从用户栈切到该线程的内核栈。

它不会自动换成另一个 PID，也不会把参数神秘地复制到“内核进程”。

## 2. 从库函数到系统调用

以下代码调用的是 glibc 包装函数：

```c
ssize_t n = read(fd, buf, sizeof(buf));
```

在 x86-64 上，包装函数按 ABI 把系统调用号和参数放入约定寄存器，执行 `syscall` 指令。内核入口保存必要现场、建立可安全执行的上下文，再分派到对应处理函数。

```text
read() 包装函数
  → 寄存器放入 __NR_read、fd、buf、count
  → syscall 指令
  → entry_SYSCALL_64
  → do_syscall_64
  → __x64_sys_read
  → ksys_read / vfs_read
  → 返回值或 -errno
  → 恢复用户现场并返回 Ring 3
```

不同 CPU 架构的入口指令、寄存器和汇编入口不同，但“受控进入—校验—分派—返回”的模型相同。

## 3. 为什么系统调用需要复制和校验

用户指针指向不受内核信任的地址。内核不能像访问自己的普通指针那样盲目解引用，通常使用 `copy_from_user()`、`copy_to_user()` 等接口，并处理地址无效、权限不足或复制过程中发生缺页的情况。

检查不仅包括地址：

- 文件描述符是否存在且允许相应操作。
- 长度相加是否溢出。
- 调用者 UID、Capability、Namespace 是否有权操作。
- 标志组合是否有效。
- 资源限制和 cgroup 是否允许继续。

`EFAULT` 常表示用户缓冲区地址不可访问；`EBADF` 表示文件描述符无效或模式不符；`EINTR` 表示操作被可处理信号打断。错误码描述失败边界，不等同于根因分析的全部结论。

## 4. 系统调用会产生哪些成本

固定成本包括入口/返回、寄存器保存、安全检查以及可能的地址空间隔离措施。真正的大成本通常来自后续工作：

- 阻塞等待磁盘或网络。
- Page Fault 和内存回收。
- 锁竞争。
- 数据复制和缓存失效。
- 调度、唤醒和上下文切换。

因此不能用“系统调用次数多”直接推出“系统调用入口是瓶颈”。需要测量每类调用的次数、耗时和阻塞原因。

## 5. vDSO 为什么不必每次进内核

某些只读、频繁调用可以借助内核映射到进程地址空间的 vDSO，在用户态读取内核维护的数据。例如部分架构上的 `clock_gettime()` 常可走 vDSO；如果条件不满足才回退到真正系统调用。

```bash
grep '\[vdso\]' /proc/self/maps
strace -c date >/dev/null
```

不要因为 `strace` 没显示某个库函数，就认定它没有执行；`strace` 观察系统调用，不观察所有用户态函数。

## 6. 阻塞、抢占和重启

系统调用执行中可能：

1. 立即完成并返回。
2. 等待条件，把当前任务置为睡眠状态并调用调度器。
3. 被更高优先级任务抢占。
4. 被信号打断，返回 `EINTR` 或由内核/运行库自动重启。

如果发生睡眠，唤醒后仍由相同逻辑任务继续系统调用，但可能运行在另一个 CPU 上。系统调用持续时间因此可能包含排队和睡眠时间，而不只是 CPU 执行时间。

## 7. 怎样观察

```bash
strace -ttT -e trace=openat,read,write,close -- cat /etc/hostname
perf stat -e task-clock,context-switches,cpu-migrations,page-faults -- cat /etc/hostname
```

示例片段：

```text
openat(AT_FDCWD, "/etc/hostname", O_RDONLY) = 3 <0.000021>
read(3, "node-a\n", 131072)                = 7 <0.000012>
read(3, "", 131072)                       = 0 <0.000006>
close(3)                                   = 0 <0.000008>
```

`read` 返回 7 表示读取 7 字节；返回 0 表示到达 EOF，不是失败。尖括号是 `strace -T` 观察到的墙钟耗时，包含跟踪开销，不能直接当成未跟踪程序的真实性能。

## 8. 源码入口

以 Linux 6.6、x86-64 为阅读基线：

| 层次 | 位置/符号 |
|---|---|
| 汇编入口 | `arch/x86/entry/entry_64.S: entry_SYSCALL_64` |
| 公共分派 | `arch/x86/entry/common.c: do_syscall_64` |
| 系统调用定义 | `fs/read_write.c: SYSCALL_DEFINE3(read, ...)` |
| 通用读取 | `ksys_read()`、`vfs_read()` |

源码函数会随版本重构，但系统调用 ABI 不能随意改变。阅读发行版源码时应使用其 SRPM 或调试源码，而不是假设与上游同版本标签完全相同。

## 9. 练习与答案

**问题：系统调用和上下文切换有什么区别？**

答案：系统调用是同一任务从用户态进入内核态；上下文切换是 CPU 从一个可调度任务切换到另一个任务。系统调用可能不触发上下文切换，也可能因为阻塞或抢占而触发一次或多次切换。

**问题：为什么 `clock_gettime()` 可能不出现在 strace 中？**

答案：运行库可能通过 vDSO 在用户态完成读取，没有执行真正的系统调用。
