# 深度性能与故障诊断命令导读

深度工具不是排障第一步。先用指标、日志和基础命令缩小对象与时间窗，再选择能证伪假设的最低开销工具；否则可能得到海量事件、改变时序，甚至把生产问题放大。

```mermaid
flowchart LR
  A["症状与 SLO"] --> B["基础资源/日志/拓扑"]
  B --> C["文件和 PID 归属"]
  C --> D["系统调用/动态库"]
  D --> E["CPU 计数器与采样"]
  E --> F["调度/锁/IO 时间线"]
  F --> G["ftrace/eBPF 动态观测"]
```

## 1. 工具选择地图

| 问题 | 首选工具 | 观察层 |
|---|---|---|
| 文件为何无法卸载/删除后仍占空间 | `lsof`、`fuser` | FD、VFS 与进程 |
| 进程卡在哪个内核接口 | `strace` | syscall、signal |
| 动态库调用与解析异常 | `ltrace`、`ldd/readelf` | PLT/library call |
| CPU 周期、指令、cache miss | `perf stat` | PMU 计数 |
| CPU 热点与调用栈 | `perf record/report/top` | 事件采样 |
| 调度延迟与迁移 | `perf sched` | sched tracepoint |
| 接近 strace 的低开销事件汇总 | `perf trace` | syscall/tracepoint |
| 内核事件可控录制与回放 | `trace-cmd` | ftrace ring buffer |
| 自定义动态聚合 | `bpftrace` | eBPF probe/map |
| 检查已加载 BPF 对象 | `bpftool` | prog/map/link/BTF |

## 2. 开销与权限

| 等级 | 例子 | 风险控制 |
|---|---|---|
| 低 | 短时 `lsof`、已有 BPF 对象查询 | 限 PID、路径和输出 |
| 中 | `perf stat`、低频 sampling、特定 tracepoint | 限 CPU/PID/频率/时长 |
| 高 | `strace -f` 高频 syscall、DWARF stack、通配 kprobe | 先在压测复现，生产短窗 |
| 很高 | 全系统高频事件、输出每个 event、硬件 watchpoint | 通常禁止直接上生产 |

还要检查 `perf_event_paranoid`、`kptr_restrict`、Yama、lockdown、BPF LSM 和容器 capability。不要为方便永久放宽全局安全参数。

## 3. 标准采证流程

1. 固定 PID/TID、cgroup、Namespace、二进制 build ID 和时间窗。
2. 写出假设以及“什么证据会推翻它”。
3. 估算事件率、样本大小、磁盘空间和性能影响。
4. 先 10～30 秒小范围采集，监控被测服务与工具自身开销。
5. 保存原始数据、命令、版本、内核、时钟和符号状态。
6. 用另一类证据交叉验证，停止探针并确认资源清理。

## 4. 符号与容器边界

调用栈质量取决于 debug symbol、frame pointer/DWARF、JIT 符号、内核 kallsyms 和 build ID。容器里路径与宿主不同：采样通常由宿主完成，但解析符号可能需要容器 rootfs、debuginfo 和相同二进制。PID Namespace 中的 PID 也要转换为宿主 PID。

## 5. 本批学习顺序

1. `lsof`、`fuser`：先解决对象归属。
2. `strace`、`ltrace`：理解用户态与内核边界。
3. `perf stat`：先计数，不急着看火焰图。
4. `perf record/report/top`：热点与调用栈。
5. `perf sched/trace`：调度和系统调用时间线。
6. `trace-cmd`：可回放的 ftrace 数据。
7. `bpftrace`、`bpftool`：动态聚合和对象治理。

## 6. 最终验收

能用最低成本回答“谁、在哪一层、等待什么、持续多久”；能解释观测偏差和缺失符号；能限定作用域、时长和输出；能在结束后证明 probe/link/perf 进程与临时文件已清理。
