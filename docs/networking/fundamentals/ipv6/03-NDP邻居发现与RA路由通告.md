# NDP 邻居发现与 RA 路由通告

IPv4 初学时经常把 ARP 理解为“查 IP 对应的 MAC”。IPv6 的 NDP（Neighbor Discovery，邻居发现）确实包含类似能力，但还负责发现路由器、判断邻居是否可达等工作。它不是把 ARP 报文换一个名字。

## 1. 先区分主机维护的几种状态

| 状态 | 回答的问题 | 常见来源 |
| --- | --- | --- |
| 本机地址 | 我可以使用哪些源地址 | SLAAC、DHCPv6、静态配置 |
| 默认路由器列表 | 不知道更具体路径时交给谁 | RA，也可能有静态路由 |
| 前缀列表 | 哪些目标被认为在本链路 | RA 的前缀信息等 |
| 邻居缓存 | 下一跳对应什么链路层地址，最近是否可达 | NS/NA、上层可达反馈等 |

有 IPv6 地址，不等于有默认路由；有默认路由，不等于下一跳 MAC 已解析成功。这是分析主机网络状态的关键分界。

## 2. 五类消息各管什么

NDP 基于 ICMPv6。核心消息和状态模型见 [RFC 4861](https://www.rfc-editor.org/rfc/rfc4861.html)。

| 消息 | 中文含义 | 主要用途 |
| --- | --- | --- |
| RS：Router Solicitation | 路由器请求 | 主机主动询问链路上有哪些路由器 |
| RA：Router Advertisement | 路由器通告 | 通告默认路由器能力、前缀及其他参数 |
| NS：Neighbor Solicitation | 邻居请求 | 解析邻居链路层地址、探测可达性，也用于 DAD |
| NA：Neighbor Advertisement | 邻居通告 | 回应或更新邻居信息 |
| Redirect | 重定向 | 路由器告知主机当前链路上更合适的下一跳 |

NS/NA 的含义取决于源地址、目标地址和标志，不能看到 NS 就一律认为“正在查询 MAC”。

## 3. 一次首次访问怎样发生

假设主机 H 已拥有可用链路本地地址，要访问远端服务器 S：

```text
H 发 RS                         → 尽快发现路由器
R 发 RA                         → H 学习默认路由和前缀等信息
H 完成可用业务地址配置          → 获得合适源地址
H 查路由：S 应经 R 到达         → 确定下一跳是 R
若缺少 R 的链路层地址，H 发 NS  → 解析的是 R，不是远端 S
R 发 NA                         → H 建立或更新邻居缓存
H 把目的为 S 的数据包交给 R     → 开始普通转发
```

RA 可以携带源链路层地址选项，因此实际首次访问可能已经有邻居信息，不必再单独执行一轮地址解析。协议能力不能被误解为每次访问固定出现同一套报文。

解析邻居地址时，NS 通常发往目标对应的 Solicited-Node Multicast（被请求节点组播）地址。其映射依赖目标地址低位，缩小接收范围，但不是密码学意义上的私密信道。

### 3.1 同一个 NS 中，IPv6 目的地址和 Target 不是一回事

以太网中，假设需要解析的**下一跳**是 `2001:db8:42:10::1234:5678`，本机还不知道它的 MAC：

```text
下一跳地址的低 24 位：                  34:56:78
对应被请求节点组播地址：                ff02::1:ff34:5678
对应以太网目的 MAC：                    33:33:ff:34:56:78
NS 的 Target Address：                  2001:db8:42:10::1234:5678
```

IPv6 目的组播地址决定“哪些节点接收这个询问”，NS 内部的 Target Address 决定“具体在询问谁”。低 24 位相同的多个地址可以共用一个被请求节点组；接收者仍要检查完整 Target，不能只凭组播 MAC 回答。地址映射分别见 [RFC 4291](https://www.rfc-editor.org/rfc/rfc4291.html) 和 [RFC 2464](https://www.rfc-editor.org/rfc/rfc2464.html)。

普通地址解析时，NS 使用合适的本机单播源地址，并携带必要的源链路层地址信息。目标通常单播回复 NA，提供自己的链路层地址。若真正要访问的是远端服务器，此处 Target 应是路由选出的网关，而不是把服务器地址直接套进以上公式。

### 3.2 各类发现报文为什么不能套同一种目的地址

| 场景 | 典型 IPv6 目的地址 | 目的 |
| --- | --- | --- |
| 主机发送 RS | `ff02::2`，本链路所有路由器 | 请求路由器尽快通告 |
| 路由器周期发送 RA | `ff02::1`，本链路所有节点 | 发布默认路由器与链路参数 |
| 收到 RS 后回复 RA | 按条件单播给请求者，或组播给所有节点 | 不保证与 RS 一一对应 |
| 首次解析下一跳 | 下一跳对应的被请求节点组播地址 | 尚不知道对方链路层位置 |
| NUD 已知邻居探测 | 被探测邻居的单播地址 | 验证已有交付路径是否仍成立 |

RA 必须以路由器的链路本地地址为源；NDP 要求接收的 IPv6 Hop Limit 为 255。这可以排除正常经过路由转发、已经递减 Hop Limit 的报文，却不能证明同链路设备可信。**Hop Limit=255 是范围校验，不是身份认证。**

## 4. RA 中最容易混淆的五项信息

| RA 信息 | 表达的内容 | 不能推出什么 |
| --- | --- | --- |
| Router Lifetime | 发送者作为默认路由器的有效时间 | 不能推出主机地址同时失效 |
| PIO 的 L 标志 | 此前缀可用于 on-link 判断 | 不等于允许自动生成地址 |
| PIO 的 A 标志 | 此前缀可用于自主地址配置 | 不等于该前缀一定被声明为 on-link |
| M 标志 | 指示可通过有状态 DHCPv6 获得地址 | 不会自动关闭 SLAAC |
| O 标志 | 指示可通过 DHCPv6 获得其他配置 | 不意味着 DNS 只能来自 DHCPv6 |

PIO 是 Prefix Information Option，前缀信息选项。A/L 是**每个前缀**的标志，M/O 属于 RA 中的配置提示，不能当成同一个全局模式开关。

特别注意：`L=0` 是“此次通告不作 on-link 声明”，不是“明确宣布这个前缀在链路外”，也不能直接删除此前学到的 on-link 状态。地址配置和 on-link 判断应独立理解，相关澄清见 [RFC 5942](https://www.rfc-editor.org/rfc/rfc5942.html)。

Router Lifetime 为零，也不表示整份 RA 都无效。设备仍可能通告前缀等信息，只是不再作为默认路由器候选。

## 5. DAD：地址生成后为什么还不能立即放心使用

DAD（Duplicate Address Detection，重复地址检测）检查候选地址是否已被当前链路上的其他节点使用。普通情况下，地址先处于 tentative（暂定）状态，通过检测后才可正常用于业务。

检测使用 NS，源地址可以是未指定地址 `::`。它是在问“这个候选地址是否已被占用”，不是宣布“我已经拥有这个地址”。

DAD 属于地址自动配置机制的一部分，见 [RFC 4862](https://www.rfc-editor.org/rfc/rfc4862.html)。它的保证有边界：链路被隔离、报文被错误过滤、检测期间没有收到对端响应，都可能导致未发现冲突。它不是整个组织的 IPAM，也不是跨路由网络的全局查重。

### 5.1 DAD 与普通解析的报文区别

| 字段／行为 | 普通地址解析 | 普通 DAD |
| --- | --- | --- |
| NS 源地址 | 已有的合适单播地址 | `::`，不能假装已拥有候选地址 |
| NS Target | 待解析的下一跳 | 本机准备使用的候选地址 |
| NS 目的地址 | Target 对应的被请求节点组 | 候选地址对应的被请求节点组 |
| 源链路层地址选项 | 组播地址解析需要携带 | 不携带 |
| 收到相应冲突信息后 | 更新／验证邻居 | 判定候选地址不能正常启用 |

已拥有地址的节点回复 DAD 请求时，NA 发往所有节点组，Solicited 标志为 0；两个节点同时尝试同一地址时，也可能通过对方的 DAD NS 发现冲突，不是必须等待一份 NA。

链路存在报文回环时，主机还要区分“自己发出的探测被送回来”与“另一个节点也在声明地址”。[RFC 7527](https://www.rfc-editor.org/rfc/rfc7527.html) 的增强 DAD 使用 Nonce 辅助区分；这不是跳过查重，也不是全局地址注册。

## 6. NUD：知道 MAC，不代表邻居现在还活着

NUD（Neighbor Unreachability Detection，邻居不可达检测）维护的是下一跳近期可达性。可将常见状态理解为：

```text
尚未解析 → INCOMPLETE → 获得有效响应 → REACHABLE
                                      ↓ 时间经过
                                    STALE
                                      ↓ 再次发送数据
                                    DELAY
                                      ↓ 尚无可达确认
                                    PROBE
```

STALE 表示“近期没有足够新鲜的确认”，通常仍可使用已有链路层地址发送，不等于连接已经断开。后续可通过上层反馈或主动探测重新确认可达性；探测失败才进一步触发失败处理。

NUD 证明的是**邻居这一跳**。网关可以正常回答 NA，但它上游的互联网出口已经中断。因此网关可达不能证明远端业务可达。

### 6.1 STALE 为什么仍然允许先发数据

缓存里已有 MAC，只是确认不够新鲜。如果每次过期都先停下业务、重新组播解析，就会给正常通信制造额外往返和发现负载。因此 NUD 将“可以尝试交付”与“已经得到近期确认”分开：

| 当前状态／事件 | 典型处理 | 对业务的意义 |
| --- | --- | --- |
| 没有 MAC，进入 INCOMPLETE | 发送组播 NS，并在有限范围内暂存待发包 | 不会无限缓存或无限重试 |
| INCOMPLETE 收到有效、带所需地址信息的 Solicited NA | 学到 MAC，进入 REACHABLE，发送暂存包 | 这一轮解析完成 |
| REACHABLE 的确认有效时间过去 | 进入 STALE | 不据此判定断链 |
| 需要使用 STALE 表项发送 | 先用已有 MAC 发送，转入 DELAY | 给上层确认留出机会 |
| DELAY 期间没有足够确认 | 转入 PROBE，单播 NS 探测 | 验证现有单播交付路径 |
| 探测达到失败条件 | 执行邻居失败处理，必要时重选下一跳 | 具体缓存显示名称取决于系统 |

上层确认必须能说明此前发送的包确实推进了通信。例如 TCP 新确认的数据可以提供依据；仅仅“收到对方任意一个包”并不能证明本机到对方的方向正常。UDP 没有 TCP 那样的通用确认语义，不能假定每个 UDP 响应都被协议栈用来刷新 NUD。

### 6.2 NA 的 R、S、O 标志不是三种地址类型

- **R（Router）**：描述目标是否为路由器，影响已有邻居的路由器属性；不代替 RA 的默认路由器生存期。
- **S（Solicited）**：是否为相应请求的响应，参与可达确认。非请求式通告并不自动证明双向路径。
- **O（Override）**：是否允许按规则覆盖已有链路层地址；仍要结合表项当前状态，而不是“为 1 就绕过全部校验”。

例如，已有 REACHABLE 表项记录 MAC-A，却收到 O=0、携带 MAC-B 的 NA，基础规则不会立即把 MAC-A 覆盖成 MAC-B，而会将可达状态转为 STALE。反过来，INCOMPLETE 阶段根本没有可用 MAC，其处理与覆盖一个已完成表项不同。不要把所有 NA 都解读成无条件的“最后到达者获胜”。

### 6.3 多个网关不是按 RA 到达先后永久选一个

主机可以同时维护多个默认路由器。更具体路由、路由器偏好以及邻居可达性都会参与选择；RA 还可以通过 Route Information Option 发布特定前缀的路由，见 [RFC 4191](https://www.rfc-editor.org/rfc/rfc4191.html)。

一次切换可能经过“原邻居探测失败 → 选择其他候选 → 确认新下一跳 → 更新目的缓存”等过程。两台路由器都持续发 RA，不等于它们共享会话状态，也不等于主机必然按包均匀负载。

Redirect 则是另一种优化：当前第一跳路由器告诉主机，某个目的可以经同链路上的更合适下一跳到达。主机需要验证消息来自当前正确的第一跳等条件；它不是任意节点可以发送的全网路由公告。

## 7. 为什么不能把 ICMPv6 全部屏蔽

全丢 ICMPv6 会同时破坏多项基础能力，而不仅是禁止别人 ping：路由器发现、邻居解析以及路径 MTU 反馈都可能受影响。

另一方面，允许 NDP 也不等于无需安全边界。恶意或错误 RA 可能改变主机默认路由；NDP 的 Hop Limit 检查可以限制非本链路注入，却不能认证同一链路上的发送者。RA Guard、接入控制和协议消息过滤需要按角色设计，不能用一个“全允许”或“全拒绝”代替。[RFC 4890](https://www.rfc-editor.org/rfc/rfc4890.html) 给出了 ICMPv6 过滤的协议层考量。

RA Guard、DHCPv6 Shield 与地址绑定分别保护什么，见 [IPv6 接入保护与二层地址绑定](../../security/layer2-security/01-地址绑定DHCP-Snooping-DAI与IPv6接入保护.md)。

## 8. 思考与解答

**拿到 DHCPv6 地址，但没有默认路由，是否矛盾？**

不矛盾。地址租约和默认路由来源不同；一般主机的默认路由来自 RA，或者由其他管理方式配置。

**邻居缓存里网关为 STALE，要不要立即认定网络故障？**

不要。先理解它只是可达信息不够新鲜，不是失败状态。还需要结合实际发送、探测和业务结果。

**网关 RA 消失后，地址会和默认路由同时到期吗？**

不一定。默认路由器、前缀和地址有不同的生命周期。可能出现地址仍在、默认路由已经失效的状态。

**收到一个 NS，怎样判断是在查 MAC 还是在做 DAD？**

结合源地址、Target 和选项判断。普通 DAD 使用 `::` 源地址，Target 是候选地址，并且不带源链路层地址选项；不能只看目的为组播就认定用途。

**为什么两个 IPv6 地址会收到同一份组播 NS，却只有一个应该回应？**

被请求节点组只按低 24 位映射，可能发生重合。NS 内部仍携带完整 Target，节点要检查自己是否负责这个地址。

**网关回答了单播 NA，能证明它的外网出口正常吗？**

不能。NUD 只验证当前邻居方向，外网路由、上游策略和远端服务都在另一个判断范围。

**一个非请求式 NA 带来新 MAC，为什么表项未必变成 REACHABLE？**

地址映射更新和双向可达确认不同。未经本机请求的通告可以提供位置变化信息，却不一定证明本机发出的包能到达对端，因此要结合标志与原状态处理。
