# SLAAC 与 DHCPv6 地址分配机制

一台主机能正常上网，至少需要可用源地址、合适路由、下一跳可达和名称解析等条件。IPv6 故意把这些信息分散在不同机制中管理，不能用“DHCP 成功了”概括全部接入状态。

## 1. 先分清谁提供什么

| 信息 | SLAAC／RA 路径 | DHCPv6 路径 |
| --- | --- | --- |
| 业务地址 | 主机根据 RA 前缀自行生成 | 服务器给出地址租约 |
| 默认路由 | 通常来自 RA | 基础 DHCPv6 协议不承担这一职责 |
| DNS 服务器与搜索域 | RA 可携带 RDNSS、DNSSL | 可通过相应选项提供 |
| 地址租约数据库 | 路由器不为 SLAAC 主机逐个分配租约 | 服务器维护分配状态 |
| 下游网络前缀 | 不靠给主机生成一个地址来完成 | IA_PD 可用于前缀委派 |

SLAAC 和 DHCPv6 可以共存，并不是二选一。RA 的 A/M/O 标志、客户端支持情况和管理员策略一起决定实际行为。

本文以已发布的 [RFC 9915](https://www.rfc-editor.org/rfc/rfc9915.html) 作为 DHCPv6 协议参考；它于 2026 年取代 RFC 8415。旧系统文档仍可能引用 RFC 8415，产品支持项不能仅凭标准版本推断。

## 2. SLAAC 的无状态到底指什么

SLAAC 是 Stateless Address Autoconfiguration，无状态地址自动配置。以普通以太网 `/64` 为例：

```text
路由器通告：2001:db8:42:10::/64，可用于自主地址配置
主机生成：  本接口的 64 位接口标识
两部分结合：得到候选地址
完成 DAD：  地址成为可用地址
```

“无状态”指路由器不必像 DHCP 服务器那样，为每个 SLAAC 地址保存“租给谁、租到何时”的分配记录。主机仍有地址状态、有效期、邻居缓存，网络也仍有各种控制状态。

接口标识不必由 MAC 地址直接生成。稳定且不暴露 MAC 的生成方式见 [RFC 7217](https://www.rfc-editor.org/rfc/rfc7217.html)；临时地址可周期性替换，机制见 [RFC 8981](https://www.rfc-editor.org/rfc/rfc8981.html)。稳定地址适合被其他节点持续访问，临时地址主要减少作为客户端时的长期地址关联，两者可以同时存在。

## 3. 地址有两个重要的倒计时

| 生命周期 | 含义 | 到期后的效果 |
| --- | --- | --- |
| Preferred Lifetime（首选生存期） | 地址适合优先用于新通信的时间 | 地址进入 deprecated，不再作为新通信的优先选择 |
| Valid Lifetime（有效生存期） | 地址仍有效的时间 | 到期后不能继续作为有效地址使用 |

假设一个地址的首选生存期还剩 30 分钟，有效生存期还剩 2 小时。30 分钟后它并不是立刻从接口消失：已有连接有机会继续使用它，新连接则尽量选择其他首选地址。

这个设计给地址重编号提供了过渡空间。但过渡能否成功还取决于旧前缀的路由是否继续存在，以及应用连接能否在有效期内结束。仅让地址保留，并不能保证上游仍接受旧源地址。

RA 可以刷新相关计时，协议还包含防止异常通告骤然破坏地址有效性的保护规则。因此不要把收到一份 RA 机械理解成“无条件覆盖所有本机计时器”。

### 3.1 地址、on-link 前缀、默认路由各有自己的计时器

假设一份 RA 通告默认路由器有效 30 分钟，PIO 通告前缀的 Valid Lifetime 为 4 小时、Preferred Lifetime 为 1 小时，并设置 A=1、L=1。主机由此创建地址，并分别管理默认路由器、on-link 前缀与地址的状态：

| 未再刷新时的时间点 | 默认路由器 | SLAAC 地址 |
| --- | --- | --- |
| 10 分钟 | 仍在有效期内 | 仍为 preferred |
| 30 分钟后 | 该默认候选到期 | 地址仍可用，但不保证有其他外网路径 |
| 1 小时后 | 不会由地址剩余寿命自动恢复 | 地址 deprecated，新通信尽量不用它 |
| 4 小时后 | 与此时刻无必然联系 | 地址 valid 到期，不能继续有效使用 |

这里是假设没有其他 RA、静态路由或候选网关的计时示例，不是推荐的生产参数。PIO 的同一个 Valid Lifetime 可以分别用于 on-link 前缀和 SLAAC 地址处理，但它们**不是一个共享状态对象**，接收规则也不完全相同。

### 3.2 “两小时规则”保护的是已有 SLAAC 地址

按 [RFC 4862 第 5.5.3 节](https://www.rfc-editor.org/rfc/rfc4862.html#section-5.5.3)，基础 SLAAC 对缩短已有地址有效期有保护规则。以未经过相应认证的 RA 为例，设地址剩余有效期为 R，新通告有效期为 V：

1. 若 V 大于两小时，或 V 大于 R，可把地址有效期设置为 V。
2. 否则，若 R 已不超过两小时，忽略此次对**地址有效期**的缩短，原倒计时继续走。
3. 否则，将地址剩余有效期缩为两小时，而不是立即失效。

例如 R=4 小时、V=0，已有地址的有效期会按上述基础规则缩为两小时；若同时通告 Preferred Lifetime=0，地址仍可以立即转为 deprecated。**不优先用于新连接**与**彻底无效**是两种结果。

此规则不是要求所有 IPv6 状态至少保留两小时：它不直接保护 Router Lifetime，不适用于 DHCPv6 租约，也不能原样套到 on-link 前缀删除。经过协议认可的认证通告有相应例外；具体系统还可能实现后续更新，不能将这个示例当作任意终端的强制计时配置。

## 4. DHCPv6 怎样表示一台客户端的资源

DHCPv6 的身份和资源模型不是简单复制 DHCPv4：

- **DUID**：DHCP Unique Identifier，标识客户端或服务器，不能一概当成 MAC 地址。
- **IAID**：客户端为一个 Identity Association（身份关联）选择的标识。
- **IA_NA**：管理非临时地址，表达的是地址租约。
- **IA_PD**：管理委派前缀，表达的是一段下游可以使用的网络空间。

克隆操作系统镜像时，如果连持久化 DUID 也一起复制，可能导致服务器无法正确区分实例。更换网卡也不一定意味着 DUID 必须变化。地址身份应按客户端实现理解，而不是只看网卡标签。

一次常见的新分配过程是：

```text
Solicit   → 寻找提供服务的服务器
Advertise → 服务器提供候选资源与能力
Request   → 客户端选择并请求资源
Reply     → 服务器返回分配结果
```

双方支持且允许 Rapid Commit 时可以采用两消息路径，不能把四消息当成唯一合法形态。DHCPv6 使用 IPv6 组播和中继机制，不需要 IPv4 广播。

### 4.1 报文中的身份、事务和资源不能混用

| 对象 | 区分什么 | 不等于什么 |
| --- | --- | --- |
| Client／Server Identifier 中的 DUID | 哪个客户端、哪个服务器 | 不一定是当前网卡 MAC |
| Transaction ID | 一次报文交换的匹配 | 不是长期租约身份 |
| IA 类型与 IAID | 某个客户端请求的资源集合 | IA_NA 和 IA_PD 不能混成同一类资源 |
| IA Address／IA Prefix | 具体地址或前缀及其生存期 | 不是默认网关选项 |
| Status Code | 这次操作或某个资源的结果 | 收到 Reply 不等于里面所有资源都成功 |

同一个 Reply 可以包含多个 IA。客户端要检查实际返回的资源与状态，不能只根据“服务器回包了”判断拿到地址，更不能把 DUID 当作用户已经通过安全认证的证明。

### 4.2 中继怎样让服务器知道客户在哪个链路

本链路客户端通常向 `ff02::1:2` 发送服务发现消息，客户端监听 UDP 546，服务器和中继监听 UDP 547。远端服务器不直接接收普通跨路由转发的这份链路范围组播，而由中继承接：

```text
客户端 DHCPv6 消息
  → 中继包装为 Relay-forward
      link-address：帮助识别客户端所在链路
      peer-address：记录收到消息时的客户端／下级中继地址
      Interface-ID 等选项：表达中继侧接口上下文
      Relay Message：携带原消息
  → 服务器按链路与策略选择资源
  → Relay-reply 沿中继关系返回
  → 中继把内部回复交付客户端
```

`link-address` 可以在特定条件下为零，服务器还需结合 Interface-ID 等信息；不能假设它永远是一个“地址池网关”。多级中继还可以嵌套封装，因此既要看服务器返回资源，也要看回复能否回到正确接入链路。

## 5. 租约如何保持，为什么不必每次重新发现

客户端在资源仍有效时根据 T1 发起 Renew，尝试向原服务器续约；必要时在 T2 进入 Rebind，寻求其他可处理该绑定的服务器。地址和前缀还各有首选与有效生存期。

这些时间不同于 RA 的 Router Lifetime。可能出现下面这种看似奇怪、实际上完全合理的组合：

```text
DHCPv6 地址租约仍有效
RA 学到的默认路由器已经过期
结果：地址还在，但外网通信失败
```

同样，DHCPv6 服务短暂不可达也不意味着所有已租地址立即失效。真正的业务窗口取决于剩余生存期、客户端重试、地址是否还能路由，以及网络是否发生了其他变化。

### 5.1 用时间线区分 Renew、Rebind 与资源过期

假设某次成功分配的一个 IA 中，T1=30 分钟、T2=48 分钟，其中地址的 Preferred Lifetime=60 分钟、Valid Lifetime=90 分钟。没有成功续约时：

```text
0 分钟     已获得地址
30 分钟    Renew：尝试与原服务器更新绑定
48 分钟    Rebind：不再只限定原服务器，寻找可处理绑定的服务器
60 分钟    该地址不再 preferred
90 分钟    该地址失效，不可继续使用
```

这些是便于演算的值，不是所有客户端固定采用的比例。T1/T2 属于 IA 的续约控制，具体地址／前缀有自己的生命周期；成功回复还可能刷新它们。

Rebind 不会让任意新服务器凭空知道旧服务器的所有绑定。它仍需满足服务器策略、可用资源和一致性条件。也不能认为 T2 一到就必须丢掉仍在有效期内的地址。

只需要 DNS 等其他配置时，客户端可以使用 Information-request 路径，不必先申请 IA_NA 地址。地址已通过 SLAAC 获得、DNS 来自 DHCPv6，是合法的组合。

## 6. 前缀委派和给网卡分地址有什么区别

设家庭或分支路由器收到 IA_PD 委派 `2001:db8:1200:3400::/56`。它可以从中为下游网络选择 `/64`：

```text
上游 DHCPv6：委派一个 /56 给分支路由器
  ├─ 办公网：2001:db8:1200:3401::/64
  └─ 访客网：2001:db8:1200:3402::/64
```

分支路由器在下游通告这些前缀，终端再按 SLAAC 等机制形成自己的地址。IA_PD 不是把整个 `/56` 当成分支 WAN 网卡的普通主机地址；上游还需要正确把委派前缀路由到该路由器。

“获得前缀”与“前缀已有可用返回路由”依然需要分别理解。

### 6.1 前缀重编号是一条跨设备的生命周期链

上游改变委派前缀后，分支要更新下游 RA，终端才能逐步获得新地址。旧前缀最好有适当的撤销／弃用过程，但下游通告的寿命不能脱离上游实际授权和可路由窗口。

如果终端还保留旧地址，上游却已撤销返回路由，已有 TCP 会话仍会失败。因此完整关系是：**委派有效期 → 下游通告与地址生命周期 → 源地址选择 → 上游去回程路由**，不是收到一个新 `/56` 就完成了所有迁移。

IA_PD 委派也不要求分支 WAN 一定先获得一个全球单播 IA_NA 地址；具体接入可以用链路本地下一跳和其他机制建立上游交付。WAN 接口地址、委派空间、默认路由仍应独立判断。

## 7. DNS 信息为什么有多个来源

RA 的 RDNSS 用于递归 DNS 服务器地址，DNSSL 用于搜索列表，见 [RFC 8106](https://www.rfc-editor.org/rfc/rfc8106.html)。DHCPv6 也可提供 DNS 信息，双栈客户端还可能使用 DHCPv4 下发的解析器。

这不是冲突本身，关键在于操作系统如何合并、排序、按接口或按域选择解析器。不能因为 RA 提供了一个 DNS，就推断应用一定向它查询；VPN、浏览器专用解析器和本地缓存都可能改变实际路径。

## 8. 思考与解答

**RA 设置 M=1，主机就不会有 SLAAC 地址了吗？**

不会自动禁用。SLAAC 还要看对应前缀的 A 标志和客户端策略。两个来源的地址可以同时存在。

**SLAAC 没有租约数据库，是否无法追踪地址属于谁？**

仍可以结合接入认证、邻居信息、交换机端口和终端记录建立映射，但不能把它等同于查询 DHCP 地址租约表。临时地址轮换也需要纳入记录模型。

**给路由器发一个 IA_NA 地址，就足以让它的多个下游网段获得前缀吗？**

不够。一个接口地址和一段可继续划分的委派前缀不是同一资源，后者需要 IA_PD 或其他前缀分配与路由机制。

**收到 Valid Lifetime=0 的 PIO，为什么已有 SLAAC 地址未必立即消失？**

已有地址的有效期缩短受 SLAAC 接收规则约束，未认证通告可能触发两小时保护；但首选生存期、on-link 状态和默认路由要分别处理，不能都套用这一规则。

**客户端收到了 Reply，但没有业务地址，协议是不是出错了？**

不一定。它可能只请求其他配置，也可能某个 IA 返回失败状态。应看请求类型、IA 和状态码，而不是只看消息名。

**T1 到期、原 DHCPv6 服务器暂时不可达，当前连接一定立即断吗？**

不一定。T1 触发续约，不是地址失效；在有效期内且路由、策略仍成立时，已有地址可以继续使用。

**为什么跨子网的 DHCPv6 请求需要中继上下文？**

链路范围的发现组播不会被当作普通单播转发到远端服务器；服务器还需要知道客户端所在链路，才能选择资源并正确返回回复。
