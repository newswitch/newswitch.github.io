# IPv4 与 IPv6 双栈通信机制

双栈的含义是同时具备 IPv4 和 IPv6 能力，而不是“一个包一半走 IPv4、一半走 IPv6”。一次普通 TCP 连接最终使用确定的一组端点；系统只是多了一组可选择的通信路径。

## 1. 把双栈拆成四个独立条件

| 层面 | 需要具备的能力 |
| --- | --- |
| 名称解析 | 正确提供所需的 A、AAAA 等记录 |
| 客户端 | 有相应地址、路由、协议栈与地址选择能力 |
| 网络 | 相应地址族的转发、MTU、策略和返回路径可用 |
| 服务端 | 正确监听、入口转发、TLS 与后端能力可用 |

仅有 AAAA 记录，不代表 IPv6 业务能用；仅有节点 IPv6 地址，也不代表容器、Service、负载均衡和业务都支持 IPv6。

## 2. 一次域名访问发生了什么

以文档示例服务为例：

```text
api.example.com
  A    → 203.0.113.80
  AAAA → 2001:db8:42:20::80
```

应用获得候选地址后，结合系统地址选择规则和自身实现决定尝试顺序。每个候选路径都要匹配可用源地址、出口与路由。

```text
应用查询域名
  ├─ IPv6 候选：选择 IPv6 源地址 → IPv6 路由 → IPv6 服务入口
  └─ IPv4 候选：选择 IPv4 源地址 → IPv4 路由 → IPv4 服务入口
最终使用成功建立的连接
```

地址排序规则与应用的并发连接策略是两个不同层次。默认地址选择的协议框架见 [RFC 6724](https://www.rfc-editor.org/rfc/rfc6724.html)。

## 3. Happy Eyeballs 为什么能改善体验

如果客户端总是等一条坏路径完全超时才尝试另一条，用户就会为“有一个不可用候选地址”付出几秒甚至更长的等待。

Happy Eyeballs 的思路是有节制地交错尝试不同候选，避免被一个不通的地址族长时间阻塞。它会考虑 DNS 响应、候选排序和连接尝试节奏，而不是无条件同时向所有地址发送业务请求。

[RFC 8305](https://www.rfc-editor.org/rfc/rfc8305.html) 给出版本 2 的机制，并给出 250 毫秒等建议参数；这不是所有浏览器和客户端都必须采用的固定实际延迟。系统、库和应用版本可能采用不同策略。

它能改善用户体验，却可能掩盖一条路径持续故障：用户通过 IPv4 成功访问，不代表发布的 IPv6 入口健康。连接成功率与各地址族的独立健康状态应分别理解。

## 4. DNS 查询用 IPv4，不妨碍得到 IPv6 地址

DNS 的传输地址族与记录类型是两件事：

- 向一个 IPv4 地址的解析器查询 AAAA，完全合理。
- 向一个 IPv6 地址的解析器查询 A，也完全合理。
- DNS 返回 AAAA，并不意味着后续 TCP 数据由解析器代转。

DNS 负责返回名称对应的数据，业务连接通常由客户端直接建立。还要区分系统解析器、应用缓存、浏览器专用解析器以及 VPN 的分域解析策略。

## 5. 服务端的“监听所有地址”有条件

IPv4 的 `0.0.0.0` 与 IPv6 的 `::` 属于不同地址族。某些操作系统允许一个 IPv6 Socket 同时接收 IPv4 映射连接，另一些应用或设置要求分开监听。

因此，看到 `::` 监听不能不加判断地认定 IPv4 一定可达；看到 IPv4 监听也不能认定 IPv6 自动可达。还要考虑 Socket 的 IPv6-only 行为、应用绑定方式、代理入口和容器端口映射。

类似地，IPv4 的 NAT、防火墙规则不一定自动覆盖 IPv6。双栈意味着需要覆盖两套实际数据路径，而不是再分一个地址就结束。

## 6. 双栈与 NAT64／DNS64 的区别

| 机制 | 客户端看到什么 | 网络做什么 |
| --- | --- | --- |
| 原生双栈 | 可选 IPv4 或 IPv6 地址 | 各自按对应地址族转发 |
| DNS64 | 特定条件下获得由 A 记录合成的 AAAA | 修改或合成名称解析结果，不转发业务数据 |
| NAT64 | IPv6 客户端访问表示 IPv4 目标的 IPv6 地址 | 在转换边界进行地址／协议转换并维护所需状态 |

DNS64 与 NAT64 常配合，使 IPv6-only 客户端访问 IPv4 服务。DNS64 的合成逻辑见 [RFC 6147](https://www.rfc-editor.org/rfc/rfc6147.html)，有状态 NAT64 的交互模型见 [RFC 6146](https://www.rfc-editor.org/rfc/rfc6146.html)。

但应用若把 IPv4 字面量硬编码进业务，单靠 DNS64 就没有机会通过查询来合成 AAAA；还可能需要其他转换机制。DNSSEC 校验、协议中嵌入地址、入站连接需求等，也会影响适用范围。

原生双栈并不要求 NAT64，IPv6 也不要求 DNS64。它们是解决不同网络边界的工具。

## 7. 为什么上线 AAAA 可能改变已有系统的表现

假设 IPv4 入口有 WAF、证书和健康后端，IPv6 地址却直接指向了另一套未完成配置的入口。发布 AAAA 后，部分客户端会开始访问新的路径，于是出现“同一域名，只有部分用户报错”。

这里的变化可能是：

- 走了不同机房、运营商或负载均衡入口。
- IPv6 入口缺少安全策略或证书绑定。
- IPv6 返回路径与 MTU 不完整。
- 客户端回退策略不同，导致有的快、有的慢、有的直接失败。

DNS 修改不会把已有 TCP 连接自动搬到新地址。连接池和长连接仍可能使用原端点，因此观察到的切换过程不会只由 TTL 一个数值决定。

## 8. 思考与解答

**域名同时有 A、AAAA，客户端是否必然先用 IPv6？**

不必然。要看地址可用性、系统排序和应用连接策略。不能只凭 DNS 记录存在判断实际流量。

**浏览器打开页面正常，能证明 IPv6 入口正常吗？**

不能。浏览器可能快速回退到 IPv4。需要区分成功连接采用的地址族与每条候选路径是否健康。

**NAT64 是不是让 IPv4 客户端天然能访问所有 IPv6-only 服务？**

不是。这里讨论的常见有状态 NAT64 模型主要解决 IPv6 客户端访问 IPv4 服务器；反向发起连接涉及其他映射和入口设计，不能倒推。
