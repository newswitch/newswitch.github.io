# IPv6 路由、ICMPv6 与路径 MTU

如果主机有 IPv6 地址、默认路由也在，是否一定可以传输一个大文件？不一定。地址、路由、邻居和报文尺寸分别解决不同问题，任何一项不满足都可能中断传输。

## 1. 先确定往哪走，再确定怎么交给下一跳

假设主机的转发表有如下信息，这是逻辑示例，不是配置命令：

```text
2001:db8:42:10::/64  → 本链路
2001:db8:42:20::/64  → 路由器 R2
::/0                → 路由器 R1
```

访问 `2001:db8:42:20::80`，匹配更具体的 `/64`，经 R2；访问其他目标，则可能使用默认路由 R1。选中下一跳后，主机还需要知道该接口上的下一跳链路层地址。

这形成两种不同失败：

- 路由没有正确下一跳：不知道交给谁。
- 路由正确但邻居解析失败：知道交给谁，却不能在当前链路上把帧交过去。

同样，控制面的路由存在，不保证它已正确进入硬件转发表。IPv6 仍要区分协议学习、路由选择和实际数据转发。

## 2. ICMPv6 是错误反馈，不只是 ping

常见 ICMPv6 类型按用途理解：

| 消息 | 表达的事实 | 不能直接得出的结论 |
| --- | --- | --- |
| Destination Unreachable | 某处报告目的不可达或被禁止等错误，具体看 Code | 不能仅凭名称判断是线路断了 |
| Packet Too Big | 某段路径无法承载这个尺寸的包 | 不意味着服务器 CPU 过载 |
| Time Exceeded | 跳数耗尽或重组超时等 | 不等于被点名的设备就是根因 |
| Parameter Problem | 首部参数或选项处理有问题 | 不一定是传输层端口关闭 |
| Echo Request/Reply | 一次诊断报文往返 | 不证明 TCP、TLS、应用业务都正常 |

NDP 同样使用 ICMPv6，但属于邻居与路由器发现用途。基本 ICMPv6 错误语义见 [RFC 4443](https://www.rfc-editor.org/rfc/rfc4443.html)。

## 3. MTU、PMTU、MSS 不是一个量

| 名称 | 范围 | 例子 |
| --- | --- | --- |
| 接口 MTU | 单条接口允许交付的三层包大小 | 某以太接口 MTU 为 1500 |
| PMTU | 一条方向性路径中可承载的最大包大小 | 路径里经过一个只能承载 1400 的隧道 |
| TCP MSS | 接收方通告的 TCP 数据段载荷上限 | 不含 IP 与 TCP 首部的 TCP 数据字节数 |

若接口 MTU 为 1500，没有 IPv6 扩展首部且按 20 字节 TCP 基本首部计算：

```text
1500 - 40（IPv6 基本首部）- 20（TCP 基本首部）= 1440 字节
```

这是一个基础预算。TCP 选项和其他首部会进一步消耗空间；线上实际数据段尺寸还受路径发现、拥塞窗口和应用数据量等影响。

去程与回程可以走不同路径，因此 PMTU 也不应被当成对称常量。ECMP 或路径切换还可能使它变化。

## 4. 一个过大的包如何促成尺寸调整

假设发送端第一跳支持 1500，路径中有一段只支持 1400：

```text
发送端发出 1500 字节 IPv6 包
  → 中间路由器无法从 1400 MTU 的出口转发
  → 丢弃该包，并向源端反馈 Packet Too Big，携带 MTU 信息
  → 源端更新路径尺寸认知
  → 传输层改用更小的数据分段继续传输
```

中间路由器不把这个 IPv6 包自动拆成两块继续送。IPv6 的路径 MTU 发现由 [RFC 8201](https://www.rfc-editor.org/rfc/rfc8201.html) 描述。

IPv6 链路需要满足至少 1280 字节的 MTU 要求；底层承载如果更小，需要在 IPv6 下方提供适配。1280 也不是“所有业务都应永久限制为 1280”的性能建议。

## 5. 为什么会出现小包成功、大包卡住

考虑下面这条因果链：

1. 小的握手包能穿过整条路径。
2. 传输数据时，包超过某一段路径的承载能力。
3. 路由器反馈 Packet Too Big。
4. 安全设备把这类 ICMPv6 错误全部过滤。
5. 发送端缺少有效反馈，继续重传过大的包。

这就是 PMTU 黑洞的一类形成方式。TCP 连接可以已经建立，TLS 或大响应却无法顺利完成。

但“大包更容易失败”只是线索，也可能与拥塞、接收队列、链路错误或应用行为有关。不能仅凭小包成功就认定唯一原因是 MTU。

## 6. MSS 调整和探测机制分别能解决什么

MSS 调整针对 TCP 握手中通告的载荷预算，可以在某些路径中减少过大的 TCP 数据段。但它不覆盖普通 UDP，也不能替代正确的隧道 MTU 与 ICMPv6 策略。

传输层还可以通过主动探测、确认和回退来发现可用包尺寸，减少对 ICMP 单一反馈的依赖。数据报传输的这种机制见 [RFC 8899](https://www.rfc-editor.org/rfc/rfc8899.html)。具体协议栈是否实现、何时触发，是实现问题，不能假设所有应用天然具备自动恢复能力。

分片也不是无成本兜底。源端分片会带来重组开销，任意分片丢失都可能影响整个原始包，还增加中间设备的状态与策略处理复杂度。

## 7. 从现象到机制的判断边界

| 现象 | 可以提出的假设 | 仍需区分的对象 |
| --- | --- | --- |
| 无可用默认路由 | RA 或静态路由状态异常 | 地址是否仍有效，是否有更具体路由 |
| 下一跳解析失败 | 链路、邻居或消息策略异常 | 本链路问题与上游问题 |
| 小响应正常，大响应停滞 | 尺寸相关问题值得优先考虑 | PMTU、丢包、应用与缓冲区 |
| IPv4 快、IPv6 慢 | 两个地址族的路径或服务能力不同 | DNS 选择、路由、入口、后端 |

这张表用来约束推理，不是把某一现象直接等同于某一根因。

### 7.1 MSS 通告与实际 TCP 数据长度要分开算

假设初始接口 MTU 为 1500，按 IPv6 基本首部 40、TCP 基本首部 20 通告 MSS 1440；若实际 TCP 使用 12 字节选项，发送时还需为选项留空间。路径后来发现 PMTU=1400，且无 IPv6 扩展首部，则该条件下实际数据预算是：

```text
1400 - 40 - 20 - 12 = 1328 字节
```

不应把 SYN 中的 1440 理解成所有后续报文都固定携带 1440 字节。扩展首部、隧道与传输层选项的预算要在正确层级扣除；MSS 通告计算规则见 [RFC 6691](https://www.rfc-editor.org/rfc/rfc6691.html)。

### 7.2 PTB 如何关联到本机通信

Packet Too Big 不只是携带一个 MTU 数字，还引用触发错误的原始报文。源端据此关联目的、协议及可获取的连接信息，检查反馈是否合理，再降低相应路径估计。

PTB 不能用来直接提高 PMTU；较大 MTU 的恢复需要后续探测或缓存管理。也不能仅因某个 ICMPv6 报文声称尺寸小，就无条件调整所有连接。协议行为与安全校验边界见 [RFC 8201](https://www.rfc-editor.org/rfc/rfc8201.html)。

例如去程经 1400 MTU 的隧道，回程走 1500 的直达链路。服务端发送大响应成功，并不能证明客户端发送同样大的请求也成功，因为反馈与路径具有方向性。

### 7.3 为什么连接迁移后还会留下尺寸问题

ECMP 成员变化、VPN 切换或多出口选路会让同一目标对应不同承载条件。缓存的旧 PMTU 过大，需要新的错误反馈或传输层探测降低；过小可能仍能通信但段数更多，不能靠“恢复路由”就证明尺寸已重新优化。

黑洞检测也需要区分拥塞丢包与尺寸丢包。DPLPMTUD 使用有边界的探测、成功确认和回退来建立尺寸认知，不是任何超时都永久缩包。见 [RFC 8899](https://www.rfc-editor.org/rfc/rfc8899.html)。

## 8. 思考与解答

**MSS 1440，PMTU 1400 且 TCP 选项 12 字节，还能每段发 1440 字节吗？**

不能。在示例无扩展首部条件下，实际数据预算是 1328 字节，还可能被窗口或应用数据量限制。

**收到“MTU 更大”的 PTB，可以立即增大报文吗？**

不可以。PTB 是降低估计的错误反馈，不能据此提高 PMTU，较大尺寸需要按协议探测与验证。

**回程大文件正常，能否排除去程 PMTU 黑洞？**

不能。两方向路径、封装与消息策略可能不同，应分别定位丢失与反馈。

**固定把所有包限制到 1280 就是最优方案吗？**

不是。它混淆最低链路要求与最佳传输尺寸，可能增加处理开销，且无法修复其他策略、路由或应用问题。

**ping 成功，为什么 TLS 还会卡住？**

因为 Echo 报文和 TLS 数据的尺寸、协议处理、安全策略、终点服务都可能不同。成功的诊断样本只能证明该样本经过的条件成立。

**把 TCP MSS 改小，是否等于修复所有 MTU 问题？**

不是。它只影响相应 TCP 连接的数据尺寸协商，不覆盖所有 UDP、扩展首部和动态变化路径。

**本机默认路由正确，远端就能把响应发回来吗？**

不能保证。对端与中间网络仍须拥有返回本机源前缀的可用路径，并允许相应流量。
