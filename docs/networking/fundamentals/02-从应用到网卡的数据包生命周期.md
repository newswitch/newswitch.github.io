# 从应用到网卡：一个数据包的完整生命周期

## 1. 学习目标 {/* #学习目标 */}

学完后能够：

- 区分应用数据、TCP Segment、IP Packet 和 Ethernet Frame。
- 解释 Socket、路由表、邻居表、队列规则和网卡各自负责什么。
- 判断同网段与跨网段通信在二层目的 MAC 上有什么不同。
- 使用 `ss`、`ip route`、`ip neigh`、`tcpdump` 验证一次真实连接。

## 2. 分层不是背诵题 {/* #1-分层不是背诵题 */}

常见的五层模型可以这样理解：

| 层 | 核心对象 | 关键标识 | 解决的问题 |
| --- | --- | --- | --- |
| 应用层 | Message | URL、域名、方法、业务字段 | 应用要表达什么 |
| 传输层 | Segment/Datagram | 源/目的端口 | 交给哪一个进程，是否可靠 |
| 网络层 | Packet | 源/目的 IP | 跨多个网络到哪台主机 |
| 链路层 | Frame | 源/目的 MAC、VLAN | 在当前二层链路交给谁 |
| 物理层 | Bit/Symbol | 电/光信号 | 如何在介质上传输 |

真实实现不会严格地“一层只能调用下一层”，但分层仍是定位问题最有效的模型。

## 3. 发送路径 {/* #2-发送路径 */}

假设应用向 `10.20.0.8:443` 建立 TCP 连接。

```mermaid
flowchart TD
    A["应用调用 connect / write"] --> B["Socket 与 TCP 状态机"]
    B --> C["构造 TCP 首部与序列号"]
    C --> D["路由策略与 FIB 查找"]
    D --> E["选择源 IP、下一跳、出口接口"]
    E --> F["邻居表查下一跳 MAC"]
    F --> G["构造以太网帧"]
    G --> H["qdisc 排队与整形"]
    H --> I["驱动描述符与 NIC TX Ring"]
    I --> J["网卡发送到链路"]
```

### 3.1 Socket {/* #21-socket */}

Socket 是进程访问内核网络栈的接口。一个 TCP 连接通常由五元组标识：

```text
源 IP、源端口、目的 IP、目的端口、协议
```

查看本机连接：

```bash
ss -ntp
ss -lntp
ss -ti dst 10.20.0.8
```

`LISTEN` 只证明本机存在监听 Socket，不证明防火墙、路由和对端访问正常。

### 3.2 路由与源地址选择 {/* #22-路由与源地址选择 */}

内核根据目的地址查询转发表：

```bash
ip route get 10.20.0.8
```

典型输出会告诉你：

```text
10.20.0.8 via 10.10.0.1 dev eth0 src 10.10.0.10
```

这行已经回答了四个问题：下一跳、出口接口、源地址和匹配结果。

### 3.3 邻居解析 {/* #23-邻居解析 */}

IP 路由确定“下一跳 IP”，但以太网发送还需要“下一跳 MAC”：

```bash
ip neigh show dev eth0
```

直连路由通常解析目标主机的 MAC；经网关的路由解析所选下一跳的 MAC，该下一跳不一定来自默认路由。以太网帧的
目的 MAC 每经过一个三层跳点都会变化，IP 目的地址通常保持不变，除非发生 NAT。

### 3.4 排队与网卡 {/* #24-排队与网卡 */}

数据包经过 qdisc 后进入驱动和网卡发送队列：

```bash
tc -s qdisc show dev eth0
ip -s link show dev eth0
ethtool -S eth0
```

应用慢不一定是“网络带宽不够”。也可能是 Socket 缓冲区、qdisc 丢包、NIC Ring、
软中断或对端窗口限制。

## 4. 接收路径 {/* #3-接收路径 */}

接收方向大致相反：

```text
NIC RX Ring
→ 驱动/NAPI
→ 二层处理
→ IP 路由与 Netfilter
→ TCP/UDP
→ 按五元组找到 Socket
→ 唤醒应用读取
```

关键区别是：网卡收到帧并不等于应用一定收到数据。数据可能因为 VLAN、目的 MAC、
路由、反向路径过滤、防火墙、连接状态、端口未监听或应用缓冲区而被丢弃。

### 4.1 从 write 到 read，没有一对一的数据包

普通缓冲式 TCP Socket 的 `write` 返回 4096，通常表示内核接受了 4096 字节，不表示它们已上网，更不表示服务器完成业务。非阻塞写还可能只接受部分数据，应用必须依据返回值继续处理。

这些字节可能被拆成多个 TCP 段，连续几次小写入也可能合成一个段。TCP 提供有序字节流，不保留写入边界。对端一次 `read` 可能得到半条消息，也可能得到多条消息，因此应用协议需要长度字段、分隔符等成帧规则。

| 可见事件 | 能说明什么 | 不能说明什么 |
| --- | --- | --- |
| write 返回 | 本机接受了相应字节 | 对端收到 |
| NIC 发送完成 | 相应描述符可回收，计数口径看驱动 | 远端 TCP 已确认 |
| 收到累计 ACK | 对端 TCP 接收了相应连续字节 | 应用已读取、落盘或提交事务 |
| 业务响应成功 | 完成响应约定的操作 | 未约定的副本同步也完成 |

例如数据库先由 TCP 确认接收 SQL，再执行事务，不能以 ACK 代替 COMMIT 响应。见 [TCP 接口语义](https://www.rfc-editor.org/rfc/rfc9293.html#section-3.8)。

### 4.2 CPU、队列和网卡怎样交接所有权

缓冲区保存数据，描述符描述地址、长度与卸载要求；NIC 通过 DMA 访问内存，发送完成后驱动回收资源。接收侧通常先准备缓冲区，NIC 填入数据并报告完成，驱动再交给协议栈。

中断和 NAPI 负责通知、轮询与分配处理预算，不是每个线上字节都要“通过中断复制一次”。RSS 可以把不同流散列到不同 RX 队列，再由不同 CPU 处理。单队列或单 CPU 忙，不要求整机 CPU 都高。

积压可能分别发生在 Socket 等待窗口、qdisc 等待发送机会、驱动等待 NIC、接收队列等待 CPU、Socket 等待应用读取。它们的容量、单位和丢弃计数不同。见 [NAPI](https://docs.kernel.org/networking/napi.html) 与 [网络多队列扩展](https://docs.kernel.org/networking/scaling.html)。

### 4.3 抓包中的大包未必在线上出现

TSO 让 NIC 对大 TCP 缓冲区分段，GSO 提供软件分段能力，GRO 则聚合接收方向可合并的报文以减少处理开销。抓包点可能处于分段之前或聚合之后。

本机看到大于 MTU 的 TCP 记录，不等于线路传输了超大以太帧；发送方向显示校验和未完成，也可能是 NIC 稍后计算。应结合抓包点、卸载配置与对端观察判断。见 [Linux 分段卸载](https://docs.kernel.org/networking/segmentation-offloads.html)。

### 4.4 三层转发与代理，重建的对象不同

客户端 `10.10.0.10:51000` 经网关访问 `10.20.0.8:443`，无 NAT、代理与隧道时，第一帧交给网关 MAC；路由器递减 TTL，查目的 IP 的 FIB，再解析出口邻居并重建二层封装。路由器不因此建立新的 TCP 连接，响应方向仍独立选路。

若中间是终止 TCP 的代理，它是前一条连接的终点，又是后一条连接的起点，两边分别维护序列号、窗口、重传与超时。定位问题前，应先确认中间设备是在转发包还是终止连接。

## 5. 同网段与跨网段 {/* #4-同网段与跨网段 */}

普通接口地址通常会生成相应的直连路由，但主机实际依据策略路由与转发表判断交付方式，不能只比较两端地址的前缀。更具体的主机路由、VPN 或策略表可能改变路径。下面假设没有这些额外策略。

### 5.1 同网段 {/* #同网段 */}

```text
源 IP：10.10.0.10/24
目的 IP：10.10.0.20
二层目的：10.10.0.20 的 MAC
```

### 5.2 跨网段 {/* #跨网段 */}

```text
源 IP：10.10.0.10/24
目的 IP：10.20.0.8
默认网关：10.10.0.1
二层目的：10.10.0.1 的 MAC
```

“目的 IP 在远端”并不意味着以太网帧直接写远端主机 MAC。

## 6. 最小实验 {/* #5-最小实验 */}

在隔离 Linux 实验机执行。以下命令创建两个 namespace 和一对 veth：

```bash
sudo ip netns add h1
sudo ip netns add h2
sudo ip link add h1-eth type veth peer name h2-eth
sudo ip link set h1-eth netns h1
sudo ip link set h2-eth netns h2

sudo ip -n h1 addr add 10.0.0.1/24 dev h1-eth
sudo ip -n h2 addr add 10.0.0.2/24 dev h2-eth
sudo ip -n h1 link set lo up
sudo ip -n h2 link set lo up
sudo ip -n h1 link set h1-eth up
sudo ip -n h2 link set h2-eth up
```

先观察初始状态：

```bash
sudo ip -n h1 route
sudo ip -n h1 neigh
```

一边抓包，一边发起通信：

```bash
sudo ip netns exec h1 tcpdump -eni h1-eth 'arp or icmp'
sudo ip netns exec h1 ping -c 2 10.0.0.2
```

再次查看邻居表：

```bash
sudo ip -n h1 neigh
```

应该先看到 ARP Request/Reply，再看到 ICMP Echo Request/Reply。

实验完成后清理：

```bash
sudo ip netns del h1
sudo ip netns del h2
```

删除 namespace 会删除其中的临时接口，仅在专用实验环境执行。

## 7. 诊断顺序 {/* #6-诊断顺序 */}

当“访问不通”时，不要直接抓全流量：

1. `ss -lntp`：服务是否监听正确地址和端口。
2. `ip addr`：源/目的地址是否存在且状态正常。
3. `ip route get <dst>`：实际选择了什么路径。
4. `ip neigh`：下一跳是否解析，状态是否反复 FAILED。
5. `nft list ruleset`：本机策略是否丢弃。
6. `tcpdump -ni <if>`：请求是否离开、响应是否返回。
7. `ip -s link`、`ethtool -S`：接口和网卡是否丢包。

## 8. 常见误区 {/* #7-常见误区 */}

- **Ping 通就代表服务正常**：ICMP 与 TCP 端口、应用协议完全不同。
- **路由表有路由就一定转发**：还要考虑策略路由、邻居、ACL、MTU 和返回路径。
- **抓不到包就是对端没发**：可能抓错接口、被硬件卸载或在更早阶段丢弃。
- **重启网络解决了就是偶发问题**：重启可能清理邻居、连接跟踪和队列，同时删除证据。

## 9. 复习题 {/* #8-复习题 */}

**跨网段访问时，目的 IP 和目的 MAC 分别是谁？**

无 NAT 的普通路由中，目的 IP 是最终服务器，当前帧的目的 MAC 是所选下一跳。三层跳点重建二层封装，不把服务器 IP 自动改成网关 IP。

**`ip route get` 比只看 `ip route` 多解决了什么问题？**

前者对给定输入执行查询，后者主要列出表项。多出口环境还应提供实际源地址、入接口或 mark 等条件；缺少这些上下文的查询不能代表全部应用流量。

**网卡 RX 计数增加但应用没有收到数据，下一步检查哪些层？**

先确认计数包含目标流量，再检查驱动队列、软中断、VLAN、路由与策略、TCP 接收状态、Socket 缓冲和应用读取。RX 总量不是目标连接交付成功的证据。

**同一连接的去回程为什么仍可能走不同路径？**

各方向按自己的目的地址、策略和拓扑独立选路。转发协议不要求路径镜像，有状态 NAT 或防火墙则可能要求两方向经过同一状态上下文。

**write 成功但最终交付失败，是不是 TCP 失去可靠性？**

不是。write 不等待最终交付；TCP 随后发送、等待确认和重传，也可能最终报告失败。可靠字节流不承诺任意断网条件下都能成功。

**一个 RX 队列忙，增加应用线程一定有用吗？**

不一定。保持流内顺序的散列通常不会把同一流任意拆到全部队列。应先判断瓶颈在接收处理、应用消费还是窗口。
