# 训练网络全链路故障排查

本篇把 Kubernetes、GPU、RDMA、Fabric 和训练框架合并为值班 Runbook。协议层细节参见
[无损 Fabric 分层排障](../fabric/09-无损Fabric分层故障排查.md)。

## 1. 先判定故障阶段

```text
A Pod 尚未创建/调度
B Pod 已启动，NCCL 初始化失败
C 训练已开始，Collective Timeout
D 训练不失败但变慢/抖动
E 只在扩容、故障或多作业时出现
```

不同阶段需要不同第一证据。

## 2. A：Pod Pending/ContainerCreating

### Pending

```bash
kubectl describe pod <pod>
kubectl get nodes
kubectl describe node <node>
```

检查：

- GPU/RDMA Extended Resource；
- Gang/Queue；
- Node Affinity/Taint；
- Preflight 状态；
- Topology Manager 可能的后续准入；
- VF/共享资源是否耗尽。

### ContainerCreating

检查 Event 和 Node：

- Multus；
- NAD；
- IPAM；
- SR-IOV CNI；
- Device Plugin；
- VF 分配；
- Driver/Runtime；
- Image 与权限。

此阶段还没有 NCCL 数据面，不应从 PFC 开始排查。

## 3. B：NCCL 初始化失败

顺序：

1. 所有 Rank/Pod 是否启动；
2. Rank Rendezvous 地址/DNS；
3. Bootstrap 接口与防火墙；
4. Pod 辅助接口/IP/Route；
5. RDMA Device/GID/LID；
6. HCA/Net Plugin；
7. GPU/NIC 拓扑与 GDR；
8. Fabric 基础可达；
9. NCCL 日志最先失败 Rank。

```bash
kubectl exec <pod> -- ip -br addr
kubectl exec <pod> -- ip route
kubectl exec <pod> -- rdma link show
kubectl exec <pod> -- ibv_devinfo
```

## 4. C：Collective Timeout

Timeout 是结果。找第一个异常：

```text
某 Rank 进程退出/GPU Error
→ 其他 Rank 等待
→ NCCL Watchdog/Timeout
```

或：

```text
链路/拥塞/重试
→ Collective 延迟不断增加
→ 超过 Timeout
```

收集：

- Job/Pod Event；
- 所有 Rank 日志，不只报错 Rank；
- GPU Xid/ECC/NVLink；
- NCCL Async/RAS；
- RDMA Retry/Error；
- Link/Queue/ECN/PFC；
- 最近变更；
- 作业并行组和消息大小。

## 5. D：训练变慢

先比较：

- 同模型同规模历史；
- 同一作业不同 Rank；
- 单机与跨机；
- Host RDMA、GPU RDMA、NCCL；
- 正常与异常节点；
- 小消息与大消息。

分流：

```text
Compute Kernel 变慢 → GPU/模型
Collective 变慢 → NCCL/RDMA/Fabric
DataLoader 变慢 → 存储/CPU
所有阶段都慢 → 节点系统/频率/争用
```

## 6. E：规模/多作业问题

单作业正常，大规模失败：

- 二分带宽；
- ECMP/IB 路由分布；
- QP/Connection Resource；
- 全局同步慢 Rank；
- PFC/ECN Threshold；
- Control Plane/SM；
- Scheduler Rank Mapping。

单作业正常，多作业慢：

- Rail/Queue 争用；
- Checkpoint；
- Admission；
- HCA/VF 资源共享；
- Storage 流误入 Lossless；
- PFC 拥塞树。

## 7. 证据包

自动收集但需脱敏：

```text
job.yaml / pod events
node/pod resource mapping
nvidia-smi/topology
rdma/ibv/gid state
NCCL logs per rank
perftest minimal result
switch path/port/queue snapshot
PFC/ECN/CNP delta
recent changes
timeline
```

证据脚本默认只读、有限并发、带截止时间，不应在故障时把设备管理面压垮。

## 8. 快速矩阵

| Host RDMA | GPU RDMA | NCCL | 方向 |
|---|---|---|---|
| 失败 | 未测 | 未测 | NIC/Fabric |
| 正常 | 失败 | 失败 | GDR/PCIe/GPU |
| 正常 | 正常 | 失败 | NCCL/Rank/框架 |
| 正常 | 正常 | 正常 | 真实模型/并行/存储 |
| 偶发 | 偶发 | 偶发 | 链路/拥塞/硬件抖动 |

## 9. 两个常见误区

### 只看最后报错 Rank

Collective 中最后报错的 Rank 可能只是等待者。按时间找最先偏离的 Rank/Node。

### 重启解决

重启可能清掉 QP、驱动状态或临时拥塞，但没有根因证据。重启前尽量保存计数、日志和拓扑；
恢复后仍需对比并建立防复发。

## 10. 恢复策略

- 单坏节点：Quarantine，作业重调度；
- 单 Rail：按容量决定降级运行或停止；
- PFC Storm：隔离根部接收端/作业；
- Driver/Firmware Bug：停止扩大，回滚 Canary；
- 错误 QoS：按故障域修复，避免全网同时改；
- 全局 SM/控制面：按主备 Runbook。

## 11. 复盘

```text
影响与浪费 GPU 小时
最先异常信号
为何未在 Preflight 发现
根因和触发条件
为何扩大到更多 Rank/作业
恢复时间线
监控/调度/变更护栏改进
```

## 12. 掌握标准

给出 Pod Pending、初始化失败、NCCL Timeout 或训练变慢之一，能够在正确阶段选择证据，
把问题缩小到一个 Rank/Node/Rail/Queue，并给出恢复与防复发措施。
