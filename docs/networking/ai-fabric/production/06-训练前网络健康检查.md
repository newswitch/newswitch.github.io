# 训练前网络健康检查

一个千卡作业因一台坏节点运行数小时后失败，代价远高于启动前几分钟的分层检查。
Preflight 的目标是阻止“已知不健康”资源进入作业，不是每次都跑满 Fabric。

## 1. 状态模型

```text
Ready       最近检查通过，可调度
Degraded    可用于低等级/受限作业
Draining    正在维护，不接新作业
Quarantined 检查失败，禁止训练
Unknown     数据过期或无法检查，默认不判健康
```

状态必须有 TTL。昨天通过不能证明今天换线后仍健康。

## 2. 静态检查

从 SoT 与 Node 对账：

- GPU/NIC 型号和数量；
- PCI BDF/NUMA；
- Rail/交换端口；
- Driver/Firmware/CUDA/NCCL；
- Link Speed/Width/MTU；
- VF/Resource 数；
- GID/LID/PKey/VLAN；
- QoS/PFC/ECN Profile Hash；
- Kubernetes Label/Taint。

静态检查快速、低扰动，适合每次节点入池。

## 3. 动态检查

### 3.1 L0 主机 {/* #l0-主机 */}

```text
GPU Health
NVLink/NVSwitch
PCIe Link
NIC Health/Temperature
Time Sync
Disk/Memory 基础
```

### 3.2 L1 RDMA {/* #l1-rdma */}

```text
Port Active
GID/LID 正确
RDMA Device 可见
无新增严重 Error
小规模 rping/perftest
```

### 3.3 L2 Fabric {/* #l2-fabric */}

```text
Route/ECMP
每 Rail Peer 可达
无持续 PFC Storm
无 Buffer Drop
队列/链路没有现存拥塞
```

### 3.4 L3 GPU/NCCL {/* #l3-gpunccl */}

```text
GPU Memory RDMA
小规模 nccl-tests
Transport/HCA/GDR 符合预期
结果在同类节点基线范围
```

## 4. 检查强度

| 时机 | 检查 |
|---|---|
| 每分钟/持续 | Link、Counter、Telemetry |
| Node 加入/重启 | 静态 + 轻量 RDMA |
| Driver/Firmware 变更 | 完整 Host/GPU RDMA |
| 大作业启动 | 选中节点 Pair/Group 轻量检查 |
| 维护后 | 完整验收 |
| 定期离线 | 全消息矩阵和故障演练 |

Preflight 不能自身制造拥塞。并发、持续时间和测试 Peer 要限流。

## 5. Peer 选择

单节点本地检查无法验证 Fabric。可维护少量健康 Probe 节点：

- 每 Rail 一个/多个；
- 跨 Leaf/跨 Pod；
- 与生产节点同硬件；
- 不成为单点；
- 自身状态先验证。

对大型作业不必全互测 `N²`，可用拓扑覆盖和抽样：

```text
每节点→同 Leaf Peer
每节点→跨 Leaf Peer
每 Rail→至少一个路径
异常节点→扩大矩阵
```

## 6. 输出

机器可读结果：

```json
{
  "node": "gpu-node-17",
  "run_id": "preflight-20260807-001",
  "status": "Ready",
  "valid_until": "2026-08-07T12:00:00Z",
  "topology_hash": "sha256:...",
  "checks": {
    "pcie": "PASS",
    "rail_a_rdma": "PASS",
    "rail_b_rdma": "PASS",
    "gdr": "PASS",
    "nccl": "PASS"
  }
}
```

原始证据单独保存，Label 只保存低基数状态。

## 7. 与调度集成

可用：

- Node Label + Node Affinity；
- Taint/Toleration；
- 自定义 Scheduler/Admission；
- 健康 CRD；
- 队列系统在提交前检查；
- Operator 自动 Quarantine/Unquarantine。

状态变更应审计。自动恢复必须要求连续多次通过，避免 Flapping。

## 8. 阈值

使用同型号健康群体基线：

```text
Bandwidth >= 同拓扑 P10 - 容忍
P99 Latency <= 基线 P99 + 容忍
Error Delta = 0 或明确允许
Link Speed/Width = SoT
NCCL Transport/GDR = 期望
PFC/ECN = 在测试模型预期范围
```

不同消息大小、Rail、固件和拓扑使用不同 Baseline Class。

## 9. 防止误判

- Probe 节点坏导致全体失败；
- 监控数据过期被当 PASS；
- 测试流量与生产作业冲突；
- 只跑小消息，漏掉 MTU/大流问题；
- 只跑 Host RDMA，漏掉 GDR；
- 节点换卡后仍使用旧 Topology Hash；
- 一次通过立刻解除隔离；
- 自动检查拥有过大生产写权限。

## 10. 失败处置

```text
检查失败
→ 标记 Unknown/Quarantined
→ 不接收新作业
→ 保留当前作业还是 Drain（按风险）
→ 生成故障证据和工单
→ 修复
→ 完整复验
→ 连续通过观察窗口
→ 恢复 Ready
```

## 11. 实验

1. 为 4 个节点建立 Topology Hash。
2. 编写只读静态检查。
3. 加入每 Rail 小规模 perftest。
4. 加入 GPU Memory/NCCL 检查。
5. 将结果写入 CRD/Label。
6. 故意让一条链路降速。
7. 验证新作业不会选中该节点。
8. 修复并经过连续通过后恢复。

## 12. 掌握标准

能够设计不压垮 Fabric 的检查矩阵；能区分 Ready、Degraded、Quarantined 和 Unknown；
能让调度使用有 TTL、有证据的健康状态，而不是永久手工 Label。
