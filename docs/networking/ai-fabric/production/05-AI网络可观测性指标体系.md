# AI 网络可观测性指标体系

AI 网络监控不能停在“端口 Up、流量 80%”。需要回答：哪个作业、哪个 Rank、哪张 GPU、
哪张 NIC、哪条 Rail、哪个交换队列导致了多少训练 Step 抖动。

## 1. 六层指标

| 层 | 指标 |
|---|---|
| 物理链路 | State、Speed/Width、FEC、Symbol/CRC、Link Down |
| Fabric | Route/ECMP、Port 吞吐、Queue Watermark、Discard |
| 无损/拥塞 | PFC Frame/Duration、ECN Mark、CNP、Buffer |
| NIC/RDMA | GID/LID、Retry、RNR、QP Error、Bytes、Temperature |
| GPU/PCIe | PCIe Width/Speed、NVLink、GPU Error/Clock |
| NCCL/训练 | Transport、Collective Time、algbw/busbw、Step Time |

上层指标必须能下钻到下层对象。

## 2. 统一资源身份

为同一端口建立映射：

```text
Cluster
→ Node
→ GPU UUID / PCI BDF
→ NIC PCI BDF
→ RDMA Device / Port
→ Netdev
→ Rail
→ Switch / Port
→ Queue / Priority
→ Job / Pod / Rank
```

PCI BDF、接口名和 `mlx5_N` 可能因硬件/启动顺序变化。SoT 要记录序列号和物理端口等持久身份，
监控采集时动态对账。

## 3. 链路指标

每端口采集：

- Admin/Oper State；
- Negotiated Speed/Width/FEC；
- Rx/Tx Bytes/Packets；
- CRC/FEC/Symbol/AER Error；
- Discard/No Buffer；
- Link Down/Recovery；
- Optic Temperature/Power（支持时）。

错误看增量和速率：

```text
rate(error_counter[5m])
```

历史累计非零不一定表示当前故障；Counter Reset/设备重启需要处理。

## 4. 队列与无损指标

按 Port、Priority、TC、Queue：

- Current/Max Queue Occupancy；
- Shared Buffer/Headroom Usage；
- ECN Mark Rate；
- CNP Tx/Rx；
- PFC Tx/Rx Frame；
- PFC Pause Duration；
- PFC Watchdog/Deadlock Event；
- Queue/No-Buffer Drop。

Pause Duration 比单纯 Frame Count 更接近影响时间。方向定义以设备为准。

## 5. RDMA/NIC 指标

根据 Driver/设备支持采集：

- Port State/Rate；
- RDMA Packets/Bytes；
- Retry/Timeout；
- RNR；
- Out-of-Sequence/Discard；
- CQ/QP/MR 资源使用；
- ECN/CNP/DCQCN；
- VF/PF Counter；
- Firmware/Driver Version；
- NIC Temperature/Health。

同一 Counter 在不同驱动版本名称和语义可能变化，采集器需要版本化映射。

## 6. NCCL 和训练

至少记录：

- Job、Pod、Rank、Node、GPU；
- Collective 类型、消息大小；
- Collective Duration P50/P95/P99；
- NET Transport/HCA/Rail；
- NCCL Async/RAS Error；
- 训练 Step Time；
- Communication/Computation Overlap；
- GPU Busy/Idle/Clock；
- Checkpoint 和 DataLoader 时间。

若框架只提供整 Step Time，仍可用 Profiler/NCCL Test 建立故障时的分层基线。

## 7. 时间同步

交换机、NIC、Node、Pod、训练日志和监控平台必须使用可靠时间源。

保存两个时间：

```text
Source Timestamp
Collector Receive Timestamp
```

流式 Telemetry 断线后可能延迟或补发。告警系统要识别数据缺口，不把“没有数据”当健康。

## 8. Label 与基数

推荐低/中基数：

```text
cluster, site, role, node, device, port, rail, priority, queue
```

高基数信息：

```text
job_id, pod_uid, rank, qp
```

不一定适合长期放入每条 Prometheus Time Series。可通过事件/Trace/日志保存映射，再按 Run ID 关联。

## 9. 大盘

### 9.1 Fabric Overview {/* #fabric-overview */}

- 健康端口/降速端口；
- Rail 吞吐和错误；
- ECN/PFC 热点；
- Queue Watermark；
- 作业与节点分布。

### 9.2 Job View {/* #job-view */}

- Step Time；
- Collective P99；
- Rank Heatmap；
- 每 Rank GPU/NIC/Rail；
- 相关端口 Queue/ECN/PFC；
- 最近变更。

### 9.3 Node View {/* #node-view */}

- GPU/NVLink/PCIe；
- NIC/RDMA；
- Driver/Firmware；
- Pod/Resource；
- Preflight 状态。

## 10. 告警

告警要有持续时间、影响和动作：

| 告警 | 条件思路 | 动作 |
|---|---|---|
| Link Degrade | Speed/Width 低于 SoT | 隔离 Rail/节点 |
| PFC Storm | Pause Duration 持续增长 | 沿下游找拥塞根 |
| ECN Without CNP | Mark 高、CNP 无 | 查接收 NIC |
| RDMA Retry | 增量超过基线 | 查丢包/路径 |
| Socket Fallback | 训练使用 NET/Socket | 检查 RDMA/HCA |
| Step Regression | 同类作业 P99 退化 | Rank→Rail 下钻 |
| Telemetry Gap | 采集缺失 | 状态 Unknown，不判健康 |

## 11. 变更关联

每次 Driver、Firmware、PFC/ECN、路由、Operator 和 Node 配置变更写入事件流：

```text
Change ID
Commit/Artifact
Device/Node/Rail
Start/End
Operator
Pre/Post Snapshot
Result
```

故障时间线先看变更，但不能因为时间接近就直接认定因果。

## 12. 实验

1. 为单个训练 Job 建 Rank→GPU→NIC→Port 映射。
2. 采集六层指标。
3. 运行 nccl-tests，生成 Run ID。
4. 制造单 Rail 降速。
5. 从 Step P99 告警下钻到 Link Speed。
6. 制造 Incast，画 Queue→ECN→CNP→PFC 时间线。
7. 断开一个采集器，验证 Unknown 告警。

## 13. 掌握标准

能从训练 Step Time 进入最慢 Rank，再定位 GPU/NIC/Rail/Queue；能区分“指标为零”和“数据缺失”，
并用变更、日志和计数器建立可复查时间线。
