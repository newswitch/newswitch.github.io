# Subnet Manager 选举、重扫与路由收敛

InfiniBand 链路亮起，只说明物理连接的一部分。端口进入可用状态、地址与分区正确、路由已经配置，以及应用通信正常，还依赖不同管理与执行步骤。Subnet Manager（SM）失效后的恢复也因此不是重启一个进程就结束。

前置阅读[InfiniBand Fabric](../../rdma-roce/ai-cluster/04-InfiniBand-Fabric原理.md)和[UFM 对象模型](./11-UFM对象模型遥测与Fabric管理.md)。这里讨论 IB 子网，不把 NVLink 的 NVLSM 当成可直接互换的服务。

## 1. SM、SA 与 UFM 分别管理什么

SM 负责发现子网、初始化相关端口并配置地址和路由等状态；Subnet Administrator（SA）提供相应管理查询与记录服务；UFM 把管理、观测和其他组件组织成平台。实现可以把多个职责放在同一个软件系统中，但故障语义仍要分开。

因此 UFM 的 WebUI 不可达，不能直接推出交换机已停止转发；SM 已经恢复，也不能说明性能采集已恢复。实际还要区分已有转发表、新拓扑处理、SA 查询和应用请求的状态。

## 2. 主备选举不是轮流写同一组路由

同一子网内可以存在多个 SM 实例，通过主备机制确定负责管理的 Master。OpenSM 手册说明 Master 选择涉及 priority 和 GUID，priority 的范围为 0～15，越大优先级越高。相同优先级仍有 GUID 等判定，不能假设同时启动就按启动先后永久决定角色。见 [OpenSM 官方手册](https://github.com/linux-rdma/opensm/blob/master/man/opensm.8.in)。

还要确认实例绑定哪个 IB 端口。多端口主机可以连接不同子网，某个 SM 正常运行，却可能不是在管理你正在排查的那张 Fabric。

教学反例：A、B 都显示进程存活，但 B 处于备用角色。此时只看服务 Active，无法判断当前写入者是谁，也无法判断 A 故障后 B 是否掌握了正确配置和权限。

## 3. 发现、计算和配置不是一个原子动作

```text
观察端口与拓扑 → 确认当前管理角色 → 分配/核对地址与分区
→ 选择并计算路由 → 下发配置 → 验证端口与目标路径
```

这是理解依赖的教学顺序，具体实现可增量处理、缓存和重试。OpenSM 提供周期 sweep，也区分需要较重处理的变化；路由缓存可以在符合条件时避免不必要的全量计算，见上述手册。

由此可知，重扫不一定等于重算全部路由，拓扑不变也不代表所有策略都不变。强制触发重扫、提高频率或更换路由算法，应当视为管理操作，而不是无副作用的查询。

## 4. SM 短暂失效，为什么已有流量可能继续

交换机已经安装的转发表可以在管理进程不工作时继续转发一部分已有流量。但如果此时链路变化、节点重启、地址或分区发生变化，就需要重新管理。不能从“当前作业还没超时”推导 Fabric 已经具备完整恢复能力。

设 A 是当前 Master，B 是备用；A 退出后，B 接管。在教学时间线上，可能先恢复管理角色，再完成状态发现与配置，最后才让新请求稳定建立。应用若已经把通信错误记入请求，网络恢复也不会自动清除它。

这解释了两种并存现象：长连接仍在传输，而新加入节点暂时不可用；或者底层路径已恢复，但某个训练作业仍需要整组重建通信。

## 5. GUID、LID 与策略版本需要分别关联

GUID 用于关联设备与端口身份；LID 是子网中的地址，不宜被当成永久资产编号。恢复后即使端口 GUID 没变，也需要确认地址、PKey 和路由配置与当前策略一致。

备用管理者如果使用旧分区文件或不同路由配置，角色切换可能带来行为变化。主备健康应包含配置一致性，而不只是二者都能发现设备。密钥和受控管理访问也属于接管条件，不能通过降低保护强度让未知实例接管。

## 6. 用三条时间线解释收敛

分别记录管理角色变化、Fabric 配置生效、应用进度恢复。教学上假设检测 3 秒、角色确定 2 秒、发现与配置 8 秒，应用重新建立通信还需 7 秒。串行模型的端到端恢复是 20 秒，管理角色在第 5 秒确定不等于业务也在第 5 秒恢复。

实际步骤可能并行，时间也随规模、失败位置和应用行为变化。应用超时若短于实际恢复窗口，可能先失败；简单放大超时则可能掩盖永久配置错误。应先量出各阶段，再决定上层的重试与超时策略。

## 7. 从现象选择下一份证据

| 现象 | 下一步核对 | 不能直接得出的结论 |
| --- | --- | --- |
| 端口物理 Up，但逻辑状态未完成 | SM 可达性、绑定子网、初始化与分区状态 | 一定是线缆坏了 |
| 主备切换后只有一组作业失败 | 作业成员、PKey、地址与路径差异 | 整个交换网络全部不可用 |
| 路由已稳定但训练仍等待 | Rank 存活、请求错误和通信上下文 | 再重启 SM 就能恢复 |
| UFM 图表停止但传输继续 | 采集链、时间戳和服务依赖 | 当前没有性能问题 |

## 8. 掌握检查

解释备用进程存活为什么不等于具备接管条件；说明已有转发与新拓扑收敛的区别；画出管理、Fabric、应用三条时间线，并算出 20 秒例子。最后说明为什么同一个 LID 的两次记录必须结合时间与 GUID 才能正确归因。
