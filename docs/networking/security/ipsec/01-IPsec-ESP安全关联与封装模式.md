# IPsec、ESP、安全关联与封装模式

两个分支通过不可信网络通信时，公网路由器仍需要知道包应该去哪个 VPN 网关，但不应因此看见被保护的内部业务内容。隧道模式通过“外层负责交付，内层承载原始通信”分开这两个职责。

## 1. IPsec、ESP 与 IKE 分别是什么

| 名称 | 主要职责 |
| --- | --- |
| IPsec | 网络层安全架构，组织策略、关联与报文处理 |
| ESP | 依据协商的参数保护实际数据报文 |
| IKE | 认证对端并建立、维护安全关联与密钥材料 |
| AH | 提供特定完整性与认证保护的另一种 IPsec 协议，不提供数据加密 |

ESP 不是 TCP/UDP 应用协议。未做 UDP 封装时，它使用 IP 协议号 50。ESP 的实际机密性与完整性能力取决于协商的变换，不能仅凭抓到 ESP 就推断采用了某个具体加密算法。[RFC 4301](https://www.rfc-editor.org/rfc/rfc4301.html) 给出总体架构。

## 2. 传输模式保护什么

传输模式大体保持原始 IP 端点关系，保护传输层数据等载荷：

```text
外部可见：原 IP 首部 | ESP 标识等
受保护：                TCP/UDP 等上层内容及相应尾部
```

它常用于端到端保护，或者与其他封装配合。不能把“没有额外隧道 IP 首部”理解为没有 ESP 开销。

ESP 通常不保护外层可变路由首部的全部字段；路由器仍需读取交付信息。AH 与 NAT 的兼容问题也与它覆盖的首部字段有关，不应认为所有 IPsec 协议都能无差别穿过地址改写。

## 3. 隧道模式把原 IP 包放在哪里

```text
原始包：内网 A 的 IP → 内网 B 的 IP → 业务数据

隧道包：网关 A 的外层 IP → 网关 B 的外层 IP
        └─ ESP：保护原始内层 IP 包
```

在典型站点到站点场景中，外部网络根据网关地址转发；接收网关完成验证和解密，再对内层包进行策略检查与路由。

IPsec 只保护选定边界之间的部分。如果业务在两侧内网仍是明文，网关到应用之间不会因隧道存在而自动获得端到端保护。TLS 与网络层 VPN 可以叠加，负责不同边界。

### 3.1 把 ESP 字段放回报文中

以使用 AES-GCM、16 字节认证标签的 ESP 隧道为例，暂不画 UDP 封装：

```text
外层 IP
  | ESP Header：SPI（4 字节）+ Sequence Number（4 字节）
  | 显式 IV（8 字节）
  | 密文：完整内层 IP 包 + Padding + Pad Length + Next Header
  | Authentication Tag（本例 16 字节）
```

SPI 和序列号需要被接收端读取以选择 SA、执行相应检查，并不隐藏在密文里。AES-GCM 的认证还覆盖相应的附加认证数据，包括 SPI、序列号等；“没有加密某个字段”不等于它一定可以不被发现地篡改。

这里的 IV（Initialization Vector，初始化向量）按算法要求参与构造 Nonce，不是第二份业务密钥。AES-GCM-ESP 还使用密钥材料中的 Salt，与报文携带的显式 IV 组合；不能把 Salt 也算成每个包都额外发送的字节。格式见 [RFC 4106](https://www.rfc-editor.org/rfc/rfc4106.html)。

Pad Length 说明填充长度，Next Header 说明解密后的内容类型。隧道模式里它可以表示内层 IPv4 或 IPv6；传输模式里则通常指向受保护的上层协议。它不是外层公网路由的下一跳字段。

AES-GCM 属于 AEAD（带附加数据的认证加密），同时提供机密性与完整性能力。不能再机械要求它一定配一项独立 HMAC，也不能把 ESP 所有变换都画成完全相同的 IV、标签和填充尺寸。

## 4. SA 为什么有方向

SA 是 Security Association，安全关联，保存处理某一方向受保护流量的算法、密钥、序列号和期限等参数。

一个常见双向通道需要对应的单向 IPsec SA：

```text
A → B：使用 B 能识别的入站 SPI 与相应密钥状态
B → A：使用 A 能识别的另一组 SPI 与密钥状态
```

SPI（Security Parameters Index）帮助接收方定位安全关联，不能单独当成全网唯一的“隧道编号”。查找还涉及协议、目的或本地处理上下文。

两边显示不同入站 SPI 可能完全正常；但某一方向找不到匹配 SA，就可能出现单向计数增长和业务失败。ESP 格式与处理规则见 [RFC 4303](https://www.rfc-editor.org/rfc/rfc4303.html)。

### 4.1 用两组 SPI 看清“我的出站就是你的入站”

假设协商中 A 为自身入站选择 SPI `0x1001`，B 为自身入站选择 SPI `0x2001`：

| 流向 | 线上 ESP SPI | 两端对应状态 |
| --- | --- | --- |
| A → B | `0x2001` | A 的出站 SA ↔ B 的入站 SA |
| B → A | `0x1001` | B 的出站 SA ↔ A 的入站 SA |

两条方向有独立密钥、序列号和接收窗口。排查时应该交叉比对 A 出站与 B 入站，而不是强求 A、B 的入站 SPI 相同。

Rekey 期间还可能暂时出现两套 SPI。数量变多可能是正常的新旧关联重叠，是否异常要看它们的生命周期、方向和实际使用情况。

## 5. SPD 和 SAD 分别决定什么

| 对象 | 主要信息 | 回答的问题 |
| --- | --- | --- |
| SPD：安全策略库 | 选择条件与保护／绕过／丢弃动作 | 这个包应该怎样处理 |
| SAD：安全关联库 | 已建立的 SA、密钥与状态 | 用哪套具体参数处理 |

因此，“SA 已建立”不等于“当前业务包匹配这个 SA”。源地址、目的网段、协议、端口及实现中的其他标记，都会影响策略选择。

入站也不应只做“能解密就接受”。还需判断解出的内层流量是否符合该对端被允许承载的范围，避免把对端身份认证误当成对任何源地址的授权。

### 5.1 完整的数据处理不在一个“加密函数”里完成

```text
出站：明文包 → 策略决定 PROTECT/BYPASS/DISCARD
              → PROTECT 找到可用出站 SA → 编号、封装、保护 → 外层选路

入站：外层包 → 定位入站 SA → 防重放初检与认证解密
              → 校验成功后更新接收状态 → 检查内层选择范围与策略
              → 继续路由和应用访问控制
```

这是架构层模型，不是 Linux 或某款设备的逐 Hook 顺序。实现可以缓存策略、卸载加解密或合并处理，但这些语义不能消失。策略选择不到可用 SA 时，包可能被丢弃、有限等待或触发协商，取决于实现与配置，不会因为“IPsec 软件已启动”就自动选择任意密钥。

总体处理模型见 [RFC 4301](https://www.rfc-editor.org/rfc/rfc4301.html)。它也说明为什么 SA 计数、转发计数与应用成功请求数不能直接视为同一个指标。

## 6. 防重放窗口如何允许正常乱序

接收方维护序列号与防重放窗口，拒绝已处理过或过旧的报文，同时允许窗口内尚未见过的乱序包。它不是简单要求所有包严格递增到达。

网络多路径、突发排队与并行加解密都可能造成乱序。超过当前窗口允许范围的延迟包，可能被丢弃；重复包也不能因为重新经过一条路径就被当成新的合法业务。

防重放与可靠交付不同：ESP 不负责替业务重传丢失包。窗口状态和序列号空间也参与密钥生命周期管理，不能把旧 SA 的序列号无约束重置后继续复用同一安全上下文。

### 6.1 一个 64 项窗口的计算例子

为便于说明，假设某入站 SA 使用宽度 W=64 的窗口，当前已验证的最高序列号 H=100，则当前窗口覆盖 `[37,100]`：

| 新到序列号 | 条件 | 结果 |
| --- | --- | --- |
| 98 | 窗口内，且此前未接收 | 验证成功后可接受，属于正常乱序 |
| 98 | 已经接收过 | 重复包，被拒绝 |
| 36 | 已落到窗口左侧 | 太旧，被拒绝 |
| 105 | 高于当前 H | 验证成功后推进为 `[42,105]` |
| 100000 | 认证验证失败 | 丢弃，不能据此推进窗口 |

64 只是本例宽度，不是所有平台不可修改的固定值。最关键的是：**不能让尚未认证的高序列号永久推进窗口**，否则伪造报文就能把真实业务挤到窗口外。

TCP 丢包后重传某段数据，进入 ESP 时会重新封装为新的 ESP 报文，获得新的 ESP 序列号；它不是要求对端再次接受同一个旧 ESP 序列号。因此 TCP 重传与 ESP 防重放不矛盾。

### 6.2 ESN 与设备切换为什么涉及安全状态

普通 ESP 线上序列号字段为 32 位；ESN（Extended Sequence Number，扩展序列号）将逻辑计数扩展为 64 位，高位按协议在两端维护，而不是额外在每个包里再插入同样大小字段。

扩大计数空间不等于同一密钥可以无限使用。算法有自己的调用量、Nonce 唯一性和安全期限约束。AES-GCM 在同一密钥下重复 IV 尤其危险，不能为了让新主机“继续接管”就把旧序列和 IV 状态随意归零。

这解释了为什么 VIP 漂移不等于 IPsec 会话无损接管：备用机还需相应 SA、密钥、计数和窗口等一致状态，或重新建立新的安全关联。

## 7. 加密成功后仍有哪些信息可见

外层端点、包长、方向、发送节奏等通常仍可被承载网络观察。IPsec 不保证流量形态匿名，也不替应用隐藏所有侧信道。

解密端需要继续执行内部访问控制。一个合法 VPN 用户不应因为能建立隧道，就天然获得全部管理网和数据库权限。

实现层可把控制面与内核数据处理分开，参见 [strongSwan 的 IPsec 概述](https://docs.strongswan.org/docs/latest/howtos/ipsecProtocol.html)。协议协商进程存活与内核 SA 正常转发，不是同一个状态。

## 8. 思考与解答

**SPI 相同就证明是同一条 VPN 吗？**

不能。SPI 要在对应目的、协议和处理上下文中解释，不是全局业务名称。

**IPsec 隧道能替代数据库账户权限吗？**

不能。它保护特定网络边界，数据库仍需验证用户身份和操作权限。

**报文乱序就一定被防重放机制丢掉吗？**

不是。窗口内尚未接收过的乱序包可以被接受；过旧或重复报文的处理才涉及丢弃。

**A、B 两端入站 SPI 不同，说明协商失败了吗？**

不说明。A 的出站对应 B 的入站，B 的出站对应 A 的入站，应按方向交叉比对。

**收到一个特别大的 ESP 序列号，应立即推进窗口吗？**

不能。可以先做快速检查，但只有验证成功后才能更新可信接收状态，不能让伪造报文改变窗口。

**TCP 重传同一段数据，为什么不会必然被 ESP 判为重放？**

重新发送的明文会被封装成新的 ESP 包，使用新的 ESP 序列号；防重放检查针对安全层的包，不是判断应用内容是否重复。

**备用网关拿到了同一个公网 IP，就能继续使用旧加密状态吗？**

不能仅凭地址接管。还需要正确的安全关联与计数状态；否则既可能无法解密，也可能产生序列和 Nonce 复用风险。
