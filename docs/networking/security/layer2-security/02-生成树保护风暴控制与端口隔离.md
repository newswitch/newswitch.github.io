# 生成树保护、风暴控制与端口隔离

把电脑接入口和交换机互联口用同一套保护策略处理，容易出现两种结果：不该参与拓扑的设备影响了网络，或者本应正常交换 BPDU 的上联被保护机制关闭。安全功能必须与端口角色匹配。

## 1. 先弄清端口应该连接什么

| 端口预期 | 需要回答的问题 |
| --- | --- |
| 单终端接入口 | 是否允许出现 BPDU，是否只有一个终端 |
| 电话／AP／虚拟化接入口 | 后面有几个逻辑终端，是否需要多 VLAN |
| 下级交换机口 | 是否允许对方成为根方向，控制消息如何检查 |
| 交换机互联／上联 | 哪些 BPDU 和链路状态是正常工作的必要条件 |

端口角色描述拓扑预期，不是看接口名字里有没有 uplink。角色判断错误时，再严密的开关组合也可能产生错误结果。

## 2. Edge／PortFast 不等于关闭生成树

边缘端口机制让预期连接终端的端口更快进入转发，减少普通终端等待。它不应被理解为“此端口已经与 STP 无关”。

一旦端口后实际出现交换设备或环路，拓扑预期发生了变化。是否收到 BPDU 后退出边缘状态、进入保护状态等，取决于具体协议与配置。

PortFast 与 BPDU Guard 的实现语义可参见 [Cisco 官方说明](https://www.cisco.com/c/en/us/support/docs/lan-switching/spanning-tree-protocol/10586-65.html)。

## 3. 三种 Guard 分别防什么

以下用常见厂商术语说明，状态名称与恢复行为需结合具体实现：

| 机制 | 触发依据 | 主要目标 |
| --- | --- | --- |
| BPDU Guard | 在不应出现 BPDU 的受保护接入口收到 BPDU | 限制意外交换设备参与拓扑 |
| Root Guard | 从不应成为根方向的端口收到更优根信息 | 保持预期根桥边界 |
| Loop Guard | 本应持续收到 BPDU 的相关端口异常失去消息 | 避免因信息消失而错误转入转发 |

BPDU Guard 不是只拒绝“更优 BPDU”，Root Guard 也不是看到任何 BPDU 都关口。Loop Guard 关注另一类风险：消息缺失不等于对端路径真的消失。

Root Guard 的角色见 [Cisco Root Guard](https://www.cisco.com/c/en/us/support/docs/lan-switching/spanning-tree-protocol/10588-74.html)，Loop Guard 与 BPDU 缺失的关系见 [Cisco Loop Guard 说明](https://www.cisco.com/c/en/us/support/docs/lan-switching/spanning-tree-protocol-stp-8021d/218321-configure-stp-with-loop-guard-and-bpdu-s.html)。

### 3.1 从触发到恢复，三种保护状态也不同

以常见 Cisco 实现为例，以下是理解状态的模型，不是跨所有产品的操作指令：

| 保护 | 典型保护状态 | 恢复依据 |
| --- | --- | --- |
| BPDU Guard | 接口进入错误禁用等保护状态 | 按配置的恢复策略处理，不等于 BPDU 消失即自动恢复 |
| Root Guard | 对应生成树进入 root-inconsistent，阻止该方向参与转发 | 更优根信息不再持续，并满足相应状态条件 |
| Loop Guard | 对应生成树进入 loop-inconsistent，保留阻塞 | 恢复接收所需 BPDU 后按规则恢复 |

Root Guard 与 Loop Guard 的保护可关联到生成树实例，不应把所有状态都叫“整个物理端口关闭”。具体状态与恢复分别见 [Root Guard](https://www.cisco.com/c/en/us/support/docs/lan-switching/spanning-tree-protocol/10588-74.html) 和 [Loop Guard](https://www.cisco.com/c/en/us/support/docs/lan-switching/spanning-tree-protocol-stp-8021d/218321-configure-stp-with-loop-guard-and-bpdu-s.html)。

### 3.2 为什么收不到 BPDU 反而可能产生环路

设下游有两条冗余上联，其中一条因生成树选择保持阻塞。若该端口物理链路仍 Up，却因为单向故障或控制消息处理异常持续收不到 BPDU，旧的根信息可能老化。

危险点不是“消息少了”，而是设备可能把消息消失误认为原有拓扑约束消失，进而把冗余路径转为转发。Loop Guard 在适用端口上阻止这种错误转换。

UDLD 等单向链路检测关注邻接的双向通信，Loop Guard 关注生成树信息持续性，二者不完全替代。链路能发送部分业务帧，也不能证明控制交互双向健康。

## 4. 为什么不能给所有端口同时打开全部保护

交换机上联本来就需要接收 BPDU，把它当终端口执行 BPDU Guard，可能阻断正常拓扑交互。某些保护还对端口角色有不同要求，或在产品中互斥。

BPDU Filter 也不是 BPDU Guard 的更温和版本。过滤可能让设备失去发现环路所需的信息，而 Guard 是检测到违反角色预期后采取保护动作。

因此，功能越多不等于边界越清晰。需要解释每个端口允许什么控制消息，以及消息出现或消失分别代表什么。

## 5. Storm Control 能限速，不能修好拓扑

二层环路可能让广播、未知单播或组播反复传播。Storm Control（风暴控制）按设备能力对这些类别设置速率约束，限制影响扩大。

但它并不自动找到并切断所有环路。阈值过低，还可能抑制合法 DHCP、ARP、邻居发现或组播业务，导致新的接入异常。

百分比、包速率和比特速率是不同计量口径；采样窗口、突发容忍及超限动作也会影响行为。不能把某个阈值当作所有速率网口的通用安全值。

### 5.1 用两个算例理解阈值口径

如果某实现把阈值定义为端口带宽的 1%，则 1 Gbit/s 口对应约 10 Mbit/s，10 Gbit/s 口对应约 100 Mbit/s。同一个百分比不是同一个绝对流量门槛。

再设每秒 10000 个报文，暂只按给定报文长度计算，不计前导码、帧间隙等额外线速开销：

```text
64 字节/包：   10000 × 64 × 8   = 5.12 Mbit/s
1500 字节/包： 10000 × 1500 × 8 = 120 Mbit/s
```

所以按 pps 与按 bps 限制，会对小包、大包产生不同效果。设备还可能有测量粒度、恢复阈值、特殊控制帧豁免与不同超限动作，见 [Cisco Storm Control](https://www.cisco.com/c/en/us/td/docs/switches/lan/c9000/lyr2-fwd/flowcontrol-stormcontrol/flow-control-and-storm-control-configuration-guide/m-storm-control.html)。

例如一秒内总量不大，但集中在很短窗口的合法地址发现流量，也可能与具体计量机制发生冲突。风暴控制需要理解正常突发和异常放大，不能只依据全天平均值设阈值。

## 6. 端口隔离与 MAC 数量限制各自的边界

Port Security 等功能可以限制端口学习的 MAC 数量或允许集合，但 MAC 数量不是身份认证强度。一个合法 AP 后有很多客户端，也不意味着出现了异常交换机。

端口隔离、Protected Port 或 Private VLAN 则限制特定端口间的二层交付。不同实现的隔离范围可能是单台交换机、本 VLAN 或完整的私有 VLAN 模型，不能仅凭名称推断跨设备范围。

隔离了二层直通，也不自动禁止经网关路由的访问。若目标是禁止两个业务主体互访，仍需在真实路径上落实相应三层或应用策略。

### 6.1 Private VLAN 的三类端口怎样相互通信

PVLAN 在一个主 VLAN 关联的范围内进一步限制二层交付，终端可以处在同一 IP 子网，却不允许彼此直接通信：

| 来源端口 | 到 Promiscuous（混杂／公共服务口） | 到同一 Community（社区） | 到其他 Community | 到 Isolated（隔离端口） |
| --- | --- | --- | --- | --- |
| Isolated | 允许 | 不允许 | 不允许 | 不允许，包括另一个同类端口 |
| Community | 允许 | 允许 | 不允许 | 不允许 |
| Promiscuous | 按关联允许 | 按关联允许 | 按关联允许 | 按关联允许 |

表格只描述相应 PVLAN 的二层许可关系，不代表流量可以绕过所有 ACL 或应用权限。公共服务口通常连接网关或共享服务；“混杂”是该功能中的角色，不是抓包网卡混杂模式。

PVLAN 要求沿实际交换路径保留相应关联，不能假设一台设备上的普通 Protected Port 设置，会自动变为跨整个网络的隔离。机制和范围见 [Cisco PVLAN 说明](https://www.cisco.com/c/en/us/support/docs/lan-switching/private-vlans-pvlans-promiscuous-isolated-community/40781-194.html)。

如果网关允许接收一个终端的数据后再路由回另一个终端，二层禁止直接交付并不自动阻止这条三层路径；“不能相互访问”的目标还要落实到网关和业务策略。

## 7. LACP 与 STP 解决的也不是同一个问题

LACP 组织符合条件的链路成为逻辑聚合；STP 处理二层拓扑中的冗余与环路。链路聚合配置不一致，或者跨独立交换机却没有兼容的多机聚合机制，都可能偏离原先的单逻辑链路假设。

不要用“已经有聚合”推导出无需再考虑生成树、故障域与对端一致性。反过来，STP 也不能补全错误的聚合伙伴关系。

## 8. 思考与解答

**Loop Guard 因收不到 BPDU 阻塞端口，是不是反而降低可用性？**

它是在信息不足时避免把仍可能存在的冗余路径误放开。损失局部可用性与避免全网环路是明确取舍，不能仅靠“端口 Up 就转发”保证正确性。

**Root Guard 触发后，必须按 BPDU Guard 的错误禁用方式恢复吗？**

不是。常见实现中二者状态和恢复条件不同，要结合实例与具体设备解释，不能把所有保护都视作同一种关口。

**10 Gbit/s 网口设置 1% 阈值，与 1 Gbit/s 网口设置 1% 等价吗？**

相对比例相同，绝对门槛不同：在按端口带宽计算的示例中，分别约 100 Mbit/s 和 10 Mbit/s；实际还要考虑硬件计量粒度。

**PVLAN 中两个 Isolated 终端处于同一 IP 子网，就一定可以直接互通吗？**

不能。IP 子网相同不推翻二层隔离规则；经允许的网关绕行又是另一条路径，需要相应三层策略约束。

**BPDU Guard 与 Root Guard 都是防根桥变化，能随意互换吗？**

不能。前者约束不应出现 BPDU 的边界，后者允许正常交互但限制更优根信息改变根方向。

**风暴控制触发后流量下降，能认定环路已经解除吗？**

不能。它可能只是限制了流量，拓扑问题仍在，合法控制消息也可能受到影响。

**端口限制一个 MAC，就能适用于所有办公接入口吗？**

不能。电话级联、AP、虚拟化和其他多终端场景需要与实际拓扑一致的数量和身份模型。
