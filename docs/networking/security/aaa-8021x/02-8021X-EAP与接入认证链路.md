# 802.1X、EAP 与接入认证链路

终端尚未获准访问办公网时，为什么还能发送认证消息？802.1X 将认证所需的交互与普通业务访问分开，允许先验证，再按结果开放相应数据访问。

## 1. 三个角色分别是谁

| 角色 | 含义 | 常见实体 |
| --- | --- | --- |
| Supplicant（申请者） | 请求网络访问的一方 | 操作系统中的有线或无线认证客户端 |
| Authenticator（认证控制者） | 控制接入并承载认证交互 | 交换机、AP 或相应控制实体 |
| Authentication Server | 执行具体身份验证与策略判断 | 后端 EAP／AAA 服务 |

Authenticator 不等于一定在本地验证证书或密码。常见模式是它转运 EAP 消息，由后端执行认证方法。角色定义见 [IEEE 802.1X](https://1.ieee802.org/security/802-1x/)。

## 2. EAP、EAPOL、RADIUS 不是三种互斥认证方式

```text
终端                           接入设备                         后端服务器
EAP 方法消息 ── EAPOL ────────→ 转运／控制 ── RADIUS 携带 EAP ─→ 方法处理
             本地接入链路                         IP 网络
```

- **EAP**：可扩展认证框架，定义交互与方法承载，不等于某一种密码算法。
- **EAP Method**：执行具体认证，例如 EAP-TLS。
- **EAPOL**：EAP over LAN，在接入链路上承载相关控制交互。
- **RADIUS**：常用于接入设备与后端间搬运 EAP 并返回策略。

EAP 见 [RFC 3748](https://www.rfc-editor.org/rfc/rfc3748.html)，RADIUS 承载 EAP 的关系见 [RFC 3579](https://www.rfc-editor.org/rfc/rfc3579.html)。

这也解释了为什么终端没有 IP 地址时仍可先执行 802.1X：终端到接入设备的这一段不以终端先获得普通 IP 通信能力为前提。接入设备到后端则需要自己的可用 IP 路径。

## 3. Controlled Port 并非第二个物理网口

Controlled Port（受控端口）和 Uncontrolled Port（非受控端口）是逻辑访问模型：

- 认证与相关控制交互能够在普通业务未授权时进行。
- 普通业务是否被允许，取决于受控状态与策略。

“非受控”不表示任意业务包都可绕过安全策略。它是为指定认证与密钥管理协议保留的交互能力。

实际设备还可能提供认证前 ACL、访客网络等扩展，因此不能根据一个逻辑模型就断言所有型号在未授权时允许或禁止完全相同的报文。

## 4. 从链路建立到获得业务访问

常见过程可以抽象为：

1. 链路建立，或终端与 AP 建立相应无线关联。
2. 终端和接入设备开始 EAP 身份及方法协商。
3. 后端完成具体方法验证，可能包含多轮 Challenge。
4. 接入设备接收认证结果与授权信息。
5. 必要的密钥安装和策略执行完成，普通数据访问才进入相应授权状态。
6. 终端继续地址配置、名称解析和业务连接。

这是依赖模型，不保证所有操作系统严格串行执行同一启动顺序。有线和无线的链路密钥过程也不同，不能把 EAP Success 当成所有数据面工作已经完成。

## 5. 802.1X 本身不等于业务链路加密

802.1X 提供基于端口的访问控制，并能与密钥体系配合。无线企业认证可以由 EAP 导出密钥材料，再通过无线握手建立链路保护；有线链路若需要加密，则要结合适用的 MACsec 等机制。

所以“端口已经通过 802.1X”不能单独证明业务数据正在被加密，更不意味着应用已经获得端到端 TLS 保护。

## 6. MAB 和多主机模式为什么需要单独理解

MAB（MAC Authentication Bypass）常用于不具备 802.1X 能力的设备，由接入设备把观察到的 MAC 等信息交给后端匹配。它不提供与证书私钥证明同等强度的身份保证。

一个物理端口后还可能接电话、AP、下级交换机或多个终端。设备的 single-host、multi-host、multi-auth 等模式决定认证状态是如何关联到端口和各终端的，不能凭名称相似就认为安全边界相同。实现示例见 [Cisco MAB 指南](https://www.cisco.com/c/en/us/td/docs/solutions/Enterprise/Security/TrustSec_1-99/MAB/MAB_Dep_Guide.html)。

以常见实现为例，可以这样区分，但实际限制和违例动作仍应核对设备：

| 模式 | 典型含义 | 需要注意的边界 |
| --- | --- | --- |
| Single-host | 端口按单个数据终端建立接入关系 | 电话级联等场景可能需要独立的语音域处理 |
| Multi-host | 一个终端认证后，允许端口后的其他终端使用已开放接入 | 不代表每个终端都已独立证明身份 |
| Multi-auth | 同一物理端口上分别认证多个终端 | 不同终端的 VLAN、角色是否能独立执行，仍受设备能力约束 |

关键问题不是“允许几台设备”，而是新增终端是否需要独立认证，以及它会继承谁的权限。

## 7. 成功与失败要按边界解释

| 现象 | 需要分清的对象 |
| --- | --- |
| 终端无法开始认证 | 客户端能力、接口、EAPOL 与接入策略 |
| 接入设备收到 EAP，却没有后端结果 | 设备到服务器的网络、登记与消息保护 |
| 身份验证成功，但仍无地址 | 授权 VLAN、DHCP 链路与策略执行 |
| 有地址却无法访问业务 | 路由、ACL、DNS、应用权限，而非直接重做身份判断 |

这张表说明依赖关系，不把单个现象当成唯一根因。

## 8. 思考与解答

**终端没 IP，为什么 RADIUS 认证还能进行？**

终端通常通过 EAPOL 与接入设备交互，真正向 RADIUS 服务器发送 IP 请求的是接入设备，不一定是终端。

**EAP-TLS 与 EAPOL 是二选一吗？**

不是。前者是具体方法，后者是接入链路上的承载方式，可以出现在同一条认证链路中。

**给一台设备做了 MAB，就等于验证了它不可伪造的身份吗？**

不等于。MAC 匹配的身份强度有限，适用时还需限制权限并结合其他设备与接入信息。
