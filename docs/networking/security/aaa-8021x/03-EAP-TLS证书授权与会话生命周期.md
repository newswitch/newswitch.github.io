# EAP-TLS、证书授权与会话生命周期

证书认证的核心不是“客户端拿出一个证书文件”。公开证书可以被复制，真正的身份证明还涉及对应私钥的持有、信任链校验，以及证书身份能获得什么权限。

## 1. 谁验证谁

常见 EAP-TLS 场景中：

```text
终端验证认证服务器：信任链、预期服务身份、有效期等
认证服务器验证终端：客户端证书、私钥证明、用途与策略
验证成功后：把证书身份映射到授权主体和角色
```

在后端终止 EAP 的常见架构中，TLS 对端是终端与 EAP 服务器，AP／交换机主要搬运消息，并不意味着终端拿认证服务器证书来验证每一台 AP。

EAP-TLS 使用 TLS 1.3 的方法规范见 [RFC 9190](https://www.rfc-editor.org/rfc/rfc9190.html)。不能把某个旧系统只支持的 TLS 或证书参数当成协议永远不变的限制。

## 2. 有可信 CA，为什么仍需校验预期身份

CA 签发证书，表达的是证书中的主体和公钥绑定满足其签发规则。客户端还要确认这个主体是不是自己打算信任的认证服务。

如果只接受某个巨大信任集合中的任何证书，却不检查预期服务器身份，安全边界就比“只信任企业指定认证服务”更宽。类似地，证书用于服务器认证还是客户端认证、是否已经过期或撤销，也需要按用途验证。

私钥保护同样重要。证书有效期很长不能弥补私钥泄露；证书文件存在也不能证明终端可以完成私钥签名。

### 2.1 一次完整握手分别证明什么

以典型双向证书的 TLS 1.3 完整握手为例，省略分段、可选消息与封装：

| 阶段 | 主要内容 | 建立的依据 |
| --- | --- | --- |
| 参数协商 | ClientHello、ServerHello 等 | 协议能力、密码套件与密钥交换参数 |
| 服务器身份验证 | 服务器证书、CertificateVerify、Finished | 证书链与预期身份、私钥持有证明、握手完整性 |
| 客户端身份验证 | 按请求提供客户端证书与对应证明 | 终端主体、私钥持有和握手一致性 |
| 方法结束 | EAP-TLS 的受保护成功指示和 EAP 结果 | 本次方法按规则成功结束 |

CertificateVerify 不是“把私钥加密后发送”，而是对握手上下文作签名，验证者用证书公钥核对；Finished 则使用派生出的密钥验证握手上下文。证书链回答“是否信任该公钥与主体的绑定”，两类证明回答“当前参与者是否掌握相应秘密、交换是否一致”。TLS 机制见 [RFC 8446](https://www.rfc-editor.org/rfc/rfc8446.html)。

TLS 1.3 下握手证书消息受到握手密钥保护；但前置 EAP Identity 等信息并不因此全部隐身。EAP-TLS 1.3 还定义方法内受保护的成功指示，再完成相应 EAP 交互，不能把任意一条外部 EAP-Success 当成跳过证书验证的理由，见 [RFC 9190](https://www.rfc-editor.org/rfc/rfc9190.html)。

## 3. 证书身份不等于用户最终权限

假设证书表示一台受管电脑，而登录使用它的人可能属于不同部门。服务器可以把证书映射到设备记录，再结合用户、设备状态或策略决定角色。

需要区分：

| 信息 | 用途 |
| --- | --- |
| 外层 EAP Identity | 可能用于路由或选择认证域，不应直接当成最终强身份 |
| 已验证证书身份 | 提供经方法认证的主体依据 |
| 目录或设备记录 | 补充主体归属、启停与管理属性 |
| 授权策略 | 决定角色、VLAN、过滤和会话限制 |

证明“是谁”与决定“允许什么”必须连接起来，但不能合并成一个不可检查的黑盒。

## 4. EAP 导出的密钥和证书私钥不是同一个东西

成功方法可导出供后续接入保护使用的密钥材料。它不是把客户端证书私钥发给 AP，也不是让所有会话直接共用证书里的公开密钥做链路加密。

无线网络还需完成相应链路握手、派生和安装会话密钥。密钥缓存或会话恢复可以减少重复认证成本，但也需要限制生命周期和适用范围。

这解释了为何认证成功、无线握手完成和业务放行是相邻但不同的状态。

### 4.1 从证书到无线密钥，中间并不是一把密钥走到底

```text
长期证书与私钥：证明主体身份
  → EAP-TLS 会话：建立本次交互的密码学状态
  → MSK 等导出材料：提供给适用的下层接入机制
  → 无线 PMK 与四次握手：进一步派生、确认和安装链路会话密钥
  → 保护该链路上的数据
```

EAP 密钥框架区分 MSK（Master Session Key，主会话密钥）与 EMSK（Extended MSK，扩展主会话密钥）。适用架构中，MSK 可经受保护的 AAA 关系提供给认证控制者；EMSK 不能直接交给认证控制者，证书私钥更不能沿这条链分发。范围约束见 [RFC 5247](https://www.rfc-editor.org/rfc/rfc5247.html)。

因此 AP 可以获得完成链路保护所需的会话材料，而不必成为终端证书私钥的持有者。即使无线链路已加密，AP 之后的转发路径仍不由这把无线链路密钥提供端到端保护。

## 5. 授权属性必须落到设备能力上

服务器发回一个 VLAN 或角色，接入设备还需要能应用它。如果 VLAN 不存在、上联未承载，或下发过滤规则无法安装，就可能出现身份验证成功但业务不可用。

动态改变 VLAN 还会影响地址上下文：终端之前持有的 IP、默认网关和 DHCP 租约未必适合新网络。不能以为改了授权属性，原有连接一定能不间断继续。

完整关系是：

```text
方法验证 → 生成策略 → 设备接受策略 → 数据面执行 → 网络配置适配 → 业务通信
```

## 6. 已经在线，为什么还会重新认证

会话可以因超时、链路变化、漫游、策略更新或管理员动作重新评估。服务器和设备需要用会话标识关联当前主体，而不能只凭可能已变化的 IP。

RADIUS CoA（Change of Authorization，授权变更）允许后端请求修改已有会话，Disconnect 用于请求终止会话，见 [RFC 5176](https://www.rfc-editor.org/rfc/rfc5176.html)。

请求发出不等于设备已经执行。设备可能确认、拒绝或不支持某属性，也可能找不到匹配会话。CoA 交互本身同样需要可信来源与消息保护，不能让设备无条件接受任意来源的授权变更。

### 6.1 会话恢复节省什么，又依赖什么

TLS 1.3 会话恢复可使用先前建立的 Ticket／PSK 关联，减少完整证书交换的开销。恢复成功证明的是与先前受认证状态的关联，不代表每次都重新传输了整条证书链，也不代表权限可以永久沿用。

例如设备之前属于研发部门，现在已调入隔离组：即使旧票据尚可用，授权依据变化也需要重新评估。若无法安全恢复必要的身份和授权上下文，应拒绝恢复并回到完整握手，而不是只凭“缓存命中”放行。EAP-TLS 恢复与授权重新评估要求见 [RFC 9190](https://www.rfc-editor.org/rfc/rfc9190.html)。

### 6.2 CoA 的确认与业务切换为什么不能画等号

后端首先需要定位目标 NAS 与会话，再表达属性变更或终止请求。只按 IP 匹配容易混入地址复用、漫游或并发会话，不能替代完整的会话定位。

对于成功的 CoA-ACK，应按协议及设备实现理解为相应授权变更被接受并处理；它并不额外证明客户端已经重新获取地址、旧连接已迁移、所有业务验证都完成。CoA-NAK 则表示未能按请求完成处理，并可能给出错误原因。动态授权语义见 [RFC 5176](https://www.rfc-editor.org/rfc/rfc5176.html)。

例如 VLAN 从办公网改为隔离网，即使交换机已经完成变更，终端继续使用旧子网地址，也可能暂时不能通信。这不是简单的“CoA 没生效”，而是授权变化之后的网络配置尚未适配。Disconnect 是终止现有会话的请求，也不保证终端一定立即开始并成功完成新认证。

## 7. 证书、时间和离线依赖

证书有效期依赖可信时间，撤销检查依赖证书策略与相应状态来源。证书链不完整、时钟偏差、私钥不可用与用户被禁用，都是不同的失败原因。

初次接入时，还要考虑终端是否能在未授权网络中获得认证所需的最小依赖。不能无条件假设“先联网下载所有依赖，再通过唯一的联网认证”不会产生启动依赖循环。

认证服务器不可达时，是保留已授权会话、给受限角色，还是拒绝新接入，需要事先定义。不可达不等于证书验证失败；服务器恢复后如何退出降级状态，也是会话机制的一部分。

### 7.1 撤销证书不等于即时删除所有已授权状态

证书撤销、票据缓存、NAS 会话超时、动态授权和无线密钥寿命是不同时间线。认证服务获知撤销，可能影响后续完整握手或恢复判断，但既有会话何时失效，还需要会话撤销或重新评估机制配合。

同理，CRL／OCSP 状态暂不可得，与得到明确撤销结果也不相同。是否允许使用仍有效的缓存状态、是否拒绝新认证，必须按安全策略定义；把网络超时当成“证书肯定有效”会丢掉验证边界。

## 8. 思考与解答

**AP 没有客户端证书私钥，为什么仍能与它建立无线加密链路？**

证书私钥用于身份验证；接入链路使用 EAP 导出并按范围交付的会话材料，再经无线握手派生密钥。不是所有阶段共用同一把私钥。

**恢复握手没有重新发送证书，就说明本次认证被绕过了吗？**

不能仅凭没有证书交换下结论。合法恢复依靠先前状态关联与 PSK 证明，但必须保留安全的身份和授权上下文，并处理策略变化。

**CoA-ACK 已收到，终端为什么还持有旧网段 IP？**

授权变更与客户端地址配置是不同状态机。交换机可能已经切换 VLAN，终端却还没有更新 DHCP 配置；ACK 不承诺现有业务连接无缝迁移。

**证书撤销后，所有已在线终端会在同一秒断开吗？**

不会天然如此。撤销状态传播、缓存、会话超时及主动终止各有时序；需要区分后续认证拒绝与现有权限回收。

**复制一份公开客户端证书就能完成 EAP-TLS 吗？**

不能。正常认证还需要证明持有对应私钥，并满足服务端的信任与授权规则。

**CoA 已经发出，就能证明用户权限改好了么？**

不能。还要区分设备确认、策略安装、会话匹配和实际数据面执行。

**证书合法，但设备被资产系统停用，是否仍应自动允许接入？**

不应只凭证书签名决定。证书证明身份，是否继续授权还取决于有效的主体状态和访问策略。
