# AAA、RADIUS、TACACS+ 与设备管理

管理员能够通过 SSH 建立加密连接，不意味着他已经被允许修改交换机配置。SSH 保护管理连接，AAA 则参与判断身份与权限；二者解决不同层面的问题。

## 1. 三个 A 各回答什么

| 能力 | 问题 | 例子 |
| --- | --- | --- |
| Authentication（认证） | 你是谁，如何证明 | 用户凭据或设备证书验证 |
| Authorization（授权） | 你可以做什么 | 只读角色、命令权限、接入 VLAN |
| Accounting（记账／审计） | 发生了什么会话活动 | 登录时间、退出原因、相应操作记录 |

认证成功但授权不足时，允许登录却拒绝配置命令是合理结果。Accounting 也不等于付费计费，它可以服务于会话追踪与审计。

## 2. 谁真正向 AAA 服务器发请求

```text
管理员 ─SSH→ 网络设备
               └─ AAA 请求 → 认证／授权服务器
               ← 结果与策略 ─┘
设备在本地执行允许或拒绝
```

对 RADIUS 而言，交换机、AP、VPN 网关等通常扮演客户端／NAS（Network Access Server）角色；终端用户并不一定直接使用 RADIUS 与服务器通信。

因此“用户客户端”“RADIUS 客户端”“NAS”不能只按中文里的客户端三个字混为一谈。授权决定返回后，真正限制端口或命令的通常还是网络设备。

## 3. RADIUS 把身份与接入属性联系起来

RADIUS 常见认证交互包括 Access-Request、Access-Challenge、Access-Accept 和 Access-Reject。Challenge 可用于多轮认证，不表示请求已被拒绝。

Accept 可以携带会话参数或授权属性，例如角色、VLAN、过滤策略或超时。设备是否理解、是否具备资源应用这些属性，是另一项检查。[RFC 2865](https://www.rfc-editor.org/rfc/rfc2865.html) 描述了基础认证交互。

传统部署常见 UDP 1812 认证与 UDP 1813 记账，但 RADIUS 并非只能使用 UDP，存在 TCP/TLS 等传输方案。端口可达只证明传输的一部分，不证明客户端登记、共享秘密、消息校验或认证方法一致。

### 3.1 报文标识、认证状态与接入会话不是一个 ID

基础 RADIUS 报文头有 Code、Identifier、Length 和 Authenticator，后面携带属性。Identifier 只有一个字节，用于一定传输上下文内的请求响应匹配，不是全球唯一用户 ID，也不能长期唯一标识一次接入。

| 对象 | 作用 | 不应混淆为 |
| --- | --- | --- |
| 报文 Identifier | 匹配一次请求和响应 | 长期接入会话标识 |
| State 属性 | 在多轮认证中把后续回答关联回服务器上下文 | 客户端可自行解释修改的角色名 |
| Class 属性 | 服务器交给 NAS、供后续记账原样带回的不透明信息 | 通用 VLAN 或权限等级属性 |
| Acct-Session-Id | 关联某个接入记账会话 | 单独就能跨所有 NAS 永久唯一的键 |

State 与 Class 的语义见 [RFC 2865](https://www.rfc-editor.org/rfc/rfc2865.html)，接入会话记账见 [RFC 2866](https://datatracker.ietf.org/doc/html/rfc2866)。属性的名字很像“状态、类别”，不代表能按日常中文含义随意赋值。

例如服务器返回 Challenge 并携带 State，NAS 把后续回答与该 State 关联后再次提交。若把请求负载分到另一个没有相应状态的认证实例，多轮交互可能失败，即使两台都能完成独立的普通登录。

## 4. TACACS+ 为什么常见于设备管理

TACACS+ 将认证、授权和记账设计为较明确分离的交互，常用于设备管理中的命令授权与操作审计。传统传输使用 TCP 49，协议描述见 [RFC 8907](https://www.rfc-editor.org/rfc/rfc8907.html)。

不要把对比简化为“RADIUS 只能控制接入，TACACS+ 一定支持任何命令”。最终能力还依赖设备如何接入授权、命令解析和角色模型。

例如某设备支持会话级角色，却不支持逐命令远端校验；即使服务器保存了精细策略，也不能凭空在设备数据面生效。

### 4.1 沿一次管理员操作区分三个判断

假设管理员已建立 SSH 连接，要执行一个查看命令，再进入配置：

1. 认证交互确认管理员身份，可能经过多轮提示和回答。
2. 会话授权决定是否允许建立相应 Shell、获得何种角色。
3. 若设备启用且支持逐命令授权，提交命令及参数等上下文，判断本次操作是否允许。
4. 设备执行允许的动作，再按记账配置上报相应活动。

因此“密码正确但配置命令被拒绝”可以是正常授权结果。设备有没有逐命令调用、哪些命令触发调用、记账是否包括执行结果，要分别确认，不能用一次认证成功代替所有后续判断。TACACS+ 的交互分离见 [RFC 8907](https://www.rfc-editor.org/rfc/rfc8907.html)。

## 5. 传统报文保护不能当成现代 TLS

RADIUS 的传统机制并不加密整个报文；TACACS+ 传统报文体保护也不等于现代、独立认证的安全传输。不能用“有共享秘密”推导出可以放心经过任意不可信网络。

部署应区分管理网络隔离、协议消息完整性和传输层保护。TACACS+ over TLS 1.3 已由 [RFC 9887](https://www.rfc-editor.org/rfc/rfc9887.html) 定义，但是否可用仍需确认双方产品实现，不能因为标准存在就断言旧设备支持。

同样，选用了安全传输，不代表服务器策略、账户生命周期和审计存储就自动正确。

## 6. Reject 与服务器不可达不是同一个失败

| 情况 | 可以确认的事实 | 不应自动推导的动作 |
| --- | --- | --- |
| 明确 Reject | 服务器处理了请求并拒绝 | 不应默认为可绕过认证 |
| Timeout | 在窗口内未得到有效响应 | 不能断定密码错误 |
| Accept 但属性应用失败 | 身份或策略返回成功，设备执行存在问题 | 不能当作端到端授权成功 |

设备的回退策略应明确区分这些情况。服务器暂时不可达时采用本地账户、受限权限或拒绝接入，是业务与安全边界选择，不是 AAA 协议替管理员统一决定的事情。

尤其不应把“认证失败”无条件等同于“试一个更弱的方法并放行”。否则严谨的主认证可能被回退路径抵消。

### 6.1 回退需要按阶段定义

认证服务器超时后允许受限本地账户，并不意味着命令授权服务器超时也必须放开全部配置。认证、会话授权、命令授权和记账，可以有不同可用性要求及失败策略。

例如允许一个已经证明身份的只读会话继续查看状态，同时拒绝新的写操作，是一种边界选择；把所有失败都映射为“允许”，则会让远端拒绝和远端不可达失去区别。设备方法列表、缓存和降级语义各不相同，不能把某产品的回退规则推广成协议规定。

还要区分“新会话如何进入”和“旧会话何时撤销”：服务器失联不会自动让所有已授权会话同时消失，也不会自动证明它们应无限期保留权限。

## 7. 审计能证明什么

会话开始、周期更新和结束记录有助于回答“哪个身份在什么设备上获得过什么会话”。网络中断可能使结束记录缺失，重传也可能带来需要关联或去重的记录。

这些记录需要会话标识、设备身份和可信时间配合，不能只按用户名或 IP 拼接。IP 会变，终端会漫游，管理员也可能同时登录多台设备。

若要求命令审计，还要确认设备到底上报了哪些命令、是否包括结果，而不是只看服务器上出现一条登录成功记录。

### 7.1 一条会话记录怎样被拼完整

考虑同一 NAS 上一次会话的 Start、多个 Interim-Update 与 Stop。网络中断可能丢失 Stop，确认丢失可能导致同一事件重传，因此“收到多少条记录”不等于“发生多少次独立登录”。

关联至少要考虑 NAS 身份与会话标识，再结合记录类型、时间及重启上下文。相同用户名可能有并发会话，同一个 IP 也可能先后属于不同终端；仅按其中一个字段合并，容易把两次活动拼成一次。

记账接收端还要区分事件发生时间与服务器收到记录的时间。延迟投递和补报可以改变到达顺序；缺失结束记录只表示观测不完整，不能证明用户一直在线。基础记账交互见 [RFC 2866](https://datatracker.ietf.org/doc/html/rfc2866)。

## 8. 思考与解答

**RADIUS Identifier 一样，就说明是同一个用户会话吗？**

不是。它用于报文交换匹配，取值范围有限，会复用；接入会话需要用 NAS、会话标识和相应上下文关联。

**返回 Class 为某个字符串，交换机就会按字符串设置角色吗？**

不能这样理解标准 Class。它是不透明的记账关联信息，不是通用角色属性；授权需要设备明确支持的属性和策略语义。

**登录认证已经通过，命令授权超时就应继续执行吗？**

不是协议自动给出的结论。身份已经确认不等于本次写操作获准，失败策略必须按授权阶段和风险定义。

**Stop 没收到，可以断定会话仍在线吗？**

不能。结束事件或确认可能丢失，NAS 也可能重启。需要结合周期记录和会话状态解释，不能把审计缺口当成持续在线证据。

**SSH 登录成功，就证明远端授权服务器正常吗？**

不一定。设备可能使用本地认证、缓存或回退路径；需要明确本次会话实际走了哪种身份与授权来源。

**服务器发了 Accept，为什么终端还可能没有业务权限？**

授权属性可能不被设备支持，或者 VLAN、ACL 等无法成功应用。返回策略与执行策略是两件事。

**TACACS+ 和 RADIUS 可以仅凭端口号互换吗？**

不能。它们的报文、会话与授权模型不同，需要两端明确支持对应协议和安全传输方式。
