# TLS 1.3 完整握手与密钥派生

本章跟踪一个没有 PSK、没有客户端证书的 TLS 1.3 完整握手。目标不是只记消息顺序，而是理解每条消息怎样改变双方状态。

## 1. 报文时序

![TLS 1.3 完整握手](/img/networking/tls-pki/tls13-handshake.svg)

```text
Client                                               Server
  |                                                     |
  | ClientHello                                         |
  | supported_versions, cipher_suites,                  |
  | key_share, signature_algorithms, SNI, ALPN          |
  |---------------------------------------------------->|
  |                                                     |
  |                                  ServerHello        |
  |                     selected_version/cipher/keyshare|
  |<----------------------------------------------------|
  |       双方计算 ECDHE Shared Secret 与 Handshake Keys |
  |                                                     |
  |                     {EncryptedExtensions}           |
  |                     {Certificate}                   |
  |                     {CertificateVerify}             |
  |                     {Finished}                      |
  |<====================================================|
  | 验证证书链、主机名、签名与 Finished                  |
  |                                                     |
  | {Finished}                                          |
  |====================================================>|
  |       双方切换到 Application Traffic Keys            |
  |                                                     |
  | {HTTP / Application Data}                           |
  |<===================================================>|
```

花括号表示已由 TLS 记录层加密保护。

## 2. TCP 之前与之后

传统 HTTPS 需要先完成 TCP 三次握手，再发送 ClientHello。若无连接复用：

```text
1 RTT：TCP 建连
1 RTT：TLS 1.3 完整握手到客户端可发送应用数据
```

真实耗时还包含 DNS、排队、重传、证书验证和服务端处理。HTTP/3/QUIC 的传输与 TLS 1.3 握手结合，不能直接套用 TCP 轮次图。

## 3. ClientHello

关键字段和扩展：

| 内容 | 作用 |
| --- | --- |
| `legacy_version` | 兼容旧设备，不是最终版本选择 |
| `random` | 本次握手随机值 |
| `cipher_suites` | 客户端支持的 TLS 1.3 AEAD/Hash 组合 |
| `supported_versions` | 声明支持 TLS 1.3、1.2 等版本 |
| `supported_groups` | 支持的密钥交换组 |
| `key_share` | 已生成的临时公钥份额 |
| `signature_algorithms` | 可验证的握手签名方案 |
| `server_name` | SNI，期望访问的服务名 |
| `application_layer_protocol_negotiation` | ALPN，如 `h2`、`http/1.1` |

SNI 用来帮助同一地址上的服务选择证书和虚拟主机，但证书验证仍以客户端访问名称与证书 SAN 为准。

## 4. ServerHello

服务端选择：

- TLS 版本；
- Cipher Suite；
- Key Share Group；
- 对应的服务端临时公钥。

双方把本地临时私钥和对端临时公钥输入 ECDHE，得到相同共享秘密。此时可以派生握手流量密钥，后续握手消息开始加密。

如果客户端没有提供服务端可接受的 Key Share，但存在共同 Supported Group，服务端可能发送 HelloRetryRequest，要求客户端重新提供指定组的 Key Share。它增加一次往返，常见于曲线或混合后量子组策略不一致。

## 5. EncryptedExtensions

服务端把不属于 ServerHello、又与连接协商有关的扩展放在这里，例如最终 ALPN。客户端若要求 `h2` 而服务端选择 `http/1.1`，应用层随后必须按服务端选择工作。

## 6. Certificate

服务端通常发送：

```text
Leaf Certificate
Intermediate CA Certificate 1
Intermediate CA Certificate 2（如需要）
```

一般不发送根 CA，因为客户端应预先拥有并信任根证书。客户端需要完成：

1. 构造并验证签名链；
2. 检查当前时间是否在有效期内；
3. 检查 SAN 是否匹配目标主机名或 IP；
4. 检查 Basic Constraints、Key Usage、EKU 和算法策略；
5. 按本地策略处理吊销和名称约束。

证书链可信还不代表对端持有叶子证书私钥，下一条消息负责证明。

## 7. CertificateVerify

服务端用叶子证书对应私钥签署包含上下文字符串和 Transcript Hash 的结构。客户端用证书公钥验证：

```text
证书链 → 公钥属于目标身份
CertificateVerify → 当前对端持有私钥，并将身份绑定到本次握手
```

攻击者不能把别处抓到的证书链直接放进当前会话，因为没有私钥就无法生成有效签名。

## 8. Finished

Finished 使用从握手秘密派生的 Finished Key 对 Transcript Hash 计算验证值。它证明：

- 对端掌握本次握手秘密；
- 双方看到的握手历史一致；
- 版本、算法、Key Share、证书等没有被静默篡改。

客户端验证服务端 Finished 后发送自己的 Finished。之后双方使用应用流量密钥发送数据。

## 9. 密钥计划

![TLS 1.3 密钥派生](/img/networking/tls-pki/tls-key-schedule.svg)

简化的 TLS 1.3 Key Schedule：

```text
PSK 或全零输入
      │
      ▼
Early Secret
      │ Derive-Secret
      ▼
ECDHE Shared Secret ──HKDF-Extract──> Handshake Secret
                                      ├─ client_handshake_traffic_secret
                                      └─ server_handshake_traffic_secret
                                                   │
                                                   ▼
                                            Handshake Keys/IVs

Handshake Secret ──派生──> Master Secret
                           ├─ client_application_traffic_secret_0
                           ├─ server_application_traffic_secret_0
                           ├─ exporter_master_secret
                           └─ resumption_master_secret
```

每个方向、每个阶段使用不同秘密。`KeyUpdate` 可以继续派生后续应用流量秘密。

## 10. 客户端认证插在哪里

mTLS 中，服务端在 Certificate 前发送 CertificateRequest。客户端在自己的 Finished 前发送：

```text
Certificate
CertificateVerify
Finished
```

服务端需要验证客户端证书链、用途、身份映射和私钥签名。握手认证成功后，应用授权仍要单独执行。

## 11. 失败定位表

| 最后可见阶段 | 优先检查 |
| --- | --- |
| TCP 没成功 | DNS、路由、ACL、监听、连接队列 |
| ClientHello 后无响应 | SNI、协议识别、中间设备、服务端日志 |
| 收到 Alert | Alert 描述、双端版本和算法策略 |
| ServerHello 后失败 | 加密握手、证书、签名、Finished；结合 Key Log |
| TLS 成功后立即 4xx/5xx | HTTP Host、路由、认证、应用，不再是握手问题 |

## 12. 练习与答案

**问题 1：** 服务端什么时候可以开始加密握手消息？

双方处理 ServerHello 并利用 Key Share 计算共享秘密、派生握手流量密钥之后。

**问题 2：** 证书签名和 CertificateVerify 是不是重复？

不是。CA 对证书签名证明公钥与身份声明的绑定；CertificateVerify 证明当前连接对端实际持有该公钥对应私钥，并绑定本次握手。

**问题 3：** 为什么服务端通常不发送根 CA？

根 CA 是客户端本地的信任锚。由服务端发送根证书不能自动让客户端信任它，发送还会增加链长度。
