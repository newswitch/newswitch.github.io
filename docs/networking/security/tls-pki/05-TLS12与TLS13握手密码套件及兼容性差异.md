# TLS 1.2 与 TLS 1.3 的握手、密码套件及兼容性差异

TLS 1.3 不是简单删除旧算法。它重构了握手、密钥派生和 Cipher Suite 语义，因此相同名称的配置项在不同版本中可能控制不同对象。

## 1. 完整握手对比

TLS 1.2 常见 ECDHE 握手：

```text
ClientHello                         →
                                    ← ServerHello
                                    ← Certificate
                                    ← ServerKeyExchange
                                    ← ServerHelloDone
ClientKeyExchange                   →
ChangeCipherSpec + Finished         →
                                    ← ChangeCipherSpec + Finished
Application Data                   ⇄
```

TLS 1.3：

```text
ClientHello + KeyShare              →
                                    ← ServerHello + KeyShare
                                    ← {EncryptedExtensions}
                                    ← {Certificate}
                                    ← {CertificateVerify}
                                    ← {Finished}
{Finished}                          →
{Application Data}                 ⇄
```

TLS 1.3 客户端在首个 ClientHello 中提前发送 Key Share，服务端在首个往返即可完成密钥协商。若需要 HelloRetryRequest，则会增加往返。

## 2. Cipher Suite 语义变化

TLS 1.2：

```text
TLS_ECDHE_RSA_WITH_AES_128_GCM_SHA256
    │      │          │        └─ PRF/Hash
    │      │          └─ Record AEAD
    │      └─ 服务端认证算法
    └─ 密钥交换
```

TLS 1.3：

```text
TLS_AES_128_GCM_SHA256
        │         └─ HKDF Hash
        └─ Record AEAD
```

密钥交换组和签名方案改由 `supported_groups`、`key_share` 与 `signature_algorithms` 独立协商。配置 TLS 1.3 时要分别检查 Cipher、Group 和 Signature Algorithm。

## 3. 删除或限制的旧机制

TLS 1.3 不再使用：

- 静态 RSA Key Exchange；
- 静态 DH/ECDH 密钥交换；
- CBC Record Cipher；
- RC4、3DES 等旧算法；
- SHA-1 握手签名；
- 压缩；
- Renegotiation。

TLS 1.3 正常 (EC)DHE 握手具备前向保密。TLS 1.2 是否具备，要看实际选择的套件，不能只看版本号。

## 4. 加密开始得更早

TLS 1.2 中证书等消息通常明文可见；TLS 1.3 在 ServerHello 后派生握手密钥，Certificate、CertificateVerify 和 Finished 都被保护。抓包缺少证书明文不代表服务端没有发送证书。

## 5. 恢复机制变化

TLS 1.2 有 Session ID 和 Session Ticket 等机制；TLS 1.3 将恢复统一到 PSK 模型，服务端通过 NewSessionTicket 提供后续连接使用的凭据。PSK 可以与新的 (EC)DHE 结合，以恢复性能同时保留新的前向保密贡献。

## 6. 版本协商与降级保护

TLS 1.3 使用 `supported_versions` 扩展进行真实版本选择，Record/ClientHello 的 legacy version 字段可能显示旧版本兼容值。只看抓包某个 `0x0303` 字段就断言连接是 TLS 1.2，可能得出错误结论。

TLS 1.3 还定义降级哨兵，帮助支持高版本的服务端在异常降级时被客户端发现。但它不能修复不安全的客户端策略；禁用证书验证或允许过旧版本仍然危险。

## 7. 生产兼容策略

常见公共服务可以考虑允许 TLS 1.2 和 1.3，同时：

- TLS 1.2 只允许 ECDHE + AEAD 等合适组合；
- TLS 1.3 使用实现提供的安全默认值并审查组织策略；
- 通过真实客户端清单确认最低版本，而非凭感觉打开 TLS 1.0；
- 单独测试 Java、OpenSSL、浏览器、SDK、代理和硬件负载均衡器；
- 监控协商版本、套件和失败率，分阶段淘汰旧客户端。

内部系统若全部可控，可以收紧到 TLS 1.3，但应先验证服务网格、数据库驱动、探针和旁路设备。

## 8. OpenSSL 验证

```bash
openssl s_client -connect example.com:443 \
  -servername example.com -tls1_2 </dev/null

openssl s_client -connect example.com:443 \
  -servername example.com -tls1_3 </dev/null
```

关注：

```text
Protocol
Cipher
Peer certificate
Verification error / Verify return code
ALPN protocol
```

“命令成功建立 TCP”不等于证书验证成功，必须读取验证结果；自动化脚本建议显式使用 `-verify_return_error` 和目标主机名校验参数。

## 9. 练习与答案

**问题：** 为什么 Nginx 的 `ssl_ciphers` 修改后，TLS 1.3 套件可能没有变化？

因为不少实现把 TLS 1.2 及以前的 Cipher List 与 TLS 1.3 Ciphersuites 分开配置。必须以具体 Nginx/OpenSSL 版本和指令行为为准。

**问题：** TLS 1.2 一定不具备前向保密吗？

不一定。选择 ECDHE/DHE 密钥交换时可以具备；旧静态 RSA Key Exchange 不具备。
