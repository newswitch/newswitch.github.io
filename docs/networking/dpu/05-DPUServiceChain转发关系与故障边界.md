# DPUServiceChain 转发关系与故障边界

创建一条服务链不等于创建了整条业务处理逻辑。服务链描述接口之间怎样转发，服务应用仍要处理自己内部的包。本文沿用 [DPF 控制对象](./04-DPF控制对象与DPU生命周期.md)的 **26.4.0** 基线，重点解释这一职责边界。

## 1. 从声明到节点转发还有多层对象

Host 集群中的 DPUServiceChain 经控制器形成 DPU 集群的 ServiceChainSet，再按节点产生 ServiceChain，最终由 SFC 控制器配置节点网络。DPUServiceInterface 则把被引用的接口纳入这个对象模型。参见 [DPUServiceChain 官方说明](https://networking-docs.nvidia.com/dpf/26.4.0/dpuservicechain)。

因此只看到最上层 CR 已创建，不足以说明每台 DPU 都安装了相应配置。应该沿对象身份、选择器、目标节点和条件向下追踪，再用数据面证据收尾。

## 2. 外部接线不负责应用内部处理

用一个教学服务表示路径：

```text
外部端口 p0 → 服务入口 eth1 → [服务内部处理] → 服务出口 eth2 → Host 侧端口
```

服务链可以表达两端接线，却不自动把 eth1 收到的包变成 eth2 发出的包。中间可能是防火墙、加密、隧道、负载均衡或用户程序；其策略、状态和转发逻辑由服务承担。这也是上述官方示例特别强调的边界。

如果入口计数增长、出口没有变化，至少有两个假设：服务没有正确处理，或出口绑定错误。先对照服务内部计数、日志和接口映射，不能直接认定物理链路损坏。

## 3. 名称相同，不表示接口身份相同

`p0`、Host PF、Representor 和 Pod 内的 `eth1` 处于不同上下文。名字要连同 DPU、节点、namespace、接口类型与对象 owner 一起解释。标签选择器表达的是对象集合，也不是天然唯一主键。

26.4.0 文档要求：物理 uplink 的归属不能冲突，服务链中的接口选择器在每个目标节点上应解析到唯一接口。零匹配和多匹配都可能使协调失败，这类冲突并不一定在 API 接收时被拒绝。

一个典型反例是两个控制入口都为同一物理端口创建接口。即使标签不同，底层端口仍只有一份实际归属，可能出现一条链就绪、另一条反复失败。若标签也相同，选择器还可能命中多个对象。正确动作是厘清权威配置和所有权，而不是反复改标签碰运气。

## 4. 一张逐跳证据表比一个 Ready 更有用

| 层次 | 需要证明的事实 | 无法单独证明的事 |
| --- | --- | --- |
| DPUServiceChain | 目标配置被接收并协调 | 每条物理链路都健康 |
| ServiceChainSet / ServiceChain | 目标 DPU、节点与规则配置一致 | 应用内部处理正确 |
| 接口与规则计数 | 指定测试流确实命中预期路径 | 所有租户流量都正确 |
| 服务入口与出口 | 应用接收、处理并发出 | 外部网络无丢包 |
| 端到端业务 | 当前测试满足正确性和性能要求 | 后续更新永不受影响 |

计数要比较同一时间窗口的增量，排除后台流量；如果测试期间发生重启或计数清零，应重新建立基线。总计数增加不能直接证明你发出的那条流已通过。

## 5. MTU 改动为什么属于路径变更

DPF 26.4.0 的 serviceMTU 有自身上限和影响范围，变更可能重启关联 Pod，具体行为见服务链文档。它不是只修改仪表盘上的一个数字。

教学上，若入口允许 9000 字节帧而某段路径只接受 1500，还需考虑隧道额外开销与不同协议的分片行为。小包测试成功、大消息失败，并不能说明规则完全正确；同样也不能仅凭现象断言一定是 MTU。

应对照外部网络、DPU 接口、服务内部与 Host 侧的有效 MTU，再检查丢弃计数及受控报文。不要一次性全网提高 MTU；先确认最小路径能力、变更作用面和回退方式。

## 6. 关键服务失效与 Host 准入不是同一动作

DPF 可以根据关键服务就绪状态影响关联 Host 节点的调度准入，具体配置见 [DPUService](https://networking-docs.nvidia.com/dpf/26.4.0/dpuservice)。26.4.0 文档描述的机制使用 NoSchedule taint：它不主动驱逐既有 Pod，有相应容忍设置的工作负载也不能仅凭该 taint 就保证被拦截。文档还说明该机制采用周期协调而非即时触发，因此存在检测与准入之间的时间窗口，不能把它当成实时故障熔断器。

因此故障分析要分别记录新任务是否被阻断、旧任务是否仍运行，以及旧连接是否仍有正确转发。把“节点已被标记”当成“故障影响已经消除”，会漏掉仍在运行但业务异常的工作负载。

## 7. 掌握检查

解释入口 eth1 到出口 eth2 为什么仍需要应用逻辑；给一个双接口冲突画出对象与物理端口映射；说明上层 Ready 不能替代哪些逐跳证据。最后设计小包与大包的对照观察，写出哪些结果支持 MTU 假设，哪些结果会否定它。
