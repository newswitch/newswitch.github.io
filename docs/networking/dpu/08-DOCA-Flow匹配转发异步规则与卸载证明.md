# DOCA Flow 匹配转发异步规则与卸载证明

DOCA 服务部署之后，还要证明业务包实际经过所需处理。DOCA Flow 是理解这种证明的一个具体入口：它用 API 定义硬件匹配与动作，但 API 接受请求、规则安装完成、包命中规则与业务正确仍然是四种状态。

本篇固定 DOCA 3.5.0 的公开 API 契约，不把闭源驱动或硬件内部实现写成源码结论。前置阅读为[Representor 与控制边界](./01-BlueField工作模式Host与Arm管理边界.md)，DPF 外部接线另见[服务链](./05-DPUServiceChain转发关系与故障边界.md)。

## 1. Pipe 是模板 Entry 是具体规则

Pipe 描述匹配结构、可用动作、监视和转发目标，Entry 将具体匹配值及动作实例化。转发目标可以是另一个 Pipe、端口、软件队列或丢弃；选择取决于业务设计与目标能力。[DOCA Flow 指南](https://networking-docs.nvidia.com/doca/archive/3-5-0/doca-flow)定义了这些对象。

教学例子：Pipe 模板允许匹配某入口的 IPv4/TCP 目的端口；一条 Entry 匹配端口 443 并转发到服务入口。创建模板不会自动匹配所有 TLS 流，更不等于执行了 TLS 解密；应用需要什么处理，必须由相应动作和服务实现。

同样，服务链把接口连起来，不会自动创建应用内部的全部策略。需要区分外部连接、Flow 规则和服务处理，避免把三个不同的配置权威混在一起。

## 2. Miss 是策略 不是单一错误

没有命中时，可能进入另一个 Pipe、软件处理或丢弃；具体行为由模式、域和 Miss 配置决定。不能把所有 Miss 都解释为故障，也不能默认 Miss 流量会安全地继续转发。

```text
输入包 → 匹配硬件规则 → 动作与目标端口
                 ↓ 未命中
             配置的 Miss 路径
                 ↓
          软件检查、继续匹配或丢弃
```

安全策略应检查默认路径。若希望只允许一组租户流量，却把未命中包送到一个不执行同样授权的软件路径，硬件规则存在也不能证明隔离有效。

## 3. 为什么返回句柄不等于已经卸载

3.5.0 的 `doca_flow_entries_process()` 推进队列中的操作，完成状态通过回调或相应查询获得；查询只报告已知状态，不替代推进。删除请求也有异步生命周期，不能在句柄失效后继续访问。[异步完成契约](https://networking-docs.nvidia.com/doca/archive/3-5-0/doca-flow)是理解这一点的依据。

用教学状态表示：

```text
请求被接受 → 操作在途 → 完成状态已知
                         ├── 安装成功 → 可验证命中
                         └── 失败 → 按接口契约清理与报告
```

这些是解释阶段，不是 API 枚举的逐字清单。批量请求中，队列处理完成不应被误写成每条规则都成功。自动化需要保留每个操作的上下文和结果，避免只等待一次队列空闲。

## 4. 四份证据构成卸载证明

第一份是控制配置：匹配、动作、方向、端口和租户都正确。第二份是安装结果：目标规则在目标设备上完成。第三份是流量证据：限定测试流命中相应规则并到达出口。第四份是效果：正确性、CPU、吞吐和尾延迟满足目标。

Ping 成功只能说明某种可达性；硬件计数增加只能说明所观察对象有流量；Host CPU 下降也可能来自负载变小。对比必须固定输入、包长、并发和测试窗口，且同时保存错误率。

## 5. 异常路径比例可以决定性能上限

设总到达速率为 `R`，软件异常路径比例为 `p`，软件能处理的速率为 `C`。稳定运行至少要求 `pR < C`，同时还要满足硬件及出口容量。教学条件：软件路径容量为 2 Mpps，硬件容量为 100 Mpps。

若 5% 流量进入软件，软件给出的理论上限为 `2/0.05=40 Mpps`；若比例升到 20%，上限降为 10 Mpps。可见“80% 已经卸载”仍可能受软件限制。该模型忽略突发、排队、包长和其他共享开销，不是产品性能数据。

更一般地，若原处理时间中只有 60% 可被卸载，且那部分加速 10 倍，串行简化模型的总加速为 `1/(0.4+0.6/10)≈2.17` 倍，而非 10 倍。加速比需要绑定原瓶颈，不由卸载功能名称决定。

## 6. 逐跳计数需要相同口径

在无重置、同一统计窗口且排除后台流量时，可比较入口包、规则命中、服务入口、服务出口与物理出口。若服务有封装、复制、聚合或过滤，输入输出本就不一定一比一，应按预期变换建立关系。

计数器还受采样与刷新粒度影响。极短测试不适合用较慢更新的累计计数判断“完全没有流量”。更换规则后应重新关联对象身份，不能把旧规则计数延续为新配置的证据。

小包正常而大包失败时，可检验有效 MTU、封装开销、分片与路径丢弃，但现象本身不能唯一确定 MTU 根因。规则容量不足、资源不足和不支持的动作也应从安装结果中分辨，不靠重启进程猜测。

## 7. 掌握检查

**得到 Entry 句柄是否能马上宣称规则已生效？** 不能，要读完成状态和流量证据。

**Miss 增长是否一定失败？** 不一定，先看预期异常路径与其容量。

**卸载比例提高是否保证 P99 更低？** 不保证，排队、突发、共享资源和软件尾部都可能主导。
