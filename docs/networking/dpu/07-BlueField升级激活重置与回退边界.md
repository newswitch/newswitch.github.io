# BlueField 升级激活重置与回退边界

DPU 既是可升级的计算环境，也可能是 Host 网络和存储的必经路径。因此“Arm 包更新成功”与“Host 业务不受影响”没有直接等号。先读[版本契约](./06-DOCA软件栈版本契约与兼容矩阵.md)，再分析一次升级实际改变什么。

## 1. 制品类型决定修改范围

NVIDIA 的 BlueField 软件安装升级手册区分完整 BF-Bundle、仅固件 BF-FW-Bundle 和标准包更新等方式。完整包包含 Arm OS、DOCA 和固件；固件包不等于 Arm 系统备份，包更新也可能仍需后续平台固件操作。具体更新路径和内容以目标发行版、SKU 及所用选项为准。[官方手册](https://docs.nvidia.com/networking/display/bluefieldbsp480/software-installation-and-upgrade.pdf)给出了这些区别。

因此维护计划不能只写“升级 DOCA”。应列出将改变的 Host 包、Arm 包、系统分区、NIC 固件、启动固件和 BMC 组件，以及哪些配置和本地数据会保留。安装配置中的凭据属于敏感材料，不能随 BFB 校验清单公开发布。

## 2. 暂存 激活与运行是三个时点

```text
制品校验 → 写入或安装 → 等待激活
                        ↓
                  指定范围的重置
                        ↓
              新版本运行 → 服务恢复 → 业务复验
```

写入完成后，当前运行固件可能仍是旧版本；包版本已更新后，进程也可能仍载入旧库。因此记录应分别保存目标版本、已安装版本、下一次启动状态和当前运行状态，而不是只读包管理器结果。

Deferred Update 将准备与激活分开，不等于无重置升级。官方流程有特定设备和软件前提；不能把某一 SKU 支持的延后激活推广到所有 BlueField。即使准备阶段不中断，最终激活仍需单独预算和验证。

## 3. 四种重置范围不能混用

| 范围 | 主要影响 | 不能假定恢复什么 |
| --- | --- | --- |
| 应用或服务重启 | 服务进程与部分状态 | 整台 DPU 固件 |
| Arm OS 重启 | Arm 进程、内核和相关服务 | 所有 NIC 或 BMC 组件 |
| Host/设备规定的系统重置 | PCIe、设备枚举及所涉业务 | 任何持久数据格式都兼容 |
| BMC 重启 | 带外管理服务与控制台 | Host 应用和 Arm 服务同步恢复 |

这张表是影响范围分类，不提供可互换的操作命令。所需 reset 或 power cycle 由版本手册规定。反复做较小范围重启不能代替所需激活；直接扩大到整机断电又可能损害运行任务和远程恢复能力。

## 4. 先检查恢复路径是否独立

假设 Host 管理 SSH 通过正在升级的 DPU 转发。升级过程中一旦失联，原先的 SSH 就不能承担恢复通道。维护前应识别 Host BMC、DPU BMC、独立管理口、RShim 或控制台等在目标平台可用的路径，并验证身份与可达性。

独立性不仅指另一根线：若备用控制台仍依赖同一电源、交换机或被替换的凭据，仍有共同失效点。恢复流程还要说明谁拥有写入权；两个协调器同时刷写或一个正在取证、另一个切电，会破坏操作顺序。

## 5. 升级顺序由依赖和所有权共同决定

常见的验收阶段是：退出新业务准入、完成旧任务与持久状态处理、冻结目标身份、校验受支持组合、准备制品、按产品顺序更新、执行所需激活、恢复管理和数据服务、资格验证、逐步放行业务。

这是不变量列表，不是所有版本通用的刷写脚本。例如某些官方流程要求先更新 Host DOCA 再安装 BlueField Bundle，但应以实际目标版本核对，不能将此口诀替代兼容矩阵。

采用 DPF 时，变更应沿其上层对象和支持的更新策略进行；手工修改生成的服务或同时运行另一套升级工具，会产生竞争。见[DPF 对象与生命周期](./04-DPF控制对象与DPU生命周期.md)。

### 5.1 Operator 升级与 BFB LTS 演进分开

DPF 26.4.0 的[升级指南](https://networking-docs.nvidia.com/dpf/26.4.0/dpf-operator-upgrade-guide)仍要求 Operator 遵循相邻 GA 版本升级策略，并区分同一发布线的补丁升级。BFB 允许跨 LTS 边界演进，并不会把 Operator 升级变成可跳过任意中间版本。

教学路径可写成 `DPF 25.7 → 25.10 → 26.4`，每条边分别检查目标发行说明、组件就绪和 DPU 状态；不能因为 BFB 版本暂时保持不变，就删除中间的 Operator 迁移。相反，更新 BFB 也不意味着 Operator、服务和所有前置组件已一起更新。

### 5.2 相同 BFB 仍可能需要重新供应

[26.4.0 发行说明](https://networking-docs.nvidia.com/dpf/26.4.0/doca-platform-framework-v26-4-0)指出：由 DPF 25.10 供应、并在升级后继续使用 3.2 LTS BFB 的受影响 DPU，需要重新供应。原因不是单纯“旧镜像跑不动”，而是该旧供应结果缺少 DPU Agent 和后续 kubelet 版本偏差验证所需的报告能力。

这意味着版本判断需要保留供应来源。新旧两张卡都显示同一 BFB 分支，不足以证明它们对新版管理面的能力相同。完成后应核对相应 Agent/kubelet 报告及控制面条件，而不是只比镜像文件名。

重新供应是会影响节点和业务的生命周期动作，不是刷新一个显示字段。这里不把发行说明中的删除 DPU CR 操作列为通用修复命令；实际应先核对受影响范围、上层期望对象、数据与业务处理及恢复入口，再按目标版本流程执行。

### 5.3 并发数不能只读一个字段

DPF 26.4.0 的 [DPFOperatorConfig](https://networking-docs.nvidia.com/dpf/26.4.0/dpfoperatorconfig)区分供应并发 `maxDPUParallelInstallations` 和更新不可用节点限制 `maxUnavailableDPUNodes`，还会与 Maintenance Operator 的限制共同作用。供应任务数、不可用节点数和业务故障域并非同一单位。

教学条件：10 台 Host 每台两张 DPU，维护任务按 DPU 计数。允许并发 4 张，既可能影响两台 Host，也可能分散影响四台；若其中任一张承载 Host 的唯一关键路径，这两种安排的业务影响不同。必须结合卡与节点映射和维护策略，不能把 4 张卡直接读成 4 台节点的业务预算。

## 6. 可用性预算要按业务故障域计算

教学条件：12 台同构服务节点，每台在当前请求结构下承载 100 请求/秒；目标流量为 800 请求/秒，维护期间仍要求保留 200 请求/秒的余量。至少需要 `(800+200)/100=10` 台可用，即同一时刻最多退出 2 台。

这个算式假设性能线性、流量可重分布、剩余节点没有其他瓶颈。若两台 DPU 同属唯一存储路径或同一业务副本组，即使总容量足够，也可能不能同时维护。预算必须同时满足数量、容量和故障域约束。

把 Canary 选成真实代表：相同型号、工作模式、网络和存储服务依赖。只在闲置 DPU 上升级成功，无法证明承载关键服务的设备具有相同恢复路径。

## 7. 回退不是把文件名改回去

回退清单应分应用、配置、Arm 系统和固件，并逐项确认支持的降级路径。新的持久格式、安全启动策略或平台限制可能使直接降级不可行；此时应有受支持的恢复或替换方案，而不是尝试强制刷入旧包。

教学反例：旧镜像启动成功，但新版本已迁移状态数据库。旧进程不能正确读取，并不因为旧 Digest 正确就自动解决。对有状态网络服务，还要处理连接、规则和外部控制器的一致性，不能仅凭容器 Running 解除隔离。

## 8. 掌握检查

**包安装结束能否宣布升级完成？** 不能，还需确认激活、运行版本及原先数据路径。

**Deferred 是否承诺所有会话不中断？** 不承诺。准备、激活和应用连续性是不同阶段。

**回退镜像能否恢复所有固件和持久数据？** 不能，必须按制品范围与支持路径分别判断。
