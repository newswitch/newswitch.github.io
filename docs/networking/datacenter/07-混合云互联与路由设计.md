# 混合云互联与路由设计

混合云不是“拉通一条 VPN”就结束。生产设计必须同时解决：

- 地址能否唯一寻址；
- 路由能否双向收敛；
- 状态防火墙是否看到对称路径；
- 加密、带宽和 MTU 是否满足业务；
- 单链路、单设备、单机房故障能否切换；
- 谁能证明一次切换真的成功。

## 1. 先做地址与路由域规划

最昂贵的网络问题通常不是协议，而是重叠地址。

建立全局 IPAM，至少记录：

```text
环境 / 地域 / VPC-VNet / VRF / CIDR / 用途 / 所有者 / 生命周期
```

如果两个网络都使用 `10.0.0.0/16`，直接路由无法区分。可选方案包括：

- 迁移或重新编号，长期最干净；
- 在边界做双向 NAT，短期缓解但增加日志和排障复杂度；
- 用独立 VRF/代理隔离，避免直接三层互通；
- 只暴露 API 或消息服务，不连接整个地址空间。

## 2. VPN 与专线如何选择

| 方案 | 优点 | 局限 | 常见用途 |
|---|---|---|---|
| Internet IPsec VPN | 上线快、成本低、天然加密 | 抖动和带宽不可控 | 备份、小规模、快速接入 |
| 云专线 | 带宽和时延更稳定 | 开通周期、端口和运营商成本 | 核心生产流量 |
| 专线 + IPsec | 稳定链路上再加密 | 运维复杂度更高 | 有强加密要求 |
| 双专线 + VPN 备份 | 故障域更完整 | 成本最高、策略需精细 | 高可用核心业务 |

专线不一定默认加密，是否需要 MACsec、IPsec 或应用层 TLS 要根据威胁模型决定。

## 3. 用 eBGP 交换路由

动态路由的目的不是“显得高级”，而是：

- 自动发布和撤销前缀；
- 用属性控制主备或负载分担；
- 用 BFD/会话状态快速触发收敛；
- 通过过滤防止错误前缀扩大故障。

### 必须存在的路由护栏

```text
只接收明确允许的云 CIDR
只发布明确允许的本地 CIDR
设置最大前缀数量
拒绝默认路由，除非架构明确要求
记录策略变更并验证实际 Adj-RIB-In/Out
```

主备控制要同时考虑去程和回程：

- Local Preference 控制本 AS 的出口；
- AS_PATH Prepend 或云侧优先级影响对端入口；
- MED 只在明确理解对端策略时使用；
- 等价路径是否真正支持 ECMP 取决于两端平台。

## 4. 对称路径与状态设备

无状态 IP 转发可以接受去回程走不同链路，但防火墙、NAT、某些负载均衡器需要看到完整连接。

典型黑洞：

```text
去程：On-Prem → Link-A → Cloud Firewall-A
回程：Cloud → Link-B → Firewall-B
结果：Firewall-B 没有会话状态，丢弃回包
```

解决方案可能是：

- 让路由策略保持会话对称；
- 防火墙集群同步状态；
- 在进入状态设备前做流量引流；
- 明确使用无状态检查，而不是假定任意非对称都安全。

## 5. MTU、封装与 TCP MSS

IPsec、GRE、VXLAN 等封装都会增加头部。物理路径 MTU 为 1500 时，隧道内可用 MTU 会下降。

常见症状：

- ping 小包正常，大包失败；
- TCP 握手成功，传输大响应时卡住；
- PMTUD 所需 ICMP 被策略丢弃；
- 某些应用正常，特定报文长度失败。

验证：

```bash
# Linux：从较小值逐步增加，并禁止分片
ping -M do -s 1300 <destination>
tracepath <destination>
ip route get <destination>
ss -ti
```

根据实测路径设置隧道 MTU或 TCP MSS Clamp，同时保留必要的 ICMP Packet Too Big/Fragmentation Needed。

## 6. 高可用不是两条线，而是独立故障域

检查两条连接是否真正独立：

- 是否进入不同的本地路由器；
- 是否经过不同运营商或物理路由；
- 是否终止在不同云边缘位置和可用区；
- 是否共享同一电源、机房、交叉连接或防火墙；
- 控制面是否有独立 BGP 会话；
- 单条链路降质但不 Down 时，是否能退出转发。

仅有接口 Down 检测无法发现高时延、高丢包或黑洞。需要主动探测，并防止阈值过敏导致路由振荡。

## 7. 割接流程

### 割接前

- 冻结并导出路由、安全、NAT 和设备状态；
- 检查前缀过滤、最大前缀与回程路由；
- 测试低风险探针；
- 明确回滚触发条件和负责人；
- 降低 DNS TTL 只对确实通过 DNS 切换的链路有效。

### 分批引流

1. 先引入测试前缀或少量业务；
2. 验证时延、丢包、连接、应用错误和日志；
3. 逐步扩大路由范围；
4. 每批等待超过典型连接和监控窗口；
5. 达到停止条件立即回滚，不继续扩大。

### 失败演练

- 断开主专线；
- 保持接口 Up 但制造数据面黑洞；
- 撤销某个前缀；
- 让 BGP 发布异常大量路由，验证最大前缀；
- 制造 MTU 不一致；
- 验证恢复后是否发生路由回切振荡。

## 8. 排障证据链

```text
应用五元组
→ 源主机路由
→ 本地边界路由和策略
→ VPN/专线隧道状态
→ 云网关收到/发布的路由
→ 云子网路由表
→ 安全组/ACL/防火墙
→ 目标监听
→ 完整回程
```

每个结论至少配一种证据：路由表、BGP RIB、流日志、接口计数器、抓包或应用日志。

## 9. 综合设计题

为“本地双机房 + 两个云区域”设计互联：

- 生产流量优先专线，VPN 为备份；
- 两端任何单设备或单链路故障不应中断关键 API；
- 不允许云端向本地发布默认路由；
- 数据库只允许指定应用网段；
- 给出 MTU、加密、路由过滤、监控和回滚方案。

最终交付不只是一张拓扑图，还应有路由矩阵、故障域表、测试用例、SLO 和变更 Runbook。
