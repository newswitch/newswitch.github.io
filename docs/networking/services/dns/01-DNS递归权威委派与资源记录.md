# DNS 递归、权威、委派与资源记录

浏览器拿到 `www.example.com` 之后，需要知道去哪里连接。这个名字并不是直接交给根服务器，再由根服务器一路代问到底。不同参与者的职责需要先分清。

## 1. 一次查询涉及哪些角色

| 角色 | 核心职责 |
| --- | --- |
| 应用解析逻辑 | 决定查什么名字、什么类型，以及如何使用结果 |
| Stub Resolver（存根解析器） | 通常把查询交给配置的递归解析器，本身不遍历完整委派树 |
| Recursive Resolver（递归解析器） | 为客户端寻找最终答案，缓存并按能力校验 |
| Authoritative Server（权威服务器） | 对自己负责的区域提供权威数据 |
| Forwarder（转发目标） | 接收下游解析器转来的查询，继续处理 |

这些是逻辑角色，不一定一一对应不同机器。一台软件进程可以具备多种能力，但公网权威服务与开放递归能力不应因此混为一谈。术语边界见 [RFC 9499](https://www.rfc-editor.org/rfc/rfc9499.html)。

## 2. 缓存未命中时，答案如何找回来

以下是简化的完整路径，假设相关委派和答案都未缓存：

```text
应用 → 本地解析逻辑 → 递归解析器
                        ↓ 问根：谁负责 .com？
                        ↓ 问 .com：谁负责 example.com？
                        ↓ 问 example.com 权威：www 的 A 记录是什么？
                        ↓ 得到答案并缓存
应用 ← 返回可用结果 ← 递归解析器
```

根通常返回下一层权威信息，而不是返回每一个网站的地址。这种“告诉你继续问谁”叫 referral（转介）。

客户端请求递归解析器替自己得到结果，是递归服务；解析器向权威逐步查询、跟随转介，是迭代查找。缓存已有 `.com` 或 `example.com` 的委派时，可以跳过部分步骤，不必每次从根重新走一遍。

### 2.1 一份 DNS 响应里，哪一部分才是答案

DNS 报文不是只有“域名、IP”两个字段。读报文时先分清四个区段：

| 区段 | 内容 | `www.example.com A` 查询中的可能表现 |
| --- | --- | --- |
| Question（问题） | QNAME、QTYPE、QCLASS | 查询名称、A 类型、IN 类别 |
| Answer（答案） | 直接回答查询的记录，也可能包含别名链 | `www` 的 CNAME 与最终目标的 A |
| Authority（权威信息） | 委派、否定答案所需的区域信息等 | 转介的 NS，或否定响应中的 SOA |
| Additional（附加信息） | 帮助使用其他记录的信息 | 到达 NS 所需的 Glue 地址 |

因此 Answer 为空不能直接解释为“名称不存在”。它可能是让解析器继续查找的 referral，也可能是没有所查类型的数据，还可能是失败响应；需要结合 RCODE 和其他区段判断。

报文头中，`QR` 区分查询与响应，`ID` 用于请求响应匹配，`RD` 表示请求递归，`RA` 表示服务器提供递归能力，`AA` 表示响应具有相应权威语义，`TC` 表示报文被截断。`RD=1` 不保证服务器一定愿意提供递归，`AA=1` 也不是 DNSSEC 验证结果。字段定义见 [RFC 1035 §4](https://www.rfc-editor.org/rfc/rfc1035.html#section-4)。

### 2.2 把冷查询拆成三次“问路”和一次“交付”

忽略别名、DNSSEC 与重试，仅观察逻辑交互：

1. Stub 向递归解析器发起查询，通常请求递归服务。
2. 解析器向根查询，获得指向 `.com` 的 NS 和适用的辅助地址，而不是网站 A 记录。
3. 解析器向 `.com` 查询，获得 `example.com` 的委派。
4. 解析器向目标区域权威查询，才取得业务记录；随后向 Stub 返回结果。

这几次上游查询是独立事务，不是同一个 IP 包依次经过四台 DNS 服务器。解析器分别建立请求、处理超时和选择服务器；对客户端返回缓存答案时，通常不会声称自己就是该区域的权威。

## 3. Domain 和 Zone 为什么不是一个概念

Domain（域）描述名称树中的一个子树；Zone（区域）描述一份实际由某组权威服务器管理的数据范围。

假设 `example.com` 把 `dev.example.com` 委派给另一组服务器：

```text
example.com 这个名称子树
├─ www.example.com       仍由 example.com 区域管理
└─ dev.example.com       在此切分委派
   └─ api.dev.example.com 由 dev.example.com 区域管理
```

父区域保留如何找到子区域的委派信息，不再负责子区域中的全部业务记录。名称层级和管理边界不完全相同，基础模型见 [RFC 1034](https://www.rfc-editor.org/rfc/rfc1034.html)。

## 4. Glue 为什么存在

若 `dev.example.com` 的权威服务器叫 `ns1.dev.example.com`，解析器会遇到一个循环：要问子区域，先得知道它的 NS 地址；要查 NS 地址，又似乎得先能问到子区域。

父区域在委派处提供必要的 A/AAAA 辅助地址，这就是 Glue（胶水记录），帮助解析器到达子区域的权威服务器。

Glue 的职责是提供引导信息，不是让父区域变成所有子区域记录的权威来源。NS 名称发生变化时，只改子区域或只改父区域的一侧，可能使委派关系失配。也不是任意 Additional Section 中的地址都能无条件信任，递归解析器还有来源范围检查。

### 4.1 NS 与 Glue 不一致时，为什么有些解析器能用、有些不能

设父区域仍提供 `ns1.dev.example.com → 192.0.2.10`，子区域已经把同名服务器地址改为 `192.0.2.20`。冷解析器可能先走旧 Glue；已有有效地址缓存的解析器可能直接走新地址。若旧地址停止服务，故障就会随缓存状态表现不同。

正确的依赖顺序是“先能到达某个权威，再取得其负责的数据”。不能要求解析器先从不可达的子区域取得最新地址，才能修复到达子区域的路径。

此外，Additional 只是报文位置，不是可信等级。与当前委派无关的附带地址不能因为出现在响应中，就覆盖已有可信数据。RRset 完整性及数据可信等级可参见 [RFC 2181](https://www.rfc-editor.org/rfc/rfc2181.html)。

## 5. 资源记录不只 A 和 AAAA

| 类型 | 作用 | 容易混淆的地方 |
| --- | --- | --- |
| A / AAAA | IPv4 / IPv6 地址 | 查询类型与承载 DNS 查询的地址族无关 |
| CNAME | 指向另一个规范名称 | 不是 HTTP 301/302，不把浏览器 URL 自动改写 |
| NS | 指定区域权威服务器名称 | 不是直接填写业务后端地址 |
| SOA | 区域管理元数据，包括序列号和计时信息 | 序列号变化不等于客户端缓存被清空 |
| MX | 邮件交换目标与优先级 | 不是普通网页负载均衡列表 |
| TXT | 承载文本数据 | 内容含义由上层协议或服务约定 |
| PTR | 反向名称映射 | 创建 A 不会自动创建 PTR |
| SRV | 服务目标、端口及优先级／权重 | 应用必须支持该发现机制才会使用 |

同一名称、类型、类别下的数据构成 RRset（资源记录集）。例如同一名称的多个 A 记录是一组答案，不意味着每一条都建立独立权威关系。

普通 CNAME 不能与同名的其他普通业务数据并存。因此区域顶点已有 SOA、NS 时，不能简单照抄子域 CNAME 的做法；云厂商的 ALIAS、ANAME 或 flattening 是产品机制，不等于标准 CNAME 规则改变。基本记录格式见 [RFC 1035](https://www.rfc-editor.org/rfc/rfc1035.html)。

### 5.1 CNAME 怎样增加查找依赖

假设 `www.example.com CNAME edge.example.net`，目标再有 A 记录。解析器必须同时解决两个问题：原名指向谁，以及目标名的地址是什么。目标记录可能已经随响应返回、已经缓存，也可能需要沿另一个区域的委派继续查询。

别名所在区域可用，不代表目标区域也可用；看到 CNAME 也不代表已经得到可连接地址。应用最终仍需要符合自己请求类型的结果，例如 IPv4 连接需要 A，而不是把 CNAME 的名称字符串当作 IP。

## 6. DNS 为什么同时需要 UDP 和 TCP

传统 DNS 常用 UDP 53，因为一次查询和响应通常很短。但响应较大、传输被截断、区域传送或客户端主动选用 TCP 时，都可能走 TCP 53。

不能只允许 UDP 53，就断言 DNS 完整可用。TCP 也不只是“区域传送专用”，相关要求见 [RFC 7766](https://www.rfc-editor.org/rfc/rfc7766.html)。

EDNS 可让双方表达更大的 UDP 响应能力，但“声明能接收较大响应”不等于路径 MTU 足够。过大的 UDP 响应仍可能遇到分片和中间设备丢弃问题。

## 7. 谁持有正确数据，谁持有旧数据

权威服务器提供区域当前数据；递归解析器按缓存状态回答；应用也可能保留自己的解析结果。三者在同一时刻返回不同信息，不一定意味着权威区域没有更新。

主、辅权威之间通常还涉及区域数据同步和序列号。即使同属一个 NS 集合，不同实例也可能在异常期间持有不同区域版本。这与递归缓存过期是两条独立时间线。

### 7.1 SOA 序列号不是缓存版本通知

辅助权威用区域序列号判断是否需要取得更新；全量传送 AXFR 与增量传送 IXFR 解决的是区域副本同步。递归解析器则按记录 TTL 使用缓存，两条链路没有“序列号递增就远程清缓存”的保证。

SOA Serial 是 32 位序列空间，不是必须按日期书写的普通整数。比较要考虑回绕，不能永远使用数值更大即更新的规则，见 [RFC 1982](https://www.rfc-editor.org/rfc/rfc1982.html)。这解释了为什么随意把序列号改小，可能使部分辅助权威不认为自己需要更新。

## 8. 思考与解答

**响应里没有 Answer，但有指向子区域的 NS，可以断言域名不存在吗？**

不能。先看是否为转介；解析器可能还需要继续向子区域查询。NXDOMAIN 由相应响应语义表达，不由 Answer 的长度单独决定。

**递归响应带 RA，但不带 AA，是不是低质量答案？**

不是。RA 描述递归能力，AA 描述权威角色，和答案新鲜度、DNSSEC 验证状态不是同一维度。合法缓存响应通常就不是权威响应。

**子区域 NS 地址已经改对，为什么第一次访问仍失败？**

可能是父侧 Glue 仍旧、旧权威地址不可达，使冷查询无法完成引导；也可能是委派或路径存在其他问题。已有缓存的成功不能证明冷查询链路完整。

**提高 SOA Serial，能让所有浏览器立即获得新 IP 吗？**

不能。Serial 推动的是区域副本更新；递归缓存、应用缓存和已有连接各有独立生命周期。

**设置 CNAME 后，浏览器地址栏会变成目标域名吗？**

不会因为 DNS 别名自动变化。浏览器仍可按原域名发送 HTTP Host 和 TLS SNI；HTTP 重定向才是另一类改变访问地址的机制。

**根服务器故障，所有 DNS 查询是否马上失败？**

不能一概而论。已有委派和答案缓存可能继续工作，实际根服务也存在多实例。影响取决于缺失哪些可用数据，以及后续能否刷新。

**一个域名有两个 A 记录，就是每个请求各分一半吗？**

不是。解析器排序、客户端选择、缓存和连接复用都会影响流量。DNS 返回候选地址不等于逐请求负载均衡。
