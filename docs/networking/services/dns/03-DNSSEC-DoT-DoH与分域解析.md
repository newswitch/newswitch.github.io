# DNSSEC、DoT、DoH 与分域解析

“安全 DNS”不是单一能力。至少有三件事需要分别回答：答案是否被伪造，查询在路上是否被旁观，以及请求是否送到了有权回答内部名称的解析器。

## 1. 先把三个安全目标分开

| 目标 | 相关机制 | 不自动解决的问题 |
| --- | --- | --- |
| 验证 DNS 数据来源与完整性 | DNSSEC | 不加密域名查询内容 |
| 保护客户端到解析器的传输 | DoT、DoH | 不保证解析器本身诚实，不自动保护其所有上游路径 |
| 按网络和名称选择正确解析范围 | 分域解析、内部视图、访问控制 | 不等同于 DNSSEC，也不等同于加密 |

即使三项都满足，也只说明名称解析这一环节具备相应保障，不代表域名指向的网站没有恶意或业务一定健康。

## 2. DNSSEC 到底签什么

DNSSEC 给 DNS 数据建立可验证的签名关系，核心对象包括：

- **DNSKEY**：区域公开密钥。
- **RRSIG**：对应资源记录集的签名。
- **DS**：父区域中关联子区域密钥的摘要记录。
- **NSEC／NSEC3**：为名称或类型不存在等否定答案提供可验证证据。

简化的信任链为：

```text
本地可信锚
  → 验证父区域的签名数据
  → 从父区域 DS 确认子区域 DNSKEY 的关联
  → 用子区域密钥验证其签名记录集
  → 得到可认证的答案或否定结果
```

DS 不是父区域替子区域保存私钥。验证者取得 DNSKEY 后，要把它与父区域提供的可信关联核对，再验证子区域数据。核心目标见 [RFC 4033](https://www.rfc-editor.org/rfc/rfc4033.html)，记录定义见 [RFC 4034](https://www.rfc-editor.org/rfc/rfc4034.html)。

### 2.1 从可信锚走到一组 A 记录

以已签名的 `example.com` 为例，验证者不能仅仅下载它自己发布的 DNSKEY，就宣布可信。公开密钥谁都可以生成，关键是它是否被已经信任的上层关系认证。

验证者先依据可信锚验证父区域，再验证父侧 DS RRset；用其中的摘要核对子侧候选 DNSKEY，并验证子侧 DNSKEY RRset 的签名。可信的子侧密钥集合建立后，才可验证 `www.example.com A` 对应的 RRSIG。DNSKEY 与 DS 的字段关系见 [RFC 4034](https://www.rfc-editor.org/rfc/rfc4034.html)。

父区域认证的是“这个子区域密钥关联”，不是每次替子区域签业务记录。反过来，子区域自己声称“这是我的新密钥”，也不能单方面更新父侧 DS。

### 2.2 “不存在”也需要证据

签名只能证明收到的数据；若没有否定证明，验证者无法分清“确实没有记录”和“记录在途中没有交付”。NSEC 描述名称顺序区间及已有类型，NSEC3 使用散列后的名称空间并有相应例外规则，让验证者能够核对否定答案。

名称不存在、类型不存在和通配符适用性，需要的证明并不完全一样；不能把一条签名 SOA 当成所有否定情况的完整证明。这里只建立验证对象之间的关系，NSEC3 的细节见 [RFC 5155](https://www.rfc-editor.org/rfc/rfc5155.html)。

## 3. 有签名，不等于签名链有效

| 状态 | 含义 |
| --- | --- |
| Secure | 按信任锚成功验证了相应数据链 |
| Insecure | 按验证规则确定该处没有要求验证的签名链，例如存在合法未签名委派 |
| Bogus | 应当验证，但签名、密钥、有效期或关联等不满足要求 |
| Indeterminate | 缺少足够信息来确定相应验证状态 |

正常启用校验的递归解析器遇到 Bogus，通常向普通客户端返回失败，而不是把未经验证的答案当成功结果交付。具体请求标志和策略可能影响处理方式，验证语义见 [RFC 4035](https://www.rfc-editor.org/rfc/rfc4035.html)。

这能解释一种情况：非验证查询似乎拿得到 IP，正常客户端却收到 SERVFAIL。原因可能是密钥轮换时父 DS 与子 DNSKEY 不匹配，也可能是签名过期，而不是路由不通。

### 3.1 DO、AD、CD 分别是谁的诉求

| 标志 | 主要表达什么 | 不代表什么 |
| --- | --- | --- |
| DO（DNSSEC OK，位于 EDNS） | 查询方可以接收 DNSSEC 相关记录 | 查询方已经完成验证 |
| AD（Authenticated Data） | 响应方按规则认为相关数据已认证 | 网络上任何 AD 都值得无条件信任 |
| CD（Checking Disabled） | 查询方请求解析器不要因验证失败而扣留数据 | 数据的签名问题已被修复 |

请求 DNSSEC 记录、执行密码学验证、向客户端表达验证结果，是三件不同的事。合法未签名委派还需要按验证规则确认其不安全边界；不能把“这次没拿到 DS”直接解释成“可以跳过校验”。参见 [RFC 4035](https://www.rfc-editor.org/rfc/rfc4035.html)。

## 4. DNSSEC 为什么依赖时间

RRSIG 有生效和到期时间。验证者时钟大幅错误时，可能把正常签名判断为尚未生效或已经过期。

因此 DNS 问题有时来自 [时间同步](../time-sync/00-时间同步学习路线.md)。关闭验证可能暂时改变现象，却移除了原本的安全保证，不能证明根因已经消失。

另外，AD 标志表达解析器认为数据通过了验证。普通客户端若只是信任远端的 AD，而不自己验证，就仍需要可信的解析器以及受保护的交互路径。不能只看一个标志位就推导出端到端的独立密码学验证。

### 4.1 TTL 没到，签名也可能已经不能使用

假设在 12:00 验证一组记录，记录 TTL 为 600 秒、RRSIG TTL 为 600 秒、RRSIG Original TTL 为 600 秒，但签名在 12:02 到期。普通验证缓存的有效上限受其中最早约束限制，不能因为记录 TTL 还剩 8 分钟，就把已过期签名继续当作有效签名。

因此密钥轮换不仅是“发布新密钥、删掉旧密钥”。父 DS、子 DNSKEY、业务 RRSIG 以及各层缓存，需要在过渡期仍能组成可验证链。KSK/ZSK 分工是一种密钥管理安排，不意味着任何部署都必须使用两把不同密钥；运营与轮换考虑见 [RFC 6781](https://www.rfc-editor.org/rfc/rfc6781.html)。

## 5. DoT 与 DoH 把哪一段加密

DoT 是 DNS over TLS，常见服务端口为 TCP 853；DoH 是 DNS over HTTPS，经配置的 HTTPS 端点传送 DNS 消息，常见端口为 443。分别见 [RFC 7858](https://www.rfc-editor.org/rfc/rfc7858.html) 与 [RFC 8484](https://www.rfc-editor.org/rfc/rfc8484.html)。

```text
客户端 ═ 加密连接 ═ 选定的递归解析器 ─ 上游查询路径 ─ 权威服务器
```

粗线主要保护客户端到所选解析器这一段。解析器仍能看到它处理的查询；之后如何访问上游、如何记录与保留数据，取决于服务设计。

DoH 使用 HTTPS，不表示它把 DNS 查询变成对目标网站的 HTTP 请求。它的 HTTPS 对端是解析服务，返回内容仍是 DNS 数据；业务连接随后另行建立。

## 6. 加密 DNS 为什么有时影响内网名称

假设企业内网只允许内部解析器回答 `db.corp.example.com`。操作系统通过 VPN 将该后缀交给企业 DNS，而浏览器启用了自己的外部 DoH 服务。

可能出现：

- 系统应用解析成功，浏览器无法解析同名目标。
- 外部解析器看不到内部视图，返回不同结果或不存在。
- 内部名称被发送到不应接收它的外部服务。

问题不在于“加密本身破坏 DNS”，而在于**选择了不同的解析路径和管理范围**。加密与分域策略需要配合，不能认为全局改为某个公共解析器就适合所有网络。

Split DNS（分域解析）常用于按名称选择解析器；Split Horizon（分视图）强调同一名称对不同来源返回不同数据。不同产品术语可能有交叠，判断时要具体看“请求被发给谁”和“谁依据什么返回答案”。

## 7. 递归服务还需要什么边界

DNSSEC 或 DoH 都不能代替递归访问控制。一个无意向公网开放的递归服务，仍可能被滥用并消耗资源。

权威服务和递归服务应分别考虑允许的请求来源、容量、速率与缓存行为。高查询量也要区分真实业务增长、客户端重试、缓存命中率下降和异常流量，不能只用“打开安全协议”概括整个可靠性设计。

### 7.1 加密、最小披露与选址之间还有取舍

DoH/DoT 减少客户端到解析器路径上的明文暴露，但选定解析器仍需处理完整查询。QNAME Minimisation（查询名称最小化）则减少递归查找时向上层权威披露的名称，例如询问 `.com` 的委派时，无需总把完整业务主机名交给根；机制见 [RFC 9156](https://www.rfc-editor.org/rfc/rfc9156.html)。

ECS 又可能为了选址而向上游带出客户端前缀。三种机制改变的是不同观察者能看到什么，不应合并成一个“安全 DNS 已开启”的布尔值。

对加密解析服务自身，还要解决端点地址发现与证书身份校验。预配置地址只能解决“连到哪里”，不能替代“对端是谁”；连接失败后的明文回退是否允许，也应是明确的安全策略，而不是悄悄失去保护。DNS 隐私边界可结合 [RFC 9076](https://www.rfc-editor.org/rfc/rfc9076.html) 理解。

## 8. 思考与解答

**子区域能提供 DNSKEY 和正确的自签名，为什么仍可能是 Bogus？**

如果父 DS 指向另一把密钥，自签名不能修复父子关联。验证者需要从已有可信关系走到该密钥，而不是只证明“数据与某把自称正确的密钥匹配”。

**打开 DO 后看到 RRSIG，能认定当前客户端已经验证成功吗？**

不能。DO 是接收相关数据的能力声明，验证还需要可信锚、完整链路、签名运算与有效期检查。接收记录与验证记录不是同一动作。

**记录 TTL 还有 600 秒，签名 120 秒后到期，有效验证缓存能保持 600 秒吗？**

不能。还要受 RRSIG TTL、Original TTL 和签名剩余有效期等限制；在此示例中，上限不超过 120 秒。

**使用 DoH 和名称最小化后，所选递归解析器还能看到完整查询吗？**

通常能。DoH 保护到它的传输，名称最小化主要减少它向上层权威披露的信息，两者没有把所选解析器排除出信任范围。

**开启 DoH，解析器返回的数据就一定通过 DNSSEC 吗？**

不一定。DoH 保护的是传输，是否验证 DNSSEC 由解析服务与客户端机制决定。

**DNSSEC 验证成功，域名对应的网站就是安全网站吗？**

不是。它验证 DNS 数据的来源与完整性，不审查业务内容，也不保证域名所有者善意。

**公共 DoH 能查公网域名，为什么查不到公司内网服务？**

因为它可能没有内部区域的数据或访问权限，也未走企业的分域解析路径。这属于名称管理范围，不是地址字符串是否正确的问题。
