# DNS TTL、负缓存与服务切换

把域名指向新服务器后，为什么还有用户访问旧地址？可能是缓存，也可能是根本没有再进行 DNS 查询的长连接。需要把“何时获得地址”和“何时建立连接”拆开。

## 1. TTL 是缓存许可，不是全网倒计时广播

DNS TTL 表示一份资源记录可被缓存使用多长时间。权威修改记录时，不会向全球递归解析器发送统一的清缓存广播。

考虑这个示例：

| 时刻 | 事件 | 解析器 R 的状态 |
| --- | --- | --- |
| 10:00 | R 得到旧地址，TTL=300 秒 | 缓存可用至约 10:05 |
| 10:02 | 权威改成新地址 | R 还剩约 180 秒旧缓存 |
| 10:03 | 另一客户端向 R 查询 | 仍可能收到旧地址，剩余 TTL 约 120 秒 |
| 10:05 后 | R 再需要答案并成功刷新 | 才取得新记录与新 TTL |

普通转发缓存会传递剩余有效时间，而不是每经过一个合规缓存就重新获得完整 300 秒。但应用缓存策略、最小／最大 TTL 限制及特殊失效处理可能改变实际表现。

## 2. 临时降低 TTL 为什么不是立刻生效

如果 10:02 才把 TTL 从 300 改成 30，已在 10:00 缓存的旧答案不会被远程改写。只有再次取得新记录的解析器，才知道新的 30 秒期限。

因此降低 TTL 改变的是**后续获取记录时的缓存许可**，不能追溯修改已经发出的旧许可。较短 TTL 还会增加对权威和递归链路的请求与可用性依赖，并非越小越好。

缓存层之间也不完全等价：浏览器、语言运行时、本地守护进程、企业转发器和上游递归服务，可能分别缓存正答案、失败或连接对象。知道某一层 TTL 不代表掌握了全部应用行为。

## 3. 没有记录，也是一种可缓存结果

| 结果 | 含义 | 示例 |
| --- | --- | --- |
| NXDOMAIN | 查询名称不存在 | 根本没有 `new.example.com` 这个名称 |
| NODATA | 名称存在，但没有所查类型的数据；通常表现为 NOERROR 且无该类型答案 | 有 A，但没有 AAAA |
| SERVFAIL | 解析过程失败 | 权威不可达、DNSSEC 校验失败等 |
| Timeout | 在等待窗口内未获得响应 | 不能仅凭超时判断记录不存在 |

NODATA 是结果类别，不是一个独立的 DNS RCODE。特别是“没有 AAAA”不等于整个名称不存在，也不能推出 A 记录查询会失败。

权威否定响应中的 SOA 信息参与负缓存期限计算；基础规则取 SOA 记录 TTL 与 SOA MINIMUM 字段中的较小值，见 [RFC 2308](https://www.rfc-editor.org/rfc/rfc2308.html)。它不是对所有响应都套用 SOA MINIMUM。

## 4. 先查不存在的名字，再创建记录，会发生什么

设 11:00 查询 `new.example.com`，得到可缓存 120 秒的 NXDOMAIN。11:00:30 才创建这个名称的 A 记录。

客户端继续使用同一个已有负缓存的解析器时，可能仍得到“不存在”，直到负缓存失效或按实现被刷新。这时反复修改新 A 记录的正 TTL，也不能直接清除旧的否定缓存。

失败缓存又是另一种机制。解析器可能短暂记住某类解析失败，避免每个客户端请求都重复冲击不可用上游。[RFC 9520](https://www.rfc-editor.org/rfc/rfc9520.html) 专门讨论失败缓存。因此“服务恢复了”和“所有下游立刻停止返回之前的失败”也不一定同时发生。

## 5. TTL 已过期，为什么仍可能返回旧答案

部分解析器具备 Serve Stale 能力：刷新失败等特定条件下，按受控策略暂时服务过期数据，以换取可用性。机制见 [RFC 8767](https://www.rfc-editor.org/rfc/rfc8767.html)。

这不是“TTL 没用”，而是在新鲜度与可用性之间采用明确的例外策略。它需要限制过期使用窗口与返回 TTL，也不能忽略 DNSSEC 等约束。

对稳定地址的普通服务，短时间继续使用旧答案可能比完全失败更好；对已撤销、已转移所有权或具有严格隔离要求的入口，旧答案则可能带来风险。设计切换时应明确这种行为是否存在。

## 6. DNS 切换不是连接迁移

设应用 12:00 解析到旧 IP，并建立可复用的 TCP 连接。12:01 权威改变，12:02 所有相关 DNS 缓存都已更新，但应用仍可能继续复用 12:00 的连接。

```text
DNS 记录更新
  ≠ 旧缓存立即失效
  ≠ 应用立即重新解析
  ≠ 已有连接立即重建
  ≠ 旧后端流量立即归零
```

TLS 会话、HTTP 连接池、数据库连接池等的行为也要分别理解。DNS 不会主动修改一个已有 TCP 连接的四元组，旧连接与新连接可以在切换窗口并存。

这就是为什么仅依据“TTL 只有 60 秒”不能保证业务 60 秒内全部离开旧端点。真实切换窗口还包含缓存实现、解析触发、连接生命周期和上游刷新健康程度。

## 7. CDN 与分线路解析怎样影响答案

权威或解析服务可能依据递归解析器位置、策略和客户端网络信息返回不同地址。传统情况下，权威主要看到递归解析器的来源，而不是每个终端的精确位置。

ECS（EDNS Client Subnet）可携带部分客户端网络前缀，帮助做更细的映射，但会影响隐私、缓存粒度和缓存键，见 [RFC 7871](https://www.rfc-editor.org/rfc/rfc7871.html)。因此两个解析器返回不同地址，不一定是其中一个“缓存错了”。

DNS 选址也不是持续健康检测本身。产品可以把探测结果用于生成答案，但发现故障、更新答案、缓存过期和客户端重连仍是不同过程。

## 8. 思考与解答

**查 AAAA 返回 NODATA，是否应该删除对应 A 记录？**

不应该。它只表示该名称没有所查类型的数据，A 可能完全正常。是否需要 AAAA 取决于服务是否准备好 IPv6 路径。

**权威查询是新 IP，但某个应用还连旧 IP，能否认定递归 DNS 故障？**

不能。还可能是应用缓存、连接池或旧长连接。要区分它到底有没有重新查询，以及实际使用了哪个解析结果。

**TTL 到零，所有解析器都必须立刻把旧对象从内存物理删除吗？**

不必如此。普通有效缓存不再按原许可直接使用，但对象可能为统计或受控 Serve Stale 策略保留。有效性与物理对象存在是两件事。
