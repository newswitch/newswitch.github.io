# PTP、硬件时间戳与 PHC 时钟体系

普通 NTP 已经能通过报文估计时间，为什么还需要 PTP？关键不是简单增加同步频率，而是把时间戳获取位置、网络设备参与方式和时钟控制链纳入更精细的设计。

PTP 是 Precision Time Protocol，相关标准由 [IEEE 1588 工作组](https://sagroups.ieee.org/1588/) 维护。以下讨论常见 PTPv2 概念，不把某一个行业 Profile 的规则当成所有网络的通用要求。

## 1. 软件时间戳里可能混入哪些等待

假设应用决定发送同步报文的时刻是 S，但报文真正离开网卡的时刻是 W：

```text
应用准备 → 调度与协议栈 → 内核队列 → 驱动 → 网卡队列 → 实际发送
    S                                                     W
```

若在靠近应用的位置记录时间，中间的等待就会影响测量。接收方向也有类似的驱动、中断、协议栈和调度延迟。

硬件时间戳让 NIC 或 PHY 等更接近实际收发的位置记录时刻，减少这部分软件路径噪声。但硬件仍有测量位置和校准误差，网络中仍可能排队，所以“硬件时间戳”不是“绝对无误差”。

## 2. Sync 与延迟测量怎样配合

仅知道发送方发出 Sync 的时刻，还不足以直接设定接收方时间，因为报文在路上有延迟。

以常见端到端延迟机制为例：

```text
上游时钟                           跟随时钟
发送 Sync ──────────────────────→ 接收 Sync
发送 Follow_Up（两步模式）───────→ 获得精确发送时间戳
接收 Delay_Req ←───────────────── 发送 Delay_Req
发送 Delay_Resp ─────────────────→ 获得请求到达上游的时间戳
```

双方组合发送和接收时间，估计路径延迟与时钟偏差，仍然依赖相应对称性和校正假设。

- **One-step（一步）**：按设备能力在 Sync 等消息中直接提供所需精确时间信息。
- **Two-step（两步）**：先发 Sync，再通过 Follow_Up 补充精确的实际发送时刻。

两步并不意味着“精度天生低一档”。区别在于精确时间戳如何进入协议交换，实际精度还取决于硬件、路径和控制算法。

## 3. E2E 与 P2P 测量对象不同

E2E（End-to-End）主要测量跟随时钟与其上游时钟之间的路径延迟；P2P（Peer-to-Peer）测量相邻 PTP 端口间的链路延迟，再结合相应设备校正。

P2P 不是“任意两个应用端点互相 ping”，它需要相邻设备具备兼容的协议能力。整条路径采用什么机制要与 Profile 和设备角色一致，不能随意在两端各选一种。

LinuxPTP 的端口、延迟机制与时间戳模式可以在 [ptp4l 文档](https://www.linuxptp.org/documentation/ptp4l/) 中对应到具体实现，但理解协议不需要先背参数。

## 4. GM、OC、BC、TC 是什么关系

| 角色 | 名称 | 作用 |
| --- | --- | --- |
| GM | Grandmaster，主参考时钟 | 为一个同步域提供最终参考来源；是角色，不必是唯一设备类型 |
| OC | Ordinary Clock，普通时钟 | 具有单个 PTP 端口，可提供时间或跟随上游 |
| BC | Boundary Clock，边界时钟 | 多个 PTP 端口，上游同步本地时钟，再向下游提供参考 |
| TC | Transparent Clock，透明时钟 | 测量并校正报文经过设备的驻留时间等，不按 BC 的方式逐级重建参考 |

例如：

```text
GM → BC 的上游端口 → BC 本地时钟 → BC 下游端口 → 服务器
```

BC 把同步层次分段，每段仍有测量和本地时钟控制误差。TC 则让接收方有机会扣除交换设备引入的驻留时间；具体校正还依赖 E2E/P2P 类型和硬件能力。

普通交换机也可能转发 PTP 包，但“能转发”不等于它能提供 BC/TC 的时间质量帮助。

## 5. BMCA 与 Profile 为什么不能忽略

BMCA（Best Master Clock Algorithm）依据通告的优先级、时钟质量、标识等数据选取参考，具体比较和角色规则取决于 Profile。它不是测一遍所有服务器延迟，然后选择 RTT 最小者。

Profile 规定某类应用采用哪些可选能力、默认值和约束。即使都写着“支持 PTPv2”，以下条件不匹配仍可能无法协同：

- domainNumber 不同。
- 二层以太网与 UDP/IP 承载不同。
- 延迟机制、单播／组播交互不同。
- 消息周期、选源规则或时间尺度要求不同。
- 设备支持的行业 Profile 不一致。

domainNumber 用于逻辑区分，不是 VLAN、密码或访问控制。错误或不可信的参考源仍需要通过管理边界与适用安全机制约束。

## 6. 网卡时钟同步，为什么系统时间仍可能不准

PHC 是 PTP Hardware Clock，PTP 硬件时钟。Linux 通过标准接口暴露它，相关框架见 [Linux 内核 PHC 文档](https://docs.kernel.org/driver-api/ptp.html)。它通常与系统时钟不是同一个计时对象。

常见硬件时间戳接收端架构为：

```text
远端 PTP 参考
  → NIC 硬件收发时间戳
  → ptp4l 控制 PHC
  → phc2sys 将 PHC 与系统时钟关联并同步
  → 应用读取系统时钟
```

因此 ptp4l 报告 PHC 已很好地跟随上游，只证明链路中的这一段。若系统时钟没有正确同步，应用日志仍可能偏差很大。

同步方向也不是永远固定的：当本机向网络提供时间时，可以存在由系统参考去校准 PHC 的设计。要明确每个时钟的来源和控制者，避免多个守护进程同时争夺同一个时钟的校准权。

## 7. 时间尺度差异会造成整数秒偏差

常见硬件 PTP 场景中，PHC 跟随 PTP 时间尺度，而系统墙上时间按 UTC 使用，两者需要正确处理 UTC 偏移与闰秒信息。

如果这层转换错了，可能出现“亚微秒偏差指标很好，应用日期却差几十秒”的现象。前者可能衡量同一时间尺度内的同步，后者暴露时间尺度转换错误。相关细节见 [phc2sys 的 Time Scale Usage](https://www.linuxptp.org/documentation/phc2sys/#time-scale-usage)。

普通容器通常也不会天然得到一块独立、完整管理的硬件时钟。它读取哪个时钟、能否访问 PHC、谁有权校时，是宿主机与运行时的边界，不能在每个容器里随意启动校时进程来解决。

## 8. 如何理解同步精度的预算

最终应用时间误差可能来自：

```text
参考源误差
  + 网络不对称与未校正排队
  + 硬件时间戳与设备校准误差
  + PHC 控制残差
  + PHC 到系统时钟的同步误差
  + 应用读取与事件记录位置的偏差
```

这是一份误差来源清单，不表示统计上总能把每项最大值简单相加成为精确预测。重点是指标必须与测量位置对应。

PTP 在受控且硬件配合的网络中可以支持很高精度，但不能仅凭软件名称承诺微秒或纳秒指标。跨普通公网、缺少硬件时间戳或路径严重不对称时，预期能力应重新评估。

## 9. 思考与解答

**时间戳显示九位小数，就有纳秒准确度吗？**

没有。那只是表示粒度，还要看测量位置、参考源与误差链。

**交换机支持转发 PTP 包，就等于支持透明时钟吗？**

不等于。TC 需要测量和校正等专门能力，普通报文转发不具备这些语义。

**ptp4l 的偏差很小，应用时间为何还不对？**

先区分它报告的是哪个时钟和哪个参考。PHC 到系统时钟的同步、UTC 偏移、应用记录位置都可能尚未正确处理。
