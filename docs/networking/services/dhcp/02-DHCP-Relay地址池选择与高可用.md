# DHCP Relay、地址池选择与高可用

企业可能有几十个 VLAN，却只运行一组集中式 DHCP 服务器。客户端最初发的是本地广播，广播又不会被普通路由转发，这两件事如何同时成立？关键是 DHCP Relay，中继代理。

## 1. 中继不是把所有二层广播扩散到远端

中继在客户端所在链路接收 DHCP 报文，以协议规定的方式转交服务器，并为回复保留足够的链路上下文。它不会把远端 DHCP 服务器变成当前 VLAN 的普通二层邻居。

```text
VLAN 10 客户端 ─广播→ VLAN 10 中继接口 ─转交→ DHCP 服务器
VLAN 20 客户端 ─广播→ VLAN 20 中继接口 ─转交→ 同一 DHCP 服务器
```

服务器需要知道请求来自 VLAN 10 还是 VLAN 20，否则即使池中有大量地址，也可能分出错误子网的配置。

## 2. giaddr 如何帮助选择子网

以传统 DHCPv4 中继场景为例，中继在 giaddr 中放入代表客户端链路的地址。服务器依据中继信息和配置选择合适子网，再选择池和参数，并将回复交给相应中继。

假设：

| 客户端网络 | 中继提供的链路信息 | 服务器应选择的子网 |
| --- | --- | --- |
| 办公网 | giaddr 对应 `10.10.10.1` | `10.10.10.0/24` |
| 访客网 | giaddr 对应 `10.10.20.1` | `10.10.20.0/24` |

这些地址仅用于说明关联关系。具体实现还可能使用链路选择选项、接口或客户端分类等，不应把“只看 giaddr”当作所有拓扑的唯一规则。

回复到中继之后，中继再按客户端状态和报文标志，在本地链路单播或广播交付。服务端到中继的单播可达，不保证最后一段客户端链路也正确。

### 2.1 一次经中继分配，往返地址分别代表谁

假设客户端位于 `10.10.10.0/24`，中继客户端侧地址是 `10.10.10.1`，服务器地址为 `192.0.2.53`：

| 阶段 | 关键上下文 | 接收方要完成的事 |
| --- | --- | --- |
| 客户端发送 Discover | 尚无地址，广播，UDP 68 → 67 | 中继识别该客户端链路 |
| 中继转交服务器 | 填入 giaddr，保留 xid 与客户端身份，通常单播至服务器 | 服务器根据链路与策略选池 |
| 服务器返回 Offer/ACK | 在 giaddr 非零的基础中继场景，回复中继 UDP 67 | 中继将响应对应到原客户端链路 |
| 中继交付客户端 | 根据客户端状态、标志与链路能力，发往客户端 UDP 68 | 客户端匹配事务并处理配置 |

所以 DHCP 服务器不需要在客户端 VLAN 上拥有一个二层端口；但它需要到中继的返回路径，中继也必须能正确交付最后一段。IP 包的源地址、中继地址和“被分配的客户端地址”不是同一个对象。回复规则见 [RFC 2131 §4.1](https://www.rfc-editor.org/rfc/rfc2131.html#section-4.1)。

基础中继下，Option 54 通常仍标识服务器，而不是把中继自动变为租约签发者。因此已配置的客户端后续通常可直接单播续租；显式代理或 Server Identifier Override 等扩展需另行判断。

### 2.2 giaddr 为什么有时不能同时承担两种职责

传统 giaddr 同时表达“客户端在哪条链路”和“服务器向哪里回信”。但客户侧地址可能在服务器不可直接到达的路由域中，此时用它回信就不合适。

Link Selection 子选项将职责拆开：giaddr 保留可达的中继回复地址，子选项表达实际分配链路。服务器不能看到可达的中继管理地址，就把管理网地址池发给办公终端。机制见 [RFC 3527](https://www.rfc-editor.org/rfc/rfc3527.html)。

跨路由传送时，服务器也不能指望从原始以太网 VLAN Tag 自动还原接入位置；它依赖的是保留下来的 DHCP 上下文及服务端映射。

## 3. Option 82 比 giaddr 多表达什么

Option 82 是 Relay Agent Information Option，中继代理信息选项，常见子项包括：

- **Circuit ID**：接入电路或端口等信息。
- **Remote ID**：帮助识别接入设备或远端主体的信息。

它可以帮助服务器区分接入位置、应用策略并留下归属记录，定义见 [RFC 3046](https://www.rfc-editor.org/rfc/rfc3046.html)。

但 Option 82 本身不是客户端的密码或数字签名。若不可信终端能够伪造并被无条件接受，它就不能作为可靠授权依据。接入边界需要明确由谁插入、是否允许保留已有信息，以及服务器信任哪些中继。

这与 [DHCP Snooping 与地址绑定](../../security/layer2-security/01-地址绑定DHCP-Snooping-DAI与IPv6接入保护.md)有联系，但不是同一个功能：中继负责报文跨链路交互，Snooping 负责在接入交换边界观察和约束 DHCP 行为。

## 4. 地址池、租约库和 IPAM 各管一部分

| 对象 | 记录的内容 | 不能替代什么 |
| --- | --- | --- |
| 子网配置 | 前缀、网关、DNS 等参数 | 不能代替实时租约 |
| 动态池 | 哪些地址允许动态分配 | 不能证明这些地址线上无人手工使用 |
| 保留项 | 特定身份应使用的地址或参数 | 不自动等于静态手工配置 |
| 租约库 | 已承诺给哪个客户端、何时到期、当前状态 | 不能完整描述组织的地址设计意图 |
| IPAM | 地址空间归属、用途、预留和分配意图 | 不能天然获知所有实时在线状态 |

例如 IPAM 里把 `10.10.10.50` 标为打印机静态地址，DHCP 动态池却仍允许分配它，冲突不会因为“已经做了登记”而自动消失。需要使意图与实际分配范围一致。

另一个常见误判是把所有池的空闲数相加。办公网有空闲地址，不能直接补给已经耗尽的访客网，除非实际地址规划和链路结构允许。

## 5. 两台 DHCP 服务器，不等于高可用

双服务器首先要回答：谁有权把某个地址承诺给客户端？如果两台互不知情的服务器都认为地址 X 空闲，就可能分别将 X 租给两个终端。

三种模型需要分清：

| 模型 | 如何避免普通重复分配 | 局限 |
| --- | --- | --- |
| 独立拆分地址池 | 两台使用不重叠的分配范围 | 一台故障后，另一台不天然掌握其全部租约和资源 |
| 热备 | 以伙伴状态和租约协调规则管理接管 | 接管条件、同步延迟和剩余租约需要专门设计 |
| 负载分担 | 按规则分工处理客户端，同时协调状态 | 不是在前面加普通 UDP 负载均衡就完成 |

Kea 的 HA 实现可作为理解伙伴通信、租约更新、故障状态和同步过程的实例，见 [Kea High Availability](https://kea.readthedocs.io/en/stable/arm/hooks.html#high-availability)。这些实现细节不是基础 DHCP 协议自动赋予所有产品的能力，也不意味着不同厂商可以直接互为 HA 伙伴。

### 5.1 沿一个地址的使用权理解同步

假设 X 最初可分配，A 向终端 C 确认租用 X，B 稍后可能接管。关键不是“两台最终都收到过一份数据库”，而是 B 何时获得足够依据，保证自己不会再把 X 承诺给另一个终端。

```text
候选地址 X
  → A 判断分配权与现有租约
  → 形成对 C 的租约承诺，并按 HA 机制同步/限制分配权
  → 向 C 确认
  → C 续租、释放或租约到期
  → 伙伴按协调后的状态回收 X
```

这是需要满足的状态关系，不是所有产品固定采用的执行时序。有的路径会等待伙伴确认，有的在允许的降级模式继续服务；必须结合其分配权规则理解，不能仅凭“同步是异步的”就断言一定冲突，也不能认为任何异步复制都天然安全。

Kea 的租约更新、伙伴状态和全量同步都有独立机制；是否等待租约更新确认、伙伴失联后的服务范围受 HA 配置与状态影响。应以所用版本的 [Kea HA 文档](https://kea.readthedocs.io/en/stable/arm/hooks.html#high-availability) 为准，不把一种厂商的行为写成 DHCP 通用保证。

## 6. 伙伴失联为什么比进程退出难判断

设服务器 A 和 B 互相收不到心跳，但两台都还能收到客户端请求。它们无法仅凭“伙伴不回复”区分：

- 对方进程已退出。
- 伙伴同步链路断了，但对方仍在服务。
- 自己与部分网络隔离。

如果双方立刻接管全部地址空间，就可能产生冲突承诺；若始终拒绝接管，又会损失可用性。HA 协议需要通过状态机、可接管范围、租约信息和额外判据管理这一权衡。

因此，高可用还包括租约数据库、复制链路、中继投递范围以及配置一致性。两台进程都存活，不代表这套状态协调正确。

## 7. 续租正常而新接入失败，怎样从原理解释

已经拥有地址的客户端通常能单播请求原服务器；新客户端首先依赖广播与中继发现。两个阶段的数据路径可能不同。

所以存在以下可能：

```text
单播续租路径正常
本地广播／中继选择或转交异常
→ 旧客户端可续租，新客户端无法完成初次分配
```

也可能只是该子网池耗尽，新分配失败，而已有租约仍能续订。判断时应分别看报文路径与资源状态，而不是笼统归为“DHCP 有时好有时坏”。

### 7.1 四个状态层必须分别成立

| 状态层 | 成功意味着什么 | 成功仍不能证明什么 |
| --- | --- | --- |
| 报文可达 | 客户端、中继、服务器间消息能交付 | 子网映射正确 |
| 分配策略 | 身份、子网、池和参数匹配 | 地址使用权没有冲突 |
| 租约与 HA | 当前节点有合法分配权，状态可协调 | 客户端已收到 ACK |
| 终端网络配置 | 客户端接受了配置 | 网关、DNS 和业务服务均可用 |

例如池选对、ACK 已发出，仍可能因返回中继路径失败而没有地址；地址已获得，仍可能因下发了错误网关而无法跨网段。这个分层比只看服务器进程是否存活更能解释现象。

旧备份恢复尤其要看第三层：备份中 X 空闲，但备份之后 A 已把 X 租给 C。恢复节点启动成功不等于可以忽略 C 的尚有效承诺；需要按 HA 恢复或租约重建规则进入可服务状态。

## 8. 思考与解答

**服务器能 ping 通中继，为什么客户端还是没有地址？**

ICMP 可达没有证明 UDP 交互、选池、客户端事务匹配和最后一段交付都成功。需要沿请求与回复的不同上下文判断，而不是把一个连通性结果推广到整个协议。

**giaddr 是中继管理网地址，服务器就应该分管理网地址吗？**

不一定。若使用 Link Selection 等扩展，应按指定的客户端链路选池；giaddr 此时主要承担返回中继的可达地址角色。

**两台服务器都看到同一个 Request，是否都应该回复以提高可靠性？**

不能由“都收到”直接决定。独立服务器选择、HA 客户端分工和分配权各有规则；未经协调同时确认冲突租约，会损害正确性。

**伙伴心跳已经恢复，租约状态一定同步完成了吗？**

不一定。通信恢复、租约同步完成、恢复节点重新取得服务资格是不同阶段。是否立即服务由产品 HA 状态机决定。

**增加一台同配置服务器，能直接提升可用性吗？**

不能保证。若允许分配相同地址却不协调租约，反而增加冲突风险。必须先明确分配权和故障接管规则。

**Option 82 能证明请求来自某个真实用户吗？**

不能单独证明。它提供接入上下文，可信程度依赖插入者与信任边界；用户身份还需要认证体系。

**租约备份恢复后，服务器认为空闲的地址就能立即随便分配吗？**

不能。备份之后可能已发出新租约，旧状态恢复后需要协调和校验，否则服务器可能把仍在使用的地址重新发给别人。
