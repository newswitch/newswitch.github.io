# DHCPv4 地址分配、DORA 与租约状态机

电脑刚接入网络，还不知道自己的 IPv4 地址，也不知道 DHCP 服务器在哪里。它怎样发出第一条请求？答案是：DHCP 为初始化状态定义了特殊的源地址、广播和报文处理方式，不要求客户端先具备普通单播通信的全部条件。

## 1. DHCP 不在每个业务包的转发路径上

DHCP 客户端向服务器申请地址、掩码、路由器、DNS 等参数。成功后，应用按这些参数通信，业务数据一般不经过 DHCP 服务器。

因此服务器宕机时，常见现象是新终端拿不到地址，老终端在剩余租约有效期间暂时正常。这并非矛盾，而是控制状态已有缓存。

“服务器发出了 ACK”也只表示分配协议走到相应状态，不保证下发的网关可达、DNS 健康或目标业务正常。

## 2. DORA 四步各自解决一个问题

常见初次分配如下，实际路径可能经过中继：

```text
客户端                           DHCP 服务器
   ── Discover：谁能提供配置？ ──────→
   ←─ Offer：我可以提供这些资源 ──────
   ── Request：我选择并申请这份配置 ─→
   ←─ ACK：确认租约与参数 ────────────
```

客户端最初通常使用 `0.0.0.0` 作为源地址，向本地广播发送 Discover。DHCPv4 客户端与服务器分别使用 UDP 68、67 端口。

Offer 是候选，不等于客户端已经可以永久占用该地址。网络中可以有多个服务器发 Offer，客户端按实现策略选择，不保证永远选择最快、最近或地址最小的服务器。

SELECTING 阶段的 Request 通常广播并包含选中服务器信息，使其他服务器知道自己的 Offer 没有被接受。后续续租的 Request 则可以单播；不要把所有 DHCPREQUEST 都解释成同一个步骤。消息与状态定义见 [RFC 2131](https://www.rfc-editor.org/rfc/rfc2131.html)。

## 3. 看懂这些字段，才不会把身份和地址混淆

| 字段或选项 | 含义 |
| --- | --- |
| xid | 事务标识，帮助匹配一次交换的请求与响应 |
| chaddr | 客户端硬件地址字段 |
| Client Identifier | 客户端标识选项，可能影响服务器如何识别租约主体 |
| ciaddr | 客户端已经知道并使用的地址，续租等阶段会用到 |
| yiaddr | 服务器给客户端的地址，即“你的地址” |
| giaddr | 中继网关地址，帮助服务器识别客户端所在链路与回复中继 |
| Server Identifier | 区分提供服务的服务器 |
| Requested IP Address | 客户端希望申请或复用的地址 |

掩码、路由器、DNS、租期等通过选项传递，选项定义见 [RFC 2132](https://www.rfc-editor.org/rfc/rfc2132.html)。客户端身份不总是 MAC 的同义词：系统重装、标识策略变化或镜像克隆都可能影响租约识别。

DHCP 通常给出的是**使用期限**，而不是所有权。固定保留地址也是服务器的分配策略，不表示客户端从此不需要租约交互。

## 4. T1、T2 与到期是三个不同时间点

假设服务器给出 8 小时租期，且没有另行指定不同的 T1/T2：

```text
获取租约          T1：通常为租期 50%       T2：通常为 87.5%       到期
  0 小时 ───────────── 4 小时 ───────────────── 7 小时 ─────────── 8 小时
  BOUND                 RENEWING                REBINDING          失去使用权
```

- **BOUND**：租约有效，正常使用地址。
- **RENEWING**：通常向原服务器单播 Request，争取延长租期。
- **REBINDING**：原服务器一直未成功响应时，广播请求，让其他能够合法处理此租约的服务器参与。
- **到期**：必须停止使用失效租约对应的地址，重新获取有效配置。

收到成功续租 ACK 后，客户端按新参数重新计时，不需要等到旧租约最后一秒。4 小时和 7 小时是这个例子的默认比例计算，不是每个网络的固定常量。

这也说明，DHCP 暂时无响应与 DHCPNAK 不同：无响应可能继续重试并使用尚有效租约；NAK 则是服务器明确否定当前申请，客户端需要按相应状态规则重新开始。

## 5. 重启后不一定重新走完整 DORA

客户端如果保留了旧租约信息，可能进入 INIT-REBOOT，先尝试确认原地址能否继续使用，而不是从 Discover 开始重新找候选。

如果机器移动到了另一个 VLAN，旧地址可能已不适用于当前链路。服务器判断需要结合请求内容、所在子网及自身授权范围，不能不加区分地接受旧地址，也不应对不了解的租约随意发 NAK。

所以一段报文只出现 Request/ACK，并不一定意味着抓包遗漏了 Discover/Offer，也可能就是合法的状态分支。

## 6. 地址池还有空位，为什么也可能无法分配

“某个池剩余 100 个地址”并不足够，还要同时满足：

1. 客户端被归入正确子网或共享网络。
2. 地址符合客户端类别、保留和策略限制。
3. 地址没有有效租约或冲突隔离状态。
4. 服务器能够提交分配状态并返回响应。

反过来，DHCP 数据库认为地址空闲，也不等于线上一定没人手工配置它。客户端进行地址冲突检测、服务器进行适用的探测，都只是降低风险，不能完全替代静态地址与动态池的统一规划。IPv4 地址冲突检测的独立机制见 [RFC 5227](https://www.rfc-editor.org/rfc/rfc5227.html)。

## 7. 租期长短为什么是资源和恢复的权衡

较长租期减少稳定客户端的续租频率，并给短暂服务故障留出更大缓冲，但离网地址可能更久才被回收。较短租期可更快回收地址和传播某些配置变化，却增加续租负载与客户端对服务器持续可用性的依赖。

一个仅用于量级理解的模型：N 个持续在线客户端，租期 L 秒，每次在约一半租期成功续租，则续租请求平均速率约为 `2N/L`。它不包含新上线、重传、多个中继重复投递和集中重启峰值，不能直接拿来作为服务器容量指标。

## 8. 思考与解答

**DHCP 服务中断，为什么已上线主机还能通信？**

因为租约尚有效，路由、邻居和 DNS 配置等状态可能已经存在，业务数据不必经 DHCP 服务器转发。持续故障最终仍会影响续租与新接入。

**Request 一定是 DORA 的第三个广播包吗？**

不是。续租、重绑定和重启确认都可能使用 Request，要结合客户端状态、目的地址与选项判断。

**把租期改短，是否立刻让所有客户端换新配置？**

不是。已发出的旧租约仍有自己的时间状态，客户端通常在下一次相关交互中获取新参数；不能将服务器改配置当成对所有客户端的即时推送。
