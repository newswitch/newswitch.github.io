# 训练与推理通信流量模型

设计 AI 网络前先回答：通信是谁产生的、何时发生、每次多大、多少 Rank 同时参与。
相同 GPU 数量，数据并行、张量并行和专家并行产生的网络形态完全不同。

## 1. 先区分三个量

```text
计算量：GPU 执行矩阵乘和其他 Kernel 的时间
通信量：跨 GPU 搬运的有效数据量
同步约束：某个 Rank 是否必须等待其他 Rank
```

网络带宽相同，同步更频繁的作业对尾时延和慢 Rank 更敏感。平均吞吐正常也可能因
一条 Rail 的 P99 抖动拖慢整个训练 Step。

## 2. Collective 基础

假设有 4 个 Rank：

| Collective | 输入与输出 | 常见用途 |
|---|---|---|
| Broadcast | 一个 Rank 的数据发给全部 Rank | 参数或元数据分发 |
| Reduce | 多 Rank 数据归约到一个 Rank | 聚合统计 |
| AllReduce | 所有 Rank 归约并获得完整结果 | 数据并行梯度同步 |
| AllGather | 每个 Rank 的分片汇聚为完整数据 | 参数/激活拼接 |
| ReduceScatter | 归约后每个 Rank 只保留一片 | ZeRO、分片并行 |
| All-to-All | 每个 Rank 向每个 Rank 发送不同分片 | MoE Token Dispatch |
| Send/Recv | 两个 Rank 点对点传输 | 流水并行 Stage 间激活 |

Collective 是语义，不等于固定算法。NCCL 可以根据拓扑、消息大小和版本选择不同算法。

## 3. 数据并行 DP

每个 Rank 保存完整模型，处理不同 Batch。反向传播后需要同步梯度，典型是 AllReduce。

若梯度总有效载荷为 `M` 字节、Rank 数为 `N`，Ring AllReduce 每个 Rank 的网络传输量
近似为：

```text
2 × (N - 1) / N × M
```

这是算法数据量，不等于线上以太网字节；还要加协议头、重试、对齐和实现开销。

流量特征：

- 梯度 Bucket 计算完成后陆续通信；
- 可与后续反向计算重叠；
- Step 末尾存在全局同步；
- 一个慢 Rank 会拖住整个通信组。

## 4. ZeRO 与分片数据并行

ZeRO 不同阶段对参数、梯度和优化器状态做分片，常见通信包括：

- ReduceScatter：把归约后的梯度分片留在各 Rank；
- AllGather：计算前临时收集参数分片；
- 某些实现使用分层通信或 Prefetch。

只看“总字节数”不够。大量较小 AllGather 可能更受启动时延影响，大消息更受带宽限制。

## 5. 张量并行 TP

一个算子被多 GPU 分片。每层或每几个算子就可能触发 AllReduce、AllGather 或
ReduceScatter。

流量特征：

- 频率高，处于模型关键路径；
- 对低时延、GPU/NVLink 拓扑非常敏感；
- 通常先把 TP Group 放在单机 NVLink/NVSwitch 域；
- 跨节点 TP 会显著提高对 NIC 和 Fabric 的要求。

调度不能只保证“8 张 GPU”，还要保证同一 TP Group 的 GPU 位于预期高速互联域。

## 6. 流水并行 PP

模型层被分为多个 Stage，前向传激活，反向传激活梯度：

```text
Stage0 --activation--> Stage1 --activation--> Stage2
Stage0 <--gradient---- Stage1 <--gradient---- Stage2
```

主要是相邻 Stage 间点对点流量。Micro-Batch 调度决定是否出现气泡和突发。

风险：

- Stage 放置不均导致某链路持续热点；
- 一个 Stage 计算变慢使上下游等待；
- PP 流与 DP AllReduce 在相同时间窗口竞争。

## 7. 专家并行 EP

Mixture of Experts 将 Token 路由到不同专家，典型通信是 All-to-All：

```text
每个 Rank
→ 按专家拆分 Token
→ 向多个 Rank 同时发送
→ 专家计算
→ 再次 All-to-All 返回
```

这是典型 Many-to-Many 流量。Token 分布不均会同时造成 GPU 负载不均和网络热点。

需要观察：

- 每个专家收到的 Token 数；
- All-to-All 消息大小分布；
- Rank 与 Rail 的映射；
- 是否有少数端口持续成为汇聚热点；
- Capacity Factor 和 Load Balancing Loss。

## 8. 多维并行叠加

真实训练常同时使用 DP×TP×PP×EP。必须记录 Rank 到物理拓扑的映射：

```text
Global Rank
├── Node
├── Local Rank / GPU
├── TP Group
├── PP Stage
├── DP Group
├── EP Group
└── NIC / Rail / NUMA
```

合理映射通常让通信最频繁、最敏感的组留在更快的拓扑域，再把带宽型通信扩展到跨节点。
具体优先级取决于模型和框架，不能套固定结论。

## 9. 推理通信

### Prefill

长 Prompt 批量计算，矩阵较大，吞吐和跨 GPU 并行通信重要。行为更接近高吞吐批处理。

### Decode

每步只生成少量 Token，反复执行，单步时延和抖动更重要。小消息和同步开销可能主导。

### 其他路径

- Tensor Parallel Collective；
- Expert Parallel All-to-All；
- KV Cache 在节点/实例间迁移；
- Prefill/Decode 分离后的 KV 传输；
- 请求入口、模型加载和存储流量。

训练网、推理网和存储网是否共用，要由流量时间特征、SLO、故障域和成本决定。

## 10. 从模型估算网络需求

建立工作负载表：

| 字段 | 示例 |
|---|---|
| 并行维度 | DP=16、TP=8、PP=4、EP=8 |
| GPU/节点 | 8 |
| 精度 | BF16/FP8 |
| 梯度/参数规模 | 实测或框架 Profile |
| Collective | AllReduce、AllGather、All-to-All |
| 消息大小分布 | P50/P95/Max |
| 调用频率 | 每层、每 Step |
| 可重叠比例 | Profile 实测 |
| 目标 Step Time | 业务要求 |

用 Profiler 和 NCCL 日志验证估算。不要仅用参数量乘字节数推断全部通信，因为分片、
重计算、梯度累积、融合 Bucket 和并行实现都会改变路径。

## 11. 实验

用 PyTorch Distributed 或 nccl-tests 分别产生：

1. 大消息 AllReduce；
2. 小消息高频 AllReduce；
3. AllGather + ReduceScatter；
4. All-to-All；
5. 两个 Rank 的 Send/Recv。

记录：

- 消息大小、Rank 和节点分布；
- `algbw`、`busbw` 或实际 GB/s；
- P50/P95/P99 时延；
- GPU 利用率与通信 Kernel 时间；
- 每个 NIC/Rail 吞吐；
- 交换端口队列和 ECN/PFC 计数。

## 12. 掌握标准

拿到一个模型的并行配置后，应能在不看网络配置的情况下先画出主要通信组、Collective、
频率和同步点；再据此判断应优先关注 NVLink、单 Rail 带宽、全局二分带宽还是尾时延。
