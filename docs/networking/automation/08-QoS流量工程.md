# QoS 分类、队列与流量工程

QoS 不能创造带宽。它决定拥塞时谁先排队、谁先丢、谁被限速，以及突发怎样被吸收。

## 1. 从拥塞点开始

```text
入口 100 Gbit/s
→ 出口只有 25 Gbit/s
→ 短时间输入超过输出
→ 队列积累
→ 延迟升高
→ 缓冲耗尽后丢包
```

如果没有拥塞，严格优先级和复杂队列通常不会改变转发结果。设计前先回答：

- 哪个接口、哪个方向拥塞？
- 是微突发还是持续超载？
- 哪类业务对延迟、抖动或丢包敏感？
- 缓冲和队列实际多大？
- 上游能否整形或降低发送速率？

## 2. QoS 处理链

```mermaid
flowchart LR
    A["Classify<br/>识别流量"] --> B["Mark<br/>DSCP/802.1p"]
    B --> C["Police/Meter<br/>测量与监管"]
    C --> D["Queue<br/>排队与调度"]
    D --> E["AQM/Drop<br/>主动丢弃"]
    E --> F["Shape<br/>按速率发送"]
```

| 动作 | 含义 |
|---|---|
| 分类 | 按地址、端口、协议、应用或入接口识别 |
| 标记 | 写入 DSCP、802.1p 等优先级字段 |
| 监管 Policing | 超过速率时丢弃或重标记，通常不等待 |
| 整形 Shaping | 把超出速率的流量放入队列延后发送 |
| 排队 Queuing | 将流量放入不同队列 |
| 调度 Scheduling | 决定各队列发送顺序和带宽 |
| AQM | 在队列完全满之前按算法标记/丢弃 |

## 3. DSCP 与信任边界

DSCP 位于 IP 头，终端也可以自行标记。必须定义：

```text
谁有权标记
在哪个入口信任
不可信标记如何重写
跨 WAN、云、隧道后是否保留
每跳如何映射到硬件队列
```

只写 DSCP 而不配置队列映射，没有实际优先效果；只配置队列而入口分类错误，也会让流量进入错误队列。

通用业务分类示例：

| 类别 | 特征 | 策略思路 |
|---|---|---|
| 网络控制 | 路由、BFD、管理关键流 | 小带宽、低时延、严格限额 |
| 交互/语音 | 对时延和抖动敏感 | 优先队列，防止饿死其他队列 |
| 关键事务 | 对延迟和丢包敏感 | 保证带宽 |
| 批量备份 | 吞吐重要、可延迟 | 普通/低优先，可整形 |
| 未知流量 | 无明确业务归属 | Best Effort |

严格优先队列必须设上限，否则持续高优先流量会让普通队列饥饿。

## 4. Token Bucket 心智模型

令牌按速率 `r` 进入容量为 `B` 的桶：

- 发送一个字节消耗相应令牌；
- 平均速率受 `r` 约束；
- 桶中累积令牌允许最多约 `B` 的突发；
- Policer 在无足够令牌时丢弃/降级；
- Shaper 则让报文等待令牌。

`B` 太小会误伤正常 TCP 突发，太大会允许过大的短时突发冲击下游。

## 5. 队列、缓冲与时延

Little's Law 的直觉：

```text
排队时延 ≈ 队列中数据量 / 出口速率
```

大缓冲能吸收突发，但持续拥塞时会产生 Bufferbloat。观察接口平均利用率不足以发现毫秒级微突发，需要硬件队列水位、丢弃计数或更高频 Telemetry。

常见调度：

- Strict Priority：优先队列先发；
- WRR：按轮询权重分配；
- DWRR：更好处理不同包长；
- 保证带宽 + 共享剩余带宽：常见硬件模型。

## 6. 端到端一致性

一条流可能经过：

```text
服务器 vSwitch
→ ToR
→ Spine
→ 防火墙
→ WAN/云网关
→ 远端交换机
```

逐跳检查：

- 分类是否一致；
- 隧道外层 DSCP 是复制、重写还是清零；
- 每台设备队列数量和映射是否相同；
- 云/运营商是否承诺保留标记；
- 出口整形是否匹配实际线路速率；
- 统计口径是原始类、队列还是丢弃原因。

## 7. Linux `tc` 实验

在 Network Namespace 或实验主机中创建受限链路，使用 `tc` 观察整形与队列。执行前先确认不会影响宿主机生产接口。

实验思路：

1. 两个 Namespace 产生交互流和批量流；
2. 将出口限制为固定速率；
3. 不做 QoS，记录 RTT、吞吐和丢包；
4. 增加两类队列，给交互流保证；
5. 对批量流整形；
6. 比较队列统计和业务结果；
7. 故意让优先流持续占满，观察普通流饥饿；
8. 增加优先队列限额后再次验证。

查看：

```bash
tc -s qdisc show dev <interface>
tc -s class show dev <interface>
ip -s link show dev <interface>
ss -ti
```

## 8. QoS 排障

| 现象 | 检查 |
|---|---|
| 标记正确但仍高延迟 | 队列映射、拥塞点是否在别处 |
| 无明显利用率但有丢包 | 微突发、采样周期、缓冲水位 |
| 普通业务完全无带宽 | 严格优先队列是否无限制 |
| TCP 吞吐低 | Policer 丢包、RTT、窗口、MTU |
| 跨隧道后策略失效 | 外层 DSCP 复制/重写 |
| 只有一个方向异常 | QoS 是逐接口逐方向生效 |

## 9. 与 AI 网络的衔接

GPU 集群中的 RDMA/RoCE 需要进一步学习 PFC、ECN、DCQCN、无损/近无损网络和拥塞树分析。不要直接把普通 TCP QoS 策略照搬为 RoCE 设计。本篇提供的是队列、标记、拥塞和验证基础，后续进入 AI 集群网络模块。

## 10. 掌握标准

你应能从业务 SLO 推导分类和带宽策略，指出真实拥塞点，解释 Policing 与 Shaping 的不同，计算队列积压造成的时延，并通过队列计数器与端到端测试证明策略生效。
