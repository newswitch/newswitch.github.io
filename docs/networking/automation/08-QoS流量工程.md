# QoS 分类、队列与流量工程

QoS 不能创造带宽。它决定拥塞时谁先排队、谁先丢、谁被限速，以及突发怎样被吸收。

## 1. 从拥塞点开始

```text
入口 100 Gbit/s
→ 出口只有 25 Gbit/s
→ 短时间输入超过输出
→ 队列积累
→ 延迟升高
→ 缓冲耗尽后丢包
```

没有队列竞争时，优先级调度带来的收益可能不明显；但监管、整形、标记和访问策略仍可能生效。不能把“物理接口未满”理解为“任何 QoS 都不会丢包”。设计前先回答：

- 哪个接口、哪个方向拥塞？
- 是微突发还是持续超载？
- 哪类业务对延迟、抖动或丢包敏感？
- 缓冲和队列实际多大？
- 上游能否整形或降低发送速率？

### 1.1 平均利用率为什么会漏掉微突发

假设输入以 100 Gbit/s 持续 200 微秒，出口能力为 25 Gbit/s，忽略其他开销且队列初始为空：

```text
这段时间新增积压
= (100 - 25) Gbit/s × 200 μs ÷ 8
= 1,875,000 字节，约 1.875 MB
```

如果随后完全没有新流量，仅排空这份积压还需要约 `1,875,000 × 8 / 25,000,000,000 = 0.6 ms`。若实际可用缓冲更小，则在达到这个积压之前就会丢包。

把这次突发平均到一分钟图表里，数值可以很低，但突发期间的排队与丢弃已经发生。这里需要的是对应端口/队列的水位、峰值或丢弃证据，而不是把监控平均值当作瞬时负载。

### 1.2 拥塞不只发生在物理出口

主机 qdisc、网卡发送队列、交换机共享缓冲、出口队列、运营商限速器和接收端都可能成为约束。100G 物理口前面若配置了 10G 的服务整形，业务在 10G 处排队是合理结果，不必等网口计数到 100G。

多个发送端同时回复一个接收端形成 Incast 时，单个发送者可能并不繁忙，但共同出口已被汇聚流量压满。网络整体平均空闲不能代替对这一个汇聚点的分析。

## 2. QoS 处理链

```mermaid
flowchart LR
    A["Classify<br/>识别流量"] --> B["Mark<br/>DSCP/802.1p"]
    B --> C["Meter / Police<br/>测量与超限处理"]
    C --> D["Queues + AQM<br/>队列与拥塞管理"]
    D --> E["Scheduler / Shaper<br/>选择与控制发送时机"]
    E --> F["Output<br/>实际链路发送"]
```

| 动作 | 含义 |
|---|---|
| 分类 | 按地址、端口、协议、应用或入接口识别 |
| 标记 | 写入 DSCP、802.1p 等优先级字段 |
| 监管 Policing | 超过速率时丢弃或重标记，通常不等待 |
| 整形 Shaping | 把超出速率的流量放入队列延后发送 |
| 排队 Queuing | 将流量放入不同队列 |
| 调度 Scheduling | 决定各队列发送顺序和带宽 |
| AQM | 在队列完全满之前按算法标记/丢弃 |

这是一种概念分工，不是所有 ASIC 和 Linux qdisc 的固定执行顺序。AQM 可以在入队或出队阶段处理，整形也可作用于父级或具体类。理解动作后，还要映射到目标系统的实际队列层次。模型见 [RFC 3290](https://www.rfc-editor.org/rfc/rfc3290.html)。

## 3. DSCP 与信任边界

DSCP 位于 IP 头，终端也可以自行标记。必须定义：

```text
谁有权标记
在哪个入口信任
不可信标记如何重写
跨 WAN、云、隧道后是否保留
每跳如何映射到硬件队列
```

只写 DSCP 而不配置队列映射，没有实际优先效果；只配置队列而入口分类错误，也会让流量进入错误队列。

通用业务分类示例：

| 类别 | 特征 | 策略思路 |
|---|---|---|
| 网络控制 | 路由、BFD、管理关键流 | 小带宽、低时延、严格限额 |
| 交互/语音 | 对时延和抖动敏感 | 优先队列，防止饿死其他队列 |
| 关键事务 | 对延迟和丢包敏感 | 保证带宽 |
| 批量备份 | 吞吐重要、可延迟 | 普通/低优先，可整形 |
| 未知流量 | 无明确业务归属 | Best Effort |

严格优先队列必须设上限，否则持续高优先流量会让普通队列饥饿。

### 3.1 DSCP、ECN 和 PCP 占哪些字段

| 标识 | 位置与位数 | 主要作用 |
| --- | --- | --- |
| DSCP | IPv4 DS 字段/IPv6 Traffic Class 中的 6 位 | 选择相应每跳行为类别 |
| ECN | 同一个八位字段中的另 2 位 | 表示拥塞通知能力与经历的拥塞 |
| PCP，常称 802.1p 优先级 | 802.1Q VLAN 标签中的 3 位 | 二层优先级标记 |

DSCP 的取值不表示一个全行业统一的“数值越大，越优先”的总排序。EF、AF、CS 等编码有约定语义，本地仍要把它映射到相应调度与丢弃行为。AF 的类与丢弃优先级也不能被当成同一个简单等级。DSCP 与每跳行为的区别见 [RFC 2474](https://www.rfc-editor.org/rfc/rfc2474.html)。

### 3.2 不同跳不必使用同一物理队列编号

一台交换机有 8 个队列，另一台有 4 个，仍可能通过不同映射满足同一业务目标；要求的是处理语义和资源约束一致，而不是强制每跳都叫“队列 3”。

标记本身既不预留带宽，也不验证身份。如果无条件信任所有终端自标的高优先级，低优先业务就可能挤入关键队列。边界重标记与关键类限额用于保护约定的行为，而非为了让报文字段看起来整齐。

## 4. Token Bucket 心智模型

令牌按速率 `r` 进入容量为 `B` 的桶：

- 发送一个字节消耗相应令牌；
- 平均速率受 `r` 约束；
- 桶中累积令牌允许最多约 `B` 的突发；
- Policer 在无足够令牌时丢弃/降级；
- Shaper 则让报文等待令牌。

`B` 太小会误伤正常 TCP 突发，太大会允许过大的短时突发冲击下游。

### 4.1 令牌桶限制的不是任意瞬间速率

在理想字节计量模型中，任意长度为 `t` 的观察区间内，符合桶约束的累计数据量最多约为：

```text
D(t) ≤ B + r × t
```

这里 `r` 使用字节/秒，`B` 使用字节。短时间可以消耗已经积累的额度，以高于 `r` 的线速发送；长时间平均才逐渐接近 `r`。这就是“配置 100 Mbit/s，抓到一个很短窗口超过 100 Mbit/s”不一定配置失效的原因。

例如桶初始有 50,000 字节，补充速率为 100 Mbit/s，实际发送线速为 1 Gbit/s。连续满线速发送时，额度以两速率之差消耗，理想排空时间约为 `50000 × 8 / (1000000000 - 100000000) = 0.444 ms`，不是简单用桶大小除以补充速率。

实际设备还有包粒度、计时精度与报文开销口径。若一个包的计费长度就大于允许的桶容量，相应实现可能持续判它超限，因此 B 也要与最大报文尺寸配合。

### 4.2 Policer 与 Shaper 的故障表现不同

Policer 主要判定是否符合速率/突发约定，超限后可丢弃或重标记；它通常不为这次约束把包排队等到有额度。Shaper 则通过等待控制发送时刻，但等待队列本身也有限，满后同样可能丢包。

因此看到丢包不能自动断言“链路拥塞”，看到时延增加也不能自动断言“运营商绕路”。前者可能是监管阈值，后者可能是本地整形队列。

双速率三色计量器进一步使用 CIR/PIR 与相应突发参数，把符合约定程度划分为绿、黄、红。颜色只是计量结果，最终是否重标记或丢弃仍由动作决定；Color-aware 还会考虑已有颜色。机制见 [RFC 2698](https://www.rfc-editor.org/rfc/rfc2698.html)。

## 5. 队列、缓冲与时延

若前面已有 Q 字节待发送，队列持续以 C 字节/秒服务，在简化 FIFO 模型中，等待时间约为：

```text
等待时间 ≈ Q / C
```

这不是直接套用 Little's Law。Little's Law 表达稳定系统中长期平均在途数量、到达率与停留时间的关系 `L = λW`；系统边界和统计口径必须一致。瞬时积压估计不能与长期平均公式随意互换。

大缓冲能吸收突发，但持续拥塞时会产生 Bufferbloat。观察接口平均利用率不足以发现毫秒级微突发，需要硬件队列水位、丢弃计数或更高频 Telemetry。

常见调度：

- Strict Priority：优先队列先发；
- WRR：按轮询权重分配；
- DWRR：更好处理不同包长；
- 保证带宽 + 共享剩余带宽：常见硬件模型。

### 5.1 权重为什么不是不变的吞吐承诺

假设两个持续繁忙的类在同一调度层按 1:3 分享剩余服务能力，理想情况下可近似获得相应比例。但某个类空闲、存在更高优先级类、父级整形或实际包长不同，结果就会变化。

按包数轮询时，两个类各发一个包，并不代表它们获得相同字节数。DRR/DWRR 引入字节额度等机制改善变长包公平性；具体调度算法、分层约束和硬件实现决定最终比例。

一般链路正在发送的普通帧也不会因为高优先包刚到就被任意截断。严格优先改善的是下一次可调度机会，不能保证物理序列化时间为零。

### 5.2 BDP 与队列容量不是同一个目标

BDP（Bandwidth-Delay Product，带宽时延积）描述把路径填满所需的在途数据量。若瓶颈带宽为 10 Gbit/s、基础 RTT 为 20 ms，则 BDP 约为 25 MB。

这 25 MB 包括路径中正在传播与传输的数据，不等于希望瓶颈队列常驻 25 MB。把 BDP 全部误当作“应该长期排队的数据”，会把低排队时延目标变成持续 Bufferbloat。

TCP 发送还受到拥塞窗口、接收窗口、应用供给与 pacing 等限制。带宽不足、窗口不足和排队过多，可能导致相似吞吐现象，却需要不同解释。

### 5.3 AQM 试图管理持续队列，而不只是等到装满

| 机制 | 观察或处理思路 | 主要边界 |
| --- | --- | --- |
| Tail Drop | 队列达到容量后丢弃新到包 | 不主动约束排队时延，可能造成集中丢失 |
| RED/WRED | 根据队列统计及类别提前概率标记/丢弃 | 参数、平均值与业务特征影响结果 |
| CoDel | 观察报文驻留时间及持续性 | 不是简单把队列长度固定到一个常数 |
| FQ-CoDel | 流分类/调度与 CoDel 结合 | 流识别、哈希碰撞和实现仍有边界 |

AQM 是拥塞管理，调度是决定服务机会；两者相互配合，但不同类的优先级不能替代主动队列管理。总体建议见 [RFC 7567](https://www.rfc-editor.org/rfc/rfc7567.html)，CoDel 与 FQ-CoDel 机制分别见 [RFC 8289](https://www.rfc-editor.org/rfc/rfc8289.html)、[RFC 8290](https://www.rfc-editor.org/rfc/rfc8290.html)。

### 5.4 ECN 如何把拥塞反馈给发送者

以支持相应协商的经典 TCP ECN 为例：

```text
发送端标识报文具备 ECN 能力
→ 支持的拥塞节点对相应包标记 CE
→ 接收端通过传输协议反馈拥塞
→ 发送端按拥塞控制算法减少负载
→ 后续队列压力有机会下降
```

网络侧写 CE 不会直接遥控服务器立即停止发送；反馈需要往返时间，发送端也必须正确响应。经典 ECN 位有 Not-ECT、ECT(0)、ECT(1)、CE 等编码，不能与 DSCP 的业务等级混淆。基础机制见 [RFC 3168](https://www.rfc-editor.org/rfc/rfc3168.html)。

ECN 不是“绝不丢包”承诺。硬性资源不足、非 ECN 流量和策略拒绝仍会导致丢弃；不同拥塞控制还可能使用不同反馈语义。DCTCP 利用被标记数据比例调整行为，但需要相应端点和网络条件，不能把所有 TCP 都视为 DCTCP，见 [RFC 8257](https://datatracker.ietf.org/doc/html/rfc8257)。

## 6. 端到端一致性

一条流可能经过：

```text
服务器 vSwitch
→ ToR
→ Spine
→ 防火墙
→ WAN/云网关
→ 远端交换机
```

逐跳检查：

- 分类是否一致；
- 隧道外层 DSCP 是复制、重写还是清零；
- 每台设备队列资源与映射能否维持目标语义，而非编号必须相同；
- 云/运营商是否承诺保留标记；
- 出口整形是否匹配实际线路速率；
- 统计口径是原始类、队列还是丢弃原因。

内外层 ECN 还需要正确传播，不能仅讨论 DSCP 复制。封装入口、承载拥塞标记和解封装处理必须遵循相应隧道规则，避免内层发送者无法得知拥塞；相关原则见 [RFC 6040](https://www.rfc-editor.org/rfc/rfc6040.html)。

对于限速器，IP 字节、二层帧字节与实际线路开销的差异也会影响“配置速率正好等于购买带宽”是否合适。先核对计量层级，再解释为什么两端计数看似不一致。

## 7. Linux `tc` 实验

在 Network Namespace 或实验主机中创建受限链路，使用 `tc` 观察整形与队列。执行前先确认不会影响宿主机生产接口。

实验思路：

1. 两个 Namespace 产生交互流和批量流；
2. 将出口限制为固定速率；
3. 不做 QoS，记录 RTT、吞吐和丢包；
4. 增加两类队列，给交互流保证；
5. 对批量流整形；
6. 比较队列统计和业务结果；
7. 故意让优先流持续占满，观察普通流饥饿；
8. 增加优先队列限额后再次验证。

查看：

```bash
tc -s qdisc show dev <interface>
tc -s class show dev <interface>
ip -s link show dev <interface>
ss -ti
```

## 8. QoS 排障

| 现象 | 检查 |
|---|---|
| 标记正确但仍高延迟 | 队列映射、拥塞点是否在别处 |
| 无明显利用率但有丢包 | 微突发、采样周期、缓冲水位 |
| 普通业务完全无带宽 | 严格优先队列是否无限制 |
| TCP 吞吐低 | Policer 丢包、RTT、窗口、MTU |
| 跨隧道后策略失效 | 外层 DSCP 复制/重写 |
| 只有一个方向异常 | QoS 是逐接口逐方向生效 |

## 9. 与 AI 网络的衔接

GPU 集群中的 RDMA/RoCE 需要进一步学习 PFC、ECN、DCQCN、无损/近无损网络和拥塞树分析。不要直接把普通 TCP QoS 策略照搬为 RoCE 设计。本篇提供的是队列、标记、拥塞和验证基础，后续进入 AI 集群网络模块。

尤其要区分：PFC 作用于相应链路优先级的暂停/恢复，ECN 传递拥塞经历，DCQCN 等机制让 RoCE 发送侧调节速率。暂停链路不是端到端减少需求，拥塞仍可能向上游传播；这些机制不能都简称为“给流量提高优先级”。

## 10. 掌握标准

你应能从业务 SLO 推导分类和带宽策略，指出真实拥塞点，解释 Policing 与 Shaping 的不同，计算队列积压造成的时延，并通过队列计数器与端到端测试证明策略生效。

## 11. 思考与解答

**接口平均只有 20% 利用率，能排除拥塞丢包吗？**

不能。短时微突发、汇聚点热点或更低速率的逻辑限速器，都可能在平均值不高时触发积压和丢弃。

**配置 100 Mbit/s 的令牌桶，任何 1 ms 窗口都不能超过它吗？**

不是。已积累的突发额度允许短期超出补充速率，理想约束是累计量不超过 B+r×t；还需考虑线速和包粒度。

**增大缓冲为什么有时让超时更严重？**

持续超载不会被增加内存消除。更深的常驻队列可能延长等待，延迟敏感请求在丢包之前就已超时。

**DSCP 数值最大，就一定获得最高优先级吗？**

不是。它是行为选择编码，不是统一分数；实际结果取决于信任、映射、调度和资源限制。

**ECN 已经开启，为什么还需要观察丢包和发送端？**

反馈不是瞬间生效，端点必须正确响应；资源耗尽和非兼容流量等仍会导致丢弃。只看交换机 CE 计数不构成完整反馈证据。

**BDP 为 25 MB，是否应该让每个交换机队列都常驻 25 MB？**

不应该。BDP 是路径在途数据的量级，不是每跳应长期积压的目标；排队预算还需独立约束。
