# 静态路由、OSPF、ECMP 与 BFD

学习路由需要区分三个问题：设备从哪里知道一条路径，为什么选择它，以及数据包如何沿这条路径真正发出去。协议邻居、拓扑数据库和硬件转发表分别回答其中的一部分。

## 1. 静态路由的价值与边界

静态路由结构简单、行为可预测，适合：

- 小规模 Stub 网络。
- 明确的默认出口。
- 管理或应急路径。
- 与动态协议配合的汇总、黑洞和浮动备份。

它的边界是：拓扑变化不会自动传播。接口仍为 Up 但远端链路断开时，静态下一跳
可能继续存在，形成黑洞。

### 1.1 前缀、下一跳、RIB 与 FIB

一条路由表达的是“某个目的前缀通过哪些下一跳到达”，不保存每一个业务连接。RIB（路由信息库）参与路线选择，FIB（转发信息库）承载实际转发所需的查找结果；还要结合 ARP/ND 邻居表得到链路层交付信息。

必须分开两个比较过程：

1. 控制面为**同一个前缀**选择可安装的来源与路径，协议优先级和度量在这里发挥作用。
2. 数据面在**已经安装的前缀**之间对目的地址执行最长前缀匹配。

例如 `/24` 与 `/16` 都在 FIB 中，发往该 `/24` 的包优先匹配 `/24`，不能用“静态路由的管理优先级更高”让另一条 `/16` 覆盖它。不同协议的 Cost 也不是天然可直接比较的统一单位。

### 1.2 下一跳递归与邻居解析

若一条业务路由指向远端 Loopback，需要继续查找到这个 Loopback 的路由，直到解析出可直接交付的接口和邻居。这个过程称为递归解析。

```text
目的业务前缀 → 远端逻辑下一跳 → 承载路径下一跳 → 出接口与邻居 MAC
```

每次转发不一定在软件里逐层重新递归；设备可以预先解析并下发下一跳组。承载路径变化后，相应依赖仍需要更新。循环递归、最终下一跳不可达和 FIB 编程失败，都会造成“控制面看见路由，数据面没有可用路径”。

## 2. 动态路由做了什么

动态路由协议不是直接转发业务包，而是：

1. 发现邻居或建立会话。
2. 交换可达性和拓扑信息。
3. 根据协议算法选出最佳路径。
4. 将结果提交到 RIB。
5. 由系统将最佳路由编程到 FIB。

因此，邻居 Established/Full 只是控制面的一环。

## 3. OSPF 心智模型

OSPF 是链路状态 IGP（内部网关协议）。每台路由器通过 LSA 描述相关状态，在规定作用域内泛洪，形成 LSDB（链路状态数据库），再独立运行 SPF（最短路径优先）算法。

同一区域内的路由器在稳定后应对区域拓扑形成一致认知，不代表多区域网络中每台设备都保存同一份完整 LSDB。ABR 按区域维护数据库并传播相应的区域间信息。

```mermaid
flowchart LR
    A["Hello 发现邻居"] --> B["建立邻接关系"]
    B --> C["同步 LSDB"]
    C --> D["LSA 泛洪"]
    D --> E["SPF 计算"]
    E --> F["安装 OSPF 路由"]
    F --> G["编程 FIB"]
```

### 3.1 邻居状态 {/* #邻居状态 */}

OSPFv2 常见邻居状态主线如下；NBMA 场景还存在 Attempt 状态，实际状态机也会回退或停留：

```text
Down → Init → 2-Way → ExStart → Exchange → Loading → Full
```

- 停在 Init：通常只收到对端 Hello，对端没有看到本端。
- 停在 ExStart/Exchange：常见 MTU、主从协商或链路质量问题。
- Full 后反复重建：检查丢包、CPU、定时器、BFD 和接口抖动。

| 状态 | 这一阶段在完成什么 |
| --- | --- |
| Init | 收到对方 Hello，但对方列出的邻居中还没有本机 Router ID |
| 2-Way | 对方 Hello 中出现本机身份，双向可见性成立；随后决定是否建立完整邻接 |
| ExStart | 协商数据库描述交换的主从关系和初始序号 |
| Exchange | 交换数据库摘要，发现对方有哪些、哪些更新的 LSA |
| Loading | 请求并接收缺少的完整 LSA |
| Full | 本次邻接所需的数据库同步完成，后续仍继续维护和更新 |

**2-Way 不一定是故障。**在广播网络中，两台 DROther 通常不相互形成 Full 邻接，而是分别与 DR/BDR 建立完整邻接。数据库交换的主从也不是 DR/BDR；这是不同职责，不能看到 Master 就认定它是网段 DR。

### 3.2 DR/BDR {/* #drbdr */}

广播多访问网络上，若所有路由器两两建立完整邻接，规模会快速增长。DR/BDR 用于
减少邻接和 LSA 交换复杂度。点到点链路不需要 DR 选举。

DR/BDR 在一条多访问链路上选举，不是为整个区域选一台“总路由器”。候选首先比较接口优先级，数值大者优先，再以 Router ID 仲裁；优先级 0 不参与竞争。已有 DR 通常不会被后来加入的高优先级设备直接抢占。

DR 维护这一网段的 Network LSA，并参与协调泛洪。**业务包不因此必须绕经 DR**；实际业务仍由各设备的路由与 FIB 决定。OSPF 的 DR 也不是 [VRRP](./vrrp/00-VRRP学习路线.md) 的虚拟网关活动角色。

### 3.3 Area {/* #area */}

Area 0 是骨干区域。多区域用于限制 LSDB 和 SPF 影响范围，但也引入 ABR、汇总、
Stub/NSSA 和故障排查复杂度。规模不大时不要为了“架构高级”过早分区。

### 3.4 常见 LSA {/* #常见-lsa */}

| 类型 | 作用 |
| --- | --- |
| Type 1 | Router LSA，描述区域内路由器链路 |
| Type 2 | Network LSA，由 DR 描述多访问网段 |
| Type 3 | Summary LSA，ABR 在区域间通告前缀 |
| Type 4 | ASBR Summary LSA，描述如何到达其他区域中的 ASBR，不是业务前缀清单 |
| Type 5 | External LSA，ASBR 注入外部路由 |
| Type 7 | NSSA 内的外部路由，满足条件时由相应 ABR 转换为 Type 5 |

### 3.5 五类报文怎样完成同步

下面采用 OSPFv2 模型。OSPF 直接使用 IP 协议号 89，不是 TCP/UDP 端口 89，也不依靠 TCP 来保证数据库交付。

| 报文 | 负责什么 | 不负责什么 |
| --- | --- | --- |
| Hello | 发现和维持邻居，携带选举等信息 | 不携带整张路由表 |
| Database Description，DD/DBD | 用 LSA 首部描述数据库摘要 | 不直接代替全部完整 LSA |
| Link State Request，LSR | 请求缺少或较新的 LSA | 不是请求对方替本机算 SPF |
| Link State Update，LSU | 承载一份或多份完整 LSA | 不等于一条固定业务路由 |
| Link State Acknowledgment，LSAck | 确认 LSA 接收，与重传机制配合 | 不保证应用已恢复 |

LSA 是状态对象，LSU 是装载这些对象的报文，二者不是同义词。数据库摘要比对后，只请求需要补齐的内容；相关优化可参见 [RFC 5243](https://www.rfc-editor.org/rfc/rfc5243.html)。

### 3.6 泛洪、版本和老化为什么缺一不可

在一个相应作用域中，OSPFv2 通过 LSA 类型、Link State ID、Advertising Router 标识状态对象，再结合序列号、校验和、年龄判断实例的新旧。

拓扑改变时，始发者更新相关 LSA；接收者判断是否更新数据库，并继续向需要的邻接泛洪。重传列表与确认处理丢失的交付，版本比较避免旧状态覆盖新状态。

没有拓扑变化也需要周期刷新，以免有效信息最终老化；撤销也可使用 MaxAge 泛洪清除状态。因此“动态路由仅在变化时发送任何消息”不适用于 OSPF 的全部行为。

数据库有一份旧 LSA，不一定会产生可用路由：SPF 还要判断拓扑可达、双向链路等条件。对象存在、参与计算和安装路由是不同步骤。LSA 模型见 [FRR OSPF 机制说明](https://docs.frrouting.org/en/latest/ospfd.html#ospf-fundamentals)。

### 3.7 从拓扑图计算到实际下一跳

假设所有链路方向的 Cost 如下，目标前缀挂在 D 上：

```text
A ──10── B ──10── D
 ╲                ╱
  ╲──5── C ──30─╱

A→B→D：20
A→C→D：35
```

A 用自己的位置作为根运行 SPF，选经 B 的较低代价路径；D 自己计算时以 D 为根，不是所有设备都采用 A 的树。若 C→D 的 Cost 改成 15，两条路径到 D 均为 20，在满足实现条件时可保留等价下一跳。

Cost 是管理度量，不是实时 ping 时延。常见设备按参考带宽计算接口 Cost，并允许覆盖；参考带宽、取整和接口代价约定不一致，会使设计意图与实际路径偏离。单向 Cost 也可以不对称。

### 3.8 多区域到底隐藏了什么

ABR（区域边界路由器）连接不同区域；ASBR（自治系统边界路由器）把外部路由引入 OSPF。同一设备可以同时承担两种角色。

Area 0 组织区域间路径。普通非骨干区域不应被当作任意两个其他区域间的透明中转；Virtual Link 是有适用条件的骨干逻辑连接机制，不是把任何异常拓扑变成正常设计的通用办法。

ABR 不是把 Type 1/2 LSA 原封不动传给所有区域。它把相应可达信息重新表达为区域间通告；Type 3 的 Summary 名称也不表示一定已经把多个前缀合成更短掩码。真正的地址汇总需要可聚合的地址与相应策略。

| 区域模型 | 主要外部路由边界 |
| --- | --- |
| 普通区域 | 可以获得相应的区域间和 Type 5 外部信息 |
| Stub | 不接收 Type 5 外部 LSA，也不需要相应 Type 4；通常用 ABR 的默认路由到外部 |
| NSSA | 允许本区域 ASBR 用 Type 7 引入外部信息，不直接泛洪其他区域的 Type 5 |
| Totally Stub／NSSA 的 no-summary 等扩展 | 进一步限制区域间明细，名称和默认行为要核对实现 |

NSSA 的 Type 7 转换还涉及转换者、标志、Forwarding Address 和策略，不能断言每条 Type 7 都无条件变成 Type 5。机制见 [RFC 3101](https://www.rfc-editor.org/rfc/rfc3101.html)。

### 3.9 E1 与 E2 的“代价”如何比较

OSPF 对同一前缀选择路径时，先考虑区域内、区域间、外部等路径类别及资格，再在适用规则内比较度量。不能跨类别只找最小的数字。

在候选均可用且属于相应同类外部路由的简单模型中：

- E1 把到转发目标的内部代价加到外部代价上。
- E2 先比较外部代价，外部代价相同后内部代价仍可能参与仲裁。

例如出口 X 的内部/外部代价为 10/100，出口 Y 为 40/80：按 E1 总代价分别为 110/120，倾向 X；按 E2 先比 100/80，倾向 Y。这是两种度量语义的对照，不是在混合 E1 与 E2 时跳过路径类型优先规则。

外部 LSA 的 Forwarding Address 非零时，数据转发目标可能不是 ASBR 本身，还需解析该地址。Type 4 解决 ASBR 可达信息，不能替代所有非零 Forwarding Address 的解析。

### 3.10 OSPFv3 不是给 v2 地址扩成 128 位

OSPFv3 基础模型以链路为中心组织邻接，常用 IPv6 链路本地地址交互，把地址前缀与部分拓扑描述分离，并引入 Link-LSA、Intra-Area-Prefix-LSA 等对象。Router ID 仍是 32 位标识，不是本机 IPv6 地址。

LSA 类型编码与作用域也有变化，不能把本节的 v2 Type 1～7 表直接套进全部 v3 输出。后续扩展还支持多地址族；协议版本和承载地址族需要分别理解。基础差异见 [RFC 5340](https://www.rfc-editor.org/rfc/rfc5340.html)。

## 4. OSPF 邻居建立条件

两端至少检查：

- 接口是否 Up、IP/掩码是否符合设计。
- Area ID 是否一致。
- Hello/Dead Timer 是否一致。
- 网络类型是否兼容。
- 认证是否一致。
- Router ID 是否唯一。
- MTU 是否导致数据库交换失败。
- ACL/防火墙是否允许 OSPF IP Protocol 89。

不要通过“把所有参数都改成一样”替代理解状态机停在哪一步。

## 5. FRRouting 配置示例

三台路由器：

```text
r1 -- 10.0.12.0/30 -- r2 -- 10.0.23.0/30 -- r3
```

r1：

```text
router ospf
 ospf router-id 1.1.1.1
 network 10.0.12.0/30 area 0
 network 1.1.1.1/32 area 0
```

r2：

```text
router ospf
 ospf router-id 2.2.2.2
 network 10.0.12.0/30 area 0
 network 10.0.23.0/30 area 0
 network 2.2.2.2/32 area 0
```

r3：

```text
router ospf
 ospf router-id 3.3.3.3
 network 10.0.23.0/30 area 0
 network 3.3.3.3/32 area 0
```

验证：

```text
show ip ospf neighbor
show ip ospf database
show ip ospf route
show ip route ospf
show ip route 3.3.3.3/32
```

验证顺序是邻居、LSDB、协议路由、系统路由，而不是只执行 `ping`。

## 6. ECMP

当多条路径前缀长度、协议优先级和代价满足等价条件时，系统可安装多个下一跳。

```text
10.20.0.0/16
  nexthop via 192.0.2.1 dev eth1
  nexthop via 192.0.2.5 dev eth2
```

数据面通常对流哈希：

```text
hash(源/目的 IP、协议、源/目的端口) → 某个下一跳
```

要点：

- 单流通常只走一条路径。
- 多流分布可能不完全均匀。
- 哈希字段和 Seed 因设备而异。
- 成员变化会重新映射一部分流。
- 非对称路径可能影响状态防火墙、NAT 和故障定位。

测试 ECMP 不能只运行一个 `iperf3` 流。

### 6.1 等价不代表均匀，更不代表最低时延

ECMP 先要求控制面允许一组等价候选，硬件再决定如何分配业务。四个等价下一跳的流量不一定各占 25%：少数大流、隧道外层字段相同及哈希碰撞都会产生倾斜。

若按包轮询分配，带宽可能更容易铺开，却会因路径时延不同导致乱序；按流哈希则通常牺牲单流聚合能力以保持较稳定顺序。Flowlet 等机制尝试利用流内空隙切换路径，适用条件和实现不同，不能视作普通 ECMP 默认行为。

### 6.2 故障后为什么正常流也可能被移动

简单取模哈希在成员数变化时可能重映射大量流；Resilient Hashing 等方法通过维持桶和成员关系减少无关流迁移，但仍有实现与资源限制。

一端已经移除失效下一跳，另一端尚未更新，也可能产生短暂微环路或不对称交付。稳定时无环的路由算法，不等于分布式更新过程中每一瞬间都不存在微环路。

## 7. BFD

路由协议 Hello 定时器通常以秒计。BFD 提供轻量、快速、协议无关的双向可达性检测，
并把会话 Down 通知给 OSPF、BGP 或静态路由。

```text
物理链路仍 Up
→ BFD 连续丢失控制包
→ BFD 会话 Down
→ 路由协议撤销邻接/路径
→ RIB/FIB 收敛
```

BFD 只加快故障检测，不自动保证业务恢复。总恢复时间还包括控制面传播、FIB 编程、
ARP/邻居更新和应用重试。

过激定时器会让 CPU 抖动或瞬时拥塞变成大规模邻居重建。定时器应基于平台能力、
链路质量和故障预算验证。

### 7.1 BFD 会话如何识别彼此

BFD 控制消息携带本地与远端 Discriminator（会话标识）、状态、计时参数等信息。Down、Init、Up 等状态相互确认双向会话；AdminDown 表示管理性关闭，不能与普通链路故障完全等同。

会话标识不是 OSPF Router ID，也不等于接口编号。多个上层协议可以使用相应的 BFD 检测结果，但上层如何撤销候选和触发收敛仍是各协议的职责。

### 7.2 检测时间由两端参数共同决定

以 Up 状态的异步模式为例，本端判断对端超时的核心关系是：

```text
本端检测时间 = 对端 Detect Multiplier
             × max(本端 Required Min RX, 对端 Desired Min TX)
```

假设本端最低接收间隔要求 100 ms，对端希望每 50 ms 发送一次，且对端倍率为 3，那么本端检测预算为 300 ms，而不是 150 ms。反向计算使用另一组参数，两端结果可以不同。具体状态、计时变更与模式规则见 [RFC 5880](https://datatracker.ietf.org/doc/html/rfc5880)。

Single-hop、Multi-hop、Echo、Demand 等能力不能混为一个开关：普通控制消息、由转发面返回的 Echo 和对多跳路径的检测具有不同条件。Echo 成功也不等于所有业务协议与大包都能通过。

FRR 示例：

```text
bfd
 peer 10.0.12.2
  no shutdown
 !
!
interface eth1
 ip ospf bfd
```

验证：

```text
show bfd peers
show ip ospf neighbor
show ip route
```

## 8. 收敛时间分解

可以把一次故障的端到端恢复拆成以下概念预算；实际阶段可能重叠，不能把所有监控时间戳机械相加：

```text
T_total =
  T_detect
  + T_protocol
  + T_rib_fib
  + T_neighbor
  + T_application
```

测量时应记录每个时间点，而不是只写“切换约 3 秒”。

## 9. 故障实验

至少完成以下实验：

1. OSPF 两端 Area 不一致，观察邻居状态和日志。
2. 两端 MTU 不一致，观察是否停在 ExStart/Exchange。
3. 构建两条等价路径，用多个五元组观察 ECMP 分布。
4. 关闭一条链路，分别比较 OSPF 原生检测与 BFD 的恢复时间。
5. 在链路上注入丢包，验证过激 BFD 定时器是否产生误切换。

每次实验保存：

```text
故障前邻居与路由快照
故障注入时间
协议状态变化
FIB 变化
业务丢包窗口
恢复后状态
```

## 10. 常见误区

- OSPF Full 就说明所有网段都可达：还要检查 LSA、路由选择和 FIB。
- BFD 越快越好：错误定时器会放大瞬时抖动。
- ECMP 等于链路带宽线性叠加：单流和哈希倾斜会限制利用率。
- 所有 OSPF External 都应进入骨干：错误重分发会形成环路和路由风暴。
- 多区域必然更稳定：额外边界也会增加汇总和故障复杂度。

## 11. 思考与解答

**同一区域内两台设备都在 2-Way，是否一定要修到 Full？**

不是。广播网络的两个 DROther 保持 2-Way 可以正常工作。应先判断网络类型和双方角色，再判断是否缺少应有邻接。

**DD 交换阶段的 Master 就是 DR 吗？**

不是。前者协调一对邻接的数据库描述交换，后者是多访问网段角色，选举范围与职责不同。

**LSDB 中已经有目标信息，为什么没有对应系统路由？**

信息还需满足拓扑可达、路径类别、下一跳有效等条件，并经过 OSPF 选路和系统 RIB 选择。数据库中存在对象不等于它已成为系统路由。若系统路由已经存在而业务仍不通，则继续检查 FIB 安装、邻居解析和实际交付；不要把后一个问题倒推为前一个阶段失败。

**BFD 双向都是三倍检测倍率，就保证同时判 Down 吗？**

不保证。两端使用的 TX/RX 间隔、最后收包时刻和设备调度不同，计算及实际观察都可能不对称。

**把 OSPF Cost 调低，就能修复该链路的拥塞吗？**

不能。它改变选路偏好，不增加物理带宽；反而可能吸引更多流量。控制面的代价不等于动态应用质量。
