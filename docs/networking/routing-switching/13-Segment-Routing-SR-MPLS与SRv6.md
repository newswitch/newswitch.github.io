# Segment Routing：SR-MPLS、SRv6 与路径指令

普通 IP 路由逐跳根据当前目的地址选择下一跳。如果一部分流量需要先经过指定节点、特定链路或某个业务处理点，怎样表达这条路径，又不让每个中间节点为每一条业务策略保存独立隧道状态？

Segment Routing（分段路由，SR）使用有序的 Segment 指令描述相应要求。本文先解释指令，再分别映射到 MPLS 标签与 IPv6，最后讨论选路、保护及实现边界。

前置知识是 [IS-IS 与链路状态路由](./12-IS-IS层次邻接泛洪与SPF.md)、[MPLS 标签与 L3VPN](./09-MPLS-VRF与L3VPN.md)，以及 IPv6 基础。

## 1. Segment 是转发指令，不一定是一条物理链路

Segment 可以表达“沿相应算法到达某个前缀”“经某条邻接交付”“执行某种业务处理”等动作。SID（Segment Identifier，段标识符）用于标识这项指令。

```text
策略意图：先到 B，再到 D
逻辑 Segment List：[到 B 的指令, 到 D 的指令]
```

到 B 的途中可以经过其他普通中转节点，不必给每一跳都列一个 SID。到达 B 后再继续执行后面的指令。

SR 也不是让远端发送任意程序到路由器执行。每个 SID 必须对应控制/管理系统已经授权和安装的明确行为，且数据面具备相应能力。基本架构见 [RFC 8402](https://www.rfc-editor.org/rfc/rfc8402.html)。

### 1.1 “核心不保存每条策略状态”不等于无状态网络

核心仍需要路由、SID/标签转发表、邻接与保护等状态。减少的是每一条端到端策略在所有中间节点上的独立路径状态，不是删除网络中的一切转发表。

入口还要知道哪些流量进入哪个策略；出口还要知道怎样解封装和交付租户。将路径信息放入报文也会增加封装和解析开销，不是免费交换。

## 2. 四类常见 SID 职责

| 指令 | 可以怎样理解 | 关键边界 |
| --- | --- | --- |
| Prefix-SID / Node-SID | 按相应算法到达前缀；Node-SID 是特定节点前缀语义 | 不必固定每条物理链路 |
| Adjacency-SID | 使用发布节点的相应邻接或邻接集合 | 常见局部 SID 必须在所属节点解释 |
| Binding SID，BSID | 在定义它的节点绑定到某份 SR Policy | 不是一条普通目的前缀 |
| 服务 SID | 进入相应业务交付或处理上下文 | 需要出口实际安装业务行为 |

不同 SID 的作用域不能混用。尤其是本地 Adj-SID，数值相同在另一台设备上可以指向完全不同的链路。

### 2.1 先到节点，再用它的局部指令

假设只有 B 知道自己的 Adj-SID `24001` 表示“从 B 经链路到 C”。远端入口不能把 24001 当成全网统一的“去 C”。

一个典型逻辑组合是先到 B，再执行 B 的邻接指令；接下来是否还需其他指令取决于目的与业务封装。这个顺序解释了为什么局部 SID 可以使用，却不能脱离所属节点直接读含义。

Prefix-SID 通常保留相应最短路径及 ECMP 的选择空间；Adj-SID 则能约束更具体的交付，但相应链路失效时的保护与回退也必须明确。

## 3. SR-MPLS 怎样编码 Segment List

SR-MPLS 使用 MPLS 数据面。入口把相应 SID 表示为标签栈，当前要处理的标签在栈顶；节点通过 LFIB 执行 Swap、Pop 等动作。

```text
逻辑执行顺序：先 B，再 D
标签栈示意：  [B 对应标签, D 对应标签, 可选业务标签]
               ↑当前栈顶
```

标签与动作仍有本地解释、特殊标签和 PHP 等规则。不能把整个栈当成所有节点都逐项解读的一份路线文本。SR-MPLS 转发规则见 [RFC 8660](https://www.rfc-editor.org/rfc/rfc8660.html)。

### 3.1 SRGB 与 SID Index 为什么需要区分

SRGB（Segment Routing Global Block，全局段标签块）是节点为相应全局段预留的本地标签空间。“Global”描述段的域内语义，不要求每台设备的标签数值范围必然相同。

用单一连续标签块做简单算例：

```text
前缀 D 的 SID Index = 40
节点 A 的 SRGB 起点 = 16000 → A 本地对应标签 16040
节点 B 的 SRGB 起点 = 20000 → B 本地对应标签 20040
```

若 A 经 B 继续到 D，就需要按 B 的相应绑定使用其理解的标签，而不是坚持沿途数值都为 16040。真实 SRGB 可以包含多个范围，不能把“起点加 Index”推广到所有复杂分配模型。

统一 SRGB 便于观察与维护，但“不同 SRGB 就一定不能互通”也不成立；必须看域内通告、索引范围与相应转发表是否正确。不同 SRGB 的解释可对照 [Cisco SR 概览](https://www.cisco.com/c/en/us/td/docs/routers/ios/config/17-x/ip-routing/b-ip-routing/m_intro-seg-routing.html)，其中平台默认值与限制不能推广到其他实现。

### 3.2 一个带具体标签的转发例子

假设入口 S 到 D 的普通最短路径经 A，但某业务需要经过 B。网络还存在 S→B→C→D，且从 B 到 D 的选定路径经 C。

为便于逐跳观察，设相关节点使用共同 SRGB 起点 16000，B 的 Node-SID Index 为 20，D 为 40；本算例对这两个段采用 No-PHP，让对应标签保留到段终点。这里只固定示例条件，不是部署参数建议。

| 位置 | 当前标签栈 | 动作 |
| --- | --- | --- |
| S 发出 | `[16020, 16040]` | 先交给通往 B 的下一跳 |
| B 收到 | `[16020, 16040]` | 完成到本节点的段，弹出 16020，继续处理 16040 |
| C 收到 | `[16040]` | 按到 D 的转发表交付，在相同映射下数值可以保持 |
| D 收到 | `[16040]` | 完成最后一个传输段，再交付内层对象 |

若启用 PHP，某个传输标签可以在到达段终点前一跳被弹出，观察到的栈会不同；这不等于没有经过那个目标。No-PHP 等标志的语义见 [IS-IS SR 扩展 RFC 8667](https://www.rfc-editor.org/rfc/rfc8667.html)。

### 3.3 传输段不代替业务隔离

若 D 是 L3VPN 出口，前面的传输段把包送到 D 后，还需要业务标签或其他上下文选择正确租户。不能因为使用了 SR 就删除 VRF、RT、业务可达性和访问策略。

可将组合读成：“SR 决定怎样到出口，VPN 状态决定出口怎样交付客户”。两者发生在不同层次。

## 4. SRv6 为什么仍需要理解 IPv6 路由

SRv6 使用 128 位 SID，并把相应当前活动 SID 放在外层 IPv6 目的地址中。普通中转节点可以按照这个目的地址的可达前缀转发；到达 SID 所属端点时，端点执行已安装的本地行为。

“普通 IPv6 能把包送到节点”与“节点会执行目标 SID”是两个条件。只配置一条 Locator 路由，不会自动生成端点解封装、VRF 查找等行为。

### 4.1 Locator、Function 与 Argument

一种基础分解是：

```text
128 位 SID = Locator + Function + 可选 Argument/其余约束位
             定位节点   本地行为标识    行为需要的信息
```

Locator 负责可路由定位，Function 对应端点已安装的行为，Argument 可提供相应参数。各部分长度由模型和部署决定，不是固定“前 64 位节点、后 64 位功能”。

十六进制中的一个 Function 值也不是跨设备天然相同的行为编号。具体 SID 绑定到什么行为，要看控制通告与本地安装，不能仅按地址后缀猜测。

### 4.2 常见端点行为负责什么

| 行为 | 核心意义 | 容易混淆的地方 |
| --- | --- | --- |
| End | 完成当前端点段，按相应规则继续 | 不是自动解封装全部业务 |
| End.X | 端点处理后按绑定的三层邻接交付 | 不等于任意目的都走普通最短路 |
| End.DX4/End.DX6 | 解封装后交给绑定的相应三层邻接 | 不等于在任意租户路由表中查找 |
| End.DT4/End.DT6/End.DT46 | 解封装并进入相应 IPv4/IPv6/双栈表查找 | 必须绑定正确表与允许的内层类型 |

这些是预定义的网络处理行为，不是让数据包执行任意应用代码。Locator、Function 与行为约束见 [RFC 8986](https://www.rfc-editor.org/rfc/rfc8986.html)。

## 5. SRH 怎样表达后续段

SRH（Segment Routing Header，分段路由头）是 IPv6 Routing Header 的一种，Routing Type 为 4。它包含段列表及 Segments Left 等字段，用于描述后续段处理。

### 5.1 线上数组顺序与逻辑执行顺序不同

为了便于观察，采用完整段列表、无压缩、无 PSP 等头部优化的简单模型。逻辑上要求依次经过 S1、S2，最后到服务 SID S3：

```text
逻辑执行：S1 → S2 → S3
SRH 数组：Segment List[0] = S3
          Segment List[1] = S2
          Segment List[2] = S1
初始：    IPv6 DA = S1，Segments Left = 2，Last Entry = 2
```

| 位置 | 入站活动目的 | 关键变化 |
| --- | --- | --- |
| 普通中转 | S1 | 按 IPv6 路由前进，不因经过一跳就减少 Segments Left |
| S1 端点 | S1 | 处理后 Segments Left 变为 1，DA 切为 S2 |
| S2 端点 | S2 | 处理后 Segments Left 变为 0，DA 切为 S3 |
| S3 端点 | S3 | 按绑定的最终服务行为继续，例如解封装后查表 |

**Segments Left 不是 IPv6 Hop Limit。**前者描述剩余段处理，后者限制转发寿命；经过普通 IP 中转也会影响 Hop Limit，但不会因此完成一个 SID。SRH 格式与处理见 [RFC 8754](https://www.rfc-editor.org/rfc/rfc8754.html)。

### 5.2 IPv6 数据面可以承载 IPv4 业务

例如入口封装一个客户 IPv4 包，外层用 IPv6/SRv6 送到出口的 End.DT4，出口移除相应外层并在指定 IPv4 表中查目的。外层协议与客户内层协议不同，不代表主机必须同时改为 IPv6 地址。

出口仍需要正确的租户路由、邻居和策略。能够执行 End.DT4 不证明这些业务依赖已经存在。

### 5.3 封装大小与硬件解析深度

在外层 IPv6 封装、完整未压缩 SRH、没有额外 TLV 的简单模型中，承载额外开销为：

```text
IPv6 基础头 40 字节
+ SRH 固定部分 8 字节
+ N 个 128 位 SID：16 × N 字节
```

三项 SID 时为 96 字节；若内层 IP 包为 1500 字节，外层 IPv6 包就是 1596 字节，再考虑链路层承载。这个计算不包含其他业务头、TLV 或嵌套隧道。

Reduced Encapsulation、PSP/USP/USD 及压缩方案会改变线上形态，各有前提，不能一律用本公式解释所有 SRv6 抓包。设备还限制压入/解析的深度与支持行为；控制面可以表达一份策略，不代表硬件必定能按线速执行它。

其中 PSP 是在倒数第二个相应段端点移除 SRH，USP 是在最终相应端点移除 SRH，USD 则涉及最终端点的外层解封装。这里的端点顺序不是所有普通 IPv6 中转路由器的跳数顺序；移除 SRH 也不等于已经移除外层 IPv6 头。每种处理都需要端点支持相应行为及前提。

## 6. SR Policy：存在路径不等于业务已经使用

SR Policy 可由 Headend（头节点）、Color 和 Endpoint 等标识。Color 表达相应策略意图，不是 DSCP，也不是 VLAN/VNI。

一份策略可以有多个 Candidate Path（候选路径）；有效候选按 Preference 等规则选择活动项，一个候选内部又可以包含多份带权重的 Segment List。需要区分：

```text
候选是否有效 → 哪个候选被选中 → 选中候选中有哪些 Segment List
                                              ↓
                                  哪些业务实际被导入这份策略
```

Preference 是策略候选选择参数，不是 BGP LOCAL_PREF。提高无效候选的 Preference 不会把不存在的 SID 或不可达的出口修好。模型见 [RFC 9256](https://www.rfc-editor.org/rfc/rfc9256.html)。

在都有效的候选中，更高 Preference 优先。例如候选 A 为 200、B 为 100，通常选择 A；若 A 失效才继续考虑 B。A 内部两份 Segment List 的权重控制的是所选候选内部的分担，不是用权重让未选中的 B 同时承担普通业务。

### 6.1 Steering 与 Binding SID

Steering（流量导入）决定哪些业务使用策略。普通 IP 路由、BGP 路由颜色关联或其他分类规则可以参与导入，具体取决于架构；只有 Policy 显示 Up，而没有业务绑定，流量仍可能使用普通最短路。

BSID 把某份策略封装为在指定节点可引用的一项指令，便于组合或减少上游必须携带的细节。它没有消除策略状态，而是把相应解释集中在定义这个绑定的节点。

### 6.2 路径从哪里计算和下发

IGP 扩展可以传播拓扑、SID 和能力；控制器可以获得拓扑后计算受约束路径；BGP SR Policy、PCEP 或本地配置等可以提供不同的策略来源。

它们分工不同：BGP-LS 传播链路状态信息，不是逐包转发；PCEP 属于路径计算相关交互，不是把业务包送给控制器；BGP EVPN/VPN 则可承载业务可达性。采用哪种组合要看系统设计，SR 并不强制每个包都询问中心控制器。

## 7. Flex-Algo、TI-LFA 与流量工程的边界

### 7.1 Flex-Algo 改变的是某种计算视图

Flex-Algo 定义相应计算规则，例如采用哪些度量、排除哪些带特定属性的链路。参与节点按照一致定义，在相应拓扑约束下计算路径。

它不是用户向路由器上传任意 SPF 程序，也不保证得到当前最空闲的路径。算法定义、参与能力、属性和前缀/SID 关系不一致都可能破坏预期。定义见 [RFC 9350](https://www.rfc-editor.org/rfc/rfc9350.html)。

### 7.2 TI-LFA 解决本地保护，不代替全网收敛

TI-LFA 利用 SR 等能力预先构造相应无环修复路径，使本地节点在检测到故障后，能在全网完成重新计算前先绕开被保护资源。

这需要剩余拓扑确实连通、保护类型合适、修复栈深在平台能力内，以及转发表已经准备好。Topology Independent 不等于任意多点故障、任意拓扑割裂都能修复。保护机制见 [RFC 9855](https://www.rfc-editor.org/rfc/rfc9855.html)。

本地切换之后，全网仍要泛洪、计算与更新。最终路径怎样接管、是否出现其他微环路窗口、应用是否超时，需要继续观察，而不能只报告“BFD 很快”。

### 7.3 能指定路径，不代表为它预留了容量

一份显式 Segment List 可以把流量带到指定节点，却不会自动增加沿途带宽或建立逐跳容量预留。两份策略还可能同时使用同一隐藏瓶颈，或者经过共享光纤等风险资源。

需要将路径约束、流量需求、准入、QoS 与真实测量关联起来。[QoS 与拥塞](../automation/08-QoS流量工程.md) 解释沿途什么时候排队、标记或丢包；SR 主要提供路径和处理指令的表达手段。

## 8. 安全与故障判断

### 8.1 SID 是可信域内的能力入口

SRv6 使用 IPv6 地址并不意味着可以把所有服务 SID 无条件暴露给不可信网络。承载边界、允许的来源与封装、控制通告授权，以及解封装后的业务策略都需要保护。

SR-MPLS 标签与 SRv6 SID 都不自动提供客户数据机密性。业务隔离与加密依旧是单独的设计要求。

### 8.2 分层判断，不用一个 Up 解释整条路径

| 现象 | 需要确认的对象 |
| --- | --- |
| 目的 Locator/Loopback 不可达 | Underlay 邻接、前缀与系统路由 |
| 目的地址可达但段处理失败 | SID 绑定、SRGB/标签映射、本地行为与地址族 |
| 策略可见但无有效候选 | Segment List 依赖、能力、约束及下一跳 |
| Policy 有效却没有业务计数 | Steering、路由递归与分类规则 |
| 小包通、大包失败 | 栈深、SRH/业务封装和路径 MTU |
| 传输段结束但客户不通 | 服务标签/SID、VRF、内层路由、邻居与回程 |

## 9. 思考与解答

**一个 Node-SID 是否固定对应一条物理链路？**

不是。它可表示按相应算法到达节点前缀，途中仍可有多跳和 ECMP。需要约束特定邻接时应理解 Adj-SID。

**SID Index 同为 40，为什么两台设备显示 16040 和 20040？**

它们的本地 SRGB 可以不同。需要按相应分配与下一跳映射解释，不能只比较一个绝对标签值。

**抓包时目标节点前一跳已经弹出传输标签，是否说明绕过目标？**

不一定，可能是 PHP。应观察弹出后实际交付的下一跳及后续活动指令。

**Segments Left 为 2，是否只允许再经过两台路由器？**

不是。它记录剩余段处理，普通中转跳数由 IPv6 Hop Limit 等机制约束。

**SRv6 网络能否承载 IPv4 租户？**

可以采用外层 IPv6 封装和适合 IPv4 交付的服务行为，例如 End.DT4；还需要对应表、路由与邻居。

**SR Policy 已有效，为什么流量仍走普通最短路？**

可能没有建立正确的业务 Steering 或递归绑定。可用策略与业务正在使用它是两种状态。

**显式指定一条路径，就能承诺最低时延和足够带宽吗？**

不能。指令决定经过哪些处理点，容量、队列、测量精度、需求变化和共享故障域仍需独立验证。

**TI-LFA 是否保证任意故障都零丢包？**

不保证。检测、保护覆盖、剩余连通性、硬件能力和并发故障都有边界，本地保护也不等于整个业务已经恢复。

## 10. 将各技术放回同一条链路

可以用三句话组织这些概念：IGP 提供拓扑和承载可达性；SR 表达并执行路径/处理指令；VPN/EVPN 等业务状态决定客户上下文及最终交付。

回到 [网络技术学习路线](../00-网络学习路线.md)，将这三层与 VXLAN 数据面、QoS 队列、BFD 检测和应用恢复分别对照，避免用“隧道已经 Up”替代整条链路的解释。
