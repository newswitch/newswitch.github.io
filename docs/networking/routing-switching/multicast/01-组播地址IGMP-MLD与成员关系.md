# 组播地址、IGMP/MLD 与成员关系

假设同一视频流有 100 个接收者。单播通常需要发送多份独立流；组播让发送者向一个组地址发送，由网络在需要分叉的地方复制。它减少的是重复传输，并不自动提供可靠交付、重传或加密。

## 1. 组地址不是某一台服务器的地址

| 通信方式 | 目的地址表达什么 | 交付范围 |
| --- | --- | --- |
| 单播 | 一个接口或端点 | 一份发往一个目的 |
| 广播 | 某广播范围内的所有接收者 | 不以应用订阅为前提 |
| 组播 | 一组有相应接收兴趣的端点 | 由组成员与转发状态决定 |

组地址不是给交换机新增的一块虚拟网卡，也不意味着某个中心服务器保存了全网接收者清单。发送者通常不必先加入该组才能发送，加入主要描述接收行为。[RFC 1112](https://www.rfc-editor.org/rfc/rfc1112.html) 定义了 IPv4 主机组模型。

## 2. 地址范围与作用域不能忽略

| 范围 | 主要含义 |
| --- | --- |
| IPv4 `224.0.0.0/4` | IPv4 组播地址空间 |
| IPv4 `224.0.0.0/24` | 本链路控制用途范围，不按普通跨网段业务组播转发 |
| IPv4 `239.0.0.0/8` | 管理范围组播，需结合边界规划 |
| IPv4 `232.0.0.0/8` | SSM 地址范围，内部还有保留规则 |
| IPv6 `ff00::/8` | IPv6 组播空间，地址中还包含作用域等信息 |

地址落在管理范围不等于自动安全隔离。边界、路由策略和接入权限仍需明确。也不能随意把协议保留组地址拿来传视频。

以太网把 IPv4 组播地址映射到 MAC 时，只使用其中部分位，因此不同 IP 组可能映射到同一个 MAC。这就是为什么“网卡收到帧”不等于应用订阅了这个 IP 组，后续仍有协议栈过滤。

## 3. 主机通过 IGMP 或 MLD 表达接收兴趣

IPv4 使用 IGMP，IPv6 使用 MLD。IGMP 直接位于 IP 之上，协议号为 2；MLD 使用 ICMPv6，不是把 IGMP 原样放进 IPv6 包。

主机侧的关系可以这样理解：

```text
应用请求接收某组／某源
  → 操作系统汇总本接口上的成员关系
  → 通过成员报告通知本链路相关设备
  → 查询与报告机制继续维护有效状态
```

同一主机两个应用订阅同一组，一个应用退出时，系统不能因此直接终止另一个应用的接收。主机内部的 Socket 状态与对网络报告的接口成员状态需要汇总。

IGMPv3 与 MLDv2 的现行基础规范分别是 [RFC 9776](https://www.rfc-editor.org/rfc/rfc9776.html) 和 [RFC 9777](https://www.rfc-editor.org/rfc/rfc9777.html)，替代了常见旧资料中的 RFC 3376 与 RFC 3810。

查询并非只有一种粒度。以 IGMPv3 为例：General Query 询问接口上的总体成员关系；Group-Specific Query 针对某个组；Group-and-Source-Specific Query 进一步询问某组中特定源是否仍被需要。

成员关系变化时可以主动报告，周期查询则帮助刷新状态并发现接收者已离开。响应采用相应计时与随机化规则，避免每台主机收到查询后都在同一瞬间发送；设备不能把“这一个时刻没有报告”直接当成组内无人。

## 4. ASM 和 SSM 的差异在于接收请求

ASM（Any-Source Multicast，任意源组播）表达“我要接收发往 G 的数据”。SSM（Source-Specific Multicast，源特定组播）表达“我要接收源 S 发往 G 的数据”。

```text
ASM：订阅 G
SSM：订阅 (S,G)
```

假设两个发布者都使用同一个组 G，订阅 `(S1,G)` 的接收者不会因此要求接收 S2 的流。组地址相同，并不意味着 SSM 通道相同。

SSM 需要应用预先知道源，通常通过业务目录、配置或其他发现机制获得，而不是靠 RP 替它发现所有发布者。协议模型见 [RFC 4607](https://www.rfc-editor.org/rfc/rfc4607.html)。

## 5. INCLUDE 与 EXCLUDE 不是防火墙名单

IGMPv3／MLDv2 可以表达源过滤状态：

- **INCLUDE**：请求接收列表中源发往该组的流量。
- **EXCLUDE**：请求接收除列表中源以外的流量。

例如 INCLUDE `{S1,S2}` 表示只对这两个源有兴趣；EXCLUDE 空列表可表达不排除任何源的接收需求。它们首先是成员关系语义，不是对发布者身份的密码学认证。

应用能提出源过滤需求，也不代表沿途交换机和路由器一定按同样精度维护状态。协议版本、设备能力和兼容模式都会影响结果，相关组合见 [RFC 4604](https://www.rfc-editor.org/rfc/rfc4604.html)。

## 6. 报告只到本链路，数据可能跨越很多路由器

IGMP/MLD 的职责是让本链路知道“这里有接收者”。跨网段分发还需要组播路由状态，例如由 PIM 建立分发树。

因此下面几个条件互不等价：

```text
应用完成订阅
  ≠ 本链路报告已被正确处理
  ≠ 末跳路由器已向上游加入分发树
  ≠ 发布者正在发送且整条数据路径可用
```

接收者也可能只监听了错误接口，或源过滤列表与真实发布地址不同。不能仅凭“程序没有报错”证明网络应该收到流量。

## 7. 思考与解答

**组播是否保证所有接收者得到同样数量的包？**

不保证。分支链路、队列和接收端可能独立丢包，可靠性与恢复由上层协议另行设计。

**主机发了 IGMP 报告，就自动具备跨网段组播能力吗？**

不是。报告建立本链路成员关系，跨网段还要有相应组播路由与可用分发路径。

**按源订阅能保证来源没有被伪造吗？**

不能。源过滤限制所需流量，不认证数据发布者。敏感业务仍需身份与完整性保护。
