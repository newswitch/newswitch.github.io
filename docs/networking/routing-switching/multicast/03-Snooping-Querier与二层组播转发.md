# Snooping、Querier 与二层组播转发

即使不跨路由器，一个 VLAN 中的组播也需要决定应该送到哪些交换机端口。若把每份组播都当成未知流量洪泛，未订阅的终端也会消耗链路和接收资源；若过度裁剪，又可能让真实接收者收不到。

## 1. Snooping 学习的是接收关系

IGMP/MLD Snooping 通过观察成员控制消息，在二层设备上建立近似这样的状态：

```text
VLAN 10，组 G
  成员端口：端口 3、端口 7
  路由器端口：上联端口 1
  附加状态：计时、协议版本、可能的源过滤信息
```

这些不是普通单播 MAC 学习表项。单播表主要从源 MAC 学习可达端口，组播成员表则来自接收意愿和协议消息。

转发需要同时考虑成员端口和路由器方向，而不是只保留接收过主机 Report 的端口。实现考虑见 [RFC 4541](https://www.rfc-editor.org/rfc/rfc4541.html)。

### 1.1 一份数据与一份报告可能走不同出口

假设 VLAN 10 的 P1 通向路由器，P3、P7 后面有组 G 的接收者，P5 是数据源，P9 无订阅：

| 输入报文 | 需要考虑的出口 | 原因 |
| --- | --- | --- |
| P3 收到成员 Report | 路由器方向 P1；其他处理依实现与协议版本 | 让三层知道此链路的需求 |
| P1 收到 General Query | 需要查询的接入端口 | 使终端有机会刷新成员状态 |
| P5 收到发往 G 的数据 | G 的成员端口及需要的路由器方向，排除入端口 | 本地接收者和远端树可能都需要数据 |
| P1 收到发往 G 的数据 | G 的有效本地成员端口 P3、P7 | 不必把普通业务数据送到 P9 |

这是典型模型，不是所有厂商的逐包规则。控制组例外、源过滤、未知组策略和端口角色都会修正结果。特别是“数据源没有订阅 G”，不应成为禁止它发数据或丢掉所有数据的理由。

### 1.2 表项粒度决定可以裁剪到多细

设备可能维护 `(VLAN,G)`，也可能维护 `(VLAN,S,G)` 甚至逐主机状态。仅按 MAC 的过滤还会受到多个 IP 组映射到同一个 MAC 的限制。

“能识别 IGMPv3 报文”不一定等于“硬件能按每个源做精确复制”。控制面识别能力、硬件表项粒度、可用容量和超限行为需要分别理解；软件能显示源列表，也不保证所有数据都按同样粒度线速转发。

## 2. 有 Snooping，为什么还需要 Querier

Querier（查询器）周期性询问链路上是否还有接收者，主机的报告使成员状态得到维护。Snooping 设备观察这些消息，更新自己的端口映射。

如果纯二层 VLAN 没有任何查询器，最初的主动成员报告可能足以让流量暂时正常，但后续状态可能因缺少刷新而老化。这是一类“刚开始能看，几分钟后断流”的成因，不是固定到某个分钟数就必然发生的协议故障。

有些交换机同时提供 Snooping Querier 功能，主动承担查询角色；不能因为开启了 Snooping 就假设它已经自动当上 Querier。

### 2.1 为什么不能把老化时间永远背成 260 秒

组播计时器用于容忍控制消息丢失，又能在主机无声消失后回收状态。设 Robustness Variable 为 RV，Query Interval 为 QI，Query Response Interval 为 QRI：

| 规范中的 Group Membership Interval | 示例 RV=2、QI=125 秒、QRI=10 秒 |
| --- | --- |
| 旧 [RFC 3376 第 8.4 节](https://www.rfc-editor.org/rfc/rfc3376.html#section-8.4)：`RV × QI + QRI` | 260 秒 |
| 现行 [RFC 9776 第 8.4 节](https://www.rfc-editor.org/rfc/rfc9776.html#section-8.4)：`RV × QI + 2 × QRI` | 270 秒 |

这是三层 IGMP 成员计时的规范差异，不表示所有现网交换机都已实现新版，也不表示 Snooping 的每个表项必须用同一个计时器。厂商实现、协议兼容状态与配置可能不同；不能看到四分多钟断流就凭一个常数下结论。

明确离组后的最后成员查询通常使用另一组更短的计时：其核心是“再次询问是否还有其他接收者”，不是等待完整的周期成员老化窗口。缩短计时可以加快释放，也会降低对控制报文丢失的容忍。

## 3. 查询器不是组播数据源，也不等于 PIM DR

在常见 IGMPv2/v3 同一链路上的路由器查询器选举中，较低的接口 IPv4 地址取得查询角色；看到更低地址的合法 Query 后，另一台路由器维持非查询器计时，超时未再听到时才可能接替。PIM DR 则有独立的职责和选举规则。

不能把这一 IPv4 比较规则直接推广到所有厂商的二层 Snooping Querier 扩展或不同地址族；尤其应确认查询消息源地址、兼容模式和角色范围。

同一设备可以同时承担多个角色，但下列名词并不互相等价：

| 角色 | 负责什么 |
| --- | --- |
| Querier | 询问本链路的接收成员 |
| PIM DR | 在特定多接入链路承担相应 PIM 协调职责 |
| RP | ASM 共享树中的汇聚与源相遇 |
| 数据源 | 真正发布业务数据 |

IGMP 查询器机制见 [RFC 9776](https://www.rfc-editor.org/rfc/rfc9776.html)。不能因为一台设备没有视频数据包就说它“没有发挥 Querier 作用”。

## 4. Router Port 为什么重要

路由器端口表示交换机认为该方向可以到达组播路由器。设备可能依据 Query、PIM 等消息动态识别，也可能按配置指定，具体来源取决于实现。

如果成员报告没有被转发到正确的路由器方向，末跳路由器可能始终不知道该 VLAN 有接收需求；如果来自路由器的数据没有正确送入成员端口，组播树已经建好，终端仍然收不到。

所以“交换机里看得到某组”不等于成员消息和业务数据两个方向都处理正确。

## 5. Unknown Multicast 不只有一种默认动作

当目的组没有匹配成员状态时，设备可能按策略洪泛、限制到部分端口或丢弃。不能把某个型号的默认行为推广到全部交换机。

控制组播还需要特殊考虑。例如一些本链路协议使用组播，却不按普通业务组播的方式先报告成员关系；一律“没有 Report 就丢弃”，可能破坏路由或发现协议。

IPv4 的 IGMP 状态也不能拿来裁剪 IPv6 的 MLD 组。尤其 IPv6 邻居发现依赖组播，错误的 MLD 处理可能表现为普通 IPv6 通信失效。IPv6 监听模型见 [RFC 9777](https://www.rfc-editor.org/rfc/rfc9777.html)。

## 6. Fast Leave 为什么有前提

假设交换机端口 7 后面接着另一台交换机，后者有两台接收者 H1、H2。H1 退出组时，如果上游立即删除整个端口 7 的成员关系，H2 也会失去数据。

Fast Leave（快速离组）的适用前提，是设备能可靠判断该端口没有其他接收者，或实现具备足够的逐主机跟踪。普通共享端口不能把一台主机退出理解成整条下游链路都退出。

类似问题也会出现在 AP、电话级联口或虚拟化宿主机后面。端口数不等于终端数。

### 6.1 主机退出、端口退出和上游剪枝是三个事件

```text
H1 退出 G
  → 本端口是否还有 H2 需要 G？有则保留该端口
  → VLAN 其他端口是否还有接收者？有则继续保留相应出口
  → 路由器此接口是否还有需求？无则按协议撤销该分支需求
  → 上游是否还有其他分支？有则不能把整棵树删除
```

最后一个本地接收者退出，并不意味着全网最后一个接收者退出。Snooping、IGMP/MLD 和 PIM 的老化／剪枝在不同范围中工作，这正是它们需要分别维护状态的原因。

部分设备会代理或汇总 Report，以减少上游控制负载。此时“路由器只看到交换机发来的一份报告”不代表 VLAN 中只有一个终端；上游不应将汇总身份直接当作终端清单。

## 7. 怎样把断流定位为一个状态问题

从原理上，可以沿下面关系拆分：

```text
主机订阅是否仍存在
  → 本链路是否有有效 Query 与 Report
  → Snooping 成员端口是否仍有效
  → 路由器方向是否被保留
  → 三层分发树是否仍向该链路发数据
```

这些状态构成连续的依赖关系。重新插网线能暂时恢复，可能只是重新触发了报告，不能据此认定网卡本身损坏。

## 8. 思考与解答

**Snooping 就是 PIM 吗？**

不是。Snooping 主要裁剪一个二层域内的出口；PIM 建立跨路由网络的分发树。

**端口后面只有一根线，能直接认为只有一个组播接收者吗？**

不能。那根线后面可能还有交换机、AP 或多个虚拟机，快速离组需要额外拓扑或跟踪依据。

**关掉 Snooping 后恢复，就证明应该永久关闭它吗？**

不证明。洪泛可能掩盖查询器、成员刷新或路由器端口问题，也可能显著增加无关端口负载。

**交换机能解析 IGMPv3，是否一定能按源地址精确转发？**

不一定。控制消息解析、硬件组表键值与容量是不同能力，需要确认实际数据面的粒度。

**为什么一台主机离组，不能立刻通知全网停止该组？**

本端口、其他端口和其他三层分支还可能有接收者。离组只减少一个范围的需求，不能跳过汇总状态。

**“四分多钟断流”能直接证明某台设备使用 260 秒老化吗？**

不能。新旧规范、厂商计时、最后一次刷新时刻和未知组策略都会影响现象；260 秒不是所有实现共同不变的定律。
