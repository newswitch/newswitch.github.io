# PIM-SM、共享树、源树与 RPF

单播主要依据目的地址选择一个下一跳。组播路由器则需要回答两个问题：这个包从哪个方向来才符合分发树？接下来要复制到哪些接口？

## 1. PIM 的 Independent 不代表不需要路由

PIM 是 Protocol Independent Multicast，协议无关组播。这里的“无关”指它不限定必须由某一种单播路由协议提供可达信息。

实现可依据相应路由信息判断到源或 RP 的方向；这些信息通常来自单播路由，也可能由独立的组播路由信息库或策略提供。没有正确可达性，PIM 邻居建立也不能保证数据分发正常。

PIM-SM 是 Sparse Mode，稀疏模式，按接收需求建立分发状态，而不是默认把所有业务流量洪泛全网。核心机制见 [RFC 7761](https://www.rfc-editor.org/rfc/rfc7761.html)。

### 1.1 控制消息与业务数据分两条线理解

PIM 使用 IP 协议号 103，而不是 TCP/UDP 的 103 端口。IPv4 Hello 发送到 `224.0.0.13`，IPv6 对应 `ff02::d`，用于发现本链路 PIM 邻居和交换能力。

| 消息 | 解决的问题 | 传播范围 |
| --- | --- | --- |
| Hello | 邻居存在、保持时间、DR 等能力 | 相邻链路 |
| Join/Prune | 下游需要／不再需要哪些树分支 | 发给相邻上游，按状态继续逐跳传播 |
| Register | 把源的初始数据封装交给 RP | 源侧 DR 到 RP 的单播路径 |
| Register-Stop | RP 暂时不需要继续接收数据注册 | RP 到源侧 DR |
| Assert | 同一共享链路出现重复转发时协调转发者 | 当前共享链路 |

Join 不是把原始报文一路路由到 RP：每台路由器接收下游需求后，维护自己的状态，再决定是否向自己的上游发送 Join。业务数据沿建立好的分支反向下发，两者不能混成一条 TCP 式连接。

## 2. (*,G) 与 (S,G) 分别表示什么

| 状态 | 主要含义 | 典型上游方向 |
| --- | --- | --- |
| `(*,G)` | 组 G 的共享树状态 | 指向 RP |
| `(S,G)` | 源 S 到组 G 的源树状态 | 指向源 S |

它们不是单纯的两条普通目的路由。还涉及树状态、RPF 邻居、入接口和出接口集合。实际 PIM 还有剪枝等更细状态，因此不能仅凭出现 `(S,G)` 就断言共享树已完全退出。

出接口集合常称 OIL（Outgoing Interface List）。一个包进入后，路由器依据相关状态向多个需要的方向复制；若没有任何下游需求，就不必继续向那些方向发送。

### 2.1 一条组播转发表不只是“目的组 → 端口”

假设 S 为 `192.0.2.10`，G 为 `239.1.1.1`，某台路由器已经处于相应源树转发状态：

```text
(S,G)：(192.0.2.10,239.1.1.1)
期望入接口：上游接口 A
有效出接口：下游接口 B、C
```

正确数据从 A 进入，设备分别向 B、C 交付，未出现在出接口集合中的 D 不获得副本。源／目的 IP 仍是 S/G；普通路由转发递减 TTL，并为各出链路重新形成二层封装，不会把目的 IP 改成每台接收者的单播地址。

若每条分支承载 20 Mbit/s，入口接收一份 20 Mbit/s，两个出口合计发送约 40 Mbit/s，忽略封装开销。组播减少公共路径上的重复副本，**并不消除分叉后的出口带宽和复制资源开销**。

## 3. 接收者先加入共享树

在典型 ASM PIM-SM 场景中，末跳路由器从 IGMP/MLD 获知本地有人订阅 G，然后向 RP 方向发送相应 Join：

```text
接收者 → 末跳路由器 → 中间路由器 → RP
                    Join 向上游传播
                    数据沿树向下游分发
```

RP 是 Rendezvous Point，汇聚点，用于让源与接收者在共享树模型下相遇。RP 不是所有组播应用都必须经过的永久中心，也不是代替 IGMP 为所有主机办理订阅的服务器。

## 4. 源的第一份数据怎样到达 RP

典型流程为：

1. 源开始向 G 发数据。
2. 源侧指定路由器把初始数据封装在 PIM Register 中，单播交给 RP。
3. RP 在有相应需求时把数据送上共享树，并可向源建立原生组播路径。
4. 原生路径建立后，RP 通知源侧停止持续的数据注册封装；仍可能有维护性注册交互。

Register 是为源发现与初始交付服务的机制，不应理解为“源必须先填写一个注册表才能发 UDP”。数据面和控制面在这里有明确配合。

### 4.1 用一条时间线分清封装数据和原生数据

假设源侧路由器为 F，末跳路由器为 L，组 G 的 RP 已正确映射，接收者已加入：

| 阶段 | 控制状态 | 此时的数据路径 |
| --- | --- | --- |
| 接收者出现 | L 向 RP 方向建立 `(*,G)` 需求 | 源还没发送时可以完全没有业务包 |
| S 开始发送 | F 向 RP 发送带业务数据的 Register | 外层单播目的为 RP，内部仍为 S→G |
| RP 收到注册且有需求 | 解封装转发，并向 S 方向建立 `(S,G)` | 接收者可以先经注册和共享树收到数据 |
| RP 开始收到原生流 | RP 抑制后续持续数据注册 | F 到 RP 不必继续对每个数据包做 Register 封装 |
| 注册被抑制期间 | F 按状态发送维护性的 Null-Register 等交互 | Null-Register 不承载完整业务数据 |

Register-Stop **也可能表示 RP 当前没有相应下游需求**，不只表示原生源树已经接通。因此看到 Stop 就宣布“所有接收者都已成功切树”是错误的。

同样，Register 单播能到 RP，不证明原生组播路径满足 RPF、组播转发表与安全策略。初始少量数据能收到、随后中断，可以从这两条不同的数据路径提出假设，但仍需证据确认。

## 5. 为什么还要从共享树切到源树

经 RP 的路径可能绕路。末跳路由器获得源信息后，可以按策略向 S 建立最短路径树 SPT，待相应数据路径可用，再剪除不再需要的重复共享树流量。

```text
初始路径：S → RP → 接收者方向
优化路径：S ─────→ 接收者方向
```

SPT 的“最短”依据路由度量，不必等于物理距离最近。是否切换、何时切换取决于策略和实现，不能把某个厂商阈值当作协议唯一要求。

### 5.1 为什么切树时会同时保留多类状态

末跳 L 决定改走源树后，不应立即拆掉当前仍可用的共享树来源，而是先请求 S 方向的路径，再依据收到数据和协议状态完成切换。

`(S,G,rpt)` 用于表示**共享树上针对源 S 的剪枝相关状态**，不是第三个业务组。它允许表达“这个接收方向不再需要 S 经 RP 绕来的副本”，同时继续保留 `(*,G)` 对其他源的接收需求。

因此有三个独立判断：已经建立 `(S,G)` 控制状态、已经收到正确源树数据、已经停止不再需要的共享树副本。它们发生时间可以不同；只看到 `(S,G)` 一行并不能完成全部判断。

## 6. RPF 检查为什么看“来的方向”

RPF 是 Reverse Path Forwarding，反向路径转发检查。在相应树状态中，设备根据到源或 RP 的可达方向，判断收到数据的接口是否符合预期。

假设到源 S 的 RPF 接口是 A，但数据从 B 进入。即使源地址、组地址都正确，设备仍可能因不符合树方向而丢弃，以防止环路和不受控复制。

共享树和源树检查的参考对象可能不同；组播 RPF 也不能与单播防源地址欺骗的 uRPF 配置简单混为一谈。

多路径下还要区分“单播数据可以任选一条 ECMP 路径”与“组播实现怎样选择 RPF 邻居”。路由变化、策略不一致或路径不对称都可能使控制面看似有路由、组播数据却无法通过检查。

### 6.1 RPF 接口与 RPF 邻居不是同一个对象

接口说明从哪条链路向上游，邻居说明这条链路上具体向谁表达 Join 需求。共享以太网里，一个接口可能有多个 PIM 路由器，不能只匹配了接口就认为所有邻居关系都正确。

基础选路给出向 S 或 RP 的方向，Assert 等机制还可能影响最终上游转发者。RPF 不是“实际包从哪来，就把哪里当正确方向”；否则环路中的复制包也会不断被接受。

### 6.2 PIM DR、Assert Winner 与 Querier 为什么可能是不同设备

| 角色 | 选择／工作的范围 | 协议目的 |
| --- | --- | --- |
| PIM DR | 每条相关链路；支持优先级选举时较高 DR Priority 优先，再比较较高地址 | 代表直连主机执行相应 PIM 工作，例如源注册 |
| Assert Winner | 共享链路上的相关组／源转发状态 | 避免多个上游同时向同一 LAN 发送重复数据 |
| IGMP Querier | 本链路成员查询；常见 IPv4 查询器选举取较低地址 | 维护接收成员关系 |

基础 PIM 中若并非所有邻居都支持 DR Priority 选项，DR 选举会退回相应的地址比较规则。不能把某设备“优先级高”推广成它必然承担以上全部角色。

在 Assert 比较中，依次比较 RPT 标志、Metric Preference、Route Metric，较小者优先；都相同时以较高地址打破平局。这意味着源树方向通常优于共享树方向，但它不是重新计算全网最短路径，而是在当前 LAN 的候选转发者间协调。[RFC 7761 第 4.6 节](https://www.rfc-editor.org/rfc/rfc7761.html#section-4.6) 给出了状态与比较规则。

Assert 不替代 STP，也不修复任意二层环路。它处理的是组播路由器向共享网段重复交付的问题。

## 7. SSM 为什么可以没有 RP

SSM 接收者明确订阅 `(S,G)`，末跳路由器可以直接向 S 建树，不必先通过 RP 找到源。因此不需要 ASM 的共享树与源注册过程。

这不是从 ASM 配置里删掉 RP 就自动变成 SSM。应用必须知道源，接入侧要表达源特定成员关系，网络也要将该范围按 SSM 语义处理。[RFC 4607](https://www.rfc-editor.org/rfc/rfc4607.html) 描述了这种服务模型。

### 7.1 RP 故障对已有流和新流的影响不同

已经完成源树切换、状态仍被维护的流，可能暂时不经过 RP；新 ASM 源发现、新接收者建共享树和其他尚未切换的流却仍可能依赖它。因此 RP 故障后“一路视频还能看”不能证明 ASM 业务完全无影响。

RP 映射机制告诉路由器“组 G 应找哪个 RP”；多 RP 的状态协同则解决不同实例如何知道源。两者不是一件事。例如 Anycast-RP 的源信息协同需要相应机制，不能只在两台设备上配置同一个 RP 地址就认定高可用完成，见 [RFC 4610](https://www.rfc-editor.org/rfc/rfc4610.html)。

SSM 去掉的是 RP 与任意源发现的依赖，不是去掉 IGP、成员报告、RPF、转发表容量和源本身的故障风险。

## 8. 思考与解答

**PIM 邻居正常，为什么视频还可能没有数据？**

邻居只证明协议交互的一部分成立。还需要本地成员、正确树状态、RPF 入接口、非空的下游需求以及正在发送的源。

**所有 PIM-SM 数据都永久经过 RP 吗？**

不是。源树切换后，接收方向的数据可以不再经过 RP；SSM 则根本不需要这种 RP 发现过程。

**单播能到源，就保证组播 RPF 一定正确吗？**

不能。还要看实际用于 RPF 的路由信息、选中的接口和邻居，以及数据真实进入的方向。

**Register-Stop 一定证明源树已建立吗？**

不一定。RP 没有相应接收需求时也可停止数据注册，要结合原生数据与树状态解释。

**已有 `(S,G)`，为什么还能看到 `(*,G)`？**

源树建立、数据切换和共享树针对某源的剪枝是不同状态；共享树还可能服务组内其他源，不能把并存直接当成错误。

**两台路由器同时给同一 LAN 送视频，应由 PIM DR 选举解决吗？**

相关重复转发主要由 Assert 协调。DR 的职责和选举依据不同，它不自动等于该源／组的 Assert Winner。

**20 Mbit/s 的流复制到三个出口，设备只需要 20 Mbit/s 的出口能力吗？**

不是。忽略封装时合计出口负担约 60 Mbit/s，还要考虑复制与队列能力；共享上游减少副本不代表下游复制免费。
