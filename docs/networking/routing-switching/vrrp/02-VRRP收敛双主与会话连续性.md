# VRRP 收敛、双主与会话连续性

“备用网关已经成为 Active”是一个控制面结果，不是整条业务路径恢复的证明。要理解为什么新连接能用、旧连接却断了，需要继续向转发表和会话状态走下去。

## 1. 一次切换至少有四段收敛

```text
判断旧 Active 不再可用
  → 新设备承担虚拟地址和转发职责
  → 交换机与邻居信息将流量交到新设备
  → 上游路由、状态处理和应用交互继续成立
```

VRRP 协议主要处理活动角色的选择。标准还规定了相关 ARP、邻居通告和虚拟 MAC 行为，见 [RFC 9568](https://www.rfc-editor.org/rfc/rfc9568.html)，但外部交换机、路由和应用有各自的状态。

判断恢复时间，应说明测量的是角色切换、首次成功转发，还是已有会话恢复。三个指标可能明显不同。

## 2. 网关还在发通告，上游却已经断了

设 R1 的用户侧接口正常，仍能发送 VRRP 通告，但互联网出口不可用。R2 持续收到合法通告，就不一定会因这次上游故障接管。

这不是选举协议出错，而是“活动角色的存活”与“目标路径的健康”没有建立关联。

不同实现提供接口、路由、BFD 或进程状态跟踪，进而改变有效优先级或实例状态。跟踪对象必须对应真实故障域：

| 观察对象 | 能支持的判断 | 不能保证的事情 |
| --- | --- | --- |
| 物理接口 Up | 本地链路没有报告断开 | 上游远端可达 |
| 路由存在 | 控制面持有候选路径 | 转发与远端业务正常 |
| 下一跳探测成功 | 到相应探测点可达 | 所有目的地可达 |
| 应用探测成功 | 指定请求样本成功 | 所有用户、租户与依赖都正常 |

若探测路径自身不稳定，还可能把短暂抖动变成反复切换。探测阈值、迟滞与恢复延迟属于稳定性设计，而非越快越好。

## 3. 为什么通告被隔离会出现双主

考虑 R1、R2 都能接收终端业务，但互相收不到 VRRP 通告：

1. 原 Active R1 继续认为自己应服务。
2. R2 计时到期，认为活动设备已失效。
3. R2 也转为 Active。
4. 同一个虚拟入口出现两个声称的承担者。

VRRP 不是多数派共识协议，没有凭空保证“任何网络分区下始终只有一个活动者”。组播过滤、VLAN 不一致、消息策略或不对称丢失，都可能破坏角色协调。

在共享二层域里，这可能伴随 MAC 到达端口反复变化；在有状态设备上，也可能让同一连接的不同报文落到不同状态实例。是否出现明显 MAC 漂移还取决于实际数据路径和实现，不能把它当成所有双主的必现证据。

## 4. VIP 接管为什么不复制 TCP 和 NAT 状态

假设 R1 把客户端连接转换为一个公网地址和端口。R2 即使接管了同一 VIP，也未必知道：

- 这个连接原来映射到哪个外部端口。
- 防火墙已允许哪个方向和状态。
- 代理进程中存在什么 TCP、TLS 或应用会话。

```text
虚拟地址相同
  ≠ NAT 映射相同
  ≠ 防火墙会话已同步
  ≠ 代理进程持有旧 TCP Socket
```

这解释了“新连接恢复，旧连接仍然失败”。连接状态复制需要独立机制，且复制粒度、延迟、序列信息和密钥状态都可能影响连续性。

纯三层无状态转发与终止 TLS 的七层代理，切换难度不能简单类比。相关数据对象见 [NAT 与连接跟踪](../../security/firewall-acl-nat/01-NAT-ACL与连接跟踪.md)。

## 5. 二层身份稳定，也要考虑平台允许不允许

虚拟 MAC 移动、源地址使用和邻居通告需要得到承载网络允许。某些云平台或虚拟交换环境按端口限制 MAC/IP 归属，设备协议运行正常，也可能无法交付虚拟入口的业务帧。

另一方面，软件 VIP 漂移方案有时使用节点自己的 MAC，此时主机 IP→MAC 映射也需变化。不能用标准虚拟 MAC 的解释覆盖所有产品模式。

架构判断必须确认：入口地址由谁拥有、是否允许迁移、哪一层负责对外发布。平台提供的负载均衡、路由发布或地址绑定接口，可能与共享二层上的 VRRP 模型完全不同。

## 6. VRRP、动态路由与分布式任播网关

| 机制 | 主要改变的对象 |
| --- | --- |
| VRRP | 同一虚拟路由器入口的活动承担者 |
| OSPF/BGP 等动态路由 | 前缀下一跳及网络内可达路径 |
| 分布式任播网关 | 多个接入位置共同提供一致网关身份，并由 Fabric 维护转发关系 |

它们可以共同使用，但不是彼此的别名。VRRP 不传播整个互联网路由，BGP 不自动同步主机的默认网关邻居状态，分布式任播网关也不是“不小心配出了双主”。

### 6.1 单向丢失为什么也能造成双主

假设 A 优先级 150，B 为 100，A 已是 Active：

| 通告交付条件 | 可能结果 |
| --- | --- |
| A→B 正常，B→A 丢失 | B 仍被 A 的通告维持在 Backup，普通稳态不因该方向单独丢失就接管 |
| A→B 丢失，B→A 正常 | B 超时成为 Active；A 听见较低优先级 B 后仍保持 Active |
| 双向丢失 | 双方可同时维持 Active |

第二种情况下 A 会再次宣告自身角色，但若 A→B 仍被阻断，不能让 B 得知更优活动者。单向通信并不等于足以选出唯一主。表中假设普通实例及给定优先级，未加入额外仲裁或强制隔离机制。

### 6.2 跟踪扣分要产生真正可用的候选

设 A 基础优先级 150、B 为 100，上游失败后 A 只扣 20，剩 130，B 仍可能不接管。即便扣到 90，也要考虑 B 的抢占策略和计时；若 B 的上游同时失败，“谁优先级高”也无法创造一条健康路径。

有效优先级、FAULT 状态、跟踪权重、恢复迟滞都是具体实现的能力。Keepalived 的跟踪对象与权重语义可查 [官方配置手册](https://www.keepalived.org/documentation/keepalived-conf/)，不能把这个算例当成所有产品的配置公式。健康证据应覆盖计划接管后实际会走的出口，避免两台设备探测同一坏目标后反复让位。

### 6.3 用具体映射解释“旧连接断、新连接通”

客户端 `10.0.0.10:51000` 经 A 转换为 `198.51.100.10:40001`，访问服务器 `203.0.113.80:443`。服务器回包仍发到公网端口 40001。B 接管地址但缺少映射时，不知道应还原给哪个内网端点；建立新映射也不等于能接上旧 TCP 序列状态。

纯路由转发只需两端 TCP 状态仍在、路径及时恢复，重传便可能跨过切换；NAT/防火墙还需匹配的会话上下文；终止 TCP/TLS 的代理进一步持有 Socket、密钥和应用状态。同步了其中一层，不能声称另外几层也被复制。

### 6.4 恢复时间如何度量

假设角色在故障后 2.6 秒切换、交换路径在 2.8 秒可用、应用直到第 4 秒才再次重试成功。应分别报告检测／角色时间、首次可用转发时间和业务观测恢复时间。不能把后两者统称为“VRRP 花了四秒”。

这些阶段可有重叠，不宜把所有最大值机械相加。恢复回切还要确认路由、会话同步和转发准备顺序，防止高优先级节点刚启动就吸走尚不能处理的流量。

## 7. 思考与解答

**A 能收到 B 通告，就排除了双主吗？**

不能。若更高优先级 A 的通告到不了 B，B 可以超时接管，A 又不会向低优先级 B 退让。

**跟踪扣分了但没有切换，一定是跟踪失效吗？**

不一定。扣分后可能仍高于备机，或者备机的普通抢占被关闭；必须把有效优先级和状态机共同分析。

**NAT 同步成功，TLS 代理旧连接就保证不断吗？**

不能。NAT 映射与代理 Socket、TLS 密钥和应用会话是不同状态，需各自的连续性机制。

**每秒一个业务探针能精确测出 100 ms 的中断吗？**

不能。它可能完全错过中断或只给出粗粒度区间；角色日志、转发证据与探测采样应分别标注精度。

**把通告间隔缩短十倍，业务中断一定缩短十倍吗？**

不一定。故障检测只是总恢复的一部分，二层学习、路由、会话恢复和应用重试可能成为主要耗时，还要考虑短周期的误判风险。

**两台设备都显示 Active，是否必须是软件 bug？**

不是。首先应考虑双方是否还能交换通告，以及实例和链路范围是否一致。协议没有脱离通信条件的唯一主节点保证。

**VIP 能通就说明旧连接不会断吗？**

不能。VIP 通常只证明新路径的一部分可达，旧连接还依赖原有 NAT、防火墙、代理或应用状态。
