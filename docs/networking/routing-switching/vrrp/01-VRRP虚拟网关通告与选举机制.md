# VRRP 虚拟网关、通告与选举机制

假设终端的默认网关是 `192.0.2.1`。这台设备损坏后，即使旁边还有另一台能上网的路由器，终端也不会自动知道应该改用它。问题不是“有没有备用设备”，而是“备用设备如何接手终端已经认识的入口”。

## 1. 虚拟路由器不是第三台物理机器

```text
终端：默认网关 192.0.2.1
             ↓
       虚拟路由器 VRID 10
       ├─ R1：实际接口地址 192.0.2.2
       └─ R2：实际接口地址 192.0.2.3
```

这里的地址用于文档说明。R1、R2 各有真实接口和路由能力，同时参与维护虚拟入口。正常情况下，一个 VRRP 实例由一台 Active（活动）设备承担虚拟入口的转发责任，其余处于 Backup（备份）状态。

老资料经常把 Active 称为 Master。本文采用 [RFC 9568](https://www.rfc-editor.org/rfc/rfc9568.html) 的 VRRPv3 术语；它替代了 RFC 5798。VRRPv3 支持 IPv4 和 IPv6，但不意味着两个地址族的状态会自动绑定为同一次切换。

## 2. 主机真正发给谁

主机访问远端服务器时，IP 目的地址仍是远端服务器；二层目的地址是网关的 MAC。VRRP 的标准以太网模型为虚拟路由器定义了虚拟 MAC：

| 地址族 | 虚拟 MAC 形式 |
| --- | --- |
| IPv4 | `00:00:5e:00:01:VRID` |
| IPv6 | `00:00:5e:00:02:VRID` |

最后一个字节按十六进制表示。例如 VRID 为十进制 10，对应末字节 `0a`。

Active 对相关 ARP 或 IPv6 邻居发现负责，并接收发给虚拟 MAC 的帧。切换后，虚拟 MAC 可以保持不变，但交换机需要把它学到新的端口上。

因此两张表不能混淆：

- 终端邻居表：虚拟 IP 对应哪个 MAC。
- 交换机 MAC 表：这个 MAC 当前位于哪个端口。

网关切换不一定要求终端把 IP→MAC 映射改成另一个值，却一定需要实际二层交付路径跟上。邻居发现的职责可对照 [NDP 与 RA](../../fundamentals/ipv6/03-NDP邻居发现与RA路由通告.md)。

## 3. VRRP 通告不是 TCP 心跳

标准 VRRP 使用 IP 协议号 112，不是 TCP 或 UDP 的 112 端口。IPv4 使用组播 `224.0.0.18`，IPv6 使用 `ff02::12`，通告中的 TTL／Hop Limit 取 255，以约束消息的链路范围。

Active 定期通告自己的实例、优先级与时间参数，Backup 据此维护超时计时。软件实现可能扩展单播对等方式，但不能把某个实现的单播选项当成标准 VRRP 在任意跨网拓扑中都可工作的保证。

这些通告回答的是“当前谁在承担虚拟路由器角色”，不是“这个设备的所有上游服务都健康”。

## 4. 优先级表达候选资格，不是带宽权重

普通备份候选使用 1～254 的优先级，数值较高更优。255 为地址拥有者保留，0 用于活动设备主动放弃角色的通告语义，不应随意作为普通候选等级使用。

需要区分：

- **地址拥有者**：受保护地址就是设备自身拥有的地址，有特殊规则。
- **普通高优先级候选**：人为配置较高优先级，但不因此成为地址拥有者。
- **平级仲裁**：状态机在相应冲突场景下还会比较通告源的主地址，不能只看两边都写了 100。

把 R1 设为 150、R2 设为 100，并不表示流量按 60% 与 40% 分担。在一个普通实例中，它们竞争的是活动角色。

## 5. 收不到几次通告后才接管

VRRPv3 使用通告间隔和优先级计算活动设备失效计时。用统一的秒单位表达：

```text
Skew Time = (256 - 本机优先级) × 活动设备通告间隔 / 256
Active Down Interval = 3 × 活动设备通告间隔 + Skew Time
```

假设 Backup 优先级为 150，收到的通告间隔为 1 秒：

```text
Skew Time = 106 / 256 ≈ 0.414 秒
Active Down Interval ≈ 3.414 秒
```

这是从相应计时起点计算的协议判定时间，不是承诺“任意故障发生后，业务恰好 3.414 秒恢复”。故障发生在两次通告之间的什么位置、设备调度、二层学习、上游路径与应用重传都会影响实际结果。

## 6. 抢占为什么会带来第二次切换

R1 故障后，R2 成为 Active。R1 恢复时，即使优先级更高，也要考虑抢占策略和状态机计时：

- 允许抢占：更优候选可以重新争取活动角色。
- 禁止普通抢占：尽量维持现有活动设备，减少恢复后的再次切换。
- 地址拥有者存在特殊的抢占规则，不能用普通候选行为概括。

抢占不是“看到较低优先级的一个包就立刻接管”的通用描述。备份状态如何处理通告、何时计时到期，决定具体转换。

工程上还可能有恢复延迟、接口或路由跟踪等扩展。这些要按实现文档理解，不是写上 `priority` 就自动具备所有健康判断。

### 6.1 把选举写成状态转移

下表是 RFC 9568 状态机的阅读索引，假设报文已通过版本、VRID、校验和、TTL/Hop Limit 等合法性检查：

| 当前状态与事件 | 行为 |
| --- | --- |
| Initialize 启动，优先级 255 | 地址拥有者进入 Active 并通告 |
| Initialize 启动，普通候选 | 进入 Backup，启动失效计时 |
| Backup 收到优先级 0 | 将失效计时缩短为 Skew Time |
| Backup 收到非零通告，禁普通抢占或对端优先级不低于本机 | 更新相应间隔并重置失效计时 |
| Backup 允许抢占，收到较低优先级非零通告 | 不以它持续重置计时，等待到期接管 |
| Active 收到更高优先级，或平级但源主地址更大的通告 | 退为 Backup |
| Active 收到不胜过自己的非零通告 | 保持角色并通告，推动对端与二层路径收敛 |

相同优先级的 Backup 不会仅因自己的源地址较大就按普通抢占条件忽略 Active 通告；平级地址比较出现在相应 Active 冲突处理里。不要把状态机不同分支压成“优先级、IP 一路比到底”。详见 [第 6.4 节](https://www.rfc-editor.org/rfc/rfc9568.html#section-6.4)。

### 6.2 主动让位与断电的时间不同

沿用 Backup 优先级 150、间隔 1 秒，最后一次合法通告在 t=0 到达，计时到 t≈3.414 秒。若 Active 在 t=0.8 秒断电，距故障到接管约 2.614 秒，而不是再次完整等待 3.414 秒。

若 Backup 在 t=0.8 秒收到优先级 0，让位后的等待约为 0.414 秒，到 t≈1.214 秒接管。该例忽略处理延迟，且还未计算二层与业务恢复。关闭命令能发出让位通告，突然断电通常不能，两种测试不能混用。

### 6.3 网关转发与访问 VIP 本机服务不同

终端访问远端服务器时，目的 IP 是服务器，只把帧交给虚拟 MAC。直接 ping VIP 则把 IP 包交给虚拟地址本身。非地址拥有者的 Active 是否把此地址当作本机端点接收，涉及 `Accept_Mode`；它与承担网关转发职责不是同一个开关。

IPv4 与 IPv6 还是独立实例，即使 VRID 数字相同，也各有通告和对应虚拟 MAC。一个地址族切换正常，不能证明另一个地址族同步完成。

## 7. 思考与解答

**最后通告后 0.8 秒断电，为什么不用再等完整失效间隔？**

因为 Backup 的定时器从上次有效重置开始运行，故障时已经走过了 0.8 秒；协议不知道精确断电时刻。

**优先级 0 是否表示永远最低的普通备机？**

不是，它是活动设备让位的特殊通告语义，用来缩短接管等待。

**较高优先级 Backup 听见较低 Active 后必然立刻接管吗？**

不是。普通抢占通过通告处理与计时到期实现；还需区分地址拥有者与厂商延迟扩展。

**VIP 不回 ping 能直接证明网关不转发吗？**

不能。访问 VIP 本机与经虚拟 MAC 转发远端包不同，还需检查 Accept Mode 和策略。

**VRID 能否代替 VLAN 来隔离网络？**

不能。VRID 标识虚拟路由器实例，不建立独立二层广播域，也不是访问控制边界。

**有两台路由器参与一个实例，是否天然双活转发？**

不是。普通 VRRP 为该虚拟入口选出 Active。多实例分担或厂商扩展是额外设计，不能混同一个实例的主备机制。

**虚拟 MAC 没变，交换机就不需要更新任何状态吗？**

仍要把该 MAC 的到达端口更新到新的活动设备。地址身份不变与物理交付路径不变是两回事。
