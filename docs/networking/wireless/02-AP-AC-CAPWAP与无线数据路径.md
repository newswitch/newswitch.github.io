# AP、AC、CAPWAP 与无线数据路径

AP 在线，不代表用户能接入；用户已连接 Wi-Fi，也不代表已获得 IP 地址。把这些状态拆开，才能解释无线管理界面一片正常、终端却无法访问业务的原因。

## 1. 先认清 STA、AP 和 AC

| 对象 | 含义 | 核心职责 |
| --- | --- | --- |
| STA | Station，站点；本文主要指终端 | 建立无线关联并收发帧 |
| AP | Access Point，接入点 | 提供无线接入，按架构执行本地处理或隧道交付 |
| AC／WLC | 接入控制器／无线 LAN 控制器 | 管理 AP、策略和相关接入状态；是否承载业务流量取决于模式 |

控制器可以是硬件、虚拟化软件或架构中的逻辑功能。云管理平台也可能只负责管理，不是所有业务的集中转发点；不能看到“统一管理”就断言数据要绕行云端。

## 2. SSID、BSSID 与 ESS 的关系

SSID 是终端看到的无线网络名称。BSS（Basic Service Set，基本服务集）是基本接入单元；基础设施模式下，终端关联到具体 BSS，BSSID 标识该 BSS，通常呈现为 MAC 地址形式。

一个 AP 可以具有多个无线电接口，并提供多个逻辑 BSS。因此 BSSID 不能简单等同于整台 AP 的机身 MAC，也不能把“相同 SSID”理解为“相同 AP”。多 BSSID、多个链路等扩展还会让物理设备和逻辑标识不再一一对应。

ESS（Extended Service Set，扩展服务集）通过分布式系统组织多个 BSS，以支持更大范围的接入。

两个地点都叫 `Office`，并不自动构成能够保持会话的同一网络。安全参数、授权、转发域、地址与移动性机制都需要匹配；同名只是显示层信息。

## 3. CAPWAP 承载的是控制与数据两类消息

CAPWAP（Control And Provisioning of Wireless Access Points）定义接入点与控制器之间的协议关系，标准中接入点角色称 WTP。

常见 UDP 传输使用 AC 侧控制端口 5246、数据端口 5247；数据通道用于隧道承载无线用户流量，控制通道负责发现后的接入管理等交互。协议及端口定义见 [RFC 5415](https://www.rfc-editor.org/rfc/rfc5415.html)，802.11 相关映射见 [RFC 5416](https://www.rfc-editor.org/rfc/rfc5416.html)。

```text
AP 管理状态 ─── 控制通道 ───→ AC
用户业务帧 ─── 数据通道 ───→ 集中转发点   ← 采用集中转发时
```

两者不是同一个健康状态：控制会话存在，并不能证明数据隧道、用户 VLAN 或出口可用。

CAPWAP 的安全设计使用 DTLS 保护控制会话；发现阶段与建立后的受保护消息需要区分，数据通道保护也有独立策略。不能将“建立 CAPWAP”直接等同于“所有承载的业务都经过隧道加密”。

厂商可能有不同架构或扩展协议。CAPWAP 是理解常见方案的模型，不是所有 AP 产品都必须采用同一数据路径的证明。

## 4. 集中转发：用户在哪里进入业务网

在典型集中转发中：

```text
终端原始业务包
 → 无线链路 → AP
 → 加外层隧道，经 AP 管理网络传输
 → 控制器／集中数据面解封装
 → 对应业务 VLAN／VRF
 → 网关、安全策略与应用
```

AP 到集中转发点的网络主要承载外层报文。内层客户端所在子网可以不同于 AP 管理子网，也不要求把每个客户端业务 VLAN 都延伸到每个 AP 接入口。

相应代价是数据隧道路径、集中设备处理能力及其业务出口成为用户数据面的一部分。AP 到 AC 的时延，也可能进入业务访问时延。

## 5. 本地转发：控制器仍然可以参与接入

典型本地转发中：

```text
控制／策略：AP ↔ 控制器及认证系统

业务数据：终端 → AP → 本地业务 VLAN → 本地网关 → 应用
```

业务包可以不经过远端控制器，但认证、策略下发、密钥管理或漫游协调仍可能依赖它。

本地转发把用户 VLAN 和接入策略的落地点移到 AP 所在网络，因此本地交换机的 VLAN 交付、网关、DHCP 和安全边界也需要成立。它不是“勾选后所有远端依赖都消失”。

不同 SSID 甚至不同策略可以采用不同路径，应按具体用户会话判断，不能给整台 AP 只画一条笼统的数据线。

## 6. AP 的地址与终端的地址来自不同状态链

AP 需要管理地址来连接控制系统；终端需要自己的地址来访问业务。两者的 DHCP 服务器、地址池、VLAN 和网关可能完全不同。

将首次接入的依赖展开，可以看到两条链：

```text
基础设施：AP 获得管理连接 → 发现并加入控制系统 → 获得无线配置

用户：发现网络 → 建立相应认证与关联状态
     → 密钥／授权生效 → 在实际业务网完成地址配置
     → DNS／网关／应用访问
```

不同安全模式的认证与关联顺序不同，这里表示依赖关系，不是统一的逐帧时序。

例如，企业认证服务器返回一个动态 VLAN，接入系统也接受了认证结果，但本地交换机没有承载该 VLAN：此时认证日志成功，终端却可能无法得到 DHCP 响应。错误发生在授权落地后的转发路径，不应再次归因于密码。

相关机制见 [EAP-TLS、授权与会话生命周期](../security/aaa-8021x/03-EAP-TLS证书授权与会话生命周期.md)和 [DHCP 中继与地址池选择](../services/dhcp/02-DHCP-Relay地址池选择与高可用.md)。

## 7. 控制器断开时，哪些业务还能继续

不能只用“瘦 AP”或“本地转发”给出通用答案，需要分别判断：

| 状态 | 依赖问题 |
| --- | --- |
| 已连接终端的数据转发 | 当前转发点是否仍可用，已有策略和密钥能否继续使用 |
| 新终端认证 | AP 是否能独立完成所需认证，或能否到达后端 |
| 密钥更新／重新认证 | 原有状态过期后，需要访问哪些服务 |
| 跨 AP 移动 | 目标 AP 能否获得会话、密钥和转发信息 |

某产品支持断连自治，不意味着所有认证模式、终端类型和移动场景都具有同样能力。既有会话短时间能通，也不能证明新用户和下一次重新认证正常。

## 8. MTU 与封装：无线和隧道不是一回事

无线帧到达 AP 后，可能再被放进有线网络上的 CAPWAP 外层。外层 IP、传输协议、CAPWAP 以及可选安全保护都会增加长度。

控制通道的小消息能通过，不代表承载大业务包的数据路径没有 MTU 问题。CAPWAP 自身的分片机制、外层 IP 分片与内层传输协议是不同层次，不能用“无线帧已经分片”证明底层隧道必然可达。

此外，Wi-Fi 链路加密、AP 到控制器的隧道保护、浏览器到应用的 TLS 各自保护不同边界。只开启其中一层，不能推导整个路径都得到同样保护。

### 8.1 AP 从通电到可服务，需要建立哪些状态

采用标准 CAPWAP 模型时，可以把正常主线读作：

```text
获得管理网络 → 发现 AC → 建立安全会话 → Join
→ 必要的镜像处理 → Configure → Data Check → Run
```

发现得到 AC 候选，不等于被接纳；DTLS 成功，不等于 AC 已接受 AP 的绑定和能力；Join 接纳后，还要取得配置并完成相应数据通道检查。镜像不匹配可能引入下载和重启分支，不能用一条直线涵盖所有设备状态。阶段与失败转换见 [RFC 5415](https://www.rfc-editor.org/rfc/rfc5415.html)。

例如重复停留在发现阶段，问题范围与已进入 Run 但某 SSID 客户端 DHCP 失败完全不同。前者看 AP 管理与控制接入，后者应继续看用户授权、VLAN、数据隧道和地址池。

### 8.2 Split MAC 不等于所有无线处理都远端执行

802.11 的时效敏感处理不能简单等远端控制器逐帧往返。Split MAC 与 Local MAC 描述 AP/AC 如何划分 MAC 层功能；集中／本地转发则描述用户帧从哪里进入业务网，两组概念有关联但不应当作同义词。

空口确认和重传、关联管理、策略处理及帧封装各有落点。分析时先确定具体绑定与产品能力，再画功能边界，不用“瘦 AP 所有事情都交 AC”代替解释。标准映射见 [RFC 5416](https://www.rfc-editor.org/rfc/rfc5416.html)。

### 8.3 无线地址不等于隧道外层地址

普通基础设施无线终端向有线服务器发送时，帧需表达无线接收者、发送者与最终二层目的；802.11 的地址字段不能机械当成 Ethernet 的源／目的两字段。AP/AC 按绑定将无线帧或转换后的帧交付至分布式系统。

在集中转发中应区分三层观察点：

| 观察点 | 能看到的对象 | 不能直接替代的证据 |
| --- | --- | --- |
| 无线侧 | STA/BSSID、重传、关联与空口帧 | 有线出口是否允许 |
| AP 管理网 | AP→AC 外层 IP、UDP 与隧道 | 内层每个客户端都成功 |
| 解封装后业务网 | 客户端地址、业务 VLAN/VRF | AP 控制会话状态 |

外层到 AC 的目的 MAC 由 AP 管理路由的下一跳决定；内层客户端去远端服务器的目的 MAC 则可能是客户端业务网关。两个网关不同完全合理。隧道加密时，中间抓包更不能直接读取全部用户内容。

### 8.4 漫游能否保 IP，取决于地址所在的转发域

同 SSID 下从 AP1 到 AP2，如果新 AP 将终端放到不同本地 VLAN，旧 IP 的子网与回程可能不再成立。集中转发或移动锚点可以在适用架构中保持逻辑业务域，但仍需同步终端位置、授权和密钥。

802.11r 等机制减少认证切换代价，不负责自动解决跨子网地址连续性。旧会话暂时能通也不代表下一次重认证或密钥更新一定成功。应分别分析空口切换、接入安全和三层移动性。

## 9. 思考与解答

**AP 的 DTLS 会话成功，就一定完成加入吗？**

不一定，Join、配置与数据检查还有独立条件，控制器可因能力或绑定等不匹配拒绝接纳。

**AP 管理口抓不到客户端原始 IP，就说明终端没发吗？**

不能。集中转发时管理网络看到的可能是 CAPWAP 外层，且内层可能加密；还要确认抓包点和实际转发模式。

**Split MAC 与集中转发是不是同一开关？**

不是。前者划分 MAC 功能，后者确定业务流量落点，要按绑定与产品实现联合判断。

**同名 SSID 加上 802.11r，就保证跨楼宇连接不断吗？**

不能。仍需相容授权、密钥处理和三层地址／回程连续性，SSID 名称本身不建立这些状态。

**AP 能从管理 DHCP 获得地址，为什么终端仍拿不到地址？**

因为它们不是同一个地址配置过程。终端可能被放入不同 VLAN，经过不同转发点、中继和地址池；AP 管理链路正常只证明基础设施自身的一部分可用。

**控制器在线，是否证明所有无线业务都经过它？**

不能。本地转发时控制器可以管理接入，而业务在 AP 附近进入有线网。要依据具体转发模式和用户策略判断。

**本地转发的终端仍能访问服务，是否证明控制器故障没有影响？**

不能。已有数据会话可能继续工作，但新认证、策略变化、密钥更新或漫游可能失败。需要将状态建立与既有状态维持分开理解。
