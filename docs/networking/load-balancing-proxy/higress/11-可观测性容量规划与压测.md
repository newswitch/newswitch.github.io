# Higress 可观测性、容量规划与压测

Dashboard 只能展示已经设计好的信号。要定位网关问题，先给每次请求建立时间线，再把流量、错误、饱和与资源映射到 Controller、Gateway、插件、服务发现和上游。

## 1. 信号设计

| 信号 | 必看内容 | 注意 |
| --- | --- | --- |
| Access Log | 请求 ID、Route、Consumer、Cluster、状态、响应标志、总/上游时间、字节 | 脱敏并采样大字段 |
| Metrics | RPS、并发、P50/P99、4xx/5xx、重试、连接、xDS、插件错误 | 标签低基数 |
| Trace | 鉴权、路由、外部调用、上游 Span | 传播统一 Trace Context |
| Controller | Reconcile、配置验证、推送、ACK/NACK、队列 | 与数据面版本关联 |
| AI | TTFT、TPOT/ITL、输入/输出 Token、取消、Fallback | 与模型服务指标对齐 |

客户端请求 ID 只能用于日志检索，不宜成为 Prometheus 标签。用户传入的 ID 要校验并与网关生成的内部 ID 分开。

## 2. 分解延迟

```text
client total
= network/LB
+ gateway queue and filters
+ upstream connect/TLS
+ upstream queue and service
+ response streaming/backpressure
```

总延迟高而 upstream service time 低，优先查网关插件、连接池、DNS、重试和慢客户端；upstream time 高则继续进入应用/推理框架。对 SSE 同时观察 TTFT 与完整流持续时间，不能只看 HTTP 总耗时。

## 3. 容量模型

容量单位至少包括 RPS、在途连接、每请求 CPU、每连接内存、入口/出口带宽、插件外调并发和上游连接池。

```text
concurrency = arrival_rate × residence_time
required_pods = ceil(peak_load / safe_capacity_per_pod) + failure_headroom
bandwidth = RPS × average_request_response_bytes × protocol_overhead
```

安全容量来自达到 SLO 前的压测拐点，而不是 CPU 100%。保留单 Pod/单节点故障、滚动升级和流量突发余量；Gateway Pod 必须跨节点/可用区，PDB 与调度约束一同验证。

## 4. 压测方法

1. 固定版本、配置、节点、连接复用、请求集和指标窗口；
2. 先测裸上游，再测无插件网关，逐个加入 TLS、认证、Wasm 与 AI 插件；
3. 分别做短连接、长连接、小/大 Body、SSE、突发和混合租户；
4. 阶梯加压直到 P99/错误率/资源出现拐点；
5. 注入 Gateway Pod、节点、Controller、Redis、Nacos 和上游故障；
6. 记录可持续容量、短时突发、恢复时间和保护策略。

压测工具发不出目标流量时，客户端本身可能先耗尽端口、CPU 或带宽。多生成器要校验总请求数与网关接收数。

## 5. 告警与看板

按用户体验告警：成功率、P99/TTFT、429/5xx、配置长时间 NACK；资源告警用于解释而不是替代。每个告警包含 Route/Cluster/Gateway 维度、Runbook、最近变更和上下游入口。Controller 正常不代表 Gateway 正常，反之亦然。

## 6. 掌握标准

你应能从一条慢请求还原各段时间，计算目标流量所需副本和带宽，找出插件增量开销，并通过单点故障和滚动升级证明容量余量真实可用。
