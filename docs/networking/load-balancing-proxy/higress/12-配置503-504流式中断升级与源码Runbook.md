# Higress 配置、503/504、流式中断、升级与源码 Runbook

排障的核心是同时追踪两条链：配置是否成为数据面状态，请求在数据面哪一步失败。不要只看控制台，也不要只在上游应用查日志。

## 1. 固定证据

事故开始先记录时间线、影响域名/Route/租户、状态码/响应标志、Request ID、最近变更、Gateway/Controller 版本和副本分布。保存 CR YAML、事件、Controller/Gateway 日志、数据面 Listener/Route/Cluster/Endpoint 状态和关键指标。

所有管理/Admin 诊断端口只从受控网络访问，输出可能包含内部拓扑和配置。

## 2. 配置不生效

```text
object exists
→ schema/admission valid
→ controller observed generation
→ translation succeeded
→ xDS stream connected
→ Gateway ACKed target version
→ Listener/Route/Cluster/Endpoint contains object
→ request matches expected host/path/header
```

`ACK` 表示资源被接受，并不等于业务请求一定正确。还要检查 Route 优先级、Host/SNI、插件作用范围和真实 Endpoint。`NACK` 时保留错误详情、资源类型、nonce/version，并确认数据面是否继续使用上一份有效配置。

## 3. 503 与 504

| 现象 | 常见方向 |
| --- | --- |
| 503 NR | 没有匹配 Route |
| 503 UH | Cluster 无健康 Endpoint |
| 503 UF/UC | 连接上游失败/被重置，端口、TLS、网络或连接池 |
| 504 | 路由/尝试超时，上游排队或响应过慢 |
| 429 | 限流、配额或过载拒绝 |

响应标志与版本相关，以当前 Envoy 文档为准。比较“网关生成的状态码”和“上游真实返回的状态码”，同时检查重试是否掩盖第一次失败并耗尽总超时。

## 4. SSE 中断

先画时间线：是否收到响应头、首个 `data:`、最后一个正常 chunk，断开由 downstream 还是 upstream 发起。逐层检查 LB/Gateway/upstream idle timeout、HTTP/2 reset、响应缓冲、插件 Body 回调、Gateway drain、客户端背压和取消传播。

用直连模型服务与经网关两组对照；若首包前失败，关注路由、鉴权、排队和 TTFT；首包后失败，关注流式链路、连接生命周期和模型进程。

## 5. 安全升级

1. 固定并阅读 Controller、Gateway、CRD、Chart 与插件兼容矩阵；
2. 备份 Helm values、自定义 CR、Secret 引用和可回滚镜像 digest；
3. 预发布重放配置并检查 deprecation、NACK 和插件 ABI；
4. 先升级少量数据面，验证短请求、SSE、mTLS、Nacos/K8s 服务发现；
5. 观察排空中连接和长流，避免强杀导致全量断流；
6. 明确数据库/CRD 是否可逆，不能只依赖 `helm rollback`。

## 6. 源码定位地图

```text
API/CRD → controller watchers/reconcile
       → config translation/validation
       → xDS resource generation and push
       → Envoy listener/HCM/route/cluster/filter
       → Higress Wasm plugin callback
```

先用日志和运行时状态确定资源类型与组件，再读对应模块；不要从仓库入口盲目搜索。复现时固定 commit、构建参数、最小配置和一条可重复请求。

## 7. 事故后复盘

复盘至少包含触发条件、故障放大器、为何未提前发现、为何保护/回滚未生效，以及一个能自动验证修复的测试。把命令、预期输出、停止条件和升级/回滚决策写入 Runbook 并定期演练。

## 8. 掌握标准

你应能回答“配置有没有到达正确 Gateway”“请求在哪个 Filter/Cluster/Endpoint 失败”“503/504 是谁产生”“流为什么中断”，并能以证据完成升级、回退与源码定位。
