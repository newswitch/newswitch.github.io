# Higress 限流、限并发、配额、降级与多租户

限流不是只有一个 `QPS` 数字。短 HTTP 请求、长 SSE 请求和大模型 Token 消耗的资源不同，必须分别限制“到达速率、在途并发、累计用量和上游容量”。

## 1. 四种控制量

| 控制量 | 回答的问题 | 典型键 | 保护对象 |
| --- | --- | --- | --- |
| 请求速率 | 单位时间允许多少请求 | 租户、Consumer、IP、Route | 网关和接口 |
| 并发数 | 同时允许多少在途请求 | 模型、上游、租户 | 连接、线程和推理槽位 |
| Token/字节速率 | 单位时间消耗多少工作量 | Consumer、模型 | 推理算力和带宽 |
| 固定配额 | 一天或一月最多消费多少 | 账号、项目 | 成本和商业额度 |

只限制请求数会让一个超长 Prompt 与一个健康检查等价；只限制 Token 又无法阻止连接洪水。生产环境通常组合使用。

## 2. 本地与全局限流

单 Gateway 实例的本地计数延迟低，但扩容后总额度随副本数变化。全局限流借助 Redis 等共享状态，能保持集群总配额，却引入网络、存储可用性和热 Key 问题。

设计时明确：

- 限额是“每 Pod”还是“整个网关集群”；
- 计数键是否包含可信 Consumer，而不是可伪造 Header；
- Redis 不可用时 fail-open 还是 fail-close；
- 突发容量、窗口算法和重试是否会形成请求脉冲；
- 被拒绝时返回 `429`、`Retry-After` 和可定位的错误码。

## 3. 多租户治理链

```text
API Key/JWT → Consumer/tenant → Route/model authorization
            → rate/concurrency/token quota
            → tenant metrics and billing label
            → upstream pool
```

认证插件先建立不可伪造的租户身份，后续限流、配额、日志和计费都引用同一个 Consumer。不要直接相信客户端传入的 `X-Tenant-ID`；即便保留，也应由网关覆盖。

多租户还需隔离 Secret、域名、路由、插件配置、缓存键、日志查询权限和上游连接池。共享全局配置必须有默认拒绝和变更审计。

## 4. 降级与过载保护

容量紧张时按顺序保护系统：拒绝低优先级新请求、限制最大 Body/Prompt、缩短允许的输出、关闭昂贵插件或非关键检索、Fallback 到低成本模型，最后才整体拒绝。Fallback 必须满足协议、数据合规和业务语义，不能悄悄把高精度请求切到不兼容模型。

重试会消耗第二份配额并放大过载。设置总超时、单次尝试超时、最大尝试数和重试预算；非幂等请求默认不自动重试。

## 5. 验证实验

1. 两个租户使用不同凭据访问同一路由；
2. 分别压测本地限流和 Redis 全局限流，再把 Gateway 从 2 扩到 4；
3. 注入 Redis 延迟/不可用，确认失败策略和告警；
4. 用短请求与长 SSE 混压，观察 QPS、并发和 Token 限额是否各自生效；
5. 检查 `429` 不被客户端无限重试，租户指标不存在串账。

## 6. 排障矩阵

| 现象 | 优先检查 |
| --- | --- |
| 扩容后总 QPS 翻倍 | 使用了实例本地限流 |
| 某租户拖慢全部请求 | 共享连接池/并发未隔离，热 Key 或队头阻塞 |
| Redis 故障后全部放行 | fail-open 策略与监控不完整 |
| 请求数很少但成本超标 | 缺少输入/输出 Token 配额 |
| 429 激增且上游仍过载 | 客户端重试风暴或限流点太靠后 |

## 7. 掌握标准

你应能根据资源瓶颈选择速率、并发、Token 与固定配额，解释本地和全局一致性的取舍，并完成租户身份、限制、指标、成本和降级的闭环。
