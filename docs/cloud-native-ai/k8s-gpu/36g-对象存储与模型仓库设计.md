# 对象存储与模型仓库设计：从 Bucket 到 GPU 节点缓存

大模型不是一个普通配置文件。一个模型版本可能包含数十到数百个分片、配置、Tokenizer 和自定义代码。生产环境需要知道：

- 下载的是哪个版本？
- 文件是否完整？
- 多个 Pod 是否会重复下载？
- 新版本失败后能否回滚？
- 对象存储故障时，已运行服务能否继续？

本篇从零建立“对象存储作为权威制品仓库，节点缓存负责高速加载”的设计。

---

## 1. 学习目标

完成本文后，你应该能够：

- 解释 Bucket、Object、Key、Prefix、Metadata 和 Version 的关系。
- 理解对象存储与 POSIX 文件系统的不同。
- 设计不可变模型 revision 和 manifest。
- 实现“下载、校验、原子发布、缓存命中”的流程。
- 在 Kubernetes 中安全传递访问凭据。
- 排查下载慢、403、404、文件不完整和缓存污染。

---

## 2. 对象存储的基本概念

```text
Bucket: ai-models
Object Key: Qwen/model-a/rev-20260806/model-00001-of-00008.safetensors
Object Data: 实际字节
Metadata: content-type、checksum、版本等
```

`Qwen/model-a/` 看起来像目录，但通常只是 Key 的共同前缀。对象存储主要通过 API 操作完整对象或对象范围。

常见操作：

- `PUT Object`：写入对象。
- `GET Object`：读取对象。
- `HEAD Object`：读取元数据。
- `DELETE Object`：删除对象。
- `LIST`：按前缀列举对象。
- Multipart Upload：把大对象分片上传。
- Range GET：读取对象的一段字节范围。

---

## 3. 对象存储不是文件系统

| 维度 | POSIX 文件系统 | 对象存储 |
|------|----------------|----------|
| 定位 | 路径 | Bucket + Key |
| 访问 | `open/read/write/rename` | HTTP API |
| 局部覆盖 | 常见 | 通常重写对象或使用特定 API |
| 目录 | 真实目录/inode | 多为 Key 前缀 |
| 文件锁 | 有相关语义 | 通常没有 POSIX 文件锁 |
| 扩展方式 | 文件系统与服务端决定 | 适合大量对象和水平扩展 |
| 权限 | UID/GID/ACL | IAM、Bucket Policy、Token |

因此对象存储适合不可变模型、数据集分片和归档；应用若必须 `mmap()` 或按 POSIX 路径加载，通常要先下载到文件系统。

---

## 4. 模型仓库目录规范

推荐按“模型 + 不可变 revision”组织：

```text
s3://ai-models/
└── qwen/
    └── model-a/
        ├── revisions/
        │   ├── sha-7d9f.../
        │   │   ├── config.json
        │   │   ├── tokenizer.json
        │   │   ├── model-00001-of-00008.safetensors
        │   │   ├── ...
        │   │   └── manifest.json
        │   └── sha-a31c.../
        └── channels/
            └── production.json
```

原则：

- revision 一旦发布就不覆盖。
- `production.json` 只保存当前指向的 revision。
- 正式切换前，revision 中所有对象已经上传并校验。
- 回滚只需把 channel 指回旧 revision。
- 训练代码、Tokenizer、配置和权重必须作为同一个版本集合管理。

不要长期使用 `latest/` 并原地覆盖所有文件，这会让正在下载的 Pod 获得新旧混合内容。

---

## 5. manifest 是完整性的核心

示例：

```json
{
  "schemaVersion": 1,
  "model": "qwen/model-a",
  "revision": "sha-7d9f...",
  "createdAt": "2026-08-06T09:00:00Z",
  "files": [
    {
      "path": "config.json",
      "size": 12450,
      "sha256": "..."
    },
    {
      "path": "model-00001-of-00008.safetensors",
      "size": 5368709120,
      "sha256": "..."
    }
  ]
}
```

下载器应检查：

1. manifest 本身来自预期模型和 revision。
2. 每个文件都存在。
3. 文件大小匹配。
4. checksum 匹配。
5. 没有多余的旧版本分片混入。
6. 全部成功后才写 `.complete`。

ETag 的含义可能受实现和 Multipart Upload 影响，不应不加验证地把它当作文件 MD5。优先使用明确保存的 SHA-256 或存储服务支持的 checksum 字段。

---

## 6. 发布模型的正确顺序

```text
准备 revision
  → 上传所有普通文件
  → 上传所有权重分片
  → 校验对象数量、大小和 checksum
  → 最后上传 manifest
  → 更新 production channel
```

`manifest.json` 相当于该 revision 的完成标志。消费者不应读取没有 manifest 的 revision。

发布和删除都应记录审计日志。对于关键模型，可启用对象版本、保留策略或不可变保护，具体能力取决于对象存储实现。

---

## 7. 下载到 GPU 节点的路径

普通路径：

```text
Object Storage
  → HTTP/TCP
  → 节点网卡
  → 内核网络栈
  → 下载进程内存
  → 节点文件系统
  → 模型进程读取
  → CPU 内存
  → PCIe H2D
  → GPU HBM
```

对象存储下载与模型加载是两个阶段。下载完成不代表模型已经进入显存。

端到端时间：

```text
冷启动时间
= 调度等待
+ 镜像拉取
+ 模型下载
+ 校验与落盘
+ 模型反序列化
+ H2D
+ GPU 初始化与预热
```

## 8. 三种 Kubernetes 分发模式

### 8.1 Init Container 下载到 emptyDir

```text
Init Container 下载 → emptyDir → 主容器加载
```

优点：结构简单、主容器启动前保证数据存在。

缺点：Pod 重建后重新下载；同节点多个 Pod 不能自然共享缓存。

示意 YAML：

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: model-loader
  namespace: ai
spec:
  initContainers:
    - name: fetch-model
      image: public.ecr.aws/aws-cli/aws-cli:2
      command: ["sh", "-c"]
      args:
        - |
          set -eu
          aws --endpoint-url="$S3_ENDPOINT" \
            s3 sync "s3://$MODEL_BUCKET/$MODEL_PREFIX" /staging/model
          test -f /staging/model/manifest.json
          touch /staging/model/.complete
      env:
        - name: S3_ENDPOINT
          value: https://s3.example.com
        - name: MODEL_BUCKET
          value: ai-models
        - name: MODEL_PREFIX
          value: qwen/model-a/revisions/sha-7d9f
        - name: AWS_ACCESS_KEY_ID
          valueFrom:
            secretKeyRef:
              name: model-store
              key: access-key
        - name: AWS_SECRET_ACCESS_KEY
          valueFrom:
            secretKeyRef:
              name: model-store
              key: secret-key
      volumeMounts:
        - name: model
          mountPath: /staging/model
  containers:
    - name: inference
      image: ubuntu:24.04
      command: ["bash", "-lc", "test -f /models/.complete && sleep 3600"]
      resources:
        limits:
          nvidia.com/gpu: 1
      volumeMounts:
        - name: model
          mountPath: /models
          readOnly: true
  volumes:
    - name: model
      emptyDir:
        sizeLimit: 300Gi
```

示例只检查了 manifest 是否存在，生产下载器还必须校验其中每个文件的大小和 checksum。

### 8.2 Init Container 下载到 PVC

PVC 可以是 Local PV、RBD 或共享文件存储。数据可跨容器重启保留，但并发下载需要锁和版本目录，不能让多个 Pod 同时写同一路径。

### 8.3 节点缓存 DaemonSet / 专用缓存服务

```text
控制器决定需要缓存哪些 revision
  → 每节点缓存组件下载并校验
  → 写入 Local NVMe
  → 更新节点缓存标签/自定义资源
  → GPU Pod 调度到已命中节点
```

适合大量推理副本，复杂度也最高。必须处理淘汰、并发、磁盘写满、节点重启和缓存状态过期。

## 9. 原子发布到本地缓存

错误方式：

```text
直接下载到 /models/current
```

如果下载中途失败，业务可能看见半份模型。

推荐：

```text
/models/.staging/<revision>-<unique-id>
  → 下载
  → 校验
  → fsync 关键元数据（按需求）
  → 同文件系统 rename 到 /models/revisions/<revision>
  → 写 .complete
```

消费者只使用包含 `.complete` 且 revision 匹配的目录。

多个下载器并发时，需要可靠锁或由单一控制器协调。仅凭“目录存在”不能判断缓存有效。

---

## 10. 并发与分片

单连接未必能跑满网络，下载器通常支持并发对象或 Multipart/Range 下载。

但并发越高不一定越快：

- RGW/S3 网关 CPU 可能饱和。
- 单节点网络可能跑满。
- NVMe 写入可能成为瓶颈。
- 大量 Pod 会形成请求风暴。
- checksum 计算消耗 CPU。

压测变量：

```text
对象大小 × 并发数 × Pod 数 × 节点数
```

记录：

- 总吞吐和单 Pod 吞吐。
- 首字节延迟。
- 失败/重试率。
- 网关、网络和本地盘利用率。
- 校验时间。

---

## 11. 凭据与最小权限

不要把 Access Key 写入：

- 镜像。
- Git 仓库。
- ConfigMap。
- Pod args。
- 模型目录。
- 日志。

最低要求：

- 使用 Secret 或工作负载身份机制。
- 下载服务只获得目标 Bucket/Prefix 的读取权限。
- 上传流水线与推理下载使用不同身份。
- 禁止推理 Pod 删除或覆盖正式模型。
- 定期轮换凭据。
- 使用 TLS，并验证服务端证书。

Secret 只是 Kubernetes 中的凭据载体，不自动解决 etcd 加密、RBAC 和容器内泄露问题。

---

## 12. Checkpoint 写入对象存储

对象存储适合归档完成的 Checkpoint，但不能简单复制本地文件系统的“边写边覆盖”逻辑。

推荐：

```text
训练进程写本地/共享临时 Checkpoint
  → 完成并校验
  → 上传到唯一 revision 前缀
  → 校验所有对象
  → 最后上传 manifest / _SUCCESS
```

恢复时只列举带完成标志的 Checkpoint。

分布式训练必须明确：

- 哪个 rank 负责上传。
- 其他 rank 的分片怎样汇聚或分别上传。
- 失败重试是否覆盖同一 Key。
- Multipart Upload 失败后如何清理。

---

## 13. 一致性不能一概而论

Amazon S3 当前对对象 PUT/DELETE 和后续读取提供强一致性，但“S3 兼容”产品的具体行为、列表语义和版本能力仍应查看对应实现文档。

更稳健的应用协议仍然是：

- revision 不可变。
- 数据对象先写。
- manifest/完成标志最后写。
- 消费者固定 revision，不在加载中追踪 `latest`。

这样既便于回滚，也减少对供应商细节的依赖。

---

## 14. 不要盲目把 S3 挂成 POSIX

S3 FUSE/CSI 网关可以为特定应用提供路径视图，但要验证：

- 是否支持应用所需的 `rename`、锁、`mmap`、随机写。
- 目录列举和小文件性能。
- 缓存一致性。
- 网络抖动时的错误语义。
- Checkpoint 原子性。
- GDS 支持矩阵。

对于标准大模型推理，更可控的方式通常是先把固定 revision 下载到本地或共享 POSIX 文件系统。

## 15. 故障排查

### 15.1 403 AccessDenied

检查：

- 使用的身份。
- Bucket Policy / IAM Policy。
- 目标 Prefix。
- KMS/服务端加密权限。
- 时间同步和签名区域。
- Secret 是否挂入正确命名空间和 Pod。

### 15.2 404 NoSuchKey

不要只检查文件名，还要检查：

- Bucket。
- 完整 Key 和大小写。
- revision/channel 指向。
- manifest 是否属于同一 revision。
- 对象是否已经被生命周期策略删除。

### 15.3 下载完成但模型加载失败

按顺序检查：

```text
文件数量 → 文件大小 → checksum → config/tokenizer
→ 权重索引 → 权限 → 框架版本 → GPU 显存
```

### 15.4 下载越来越慢

同时看：

- 对象网关请求率、延迟、5xx 和限流。
- 节点入口网络。
- 本地 NVMe 写延迟。
- 下载器重试和并发。
- 是否所有 Pod 同时冷启动。

### 15.5 磁盘中有多个半成品

说明下载没有采用唯一 staging 目录和完成标志。先停止新消费者，再根据 manifest 判断有效 revision，清理必须由了解引用关系的缓存控制器执行。

## 16. 监控与 SLO

对象存储：

- GET/PUT 请求率。
- 首字节和完整请求延迟。
- 4xx/5xx、限流和重试。
- 每个 Bucket/Prefix 流量。
- 网关 CPU、内存和网络。

下载器：

- revision。
- 总字节、完成文件数。
- 下载/校验耗时。
- 重试次数。
- 缓存命中率。

业务：

- Pod 从 Scheduled 到 Ready 的时间。
- 模型加载阶段耗时。
- 扩容成功率。
- 因模型缺失或损坏启动失败的次数。

---

## 17. 推荐生产架构

```text
训练/发布流水线
  → 对象存储不可变 revision
  → manifest 与 channel
  → 节点缓存控制器
  → Local NVMe
  → GPU Pod 只读加载
```

保留共享文件存储作为需要 POSIX 协作的工作区；对象存储负责权威制品和归档；本地 NVMe 负责热路径。

---

## 18. 本篇总结

对象存储的核心不是“容量很大”，而是：

- 通过 API 管理不可变对象。
- 用 revision 和 manifest 表达完整模型。
- 通过并行下载和分层缓存扩展分发能力。
- 把权威副本与 GPU 节点热缓存分离。
