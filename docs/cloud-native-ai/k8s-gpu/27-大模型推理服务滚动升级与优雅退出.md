# 大模型推理服务滚动升级与优雅退出

> **版本提示**：固定 vLLM / Operator / 驱动版本。示例基于 Deployment + vLLM OpenAI 兼容服务。

难点：单 Pod 占贵 GPU、冷启动长、请求与流式连接久、`maxSurge` 可能双倍占卡、模型加载慢。默认滚动易导致新 Pod 因无 GPU Pending、升级卡住，或旧 Pod 被提前杀、流式输出截断。探针见 [第 26 篇](./26-大模型服务%20Kubernetes%20探针设计.md)。

---

## 1. 学习目标

理解 `maxSurge` / `maxUnavailable`；算升级额外 GPU；用 Readiness 控流量；`preStop` 与 `terminationGracePeriodSeconds`；PDB；有/无余量方案；回滚。

---

## 2. 滚动参数与 GPU 账

`maxSurge`：允许超出期望副本的新 Pod 数；`maxUnavailable`：允许不可用副本数。

**零停机倾向**：`maxSurge: 1` + `maxUnavailable: 0` → 先起新、Ready 后再删旧。须有额外 GPU。

例：`replicas=2`、每 Pod 4 卡、`maxSurge=1` → 稳态 8 卡，升级峰值 **12 卡**（多 4 卡）。无空闲则新 Pod Pending，且旧 Pod 不能先删 → 卡住。

**无额外 GPU**：`maxSurge: 0` + `maxUnavailable: 1` → 先停旧再起新，容量暂时下降；单副本会停机。

单副本且无备用卡：只能 `Recreate` 停机、临时借卡，或蓝绿（双 Deployment + 切流量）。

---

## 3. 推荐配置要点

```yaml
spec:
  replicas: 2
  minReadySeconds: 30
  progressDeadlineSeconds: 3600   # 冷启动可能很长
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxSurge: 1
      maxUnavailable: 0
  template:
    spec:
      terminationGracePeriodSeconds: 600
      containers:
        - name: vllm
          # exec vllm serve ...  ← 让 vLLM 成为 PID 1，正确收 SIGTERM
          lifecycle:
            preStop:
              exec:
                command: ["/bin/bash", "-lc", "sleep 30"]  # 给 Endpoint/网关摘流时间
          # startup / readiness / liveness 见第 26 篇
```

`preStop` 不能单独保证长连接排空；真正排空需网关停新流量、等 inflight 归零再删 Pod。开发态 `/pause` 等勿当生产控制面。

流式请求 P99 可能数分钟：`terminationGracePeriodSeconds` 应按 P99 耗时 + preStop + 关闭时间定（如 600），也不能无限大以免维护卡住。

## 4. PDB

```yaml
apiVersion: policy/v1
kind: PodDisruptionBudget
metadata:
  name: qwen-vllm-pdb
spec:
  maxUnavailable: 1
  selector:
    matchLabels:
      app: qwen-vllm
```

保护 drain / 主动 Eviction；**不能**替代 Deployment 滚动参数，也不能防宕机与进程崩溃。

---

## 5. 操作与排查

```bash
kubectl set image deployment/qwen-vllm vllm=vllm/vllm-openai:<新版本> -n ai-model
kubectl rollout status deployment/qwen-vllm -n ai-model --timeout=60m
kubectl get pods,rs -n ai-model -w
```

| 卡住点 | 处理 |
|--------|------|
| 新 Pod `Insufficient nvidia.com/gpu` | 扩容卡、降 `maxSurge`、允许 `maxUnavailable`、蓝绿 |
| 新 Pod 不 Ready | 日志/探针/OOM/参数/NCCL |
| 旧 Pod 久 Terminating | preStop、SIGTERM、宽限期、Volume |

回滚：`kubectl rollout undo deployment/qwen-vllm -n ai-model [--to-revision=N]`。

验收对比：版本、启动时间、显存/利用率、TTFT/TPOT、吞吐、错误率、排队、KV、流式完整性、是否重复重启。

---

## 6. 生产策略摘要

| 条件 | 策略 |
|------|------|
| GPU 充足 | `maxSurge:1` / `maxUnavailable:0` |
| 紧张但多副本 | `maxSurge:0` / `maxUnavailable:1` |
| 单副本无备用 | 维护窗 / Recreate / 临时借卡 |
| 高可用 | ≥2 副本、反亲和、PDB、余量、网关排空、回滚预案 |

---

## 7. 本篇总结

核心不是 YAML，而是：**有没有额外 GPU、新 Pod 多久 Ready、旧请求多久完成、SIGTERM 是否到位、网关是否摘流**。

```text
准备余量 → 起新 Pod → 完全 Ready → 停旧新流量
→ 等在途 → SIGTERM → 释放 GPU → 下一副本
```

零停机需要：GPU 容量 + 探针 + Deployment 策略 + 宽限期 + 排空 + 网关 + 监控回滚。
