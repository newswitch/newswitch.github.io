# 大模型冷启动优化

> **版本提示**：示例以 Kubernetes、PVC/Local PV、Hugging Face 缓存与 vLLM 为主。替换 StorageClass、路径、镜像与密钥；固定版本，勿用 `latest`。

冷启动 = 新推理实例从「不存在/未初始化」到**能稳定接请求**的全过程，不止权重加载，还包括调度、拉镜像、挂卷、模型准备、CUDA/NCCL、显存与 KV、Graph、HTTP、预热、Readiness。**Pod Running ≠ 已可服务**。

存储方案见 [第 36 篇](./36-大模型文件在%20Kubernetes%20中的存储方案.md)；探针 [26](./26-大模型服务%20Kubernetes%20探针设计.md)；滚动升级 [27](./27-大模型推理服务滚动升级与优雅退出.md)。

---

## 1. 学习目标

拆分并测量各阶段；优化镜像、下载/读取、节点缓存与 HF 缓存；优化 vLLM 加载与预热；配合探针与滚动；建立指标与验收。

---

## 2. 链路与时间分解

```text
创建 Pod → 调度 GPU → 拉镜像 → Sandbox → 挂 PVC
→ 模型准备 → vLLM → CUDA/NCCL → 读权重 → 拷到 GPU
→ 显存/KV/Graph → HTTP → /health → 预热 → Ready → 接流量
```

```text
T总 ≈ T调度 + T镜像 + T挂载 + T模型准备 + T权重加载 + T引擎初始化 + T预热
```

先找最大耗时：读模型占 300s 时只调探针无效；拉镜像占 180s 时只优化模型文件也无效。

测量：`kubectl describe` / `kubectl events` 看 Scheduled、Pulling、Probe；用 conditions 时间戳与 `--timestamps` 日志对齐「开始加载 / 权重完成 / KV / HTTP / health」。

---

## 3. 优化清单

### 3.1 缩短调度等待

GPU 不足、碎片、标签/污点、多卡找不齐单节点、队列/PVC 限制 → 见 [Pending 排查](./08-GPU%20Pod%20一直%20Pending%20的排查流程.md)。预留生产容量、节点池、PriorityClass；**把「等 GPU」与「模型自身启动」分开统计**。

### 3.2 减少镜像拉取

运行时镜像（vLLM+CUDA+依赖）与模型存储分离，勿默认把百 GB 模型打进镜像。固定 tag 或 `@sha256:`，`IfNotPresent`。可用 GPU 节点 DaemonSet 预拉镜像，完成后删 DS，层仍在节点缓存（直至 GC）。

### 3.3 避免每 Pod 重复下载

100GB @ 500MB/s 仅传输就约 200s。改为：独立 Job 写入持久存储，或对象存储 → 节点预热 → 本地 NVMe → vLLM 直读。

### 3.4 Hugging Face 缓存

`HF_HOME` / `HF_HUB_CACHE` 指到 PVC 或 Local PV。缓存完整后可设 `HF_HUB_OFFLINE=1`（缺文件会失败）。更推荐已准备好的路径：`vllm serve /models/qwen3-32b/<revision>`。

### 3.5 节点本地缓存 + 标签

中央对象存储 → NVMe → Local PV。缓存完成（校验 + `.complete`）后再打标，例如 `model.example.com/qwen3-32b=<sha>`，Deployment 用硬 Affinity 选已缓存节点；换模用新标签，勿覆盖在用目录。

### 3.6 共享存储与分批启动

区分「单 Pod 慢」与「多 Pod 并发才慢」。可本地缓存、提高吞吐、`maxSurge: 1` 避免同时大量副本读盘。

### 3.7 vLLM 加载

`--download-dir` 落到缓存盘；比较 `--load-format auto|safetensors|pt|npcache`（以固定版本实测为准）。给足 CPU/内存（多卡加载别只写 `gpu: 4` 配 `cpu: 1`）；关注 NUMA/PCIe（[第 02 篇](./02-GPU%20服务器硬件拓扑与%20NUMA.md)）。用日志区分「存储读」vs「引擎初始化」（Graph/编译）。

### 3.8 预热后再 Ready

`/health` 成功后仍可能首次业务更慢。启动脚本：后台起 vLLM → 等 health → 发一次小 chat → `touch /tmp/model-warmed`；Readiness 检查该文件，Liveness 仍用 `/health`。Startup Probe 覆盖最慢正常启动并留余量——**拉长探针 ≠ 优化冷启动**。

### 3.9 滚动时预热

有余量：`maxSurge:1` / `maxUnavailable:0`，新 Pod Ready（含预热）再切流量。无余量：先停旧再起新，容量暂时下降。

## 4. 推荐架构与收益

```text
对象存储源仓 → 同步 Job → 节点 NVMe / Local PV
→ 节点已预拉运行时镜像 → vLLM 加载本地固定 Revision
→ Startup 成功 → 预热 → Readiness → 接流量
```

| 优化项 | 主要阶段 |
|--------|----------|
| 镜像预拉 | 拉镜像 |
| PVC / Local PV / 固定 Revision | 下载/读盘/解析 |
| HF 离线 | 元数据请求 |
| 节点标签 | 调度到已缓存节点 |
| 预热 / 分批滚动 | 首请求 / 并发读 |
| CPU/NUMA | 权重加载 |

---

## 5. 实验与记录

对比：无缓存全量下载；仅镜像缓存；共享 PVC；本地 NVMe；并发 1/2/4 Pod。模板记录：模型 Revision/大小/格式、vLLM/GPU/TP、存储类型，以及创建→调度→拉镜像→挂载→加载→KV→HTTP→预热→Ready 各时间戳与总冷启动。

**误区**：打进镜像一定最快；共享存储永远够用；Running 即完成；二次启动快=存储已优化（可能是页缓存）；只加长 Startup Probe。

验收示例（按模型体量自定）：镜像已缓存 P95&lt;8min；本地模型缓存 P95&lt;5min；共享存储 P95&lt;10min；启动失败率 &lt;1%。另盯缓存命中率、挂载/拉镜像失败率、首次预热时间。

---

## 6. 本篇总结

```text
测量各阶段 → 找最大耗时 → 镜像 → 模型分发 → 持久/本地缓存
→ vLLM 加载 → 预热 → Ready 后接流量
```

最终看的是：**从 Pod 创建到稳定处理真实请求用了多久**，不是「文件下完了 / Running / 端口开了」。
