# 异步并发、背压与任务依赖

Ray 的 `.remote()` 是异步提交，但异步提交不等于系统拥有无限容量。生产者持续创建 Task，而消费者、对象存储、
GPU 或外部服务处理不过来时，队列和 ObjectRef 会不断增长。背压的目标是把“下游已饱和”传回上游，限制在途
工作和内存。

## 1. 先区分三种并发

| 层次 | 含义 | 常用机制 |
| --- | --- | --- |
| 集群任务并行 | 多个 Task/Actor 分布到 Worker | `.remote()`、资源调度 |
| Actor 内并发 | 同一 Actor 同时处理多个方法 | Async Actor、Threaded Actor、Concurrency Group |
| Driver 异步 | Driver 不阻塞事件循环地等待结果 | `await ObjectRef`、`asyncio.gather`、`ray.wait` |

这三层不能互相替代。Driver 使用 `asyncio` 不会让一个默认串行 Actor 同时执行多个方法；提高 Actor
`max_concurrency` 也不会增加集群 GPU 数量。

## 2. ObjectRef 构成依赖图

```python
@ray.remote
def read(partition: str):
    return load(partition)

@ray.remote
def transform(rows):
    return normalize(rows)

@ray.remote
def write(rows, target: str):
    return publish(rows, target)

read_ref = read.remote("part-0001")
transform_ref = transform.remote(read_ref)
write_ref = write.remote(transform_ref, "result/part-0001")
ray.get(write_ref)
```

Driver 只在最终边界等待。Ray 可以在依赖尚未完成时记录下游工作，并在对象就绪和资源可用后执行。

不要为了“看起来清晰”在每个阶段 `ray.get()`，否则把分布式 DAG 变成 Driver 控制的同步流水线。

## 3. 为什么无限提交会失败

```python
# 反模式：输入无界时，pending会持续增长
pending = [process.remote(item) for item in infinite_stream()]
```

即使 Worker 数固定，提交本身仍会创建：

- Task 元数据；
- ObjectRef；
- 参数和闭包引用；
- Pending 资源需求；
- 完成但尚未消费的返回对象；
- 日志与状态事件。

最终压力可能首先出现在 Driver Heap、GCS 元数据、Object Store、Spill 磁盘或下游服务，而不是 CPU。

## 4. 使用 `ray.wait()` 建立窗口

```python
import ray

@ray.remote
def process(item: int) -> int:
    return item * 2

def run_bounded(items, max_in_flight: int = 32):
    pending = []
    results = []
    for item in items:
        pending.append(process.remote(item))
        if len(pending) >= max_in_flight:
            ready, pending = ray.wait(pending, num_returns=1)
            results.extend(ray.get(ready))
    while pending:
        ready, pending = ray.wait(pending, num_returns=1)
        results.extend(ray.get(ready))
    return results
```

窗口大小不是 CPU 数的机械倍数。应综合：

- 单 Task 平均/P99 时间；
- CPU/GPU Worker 数；
- 单对象大小；
- 下游并发上限；
- 允许排队时间；
- Spill 与网络吞吐；
- 失败后的重试放大。

## 5. 按完成顺序消费

`ray.get(refs)` 等待全部结果，最慢任务决定整体返回时间。`ray.wait()` 可以按完成顺序增量消费：

```python
pending = [process.remote(item) for item in items]
while pending:
    ready, pending = ray.wait(pending, num_returns=8, timeout=2)
    if not ready:
        report_slow_tasks(pending)
        continue
    for result in ray.get(ready):
        consume(result)
```

如果 `consume()` 本身很慢，应把消费也变成有界 Task/Actor 阶段，或将结果批量写入外部存储。

## 6. Driver 中使用 asyncio

在支持的 Ray/Python 版本中，ObjectRef 可以与 asyncio 集成：

```python
import asyncio
import ray

@ray.remote
def compute(value: int) -> int:
    return value * value

async def main() -> None:
    refs = [compute.remote(value) for value in range(8)]
    results = await asyncio.gather(*refs)
    print(results)

ray.init()
asyncio.run(main())
```

这避免阻塞 Driver 事件循环，但不会绕过 Ray 资源限制。目标版本若改变 Awaitable 接口，应以 API 文档和最小实验
为准。

不要在异步函数中直接执行长时间同步 I/O 或 CPU 计算；它仍会阻塞事件循环。

## 7. Async Actor 的协作式并发

```python
import asyncio
import ray

@ray.remote
class Gateway:
    def __init__(self):
        self.semaphore = asyncio.Semaphore(16)

    async def call_backend(self, request):
        async with self.semaphore:
            return await send_request(request)
```

`Semaphore` 控制 Actor 内部下游并发。Ray 的 Actor 最大并发控制进入 Actor 的方法数量，应用级 Semaphore
控制实际访问某个后端的数量；两层可以不同。

Async Actor 需要方法定期 `await`。若同步函数占用事件循环，健康检查和取消都可能无法及时执行。

## 8. Threaded Actor 的边界

线程适合阻塞 I/O 或会释放 GIL 的 C/C++ 库。纯 Python CPU 密集任务无法通过线程获得等比例并行。共享状态
需要锁，锁顺序错误会造成死锁。

若每个请求都执行独立 CPU 计算，使用多个 Task/Actor 进程通常比把一个 Actor 的线程数开得很大更清晰。

## 9. 分阶段流水线

```text
Source
→ CPU Parse
→ GPU Infer
→ CPU Postprocess
→ External Sink
```

每个阶段都应独立设定：

- Worker/Actor 数；
- 单批大小；
- 最大在途数量；
- 输入与输出对象大小；
- 超时和重试；
- 队列满时的阻塞、拒绝或降级策略。

最慢阶段决定稳态吞吐。只扩大上游并发会扩大排队，不会提高最终吞吐。

## 10. Actor Pool 与负载分配

一组同构 Actor 可以处理 GPU 推理或昂贵状态服务：

```text
Dispatcher
├─ Actor 0：in-flight=4
├─ Actor 1：in-flight=2
└─ Actor 2：in-flight=8
```

简单轮询无法感知长短请求。可以根据在途数、预计 Token、队列时间或缓存命中路由，但状态采集本身也有延迟。
在线 LLM 服务优先使用 Ray Serve 等已有调度层，而不是手写一个无监控的 Dispatcher。

## 11. Deadline 与取消传播

请求应携带绝对 Deadline 或剩余预算：

```text
网关总预算 30s
→ 排队最多 3s
→ 预处理 2s
→ 推理 23s
→ 返回与清理 2s
```

上游超时后，如果不取消下游工作，会出现“客户端早已离开，集群仍在计算”。取消也不能回滚已发生的副作用，
应配合幂等、协作式检查和资源清理。

## 12. 背压策略

| 策略 | 适用场景 | 代价 |
| --- | --- | --- |
| 阻塞生产者 | 离线任务、不能丢数据 | 上游延迟增加 |
| 拒绝新请求 | 在线服务保护 SLO | 客户端需重试/降级 |
| 丢弃旧任务 | 只关心最新状态 | 不适合事务工作 |
| 批量合并 | 小任务、高固定开销 | 等待成批会增加延迟 |
| 降低质量 | 可降级推理/采样 | 需明确业务契约 |
| 扩容 | 长期容量不足 | 冷启动、成本、资源上限 |

扩容不是即时背压。新节点和模型副本启动期间，入口仍必须有限流和排队上限。

## 13. 避免资源等待

父 Actor 占满全部 CPU 后等待子 Task，子 Task 又需要 CPU，会发生逻辑死锁。常见修复：

- 协调器不占用昂贵资源；
- 为子 Task 保留独立资源；
- 不在持有资源时同步等待同资源子任务；
- 使用 ObjectRef 让依赖自然传播；
- 将不同阶段放入明确的 Placement Group Bundle。

## 14. 观测指标

- 各阶段提交、完成、失败和取消速率；
- Pending、Running、在途和队列长度；
- Task/Actor Method 排队时间与执行时间；
- Object Store 与 Spill；
- Driver/Worker Heap；
- CPU/GPU 利用率；
- 下游连接池、限流和错误；
- Deadline 超时后仍继续执行的工作量。

只有吞吐而没有队列和延迟分位数，无法判断系统是在稳定运行还是积压。

## 15. 故障实验

1. 将生产速率提高到消费速率两倍，观察无界提交的内存增长；
2. 使用 16、32、64 三种窗口比较吞吐与内存；
3. 注入一个 P99 慢 Task，比较 `ray.get(all)` 和增量消费；
4. 让下游返回限流错误，验证重试是否放大压力；
5. 在客户端 Deadline 后取消工作，验证 GPU/CPU 和队列是否及时释放。

## 16. 掌握标准

- 能区分集群并行、Actor 内并发和 Driver 异步；
- 能用 ObjectRef 构建不经过 Driver 的依赖；
- 能用 `ray.wait()` 实现有界在途窗口；
- 能为每个流水线阶段定义背压策略；
- 能识别父子任务资源等待和超时后幽灵工作；
- 能用队列、延迟、内存和资源指标验证稳定性。
