# ldd、ldconfig、readelf 与 objdump：动态链接库诊断

`libcudart.so not found` 与 `undefined symbol` 是两类不同故障：前者通常是“库没有被找到”，后者往往是“找到了库，但版本或ABI不提供调用方所需符号”。必须同时检查调用方声明、搜索规则、实际装载路径和符号版本。

## 1. 动态装载模型

```text
ELF 可执行文件/扩展模块
├─ DT_NEEDED：需要哪些 soname
├─ DT_RPATH / DT_RUNPATH：对象内置搜索路径
├─ LD_LIBRARY_PATH：进程环境路径
├─ /etc/ld.so.cache：ldconfig 生成的缓存
└─ 默认目录：/lib、/usr/lib 及架构目录
```

安全模式、setuid程序、容器和不同glibc版本会改变细节。在线进程的真实答案以 `/proc/<pid>/maps` 为准。

## 2. 找到被分析对象 `[R]`

```bash
python -c 'import torch; print(torch._C.__file__)'
python -c 'import importlib.util; print(importlib.util.find_spec("vllm._C").origin)'
file /path/to/extension.so
stat /path/to/extension.so
```

保存对象哈希、镜像摘要和包版本，避免分析过程中对象被升级替换。

## 3. ldd：解析当前环境会装载什么 `[R]`

```bash
ldd /path/to/extension.so
ldd -v /path/to/extension.so
ldd -r /path/to/extension.so
ldd -u /path/to/extension.so
```

常用选项：

| 选项 | 含义 |
|---|---|
| `-v/--verbose` | 显示符号版本信息 |
| `-r/--function-relocs` | 执行数据和函数重定位，暴露缺少符号 |
| `-d/--data-relocs` | 执行数据重定位 |
| `-u/--unused` | 显示未使用的直接依赖 |

安全提示：不要对不可信二进制直接运行 `ldd`。部分实现可能通过加载器执行对象；不可信样本改用 `readelf -d` 或 `objdump -p` 静态检查。

## 4. readelf：静态读取 ELF `[R]`

```bash
readelf -h /path/to/object.so
readelf -d /path/to/object.so
readelf -Ws /path/to/object.so
readelf -V /path/to/object.so
readelf -n /path/to/object.so
readelf -S /path/to/object.so
```

关键选项：

| 选项 | 内容 |
|---|---|
| `-h/--file-header` | 架构、位数、ABI和文件类型 |
| `-d/--dynamic` | `NEEDED`、`SONAME`、`RPATH`、`RUNPATH` |
| `-s/--syms`、`--dyn-syms` | 符号表与动态符号表 |
| `-W/--wide` | 不截断输出，常与其他选项组合 |
| `-V/--version-info` | GLIBC、GLIBCXX 等符号版本需求 |
| `-n/--notes` | Build ID、ABI note |
| `-r/--relocs` | 重定位项，辅助确定谁引用了符号 |
| `-p/--string-dump`、`-x/--hex-dump` | 查看指定节内容 |

```bash
readelf -d extension.so | grep -E 'NEEDED|RPATH|RUNPATH'
readelf -Ws extension.so | grep 'missing_symbol'
```

## 5. objdump、nm 与 c++filt `[R]`

```bash
objdump -p object.so
objdump -T object.so
nm -D --defined-only provider.so
nm -D --undefined-only caller.so
c++filt '_ZN...'
```

- `objdump -p` 能查看动态节摘要。
- `objdump -T`/`nm -D` 用于动态符号。
- C++ 符号先通过 `c++filt` 反修饰，再比较函数签名和命名空间。
- `strings libstdc++.so.6 | grep GLIBCXX_` 只能作线索；正式证据使用 `readelf -V` 和符号表。

## 6. ldconfig 与系统缓存 `[R/W]`

```bash
ldconfig -p | grep -E 'libcuda|libcudnn|libnccl'
ldconfig -vN 2>/dev/null
cat /etc/ld.so.conf
grep -R . /etc/ld.so.conf.d
```

常见参数：

| 参数 | 含义与边界 |
|---|---|
| `-p` | 只打印当前缓存，安全取证 |
| `-v` | 详细显示扫描目录和链接 |
| `-N` | 不重建缓存 |
| `-X` | 不更新符号链接 |
| `-n DIR...` | 只处理命令行目录，不读取可信目录 |
| `-r ROOT` | 使用替代根目录 |

不带限制运行 `ldconfig` 会更新缓存和soname链接，属于系统级写操作。容器构建和主机变更要分开处理，不能通过挂载宿主机 `/etc/ld.so.cache` 解决镜像依赖。

## 7. 动态加载器诊断 `[R/A]`

```bash
LD_DEBUG=libs,versions python -c 'import torch' 2>ld-debug.log
LD_TRACE_LOADED_OBJECTS=1 /path/to/program
```

`LD_DEBUG` 输出很大，可能包含路径和内部信息；只在受控复现环境中短时启用。不要给整个在线服务长期设置。

glibc系统还可直接调用加载器列出依赖或诊断，但路径随架构不同：

```bash
/lib64/ld-linux-x86-64.so.2 --list /path/to/program
/lib64/ld-linux-x86-64.so.2 --list-diagnostics /path/to/program
```

## 8. 在线进程实际装载结果 `[R]`

```bash
grep -E 'libcuda|libcudnn|libnccl|libtorch|libstdc\+\+' /proc/<pid>/maps
lsof -p <pid> | grep -E '\.so($|\.)'
```

这一步能发现：服务启动后文件已被替换、进程仍持有已删除inode；宿主机和容器看到不同路径；插件运行时才加载了另一份库。

## 9. CUDA/NCCL 排障闭环

```bash
# 1. 调用方声明
readelf -d extension.so | grep -E 'NEEDED|RPATH|RUNPATH'

# 2. 当前解析
ldd -v extension.so

# 3. 系统候选
ldconfig -p | grep -E 'libcuda|libnccl|libcudnn'

# 4. 符号需求与提供
nm -D --undefined-only extension.so | grep SYMBOL
nm -D --defined-only /resolved/provider.so | grep SYMBOL

# 5. 在线进程事实
grep provider.so /proc/<pid>/maps
```

| 现象 | 典型原因 |
|---|---|
| `not found` | 搜索路径、容器注入、soname或挂载缺失 |
| `wrong ELF class` | 32/64位或架构不一致 |
| `version 'GLIBCXX_x' not found` | 运行时 libstdc++ 旧于构建环境 |
| `undefined symbol` | 加载到错误版本、符号被隐藏、ABI/构建选项不兼容 |
| 宿主机正常、容器失败 | Toolkit注入、镜像RUNPATH、挂载覆盖或环境变量差异 |

## 10. 掌握标准 {/* #掌握标准 */}

能静态读出 ELF 依赖与路径；能证明解析到哪一个库；能比较调用方所需和提供方导出的符号；能从在线进程映射确认最终事实；不会使用全局 `LD_LIBRARY_PATH` 或复制随机 `.so` 作为长期修复。
