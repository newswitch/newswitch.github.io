# 训练数据从对象存储到加速器的完整路径

训练性能不只取决于GPU/NPU计算。一个Batch到达加速器前可能经过：

```text
对象存储/数据湖
→ 数据集Manifest
→ 节点下载或流式读取
→ 本地SSD/内存缓存
→ 解压、解析、清洗和Tokenization
→ Sample Sharding与Shuffle
→ DataLoader Worker
→ Host Batch与Pinned Memory
→ H2D拷贝
→ GPU/NPU计算
```

任一环节供给不足都会形成设备空洞。

## 1. 先固定数据集身份

数据集不能只写成`s3://bucket/train/`。至少固定：

```yaml
dataset_name: pretrain-v4
manifest_uri: s3://datasets/pretrain-v4/manifest.jsonl
manifest_sha256: <hash>
schema_version: "3"
sample_count: <count>
total_bytes: <bytes>
tokenizer_revision: <hash>
filter_config_sha256: <hash>
```

Manifest逐分片记录URI、大小、摘要、样本数和可选统计。目录内容发生变化时，训练仍能复现相同快照。

## 2. 文件粒度

大量小文件会产生：

- 对象存储请求放大；
- Metadata和TLS开销；
- DataLoader频繁打开关闭；
- Shuffle和恢复状态复杂；
- 共享文件系统Metadata瓶颈。

超大单文件又会降低并行读取和故障恢复粒度。常见做法是将样本打包为适中Shard，并在Shard内建立索引。

最佳大小取决于网络、压缩、样本大小、Worker数和故障恢复要求，需要压测。

## 3. 三种读取方式

| 方式 | 优点 | 风险 |
| --- | --- | --- |
| 共享文件系统直读 | POSIX简单 | 集群并发、Metadata与网络热点 |
| 对象存储流式 | 无需全量落盘 | 网络抖动、重试、随机访问成本 |
| 预取到节点本地SSD | 训练稳定、吞吐高 | 缓存容量、预热时间、一致性 |

大规模训练常采用“对象存储为真源、本地SSD为可丢弃缓存”。缓存键使用内容摘要而不是可变路径。

## 4. 分布式Sharding

设`world_size=N`，每个Rank应获得不重复且覆盖完整的数据子集：

```text
global sample stream
→ 按epoch和seed打乱
→ shard by rank/worker
→ 每Rank本地batch
```

需要明确：

- Shuffle Seed；
- Epoch定义；
- 最后不足Batch是丢弃、Padding还是不均；
- DataLoader Worker再分片；
- 节点弹性变化后如何重算；
- 恢复时从Sample、Shard还是Step继续。

错误分片可能不报错，却让样本重复或遗漏，直接影响训练质量。

## 5. Tokenization位置

### 5.1 离线Tokenization {/* #离线tokenization */}

优点是训练CPU开销低、长度可提前统计；缺点是Tokenizer变化需要重建数据且存储更大。

### 5.2 在线Tokenization {/* #在线tokenization */}

优点是数据灵活；缺点是CPU、进程间传输和抖动可能让加速器等待。

无论哪种方式，Tokenizer和Chat/训练模板Revision必须进入数据Manifest。

## 6. DataLoader流水

```text
Storage Reader
→ Decode/Parse
→ Tokenize/Augment
→ Collate/Pad/Pack
→ Prefetch Queue
→ Pinned Host Memory
→ Async H2D
```

调优参数包括Worker数、Prefetch深度、Persistent Worker、Pinned Memory和Batch Packing。Worker越多不一定越快，过多会竞争CPU、内存带宽、文件句柄和对象存储连接。

## 7. 判断数据供给不足

证据组合：

- GPU/NPU Kernel后出现周期性长空洞；
- 每Step Data Time高或抖动大；
- DataLoader队列经常为空；
- CPU解析/Tokenization满；
- 本地盘或网卡吞吐达到上限；
- 对象存储延迟和错误上升；
- 增大纯计算Batch后设备利用率仍不上升。

应分段测存储读取、CPU处理、Host Batch和H2D，不能只看总Step Time。

## 8. Checkpoint里必须有什么

恢复训练不只保存模型参数：

```text
模型权重
优化器状态
LR Scheduler
GradScaler/混合精度状态
全局Step与Epoch
随机数状态
数据集Manifest摘要
Sampler/Shard游标
并行拓扑与分片元数据
代码、镜像和配置坐标
```

缺少数据游标时，恢复可能重复大量样本；缺少随机状态时，结果不再严格可复现。

## 9. 分布式Checkpoint一致性

每Rank写分片时需要一个提交协议：

```text
所有Rank写临时目录
→ 各分片完成并生成摘要
→ Barrier/协调器确认齐全
→ 写Checkpoint Manifest
→ 原子发布COMPLETED标记
```

恢复端只读取带完成标记且Manifest校验通过的版本。不能把“目录存在”当成完整Checkpoint。

## 10. 对象存储写入

推荐：

```text
训练进程写节点本地临时文件
→ 异步上传到唯一版本路径
→ 校验对象ETag/摘要
→ 最后上传Manifest与完成标记
→ 生命周期策略清理旧版本
```

直接覆盖`latest/`容易在上传中被恢复任务读到半成品。`latest`只能是指向不可变Checkpoint ID的小元数据。

## 11. 恢复演练

1. 正常Step触发Checkpoint。
2. 写到一半杀死一个Rank，确认不会发布完成标记。
3. 从最近完整Checkpoint恢复。
4. 核对全局Step、Loss、LR和数据游标。
5. 比较恢复前后短窗口训练曲线。
6. 节点数不变与变化两种场景分别验证。
7. 模拟对象存储超时和分片损坏。

“程序能加载权重”不是完整恢复验收。

## 12. 观测指标

```text
data_wait_time / step_time
samples_per_s / tokens_per_s
对象存储请求延迟、吞吐、重试
本地缓存命中与容量
DataLoader Queue深度
CPU/内存/本地盘/网卡
H2D时间
Checkpoint生成、上传和恢复时间
损坏/不完整Checkpoint数量
```

## 13. 验收清单

```text
[ ] 数据Manifest不可变并有摘要
[ ] Rank/Worker分片无重复遗漏
[ ] Tokenizer和模板进入数据版本
[ ] 数据供给在目标规模有余量
[ ] 节点缓存可丢弃且自动重建
[ ] Checkpoint包含模型外的训练状态
[ ] 分布式写入有完成协议
[ ] 恢复验证包含数据游标与训练曲线
[ ] 存储故障不会产生可见半成品
```
