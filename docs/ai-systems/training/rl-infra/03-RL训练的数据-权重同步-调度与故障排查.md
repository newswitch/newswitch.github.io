# RL 训练的数据、权重同步、调度与故障排查

大模型 RL 系统不是单一训练 Job，而是多个速率不同、状态不同、失败方式不同的阶段：

```text
Prompt Queue
→ Rollout Pool
→ Reward/Verifier Pool
→ Experience Store
→ Trainer
→ Weight Publisher
→ Rollout Pool加载新版本
```

稳定运行的关键是：每条数据能解释、每个版本能定位、每段队列有上限、任一阶段失败后能从一致状态继续。

## 1. 数据面：Experience 不是普通文本

Experience 同时包含语义数据和训练状态：

- Prompt/Completion Token；
- Old/Reference Log Prob；
- Reward、Advantage、Mask；
- Policy/Tokenizer/Template Version；
- Sampling 参数和结束原因；
- Group/Trajectory ID；
- 可选 Value、Router Route、过程奖励；
- Schema Version 与 Checksum。

文本相同不代表 Experience 等价：不同 Policy 产生的 Old Log Prob 不同，不同模板得到的 Token 也不同。

## 2. 原子提交

一条轨迹常由多个对象组成。推荐状态机：

```text
WRITING
→ Token/LogProb/Route等分片写入临时位置
→ 校验长度与Checksum
→ 写Manifest
→ 原子标记COMMITTED
→ 下游只读取COMMITTED
```

若直接让 Trainer 监听目录中新文件，可能读到半写入对象。对象存储没有传统文件 Rename 语义时，可用不可变对象 Key + 最终 Manifest/Commit Marker。

## 3. 有界队列与反压

设各阶段处理率：

```text
λ_rollout, μ_reward, μ_train
```

若 Rollout 长期快于 Trainer，Experience 会无限堆积，带来：

- 存储和 Host Memory 膨胀；
- Policy Version Lag 增大；
- 训练越来越 Off-policy；
- 故障恢复窗口变长。

每段队列需要：

- 最大对象数/Token 数/字节数；
- 高低水位；
- Producer 暂停或降速；
- 过旧版本拒收/丢弃策略；
- 超时、重试和 Dead Letter；
- Queue Age 与 Version Lag 告警。

反压是正确性机制，不只是资源保护。

## 4. Policy Version 协议

每次可发布权重分配不可变版本：

```text
policy_version = checkpoint_hash + training_step + model_config_hash
```

Rollout 开始一组采样前锁定版本，并将其写入每条 Experience。同一 GRPO Group 不应在生成过程中混用两个 Policy Version。

Trainer 对每批数据定义接受窗口：

- 严格 On-policy：只接受当前或指定 Old Policy；
- 有界陈旧：允许落后不超过 `N` 个版本；
- 超窗数据丢弃或重新生成；
- 任何策略都需由算法验证，而不是由队列偶然决定。

## 5. 权重发布不是复制一个目录

完整发布流程：

```text
Trainer完成一致Checkpoint
→ 写临时版本目录
→ 校验参数分片、配置和Tokenizer
→ 生成Manifest与Hash
→ 转换为Rollout需要的并行/推理布局
→ 在Canary Rollout Worker加载
→ 健康、数值与生成测试
→ 原子更新Active Version指针
→ 其他Worker在安全边界切换
```

需要避免：

- TP/PP/EP 分片布局与 Rollout 不一致；
- Worker 只加载了一部分 Shard；
- 一半副本已切新版本、一半仍旧版却没有路由隔离；
- KV/Prefix Cache 跨权重版本复用；
- 加载失败后 Active 指针已提前更新。

## 6. 权重同步方式

| 方式 | 优点 | 边界 |
| --- | --- | --- |
| Checkpoint/对象存储 | 解耦、可审计、易恢复 | 写读慢、转换与冷加载成本高 |
| CPU内存/RDMA传输 | 延迟低 | 协议、拓扑、内存和失败恢复复杂 |
| 训练/推理共置切换 | 少跨机传输 | 资源相互干扰、KV/Optimizer切换复杂 |
| 增量/Adapter同步 | 传输量小 | 只适用于权重更新形式和Runtime支持的场景 |

选择时比较“每个有效训练 Step 的总时间”，而不是只比较网络传输峰值。

## 7. 资源调度

Rollout、Reward 和 Trainer 的资源曲线不同：

| 阶段 | 主要资源 | 典型瓶颈 |
| --- | --- | --- |
| Rollout | GPU/NPU HBM、KV、Decode带宽 | 长尾生成、Prefix、调度和推理Kernel |
| Reward | GPU/NPU或CPU、批处理 | 长度、多个Verifier、外部工具 |
| Trainer | GPU/NPU计算、激活、Optimizer、集合通信 | Backward、AllReduce、Checkpoint |
| Data/Store | CPU、内存、网络、对象存储 | 序列化、小文件、队列和版本GC |

调度器需要考虑：

- Gang Scheduling 与分布式训练全员到齐；
- GPU/NPU 型号和拓扑；
- Rollout/Trainer 是否允许抢占；
- 权重版本和数据位置；
- 训练 Checkpoint 窗口；
- N-1、发布和故障恢复余量。

## 8. Checkpoint 应保存哪些状态

只保存模型权重不足以恢复 RL 闭环：

```text
Actor/Policy参数
Optimizer与LR Scheduler
Critic/Reward（若共同训练）
随机数状态
训练Step/Epoch
Prompt数据游标
已消费Experience边界
Active/Old/Reference版本
GRPO Group完成状态
QAT/Router等扩展状态
Schema与代码版本
```

恢复时要么重放一个明确定义的幂等边界，要么丢弃未提交批次。不能同时“继续消费旧队列”又“从更早训练 Step 恢复”而不处理重复样本。

## 9. 阶段级 SLO

| 阶段 | 关键指标 |
| --- | --- |
| Prompt | 可用数量、重复率、过滤率 |
| Rollout | tokens/s、P99时长、完成率、Version |
| Reward | Queue Age、评分延迟、各子项分布、错误 |
| Experience | COMMITTED率、字节、Schema错误、Version Lag |
| Trainer | Step时间、MFU、KL、Clip、梯度、有效样本/s |
| Weight Sync | 发布时长、加载成功率、活动版本分布 |

最终容量指标建议使用：

```text
有效且满足数据/质量门槛的训练Token或样本 / GPU小时
```

Rollout tokens/s 很高但大部分样本因版本过旧或 Reward 失败被丢弃，不是有效吞吐。

## 10. 典型故障一：Trainer 等不到数据

按顺序检查：

1. Prompt Producer 是否还有数据；
2. Rollout Queue、运行副本和生成完成率；
3. Reward 是否积压或外部 Verifier 超时；
4. Experience 是否停在 WRITING；
5. Schema/Version 校验是否大批拒绝；
6. Group 是否因一个缺失 Completion 永远不完整；
7. Trainer 是否在数据、通信或 Checkpoint Barrier 等待。

不要只扩 Trainer GPU。若 Reward 是瓶颈，扩训练只会增加空等成本。

## 11. 典型故障二：Reward 突然漂移

检查：

- Reward Model/规则版本是否变化；
- 输入模板、截断和解析是否变化；
- Completion 长度分布是否变化；
- 某子项是否常量、NaN 或权重配置错误；
- GRPO Group 是否错误混合；
- 新 Policy 是否发现 Reward 漏洞；
- 抽样原始案例能否人工复核。

总 Reward 平均值可能正常，但某个关键子项已经失效，因此必须保留分项和版本。

## 12. 典型故障三：权重发布后 Rollout 异常

快速回退 Active Version，然后比较：

- Manifest、Shard 数与 Hash；
- Trainer 和 Rollout 并行布局；
- Tokenizer/模板/模型配置；
- 量化或推理格式转换；
- Worker 实际活动版本；
- KV/Prefix Cache 是否清空或按版本隔离；
- Canary 数值和固定 Prompt 输出。

发布成功的结束条件不是“文件复制完成”，而是目标副本加载、版本一致、生成契约和性能通过。

## 13. 典型故障四：GPU 利用率高但有效样本下降

可能原因：

- 生成长度变长但 Reward 通过率下降；
- Trainer 重复计算被丢弃的旧版本 Experience；
- Reward/格式错误导致样本无效；
- 大 Group 增加采样但组内同分，优势接近零；
- 通信或重算让设备忙，却没有提高有效 Token；
- 过深队列提高利用率但放大 Version Lag。

要把设备忙碌、原始吞吐和有效训练吞吐分开。

## 14. 故障注入与恢复演练

至少验证：

- Kill 一个 Rollout Worker，未完成轨迹如何清理；
- Reward 服务超时，是否有重试上限和幂等 ID；
- Experience 写到一半进程退出，下游是否拒读；
- Trainer 在参数更新/Checkpoint 中断，恢复边界是什么；
- 权重转换失败，Active Version 是否保持不变；
- 一半 Rollout Worker 加载新版本失败，是否能隔离和回滚；
- 对象存储短暂不可用，内存队列是否有界；
- 恢复演练能否还原数据游标、Policy Version 和 Optimizer。

## 15. 自测题与答案

### 15.1 为什么队列必须限制 Token/字节，而不能只限制对象数？

轨迹长度差异很大，同样 1000 个对象可能相差数十倍内存和存储。按对象数、Token、字节和 Age 同时设界限，才能反映真实资源和版本陈旧风险。

### 15.2 为什么同一 GRPO Group 不能混用两个 Policy Version？

组内 Completion 应来自同一行为策略，Old Log Prob 和相对 Reward 才有一致解释。混用版本会把策略差异掺入组内比较，破坏 Ratio 与 Advantage 语义。

### 15.3 权重同步完成的判据是什么？

一致 Checkpoint 已生成并校验，转换布局与制品完整，Canary 加载和固定输入验证通过，Active Version 原子切换，目标 Worker 报告同一版本，并且失败时可回退。

### 15.4 为什么“每天有备份”仍不足以保证可恢复？

恢复还依赖优化器、数据游标、队列提交边界、Policy/Reference版本和运行代码。必须定期在隔离环境完成 Restore、启动、数据一致性和继续训练验证。

### 15.5 Rollout 与 Trainer 速率不匹配时先扩谁？

先看各阶段处理率、Queue Age 和有效样本丢弃原因。瓶颈在 Rollout 才扩 Rollout，瓶颈在 Reward 或 Trainer 则处理对应阶段；若数据因版本陈旧被丢弃，还应降低上游速率和缩短同步周期。
