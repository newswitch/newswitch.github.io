# Prolog、Epilog 与作业清理边界

Prolog/Epilog 是 Slurm 生命周期中的扩展点，适合执行短小、可重复的环境检查和清理。它们不是新的配置管理系统，也不能代替应用的 Checkpoint 协议。钩子放错位置，可能把一次业务故障扩大成节点不可调度。

## 1. 同样叫钩子，执行位置并不一样

| 类别 | 典型位置和身份 | 需要区分的时机 |
| --- | --- | --- |
| Prolog / Epilog | 计算节点，由 slurmd 侧执行，通常为 SlurmdUser | 节点上的作业准备与终止清理 |
| PrologSlurmctld / EpilogSlurmctld | 控制器，以 SlurmctldUser 执行 | 资源分配与释放相关事件 |
| TaskProlog / TaskEpilog | 任务节点，以任务用户身份执行 | 单个任务执行前后 |
| SrunProlog / SrunEpilog | 发起 srun 的位置 | Step 提交侧生命周期 |

节点 Prolog 默认并非“资源一分配就立刻在所有节点执行”，其触发还与首次启动及 `PrologFlags=Alloc` 等设置有关。应根据目标版本配置确认，不要把一个钩子的时间轴套到另一个上。官方执行身份、顺序和失败语义见 [Prolog and Epilog Guide](https://slurm.schedmd.com/prolog_epilog.html)。

一个直接推论是：控制器能访问的路径，计算节点未必能访问；提交节点的临时文件，也不会因为同一个 Job ID 自动出现在各节点。钩子依赖共享存储时，要明确存储故障是否应该阻断调度。

## 2. 失败语义决定故障的扩散范围

节点 Prolog 失败可以使节点 DRAIN，并使批作业重新排队、按配置进入 hold；节点 Epilog 失败也可以导致 DRAIN。控制器 Epilog 失败的处理并不相同，不能泛化成“任何 Epilog 非零都会自动重试作业”。具体规则仍以上述官方指南及本集群选项为准。

这意味着一个临时 DNS 请求、慢 API 或不稳定挂载，如果被设置为 Prolog 的硬依赖，就可能批量耗尽可调度节点。决定钩子退出码之前，应定义这个检查是否真的说明“节点不应再接任务”。外部通知失败通常不应与残留设备访问同级处理。

## 3. 幂等清理比“最后运行一次”更重要

可恢复的钩子应满足：准备执行到一半失败时能再次执行；资源已经不存在时清理仍能正确结束；失败日志能指出清理的是谁的资源。建议用 Job、节点及运行尝试关联临时对象，避免共享一个全局临时目录。

考虑教学时间线：

```text
创建临时目录成功 → 挂载失败 → Prolog 返回非零
→ 作业重新尝试 → 再次创建与检查
```

如果第二次仅因“目录已存在”就失败，会形成无意义重试；如果直接清空整个父目录，又可能删除其他作业数据。正确实现需要识别所有权、检查实际挂载状态，并只处理明确属于本次对象的资源。清理动作应有上限和超时，不做无限等待。

## 4. 为什么 Prolog 里的 GPU 编号会不同

钩子执行上下文与任务的设备 cgroup、CUDA 可见性可能不同。宿主机物理编号为 1 的 GPU，在只暴露这张卡的任务内可能成为逻辑编号 0。这不等于分错了卡。

因此日志应优先关联 UUID、PCI BDF 与资源分配记录，再解释上下文内的编号。不能把 Prolog 看到的 `CUDA_VISIBLE_DEVICES=1` 原样写进容器，期待里面必然存在设备 1。隔离层原理见 [cgroup 与亲和性](./04-cgroup-CPU-GPU-NUMA与进程亲和性.md)。

## 5. 钩子不要变成隐藏的控制平面

官方建议保持钩子短小，并避免在其中调用 Slurm 命令。大量作业同时启动时，每个钩子再轮询控制器，可能形成放大请求和相互等待。基础镜像准备、软件安装与长健康检查更适合放在节点交付或入池流程中。

设一个教学集群同时释放 200 个节点，每个钩子每秒查询控制器两次，单个钩子持续 30 秒，就额外产生约 `200×2×30=12000` 次请求。这个数字不是 Slurm 容量上限，只说明为什么看似轻量的局部轮询会变成全局压力。

以 root 运行的节点钩子还应把用户输入视为不可信数据：参数要校验，路径要限定，程序用绝对路径，不执行用户可写目录里的脚本，不把环境变量直接拼成 shell 命令。生命周期便利不构成提升租户权限的理由。

## 6. Epilog 为什么不能承担最后一次模型保存

应用结束、异常退出或节点失联后，训练进程可能已经不存在。即便 Epilog 可以执行，也未必有权恢复它的显存和分布式状态。因此模型保存应在应用仍持有一致状态时完成；Epilog 更适合验证残留、归档短日志和释放临时资源。

验收清理不能只看 Epilog 退出零。还要检查没有遗留进程、设备访问和作业专属挂载，节点能重新运行受控测试。若清理失败导致 DRAIN，应保留原因并验证修复，不应自动清除状态掩盖问题。

## 7. 掌握检查

解释为什么一个通知接口超时可能导致全池 DRAIN；为什么控制器钩子不能假定本地拥有 GPU；为什么同一张卡在钩子和任务中编号不同；为什么清理代码必须支持部分执行后重试。再为一个挂载检查明确写出：超时、退出码、所有权和失败后的最小动作。
