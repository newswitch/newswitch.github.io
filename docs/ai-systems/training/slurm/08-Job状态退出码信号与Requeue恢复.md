# Job 状态、退出码、信号与 Requeue 恢复

Slurm 的成功状态、进程退出结果与训练结果是三份不同事实。可靠恢复不是给作业加一个 requeue 开关，而是让调度器重新启动之后，应用能够识别上一次尝试、读取完整状态并继续产生正确结果。

## 1. 先区分 Job、Step 与一次运行尝试

Job 是资源申请和分配的管理对象，Step 是其中启动的执行单元。批脚本本身也有执行记录；训练进程、预处理和结果上传可能属于不同 Step。一个 Job 经过重新排队，可以对应多次从脚本开头开始的运行尝试。

Slurm 内部状态包含基本状态及标志，命令行显示可能把某个标志折叠成最终看到的状态名。`COMPLETING` 可以表示正在清理，而不是训练仍在计算；`RUNNING` 也不等于所有 Rank 都在正常推进。参见 [Job 状态定义](https://slurm.schedmd.com/job_state_codes.html)。

因此应保存 Job ID、Step ID、节点、开始结束时间和重启次数，另外给应用建立稳定的逻辑 run ID。不要让“第几次执行”只存在于日志文件名中。

## 2. 为什么训练失败，Job 却可能 COMPLETED

批作业的 Job 退出码来自批脚本，而不是自动替所有业务步骤做正确性判断。Step 各自有退出码；记账中的 `exit:signal` 分别表示退出值与终止信号。DerivedExitCode 可提供 Step 汇总线索，但也不是训练结果验证器。见 [Slurm 退出码说明](https://slurm.schedmd.com/job_exit_code.html)。

下面的错误传播差异可在没有 GPU 的 Bash 环境中理解：

```bash
# 错误示意：上一条失败后，成功的 echo 成为脚本最终退出结果
false
echo 'finished'
```

真实作业若把 `false` 换成失败的 `srun`，也可能隐藏错误。最小的显式传播方式是：

```bash
srun ./train
task_rc=$?
if [ "$task_rc" -ne 0 ]; then
    exit "$task_rc"
fi
./verify_output
```

此示例假设没有提前触发的 `set -e`，并且训练在前台执行。使用管道、后台进程或多次 `wait` 时，还要分别定义错误汇总规则；不能只添加一行 `set -e` 就认为所有异步错误都被覆盖。即使所有命令返回零，模型制品仍需要完整性和语义检查。

## 3. 信号是通知，不是 Checkpoint 事务

`--signal` 可以在时间限制前发送通知。默认目标与 `B:` 指定的批 shell 不同：`B:` 只通知批 shell，不会自动替它通知所有 Step。通知时间也不是实时系统意义上的精确秒点，参见 [sbatch 信号选项](https://slurm.schedmd.com/sbatch.html)。

设计时要回答：谁收信号、谁协调各 Rank、谁写状态、谁确认写完。Shell 收到信号，不代表 Python 已处理；某个 Rank 写完，也不代表全部分片已经可恢复。节点突然失联甚至没有机会处理通知。

更稳妥的应用设计是让处理器设置停止请求，由训练主循环在安全边界协调保存，再发布完成标记。不要在异步信号处理器中直接执行复杂分布式通信，并假设不会与正常通信死锁。

## 4. Requeue 恢复的是调度资格，不是内存

重新排队后，批脚本从头执行；GPU 上下文、进程地址空间和未落盘优化器状态不会因此回来。是否允许以及何时发生 requeue，还受集群配置、作业选项、抢占和故障策略影响。见 [sbatch 的 requeue 语义](https://slurm.schedmd.com/sbatch.html)。

应用恢复应按如下顺序思考：

```text
重新获得资源 → 识别新尝试 → 找到已提交的 Checkpoint
→ 校验分片与版本 → 恢复状态 → 重建通信 → 从一致进度继续
```

“目录存在”不是已提交。一个恢复点至少应关联模型、优化器、调度器、随机状态、数据消费位置，以及分布式分片布局。哪些状态可重建，必须由算法与框架明确保证，详见[容器、数据与 Checkpoint](./06-Enroot-Pyxis-Apptainer数据挂载与Checkpoint.md)。

## 5. 时间线推演：为什么只能退回到更早一步

假设 step 100 的全部分片和 manifest 已完成提交；step 120 只写出部分文件时节点故障。新尝试不能因为目录编号更大就选择 120，应回到已验证的 100，并按定义重新处理后续数据。

若每步耗时 2 秒、每 20 步提交一次，稳定运行中的重算窗口约为 0 到 40 秒，另加保存与恢复成本。这只是教学模型：故障分布不均、异步保存延后提交、多阶段状态不同步，都可能扩大窗口。

重复尝试还会重复执行脚本前面的副作用。创建实验记录、上传结果、扣费或通知都需要幂等设计；“检查文件存在就跳过”也要防止把半成品当成功。相同逻辑运行的结果发布应有去重身份，不要把 Job ID 相同误读为只执行过一次。

## 6. 恢复需要的最小证据

先用 `sacct` 对比 Job 与各 Step 的 State、ExitCode、DerivedExitCode 和时间，再结合控制器、节点、应用日志重建时间线。记账可能存在延迟或采集缺口，不能把查不到记录直接当成未执行。

每次恢复至少记录选择了哪个 Checkpoint、为何它完整、恢复到了哪一步、哪些输出可能重复、是否更换了节点与资源布局。只看到新 Job 进入 RUNNING，还没有证明恢复成功。

## 7. 掌握检查

请解释四个反例：Job 返回零而训练 Step 失败；批 shell 收到 USR1 而 Rank 未保存；requeue 后从头训练；最新 Checkpoint 目录存在但不能恢复。进一步说明：如果恢复时 world size 改变，哪些状态必须由框架进行重分片，而不是运维脚本简单复制。
