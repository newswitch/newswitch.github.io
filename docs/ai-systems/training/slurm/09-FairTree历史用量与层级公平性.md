# Fair Tree、历史用量与层级公平性

公平调度不是让每个用户此刻获得相同 GPU 数。Slurm Fair Tree 用组织层级和历史消耗影响优先级，让近期使用较多的关联在相应兄弟范围内让出机会。它不同于瞬时资源均分，也不同于一份永久资源预留。

本文聚焦 `priority/multifactor` 中的 Fair Tree；实际是否启用、TRES 如何计费和历史如何衰减，以集群配置为准。不能把 Classic Fairshare 的公式拿来代替它。

## 1. Shares 是树上的权重，不是整集群配额

账户与用户关联组成树。一个节点的 shares 首先在其兄弟集合内归一化；跨层比较原始 shares 没有直接意义。例如某部门 shares=10，不表示它必然比另一个部门下面 shares=20 的用户获得更低待遇。

历史用量也要放在同级父关联范围内解释。GPU、CPU 等资源如何形成计费量，受到 TRES 权重和记账策略影响。一个 GPU 小时与一个 CPU 小时不能凭名称直接相加比较。

因此应先画账户树，再标注各关联的份额、用量和资源计费单位。缺少树的“某用户公平性低”截图，很容易把父账户的历史影响误归因于该用户本人。

## 2. 核心过程：同级比较，再沿树排名

Fair Tree 使用 Level FS 比较同级关联，基本关系为 `LF = S / U`：S 是相对兄弟归一化的 shares，U 是相对兄弟归一化的有效用量。算法按层级组织排序和用户排名，而不是把所有用户的 LF 扔进一个全局排序表。更高排序的兄弟账户，其后代用户的 Fairshare 因子高于较低排序账户的后代。规则与平局处理见 [SchedMD Fair Tree 说明](https://slurm.schedmd.com/fair_tree.html)。

零用量会形成特殊排序值；相同 LF 还涉及合并比较等平局规则。下面刻意避开这些情况，专门说明层级优先于跨部门局部比较的含义。

## 3. 手算一个没有平局的账户树

假设只有两个一级账户 A、B，各有两个用户。所有历史用量已经按同一计费规则得到，不额外考虑其他关联：

```text
root
├─ A：shares 1，用量 30
│  ├─ a1：shares 1，用量 10
│  └─ a2：shares 1，用量 20
└─ B：shares 1，用量 70
   ├─ b1：shares 1，用量 5
   └─ b2：shares 1，用量 65
```

一级比较得到 A 的 `S=0.5，U=0.3，LF≈1.667`，B 的 `LF≈0.714`，所以先访问 A 的分支。在 A 内，a1 的 `LF=0.5/(10/30)=1.5`，a2 为 `0.75`；在 B 内，b1 为 `7`，b2 约为 `0.538`。

最终用户顺序是 `a1 → a2 → b1 → b2`，不是按全局 LF 得到的 b1 第一。若这四个就是参与排名的全部用户关联，按文档的 rank/用户关联总数计算，Fairshare 因子依次为 `1、0.75、0.5、0.25`。

这说明部门内部节制使用的用户，仍受到部门整体历史用量影响。这是层级政策的结果，不是计算精度错误。改变组织树相当于改变政策，不能只为调整某个人的排队位置随意重挂账户。

## 4. 历史衰减为什么不等于“到点清零”

若采用半衰期模型，较早的用量随时间降低影响；这与按月硬重置不同。具体衰减、重置、计算周期配置见 [多因子优先级文档](https://slurm.schedmd.com/priority_multifactor.html)。

教学上，假设一次用量为 80 单位，半衰期一天且没有新用量，过一天贡献为 40，两天为 20。但若 A、B 的用量都按同一比例衰减，二者的归一化比例不变，LF 和相对排名也可能不变。不能承诺“等一个半衰期，我就一定排到前面”。

新用量、活跃关联、账户结构变化以及计算周期都会影响观察。重新载入配置后，相关计算也不一定在同一瞬间全部刷新，分析要保存采样时间。

## 5. Fairshare 排名不是最终开跑顺序

多因子优先级还可能包含 Age、Partition、QOS、Job Size、TRES 等因素及权重。即便最终优先级更高，也必须满足限制、节点形状、预约和其他可行性条件；Backfill 还可能让不妨碍未来预约的小作业先运行。详见[Backfill 与调度](./03-Backfill-优先级-抢占-Gang与拓扑调度.md)。

排查时分三步：先用 `sshare -l` 理解关联层级与 Level FS，再用 `sprio` 理解具体 Job 的各项优先级贡献，最后查看 Pending 原因和资源形状。Fair Tree 下展示的 NormUsage 不能被直接当成参与 LF 的同级有效用量来套公式。

## 6. 源码：为什么不是全局 LF 排序

以 [Slurm 25.05.9 的 fair_tree.c](https://github.com/SchedMD/slurm/blob/slurm-25-05-9-1/src/plugins/priority/multifactor/fair_tree.c) 为阅读基线。`_ft_set_assoc_usage_efctv()` 使用当前关联与其公平性父关联的原始用量计算同级有效用量；`_calc_assoc_fs()` 再计算 LF，并单独处理零 shares 和 USE_PARENT 等情况。这里还调用了 NormUsage 更新函数，但 LF 使用的不是那个展示字段。

关键在 `_calc_tree_fs()` 接收的是兄弟数组，计算当前层后执行下面这句排序，而不是构造全部用户的全局数组：

```c
qsort(siblings, i, sizeof(slurmdb_assoc_rec_t *), _cmp_level_fs);
```

遍历遇到用户时写入排名因子，遇到账户时组织其子项并递归。因子赋值为：

```c
assoc->usage->fs_factor =
    *rank / (double) g_user_assoc_count;
```

这条调用关系解释了前面 a2 为什么仍能排在 b1 前面：父分支已经决定了访问顺序。平局还走专门路径，不能用本篇无平局手算替代所有边界。阅读入口中的锁保护与随后 Job 加权计算也说明，关联公平性和最终作业优先级是两个阶段。源码片段仅解释该 tag 的实现特色，不把它扩展成其他版本的性能结论。

## 7. 掌握检查

能手算上面的树，并回答：为什么 LF=7 的 b1 仍排在 a2 后；为什么账户 shares 不是 GPU 硬配额；为什么共同衰减不一定改变排名；为什么 Fairshare 第一也可能继续 Pending。最后用一个实际 Job 的优先级分解说明，改变 Fairshare 权重是否真的足以改变排序。
