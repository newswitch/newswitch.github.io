# FunASR 组件、模型与离线、流式、两遍识别链路

分析FunASR最有效的方法不是背模型名，而是追踪“一段音频从字节到最终文本”的状态变化。每个组件都应有明确输入、输出和失败表现，这样遇到空结果、乱码、延迟或句尾不返回时，才能把问题定位到具体一层。

## 1. 输入不是“声音”，而是有格式的数字序列

客户端提交的音频至少包含四个关键属性：

| 属性 | 含义 | 不匹配的影响 |
| --- | --- | --- |
| 采样率 | 每秒采样点数，如16 kHz | 语速、频谱和模型时间尺度错误 |
| 位深 | 每个采样点精度，如16-bit | 按错误字节宽度解析会产生噪声 |
| 声道 | 单声道或双声道 | 错误交织会改变波形或时长 |
| 编码/容器 | PCM、WAV、MP3等 | 原始PCM没有文件头，不能自动猜全部参数 |

16 kHz、16-bit、单声道PCM的原始数据率为：

```text
16000 samples/s × 2 bytes × 1 channel = 32000 bytes/s
```

若客户端每40 ms发送一次，应约为1280字节。这个简单计算可以快速发现WebSocket客户端发送块大小、采样率声明和实际音频不一致。

### 1.1 WAV与PCM不能混为一谈

WAV通常带有描述采样率、声道和编码的文件头；裸PCM只有采样值，服务必须从参数知道怎样解释。把带WAV头的数据当裸PCM发送，开头几十字节会被当成波形；把裸PCM当文件上传，解码器可能直接拒绝。

可先用工具确认：

```bash
ffprobe -hide_banner input.wav
soxi input.wav
file input.wav
```

统一为常见的16 kHz单声道PCM WAV：

```bash
ffmpeg -i input.mp3 -ar 16000 -ac 1 -c:a pcm_s16le output.wav
```

具体采样率应以所选模型说明为准，不是所有模型都固定16 kHz。

## 2. 组件关系

```text
音频输入
  │
  ├─ 解码/重采样：把各种文件和编码统一为模型需要的波形
  │
  ├─ VAD：回答“哪里有人声、句子何时开始和结束”
  │
  ├─ ASR：回答“这段语音说了什么”
  │   ├─ online：按Chunk增量输出
  │   └─ offline：看到完整语音段后输出
  │
  ├─ 时间戳：把字、词或句与音频时间位置对齐
  │
  ├─ PUNC：恢复逗号、句号、问号等标点
  │
  └─ ITN：把口语文本规范化，如数字、日期、金额
```

### 2.1 VAD不是识别模型

VAD通常输出语音片段的开始和结束位置，不负责把声音变成文字。它的阈值过于激进会截掉句首/句尾，过于保守会把长静音送给ASR，增加延迟和无效计算。

### 2.2 ASR是核心识别层

ASR从声学特征或波形生成Token/文字。在线模型为了低延迟只能看到有限的左侧上下文，离线模型看到完整语音段，通常能利用更完整的上下文得到更稳定的结果。

### 2.3 标点和ITN是文本后处理，但不是装饰

无标点文本可读性差，语音命令的语义边界也可能不清楚。ITN把“二零二六年九月二日”规范为业务需要的表达形式。它们会影响最终文本，因此升级时必须分别验证，不能只判断HTTP 200。

## 3. 离线识别完整路径

```text
HTTP/文件/内存中的完整音频
  → 音频解码
  → 重采样和声道转换
  → VAD切出一个或多个语音段
  → 段级ASR
  → 时间戳对齐
  → 合并各段
  → 标点恢复
  → ITN
  → 最终文本
```

离线识别已经拥有完整音频，容易做批处理和更大上下文推理。它的主要延迟是上传、排队、解码和全部音频推理时间，而不是“第一个Token”。

对于离线服务，常用指标是：

- 请求总延迟；
- 排队时间；
- 音频解码时间；
- VAD和ASR时间；
- RTF；
- 每小时音频吞吐量；
- CER/WER和空结果率。

## 4. 在线流式识别路径

客户端先建立长连接并发送控制参数，再连续发送音频块：

```text
建立WebSocket
  → 发送模式、采样率、Chunk和热词等配置
  → 连续发送二进制音频Chunk
  → 服务为该连接维护在线模型状态
  → 周期性返回临时结果
  → 客户端发送结束标志
  → Flush剩余状态并返回最终结果
  → 释放会话缓存
```

流式模型不能每收到一个Chunk就从头识别全部历史音频，否则计算量会随会话长度不断增长。服务通常为每个会话维护Encoder/Decoder缓存和上下文。

### 4.1 Chunk参数的含义

FunASR官方WebSocket示例会出现：

- `chunk_size`：模型处理块的结构配置；
- `chunk_interval`：客户端发送与模型处理块之间的节奏关系；
- `encoder_chunk_look_back`：Encoder回看多少历史块；
- `decoder_chunk_look_back`：Decoder使用多少历史上下文；
- `audio_fs`：客户端声明的采样率；
- `hotwords`：热词及其权重；
- `itn`：是否使用文本规范化。

这些参数不是越大越好：

| 调整 | 潜在收益 | 代价 |
| --- | --- | --- |
| 更小Chunk | 临时结果更快 | 调用频繁、上下文少、效率下降 |
| 更大Chunk | 计算效率和上下文可能更好 | 首结果与增量延迟上升 |
| 更多look-back | 上下文更完整 | 会话状态和计算量增加 |

参数必须与模型支持的流式配置匹配，不能把另一模型的经验值直接照搬。

## 5. 两遍识别为什么既“在线”又“离线”

两遍识别把低延迟与最终质量分开：

```text
第1遍：online模型
音频Chunk → 快速临时文本 → 用户实时看到

第2遍：offline模型
VAD检测句尾 → 收集完整语音段 → 离线重识别
→ 用更稳定的最终文本替换或修正临时文本
```

因此客户端必须理解“结果版本”：

- 在线结果可能变化，不能立即当成不可修改的业务事实；
- 最终结果应带会话、句段和状态标识；
- 客户端需要按句段更新，而不是把第二遍文本简单追加一次；
- 句尾未到达时，第二遍结果不会产生。

若用户反馈“同一句话出现两遍”，常见根因不是模型重复识别，而是客户端没有用最终结果替换临时结果。

## 6. 热词怎样进入链路

热词用于提高人名、产品名、地点和专业词汇等特定词的识别倾向。需要同时考虑：

1. 模型与当前服务路径是否支持热词；
2. 热词格式、权重和字符编码是否正确；
3. 权重过大是否把相似发音错误吸引到热词；
4. 每请求动态热词是否影响缓存和性能；
5. 升级后热词召回与误识别是否回归。

测试不能只准备包含热词的正样本，还需要准备发音相近但不应该识别为热词的负样本。

## 7. 模型加载和单次请求的执行层

在Python层，FunASR负责模型选择、输入处理、组件编排与结果组织；实际张量计算仍由PyTorch及其设备后端执行：

```text
FunASR服务/API
  → 模型与音频预处理
  → PyTorch Module/算子
  → CPU Kernel 或 CUDA Kernel
  → CPU内存或GPU显存
```

启动时通常经历：

```text
解析参数
→ 查找或下载模型
→ 读取配置与权重
→ 构建VAD/ASR/PUNC等组件
→ 权重装入CPU内存或GPU显存
→ 可选预热
→ 服务真正Ready
```

所以端口监听不应作为唯一readiness条件。模型还在下载或加载时就接收流量，会造成第一个请求超时甚至OOM。

## 8. 常见错误推断

### 8.1 “小音频能识别，所以音频格式一定正确”

不成立。某些解码器会自动转换文件格式，而流式裸PCM路径不会；文件API成功不能证明WebSocket参数正确。

### 8.2 “GPU利用率低，所以应继续增加连接数”

不一定。服务可能卡在音频解码、VAD、CPU后处理、排队、Python调度或小批次，GPU低利用率只是结果。

### 8.3 “连接没断，所以会话状态正常”

不成立。音频Chunk可能没有按实时节奏发送、结束标志缺失、服务端状态已异常或临时结果被客户端丢弃。

### 8.4 “两遍识别结果不同就是错误”

第二遍本来就用于利用完整句段修正第一遍。要判断的是最终结果质量、修正延迟和客户端替换逻辑，而不是要求两遍文本始终相同。

## 9. 课后练习

### 9.1 练习1：为什么VAD阈值不合理会同时影响延迟和准确率？ {/* #练习1为什么vad阈值不合理会同时影响延迟和准确率 */}

**答案：**过于保守会等待更长静音才判定句尾，增加最终结果延迟，并把无效静音交给ASR；过于激进会截断短停顿或句尾，导致语音段不完整、识别错误。

### 9.2 练习2：为什么两遍识别需要句段ID？ {/* #练习2为什么两遍识别需要句段id */}

**答案：**在线临时结果与离线最终结果属于同一语音段。句段ID让客户端知道应该更新哪一段，避免把修正结果追加成重复文本，也支持乱序和重连处理。

### 9.3 练习3：16 kHz、16-bit单声道PCM每100 ms应发送多少字节？ {/* #练习316-khz16-bit单声道pcm每100-ms应发送多少字节 */}

**答案：**`16000 × 2 × 1 × 0.1 = 3200`字节。不符合该数量应检查采样率、位深、声道和客户端切块逻辑。

### 9.4 练习4：标点模型异常时，ASR可能仍然返回200吗？ {/* #练习4标点模型异常时asr可能仍然返回200吗 */}

**答案：**可能。主识别已经生成文字，服务可能降级为无标点输出或后处理失败但请求仍返回。因此监控需要区分ASR、PUNC、ITN各阶段状态，并用功能样本验证结果结构。
