# BF16、FP16、INT8 与量化制品

精度选择同时影响：

```text
模型权重大小
HBM带宽
矩阵计算Kernel
通信量
激活与KV Cache
输出精度
硬件和框架支持
```

“8位模型一定比16位快一倍”通常不成立。真实收益取决于Kernel、Shape、量化/反量化开销、通信和瓶颈位置。

## 1. BF16与FP16

二者都使用16位，但指数和尾数分配不同：

| 格式 | 特征 | 常见取舍 |
| --- | --- | --- |
| FP16 | 尾数精度相对高、指数范围较小 | 更容易溢出/下溢 |
| BF16 | 指数范围接近FP32、尾数较短 | 范围更稳，细粒度精度较低 |

模型训练和目标硬件支持通常决定推荐格式。推理不能仅凭名称切换dtype后假设输出等价。

## 2. 量化命名

常见写法：

```text
W8A8：权重8位、激活8位
W8A16：权重8位、激活16位
W4A16：权重4位、激活16位
KV8：KV Cache使用8位表示
```

但名称没有表达：

- 对称/非对称；
- Per-Tensor/Per-Channel/Per-Group；
- 静态/动态激活Scale；
- Group Size；
- Scale dtype；
- 权重Packing布局；
- 哪些层保持高精度；
- 目标Backend与Kernel。

所以“都是W8A8”的两个制品不一定兼容。

## 3. PTQ与QAT

| 方法 | 原理 | 代价 |
| --- | --- | --- |
| PTQ | 训练后用校准数据估计Scale并转换 | 快，但对校准和异常值敏感 |
| QAT | 训练中模拟量化误差 | 成本高，通常精度更稳 |
| Weight Only | 只压缩权重 | 激活仍高精度，兼容性通常较好 |
| Dynamic | 运行时估计部分Scale | 灵活但增加运行开销 |

大模型部署最常见的是PTQ或Weight Only，但应按模型、任务和硬件支持选择。

## 4. 内存节省怎么算

权重理论大小：

```text
M_weights ≈ parameter_count × bits_per_weight / 8
```

实际还要加：

- Scale和Zero Point；
- Padding和Packing；
- 未量化层；
- 权重索引/Runtime元数据；
- 反量化或融合Workspace；
- TP分片对齐。

量化权重不会自动压缩BF16 KV Cache，除非另外启用受支持的KV量化。

## 5. 为什么性能可能不升

- 模型不是权重带宽瓶颈；
- 目标Batch/Shape没有高效量化Kernel；
- 频繁Quant/Dequant；
- 小Batch被Host Launch限制；
- TP通信或网络才是瓶颈；
- 某些层回退高精度实现；
- Graph不支持目标量化路径；
- 量化后能容纳更大Batch，测试却仍用原小Batch。

需要用端到端TTFT、TPOT和tok/s验证，而不是只比较权重文件大小。

## 6. NVIDIA与Ascend制品边界

同一逻辑算法在CUDA和Ascend上可能要求不同：

- 权重布局与Packing；
- Scale组织；
- 转换工具；
- 自定义Kernel；
- 模型适配代码；
- Graph和Attention Backend。

不要把面向AWQ/GPTQ/FP8 CUDA Kernel的制品直接假设为vLLM-Ascend或MindIE可用。使用各框架模型教程明确支持的格式和转换链。

## 7. 校准数据

校准集应覆盖真实任务：

- 中文/英文和代码比例；
- 长短Prompt；
- 数学、工具调用与结构化输出；
- 多轮对话；
- 领域术语；
- 多模态输入（适用时）。

只用几十条通用短句可能无法暴露长上下文和异常激活问题。校准集需要版本和摘要，避免无法复现。

## 8. 精度评测

至少三层：

```text
数值层：Logits/隐藏状态差异（开发阶段）
任务层：准确率、Pass@k、ROUGE、人工/模型评审
协议层：工具调用、JSON、停止和流式行为
```

候选与BF16基线使用相同Prompt、模板、Tokenizer、Sampling Seed和最大输出。随机生成任务要运行多样本并给出统计区间。
