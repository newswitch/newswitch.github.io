# 模型服务线上故障应急 Runbook

模型服务发生故障时，最危险的做法不是“排查得慢”，而是在没有保存证据、没有控制变量的情况下连续重启、改参数和切流量。这样可能暂时恢复服务，却会同时扩大影响并破坏根因现场。

一份合格的 Runbook 要解决三个问题：现在怎样降低业务影响、怎样用最少证据判断故障层次、怎样证明服务已经真正恢复。

## 1. Runbook 的适用范围

本文适用于运行中的训练或推理服务，重点覆盖在线推理场景：

- 请求大量失败、超时或连接中断；
- TTFT、ITL、端到端时延突然恶化；
- 队列持续增长，但 GPU/NPU 利用率异常偏低；
- KV Cache 抢占、重计算或 OOM；
- Worker、EngineCore、Rank 或设备进程退出；
- Pod 仍为 Running，但健康检查或真实请求已经失败；
- 单节点、单副本、单可用区或全局容量下降。

如果故障发生在容器启动之前，应先阅读[模型服务启动与故障排查学习路线](../startup-troubleshooting/00-模型服务启动与故障排查学习路线.md)。运行期故障的共同基础是[一个在线请求的完整证据链](01-一个在线请求的完整证据链.md)。

## 2. 先定义故障，而不是先登录机器

接到“模型变慢了”的告警后，先把模糊描述转换成可验证的故障声明：

| 维度 | 必须回答的问题 |
| --- | --- |
| 开始时间 | 第一个异常点是什么时间，时区是什么 |
| 影响范围 | 全部模型、单模型、单租户、单机型还是单副本 |
| 失败类型 | 连接失败、HTTP 5xx、超时、空结果还是流式中断 |
| 性能影响 | TTFT、ITL、TPS、并发和排队时间分别怎样变化 |
| 变更关联 | 故障前是否发布镜像、模型、参数、路由或节点变更 |
| 容量状态 | 请求量是否增长，健康副本数是否下降 |
| 用户影响 | 多少请求失败，是否存在可用的降级路径 |

一个可操作的故障声明示例是：

> 14:20 起，Qwen 服务约 30% 的请求在 60 秒后超时；入口请求量没有增长，异常集中在一个副本，该副本队列上升、设备利用率低于其他副本。

这比“GPU 有问题”更接近排障起点。

## 3. 应急处理的固定顺序

线上处置按以下顺序执行：

1. **确认影响**：通过真实请求、网关指标和客户端现象证明故障存在。
2. **限制扩散**：抑制重试风暴、限制新流量，保护仍健康的副本。
3. **保存证据**：采集时间线、日志、指标、事件、配置和设备状态。
4. **定位故障层**：入口、排队、推理引擎、通信、设备或依赖服务。
5. **实施单一止损动作**：切流、降载、回滚、隔离或重启。
6. **验证恢复**：同时检查成功率、延迟、队列、吞吐和副本健康。
7. **持续观察**：至少覆盖一个业务高峰或预先约定的观察窗口。
8. **复盘改进**：把临时操作转化为监控、容量和自动化措施。

“重启后正常”只能证明进程重新进入了工作状态，不能单独证明根因已经消失。

## 4. 前 5 分钟：确认影响并防止扩大

### 4.1 从用户入口验证

至少使用一次真实协议请求，不要只看 Pod Ready：

```bash
curl -sS -N \
  -H 'Content-Type: application/json' \
  -d '{"model":"MODEL_NAME","messages":[{"role":"user","content":"返回 ok"}],"max_tokens":8}' \
  --connect-timeout 3 \
  --max-time 30 \
  http://SERVICE_ENDPOINT/v1/chat/completions
```

记录请求开始时间、HTTP 状态码、首字节时间、总耗时和请求 ID。不要在公开工单中保留令牌、完整业务提示词或用户数据。

### 4.2 检查影响是否集中

```bash
kubectl -n NAMESPACE get pod -l app=MODEL_APP -o wide
kubectl -n NAMESPACE get endpoints SERVICE_NAME -o wide
kubectl -n NAMESPACE get events --sort-by=.lastTimestamp
kubectl -n NAMESPACE top pod -l app=MODEL_APP --containers
```

关注以下差异：

- 是否只有一个 Pod 错误率或延迟升高；
- 是否只有某个节点、机型或可用区异常；
- Service Endpoints 中是否仍包含已经失去服务能力的副本；
- 健康副本减少后，剩余副本是否因流量集中进入过载。

### 4.3 立即处理重试风暴

客户端、网关和服务端同时重试时，原始故障会被放大。优先确认：

- 重试是否有最大次数和指数退避；
- 超时请求是否仍在服务端继续生成；
- 断开的流式请求是否及时取消；
- 网关是否把失败流量持续压向同一异常副本。

必要时先降低入口并发、限制超长请求或暂停非关键租户。止损的目标是让系统重新进入可测量状态，而不是追求满负荷运行。

## 5. 前 15 分钟：保存最小证据集

所有证据使用同一时区，并记录命令执行时间。

```bash
date -Ins
kubectl -n NAMESPACE get pod POD_NAME -o yaml
kubectl -n NAMESPACE describe pod POD_NAME
kubectl -n NAMESPACE logs POD_NAME -c CONTAINER --since=30m --timestamps
kubectl -n NAMESPACE logs POD_NAME -c CONTAINER --previous --timestamps
kubectl get node NODE_NAME -o yaml
```

同时保存以下指标的故障前、故障中和处置后曲线：

- 请求速率、成功率、HTTP 状态码和取消数；
- TTFT、ITL、端到端时延的 P50/P95/P99；
- 等待请求数、运行请求数、批大小和 token 吞吐；
- KV Cache 使用率、抢占、换出或重计算次数；
- CPU、内存、文件描述符和网络收发；
- GPU/NPU 利用率、显存/HBM、温度、功耗和设备错误；
- 多卡通信错误、Rank 状态和集合通信超时。

日志不能只采集最后几十行。故障原因通常出现在退出堆栈之前，进程重启后还应读取 `--previous` 日志。

## 6. 用症状选择排障分支

### 6.1 所有请求立即失败

检查顺序：

1. DNS、负载均衡和 Ingress/Gateway 是否可达；
2. Service 是否存在健康 Endpoint；
3. 端口、监听地址和 NetworkPolicy 是否变化；
4. API Server 是否仍能接收请求；
5. 后端 EngineCore/Worker 是否已经死亡。

如果健康检查只验证 TCP 端口，API 进程可能仍在监听，但推理后端已经不可用。应增加一个轻量、限频的端到端就绪探测。

### 6.2 只有部分请求失败

优先按副本、节点、输入长度、租户和路由标签聚合错误。常见原因包括：

- 单副本 Worker 退出，但仍未从 Endpoint 摘除；
- 单节点设备或网络异常；
- 长上下文请求触发 KV Cache 压力；
- 特定请求模板、工具调用或多模态输入触发异常分支；
- 滚动发布期间新旧版本行为不一致。

不要用所有实例的平均值掩盖单实例故障。

### 6.3 TTFT 上升，ITL 基本正常

这通常指向请求进入生成前的路径：

- 入口排队或调度等待；
- Tokenizer/Processor 变慢；
- Prefill 计算或长上下文增加；
- Prefix Cache 命中率下降；
- 模型权重或多模态资源临时读取；
- 健康副本减少导致单副本排队。

结合[排队、Prefill、Decode 与性能指标联合分析](03-排队-Prefill-Decode与性能指标联合分析.md)判断 TTFT 是“等得久”还是“算得久”。

### 6.4 TTFT 正常，ITL 或生成时延恶化

优先检查 Decode 阶段：

- 活跃序列数和批大小是否过大；
- 长短请求是否相互干扰；
- KV Cache 是否频繁抢占或重计算；
- Tensor Parallel Rank 是否存在慢卡；
- 温度、功耗限制或频率下降；
- 采样、输出处理或流式发送是否阻塞。

### 6.5 队列增长，但设备利用率偏低

这不等于“模型计算量不足”。请求可能没有到达设备执行层：

- Tokenizer、模板渲染或输入校验阻塞；
- Scheduler 无法形成可运行批次；
- KV Cache 无可分配块；
- Worker/RPC/多进程队列阻塞；
- 某个 Rank 异常，其他 Rank 在集合通信处等待；
- 输出反压导致执行链无法继续推进。

沿[一个在线请求的完整证据链](01-一个在线请求的完整证据链.md)逐层确认“最后一个仍在前进的组件”。

### 6.6 HBM 很高、KV 抢占增加或 OOM

先区分权重、KV Cache、激活值和非框架分配：

- OOM 发生在偶发超长请求，还是普通请求也会触发；
- KV Cache 使用率升高是否伴随抢占和 TTFT 恶化；
- `max_model_len`、并发和批 token 上限是否同时放大；
- 进程重启后显存是否释放；
- 是否存在额外模型、图缓存或通信缓冲区。

参见[KV Cache 抢占、重计算与运行中 OOM](05-KV-Cache抢占-重计算与运行中OOM.md)。

### 6.7 Worker、EngineCore 或 Rank 退出

先保存首个异常进程的日志和设备状态，再判断：

- Python 异常、操作系统 OOMKill 还是设备错误；
- 单 Rank 先退出，其他 Rank 随后被通信错误拖垮；
- API 进程是否仍存活并继续接收请求；
- 自动重启是否形成 CrashLoop；
- 同一节点是否反复出现同类故障。

参见[Worker 退出、EngineCore 死亡与服务假活](06-Worker退出-EngineCore死亡与服务假活.md)。

## 7. 止损动作的优先级

从影响小、可回滚的动作开始：

| 优先级 | 动作 | 适用场景 | 主要风险 |
| --- | --- | --- | --- |
| 1 | 限流、减少重试、拒绝超长请求 | 过载和排队扩散 | 部分请求被主动拒绝 |
| 2 | 将异常副本摘流 | 单副本异常 | 剩余容量不足 |
| 3 | 切换备用模型或降级参数 | 主模型不可用 | 输出能力或质量下降 |
| 4 | 回滚最近变更 | 故障与发布高度相关 | 回滚也需要冷启动 |
| 5 | 扩容健康副本 | 请求量增长、容量不足 | 冷启动慢、资源不足 |
| 6 | 重启异常进程或 Pod | 状态损坏、进程失活 | 证据丢失、再次冷启动 |
| 7 | 隔离节点或设备 | 故障绑定物理节点 | 集群容量下降 |

每次只执行一个主要动作，记录开始时间、操作者、预期结果和回滚条件。多个动作同时发生后，即使恢复也难以判断哪一个真正有效。

## 8. 恢复验收不能只看“接口返回 200”

至少同时满足以下条件：

- 真实请求成功，流式输出能够完整结束；
- 错误率和超时率回到基线；
- TTFT、ITL 和端到端时延回到 SLO 范围；
- 等待队列没有持续增长；
- token 吞吐与当前流量匹配；
- KV Cache 抢占、OOM 和设备错误不再增长；
- 所有预期副本都能完成端到端请求；
- 日志中没有持续重复的后台异常；
- 降级、切流和临时限流均有明确的恢复计划。

恢复后需要继续观察。如果问题只在高并发或长请求下出现，低流量下的短请求验证并不充分。

## 9. 升级时必须提供的故障包

向框架、设备、网络或平台团队升级时，至少提供：

1. 精确时间线和时区；
2. 影响模型、镜像、框架和驱动/CANN/CUDA 版本；
3. 启动命令及非敏感环境变量；
4. 可脱敏的最小复现请求；
5. 首个异常日志，而不只是最终退出日志；
6. 故障时间窗内的核心指标；
7. Pod、节点、设备和通信状态；
8. 已执行的动作及每次动作后的结果；
9. 是否绑定特定节点、设备、请求类型或版本；
10. 诊断包校验值和采集时间。

下一篇[运行期证据自动采集与诊断包](11-运行期证据自动采集与诊断包.md)会把这些材料固化成可重复的采集流程。

## 10. 复盘要输出系统改进

复盘不以“某人执行了错误操作”结束，而要回答：

- 为什么用户先于监控发现问题；
- 为什么异常副本没有及时摘流；
- 为什么重试、超时或队列会放大故障；
- 为什么容量没有覆盖单副本或单节点故障；
- 为什么恢复动作没有自动化或缺少验收条件；
- 哪个指标、日志字段或请求 ID 能缩短下次定位时间；
- 哪项改进有负责人、截止时间和验证方式。

最终应形成监控规则、容量冗余、发布保护、自动采集、故障演练和操作权限六类改进，而不是只增加一篇故障记录。

## 11. 一页式检查清单

```text
[ ] 记录开始时间、影响范围、失败类型和最近变更
[ ] 使用真实请求确认故障，不只看进程和 Ready 状态
[ ] 检查是否存在重试风暴，并先保护健康容量
[ ] 保存当前与 previous 日志、事件、指标和设备状态
[ ] 按入口、排队、Prefill、Decode、KV、通信、设备分层定位
[ ] 每次只执行一个主要止损动作，并记录预期和结果
[ ] 用成功率、TTFT、ITL、队列、吞吐和资源共同验收
[ ] 持续观察一个足够覆盖故障触发条件的窗口
[ ] 形成根因、促成因素和可验证的长期改进项
```

Runbook 的价值不是让所有故障都按同一个答案处理，而是让团队在压力下仍能保持同一个证据标准和决策顺序。
