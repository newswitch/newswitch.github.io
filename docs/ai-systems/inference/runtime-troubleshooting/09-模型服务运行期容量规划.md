# 模型服务运行期容量规划

容量规划不是“单卡能跑多少并发”，而是回答：在真实流量和故障条件下，有多少请求能够同时满足正确性、
TTFT、ITL、错误率和成本目标。

```text
业务流量模型
→ 单副本安全容量
→ 多副本与 N-1
→ 冷启动和突发
→ 发布与故障余量
→ 成本和扩缩容
```

## 1. 先定义容量单位

LLM 服务至少有四种容量单位：

| 单位 | 适用 | 局限 |
|---|---|---|
| Request/s | 接口吞吐 | 不反映长短请求成本 |
| Input Token/s | Prefill 负载 | 不包含 Decode |
| Output Token/s | Decode 负载 | 不包含 Prefill |
| Goodput req/s | 满足 SLO 的请求 | 必须定义 SLO 和分布 |

因此容量结论应包含 Token 分布，而不是只写 QPS。

## 2. 定义 SLO

示例：

```text
成功率 ≥ 99.9%
TTFT P95 ≤ 1.5 s
ITL P95 ≤ 60 ms
E2E P95 按输出长度分桶
取消传播 P99 ≤ 2 s
```

阈值必须由业务确定。容量测试的任务是找出满足阈值的最大稳定负载，而不是把设备压到 100%。

## 3. 建立真实工作负载画像

至少统计：

- Input Token P50/P90/P95/P99。
- Output Token P50/P90/P95/P99。
- 输入与输出的联合分布。
- 流式比例。
- 多模态比例、图片数量和分辨率。
- Prefix Cache 可复用前缀。
- 模型、LoRA、租户和优先级。
- 请求率、并发和突发持续时间。
- 超时、取消和重试行为。

输入长和输出长可能相关，分别抽样后随机组合会构造出不存在或遗漏真实的极端请求。最好使用脱敏 Trace Replay。

## 4. 单副本资源边界

一个副本首先受：

```text
权重固定内存
KV Cache Token 容量
Prefill 激活峰值
Graph/Workspace
通信 Buffer
CPU/Tokenizer
网络与输出
```

单副本定义必须固定：模型 revision、dtype/量化、设备型号和数量、TP/PP/EP、上下文、Batch、框架和参数。

## 5. KV 驻留而不是并发请求数

某时刻请求的 KV 驻留近似：

```text
resident_tokens
≈ input_tokens + generated_tokens_so_far
```

总驻留：

```text
total_resident_tokens
≈ Σ active_request_resident_tokens
```

100 个 512 Token 请求与 10 个 32k 请求的并发数差十倍，但后者 KV 压力可能更大。

## 6. Prefill 与 Decode 分开建模

### 6.1 Prefill

需求近似与 Input Token 到达率相关：

```text
prefill_token_rate
= Σ input_tokens / observation_window
```

还要考虑 Prefix Cache 命中和重计算。

### 6.2 Decode

需求与活跃 Sequence、输出 Token 和 ITL 相关：

```text
decode_token_rate
= Σ output_tokens / observation_window
```

Prefill 和 Decode 在同一设备混合时互相干扰，不能把两个独立峰值简单相加或分别测试后直接采用较大值。

## 7. Little 定律用于一致性检查

在稳定系统中：

```text
平均并发 L ≈ 到达率 λ × 平均停留时间 W
```

例如 5 req/s、平均端到端 4s，平均在途请求约 20。它可以校验监控和压测是否自洽，但不能使用平均值覆盖 P99、突发和长尾 KV。

## 8. 单副本容量曲线

使用固定工作负载，逐级增加请求率或并发：

| 负载 | TTFT P95/P99 | ITL P95/P99 | Queue P99 | Goodput | KV/抢占 | 错误率 |
|---:|---:|---:|---:|---:|---:|---:|
| | | | | | | |

识别三个点：

1. **舒适点**：SLO 余量充足。
2. **可售容量点**：满足全部 SLO 的最大稳定负载。
3. **饱和点**：Queue 持续增长或错误/抢占显著增加。

生产目标应低于饱和点，并为流量波动和设备差异保留余量。

## 9. Goodput 的计算

```text
Goodput
= 单位时间内满足全部约束的成功请求数
```

约束可包括：

- TTFT。
- ITL/TPOT。
- E2E。
- 正确响应。
- 未发生重试或降级。

增加并发后总 Token Throughput 上升，但超出 TTFT 的请求更多，Goodput 可能下降。容量点应按 Goodput 和 SLO 选取。

## 10. 长短请求分池

如果交互短请求和离线长请求 SLO 差异很大，可分别建立资源池：

| 池 | 流量 | 优化目标 |
|---|---|---|
| Interactive | 短 Prompt、流式 | TTFT/ITL |
| Long Context | 长 Prompt | Prefill、KV、稳定性 |
| Batch | 离线生成 | 吞吐和成本 |

分池减少队头阻塞，但降低全局 Batch 复用并增加容量碎片，需要用总 Goodput 和成本验证。

## 11. 多副本基础数量

若单副本可售容量为 `C`，峰值目标负载为 `L`：

```text
基础副本数 = ceil(L / C)
```

这只覆盖正常状态。还需要增加：

- N-1/N-k 故障。
- 节点故障域。
- 发布替换。
- 冷启动等待。
- 缓存未热。
- 突发和预测误差。

## 12. N-1 不只是多一个 Pod

如果同一节点上有多个模型副本，节点故障可能同时丢失多个副本。应按故障域计算：

```text
单 Pod 故障
单 GPU/NPU 故障
单节点故障
单机架/网络域故障
单存储或控制面故障
```

N-1 后剩余副本还必须在真实流量下满足 SLO，而不是只保证请求最终完成。

## 13. 冷启动进入容量模型

被动扩容只有在下面条件成立时有效：

```text
流量增长可提前预测
或
现有热余量能覆盖冷启动窗口
```

记录：

- Pod Pending。
- 镜像拉取。
- 模型分发。
- 权重加载。
- 编译和 Graph。
- 预热与 Readiness。

如果完全冷启动 10 分钟，而流量 1 分钟内翻倍，单靠 HPA 无法避免过载。

## 14. 扩容信号

推荐组合：

```text
Token arrival rate
Queue Age / Waiting
TTFT/Goodput
KV 余量与抢占
健康副本数
冷启动预测
```

GPU/NPU 利用率只是辅助信号。利用率低但 Queue 高可能来自 CPU、KV、路由或慢 Rank。

## 15. 缩容边界

缩容前验证：

- 摘流后能排空运行请求。
- 剩余容量满足当前流量和 N-1。
- 不会丢失热 Prefix/编译缓存造成性能骤降。
- 长请求有最大排空时间和明确取消语义。
- 缩容滞后足够避免频繁抖动。

## 16. 发布容量

滚动发布同时存在：

```text
旧副本排空
新副本冷启动
新副本缓存未热
流量逐步迁移
```

发布前应计算最小可用副本、最大不可用、最大额外副本和模型存储启动风暴。不能让所有副本同时编译或读取共享存储。

## 17. 成本模型

```text
单位有效请求成本
≈ GPU/NPU 小时成本 / Goodput
```

还要包括：

- 节点 CPU/内存和高速网络。
- 模型存储和分发。
- 热备用。
- 冷启动空转。
- 过载重计算和无效重试。
- 运维与故障成本。

更高设备利用率不一定降低单位 Goodput 成本，如果尾延迟导致大量请求不满足 SLO。

## 18. 容量报告模板

```markdown
## 固定环境
模型、镜像、设备、并行、参数

## 工作负载
输入/输出 Token 联合分布、请求率、突发、Cache

## SLO
TTFT、ITL、E2E、错误、取消

## 单副本曲线
舒适点、可售点、饱和点、KV 与 Goodput

## 集群容量
基础副本、N-1/故障域、冷启动、发布余量

## 扩缩容
信号、阈值、滞后、排空

## 成本与风险
单位 Goodput 成本、已知边界、回滚条件
```
