# 过载保护、背压、限流与熔断

模型服务的请求成本差异很大：一个 100 Token 的短请求和一个 100k Token 的长请求不能都按“1 个请求”计费和准入。
如果系统只依赖无限排队，最终会出现 TTFT 超标、客户端超时、重试放大和 KV 抢占。

过载保护的目标不是让所有请求都进入，而是：

> 在有限资源下保护已经接纳的请求和整体 SLO，并对无法及时处理的请求快速、明确地反馈。

## 1. 为什么普通 QPS 限流不够

LLM 请求成本受：

- Input Token。
- 最大 Output Token。
- 多模态图片/视频规模。
- 模型、dtype 和量化。
- Prefix Cache 命中。
- TP/EP 通信。
- 优先级和 SLO。

两个相同 QPS 的流量，Token 速率和显存压力可能相差几十倍。

## 2. 四层保护

```text
边缘/Gateway：身份、配额、QPS、请求体、重试
→ API：模型参数、Token 上限、并发、租户
→ Engine：Running、Waiting、Batch Token、KV
→ Cluster：副本、节点、N-1、扩缩容
```

单层无法解决全部问题。网关不知道实时 KV，Engine 也不应该承担所有租户配额和攻击流量。

## 3. 准入控制

请求进入系统前先估算成本：

```text
estimated_tokens
= input_tokens
+ requested_max_output_tokens
+ multimodal_token_budget
```

准入可以同时检查：

- 单请求最大输入和输出。
- 租户并发和 Token 预算。
- 实例 Running/Waiting。
- 当前 KV Cache 余量。
- 当前 Queue Age 和 SLO 预测。
- 模型副本健康数。

估算不必完全准确，但必须保守、可解释并用实际数据校准。

## 4. 有限排队

Queue 可以吸收短时突发，但不能创造算力。

至少设置：

- 最大等待请求数。
- 最大等待 Token 预算。
- 最大 Queue Age。
- 每租户 Queue 配额。
- 长短请求或优先级队列。
- Queue 满后的明确拒绝。

只限制请求数可能让少量超长请求耗尽 Token 和 KV 预算。

## 5. 背压

背压是下游把容量状态向上游传递，让上游降低发送速度，而不是继续堆积。

常见信号：

- HTTP 429：超过配额或限流。
- HTTP 503：当前无健康容量或临时过载。
- `Retry-After` 或平台定义的重试时间。
- SDK 并发窗口收缩。
- 消息队列消费者降低拉取速度。

具体状态码和重试语义应形成协议，不能让客户端对所有 5xx 立即重试。

## 6. 限流维度

| 维度 | 保护对象 | 局限 |
|---|---|---|
| QPS | API 与连接 | 不反映 Token 成本 |
| 并发 | 运行槽位 | 长短成本不同 |
| Input Token/s | Prefill 算力 | 不含输出 |
| Output Token/s | Decode 算力 | 请求时只能估算 |
| Token Budget | 综合成本 | 需要预测和归还 |
| 租户配额 | 公平性 | 需要身份准确 |
| 模型配额 | 多模型隔离 | 需考虑不同硬件成本 |

生产中通常组合使用，而不是选择唯一一种。

## 7. 长短请求隔离

长 Prompt 可能占用大量 Prefill Token 和 KV，造成短请求队头阻塞。可采用：

- 按输入 Token 分队列。
- 为长请求设置独立副本池。
- 使用 Chunked Prefill，验证公平性。
- 限制长请求并发。
- 为交互请求和离线批处理设置不同 SLO。

隔离策略会牺牲部分全局 Batch 效率，需要以 Goodput 和尾延迟验证。

## 8. 优先级和公平性

优先级不是“高优请求永远插队”。需要防止低优任务永久饥饿：

- 加权公平队列。
- 每租户并发/Token 上限。
- Aging：等待越久优先级逐步提高。
- 高优流量总量保护。
- 离线任务可暂停或迁移。

还要明确已经运行的低优请求是否允许被抢占，以及抢占的重计算成本。

## 9. 熔断

熔断器在下游出现连续失败或不可用时，暂时阻止新调用，避免每个请求都等待到超时。

适合触发的信号：

- 健康副本为零。
- Engine 永久失败。
- 5xx/超时超过阈值。
- Queue Age 已无法满足 SLO。
- 设备或模型存储发生区域性故障。

不适合只凭瞬时 GPU 利用率或一次慢请求打开全局熔断。

熔断状态：

```text
Closed：正常放行
Open：快速拒绝
Half-Open：少量探测恢复
```

## 10. 降级

无法满足原服务时，可选择：

- 更短最大输出。
- 更小模型或量化模型。
- 关闭非必要多模态/工具功能。
- 将离线任务延后。
- 返回缓存结果。
- 只接受高优租户。

降级必须由业务接受，并在响应中明确标识，不能悄悄切换到质量不同的模型。

## 11. 重试预算

重试应满足：

```text
重试总量 ≤ 请求总量的一小部分预算
```

并包含：

- 最大次数。
- 指数退避和随机抖动。
- 仅重试明确的临时错误。
- 尊重 Deadline，剩余时间不足时不重试。
- 部分流式输出后谨慎重试。
- 端到端幂等或去重标识。

网关、SDK 和业务服务如果各自重试 2 次，最坏可能产生乘法放大，需要统一治理。

## 12. 过载指标

流量：

```text
arrival request/token rate
accepted/rejected rate
retry rate
per-tenant usage
```

队列与 SLO：

```text
waiting/running
queue age
TTFT/ITL/E2E
goodput
```

引擎与资源：

```text
scheduled tokens
KV usage
preemption/recompute
GPU/NPU utilization and memory
healthy replicas
```

扩缩容信号应组合 Token 到达率、Queue、Goodput 和副本状态，而不是只看 GPU 利用率。

## 13. 过载状态机

可以定义：

| 状态 | 条件 | 动作 |
|---|---|---|
| Normal | Queue 与 SLO 正常 | 正常准入 |
| Busy | Queue/利用率接近阈值 | 收紧低优并发，触发扩容 |
| Overloaded | Queue Age/SLO 失守 | 快速拒绝、限流、降级 |
| Failed | 无健康 Engine | 熔断、切流、恢复 |
| Recovering | 新副本预热中 | 小流量探测，逐步放量 |

阈值需要基于容量实验，不使用拍脑袋百分比。

## 14. 一个故障放大案例

```text
流量增加 30%
→ Queue 增长
→ TTFT 超过客户端 30s Deadline
→ 客户端立即重试
→ 原请求未取消，仍在 Engine 中
→ 实际计算量翻倍
→ KV 抢占和重计算
→ Goodput 降低
→ 更多超时
```

止损顺序：

1. 限制重试和新增长请求。
2. 快速拒绝已经无法满足 SLO 的低优请求。
3. 确认超时请求向 Engine 传播取消。
4. 保护健康副本，避免同时重启。
5. 在有节点资源和冷启动时间可接受时扩容。

## 15. 容量实验

使用真实 Token 分布，逐级增加请求率而非只固定并发：

| 到达 Token/s | Accepted | Rejected | Queue P99 | TTFT P99 | Goodput | KV/抢占 |
|---:|---:|---:|---:|---:|---:|---:|
| | | | | | | |

找到：

- Queue 开始持续增长的点。
- Goodput 峰值。
- 抢占开始显著增加的点。
- 拒绝策略能否保护已接纳请求。
- 扩容完成前需要多少热余量。

## 16. 发布验收

- 超长和超大请求在边缘明确拒绝。
- Queue 有请求数、Token 和年龄上限。
- 429/503 与重试语义明确。
- 客户端取消能释放 Engine 资源。
- 高低优流量不会互相完全拖垮。
- 所有层重试总预算受控。
- 熔断 Half-Open 能安全恢复。
- 降级模型和响应标识经过业务验收。
- 扩容信号与冷启动时间匹配。
