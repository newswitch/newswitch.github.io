# 一个在线请求的完整证据链

用户说“模型很慢”，只能确认端到端体验有问题。要定位根因，必须知道请求在哪一层进入、等待、计算、返回，
并且能把各层日志和指标关联到同一次调用。

```text
客户端
→ DNS / LB / Ingress / Gateway
→ API Server
→ Chat Template / Tokenizer
→ 准入与等待队列
→ Scheduler
→ Prefill
→ KV Cache
→ Decode
→ Detokenizer / Output Processor
→ SSE / HTTP 返回
```

## 1. 请求生命周期和启动生命周期不同

启动生命周期以进程和模型 Ready 为终点；请求生命周期从客户端发出开始，以完整响应、错误或取消结束。

| 生命周期 | 主要对象 | 关键问题 |
|---|---|---|
| 启动 | Pod、进程、Worker、模型 | 为什么没有 Ready |
| 运行 | Request、Sequence、Batch、KV Block | 为什么慢、失败或卡住 |

运行期排障不能只看启动日志中的显存和版本，还需要请求级时间线、输入/输出 Token、队列状态和调度决策。

## 2. 先建立统一请求标识

理想链路包含：

```text
trace_id：跨服务调用链
request_id：一次推理请求
client_request_id：调用方幂等或业务标识
pod / process / worker / rank：执行位置
model / revision：实际模型身份
```

推荐由最外层网关生成或接收 `X-Request-ID`，向下游透传，并由模型 API 在响应头和日志中返回。
不要把用户 Prompt 当作关联标识：它可能重复，也可能包含敏感数据。

一个请求跨多个进程时，可以使用：

```text
request_id=req-123
api_pid=20
engine_pid=59
worker_rank=0,1
pod=model-a-7d9f
```

## 3. 第一层：客户端与网络入口

客户端应记录：

- DNS、TCP、TLS 和连接复用时间。
- 请求发送完成时间。
- 首个响应字节或首个 SSE 事件时间。
- 最后一个事件时间。
- HTTP 状态码和超时类型。
- 重试次数。

对于流式模型接口：

```text
客户端 TTFT = 发出请求 → 收到第一个有效 Token 事件
```

它包含网关、排队和模型 Prefill，不等于框架内部 TTFT。不同工具对 TTFT 起止点可能不同，报告中必须注明口径。

## 4. 第二层：网关、Ingress 与代理

网关可能完成：

- TLS 终止和认证。
- 请求体大小检查。
- 路由和模型选择。
- 限流、排队和重试。
- 连接池管理。
- 流式响应转发。

需要记录：

```text
gateway_receive_time
upstream_connect_time
upstream_first_byte_time
gateway_total_time
upstream_status
upstream_host
request_id
```

常见问题：

- 代理默认缓冲 SSE，模型已生成但客户端迟迟看不到。
- 网关超时短于模型最大执行时间。
- 自动重试非幂等生成请求，造成重复计算。
- 连接池耗尽，时间花在建立上游连接之前。
- 所有请求被哈希到同一副本，其他 GPU 空闲。

## 5. 第三层：API Server

API 层负责协议解析、参数校验、鉴权、模型别名、Chat Template、请求对象创建和流式输出。

日志至少包含：

- Request ID 和实际模型。
- 请求到达、提交引擎、首 Token、结束或取消时间。
- 输入、输出 Token 数，不记录敏感全文。
- HTTP 状态、错误类型和取消来源。
- 当前 Pod 和引擎实例 ID。

如果 API 收到请求很晚，问题在它之前；API 很早收到、很晚提交引擎，则要查 Tokenizer、准入或内部锁。

## 6. 第四层：Chat Template 与 Tokenizer

客户端字符数与模型 Token 数不同。API 可能执行：

```text
消息角色校验
→ Chat Template 渲染
→ Tokenization
→ 长度检查
→ 特殊 Token 和多模态占位符处理
```

这一层主要消耗 CPU。常见瓶颈：

- 超长 Prompt 的 Tokenization。
- Python GIL 或线程池饱和。
- Chat Template 逻辑复杂。
- 多模态图片下载、解码和预处理。
- Tokenizer 进程与 API 线程争抢 CPU。

GPU 利用率低、请求尚未进入 Scheduler 时，应先看 CPU 和前端队列，而不是增加 GPU Batch。

## 7. 第五层：准入与等待队列

请求进入引擎后可能先处于 Waiting：

- 运行请求已达到上限。
- 当前批次 Token 预算不足。
- KV Cache Block 不足。
- 长 Prefill 被分块调度。
- 优先级或配额策略暂缓请求。

需要观测：

```text
waiting_requests
running_requests
queue_time
queued_tokens
admission_rejects
```

排队时间高说明请求还没有真正执行。此时 GPU 利用率可能高，也可能因为调度、CPU 或慢 Rank 导致无法组成有效批次。

## 8. 第六层：Scheduler 与 Batch

Scheduler 在每个 Step 决定：

- 哪些请求进入运行。
- 本轮处理 Prefill 还是 Decode。
- 每个请求分配多少 Token。
- 是否分配、复用或回收 KV Block。
- 是否抢占或重计算请求。
- 是否采用 Chunked Prefill。

调度证据包括：

- 每轮 Scheduled Token 数。
- Batch 中 Prefill/Decode 请求数。
- 被抢占请求和原因。
- KV Cache 可用 Block。
- Scheduler Step 间隔。

框架实现不同，但这些通用问题相同。

## 9. 第七层：Prefill

Prefill 处理输入 Token，并建立对应 KV Cache。它通常具有较高并行度和计算密度。

影响 Prefill 的因素：

- 输入 Token 数和 Batch Token 数。
- Prefix Cache 命中率。
- Chunked Prefill。
- Attention Backend。
- TP 通信和慢 Rank。
- 多模态 Encoder。
- GPU/NPU 算力、频率和功耗限制。

一个长 Prompt 会延迟自己的首 Token，也可能阻塞同批短请求。分析 TTFT 时必须按输入 Token 长度分桶。

## 10. 第八层：KV Cache

Prefill 和后续 Decode 都依赖 KV Cache。需要关联：

- 已用/可用 KV Block。
- Prefix Cache 命中与复用。
- 抢占和重计算次数。
- 请求当前 Token 数。
- KV 数据类型。
- 每个 Rank 的缓存状态。

KV Cache 不足首先表现为排队、抢占和 TTFT 尾延迟，未必立即 OOM。

## 11. 第九层：Decode

Decode 每轮通常为每个活跃 Sequence 生成一个或少量 Token。它更容易受 Kernel Launch、调度间隙和通信影响。

观察：

```text
inter-token latency / TPOT
decode batch size
output token throughput
scheduler step time
collective communication time
slow rank
GPU clock / power / utilization
```

TTFT 正常而输出逐 Token 变慢，重点应转向 Decode、通信、Batch 和设备状态。

## 12. 第十层：输出处理与流式返回

模型产生 Token 后，还要经过：

```text
采样结果
→ Detokenization
→ Stop 条件
→ Reasoning/Tool Parser
→ SSE 编码
→ 代理转发
→ 客户端解析
```

框架已经生成首 Token，但客户端没有收到，问题可能在 Detokenizer、输出队列、事件循环或代理缓冲。

## 13. 端到端时间如何拆分

```text
E2E
= 客户端与网络
+ 网关等待/连接
+ API 与 Tokenization
+ Scheduler Queue
+ Prefill
+ Decode
+ 输出与代理转发
```

对于流式请求：

```text
TTFT_client
= T_network_in
+ T_gateway
+ T_frontend
+ T_queue
+ T_prefill
+ T_first_output

Generation_client
= T_decode
+ T_output_processing
+ T_network_out
```

公式用于建立阶段模型，实际阶段可能重叠，例如 Detokenization 与后续 Decode 可以流水并行。

## 14. 一张请求证据表

| 时间 | 层 | 事件 | Request ID | Pod/Rank | Token/资源 |
|---|---|---|---|---|---|
| T0 | Gateway | 收到请求 | req-123 | gateway-1 | body size |
| T1 | API | Tokenization 完成 | req-123 | model-pod-a | input tokens |
| T2 | Scheduler | 进入 Running | req-123 | engine-59 | queue time |
| T3 | Worker | Prefill 完成 | req-123 | rank 0..N | computed tokens |
| T4 | API | 首 Token | req-123 | model-pod-a | TTFT |
| T5 | Worker | Decode 完成 | req-123 | rank 0..N | output tokens |
| T6 | Gateway | 响应结束 | req-123 | gateway-1 | E2E |

缺少哪个阶段，就先补哪个阶段的日志或指标，不要凭感觉分配耗时。

## 15. 一次标准分析流程

1. 用 Request ID 找到网关、API 和引擎记录。
2. 核对模型、输入/输出 Token 和参数。
3. 计算客户端 TTFT 与端到端延迟。
4. 提取 Queue、Prefill、Decode 和输出阶段。
5. 对齐同一时刻的请求数、KV Cache、GPU/NPU 和通信指标。
6. 与相同 Token 桶的正常请求比较。
7. 提出一个可证伪假设并做单变量实验。

## 16. 推荐最小字段

为了控制日志量，优先保存结构化摘要：

```text
request_id, trace_id, model, pod, engine_id
arrival_time, scheduled_time, first_token_time, finish_time
input_tokens, output_tokens, finish_reason
queue_ms, prefill_ms, decode_ms, e2e_ms
cancelled, error_type, http_status
```

Prompt 正文、图片和敏感文档应默认脱敏或不记录。
