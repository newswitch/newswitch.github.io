# 模型服务运行日志的分层阅读方法

启动日志通常围绕一个进程生命周期，运行日志同时包含大量并发请求。相邻日志行可能来自不同 Request、
不同 Worker 和不同 Rank，不能只按文本顺序阅读。

运行日志需要五个索引：

```text
Request：哪一次请求
阶段：请求执行到了哪里
进程：哪个组件在处理
Rank/设备：哪张卡执行
时间：事件先后和持续多久
```

## 1. 先定义要回答的问题

常见现象对应不同分析目标：

| 现象 | 首要问题 |
|---|---|
| 单个请求慢 | 时间花在哪个阶段 |
| 所有请求慢 | 共享资源或过载在哪里 |
| 请求卡住 | 哪个阶段不再推进 |
| 流式中断 | 客户端、代理、API 还是引擎先结束 |
| 部分请求 5xx | 哪个 Pod/Rank/输入类型共同出现 |
| API 200 但无输出 | 引擎、输出处理或协议状态是否异常 |
| GPU 空闲但有排队 | 请求是否还在前端或调度受阻 |

没有问题定义，就容易在海量日志中搜索所有 Warning，而没有形成结论。

## 2. 六层日志来源

```text
L1 客户端 / SDK
L2 Gateway / Ingress / Service Mesh
L3 API Server / Tokenizer
L4 Scheduler / EngineCore
L5 Worker / Rank / Kernel Backend
L6 Kubernetes / Node / Device
```

每一层只对自己观察到的时间负责。例如网关 `upstream timeout` 不能证明模型计算死锁，只能证明在网关截止时间前没有收到所需响应。

## 3. 日志关联键

优先级从高到低：

1. Trace ID。
2. Request ID。
3. Engine Request ID 或 Sequence ID。
4. Pod、PID、Worker、Rank、设备 UUID。
5. 时间窗口、模型和请求特征。

如果 API 到 EngineCore 生成了新的内部 ID，应在提交时记录映射：

```text
external_request_id=req-123 engine_request_id=eng-9f2
```

只有时间而没有 ID 时，高并发场景很容易把两个请求拼成一条错误时间线。

## 4. 统一时间和时钟

需要确认：

- 日志时区。
- 时间精度是秒、毫秒还是微秒。
- 节点是否同步时钟。
- 单调时钟还是墙上时钟。
- 网关和模型 Pod 是否处于不同节点。

阶段耗时最好由同一进程的单调时钟计算；跨进程时间线再使用同步后的 UTC 时间拼接。

## 5. 为日志标注请求阶段

| 阶段 | 常见状态 |
|---|---|
| R0 | Gateway Received |
| R1 | API Parsed / Tokenized |
| R2 | Engine Waiting |
| R3 | Scheduled / Running |
| R4 | Prefill |
| R5 | First Token |
| R6 | Decode |
| R7 | Finished / Cancelled / Error |
| R8 | Response Closed |

一条请求最后出现在 R2，说明它尚未进入计算；最后出现在 R6，则需要检查 Decode、通信、输出和客户端连接。

## 6. 第一条异常和最后一条错误

多进程在线故障可能这样传播：

```text
rank 3：设备错误或 OOM                ← 首条异常
其他 rank：collective timeout          ← 等不到 rank 3
EngineCore：worker died                ← 引擎失去执行进程
API：engine unavailable                ← 请求失败
Gateway：upstream reset / 503           ← 用户现象
```

排查步骤：

1. 收集故障 Pod 的所有进程和 Rank 日志。
2. 统一时区并排序。
3. 找每个 Rank 的第一条异常。
4. 排除取消请求、连接关闭等后果日志。
5. 回到最早异常前的资源和系统事件。

## 7. 慢请求和卡住的区别

### 7.1 仍在推进

证据可能包括：

- 输出 Token 数持续增长。
- Scheduler Step 持续完成。
- 请求状态仍在 Running。
- Rank 的集合通信序号同步推进。
- GPU/NPU Kernel 持续执行。
- SSE 仍有事件，只是间隔变长。

### 7.2 可能卡住

- 请求状态长时间不变化。
- 所有输出 Token 停止增长。
- 某个 Rank 消失，其他 Rank 等待。
- Scheduler 主循环不再产生 Step。
- API 事件循环被同步任务阻塞。
- Worker 活着但心跳或进度计数停止。

“长时间”必须相对同类请求基线定义。100k Token Prefill 与 100 Token 请求不能使用同一个卡住阈值。

## 8. 取消日志怎样阅读

取消可能来自：

- 用户主动关闭连接。
- 客户端 Deadline。
- 网关/Ingress 超时。
- API 主动拒绝或终止。
- 发布过程中连接被关闭。
- 上层服务取消下游调用。

需要同时记录：

```text
cancel_source
cancel_time
engine_abort_time
kv_release_time
response_close_time
```

API 看到连接断开不代表 Engine 已经停止。若 Abort 没有传播，GPU 可能继续为无人接收的请求生成 Token。

## 9. 错误分类不要只依赖 ERROR 级别

| 行动分类 | 示例 |
|---|---|
| Request Error | 参数、长度、认证、超时 |
| Capacity Risk | 排队上升、KV Cache 接近上限 |
| Performance Fallback | Kernel 或 Graph 回退 |
| Worker Fatal | OOM、设备故障、进程退出 |
| Dependency Error | 网关、存储、Tokenizer 服务 |
| Client Cancel | 客户端主动终止，不一定是服务故障 |

一个符合预期的 400 参数错误不应触发 Worker 事故告警；持续 KV 抢占即使只有 INFO 日志，也可能预示 SLO 即将失守。

## 10. 日志采样和敏感信息

在线服务不能为每个 Token 打 INFO 日志。建议：

- 所有请求记录开始和结束摘要。
- 慢请求、错误和取消请求记录详细阶段。
- 正常请求按比例采样详细日志。
- Worker Step 使用聚合指标，不逐 Token 输出。
- Prompt、图片和输出默认不写日志。
- Token、API Key、Cookie 和文件路径进行脱敏。

日志量过大不仅增加成本，还可能阻塞应用输出、污染时间线和泄露数据。

## 11. 结构化日志字段

推荐字段：

```json
{
  "timestamp": "2026-08-25T10:00:00.123Z",
  "level": "INFO",
  "component": "scheduler",
  "request_id": "req-123",
  "engine_request_id": "eng-9f2",
  "pod": "model-a-7d9f",
  "rank": 0,
  "stage": "waiting_to_running",
  "input_tokens": 4096,
  "queue_ms": 83.4
}
```

不要把所有信息拼进一段无法解析的 `message`。

## 12. 从正常请求建立基线

按这些维度分桶：

- 模型和版本。
- 输入 Token 区间。
- 输出 Token 区间。
- 流式/非流式。
- 多模态类型和图片规模。
- 优先级或租户。
- Pod、节点和设备型号。

比较同桶 P50/P95/P99，而不是拿一个 32k Prompt 与全站平均值比较。

## 13. 一份请求时间线示例

```text
10:00:00.000 gateway received req-123
10:00:00.008 api received req-123
10:00:00.020 tokenization done input_tokens=4096
10:00:00.021 engine waiting
10:00:00.105 engine scheduled queue_ms=84
10:00:00.310 prefill done
10:00:00.321 first token
10:00:01.820 decode done output_tokens=128
10:00:01.825 response closed
```

可以得到：

```text
Gateway 到 API ≈ 8 ms
Tokenization ≈ 12 ms
Queue ≈ 84 ms
Prefill 到首 Token ≈ 216 ms
Decode 与输出 ≈ 1.5 s
E2E ≈ 1.825 s
```

如果客户端测得 TTFT 500 ms，而服务端首 Token 321 ms，需要继续查看代理缓冲和网络下行。

## 14. 在线排障的证据顺序

1. 保存 Request ID、用户时间和请求特征。
2. 查网关访问日志和上游状态。
3. 查 API 请求摘要。
4. 查 Scheduler 状态和 Queue Time。
5. 查 Worker/Rank 的第一条异常或慢 Step。
6. 对齐 KV、GPU/NPU、网络和节点指标。
7. 与相同 Token 桶、相同版本的正常请求比较。
8. 只做一个可回滚的验证实验。

## 15. 常见错误

- 只搜索最后一条 `500`。
- 只有时间窗口，没有 Request ID。
- 只收集 Rank 0。
- 把客户端超时当作引擎停止。
- 把平均延迟当作每类请求基线。
- 为排障临时输出全部 Prompt 和逐 Token 日志。
- 看到 GPU 利用率低就直接增加并发。
