# 请求卡住、超时、取消与流式断连排查

“请求超时”只表示某一层的截止时间到了，并不代表模型停止计算；“连接断了”也不代表请求已经从 Scheduler
和 KV Cache 中删除。如果取消不能端到端传播，服务会继续消耗 GPU/NPU，最终形成幽灵请求和过载。

## 1. 五种不同现象

| 现象 | 客户端看到什么 | 服务端可能状态 |
|---|---|---|
| 排队过久 | 首 Token 前超时 | 请求仍在 Waiting |
| 计算过久 | 首 Token 或中途超时 | Worker 仍在 Prefill/Decode |
| SSE 被缓冲 | 很久后一次收到大量 Token | 模型已经持续生成 |
| 连接断开 | EOF、Reset、502/504 | 请求可能继续运行 |
| 引擎卡住 | 长期无新 Token | Worker/Rank/Scheduler 不再推进 |

第一步不是重启，而是确认最后一个成功阶段和请求是否仍存在于引擎。

## 2. 超时是一条预算链

```text
客户端 Deadline
≤ SDK Timeout
≤ 业务服务 Timeout
≤ Gateway / Ingress Timeout
≤ 模型 API Timeout
≤ 引擎执行上限
```

这不是绝对的大小规则，而是提醒每层必须协调。外层先超时、内层无取消，会留下无消费者的计算；内层先超时，
外层应及时收到明确错误，而不是继续等待到自己的 Deadline。

建立超时表：

| 层 | 连接超时 | 首响应超时 | 空闲超时 | 总请求超时 | 取消方式 |
|---|---:|---:|---:|---:|---|
| 客户端 SDK | | | | | |
| 业务服务 | | | | | |
| Gateway/Ingress | | | | | |
| 模型 API | | | | | |
| 推理引擎 | | | | | |

没有统一表时，经常出现网关 60 秒、模型允许 10 分钟、客户端重试三次的放大事故。

## 3. 先判断卡在哪个阶段

```text
API 是否收到请求？
├─ 否：客户端、DNS、网络、网关、路由
└─ 是
   ├─ Tokenization 完成？否：CPU、模板、多模态预处理
   ├─ 进入 Running？否：排队、准入、KV、调度
   ├─ 首 Token 产生？否：Prefill、慢 Rank、设备
   ├─ Token 持续增加？否：Decode、通信、引擎进度
   └─ 服务端有 Token、客户端没有？输出队列、代理缓冲、连接
```

每一个“是/否”都应由 Request ID、阶段日志或指标证明。

## 4. 客户端超时怎样取证

客户端记录：

- 请求开始和 Deadline。
- DNS/TCP/TLS 时间。
- 请求头和请求体发送完成时间。
- 第一个响应头、首个 SSE 事件和最后事件时间。
- 超时类型：Connect、Read、Idle、Total。
- 是否自动重试。
- Request ID 和服务端返回的 Trace ID。

不要只记录 `timeout` 字符串。连接超时与读取超时指向完全不同的层。

## 5. 使用 curl 验证流式响应

```bash
curl --no-buffer --verbose \
  --connect-timeout 3 \
  --max-time 120 \
  http://127.0.0.1:8000/v1/chat/completions \
  -H 'Content-Type: application/json' \
  -H 'X-Request-ID: stream-test-001' \
  -d '{
    "model": "Qwen",
    "messages": [{"role": "user", "content": "连续输出十个短句"}],
    "stream": true,
    "max_tokens": 256
  }'
```

`--no-buffer` 避免 curl 自己缓冲。依次从容器 localhost、Pod IP、Service、Gateway 测试，可以定位哪一跳开始聚合或中断事件。

测试命令不要携带真实生产密钥和敏感 Prompt。

## 6. SSE 缓冲怎样识别

典型证据：

- Worker 的 Output Token 持续增加。
- API 已持续写出事件。
- 网关 `upstream_first_byte_time` 很早。
- 客户端长时间没有事件，之后一次收到多段内容。

可能位置：

- API 框架没有及时 Flush。
- 响应压缩或中间件缓冲。
- Nginx/Ingress/Envoy 默认缓冲。
- 上游业务服务把 Streaming 转为完整字符串。
- 客户端 SDK 没有逐事件读取。

应逐跳对比首事件时间，不要仅通过增加总超时掩盖缓冲。

## 7. 空闲超时和总超时不同

对于长流式请求：

- 总超时限制请求最长生命周期。
- 空闲超时限制连接多久没有任何字节。

如果模型某次 Token 间隔超过代理空闲超时，连接可能中断；持续发送数据可能绕过空闲超时，却仍会触发总超时。
需要根据 SLO、最大输出和异常保护共同设计，而不是把所有超时设为无限。

## 8. 取消应该如何传播

理想链路：

```text
客户端关闭/Deadline
→ Gateway 关闭上游或发送取消
→ API 检测 Disconnect
→ Engine Abort(request_id)
→ Scheduler 删除 Waiting/Running 请求
→ Worker 停止后续 Step
→ KV Block 和输出 Buffer 释放
→ 指标记录 cancel_source 和释放耗时
```

任意一环断裂，取消都可能停留在上层。

## 9. 怎样证明取消真正生效

取消前后观察：

- Request ID 是否从 Waiting/Running 消失。
- Output Token 是否停止增长。
- KV Cache Block 是否释放。
- 活跃 Sequence 是否减少。
- API 是否记录 `client_disconnect`。
- Engine 是否记录 Abort/Finished。
- 设备负载是否回落到符合剩余请求的水平。

只看到客户端 EOF 不能证明取消生效。

## 10. 重试为什么可能放大故障

生成请求通常成本高，且不天然幂等。若客户端在超时后立即重试，而原请求仍运行：

```text
1 个用户请求
→ 原请求继续执行
+ 第 1 次重试
+ 第 2 次重试
→ 负载放大
→ Queue 更长
→ 更多超时和重试
```

治理措施：

- 明确哪些错误可重试。
- 使用有限次数、指数退避和随机抖动。
- 为业务请求提供幂等键或去重语义。
- 超时后优先传播取消。
- 对 429/503 尊重 `Retry-After` 或平台策略。
- 在网关层限制重试预算。

## 11. 请求卡在 Waiting

证据：

- Queue Time 持续增长。
- Request 状态仍为 Waiting。
- 没有 Prefill 开始记录。

检查：

- Running 和 Waiting 数。
- 最大并发与 Batch Token 限制。
- KV Cache 可用 Block。
- 长请求和优先级。
- Scheduler 是否仍在 Step。
- 引擎是否处于过载或某个 Worker 已死亡。

Waiting 卡住不应通过增大客户端读取超时作为唯一解决方案。

## 12. 请求卡在 Prefill

区分：

- 超长输入正常慢。
- Chunked Prefill 分多轮推进。
- 多模态 Encoder 预处理慢。
- 某个 TP Rank 慢或通信卡住。
- Kernel/设备错误后没有正确传播。

观察已计算 Prefill Token 是否增长、所有 Rank 是否同步推进，以及设备是否有有效 Kernel。

## 13. 请求卡在 Decode

表现为已经收到部分 Token，之后长期停止。检查：

- 输出 Token 计数是否继续增长。
- Scheduler Step 是否继续。
- 是否只有一个请求受影响。
- 是否达到 Stop、长度或 Parser 异常边界。
- 某个 Rank 是否出现通信超时、设备错误或降频。
- API 输出队列是否阻塞。

如果 Engine Token 持续增长但 API 不再发送，根因在输出侧，不在 GPU Decode。

## 14. 发布和缩容造成的断连

滚动升级期间需要：

```text
Readiness 失败/主动摘流
→ 停止接收新请求
→ 等待运行请求完成或到达排空上限
→ 超时请求明确取消
→ 释放资源
→ 进程退出
```

`terminationGracePeriodSeconds` 必须覆盖排空策略，但不能无限等待。客户端还需要识别发布断连是否可重试。
参考[大模型推理服务滚动升级与优雅退出](../serving/05-大模型推理服务滚动升级与优雅退出.md)。

## 15. 一张故障对照表

| Engine 状态 | API 输出 | Gateway | 客户端 | 方向 |
|---|---|---|---|---|
| 未收到请求 | 无 | 无上游 | Connect/404 | 路由与网络 |
| Waiting | 无首 Token | 等待 | TTFT 超时 | 准入、容量、KV |
| 正常生成 | 持续写 | 缓冲 | 突发收到 | 代理/客户端缓冲 |
| 正常生成 | 写失败 | 连接关闭 | EOF | 取消传播 |
| Token 停止 | 无新事件 | 等待 | 空闲超时 | Decode/Rank/Worker |
| 已完成 | 已结束 | 仍未结束 | 总超时 | 协议/代理结束状态 |

## 16. 监控指标

- 各层 Timeout 和 Cancel 计数。
- Client Disconnect 到 Engine Abort 延迟。
- 被取消请求继续生成的 Token 数。
- Waiting/Running 请求年龄。
- 流式首事件与最后事件时间。
- SSE 连接持续时间和异常结束率。
- 429、499、502、503、504 分类。
- 发布期间断连和重试量。

状态码语义受代理实现影响，例如 499 常被某些网关用于表示客户端关闭，应以实际组件文档为准。

## 17. 验证修复

1. 构造可控的长输出请求。
2. 在客户端主动中断连接。
3. 验证所有层记录相同 Request ID。
4. 验证引擎及时 Abort，KV 和运行槽位释放。
5. 分别从 localhost、Service 和 Gateway 验证 SSE 间隔。
6. 验证超时后不会自动形成重试风暴。
7. 验证正常长请求仍可在业务允许时间内完成。
