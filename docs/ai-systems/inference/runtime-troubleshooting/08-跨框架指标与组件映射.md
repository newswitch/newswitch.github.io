# 跨框架指标与组件映射

框架名称、进程模型和指标前缀不断变化，但在线推理必须解决相同问题：接收请求、分词、排队、调度、
管理 KV、执行模型、采样并返回输出。跨框架排障的关键不是记住所有类名，而是把现象映射到共同职责。

:::info 版本边界

本文提供逻辑映射，不承诺具体类名和指标名在所有版本中不变。生产排障应固定镜像 digest，并以目标版本
日志、`/metrics` 输出和源码为准。

:::

## 1. 共同七层模型

```text
接入协议
→ 模板与 Tokenizer
→ 请求状态与排队
→ Scheduler
→ KV/Prefix Cache
→ Model Runner / Device Backend
→ Output / Detokenizer / Streaming
```

底部还依赖两条横向能力：

```text
并行通信：NCCL / HCCL
设备执行：CUDA / CANN、Kernel、Graph、显存/HBM
```

## 2. 核心组件映射

| 共同职责 | vLLM V1 | vLLM-Ascend | SGLang | MindIE |
|---|---|---|---|---|
| API/协议 | API Server、Serving Handler | 复用 vLLM API 层 | HTTP Server | Server |
| 模板/分词 | Renderer、Tokenizer、InputProcessor | 复用上游前端 | TokenizerManager | Tokenizer/Server 前端 |
| 请求协调 | AsyncLLM、EngineCoreClient | 复用上游控制面 | TokenizerManager ReqState | LLM Manager Interface/Engine |
| 调度 | EngineCore Scheduler | upstream Scheduler | Scheduler Process | LLM Manager Scheduler |
| 逻辑缓存 | KVCacheManager、BlockPool | upstream KV 逻辑 + Ascend 适配 | Radix Cache、Token-to-KV Pool | Block Manager |
| 执行协调 | Executor、Worker | Executor、NPU Worker | TP Worker | Executor、Text Generator |
| 设备热路径 | GPUModelRunner | NPUModelRunner | ModelRunner | Modeling、ATB/CANN |
| 输出 | OutputProcessor、Detokenizer、SSE | 复用上游输出路径 | DetokenizerManager、TokenizerManager | Text Generator/LLM Manager/Tokenizer |
| 通信 | NCCL | HCCL | NCCL；平台适配时可能不同 | HCCL |
| 图优化 | CUDA Graph/Compile | ACLGraph/npugraph 等 | CUDA Graph/Kernel Backend | 图模式、ATB/CANN 能力 |

这张表不是说组件一一等价，而是说明出现某类现象时应先到哪个职责层取证。

## 3. 请求接入差异

### 3.1 vLLM 与 vLLM-Ascend

vLLM-Ascend 以平台插件方式复用大量上游 vLLM 控制面，因此 OpenAI API、Tokenizer、EngineCore 和
Scheduler 的基本请求语义相近，主要差异集中在设备 Worker、ModelRunner、Attention、Graph、HBM 和 HCCL。

### 3.2 SGLang

SGLang 把 TokenizerManager、Scheduler 和 DetokenizerManager 组织成显式管线，并通过 IPC 传递请求和结果。
因此 GPU 利用率低时，还应检查 TokenizerManager、ZMQ/IPC 和 DetokenizerManager 是否形成前后端空洞。

### 3.3 MindIE

MindIE 使用 Server、LLM Manager、Text Generator 和 Modeling 分层。Scheduler、Block Manager 和 Executor
位于 LLM Manager 责任域，设备执行进一步进入 Text Generator、ATB/CANN。

## 4. Queue 指标的共同语义

框架可能叫 Waiting、Pending、Queue、Prefill Queue，但应回答：

- 当前多少请求尚未首次调度。
- 最老请求等待多久。
- 为什么没有进入运行：并发、Token Budget、KV、优先级还是 Worker 不可用。
- 到达率是否持续超过完成率。

统一指标建议：

```text
inference_waiting_requests
inference_running_requests
inference_queue_time_seconds
inference_oldest_waiting_age_seconds
```

采集层将框架原始指标转换为统一名称，同时保留原始标签和版本。

## 5. Prefill 与 Decode 指标

共同指标：

```text
input_tokens
prefill_computed_tokens
prefill_seconds
output_tokens
decode_seconds
inter_token_latency
scheduled_tokens_per_step
```

框架是否直接暴露 Prefill/Decode 直方图取决于版本。缺少请求级阶段指标时，可通过 Scheduler 事件、首 Token、
Step 计数和 Trace 近似，但必须标记推导口径。

## 6. KV Cache 映射

| 概念 | vLLM | SGLang | MindIE |
|---|---|---|---|
| 逻辑分配 | KVCacheManager/BlockPool | Token-to-KV Pool、分配器 | Block Manager |
| 前缀复用 | Prefix Cache | Radix Cache/RadixAttention | 以版本和配置能力为准 |
| 物理存储 | Worker KV Tensor | ModelRunner KV Pool | NPU/CPU KV Block |
| 压力表现 | Waiting、Preemption/Recompute | 可用 Token/KV Pool、Eviction | Block 不足、抢占/CPU KV 路径 |

SGLang 的 Radix Tree 表达前缀关系，不等于物理 KV Tensor；MindIE 的 `cacheBlockSize`、`npuMemSize` 也不能
直接换算成 vLLM 的同名或近似参数。

## 7. Prefix Cache 指标怎样统一

统一观察：

- 可缓存 Token。
- 命中 Token，而不只命中请求数。
- Eviction/回收。
- 命中节省的 Prefill 时间。
- 租户与模型隔离。

框架算法不同，命中率不能直接横向比较。比较框架时应使用同一 Prompt 集、相同 Cache 预热和相同统计口径。

## 8. 执行层和设备层映射

```text
Scheduler 计划
→ Executor/Worker
→ ModelRunner/Text Generator
→ Attention/GEMM/Sampling Kernel
→ CUDA/CANN
→ GPU/NPU
```

共同指标：

- 每 Step 时间。
- Batch/Token 数。
- Kernel 和 Graph 命中/回退。
- 每 Rank 计算与通信时间。
- 设备利用率、显存/HBM、功耗、频率和错误。

同样的 GPU/NPU 利用率不能证明同样的有效 Token 吞吐。

## 9. 通信映射

| 现象 | NVIDIA 路线 | 昇腾路线 |
|---|---|---|
| 通信库 | NCCL | HCCL |
| 节点内高速互联 | NVLink/NVSwitch/PCIe | HCCS/PCIe |
| 节点间 | RoCE/InfiniBand/TCP 路径 | RoCE/HCCL 网络 |
| 排障对象 | Rank、Collective、链路、拓扑 | Rank、HCCL、HCCS、RoCE、拓扑 |

框架只显示 Collective Timeout 时，仍要回到第一条 Rank 异常；某 Rank 的 OOM 或设备错误可能先于通信超时。

## 10. 输出链路映射

| 框架 | 输出关键层 |
|---|---|
| vLLM | ModelRunnerOutput → EngineCoreOutput → OutputProcessor/Detokenizer → SSE |
| vLLM-Ascend | NPUModelRunner 输出回到 upstream EngineCore/OutputProcessor |
| SGLang | Scheduler → DetokenizerManager → TokenizerManager → SSE |
| MindIE | Text Generator → LLM Manager → Tokenizer/Server → 响应 |

Engine 已产生 Token 而客户端未收到，应检查各框架对应的输出 IPC、反分词、Parser、事件循环和代理。

## 11. 症状到共同层

| 症状 | 共同层 | 框架专项入口 |
|---|---|---|
| API 收不到请求 | 接入/网关 | 各 Server/API 日志 |
| GPU/NPU 空闲、Scheduler 无请求 | Tokenizer/IPC | TokenizerManager、API、Tokenizer 进程 |
| Queue 高 | Scheduler/KV | Waiting、Block、Token Budget |
| TTFT 高、Queue 低 | Prefill/Encoder | ModelRunner/Text Generator、Kernel |
| ITL/TPOT 高 | Decode/通信 | Step、Batch、Graph、Rank |
| 生成了 Token 但客户端无输出 | Output | Detokenizer、Parser、SSE |
| HBM/OOM | 权重/KV/激活/Graph | Worker、ModelRunner、Block Manager |
| 单 Rank 慢 | 执行/通信/设备 | NCCL/HCCL、拓扑、频率 |

## 12. 参数不能直接翻译

跨框架选型时常见错误是把：

```text
vLLM gpu_memory_utilization
SGLang mem_fraction_static
MindIE npuMemSize
```

当成相同百分比。它们的预算对象、默认预留、Graph/Workspace、缓存布局和单位可能不同。
正确方法是把参数映射到“权重、KV、激活、Graph、通信和安全余量”的共同资源账本，再用启动日志和压测验证。

## 13. 建立统一 Dashboard

建议三层：

### 13.1 业务层

```text
request/token arrival
success/error/cancel
TTFT/ITL/E2E
goodput
tenant/model
```

### 13.2 引擎层

```text
waiting/running
queue/prefill/decode
scheduled tokens
KV/prefix/preemption
worker/rank health
```

### 13.3 资源层

```text
CPU/RSS
GPU/NPU utilization, memory, clock, power
communication/network
device errors
```

转换器应附加 `framework`、`framework_version`、`model_revision`、`pod`、`rank` 和 `device_uuid` 标签；
高基数字段如 Request ID 不放入 Prometheus Label，而进入日志或 Trace。

## 14. 跨框架对比实验

必须固定：

- 同一模型和等价权重/量化。
- 同一 Tokenizer 与 Chat Template。
- 相同输入/输出 Token 数据集。
- 相同硬件数量和拓扑。
- 相同并发/请求率模型。
- 相同 SLO 和统计窗口。
- Cache 冷热状态。

比较：

```text
正确性
TTFT/ITL/E2E 分位数
Goodput
Token 吞吐
显存/HBM 与功耗
冷启动
故障恢复
```

如果硬件平台不同，只能比较端到端目标与成本，不能把 CUDA 和 CANN 的单个 Kernel 数字直接当作框架优劣。
