# 运行期证据自动采集与诊断包

线上故障发生后，人工逐条复制命令有三个问题：采集时间不一致、容易遗漏进程重启前的证据、不同值班人员得到的材料不可比较。诊断包的作用，是在不改变服务状态的前提下，把一次故障的最小证据集自动保存下来。

诊断包不是“把整台机器全部打包”。它必须有明确的目标工作负载、时间窗口、大小上限和脱敏规则。

## 1. 诊断包要回答什么

一个可以交给其他团队复核的诊断包，应能回答：

- 故障发生在哪个集群、命名空间、Pod、容器、节点和设备；
- 当时运行的镜像、模型、框架和关键配置是什么；
- 请求在哪一层停止前进；
- 第一个异常是什么，后续错误是怎样扩散的；
- 故障前后的请求、队列、KV Cache 和设备指标怎样变化；
- 是否发生过重启、调度、驱逐、OOMKill 或节点状态变化；
- 采集是否完整，哪些命令失败，文件是否被再次修改。

诊断包与[模型服务线上故障应急 Runbook](10-模型服务线上故障应急Runbook.md)配套使用：Runbook 规定决策顺序，诊断包保证证据标准。

## 2. 设计原则

### 2.1 默认只读

采集程序不得重启进程、删除 Pod、清理缓存、修改 sysctl 或执行设备复位。它的权限应该低于处置工具，避免“采集证据”本身改变现场。

### 2.2 范围明确

输入至少包含：

- 集群上下文；
- Namespace；
- Pod 或标签选择器；
- 容器名称；
- 采集起止时间或 `--since` 时间窗；
- 是否允许执行容器内和节点侧只读命令。

禁止默认扫描整个集群或整台主机。

### 2.3 时间一致

采集开始时记录控制端、Pod 和节点时间。所有日志启用时间戳，指标使用绝对起止时间。否则无法判断“队列先升高”还是“Worker 先退出”。

### 2.4 有界采集

每个命令都应设置超时，每类日志设置最大字节数，整个诊断包设置容量上限。故障期间无限制抓取日志可能进一步占满磁盘或 API Server。

### 2.5 脱敏优先

不得收集 Kubernetes Secret 值、访问令牌、私钥、完整用户提示词和业务响应。环境变量、Pod 注解、请求头和启动命令都要经过规则化脱敏。

### 2.6 可验证

采集结束后生成文件清单、大小、SHA-256 校验值、失败项和工具版本。这样才能判断诊断包是否完整、传输后是否变化。


## 4. 第一层：Kubernetes 对象和生命周期证据

### 4.1 对象快照

```bash
kubectl -n NAMESPACE get pod POD_NAME -o json
kubectl -n NAMESPACE describe pod POD_NAME
kubectl -n NAMESPACE get deploy,statefulset,daemonset -l app=MODEL_APP -o json
kubectl -n NAMESPACE get service,endpoints,endpointslice -l app=MODEL_APP -o json
kubectl -n NAMESPACE get events --sort-by=.lastTimestamp -o json
kubectl get node NODE_NAME -o json
```

原始对象可能包含明文环境变量、内部地址或业务注解。生产工具不应直接把原始输出放入最终压缩包，而应先转换结构化 JSON，再按字段进行保留或脱敏。

推荐采用“允许清单”而不是只靠关键词替换：

- 保留资源请求/限制、镜像、命令、重启次数和状态；
- Secret 只保留引用名称，不解析值；
- 明文 `env.value` 默认替换成 `[REDACTED]`；
- 删除 `kubectl.kubernetes.io/last-applied-configuration` 等大块注解；
- 删除 ServiceAccount Token、认证头和私有仓库凭据。

### 4.2 生命周期字段

自动提取以下字段到摘要中：

- `.status.containerStatuses[].restartCount`；
- 当前和上一次 `state`、`lastState`、`reason`、`exitCode`；
- Pod `conditions` 的变化；
- `nodeName`、QoS、资源请求和限制；
- OOMKilled、Evicted、Preempted、Unhealthy 等事件；
- Readiness、Liveness、Startup Probe 的失败记录。

对象快照用于回答“容器为什么不在原来的状态”，日志用于回答“进程退出前发生了什么”，两者不能相互替代。

## 5. 第二层：当前日志和上一次日志

```bash
kubectl -n NAMESPACE logs POD_NAME -c CONTAINER \
  --since=30m --timestamps --limit-bytes=52428800

kubectl -n NAMESPACE logs POD_NAME -c CONTAINER \
  --previous --timestamps --limit-bytes=52428800
```

采集器要处理四种情况：

1. 当前容器没有重启，`--previous` 不存在；
2. Pod 包含 API、代理、指标和设备插件等多个容器；
3. 日志量超过上限，只能保留故障窗口和截断标记；
4. Pod 已被删除，需要从集中日志系统按 Pod UID 查询。

日志文件头部应写入 Pod UID、容器 ID、镜像摘要、采集时间窗和是否截断。搜索错误时先建立时间线，再按[模型服务运行日志的分层阅读方法](02-模型服务运行日志的分层阅读方法.md)区分根因和传播错误。

## 6. 第三层：运行时和操作系统状态

容器内只执行经过审核的只读命令，并为每条命令设置超时：

```bash
date -Ins
ps -eo pid,ppid,stat,etime,%cpu,%mem,args
cat /proc/meminfo
cat /proc/pressure/cpu
cat /proc/pressure/memory
cat /proc/pressure/io
ss -lntp
ulimit -a
```

需要特别注意：

- `ps` 的命令行可能包含令牌，写包前必须脱敏；
- `env` 会直接暴露凭据，不应作为默认采集命令；
- `lsof`、递归文件扫描和核心转储可能很慢或很大，应单独授权；
- `/proc/PID/environ`、Secret 挂载目录和用户请求缓存默认禁止采集；
- 节点侧 `dmesg`、systemd 日志通常需要更高权限，应由受控的节点采集器完成。

### 6.1 版本信息要形成兼容矩阵

至少记录：

- 镜像 tag 和不可变 digest；
- Python、PyTorch、vLLM/SGLang/MindIE 版本；
- CUDA/NVIDIA Driver 或 CANN/固件/驱动版本；
- Kubernetes、容器运行时和内核版本；
- 模型路径对应的版本、校验值或制品 ID；
- 插件、算子包和通信库版本。

只记录镜像标签不够。同一个可变标签可能在不同时间对应不同镜像内容。

## 7. 第四层：GPU/NPU 和集合通信证据

设备采集命令应由机型决定。例如 NVIDIA 环境通常采集：

```bash
nvidia-smi -L
nvidia-smi --query-gpu=index,uuid,name,temperature.gpu,power.draw,clocks.sm,utilization.gpu,memory.used,memory.total,ecc.errors.uncorrected.volatile.total --format=csv
nvidia-smi dmon -s pucvmet -c 5
```

昇腾环境通常采集：

```bash
npu-smi info
npu-smi info -t usages
npu-smi info -t health
npu-smi info -t power
```

不同驱动和 `npu-smi` 版本支持的 `-t` 类型可能不同，采集器应先探测能力，并把“不支持”记入失败项，而不是中断整个采集流程。

还应保存：

- 容器可见设备与节点物理设备的映射；
- Pod 资源分配和设备插件状态；
- 首个异常 Rank、后续受影响 Rank 和通信错误时间；
- HCCL/NCCL 超时、链路和拓扑信息；
- 设备健康、ECC/UCE、温度、功耗和降频证据；
- 同节点其他 Pod 是否同时异常。

设备连续采样需要严格限制次数和间隔，避免诊断命令长期占用管理通道。

## 8. 第五层：指标窗口，而不是一张当前值截图

模型服务的很多问题只能从趋势判断。至少导出故障前 15 分钟到故障后 15 分钟的序列：

- 请求速率、错误率、取消数、输入/输出 token；
- TTFT、ITL、端到端时延；
- 等待和运行请求数；
- Prefill/Decode token 吞吐与批大小；
- KV Cache 使用率、抢占、命中和重计算；
- CPU、内存、网络、磁盘和设备指标。

诊断包同时保存查询表达式、步长和 Prometheus 数据源标识。只有导出数值却没有查询条件，其他人无法重放分析。

推荐在采集器中维护逻辑指标名，再为不同框架配置映射：

```yaml
logical_metrics:
  queue_depth:
    vllm: vllm:num_requests_waiting
    sglang: sglang:num_queue_reqs
  kv_cache_usage:
    vllm: vllm:kv_cache_usage_perc
    sglang: sglang:token_usage
```

实际指标名称会随框架版本变化，必须结合[跨框架指标与组件映射](08-跨框架指标与组件映射.md)维护版本化配置，不能在脚本里永久写死。

## 9. 自动采集流程

一个稳健的采集器可以拆成以下阶段：

```text
参数校验
  ↓
创建临时工作目录
  ↓
记录清单、时钟和采集器版本
  ↓
并发执行有超时的只读采集任务
  ↓
结构化脱敏与敏感词二次扫描
  ↓
生成失败项、文件清单和校验值
  ↓
压缩到受控目录
  ↓
删除临时明文文件
```

每个任务返回统一状态：

```json
{
  "name": "pod-previous-log",
  "started_at": "2026-08-25T14:31:15+08:00",
  "duration_ms": 842,
  "status": "skipped",
  "reason": "container has no previous instance",
  "output": null
}
```

“没有数据”“权限不足”“命令不支持”和“命令超时”是四种不同结果，不能都写成采集失败。

## 10. 触发方式与权限模型

### 10.1 手动触发

适合首次建设。值班人员提供故障编号、目标 Pod 和时间窗，系统显示预计采集范围，确认后执行。

### 10.2 告警触发

适合 Worker 退出、OOMKill、设备错误等短暂现场。应增加：

- 同一对象的冷却时间；
- 每小时最大触发次数；
- 全局并发上限；
- 诊断包大小和保留期限；
- 告警恢复后仍可关联到原事件的故障 ID。

### 10.3 Kubernetes 事件触发

控制器监听 OOMKilled、Unhealthy、Evicted 或节点设备告警，再创建一次受限采集任务。控制器不应直接拥有集群管理员权限，可将节点级采集交给独立、受审计的 DaemonSet。

权限建议拆分为：

| 身份 | 权限 |
| --- | --- |
| 工作负载采集器 | 读取指定 Namespace 的 Pod、事件、日志和工作负载 |
| 指标采集器 | 查询允许的时间序列，不读取告警系统凭据 |
| 节点采集器 | 读取指定节点状态和设备信息，不修改设备 |
| 打包服务 | 读取脱敏后的中间文件并写入制品库 |

## 11. 脱敏验收

打包前执行两轮检查：

1. **结构化规则**：删除或替换明确字段，如 Secret、Token、Authorization、Cookie、密码和用户请求体；
2. **内容扫描**：检查常见凭据格式、私钥头、内部域名、邮箱、手机号和模型输入输出。

扫描命中后默认阻止上传，由人工确认是否为误报。脱敏后的文件仍保留字段名，例如：

```text
Authorization: [REDACTED]
HUGGING_FACE_HUB_TOKEN=[REDACTED]
prompt_sha256=8c6c...  prompt_content=[NOT_COLLECTED]
```

保留哈希可以关联相同请求，避免保存原始内容。

## 12. 诊断包的质量验收

生成后的包必须通过以下检查：

```text
[ ] manifest 包含目标、时间窗、版本、时区和采集范围
[ ] current 与 previous 日志的存在状态有明确记录
[ ] Kubernetes 对象已结构化脱敏
[ ] 指标包含查询表达式、步长和绝对时间范围
[ ] 设备命令与实际硬件类型匹配
[ ] 每个采集任务都有成功、跳过、超时或失败状态
[ ] 没有 Secret、Token、私钥和完整用户内容
[ ] 文件数量、总大小和 SHA-256 校验值已生成
[ ] 包可以在隔离环境解压并按 README 复核
[ ] 保留期限、访问权限和删除流程明确
```

## 13. 从诊断包走向自动诊断

自动采集完成后，可以继续做规则分析，但不要让规则替代原始证据：

- `restartCount` 增加且 `lastState.reason=OOMKilled`，关联内存曲线；
- 队列上升、设备利用率低、通信超时，提示检查首个异常 Rank；
- TTFT 上升、ITL 稳定、Prefix Cache 命中下降，提示 Prefill 路径；
- KV Cache 高水位与抢占同时增长，提示容量或长上下文压力；
- API 进程健康但 EngineCore 日志停止，提示服务假活。

自动诊断输出应使用“证据—判断—置信度—下一步验证”的形式，不能只给一个无法复核的根因结论。

完成诊断包建设后，下一步是通过[模型服务故障注入与恢复演练](12-模型服务故障注入与恢复演练.md)验证：异常发生时是否真的能采到证据，告警和 Runbook 是否真的可用。
