# 模型服务运行期分析学习路线

启动排障回答“模型为什么没有起来”，运行期分析回答“模型已经起来，为什么请求仍然慢、失败、卡住或拖垮服务”。
本模块使用跨框架的通用模型，不重复 vLLM、vLLM-Ascend、SGLang 和 MindIE 的源码细节。

```text
客户端与网关
→ API 与 Tokenizer
→ 准入和排队
→ Scheduler
→ Prefill
→ KV Cache
→ Decode
→ Detokenizer 与流式返回
```

## 4. 模块边界

GPU Xid、ECC、掉卡、温度、功耗以及昇腾 UCE 等设备故障归入 `gpu/cluster/troubleshooting/`，
本模块只解释设备故障如何传导到在线请求。

## 5. 学习方法

每篇文章都使用相同的证据顺序：

```text
用户现象
→ 请求阶段
→ 日志和指标
→ 资源状态
→ 可证伪假设
→ 单变量实验
→ 恢复与复盘
```

不要从“GPU 利用率不高”直接跳到“增加并发”，也不要从“请求超时”直接跳到“重启 Pod”。
先确定时间花在哪个阶段、哪个进程仍在推进，以及超时之后计算是否已经取消。

## 6. 学习完成标准

完成本模块后，应能够：

- 用 Request ID 串联客户端、网关、API、Scheduler、Worker、Rank 和设备。
- 把端到端延迟拆成网关、Tokenization、排队、Prefill、Decode 与输出阶段。
- 区分算力不足、调度不当、KV Cache 压力、通信慢 Rank 和上游超时。
- 判断请求是慢、卡住、已取消但仍执行，还是 Worker 已经死亡。
- 设计准入、背压、限流、超时、熔断和降级边界。
- 使用真实 Token 分布和 SLO 验证修复，而不是只看平均 GPU 利用率。
- 在 vLLM、vLLM-Ascend、SGLang 和 MindIE 之间建立同层组件与指标映射。
- 根据工作负载、Goodput、KV Cache 和故障冗余完成容量规划。
- 使用 Runbook、诊断包和故障演练验证检测、隔离与恢复能力。
