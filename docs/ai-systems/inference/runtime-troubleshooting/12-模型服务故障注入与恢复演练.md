# 模型服务故障注入与恢复演练

监控、Runbook 和高可用架构写在文档里，不代表故障发生时一定有效。故障演练的目标，是在可控范围内验证系统能否发现异常、限制影响、保存证据并恢复服务。

一次有价值的演练必须有假设、观测指标、影响边界、终止条件和恢复验收。只执行一次 `kubectl delete pod` 然后看到 Pod 重建，不等于完成了高可用验证。

## 1. 演练要验证哪些能力

模型服务的恢复能力可以拆成六项：

| 能力 | 要回答的问题 |
| --- | --- |
| 检测 | 告警能否在用户大面积失败前触发 |
| 定位 | 日志、指标和请求 ID 能否确定故障层次 |
| 隔离 | 异常副本能否及时停止接收新流量 |
| 降级 | 限流、短上下文、备用模型等策略是否可用 |
| 恢复 | 副本、节点或依赖恢复后，容量能否平稳回归 |
| 复盘 | 是否形成可验证的长期改进，而非只记录现象 |

演练对象不仅是推理进程，还包括网关、调度、模型存储、Kubernetes、设备插件、节点和监控系统。

## 2. 安全边界

### 2.1 环境顺序

按以下顺序逐级验证：

1. 本地或开发环境；
2. 独立测试集群；
3. 与生产配置接近的预发布环境；
4. 获得审批后，在生产环境执行低风险、极小范围演练。

网络丢包、进程终止、Pod 删除等动作必须绑定明确的测试 Namespace、标签和目标对象。不得使用没有范围限制的选择器，也不得通过制造真实硬件损坏来验证设备故障。

### 2.2 演练前置条件

```text
[ ] 已确定负责人、观察员和停止演练的授权人
[ ] 已记录目标对象的 UID、节点和流量比例
[ ] 已确认备用容量和回滚路径真实可用
[ ] 已冻结无关发布和配置变更
[ ] 已保存演练前基线和当前配置
[ ] 已验证监控、日志和诊断包采集链路
[ ] 已通知受影响团队并建立沟通频道
[ ] 已设置最大持续时间和自动清理时间
```

### 2.3 立即终止条件

任何一个条件成立都应停止注入并恢复：

- 影响超出预定模型、租户、副本或可用区；
- 错误率、TTFT 或队列超过硬阈值；
- 备用容量无法承接流量；
- 监控或日志失效，无法继续观察；
- 出现未预期的数据安全、设备健康或集群控制面风险；
- 清理或回滚步骤无法按预案执行。

停止条件必须在演练前量化，不能在故障扩大后临时讨论。

## 3. 使用实验假设驱动演练

先写假设，再选择注入方式：

```text
实验编号：EXP-INF-007
稳态：Qwen 服务成功率 >= 99.9%，P95 TTFT <= 2 s
假设：任意一个推理 Pod 退出后，30 s 内停止接收流量，
      其余副本保持 P95 TTFT <= 3 s，5 min 内恢复冗余容量
目标：单个测试副本
注入：终止容器主进程
持续时间：最长 10 min
观测：成功率、TTFT、队列、Endpoint、重启、诊断包
停止条件：错误率 > 2% 持续 1 min，或任一非目标服务异常
恢复：停止注入，确认 Pod Ready，再按小流量逐步恢复
```

稳态指标应该从用户视角定义，同时包含系统内部信号。只检查 Pod 数量，无法证明模型服务仍然可用。

## 4. 建立演练基线

注入前至少运行一个稳定观察窗口，记录：

- 每秒请求数、并发和输入/输出 token 分布；
- 成功率、TTFT、ITL、端到端时延；
- 等待请求数、批大小和 token 吞吐；
- KV Cache 水位、抢占和 Prefix Cache 命中；
- CPU、内存、GPU/NPU 利用率和 HBM；
- 当前副本数、Endpoint 数、节点和设备分布；
- 自动扩缩容、健康检查和告警状态。

压测流量必须能代表真实负载。全是短输入、短输出的请求，无法验证长上下文导致的 KV Cache 压力；恒定到达率也无法验证突发流量和排队。

## 5. 演练一：客户端取消与流式断连

### 5.1 要验证的假设

客户端关闭连接后，网关和推理框架能够把取消信号传递到执行层，已取消请求不会长期占用 KV Cache 和 Decode 计算。

### 5.2 注入方式

在测试客户端中发送一批流式请求，并在收到少量 token 后主动断开连接。不要直接使用生产用户请求作为实验流量。

### 5.3 观测点

- 网关是否记录客户端取消，而不是全部归类为服务端 5xx；
- 框架取消计数是否增长；
- 运行请求数和 KV Cache 是否及时下降；
- 其他请求的 ITL 是否受到持续影响；
- 日志能否通过请求 ID 串起入口、Engine 和 Worker。

如果连接已经断开，但生成仍持续到 `max_tokens`，需要检查取消信号传播和输出反压处理。参见[请求卡住、超时、取消与流式断连排查](04-请求卡住-超时-取消与流式断连排查.md)。

## 6. 演练二：突发流量与过载保护

### 6.1 要验证的假设

请求超过稳定容量后，系统会在有界队列内排队，超过阈值的请求被快速、明确地拒绝，不会通过无限排队和重试拖垮全部副本。

### 6.2 负载阶梯

不要一步压到极限，按阶梯增加 offered load：

```text
基线 50% 容量 → 70% → 85% → 100% → 120% → 降回 50%
```

每个阶段保持足够时间，使队列和 KV Cache 到达稳定状态。

### 6.3 观测点

- 请求到达率与完成率何时开始分离；
- 队列是否持续无界增长；
- TTFT 和 ITL 哪一个先恶化；
- 拒绝码是否明确，客户端是否遵守退避；
- 降低流量后队列能否自行恢复；
- 自动扩容触发时，冷启动是否快于队列耗尽时间。

如果吞吐已经不再增长，而延迟和错误率继续上升，就已经越过有效容量边界。容量判定方法见[模型服务运行期容量规划](09-模型服务运行期容量规划.md)，保护策略见[过载保护、背压、限流与熔断](07-过载保护-背压-限流与熔断.md)。

## 7. 演练三：单推理进程或单 Pod 退出

### 7.1 要验证的假设

单副本退出不会造成全局不可用；异常副本能迅速摘流；剩余容量可承接请求；新副本完成真实就绪后才重新接流。

### 7.2 分层注入

先在隔离测试 Namespace 中逐级执行：

1. 让容器主进程正常退出；
2. 模拟进程异常退出；
3. 删除一个明确命名的测试 Pod；
4. 在预发布环境模拟单节点不可用。

例如，删除 Pod 的实验必须使用已经人工核对的完整名称：

```bash
kubectl config current-context
kubectl -n inference-chaos get pod TEST_POD -o wide
kubectl -n inference-chaos delete pod TEST_POD --wait=false
```

这里的 `inference-chaos` 是独立演练环境示例。不要把命令直接复制到生产，也不要使用会匹配多个对象的模糊标签。

### 7.3 观测点

- Readiness 失败到 Endpoint 摘除的时间；
- 在途请求是完成、重试还是失败；
- 剩余副本的队列、TTFT 和 HBM；
- Deployment/StatefulSet 创建替代副本的时间；
- 模型下载、权重加载和图编译耗时；
- 新副本是否在真实推理可用前就被标记 Ready；
- 自动诊断包能否保留 `--previous` 日志。

只要 API 进程还在，Worker 或 EngineCore 退出后就可能出现“Pod Ready、请求失败”的假活，详见[Worker 退出、EngineCore 死亡与服务假活](06-Worker退出-EngineCore死亡与服务假活.md)。

## 8. 演练四：慢副本与慢 Rank

### 8.1 为什么比“直接退出”更难

进程退出容易被健康检查发现，慢副本仍能返回结果，却会增加排队并拖累尾延迟。Tensor Parallel 中一个 Rank 变慢，其他 Rank 可能在集合通信处等待，表现为所有设备利用率波动。

### 8.2 安全注入方式

在测试环境使用框架测试钩子、限频的代理延迟或 Chaos 工具控制 CPU/网络延迟。不要通过温度、功耗或破坏性设备操作人为制造真实硬件异常。

### 8.3 观测点

- 负载均衡是否仍向慢副本发送同等流量；
- P50 正常时，P99 是否已显著恶化；
- 慢 Rank 是否导致集合通信等待；
- 异常检测能否按实例和 Rank 发现离群值；
- 是否可以只摘除异常副本，而不是重启全部服务。

演练通过标准不是“最终仍能返回”，而是在规定 SLO 内发现并隔离慢副本。

## 9. 演练五：KV Cache 压力与运行中 OOM

### 9.1 要验证的假设

长上下文和高并发进入系统后，KV Cache 有清晰的水位监控和保护阈值；系统优先限流或拒绝不合规请求，而不是让进程被 OOMKill。

### 9.2 输入矩阵

使用合成内容构造可控组合：

| 组别 | 输入长度 | 输出长度 | 并发 | 目的 |
| --- | ---: | ---: | ---: | --- |
| A | 短 | 短 | 低 | 基线 |
| B | 长 | 短 | 中 | Prefill 与 KV 分配 |
| C | 短 | 长 | 中 | Decode 驻留时间 |
| D | 长 | 长 | 逐级增加 | 最坏压力 |

### 9.3 观测点

- KV Cache 使用率和可用块；
- 抢占、重计算、换入换出次数；
- TTFT、ITL 和完成吞吐；
- 容器内存与 HBM 是否同步增长；
- 请求被拒绝时是否返回可识别错误；
- 降低负载后缓存水位能否恢复。

不应以触发真实 OOM 作为唯一成功条件。更重要的是验证系统能否在 OOM 之前告警并进入受控降载。原理见[KV Cache 抢占、重计算与运行中 OOM](05-KV-Cache抢占-重计算与运行中OOM.md)。

## 10. 演练六：网关、网络和依赖服务异常

模型服务可能依赖 DNS、Ingress/Gateway、鉴权、模型存储、对象存储、注册中心和指标系统。演练要逐个隔离变量。

### 10.1 可测试场景

- 网关到单个后端的连接超时；
- 测试 Pod 的网络增加固定延迟或少量丢包；
- DNS 响应变慢；
- 模型制品存储短时不可用；
- 鉴权服务变慢或返回错误；
- 指标系统不可用，但推理服务仍应工作。

### 10.2 观测点

- 超时预算是否逐层递减，还是内层超时长于外层；
- 重试是否跨副本并具有退避；
- 熔断是否只影响故障依赖；
- 已加载模型能否在制品存储短时不可用时继续服务；
- 监控失效是否触发单独告警，而不是被误判为业务恢复。

网络注入只允许应用到明确的测试 Pod 或测试流量。演练结束后必须验证所有网络规则、代理和 `tc` 配置均已清理。

## 11. 演练七：节点与可用区容量损失

### 11.1 要验证的假设

失去一个节点或一个故障域后，剩余资源满足 N-1 容量，调度器能在预期位置重建副本，业务不会因模型冷启动造成长时间容量缺口。

### 11.2 检查重点

- 副本是否真正分散到不同节点、机架或可用区；
- PodDisruptionBudget 是否允许维护，又能防止同时失去过多副本；
- 模型存储带宽能否支持多个副本同时冷启动；
- GPU/NPU 资源碎片是否导致替代 Pod 长期 Pending；
- 亲和性、污点、容忍和设备类型约束是否阻止调度；
- 自动扩容能否获得真实可用的加速卡节点；
- 流量何时恢复到新副本，是否有预热和慢启动。

容量规划不能只按正常日均流量计算。应使用[模型服务运行期容量规划](09-模型服务运行期容量规划.md)中的 N-1、冷启动和故障域方法预先证明冗余。

## 12. GPU/NPU 故障怎样安全演练

设备故障通常包括 ECC/UCE、掉卡、驱动异常、温度降频和集合通信错误。安全的演练方式是模拟“上层能观察到的结果”，而不是故意损坏设备：

- 让测试 Worker 返回设备不可用错误；
- 使用测试钩子模拟某 Rank 退出或超时；
- 给测试节点添加故障标签，验证自动隔离控制器；
- 在资源管理层将一张测试卡标记为不可调度；
- 回放经过脱敏的设备错误日志，验证告警和归因规则。

需要验证：

1. 首个设备错误是否被保存；
2. 故障卡是否停止承接新工作负载；
3. 节点隔离是否影响同机其他健康卡；
4. 重新纳管是否经过健康检测和压力验证；
5. 反复故障是否自动升级到硬件维修流程。

禁止在生产设备上通过超频、断电、强制复位或制造高温来验证故障处理。

## 13. 恢复阶段要防止第二次故障

注入停止后，不要立即一次性恢复全部流量。推荐按以下顺序：

1. 确认故障注入对象和临时规则已经清理；
2. 验证新旧副本的版本和配置一致；
3. 对恢复副本执行端到端探测；
4. 先引入少量流量，观察错误率、TTFT、ITL、队列和 HBM；
5. 分阶段恢复到正常流量；
6. 确认自动扩容、熔断和限流回到正常策略；
7. 继续观察一个完整负载窗口。

如果大量请求在恢复瞬间同时重试，系统会出现恢复风暴。客户端和网关必须使用指数退避、抖动和重试预算。

## 14. 演练结果怎样判定

结果不只分“成功”和“失败”，还应分解为：

| 项目 | 结果示例 |
| --- | --- |
| 故障注入 | 按目标范围生效，无额外影响 |
| 检测时间 MTTD | 42 秒，符合 60 秒目标 |
| 摘流时间 | 75 秒，超过 30 秒目标 |
| 用户影响 | 0.8% 请求超时，超过 0.2% 预算 |
| 证据完整性 | 缺少 previous 日志和设备健康快照 |
| 恢复时间 MTTR | 6 分 20 秒，超过 5 分钟目标 |
| 容量恢复 | 新副本冷启动期间队列持续增长 |
| 清理 | 网络规则和测试流量全部移除 |

即使业务没有中断，只要告警、证据或恢复过程不符合假设，演练也发现了真实缺口。

## 15. 把演练结果变成工程改进

每个问题都写成可验收的行动项：

```text
问题：Worker 已退出，但 Pod 在 94 秒内仍为 Ready
改进：就绪探测增加受限的 EngineCore 状态检查
负责人：推理平台组
期限：2026-09-10
验收：下一次单 Worker 退出演练中，30 秒内摘流
```

常见改进包括：

- 为 TTFT、ITL、队列和 KV Cache 建立联合告警；
- 修正 Readiness，使其覆盖实际推理链路；
- 限制重试并加入退避和随机抖动；
- 建设长短请求隔离和过载拒绝；
- 缓存模型制品并缩短冷启动；
- 建立设备故障自动隔离和重新纳管流程；
- 自动生成[运行期证据自动采集与诊断包](11-运行期证据自动采集与诊断包.md)；
- 将验证过的处置步骤更新到[线上故障应急 Runbook](10-模型服务线上故障应急Runbook.md)。

## 16. 演练成熟度路线

### 16.1 阶段一：人工、单组件 {/* #阶段一人工单组件 */}

在测试环境手动终止单 Pod、发送过载请求，人工检查告警和恢复。

### 16.2 阶段二：自动采集、可重复 {/* #阶段二自动采集可重复 */}

实验参数、稳态验证、故障注入和清理脚本化，自动生成诊断包和结果报告。

### 16.3 阶段三：跨组件 GameDay {/* #阶段三跨组件-gameday */}

联合网关、Kubernetes、模型框架、网络、存储和设备团队，验证复杂故障的协作和升级流程。

### 16.4 阶段四：持续韧性验证 {/* #阶段四持续韧性验证 */}

将低风险实验纳入周期任务，在版本发布、驱动升级和容量变更后自动验证关键假设。

自动化不是让故障注入无限制运行。越接近生产，审批、范围控制、审计和自动终止就越重要。
