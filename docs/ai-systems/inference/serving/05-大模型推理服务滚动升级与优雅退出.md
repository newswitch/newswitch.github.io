# 大模型推理服务发布：滚动升级、流量排空、回滚与容量门禁

普通 Web 服务镜像几十秒即可启动，请求通常很短；大模型服务发布则可能同时面对：

- 单个副本占用 1～8 张 GPU；
- 模型文件数十到数百 GB；
- 冷启动数分钟；
- TP 任一 rank 失败导致整个副本失败；
- 流式请求持续较长时间；
- 新旧模型的 tokenizer、模板、量化和行为不同；
- `maxSurge: 1` 可能没有额外 GPU 可调度；
- 新旧模型同时存在会放大存储、CPU 内存和缓存压力。

所以发布不是“修改 image tag 然后 `kubectl rollout status`”，而是容量、制品、流量、SLO、回滚和故障域共同参与的状态机。

## 1. 学习目标

完成本文后，应能够：

- 定义模型服务的完整发布单元；
- 比较 Recreate、RollingUpdate、Blue/Green、Canary 和 Shadow；
- 计算 GPU surge、模型存储与冷启动容量；
- 解释 Pod termination 与 EndpointSlice ready/serving/terminating；
- 设计 SIGTERM、readiness、请求排空和最大终止时间；
- 建立离线门禁、金丝雀 SLO 和自动/人工回滚条件；
- 演练新 Pod Pending、加载失败、质量回归和滚动期间 5xx。

## 2. 发布单元不只是镜像

一次可回滚发布至少包含：

```yaml
release:
  application_image: sha256:example
  model_id: example
  model_revision: immutable-revision
  tokenizer_revision: immutable-revision
  chat_template: checksum
  quantization: example
  vllm_config: checksum
  runtime:
    driver_baseline: example
    cuda: example
    vllm: example
  routing_policy: version
  probe_policy: version
  autoscaling_policy: version
```

只回滚镜像但保留新 tokenizer/模型配置，可能仍然错误。所有组件必须有不可变坐标和兼容矩阵。

## 3. 发布前四类门禁

### 3.1 制品门禁

- manifest/checksum/签名；
- 模型、tokenizer、config、template 成套；
- 权限和 license；
- 对象/文件完整；
- 不依赖可变 `latest`。

### 3.2 功能与质量门禁

- 固定评测集；
- 输出结构与 OpenAI 兼容 API；
- 关键任务质量；
- 安全/拒答/敏感内容；
- 新旧结果差异阈值；
- streaming、tool call、JSON 等协议兼容。

### 3.3 性能门禁

- 冷/热启动；
- TTFT、TPOT、吞吐、P99；
- HBM、KV Cache、CPU memory；
- TP/NCCL；
- 目标输入/输出长度和并发；
- 稳态与过载。

### 3.4 平台门禁

- GPU 型号、数量、拓扑；
- 存储和节点 cache 空间；
- surge GPU 容量；
- quota/queue；
- PDB、污点和故障域；
- 镜像和模型拉取带宽；
- 回滚版本仍可获取。

## 4. 五种发布策略

| 策略 | GPU 额外容量 | 停机风险 | 验证能力 | 适合 |
|---|---:|---|---|---|
| Recreate | 0 | 高 | 弱 | 实验/无法并存且可接受停机 |
| RollingUpdate | 取决于 surge | 中 | 按 Pod 逐步 | 同接口、小变更、容量足 |
| Blue/Green | 接近 100% | 低 | 完整环境验证、切换快 | 大版本/高风险 |
| Canary | 少量额外容量 | 低 | 真实小流量评估 | 常规生产发布 |
| Shadow | 额外推理容量 | 不影响主响应 | 可比较输出/性能 | 模型质量与兼容评估 |

Shadow 请求必须处理隐私、成本和副作用，不能把带写操作的业务无条件复制。

## 5. GPU surge 容量

设：

```text
R = 目标副本数
G = 每副本 GPU 数（例如 TP size）
S = maxSurge 副本数
```

滚动期间理论 GPU 需求：

```text
GPU_rollout_max = (R + S) × G
```

例如 4 个 TP=4 副本，`maxSurge=1`：

```text
稳态  = 4 × 4 = 16 GPU
滚动峰值 = 5 × 4 = 20 GPU
```

还需考虑节点碎片：集群即使空闲 4 张 GPU，若分散在四台各 1 张，单 Pod 请求 4 张仍可能 Pending。

## 6. RollingUpdate 参数不是固定答案

```yaml
strategy:
  type: RollingUpdate
  rollingUpdate:
    maxUnavailable: 0
    maxSurge: 1
minReadySeconds: 60
progressDeadlineSeconds: 1800
```

含义：

- `maxUnavailable: 0`：希望发布期间不主动降低可用副本；
- `maxSurge: 1`：允许多一个新 Pod；
- `minReadySeconds`：新 Pod Ready 后还需稳定一段时间才算 Available；
- `progressDeadlineSeconds`：超过时间未推进，Deployment 标记进度失败。

但如果没有额外 GPU，新 Pod 永远 Pending，旧 Pod 又因 `maxUnavailable=0` 不会释放，发布停滞。

可选方案：

1. 预留 surge GPU；
2. 发布前临时扩节点池；
3. 使用独立 Canary/Blue-Green 池；
4. `maxSurge=0,maxUnavailable=1` 逐个先释放旧副本，但会降低容量；
5. 分池/分区域发布；
6. 使用外部流量路由而不是单 Deployment 原地替换。

选择必须根据容量和 SLO，不应复制通用 Web 服务默认 25%。

## 7. 模型与存储 surge

滚动期间可能同时存在：

```text
旧模型文件
+ 新模型文件
+ 下载临时文件
+ 解压/转换副本
+ 多节点 cache
+ 旧/新容器镜像
```

节点缓存最低容量要覆盖：

```text
old_version + new_version + staging + safety_margin
```

若新 Pod 并发从 NFS/Ceph/S3 拉取模型，会形成冷启动风暴。使用分批预热、并发限制、checksum、不可变目录和回源保护。

不要在所有节点下载完成前删除旧模型；回滚依赖旧制品仍在且可读。

## 8. 冷启动决定发布速度

记录：

```text
T_schedule
T_image_pull
T_volume_mount
T_model_download
T_deserialize
T_gpu_load
T_tp_nccl
T_warmup
T_ready
```

Deployment progress deadline 必须覆盖正常冷启动，但不能无限大。若 P99 正常冷启动 12 分钟，默认 10 分钟可能误判；
如果设成 2 小时又没有阶段指标，真实失败会占用 GPU 很久。

## 9. 从 Pod 删除到进程退出

Kubernetes 简化流程：

```text
Pod 获得 deletionTimestamp
 -> EndpointSlice endpoint 标记 terminating，ready 通常为 false
 -> kubelet执行 preStop（若配置且 grace 非 0）
 -> runtime 向容器 PID 1 发送 TERM
 -> 等待 terminationGracePeriodSeconds
 -> 超时后强制终止
```

preStop 执行时间包含在 termination grace 内，不是额外时间。节点突然掉电/进程被 OOMKill 时也不能依赖 preStop。

EndpointSlice 有三个相关条件：

```text
ready       通常等价于 serving && !terminating
serving     endpoint 是否仍能服务
terminating 是否正在终止
```

不同 proxy/LB 如何消费 terminating+serving 需要实测，不能假定所有外部 LB 会立即停止发送。

## 10. 应用优雅退出状态机

```text
RUNNING
  -> 收到 SIGTERM / 管理面 drain
  -> DRAINING
     1. readiness=false
     2. 拒绝新请求或返回明确 503/429
     3. 等待 LB/Endpoint 传播
     4. 完成或按策略取消在途请求
     5. flush 指标/日志
     6. 关闭 worker/NCCL
  -> EXIT
```

需要定义：

- 最大请求允许运行多久；
- streaming 客户端断开如何处理；
- 超过 drain deadline 是取消还是继续；
- 客户端是否安全重试；
- 相同请求是否幂等；
- 多 rank 谁协调退出；
- sidecar/mesh 与主容器关闭顺序。

## 11. PID 1 与信号

容器 entrypoint 如果使用 shell 且没有 `exec`，SIGTERM 可能只到 shell，业务进程收不到。

不推荐：

```sh
#!/bin/sh
python -m vllm.entrypoints.openai.api_server ...
```

更明确：

```sh
#!/bin/sh
exec python -m vllm.entrypoints.openai.api_server ...
```

使用镜像内实际命令和 vLLM 版本验证。检查：

```bash
kubectl exec -n <namespace> <pod> -- ps -o pid,ppid,stat,args
```

## 12. preStop 的正确用途

preStop 可用于调用本地 drain API：

```yaml
lifecycle:
  preStop:
    httpGet:
      path: /drain
      port: admin
terminationGracePeriodSeconds: 300
```

或短暂等待 endpoint/LB 传播。但风险：

- hook 与 TERM 顺序/应用行为需要实测；
- hook 卡住会消耗 grace；
- 仅 `sleep 30` 不知道请求是否排空；
- Pod 删除前应用也可能因故障退出；
- admin 端点需要访问控制且幂等。

最佳方案是应用自身在 SIGTERM 后进入 DRAINING，并让 preStop 作为显式触发/兼容，而不是所有逻辑都藏在 shell sleep。

## 13. Readiness 与发布

新 Pod 只有在以下条件满足后才 Ready：

- 目标模型 revision 与 tokenizer 加载完成；
- 所有 TP/PP worker ready；
- KV Cache/Graph/warm-up 完成；
- API 能完成轻量 smoke；
- 没有进入 drain/过载保护；
- readinessGate（若有）通过。

旧 Pod 开始终止后 readiness 应立即失败，停止新流量。详见 [探针设计](./04-大模型服务%20Kubernetes%20探针设计.md)。

## 14. Canary 流量设计

不要只按“1% 请求”描述 Canary。LLM 请求成本差异很大，还要控制：

- 输入 Token；
- 最大输出 Token；
- streaming/non-streaming；
- 租户与功能；
- 模型任务类型；
- 工具调用；
- 长上下文；
- 并发与峰值。

路由可按 header、租户、模型别名或哈希稳定分桶。保留 control group，使新旧版本处理相似分布。

## 15. Canary 门禁

### 平台健康

- Pod Ready/restart；
- 模型加载成功；
- GPU Xid/ECC；
- OOM；
- NCCL；
- EndpointSlice/网关错误。

### SLO

- success rate；
- TTFT/TPOT/端到端 P95/P99；
- queue time；
- 429/503；
- streaming 中断；
- timeout/cancel。

### 质量

- 离线评测；
- 在线 pairwise/业务反馈；
- safety；
- JSON/tool-call 格式；
- tokenizer/template 差异。

### 资源与成本

- HBM/KV；
- tokens/s；
- GPU-hours / million tokens；
- cache 命中；
- CPU/存储/网络。

晋级应使用最小样本量、最长观察窗和三值结论：Pass/Fail/Unknown。低流量没有足够样本时不能自动当 Pass。

## 16. 发布阶段

```text
0. 制品与离线门禁
1. 测试/预发
2. 生产 0 流量加载与 smoke
3. 1 个 Canary 副本、小流量
4. 扩大到一个节点池/区域
5. 25% -> 50% -> 100%
6. 保留旧版本回滚窗口
7. 清理旧制品（独立流程）
```

每阶段定义：进入条件、观察时间、自动停止、人工审批、回滚动作和证据链接。

## 17. 回滚必须回滚完整单元

回滚包括：

- image；
- model revision；
- tokenizer/template；
- vLLM flags；
- runtime/量化；
- Service/Gateway route；
- autoscaling/admission policy；
- probes；
- ConfigMap/Secret schema。

旧镜像和模型必须仍存在且已验证能在当前节点/驱动运行。回滚本身也可能产生冷启动和 GPU surge，必须演练。

## 18. 失败场景与故障树

### 18.1 新 Pod 一直 Pending

```text
GPU surge 容量是否足够？
 -> 单节点连续 GPU 是否足够
 -> quota/queue
 -> affinity/taint/topology
 -> PVC/zone
 -> 旧 Pod 是否因 maxUnavailable=0 不释放
```

### 18.2 新 Pod Running 但不 Ready

检查 startup、模型下载、CPU OOM、GPU OOM、TP rank、NCCL、probe path 和真实冷启动分布。

### 18.3 发布中 502/503

对齐 EndpointSlice conditions、网关 upstream、readiness 变化、终止时间和连接复用。检查旧 Pod 是否在 endpoint 传播前退出，
以及新 Pod 是否过早 Ready。

### 18.4 streaming 响应中断

检查 drain deadline、网关 idle/read timeout、客户端取消传播、Pod 强制退出和 sidecar 顺序。普通短 health test 无法覆盖。

### 18.5 新版本延迟变差但错误率正常

对比请求 Token 分布、queue、KV Cache、TP、GPU kernel、量化和输出长度。输出变长本身会提高端到端延迟，必须看 TPOT 与长度归一指标。

### 18.6 回滚也 Pending

可能是旧节点 cache 已清、旧镜像不可用、GPU 被新 Pod 占用或 maxSurge 策略锁住。Blue/Green 切换比重新拉起旧版本更快，但需要额外容量。

## 19. 发布观测面板

同一时间线展示：

```text
Deployment desired/updated/available
ReplicaSet/Pod revision
Pending/Ready/restart
EndpointSlice ready/serving/terminating
网关新旧版本流量
5xx/429/timeout
TTFT/TPOT/queue
GPU HBM/SM/Xid
模型下载/启动阶段
发布事件与人工操作
```

所有指标必须有 `release/model_revision/pod/node` 等可关联 label，但避免把高基数字段无控制写入 Prometheus。

## 20. 安全实验

### 实验一：GPU 不足导致 rollout 卡住

在测试环境设置 `maxUnavailable=0,maxSurge=1` 且无额外 GPU，观察新 Pod Pending 和 rollout status，再验证批准的解锁方案。

### 实验二：慢冷启动

使用冷缓存节点发布，验证 startup 与 progress deadline，记录每阶段耗时。

### 实验三：流量排空

启动长 streaming 请求后删除测试 Pod，观察 EndpointSlice、SIGTERM、响应是否完成以及最终退出时间。

### 实验四：Canary 性能回归

人为使用较低并发配置部署测试 Canary，验证门禁能检测 queue/TTFT 回退并停止晋级。

### 实验五：质量回归

使用已脱敏测试集让 Canary 返回格式差异，验证质量门禁而非只看 HTTP 200。

### 实验六：完整回滚

从 25% 流量回滚镜像、模型、配置和路由，验证旧制品、启动时间和 SLO。

## 21. 生产验收

- [ ] 发布单元有不可变 manifest；
- [ ] GPU、节点碎片、存储和 cache surge 已计算；
- [ ] 冷/热启动 P99 与 progress deadline 匹配；
- [ ] startup/readiness/liveness 语义正确；
- [ ] EndpointSlice termination 和网关行为已实测；
- [ ] 应用正确处理 SIGTERM、drain 和 streaming；
- [ ] Canary 覆盖质量、SLO、资源和成本；
- [ ] 每阶段有 Pass/Fail/Unknown 与停止条件；
- [ ] 回滚覆盖完整发布单元；
- [ ] 旧模型/镜像在回滚窗口内保留；
- [ ] GPU 不足、加载失败、流式终止和回滚演练通过。
