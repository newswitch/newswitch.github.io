# 大模型推理服务性能指标设计

推理服务「能不能跑」靠探针；「好不好、卡不卡」靠指标。vLLM 在 OpenAI 兼容 API 服务上暴露 **`/metrics`**（Prometheus 格式）。本文整理自官方 [Production Metrics](https://docs.vllm.ai/en/stable/usage/metrics/)，并按运维视角归类：延迟、吞吐、排队、KV Cache、前缀缓存等。部署见 [第 23 篇](./01-Kubernetes%20部署%20vLLM%20推理服务.md)；与 DCGM / Grafana 关联见后续监控篇。

---

## 1. 怎么拿到指标

启动服务（本机或容器内）：

```bash
vllm serve unsloth/Llama-3.2-1B-Instruct
```

拉取：

```bash
curl http://0.0.0.0:8000/metrics
```

示例片段：

```text
# HELP vllm:iteration_tokens_total Histogram of number of tokens per engine_step.
# TYPE vllm:iteration_tokens_total histogram
vllm:iteration_tokens_total_sum{model_name="unsloth/Llama-3.2-1B-Instruct"} 0.0
...
```

K8s 中可对 Service 做 port-forward，或用 ServiceMonitor / PodMonitor 抓取容器 8000 端口的 `/metrics`。

---

## 2. 业务侧先记住的几个概念

| 概念 | 含义 | vLLM 对应（常见） |
|------|------|-------------------|
| **TTFT** | Time To First Token，首 token 延迟 | `vllm:time_to_first_token_seconds` |
| **TPOT / ITL** | 每输出 token 间隔 | `vllm:time_per_output_token_seconds`、`vllm:inter_token_latency_seconds` |
| **E2E** | 端到端请求延迟 | `vllm:e2e_request_latency_seconds` |
| **排队** | 进不了执行批 | `vllm:num_requests_waiting`、`request_queue_time_seconds` |
| **吞吐** | prompt / generation tokens | `vllm:prompt_tokens`、`vllm:generation_tokens` |
| **KV 占用** | 显存侧缓存压力 | `vllm:kv_cache_usage_perc`（1 = 100%） |

看板设计建议：先看 **waiting + TTFT + kv_cache_usage**，再下钻 prefill/decode 分段时间。

## 3. 通用指标一览（官方表整理）

下列名称以文档为准；版本升级可能增减，废弃策略见文末。

### 3.1 Counter（累计）

| 指标 | 说明 |
|------|------|
| `vllm:prompt_tokens` | Prefill 处理的 token 数 |
| `vllm:prompt_tokens_by_source` | 按来源统计的 prompt tokens |
| `vllm:prompt_tokens_cached` | 命中缓存的 prompt tokens（本地 + 外部） |
| `vllm:generation_tokens` | 生成侧 token 数 |
| `vllm:request_success` | 成功处理的请求数 |
| `vllm:num_preemptions` | 引擎抢占累计次数 |
| `vllm:prefix_cache_hits` / `prefix_cache_queries` | 前缀缓存命中 / 查询（token 数） |
| `vllm:external_prefix_cache_hits` / `queries` | 跨实例 KV connector 外部前缀缓存 |
| `vllm:mm_cache_hits` / `mm_cache_queries` | 多模态缓存 |
| `vllm:corrupted_requests` | logits 出现 NaN 的损坏请求数 |

### 3.2 Gauge（瞬时）

| 指标 | 说明 |
|------|------|
| `vllm:num_requests_running` | 当前在执行批里的请求数 |
| `vllm:num_requests_waiting` | 等待处理的请求数 |
| `vllm:num_requests_waiting_by_reason` | 按原因拆分：`capacity`（调度容量）、`deferred`（LoRA / KV transfer 等瞬时约束）；各 reason 之和 = waiting |
| `vllm:kv_cache_usage_perc` | KV Cache 使用率，1 表示 100% |
| `vllm:lora_requests_info` | LoRA 请求相关统计 |
| `vllm:engine_sleep_state` | Sleep 状态：`awake=0` 休眠；`awake=1` 醒着；`weights_offloaded=1` 为 sleep level 1；`discard_all=1` 为 level 2 |

### 3.3 Histogram（分布）——延迟与请求形态

| 指标 | 说明 |
|------|------|
| `vllm:time_to_first_token_seconds` | TTFT |
| `vllm:inter_token_latency_seconds` |  token 间隔延迟 |
| `vllm:request_time_per_output_token_seconds` | 单请求 TPOT |
| `vllm:e2e_request_latency_seconds` | 端到端延迟 |
| `vllm:request_queue_time_seconds` | WAITING 阶段耗时 |
| `vllm:request_prefill_time_seconds` | PREFILL 阶段耗时 |
| `vllm:request_decode_time_seconds` | DECODE 阶段耗时 |
| `vllm:request_inference_time_seconds` | RUNNING 阶段耗时 |
| `vllm:request_prompt_tokens` | 单请求 prefill tokens |
| `vllm:request_generation_tokens` | 单请求 generation tokens |
| `vllm:request_prefill_kv_computed_tokens` | Prefill 新计算的 KV token（不含已缓存） |
| `vllm:request_max_num_generation_tokens` | 请求的最大生成长度分布 |
| `vllm:request_params_max_tokens` / `request_params_n` | 参数 `max_tokens`、`n` 分布 |
| `vllm:iteration_tokens_total` | 每个 engine_step 的 token 数 |

### 3.4 KV Block 采样指标

需配合 `--kv-cache-metrics-sample` 等采样控制：

| 指标 | 说明 |
|------|------|
| `vllm:kv_block_idle_before_evict_seconds` | 驱逐前空闲时间 |
| `vllm:kv_block_lifetime_seconds` | 从分配到驱逐的生命周期 |
| `vllm:kv_block_reuse_gap_seconds` | 连续访问间隔（ring buffer 记最近访问） |

## 4. 专项指标

### 4.1 Speculative Decoding

| 指标 | 说明 |
|------|------|
| `vllm:spec_decode_num_accepted_tokens_per_pos` | 各 draft 位置接受的 token 数 |

### 4.2 NIXL KV Connector

跨实例 KV 传输场景：失败通知 / 传输、过期请求（P 侧）、字节与耗时直方图等（`vllm:nixl_*`）。做 Prefill/Decode 分离或远程 KV 时再重点盯。

### 4.3 MFU（Model Flops Utilization）

需 `--enable-mfu-metrics`：

| 指标 | 说明 |
|------|------|
| `vllm:estimated_flops_per_gpu_total` | 每 GPU 估算 FLOPs |
| `vllm:estimated_read_bytes_per_gpu_total` | 每 GPU 估算读字节 |
| `vllm:estimated_write_bytes_per_gpu_total` | 每 GPU 估算写字节 |

## 5. 推荐指标分层（设计看板时）

### L1 业务健康（告警优先）

- `num_requests_waiting` 持续升高  
- `kv_cache_usage_perc` 长期接近 1  
- `e2e_request_latency_seconds` / TTFT P99 恶化  
- `request_success` 增速骤降或 `corrupted_requests` 非零  

### L2 容量与调度

- `num_requests_running` vs 配置的 max batch / 并发  
- `waiting_by_reason{reason="capacity"}`  
- `num_preemptions` 上升（可能在挤 KV）  

### L3 效率与优化

- 前缀缓存命中率 ≈ `prefix_cache_hits / prefix_cache_queries`  
- Prefill vs Decode 时间比  
- `iteration_tokens_total`（批效率）  
- 多实例时看 external prefix / NIXL  

### L4 与 GPU 层对齐

把 vLLM 指标与 DCGM（利用率、显存、SM）对照：例如 **KV 满但 SM 低** → 常是缓存/调度瓶颈而非算力打满。详见后续 [大模型业务指标与 GPU 指标关联](../../../sre/observability/gpu/05-大模型业务指标与%20GPU%20指标关联分析.md)。

## 6. Prometheus 抓取示意

```yaml
# ServiceMonitor 概念示例（按集群 CRD 调整）
apiVersion: monitoring.coreos.com/v1
kind: ServiceMonitor
metadata:
  name: vllm
spec:
  selector:
    matchLabels:
      app: mistral-7b   # 与 Service 标签一致
  endpoints:
    - port: http-mistral-7b
      path: /metrics
      interval: 15s
```

若 Service 的 port 名不同，改 `port` 字段；仅 ClusterIP 时确保 Prometheus 所在网络能访问。

Production Stack 自带路由与看板能力，多副本时优先在 Router / 各引擎上分别抓指标，再做聚合。

---

## 7. 废弃策略（跟版本升级）

官方约定：指标在版本 `X.Y` **标记废弃** → `X.Y+1` **默认隐藏**（可用 `--show-hidden-metrics-for-version=X.Y` 临时打开）→ `X.Y+2` **移除**。

升级 vLLM 后若 Grafana 面板空了，先查 release note / 该 escape hatch，再改看板。

## 8. 小结

| 目标 | 先看哪些 |
|------|----------|
| 用户是否卡顿 | TTFT、E2E、ITL/TPOT |
| 是否该扩容 | waiting、kv_cache_usage、running |
| 缓存是否生效 | prefix_cache_hits/queries |
| 分段耗时 | queue / prefill / decode / inference histograms |

下一篇可结合探针与滚动升级，把「指标恶化 → 扩容 / 限流 / 缩上下文」做成运维手册；监控告警模板见第 39 篇规划。
