# 模型服务启动成功后的标准验收流程

看到下面的日志只能说明 Web Server 开始监听：

```text
Application startup complete
Uvicorn running on http://0.0.0.0:8000
```

它不能证明加载的是正确模型、推理结果正确、流式连接完整、边界输入可用或 Kubernetes Service 已经接通。
标准验收应从进程逐层推进到真实业务。

## 1. 验收分为六道门

```text
G1 进程与容器稳定
→ G2 模型身份和配置正确
→ G3 健康与就绪正确
→ G4 功能与结果正确
→ G5 边界、并发和资源安全
→ G6 发布、故障恢复和回滚可用
```

任何一道门失败，都不能用后一道门的偶然成功掩盖。例如短请求成功不能替代长上下文验收。

## 2. 验收前固定环境清单

先保存：

| 项目 | 示例内容 |
|---|---|
| 镜像 | 仓库、Tag、Digest |
| 模型 | 名称、Revision、权重校验值 |
| 硬件 | GPU/NPU 型号、数量、拓扑 |
| 软件栈 | Driver、CUDA/CANN、PyTorch、框架 |
| 参数 | dtype、量化、上下文、并行、缓存 |
| API | 协议、端口、鉴权、模型别名 |
| Kubernetes | Namespace、Workload、Service、探针 |

没有这张清单，测试通过也难以复现。

## 3. G1：进程和容器稳定

验收内容：

- 进程数量符合架构。
- 所有 Worker 和 Rank 存在。
- 容器重启次数不增长。
- 启动后观察窗口内没有异常退出。
- 没有持续编译、重复加载或错误重试风暴。
- CPU 内存、设备显存和临时磁盘稳定。

Kubernetes 检查：

```bash
kubectl get pod <pod> -n <ns> -o wide
kubectl get pod <pod> -n <ns> \
  -o jsonpath='{range .status.containerStatuses[*]}{.name}{" restart="}{.restartCount}{" ready="}{.ready}{"\n"}{end}'
kubectl logs <pod> -n <ns> --since=10m --timestamps
```

观察窗口要覆盖一次完整启动和多笔请求，不应在出现 Ready 的同一秒就结束。

## 4. G2：验证模型身份

服务能输出文本，但可能加载错了模型或模型别名。需要验证：

- API 返回的模型 ID。
- 运行日志中的真实模型路径。
- 模型别名和客户端请求名称是否匹配。
- dtype、量化和最大上下文是否符合发布清单。
- TP/PP/DP/EP 和设备数量是否符合预期。
- Tokenizer、Chat Template 与模型版本是否一致。

OpenAI 兼容接口通常可以查询：

```bash
curl --fail --silent --show-error \
  http://127.0.0.1:8000/v1/models | jq
```

不能只比较展示名称；应把接口、日志、模型 Manifest 和镜像配置交叉验证。

## 5. G3：区分 Live、Ready 和业务健康

| 检查 | 应回答的问题 | 失败后的动作 |
|---|---|---|
| Live | 进程是否不可恢复地失去工作能力 | 必要时重启 |
| Ready | 当前实例是否能接收新请求 | 从流量端点摘除 |
| Startup | 冷启动是否在允许窗口内推进 | 超时后判定启动失败 |
| Business Smoke | 真实模型链路是否返回正确 | 阻止发布或告警 |

健康接口应低成本、快速，不应每几秒执行完整生成；完整业务 Smoke 可以由发布流水线或低频探测执行。

## 6. G4：最小功能请求

OpenAI Chat 兼容接口示例：

```bash
curl --fail --silent --show-error \
  http://127.0.0.1:8000/v1/chat/completions \
  -H 'Content-Type: application/json' \
  -d '{
    "model": "Qwen",
    "messages": [{"role": "user", "content": "只回答数字：1+1等于几？"}],
    "temperature": 0,
    "max_tokens": 8
  }' | jq
```

检查：

- HTTP 状态码。
- 响应 `model` 身份。
- `choices` 是否存在。
- Finish Reason 是否合理。
- Usage 中输入和输出 Token 是否非负、合理。
- 响应时间是否在冒烟基线内。
- 服务日志能否用 Request ID 关联。

生成模型不是确定性计算器。正式正确性验收应使用固定评测集和可接受阈值，而不是只依赖这一条问题。

## 7. Chat Template 和 Tokenizer 验收

重点测试：

- System、User、Assistant 多轮角色。
- 中文、英文和特殊字符。
- 空内容、超长内容和非法角色。
- Stop Token 与 EOS。
- 工具调用或 Reasoning Parser（如果启用）。
- 模型不支持的参数是否明确拒绝。

常见问题是基础 Completion 正常，但 Chat Template 使用错误，导致模型重复角色标记、无法停止或回答质量异常。

## 8. 流式接口验收

```bash
curl --no-buffer --fail --show-error \
  http://127.0.0.1:8000/v1/chat/completions \
  -H 'Content-Type: application/json' \
  -d '{
    "model": "Qwen",
    "messages": [{"role": "user", "content": "用三句话介绍KV Cache"}],
    "stream": true,
    "max_tokens": 128
  }'
```

检查：

- 首个事件是否在 TTFT 阈值内。
- 每个 SSE 事件格式是否完整。
- UTF-8 多字节字符是否被错误截断。
- 最终结束标记是否到达。
- 客户端主动断开后，服务是否释放请求和 KV Cache。
- Ingress、网关和代理是否错误缓存或缓冲流式响应。

只测试非流式接口会遗漏代理缓冲、连接超时和取消请求泄漏。

## 9. 边界输入验收

至少覆盖：

| 场景 | 目的 |
|---|---|
| 空或最短输入 | 参数和模板边界 |
| 典型 Token 分布 | 业务基线 |
| 接近最大上下文 | 长度、KV 和 Prefill 峰值 |
| 超过最大上下文 | 应明确拒绝，不应 OOM |
| 最大输出长度 | Decode、超时和取消 |
| 多模态最大图片/视频 | Encoder、Token 预算和显存 |
| 非法 JSON/参数 | API 错误是否清晰 |

客户端字符数不等于 Token 数。长上下文验收应记录 Tokenizer 后的实际 Token。

## 10. 资源验收

记录三个状态：

```text
启动前
启动后空闲
代表性请求与边界请求峰值
```

至少观察：

- CPU 使用率和 RSS。
- GPU/NPU 利用率和显存/HBM。
- 磁盘、模型读取和临时目录。
- 网络与多卡通信。
- KV Cache 使用率和抢占。
- 请求队列与运行请求数。

启动后显存稳定不代表边界 Prefill 不会出现激活峰值。

## 11. 小规模并发验收

冒烟阶段不需要立即压到极限，但应至少验证：

```text
并发 1
→ 小并发阶梯
→ 目标发布流量的一小部分
```

观察 TTFT、TPOT/ITL、端到端延迟、吞吐、错误率、队列和显存。性能命令见
[推理服务命令参考库](../commands/00-推理服务命令参考库.md)。

理论 KV 并发不是业务并发。验收阈值要以真实输入/输出 Token 分布和 SLO 为准。

## 12. Kubernetes 服务链路验收

逐级测试：

```text
容器 localhost
→ Pod IP
→ Service ClusterIP
→ Ingress / Gateway
→ 外部调用方
```

检查 EndpointSlice：

```bash
kubectl get endpointslice -n <ns> \
  -l kubernetes.io/service-name=<svc> -o wide
```

如果 localhost 成功、Service 失败，重点不再是模型权重，而是标签选择器、端口、网络策略或代理。

## 13. 故障和恢复验收

生产发布至少验证：

- 终止一个空闲副本，流量是否转移。
- 终止一个正在处理请求的副本，客户端是否得到明确结果或可重试错误。
- Pod 重建后能否在启动窗口内 Ready。
- 模型存储短暂变慢时是否触发重启风暴。
- 一个 GPU/NPU 不健康时是否停止调度并告警。
- 多卡实例中单个 Worker 退出后，整体是否明确失败并恢复。
- 回滚到旧镜像和模型需要多长时间。

故障注入应在隔离环境或受控灰度中执行。

## 14. 安全验收

- 未授权请求是否被拒绝。
- 模型 API 是否意外暴露到公网。
- 请求体、上下文、输出和并发是否有限制。
- 错误响应是否泄露本地模型路径、Token 或内部堆栈。
- 日志是否记录敏感 Prompt/文档。
- 管理和指标接口是否有独立访问控制。

## 15. 发布门禁表

| 门禁 | 通过条件 | 证据 |
|---|---|---|
| 环境一致 | 版本与 Manifest 一致 | 环境指纹 |
| 模型身份 | 模型、Tokenizer、参数正确 | API + 日志 + 校验值 |
| 启动 | 冷启动在窗口内 | 多次启动统计 |
| 功能 | 代表性测试集通过 | 测试报告 |
| 边界 | 最大支持输入稳定，超限明确拒绝 | 边界报告 |
| 性能 | 小规模与目标容量满足 SLO | 压测报告 |
| 可靠性 | 重启、摘流、回滚可用 | 演练记录 |
| 安全 | 认证、限流、日志策略通过 | 安全检查 |

## 16. 验收结论模板

```markdown
## 发布对象
镜像、模型、设备、参数、并行配置

## 通过项
进程、身份、健康、功能、边界、资源、服务链路

## 未通过项
现象、影响、证据、负责人、截止时间

## 已知风险
触发条件、监控、临时措施、回滚条件

## 结论
允许发布 / 限制性发布 / 禁止发布
```

验收的价值是把“我这里能调用”变成可复现、可审计、可回滚的发布结论。
