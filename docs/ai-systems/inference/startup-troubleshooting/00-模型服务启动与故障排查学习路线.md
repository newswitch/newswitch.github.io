# 模型服务启动与故障排查学习路线

本模块不绑定某一种模型或推理框架。目标是面对 vLLM、vLLM-Ascend、SGLang、MindIE、
Triton 或上层业务服务的启动日志时，能够还原启动阶段、识别风险并设计下一步验证。

```text
容器与 Kubernetes
→ Python 环境和动态库
→ 模型制品与配置
→ 推理框架参数
→ CUDA / CANN 与分布式通信
→ 权重加载
→ 编译、Kernel 与 Graph
→ 显存和 KV Cache
→ API 监听、就绪探针与真实请求
```

## 2. 案例使用方式

`cases/` 保存真实日志案例。案例用于练习通用方法，不代表需要系统学习对应的业务产品。
阅读案例时依次回答：

1. 服务是否真正成功启动？
2. 日志覆盖了哪些阶段，缺少哪些阶段？
3. 第一条需要行动的异常是什么？
4. 权重、编译、缓存和通信分别消耗了多少时间与资源？
5. 下一步需要执行什么验证，才能关闭风险？

## 3. 学习完成标准

给出一份陌生模型服务日志后，能够在不猜测的前提下：

- 画出进程、Worker、Rank 和设备关系。
- 定位当前处于配置、运行时、权重、编译、显存、通信还是 API 阶段。
- 区分致命错误、容量风险、性能回退、弃用警告和正常信息。
- 用日志重建启动耗时与显存预算。
- 给出最小验证命令、对照实验和 Kubernetes 处置方案。
- 明确哪些结论已有证据，哪些仍需真实请求或压力测试验证。
