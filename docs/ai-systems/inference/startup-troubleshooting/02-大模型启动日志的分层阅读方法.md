# 大模型启动日志的分层阅读方法

启动日志不是从上往下“看到 ERROR 就搜索”。一份日志可能混合 API Server、EngineCore、Worker、
Rank、容器运行时和日志平台输出，同一故障还可能产生几十条连锁异常。

稳定的方法是建立五个维度：

```text
时间：什么时候开始、在哪个阶段停止
进程：哪一个组件、PID、Worker 或 Rank 输出
阶段：配置、设备、通信、权重、编译、显存还是 API
资源：CPU、内存、磁盘、GPU/NPU、网络
严重性：致命、风险、回退、弃用还是正常信息
```

## 1. 先保存原始证据

不要直接复制终端最后几十行。需要同时保存：

- 完整启动命令和环境变量。
- 容器镜像 digest。
- 模型目录、版本和文件摘要。
- Pod 当前日志与上一次容器日志。
- Pod Spec、状态、事件和退出码。
- 节点、设备、驱动与运行时版本。
- 故障开始和恢复的准确时间。

在 Kubernetes 中可以先收集：

```bash
kubectl get pod <pod> -n <ns> -o yaml
kubectl describe pod <pod> -n <ns>
kubectl logs <pod> -n <ns> --all-containers --timestamps
kubectl logs <pod> -n <ns> --all-containers --previous --timestamps
kubectl get events -n <ns> --sort-by=.lastTimestamp
```

如果容器反复重启，`--previous` 往往比当前日志更重要。

## 2. 第一步：统一时间轴

常见日志可能同时包含：

```text
日志平台时间：2026-08-20T02:28:30Z
应用时间：    08-20 10:28:30
```

前者可能是 UTC，后者可能是 Asia/Shanghai。两者相差八小时不代表服务卡住八小时。

统一时间时记录：

| 字段 | 内容 |
|---|---|
| 日志时区 | UTC / 本地时区 / 未知 |
| 节点时钟 | 是否同步 |
| 容器启动时间 | `status.containerStatuses[].state.running.startedAt` |
| 应用第一行日志 | 进程开始输出的时间 |
| 引擎 Ready | 模型引擎可接受请求的时间 |
| Pod Ready | Readiness 成功的时间 |

没有时间戳的多行堆栈要归属到其前面的首行异常，不要把每一行当作独立事件。

## 3. 第二步：识别日志发出者

给每行日志补上逻辑身份：

```text
[kubelet]       容器和探针
[api pid=21]    HTTP Server
[engine pid=59] EngineCore
[worker rank=0] GPU/NPU Worker
[worker rank=1] GPU/NPU Worker
```

重点提取：

- PID、PPID 和进程名。
- Rank、Local Rank、World Size。
- 节点名、Pod 名和容器名。
- 物理设备 ID 与容器内逻辑设备 ID。

如果只有 `rank=3` 报错，其他 Rank 的“connection closed”通常是后果。根因要回到最先异常的 Rank。

## 4. 第三步：给每行日志标注阶段

推荐使用固定阶段编号：

| 编号 | 阶段 | 常见关键词 |
|---:|---|---|
| S0 | 容器与进程 | `entrypoint`、`exec`、`permission`、`signal` |
| S1 | Python 与依赖 | `import`、`module`、`undefined symbol` |
| S2 | 参数与模型配置 | `config`、`tokenizer`、`architecture` |
| S3 | 设备运行时 | `CUDA`、`CANN`、`device`、`context` |
| S4 | 分布式通信 | `rank`、`world_size`、`NCCL`、`HCCL`、`Gloo` |
| S5 | 权重加载 | `safetensors`、`shard`、`load weights` |
| S6 | Profiling 与显存 | `memory`、`KV cache`、`block`、`OOM` |
| S7 | 编译与 Graph | `Dynamo`、`Inductor`、`Triton`、`capture` |
| S8 | API 与路由 | `Uvicorn`、`listen`、`route`、`ready` |
| S9 | 预热与验收 | `warmup`、健康接口、真实请求 |

先找到最后一个完成的阶段，再看下一个阶段为什么没有完成。这比从尾部堆栈猜根因稳定得多。

## 5. 第四步：对消息进行行动分级

日志级别不等于行动级别。可以使用下面的分类：

| 行动级别 | 含义 | 示例 |
|---|---|---|
| Fatal | 当前启动无法继续 | 权重缺失、设备初始化失败、OOM |
| Risk | 当前能启动，边界输入可能失败 | 最大上下文小于多模态最坏预算 |
| Fallback | 使用兼容但较慢的路径 | FlashAttention 回退到 XFormers |
| Deprecated | 当前可用，未来版本可能移除 | 旧包或旧环境变量警告 |
| Info | 正常阶段信息 | 单卡 Rank 连接 0 个 Peer |

不要把所有 `WARNING` 都升级为事故，也不要因为没有 `ERROR` 就忽略容量风险。

## 6. 第五步：寻找第一条异常，而不是最后一条异常

一个多进程故障经常这样传播：

```text
Rank 2：CUDA out of memory           ← 首个资源根因
Rank 0：collective operation timeout  ← 等不到 Rank 2
API：EngineCore died                 ← 引擎子进程退出
Uvicorn：startup failed              ← 上层无法就绪
Kubernetes：Back-off restarting      ← 容器反复重启
```

最后一行最接近用户看到的现象，但第一条异常才最接近根因。

寻找第一条异常时：

1. 按统一时间排序所有进程日志。
2. 去掉相同堆栈和连接关闭噪声。
3. 标记每个 Rank 的第一条异常。
4. 判断异常发生前最后一个成功阶段。
5. 用系统证据验证，而不是只搜索错误文本。

## 7. 区分“卡住”和“正在工作”

编译、权重读取和 Graph 捕获可能长时间没有日志。判断是否卡住，要观察进展证据：

| 观察 | 仍在工作 | 可能卡住 |
|---|---|---|
| CPU | 编译进程持续使用 CPU | 所有相关线程长期无活动 |
| 磁盘 | 权重读取量持续增长 | I/O 无进展且进程等待异常 |
| GPU/NPU | 显存或利用率按阶段变化 | 固定状态超过历史上限 |
| 缓存目录 | 文件持续创建或更新时间变化 | 无变化且堆栈停在同一锁点 |
| Rank | 所有 Rank 逐步完成 | 某个 Rank 消失，其他 Rank 等待 |

关键是和相同镜像、模型、设备的正常启动基线比较。没有基线时，只能说“超过当前观察窗口”，
不能立即断言死锁。

## 8. 建立假设—证据—实验表

每个排障方向都写成可证伪假设：

| 假设 | 支持证据 | 反对证据 | 下一步实验 |
|---|---|---|---|
| 模型文件损坏 | 某分片读取报错 | 同一文件在另一节点成功 | 校验 SHA-256、换只读副本 |
| GPU 显存不足 | 首个异常是 OOM | 启动前显存充足 | 降上下文/并发做单变量实验 |
| 编译缓存损坏 | 只在复用缓存时失败 | 清缓存后成功 | 使用新隔离缓存目录对比 |
| 多卡通信异常 | 某 Rank 卡在集合通信 | 单卡启动正常 | 跑通信测试并检查网卡映射 |

一次只改变一个关键变量。重启后偶尔成功只能证明问题具有时序性或环境差异，不能证明根因消失。

## 9. 正常启动与异常启动做结构化 Diff

比较时不要直接用整份文本 `diff`，先提取稳定字段：

```text
镜像 digest
模型 revision 与校验值
启动参数和环境变量
节点、设备型号和逻辑设备映射
驱动、运行时、PyTorch、框架版本
TP/PP/DP/EP 与 world_size
权重加载、编译、Graph、Ready 耗时
启动前空闲显存与 KV Cache 容量
```

时间戳、PID、随机端口和缓存哈希属于易变字段，应先归一化再比较。

## 10. 日志缺失本身也是证据

例如正常日志应该出现：

```text
加载配置
→ 加载全部权重分片
→ 分配 KV Cache
→ Engine Ready
```

异常日志只出现第一片权重后进程直接退出，则要继续查：

- 容器退出码是否为 137。
- 节点内核是否发生 OOM Kill。
- 容器日志是否因为缓冲未刷盘而缺失。
- 磁盘、网络存储或进程是否被外部信号中断。

不要把“没有 Python Traceback”解释为“应用没有错误”。SIGKILL、节点故障和设备复位可能不给应用清理机会。

## 11. 一份标准排障记录应包含什么

```markdown
## 现象和影响
## 环境与版本
## 启动命令和关键配置
## 正常与异常时间线
## 首条异常及其阶段
## 假设、证据和排除过程
## 根因
## 临时恢复措施
## 永久修复
## 验证结果
## 监控和预防措施
```

如果根因尚未证实，就写“当前最可能原因”和缺失证据，不要为了让文章完整而伪造确定性。

## 12. 分钟日志分析清单 {/* #12-30-分钟日志分析清单 */}

前 5 分钟：

- 保存原始日志、Pod 状态、事件、命令和版本。
- 判断服务成功、失败、卡住还是反复重启。

第 5～15 分钟：

- 统一时区，识别进程、Rank 和最后完成阶段。
- 找到所有 Rank 的首条异常。

第 15～25 分钟：

- 检查设备、显存、模型分片、磁盘和通信证据。
- 与正常启动做结构化 Diff。

第 25～30 分钟：

- 给出一个最小、可回滚、单变量的验证实验。
- 记录风险，避免无证据地同时修改多个参数。

掌握这套方法后，产品名称会变化，但排障过程仍然稳定。
