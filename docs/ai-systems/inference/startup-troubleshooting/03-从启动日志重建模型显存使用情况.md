# 从启动日志重建模型显存使用情况

部署模型时最常见的误区是：

```text
模型参数量 × 数据类型字节数 = 需要的全部显存
```

这个公式只能估算权重主体。一个在线推理实例的设备内存还包含激活、KV Cache、通信缓冲、
CUDA/ACL Graph、编译工作区、运行时 Context、分配器保留和碎片。

本文关注如何从启动日志重建资源账本。vLLM 参数级容量计算可继续阅读
[vLLM GPU 显存组成与容量规划](../serving/02-vLLM%20GPU%20显存组成与容量规划.md)。

## 1. 先区分四个容量问题

| 问题 | 关注点 |
|---|---|
| 模型能否加载 | 权重和固定开销是否装得下 |
| 最大上下文能否运行 | 单请求激活与 KV 是否能容纳 |
| 能承载多少并发 | 所有活跃请求的 KV、激活和调度开销 |
| 峰值是否稳定 | 碎片、Graph、通信、异常输入和其他进程 |

“启动成功”只部分回答第一个问题。

## 2. 显存账本

```text
设备总内存
├── 驱动、Runtime 与 Context
├── 模型权重和量化元数据
├── 固定 Buffer
├── 峰值激活和临时 Tensor
├── 编译与 Kernel Workspace
├── CUDA Graph / ACL Graph 私有内存
├── NCCL / HCCL 通信缓冲区
├── KV Cache / Encoder Cache
├── 分配器保留、碎片和不可见开销
└── 安全余量
```

不同框架的日志字段不同，但最终都能映射到这些类别。

## 3. 权重主体怎样估算

最粗略的公式是：

```text
权重主体 ≈ 参数量 × 每参数字节数
```

| 数据类型 | 理论字节/参数 |
|---|---:|
| FP32 | 4 |
| FP16 / BF16 | 2 |
| INT8 | 1 |
| INT4 | 0.5 |

例如 7B BF16：

```text
7 × 10^9 × 2 Byte ≈ 14 GB ≈ 13.04 GiB
```

注意 GB 与 GiB 不相等。日志、厂商规格和监控工具可能使用不同单位。

实际权重还可能包含：

- 未量化的 Embedding、LM Head 或归一化层。
- INT4/INT8 的 Scale、Zero Point 和分组元数据。
- MoE 中未按预期切分或复制的参数。
- Adapter、LoRA 和多模态 Encoder。
- TP Rank 之间重复保存的小参数。
- 权重重排、对齐和后端私有格式。

所以理论值适合部署前筛选，启动日志和真实设备指标才适合验收。

## 4. 多卡后为什么不能简单除以卡数

对于 TP=4：

```text
每卡主体权重 ≈ 可切分权重 ÷ 4 + 每卡复制权重
```

并不是所有 Tensor 都沿同一维度切分。每张卡还拥有自己的：

- Runtime Context。
- KV Cache 分片。
- 激活和临时工作区。
- NCCL/HCCL 通信缓冲区。
- Graph 与 Kernel Workspace。

容量分析必须按 Rank 分别记录，不能只看四张卡显存总和。只要一张卡 OOM，整个模型实例都会失败。

## 5. KV Cache 是在线容量的主体变量

标准多头或分组查询注意力中，单 Token 的 KV 主体可近似写为：

```text
单 Token KV 字节
≈ 2 × 层数 × KV Head 数 × Head Dim × KV 元素字节数
```

其中 `2` 表示 Key 和 Value。所有请求的总 KV 近似为：

```text
总 KV ≈ 单 Token KV × 所有已缓存 Token 数
```

如果采用 TP、量化 KV、跨层共享、滑动窗口或混合架构，公式会变化，应以框架报告的 KV Block
大小和总 Token 容量校准。

理论并发通常按下面的方法计算：

```text
理论并发 ≈ KV Cache Token 容量 ÷ 每请求规划 Token 数
```

它没有计算排队、视觉 Encoder、CPU 预处理、算力和延迟 SLO，不能直接作为生产并发。

## 6. 激活和临时内存为什么会出现峰值

激活受以下因素共同影响：

- Prefill Token 数。
- Batch 中同时执行的 Token 数。
- Hidden Size、中间层大小和模型架构。
- Attention Backend 和 Kernel 实现。
- 多模态 Encoder 的图片数量与分辨率。
- Chunked Prefill 和最大批处理 Token。

框架常在启动时用最坏或代表性形状执行 Profiling，记录峰值激活，再把剩余空间交给 KV Cache。
如果 Profiling 的输入上限小于真实业务上限，启动成功后仍可能运行中 OOM。

## 7. `allocated`、`reserved` 和设备占用不是一回事

PyTorch Caching Allocator 常见三个口径：

```text
allocated：当前活跃 Tensor 正在使用
reserved：PyTorch 从设备申请并保留的内存池
device used：设备看到的进程总占用
```

通常：

```text
allocated ≤ reserved ≤ device used
```

差额可能来自空闲缓存块、碎片、CUDA Context、NCCL、Graph 或其他非 PyTorch 分配。
看到 `reserved` 很高不能直接判断泄漏，也不能只看 `allocated` 就认为还有大量可用空间。

## 8. 从日志提取哪些数字

建立下面的表：

| 字段 | 日志或命令来源 | 用途 |
|---|---|---|
| 设备总内存 | 启动日志、设备工具 | 总上限 |
| 启动前空闲 | Profiling 前日志 | 判断其他进程干扰 |
| 框架目标比例 | `gpu_memory_utilization` 等 | 框架预算 |
| 权重占用 | 模型加载完成日志 | 固定主体 |
| 非框架内存 | Profiling 日志 | Runtime/外部库估算 |
| 峰值激活 | Profiling 日志 | 单轮计算峰值 |
| Graph 内存 | Capture 日志 | 图模式固定开销 |
| 通信缓冲 | NCCL/HCCL 或设备差额 | 多卡固定/动态开销 |
| KV Cache | 缓存初始化日志 | 并发与长度预算 |
| 最终设备占用 | 设备监控 | 校验总账 |

框架没有输出的字段写“未知”，不要强行用总差额给它命名。

## 9. 一个通用重建示例

假设单卡总显存 80 GiB，框架目标使用比例 0.9：

```text
框架目标预算 = 80 × 0.9 = 72 GiB
```

启动日志给出：

| 项目 | 数值 |
|---|---:|
| 权重 | 31.5 GiB |
| 峰值激活 | 4.2 GiB |
| 非框架内存 | 1.8 GiB |
| Graph | 1.0 GiB |
| 已知固定与峰值 | 38.5 GiB |

理论剩余：

```text
72 - 38.5 = 33.5 GiB
```

框架最终只分配 31 GiB KV Cache，则约 2.5 GiB 差额可能是对齐、分配器、额外 Buffer 或安全保留。
在没有日志或 Profiling 证据前，不应把它全部归为“显存碎片”。

## 10. 启动 OOM 与运行中 OOM

### 10.1 启动 OOM

常发生在：

- 创建模型或加载权重。
- 权重格式转换或量化重排。
- 最坏形状 Profiling。
- 分配 KV Cache。
- CUDA/ACL Graph 捕获。

排查时先定位是哪一步 OOM。减少 KV Cache 对权重加载 OOM 没有帮助；禁用 Graph 也不会修复模型主体装不下。

### 10.2 运行中 OOM

常发生在：

- 输入超过 Profiling 假设。
- 并发或 Batch Token 突增。
- 多模态图片、视频超出常规规模。
- 某个 Kernel 临时工作区变大。
- 取消请求后资源没有及时释放。
- 同卡出现新进程或监控组件占用。

运行中 OOM 要关联请求长度、并发、调度批次和每张卡峰值，不能只保留 OOM 最后一行。

## 11. NVIDIA 与昇腾的验证命令

NVIDIA 环境：

```bash
nvidia-smi --query-compute-apps=pid,process_name,used_memory \
  --format=csv,noheader,nounits
nvidia-smi dmon -s pucm -d 1
```

昇腾环境：

```bash
npu-smi info
npu-smi info -t usages
```

设备工具负责观察进程和设备总量；框架日志负责解释权重、KV、激活等内部分类。两者需要结合，
不要互相替代。

## 12. 单变量容量实验

建议按下面顺序实验：

1. 固定模型、镜像和单请求，记录启动后空闲显存。
2. 逐级增加最大上下文，观察 KV 容量和 Profiling 峰值。
3. 固定长度，逐级增加并发。
4. 对比 Eager 与 Graph 模式。
5. 多卡时比较每个 Rank，而不是只看平均值。
6. 注入最大业务输入，确认仍保留安全余量。

每次只修改一个变量，否则无法判断容量变化来自哪里。

## 13. 最终交付物

一个可上线模型实例应有自己的显存基线表：

```text
模型、revision、dtype、量化
设备型号与单卡容量
TP/PP/DP/EP
上下文和批处理上限
权重、激活、Graph、通信、KV 和未知差额
空闲、典型、峰值显存
最大安全并发与对应 SLO
OOM 保护和降级策略
```

这张表比一句“80G 卡可以运行”更有复用价值。
