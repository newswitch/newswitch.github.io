# 大模型冷启动时间分析与优化

大模型冷启动不是一个数字。用户看到的“扩容需要五分钟”可能包含调度、拉镜像、挂载模型、加载权重、
编译、Graph 捕获、预热和探针周期。只优化其中最显眼的一段，整体时间可能几乎不变。

## 1. 先定义四种启动时间

| 指标 | 起点 | 终点 | 用途 |
|---|---|---|---|
| 进程启动时间 | 容器进程创建 | 应用开始执行 | 入口和依赖 |
| 引擎启动时间 | 创建推理引擎 | Engine Ready | 权重、编译、缓存 |
| Pod Ready 时间 | Pod 创建 | Readiness 成功 | Kubernetes 扩容 |
| 首个成功请求时间 | Pod 创建/发布 | 代表性请求完成 | 用户真正可用 |

还应区分：

- **完全冷启动**：节点无镜像、无模型、无 Page Cache、无编译缓存。
- **节点热启动**：镜像和模型已在节点，但进程全新。
- **编译缓存命中启动**：模型与编译产物已存在。
- **进程内首请求**：服务已 Ready，但某条 Shape 第一次执行。

不同条件的数字不能直接比较。

## 2. 端到端阶段分解

```text
T_ready =
  T_schedule
+ T_image_pull
+ T_sandbox
+ T_volume_mount
+ T_python_import
+ T_config
+ T_device_comm
+ T_weight_load
+ T_profile
+ T_compile
+ T_kv_allocate
+ T_graph_capture
+ T_warmup
+ T_probe_wait
```

部分阶段可以并行，公式用于建立账本，不表示所有实现都严格串行。

## 3. 怎样得到阶段时间

组合四类证据：

| 证据 | 能得到什么 |
|---|---|
| Pod Conditions 与 Event | 调度、拉镜像、挂载、容器创建 |
| 应用时间戳 | 配置、权重、编译、缓存、Ready |
| 设备和系统指标 | I/O、CPU、GPU/NPU、网络实际活动 |
| 探针与 EndpointSlice | 何时真正进入服务流量 |

推荐生成阶段表：

| 阶段 | P50 | P95 | P99 | 占总时间 | 波动原因 |
|---|---:|---:|---:|---:|---|
| 调度 | | | | | |
| 镜像 | | | | | |
| 模型挂载/下载 | | | | | |
| 权重加载 | | | | | |
| 编译与 Graph | | | | | |
| 预热与探针 | | | | | |

不要只测一次。冷启动容易受节点缓存、共享存储竞争和并发扩容影响。

## 4. 调度为什么可能是最大耗时

大模型 Pod 请求多张同型号加速器、CPU、内存和本地存储，调度等待可能远大于应用启动。

常见原因：

- 集群没有足够空闲 GPU/NPU。
- 资源碎片导致 TP=8 无法在同一节点满足。
- NodeSelector、亲和性和污点条件过严。
- 节点自动扩容需要创建新机器。
- PVC 拓扑限制与加速器节点冲突。

应用层无法优化 `Pending`。需要容量预留、资源池划分、占位 Pod、合理优先级或更合适的并行/副本设计。

## 5. 镜像拉取优化

大模型镜像可能包含 PyTorch、CUDA/CANN、编译器和推理框架，体积较大。

优化顺序：

1. 固定基础镜像，减少无关包和构建缓存层。
2. 让高复用依赖位于稳定层，业务代码位于上层。
3. 使用集群内高带宽镜像仓库和镜像缓存。
4. 在目标节点池预拉取经过验证的镜像 digest。
5. 避免把频繁更新的巨大模型权重塞进应用镜像。

预拉取缩短节点热启动，但不能替代完全冷启动和镜像仓库故障演练。

## 6. 模型分发优化

可选方式：

```text
共享文件系统直接读取
对象存储下载到节点缓存
DaemonSet/任务预分发到本地 NVMe
模型随镜像分发
```

主要权衡：

| 方案 | 启动速度 | 一致性 | 扩容风暴风险 |
|---|---|---|---|
| 本地 NVMe 缓存 | 快 | 需自行治理 | 低 |
| 共享文件系统 | 中等/依负载 | 集中 | 高 |
| 对象存储现拉 | 依网络和大小 | 版本清晰 | 高 |
| 镜像内置 | 取决于镜像缓存 | 强绑定 | 转移到镜像拉取 |

推荐把制品源和运行缓存分开：不可变制品库负责真相，本地缓存负责速度。缓存必须校验完整性后再原子发布。

## 7. 权重加载优化

先判断瓶颈是存储、CPU 反序列化、Host-to-Device 复制还是多 Rank 同步。

可能措施：

- 使用适合框架的 Safetensors 或优化加载格式。
- 避免不必要的 dtype 二次转换。
- 让每个 Rank 只读取需要的分片（框架支持时）。
- 控制多副本同时读取共享存储。
- 使用本地 NVMe 和热 Page Cache，但同时保留冷启动基线。
- 减少启动时在线模型下载和格式转换。

如果日志显示权重加载只占总时间 2%，继续优化磁盘没有价值。

## 8. 编译和 Graph 优化

编译可能占冷启动主体。优化方法：

- 固定镜像、模型、设备和 Shape，提升缓存可复用性。
- 按版本和设备架构隔离编译缓存。
- 在受控环境预生成或预热编译产物。
- 减少无业务价值的 Graph Capture Size。
- 避免每个扩容副本同时争抢 CPU 编译和共享缓存。
- 评估 Eager、Compile、Graph 的冷启动与稳态综合收益。

不能为了缩短启动直接关闭所有编译；这可能让 Decode 性能和单位请求成本长期变差。

## 9. 通信初始化优化

多卡/多机冷启动还包含 Rendezvous、拓扑发现和通信组创建。

重点检查：

- DNS、主地址和控制面网络是否稳定。
- 网卡选择和 RDMA 设备是否确定。
- 所有 Rank 是否同时拉起。
- 通信库是否反复探测不可用接口。
- 多机节点准备时间差是否让早到 Rank 长期等待。

如果某个 Worker 权重加载慢，其他 Worker 的 Barrier 时间会被记到通信阶段，需要结合每个 Rank 时间线拆分。

## 10. 预热应该覆盖什么

预热不是随便发一条“你好”。应覆盖生产常用路径：

- Chat Template 和 Tokenizer。
- 短 Prefill + Decode。
- 典型上下文长度。
- 流式响应。
- 常用 dtype、LoRA 或多模态路径。
- 常见 Batch/Shape Bucket。

预热太少会把编译或 Kernel 初始化转嫁给用户；预热太多又会延迟 Ready。需要按真实流量占比选择有限集合。

## 11. 探针周期也会增加可见启动时间

如果引擎在 61 秒就绪，Readiness 每 30 秒检查一次，Pod 可能到约 90 秒才进入 Endpoint。

优化时区分：

```text
引擎 Ready 时间
Pod Ready 时间
Endpoint 可用时间
```

适当缩短 Readiness 周期可以减少探针等待，但不能用过短超时和过低失败阈值制造负载或抖动。

## 12. 扩容不是单副本启动乘以副本数

同时扩容 N 个副本会竞争：

- 镜像仓库带宽。
- 模型存储带宽和元数据。
- 节点 CPU、磁盘和 Page Cache。
- 编译缓存锁与临时目录。
- GPU/NPU 节点库存。

必须做“扩容风暴”实验，例如同时启动 1、2、4、8 个副本，记录 P95 Ready 时间和失败率。

## 13. 冷启动怎样影响容量和 SRE

如果一个副本需要 8 分钟 Ready，基于分钟级流量突增的被动扩容通常来不及。需要组合：

- 保持最小热副本。
- 按历史流量预测扩容。
- 为 N-1 故障保留容量。
- 预留节点或加速器资源。
- 按排队、Token 速率和 SLO，而不是只按 GPU 利用率扩容。
- 让网关在过载时限流和降级。

相关容量设计见[多副本、N-1、冷启动与扩缩容容量规划](../vllm/22-多副本-N-1-冷启动与扩缩容容量规划.md)。

## 14. 优化实验设计

建立基线 A，然后一次修改一个变量：

| 实验 | 变量 | 其他条件 |
|---|---|---|
| A | 完全冷启动 | 固定 |
| B | 镜像预拉取 | 与 A 相同 |
| C | 模型本地缓存 | 与 B 相同 |
| D | 编译缓存命中 | 与 C 相同 |
| E | 调整 Graph Bucket | 与 D 相同 |
| F | 优化探针周期 | 与 E 相同 |

每个实验重复多次，记录 P50/P95/P99、失败率和稳态性能。不要用一次最快结果作为结论。

## 15. 常见错误优化

- 只看应用日志，忽略 Pod Pending 和镜像拉取。
- 使用热 Page Cache 数字承诺节点重启恢复时间。
- 多个 Pod 共享同一可写编译缓存而无隔离。
- 为减少 30 秒启动时间，牺牲所有请求的长期性能。
- 探针窗口比冷启动 P99 短，造成无限重启。
- 使用 `latest` 镜像，导致缓存和启动基线无法复现。
- 在线下载、转换并覆盖正在使用的模型目录。

## 16. 冷启动 SLO

可以按场景分别设定：

```text
进程重启恢复 P99
节点热启动 P99
新节点完全冷启动 P99
单副本故障到容量恢复时间
批量扩容到目标副本时间
首个成功业务请求时间
```

每个 SLO 都要有监控起点和终点。只有“启动慢”而没有定义，就无法判断优化是否有效。

## 17. 最终交付物

一份冷启动分析应包含：

```markdown
## 环境和启动类型
## 端到端时间线
## 各阶段 P50/P95/P99
## 最大耗时与最大波动阶段
## 单变量实验
## 优化前后对比
## 稳态性能和显存副作用
## 扩容风暴结果
## 冷启动 SLO 与回滚条件
```

真正有效的优化，是在不破坏正确性、稳定性和稳态性能的前提下，缩短用户感知的可用时间。
