# 多副本、N-1、冷启动与扩缩容容量规划

有了单副本 SLO 容量，还不能直接用 `峰值流量 ÷ 单副本容量` 得到副本数。生产集群必须覆盖：

- 一个副本或一个节点故障；
- 发布与维护；
- 流量突发；
- 新副本加载权重和编译；
- Prefix Cache 冷态；
- 路由不均与长请求 Drain；
- 扩缩容控制环延迟。

---

## 1. 基础副本数

假设：

```text
λ_peak = 目标峰值到达率
C_replica = 单副本满足 SLO 的安全容量
H = 额外业务/预测余量系数
```

基础估算：

```text
N_base = ceil(λ_peak × H / C_replica)
```

`C_replica` 必须来自上一章的真实联合 token 分布和 Open-loop 测试，不能使用理论最大 QPS。

如果不同请求 GPU 成本差异很大，更适合用 token/工作单元而不是请求率：

```text
work_rate
= prefill_compute_tokens/s
+ weighted_decode_tokens/s
```

权重要通过基准测试校准。

---

## 2. N-1 不只是多加一个 Pod

如果一个副本故障，剩余副本必须在 SLO 下承接全部目标流量：

```text
(N - 1) × C_replica ≥ λ_target
```

但若一个节点承载多个副本，真正故障域可能是节点、机架、交换机或可用区：

```text
N-k: 同一故障域同时失去 k 个副本
```

因此容量按最大可信故障域计算，而不是机械加 1。

同时验证：

- 故障探测与摘流时间；
- Gateway 是否把失败请求重试放大；
- 剩余副本 KV/queue 的瞬态；
- 长流式请求是否能重试；
- 新副本何时真正 Ready。

---

## 3. 冷启动时间分解

```text
T_ready
= T_schedule
+ T_image_pull
+ T_model_download_or_mount
+ T_weight_load
+ T_distributed_init
+ T_kv_profile_and_allocate
+ T_compile_and_cudagraph
+ T_warmup
+ T_endpoint_propagation
```

模型已在本地磁盘/内存缓存时与完全冷节点可能相差巨大。容量规划要保存至少三种分布：

- 热节点重启；
- 镜像热、模型冷；
- 新节点全冷。

Autoscaler 看到 waiting 后才创建 GPU Pod，如果 `T_ready` 为 10 分钟，它无法救当前 1 分钟流量尖峰。尖峰需要预留热容量、预测扩容或排队/降级共同处理。

---

## 4. Ready 不等于热缓存 Ready

新副本完成权重加载后可以服务，但 Prefix Cache 为空：

```text
新副本接入
→ 相同 System Prompt 重新 Prefill
→ 单请求计算成本高于旧副本
→ TTFT 与 GPU 负载短期上升
```

扩容控制要考虑冷态 `C_replica_cold`，它可能小于稳态 `C_replica_hot`。

策略：

- 上线前用安全请求 Warmup 常见 Shape；
- 逐步增加流量权重；
- 缓存感知但有界的路由；
- 将冷态 TTFT 纳入 Ready 后观察期；
- 不使用真实敏感 Prompt 做无隔离预热。

---

## 5. 为什么不能只按 GPU Util 扩容

GPU Util 低但 waiting 高可能来自 CPU/KV/路由；GPU Util 高但队列稳定也可能是高效健康状态。

更稳健的扩容信号组合：

```text
预测工作到达率
+ Engine queue time / waiting
+ KV 余量
+ TTFT burn rate
+ 每副本 token throughput
+ 冷启动时间
```

### 扩容触发

例如连续多个窗口满足：

- queue time 上升；
- 预测负载超过 N-1 安全容量；
- 不是单副本路由热点；
- 当前新副本数未超过启动预算。

### 缩容触发

需要更慢、更保守：

- 在长窗口低于安全水位；
- 缩容后仍满足 N-1；
- 目标副本已停止接新请求；
- 长流已 Drain 或达到最大等待；
- 不会造成 Prefix Cache 大规模抖动。

---

## 6. 扩缩容控制环

```text
观测负载/SLO
→ 估算未来 T_ready 后的工作量
→ 计算目标副本数
→ 限制单次扩容步长
→ 启动并验证 Ready
→ 小流量 Warmup
→ 提升路由权重
→ 继续观测
```

避免振荡：

- 扩容与缩容使用不同阈值；
- 缩容稳定窗口更长；
- 记录在途启动副本；
- 设置最小热副本；
- 发布期间冻结或调整 Autoscaler；
- 对预测误差设置余量。

---

## 7. Token 预算准入

Gateway 可以为请求估计工作量：

```text
estimated_work
= estimated_uncached_input_tokens × prefill_weight
+ max_or_expected_output_tokens × decode_weight
```

用途：

- 按副本 outstanding token 选择路由；
- 对极长请求单独排队；
- 在过载时拒绝/降级，而不是无限积压；
- 为租户建立 token bucket。

估算不能替代 Engine 实际状态。Tokenizer 前的估计可能不准，需要将 API 得到的真实 token 长度回传路由/观测系统校准。

---

## 8. 发布容量

滚动升级会同时出现：

- 旧副本 Drain；
- 新副本冷启动；
- 新旧版本容量/指标差异；
- Prefix Cache 重新变冷；
- 长流使旧 Pod 很久不能退出。

发布期间需满足：

```text
available_old + ready_new
在每个时刻都能承载目标流量 + 余量
```

配置：

- 合理 `maxUnavailable` / `maxSurge`；
- startup/readiness 与模型真正状态一致；
- PreStop 先摘流后 Drain；
- 最长生成时间与 termination grace 匹配；
- 新版本小流量验证 SLO 与错误后再扩大。

不能让 Autoscaler 把发布期的冷启动/Drain 误判为永久业务增长，或在发布后立即缩掉刚热起来的副本。

---

## 9. 故障演练场景

至少季度验证：

1. 杀死一个 Worker/TP 副本；
2. 下线一台 GPU 节点；
3. Gateway 到一个副本超时；
4. 新节点全冷扩容；
5. Prefix Cache 全冷；
6. 流量瞬时增加 50%～100%；
7. 长请求占满 KV；
8. 发布过程中同时失去一个故障域。

记录：探测、摘流、SLO、重试放大、扩容 Ready、恢复稳定各用了多久。

## 10. 成本模型

```text
cost_per_1k_tokens
= GPU_hour_price × allocated_GPU_count × time
  / completed_business_tokens × 1000
```

进一步区分：

- Prompt 与 Generation token；
- 热容量空闲成本；
- 冷启动无服务时间；
- 抢占重算/推测拒绝的内部 token；
- 失败/取消但已消耗的 GPU 时间。

降低副本数可能让 GPU Util 更高，却让 TTFT、N-1 和故障恢复失守。ROI 优化的约束首先是 SLO 与可靠性。
