# 大模型推理学习路线

## 1. 理解共同原理 {/* #第一阶段理解共同原理 */}

先学习[推理基础原理学习路线](./fundamentals/00-推理基础原理学习路线.md)，再从
[vLLM 与大模型推理学习路线](./vllm/00-vLLM学习路线.md)建立源码主线，重点掌握：

- [PyTorch、Transformers从模型目录到GPU Kernel的完整执行链路](./fundamentals/08-PyTorch-Transformers从模型目录到GPU-Kernel完整执行链路.md)。
- 请求从 HTTP、Tokenizer 到首个 Token 的生命周期。
- Prefill、Decode、KV Cache、Continuous Batching 和 PagedAttention。
- TP、PP、DP、EP 的通信与显存代价。

## 2. 掌握推理引擎与模型服务器 {/* #第二阶段掌握推理引擎与模型服务器 */}

各技术栈都使用相同的学习模板：架构与请求生命周期 → 参数与资源模型 → 性能与故障。学习时要先区分推理引擎和模型服务器：引擎负责执行模型与调度 Token，服务器负责协议、模型仓库、批处理和多模型管理；一个产品可能同时覆盖两层。

| 框架 | 学习入口 | 重点 |
|---|---|---|
| vLLM | [vLLM 学习路线](./vllm/00-vLLM学习路线.md) | V1 EngineCore、Scheduler、KVCacheManager、GPUModelRunner |
| vLLM-Ascend | [vLLM-Ascend 学习路线](./vllm-ascend/00-vLLM-Ascend学习路线.md) | Platform Plugin、NPUModelRunner、ACLGraph、CANN、HCCL |
| SGLang | [SGLang 学习路线](./sglang/00-SGLang学习路线.md) | Tokenizer/Scheduler/Detokenizer 管线、RadixAttention、Kernel Backend |
| MindIE | [MindIE 学习路线](./mindie/00-MindIE学习路线.md) | Server、LLM Manager、Text Generator、ATB/CANN |
| TensorRT-LLM | [TensorRT-LLM 学习路线](./tensorrt-llm/00-TensorRT-LLM从零到生产学习路线.md) | PyExecutor、Scheduler、KVCacheManager、Engine、Plugin 与量化 |
| Triton Inference Server | [Triton 学习路线](./triton-server/00-Triton-Inference-Server从零到生产学习路线.md) | Model Repository、Scheduler、Backend、Batcher、Ensemble 与实例组 |

完成后阅读[vLLM、vLLM-Ascend、SGLang、MindIE 框架对比与选型](./01-vLLM-vLLM-Ascend-SGLang-MindIE框架对比与选型.md)，把组件和参数映射到同一套 Prefill、Decode、KV、Graph 与 SLO 模型。

### 2.1 语音识别技术栈

[FunASR从零到生产学习路线](./funasr/00-FunASR从零到生产学习路线.md)单独介绍语音识别服务。它与上表的大语言模型推理引擎不是同一类框架，学习重点是音频格式、VAD、ASR、标点、ITN、离线/在线/两遍识别、流式会话、RTF和语音质量。部署时仍会复用PyTorch、CPU/GPU、Docker、Kubernetes、网关和可观测性等基础设施。

## 3. 掌握启动与故障排查 {/* #第三阶段掌握启动与故障排查 */}

进入[模型服务启动与故障排查学习路线](./startup-troubleshooting/00-模型服务启动与故障排查学习路线.md)，
把容器、Python、模型制品、加速器运行时、权重、编译、显存、通信和 API 就绪串成一条证据链。
真实日志按案例保存，不为单个业务模型重复建立一套通用原理。

## 4. 分析运行期性能与故障 {/* #第四阶段分析运行期性能与故障 */}

进入[模型服务运行期分析学习路线](./runtime-troubleshooting/00-模型服务运行期分析学习路线.md)，
用 Request ID 串联网关、API、Scheduler、Worker、Rank 和设备，把延迟拆成排队、Prefill、Decode、
KV Cache 与输出阶段，并建立取消、过载和引擎故障的处理闭环。

## 5. 构建生产服务控制面 {/* #第五阶段构建生产服务控制面 */}

先学习[KServe 从零到生产学习路线](./kserve/00-KServe从零到生产学习路线.md)，理解 `InferenceService`、`ServingRuntime`、`LLMInferenceService`、Gateway、EPP、LeaderWorkerSet 和扩缩容的职责边界；再进入 `serving/` 中的 Kubernetes 部署、显存容量、多卡部署、探针、优雅退出和指标体系。

至此可以用四层模型分析生产服务：

```text
KServe / Gateway / Autoscaler：服务控制面
→ Triton / vLLM API Server：协议、队列和模型服务
→ TensorRT-LLM / vLLM Engine：调度、KV Cache和模型执行
→ CUDA / CANN / GPU / NPU：Kernel、通信和设备
```

## 6. 掌握运维命令与容量验证 {/* #第六阶段掌握运维命令与容量验证 */}

进入[推理服务命令参考库](./commands/00-推理服务命令参考库.md)，依次掌握：

1. vLLM、vLLM-Ascend、SGLang、MindIE 与 Triton 服务端的模型、显存/HBM、并行和安全边界。
2. `curl`、`grpcurl` 对健康、模型身份、SSE完整性和gRPC协议分层验证。
3. `vllm bench`、GenAI-Perf、Perf Analyzer建立TTFT、ITL、吞吐和Goodput容量曲线。
4. Model Analyzer搜索候选配置，再用真实流量和SLO进行二次验证。

学习完成的标准不是“能启动 vLLM”，而是能根据模型、上下文长度、并发目标、
GPU 型号和 SLO 设计容量，并定位请求排队、OOM、NCCL 超时和尾延迟问题。
