# GPU 容量、利用率与多租户归因

“集群 GPU 利用率 80%”至少缺少三个信息：统计哪些设备、在什么时间范围、80% 测量的是什么。容量规划必须先定义分母；多租户优化则还要证明指标可以归因给谁。

前置阅读 [DCGM 指标](./01-DCGM%20Exporter%20GPU%20监控指标详解.md)与[业务关联](./05-大模型业务指标与%20GPU%20指标关联分析.md)。本篇不提供一组通用告警阈值，而是建立可检验的统计口径。

## 1. 五个数字分别回答五个问题

| 口径 | 回答的问题 | 典型反例 |
| --- | --- | --- |
| 物理库存 | 实际安装了多少、是什么型号 | 故障卡也仍在机箱里 |
| 可分配容量 | 当前允许交给工作负载多少 | 维护节点不参与调度 |
| 已分配资源 | 调度器已承诺给谁多少 | 分配后程序仍在下载模型 |
| 设备活动 | 采样窗口内硬件如何工作 | 通信或低效率 kernel 也会活动 |
| 有效产出 | 完成了多少满足约束的工作 | 重算很多但有效 step 很少 |

这五项不能互相代替。调度占满而设备很闲，可能需要分析启动与等待；设备很忙而有效产出低，则要分析重算、算子效率和业务结构。

“GPU_UTIL”也不等于峰值 FLOPS 的使用比例。DCGM 各字段有不同测量范围、单位和 entity 支持，解释前应查[字段定义](https://docs.nvidia.com/datacenter/dcgm/latest/dcgm-api/dcgm-api-field-ids.html)。某个窗口的活动率高，不代表计算单元、带宽、容量都已同时饱和。

## 2. 容量变化时，用资源时间作分母

教学例子：一小时内，前 30 分钟有 8 张同型号 GPU 可分配，后 30 分钟只有 4 张。可分配量为 `8×0.5+4×0.5=6 GPU·h`。如果两个阶段都占用 4 张，已分配量为 `4 GPU·h`，时间加权占用率是 `4/6≈66.7%`。

简单平均两个时刻的占用百分比得到 `(50%+100%)/2=75%`，与资源时间口径不同。两者并非数学上谁错了，而是分母不同；报告必须说明想衡量的是“时刻百分比平均”还是“资源时间占用”。

如果只统计健康在线的四张卡，可以得到很漂亮的利用率，却隐藏掉线损失。因此同时报告物理库存时间、可分配资源时间和维护/故障损失，才能防止通过缩小分母“优化”数字。

## 3. 型号不同，不要把卡数直接当计算能力

两种 GPU 各一张，不代表可交换的两份算力。显存、精度支持、带宽、互连和模型形状都会影响有效容量。异构集群可以按型号分别报告卡时，再用固定代表工作负载建立业务等价容量。

等价容量也是有条件的：模型、批量、上下文长度或并行方式改变后，原来的换算系数可能失效。不要用理论峰值 FLOPS 给所有训练与推理任务套一把统一尺子。

## 4. 共享 GPU 的标签关联不等于用量归属

假设同一张物理卡被 A、B 两个 Pod 共享，设备级活动率为 70%。若 exporter 或查询把这份指标各关联到一个 Pod，求和会得到 140%，但没有新增任何硬件工作。

先确定指标实体：物理 GPU、MIG 实例、进程还是业务请求。再确定映射的基数：一对一、一对多还是多对多。只有能归因的实体才能用于租户计量，不能为了让图表有 Pod 标签就复制总值并相加。

如果平台只能准确提供设备活动和租户显存，请分别展示它们并说明无法精确分解计算时间。按显存份额分摊功耗或活动率是一种成本模型，不是测量事实；必须单独标注假设。

## 5. MIG 与设备重建引入身份时间线

MIG 实例并非永久设备编号。实例重建、Pod 重建、节点替换后，同一个短名称可能指向不同对象。物理卡 UUID、实例身份、Pod UID 与有效时间应共同参与关联。

也不能把父 GPU 与子实例指标同时加总，除非指标定义明确说明它们可加且没有重复范围。某些字段不支持某种 entity，缺失值不能填零来营造低利用率。设备发现与身份变化的机制见 [MIG 原理](../../../gpu/cluster/sharing/09-MIG%20原理与%20Kubernetes%20配置.md)。

## 6. 采样、计数器与缺失值的边界

Gauge 是当前观测，Counter 是累计事件或数量，两者处理方式不同。累计 token 数应转换为窗口速率，进程重启造成的 Counter reset 需要被正确处理；对 GPU 活动率 Gauge 再求增长速率通常没有业务意义。指标设计原则见 [Prometheus Instrumentation](https://prometheus.io/docs/practices/instrumentation/)。

在 10 秒内，程序可能集中计算 1 秒，其余等待。粗粒度平均会把短突发摊平；不同采样窗口的业务延迟和设备活动，也不能凭曲线同时变化就认定因果。

应同时观测采集链路、样本时间和缺失率。Exporter 不可达时显示“无数据”，与 GPU 正常但空闲是完全不同的状态。分析窗口还要固定，避免把五分钟峰值与一小时平均放在一起推导。

## 7. 最终用有效产出约束优化

训练可用满足正确性条件的有效 step/s、完成目标所需时间；推理则同时看吞吐、排队、TTFT、每 token 延迟和错误率。实际指标名称与单位应核对引擎版本，例如 [vLLM Production Metrics](https://docs.vllm.ai/en/stable/usage/metrics/)。

教学例子：方案 A 每小时处理 100 万 token，但只有 90% 满足 SLO；方案 B 处理 95 万，98% 满足。若定义的有效产出是满足 SLO 的 token，则分别为 90 万和 93.1 万。即使 A 的 GPU 活动更高，也不能据此宣布它更好。真实 SLO 可能按请求而非 token 定义，必须使用相应业务分母。

## 8. 掌握检查

独立算出 6 GPU·h 的例子，并说明为什么会出现 66.7% 与 75% 两种结果；解释共享 Pod 求和为什么可能超过 100%；区分 MIG 缺失指标与零活动；最后为一个容量报告列出库存、可分配、已分配、活动和有效产出五个分母。
