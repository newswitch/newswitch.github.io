# AI 基础设施威胁模型、信任边界与攻击面

## 1. 从数据流而不是产品清单开始

```text
开发者/流水线
→ 镜像与模型仓库
→ Kubernetes/Slurm控制面
→ 训练或推理容器
→ GPU/NPU与RDMA
→ Dataset/Checkpoint/日志
→ 外部客户端
```

每跨越一次主体、Namespace、节点、网络或存储账户，都可能跨越信任边界。

## 2. 五个基本问题

1. 保护什么：模型、数据、算力、凭据、可用性；
2. 谁能访问：人、CI、Controller、Pod、节点、第三方；
3. 从哪里进入：API、镜像、模型文件、Notebook、SSH、BMC、RDMA；
4. 信任什么：证书、Digest、签名、ServiceAccount、设备身份；
5. 失败后果：泄漏、篡改、资源耗尽、横向移动、不可恢复。

## 3. 典型攻击面

| 面 | 示例 |
| --- | --- |
| 控制面 | 过宽 RBAC、泄漏 kubeconfig、恶意 Admission 配置 |
| 供应链 | 污染镜像、可变 Tag、恶意 Pickle/Remote Code |
| 运行时 | Privileged、HostPath、宿主 Socket、过量 Capability |
| 加速器 | 未隔离设备、错误 MIG/MPS 共享、设备插件越权 |
| 网络 | RDMA 绕过策略、无认证管理口、推理接口暴露 |
| 存储 | Dataset/Checkpoint 公共 Bucket、缓存残留、日志泄密 |
| 可用性 | 超长上下文、无限并发、Checkpoint Storm、GPU 独占 |

## 4. 安全属性

对每条数据流评估：

- 机密性：谁能读取内容；
- 完整性：谁能替换模型、代码或结果；
- 可用性：谁能消耗队列、显存、连接或存储；
- 可追溯性：能否把动作映射到稳定身份；
- 隔离性：一个租户失败是否影响其他租户。

## 5. 风险优先级

风险不能只按漏洞评分，还应结合可达性、权限、资产价值、检测能力和爆炸半径。一个内部 Notebook 的任意代码执行是预期能力，但如果它挂载全局模型仓库写权限，就成为高风险组合。

```text
风险 = 发生可能性 × 影响范围 × 暴露时间 ÷ 检测与恢复能力
```

公式用于统一讨论，不代表精确数学概率。

## 6. 技术控制映射

```text
身份 → OIDC/SPIFFE/ServiceAccount/短期凭据
准入 → Schema/Policy/Image Signature
运行时 → Non-root/seccomp/AppArmor/Device最小化
网络 → NetworkPolicy/RDMA隔离/mTLS
数据 → KMS/ACL/不可变版本/Checksum
可用性 → Queue/Quota/Token预算/超时
检测 → Audit/Runtime/GPU/Storage关联事件
```

任何单一控制都可能失败，应为高价值资产设计预防、检测和恢复三层。

## 7. 输出物

威胁模型至少包含架构图、资产清单、主体与权限、数据流、信任边界、威胁场景、当前控制、残余风险和验证方法。它应随新模型 Runtime、RDMA 网络或跨集群架构更新。

参考：[NIST AI Risk Management Framework](https://www.nist.gov/itl/ai-risk-management-framework)、[Kubernetes Threat Model](https://kubernetes.io/docs/concepts/security/kubernetes-api/)。
