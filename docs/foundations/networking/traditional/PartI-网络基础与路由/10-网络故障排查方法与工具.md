# 网络故障排查方法、证据链与工具箱

## 1. 排障的产物不是“一个命令”

高质量排障应交付：

```text
影响范围
时间线
期望路径与实际路径
被验证/证伪的假设
根因与促成因素
恢复动作与风险
长期改进与负责人
```

如果最终只留下“重启后恢复”，下一次仍会从零开始。

## 2. 先定义现象

将“网络不通”改写成可测量描述：

- 谁访问谁：源/目的 IP、端口、协议、租户、地域。
- 何时开始：首次失败和最近成功时间。
- 影响比例：全部、部分节点、部分五元组还是特定包长。
- 表现：超时、拒绝、重置、解析失败、慢、丢包或乱序。
- 最近变化：网络、主机、应用、证书、DNS、路由和安全策略。

一个精确样本比“很多用户反馈慢”更容易形成证据链。

## 3. 画出期望路径

至少画出：

```text
Client
→ DNS
→ Gateway/NAT
→ Load Balancer
→ Firewall
→ Server
→ 返回路径
```

对 Kubernetes 或云网络还要加入：

```text
Pod veth → CNI → Node → Overlay/Underlay → Service/LB → Backend
```

不知道预期经过哪些设备，就无法判断在哪一跳偏离。

## 4. 三平面 + 五张表

### 三个平面

- 管理平面：SSH/API/控制器是否可用。
- 控制平面：STP、OSPF、BGP、EVPN 邻居和路由是否正确。
- 数据平面：MAC、ARP、FIB、ACL、会话、隧道是否按预期转发。

管理面失联不代表数据面一定中断；控制面恢复也不代表 FIB 和业务已恢复。

### 五张基础表

```text
接口/链路状态
MAC/FDB
ARP/ND 邻居
RIB/FIB
Conntrack/会话与策略命中
```

每一跳都可以用这五类状态回答“包下一步去哪”。

## 5. 从边界开始二分

对长路径逐点抓包效率很低。先找两个边界：

1. 源端是否发出。
2. 目的端是否收到。

如果目的端收到请求：

- 问题在应用处理或返回方向。

如果目的端未收到：

- 在中间选择一个可观测边界继续二分。

这种方法比从第一台交换机逐跳检查更快。

## 6. Linux 工具箱

### 地址与路由

```bash
ip -br addr
ip -s link
ip route get <destination>
ip rule
ip route show table all
ip neigh
```

### Socket 与 TCP

```bash
ss -lntup
ss -nto state established
ss -ti dst <destination>
nstat -az
```

### 链路与网卡

```bash
ethtool <interface>
ethtool -S <interface>
ethtool -k <interface>
tc -s qdisc show dev <interface>
```

关注 CRC/FCS、丢弃、Pause、队列 Drop、Carrier、FEC 和驱动错误。字段名因网卡驱动
不同而异，必须结合厂商定义。

### 路径与质量

```bash
ping -c 20 <destination>
tracepath <destination>
traceroute -n <destination>
mtr -rwzc 100 <destination>
```

中间跳点对 ICMP 限速会显示“某一跳丢包”，但后续跳点正常时，不能断言该跳转发丢包。

### 抓包

```bash
tcpdump -ni any host <ip>
tcpdump -ni eth0 'tcp port 443'
tcpdump -ni eth0 -w incident.pcap 'host <ip>'
```

抓包前记录：

- 哪个接口、网络 namespace、方向。
- 时间同步状态。
- Offload 是否影响观察。
- 文件大小、滚动策略和敏感数据处理。

生产抓包必须限定过滤器和保留时间。

## 7. 常见现象的推理

### 7.1 Connection refused

通常说明某个节点主动返回 RST：

- 目标端口未监听。
- DNAT 指向错误后端。
- 防火墙配置为 Reject。

它与静默 Drop 导致的 Timeout 不同。

### 7.2 小包通、大包不通

优先检查：

- 端到端 MTU。
- VXLAN/IPsec/GRE 等封装开销。
- ICMP Fragmentation Needed/Packet Too Big 是否被过滤。
- MSS Clamping 是否正确。

### 7.3 部分流量失败

优先考虑：

- ECMP/LACP 某一成员故障。
- 多副本中某一后端异常。
- 哈希到某条错误路径。
- 源端口/NAT 映射耗尽。
- IPv4 正常但 IPv6 路径异常。

### 7.4 单向通信

检查：

- 返回路由。
- 非对称路径上的状态防火墙。
- ACL 应用方向。
- NAT 原始/回复映射。
- 反向路径过滤。

### 7.5 延迟周期性尖峰

关联：

- 队列深度与 Drop。
- 链路微突发。
- 路由/BFD 抖动。
- DNS 重试。
- TCP 重传与 RTO。
- 应用 GC、CPU 调度和存储延迟。

网络延迟必须与主机和应用指标对齐分析。

## 8. 假设表

| 假设 | 支持证据 | 反证 | 下一步 |
| --- | --- | --- | --- |
| DNS 返回旧地址 | 失败客户端解析到旧 IP | 权威记录已更新不能直接反证客户端缓存 | 对比本地/递归/权威结果与 TTL |
| 某 ECMP 路径丢包 | 仅部分五元组失败 | 单次 Ping 正常不能否定 | 多端口探测并关联接口计数 |
| 服务未监听 | SYN 后收到 RST | LB 健康正常不能证明该后端 | 在目标 namespace 查看 `ss` |

每一步应优先选择能最大程度区分多个假设的检查。

## 9. 安全恢复原则

1. 先限流、切流或隔离，避免影响扩大。
2. 重启前保存路由、邻居、会话、日志、计数器和抓包。
3. 一次只改变一个变量。
4. 设置停止条件与回滚时间。
5. 恢复后验证业务指标，不只验证设备 Up。

## 11. 第一阶段排障演练

至少主动制造并定位：

1. 错误 `/24` 与 `/25` 掩码。
2. VLAN/PVID 不一致。
3. LACP 一条成员单向丢包。
4. OSPF Area 或 MTU 不一致。
5. BGP 入站策略过滤正确前缀。
6. NAT 端口或 Conntrack 接近上限。
7. 隧道导致 PMTU 黑洞。

限制：每次演练只能在保存证据后修复，并写出为什么该证据足以排除其他层。
