# `base64` 命令详解：RFC 4648 编码、解码与数据安全边界

`base64` 把任意字节按 RFC 4648 Base64 Alphabet 转为可打印 ASCII，或还原为原字节。编码体积约为原始数据的 133%，不提供机密性、完整性、认证或压缩。

## 1. 命令档案

| 项目 | 内容 |
|---|---|
| 实现 | GNU coreutils |
| 文档基线 | GNU coreutils 9.11 |
| 安全级别 | 转换本身 `[R]`；输出会明文泄露原数据，解码写文件 `[W]` |
| 主要对象 | 原始字节、RFC 4648 Base64 字符、Padding 和换行 |

```bash
type -a base64
env base64 --version
env base64 --help
```

## 2. 完整语法与全部参数

```text
base64 [OPTION]... [FILE]
base64 --decode [OPTION]... [FILE]
```

| 短参数 | 长参数 | 作用 |
|---|---|---|
| `-d` | `--decode` | 解码为原始字节，默认是编码 |
| `-i` | `--ignore-garbage` | 解码时忽略不在 Alphabet 内的字节；换行本来就允许 |
| `-w COLS` | `--wrap=COLS` | 编码每 COLS 字符换行，默认 76；0 表示不换行 |
| 无 | `--help`、`--version` | 帮助与版本 |

GNU 只接受零或一个 FILE；无文件或 FILE 为 `-` 时读标准输入。`-w` 只影响编码，不恢复/改变解码后的原字节。

## 3. 编码模型与 Padding

每 3 字节（24 Bit）拆为 4 个 6 Bit 值，映射到 `A-Z a-z 0-9 + /`。输入末尾不足 3 字节时以 `=` Padding 补足四字符块：

```text
1 input byte  → 2 data chars + ==
2 input bytes → 3 data chars + =
3 input bytes → 4 data chars
```

```bash
printf 'f'   | base64 --wrap=0   # Zg==
printf 'fo'  | base64 --wrap=0   # Zm8=
printf 'foo' | base64 --wrap=0   # Zm9v
```

Shell `echo` 默认可能添加换行，它会成为被编码数据：

```bash
printf %s 'secret' | base64 --wrap=0
printf 'secret\n' | base64 --wrap=0
```

两者结果不同。

## 4. 行包装

GNU 默认 76 字符一行并在末尾输出换行：

```bash
base64 --wrap=76 -- binary.dat > binary.b64
base64 --wrap=0 -- binary.dat > binary.one-line.b64
```

PEM、MIME、Kubernetes YAML、JSON 和 API 字段对换行要求不同。不要随意 `tr -d '\n'` 处理未知 Base64 文本；应在编码时指定 `--wrap=0`。不同平台的 `base64` 参数不同，macOS/BSD 常见写法不能假设支持 GNU `-w`。

## 5. 严格与宽松解码

```bash
base64 --decode -- input.b64 > output.bin
base64 --decode --ignore-garbage -- noisy.txt > output.bin
```

默认解码允许换行，但遇到其他非 Alphabet 字节或错误长度/Padding 应失败。`--ignore-garbage` 会忽略未知字节，适合从已知包装文本中恢复，但也可能隐藏截断、注入、复制污染或协议错误。安全验证优先严格解码；只有输入格式明确允许装饰字符时才宽松解码，并记录被忽略内容。

必须检查退出码：某些实现可能在发现尾部错误前已经向输出写出一部分数据。先解到临时文件，成功并校验后再发布。

## 6. 二进制安全管道

```bash
umask 077
tmp=$(mktemp) || exit 1
if base64 --decode -- artifact.b64 >"$tmp"; then
  sha256sum "$tmp"
  file -E -- "$tmp"
else
  rm -f -- "$tmp"
  exit 1
fi
```

解码结果可包含 NUL、终端控制符、可执行文件、压缩炸弹或恶意文档。不要直接打印终端、Source 到 Shell 或自动执行；用 `od -A x -t x1z -N 256`、`file`、Hash 和格式专用验证器检查。

## 7. 编码不是安全措施

Base64 可被任何人无密钥还原：

- 不能替代 TLS/磁盘加密/Secret Manager；
- 不能证明内容未被篡改，需 Hash/MAC/数字签名；
- 不会隐藏 Token，终端历史、日志、YAML 和环境变量仍会泄露；
- 不压缩，反而增大约 4/3，编码前按协议决定是否压缩；
- 多次 Base64 仍不是加密。

Kubernetes Secret 的 `data` 字段只是 Base64 编码；访问控制、etcd Encryption at Rest、审计和外部密钥管理另行负责安全。

## 8. Base64 与 Base64url

标准 Base64 使用 `+/`；URL-Safe Base64 使用 `-_`，Padding 规则还可能由协议省略。GNU `base64` 不是 Base64url 转换器。JWT、URL 和 Web API 应使用理解该协议的库或 GNU `basenc --base64url`（先核对版本），不要只做字符替换而忽略 Padding 与 Canonical Encoding。

## 9. Round Trip 与完整性

```bash
base64 --wrap=0 -- source.bin > source.b64
base64 --decode -- source.b64 > restored.bin
cmp -- source.bin restored.bin
sha256sum source.bin restored.bin
```

Round Trip 证明本次转换可逆，不证明传输中真实性。跨系统交换时同时提供可信渠道的 Hash/Signature、编码 Variant、是否 Padding、字符集和换行约定。

## 10. 大文件与流式行为

Base64 可流式处理，不需把整个文件放进内存，但输出增加约 33%，会增加网络、磁盘和日志配额。管道下游失败时需 `pipefail`；大文件解码写满磁盘会留下部分输出。不要把大型 Artifact 嵌入环境变量、命令参数或 Kubernetes 对象，使用对象存储/Registry 并传引用与 Digest。

## 11. 常见生产用法

### 11.1 Kubernetes Secret 只读核对

```bash
kubectl get secret app-secret -n ai-prod \
  -o jsonpath='{.data.username}' \
  | base64 --decode
printf '\n'
```

这会把 Secret 明文写终端/审计附近环境，仅在批准终端执行，禁止录屏、Shell Trace 和工单粘贴。优先验证 Hash/长度而非显示内容。

### 11.2 JSON 单行字段

```bash
payload=$(base64 --wrap=0 -- artifact.bin) || exit 1
```

Shell 变量不适合 NUL 原数据，但 Base64 文本可存；仍受环境/参数长度、内存和泄密限制。大型数据不用这种方式。

### 11.3 证据传递

小型二进制可编码后通过纯文本通道，但同时记录源 Hash、编码命令、工具版本和解码验证，确认通道没有自动换行/截断。

## 12. 退出状态与排查

成功为 0，参数、读写或无效解码输入为非 0。

| 现象 | 检查方向 |
|---|---|
| 同一文本编码不同 | `echo` 增加换行、输入编码/BOM、换行包装 |
| JSON 中包含换行 | 编码未使用 `--wrap=0` |
| 解码 invalid input | Alphabet Variant、Padding、截断、非允许垃圾字符 |
| `-i` 后成功但 Hash 不符 | 宽松模式隐藏了污染/丢失，回到严格协议验证 |
| JWT 解不开 | 它使用 Base64url 且可能省略 Padding |
| 解码文件仍不正确 | Base64 只还原字节；检查上游压缩、加密、字符集和层级 |

## 13. 动手实验

1. 比较 `printf` 与 `echo` 的编码结果。
2. 为 1/2/3/4 字节输入观察 Padding。
3. 比较默认 Wrap、`-w 8` 和 `-w 0`。
4. 在编码中插入空格/标点，比较严格与 `-i` 解码和退出码。
5. 对随机二进制做 Round Trip、`cmp` 和 Hash。
6. 比较标准 Base64 与 JWT Base64url 字段，说明 Variant 差异。

- 能解释 3→4 转换、Padding、换行和体积膨胀。
